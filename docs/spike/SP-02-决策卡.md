## 2. 三件套逐项结论

### 2.1 ① 消息序列合法性 —— 成立【实测】

**E1（官方循环形态）续跑请求原文**（取证代理 `wire-02-request.json` / `wire-02-response.json`，全部原文见
`docs/spike/logs/sp02/wire/`）：

| 位置 | 内容 |
|---|---|
| 请求 messages[0] | `system`（160 字符，系统提示原文） |
| 请求 messages[1] | `user`（59 字符，"帮我算一下 6 乘 7…同时读取用户 u-1024 的前端资料…"） |
| 请求 messages[2] | `assistant`，`tool_calls = [call_00_KLREinZhv165NVFBgE519342 → calculate({"a":6,"operator":"multiply","b":7}), call_01_ImAnOuU5ZkmMyOFhK4vr4414 → get_user_profile({"userId":"u-1024"})]` |
| 请求 messages[3] | `tool`，`tool_call_id = call_00_KLREinZhv165NVFBgE519342`，content=27 字符（后端计算结果 `42`，**由崩溃前的实例执行**） |
| 请求 messages[4] | `tool`，`tool_call_id = call_01_ImAnOuU5ZkmMyOFhK4vr4414`，content=91 字符（**崩溃后由前端回灌进 Redis 的资料**） |
| 响应 | **HTTP 200**，`finish_reason = stop`，耗时 1136ms，正文为最终回答（含 `42` 与前端令牌） |

**跨场景的请求形状**（同一套重建逻辑，`messageJson` + `inFlightToolCalls` + `sp02:hitl` 三者拼装）：

| 场景 | 续跑请求 messages（role 序列） | 响应 |
|---|---|---|
| E1（`blocking`） | `system / user / assistant(tool_calls×2) / tool / tool` | 200 · stop |
| E2（`blocking`，敏感工具） | `system / user / assistant(delete_config) / tool` | 200 · stop |
| E3（`predicate`） | `system / user / assistant(calculate,get_user_profile) / tool / tool` | 200 · stop |
| E4（`explicit`） | `system / user / assistant(calculate,get_user_profile) / tool / tool` | 200 · stop |
| E6（`blocking`，续跑后再产生新工具调用） | `system / user / assistant(get_user_profile) / tool` → 模型回 `tool_calls=[calculate]` → 第二次请求 `assistant(calculate) / tool` | 200 · stop |

**证据口径**：本次全部实验通过取证代理发出的模型请求共 **12 次，全部 HTTP 200，0 次 400**（其中三件套相关的 5 个场景 11 次 + E5 未测场景 1 次）
（`docs/spike/logs/sp02/wire-status-counts.json` = `{"200": 12}`）。即：`assistant(tool_calls)` + `role:tool` 的**配对关系与
id 一致性**被模型 API 接受。

**边界（诚实披露）**：① 只覆盖 `deepseek-flash`、单 key、当日模型版本；② 未覆盖 `deepseek-v4-pro` 等推理模型
（其 `reasoning_content` 回填见 ADR-4，与本次续跑重建无关但会叠加风险）；③ 请求里 `assistant` 消息**不带
`reasoning_content`**（Spring AI 官方行为），本次零 400，与 SP-01ab §7.2 结论一致。

### 2.2 ② 不重放 —— 成立【实测】

「不重放」在本次拆成三个可独立证伪的口径，每个都有反例可构造：

| 口径 | 机制 | 实测证据 |
|---|---|---|
| **已执行过的后端工具不再执行** | 执行前查**跨进程台账**（`sp02:ledger:<runId>`，按 `toolCallId`） | E1-8b：`calculate` 在续跑中被标为 `executed-by-previous-instance(instance-…-pid29264…)`；E1-11：**新实例本地 `calculate` 计数 = 0**、台账 `calculate` 恰好 1 条 |
| **前端工具/确认门的"请求"不再重发** | 请求事件只在**挂起路径**发出；续跑路径只读状态、不发请求 | E1-5 / E3-7：`frontend_tool_request` 事件计数 = **1**（跨重启全程）；E1-12 / E3-7 / E6-6：前端工具哨兵桩体执行计数 = **0** |
| **不重放第 1 轮的模型请求** | 续跑只发"续接请求"（请求体含 `assistant(tool_calls)`+`tool`），**不是**原始 prompt | E1-9：重启后仅 1 个 `wire-*-request`（`wire-02`，其 messages 与 `wire-01` 明显不同）；E3-6、E6-5 同 |
| **续跑幂等** | `DONE` 直接返回、不发模型请求 | E1-14：再次 `POST /api/resume` → `{resumed:false, reason:"ALREADY_DONE"}` 且 wire 文件数不变 |
| **准入校验（未落定即拒绝）** | 任一 `sp02:hitl` 条目仍 `PENDING` → 409 | E1-6：`409 PENDING_UNRESOLVED`、`wireDelta=0`；E5 留档运行：前端项已落定但 `delete_config` 仍 `PENDING` → 409 且 `unresolved` 只列该敏感项 |

> **「不重复产出已向用户发送的内容」的口径说明**：官方循环在工具轮次**不向下游产生任何内容事件**
> （SP-01d §1.2d 已实测；本次 `blocking` 形态的 E1/E6 亦复现：挂起前的 `delta` 事件数 = 0），因此"已发送正文"
> 在本形态下为空集；实际可观测的重复风险集中在**工具副作用**与**模型请求重放**上，两者均已上述证伪。
> 唯一会重复产出的写法（把整条历史重新发给模型重跑一遍）本次未采用，其等价反例见 SP-01d `vd1-refmodel-mid`（"我是我是"）。

### 2.3 ③ 流式续接 —— 成立【实测】

| 场景 | 续跑流的观测 | 终态 |
|---|---|---|
| E1 | `reattached` → `frontend_result_stored` → `tool_result`/`frontend_tool_result` → **117 个 `delta`** → `model_round` → `resume_done` → `run_finished` | `done`（`status=DONE`），回答含 `42` 与前端令牌 |
| E2 | `confirm_resolution` → `tool_result` → **66 个 `delta`** → … → `run_finished` | `DONE`，回答"已执行删除" |
| E3 / E4 / E6 | 续跑流 **113 / 143 / 65 个 `delta`** + `resume_done` + `run_finished` | 均 `DONE` |

（计数口径 = 续跑侧 SSE 原文里 `event:delta` 行数，逐场景归档文件可复核）

续跑流是**真实的 SSE 流**（`SseEmitter`，逐帧原文含毫秒级到达时间戳，见
`docs/spike/logs/sp02/E1-instance2-sse-raw.txt` 等）。**关键前提**：续跑请求本身是流式请求
（`ChatModel.stream` + `stream=true`），因此"续跑能否流式"实际等于"重建请求能否走官方流式路径"——实测可以。

> 附：本次续跑的对外可见正文**不含任何"重复的前缀"**（每个场景的最终回答均为一次性回答，见
> `*-final-answer.txt`）；一个续跑流里出现的正文**全部是新内容**（旧实例在挂起前未向客户端产出任何正文，见 §2.2 说明）。
> 令牌是否被模型复述因场景而异（E1 2 次、E3 2 次、E4 3 次、E2/E6 各 0 次）——**不重放的口径不依赖模型复述**
> （与 SP-01ab §7.4 的教训一致），一律以台账、请求计数与本地计数器为准。

## 3. 补充验证①：确认门「已放行未执行」的决策在重启后被发现并继续执行 —— 成立【实测】

GLM-R 反例场景（挂起期进程死亡 → 已放行的人工决策无声丢失）的 SP-02 版本：**决策已写入 Redis，但工具尚未执行**。

**故障注入**：`spike.exec-delay-ms-after-approve=8000`——确认门放行后、委托官方执行工具前插入 8s 窗口
（生产等价物 = "决策落库后、执行前进程死亡"）。脚本在 `POST /api/confirm` 返回后立即 `kill -9`。

E2 逐帧证据：

| 步骤 | 实测原文 |
|---|---|
| 1. 确认门挂起并外置 | `sp02:hitl:<runId>` 出现 `delete_config` 条目（`status=PENDING`），进程内还有一个只用于唤醒的 `Gate` |
| 2. 人工放行 | `POST /api/confirm {approved:true}` → `{accepted:true, status:"APPROVED", wokeInProcessGate:true}`；Redis 原文 `…"status":"APPROVED","executed":false,"executedBy":null,"executedAtMs":0…` → **决策已落库、尚未执行** |
| 3. 旧实例被 `kill -9` | 直接读 Redis：`LLEN sp02:ledger:<runId>` = **0**（工具确实没被执行，8s 窗口内被杀死） |
| 4. 新进程发现 | `GET /api/runs` 列出该轮 `status=SUSPENDED`；`pending[0] = {status:"APPROVED", executed:false, reason:"允许删除（PoC）"}` |
| 5. 续跑 | `POST /api/resume` → `202 {resumed:true, rebuiltTools:["call_00_…:APPROVED:executed-here"]}`，`promptMessages` = `system/user/assistant(delete_config)/tool(responseData="后端已执行删除：配置 def-777 及其 3 行生效数据已删除。")` |
| 6. 执行归属 | 台账唯一一条：`{name:"delete_config", executedBy:"instance-Lenovo-pid28140-d83206"}` = **新实例**（`/api/dev/info` 的 `instanceId` 与之相同）；**新实例本地 `delete_config` 计数 = 1，旧实例 = 0** |
| 7. 收尾 | 续跑流 **66 个 `delta`** + 终帧；回答："配置定义 def-777 已删除，同时连带删除了 3 行生效数据" |

**结论**：`APPROVED 且 executed=false` 这一状态是**可持久、可发现、可恢复执行**的：新进程凭 Redis 就能把
"人已经批准但机器还没做"的操作补做，且**恰好一次**（台账 + 双实例计数器互证）。
→ ADR-2 / Q10 的"挂起期进程死亡丢决策"在**有外置**的前提下不再成立；但**决策落库与执行之间的原子性仍未解决**
（见 §6 风险：若新进程在补执行途中死亡，仍是"未执行"，不会重复执行——本次的 `executed` 标记是在执行返回后写的，
即最坏情况是**重复执行**而非丢执行，S4 需要为写操作加幂等键）。

## 4. 补充验证②：`eligibility-predicate` 返回 false 对续跑路径的影响 —— 成立【实测+实测-字节码】

### 4.1 官方实现事实（字节码核对，Spring AI 1.1.8）

```java
// org.springframework.ai.model.tool.DefaultToolExecutionEligibilityPredicate（javap -c）
public boolean test(ChatOptions options, ChatResponse response) {
    return ToolCallingChatOptions.isInternalToolExecutionEnabled(options)   // internal 开关
        && response != null && response.hasToolCalls();
}
```

```java
// org.springframework.ai.openai.OpenAiChatModel（javap -c）
// 流式路径：predicate 为假 → 官方循环不执行工具，把响应原样交回调用方
private Publisher lambda$internalStream$9(Prompt p, ChatResponse r) {
    if (toolExecutionEligibilityPredicate.isToolExecutionRequired(p.getOptions(), r)) {
        return Flux.deferContextual(...).subscribeOn(Schedulers.boundedElastic());  // 执行工具 → 递归续跑
    }
    return Flux.just(r);                                                            // ← 交回调用方
}
// 工具执行后的续跑请求：只带 tool-execution 历史（详见 §7.1）
new Prompt(toolExecutionResult.conversationHistory(), prompt.getOptions())
```

即：**predicate 与 `internalToolExecutionEnabled` 是同一个判定点**（前者是后者的动态版本），
返回 false 的语义 = "本轮工具交给调用方，续跑权收回业务侧"。

### 4.2 实测

| 观测 | 结果 |
|---|---|
| predicate 对「含外部工具的本轮」返回 false → 调用方拿到 `assistant(tool_calls)` | **E3-1 PASS**：调用方在一次 `model_round` 里看到 `tool_calls=[calculate, get_user_profile]`；随后 `run_suspended`（进程未阻塞） |
| 粒度：**一整轮**全有或全无 | **E3-2 PASS**：同一轮的**后端**工具 `calculate` 也没有被官方执行，由调用方执行（`tool_result` 事件 `path=predicate`；台账 `calculate` 一条，`executedBy=旧实例`） |
| `internalToolExecutionEnabled=false` 是否等价 | **E4-1 PASS**：同一场景、同一重建逻辑 → 同样交回（`form=EXPLICIT`） |
| predicate 形态下**续跑**能否走通 | **E3-5/6/7/8 PASS**：`202 resumed`，重建请求含 `assistant(tool_calls)+tool`，1 次模型请求，回答含 `42`+令牌 |
| 官方循环形态（internal 执行**开启**）下**续跑**能否走通 | **E1/E2/E6 PASS**：`form=BLOCKING`，续跑请求同样合法；E6 更证明**续跑后模型新发起的工具调用仍由官方循环在新进程内执行**（台账 `calculate` `executedBy=新实例`，参数 `{a:880,operator:multiply,b:2}` 取自前端回灌的积分 → 结果 1760） |

### 4.3 对"是否必须配合 `internalToolExecutionEnabled=false`"的回答

**不必须。** 分三层说清楚：

1. **`/api/resume` 的续跑请求本身不依赖该开关**：它只是一个"带完整历史的普通官方请求"；`internalToolExecutionEnabled`
   与 predicate 都**不进 HTTP 报文**（E1 与 E3/E4 的 wire 请求形状除 messages 内容外无差别）。
2. **该开关决定的是"续跑之后新产生的工具调用由谁执行"**：
   - 关闭（或 predicate=false）→ 官方循环把 `assistant(tool_calls)` 交回调用方，**调用方必须自己驱动后续轮次**
     （E3/E4 实测；代价：一轮里连后端工具也要自己执行，见 4.2 第 2 行）；
   - 开启（默认）+ 自定义 `ToolCallingManager` → 官方循环继续驱动，工具调用仍经过我们的扩展点
     （**E6 实测**：新工具调用在新进程内被官方循环执行；**E1 实测**：挂起前的两类挂起都在该扩展点内成立）。
3. **对 ADR-2 的落地含义**：生产形态（ToolCallingManager 阻塞挂起 + 挂起态外置）**无需**改成
   `internalToolExecutionEnabled=false` 的显式循环即可续跑，因此 **ADR-2 的"预登记回退"不必启用**；
   反过来，若将来为"请求边界暂停/不占线程"等理由选择调用方驱动形态，predicate 与 flag 两种写法等价
   （E3 vs E4 实测），可以任选，但此时**必须**打开其中一个开关——否则官方循环会把前端工具按普通
   `@Tool` 直接执行（哨兵桩体将被执行）并把敏感工具**绕开确认门**执行（【推断】：由 SP-01ab §4
   "唯一扩展点"实测 + 官方循环只经 `ToolCallingManager` 执行工具推出，本次未运行"默认管理器 + 外部工具"的对照实验）。

## 5. 续跑协议（本次实测通过的形态，可直接作为 S4 实现依据）

1. **挂起时先外置、再阻塞**：进入工具执行扩展点后，先把 `assistant(tool_calls)` 与每个待办条目写入 Redis
   （`suspend_persisted` 事件里带 Redis 键与写入者实例标识），**然后**才等待外部输入；进程内的 `Gate` 只承担
   "唤醒"职责，不承载状态（E1-7：新进程里 `wokeInProcessGate=false`，回灌仍生效）。
2. **外部输入只写 Redis**：`POST /api/frontend-tool-result` / `POST /api/confirm` 先写状态、再唤醒同进程的门；
   重复提交按状态幂等拒绝（`duplicate=true`）。
3. **重启后发现**：`GET /api/runs`（索引 `sp02:runs`）+ 单轮快照；前端可用 SSE `reattached` 事件重新挂接并渲染
   挂起态展示（本次实现了该事件，证据见各 `*-sse-raw.txt` 首帧）。
4. **准入校验**：状态非 `SUSPENDED` → `ALREADY_DONE`/`ALREADY_RUNNING`；任一待办仍 `PENDING` → `409 PENDING_UNRESOLVED`
   （**不改动任何状态、不发模型请求**）。
5. **重建请求**：`history = messageJson` + `assistant(content=assistantContent, toolCalls=inFlightToolCalls)`
   + `ToolResponseMessage(responses = 按 inFlightToolCalls 顺序，取自 sp02:hitl 的 resultText)`；
   已执行过的条目从台账复用结果文本，未执行的（如 APPEND 的敏感工具）在续跑时补执行并记台账。
6. **落定后立刻回写**：重建出的 assistant/tool 消息追加进 `messageJson`、清空 in-flight，**再**发起模型请求——
   保证"续跑途中再次崩溃"不会重复重建（E1-14 证明重复调用幂等）。
7. **TTL**：全套键带 TTL（本次 6h，`spike.run-ttl-hours`）；S4 需按业务确认（ADR-2 待裁决项）。

## 6. 卡点与未测项（诚实披露）

### 6.1 E5：「续跑后新一轮又发起**外部工具**调用 → 是否在新进程内再次挂起」= **未测**

E5 共 4 次尝试均未构造成目标轮次结构（前 3 次失败即停；第 4 次仅为"把该场景的原始证据留档"而重跑）：

| 尝试 | 现象 | 归因 |
|---|---|---|
| 1 | 脚本等待 `model_round` 超时 | **脚本口径错**：`blocking` 形态下 `callRound` 在官方循环内阻塞，`model_round` 事件要等人工决策后才发出（见 §7.2） |
| 2 | 续跑后模型**拒绝**调用 `delete_config` | **模型行为**：模型判定"前端缓存数据不可信/破坏性操作"，第二轮只作答不改数据（该次原文未随最终归档保留） |
| 3 / 4（留档） | 第 1 轮模型把两步**合并**成一次（同轮含 `get_user_profile` + `delete_config`） | **模型行为**：不符合"先挂起前端工具、续跑后再挂起敏感工具"的预期结构；模型反正不按脚本假设的轮次走 |
| 3 / 4 的**副产品（有价值）** | 前端项已落定、敏感项仍 `PENDING` 时续跑被拒 | `E5-resume-request.json`：`409 PENDING_UNRESOLVED`，`unresolved` 只列未落定的 `delete_config`；`E5-suspend-1.json` 给出**同轮混合挂起**（前端 + 敏感）的外置条目原文 |

> 留档的第 4 次证据：`E5-checks.json`（0/3）、`E5-suspend-1.json`、`E5-resume-request.json`、
> `E5-app-instance{1,2}.log`、`E5-instance{1,2}-sse-raw.txt`、`E5-wire-index.json`（本次 E5 只发出 1 次模型请求，
> 续跑被拒故无第二个请求；其请求即 `wire/wire-12-*`）。

**现有旁证（不足以替代实测）**：E6 已证明续跑后的新工具调用落在**新进程**内、由官方循环经**同一个自定义
`ToolCallingManager`** 执行（台账 `executedBy=新实例`）；E1 已证明该管理器对挂起项的阻塞/外置逻辑成立。
因此"续跑后再挂起"在机制上【推断】成立，但**缺一次端到端实测**。
→ 建议在 S4 补用例（编号建议 `TC-AI-03b`：跨重启的多轮外部工具调用），并注意其模型行为依赖需要用
   "把待办参数写进用户消息"之类的确定性构造来稳定。

### 6.2 其他边界（未测/已知限制）

1. **多实例（非重启）续跑未测**：本次是"同一台机器上的新进程"，未起两个实例同时连着同一 Redis。键结构天然支持，
   但**没有互斥**（两个实例同时对同一 runId 调 `/api/resume` 会并发发两次模型请求）→ S4 需要 runId 级锁（与 ADR-5 同族）。
2. **Redis 侧的单点/丢数据风险未变**：本卡只证明"进程死不掉挂起态"，**Redis 自身的重启/淘汰**仍会导致挂起态全灭
   （Challenger P6 的攻击路径在本卡范围之外；DC-11 的 HA 形态仍是前提）。
3. **未做并发/压测**：单轮单会话。挂起线程的承载本次用**有界平台线程池**
   （`ThreadPoolExecutor(0, spike.suspend-pool-size=16, SynchronousQueue, AbortPolicy)`，超限 `503 SUSPEND_POOL_SATURATED`
   快速失败）——与 **DC-12（禁用虚拟线程）** 一致，但**未做容量/并发上限验证**（CH-P8 的取值仍待 S4.2 压测）。
   另注：承载形态只影响"谁来阻塞"，与本卡的续跑协议无关（挂起态在 Redis，不在承载线程里）。
4. **未覆盖非流式续跑**：本次续跑一律走 `stream`（任务书要求流式续接）；非流式重建请求的形状结论
   （`assistant+tool` 合法）由同一 codec/prompt 路径**推断**成立。
5. **重建请求里的 tool 结果文本形状**：委托官方执行的后端工具结果被 JSON 序列化（多一层引号，
   `"\"后端计算器结果：6 multiply 7 = 42\""`），与 SP-01ab §7.1 一致；前端回灌文本为原文透传。S4 建议统一。

## 7. 次要实测发现（与 ADR-1/ADR-2/ADR-6 相关，建议一并记录）

1. **【实测+字节码】官方循环自己的"工具后续跑请求"只带工具执行历史，丢掉 `system` 与 `user`**：
   字节码 `new Prompt(toolExecutionResult.conversationHistory(), prompt.getOptions())`；报文证据 `wire-11`：
   第二次请求 messages 仅 2 条 = `assistant(tool_calls=[calculate])` + `tool(结果)`。
   含义：官方循环在多轮工具调用时，模型**看不到系统提示与用户原话**。SP-02 的续跑路径反而更完整
   （`wire-02` 带 `system/user/assistant/tool` 全量）。→ 若产品的系统提示承载强约束（如安全规则），
   需要在 S4 明确处理（每轮补挂 system，或按 ADR-2 的调用方驱动形态自建循环）。
2. **【实测】`blocking` 形态下调用方的流拿不到"被官方循环消费掉的工具调用"**：E6 的 `model_round.toolCalls`
   为空，而挂起信息只能从**外置状态/管理器事件**获得（SP-01d §1.2d 的独立复现）→ 这是"挂起态必须外置"的又一条理由。
3. **【实测】`blocking` 形态下一"轮"在调用方视角直到人工决策后才结束**：`callRound` 阻塞在官方循环内部
   （首次 E5 尝试因此超时）→ 前端展示挂起态不能依赖"调用方回调"，只能依赖 SSE 事件与外置状态。
4. **【实测】事件留档窗口是个真问题**：本次首版把 `sp02:events:<runId>` 裁到 400 条，长回答（>400 个 delta）
   会把**挂起期事件挤出历史**，导致事后无法取证（E6 一次运行因此出现"事件缺失"假象）。已改为 3000 条并重跑全部场景。
   → 生产必须把"关键状态变更事件"与"流式 delta"**分表/分级**存储。
5. **【实测】故障注入旋钮的必要性**：`exec-delay-ms-after-approve` 是把"已放行未执行"窗口稳定复现出来的唯一手段
   （否则放行与执行在同一毫秒级窗口内完成，无法注入崩溃）。S4 的等价回归用例需要类似的可注入点。

## 8. 对 ADR-2 的回填建议（供 S3 定稿直接采用）

1. **证据等级**：ADR-2 的处置方向（挂起态 Redis 外置 + 续跑协议）由【推断】升级为
   **【实测】**（SP-02：E1 16/16、E2 8/8、E3 9/9、E4 5/5、E6 8/8，共 46/46；三件套相关的 11 次模型请求零 400，全部实验 12 次零 400）。
2. **CH-P1 条件 1 的关闭**：三件套（消息序列合法性 / 不重放 / 流式续接）**逐项成立**，可关闭该致命项。
3. **推翻条件修订**：原"方案 B 实测不成立时启用预登记回退"——**未触发**；建议改写为：
   "① 若 S4 实测出'续跑后再挂起'不成立（SP-02 §6.1 未测项）则回退；② 若 Spring AI 提供一等 suspend/resume
   则重审。"并将 `internalToolExecutionEnabled=false` 从"回退选项"降级为"可选形态"（与 predicate 等价，§4.3）。
4. **新增两条硬规范**：
   - **外置先于阻塞**：进入挂起前必须先写 Redis（含 `assistant(tool_calls)`），进程内的等待对象不得承载状态；
   - **续跑必须重建完整历史**：不能复用官方循环的"仅工具历史"续跑请求（§7.1），否则会丢掉 system/user 上下文。
5. **新增待办（S4）**：runId 级续跑互斥锁；`executed` 标记与工具副作用之间的幂等键；事件分级存储；
   跨重启多轮外部工具调用用例（§6.1）。

## 10. 推翻条件

1. 出现"续跑后再挂起"（跨重启的多轮外部工具调用）实测失败 → §4.3 与 §5 的协议需要重做（§6.1 的未测项是唯一已知缺口）。
2. Spring AI 升版后 `ToolExecutionEligibilityPredicate`/`internalStream` 语义变化（例如官方自带 suspend/resume 或续跑请求开始携带完整历史）
   → §4.1 的字节码结论与 §7.1 的发现都要重测。
3. 生产 Redis 不满足 TTL/容量/HA 前提（Challenger P6）→ 本卡"进程死不掉挂起态"的结论只在 Redis 活着时成立。
4. 采用多实例部署且未加 runId 级续跑互斥 → 本卡的幂等结论（单实例口径）不再成立。
5. 换成推理类模型（如 `deepseek-v4-pro`）或非官方 OpenAI 兼容实现 → 消息序列合法性需重测（本卡只覆盖 `deepseek-flash`）。
