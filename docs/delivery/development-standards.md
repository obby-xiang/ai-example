# 统一开发规范与提交审查门禁

> 适用范围：本仓全部生产代码、测试与压测代码、脚本、CI 配置和文档。开发与审查人员在施工前必须阅读；提交前必须对当前暂存区逐 hunk 审查并留下有效记录。
> 记录文件：`docs/delivery/development-standards-review.json`。D6 迁移指南及其 `d6-review.json` 仅作历史参考，正文和已有记录保留；不再作为提交门禁，不要求更新 D6 或新增 D6 审查记录。
> 证据口径：本规范中的“已审查”只表示人工逐 hunk 检查，不表示测试、真实接口或真实 Redis 已验证。

## 1. 基本原则与规格变更

1. 先复用项目已有能力，再新增实现；先保持协议与行为兼容，再做优化。不得为了形式统一而重写已经正确且不在本批范围内的代码。
2. 任何新增或升级依赖都必须得到用户明确授权；锁文件中出现不等于获得新依赖授权。
3. 需求、协议、状态语义、用户文案、配置键、数值门槛或本规范发生变化时，必须在当次审查记录的 `specChanges` 中写明变化、原因和影响面；无变化使用空数组。
4. 历史规格、研究稿和证据稿不被静默改写为“当前事实”。需要修正现行口径时，应同步对应规格或决策文档，并在记录中指向该变化。
5. Java 方法行数、Java 方法复杂度、模型并发上限和审查记录是本批变更的硬门槛。发现既有越界 Java 方法时，本批触及的方法应一并收敛；无法收敛必须在理由中写明具体阻塞和后续去向，不得把旧代码存在当作新代码越界的理由。前端不设置单函数 50 行或圈复杂度 20 门槛。

## 2. 依赖与复用顺序（`dependency-reuse`）

### 2.1 后端

按以下优先级选择实现：

1. **Apache Commons**：优先使用项目已有的 Commons Lang、Commons Collections、Commons IO 等成熟 API。
2. **Guava**：Commons 没有合适能力时使用项目已有 Guava API。
3. **Spring**：前两者不适合时，使用 Spring 的集合、字符串、资源、并发和 Web 能力。
4. **手搓**：只有上述能力确实不满足时才自行实现，并在审查理由中说明已核对的库能力和缺口。

不得复制库源码、另写同名工具类或引入第二套并行工具库来绕过该顺序。

### 2.2 前端

- 样式优先使用 **Tailwind CSS** 与项目现有组件；数据处理优先使用项目已有 **lodash**，然后才考虑手写工具函数或 CSS。
- 不得用重复的工具函数、手写深拷贝、手写防抖/分组/排序等替代已有 lodash 能力；不得在手写样式与 Tailwind 之间无依据地来回切换。
- Mermaid、Markdown、表格引擎等专用渲染继续复用现有组件，不因卡片治理另造渲染器。

### 2.3 禁止自写脚本分析或修改源代码

- 禁止编写 Python、Shell、PowerShell、JavaScript 等脚本或内联命令，对源代码进行方法识别、行数统计、圈复杂度计算、语法结构分析、批量替换或自动重构；不得通过正则、字符串切片、括号匹配等方式另造代码解析器。
- 静态分析必须使用经批准的成熟组件及其规则能力。当前 Java 使用 Checkstyle 与 PMD；组件能力不满足项目口径时，应先审查并扩展其 AST 规则，不得退回自写脚本。
- 源代码修改必须通过可逐文件、逐 hunk 审查的正常编辑流程完成。确需自动化重构时，只能使用经审查的成熟 AST 重构工具，不得使用自写脚本直接写入源文件。
- 既有 CI、构建和压测脚本不得承担上述源代码分析或修改职责；发现此类脚本不得以其结果作为开发验收或审查证据。

### 2.4 废弃代码直接删除

- 已确认废弃的方法、类、字段、配置、分支或其他代码必须直接删除，并同步清理调用方和无效引用，不得继续保留死代码。
- 禁止为废弃代码添加 `@Deprecated`、废弃注释、保留说明或兼容委托，也不得就如何保留废弃代码进行调研。
- 不得以兼容、历史参考或后续可能使用为由保留废弃入口；确需保留的现行公开契约不属于废弃代码，必须具有实际消费者和明确职责。

## 3. Java 与通用代码形态（`java-api-style`）

### 3.1 集合、Map 与数组返回

- 返回集合、Map 或数组的方法不得返回 `null`；无结果返回空集合、空 Map 或空数组。
- 共享空实现只可用于不可变对象，例如 `List.of()`、`Set.of()`、`Map.of()` 或 `Collections.empty*()`。禁止共享可被调用方修改的空数组或空集合。
- 返回空数组时新建数组，或返回私有共享数组的副本。返回内部数组、集合或 Map 前必须明确可变性契约：需要隔离时 defensive copy；需要只读时返回不可变视图或不可变副本。
- 调用方不得假定返回值可修改。确需可修改返回值时，方法契约必须明确，且不得泄漏可破坏内部状态的共享实例。
- `List.of`、`Set.of`、`Map.of`、`Map.ofEntries` 和 `Map.entry` 创建的是不可变对象：禁止元素、key 或 value 为 `null`，否则抛出 `NullPointerException`；`Set.of` 的重复元素、`Map.of/ofEntries` 的重复 key 会抛出 `IllegalArgumentException`。调用 `add`、`put`、`remove`、`set`、`clear`、迭代器删除等修改操作会抛出 `UnsupportedOperationException`。`Set/Map` 的遍历顺序不得依赖，`List` 虽保持元素顺序但仍不可修改。
- `List.copyOf`、`Set.copyOf`、`Map.copyOf` 返回不可变副本，同样禁止 `null` 元素/key/value；`Set.copyOf` 可从含重复元素的集合中保留任意一个重复项，不得把它当成重复检测器。`Collections.empty*` 是共享不可变空实现，`Collections.unmodifiable*` 是原对象的只读视图而非独立副本，底层对象变化仍可能反映到视图中。
- 不同集合的 `null` 和修改语义不得混淆：`HashMap`/`LinkedHashMap` 允许一个 `null` key 和多个 `null` value；`ConcurrentHashMap`、`Hashtable` 禁止 `null` key/value；`TreeMap` 在自然排序下不接受 `null` key，自定义比较器是否支持必须单独确认；`Arrays.asList` 是定长视图，允许 `null` 和 `set`，但不支持 `add/remove`，且与原数组共享数据。
- 不是自己创建的集合、字典、数组、实体或包装对象，不得默认可修改，也不得在无法确认副作用时直接修改。方法参数、库返回值、JPA/Jackson/Redis 投影、共享缓存和框架对象均按只读处理，除非其契约明确允许修改且不会破坏其他消费者。
- 确需修改外部来源数据时，先核对 `null`、元素类型、重复键值和所有权，再创建自己拥有的可变副本，例如 `new ArrayList<>(source)` 或 `new LinkedHashMap<>(source)`；不得通过修改入参、共享实例或只读视图绕过限制，跨线程共享时还必须使用明确的并发与所有权策略。

### 3.2 方法规模与复杂度

本小节仅适用于 Java；前端不设置单函数行数或圈复杂度门槛。

- 单个方法最多 **50 行**：计入方法头、注解和声明，不计注释与空行。超过时按单一职责拆分，不得通过压缩多条语句到一行规避。
- 方法内圈复杂度最多 **20**。审查按方法内决策点计算，循环、条件、分支、`case`、捕获和布尔短路的组合都应计入；嵌套回调、 lambda 和局部类不得用来把复杂度藏到另一层。
- 拆分后保持真实状态与异常语义，不得为了凑行数增加无消费者的抽象层。

### 3.3 命名、集合访问与 import

- 布尔方法使用 `is`、`has`、`can`、`should`、`get`、`contains`、`lock` 之一作为前缀。使用 `get` 或 `lock` 时必须确认语义确为布尔读取或锁状态获取，不得为了迎合名单制造误导名称。
- 布尔 getter 改名或新增时，必须检查 JavaBean、Jackson、JSON 字段、Map 序列化、前端类型及持久化投影，避免 `isX`/`getX` 被序列化成不同字段或重复字段。
- JDK 21 顺序集合首尾元素使用 `getFirst()` / `getLast()`，不再写 `get(0)` / `get(size() - 1)`；调用前仍须处理空集合。
- 禁止通配 import，禁止 static import。完全限定名应通过单一明确 import 和可读命名简化；只有类型冲突无法消除时才保留必要的完全限定名。

### 3.4 JSON、类型转换与 Lombok

- 涉及 JSON 序列化或反序列化的实体，其 JSON 字段名称必须通过 `@JsonProperty` 显式声明并保持稳定；字段、record 组件、构造器参数及属性访问器均不得依赖 Java 字段名或方法名隐式推导。重命名字段、方法或类时不得改变既有 `@JsonProperty` 值，并同步检查重复属性和派生 getter。
- 能够使用项目已有 Lombok 等价实现时，不得手写重复的 getter、setter、构造器、`toString` 或 builder。替换前必须核对访问级别、惰性初始化、继承、Jackson/JPA 和 `toString` 语义。
- 禁止使用 Lombok 自动生成 `equals` / `hashCode`：不得使用 `@EqualsAndHashCode`，也不得使用 `@Data`、`@Value` 等会隐式生成这两个方法的组合注解。业务确实涉及相等性判断时，必须手动覆写 `equals` 和 `hashCode` 并保持二者契约一致；不涉及相等性判断时不得覆写，也不得通过 Lombok 或 IDE 模板额外生成。
- JSON 序列化和 `toString`（包括 Lombok、record 或其他框架自动生成）不得泄露明文密钥、密码、令牌、私钥、证书、连接串、会话凭据、个人信息或其他敏感信息。敏感字段必须从 JSON 输出中排除，可使用 `@JsonIgnore`；`toString` 默认按白名单输出安全字段，Lombok 使用 `@ToString(onlyExplicitlyIncluded = true)` 配合 `@ToString.Include`，或使用 `@ToString.Exclude` 排除敏感字段。record 自动 `toString` 会包含全部组件，存在敏感组件时必须手动提供安全的 `toString`。
- 不得仅依赖字段命名、全局 Jackson 配置或“不会记录日志”的假设防止泄露；新增或修改实体时必须检查序列化、继承、派生属性和 `toString` 的实际输出面。确需持久化敏感配置时必须经过既有加密边界，不得把明文序列化结果用于 API、日志、异常或排障输出。
- JSON 实体中的 `long` / `Long` 必须使用显式 Jackson 注解将 JSON 表示固定为字符串。可使用 `@JsonFormat(shape = JsonFormat.Shape.STRING)`，或使用 `@JsonSerialize(using = ToStringSerializer.class)` 配合明确的字符串到 `long` / `Long` 反序列化器；序列化时 `long` 转字符串，反序列化时字符串恢复为 `long` / `Long`。不得为了接收 JSON 值而把 Java 字段、record 组件或方法参数改成 `String` 等其他类型。
- 对可能存在跨语言精度丢失或格式歧义的其他数值、日期时间、枚举、二进制及自定义值类型，也必须显式评估并固定 JSON 格式和转换器，不得只处理 `long` 而忽略同类风险；新增或修改转换器时须同时覆盖序列化和反序列化方向及 `null`、非法值和边界值语义。

### 3.5 可空值、包装类型与 Boolean

- 对可能为 `null` 的参数、返回值、字段、集合元素、Map 值、反序列化结果和外部调用结果，必须在使用前进行判空或采用具有明确空值语义的安全 API，避免空指针异常；不得仅凭调用惯例、字段名称或历史数据推断非空。
- 已确认非空的参数、返回值、字段和 record 组件应使用项目现有 Lombok `@NonNull` 或项目统一的 `@NonNull` 体系显式标记，不得为此新增另一套注解依赖。注解不能替代外部输入、持久化数据和反序列化边界的实际校验。
- 基本类型与包装类型之间发生拆箱、比较、算术、条件判断或方法引用时，必须先处理包装类型为 `null` 的场景；包装对象比较不得误用引用相等代替值相等。
- `Boolean` 不得直接用于 `if`、三元表达式或其他布尔条件。优先使用 Apache Commons Lang 的 `BooleanUtils.isTrue`、`isFalse`、`isNotTrue`、`isNotFalse` 等工具，并根据业务明确 `null` 应表示 false、true 还是独立未知状态；不得通过未经判空的 `booleanValue()` 拆箱。
- 基本类型本身不可能为 `null`，不得增加无意义的判空；将包装类型转换为基本类型前必须完成空值归一或显式拒绝，且不得把未知状态静默伪造成确定事实。

## 4. 日志、异常与对外错误（`logging-exception-safety`）

### 4.1 日志

- `catch` 中需要记录日志时使用 `error`、`warn` 或 `fatal`；必须同时控制重复来源、重试循环和逐帧/逐条处理造成的刷屏，可采用聚合、采样、限频或首末次记录。
- `DEBUG`、`TRACE` 日志必须先做对应级别开关判断。字符串拼接、序列化、大集合计算、远程读取等昂贵参数也必须在开关内求值，不能只依赖日志框架占位符惰性。
- 禁止在日志中打印实体的 JSON 序列化结果，禁止在日志参数、字符串拼接或惰性 Supplier 中对实体、record、DTO、领域对象等调用 `writeValueAsString`、`toJson`、`toJSONString` 或同类序列化方法，避免序列化耗时、异常和敏感信息泄露影响业务。该禁令适用于所有日志级别，即使已判断 DEBUG/TRACE 开关也不得序列化实体。
- 排障日志只输出明确白名单内的安全标量、业务标识、状态、数量和长度等摘要，使用简单的键值形式；不得先序列化整个实体再脱敏，也不得以 `toString` 变相输出完整实体。
- 日志与异常技术消息使用英文硬编码；面向用户的业务文案走安全业务码和 i18n，不把中文技术异常硬编码进日志。
- 记录异常时，异常对象必须作为最后一个 `Throwable` 参数传入，保留堆栈和因果链；不得只记录 `e.getMessage()` 替代异常对象。
- 日志不得写入原始上游响应体、敏感请求体、密钥、令牌、服务器内部地址或个人信息。

### 4.2 异常与响应

- 禁止把 `getMessage()`、异常类名、堆栈或上游原始错误直接返回前端。对外使用稳定、安全的业务码和通用 i18n 文案。
- 安全业务码或 i18n 例外必须由审查人员逐条确认：只含已批准的业务动态字段，不含服务器、路径、SQL、Redis 键、内部类名和原始异常。
- API 响应、验证报告、审查报告和证据附件不得保存原始异常体或原始响应体；确需排障样本时，只保留脱敏、白名单化且有界的数据。
- 降级必须呈现真实结果。不能把异常吞成空成功、伪造完成或把未确认状态改成确定成功。

## 5. ToC 设计、交互与渲染（`toc-interaction`）

### 5.1 文案与恢复

- 面向终端用户的交互必须简单易懂，优先静默恢复和原地收口；只有确需用户决策或人工核对时才提示。
- 禁止出现技术、开发、测试话术，包括但不限于 runId、toolCallId、回灌、帧、桩、测试环境、服务器、Redis、异常类名和本地路径。
- 不暴露服务器信息、敏感配置或原始标识。业务名称、字段和结果使用后端提供的动态业务字段，不在前端硬编码某业务专属标签。
- 通用文案使用 i18n 键和参数化插值；新增或变化字段同步中英文及降级文案，不在模板中拼接不可翻译句子。
- 不做“操作成功”“可以继续”等无行动价值提示，不把“已批准·等待执行”等多个事实压成复合状态。自动核对期间保持静默，核对后显示真实单一状态。

### 5.2 卡片与滚动

- 正式业务卡片卡头始终单行：图标、标题、可选副标题、状态和折叠控件按统一顺序排列；窄屏先隐藏副标题，不换行。
- 状态图标、状态色和状态文本使用统一映射，并提供可访问名称；不得用图标制造与真实状态不一致的复合含义。
- 卡体按内容类型分级限高。每张正式卡片最多一个纵向滚动区，卡头与主要操作留在滚动区外；表格必要的横向滚动不额外制造纵向滚动。
- 块级、卡头、卡体和内层间距统一归口，禁止外层 margin、内层 padding 和相邻块间距重复叠加。
- Mermaid 与纯 Markdown 不套业务卡片体系，不破坏其围栏闭合后渲染、源码降级、缩放、复制和现有滚动行为；样式修改必须检查防误伤。

## 6. API、SSE、Redis、并发与状态机（`protocol-redis-concurrency`）

### 6.1 协议与状态

- API、SSE 和历史数据保持向后兼容：新增字段应为可选 additive 变更；删除、改义、改类型和新增必填字段必须经过明确规格变更与迁移设计。
- 取消、确认、回灌、重试和恢复必须幂等；重复请求接受已有真实终局或返回可判定结果，迟到帧和旧代次不得复活或覆盖新状态。
- 状态只来自真实执行、存储或权威对账结果。禁止伪造进度、成功、取消、提交、清理或校验结果；未知必须保持未知并给出真实人工出口。
- pre 与 post 结果分别承载，post 不得被 pre 的旧结果覆盖，pre 也不得被用来冒充 post 执行成功。状态迁移遵守终态吸收、代次和 fence 约束。

### 6.2 Redis 与清理

- 禁止无界 `KEYS`、无界 `SCAN` 和无界批量读取。SCAN 必须有游标续页、单页上限、总次数或总量上限及终止条件。
- pipeline 必须有批大小、总数据量和错误处理边界；Cluster 多键操作保持同槽，不把 pipeline 当作跨键事务。
- Redis 中的所有数据都必须有与实际业务生命周期匹配的失效时间，**7 天只是绝对上限，不是默认值、目标值或统一配置值**，禁止永久存储、`PERSIST` 或无过期策略的写入。基本不应有数据需要达到 7 天；必须根据访问频率、刷新周期、锁持有时间、会话生命周期、任务恢复窗口、数据体积和回收成本选择更短的合理时限，并说明依据，不得为了省事直接填 7 天。
- 活跃数据只能通过真实活动续期，续期时长同样按场景设置，不得借续期变相永久保存；终态、锁、缓存、索引、台账、临时键和会话数据均须明确回收期限。写入后必须能核验 TTL，不得以键类型或后台任务清理替代过期约束，也不得把既有较长配置无评估地延长到上限。
- AI 对话数据采用 **24 小时滑动过期**：以最后一次真实用户活动为起点计算 24 小时，用户继续对话、查询该对话历史、确认或执行其他会话内操作后，必须将该对话全部关联数据的失效时间重新刷新为 24 小时，刷新次数不限，不得使用 7 天作为对话数据目标 TTL。
- 对话 TTL 刷新必须覆盖该会话现有 transcript、run、事件帧、上下文、表单、待处理状态、索引和关联缓存，通过有界索引和同槽批量机制执行，不得无界 SCAN，不得复活已删除或已到期的数据。锁、租约和短期 fence 等安全机制保持各自更短 TTL，不得机械延长为 24 小时；无真实用户活动的后台读取不得冒充用户续期。
- 对话 TTL 刷新必须设置节流，避免高频历史查询、会话操作或多实例并发导致整组键反复写入。节流窗口应明显小于 24 小时并按实际负载配置，窗口内可跳过冗余刷新，窗口到期后的真实用户活动必须能及时续期，不得因节流导致活跃对话过期。
- 多服务实例下不得使用本地内存时间戳、本地 Map、本地锁或单机 RateLimiter 作为对话续期节流依据。必须使用带租户和会话边界的 Redis 节流键及原子操作（例如同槽 `SET NX PX` 或 Lua）协调所有实例，节流键自身也必须有合理短 TTL；随机路由到任意实例时都必须得到一致的节流结果。
- 其他重试、轮询、缓存刷新、通知、定时清理和防抖场景也必须评估重复调用造成的性能放大，并按场景设置节流、去重、退避或抖动；跨实例共享的动作必须使用 Redis/数据库等共享协调机制，只有确属单实例本地的动作才可使用内存节流，不得以客户端防抖代替服务端跨实例控制。
- 清理完成后必须留下可核验证据：真实键或游标前后对照、TTL、索引/游标回收、post 状态和必要的重试记录。不得只以“已调用清理方法”作为清理成功证据。

### 6.3 模型并发

- 模型调用总并发不得超过 **10**。直接聊天、压缩、摘要、KB、工具内部调用及其他间接模型路径共用同一限流边界，不得每个入口各放 10 个。
- 新增间接调用时必须沿完整调用图核对限流获取与释放；取消、异常和超时都要释放许可，排队必须有界。
- 压测代码也必须走同一限流语义，不能通过压测入口绕过生产模型并发上限。

### 6.4 线程池与定时任务池生命周期

- 线程池、定时任务池及其执行器不得声明为静态变量或静态常量，包括 `static final` 的共享池；不得在任何普通方法内创建，包括业务方法、日志或异常分支、回调和局部工厂方法。只能在实例成员变量声明、构造方法或 Spring `@Bean` 声明中创建。
- 线程池变量通常只能赋值一次，实例字段应使用 `final`；确需重新赋值必须具有明确的生命周期原因并同步关闭旧池，不得覆盖后遗留未关闭的执行器。
- 禁止使用 `new Thread` 直接创建线程，包括自定义 ThreadFactory、回调和定时任务。统一使用受管理的线程池、执行器或框架调度能力。
- 禁止继承或覆写线程池、定时任务池及其执行器，包括 `ThreadPoolExecutor`、`ScheduledThreadPoolExecutor`、`ForkJoinPool`、`AbstractExecutorService` 等；不得通过继承或覆写 `execute`、`submit`、`schedule`、`newTaskFor`、`afterExecute` 等方法改变池行为。需要限流、监控或生命周期控制时使用组合委托、框架扩展点或既有组件，不得另造继承体系。
- 线程池和定时任务池必须设置与业务负载匹配且有界的线程数量、队列容量、线程存活时间、拒绝策略和调度周期；禁止无界线程、无界队列、永久存活且无回收策略或不受控的调度频率。核心线程数、最大线程数、队列及超时配置不得在未评估的情况下沿用可能无界的默认值。
- 对象自管的线程池必须随所属对象或 Bean 销毁，使用 `@PreDestroy`、`AutoCloseable` 或等效生命周期入口，根据任务特性选择优雅停止、有限等待、取消剩余任务及必要时强制关闭；中断标记必须正确恢复，不得泄漏线程或让关闭过程无限等待。
- Spring 容器托管的线程池优先复用框架生命周期，不得重复销毁容器负责的执行器；对象只负责释放自身持有的任务、订阅和回调，并核对取消后不再提交新任务。

### 6.5 多线程安全与上下文传播

- 涉及多线程的共享状态必须明确线程安全和所有权策略，使用不可变对象、线程封闭、并发集合、原子变量、锁或其他适当机制保证安全；不得无保护共享可变 `HashMap`、`HashSet`、`ArrayList`、字段或缓冲对象。
- 使用线程安全类型不代表复合操作天然安全，检查后再执行、读改写、多键一致性和状态迁移仍需通过 `compute`、CAS、锁、代次或其他机制保证原子性；并发集合的 `null` 限制和弱一致迭代语义也必须遵守。
- 线程池、定时任务、`CompletableFuture`、异步回调及其他线程切换场景必须显式传播租户、用户、会话、追踪和业务上下文。优先使用项目现有 TransmittableThreadLocal 与 `RequestContextUtils` 的捕获、包装和恢复能力，在任务提交时捕获，在执行前后恢复并清理，不得依赖普通 ThreadLocal 自动跨线程继承。
- 上下文快照应优先不可变，禁止跨任务共享可变上下文造成租户串扰、数据污染、重复提交或其他副作用；任务取消、异常和完成路径都必须恢复调用方上下文并清理 MDC/身份状态，确保不会泄漏到下一个复用任务。

### 6.6 租户发现与索引

- 禁止调用或臆造外部环境不存在的“获取租户列表”接口，也不得通过全表扫描、遍历全部业务数据或跨租户读取来代替租户发现。
- 确需知道当前系统出现过的租户时，应在经过身份认证的请求拦截或过滤器中记录合法租户身份，并写入项目自有的 Redis 租户索引后再使用；索引必须遵循租户隔离、数据最小化和最长 7 天 TTL，只能由真实活动续期，不得接受伪造身份或向无权用户暴露租户清单。

### 6.7 多服务实例与 Redis Cluster

- 开发实现必须默认按多服务实例和 Redis Cluster 运行，用户请求可能被随机路由到不同实例，不得假设会话亲和、固定实例或连续请求落在同一进程。创建、查询、确认、取消、恢复、重挂、导出和清理等后续请求落到任意实例时都必须可用。
- 不得把进程内 Map、本地锁、ThreadLocal、内存队列、单机调度或本地文件作为跨请求唯一事实源。共享状态必须存入具有租户隔离、最长 7 天 TTL 和明确一致性与恢复策略的 Redis/数据库；本地缓存只能作为可丢弃的性能优化，不得阻止其他实例读取真实状态。
- 跨实例写入、取消、确认和执行必须幂等，使用唯一请求标识、原子操作、CAS、Lua、代次和 fencing 等机制防止重复执行、旧实例覆盖新状态或迟到请求复活终态。实例崩溃、租约过期和接管后必须能够恢复，续租与心跳不得代替终态 fencing。
- Redis Cluster 多键读取、Lua、原子状态迁移和清理必须保证相关键位于同一 slot，必要时使用合法 hash tag；不得把 pipeline 当跨键事务，不得依赖单机 Redis 的跨槽原子性，并正确处理 MOVED/ASK、超时、部分失败和重试。
- 每个请求都必须根据当次认证和权威存储重新建立上下文，不得依赖上一实例遗留的身份或内存状态；多实例定时任务、后台扫描和后台执行必须具备所有权、租约、 heartbeat、fence 和重复执行防护。
- 审查涉及共享状态的改动时，必须核对实例 A 写入后实例 B 查询、确认、取消或恢复的路径，以及 Cluster 同槽、TTL、故障接管和随机路由场景，不得只按单实例或单节点 Redis 推断正确性。

### 6.8 租户隔离与规模容量

- 不同租户的数据必须严格隔离。业务标识只能假定在租户内唯一，不能假定跨租户唯一；数据库约束、查询条件、Redis key、缓存、锁、幂等键、去重键、任务标识和审计记录必须包含合法租户边界，必要时同时包含用户边界，禁止跨租户去重、覆盖、读取或清理。
- 容量评估按约十个租户、最多上百个服务实例进行，不能只计算单实例资源。线程数、队列、连接数、定时任务、轮询频率、Redis 请求量和后台扫描量必须评估“每实例 × 实例总数 × 租户数”的全局放大，并同时满足模型、数据库和 Redis 的全局限额。
- 禁止按租户或实例无节制创建线程池、定时任务和轮询循环。优先使用共享有界执行器、全局租约、批量处理、事件驱动、指数退避和抖动，避免上百实例重复扫描同一租户；单实例看似很小的线程池或轮询间隔也必须先核算全局总量。
- Redis 键数量、单键大小、SCAN 范围、pipeline 批量、TTL、内存和访问频率必须有界；不得因租户和实例增长产生永久键或无界索引。Cluster hash tag 只用于确需同槽原子操作的键组，不得把全部租户或全部数据集中到少数 slot 形成热点，并避免单租户热点影响其他租户。
- 多租户共享执行器、队列和缓存必须具有配额、公平性和隔离策略，防止单租户或单实例占满资源；任务调度和清理按实际工作量去重，不得按“租户数 × 实例数”重复执行同一任务。

### 6.9 容器规格与配置固定性

- 项目按每个服务实例固定 **2C4G** 容器规格设计，线程池、定时任务池、连接池、队列、缓存、批量、并发、超时和其他容量配置必须使用经过审查的固定值或固定配置项及其明确上限，不得根据 CPU、内存或容器资源指标动态计算、自动扩缩或调整。
- 项目代码和配置不得读取或依赖 CPU 核数、JVM/系统/容器内存、cgroup 指标或相关环境变量作为任何决策、计算或配置输入。禁止 `Runtime.availableProcessors()`、`maxMemory()/freeMemory()/totalMemory()`、操作系统资源 MXBean 及同类动态容量推导。
- 不得以“适配机器”“提高利用率”为由引入 CPU/内存关联逻辑；容量只能通过明确的业务负载、全局实例数、租户数、下游限额和有界配置评估，超出容量时使用既有拒绝、背压、退避和降级策略，不得自行改变资源参数。

### 6.10 资源释放与异常保序

- 资源释放本身可能失败，必须确保业务逻辑、日志记录或前一次释放失败不会阻断后续资源释放。文件、流、连接、锁、租约、订阅、线程池、定时任务和上下文清理均适用，不得因 `return`、异常或清理顺序遗漏释放。
- 优先使用 try-with-resources 自动按获取逆序释放并保留抑制异常；手动释放时必须通过嵌套 `try/finally` 或逐项独立保护保证每项释放都会执行，不得在同一个未保护的 `finally` 中顺序调用多个可能抛异常的释放方法。
- 原始业务异常不得被释放异常掩盖。需要手动聚合时保留原始异常为主异常，将后续释放异常作为 `addSuppressed`；记录释放失败时使用有界 WARN/ERROR 且异常对象为最后参数，日志失败也不得阻断其他清理。
- 释放操作应尽量幂等，并核对所有权、代次和 fence，避免重复释放或释放其他实例/租户的资源；中断标记必须恢复，线程池停止、任务取消、连接归还和上下文清理不得互相依赖后才能执行。
- 不得为跳过释放异常而空吞 `catch`，也不得以“关闭通常不会失败”为由省略保护；确无失败语义的框架释放方法必须依据其明确契约使用。

## 7. Unicode 与流式解析（`unicode-stream-parsing`）

- 字节流使用增量 UTF-8 解码，跨 chunk 保留未完成字节序列；禁止对每个二进制 chunk 独立 `new String(...)` 或等价的重复解码。
- 不在 UTF-16 代理对中间切分，不在组合字符或字素簇中间截断。用户可见截断优先使用字素边界，服务端与前端的长度口径必须明确。
- 只在完整 SSE 事件、完整 JSON/协议帧到达后解析。未闭合围栏、未完成 Mermaid 和不完整 JSON 不得提前当成完整内容。
- 不完整或非法帧按协议真实降级：保留已接收内容、标记截断或失败、允许后续恢复；不得静默丢弃、伪造完成或把半截内容当成功。
- 已解码文本不再二次转码。后端、网络适配层和前端只在一个明确边界完成字节到文本的转换。

## 8. 验证与独立审查（`verification-review`）

1. 静态审查必须明确写“静态审查”，不得冒充实测。没有执行的检查写 `NOT_RUN`，不得写成 `PASS`、`通过`、`已验证` 或绿色结论。
2. 涉及真实接口、SSE、Redis、状态机或清理的变更，验收应读取真实接口结果和真实 Redis 键/TTL/游标/post 状态。静态阅读只能作为施工审查，不能替代这些运行证据。
3. 提交前由审查人员对当前暂存区**逐文件、逐 hunk**检查；独立审查应由非施工者或独立审查上下文完成，不得只复述施工结论。审查记录必须覆盖生产、测试、压测、脚本和文档文件。
4. 代码修改结束后，必须确保修改相关的非测试代码已由实际编译命令覆盖并编译通过；编译不通过不得提交或推送。不执行测试不等于不编译，静态审查、旧构建产物和其他模块的编译结果均不能替代本次修改的编译证据。审查记录必须写明实际编译命令、覆盖范围和结果；编译错误未清零时不得声称修复完成或启动旧产物冒充当前代码。
5. 代码必须使用 IDEA 能力执行 Reformat Code 格式化；IDEA Inspect Code 及其检查问题处理当前暂缓，不作为提交门禁。不得用人工浏览、其他格式化工具或编译成功代替 IDEA 格式化。审查记录必须写明 IDEA Reformat Code 的实际覆盖文件和结果；格式化导致的后续变化必须重新审查，未执行 Inspect Code 不得写成检查通过。
6. 前后端服务启动后必须观测启动及运行日志，不能只凭健康检查、端口可访问或进程存活判定服务正常。对报错、告警和异常堆栈必须逐条分析并记录日志位置、时间和分类依据：确认是问题的必须处理并复验闭环；确认不是问题的必须记录摘要、判断依据和备案位置；无法判定的按问题处理，不得忽略、掩饰或只以健康检查通过代替日志验收。
7. 审查以最终暂存内容为准。审查后导致覆盖暂存状态变化的修改、重暂存或文件集合变化都会使指纹失效，必须重新逐 hunk 审查并新增记录。
8. 测试替身、桩和静态门禁只能证明其实际覆盖面；不得外推为真实模型、真实浏览器、真实 Redis Cluster 或多实例验证。

## 9. 提交门禁与记录格式

### 9.1 指纹、append-only 与防复用

- pre-commit 执行敏感信息扫描和 `node scripts/ci/check-d6-sync.mjs --standards` 两道检查。统一规范门禁缺少 Node、脚本、有效记录或指纹匹配时均阻断提交；敏感信息逃生口不能豁免它。
- standards 指纹版本为 `development-standards/v2`，覆盖除 `development-standards-review.json` 自身以外的全部暂存变更。每个条目使用无歧义 JSON 元组 `[status, mode, fromPath, path, blob]` 排序后散列；路径取 Git `-z` 原始字符串，standards 禁用 rename detection，以删除加新增表示。
- 审查记录必须在同一提交**仅追加**。父 ledger 的 `reviews` 必须是当前 `reviews` 的严格前缀，历史条目不得删除、修改或重排。
- 父 ledger 中已经出现过的 fingerprint 不得再次使用，即使修改理由、时间或其他字段也不视为新记录。审查后导致覆盖暂存状态变化的修改必须重新审查并生成新指纹。
- 当前和父 ledger 的 `reviews` 都必须存在且为数组，缺失或非数组均为 `rc=2`。父 ledger 只有经 Git 树读取确认不存在时才按空历史处理；pre-commit 的 unborn HEAD 单独视为 `parentReviewText=null`，其他 Git 错误、非法 JSON、版本或结构不符均失败关闭。

### 9.2 merge 与 CI 范围

- CI 使用 `--standards --base <base> --head <head>` 验证范围内的**所有引入提交**，包括普通提交和 merge，不无条件跳过 merge，也不依赖修改分支保护。
- 两父 merge 先以 `git merge-tree --write-tree parent1 parent2` 计算自动合并预期 tree。merge tree 等于任一父 tree 仍可豁免；仅 merge-tree 状态 0 且 merge tree 等于该预期 tree 时才也可豁免，状态 1 必须追加 merge 自身记录。非法 tree 输出、其他退出状态和 octopus 继续失败关闭，所有引入提交仍逐笔验证。
- 需要 merge 自身记录时，以第一父提交的 diff 和 ledger 为本次指纹及 append 基线，其他引入提交仍分别验证。
- push 的 before 必须有效且是 head 祖先，全零、非祖先或异常空范围失败关闭。PR workflow 先执行 `git merge-base PR_BASE_SHA PR_HEAD_SHA` 求实际分叉点，再交给检查器，不能要求原始 `base.sha` 是 head 祖先。仅 base/head 解析为同一 commit 时允许空范围。

### 9.3 必填字段与规范域

每条记录至少包含：

- `fingerprint`：当前 v2 变更指纹；
- `status`：`reviewed`，或符合下方白名单的纯文档变更使用 `not-affected`；
- `reason`：本批逐 hunk 审查范围和结论的具体理由；
- `reviewedAt`：带时区的 ISO 8601 时间；
- `reviewer`：实际审查人员或审查上下文；
- `specChanges`：规格变化数组，无变化为 `[]`；每项必须是 `{change, reason, impact}`，分别写清变化、原因和影响面，三个字段都逐项校验；
- `files`：除记录文件自身外每个变更文件一项，含 `path`、`status` 和具体 `reason`；
- `domains`：以下七个域全部必填，每域含 `status` 和具体 `reason`。

| 域 ID | 审查内容 |
| --- | --- |
| `dependency-reuse` | 依赖授权、Apache Commons/Guava/Spring、Tailwind/lodash 复用顺序 |
| `java-api-style` | 空返回、可变性、Java 50 行与复杂度 20、布尔命名、首尾访问、import、JSON 显式字段名、Lombok、Long 字符串转换 |
| `logging-exception-safety` | 日志级别与开关、英文技术消息、Throwable、脱敏、前端错误 |
| `toc-interaction` | ToC 文案、静默恢复、动态字段、i18n、卡片与渲染 |
| `protocol-redis-concurrency` | API/SSE、取消幂等、真实状态、Redis、pre/post、模型并发 |
| `unicode-stream-parsing` | UTF-8、代理对、字素簇、完整帧与降级、禁止二次转码 |
| `verification-review` | 逐 hunk、证据真实性、规格变化、NOT_RUN 边界 |

域和文件的 `status` 使用 `checked` 或 `not-affected`。`checked` 表示已检查适用 hunk，不表示运行测试通过；`not-affected` 必须写明该域与本批文件的具体适用关系。

所有理由和 `specChanges` 字段都拒绝空值、整体 `<...>`、已知模板原文及“已审查”“符合规范”“不涉及”“无影响”“同上”等泛化套话。仅由已知泛化子句、连接词和标点组成的组合套话同样拒绝；包含文件、hunk 或具体技术对象的说明不按该组合规则误伤。模板生成器只提供空字符串等待填写，不提供可直接提交的答案。

### 9.4 文档白名单与语义边界

standards 全链路的 ledger 排除都使用原始 `String` 严格相等，不做路径归一化；文档白名单也不把原始反斜杠当作目录分隔符。文档判断由 standards 白名单独立决定：

- `docs/` 下仅 `.md`、`.markdown`、`.rst`、`.adoc`、`.asciidoc`、`.txt` 可自动按文档处理；`.js`、`.json`、`.html` 等可执行或结构化文件不因位于 docs 就自动当文档。
- `docs/` 外，`.md`、`.markdown`、`.rst`、`.adoc`、`.asciidoc` 文件，以及无扩展名或 `.txt` 的 `README` 可按白名单处理；原 D6 block 路径内的纯文本文档也可使用 `not-affected`，但代码、类型、配置和结构化数据仍不行。

门禁只验证记录结构、指纹、新鲜度和 append-only 约束，**不证明理由、审查语义或验证证据真实**。独立逐 hunk 审查和真实运行验证仍是必要补充。

## 10. 本轮门禁实现的验证边界

以下场景仅做独立静态实现复核，均为 `NOT_RUN`：两父 merge-tree 预期 tree、父 tree 复用、evil merge、octopus、PR merge-base、push 祖先与空范围、全零 before、append 历史删改、父 fingerprint 防复用、组合套话及具体理由防误伤、mode/fromPath/原始 String 路径、rename 禁用、文档白名单、当前和父 `reviews` 缺失/非数组、父 ledger 读取/JSON/版本错误、unborn HEAD、`specChanges` 三字段。未修改任何测试代码，未执行测试、构建、git、pre-commit 或 CI，不得据此主张这些场景已经动态通过。
