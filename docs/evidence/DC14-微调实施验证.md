### 3.2 T2 模型侧工具结果截断（配置化）

**结论：已实现并实测生效，两条通道分离成立。**

- 配置键：`app.ai.tool-result.max-rows`（初值 200）/ `max-chars`（初值 8000），`AiProperties.ToolResult` 绑定，`ToolResultLimiterTest#defaultLimitsAre200RowsAnd8000Chars` 把初值本身锁成契约；
- 应用点两处、同一口径：`SpToolCallingManager`（本轮循环回填）与 `ResumeService`（续跑重建 `role:tool`）；
- 截断标记形如 `…[结果已截断：原 N 行 / M 字符，仅前 X 行|字符；完整结果见本轮工具调用记录（前端帧与台账不截断）。如需更多细节，请缩小查询范围或分页获取。]`。

**行数上限实测**（后端 `--app.ai.tool-result.max-rows=3`，真实工具 `list_config_defs` 返回 15 行）：

- 模型侧（第 2 次上游请求原文，`<EV>/raw/upstream-req-rows3.json`）：
  `"- CURRENCY（货币字典）层级:GLOBAL 字段数:4\n- DOC_TYPE（单据类型）层级:GLOBAL 字段数:4\n- APPROVE_ROLE（审批角色）层级:GLOBAL 字段数:3\n
  …[结果已截断：原 15 行 / 560 字符，仅前 3 行；…]"`
- 前端帧（`<EV>/raw/frames-A3-rows3.sse`，seq=4）：`tool_result.result` 长度 = **560**，无截断标记 → **前端拿到全文**。

**字符上限实测**（后端 `--app.ai.tool-result.max-chars=50`）：

- 模型侧（`<EV>/raw/upstream-req-chars50.json`）：`仅前 50 字符`（原始 560 字符）；
- 前端帧（`<EV>/raw/frames-A4-chars50.sse`）：`tool_result.result` 长度仍 **560**。

### 3.3 T2 的实测发现（关键）：官方结果转换器会 JSON 转义换行

实测发现后端工具结果经官方 `DefaultToolCallResultConverter` 序列化后，**换行在字符串里是字面两字符 `\n`**（不是真实换行）：

```
"- CURRENCY（货币字典）层级:GLOBAL 字段数:4\n- DOC_TYPE（单据类型）层级:GLOBAL 字段数:4\n- …"
```

只数 `'\n'` 会得到"1 行"，**行数上限在真实链路里等于没生效**（第一次实测即踩到：标记显示"原 1 行 / 560 字符"）。因此 `ToolResultLimiter` 的行数统计与切分**同时认两种分隔形态**（真实 `\n` 与字面 `\n` 两字符），并新增 `truncatesRowsOnJsonEscapedText` 用例锁住。修正后复测即得"原 15 行 / 560 字符，仅前 3 行"（§3.2）。

> 为何不改成"先反转义再计数"：会给"前端回灌结果"（本来就不是 JSON 字符串）引入误判与额外失真；两种分隔一并计数既覆盖两条来源，也不改变任何原文。

### 3.4 T4 `confirm_request` 补 `expiresAt`

**结论：已实现并实测。** 帧字段为**绝对毫秒**（= 帧生成时刻 + `timeoutSeconds`），与 `atMs` 的实测差值**精确 120000ms**：

```
{"type":"confirm_request","toolCallId":"call-dc14-1","name":"start_import","timeoutSeconds":120,
```
