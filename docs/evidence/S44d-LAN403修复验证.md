## 1. 根因（一句话）

`changeOrigin: true` 使 vite 代理把转发给后端的 `Host` 头改写成代理目标（`localhost:<后端端口>`），而浏览器发出的 `Origin`（LAN 源 `http://<LAN_IP>:<vite端口>`）原样透传；Spring 6.2.18 的 `CorsUtils.isCorsRequest` 以 **`Origin` 的 scheme/host/port 是否等于请求自身（Tomcat 依 `Host` 头解析出的）scheme/serverName/serverPort** 判定同源，二者不一致即判为跨域请求，再经后端 `CorsFilter` 白名单（仅 `http://localhost:*`、`http://127.0.0.1:*`）比对失败，返回 **403 `Invalid CORS request`** —— 这是"LAN 下所有非 GET 请求 403、本机 localhost 正常"的完整解释（GET 类请求浏览器不携带 `Origin`，故不受影响）。

### 1.1 后端侧证据（直连后端，不经代理）

`<REPO_ROOT>/backend/src/main/java/com/example/configmgr/config/WebConfig.java:18`：

```java
config.setAllowedOriginPatterns(List.of("http://localhost:*", "http://127.0.0.1:*"));
```

直连后端 `:18331` 的隔离矩阵（`POST /api/ai/chat`，请求体 `{}`）：

| Origin | 请求 Host（curl 显式指定） | 响应 | 说明 |
|---|---|---|---|
| `http://<LAN_IP>:5203` | `localhost:18331`（默认） | **403** `Invalid CORS request` | 不同源 + 不在白名单 ⇒ 拒 |
| `http://localhost:5203` | `localhost:18331`（默认） | 503 `AI_UNAVAILABLE` | 命中白名单 ⇒ 放行（业务层） |
| （无 Origin） | `localhost:18331`（默认） | 503 `AI_UNAVAILABLE` | 无 Origin ⇒ 非跨域 ⇒ 放行 |
| `http://localhost:5203` | `<LAN_IP>:5203` | 503 `AI_UNAVAILABLE` | 不同源但命中白名单 ⇒ 放行 |
| `http://<LAN_IP>:5203` | `localhost:18331` | **403** | 不同源 + 不在白名单 ⇒ 拒 |

结论：**判定同时看 `Origin` 与请求 Host 的"是否同源"，再叠加白名单**。`changeOrigin` 影响的正是 Host 这一侧。

### 1.2 框架侧证据（字节码级）

从既有产物 `backend/target/config-mgr.jar` 内取 `BOOT-INF/lib/spring-web-6.2.18.jar`，`<JDK_HOME>/bin/javap -p -c` 反汇编 `org.springframework.web.cors.CorsUtils#isCorsRequest`，可见其并非"只看 Origin 是否存在"，而是：

```
invokeinterface HttpServletRequest.getHeader("Origin")   // 取 Origin
invokeinterface HttpServletRequest.getScheme()           // 请求 scheme
invokeinterface HttpServletRequest.getServerName()       // 请求 Host（由 Host 头解析）
invokeinterface HttpServletRequest.getServerPort()       // 请求端口
... ObjectUtils.nullSafeEquals(scheme, originUrl.getScheme())
... ObjectUtils.nullSafeEquals(host,   originUrl.getHost())
... getPort(scheme, port) == getPort(originUrl.getScheme(), originUrl.getPort())
```

三者全等 ⇒ 返回 `false`（非跨域请求）⇒ `DefaultCorsProcessor` 直接放行，**不查白名单**。这就是 `changeOrigin: false` 能修好的机制性原因。

### 4.3 方法学警示（重要：一种会误导的测法）

下例**不是** LAN 场景，但在本棒早期曾造成误判，特此记录以免复跑时被带偏：

```
# 用 localhost 寻址，却人为塞入 LAN Origin —— 浏览器不会产生这种组合
$ curl -i -X POST http://localhost:5203/api/ai/chat \
    -H "Origin: http://<LAN_IP>:5203" -H "Content-Type: application/json" -d '{}'
```

该请求下 `changeOrigin` 为 `true` 或 `false` **都返回 403**（修复后被削去的 Host 改写都不发生：`false` 时 Host=`localhost:5203` 仍与 Origin 不同源，`true` 时 Host=`localhost:18331` 亦不同源）。原因见 §1.1：判定的两半是"是否同源"与"是否命中白名单"，而该组合两半皆不满足。**判据必须以真实 LAN 寻址（URL 主机名 = Origin 主机名）为准。**
