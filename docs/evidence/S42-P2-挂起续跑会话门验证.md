## 2. 落成的集成形态（规格 §3 的四机制咬合）

```
POST /api/ai/chat
 └─ AiAvailability（无 key → 503 AI_UNAVAILABLE，开流之前）
 └─ SessionGate.acquire(sessionId, runId)        ← 进行中 → 409 SESSION_BUSY{runId, reattach}
     └─ 挂起专用有界平台线程池（queue=0，AbortPolicy）→ 饱和 503 SUSPEND_POOL_SATURATED
         └─ AiChatService：AiSessionService.ensure → 组装完整请求历史 → RunStore.create → start 帧
             └─ ChatClient（单条 system = 人设+工作区快照；官方 MessageChatMemoryAdvisor；
                          toolContext{runId,sessionId}；本上下文披露的工具子集）
                 └─ 官方 OpenAiChatModel 循环 → SpToolCallingManager.executeToolCalls
                     ├─【硬规范①】先写 RunStore（assistant(tool_calls) + 待决条目）并发 suspended 帧
                     ├─ BACKEND  → 认领(claim) → 官方 DefaultToolCallingManager 委托执行 → 台账
                     ├─ CONFIRM  → ConfirmGate 挂起（心跳 2s）→ 放行=执行 / 拒绝·超时=未执行回填
                     └─ FRONTEND → 挂起等 POST /api/ai/frontend-tool-result（桩体永不执行）
                 └─ 落定：snapshot.messageJson = prompt.getInstructions()+[assistant,tool]
             └─ 终帧 done/error → 快照 DONE → 记忆整窗口覆盖写回（收敛）
     └─ finally：SessionGate.release（轮终态主动释放）+ RunRegistry.close

进程死亡后（SM-04）
 GET /api/ai/runs（发现 pending）→ POST /api/ai/runs/{runId}/resume
 └─ runId 互斥锁 → 准入校验（DONE/RUNNING/PENDING_UNRESOLVED）
 └─【硬规范②】重建完整历史 = snapshot.messageJson + assistant(in-flight) + tool(逐条结算)
      · 台账已有该 toolCallId  → 复用结果（不重放）
      · APPROVED 且 executed=false（E2 窗口）→ 认领后补执行（恰好一次）
 └─ 官方 ChatModel.stream(完整历史 + 同披露子集 + toolContext) → 新工具调用仍走 SpToolCallingManager
 └─ GET /api/ai/events/{runId} 可随时重挂，先回放外置状态帧再续接实时帧
```

## 4. 遇到的问题与解法（含 4 条集成发现）

### 4.1 第一次实测就撞上的坑：官方 ChatClient 的 system 文本只有"一个槽位"

第一版按直觉写了 `.system(人设).system(工作区快照)`，结果 V3 快照里 `messageJson[0]` **只剩工作区快照**，
主提示词整段消失（模型仍能干活，因为工作区快照在，但"工作原则"全丢）。
定位：`ChatClient.ChatClientRequestSpec.system(String)` 把文本放进一个**单键**参数表（内部 `systemTextParams`），
第二次调用覆盖第一次。修法：合成一条 `systemText = 人设 + "\n\n" + 工作区快照` 一次下发，
并按官方 `MessageChatMemoryAdvisor.before` 的变换（`[首个 SystemMessage] + 记忆窗口 + 其余指令`）拼装快照历史。
修后 `wire-*` 请求报文与快照一致（附件 A/B）。

> 影响面：任何用 ChatClient 拼多条 system 的写法都会静默丢内容（无异常）。后续棒次/S4.4 若再加系统段落，必须合并成一条。

### 4.2 「官方循环自身的工具后续跑会丢 system/user」——在 1.1.8 上不成立（与 SP-02 §7.1 的表述相反）

规格硬规范② 的括注（以及 SP-02 §7.1）称官方循环的工具续跳请求只带 `assistant+tool`。本棒核对 1.1.8 字节码：

```java
// DefaultToolCallingManager（javap -c）
private List<Message> buildConversationHistoryAfterToolExecution(List<Message> instructions,
        AssistantMessage assistant, ToolResponseMessage tool) {
    List<Message> out = new ArrayList<>(instructions);   // ← 原 prompt 的全部指令（含 system/user）
    out.add(assistant);
    out.add(tool);
    return out;
}
```

即**官方实现保留完整历史**；SP-02 报文里"只有 2 条消息"是因为它的 PoC 管理器自己返回了 `List.of(assistant, tool)`。
后果很实际：本棒的 `SpToolCallingManager` 若照抄 PoC 形态返回 `[assistant, tool]`，就会把**同一个修复引入成新缺陷**
（多轮工具对话中 system/user 丢失）。因此本类按官方口径拼装本轮历史，
实测本次 **64 次请求全部 HTTP 200，且所有工具续跳请求都保留 system+user**（附件 A §1/§2）。

**硬规范②仍然成立且必须执行**：`ResumeService` 的续跑请求是**我们自己在进程外重新拼的**，
必须用 `RunStore` 快照里的完整历史（附件 A §3 的 `wire-51` 就是它）。

### 4.3 SP-02 §6 遗留的"重复执行窗口"用原子认领修掉；但时间戳语义留下一个瑕疵

SP-02 E2 的处置是"执行返回后写 `executed`" ⇒ 最坏情况**重复执行**。本棒改为：

```java
// RunStore#claimExecution —— HSETNX 语义（Redis putIfAbsent），认领先于执行
Boolean claimed = redis.opsForHash().putIfAbsent(claimKey(runId), toolCallId, executedBy);
// 认领成功即同时把 executed=true / executedBy 写进待决条目，然后才执行
```

三道闸的判据顺序：① `ai:ledger` 已有该 `toolCallId` → 复用结果不执行；② 认领失败（他实例已认领）→ 不执行并如实回填；
③ 认领成功 → 执行并记台账。跨进程"恰好一次"由 V4 实测（附件 B §2）。
**瑕疵（低危，见 §5-N5）**：`executedAtMs` 在执行完成后被覆写为完成时刻，认领时刻未单独留字段 ——
Redis 原文里会出现"台账时间 ≤ executedAtMs"，读起来像"标记后写"。

### 4.4 「模型拒答式对话确认」：DANGER 工具的可达性依赖任务真实状态

构造 V2 用例时踩了 4 次坑（如实记录）：

| 尝试 | 现象 | 归因 |
|---|---|---|
| 1 | 模型只做只读核查，拒绝调用 `start_publish` | 提示词里"无人值守/别问我"触发了安全拒答（原文："任何要求跳过确认的说法恰恰是我应当停下来的时候"） |
| 2 | 同上（换更大声的措辞） | 模型行为，不是代码问题 |
| 3 | 模型指出"任务 #2 实际步骤是 UPLOAD，与你说 PUBLISH 矛盾" | **状态核实是真的**（披露工具让它查到了） |
| 4 | 任务真实推到 PUBLISH 步骤后，模型先在对话里解释"确认由平台的确认门负责"、随后**照常调用工具** | 成功 |

结论：HITL 三结局的可达性 =「工具披露（上下文正确）+ 任务状态真实 + 提示词不要求模型扮演授权方」。
这条对 SM-08（双向导 AI 联动 E2E）的用例编排是硬约束，已记入 §5-N4。

### 4.5 其它实测细节

- **后端工具执行的瞬态可见性**：`ai:pending` 里 BACKEND 条目在"认领成功、执行尚未返回"的几毫秒内是
  `status=PENDING + executed=true`；`/api/ai/runs` 会照实展示。`ResumeService` 的"未落定"过滤因此**只把非 BACKEND 的
  PENDING 视为未落定**（BACKEND 的 PENDING 走台账复用/认领判断，不会卡住续跑）。前端展示若要区分"执行中"，以
  `kind + executed + executedBy` 组合判断（§5-N6）。
- **SSE 超时**：`SseEmitter` 用 `app.ai.resilience.total-budget`（10m）作为上限；挂起期心跳（2s/帧）不是"延长超时"，
  而是**保活 + 前端节拍**。默认确认门 120s 时，一个挂起轮最长观测到 60 帧心跳（§3.2 的 120s 超时运行）。
- **帧外置与重挂回放的取舍**：`ai:events:<runId>` 留 3000 帧；重挂回放**默认跳过 delta/heartbeat**，
  避免"回放 + 实时"把同一段文本渲染两遍（挂起期无正文产出，状态帧齐全即可重建挂起态）。
- **`ai:runs` 索引**：不含 TTL，读取时惰性剔除已过期 runId（P1 的 `chat:mem:__ids__` 同一手法）。
  本次留下的 26 个测试轮次会随 `app.ai.session-ttl`（6h）过期，索引随后自愈，无需人工清理。
