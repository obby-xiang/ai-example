## 逐条评议

**D1 守卫单点下沉 —— 采纳。** 与红队 MAJOR-2 建议（`createAndStart` 加终态守卫）同款；该方法是 REST `POST /api/tasks/{id}/jobs` 与 AI 四件 start_\* 的共同入口（JobService.java:62 注释自证），单点下沉可同时封住两条通道并覆盖未来调用方。范式 A（落库前抛、参照 `assertNoJobInFlight` :113-122）正确：被拒请求不留 PENDING 行，不会反钉互斥守卫。**前提**：终态判定口径须按 D2 修正案（见下）。

**D2 终态集 —— FAILED 放行部分采纳；COMPLETED 一刀切部分驳回，须修正。**
- FAILED 放行**不构成洞**，采纳。理由：①FAILED 来源是作业失败或僵尸恢复（StaleJobRecoveryRunner:68），语义即"可恢复重试"，与前端 `isCurrentTaskReadOnly` 对 FAILED 返回 false 同口径；②IMPORT/PUBLISH 即便在 FAILED 任务上发起，仍受 `assertPrecheckPassed` 从严闸约束，无绕行只读的实质写口；③若把 FAILED 也拒，僵尸恢复后的任务被永久钉死，违背"到终态即可再发起"的既有互斥语义。残余风险（可接受，建议补测钉住）：FAILED 任务可能处于条目归零的不一致快照，EXPORT 重跑无害；应在 D8 补 FAILED 任务上 start_\* 放行正向用例。
- **COMPLETED 一刀切是本卡最大漏项，驳回现口径**。实测态机：`PrecheckJobRunner:268` 预检查 0 错误 → 作业 COMPLETED → `JobTerminalWriter:84 applyJobOutcome` → **任务即置 COMPLETED**；而前端 workspace.ts:341-343 注释明说"导入侧预检查 0 错误即置 COMPLETED，但流程仍可继续"。即 **IMPORT 任务在预检查通过后就挂 COMPLETED 状态，随后的 start_import 是主路径**。若 D1+D2 按字面实现，导入流程在预检查后被 TASK_FINALIZED 掐断；D4 的 goToStep 状态守卫同样会把"预检查后跳导入执行步"这一正常操作拒绝。修正案：终态判定不能只看 Task.status，须与前端 `isCurrentTaskReadOnly` 同口径**按类型核最终作业**——IMPORT 任务仅当最近一次 PUBLISH 作业 COMPLETED 才算终态（IMPORT 作业成功不置任务终态，ImportJobRunner 无 updateStatus，实测核实），EXPORT 任务当 EXPORT 作业 COMPLETED；CANCELLED 维持按任务状态拒绝（取消是用户明确意志，重开应走新任务）。该口径应在 D8 补测用例中双向覆盖：终态拒建 + 预检查后 COMPLETED 任务上 start_import 放行。
