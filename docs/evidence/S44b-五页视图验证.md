### V3 附带：**发现并修复一处会导致导入数据全错的缺陷（ExcelIO 保存注入水印表）**

- 现象：用 SpreadJS **评估版 ExcelIO `save()`** 生成的 xlsx，工作簿首位被插入一张**可见**的 `Evaluation Version` 表；而后端 `ExcelReader#findDataSheet` 取「第一个非 `_` 前缀且未隐藏的表」→ 读到水印表：
  ```
  # 用 ExcelIO 保存的文件上传后预检查
  task 5 / job 11 PRECHECK → FAILED, errorCount=8, 3/3 行
  issues: 行 2 必填字段 [货币代码] 不能为空 / 行 2 必填字段 [对人民币汇率] 不能为空 / 行 3 主键重复…
  ```
  即把 `Powered by Spread.Sheets.` 等三行水印文本当成了数据行（8 条校验错误）。
- 修复（`<MAIN_V2>/frontend/src/utils/excel.ts`）：**写路径不再用 ExcelIO**，改为 `buildRowsXlsxBlob()` 自产最小 OOXML（JSZip 打包）：数据表（表头 + 数据，必填加 `*`，数值按字段类型写数字）+ 隐藏 `_dict`（ENUM 选项）+ 隐藏 `_meta`（`def_code` + 字段编码），与后端 `ExcelTemplateBuilder` 同形；读路径仍用 ExcelIO（`open` 不受影响）。
- 复测：同一份内容 → 预检查 `task 2 / job 2 PRECHECK → COMPLETED, errorCount=0, 1/1 行`；openpyxl 读回 sheet 顺序 `[货币字典 visible, _dict hidden, _meta hidden]`（无水印表）；导出的结果表格仍能被 ExcelIO 正常打开（截图 `main-25-export-step3-final.png`）。
- 附：本修复同时消除了对 4.7MB ExcelIO 保存能力的依赖（写 xlsx 只需 JSZip）。

## V5 发布冲突按 Q4 异步形态展示（作业 FAILED + issues 文案）

构造（真实并发场景）：任务 A(#3) 导入 `9.11` 并完成 IMPORT（暂存快照 = 发布行版本 3）→ 任务 B(#4) 导入 `9.22` 并**先发布**（发布行版本 → 5）→ 回到任务 A 点「确认发布」。

实测（截图 `main-16-conflict-q4.png`）：

```
发布冲突（异步形态）：发布冲突：行 CNY 在导入后被其他操作修改（快照版本 3，当前版本 5），请重新导入后再发布
作业 #10 终态 FAILED；冲突行：CURRENCY#CNY。发布请求本身已受理（201），请按提示重新导入后再发布。

JobProgress: 失败 | 1 / 1 | CURRENCY 成功 1/1 失败 1 | 说明：发布冲突：行 CNY 在导入后被其他操作修改（快照版本 3，当前版本 5）…
ElMessage: 发布未成功：请查看冲突明细后重新导入再发布
```

核对点：
- 前端**没有**把发布当同步请求判错：`POST /tasks/3/jobs` 返回 201 且界面照常进入「作业执行中」，冲突仅在终态拉取后呈现（`watchJob` 的 `onFinal` → `GET /jobs/10/issues` → `buildPublishConflict()` 组装 `PublishConflictAsync`）；
- 冲突证据链完整：作业终态 FAILED（`GET /api/jobs/10` → `FAILED`）+ 行级 issues（`rowIndex/fieldCode/message` 展开可见）+ 冲突行 key（`defCode#rowKey`）；
- **刷新不丢**：重新加载 `/import?taskId=3` 后 `resumeJobs()` 读到最新 PUBLISH 作业为 FAILED → 冲突卡与问题明细照常呈现（截图 `main-17-conflict-reload.png`），任务 tag 显示「已失败」（与 `GET /api/tasks/3` 的 `status=FAILED` 一致）。

**结论：通过**。
