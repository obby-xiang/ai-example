## 3 一批多 toolCall 的请求帧流（实证）

**源码事实**（`SpToolCallingManager.executeToolCalls` :261-331）：`suspended` 帧只在进入循环前发**一次**（:263，`toolCalls[]` 列出本批全部条目），随后**逐条** `for (pending : pendings)` → `awaitConfirm/awaitFrontend`（:302-303）——即**每个 await 各自发自己那张卡的请求帧**，然后各自阻塞等人。

**因此实际帧流（两卡批次）**：

```
suspended[card-1, card-2]  → tool_start(card-1) → confirm_request(card-1) → 〔本连接被 complete〕
  （用户决策 card-1）
confirm_decision(card-1) → tool_start(card-2) → confirm_request(card-2)   ← 此刻零订阅者，只落档
  （前端 ?lastSeq 重连 → 差量回放补齐上面三帧）
  （用户决策 card-2）→ tool_result(card-2) → … → done
```

**结论**：断连点在本 await 的请求帧之后，所以**任何一张卡的请求帧都发在"该帧之前"的断连点之后**，不存在被截断的卡；第 2 张卡的卡面由"决策后重连 + 差量回放"送达（正是前端 B1 的恢复路径）。`suspended` 帧里已列出全部条目，第 2 张卡在前端另有 `suspended` 帧承载的占位段，不会出现"卡凭空消失"。

**用例锁**：`SuspendDisconnectGateTest.everyCardRequestFrameSurvivesTheSuspendDisconnect`（真实 gate/emitter/store + 两卡批次 + 决策线程）断言：①卡 1 请求帧投递后 `subscriberCount()==0`；②零订阅者期间归档出现第 2 张 `confirm_request`；③`replayAndAttach(lastSeq=卡1后最大号)` 的差量回放恰好含 `confirm_decision`/`tool_start`/`confirm_request(call-2)`；④两卡都决策后整批结算、归档里 `confirm_request` 恰 2 帧。

## 6 偏差、取舍与留痕

1. **`frontend/src/api/sse.ts` 属必要改动（超出卡片点名的 7-10 条，但为裁决 8 的必要实现点）**：`streamChat` 原逻辑在"未收终帧即关流"时**自动 `tryReattach`**；若不改，挂起断连会在 1ms 后由客户端自己重连并挂住（还白吃 2s 心跳），"挂起期不占连接"直接失效，`send()` 也不会在挂起时收尾（`onClose` 永不触发）。故新增 `StreamState.awaitsInput`（仅由卡面请求帧置位）→ 挂起收流走 `finish(false, …)`、`suspended=true`；`reattach().scheduleReconnect` 同判据**不重连**。两条负控制用例锁住"普通断流仍自动重挂"。
2. **挂起收流时不封口消息**（`send().finally` 的 `target.done=true` 在挂起收流时跳过）：为保持与流派 A 相同的"气泡仍在流式"观感（本批禁动样式/位置），终帧到达由 `handleFrame` 既有路径封口。卡片未点名此项，登记为**实现取舍**。
3. **`stop()` 之后不再重连**（裁决 10 只要求发 POST cancel + 清态）：因此"挂起中停止"后本地确认卡仍会停留为待决（后端已取消，刷新或再次操作时由既有 409/`syncGateFromAuthority` 路径收敛）。加一次重连会把 `loading` 重新点亮、与"停止即空闲"相悖，故不加；**登记为已知残留**，建议下批评估（如需收敛可在 `cancel` 成功后拉一次 `runs/current` 就地落终态）。
4. **`scripts/verify-e2e.ps1` 零改动（审后结论）**：`Read-Sse`（:230-276）以 `$stopOn` 命中即 `break` 并 `Dispose`（:263 break；:270-274 finally 三 Dispose）；`Invoke-AiTurn`（:281-334）与 `Invoke-FormTurn`（:1233-1262）在 stopOn 之后一律用 `GET /api/ai/events/{runId}?lastSeq=N` **续读**，且每个 suspension 分支都 POST 决策/回灌后重新读流 —— 即脚本本就按"关流即正常收尾、决策后 lastSeq 续读"编写（TC23 :2196 注释原文："Read-Sse 在 confirm_request 处早退并 Dispose —— 即整页刷新形态"）。所有 chat 流的 stopOn 均含 `confirm_request`/`frontend_tool_request`（:289/:293/:2103/:2184 等），无"依赖连接存续"的点。delta 入档后受影响的只有 delta 相关断言，且它们本就被降级为 INFO（:1567/:1750/:1851）或"至少 1 帧"（:1116）。**唯一不会自动变绿的风险**：若某用例断言"全量回放里没有 delta"，现在会看到 delta —— 全量 grep 无此断言。本棒**不运行 E2E**（需服务）。

### 7.1 C-1（Critical）修法：轮次判据由 controller 引用改为**轮次纪元**

- 缺陷链（复审 §5 C-1）：`frontend_tool_request` → `handleFrame` 起 `runFrontendTool`（`stores/ai.ts`），入口捕获 `currentAbort`；服务端在请求帧之后立刻收流 → `send()` 的 `finally` 把 `currentAbort` 置 `null`；当工具 resolve 晚于收流时，旧判据（`currentAbort !== controllerAtStart`）判真并直接 `return` ⇒ **不写段终态、不发回灌 POST**，段恒 `running`，后端只能等满 120s 前端工具上限。波及 6 个非 GF FRONTEND 工具（`navigate_to` / `select_definitions` / `set_condition` / `confirm_step` / `open_export_file_editor` / `download_export_files`）。
- 修法：新增模块级 **`roundEpoch`（轮次纪元）**——只在**真正换轮**时递增：
  - `send()` 起新轮（新用户消息 / 编辑重跑 / 重试）；
  - `reattachActive()` 重挂到既有轮（新连接接管）；
  - `adoptFreshSession()` 换会话（新建对话 / 复制页签 / reset）；
  - `stop()` 取消本轮。
  `runFrontendTool` 入口捕获 `epochAtStart`，`executeFrontendTool` 返回后比对 `roundEpoch !== epochAtStart` 决定是否丢弃晚到结局。
  落点：`frontend/src/stores/ai.ts:75`（`roundEpoch` 声明与口径注）、`:1474`（`send()`）、`:1673`（`reattachActive()`）、`:2267`（`stop()`）、`:2320`（`adoptFreshSession()`）、`:3027`（捕获）、`:3053`（守卫）。
- 为什么不是"保留 controller"：挂起收流（`StreamCloseInfo.suspended` → `suspendedClose`）与决策后的**同轮重连**（`resumeSnapshotStream` 换新 controller）都不属于换轮——若按 controller 引用判，用户先决策重连、慢工具后返回时仍会被误杀；若"挂起时不置 null"，则 `stop()` 后旧回复灌窗口被无限拉长。纪元只随换轮变化，两种误判同时消掉。
- 不放过 true positive（复审点名）：用户已发新消息起新轮（③）、`reattachActive` 重挂 / 换会话 / `stop()` 之后（④），旧工具结局仍**丢弃**——不写段终态、不回灌，防向新轮或已取消轮回灌。
- 写段/回灌落点不变：`upsertToolPart(status=succeeded/failed/unknown)` → `deriveProjections` → `submitFrontendToolResult`（POST 成功后照常触发 `reconnectSuspendedRun` 带 lastSeq 重连）。
