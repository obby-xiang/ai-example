### 2.1 ⑤ 的事务模型（本次最关键的结构变化）

```
执行器（@Transactional，数据面：暂存行/已发布行/校验问题/任务条目）
├─ progressService.markRunning(jobId)        REQUIRES_NEW ──┐  快照通道（独立连接/独立事务）
├─ 分片边界：progressService.snapshot(行级)   REQUIRES_NEW ──┤  一写即提交 ⇒
├─ 分片边界：progressService.updateItem(...)  REQUIRES_NEW ──┤  列表/详情/SSE 权威通道立即可见
└─ 方法返回 ⇒ 数据面事务提交
             └─ afterCommit: JobTerminalWriter.complete(...) ── REQUIRES_NEW
                     ├─ progressService.finish(终态+行级进度)
                     ├─ taskService.applyJobOutcome(任务态联动 ⑥)
                     └─ taskSseService.publish(JOB_DONE)
```

两条硬约束（都由实测逼出来，非推断）：

1. **执行器自己不得写 jobs/job_items 行**：否则外层长事务持有该行锁，`REQUIRES_NEW` 的写入会撞锁；快照通道要求这两张表只有一个写入者。
2. **终态写入整步必须 `REQUIRES_NEW`**：`afterCommit` 处于"旧事务已提交、资源仍绑定本线程"的临界态，此时用 `REQUIRED` 打开的业务写入会**静默加入那个已完成的事务而不落库**。首轮实测即踩到：作业行的终态与 `finishedAt` 写进去了，任务行 `version` 仍为 1、状态仍 ACTIVE（V3 首轮）。已修为整步 `REQUIRES_NEW`，并留回归用例 `terminalWriteRegisteredInAfterCommitStillLands`。

## 6. 与规格/基座的一致性说明

- PublishJobRunner 的数据面语义（行级 upsert / 范围差集删除 / baseVersion 快照文案 / 整批回滚）**逐字保留**，仅把作业行与条目的状态写入移出数据面事务；S4.3a 的 4 个用例在本次改动后仍全绿（V1）。
- `:kw = ''`、`CAST(t.id AS string)`、type/status 过滤等既有检索语义未变，仅在 LIKE 处加 `ESCAPE` 与入参转义。
- `JobCancellationRegistry.cancel()` 与 `JobService.cancel()` 的签名变化只影响 `JobController`（AI 工具未调用取消路径，`ai/` 包零改动）。
