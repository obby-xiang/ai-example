## 1. 问题清单（逐条编号）

### 问题 1【严重】收敛契约②「轮次上限」在"消息长度不增"场景被系统性绕过；自检④的收敛自证恰好不覆盖该形态

- **证据等级**：【实测】（复现步骤见下）+【推断】（影响分析）。
- **代码位置**：`<REPO_ROOT>/scripts/ci/stub-upstream.mjs:277-282`（"同一提示词的新轮次：消息数回退即视为新轮次，台账清零"——同时清零 `bucket.calls` **与** `bucket.used`）、`:290`（`bucket.calls > maxCalls` 上限检查）、`:304`（`bucket.used.includes(route.id)` 每路由一次检查）。
- **实测复现**【实测】：
  1. 起桩（端口 18399，`<RT_DIR>` 为 dump 目录）。
  2. 对同一 prompt（`scenario=FILTER` + 唯一标记）连续发 **8 次**结构完全相同的请求（`[system,user]`，长度恒为 2，`tools[]` 含 `generative_form`，无 `role=tool`）。
  3. 结果：**8/8 全部发出 `tool_call`**——`maxCallsPerTurn=6` 从未生效。原因：每次请求 `messages.length(2) <= bucket.lastLen(2)` 成立 → `calls` 与 `used` 双双清零 → 路由重新可用、计数从零开始。
  4. 对照实验（同 fingerprint、消息长度**递增**、无 `role=tool`，8 次）：第 1 次请求 `tool_call`，第 2 次起**全部文本收尾**——因为 `bucket.used` 已含该路由 id（`:304`），即递增场景下实际是"**每路由仅 1 次**"，比自检声明的"≤6"更严格。
- **为什么这是自证盲区**：`--self-check` 第④项（`stub-upstream.mjs:540-565`）的模拟循环是**每次向 messages 追加一条 tool 消息**（长度递增形态），从不构造"长度不变/回退"的重复请求——而后端 `ResilientChatService` 流失败重试时**原样重发同一请求（长度不变）**，恰好落进绕过侧。
- **影响分析**【推断】：后端重试受 `max-attempts=2` 与 `total-budget=300s` 约束，CI 又有 `timeout-minutes: 25` 兜底，故**不构成请求风暴的实际通路，更不构成假绿**（桩若反复发工具调用，用例会以 FAIL/超时变红）。真正的问题是：①证据文档 §3.1"[PASS] 收敛自证通过"与 §0"收敛自证"表述的覆盖面不完备——裁决 #5 把"自带 `--self-check` 契约自检"定为硬要求，收敛自证是其中一项，它对"长度不变重发"（后端重试的真实形态）没有证明力；②重试场景下桩会**重新发起工具调用**，DANGER 工具在确认门挂起（无重复执行）、BACKEND 通道工具会被重复执行（幂等性由产品侧承载，桩不保证）。
- **建议**：自检④补一条"长度不变重复请求"的形态（断言 `calls` 不被重置或改用按 `tool_call_id` 去重的台账）；或把台账键改为"fingerprint + 首条消息的 tool_call 幂等键"。是否修属指挥官裁决。

### 问题 2【严重】桩进程在一次异常输入攻击序列后静默死亡、无崩溃痕迹；桩无任何异常兜底是结构性根因（死亡本身未复现，如实标注）

- **证据等级**：【实测】（死亡事实与时间戳）+【推断】（根因归属）；**未复现**（三轮定向复现均存活）。
- **实测事实**【实测】：
  1. 本队第一轮攻击序列（简单请求 ×9 → 30 并发 → 3 次 50ms 客户端中断 → 端口占用测试 → 5MB body 请求）后，桩进程死亡：`netstat` 无 LISTEN、进程消失、后续请求空响应。
  2. 时间戳定位：dump 目录最后一条 `req-048.*`（恰为 5MB 请求）与桩 stdout 日志的 mtime **同为 15:41:16.621**，即桩完整处理并记录了该请求（含 `[req-048]` 日志行），随后约 1 秒内死亡；**日志中无任何崩溃栈**。
  3. 定向复现三轮均**未**再现：①单独 5MB 请求（存活）；②5MB + 10 次 30ms 中断 + 5 次发送中途 RST（存活，且桩仍正常记录与响应）；③精确重放第一轮序列"3 次中断 → 端口占用崩溃测试 → 5MB"（存活）。同期以完全相同方式启动的另一实例（违规模式，端口 18398）全程存活——排除环境性清理。
- **结构性根因**【推断】：`stub-upstream.mjs` 的 `startServer()`（`:431-455`）**没有** `process.on('uncaughtException')`、`server.on('error')`、`req.on('error')` 任何一层兜底；任何未捕获异常都会击杀整个桩进程。且 CI/workflow 用 `nohup … > stub.log 2>&1 &` 启动，stdout 进入**全缓冲**模式——进程被异常击杀时缓冲区不落盘，崩溃栈丢失，桩"死无对证"。本队第一轮的死亡无痕与此一致。
- **CI 影响**【推断】：方向 fail-safe（桩死 → 上游连接拒绝 → 后端重试耗尽 → 用例 FAIL → 门禁红），**不构成假绿**；但归因会误导：`boot.log` 呈现 `WebClientRequestException: Connection refused`，首屏结论像"环境/网络故障"，而真正的"桩进程崩溃"证据（崩溃栈）因缓冲丢失不可得，`req-*` dump 停在死亡点。这正是设计草案 R1"归因耗时"风险的又一形态。
- **建议**：桩加 `process.on('uncaughtException')`（记录后 `process.exit(1)`）与 `server.on('error')`；workflow 的桩启动行改为 `node … 2>&1 | tee -a`（或启动时 `NODE_OPTIONS`/定期 `console.error` 触发 flush）以保证崩溃栈落盘。是否修属指挥官裁决。

### 问题 4【建议】自检③的"白名单对账"对账对象是桩内副本而非产品事实源，且副本缺 5 项上限——产品侧白名单收紧时自检仍绿

- **证据等级**：【实测】（对账 + 副本缺口清单）。
- **证据**：`stub-upstream.mjs:62-68` 的常量（`FIELD_TYPES`/`SCENARIOS`/`FORM_ATTRIBUTES`/`FIELD_ATTRIBUTES`/`OPTION_ATTRIBUTES`/`PLACEHOLDER_TYPES`/`FORBIDDEN_KEYS`/`KEY_PATTERN`）是 `GenerativeFormRules.java:67-115` 同名常量的**手工副本**，自检③（`:504-537`）用它校验路由表模板。本队逐常量对账：**当前 8 组内容与产品侧逐字一致**（含禁键三兄弟与 `^[A-Za-z_][A-Za-z0-9_]{0,39}$` 正则）——施工棒交付时点无失配。
- **盲区**：①若产品侧将来收紧白名单（新增禁属性/改正则），桩自检不知道，仍绿——失配要到运行期以 `FORM_SCHEMA_REJECTED` → SKIP → 门禁红才暴露（可检测，但自检声明"对账通过"会给人以"已对过产品"的错觉，证据文档 §3.1 的表述应加"经桩内副本"限定）；②副本缺 5 项上限：`title ≤ 100`、`options ≤ 50`、`option value ≤ 100` 且不得重复、`placeholder ≤ 100`、`form 序列化 ≤ 8000` 字符——模板被改坏超出这些上限时自检不报（当前模板远低于各上限，无实际暴露）。
- **建议**：自检白名单从副本改为读取 `GenerativeFormRules`（需后端暴露常量或测试期生成 JSON），或至少在桩文件头注明"副本，升级棒次必须与事实源手工对账"（设计草案 R5/R9 已有同向要求，此处是把它落到桩自检层面）。

### 问题 5【建议】GFSKIP 摘要文案与桩模式零容忍分支语义矛盾

- **证据等级**：【实测】。
- **证据**：`<REPO_ROOT>/scripts/verify-e2e.ps1:2182` 摘要行仍写"GFSKIP={0}（模型未触发 SKIP，**不计退出码**；GF1–GF4 全部 SKIP 判整棒 FAIL，裁决 #1）"，而 `:2186` 新分支在 `E2E_STUB_MODE=1` 时 `GFSKIP≥1` 即 `exit 1`。CI 桩模式下一旦出现 SKIP，日志先打印"不计退出码"再以退出码 1 结束，会误导排查者。
- **建议**：摘要行按 `E2E_STUB_MODE` 分支措辞，或补一句"桩模式下 GFSKIP≥1 即整棒 FAIL"。属文案级，不改判定。

### 问题 6【建议】workflow 两处冗余/隐式依赖（不构成错误）

- **证据等级**：【实测】（读码 + YAML 解析）。
- ① `ci.yml:170-176`"运行 E2E"step 声明 `shell: pwsh` 且 `run` 内容又以 `pwsh -NoProfile -File …` 开头——双层调用。功能正确（外层 pwsh 模板会把 `$LASTEXITCODE` 透传为 step 退出码，实测语义成立【推断，基于 GitHub 官方 shell 模板行为】），但冗余；若哪天有人把 `shell` 改成 `bash`，反引号续行符立即失效，是个埋雷点。
- ② e2e job 无 `setup-node` 步骤，依赖 `ubuntu-latest` 预装 Node（桩为纯 ESM 零依赖，当前预装版本可用【实测：本机 Node 22 运行正常】）。镜像迁移（R7 已知风险）时 Node 版本不受控。
- **建议**：二选一：去掉 `shell: pwsh` 或去掉 run 内的 `pwsh` 前缀；可加一行 `setup-node` 固定版本。

### 问题 7【建议】就绪门 grep 依赖 Jackson 无空格序列化形态

- **证据等级**：【实测】（当前形态匹配）+【推断】（脆弱性）。
- **证据**：`ci.yml:159` 用 `grep -q '"redis":{"available":true'` 判定就绪，依赖后端 `/api/ai/health` 的 JSON 序列化**不含空格**（当前实测/证据自报原文均无空格，匹配成立）。若后端将来改 Jackson 缩进/空格配置，就绪门会持续失败——方向 fail-safe（红，不绿），但表现为"环境坏"假象。
- **建议**：可改为 `grep -q '"available":true'` + 独立 `grep -q '"failures"'` 或 jq 判定。低优先。
