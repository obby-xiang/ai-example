## 3. types/ 与后端字段核对记录（逐个 DTO）

核对方式：直接读后端源码（实体 + 控制器 + record），并用仓库内**真实响应原文**证据交叉验证（比读注解更硬）。

| DTO / 契约 | 后端来源 | 核对到的真实字段 | 结论 |
|---|---|---|---|
| `ApiResponse<T>` | `common/ApiResponse.java` | `success`(bool) / `message` / `code` / `data`，`@JsonInclude(NON_NULL)` | ✔ 一致；前端信封判定用 `typeof success === 'boolean'`（AI 端点裸对象无该字段） |
| `PageResult<T>` | Spring Data `Page`（`W3-附件-分页与过滤-请求响应原文.json`） | `content, totalElements, totalPages, number, size, numberOfElements, first, last, empty`（另有 `pageable/sort` 未用故未声明） | ✔ 一致（真实原文逐键比对） |
| `ConfigDefinition` / `ConfigField` | `definition/entity/*.java` + `G2-附件-A-15定义API原文.json` | 定义：`id,code,name,level,description,sortOrder,fields,createdAt,updatedAt`；字段：`id,defCode,code,label,fieldType,required,sortOrder,optionsJson,refDefCode,refFieldCode,**key**` | ✔ **Q3 根治**：真实原文里是 `"key":true`，**不存在 `isKey`**（Lombok `isKey()` → Jackson 去 `is` 前缀）；`optionsJson` 是**字符串/ null**（不是数组，故提供 `parseFieldOptions`） |
| `Task` / `TaskItem` / `TaskFile` / `TaskSummary` | `task/entity/*.java`、`task/controller/TaskSummary.java` + `W3` 原文 | Task：`id,type,title,currentStep,status,settingsJson,version,items,createdAt,updatedAt`；TaskItem：`id,taskId,defCode,sortOrder,conditionJson,status`；TaskSummary：`task,itemCount,fileCount,latestJob` | ✔ 一致；`settingsJson/conditionJson` 是 **JSON 字符串**（不是对象），故给 `readImportMode()` 做安全解析 |
| `Job` / `JobItem` / `ValidationIssue` | `job/entity/*.java`、`JobProgressService` + `W3` 原文 | Job：`id,taskId,jobType,status,progress,total,errorCount,warningCount,resultJson,items,createdAt,startedAt,finishedAt`；JobItem：`id,jobId,defCode,status,processed,total`；Issue：`id,jobId,defCode,rowKey,fieldCode,severity,message,rowIndex` | ✔ 一致；**口径确认**：`jobs.progress/total` 是**行级**，`job_items.processed/total` 是**配置项级**（JobProgressService 类注释） |
| `ConfigDataRow` / `ConfigStagingRow` | `data/entity/*.java` | 数据行：`id,defCode,scopeType,scopeKey,rowKey,dataJson,version,createdAt,updatedAt`；暂存行：`id,taskId,defCode,opType,rowKey,scopeType,scopeKey,dataJson,status,baseVersion,createdAt` | ✔ 一致；`dataJson` 同样是字符串（提供 `parseRowData`）；`baseVersion` 为发布并发冲突依据 |
| `Region` / `Project` | `masterdata/entity/*.java` | `id,code,name,createdAt` / `id,code,name,regionCode,createdAt` | ✔ 一致 |
| 时间字段形态 | `W3` 原文 + `G2` 原文 | 实际是 **ISO-8601 带纳秒**：`"createdAt":"2026-10-07T01:12:20.597158"` | ⚠ 与 `JacksonConfig` 里 `@Primary ObjectMapper` 配的 `yyyy-MM-dd HH:mm:ss` **不符**——说明 HTTP 消息转换并未走那个 mapper（见 §5）。dayjs 两种都能解析，展示层不受影响；已在 `utils/format.ts` 注明 |
| SSE 帧 | `ai/run/SseChatEmitter.java` | `start{runId,sessionId}`、`delta{text}`、`tool_start`、`tool_result`、`confirm_request`、`confirm_decision`、`frontend_tool_request`、`frontend_tool_result`、`suspended{toolCalls[],stateKey,pendingKey,writtenBy}`、`heartbeat`、`retry`、`done{cancelled?}`、`error{code,message}` **共 13 类**，帧体是 JSON 且带 `type`（无名事件） | ⚠ 规格 §3 简写的 `tool_call` 实际是 **`tool_start` + `tool_result` 两帧**；另有 `confirm_decision`/`frontend_tool_result`/`retry` 未在规格列出。已按**后端实测帧集**定义判别联合（13 类全收），并在 `types/sse.ts` 头部记录该差异 |
| `PendingToolCallSnapshot` | `ai/run/PendingToolCall.java#asMap` | `toolCallId,name,type,kind,arguments,status,reason,resultText,executed,executedBy,claimedAtMs,executedAtMs,requestedAtMs,resolvedAtMs` | ✔ 一致；`status` 取值 `PENDING/APPROVED/REJECTED/TIMEOUT/FRONTEND_RESULT/CANCELLED/EXECUTED`，`kind` 取值 `CONFIRM/FRONTEND/BACKEND` 已入类型 |
| `AiChatRequest` / `AiChatContext` | `ai/web/AiChatRequest.java`、`ai/tool/AiContext.java` | `sessionId,message,context{page,taskType,step,taskId,extra}` | ✔ `buildContext()` **严格只发这 5 键**（多余信息进 `extra`）；原文证据里出现过 `"context":{}`（`S42-P1-附件-上游请求矩阵.txt`），说明各键均可缺省 |
| `ConfirmRequest` / `ConfirmResult` | `ai/web/ConfirmRequest.java`、`AiController#confirm` | 请求：`runId,toolCallId,approved,reason`；响应（**裸对象**）：`accepted,duplicate,runId,toolCallId,status,approved,reason,executed,wokeInProcessGate,storedBy,note` | ✔ 一致；HTTP 层**不套 ApiResponse**（`http.ts` 的 `isApiResponse` 守卫已容错） |
| `FrontendToolResultRequest` / `Ack` | `ai/web/FrontendToolResultRequest.java`、`AiController#frontendToolResult` | 请求：`runId,toolCallId,result,source`；响应：`accepted,duplicate,runId,toolCallId,status,executed,wokeInProcessGate,storedBy` | ✔ 一致 |
| `AiHealth` | `AiController#health` | `available,code,model,baseUrl,memoryBackend,sessionTtl,confirmTimeoutSeconds,suspendPoolSize,activeSuspendGates,heldSessions,sessionLockRenewals,resumeOnStartup,instanceId,checkedAt,message?,redis,resilience,cancellations`；不可用时 **503 + 同一个体** | ✔ 一致；故 `api/ai.ts#health` 把 503 当**正常返回**处理（只有网络异常才 reject） |
| `AiHistory` | `AiController#history` | `{sessionId,count,messages:[{type,text,toolCalls?,toolResponses?,timestamp?}]}` | ✔ 一致；`type` 是 Spring AI 的 `MessageType` 名（USER/ASSISTANT/TOOL/SYSTEM），前端映射为展示角色 |
| 错误码 | `AiController`（各 409/503 现场）+ `job/service/JobService#cancel` + `common/GlobalExceptionHandler` | 规格点名 5 码之外，实测另有 `DUPLICATE_TOOL_CALL_ID`、`UNKNOWN_TOOL_CALL`、`UNKNOWN_RUN`、`BAD_REQUEST`、`AI_RUN_FAILED` | ✔ 共 10 码入 `ErrorCode`（前 5 个是规格点名码，其余为**实测附加码**，已分组注释） |
| 工具契约 | `ai/tools/AiTools.java` + `ToolScope/ToolRisk/ToolChannel/ToolMeta` | 12 个工具：2 个 `FRONTEND`（`open_export_file_editor`、`download_export_file`，scope `task:EXPORT/EXPORT`）+ 10 个 `BACKEND`（含 `start_publish` = `DANGER` 走确认门） | ✔ `types/tools.ts` 头部逐条抄录 name/scope/risk/channel；前端只描述 2 个前端工具（后端工具由后端披露） |
| 发布冲突异步形态 | 规格 Q4 + `JobController#getIssues`、`JobService#cancel` | 发布恒 201；冲突 = 作业 `FAILED` + `GET /api/jobs/{id}/issues` 文案 | ✔ 类型 `PublishConflictAsync`（jobId/jobStatus/issueKeys/message）+ `task store#watchPublishOutcome`（等终态→查 issues→组装），**不按同步错误处理** |
| 操作流水 | `task/service/TaskService#delete` 注释 + ADR-11b | 无 `AuditLog` 表；当前只有结构化日志行 + `TASK_CHANGED` 事件的 `summary` | ⚠ 前端 `OperationLogEntry` 是展示形态定义；落库表属 DC-10 P2 → 见 §6【待裁决】 |

**结论**：除 3 处「规格简写 vs 后端实测」的差异（SSE `tool_call`→`tool_start/tool_result`、时间格式 ISO、错误码附加 5 个）外，契约层与后端**逐字段对齐**；Q3 的 `key`/`isKey` 已用真实响应原文根治（`"key":true`）。

## 5. 与规格书 / 任务书的差异与修正

1. **SSE 帧名**：规格 §3 写 `tool_call`，后端实际是 `tool_start` + `tool_result` 两帧（另有 `confirm_decision`/`frontend_tool_request`/`frontend_tool_result`/`retry`）。types 按**后端实测 13 类**定义，未按规格简写臆造帧名。
2. **通道形态**：`POST /api/ai/chat` 是 POST + `text/event-stream`，`EventSource` 只支持 GET → `api/sse.ts` 实现**两条通道**：`streamChat`（fetch + ReadableStream 自解 SSE）与 `reattach`（EventSource）。两者共用同一帧解析器与终帧校验（缺 `done`/`error` → 判断流 → 有 runId 则 reattach，仍失败按 ADR-6 提示）。
3. **日期格式**：实测 HTTP 输出为 ISO-8601 带纳秒，而非 `JacksonConfig` 里那个 `@Primary ObjectMapper` 配置的 `yyyy-MM-dd HH:mm:ss` —— 说明 HTTP 消息转换未走该 mapper（实体的 `@Primary` 与 Web 层两套并存）。前端展示层对两种格式都能解析；若后端后续统一日期格式，前端无需改动。
4. **代理默认值**：本棒任务书提到「/api 代理指向 18315」，而规格 §1 明写默认 `http://localhost:8080` —— 以**规格为准**（默认 8080，可用 `VITE_API_BASE` 覆盖）。联调时若后端端口不同，改 `.env.local` 即可，源码不动。
5. **Element Plus 分包**：蓝本把 element-plus 混在 `vendor` 里；本棒拆出 `element` 分包（1.09MB 独立，便于按需优化）。
6. **`.tmp-esbuild` 而非蓝本的 `.tmp-build`**：仓库根 `.gitignore` 已排除 `frontend/.tmp-esbuild/`，用现成条目可避免改 `.gitignore`（本棒不允许改 `frontend/` 之外的文件）。
