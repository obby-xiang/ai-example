## 2. 四个机制在本棒的落地形态

### 2.1 韧性（`ResilientChatService` + `StreamWatchdog`）

1. **每轮/每次尝试重建请求**：`runAttempts(...)` 接收一个 `IntFunction<Flux<ChatResponse>>`，每次尝试都重新调用它 —— ChatClient 路径重新组装 `.system/.user/.advisors/.toolContext/.toolCallbacks`（流式装配按 1.1.8 身份装配的 4 个自定义 bean 组装，见 S4.2-P1），续跑路径重新构造 `Prompt`。数据点：每次尝试都有独立日志 `本轮第 N 次尝试组装请求`。
2. **双超时 + 总预算**（`app.ai.resilience.*`，初值 30s / 90s / 2 / 300s，标注待 §13.2 #2 压测）：
   - 首包：`upstreamEvents == 0` 时的静默上界（SM-02(e) 实测触发，30s 阈值实例另设 5s）；事件间：已有事件后的静默上界（SM-02(f)(g) 实测触发）；
   - 静默锚点 = `max(最后上游事件时刻, 最后工具活动时刻)`，且**工具活跃期不参与判定**（硬规范①）；
   - 总预算：墙钟上界，同时兜 `CompletableFuture.get(remaining)` 与 SSE `SseEmitter` 超时。
3. **重试三条件**：`次数未尽 && 预算未耗尽 && 本次尝试未产出内容 && 本次尝试无副作用`。
   副作用两侧口径：进程内 `ToolActivityBeacon.startedCount`（尝试前后取差）+ 跨进程 `ai:ledger` 中 `atMs >= 尝试开始时刻` 的条数。
4. **完成帧校验（硬规范②）**：一次尝试的 flux **正常结束**时，必须见过非空 `finishReason`；否则判 `UPSTREAM_STREAM_INCOMPLETE`（TCP 静默 FIN 的形态）。
   实测教训（第一轮就直接踩到并修正，见附件A §2(c) 的末帧序列）：**不能拿 "usage 非空" 当终帧** ——
   ① Spring AI 流式聚合对每个分片都挂 Usage（0/0/0）；② 带工具的一轮里客户端可见的 usage 可能来自**前一个工具轮**，于是"第二轮被静默截断"会被 usage 掩盖。
5. **失败码**：`UPSTREAM_FIRST_BYTE_TIMEOUT` / `UPSTREAM_SILENT_TIMEOUT` / `UPSTREAM_STREAM_INCOMPLETE` / `UPSTREAM_CONNECTION_BROKEN` / `UPSTREAM_STREAM_ERROR` / `TOTAL_BUDGET_EXCEEDED` / `AI_RUN_CANCELLED`；终态错误再按 `_AFTER_PARTIAL` / `_AFTER_TOOL_SIDE_EFFECT` 后缀标明"为什么不能重试"。

### 2.2 取消（`CancellationRegistry` + 端点）

- **权威态**：`ai:cancel:<runId>`（STRING，值 = 发起取消的实例标识，TTL = 2×总预算）。跨实例/跨进程一致；重启后仍能拦住续跑。
- **加速态**：进程内 `AtomicBoolean` + 监听者集合。同进程取消当场唤醒（`wokeInProcess=true`）：看门狗当场断开上游、确认门/前端工具的等待当场解开。
- **轮询点（≤1 分片）**：看门狗每 1s 一拍（等价事件边界）读一次 Redis 标志；`ConfirmGate` 等待循环每 2s 心跳节拍读一次（等价分片边界）。两者都只在"未命中加速态"时才去撞 Redis。
- **降级**：Redis 异常 → 退回进程内标志 + 每 5s 一次的退避重试（避免每拍都阻塞 `spring.data.redis.timeout`），事实写日志与 `GET /api/ai/cancel/{runId}.degraded`。
- **终态**：`done{cancelled:true}`；快照 `CANCELLED`（含 `cancelled=true`、不再取半截 assistant 正文）；该轮未决挂起条目一律转 `CANCELLED/executed=false`（跨进程续跑不会把它执行掉）；`POST /runs/{id}/resume` 返回 `ALREADY_CANCELLED`。

### 2.3 启动自动续跑（N3/N8）

`StartupResumeRunner`：`ApplicationReadyEvent` → 延迟 `app.ai.resume.startup-delay`（默认 8s）→ 扫 `ai:runs` → 对每一轮用**与运维端点同一口径**判定：

| 情形 | 处置 |
|---|---|
| `ai:cancel` 命中 / 快照终态（DONE/FAILED/CANCELLED） | 跳过（`CANCELLED` / `TERMINAL_OR_RUNNING`） |
| 仍有 `PENDING` 的**外部**挂起项（确认门/前端工具未决） | **跳过**（`PENDING_UNRESOLVED`）—— 自动补执行的前提永远是"人已在挂起当时给过决策"，不绕开人审 |
| `SUSPENDED` 且外部输入已决 | 自动续跑 |
| `RUNNING` 且 `updatedAtMs` 超龄 `app.ai.resume.zombie-age`（默认 60s） | **僵尸接管**（`forceTakeover=true`），日志 WARN 记录超龄毫秒数 |
| `RUNNING` 未超龄 | 跳过（保守：可能是另一个实例在跑） |
| Redis 不可用 | 扫描"响亮地失败"：WARN + 报告里带 error，不让启动线程抛异常 |

开关：`app.ai.resume.on-startup`（代码默认 false，本仓 `application.yml` 置 true）；另 `max-on-startup`（默认 10）限制单次启动接管数量。

### 2.4 `claimedAtMs`（N5）

`RunStore.claimExecution` 在 `HSETNX` 认领成功的同一时刻写 `claimedAtMs`（执行**之前**）；`executedAtMs` 只在执行完成后由执行侧写。实测：放行臂 `claimedAtMs=1791313459896 < executedAtMs=1791313459900`（附件A §5(a)），`requestedAtMs < claimedAtMs < executedAtMs` 三时刻不再互相覆写。

### 8.2 R3 验证

**(a) 长流式长轮不被误判（构造：事件持续流动但快照不刷新）**

代理 `mode=drip, dripMs=700`（每事件 0.7s）+ 实例 `--app.ai.resume.zombie-age=20s`，session `s42p3-r3a`：

```
t+26s  GET /api/ai/runs：
{"runId":"3c1e25db-…","status":"RUNNING",
 "snapshotUpdatedAgeMs":26020,        ← 快照已 26.0s 未刷新（> 阈值 20s）
 "activeAtAgeMs":3726,                ← 末帧仅 3.7s 前（流式活动心跳）
 "zombieAgeThresholdMs":20000,"zombieRunning":false,"resumeable":false}

同一时刻 POST /api/ai/startup-resume/scan（强制重扫）：
候选 66 | 受理数 0 | 本轮被受理? false
本轮在跳过列表: [{"runId":"3c1e25db-…","status":"RUNNING","reason":"TERMINAL_OR_RUNNING"}]
→ 活轮未被接管（判据只看快照会判成僵尸并二次执行，见下方反证）
```

该轮随后以 `{"type":"error","code":"TOTAL_BUDGET_EXCEEDED_AFTER_PARTIAL","message":"本轮总预算 PT5M 已耗尽"}` 结束 —— 这是**总预算**机制在"人为把每个事件放慢 0.7s"下的正常收尾，与僵尸判定无关（该轮 203 个 delta、53 帧流式心跳）。

**反证（同一构造，补丁前的构建 `638775a2`）**：

```
t+26s  {"status":"RUNNING","snapshotUpdatedAgeMs":26042,"activeAtAgeMs":25976,
        "zombieAgeThresholdMs":20000,"zombieRunning":true,"resumeable":true}
       → activeAtAgeMs == 快照年龄（当时既没有末帧判据、也没有流式心跳）⇒ 活轮被误判为僵尸
同一时刻强制扫描：受理数 1，本轮被受理? true ⇒ 正在流式产出的活轮被**接管**
```

补丁把这一条堵住了。补丁前的另一条独立证据：一次 drip 轮的 `start` 帧与第一个 `delta` 帧相隔 **57.4s**
（`atMs 1791315445916 → 1791315503361`，模型 reasoning 阶段客户端无正文）—— 正是"快照与帧都长时间不动"的成因，
也是流式活动心跳存在的理由。

**(b) 真僵尸（无事件无刷新超龄）被接管**

session `s42p3-r3b`（runId `20c42629-…`）：drip 流式轮进行中被 `taskkill /F` 杀（快照 RUNNING、快照从未刷新、末帧 = 杀时刻）；

```
WARN ResumeService : 僵尸轮接管 runId=20c42629-… sessionId=s42p3-r3b
     活跃时刻距今 48473ms（快照 121220ms / 末帧 48473ms，阈值 PT20S）
INFO StartupResumeRunner : 启动自动续跑完成：候选 68 轮，受理 2 轮，跳过 66 轮
→ 两个锚点都超龄 ⇒ 判为僵尸并接管 ✓（日志同时打印双锚点，判定依据可复核）
```
