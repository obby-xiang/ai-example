## 1. 逐条复核

### 1.1 P1（严重）收敛契约：清零条件改为严格小于 —— **成立**【实测】

**红队原始攻击**：同 fingerprint、消息长度不变连发 8 次 ⇒ 修复前 8/8 全部 `tool_call`（`calls`+`used` 双重重置绕过两道闸）。

**本队复现（桩端口 18340，仓库外探针脚本直发）**【实测】：

1. **等长 8 连发**（同 prompt、`messages.length` 恒为 2、`tools[]` 含 `generative_form`、无 `role=tool`）：响应序列 `tool_call, text, text, text, text, text, text, text`（HTTP 均 200）——**仅首轮 tool_call，其后 7 轮全部文本收尾**，绕过闭合。
2. **递增形态对照**（同 fingerprint、每轮追加 tool 消息、8 次）：`tool_call, text ×7`——与修复前行为一致，无回归。
3. **原始攻击序列重放**（红队报告问题 2 的触发序列简化重放）：简单请求 ×9（各新 fingerprint，逐一 `tool_call` 属新会话正常行为）→ 30 并发（30/30 均 200，dump 完整）→ 3 次 50ms 客户端中断 → 5MB body（200、正常判定落盘）→ 探活 **200，桩全程存活**，dump 目录 340 份文件完整。
4. **代码核对**：`stub-upstream.mjs` 轮次清零条件现为 `messages.length < bucket.lastLen`（严格小于），等长重发不清零台账；自检新增 ④b 等长重发回归用例（同 fingerprint、`maxCalls+2=8` 次，断言仅首轮 `tool_call` 且总数 ≤ 6）——红队问题 1 的"自证盲区"同时闭合。

### 1.2 P2（严重）异常兜底 —— **成立**【实测】

1. **端口占用路（真实交付物）**：先起桩于 18340，再对同端口起第二实例 ⇒ **退出码 1**；stderr 与 `<RT_DIR> dump/stub-crash.log` **同刻同步落盘** `[FATAL] server.error … Error: listen EADDRINUSE …` 完整堆栈（`fs.writeSync` 同步写出，两处逐字一致）。第一实例不受影响。
2. **uncaughtException 路（仓库外副本注入）**：在仓库外副本桩注入 `/boom-uncaught` 端点（10ms 后 `throw` 异步异常），POST 触发 ⇒ **退出码 1**；`[FATAL] uncaughtException … Error: 合成未捕获异常…` 连同栈同步落盘（stderr + `stub-crash.log`）；端口随即释放——进程**带证据死亡，非静默消失**。
3. **代码核对**：四层兜底齐备（`process.on('uncaughtException'/'unhandledRejection')`、`server.on('error')` 走同一 `crashReport`、`req`/`res` error 只记日志不升级、请求处理整体 try/catch 回 500 进程存活；响应写出 try/catch 防客户端断开致命）。
4. **边界如实印证**：施工方声明"启动前配置类失败仍走 Node 默认栈"——本队副本桩在缺路由表时启动失败，Node 默认栈完整打印、退出码非零、**同样非静默**，与声明一致【实测】。
5. workflow 侧启动行已改进程替换 + tee（`> >(tee -a …) 2>&1 &`，`$!` 仍为 node PID），本队静态核对通过（见 1.5）；CI 侧运行时行为属本机无法复现项，维持【推断】。

### 2.8 本队环境清理复盘（诚实标注）

- Git Bash `kill` 对 Windows 原生 node/java 进程无效：本队按既往肌肉记忆 kill 后未复核端口，导致①一次旧后端存活引发新后端 H2 文件锁崩溃（该崩溃恰好又验证了"配置类失败非静默"）、②一次 E2E 打到旧后端而 `-BackendLog` 指向新后端的崩溃日志，制造了两轮**本队自造的** FAIL。改用 `taskkill` 清理后，有效轮次（§1 各表数据）全部来自干净环境。
- 教训已内化：Windows 下停进程必须 `taskkill` + 事后 `netstat` 复核；该缺陷不影响任何复核结论。
