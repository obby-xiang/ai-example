# 保留意见（不改判定，但影响后续引用方式）

1. **`poolActiveDuringBlock` / `poolQueueDepthDuringBlock` 是瞬时快照，不可作跨运行比对的稳定标识**。pool=4 格因 4 线程被确定性占满而稳定在 `4 / 6`；pool=8 格有余闲，实测出现 `5/0`、`4/1`（原报告为 `4/0`）。三者判定结论相同。若后续审计逐字段 diff 这两列，会产生假阳性不一致。
2. **`healthyCadenceDeviationMsMax = -1` 是哨兵，不是"负偏差"**。它表示"到达帧数 < 2，无法计算偏差"。报告表格里的"—（饿死）"即此值，引用时不应写成数值。
3. **饿死是池级头阻塞，不是逐 run 现象**：pool=4 格中 `healthyFramesAfterBatch1 = 4/10`，即 10 个 run 里**只有 4 个**拿到第 1 批帧，另外 6 个（含无慢订阅者的 run）也没拿到 —— 与"排队 drain 被 4 条阻塞线程头阻塞"机制一致。
4. **口径边界（复述原报告自我声明，非新发现）**：本格是进程内替身口径（`SseEmitter.send` 阻塞在 latch 上模拟 TCP 背压），慢 drain 在整格测量窗口内**持续阻塞**（60s 上限），比真实慢客户端更极端；结论应表述为"池容量必须严格大于**预期同时存在的慢连接数**"，而非"pool=4 无法支撑任何慢客户端"。
