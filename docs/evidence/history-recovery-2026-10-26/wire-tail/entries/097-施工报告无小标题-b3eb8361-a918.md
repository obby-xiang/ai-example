# 症② 倒计时闪回 —— 根因：`foldDeadline` 的"剩余时长折算"在本仓后端口径下**恒等于满额**，任何一次重派生都按"此刻 + 240s"重算

**起点取自哪：既不是挂起时刻，也不是真·剩余 —— 而是"本地 now + (expiresAt − atMs)"，而后端把 `expiresAt` 定义成 `atMs + T`，差值恒为常量 T。**

证据链（后端）：
1. `backend/.../run/SseChatEmitter.java:1067-1071` `expiresAtEpochMs(frame, T)` = **本帧 `atMs` + T**，注释自陈"对任意 TOCTOU 都恒有 `expiresAt − atMs == timeoutSeconds * 1000L`（long 精确等式）"。
2. 用到它的两处：`confirmRequest`（`:575-585`，`expiresAt` 在 `:582`）、`frontendToolRequest`（`:599-611`，`:608`）。`frame()` 在 `:677-681` 给**每一帧**（含实时帧）写 `atMs = System.currentTimeMillis()`（T4-3 后半，`docs/M2-排期计划.md:188` 登记为"实时帧全覆盖"）。
3. 挂起登记处另算一份真值：`gate/SpToolCallingManager.java:161-176` `suspendedAtMs` / `expiresAt = suspendedAtMs + T`，随 `saveSuspended → putPending`（`run/RunStore.java:354-358`、`:371`）落 Redis。

证据链（前端）：
4. `frontend/src/stores/ai.ts:101-114` `foldDeadline`：`atMs > 0 && expiresAt >= atMs` ⇒ 返回 `nowMs + (expiresAt − atMs)` —— 差值恒为 `T*1000` ⇒ 恒返回 `Date.now() + T*1000`。
5. `frontend/src/components/AiPanel/AiPanel.vue:2502-2517` `resetPendingWatch`：`confirmDeadline.value = foldDeadline(pending.expiresAt, pending.atMs, pending.timeoutSeconds)`（工作区 `:2514`；HEAD `:1339`）；`:1172-1177` `remainingSeconds = ceil((confirmDeadline − now)/1000)`，`:1093-1103` `now` 由 1s 节拍（`onMounted` `:2578-2584`）推进。

可达触发（逐条查证）：

同一根因的历史闭环证据（这是**回归**，不是新症）：
- `git show f0cff88`（T4-3 折算）删掉的旧实现注释原文："…不再用'本地收到帧的时刻 + timeoutSeconds'推断 —— 后者会把网络/渲染延迟算进倒计时，且**重挂（帧回放）时会把已经过去的等待时间重新计一遍**"，旧实现 = 直接用**绝对** `expiresAt`。即：**f0cff88 用"免疫客户端钟漂移"换回了它自己声称修掉的"重挂重计一遍"**；`foldDeadline` 的注释（`:96-99`）把它写成"重挂后本地倒计时可能偏长"，但在本仓 `expiresAt = atMs + T` 口径下实际是**每次都回到满额**。
- 施工前的活口：`docs/M2-排期计划.md:178` 记"实时帧不含 `atMs`（只有归档/回放帧含）⇒ 实时帧走回落分支（绝对 `expiresAt`）"，`M2:188` 记 T4-3 后半把**所有实时帧都补上 `atMs`**——正是这一步让"折算分支"从"仅回放帧"扩到"全帧"，绝对口径彻底退场。

**修法方向（一句话）**：拆掉"差值回推"——恢复绝对 `expiresAt` 口径但用首帧偏移校正（记 `skew = atMs − Date.now()`，`deadline = expiresAt − skew`，重派生幂等、既不闪回也不受钟漂移），或直接消费服务端权威剩余（见下条心跳）；并把 `resetPendingWatch` 的"重算"与"重置拒绝原因"解耦（只在 `toolCallId` 变化时才重置）。

**附：被白扔的现成通道** —— `SseChatEmitter.java:545-546` 注释"挂起期心跳…**也是前端展示倒计时的节拍**"，`ConfirmGate.java:338-349` `heartbeatData` 每 2s 带 `waitedSeconds` + `timeoutSeconds`（服务端权威剩余 = `timeoutSeconds − waitedSeconds`），而前端 `stores/ai.ts:1982-1984` 只 `break`。这正是最小改动修法入口。

# 症③ 刷新后倒计时重置回最初时间 —— 与症②**同一根因**，且违反 R-160 已验收口径

- **恢复链路上 `expiresAt` 没丢**：后端 `PendingToolCall.expiresAt/atMs`（`run/PendingToolCall.java:111-114`，`SpToolCallingManager:161-176` **先 set 后 `saveSuspended`** 落 Redis）→ `AiController.java:451-465` `runsCurrent.pendingEntries` **透出** `expiresAt`/`atMs`（`:459-460`）→ 前端 `stores/ai.ts:969-980` 读回写入段 → `AiPanel.vue:2514` `foldDeadline`。
- **丢的不是字段，是"已经等过多久"**：`entry.expiresAt − entry.atMs ≡ T`（240s，`AiProperties.java:120` `confirmTimeout = Duration.ofSeconds(240)`），所以刷新后 `deadline = Date.now() + 240s` ⇒ 无论已等 5s 还是 200s，一律回到 04:00。刷新链路里**没有任何一处记录挂起时刻或已等待时长**（本地 `now`/`confirmDeadline` 是 `AiPanel` 组件内 ref，刷新即销毁；镜像只存段与 `expiresAt/atMs`）。
- **这正是 R-160 要修、且已被用户验收的缺陷**：`<LOCAL_WORK>/r160-hitl/demo-验证报告.md:11` 记 C现状 = "约 5s 后刷新→卡折叠 + **重置 04:00**"；`:12` 记 C修复验收 = "刷新后卡仍展开、⏳ **03:48（按剩余继续）**"；`决策卡-R160-定稿.md:11`、`docs/M2-排期计划.md:349` 场景①"pending 门倒计时续走"。**当前实现给回了 C现状**（04:00），验收口径未达成。

**修法方向（一句话）**：同症②——续走必须建立在"服务端绝对 `expiresAt` + 本地偏移校正"或"心跳 `waitedSeconds`"之上；`foldDeadline` 的 `now + (E−A)` 口径在 `E≡A+T` 的后端下不可能续走。
