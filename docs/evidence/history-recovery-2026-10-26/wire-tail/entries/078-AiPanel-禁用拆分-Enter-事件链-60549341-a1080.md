### 1.2 本地 disabled 拆分，不改 store `canSend`

当前 `:735` 是 `:disabled="!ai.canSend"`，而 `canSend` 的语义是“是否可以开始新一轮”（`stores/ai.ts:923-926`，`!loading`）。直接保留会把“流式可编辑”再次禁掉；直接把 `canSend` 改成 `!loading && ...` 又会污染其他调用点。正确做法是**只新增组件本地 computed**：

```ts
const aiUnavailable = computed(() =>
  ai.healthError !== null || (ai.health !== null && !ai.available)
)
const composerHardDisabled = computed(() =>
  aiUnavailable.value || ai.suspended || ai.pendingToolCall !== null
)
```

- textarea：`:disabled="composerHardDisabled"`，不再用 `!ai.canSend`。
- `composerHardDisabled` 的真实禁用来源：降级/不可用、挂起等待（确认门/前端工具/GF）、待处理调用兜底。
- **不包含 `ai.loading`**：普通流式中 textarea 保持可编辑。
- `ai.health === null`（首屏 health 探测未回）不算“真实不可用”，保持可输入；这与现有 `canSubmit` 里 `ai.available` 的按钮禁用并不冲突，避免首屏闪禁用。若直接写 `!ai.available` 会在 health 未回时把输入框也禁掉，并可能影响现有测试夹具。
- `canSubmit` 可改为 `!composerHardDisabled.value && ai.available && inputText.value.trim().length > 0`，这样发送钮不再依赖 `ai.canSend`；store 的 `canSend` 保持原样。
- `send()` 里 `:2590` 的 `if (!ai.canSend)` 程序化守卫可以保留不动；但**流式 Enter 不能走到它**，否则会弹 `noticeBusySend()`，违反“无响应、不提示”。

### 1.3 Enter 事件链

把 `:737` 的 `@keydown.enter.exact.prevent="send"` 改为 `@keydown="onComposerKeydown"`，并加 `@compositionstart` / `@compositionend`。建议行为矩阵：

| 状态 | Enter | Shift+Enter |
|---|---|---|
| 空闲、非硬禁用 | `preventDefault()` + `send()` | 不拦截，浏览器换行 |
| 流式中 `ai.loading` | `preventDefault()` + `return`；**不发送、不换行、不提示** | 不拦截，浏览器换行 |
| IME 组合期 | 直接 `return`，不 `preventDefault`，交给输入法确认候选 | 按 demo 规则不拦截 |
| `compositionend` 后 30ms 内 | `preventDefault()` + `return`（Safari 兜底） | 不拦截 |
| `event.repeat` | `preventDefault()` + `return` | — |
| 硬禁用 | textarea 已 disabled，事件不会到达 | — |

关键防错：

- 流式普通 Enter **必须 `preventDefault()` 后返回**。只 `return` 会插入换行；调用 `send()` 会触发 store 的 busy 提示；手动改 `inputText` 或追加 `\n` 也都是错的。
- 组合期 Enter 不能 `preventDefault`，否则会干扰输入法候选确认。
- 不要用 `noticeBusySend()` 表达“流式 Enter 无响应”。

### 1.4 `send()` 与焦点、草稿保存

当前 `:2584-2619`：

- 发送前 `trim()`、空内容静默返回；
- 编辑重跑分支 `:2601-2614`；
- 普通路径在 `await ai.send(text)` **之前** `inputText=''`（`:2617`）。

需要增加：

1. 发送前保存原始草稿 `const draft = inputText.value`（不要只存 trim 后文本）。
2. 清空后立即 `composerRef.value?.focus({ preventScroll: true })`。现在 textarea 在流式中不再 disabled，focus 可以成立；这也修复“点击发送后焦点落到 body/被移除的按钮”。
3. `await ai.send(...)` 后按返回值处理：
   - `ok`：不恢复；
   - `cancelled`：**不恢复**，用户主动停止；
   - `error` / `interrupted` / `not-sent`：若 `inputText.value === ''`，恢复 `draft`；若用户流式中已经输入了新内容，不覆盖。
4. 恢复时只写 `inputText`，**绝不能再次调用 `ai.send()` 或 `recordUserMessage()`**；否则就是重复发送/重复用户消息。

## 2. `stores/ai.ts` 的 `send()` 返回值

### 2.1 当前事实

| 项 | 当前行为 | 位置 |
|---|---|---|
| `send()` 返回 | `Promise<void>`，所有路径都解析为 `undefined`；内部 catch 后不 rethrow | `stores/ai.ts:1483-1573` |
| 用户消息写入 | 在请求前就 `recordUserMessage(content)` | `:1497` |
| 新一轮复位 | `lastRoundOutcome='ok'` | `:1504` |
| SSE `error` 帧 | `lastRoundOutcome='error'` | `:2876` |
| 流断（无终帧） | `lastRoundOutcome='interrupted'`，并置 `streamInterrupted` | `:1531` |
| 开流前失败 | `catch → handleChatError()`；`handleChatError` **不写 `lastRoundOutcome`**，所以仍停留在 `'ok'` | `:1554-1557`、`:1576-1639` |
| 用户主动 stop | `stop()` 先置 `lastRoundOutcome='cancelled'`、`stopped=true`，再 abort；onClose 的 interrupted 分支被 `stopped` 抑制 | `:2326-2329`、`:1528` |

结论：**只用现有 `lastRoundOutcome` 不能可靠区分“开流前失败”与成功**。`handleChatError` 覆盖 409/503/网络等开流前失败，但 outcome 仍是 `'ok'`；`notice` 也可能被重连提示污染；`errorCard` 对 `SESSION_BUSY` 返回 `null`（`utils/error-card.ts` / 测试 `:4039-4043`），不能作为失败判据。因此若要求“所有失败/断流都保稿”，**必须小幅改 `stores/ai.ts`**。

### 2.2 最小接口变更

建议只改 `send()` 的返回类型和内部返回，不新增 store 状态、不改 `canSend`/`stop()`/`handleChatError`/`lastRoundOutcome` 的现有语义：

```ts
type SendOutcome = 'ok' | 'error' | 'interrupted' | 'cancelled' | 'not-sent'
interface SendResult {
  outcome: SendOutcome
  userMessageId: string | null
}

async send(text, resend = {}): Promise<SendResult>
```

返回映射：

- 空内容 / `loading` 早退：`{ outcome: 'not-sent', userMessageId: null }`；
- 正常结束：`{ outcome: 'ok', userMessageId: userMessage?.id ?? null }`；
- SSE error 或 `catch` 开流前失败：`'error'`；
- 断流：`'interrupted'`；
- `this.stopped === true`：`'cancelled'`。

计算方式只需一个局部标志，例如 `let thrown = false`；`catch` 里 `if (isCurrentRound()) { thrown = true; handleChatError(...) }`；最后：

```ts
const outcome = this.stopped
  ? 'cancelled'
  : thrown
    ? 'error'
    : this.lastRoundOutcome
return { outcome, userMessageId: userMessage?.id ?? null }
```

`userMessage` 来自 `recordUserMessage` 的返回值（`:2583-2600` 已返回 `ChatMessage`）；`skipUserRecord` 时为 `null`。这样不需要改 `handleChatError`，也不需要新增 outcome 状态。

### 2.3 如何避免“失败保存草稿”变成重复用户消息

当前失败时用户消息已经在 `:1497` 写入消息流；如果只恢复输入框，用户再按发送会再 append 一条同样的用户消息。最小防重复方案是复用现有“编辑重跑”机制：

- store 在失败时返回 `userMessageId`；
- 组件恢复草稿时，同时把 `editingMessageId` 设为该 `userMessageId`（`AiPanel.vue:2457`、编辑分支 `:2601-2614`）；
- 下一次发送走现有编辑重跑分支：原地更新该用户消息、`splice(cut+1)` 删除其后的错误助手消息、`ai.send(text, { skipUserRecord: true })`，不会新增第二条用户消息；
- 如果本次是编辑重跑（`skipUserRecord: true`）失败，store 返回的 `userMessageId` 为 `null`，组件用发送前保存的本地 `editId` 恢复锚点；
- 恢复路径绝不调用 `send()` / `recordUserMessage()`。

代价需要明说：复用编辑锚点意味着“重发”会截断该轮的错误助手消息/半截回复。若产品要求保留半截回复再重发，就需要单独的 retry/resend 接口，超出本最小批，不应在本次偷偷用普通追加发送实现。
