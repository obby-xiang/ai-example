### 手册与代码的出入（6 处，都会误导排障）

1. **手册只有 12 个，漏了 `memory_window`**（`MemoryWindow.java:196-205`，生产路径 `ResilientChatService.java:1494` 与 `ResumeService.java:631`）。它和 `compaction` 刻意分开："读进来的历史为什么变短"只有它答。手册 2.7 只讲 compaction，运维照手册查会漏掉一半"上下文变短"的原因。
2. **`upstream_first_byte.events` 语义写错**。手册写"已收上游事件数"，代码是 `accumulator.meter().frames()`（`ResilientChatService.java:641` → `ContextMeter.java:134`），即**采到的非空 usage 帧数**。实抓日志里同一轮 `events=0` 而 `turn_retry.upstreamEvents=1` —— 按手册读会把"上游正常"误判成"上游没动"。
3. **`upstream_first_byte.chars` 不是首包瞬间的值**。它在 `awaitSettled` 之后才写（`ResilientChatService.java:519-520`，注释自认"代价是等尝试落定后才写出"），是**落定时刻**的正文长度。
4. **`approval_decided` 没有 `kind` / `timeoutS` / `preflight`**。手册 2.6 把这三个列成两事件共用字段，代码里只有 suspend 带（`ConfirmGate.java:499` vs `:990`）。后果：决策行分不出"人批的确认卡"和"前端回执"，必须回连 suspend 行。
5. **`turn_end.status` 没有 `empty_reply` 这个值**。手册 2.8 列了五个终态，代码里空回复是 `status=failed code=EMPTY_REPLY`（`ResilientChatService.java:927`），按 `status=empty_reply` 聚合永远查不到。
6. **`tool_call_start`/`tool_call_end` 并非成对**。三种情况只有 start 或干脆两端都没有：
   - 工具执行中被取消 → `checkCancelled` 抛异常（`SpToolCallingManager.java:423`），`tool_call_end` 永远不写；
   - 预检未通过 / 步数到顶 / 首错即停跳过的调用 → 在 `eventOn` 之前 `continue`（`:376-391`），**一行都没有**。
   也就是说"每个工具都有两端"在**最需要排查的取消场景**下恰好不成立。

另两处实测细节：`compaction` / `approval_decided` 实抓样本行首锚点是空的（`INFO   34756 --- …`，发射线程没绑 MDC），只能靠正文里的 `runId=` 命中；`grep <runId>` 仍能捞到，但"只按行首锚点扫"的脚本会漏。

## 三、结论与最小补齐集

### 判定：差一点点 —— 但"差"分两类，别混在一起缓议

**A 类：同一机制内加字段 / 加 3 个事件就够**（不动语义、零新依赖、一批可完）

| 位置 | 补什么 | 解决哪条 |
|---|---|---|
| `turn_end` | `queueMs`（accepted→start）、`runTotalMs`（run 创建→结束，跨段）、`provider`、`frames`+`dirty`、`attempt` | 慢的排队段、续跑时长失真、token 归因、usage 可信度 |
| `tool_call_end` | `execMs`（= `ms` − 审批等待）；预检拦截/步数到顶/首错即停也要发一条（`skipped=true`） | 工具执行 vs 审批可分；`toolCalls` 与前端卡片数不再打架 |
| `tool_call_end`（取消路径） | 在 `checkCancelled` 抛出前补写 end 行（`outcome=cancelled`） | 取消场景下"工具到底执行了没有"能一眼看到 |
| `approval_decided` | `kind`、`timeoutS`、`suspendMs`（suspend 行→决策行，与 `waitedMs` 区分） | 决策行自解释，不必回连 suspend |
| `turn_retry` | `attemptMs`（本次尝试耗时）、`firstByteMs`、该次尝试的 token | 重试成本与"哪次慢" |
| `turn_start` | `resumeReason`（startup / manual / deadcard / reattach） | 现在四种续跑全压成 `resumed=true` |
| 新增事件 `turn_denied` | 在 `AiTrace.bind` **之前**用 `eventOn` 显式锚点写：`code=SESSION_BUSY / RATE_LIMITED / AI_UNAVAILABLE / REDIS_DOWN / MODEL_NOT_FOUND / BAD_REQUEST` | 堵死"请求被拒零日志"这个最大的盲区 |
| 新增事件 `turn_exception` | 环外未捕获异常也写一条终态行（`code=UNCAUGHT`） | 保证"每轮必有终态行"这条手册承诺成立 |
| 新增事件 `sse_detach` | 订阅者被摘/写超时（替掉或伴随 `SseChatEmitter.java:1391` 的 WARN） | "后端 done 了用户没看到" |
| 日志行首 | `instanceId`（MDC 一键 + pattern 一列，`RunStore.instanceId()` 已有） | 跨实例归因 |
| 手册 | 修 6 处出入（尤其 `events` 语义、`empty_reply`、approval 字段表） | 避免照手册排错排反 |

**B 类：改字段救不了，必须新面或新地基**

1. **落盘与留存（最要紧，且它不属于 metrics）**：logback rolling file（time+size、`maxHistory`、`totalSizeCap`）或交给采集端。不做，问题 4/6/7 直接判死。L-55 里"metrics/OTel/eval 缓议"没有点名留存，很容易被"零组件日志面"这句话连带缓议掉 —— 但留存是日志面自己的地基，不是指标面。
2. **聚合/时间序列/告警**：p50/p95 首包、按模型错误率、审批等待分布、token 日曲线。要么上 metrics（actuator+micrometer 的四个计时器 L-55 已经 scope 过：上游首包/轮总耗时/工具执行/审批等待），要么把日志送进 Loki/ELK。日志文件能算，但要写脚本、跑全量、跨天不便宜 —— 这是"能不能回答趋势"的真边界。
3. **跨实例现势视图**：`/health` 是进程内（L-32 已登记），要"全局现在多少卡着/多少在跑"需要 Redis 计数族。
4. **JSON 化**（可选）：grep 型排障不受益，只有在第 2 条落地成日志平台时才值得做；现在做是纯成本。

### 一句话给用户

"日志打印就行"这个裁决在**单实例、当天、按 runId 追一轮**的场景下是成立的，手册那套 grep 菜谱基本能用。但它现在缺的不是"更花哨的面"，而是三样很便宜的东西：**十来个字段、三个事件（尤其是被闸门拒的那一类）、一个文件 appender**。前两样一批就能补完；第三样不做的话，"某个会话昨天发生了什么"这个问题在 24h 后依然只能回答"取决于日志有没有被重定向下来"。真正的 metrics/趋势面可以继续按 L-55 缓议，不受影响。
