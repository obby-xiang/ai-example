## 结论

在 440px 面板的 composer 附近，**非模态 inline 状态提示**最符合“低干扰且不易漏看”。

它把“为什么没发出去 + 下一步做什么”放在用户当前注意力和焦点所在的位置，并且可以持续到状态改变。toast 视觉上干扰低，但会自动消失、可能在角落、屏幕阅读器还可能被 assertive 打断；modal 最不容易漏看，但遮挡和焦点陷阱带来的干扰最大。

下面是设计建议，不是标准强制。WCAG 只要求状态消息能被辅助技术获取且不夺取焦点，具体用 inline、toast 还是 dialog 是设计判断。

## 一、事实依据

### 1. WCAG 4.1.3：状态消息应“不夺焦点”地被辅助技术获取

WCAG 2.2 的 4.1.3 Status Messages 要求：状态消息能通过 role 或属性被程序化确定，并由辅助技术**在不接收焦点的情况下**呈现。其 Intent 把 status message 定义为：不是 context change，且提供操作结果、等待状态、进度或错误存在性的信息；并明确说，对话框里的错误因为夺取焦点属于 context change，不在该 SC 范围内。

来源：[Understanding SC 4.1.3: Status Messages](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)

### 2. WAI-ARIA APG：alert 不应影响键盘焦点，也不应自动消失

APG 的 Alert pattern 说：alert 是 brief、important message，用来吸引注意但**不打断用户任务**；“crucial they do not affect keyboard focus”。APG 还明确建议避免设计会自动消失的 alert，并提醒频繁打断会损害可用性，引用 WCAG 2.2.3 和 2.2.4。

来源：[WAI-ARIA APG Alert Pattern](https://www.w3.org/WAI/ARIA/apg/patterns/alert/)

### 3. `role=status` 与 `role=alert` 的语义差异

WAI-ARIA 对 `status` 的定义是：给用户的 advisory information，**不够重要到需要 alert**；隐式 `aria-live="polite"`、`aria-atomic="true"`；作者应确保 status 不因内容变化而接收焦点。

`alert` 则是 important、usually time-sensitive 的信息，隐式 `aria-live="assertive"`、`aria-atomic="true"`，会立即打断当前播报，应少用。MDN 还说明：同一段文本重复注入通常不会再次播报；若要再次触发，通常需要先清空再写入——这正好解释了为什么“每次 Enter 都重新插一遍”会造成重复打扰。

来源：[WAI-ARIA `status` role](https://www.w3.org/TR/wai-aria-1.2/#status)、[MDN `alert` role](https://developer.mozilla.org/en-US/docs/Web/Accessibility/ARIA/Roles/alert_role)

### 4. Fluent 2：message bar 承担上下文提示，toast 不承载必要操作，dialog 才移动焦点

Fluent 2 的 MessageBar 文档：info/success 为 polite，warning/error 为 assertive；message bar 用于说明整个 surface 或容器状态。Toast 文档：无 action 时 **7 秒**超时；无 action 的 toast 不接收键盘焦点；并明确说“Don’t use toasts for necessary actions”，必要操作应改用 message bar 或 dialog。Dialog 文档：打开时焦点移到第一个可交互元素并困在对话框内，关闭后回到触发点；alert dialog 只用于潜在损失、未保存更改、破坏性操作。

来源：[Fluent 2 MessageBar](https://fluent2.microsoft.design/components/web/react/core/messagebar/usage)、[Fluent 2 Toast](https://fluent2.microsoft.design/components/web/react/core/toast/usage)、[Fluent 2 Dialog](https://fluent2.microsoft.design/components/web/react/core/dialog/usage)

### 5. Carbon、Polaris、Material 对 toast 的边界高度一致

- Carbon：inline notification **不会自动消失**，会持续到用户关闭或问题解决；toast 是 time-based，通常几秒后消失；通知本身“disruptive and should be used sparingly”。
- Polaris：toast 使用 `aria-live="assertive"`，会自动消失、键盘不易访问、可能出现在当前焦点之外；明确不建议用 toast 承载关键信息；带 action 的 toast 至少 **10,000ms**。
- Material 3：无 action 的 snackbar 通常 **4–10 秒**自动消失；并提醒 Web 上自动消失时应有 inline 承载。

WCAG 2.2.1 的 Understanding 还以 toast 为例：如果同一信息没有其他获取途径，自动消失就构成需要满足 2.2.1 的时限；如果有其他途径（如收件箱），才不构成时限。

来源：[Carbon Notification](https://carbondesignsystem.com/components/notification/usage/)、[Polaris Toast](https://polaris.shopify.com/components/feedback-indicators/toast)、[Polaris Banner](https://polaris.shopify.com/components/feedback-indicators/banner)、[Material 3 Snackbar](https://m3.material.io/components/snackbar/guidelines)、[WCAG 2.2.1 Timing Adjustable](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html)

**toast 时长对照（均为设计系统建议值，不是 WCAG 固定秒数）：**

| 系统 | 时长/行为 |
|---|---|
| Material 3 | 4–10 秒；Web 自动消失需有 inline 兜底 |
| Fluent 2 | 无 action 7 秒；无 action 不收键盘焦点 |
| Carbon | 可配置 5 秒；inline 不自动消失 |
| Polaris | 带 action 至少 10 秒；toast 用 assertive |

## 二、三种方案对比

| 方案 | 干扰 | 漏看风险 | 焦点 | 对本场景的判断 |
|---|---|---|---|---|
| **非模态 inline** | 低：不遮挡、不抢焦点、不阻断输入 | 中低：位置固定、持续可见；需要视觉上足够明显 | 不移动 | **最符合** |
| **自动消失 toast** | 视觉低；屏幕阅读器可能高（assertive） | 高：4–10 秒消失、可能在角落、键盘不易访问 | 不移动，但键盘用户难以到达 | 不适合承载“下一步” |
| **模态确认** | 高：遮挡、焦点陷阱、打断流式 | 低 | 移动并困住 | 过度；只适合破坏性/不可逆确认 |

## 三、设计建议（非强制）

### 1. 形态与位置

建议在 composer **正上方**放一行 inline 状态提示，留在同一个 440px 内容列里，不要用浮层。

- 左侧 info 图标 + 文本，不要用 warning/error 样式；这不是错误，只是当前状态。
- 文案同时说清三件事：**当前状态 + 下一步 + 草稿安全**。
  - `正在生成。先点“停止”，再按 Enter 发送。草稿已保留。`
- 控制在 1–2 行。Carbon 和 Fluent 都建议通知内容短、可扫读，并说明下一步。
- 保留现有的“停止”按钮，不要新增第二个停止入口；可以在提示出现时给停止按钮一个轻微的视觉强调（细环/短暂高亮），但不要移动焦点，并尊重 `prefers-reduced-motion`。
- 440px 下建议预留这一行的高度，避免提示出现时把 composer 或发送键顶走。

### 2. 出现与消失时机

建议：

- **出现**：流式进行中，composer 有非空草稿，用户第一次按下“真正的发送 Enter”时出现。
  - 不处理 `Shift+Enter`。
  - 不处理中文/日文输入法正在组合文本时的 Enter（`isComposing` / `keyCode 229`）。
  - 不处理按住 Enter 产生的重复 keydown（`event.repeat`）。
- **持续**：只要还在流式且草稿还在，就保持可见；**不要用定时器自动消失**。
- **停止后**：不要立刻消失，改成“已停止，可以按 Enter 发送”，保留到用户发送或清空草稿。这样用户能确认“现在可以发了”。
- **自然结束后**：改成“回复已结束，可以按 Enter 发送”，同样保留到发送或清空。
- **发送后/草稿清空后**：移除提示。
- 草稿为空时不要显示；不要每敲一个键就更新提示。

如果产品更看重“提前预防”，也可以在“草稿非空 + 正在流式”时显示同一行低强调 helper；但不要同时再叠一个 toast。

### 3. 焦点与草稿

建议：

- **焦点始终留在 textarea**，不移动、不 blur、不自动聚焦“停止”按钮。
- 保留草稿、光标位置和选区；按 Enter 被拦截时不清空输入。
- Enter 只做一件事：阻止默认发送并显示提示。**不自动停止、不自动发送、不排队。**
- 停止只由用户点“停止”触发；停止后**不自动发送**，等用户再次按 Enter 才发送。
- 如果提示里要放“停止”控件，它是 live region 之外的真实按钮，可 Tab 到达，但不自动聚焦；不要嵌套在 `role=status` 里。

### 4. 屏幕阅读器播报

建议用一个**预先挂载**的 visible `role="status"` 区域，放在 composer 附近：

- `role="status"` 已隐式 `aria-live="polite"`、`aria-atomic="true"`，不需要再设 assertive。
- 第一次拦截 Enter 时写入一次：
  - `正在生成回复。请先停止，再按 Enter 发送。草稿已保留。`
- 停止后写入一次：
  - `已停止生成。可以按 Enter 发送。`
- 自然结束后写入一次：
  - `回复已结束。可以按 Enter 发送。`
- 不要用 `role="alert"` 或 `aria-live="assertive"`；这不是需要立即打断的紧急信息。
- 不要把流式回答本身放进这个 live region，否则会逐段播报。
- 可以用 `aria-describedby` 把该提示关联到 textarea，方便屏幕阅读器用户回到输入框时再次发现它；但避免同时维护两个 live region 造成重复播报。
- polite 播报可能等到用户停止输入/空闲时才出现，这是可接受的；可见文本会持续存在，用户不会因为没听到就永久丢失信息。

示意：

```html
<div id="composer-status" role="status" aria-live="polite" aria-atomic="true">
  正在生成。先点“停止”，再按 Enter 发送。草稿已保留。
</div>

<textarea aria-describedby="composer-status"></textarea>
```

### 5. 重复 Enter 的处理

建议：

- 同一次流式过程中，**保持同一个 status 节点和同一段文本**，不要清空再插入；这样不会反复触发播报。
- 后续 Enter 不再更新 live region、不叠 toast、不弹 modal、不自动停止或发送。
- 用 `event.repeat` 忽略按住 Enter 的重复 keydown。
- 如果需要让用户感到“按键被接收了”，用**纯视觉**反馈：停止按钮轻微脉冲/描边，不要用第二次播报。
- APG 明确提醒频繁打断会损害可用性；对屏幕阅读器用户，连续 `role="alert"` 比“没有反应”更糟。

### 6. 三种形态的适用边界

- **Helper text**：适合始终为真的静态说明，例如“Enter 发送，Shift+Enter 换行”。不适合随流式状态出现/消失的动态提示；如果动态替换，它实际上已经是 inline status，应加 live region 语义。
- **Inline message / status**：适合当前上下文的状态、下一步、可恢复的问题；可持久、可带一个明确动作。**本场景选它。**
- **Toast**：适合非关键、无需用户行动、且信息在别处也能找到的短暂确认。不适合“必须先停止才能发送”这种下一步指令；不要把它作为唯一提示。
- **Modal / alertdialog**：适合必须打断工作流并要求决策的场景，例如未保存更改、破坏性操作确认。APG 的 alertdialog 定义就是“interrupts the user’s workflow ... and acquire a response”；Fluent 也把 alert dialog 限定在潜在损失/破坏性操作。本场景不需要用户做决定，所以不建议。

### 7. 文案建议

优先用短句，避免只写“无法发送”：

- 首次拦截：`正在生成。先点“停止”，再按 Enter 发送。草稿已保留。`
- 停止后：`已停止，可以按 Enter 发送。`
- 自然结束：`回复已结束，可以按 Enter 发送。`

如果 440px 横向空间紧张，可缩为：

- `正在生成。先停止，再按 Enter 发送。`
- `已停止，可以发送。`

关键不是把标准条文搬进 UI，而是让用户在当前焦点附近、持续地看到“为什么”和“下一步”，同时不打断输入、不重复播报。
