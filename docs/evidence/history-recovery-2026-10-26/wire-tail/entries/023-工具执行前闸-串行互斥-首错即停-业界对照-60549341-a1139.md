## 先给结论

1. 主流不是一道总闸，而是**多层闸门串联**：schema → 权限/范围 → 前置状态 → 风险审批 → 互斥/并发 → 失败分流。

## 1) 执行前主流有哪几道闸

| 闸门 | 主流做法 | 官方依据 | 定性 |
|---|---|---|---|
| **Schema/结构** | JSON Schema、`required`、`additionalProperties:false`、枚举、输出 schema；严格模式 | OpenAI `strict:true` 会拒绝不合规 schema，并建议始终开启；Anthropic `strict:true` 用约束解码保证工具名和输入符合 schema；Gemini `VALIDATED` 模式保证 schema 遵循；MCP 的 `inputSchema`/`outputSchema`；LangChain Pydantic `args_schema`；SK 自动序列化 JSON schema | 【协议/API】+【框架能力】 |
| **权限/身份** | 每次调用做认证、授权、scope 校验；禁止 token 透传；按用户角色裁剪工具 | MCP 服务端 **MUST** 实现访问控制，且 **MUST NOT** 接受非签发给本服务的 token；SK filter 可在审批前校验权限；LangChain 可按用户角色动态过滤工具 | 【协议要求】MCP；【框架能力】SK/LangChain |
| **范围/工具面** | 工具白名单、`allowed_tools`、`allowed_function_names`、`tool_choice:none`、控制工具数量 | OpenAI `allowed_tools` 可限制本轮可调用子集；Gemini 建议活跃工具控制在 10–20 个；MCP 要求 scope 最小化；LangChain 支持按权限/状态动态选工具 | 【协议/API】+【应用建议】 |
| **前置状态** | 先读后写、显式 handle、版本/ETag 校验、过期检查、重新取状态 | MCP 明确“无协议级 session”，有状态工具应返回显式 handle，服务端每次调用都要校验授权，过期 handle 返回可恢复错误；SK 文档明确提示购物车可能已变化，应重新读取；Gemini 建议把当前日期/时间/地点放入系统指令 | 【协议要求】MCP；【框架能力】SK/LangGraph；【应用建议】版本校验 |
| **风险审批** | 按风险等级暂停，人工批准/拒绝/编辑参数；审批失败默认拒绝 | OpenAI `needs_approval` 可逐调用判断，且参数缺失、空、畸形 JSON、非对象、`NaN/Infinity` 时**fail closed**，强制人工审批；Gemini 最佳实践明确“有重大后果的调用应先向用户确认”；MCP 客户端 **SHOULD** 对敏感操作提示确认，本地 server 一键配置 **MUST** 先展示完整命令并取得明确同意；LangGraph `interrupt()` 可在工具内暂停审批 | 【协议/API】+【框架能力】 |
| **资源锁/互斥** | 按资源键串行、单写者队列、租约/ fencing token、并发上限 | 没有哪家协议提供分布式锁原语。OpenAI 只有 `max_function_tool_concurrency` 并发上限；Anthropic 只给“副作用/共享状态建议串行”的应用指导；LangGraph 用 super-step 并行 + reducer 解决状态合并，不是互斥锁；MCP 用显式 handle 维持跨调用状态 | 【框架能力】有限；【应用建议】为主 |

## 2) 副作用与共享状态工具的串行/互斥/首错即停惯例

### 串行与互斥

- **Anthropic 给得最明确**：API 不规定执行顺序，由应用决定；独立只读操作通常可并行；**有副作用、共享状态或顺序要求的工具，最好串行**。它还提供 `disable_parallel_tool_use:true` 来限制一次只发一个工具调用。
  [Anthropic Parallel tool use](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/parallel-tool-use)
- **OpenAI 提供的是“模型侧限制 + 宿主侧并发上限”**：`parallel_tool_calls:false` 保证一次最多一个工具调用；Agents SDK 的 `max_function_tool_concurrency` 控制本地函数工具的并发数，默认会把同一轮发出的调用全部启动，设为 1 才等价于串行。
  [OpenAI function calling](https://platform.openai.com/docs/guides/function-calling)、[Running agents](https://openai.github.io/openai-agents-python/running_agents/)
- **LangGraph 不是锁**：同一 super-step 内的节点会并行，状态冲突靠 reducer 合并；真正需要互斥时，应在节点/工具内部按资源键加租约或队列。
  [LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)
- **MCP 没有协议级 session，也没有锁**：跨调用状态要靠显式 handle；服务端每次都要重新校验授权。互斥应由客户端或服务端按资源实现。
  [MCP 有状态工具](https://modelcontextprotocol.io/docs/concepts/tools)

### 首错即停

- **不是通用默认**。Anthropic 的 computer/browser 工具集是明确的例外：同一批调用必须按出现顺序串行执行，并**在第一个失败处停止**；未执行的调用仍要返回 `is_error:true` 和简短说明。
  [Anthropic Parallel tool use](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/parallel-tool-use)
- OpenAI 默认会启动同一轮的所有本地函数工具；只有 guardrail tripwire 会中止整个 run，`max_function_tool_concurrency` 只是限流，不是首错停止。
  [OpenAI Guardrails](https://openai.github.io/openai-agents-python/guardrails/)、[Running agents](https://openai.github.io/openai-agents-python/running_agents/)
- LangChain/LangGraph 提供工具错误处理和 `ToolNode`，但没有“批内首错即停”的强制默认；需要应用自己配置。
  [LangChain Tools](https://docs.langchain.com/oss/python/langchain/tools)

**可落地的惯例**：只读、幂等、无共享状态的批量可以并行并聚合错误；**有副作用、非幂等、共享状态、外部不可回滚的批量，按资源键串行，并采用首错即停 + 未执行调用显式返回“未执行/错误”**。这是应用建议，不是协议强制。

## 3) 幂等、去重、审计、补偿/回滚的主流模式

| 主题 | 主流模式 | 官方依据 | 定性 |
|---|---|---|---|
| **幂等** | 幂等键、upsert、先读后写、写前查重；恢复/重放前先对账 | LangGraph 明确要求节点可重入：插入数据库行重复执行不能产生重复行，建议使用 idempotency keys、upserts、read-before-write；OpenAI HITL 明确生产应用必须在重试前对账工具副作用 | 【框架能力】LangGraph；【应用建议】OpenAI 明确要求 |
| **去重** | 用调用 ID 关联请求/结果；用业务幂等键去重；审批恢复做原子 owner-check | OpenAI `call_id`、Anthropic `tool_use_id`、MCP JSON-RPC `id` 都是关联 ID，不是天然的幂等键；OpenAI HITL 要求用原子 owner-checked transition，防止并发或重放把同一快照恢复两次；MCP 的 `idempotentHint` 只是提示 | 【协议/API】关联 ID；【应用建议】去重键 |
| **审计** | 记录调用方、工具、参数摘要、调用 ID、决策、结果、审批人、耗时；敏感字段脱敏 | MCP 客户端 **SHOULD** 记录工具使用以供审计；MCP 安全页要求记录 scope elevation 事件和 correlation ID；OpenAI tracing 支持 `workflow_name`、`trace_id`、`group_id` 和敏感数据开关；LangGraph checkpointer 可保存线程状态；SK filter 可做前后日志 | 【协议要求】MCP 日志建议；【框架能力】OpenAI/LangGraph/SK |
| **补偿/回滚** | Saga、outbox、补偿动作、人工对账；**没有协议级事务回滚** | LangGraph checkpoint 保存的是图状态，不是外部系统快照；OpenAI HITL 明确“恢复执行不等于撤销副作用”，生产应用要自行协调；MCP 有状态工具也没有事务语义 | 【应用建议】；官方文档没有自动补偿原语 |
| **超时/结果不确定** | 不盲目重试；先按幂等键查询结果，再决定重试/补偿/人工处理 | OpenAI HITL 提到恢复前要 reconcile side effects；LangGraph 要求可重入；LangChain 明确 tool error middleware **不会自动重试**，重试要显式组合 retry middleware | 【框架能力】LangChain 显式重试；【应用建议】先对账 |

**要点**：不要把这几个 ID 当成幂等保证。调用 ID 只解决“这是哪一次调用”，幂等键要解决“这次业务效果是否已经发生”。
官方：[LangGraph Graph API](https://docs.langchain.com/oss/python/langgraph/graph-api)、[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)、[OpenAI HITL](https://openai.github.io/openai-agents-python/human_in_the_loop/)、[MCP Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)、[MCP 安全最佳实践](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices)、[LangChain 内置 middleware](https://docs.langchain.com/oss/python/langchain/middleware/built-in)。

## 4) 参数或状态不对时，如何区分五类处理

| 情形 | 建议动作 | 理由与官方依据 | 定性 |
|---|---|---|---|
| **纯语法/表示层问题，语义可保持不变** | **安全归一**：去空白、大小写不敏感匹配 enum、数字字符串转数字、补显式默认值；归一后重新校验并记录 | Anthropic 明确建议 enum 大小写不敏感比较；SK 会把 JSON 参数反序列化为枚举/类型；LangGraph 的 `response_schema` 可用 Pydantic 校验和强制转换 | 【应用建议】，官方只背书“无歧义归一”，不背书“猜值” |
| **值不合法但模型可修正**：格式错误、越界、业务规则不满足 | **回模型重试**：返回结构化错误，让模型改参数再调用 | MCP 把“输入校验错误、API 失败、业务逻辑错误”归为 tool execution error，建议返回 `isError:true` 让模型自纠；Anthropic 用 `is_error:true`；LangChain 把异常转成 `ToolMessage`；SK 明确应提供清晰错误让模型重试 | 【协议/API】+【框架能力】 |
| **缺参数、意图歧义、多个合理解释** | **问用户**，不要自动补 | Gemini 最佳实践明确“信息不足时问澄清问题”；SK 的 required 参数会让模型先向用户询问；MCP 客户端 **SHOULD** 在敏感操作前展示输入并确认 | 【协议/API】+【应用建议】 |
| **未知工具、请求结构错误、未授权、scope 不足、策略违规** | **硬拒绝**，不猜、不模糊匹配 | MCP 把 unknown tool、malformed request 归为 protocol error，明确“模型不太可能修好”；OpenAI 默认对未知工具抛 `ModelBehaviorError`，只有显式配置才回错误给模型；guardrail tripwire 直接中止 | 【协议/API】 |
| **前置状态已变化**：版本过期、handle 失效、资源已被别人修改 | **中止/重读/重规划**，不要拿旧参数重试 | MCP 有状态工具要求过期 handle 返回明确错误，让模型重新创建；SK 文档提示购物车可能变化，应重新读取而不是依赖旧消息；LangGraph 在恢复时重跑节点，状态可能已变 | 【协议要求】MCP；【应用建议】版本校验 |
| **破坏性但参数合法** | **风险审批**，不是“修” | OpenAI `needs_approval`；Gemini 要求重大后果调用先问用户；MCP 敏感操作确认；LangGraph 工具内 interrupt | 【协议/API】+【框架能力】 |
| **副作用结果不确定**：超时、连接中断、审批恢复 | **先对账再决定**，不要静默重试 | OpenAI HITL 要求恢复前 reconcile；LangGraph 要求幂等；LangChain 明确错误中间件不自动重试 | 【应用建议】 |

**一句话规则**：
**能证明“只是表示层差异”才归一；能证明“模型能改对”才回模型；涉及用户意图/不可逆后果就问；涉及权限/结构/策略就拒绝；涉及外部副作用就先对账。**

## 5) 哪些“自动修复”危险或至少无官方背书

| 自动修复 | 风险 | 官方依据/定性 |
|---|---|---|
| **自动批准、自动回答审批、自动恢复 HITL** | 绕过人类意图，可能执行破坏性操作；恢复快照可能被重放 | MCP 要求本地 server 一键配置 **MUST** 先展示完整命令并取得明确同意；OpenAI 要求审批人必须认证、授权，且用原子 owner-check 防止重复恢复；Gemini 要求重大调用先向用户确认。**明确违背官方要求** |
| **静默重试有副作用的调用** | 可能重复下单、重复发邮件、重复扣款 | LangGraph 明确要求副作用可重入；LangChain 明确 tool error middleware **不会自动重试**；Anthropic 对未执行调用要求返回 `is_error` 让模型下一轮再发。**无官方背书，且与主流做法相反** |
| **自动补全缺失参数/猜测用户意图** | 把“不知道”变成“编一个”，可能写错对象 | Gemini 明确要求信息不足时问澄清；SK 的 required 参数设计就是让模型先问；MCP 把输入校验错误回给模型，而不是替模型补。**无官方背书** |
| **放宽 schema、强行把非法值转成合法值** | 掩盖语义错误；可能把错误对象/错误金额写进去 | OpenAI `strict:true` 对不合规 schema 直接拒绝，并建议始终开启；Anthropic strict 也只保证 schema 合规，不保证 enum 大小写；没有官方“自动放宽 schema”机制。**无官方背书** |
| **信任 `readOnlyHint`/`destructiveHint`/`idempotentHint` 自动放行或自动重试** | 不可信 server 可以撒谎；annotation 不是契约 | MCP 官方博客明确：所有 annotation 都是 hint，来自不可信 server 时客户端必须视为不可信；默认假设最坏：非只读、可能破坏、非幂等、开放世界；安全保证应放在确定性控制里。**明确警示** |
| **未知工具自动模糊匹配到“最像的工具”** | 可能调用错误工具，产生副作用 | OpenAI 默认对未知工具抛 `ModelBehaviorError`；MCP 把 unknown tool 归为 protocol error。**无官方背书** |
| **自动重放反序列化的 RunState/审批快照** | 可能重复执行同一批工具调用；快照本身不认证 | OpenAI HITL 明确 `RunState.from_json()` 不认证快照或提交人；必须认证、授权、校验 pending 项、原子消费。**明确警示** |
| **自动执行本地 MCP server 的启动命令** | 任意代码执行、继承用户全部权限、读取 SSH/云凭据 | MCP 安全页要求一键配置 **MUST** 展示完整命令并取得明确同意；本地 server 应沙箱化、限制文件系统和网络。**明确违背官方要求** |
| **自动回滚/自动删除“补偿”** | 可能删掉本不该删的数据；checkpoint 不覆盖外部系统 | LangGraph checkpoint 只保存图状态；OpenAI 明确恢复不等于撤销副作用，生产应用要自行对账；官方文档没有自动补偿/回滚原语。**无官方背书** |
| **自动关闭 guardrail、提高 max turns、忽略 tripwire 以“修复”失败** | 把安全拦截当成故障绕过 | OpenAI guardrail tripwire 触发即抛异常并停止；没有官方“自动降级/自动关闭”建议。**无官方背书，且危险** |

## 6) 可落地的治理分层（只设计，不施工）

### L0 接口/协议层：先把“能调用什么、长什么样”锁死

- 每个工具必须有：`inputSchema`、`outputSchema`、`strict`、`additionalProperties:false`、枚举/范围、必填项。
- 工具默认 `tool_choice` 为 `auto`，高风险场景用 `allowed_tools`/`allowed_function_names` 收窄。
- 统一错误语义：协议错误 vs 工具执行错误；工具执行错误带 `isError`/`is_error`，可回模型；协议错误直接拒绝。
- 调用 ID 全链路透传：OpenAI `call_id`、Anthropic `tool_use_id`、MCP JSON-RPC `id`。

### L1 宿主准入层：每次调用前做“身份 + 权限 + 范围 + 风险”四件事

- 认证调用者，授权到“工具 + 资源 + 操作”，不要只校验“有没有登录”。
- 按用户/租户裁剪工具清单，默认最小权限；高风险工具默认不暴露。
- 风险分级：`read-only` / `additive` / `destructive` / `open-world`；结合 MCP annotation，但**不把 annotation 当安全保证**。
- 审批策略：破坏性、不可逆、跨边界、超额、开放世界工具 → 必须人工批准；审批参数畸形 → fail closed。

### L2 执行层：互斥、并发、超时、首错

- 以“资源键”做单写者队列或租约：同一订单、同一文件、同一账户同一时间只允许一个写操作。
- 只读批量可并行；副作用批量默认串行；破坏性批量首错即停，未执行调用显式返回“未执行”。
- 设置并发上限、单调用超时、整轮预算、取消传播。
- 执行前做前置状态探针：读版本/ETag/状态机，确认仍可执行；不一致则中止并重规划。
- 执行后用 `outputSchema` 校验结果，校验失败不要当成功。

### L3 恢复路由层：把失败分成五类，而不是一个“重试”

| 分类 | 默认动作 |
|---|---|
| 表示层可无损归一 | 归一 → 重新校验 → 记录 |
| 参数可修正、工具幂等 | 带结构化错误回模型，限定重试次数 |
| 用户意图缺失/高风险 | 暂停，问用户/审批 |
| 权限/结构/策略错误 | 硬拒绝，不重试 |
| 外部副作用不确定 | 按幂等键对账；确认未发生才重试，确认已发生则补偿/人工 |
| 状态过期 | 重新读取/重新规划，不拿旧参数重试 |

同时维护：幂等键存储、调用结果缓存、补偿动作注册表、人工对账队列。

### L4 审计与运营层：让每次执行可解释、可回放、可止血

- 追加式审计日志：调用 ID、父 run/thread ID、工具、参数摘要、风险等级、审批人、决策、结果、耗时、错误分类。
- 敏感字段脱敏；审批快照服务端保存，不把完整快照交给浏览器/移动端。
- 指标：审批拒绝率、首错率、重试成功率、幂等命中率、补偿率、越权拦截数。
- 一键停用某工具/某 server/某类调用；保留 kill switch。
- 定期回放与对账：抽查“调用成功但业务未生效”和“业务已生效但调用报错”的两类偏差。

### 工具注册时建议必填的 10 个字段

`风险等级`、`所需 scope`、`是否幂等`、`资源键`、`前置状态探针`、`审批策略`、`超时`、`重试策略`、`补偿动作`、`审计脱敏规则`。

### 默认策略矩阵（应用建议）

| 工具类型 | 并发 | 重试 | 审批 | 首错 |
|---|---|---|---|---|
| 只读、幂等 | 可并行 | 可带退避重试 | 通常不需要 | 可继续并聚合 |
| 追加写、幂等 | 按资源键并行 | 仅带幂等键重试 | 视外部影响 | 可继续 |
| 破坏性、非幂等 | 按资源键串行 | 禁止自动重试 | 必须审批 | 首错即停 |
| 开放世界/可外传 | 默认拒绝或严格限流 | 不自动重试 | 必须审批 + 出口白名单 | 首错即停 |
