### 1.2 结论

**a) 发送 vs 填入：消费级/搜索类主流是"发送"，开发工具倾向"填入"。**
- 点击即发送的典型：Perplexity Related、Gemini Enterprise 的 suggested prompt、Copilot Studio 欢迎页提示、模式库的推荐做法。
- 点击只填入的典型：Claude Code 的 suggested reply（issue #84375 明确"填入后还要单独提交"）。
- 分界线不是"消费 vs 开发"，而是**这一步是否可逆/是否有副作用**：问答、检索类建议可以一击发送；会改配置、会触发工具/外部系统的建议，业界更倾向"填入 → 用户可改 → 再发"。这也解释了为什么 ChatGPT 桌面端把"回复期间的新消息"做成 Steer / Queue 两种显式行为而不是隐式发送（[ChatGPT Learn](https://learn.chatgpt.com/docs/prompting)）。

**b) 每轮是否再出：不是普遍义务，且"每轮都出"正在被用户反感。**
- 真正每轮都出的只有搜索型产品（Perplexity）和部分聊天产品的"文本追问"（ChatGPT/Claude/Gemini 的结尾追问，PCWorld 那篇就是在教用户关掉它）。
- 企业 agent 平台反而克制：Copilot Studio 的建议提示只在欢迎页，官方专门澄清"不是动态 follow-up"。
- 生成方式三档：**静态配置**（Copilot Studio、Gemini Enterprise，运营可控）→ **模型按当前答案生成**（Perplexity、模式库推荐）→ **规则/确定性生成**（Security Copilot 的 "dynamic suggested prompts" 强调 deterministic）。企业内网产品选第一/第三档更稳（可评测、可审计、不会胡说八道地推荐不存在的功能）。

**"每轮增量"几乎没人做主指标**：Claude Code 只在 spinner 旁显示本轮**输出** token，不把它当上下文占用；增量对用户没解释力（用户关心的是"还能聊多久"）。

### 2.2 结论（对本仓最关键的一条）

- **开发者产品的惯例**：总量百分比 + 类目拆分 + 可查命令 + 阈值预警（Claude Code 80% 左右自动压缩、Copilot CLI 约 80% 后台压缩，95% 时短暂暂停）。
- **普通用户产品的惯例**：**默认不显示**，只在"要出事"时用人话提示（"这段对话有点长了，我可能记不住最早的内容"）+ 给"开新会话/总结一下"的动作。
- 本仓受众是普通终端用户 → 常驻百分比是**反惯例**的；token 数字会制造"我是不是快用完了"的焦虑，而用户并不能据此做有效动作。若必须给，给"剩余可用对话轮次/状态灯"这类可行动信号，而不是 `37.2K/128K`。

> 说明：本仓 2026-10-21 的 `_ctx-research/调研-上下文统计与压缩业界惯例` 已把各家计量口径与压缩谱系做得很细，本节只补"**该不该给终端用户看**"这一层，不重复。

## 三、agentic 多步任务推进

### 3.1 a) 一轮走到底，还是每步确认

| 产品 | 默认推进方式 | 什么时候才停 | 来源 |
|---|---|---|---|
| **Claude Code** | 默认 `auto`（后台分类器代替逐次确认），一路做到完 | 只有"任何模式都不自动批"的动作才停：显式 ask 规则、`AskUserQuestion`、`rm/rmdir` 关键路径删除、越界读、组织策略 | [Permission modes](https://code.claude.com/docs/en/permission-modes) |
| **VS Code / Copilot agent mode** | agent loop 自主迭代（读→改→跑测试→再改），用户只看 diff | 权限级别决定哪些工具要批；**默认 25 次请求后暂停问"是否继续"**（`chat.agent.maxRequests`） | [Build with AI in VS Code](https://code.visualstudio.com/docs/copilot/agents/overview)、[AI settings reference](https://code.visualstudio.com/docs/agents/reference/ai-settings)、[v1.97 release notes](https://code.visualstudio.com/updates/v1_97) |
| **ChatGPT agent** | 从任务开始跑到结束，narration 展示进度 | **只在"有真实后果的动作"前要授权**（下单、发布）；发邮件等关键任务要求 Watch Mode；银行转账直接拒 | [Introducing ChatGPT agent](https://openai.com/index/introducing-chatgpt-agent/) |
| **Claude in Chrome / Cowork** | 连续执行，用户可随时接管 | 逐站点授权 + 后果性动作前确认；"自动批准"模式下由独立安全分类器复核每个后果性动作 | [Chrome Web Store 官方描述](https://chromewebstore.google.com/detail/claude/fcoeoabgfenejglbffodgkkbkcdhcgfn)（一手产品页）、[9to5Mac](https://9to5mac.com/2026/08/12/claude-cowork-chrome/) |
| **Devin** | 先给计划，再自主执行到 PR | 计划阶段（可改）；缺凭据、缺环境时主动要 | [Devin Docs · Testing](https://docs.devin.ai/work-with-devin/testing-and-recordings)（"sends you the plan as a short message before executing"） |
| **AG-UI / LangGraph（协议层）** | run 一直跑，直到 `RunFinished` | 只有显式 `interrupt` 才挂起：`tool_call`（工具审批）/`input_required`（缺结构化输入）/`confirmation`（自由 yes/no） | [AG-UI Interrupts](https://docs.ag-ui.com/concepts/interrupts)、[LangChain HITL](https://docs.langchain.com/oss/python/langchain/human-in-the-loop) |

**结论**：**"一轮自动走到底"是绝对主流**；"每步停下来确认"只在低权限模式/高危动作下出现。业界把"中途无故停下"当缺陷而不是稳妥——VS Code 社区就有大量"Copilot 说完计划就停，要我说 continue"的抱怨（[discussion #184524](https://github.com/orgs/community/discussions/184524)）。停顿点收敛为三类：**不可逆/有外部后果**、**缺关键输入**、**预算/步数上限**。

### 3.2 b) 结构化确认卡 vs 文字询问

| 场景 | 业界形态 | 依据 |
|---|---|---|
| 执行有副作用的动作（写配置、发通知、导出到外部、删除） | **结构化卡**，且要"具体"：目标对象、影响范围、参数可编辑、按钮写清后果 | AG-UI `reason:"tool_call"` + `responseSchema` + approve-with-edits（`editedArgs` 全量替换）；LangChain `approve/edit/reject`；NN/g "restate the request, be specific, buttons summarize outcome" |
| 在多个选项中选一个（策略、范围、环境） | **结构化卡**（单选/多选） | Claude Code 的 `AskUserQuestion` 属"任何模式都不自动批"的交互工具；AG-UI `input_required` 必须带 `responseSchema` |
| 开放式补充信息（"这个配置项你们内部叫什么？"） | **文字询问可接受** | LangChain 把 `respond`（自由文本）定义为"ask_user 类工具的合法决策类型"，并警告**不能**用它代替 reject 去否定副作用动作 |
| 一次一批待决 | 一次给全，逐项可决；**不允许"发一张等一张"** | AG-UI「Cover all open interrupts」「Pending interrupts block new input」；Anthropic 要求所有 `tool_result` 同一条消息回灌 |

**"有时出卡、有时文字问"业界怎么评价：负面，但要区分两种"混"。**

1. **同一语义换形态（坏）**：同一个"是否执行导出"的决策，这次出卡、下次文字问"要导出吗？"。这违反一致性启发式，也破坏可预期性；NN/g 的确认对话框研究强调"过度确认会让用户形成自动点 Yes 的习惯"（habituation），形态漂移会加速这一过程。更硬的一条来自 AG-UI：**有 pending interrupt 时，新输入必须携带 resume**——也就是说协议层就不允许"卡还挂着，用户用自由文本回一句"这种混用，否则状态无法对齐（[Interrupts](https://docs.ag-ui.com/concepts/interrupts)）。
2. **按语义分工（好，且是主流）**：**要授权 → 卡；要信息 → 文字/表单**。这是 LangChain 四种决策类型（approve/edit/reject/respond）和 AG-UI 三种 reason 的直接设计意图。判断标准不是"重要不重要"，而是"**这一步是需要一个决定，还是需要一段内容**"。
3. 反模式清单（多家共同指向）：
   - 卡里塞自由文本框却没有 schema / 校验（AG-UI 要求 `responseSchema`，客户端应先校验再提交）；
   - 卡只写"确定/取消"，不复述后果（NN/g 明确批评 `Are you sure?`）；
   - 把多个高危操作打包成一次批准（Microsoft 的 AG-UI HITL 教程明确建议"逐个敏感操作单独批准，不要批量"）；
   - 每个常规步骤都出卡（NN/g：routine 不要确认；Claude Code/VS Code 的默认自治就是对这条的背书）。

## 四、对本仓的建议（企业内部配置工具，受众普通终端用户）

**1. 建议话术（chips）**
- 位置：只在**一轮结束且任务确实可分叉**时出，2–3 个；不要每轮强推，不要出现"再解释一下"这类空话。
- 点击语义按风险二分：
  - 只读/查询类（"看看这个配置影响哪些服务"）→ **直接发送**，与 Perplexity/Gemini 一致；
  - 会改配置/触发导出/影响他人 → **填入输入框并聚焦**（可编辑），用户再按发送。这既符合 Claude Code 的"填入"惯例，也避免"手滑改生产"。
- 生成方式优先**规则/模板 + 上下文槽位**（如"把 `svc-a` 的副本数从 3 改成 5"），模型只负责选模板和填槽；企业内网不要用自由生成的 chip 推荐不存在的功能。每轮刷新、去重，用户忽略两次后自动收起。
- 空态建议（欢迎页）可与"每轮 chip"分开：前者是能力发现（Copilot Studio 模式），后者是任务续接。

**2. 上下文占用**
- **不做常驻百分比**（普通用户产品的惯例是隐藏）。
- 做**两级信号**：① 70% 左右给一次轻提示（"对话有点长了，我可以先总结再继续"）；② 85% 给一次明确动作（"开新会话 / 总结后继续"），并把"已自动压缩、可能忘记早期细节"说清楚。压缩必须**可见**（Claude Code 的 "Compacted"、Cline 的可见摘要 tool call 都是这个思路）。
- 若确实要给数字，放"详情"里给"已用/上限 + 主要占用类目"，不要放在主动线上的常驻位置（Cursor 把百分比从状态栏收进 hover 后被用户抗议，说明"常驻 vs 可查"要按受众选，本仓受众不是开发者，选可查）。

**3. 多步任务（如"导出配置"：预检→导出→完成）**
- **默认一轮走到底**，前端用步骤条/时间线展示 预检→导出→完成，而不是每步一个"继续吗"。
- 只在这三处停：① **写操作前**（导出到外部/覆盖现有配置/影响他人可见范围）出确认卡；② **预检失败且需要用户决策**（缺权限、目标冲突、版本不一致）出带修复项的选择卡；③ **超过步数/时间预算**时暂停并给"继续/停止"（VS Code 的 25 次上限就是这个作用）。
- 预检结果要"具体"：列出将影响的对象数、目标环境、差异摘要；按钮写"导出到 X（覆盖 3 项）"而不是"确定"。

**4. 卡 vs 文字的硬规则（建议写进前端规范）**
- 决策表：**需要授权/在选项中选择/批量逐项处理 → 结构化卡；需要一段自由文本（命名、路径、原因）→ 文字或表单**。
- **同一决策永远同一形态**；卡的类型按 AG-UI reason 对齐（`tool_call` / `input_required` / `confirmation`），前端按 reason 路由到固定组件，不要按"这次感觉"临时决定。
- **有卡挂着时，不接受自由文本推进**：输入框禁用或提示"请先处理上面的确认"（AG-UI 的 pending-blocks-input 规则）。这条能直接消灭"卡和文字各说各话、状态错配"的一类 bug。
- 卡必须可"批准并编辑"（改参数后执行），并保留审计三元组：原始提议 → 用户编辑 → 实际执行结果（AG-UI 的 tool_call 审计链就是这么定义的）。

**5. 不建议照搬的地方**
- 不要照搬开发者产品的 token 明细/`/context` 面板给终端用户；
- 不要照搬"每轮都生成 chip"（Perplexity 是搜索产品，追问就是它的核心循环；配置工具的核心循环是"改对一项配置"）；
- 不要用"文字问一句要不要继续"来代替确认卡（不可审计、无法携带参数、容易与 pending 状态冲突）。
