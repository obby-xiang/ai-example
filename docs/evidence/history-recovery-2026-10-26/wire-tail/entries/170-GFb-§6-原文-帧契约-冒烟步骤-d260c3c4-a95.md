## b) 源码为准的帧契约

`SseFrontendToolRequestFrame`（`frontend/src/types/sse.ts:175-186`）：`type` / `runId?` / `seq?` / `toolCallId` / `name` / `args?`(JSON **字符串**) / `timeoutSeconds` / `expiresAt?` / `callback?`。

- **帧里没有 `sessionId`**：`sessionId` 只出现在 `start` 帧和 `POST /api/ai/chat` 的请求体（`types/ai.ts:32-37`）；回灌体也不带 sessionId（`types/ai.ts:66-73`：`{runId, toolCallId, result?, source?, cancelled?}`）。
- **没有 WebSocket**：`api/sse.ts:1-14` 明确两个通道——`POST /api/ai/chat` 用 `fetch + ReadableStream` 自解 SSE；`GET /api/ai/events/{runId}` 用 `EventSource`（reattach）。`vite.config.ts` 代理显式 `ws: false`。所以"拿 WS 对象 send 帧"这条路不存在。
- `timeoutSeconds`/`expiresAt` 都是**可选**：`stores/ai.ts:665-684` 里 `expiresAt` 优先，否则按 `timeoutSeconds` 折算，两者都缺则 `deadline = null`（不武装本地计时器、无倒计时）。
- `args` 必须是字符串，内容形如 `{"form":{...}}`；`toPendingCall` 会用 `parseToolArgs` 解析（`utils/frontend-tools.ts:125-138`），`openGenerativeForm` 取 `args.form` 交给 `parseFormSchema`（`types/form-schema.ts:106-134`，六型白名单，enum/multi_select 必须 `[{value,label?}]` 非空）。
- **`handleFrame` 的第二个参数决定卡片挂到哪条消息**：`handleFrame(frame, assistantId?)`（`stores/ai.ts:831-834`），§6 未提这个参数，而"两次投递到两条消息"必须用它。

控制台可达性（`window.*` 全仓无调试入口，`grep window.` 仅命中 SpreadJS 注释），但两条可用路径都已验证：

1. Vue 应用容器（dev/prod 都行，`__vue_app__` 在 runtime-core 的 `mount()` 里是无条件赋值）：`document.getElementById('app').__vue_app__.config.globalProperties.$pinia._s.get('ai')`（`_s: new Map()` 已在 pinia 2.3 产物中确认）。

## b) 可直接粘贴的冒烟步骤

前置：`cd frontend && yarn dev` 起前端（默认 `http://localhost:5200`），后端按需（要 200/DUPLICATE 闭环才必须）。打开任意页面，点页头「显示 AI 栏」（`App.vue:23`，AiPanel 在右侧 aside，收起时看不见卡片）。

取得 store、准备帧（`<RUN_ID>`/`<TOOL_CALL_ID>` 可任意 UUID 字符串，纯前端冒烟用；要与后端闭环就必须用真实 run 的值）：

```js
const ai = document.getElementById('app').__vue_app__.config.globalProperties.$pinia._s.get('ai')
ai.expanded = true

const FRAME = {
  type: 'frontend_tool_request',
  runId: '<RUN_ID>',
  toolCallId: '<TOOL_CALL_ID>',
  name: 'generative_form',
  timeoutSeconds: 120,
  expiresAt: Date.now() + 120000,
  args: JSON.stringify({
    form: {
      scenario: 'FILTER',
      title: '导出筛选条件',
      fields: [
        { key: 'keyword', label: '配置编码关键词', type: 'text', required: true, placeholder: '如 DOC_TYPE' },
        { key: 'limit', label: '最大行数', type: 'number' },
        { key: 'includeDisabled', label: '包含停用', type: 'boolean' },
        { key: 'asOfDate', label: '数据日期', type: 'date' },
        { key: 'level', label: '层级', type: 'enum', options: [{ value: 'high', label: '高' }, { value: 'mid', label: '中' }] },
        { key: 'tags', label: '标签', type: 'multi_select', options: [{ value: 'a', label: 'A' }, { value: 'b', label: 'B' }] }
      ]
    }
  })
}
```

两次投递（同一 `toolCallId`，落到两条不同的 assistant 消息）：

```js
const m1 = ai.appendAssistantMessage('（冒烟①）')
ai.handleFrame(FRAME, m1.id)

const m2 = ai.appendAssistantMessage('（冒烟②）')
ai.handleFrame(FRAME, m2.id)

// 客观计数（不靠肉眼数）：
;[...document.querySelectorAll('button')].filter(b => b.textContent.trim() === '提交').length  // 期望 2
ai.messages.filter(m => m.pendingCall?.toolCallId === FRAME.toolCallId).length                 // 期望 2
ai.activeForm.toolCallId === FRAME.toolCallId                                                 // 期望 true（仅一份）
```

肉眼核对清单：

| 看什么 | 预期 |
|---|---|
| 消息流 | 多出 2 条助手消息，各挂一张灰底卡片；卡头「生成式表单」+ 蓝色 tag「自动」（`AiPanel.vue:169-175`） |
| 表单卡内容 | 两张卡各自完整渲染六型控件；标题「导出筛选条件」、scenario tag「筛选条件」（`FormRenderer.vue:5-6,145`）；两卡倒计时**同刻同值**跳变（共享同一 `activeForm.deadline`） |
| 共享同一 activeForm 的证据 | 在卡①填值→卡②控件**不同步**（值模型是组件本地 `ref`，`FormRenderer.vue:138`），但**提交中 loading、错误文案、倒计时、取消后的状态 tag 两卡一致**（都读 `ai.activeForm`）；在 console 改 `ai.activeForm.error = 'X'` 两卡同时显示 |
| 点卡①「取消」 | 两张卡同时收起为 tag（`liveForm=null` ⇒ `v-if` 两条都变 false）；因 `ai.activeForm.status==='cancelled'`，**两卡都显示** tag「表单已取消」（`AiPanel.vue:215`，这里读的是全局 `ai.activeForm`，不是各自的 `pendingCall`） |
| Network → `frontend-tool-result` | 取消/提交各发一次 POST；body 形如 `{runId:'<RUN_ID>',toolCallId:'<TOOL_CALL_ID>',cancelled:true,source:'http-post'}` 或 `{...result:'{"keyword":"DOC_TYPE",...}',source:'http-post'}`（**注意 cancelled 分支不带 result**，`stores/ai.ts:614-618`） |
| 无真实挂起条目时的回灌 | HTTP **409 `UNKNOWN_TOOL_CALL`**（后端 `AiController.java:242-243`）；卡内出现 `取消回灌未送达（未知或已过期的 runId/toolCallId），后端将在超时后自动收尾` 或 `提交失败：未知或已过期的 runId/toolCallId（可重试或点「取消」放弃）`，且回填 `filling` 态 |
| 结局帧收敛（关键观察） | 投递一次 `{type:'frontend_tool_result', runId:'<RUN_ID>', toolCallId:'<TOOL_CALL_ID>', name:'generative_form', ok:true, executed:false, status:'FRONTEND_RESULT'}`（`ai.handleFrame(结局帧, m1.id)`）：**只有被投递的那条消息**清掉 `pendingCall`（挂起块整块消失），`activeForm` 置 null ⇒ 另一张卡降级为 tag「表单状态已丢失（刷新后无法续填），等待后端超时收敛」。对 m1、m2 各投一次结局帧，两卡才同时消失 |
| 本地超时 | 把 `expiresAt` 设为 `Date.now()+8000` 重做，8 秒后两张卡同时收起并自动发一次 `cancelled:true` 回灌（`stores/ai.ts:678-684`） |

后端"重复提交 409 幂等封顶"的**正确触发方式**（重要）：两次投递同一个 `frontend_tool_request` 帧**不会**产生 409——409 只发生在回灌 POST 上，且只有服务端**确实持有该 `(runId, toolCallId)` 挂起条目**时才会是幂等码。要看到真正的封顶，用一条真实轮次产生的 `runId`/`toolCallId`（从 DevTools Network 里 `POST /api/ai/chat` 的 SSE 响应体或 `GET /api/ai/events/{runId}` 的流里复制那段 `frontend_tool_request` JSON，改造成上面的 `FRAME`），然后：

```js
await ai.submitFrontendToolResult('<TOOL_CALL_ID>', '{"keyword":"DOC_TYPE","limit":10,"includeDisabled":false,"asOfDate":"2026-10-07","level":"high","tags":["a"]}', 'http-post', false, '<RUN_ID>')
// 第 1 次：200 {accepted:true,duplicate:false,status:'FRONTEND_RESULT'} → {ok:true}
await ai.submitFrontendToolResult('<TOOL_CALL_ID>', '{"keyword":"DOC_TYPE"}', 'http-post', false, '<RUN_ID>')
// 第 2 次：409 {code:'DUPLICATE_TOOL_CALL_ID',status:'FRONTEND_RESULT',duplicate:true} → {ok:false,duplicate:true} + notice「该工具结果已回灌过（幂等拒绝）」
```

- 后端分支事实源：`ConfirmGate.java:346-364`（`pending==null`→NOT_FOUND→409 `UNKNOWN_TOOL_CALL`；状态非 `PENDING`→DUPLICATE→409 `DUPLICATE_TOOL_CALL_ID` 带 `status`；回灌值不合 schema→400 `FORM_RESULT_REJECTED`，状态不变仍 `PENDING`）。
- 前端分流：只有 `DUPLICATE_TOOL_CALL_ID` 走 `duplicate:true` + notice「幂等拒绝」；`UNKNOWN_TOOL_CALL` 落通用失败分支（`stores/ai.ts:620-636`）——两者都是 409 但语义不同，别混淆。
- 取消两次同样封顶（第 2 次 notice「该工具调用已是终态（幂等拒绝）」，`status:'FRONTEND_CANCELLED'`）。

清理（避免 sessionStorage 镜像残留污染后续观察）：`ai.resetSession()` 后刷新页面，或直接关标签页。

## c) §6/红队 描述与当前源码不一致处（以源码为准）

1. **传输通道**：任务背景里的"WebSocket/帧协议"在源码中不成立。本项目**没有 WebSocket**——chat 是 `fetch` POST + ReadableStream（`api/sse.ts:312-373`），reattach 是 `EventSource`（`api/sse.ts:401-518`）。因此"从 Network 面板复制帧改 toolCallId 重放"这条替代路径**可行**（帧就是 SSE 的 `data:` JSON 文本，出现在 `chat` 的流式响应体或 `events/{runId}` 流里），但不存在"复制 WS 帧再 `ws.send()`"的玩法。
2. **§6 漏了 `handleFrame` 的 `assistantId` 参数**。双卡必须把两帧分别投给两条不同消息；只调 `currentAssistantMessage()` 会把两帧落到同一条消息上（第二次只是就地覆写 `pendingCall`，永远只有一张卡）。操作口径以 GFc §7 O1 建议 A 为准。
3. **§6 说"帧必须自带 `runId`/`timeoutSeconds`/`expiresAt`"**：源码里只有 `runId` 是实质必需（`frame.runId ?? this.activeRunId`，两者皆空才走取消收敛，`stores/ai.ts:653-664`）；`timeoutSeconds`/`expiresAt` 缺省时只是不武装本地超时与倒计时，表单照样渲染（`stores/ai.ts:665-684`；`AiPanel.vue:399-404` 返回 `null`）。
4. **文档时效（最需要注意的一条）**：GFb 复核 §3 与 `GFb-红队审查-DS-V4-Pro.md` 的"问题 1（`activeForm.runId` 全仓零读点）"在当前源码**已不成立**——`stores/ai.ts:700`/`:730` 现在把 `form.runId` 作为第 5 参直传（`:606-608` 注释写明"GF-B 修复（红队问题 1）"），且 `ActiveGenerativeForm` 里已无 `messageId` 字段（`types/ai.ts:232-242`）。红队问题 2（断流不清表单态）也已修（`stores/ai.ts:426`、`:548` 两处收尾出口）。这些修复在 commit `8f5c2a3`（"含红队修复 7 项"）落地，而 GFb/红队文档写于 `b41784a` 之上的未提交工作区，所以两份文档的这一条已过期；冒烟时按当前源码行为预期（回灌 runId 来自表单捕获值，不会错配到新 run）。
5. **一个不影响执行的表述差异**：§6 写"args 为含 form schema 的 JSON 字符串"是对的，但 `openGenerativeForm` 实际优先取 `message.pendingCall.args`（已被 `parseToolArgs` 解析成对象）而不是重新解析 `frame.args`（`stores/ai.ts:651`）——两者同源，结果一致。
