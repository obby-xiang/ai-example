## 4. 综合判断

**不成立。** 「resume → confirm 门再挂起 → 取消」后，history（=记忆）里不存在「A(T) 无紧随 TOOL」的可达形态。链：

1. 一切传给 `SpToolCallingManager.executeToolCalls` 的 `prompt` 都不含本跳的 A(T)（上游 1.1.8 `OpenAiChatModel.internalStream` 用 `executeToolCalls(prompt, response)`，下一跳才用 `conversationHistory()`）→ `saveSuspended`（`RunStore.java:366`）写下的 messageJson 恒为「完整配对序列」；本跳 A(T) 另存 `inFlightToolCalls`。
2. resume 重建是 A(T')+T' **同批**落 messageJson（`ResumeService.java:302,320,321`），其后 `driveResumed` 的首跳 prompt 就是这串（`:341-345`）。
3. 再挂起的 messageJson 因此仍以完整对收尾；取消用 `snapshot.getMessageJson()` 收敛（`ResilientChatService.java:522,530`），**不删不加** → 记忆尾部以 TOOL 收尾。
4. 记忆另外两个写点也无害：advisor 只在首轮写 USER/纯文本 assistant；`trimKeepingToolPairs:600-609` 只从**头部**丢且不裸 TOOL，尾部分配对不受影响。

**「整对丢弃」是否存在？→ 存在，但形态是「整跳从不入史」而非「删掉半条」**：取消命中正在进行的一跳（含 confirm 门挂起）时，该跳的 A(T)+T **都没进** messageJson/记忆（`SpToolCallingManager.java:169/192` 早于 `settle:198-203`）。极端子情形值得留档：同一跳内**多工具**时先执行的兄弟工具（如 BACKEND 已落台账、有副作用）其结果也只留在 `ai:ledger`，模型侧历史完全看不到这一跳——这是保真度缺口，不是「悬空 A(T)」。另外已提交进 messageJson 的完整对，任何取消路径都不删除（`cancelTerminal` 无删除逻辑；`ResumeService:244-253` 的 ALREADY_CANCELLED 早退连 messageJson 都不碰，但**也不收敛记忆**）。

附带观察（超出本问、未实证）：`MessageWindowChatMemory` 官方裁剪只从头部按 max=40 丢单条（`process()`），若窗口恰在 40 上限，下一轮 advisor `before` 追加 USER 后可能把头裁成 **TOOL 开头**（方向与本问相反）。`convergeMemory:600-609` 的配对保护只作用于自己那一次写入，不兜住这次官方裁剪——是否可达需另行实证。
