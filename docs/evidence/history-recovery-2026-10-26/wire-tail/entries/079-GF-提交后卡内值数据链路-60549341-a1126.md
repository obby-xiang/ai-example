### 已提交展开时显示空值的条件

按可能性排序：

1. **结局帧先于 POST 应答（主因，后端顺序决定）**
   后端在 HTTP 请求处理中先写 `resultText`、发 `frontend_tool_result` 帧，再返回 HTTP 响应：`AiController.java:260-275` 调 `ConfirmGate.submitFrontendResult`，`ConfirmGate.java:486-492` 内先 `setResultText`、`frontendToolResult(...)` 发帧、`signal` 唤醒。前端收到帧后 `applyFrameToParts` 把段置 `succeeded + requiresAction:false`（`utils/parts.ts:440-467`），`activeForm` 清空（`stores/ai.ts:2823-2831`），只读卡随即挂载。此时 `part.submittedValues` 还是 `undefined` → `readOnlyFormValues` 返回 `null` → `model` 回落 `buildInitialValues`。随后 POST 返回，`writeSubmittedValues` 才把值写段（`stores/ai.ts:2274-2278`），但组件已挂载且不响应 prop。
2. **`v-show` 让只读体在折叠时也已挂载**：`AiPanel.vue:331` 是 `v-if="isReadOnlyCard(part)" v-show="isBlockExpanded(block)"`。所以即使当时卡是折叠的，`FormRenderer` 也已经以 `null` 完成 setup；之后用户再展开不会重新取值。
3. **写回失败/写错宿主**：`writeSubmittedValues` 用 `this.messages.find(...)` 找**第一条**含该 `toolCallId` 的消息（`stores/ai.ts:2221-2224`），而 `AiPanel` 的宿主是**最后一条**仍在途的挂起消息（`AiPanel.vue:1535-1553`）。代码注释明确承认同一 `toolCallId` 可能残留在多条消息上；若首条不是渲染卡所在消息，值会写到另一段。
4. **取消/超时**：`readOnlyFormValues` 按 F9 返回 `null`，刻意不保留半成品值（`AiPanel.vue:2754-2759`）。这是设计，不是缺陷。
5. **值形状不符**：`initialModel` 只接受严格类型（`FormRenderer.vue:260-287`）。number 传成字符串、enum 值不在 options、multi_select 非数组等会被丢弃，回落初值。
6. **历史 JSON 解析失败**：`JSON.parse` 失败兜底 `undefined`（`stores/ai.ts:1177-1185`），只读卡回落初值。GF 正常提交是 `JSON.stringify`，概率低。

### 空值具体长什么样（按字段类型）

| 字段类型 | 缺 `submittedValues` 时的显示 |
|---|---|
| text / date | 空串 |
| number | 空 |
| boolean | `false`（开关显示为关） |
| enum | **第一个选项**，不是空（`types/form-schema.ts:160-167`） |
| multi_select | 全部未勾选 |

所以「选择导出任务」如果 是 enum，用户看到的可能不是空，而是**被重置成第一个导出任务**；如果是 multi_select，则是全不勾选。两者都容易被读成“数据丢了”。

### 一个可区分的验证点

提交后看**折叠卡头摘要**：`cardSummary` 对已提交 GF 走 `generativeFormSummary(part)`，实时读 `part.submittedValues`（`AiPanel.vue:2432-2440`、`:2712-2719`）。如果**卡头摘要已经出现提交值、展开后字段却是空/默认值**，就锁定是“只读卡 setup 快照未重灌”，不是数据面丢失。
再刷新页面：历史链路会在挂载时直接带入值（`stores/ai.ts:1177-1185`），字段应恢复。若刷新后仍空，才需要查 history 响应里的 `toolCallStates[toolCallId].submittedValues` 是否为空/解析失败。

## 二、只读/已提交字段的 DOM 与视觉

### 当前 DOM

| 字段类型 | 元素 | 只读属性 |
|---|---|---|
| text | `<input type="text">` | `:disabled="disabled"` |
| number | `<input type="number">` | `:disabled` |
| date | `<input type="date">` | `:disabled` |
| enum | `<select>` | `:disabled`（不是可点击 select，是原生 disabled select） |
| boolean | 原生 `<input type="checkbox">` 绝对定位覆盖自绘 track/thumb | checkbox `:disabled`；track/thumb 无 disabled 样式 |
| multi_select | `<label>` 胶囊包原生 checkbox | checkbox `:disabled`；胶囊只加了 `cursor-default` |

`disabled` 判据在 `FormRenderer.vue:304`：`props.readonly === true || props.submitting || expired`。只读态下 `submitting=false`、`remainingSeconds=null`，所以纯粹由 `readonly` 锁定。

**没有** DOM `readonly` 属性，**没有** `aria-readonly`（grep 零命中），**不是**纯文本渲染。`readonly` 只是组件 prop（`FormRenderer.vue:208`）。所有控件是原生 `disabled`，语义上不可聚焦、不可编辑。

### 具体 Tailwind 类

`FormRenderer.vue:232-241`：

- `FI_BASE`：`w-full border rounded-[8px] px-[9px] py-[6px] ... text-[#1f2328] [outline:none] ... focus:border-[#2563eb] disabled:cursor-default`
- `FI_DISABLED`（提交中/超时）：`disabled:bg-[#f6f7f9] disabled:text-[#8b949e]`
- `FI_READONLY`（已决只读）：`disabled:bg-white disabled:text-[#57606a]`
- `FI_IDLE`：`border-solid border-[#e3e6ea] bg-white`
- `fieldClass` 在 `:362-365` 组合：只读 = `FI_BASE + FI_READONLY + FI_IDLE`

也就是说，只读输入框：

- 背景仍是 `bg-white`，不是灰底；
- 边框仍是 `#e3e6ea`，与待填写完全一致；
- 文字从 `#1f2328` 变成 `#57606a`，仅此而已；
- 没有 `disabled:opacity-*`、没有虚线、没有锁图标；
- 光标是 `cursor-default`，不是 `not-allowed`。

对比之下，**提交中/超时**用的 `FI_DISABLED` 反而有灰底 `#f6f7f9` + 更灰的字 `#8b949e`，视觉上比“已提交只读”更像禁用。这是“只读不像禁用”的直接原因。

布尔开关更明显：`:63` 的 checkbox 只有 `disabled:cursor-default`，`:68-77` 的 track/thumb 只按 `model[field.key] === true` 上色，**完全不读 disabled/readonly**。所以锁定的开关看起来和可操作时一模一样。
多选胶囊 `:104-110` 只加 `readonly ? 'cursor-default' : 'cursor-pointer'`，选中态仍是蓝底蓝字，原生 checkbox 被 disabled 只影响那个小方框。
只读卡正文里也**没有「只读」文字/锁图标**；唯一提示是卡头的 `✓ 已提交` 状态标签和摘要（`AiPanel.vue:320-325`、`:2432-2440`）。
