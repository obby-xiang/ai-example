## 发现的缺陷（未改 src，均为登记项）

1. **F-1（P2）String 返回型工具结果被二次 JSON 编码**：`role=tool` 里 `message` 是再编码字符串（模型看到 `\"<knowledge>\\n…`），KB 三工具全部命中；证据 `stub/req-004.json`（`message` 首字符为 `"`，需再 parse 一次）。
2. **F-2（P2）主/降级两实例共用相对 KB 目录**：harness 让两个后端同 cwd 起，`app.ai.kb.dir/index-dir` 相对路径相同 ⇒ Lucene `write.lock` 竞争，落后方要等 10m 刷新周期才就绪（我这一棒首跑即命中，`backend.log` 有 `write.lock` 失败行）；本域 `beforeAll` 用 `POST /api/ai/kb/reload` 兜底并已注释说明。
3. **F-3（P2）`kb_read_doc` 页大小与结果限流器口径冲突**：`max_chars` 上到 8000，但 `ToolResultLimiter` 以 200 行做 head 截断，截断后 `</knowledge>` 与 `[truncated/next_offset]` 尾巴一起丢失 ⇒ 模型按 `next_offset` 翻页会**漏读**被截掉的那段（`originalChars=6560 / returnedChars=5126` 实测）。
4. **F-4（P3）`CONTEXT_OVERFLOW` 用户可见文案是上游原文**：`code` 分类正确，但 message 为「上游返回 HTTP 400：{…}」，没有指向「上下文超窗 / 压缩」的可行动提示（设计稿要求「文案指向压缩而非网络」）。
5. **F-5（P2）压缩分母有两个来源**：`ContextCompactor` 的触发判定用 `AiProperties.Context.limitTokens`（过渡键），而 `/context`、`/health`、压缩日志用 `ContextLimitResolver`（DB `ai_model.max_context`）。我这一棒把过渡键设 1500、DB 仍 128000，日志同时出现 `limit=128000` 与 `ratio=1.258`（分母 1000）—— 两者漂移时「显示的百分比」与「触发百分比」会不一致，与「分母单点」的设计承诺冲突（证据：`.e2e-run-kqc-compact/backend.log`）。
