## 1. SSE 推流与慢订阅者（R1）

**现状摘要**
- 发射端是**自研 `SseChatEmitter`**（每个 runId 一个，由 `RunRegistry` 持有）；一帧广播给本轮全部订阅者（`Vector`/`CopyOnWriteArrayList`）。首轮响应由 `AiController` 建 `new SseEmitter(budgetMillis())` 并 `attach()`；reattach 经 `GET /api/ai/events/{runId}` 新建 emitter + `replayAndAttach()`。
- **出帧全串行**：`emit()` 在 `emitLock` 内完成「取号 → 落归档 → 遍历订阅者逐个同步 `send`」，同一把锁还覆盖 `replayAndAttach` 的交接。
- **写失败处理**：`sendTo` 吞掉一切异常（IOException / AsyncRequestNotUsable / 已 complete）→ DEBUG 日志 + 从 subscribers 摘除，**不冒泡、不打断运行线程**；`attach` 注册的 `onCompletion/onTimeout/onError` 也只做摘除。
- **无细分超时/缓冲/丢弃策略/背压**：唯一的超时是 `SseEmitter(timeout)` = `resilience.total-budget`（300s），到点只是移除订阅者；没有发送队列，TCP 背压会**阻塞运行线程**。
- **heartbeat**：挂起期 `ConfirmGate` 每 **2s** 一帧（`confirm/frontend-tool` + waitsSeconds + timeoutSeconds）；流式期 `ResilientChatService` 每 ≥**5s** 一帧（`phase=streaming/attempt/upstreamEvents`）。心跳帧**不占业务 seq、不入归档**（T7），只写 `ai:beat:<runId>` 活动戳。
- **emitter 与 gate 生命周期**：`RunRegistry` 只做进程内 `runId→emitter` 注册；终态由 `AiController.chat` 的 finally / `ResumeService` 调 `registry.close(runId)` 收尾。挂起期 HTTP 线程已返回，`ConfirmGate`/`SpToolCallingManager` 用 `registry.of(runId)` 继续写心跳与后果帧；进程重启后 `of()` 惰性新建「零订阅者」emitter，帧照落归档。

## 2. 事件 seq 与持久化（R2）

**现状摘要**
- 帧归档在 Redis LIST `ai:events:<runId>`：`appendEvent` → rightPush + `trim(-3000,-1)` + TTL=**app.ai.session-ttl（6h）**；帧补 `atMs`；**心跳帧直接跳过归档**。
- **seq 单调、跨进程续号**：`nextSeq()` 首帧前惰性读 `RunStore.lastEventSeq(runId)`（LRANGE -1 -1 取归档末帧 `seq`），归档为空从 1 起；心跳走独立 `heartbeatSeq`（不占业务号，避免把续号锚点顶前）。
- **全部键**：`ai:run:<runId>`（快照 JSON）、`ai:runs`（SET 索引）、`ai:pending:<runId>`（HASH）、`ai:claim:<runId>`、`ai:ledger:<runId>`、`ai:events:<runId>`、`ai:beat:<runId>`、`ai:session:current:<sessionId>`。

## 4. 预检查后替换窗口

**现状摘要**
- 流程是**两阶段（预检查 → 替换），但不是两阶段锁**：`PRECHECK` 作业核验上传件，`IMPORT`/`PUBLISH` 各自独立作业；之间只由 `JobService.assertPrecheckPassed` 把关。
- 闸门口径（**从严**）：IMPORT/PUBLISH 前必须存在**最近一次** `status=COMPLETED && errorCount==0` 的 PRECHECK，否则 409 `PRECHECK_NOT_PASSED`；另有同类互斥 `JOB_ALREADY_RUNNING`（同 task+同 jobType 在 PENDING/RUNNING → 409）。两者都在**作业落库之前**抛，不留 PENDING 僵尸行。
- **判据只看"最近一次 PRECHECK 的状态"，不看文件身份**：`PrecheckJobRunner` 在作业执行时按 `task_files(UPLOAD 或 EXPORT)` 读盘，`ImportJobRunner` 在导入执行时**再次按 `task_files` 读盘** → 预检查读完到导入读盘之间，上传件可被替换而旧结论仍放行。代码注释已明文承认这是「已知边界」。
- **无锁/无版本锚定**：上传与替换走 `task_files` upsert，与 PRECHECK 之间没有 hash/mtime/version 绑定；PUBLISH 侧唯一的并发保护是**行级** `baseVersion` 快照（导入时刻记录、发布前比对），管的是"行被并发改过"，不是"文件被换过"。
- REPLACE 模式的范围差集删除用 staging 行 `createdAt` 作 `importedAt` 做保护（行级），同样不覆盖文件替换。

- 触发：`loadHistory` → `restoreSuspendedSnapshot`，仅在 `found && runId && awaitingExternal` 时重建挂起卡并以 `lastSeq = archiveMaxSeq` 调 `resumeSnapshotStream`（禁全量回放）。

### 6b 后端 `/runs/current` 对死闸门
**现状摘要**
- `GET /api/ai/runs/current?sessionId=` **只读 Redis**：`sessionCurrentRunId` → 快照 → `pendings` → `lastEventSeq`；**没有任何"闸门是否活着"的判定**。
- `RunRegistry` 只有 `of/find/close`，**无查活闸门方法**；`ConfirmGate` 只暴露 `pendingGates()`（计数）与 `signal()`，`latches` 是私有 `Map<"runId|toolCallId", Latch>`，无按 runId 查询。
- 索引 `ai:session:current:<sessionId>` TTL = `app.ai.session.lock.ttl`（10m），由 `ConfirmGate` 心跳 `renewSessionCurrent` 续期；**死闸门后最长 10m 内索引仍在** → 返回 `found:true` + `snapshotStatus=SUSPENDED` + `awaitingExternal`（按 pendings 可能为 true）+ `archiveMaxSeq=N`，**与活闸门不可区分**。
- 索引过期或快照已消失 → 明确空态 `found:false`（含 `archiveMaxSeq:0`）。三分支语义（TIMEOUT / FRONTEND_RESULT / 进程已死）已在测试中锁定。

### 6c ConfirmGate / HITL 确认卡挂起轮的构造方式
**现状摘要**
- **没有任何前端交互能"直接造出"CONFIRM 类挂起**：CONFIRM 类 `PendingToolCall` 只由**模型调用 DANGER 风险工具**触发。DANGER 工具（`create_task` / `start_export` / `start_precheck` / `start_import` / `start_publish`）经 `SpToolCallingManager.kindOf`（`riskOf == DANGER` → `KIND_CONFIRM`）判定。
- 时序：先 `saveSuspended`（硬规范①：外置先于阻塞）→ 发 `suspended` 帧 → 挂起循环 → `awaitConfirm` → `ConfirmGate.await` 发 `confirm_request` 帧并阻塞（每 2s 心跳）。前端 `stores/ai.ts` 在 `confirm_request` 帧上建挂起卡（`AiPanel.vue:181` 渲染"需确认"），用户点按钮 → `aiApi.confirm`（`stores/ai.ts:754`）→ `POST /api/ai/confirm`。
- **手工 `POST /api/ai/confirm` 不可行（无前置挂起时）**：`submitDecision` 先 `store.pending(runId, toolCallId)`，null → `NOT_FOUND` → **409 `UNKNOWN_TOOL_CALL`**。前置状态必须是：`ai:pending:<runId>` HASH 里存在该 toolCallId 且 `status=PENDING`（即真有一轮挂在中间）。实测旁证：`docs/evidence/S42-P2-挂起续跑会话门验证.md:347`（空 key 下 POST confirm 也是 409）。

**T3 运行验证建议构造路径**
- ① **桩上游强制 tool_call**（推荐，无需 key）：`scripts/ci/stub-upstream.mjs` 已支持按路由吐 `tool_calls` 帧，且已有 `start_publish` 工具轮用例（`:700`）。走真实 `POST /api/ai/chat` 让 DANGER 工具真实挂起 → 得到 `confirm_request` + Redis PENDING 条目。
- ② 复现 S42-P2 的实模型路径（需 `AI_API_KEY`），证据形态见 `docs/evidence/S42-P2-挂起续跑会话门验证.md:164-173`（`confirm_request` → 心跳 → `confirm_decision` → `tool_result` → `done` 原文）。
- ③ **观察"死闸门/零帧"不需要 POST confirm**：挂起后直接 kill 进程（或等闸门所在进程死）再 `GET /api/ai/runs/current` + 前端刷新，即是最小复现：`found:true/awaitingExternal:true` 但无任何新帧。
- 构造注意：同一 session 第二轮会 409 `SESSION_BUSY`（携 runId）；整轮受 `total-budget` 300s 与 `hitl.timeout` 120s 限制；测试后需 `POST /api/ai/cancel/{runId}` 清理（否则未决条目留 Redis）。

**设计约束/风险（本节）**
- 【实测】`/runs/current` **无法区分"活着的挂起"与"进程已死的挂起"**（只要索引未过 10m TTL），S2-1 的候选方案 2 缺的正是这个判据。
- 【实测】前端零帧超时链路合计约 **90s+1s+90s+2s+90s ≈ 4.5 分钟**才提示，且**只提示不收敛卡片**（聚合时长为【推断】，各段常量与重连次数为【实测】）。
- 【推断】若走候选方案 2（后端死闸门判定），最省事的实现是复用 `ConfirmGate` 增一个 `hasLiveGate(runId)`（latches 按 `runId|` 前缀扫或加一份 `runId→count` 索引），并在 `/runs/current` 里把"索引在但无活闸门 + 快照 SUSPENDED"判为 `found:false` 或 `entry expired`；否则前端仍要等 4.5 分钟。
- 【实测】构造 CONFIRM 挂起轮**必须**经过真实挂起路径（模型/桩驱动），无法用一次手工 POST 造出 PENDING 条目；T3 验证卡需明确这条前置，否则用例会被 409 `UNKNOWN_TOOL_CALL` 挡在门口。
