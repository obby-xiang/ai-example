## 1. 结论先行

业界**普遍分通道**，但分法不是"给两条通道各设一个数字"，而是三层结构：

1. **数据模型层**：一个工具结果对象内部再切出一份"模型可见载荷"和一份"仅 UI/调用方可见载荷"（同源双形态）。
2. **传输层**：两个数值各有各的约束来源——模型侧受 context/token 预算约束，UI 侧受帧/消息体积约束。**单位不同（token/字符 vs 字节），因此不存在"固定倍数"惯例。**
3. **溢出层**：超过模型阈值时不做硬截断，而是把全量落到可寻址存储，模型拿 handle + 预览，UI 拿全量或同一 handle。

"8 倍"这个比例在业界找不到对应惯例；能被观察到的惯例是"各按各的约束定值 + 阈值可配 + 溢出走引用"。

---

## 2. 分通道的实证

| 系统 | 模型通道 | UI / 私有通道 | 官方依据 |
|---|---|---|---|
| **MCP** | `content`（text/image/audio/resource_link/embedded resource）+ `structuredContent` | 无独立通道；大对象通过 `resource_link` 走**引用**而非内联 | [MCP Tools 规范](https://modelcontextprotocol.io/specification/2025-06-18/server/tools) |
| **OpenAI Apps SDK / MCP Apps** | `content` + `structuredContent`（"Surfaced to the model and the component"） | `_meta`（"Delivered only to the component. **Hidden from the model**"） | [Apps SDK reference](https://developers.openai.com/apps-sdk/reference) |
| **LangChain** | `ToolMessage.content` | `ToolMessage.artifact`（"Additional data **not sent to the model**… raw results… without cluttering the model's context"） | [LangChain Messages](https://docs.langchain.com/oss/python/langchain/messages) |
| **Vercel AI SDK** | `ModelMessage` + 每工具的 `toModelOutput`（"map to tool result content for LLM consumption"） | `UIMessage`（前端渲染与持久化的"source of truth"） | [AI SDK Tool Calling](https://ai-sdk.dev/docs/ai-sdk-core/tools-and-tool-calling)、[消息持久化](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-message-persistence) |
| **Pydantic AI Harness** | `ToolReturn.content`（模型可见） | `ToolReturn.return_value`（程序/UI 用），两者用**同一套 band 规则分别裁剪** | [Tool Output Limits](https://pydantic.dev/docs/ai/harness/tool-output-limits/) |
| **AG-UI**（反例） | `ToolCallResult.content` 单一载荷，既渲染又进历史 | 无 | [AG-UI Events](https://docs.ag-ui.com/concepts/events) |

两点值得注意：

- **MCP 规范本身不设任何结果大小上限**，把限制留给客户端/传输实现；但它明确给了"大对象走引用"的机制（`resource_link`），并要求"a tool that returns structured content **SHOULD** also return the serialized JSON in a TextContent block"——即**双形态同源**是规范级要求，不是最佳实践。
- **AG-UI 是单通道设计**：一个 `content` 同时用于渲染和回灌模型，也不定义上限。说明"分通道"是宿主实现的选择，协议层并不强制。

## 3. 数值惯例（可比的只有模型侧）

| 系统 | 模型侧阈值 | 备注 |
|---|---|---|
| **Claude Code** | `MAX_MCP_OUTPUT_TOKENS` 默认 **25,000 tokens**，超过 **10,000 tokens** 就警告；bash 输出"middle-truncated"；文件读取另有独立 token 上限 | 见 [Claude Code settings](https://docs.claude.com/en/docs/claude-code/settings) |
| **Gemini CLI** | `tools.truncateToolOutputThreshold` 默认 **40,000 字符**（0/负数=禁用） | 见 [Gemini CLI configuration](https://geminicli.com/docs/reference/configuration/) |
| **Pydantic AI Harness** | 默认 **10,000 字符**触发 spill；示例 band 为 5k Truncate / 20k Summarize / 100k Spill | 见上表链接 |
| **MCP** | 无上限（客户端自定） | 规范不设 |

换算一下：8,000 字符 ≈ 2,000 tokens，**明显低于**业界模型通道 10k–25k tokens（约 4 万–10 万字符）的常见区间；40,000 字符 / 25,000 tokens 大致是"能装下一整个文件或一段构建日志"的量级。所以本仓的 8000 更像是"早期为了安全拍的保守值"，而不是业界口径。

UI 通道 64KB 本身处于合理区间（前端一次渲染 64KB 文本已偏大，SSE 单帧这个量级也常见），问题不在数值，而在**语义**（见第 5 节）。

---

## 4. 一致性契约：业界怎么保证两边不打架

1. **同源裁剪（single reduction）**：只裁一次，两边引用同一结果。Pydantic 明确"measures and reduces **both** `return_value` and `content` with the same band logic"；MCP 要求结构化结果同时给一份等价的文本 JSON；AI SDK 用 `toModelOutput` 从同一个 `output` 派生模型视图。反模式是"模型侧裁一刀、UI 侧再裁一刀"，两边标记无法对齐。
2. **结构化结果禁止字符截断**。Pydantic 原文："Structured / nested returns spill (or summarize) by preference — **truncating JSON produces invalid JSON**"。JSON 只能字段级裁剪或整体 spill。
3. **截断标记必须显式且确定性**：
   - 标记本身计入预算（"Markers and all retained characters count toward `max_chars`"）；
   - 策略可枚举：`head` / `tail` / `head_tail`（默认）/ middle（Claude Code bash）；
   - 要给出**总量**与**续读方式**（handle + offset / `read_tool_result(handle, offset, limit, from_end, pattern)`）。
4. **模型侧与 UI 侧字段名对齐**：Apps SDK 明确只有 `content`/`structuredContent` 进对话记录，`_meta` 不进；并提示"Keep fields concise; the model reads them verbatim"——即模型侧要主动写短，而不是靠传输层砍。
5. **UI 上限应是"帧/事件级"而非"数据级"**：超限时正确做法是分片或改引用，绝不能把 SSE 帧静默截成半截 JSON。

---

## 5. 「大结果先落地、模型只拿摘要+引用」——成熟模式确实存在

四种成熟度，从轻到重：

- **引用替代内联**：MCP `resource_link`（URI + annotations，客户端按需 fetch）。
- **UI 私有车道**：Apps SDK `_meta`、LangChain `artifact`——全量数据直接进前端，模型完全看不到。
- **Spill + handle + 预览 + 分页读回**：Pydantic `ToolOutputLimits` 的 `Spill` 模式（**默认策略**："Spill(then=Truncate()) at a 10,000-character threshold: lossless when a store accepts the write"），模型拿到 handle、预览和顶层 shape sketch，再用 `read_tool_result` 按行/偏移回读。据其文档，这是"the Claude Code pattern"。Claude Code 对应实现是 per-tool `maxResultSizeChars`，超限写盘并给模型"预览 + 路径"（见 [issue #78478](https://github.com/anthropics/claude-code/issues/78478) 中的真实报错文本 `Output has been saved to .../tool-results/...`，注意这是 issue 证据而非官方文档）。
- **LLM 摘要**：Pydantic 的 `Summarize` band——一次真实模型调用、计入 usage，代价最高，只适合"20k 以上且必须压缩"的场景。

对"取样数据"类工具，最契合的是第 3 种：**全量样本落盘/落库，模型拿 schema + 前 N 行 + `total`/`returned` + handle**，UI 拿全量渲染。这样 64KB 与 8000 都不再是瓶颈。

---

## 6. 对本仓的对齐方案建议

**(a) 两个数值是否合理**

- 模型侧 8000 字符：**偏保守**，低于业界 10k tokens 量级。建议改为"可配置阈值 + 按工具分类分档"，默认 10k–20k 字符，保留 8k 作为"未知工具"的兜底档。理由是 Claude Code 已经证明"按工具分档"（bash / 文件读 / MCP 各不相同）是常规做法。
- UI 侧 64KB：**数值合理，但要重新定义语义**——它是"单条 SSE 事件的 payload 上限（按字节计）"，不是"工具结果的数据上限"。

**(b) 是否该联动**

**不该按固定倍数联动**，因为两者单位与约束来源不同（模型侧最终是 token，UI 侧是字节）。应该联动的是**溢出策略**，不是数值：

```
原始结果 R
 ├─ R > 模型阈值  →  spill(R) → 模型拿 {handle, 预览, total, schema}
 ├─ R ≤ 模型阈值  →  模型拿 R
 └─ R > UI 帧上限 →  分片多帧 或 直接推 handle（前端自行 fetch 全量）
```

配置上收敛到**一个 `ToolResultLimits` 配置对象**（`modelChannelChars` / `uiFrameBytes` 两个字段独立可调），禁止两处硬编码常量——这正是 AI SDK（`toModelOutput`）和 Pydantic（同一 band 逻辑双裁剪）的统一入口思路。

**(c) 截断标记契约（建议直接落成字段）**

```json
{ "truncated": true, "strategy": "head|tail|head_tail|middle",
  "originalChars": 200000, "returnedChars": 8000,
  "handle": "tool-result://run/<runId>/call/<callId>", "offset": 0,
  "notice": "…[truncated: 200000 chars total, showing first 8000; read full via handle]"
}
```

要求：
1. 模型侧与 UI 侧**用同一套字段名**，`truncated` 在两侧都必须是布尔真相，不允许 UI 侧为 false 而模型侧为 true；
2. 结构化结果不发字符截断，改字段级降采样（`total` / `returned` / `sampleStrategy`）；
3. 标记长度计入阈值（避免"标完还超限"）；
4. 中文/emoji 场景一律按 **UTF-8 字节**计，不按字符——否则 64KB 字符上限会在 transport 层被字节上限提前砍断。

**(d) 一致性测试（防未来失控的护栏）**

- 断言：`modelPayload` 恒为 `uiPayload` 的前缀或可重建子集，且 `truncated` 标记一致；
- 断言：UI 在 64KB±1 字节边界不产生非法 JSON / 半帧；
- 断言：任一结构化工具结果在超限时要么 spill、要么字段降采样，**不出现非法 JSON**；
- 断言：spill 后的 handle 可被 `read_tool_result` 风格的分页接口读回，且分页结果拼起来等于原始结果（Pydantic 的做法是预置 `json_lines`/`indented_json` 序列化器保证"行=记录"，值得借鉴）。

### 一句话版本

业界主流是「**一份结果、两套呈现、各按各的预算定值、超限走引用而非硬砍**」：模型通道 10k–25k tokens（≈4 万字符）是常态，UI 通道 64KB 量级合理但应定义为帧上限；8 倍关系没有先例，应解除倍数耦合，改为"可配阈值 + 共享配置源 + 统一截断字段 + spill handle"。
