## 19. 「复制页签」的 per-tab 会话隔离：**别指望导航类型，用「会话 id 所有权握手」**
- **结论先行**：业界没有能区分 duplicate / restore 的官方 API；成熟解法是**不判断来源、只判断"这个 session id 是否已有人持有"**——sessionStorage 里放一个 per-document 的 `pageId/TabId`，加载时用 **BroadcastChannel**（无该 API 时回退 localStorage `storage` 事件）向同源其它文档发"SEARCH"，有应答即为副本；接管策略（换新 id / 只读 / 提示 / 接管旧页签）由产品自定。原生首选原子原语是 **Web Locks API**。
- 你观察到的 `back_forward` 有官方旁证：Chromium bfcache-dev 邮件列表明确写"**duplicate tab / 退出浏览器后重开 tab，`performance.getEntriesByType("navigation")[0].type` 都是 `back_forward`**；Firefox 同、Safari 保持原类型"（[chromium bfcache-dev](https://groups.google.com/a/chromium.org/g/bfcache-dev/c/Cs5ISWbKhKU)）；MDN 也说明"复制一个 back/forward 导航到新标签时，**某些浏览器会沿用原标签的导航类型**"（[MDN notRestoredReasons](https://developer.mozilla.org/en-US/docs/Web/API/PerformanceNavigationTiming/notRestoredReasons)）→ **导航类型只能证明"两者都不可区分"，不能作判据**。
- **a. BroadcastChannel 占有握手**：可靠性高、延迟毫秒级、结构化消息；**硬边界是"必须等一个超时窗口才能下结论"**——unique-tabid 的实现把等待设为可配置、**默认 1 秒**，并自曝"调试器断点可能打乱该流程"（[unique-tabid](https://github.com/YussufSassi/es5-unique-tabid)）。leader election 是它的成熟变体（[pubkey/broadcast-channel 自带 leader-election，无 BroadcastChannel 时回退消息选举](https://github.com/pubkey/broadcast-channel)、[purrtabby](https://github.com/let-sunny/purrtabby)、[Tab Leader Pattern](https://dev.to/smy/browser-tab-leader-pattern-stop-wasting-api-calls-across-browser-tabs-173k)），但选举只回答"谁干活"，不回答"谁是副本"，语义要自己补。
- **b. window.name + nonce**：语义清楚（**同标签内跨导航保留、新开标签为空**，所以常被拿来装 per-tab id），但我**未找到权威文档说明"复制标签页是否复制 window.name"**——属于需要本地实测的项；因此**不建议单独作判据**，只作"同一标签内稳定"的辅助信号（可信度：低）。旁证是 Mozilla 的同类讨论把"复制 sessionStorage"当作 target=_blank/rel=opener 的行为来处理（[Bugzilla 818389](https://bugzilla.mozilla.org/show_bug.cgi?id=818389)）。
- **c. storage 事件**：**不能用来检测 sessionStorage 被复制**——`sessionStorage` 的 `storage` 事件**不跨标签/窗口**（只有同标签内 iframe 会收到，[use-session-storage-state 文档](https://github.com/astoilkov/use-session-storage-state)）；要跨标签收到事件必须写 **localStorage**（代价：全局污染 + 需清理 + 自己写入不触发事件），因此它在本案里只能当 BroadcastChannel 的**降级 fallback**（[SitePoint 的 fallback 实现](https://www.sitepoint.com/javascript-broadcast-channel-api-tab-sync/)）。
- **d. pageId/tabId 库（最有价值的一手先例）**：`unique-tabid` 文档化地为 duplicate 而生——加载时查 sessionStorage 是否已有 TabId：**没有 = 新标签（生成）；有 = 要么是刷新（保留），要么是被复制的副本（必须换新 id）**，通过 BroadcastChannel `SEARCH`/`FOUND` 握手确认，并**返回 `isNewTab` 与 `parentTabId`**（[README](https://github.com/YussufSassi/es5-unique-tabid)）。更强的行业先例是 **Epic on FHIR 的 OAuth2 文档**：明确要求"若应用把 tab-specific 数据存入 session storage，必须用 unique tabId 分桶（`sessionStorage.setItem(tabId, ...)`）"（[Epic on FHIR OAuth2](https://fhir.epic.com/Documentation?docId=oauth2)）——医疗级授权流程把 duplicate tab 当必答题。
- **e. Google/GitHub 等自家产品**：**未找到针对 duplicate tab 会话隔离的公开工程博客**（诚实标注：无一手来源）。可观察的证据是两条路线：① **服务端参与**——OutSystems 社区推荐的成熟做法是"sessionStorage 放 TabToken，服务端库存同值，不匹配就登出"（[OutSystems](https://www.outsystems.com/forums/discussion/103025/automatically-logout-in-duplicate-tab-ana-new-tab/)），ABP 的 SPA OIDC 也给出同族建议（state/nonce 按标签隔离、避免多标签同时走认证流，[ABP](https://abp.io/support/questions/9518/Validating-accesstoken-failed-wrong-statenonce)）；② **不隔离而共享**（Figma/Google Docs 类协同编辑器是同文档多标签共存，工程细节无公开博客）。另有安全侧的明确案例：复制标签会让 **access/refresh token 出现两份**（[InfoSec SE](https://security.stackexchange.com/questions/276952/duplicate-of-chrome-tabs-causes-stale-tokens)）。
- **f. "检测 sessionStorage 被复制"的专门技巧**：**没有官方 API**；唯一被文档化的技巧就是 **a+d 的组合（BroadcastChannel 占有查询 + sessionStorage 存 TabId）**，其余可用信号都不足以判定：`back_forward`（你也测到，duplicate 与 restore 同值）、`pageshow.persisted`、`visibilityState`（恢复的标签通常 visible）都只能当辅助。关键补充事实：**Chrome 的"重开已关闭标签"会连带恢复 sessionStorage**（Chromium `session_restore.cc` 用 persistent id 调 `RecreateSessionStorage`，[Chromium review](https://chromiumcodereview.appspot.com/10572015/patch/2001/3001)）→ **restore 与 duplicate 在存储层"同样带着旧值"，所以永远分不开，只能靠握手定所有权**。另外记住**复制标签必然复制 sessionStorage**是规范/实测双重确认的行为（[MDN content issue #3688](https://github.com/mdn/content/issues/3688)、[DEV 实测表](https://dev.to/bharathvaj_ganesan/what-happens-to-sessionstorage-when-you-duplicate-a-tab-431h)）。

### 方案对比（可靠性 / 边界）

| 方案 | 检测 duplicate 的可靠性 | 与「重开已关闭标签」的可区分性 | 崩溃/异常恢复 | 快速连击（连按两次 duplicate） |
|---|---|---|---|---|
| **BC 握手 + sessionStorage TabId**（unique-tabid 同款） | 高，但**依赖超时窗口**（默认 1s；断点/冻结标签会漏答） | **不能区分**（两者都带旧 TabId），需按产品策略统一处理 | 内存态全失，重载后重新握手即可 | 两个副本可能互不见（时序竞争），需加随机退避/二次广播 |
| **Web Locks `ifAvailable` 竞标**（+BC 广播） | 高且**原子**，同一瞬间只有一方拿到锁（[dev.to](https://dev.to/grimicorn/the-web-locks-api-one-tab-does-the-work-the-rest-wait-12om)、[mironsoft](https://www.mironsoft.de/en/blog/javascript-web-locks-api-for-tab-coordination)） | 同上（锁不问来源） | **免费 failover**：文档销毁即释放；但锁**不持久**、`steal:true` 只该当救援手段 | **最佳**：原子性天然抗连击 |
| **localStorage + storage 事件**（BC 的 fallback） | 中：事件可靠但**自己写入不触发**、需用值比对/时间戳去重 | 不能区分 | 会残留 stale claim，需心跳+过期 | 中（事件排队可能合并） |
| **window.name + nonce** | **未验证**（复制行为无权威文档） | 不能区分 | 随标签销毁 | 低（无协调机制） |
| **服务端 TabToken 校验** | 高（服务端裁决，最接近唯一真相） | 不能区分（可加策略） | 好（服务端可撤销、可过期） | 好（服务端串行化） |
| 导航类型 / pageshow 信号 | **不可用**（duplicate 与 restore 同为 back_forward） | 不可区分 | — | — |

### 本案推荐（一句话）
**用「sessionStorage 存 pageId + BroadcastChannel 握手（无 BC 时回退 localStorage storage 事件）+ Web Locks `ifAvailable` 做原子去重」的三层组合：握手有应答或锁竞标失败即判定本页是副本，然后按产品策略"接管旧页签并换发新会话 id"（这样重开已关闭标签也能正常恢复），并把超时窗口设成 300–500ms（而非 1s）以兼顾首屏速度。**
