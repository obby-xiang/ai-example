## 0. 自证与结论先行

**自证**（取自本 agent wire 的 `profile.bind` 事件行，非首行 metadata）：

**五条结论（其中 3 条修正/补强设计稿，请指挥官先看）**

1. **租约必须覆盖「挂起等待期」，不能只覆盖「续跑期」**——否则设计稿 §5-2 第 1 条（挂起在 A、决策落 B → 恰一次续跑）在结构上不可能成立。理由：A 的等待循环每 2s 轮询 Redis 发现「已决」后会**在原地继续驱动本轮**（`ConfirmGate.java:359-395` 返回 fresh → `SpToolCallingManager.awaitConfirm:580` → `executeOnce`），此时若 B 只凭「本进程无 latch + 快照 SUSPENDED」就抢到租约并 `resume`，同一轮会被两个实例同时驱动（`claimExecution` 只挡得住工具副作用，挡不住第二轮模型调用与双份帧）。所以：**等待方持租**，抢不到的决策方只落决策。

2. **`submitDecision` 本身就是跨实例读-判-写非原子**（`ConfirmGate.java:621-652`：锁外 `store.pending()` → 改状态 → 锁内 `putPending` 全量覆写）。看板 `:402` 已经点过「与既有 `submitDecision` 锁外读 + 全量覆写同族」。若不修，「双决策并发 = 一次执行一次拒」这条验收无法证明（现状两边的 HTTP 都会回 `accepted:true`）。**建议批②纳入**（与 M-2 同一套「单写者」修法，见 §2.5）。

3. **`ai:claim:` 与租约不是同一原语**：claim 是一次性、无 TTL、永不释放的认领（`RunStore.java:461-475`，`HSETNX` 已原子）；租约是 TTL + 续租 + 释放。设计稿「值从 instanceId 改 epoch」可以照做，但**不要**把 claim 变成「永不释放的租约特例」（会引入特殊分支）。建议：claim 保留 `HSETNX`，只是把值改成 `<epoch>|<instanceId>`，`claimedBy()` 剥前缀（`ToolFrameSequenceConformanceTest:180` 的 `claimedBy == instanceId` 断言因此零改动）。

4. **构造器加参不会「爆所有测试点」**：`new ConfirmGate(...)` 共 **13 处 / 10 个文件**，其中只有 **2 处**用 8 参 `@Autowired` 构造器（`ConfirmGateDeadlockResumeTest:90`、`:235`）；其余 11 处用 6 参兼容构造器。只要**新增 10 参 `@Autowired` 构造器、把现有 8 参降为委派 null 的兼容构造器**，13 处全部零改动。`ConfirmGateWiringTest`/`SpToolCallingManagerScopeGuardTest`/`ToolOutcomeExitTest`/`AiControllerHistoryDeleteTest` 用的是 `mock(ConfirmGate.class)`，与构造器无关。**建议走这条**（不用字段注入的黑魔法，虽然 `AiController:134-141` 有字段注入先例）。

5. **E2E 口径基准是 29 不是 31**：`scripts/verify-e2e.ps1:2/41` 明写「29 个用例计入 PASS/FAIL 与退出码（TC1–TC22 + GF1–GF5 等），Q8 两项单列不计」。设计稿 §5-3 的「E2E 31 用例」是陈旧表述，建议顺手改文档。

## 二、施工方案要点

### 2.1 LeaseService 设计

**包位置**：`backend/src/main/java/com/example/configmgr/ai/run/LeaseService.java`（与 `RunStore`/`ResumeService` 同包，`ai/run/`；L1 批③的 `ai:lock:task:` / `ai:lock:job:` 复用同一实例，无需跨包）。

```java
public interface LeaseService {
    /** 抢占：空键 → 新建 epoch；同实例已持有 → 返回同一 epoch（可重入）；他人持有 → null。 */
    Optional<Lease> tryAcquire(String key, Duration ttl);

    boolean renew(Lease lease, Duration ttl);      // GET 比对 epoch 后 EXPIRE
    boolean release(Lease lease);                  // GET 比对 epoch 后 DEL
    long heldEpoch(String key);                    // 0 = 本实例未持有（进程内视图）
    void markDriving(Lease lease);                 // 由「等待期心跳续租」切到「调度器续租」
    boolean leaseOk();                             // /health 自检（一次 PING/一次 EVAL 探针）
}
public record Lease(String key, long epoch, String owner) { }
```

**Lua（三支，`DefaultRedisScript` 静态常量，仿 `RedisChatMemoryRepository.DELETE_WITH_INDEX:71-74`）**

```lua
-- ACQUIRE（KEYS[1]=leaseKey, ARGV[1]=epoch, ARGV[2]=ttlMs）
local cur = redis.call('GET', KEYS[1])
if cur then return cur end                       -- 已被持有：返回现值（调用方比对 owner 决定可重入）
redis.call('SET', KEYS[1], ARGV[1], 'PX', ARGV[2])
return ARGV[1]

-- RENEW（KEYS[1], ARGV[1]=epoch, ARGV[2]=ttlMs）
if redis.call('GET', KEYS[1]) ~= ARGV[1] then return 0 end
redis.call('PEXPIRE', KEYS[1], ARGV[2]); return 1

-- RELEASE（KEYS[1], ARGV[1]=epoch）
if redis.call('GET', KEYS[1]) ~= ARGV[1] then return 0 end
return redis.call('DEL', KEYS[1])

-- FENCED SET（runEpoch 写回校验；KEYS[1]=runKey, KEYS[2]=fenceKey, ARGV[1]=epoch, ARGV[2]=json, ARGV[3]=ttlSec）
local f = redis.call('GET', KEYS[2])
if f and tonumber(f) > tonumber(ARGV[1]) then return 0 end
redis.call('SET', KEYS[1], ARGV[2], 'EX', ARGV[3])
redis.call('SET', KEYS[2], ARGV[1], 'EX', ARGV[3])
return 1
```

抢占脚本返回「现值」而非 1/0，是为了把**可重入**（同 owner 再抢）与**占用拒**（他 owner）合并成一次往返：Java 侧拿到现值后判断 `owner.equals(this.instanceId)` 即可（L3/L2 同一支脚本覆盖）。

**epoch 生成方式**：建议 **全局单调 `INCR ai:lease:epoch`**（无 TTL，单键）。
- 不建议「每租约键各自 INCR」：租约键过期/被 `deleteRun` 删后计数键也会过期 ⇒ epoch 回绕，fencing 失效（ABA）。
- 不建议「UUID+序列」：不可比较大小，fence 的 `>` 判据就没了。
- 全局单键的代价：一次额外的 `INCR`（与 `ai:seq:` 同型，量级可忽略）。键永不过期（常量级 1 个键）。

**挂起期/驱动期续租**：`LeaseService` 内置单线程 `ScheduledExecutorService`，对 `markDriving` 的租约每 `ttl/3`（10s）续一次；
- **等待期**由 `ConfirmGate.await` 的 2s 心跳续（线程活着 = 有活人，活人死了 = 不续，租约 30s 后自然失效 → 他实例可接管）。这条与设计稿「数据 TTL 不依赖挂起线程」不冲突：数据 TTL（24h）靠读侧 touch，租约 TTL（30s）**必须**依赖活性。
- 释放点：`RunStore.save` 检测到 `RunSnapshot.isTerminal(status)` 时 best-effort `lease.release(runId)`（该处已有终态分支，`RunStore.java:207-209`），外加 `deleteRun`/取消路径。

**配置**：`AiProperties.Lease{ ttl=30s, renewInterval=10s, retryDelay=35s }`。

### 2.2 `ai:claim:` / `ai:resume:lock:` 归并步骤（建议：一个一步到位，一个只升值）

| 键 | 归并方式 | 理由 |
| --- | --- | --- |
| `ai:resume:lock:<runId>` → `ai:lease:run:<runId>` | **一步到位替换**（改键名 + 值 = epoch + 走 Lua） | 全仓读者只有 `ResumeService:438-468` 自己（grep 确认无外部读取、无测试锚定该字符串）；新旧并存反而制造「两套锁假拒」——正是勘察结论 1 要消灭的。部署形态是**进程重启**（非滚动），不存在新旧实例并行窗口；harness 两实例同 jar。 |
| `ai:claim:<runId>` | **保留 `HSETNX` 原子性，只把值升为 `<epoch>\|<instanceId>`**；不改成 TTL 租约 | claim 语义是「一次性、永不释放」的认领（SP-02 E2），与「TTL+续租+释放」不同原语。改成租约要么造「永不释放」特例，要么引入「认领过期 ⇒ 二次执行」的新风险。升值的收益是让 claim 可被 fence 校验（`claimedEpoch` 进 `PendingToolCall`）。 |
| `ai:fence:run:<runId>`（新增） | 随 `save` 写入，TTL 随快照 | 写回校验的锚，见 2.1 第四支脚本 |

**兼容顺序**：批②提交时同时做「键名替换 + fence 键上线 + claim 升值」，并在 `describe()`（`ResumeService:205-206` 的 `keys` 映射）里把 `claim` 旁增 `lease`/`fence`，让运维端点直接可见（取证成本最低）。旧键 `ai:resume:lock:` 残留无害（TTL 到期自清），不做迁移。

### 2.3 `maybeTriggerResume` 改造伪码

「抢不到 = 只落决策不执行」的落点：**决策此刻已经落完**了 —— `submitDecision` 在调用 `maybeTriggerResume` 之前已经完成「`putPending` → `confirm_decision` 帧 → `signal`」三件事（`ConfirmGate.java:648-653`，`submitFrontendResult`/`dismiss` 同构）。因此抢不到时**不需要再补写任何状态**，只需：①不派发续跑；②回一个精确结论；③安排一次延迟重试（救 holder 已死的场景）。

```java
private ResumeTrigger maybeTriggerResume(String runId, boolean woke) {
    if (woke) return ResumeTrigger.skipped("WOKE_IN_PROCESS_GATE", null);       // 不变：本地快路径
    if (hasActiveLatch(runId)) return ResumeTrigger.skipped("ACTIVE_LATCH_IN_PROCESS", null);
    RunSnapshot snapshot = this.store.get(runId);
    if (snapshot == null || !RunSnapshot.SUSPENDED.equals(snapshot.getStatus()))
        return ResumeTrigger.skipped("SNAPSHOT_NOT_SUSPENDED", ...);
    if (leaseService == null) { /* 单实例/降级：原逻辑（派发不带 token） */ }

    Lease lease = leaseService.tryAcquire(leaseKey(runId), ttl).orElse(null);
    if (lease == null) {
        log.info("决策已落库，续跑权在别处 runId={}（本实例不驱动）", runId);
        scheduleLeaseRetry(runId);                     // retryDelay 后重来一次；holder 活着则 ARLEADY_RUNNING
        return ResumeTrigger.skipped("LEASE_HELD_ELSEWHERE", "另一实例持有续跑租约");
    }
    try { this.resumeTriggerExecutor.execute(() -> runResume(runId, lease)); }
    catch (RejectedExecutionException ex) {
        leaseService.release(lease);                   // 派发失败必须还租约，否则 30s 内谁都跑不了
        return ResumeTrigger.skipped("EXECUTOR_SATURATED", ...);
    }
    return ResumeTrigger.dispatched();
}

private void runResume(String runId, Lease lease) {
    if (hasActiveLatch(runId)) { leaseService.release(lease); return; }   // 既有复查保留
    ResumeService service = provider.getIfAvailable();
    if (service == null) { leaseService.release(lease); return; }
    ResumeService.ResumeResult r = service.resume(runId, false, lease);    // 带 epoch 重载：不再自己抢锁
    if (r.outcome() != ACCEPTED) leaseService.release(lease);              // ACCEPTED ⇒ 交棒给驱动到终态
    log.info("死卡兜底续跑结局 runId={} outcome={} epoch={}", runId, r.outcome(), lease.epoch());
}
```

要点：
- **ACCEPTED 不释放**：续跑把 `suspendExecutor` 的任务交出去，租约由 `markDriving` 转调度器续租，终态时由 `RunStore.save` 释放。非 ACCEPTED 一律当场释放（否则 `IN_PROGRESS`/`PENDING_UNRESOLVED` 之后 30s 真空）。
- `ResumeService` 侧新增 `resume(runId, forceTakeover, Lease)`：跳过 `acquireResumeLock`，改为「校验 `lease.epoch() == heldEpoch(runId)`」；`finally` 里的 `releaseResumeLock` 改成 `release` 只在「本方法真正获得了独占」时执行（旧签名自抢的情况）。
- 旧签名 `resume(runId)` / `resume(runId, boolean)` 保留，内部改为「`tryAcquire` → 调重载 → 未 ACCEPTED 则 release」。`StartupResumeRunner:143` 与 `AiController:540` 因此自动获得 fencing，零改动调用点。
- `Outcome` 增 `LEASE_HELD_ELSEWHERE`；`AiController:541-548` 的 `switch` 落在 `default` → 409，符合「运维端点复跑被别的实例占用」的语义。

### 2.5 `markRequestEmitted` 原子化 + `:389` 误路由的承接

**M-2 修法（建议 A：独立位 hash + `HSETNX`，`pending` 行保持单写者）**

```
ai:req:<runId>      HASH  field=toolCallId  value=<atMs>     ← HSETNX，首写者胜
ai:decided:<runId>  HASH  field=toolCallId  value=<status>|<atMs>|<instanceId>   ← HSETNX，兼作决策 WAL
```

- `markRequestEmitted` 不再读改写 pending JSON，只 `HSETNX ai:req:`；`pending()`/`pendings()` 读出后**合并** req 位（一次 `HGET`/一次 `HMGET`）。
- `submitDecision` 先 `HSETNX ai:decided:` 抢决策权：抢到才写 pending（唯一写者）；抢不到 → 读 pending：已决 → `DUPLICATE`；仍是 PENDING（有人抢了 guard 却死在写 pending 前）→ 按 guard 里的值补齐（R5 的 WAL 语义）。
- **为什么不用 cjson 在 Lua 里改 JSON**：`cjson.encode` 会把大整数编码成 `1.79e+12` 之类的浮点，`reqAtMs/claimedAtMs` 精度必丢；仓内 JSON 反序列化是 `long`，一旦丢精度就是静默数据损坏。
- **WATCH/MULTI 乐观事务**是可行替代（同键结构、不改读侧），但要在 Spring 连接池上做 `SessionCallback` + 重试循环，复杂度高于「多一个小 hash」。
- `markRequestEmitted` 用 `HSETNX` 后 **L0 的 M-1「写后复判」可以删掉**（`ConfirmGate.reserveRequestSlot:451-455` 的复判不再是必需；保留也无害，建议保留注释说明它已退化为兜底）。

**`:389` 误路由的承接关系**（两件事一起才闭环）：
1. **等待方持租**（§2.3 G1）＝ 「另一实例正在等人」这件事第一次有了跨进程判据 —— 旧代码只有进程内 `hasActiveLatch`（`:802`），这正是看板 `:389` 说的「跨实例仍裸」。
2. **抢不到只落决策**（G3）＝ 决策不再引发第二个驱动者。
3. **M-2/决策原子化**（R1/R4）＝ 两个实例同时收到同一张卡的决策时，只有一个能落库、只执行一次。
4. 结论：`:389` 与 `:402` 在批②由**同一把租约 + 同一套单写者**收口；`:389` 不再需要「探测对方是否在等」的额外机制。

**其余风险（登记即可，不需裁决）**
- 租约 30s TTL 意味着「holder 被杀 → 最长 30s 空窗」（叠加 retry 约 35-40s）；这是 fencing 的固有代价，若嫌长可把 TTL 调到 15s（renew 5s），代价是心跳/调度更频繁。
- 等待期租约靠等待线程续：若等待线程被中断但 JVM 活着，租约 30s 后失效 → 他实例可接管，而旧线程的 `finally` 会尝试 release（epoch 已换，L6 保证不会误删）。这是刻意选择的可恢复一侧。
- Redis Cluster 迁移：`ai:lease:*`、`ai:fence:*` 全是单 key 脚本，Cluster 安全；`ai:decided:`/`ai:req:` 也单 key。与 `RedisChatMemoryRepository` 的多 key 脚本约束不同，无需 hash tag。
- 首轮（未挂起）的驱动权仍靠「`RUNNING` + 僵尸年龄 + `claimExecution`」三重兜底，不含租约 —— 若要求「运行权全覆盖」，属批③/后续（登记为范围外）。
