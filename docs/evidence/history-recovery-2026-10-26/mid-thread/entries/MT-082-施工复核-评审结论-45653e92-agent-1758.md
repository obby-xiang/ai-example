## Critical（必须修，阻断验收）

### C-1 确认判定读"本地模式"，与后端真实模式可背离 ⇒ REPLACE 发布不弹确认

- 位置：`frontend/src/views/ImportWizardView.vue:995`（`confirmPublishByMode(importMode.value)`）、`:1188-1200`（`onImportModeChange` 失败只弹错、**不回滚** `importMode`）、`frontend/src/stores/workspace.ts:444-453`（`resolvePublishImportMode` 的 `catch { return 'MERGE' }`）。
- 后果：`PublishJobRunner.resolveImportMode` 是**作业执行时读 settings_json**（`PublishJobRunner.java:338-355`），页面本地 `ref` 只是副本。以下任一情形都会"本地 MERGE / 服务端 REPLACE"：
  1. 用户把 REPLACE 切成 MERGE，`PUT /tasks/{id}/import-mode` 失败（网络/500）——单选已随 `v-model` 变成 MERGE，页面却提示"设置失败"，此时点「发布」**零确认**，后端照 REPLACE 删范围内旧行；
  2. 另一标签页/实例改了模式（本仓有双实例脚本），本页副本陈旧；
  3. `resolvePublishImportMode` 读 `getTask` 抛错时 `catch → 'MERGE'`，`run_job` 路径零确认直接 `createJob`。
- 这是**确认门的 fail-open**，不是文案问题；新测试只覆盖"模式读成功"的理想路径，锁不住它。
- 修法（最小且统一）：确认前用**权威值**判定，且未知一律**fail-closed**。
  ```ts
  // workspace.ts:444 — 读不到不等于 MERGE
  async function resolvePublishImportMode(taskId: number): Promise<ImportMode> {
    try { return readImportMode(await tasksApi.getTask(taskId)) ?? 'MERGE' }
    catch { return 'REPLACE' }   // 未知 ⇒ 按会删数据对待（弹确认），或直接 fail 掉不建作业
  }
  ```
  页面侧（`startPublish`）改为同样按 `taskId` 重新读一次再确认；并在 `onImportModeChange` 的 `catch` 里把 `importMode.value` 回滚到 `readImportMode(task.value) ?? 'MERGE'`（成功后同步 `task.value`）。
- 配套用例：`setImportMode` reject 后点发布 → **仍弹确认、取消即零 createJob**；`getTask` reject 的 `run_job` → 仍弹确认（或明确"未启动"）。

### I-4 成功回执在"未离开第 1 步"时给出两句假话

- 位置：`ImportWizardView.vue:1300`（`index` 可为当前步或更早步）、`:1319-1324`。
- 当 `confirm_step` 传入的 `step` 等于当前步（模型常说"确认这一步"）或回退步时：`goStep` 不触发 flush（`:866-878` 只在 `next > stepIndex && stepIndex===0`），于是回执输出「**已推进到**…」+「**本次未写回服务端文件（没有可写回的编辑区内容）**」——既没推进，也可能明明有未写回编辑。这正是本轮新加的 `writeNote` 引入的新假话。
- 修法：按 `index` 与 `stepIndex` 关系分支：`index === stepIndex` → "步骤未改变：当前已在「X」"；`index < stepIndex` → "已回退到「X」，本次未触发写回"；只有真正 `index > stepIndex && 原 stepIndex===0` 才输出 writeNote，其余情况写"本次未从第 1 步离开，未触发整表写回"。
