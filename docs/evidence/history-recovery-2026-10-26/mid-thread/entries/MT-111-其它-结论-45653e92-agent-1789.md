### C1. A6 抛异常发生在“认领已写、执行未做”之间 → 永久假认领，用户被告知“已执行”

`<REPO>/backend/src/main/java/com/example/configmgr/ai/run/RunStore.java:1252-1266`

顺序是：`HSETNX claimKey`（1252）→ `expire`（1253）→ `pending(runId, toolCallId)`（1258）→ A6 `decisionMarker` 读失败**抛**（`:993` 调用，`:1025` 起抛）。

后果链（已逐处核对）：

1. claim 记录已落（TTL = `ttlFor` = session-ttl，24h）；
2. `pending()` 抛 `IllegalStateException`，`tryClaimExecution` 不回滚、不捕获；
3. `SpToolCallingManager.claimAndExecute` 的上层 `catch (RuntimeException)` 调 `traceToolAborted`（`:721`）→ 里面又调 `store.pending(...)` → **A6 再抛**，原始异常被替换，连 `tool_call_end` 日志行都写不出（正是该函数想消灭的“孤儿 start”）；

- `traceToolAborted` 改为容错读（读不到就用入参 `pending`），诊断路径不得改变原始异常类型。

## Important

### I1. A4 的降级回读仍会“错窗 + 少帧”，且 `lastSeq`/号回退修复仍把读失败折成 0

`RedisFrameStore.java:326-346`、`:369`、`:169`

- 末号探测失败时 `from = max(afterSeq, 0)`；`afterSeq==0`（首次回放/前端 `lastSeq=null`）走 `Range.unbounded()` + `COUNT window` ⇒ XRANGE 升序只取**最旧**窗口。这正好违反上一段自己写的 M′ 理由（“否则拿到的是最旧的窗口条，被丢掉的反而可能是含终帧 `done` 的最新几条”）。`SseChatEmitter.stageReplay:675` 传 `afterSeq=0`，所以长轮重连会回放最旧窗口、拿不到 `done`，客户端挂到超时。
- 对调用方**不可区分**：`FrameRead.degraded` 只进 `log.debug`（`:264`），`FrameStore` 接口只回 `List`。日志层“不静默”，API 层仍静默。
- `lastSeq()`（`:369`）在末端探测失败时返回 `max(legacyTail, 0)`，即“0 帧” —— `AiController.archiveMaxSeq:894` 会把它当 `lastSeq=0` 下发，前端于是请求全量回放，落进上面的错窗。
- `repairRollback`（`:169`）用 `streamTailSeq().seq()` 的 0 当锚点，号回退修复可能抬不到位 ⇒ 同号帧 / 显式 ID 被拒 → 自动 ID 兜底，物理序退化。

**修法**：
- 回放面（`stageReplay`，afterSeq=0）在 tail 未知时**不得**用无界 XRANGE 当“最新窗口”，二选一：①先重试一次末号探测，仍失败则返回空 + 显式降级信号（宁可让前端等下一拍，也别回最旧窗）；②用 `XINFO STREAM` 的 `last-generated-id` 作下界参考（注意：自动 ID 兜底态下它是上界，需与 `seq` 字段过滤配合，不能直接当 seq 用）；
- 给 `FrameStore` 增加 `boolean lastReadDegraded()` 或把 `readFrom` 换成带 `degraded` 的返回，让 SseChatEmitter/AiController 能拒绝“把降级读当完整差量”；
- `lastSeq` 读失败返回可区分的哨兵（或 `OptionalLong`），端点回 503/`degraded:true`，不要回 0。

### I2. fail-closed 一律用 `IllegalStateException` → 全局映射成 **HTTP 400**，把基础设施故障报成客户端错误

`common/GlobalExceptionHandler.java:68-72`：`IllegalStateException → BAD_REQUEST + ILLEGAL_STATE`。因此：

- B3 上传登记失败（`RedisFormAttachmentStore.java:75`）→ 前端收到 **400**「附件登记失败（Redis 不可用…）」；

同一次 Redis 故障在不同入口得到 **400 / 500（A5 是 RuntimeException）/ 静默（A3/A4）** 三种口径，监控上还会把故障统计成 4xx。报告里“告知上传失败”与真实状态码不符。

**修法**：新增 `AiStateUnavailableException`（或复用 `AiUnavailableException`）→ 统一 503 + `AI_REDIS_UNAVAILABLE`（`RedisAvailability.code()` 不变，符合“503 口径不变”）；表单面另加 typed `FormIssueCodes.ATTACHMENT_UNAVAILABLE`，让用户看到“稍后重试”而不是“请求非法”。

### I3. L-139 逐键 try 把最坏等待放大 10–13 倍，且发生在请求线程与确认门心跳上

`RunStore.java:1745-1757`；`spring.data.redis.timeout: 2s`（`application.yml:81`）
