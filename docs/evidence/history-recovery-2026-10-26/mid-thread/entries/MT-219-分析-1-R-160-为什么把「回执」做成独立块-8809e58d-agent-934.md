## 1. R-160 为什么把「回执」做成独立块

**原始缺陷（issue #14 ①，现象有三层，全部源于「回执做在工具卡卡体内」）**

R-158 #10 把只读回执卡做在工具卡**卡体**里（`v-else-if`，随卡展开/收起）。于是：

- **(a) 动作后被折叠带走**：用户确认/提交后 `requiresAction` 变 `false` → `defaultExpandedOf` 返回 false（`frontend/src/utils/blocks.ts:51-53`）→ 卡自动折成一行 → 回执藏进卡体，必须点卡头才能看见。demo 原文：「现状：回执渲染在工具卡折叠体内，确认后 requiresAction=false → 卡自动折叠 → 回执被藏」（`docs/demo/hitl/r160-hitl-issue14.html:195,201`）。
- **(b) 刷新后回执卡整卡不渲染**：`toolCallStates` 只回 `{status}`、`kind` 缺 → `kind2='UNKNOWN'` → 回执判据不成立 → 回执消失，只剩折叠工具卡（同文件 `:308-314`；`docs/evidence/补档-R160-现状取材-issue14.md:30`）。
- **(c) 刷新后展开态不恢复**（会审 MAJOR-2）：原以为「展开态随服务端恢复」前提错——`expandedBlocks` 是**会话内存态**（`blocks.ts:12` 注释），刷新后回落 `defaultExpanded=false`，回执仍藏折叠卡里（`docs/evidence/补档-R160-会审报告.md:8`）。
- **(d) 即使强渲，徽标退化为 status 派生、无时间戳、无已提交值**（元数据未持久化，由 M1 修）。

**判定独立成块的理由**：会审明确要求「回执卡移出工具卡折叠体 → 独立块」（`补档-R160-会审报告.md:8`、`补档-R160-决策卡-定稿.md` M2）。机制上是用 `defaultExpanded=true` + **模板直渲、不参与 expandedBlocks**（`blocks.ts:83-84,108-115`）来**机械保证「恒可见」**，使回执与卡折叠态、刷新态彻底解耦；同时靠 id 加 `messageId:receipt:` 前缀消解同段两卡撞 id（F1，三审 `:11`）。施工报告偏差 3 明载：「回执渲染位置由工具卡体内改为独立恒可见块，系 M2 定稿口径」（`补档-R160-施工报告.md:35`）。

**关键点：原始缺陷不是「卡被清除」**——卡一直在消息流里，问题是回执挂在**会折叠的卡体**上。

## 2. 代码现状

**提交后原卡的状态**（卡留在流里，不消失）：

- `confirm()`（`frontend/src/stores/ai.ts:1766-1833`）：往**原工具段**写 `status`（approved→`running` / rejected→`rejected`）、`decision`、`decidedAt=Date.now()`、`requiresAction=false`（:1791-1799）；失败回退清缺省（:1820-1828）。
- GF `submitGenerativeForm()`（`ai.ts:1968-2014`）：成功后写 `submittedValues` + `requiresAction=false`（:1993-1999）。
- 结局帧 `frontend_tool_result`（`ai.ts:2400-2419`）清 `activeForm`（:2416），段终态由 `applyFrameToParts` 落。
- 渲染：卡仍走 `activity` 块（`AiPanel.vue:316-345` 卡头），交互体由 `v-if="part.requiresAction"` 收起（`AiPanel.vue:382`）——即**已决卡 = 折叠单行（工具名 + 摘要 + 状态 chip）**。

**receipt 独立块承载了什么**：**零新增数据**。`blocks.ts:108-115` 的 receipt 块 `parts` = 同一个 tool part，模板只读 `part.status / decision / decidedAt / args / submittedValues`（`AiPanel.vue:236-280`），而这些本就在工具段上（`frontend/src/types/ai.ts:288-291`）。receipt 块只是**同一 tool part 的第二种渲染投影**。

**loadHistory 重建**（`ai.ts:946-965`）：从 `toolCallStates` 回读三字段写进 tool part；receipt 块不单独重建，由 `groupParts` 渲染时派生。后端字段闸在 `backend/.../run/ResilientChatService.java:717-741`。

## 3. 结论：改为「原卡原地只读态」可行吗

**数据面已具备，无需新增持有**——原卡现在已持有 `status / kind2 / decision / decidedAt / submittedValues / args`，receipt 块是纯投影，合并回去不改数据模型。

**但 R-160 的原始缺陷不会「天然规避」，取决于只读态渲染在哪一层**：

- 缺陷 (b)(c)（`kind2=UNKNOWN`、刷新不回读元数据）**已被 R-160 M1 修好，与块形态无关**——原地只读同样吃 M1 的持久化 + `loadHistory` 回读红利。
- 缺陷 (a)（回执藏卡体、刷新后 `defaultExpanded=false`）**正是「回执放卡体内」的因果，会原样复现**。要让「原地只读」不踩旧坑，必须二选一：
  - 只读摘要（徽标 + 时间 + 摘要）落在**卡头恒可见行**（细节才进展开体）；或
  - 已决 HITL 段 `defaultExpanded` 强制 true。
  若只读 UI 落在卡体、又依赖默认展开，刷新后 `expandedBlocks` 已丢（内存态）→ 卡折叠 → 回执再次看不见，即 R-160 旧坑。
- 注意第二种方案会与 R-154「每卡默认折叠单行摘要」口径冲突（`blocks.ts:44-53`，全批用户直裁），且同会话内用户手动收起后回执又藏起来，与「恒可见」语义有差。

**RC-2 守卫竞态**（`ai.ts:1981`）：`await submitFrontendToolResult` 期间若 SSE `frontend_tool_result` 帧先到（:2409-2416 置 `activeForm=null`），`submittedValues` 回写被该守卫 `return` 吞掉；段上**没有第二条写 `submittedValues` 的路径**（`utils/parts.ts` 的 `applyFrameToParts` 只落 status/reason，已确认无 `submittedValues`）。后果：提交后**本会话内**「已提交值」缺失，刷新后才由 M1 从后端 `resultText` 重建。**这与块形态无关**——无论独立块还是原地只读都读同一个 `part.submittedValues`。若新设计把已提交值当作只读态的核验证据，需先修此守卫（如回写不依赖 `activeForm` 身份，或由帧路径兜底）。

**其他合并注意**：receipt 块 id 机制（`blocks.ts:108-115`）可整体删除，F1 撞车面消失；但现有独立回执有大量 testid 断言（`frontend/tests/ai-panel-parts-render.spec.ts:1003-1070,1485-1521`：`hitl-receipt` / `receipt-args-toggle-*` / `receipt-values` / DOM 序「tool-card 在前、receipt 在后」），合并需改写这批用例；卡头已承载 R-163/R-165 视觉基线（`AiPanel.vue:321-345`），叠加徽标/时间需不破该基线。

**一句话**：独立块不是为「数据」而拆，是为「恒可见」而拆；新设计的数据面已就绪，但必须把只读摘要钉在**不由 `expandedBlocks` 控制的可见层**，否则 (a) 类缺陷回归，同时先修 `ai.ts:1981` 的 `submittedValues` 守卫竞态。
