## 实现方案（最小安全面）

### 1. 键形与同槽

- final：`chat:mem:{<cid>}`
- staging：`chat:mem:staging:{<cid>}:<uuid>`
- 全局索引：`chat:mem:__ids__`，**刻意不加 tag**，避免把所有会话压进同一槽

staging 与 final 的 hash tag 都是 `<cid>`，`RENAME` 在 Cluster 下同槽。staging 的 UUID 只放在 tag 之后，避免并发写互相覆盖临时键；UUID 不影响槽号。

### 2. 删除：单键操作

`deleteByConversationId` 只发一条 `DEL chat:mem:{<cid>}`（`RedisChatMemoryRepository.java:236`）。原来的 `DELETE_WITH_INDEX` 两键 Lua 已删除，因此不再出现 `CROSSSLOT`。索引不在此同步 `SREM`，stale 成员由现有 `findConversationIds()` 的逐 id `EXISTS` + 惰性 `SREM` 清理。

为保持 `/history` 的 `removedFromIndex` 即时语义，`isConversationIndexed` 改为 `SISMEMBER` 短路后再 `EXISTS` 数据键：索引成员还在但数据已删时立即判 false（`RedisChatMemoryRepository.java:177`）。这是两次单键往返，不做全量索引扫描。

### 3. 非空 saveAll：同槽 staging + RENAME

顺序（`RedisChatMemoryRepository.java:204`）：

1. 先在内存完成序列化（序列化失败没有任何 Redis 副作用）
2. `RPUSH staging`
3. `EXPIRE staging`（TTL 随 RENAME 继承到 final）
4. `RENAME staging final`（原子覆盖，不先删旧历史）
5. RENAME 成功后才 `SADD chat:mem:__ids__`

失败处理：

- push / expire / rename 任一步失败：`finally` 只删除 staging，旧 final 原样可读
- 索引 `SADD` 失败：只打 WARN，包含 `conversationId` 和 final key，**不回退已提交的新历史**；下一次成功保存会重新 SADD 自愈

空 / null 列表仍委托 `deleteByConversationId`，语义不变。

## 全局索引最终一致性 / 是否需要调用方 clear

**不需要调用方额外 `clear()`。** 删除语义已含数据键清理；`ChatMemory.clear` 仍落到单键 `deleteByConversationId`。

索引一致性分两类：

- **stale 成员**（删除后未 SREM、TTL 过期）：`findConversationIds()` 枚举时逐 id `EXISTS` 并移除；删除后 `isConversationIndexed` 也立即返回 false。
- **缺失成员**（RENAME 成功但 SADD 失败）：历史按 id 仍可读，但 `findConversationIds()` 不会自动发现它。当前可观测手段是 WARN 日志（带 `conversationId` + final key）；下一次成功保存会 SADD 自愈，也可按日志人工对账。
- 并发 `delete + save` 与惰性清理之间仍存在极窄窗口：清理可能删掉刚重新 SADD 的成员。结果仍是“历史可读、索引短暂缺失”，下一次保存自愈；不影响按 conversationId 读历史。这是“删除退化非原子 + 对账”方案的已知边界。

## 迁移注意

1. **键形变更**：旧 `chat:mem:<cid>` 不再被读取。默认 `session-ttl: 24h`，上线后旧会话历史会不可见到过期。可选：
   - 接受 24h 自然过期；
   - 或一次性迁移：枚举旧索引/旧键后调用 `saveAll` 重写。**不能直接 RENAME 旧键到新键**：旧键无 tag，可能不同槽。
2. **`AiController.deleteHistory` 的 `memoryKey`** 仍输出 `KEY_PREFIX + sessionId`（即 `chat:mem:<sid>`），实际键已是 `chat:mem:{<sid>}`。集成时建议改为 `redisRepository.keyFor(sessionId)`。
3. **e2e / 运维脚本**中按 `chat:mem:${sid}` 删除或检查键的地方（如 `frontend/e2e/13-nfezui.spec.ts:264/274`）需改成新键形；本次未改。
4. **`ResilientChatService` 的 `clear()+add()`** 本次未动。删除变单键后 `clear` 不会再跨槽抛错，但 `clear` 成功后若 `add` 失败，旧历史已在 clear 时丢失。集成建议：该路径改为只 `add`（`saveAll` 已是整窗口覆盖写），或“先写后清余量”，并把 `clear` 单独 try。
5. **任意 sessionId 的边界**：hash tag 直接包 `<cid>`；若 id 为空或以 `}` 开头，tag 会为空，staging/final 可能分属不同槽。当前前端使用 `crypto.randomUUID()`，正常路径安全；若允许任意 id，集成时需对 `{`/`}` 做编码或校验。
6. 未做旧键双读兜底，避免删除语义与旧键复活问题复杂化。
