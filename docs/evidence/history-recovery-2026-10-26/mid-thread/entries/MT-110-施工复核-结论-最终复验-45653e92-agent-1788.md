## P1（必须修，或经明确裁决接受）

### P1-1　Redis **写**失败被吞掉，跨实例闸门会 fail-open（最接近 P0）

- `<REPO>/backend/src/main/java/com/example/configmgr/job/service/JobHeartbeatRegistry.java:235-244`：`renewRunnerActive` 捕获 `RuntimeException` 只记日志，注释写“删除侧将 fail-closed”——**不成立**。`isRunnerAlive`（`:148-168`）只在 **读** 失败时抛异常；若 `beginRunner`/`beat` 的 `SET` 失败但随后 `HASKEY` 能成功，B 实例看到“无键”就放行，A 的 runner 仍在长事务里写子表 → 原始 C1 孤儿窗口重新打开（H2 提交期不复检 FK）。
- 测试盲区：`backend/src/test/java/com/example/configmgr/task/service/RunnerActiveMultiInstanceTest.java:138-151` 把 `SET` 和 `HASKEY` 都设为失败，恰好绕开了“写失败、读成功”的组合；`:124-135` 只测续期成功。
- **修法**：`renewRunnerActive` 返回布尔；`beginRunner` 失败则拒绝启动该作业（terminalize FAILED），runner 在每个分片边界发现续期失败时**中止自身**（fail-closed 在写侧），而不是继续裸跑；补一条“SET 抛、HASKEY 返回 false → B 删除仍 409”的用例。

### P1-2　`beginRunner` 在 afterCommit 才登记，存在“提交后、登记前”窗口

- `backend/src/main/java/com/example/configmgr/job/service/JobService.java:175-184`：`beginRunner` 在 `afterCommit` 内、`execute` 之前。数据库提交已释放 task 行锁，而登记尚未发生。并发序列可成立：A 提交 job（PENDING）→ B `cancel`（拿 task 锁，改 CANCELLED）→ B `delete`（状态无在途、Redis 无键）→ A 才 `beginRunner` + 启动 runner。
- 后果：runner 在任务已被删后才启动；DB 写入因 FK 在语句期被拒（不会产生 DB 孤儿），但 **Export 先写盘后落行** 会留物理文件（物理残留不在本轮已验证范围）；此外与“runner 未退出不能删”的字面口径不符。
- **修法**：在事务内（`jobRepository.save` 之后、提交之前）登记 runner，并在 `afterCompletion(ROLLED_BACK)` 里 `endRunner` 回滚；这样 task 行锁覆盖“提交→登记”全窗口。补一条并发 cancel+delete 用例。

### P1-3　创建作业不查 runner 存活：取消后同一任务可并行起第二个写者

- `backend/src/main/java/com/example/configmgr/job/service/JobService.java:44-45`（`IN_FLIGHT` 只含 PENDING/RUNNING）与 `:153-159`（`createAndStart` 只做同类在途守卫）。job 一旦 CANCELLED，旧 runner 可能仍在写 `config_staging_rows`/`task_files`；此时新建同类型（甚至 PUBLISH 读 Import 尚未写完的暂存行）会被放行 → 两个写者并发改同一任务，正是本轮删除闸门想避免的 c1 类问题，只是从“删”换成了“建”。
- **修法**：`createAndStart` 拿 task 锁后，对 `jobRepository.findByTaskId` 的作业逐个 `isRunnerAlive`（Redis 读失败同样 fail-closed）；有存活 runner → 409 “作业正在收尾”。补测试：cancel 后 runner 未退出 → create 409；`endRunner` 后 create 通过。

### P1-4　异步启动拒绝：job 残留 PENDING、取消注册表泄漏、HTTP 500

- `backend/src/main/java/com/example/configmgr/job/service/JobService.java:180-184`：`execute` 抛 `TaskRejectedException`（线程池 `AbortPolicy`，`AsyncConfig.java:66`）时只 `endRunner/clear` 后**原样 rethrow**。结果是：job 行已提交为 PENDING、runner 从未运行、`JobCancellationRegistry.register`（`:166`）未 `unregister`；异常从 `afterCommit` 冒到调用方 → 500；删除被“PENDING 在途”守卫挡到看门狗 30m（`application.yml:419`），只能靠用户先 cancel 解套。
- **修法**：catch 内把 job 置 FAILED（`JobTerminalWriter`/条件 UPDATE）并 `cancellationRegistry.unregister`；不再从 afterCommit 抛出，返回可读的 503/错误码；补拒绝路径测试。

### P1-5　`selectDefs` 仍不取 task 行锁（上一轮 I-4 的残余）

- `backend/src/main/java/com/example/configmgr/task/service/TaskService.java:127-156`：读任务不加锁 → 删/插 `task_items` → 最后 `save(task)` 更新任务行。与 `TaskService.delete`（`:388` 持 task X 锁后删子表）并发时构成环：delete 持 task 锁等 `task_items` 行锁；`selectDefs` 持子表行锁等 task 行 → H2 死锁检测回滚一方 → 500。`FileController` 已用 `lockTask`（`FileController.java:329-332`）修好同类路径，`selectDefs` 漏了。
- **修法**：`selectDefs` 入口 `lockForUpdate(taskId)`（task→child 顺序）；补“selectDefs 与 delete 并发”用例。

### P1-6　多实例重启：`StaleJobRecoveryRunner` 会把另一实例在跑的作业判 FAILED

- `backend/src/main/java/com/example/configmgr/job/service/StaleJobRecoveryRunner.java:45-80`：启动时扫描**全部** PENDING/RUNNING 并置 FAILED，完全不看 runner-active 键/实例归属；在 `scripts/b23l1-dual-instance.ps1` 这类双实例（共享 DB/Redis）滚动重启时，B 启动会把 A 正在跑的 job 判 FAILED。A 的 runner 继续写；随后因 job 已终态（P1-3）可再起新 job → 两个 runner 并发写同一任务。删除闸门本身仍会因 A 的键返回 409，**但作业态与并发写者已被破坏**。
- 启动顺序还会放大问题：`RunnerActiveKeyCleanupRunner` `@Order(1)` 在恢复（`@Order(0)`）之后；若将来在恢复里加存活检查，必须先清理本机死进程键再恢复。
- **修法**：恢复前先清理本机死键；恢复时对每个 job 查 `isRunnerAlive`（或键的实例/PID 存活），存活则跳过；并把心跳/看门狗的多实例归属问题一并登记。补双实例恢复用例（当前 `RunnerActiveMultiInstanceTest` 不覆盖恢复）。

## 已知边界（需产品/运维明确签署，不算 P0/P1 缺陷）

1. **1h TTL**：runner 卡住 >1h（或 `hold` 的长临界段 >1h，`JobHeartbeatRegistry.java:209-213` 只续期一次）→ 键过期后 B 可删；H2 提交期不校验 FK，仍可能产生孤儿。建议独立续期线程（不依赖 runner 进度）或在续期失败时中止 runner（与 P1-1 同一修法）。
2. **同实例卡死 runner**：`activeRunners` 永不过期，看门狗只清心跳（`JobWatchdog.java:239-244`），任务在该实例上**永远不可删**，只能重启进程；没有 force-delete。语义上 fail-closed，但运维需知。
3. **重启清理只认同 hostname + 死 PID**（`JobHeartbeatRegistry.java:175-200`）：容器重启后 hostname 变化或 PID 1 复用（`ProcessHandle.of(1)` 为真）→ 旧键保留到 TTL，重启后最长 1h 内删除都被 409；`endRunner` 的 Redis delete 失败同理。
4. **Redis 不可用/降级模式**：有作业历史的任务一律 409（读失败 fail-closed）。这是本轮要求，但意味着无 Redis 的降级部署无法删任务（tasks 无 job 不受影响）。
5. **所有实例必须使用同一个 Redis database**：dual-instance 脚本满足（`spring.data.redis.host/port` 共享、无 database 覆盖）；E2E harness 会按实例设置 `spring.data.redis.database`，若跨实例不同库，共享键不可见，闸门退化为单实例。
6. **物理文件**：未验证。Export 先写盘后落行、取消/拒绝路径仍可能残留；`FileControllerTaskGoneTest` 只对 mock `FileStorageService` 断言 `delete(path)`，没有真实文件系统/崩溃窗口验证。
7. **真实多实例**：未验证。`RunnerActiveMultiInstanceTest` 是同一 JVM 内两个 `JobHeartbeatRegistry` + mock `StringRedisTemplate`，不是两个进程/真 Redis/共享 H2。
8. `jobs.task_id` 仍无 FK（历史 1 条 999999 孤儿），V6 只覆盖五张子表；H2 锁/FK 语义结论换 MySQL/InnoDB 需重评估。
