### 代码事实（决定结论的四条）

1. **无双读**：`RunStore` 每族只有一种键形，没有"新键缺失回落旧键"的分支 ⇒ 升级窗口内**混版运行会分叉**（老实例写旧键、新实例读不到 ⇒ 重复续跑）。所以不存在"滚动升级"选项。
2. `RunStore.allRunIds()`（`RunStore.java:783-803`）会 `SREM` 掉"快照键不存在"的成员 ⇒ **新版本第一次 `GET /api/ai/runs` / 启动扫描就会把旧 runId 从 `ai:runs` 索引里删掉**。迁移必须在"新版本首次调用它之前"完成。
3. `GET /api/ai/runs/current`（`AiController.java:816-826`）：`ai:session:current` 残留而快照缺失 ⇒ 直接返回 `found:false` 空态，**不报错**：升级后在途卡是"静默消失"，不会给出可诊断的错误。

### 方案对比

| | A. 停机 drain（无在途后切换） | B. 一次性离线迁移（停实例→搬键→起新） |
|---|---|---|

### 结论（用代码证据回答"最短停机 drain 是否可行"）

**"drain 到无在途"本身不可控**：在途挂起**没有超时**（事实 4），所以"等它自然结束"没有时间上界；把它压成"最短"的唯一办法是**逐轮取消**——那是**有损**的，而且要面对"驱动进程已死 ⇒ cancel 不生效"的残局。因此：

- **窗口内确实没有在途挂起轮时**（`GET /api/ai/runs` 返回空/全终态）：A 最省事，等价"直接重启"，不需要任何脚本 —— 这是唯一 A 更快的场景。
- **有在途挂起轮且不想丢卡**：**B 更快也更安全**（窗口由脚本时长决定，秒级~分钟级；A 的窗口由人决定，可能数小时）。代价是要写一个幂等的一次性搬运脚本（运维侧，不进 `backend/src/main`，避免碰 CI 的 `KEYS/SCAN` 守卫）。

## 二、N-1 落地：ACQUIRE 三键同槽原子自愈

`LeaseService.ACQUIRE_SCRIPT` 现在 **KEYS = 租约键 / 计数器 / fence**（三者同 `{run:<runId>}` tag ⇒ 同槽），一次 `EVAL` 内完成：

```
GET 租约
fence = tonumber(GET fence) or 0
若现值存在且 curEpoch ≥ fence（有效租约）：
    counter < curEpoch 时 SET counter = curEpoch      ← 补计数器（重入也能救回）
    PEXPIRE counter                                              ← 刷新计数器 TTL
    return 现值 .. '|0'                                          ← 不推进号、不动租约 TTL（不替别人续租约）
否则（无租约 / 陈旧租约 epoch < fence）：
    epoch = INCR counter
    if epoch ≤ fence: epoch = fence+1; SET counter = epoch        ← 自愈
    PEXPIRE counter；SET 租约 = "<epoch>|<owner>" PX
    return "<epoch>|<owner>|1"
```

- **计数器先死 / 被淘汰 / 迁移没搬**：`INCR` 从 1 起也无妨 —— 脚本当场抬到 `fence+1`，不再产生"永久 STALE_EPOCH"。
- **不得覆盖有效高号租约**：`curEpoch ≥ fence` 的现值一律原样返回（Java 侧按 owner 判重入/占用），只有 `epoch < fence` 的陈旧租约才会被替换（它本来就写不进去）。
- **fence / counter 任一缺失**：`tonumber(...) or 0` 按 0 处理。
- **SET 失败**：Lua 无回滚 ⇒ 只跳号（号已 `INCR`），单调性不受影响。
- **被拒不取号** 仍成立（`GET` 命中在 `INCR` 之前返回）；重入会对计数器做一次幂等 `SET`（不 `INCR`）。

**生产调用点全部切到 fenced 版本**（否则同一把租约会走两套语义）：
- `RunStore.acquireRunLease` → `facility.acquireFenced(runLeaseKey, fenceKey, ttl)`
- `ConfirmGate:462`、`ConfirmGate:1400` → `tryAcquireFenced / acquireFenced(..., store.fenceKey(runId), ...)`

## 三、Minor 1：fence 与租约键必须同 tag（入口 fail-fast，不静默降级）

在 `LeaseService.acquire(key, fenceKey, ttl, owner)` 的 **try 之外**新增入口闸：

```java
String leaseTag = hashTagOf(key);
String fenceTag = hashTagOf(fenceKey);
if (leaseTag == null || !leaseTag.equals(fenceTag)) {
    throw new IllegalArgumentException("fenceKey 必须与租约键同槽（同一 hash tag）：key=… tag=… ，fence=… tag=…");
}
```

- 位置理由：跨 tag 的 fence 会让三键脚本在真集群 CROSSSLOT，而 CROSSSLOT 会被本方法下面的
  `catch (Exception)` 折成 `UNAVAILABLE`（整轮静默退化为进程内互斥）—— 所以必须在 `try` 外抛，做**编程错误**而非运行时降级。
- 顺带把 tag 解析收成 `static hashTagOf(String)`（`epochKeyFor` 复用，行为不变），避免两处各写一份花括号解析。

**新增 3 条用例**：

| 用例 | 断言 | 结果 |
|---|---|---|
| `fenceKeyFromAnotherRunIsRejectedInsteadOfSilentlyDegrading` | 传 `OTHER_RUN` 的 fence → `IllegalArgumentException`，消息含"同槽"与该 runId | ✅ |
| `fenceOnAnUntaggedLockKeyIsRejected` | 无 tag 资源锁 + 任意 fence → 同样入口被拒 | ✅ |
| `matchingTagsStillAcquire` | 正向控制：同 run 的 lease/fence 正常 `ACQUIRED`（守护不误伤生产路径） | ✅ |
