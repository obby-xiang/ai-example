# 结论：**多选 + 「其它」自由文本混着提交成立**，且是主流产品的标准能力

| 核查点 | 结论 | 来源 |
|---|---|---|
| **Google Forms 能勾 A、B 再勾「其它」填文本吗** | **能**。复选框题勾选多项 + 勾「Other」并输入，结果里**选项与其它文本都保留**："Show all selected options as a list; **Show the typed answer when the 'Other' option was selected** — in results, CSV exports, and Google Sheets" | 【事实】[fomr.io 复选框响应说明](https://fomr.io/help/features/components/checkboxes) |
| **Google Forms 提交结构** | **扁平化的逗号分隔字符串**——"Are included in exports as **comma-separated values**"；分析时要"clean and separate the comma-delimited strings"。**代价：丢掉了"哪一项是 Other"的区分** | 【事实】[fomr.io](https://fomr.io/help/features/components/checkboxes)、[Doc2Form](https://doc2form.dev/blog/single-vs-multiple-choice-google-forms/) |
| **Typeform 多选 + other** | **能，且结构更干净**：官方 Responses API 里多选走 `answers[n].**choices.labels**`（数组），单选走 `answers[n].choice.label`；**选中 Other 时 label 就是字面量 `"Other"`**（官方示例：`"choice": { "label": "Other" }`），而用户输入的文本以**另一个对象/键**返回（集成方需单独映射 `other` 字段，否则漏数据） | 【事实，官方】[Typeform JSON Response 说明](https://www.typeform.com/developers/responses/JSON-response-explanation/)、[Zapier 社区（other 需额外映射）](https://community.zapier.com/how-do-i-3/typeform-trigger-responses-with-other-content-and-filtering-action-for-certain-responses-10293)、[n8n 社区（返回 other 键 + 文本值）](https://community.n8n.io/t/typeform-how-to-parse-other-answers/13854) |
| **飞书多选下拉 / 钉钉多选列表 / Slack `multi_static_select`** | 都是**预定义选项**，**未找到**支持终端用户自填「其它」的官方说明 | 【未找到】[飞书选择器规范](https://open.feishu.cn/document/design-specification/component---data-entry/select)、[钉钉交互组件](https://open.dingtalk.com/document/development/interactive-components) |
| **框架层先例（选项 + 自由输入混排）** | **Ant Design `Select mode="tags"`**："**Tag Mode – Enables users to input custom values and display them as tags**"——预定义选项与用户自建值在同一个控件里混排 | 【事实，官方】[Ant Design Select](https://3x.ant.design/components/select/)、[creolestudios 指南](https://www.creolestudios.com/ant-design-select-guide/) |
| **企业表单系统的同类先例** | SharePoint 选择列支持「**Allow "fill-in" choices**／Can add values manually」——即在固定选项之外允许手动填写，且可导出为多选 | 【事实】[OpenForms 导出说明](https://help.openforms.com/Create/Configure-Your-Form-to-Export-Response-Data-to-SharePoint) |

# 校验规则

| 问题 | 结论 | 来源 |
|---|---|---|
| 勾了「其它」但不填文本，能不能提交 | **不能**（产品通行行为：Other 被勾选即展开文本框，文本框为空视为该题未完成）。**官方逐字条文未找到** | 【推断（产品惯例）+ 未找到（官方条文）】 |
| 勾了普通选项、又填了其它，「其它」还算必填吗 | **只要勾了「其它」，那个文本框就是必填的**——因为"Other"本身不携带信息量，空文本等于该选项无效 | 【推断】 |

# 一句话结论

**多选 + 「其它」混着提交成立且是主流能力**；数据结构应定为 **`{ selected: ["optA","optB"], other: "自定义文本" }`**（保留"哪项是 Other"的元信息，避免 Google Forms 的扁平化坑），**校验规则为"勾了「其它」则其文本必填、且该文本框为空视为未完成"**，回显时**选项标签与其它文本分列展示**（chip + 单独一行「其它：…」）。

# Q1：多步 HITL 允许跳过吗？——**允许，但必须显式且留痕**

| 证据 | 内容 | 来源 |
|---|---|---|
| **向导的跳过规则（最完整的一套）** | "**R5 — Skip semantics**：Optional steps render **Skip button alongside Next**；Skipping marks step as **'skipped'（指示器里灰色 ↷）not 'complete'**；**Required steps NEVER show Skip**" | 【事实（设计规范）】[Koder Design 多步向导](https://kds.koder.dev/en-US/patterns/patterns-wizard-multistep.html) |
| **步骤指示器要标出可选** | "Toggle the **optional step items** to match the flow length"；且"Completed 与 Active 用不同状态语言" | 【事实】[Create UI Step Indicator](https://createui.co/components/step-indicator) |
| **可选步骤必须有显眼的 Skip** | "**If a step is optional**（e.g. 'Add a secondary address'）, provide a **prominent 'Skip' button** rather than forcing the user" | 【事实】[Flutter Steppers 最佳实践](https://fluttergems.dev/stepper/) |
| **skip 是每步的配置项** | 表单 schema 里 `allowSkip: boolean`（"Wizard step-gat[ing]"） | 【事实】[UI Protocol schema](https://objectstack.ai/docs/references/ui/view) |
| **进程性约束** | CopilotKit：**所有 interrupt 都被 addressed 才恢复**（`resolve` 或 `cancel` 都算 addressed，所以"跳过"要显式调用 `cancel`） | 【事实，官方】[CopilotKit useInterrupt](https://docs.copilotkit.ai/human-in-the-loop/useInterrupt) |
| **企业审批真的会跳过审批人** | ServiceNow：审批可置为 **"No Longer Required"**，此时活动结果为 **"skipped" 而非 "not_required"**；常见触发：申请人与审批人同一人、同一人多组重复审批 | 【事实，官方 KB + 社区】[ServiceNow KB](https://support.servicenow.com/kb?id=kb_article_view&sysparm_article=KB2588470)、[重复审批置为 No Longer Required](https://www.servicenow.com/community/developer-forum/skip-approval-for-group-if-same-person-present-in-all-groups/td-p/3271493)、[申请即审批人则跳过](https://www.servicenow.com/community/it-service-management-forum/want-to-skip-approval-if-requested-by-is-same-as-approver/m-p/438572) |
| 其他企业先例 | SAP Concur「**Skip Approval Step if Approver Has Already Approved**」；Harness「审批步骤可按条件跳过（如非受监管环境）」；DigiCert 可对管理员/经理跳过审批步骤 | 【事实】[SAP KB](https://userapps.support.sap.com/sap/support/knowledge/en/3814944)、[Harness changelog](https://headwayapp.co/harness-changelog/skip-approval-steps-160008)、[DigiCert](https://docs.digicert.com/en/certcentral/order-and-manage-certificates/approve-certificate-requests-and-manage-order-level-access/remove-or-skip-the-approval-step-for-certificate-requests.html) |

**审计口径**：**skipped 是一种被记录的决策/状态，不是"未发生"**——ServiceNow 把它落成活动结果 `skipped`，指示器里也以灰色 ↷ 与"完成"区分。**【事实】**

> **一句话结论 1**：多步 HITL **允许跳过**，但规则是"**只有可选步骤才给 Skip、必填步骤永不显示、跳过要落成独立的 `skipped` 状态（谁跳、何时、为何）**"，而不是让用户"直接不答"。

> **一句话结论 2**：**异构组合成立且是主流**（选择 → 输入 → 确认可以分步混排；批量 interrupt 也可含不同 action），但没有"批准/拒绝必须独占一步"的行业规则——正确做法是**每张决策卡独立声明自己的动作集**，而不是强行按类型拆步。

# Q3：多步完成后的「总结摘要页」——**标准配置，且是附加物不是替代物**

| 证据 | 内容 | 来源 |
|---|---|---|
| **PatternFly 向导规范** | "Final Step - **Summary (optional)**: The last step in the wizard can be a **Review step** that shows a **summary of the information selected and/or set in the previous steps**" | 【事实，设计系统官方】[PatternFly Wizard](https://pf3.patternfly.org/v3/pattern-library/communication/wizard) |
| **Baymard 对 review step 的硬要求** | "**Standardize the review step. The review page should be a summary of known facts; introducing new fees or shipping costs here destroys user trust**"；"Ensure users can **verify all details** before placing the order. Is the summary **optimized for skimming**?" | 【事实】[Baymard Checkout UX](https://baymard.com/blog/checkout-flow-ux-optimization)、[Baymard 审计清单](https://baymard.com/blog/audit-checkout-flow-hidden-friction) |
| **摘要要"随时可达"** | "The order summary should be **visible on the payment step or easily accessible without leaving the checkout**" | 【事实】[Baymard Payment UX](https://baymard.com/blog/payment-ux) |
| **步骤级折叠与最终 review 并存** | "**Always Collapse Completed Accordion Checkout Steps into Summaries**"——这是**步骤级摘要**；最终 review 页是**另一层汇总**。两者不是二选一 | 【事实】[Baymard Accordion](https://baymard.com/research-articles/accordion-checkout-usability) |
| **review 页的内容边界** | 只汇总**已知事实**；不得在 review 阶段引入新信息/新费用（Baymard 明确点名这是信任杀手） | 【事实】同上 |

**推论（对我们的回执卡）**：多步完成后应当**同时**保留两类对象——
1. **逐步的只读卡**（折叠成摘要行，可展开看原值）——满足可回溯；
2. **一个最终 review/summary 页**（汇总 + "Place/提交"按钮 + 可点回某步修改）——满足"提交前最后核对"。

> **一句话结论 3**：**最终摘要页是标准配置，但它是对"逐步只读卡"的附加层，不是替代物**——Baymard/PatternFly 都是"**已完成步骤折叠为摘要** + **最后一步 review 汇总**"两层并存，且 review 页只准复述已知事实、必须可 skim、可回改。

## 对你们（400px 窄栏、配置管理）的落地提示

| 议题 | 建议 |
|---|---|
| **跳过** | 只在"可选步骤"给 `跳过`，且按钮与"下一步"并列；步骤指示器标 `已跳过`（灰 ↷，≠ 已完成）；落地字段 `status: "skipped" + actor + at + reason`，审计上算一个决策 |
| **异构组合** | 允许"选择 → 填写 → 确认"分步混排；但**每个确认门独立声明动作集**（如"批准/不执行/暂不"），不要用一套动作套所有卡 |
| **摘要页** | 两步都要：每步完成后折叠成摘要行（可展开看原值）；全部完成后给一个 review 页（汇总 + 回改入口 + 提交）。review 页**只许复述已知事实**，不得新增字段或隐藏变更 |
