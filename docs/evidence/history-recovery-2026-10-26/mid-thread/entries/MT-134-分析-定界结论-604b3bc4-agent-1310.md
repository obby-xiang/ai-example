## 根因（当前源码即可复现的竞态）

1. `ResumeService.resume(runId, false)`：先读 `epochBefore`，再 `acquire`（`ResumeService.java:252-263`），用 `fresh = epochBefore != lease.epoch()` 判"是不是我抢到的"。
2. 两路 resume 同时到达 B：两线程都读到 `epochBefore=0`；`LeaseService.acquire` 的 Lua 只有第一条真正 SET，第二条拿到**同值租约**（`<epoch>|<owner=B>`，owner 是自己）→ 两条都返回 `ACQUIRED`（`LeaseService.java:242-263`，可重入短路/同 owner 双保险）→ **两条都 `fresh=true`**。
3. 败方在 `resume(runId,false,lease)` 里命中 `resuming` 互斥返回 `IN_PROGRESS`；回到外层后因 `fresh=true` 且非 ACCEPTED，执行 `releaseRunLease`（`ResumeService.java:276-285`）。
4. `releaseRunLease` → `releaseIfHeld`（`LeaseService.java:344-347`）删的是**同一个 token**——胜方刚拿到的租约，同时清空本进程 `held` 视图。
5. 胜方随后 `markDriving` 只能对着一个已不存在的租约续租；`RunStore.save` 读到 `heldRunEpoch=0` → 走 plain SET（`RunStore.java:283-307`），fence 键从未写入，快照 `runEpoch` 保持 0。

时间线也吻合：败方的 release 发生在胜方的 RUNNING save 之前，所以连第一次 fenced 写都没有。

## 移交后端的最小修法（不改后端，仅建议）

- `LeaseService.ACQUIRE` Lua 额外返回"本次是否由我 SET"的标志（`GET` 命中 → `created=0`；`INCR+SET` → `created=1`），`AcquireResult` 增加 `created` 字段；重入短路同样 `created=false`。
- `ResumeService` 用 `acquired.created()` 取代 `epochBefore != lease.epoch()` 作为 `fresh`，**只有租约的创建者才允许 release**。
- 兜底方案：`fresh` 分支 release 前加 `!this.resuming.containsKey(runId)`（败方返回 IN_PROGRESS 时该表必已有胜方）——但不如 created 标志根治。
