## ① 回执卡出现的完整用户场景 + 具体例子

**一句话场景**：AI 在高风险工具执行前先在对话里渲染一张「门卡」（确认门）或「生成式表单卡」，用户在卡上做决定（批准/拒绝，或填写并提交）；用户一动作，原卡**原地/紧随其后**换成一张只读的**回执卡**，记录"这件事已办成/被拒"的结论。

## ② 回执卡展示什么数据

按 demo `.receipt` 结构三段（`AiPanel.vue:241-277`）：

## ④ RC-1 / RC-2 对该场景的影响

- **RC-1**：`hitlReceiptSummary`（`AiPanel.vue:2381-2394`）只对 `args` 做通用 `key=value` 摘要，**没有 GF 分支**；而 GF 的 `args` 就是整份表单 schema（`{scenario,title,fields}`，`AiTools.java:520`），于是卡面退化成 `生成式表单 · scenario=FILTER，title=…，fields=[…]` 的 schema JSON —— 回执卡变成长 JSON 容器，扫读不了（demo v7.8 尾批第 18 节 `:1059` 场景清单与「现状 · v7.3 版」栏就是这个缺陷实景）。
- **RC-2**：`submitGenerativeForm` 在 `stores/ai.ts:1981` 的守卫 `if (this.activeForm?.toolCallId !== form.toolCallId) return` 位于写回 `submittedValues`（`:1985-2000`）**之前**；当 `frontend_tool_result` 结局帧先到并把 `activeForm` 置 `null`（`:2409-2417`）时，守卫短路 return，**已填值永不写回**工具段 —— GF 回执丢失已提交值，详情盒只剩 schema，刷新/历史恢复也回溯不到已填值（正是 demo v7.8 定稿要补齐的「详情含 `values` 键」）。

**一句话**：两者叠加会让 GF 场景的回执卡从「一行人话 + 可查详情」退化成「又一张 schema JSON 卡，且已填值还查不到」。
