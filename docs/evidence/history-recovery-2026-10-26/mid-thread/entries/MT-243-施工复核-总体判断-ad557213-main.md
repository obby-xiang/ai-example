## 二、确凿重复造轮子（有替代品且成本不高）

### 后端

**Excel 导入：三份全量内存拷贝。** `file/FileStorageService.java:52` `Files.readAllBytes` → `excel/ExcelReader.java:32` `new XSSFWorkbook(ByteArrayInputStream)`（DOM 全量）→ 全表 `List<Map>`。POI 自带 `XSSFReader` + `ReadOnlySharedStringsTable` 的 SAX 流式读；EasyExcel/FastExcel 已封装成"逐行回调"。`5MB` 的 multipart 上限只是卡住上传口，绕不过任务中心复用导出件的路径。

**导出：SXSSF 形同虚设。** `excel/ExcelWriter.java:31` 正确用了 `SXSSFWorkbook(100)`，但调用方 `job/service/ExportJobRunner.java:128-174` 先把全部过滤结果装进 `List<Map>` 才交给它——SXSSF 的"边取边写"价值被上游全额抵消。

**作业编排：手搓了一个"最小 Spring Batch"。** `jobs`/`job_items`/`validation_issues` 三张表 ≈ `BATCH_JOB_EXECUTION`/`STEP_EXECUTION`/`ExecutionContext`，自写 5 态状态机 + 取消 + 启动恢复。更具体的是**整作业单事务 + 手搓分片**：`job/service/ImportJobRunner.java:60` 方法级 `@Transactional`，`:141` 攒 100 行 `saveAll` 后 `Thread.sleep` 模拟分片——分片边界是装饰品。这直接导致了三个下游补丁：`REQUIRES_NEW` 进度旁路、`heartbeatRegistry.hold()` 慢临界段豁免、runner 存活闸门。
> 但要说清楚：换成 Spring Batch **换不来断点续跑**（数据面不是 step 粒度，产品也明确"一律 FAILED、用户重跑"），且 `jobs` 表已被前端/AI 工具直接消费。结论是"整作业单事务该改成 per-chunk 提交"，不是"该引 Spring Batch"。

**下载/打包：全量 `byte[]` + 手写 zip。** `task/controller/FileController.java:239` `buildZip` 用 `ByteArrayOutputStream` 拼完整包；`:189` 手写 `URLEncoder` + `filename*=UTF-8''`。`download-all` 对含 20 个导出件的任务会把全部 xlsx 读进堆（2× 峰值）。替代：`StreamingResponseBody`、`ContentDisposition.attachment().filename(name, UTF_8)`——低风险，代价是失去 Content-Length。

**条件查询的内存分页。** `data/service/ConfigDataService.java:68` `matched.subList(from,to)` + `new PageImpl<>`，`:99` 全量读 + 逐行 `readValue`；而无条件路径 `:41` 是正确用 `Pageable` 的。根因是字段存在 `data_json` CLOB（`Specification` 表达不了），所以"过滤只能内存做"是 schema 设计问题——但分页这层确实是手搓的。

**发布差集删除逐行遍历。** `ConfigDataService.java:212-221` 外层 `findRowsInScope` → 内层 `contains(rowKey)` → 逐个 `delete`。数据库一条 `DELETE … WHERE … AND row_key NOT IN (…) AND updated_at < ?` 就能完成，并发保护条件可以原样放进 `WHERE`。

**分布式锁 ≈ Redisson `RLock`。** `ai/session/SessionGate.java:85` `setIfAbsent(key, runId, ttl)` 抢锁 + `:159` 定时 `expire` 续期 + 释放比对 runId——这就是 Redisson 看门狗语义的 1:1 手写版。同类还有 `ToolResourceLocks`（5 段 Lua）。
> 但要区分：`LeaseService` 的 `fence/epoch` 是 Redisson **给不了**的（单调写回权令牌），那部分属合理自研。

**`SseWriteBudget`：150 行包住 JDK 三行。** `common/sse/SseWriteBudget.java:187-201` 本质是 `executor.submit()` → `future.get(15s)` → `cancel(true)`；`:134` 的 `corePool=0 + SynchronousQueue + 60s keepAlive` 与 `Executors.newCachedThreadPool` **逐参数相同**。附带的 `Result/Outcome/WriteFailure` 只是把 `ExecutionException` 拆回原异常。

**`saveAll` 实际不成批。** `ImportJobRunner.java:141` 的 `saveAll(100行)` 因主键是 `GenerationType.IDENTITY`（`data/entity/ConfigDataRow.java:16`），Hibernate 会禁用 JDBC batching，仍是 100 条独立 INSERT；`application.yml` 也没有 `hibernate.jdbc.batch_size`。意图与事实不符。

**其他手搓小项**：导入每行查一次 `baseVersion`（N+1，`ImportJobRunner.java:134`）；依赖拓扑排序手写 Kahn 且含 18 行死代码（`definition/service/DependencyResolver.java:52-69` 建了两个从未读取的 map），而建好的 `config_dependencies` 表（`V1__schema.sql:50`）全仓 0 引用。

## 四、一个值得单独说的模式

代码注释里反复出现"我们评估过 XX，不值得引入，所以自己写"——但**至少 3 处的事实前提是错的**：

- `ContextEstimator` 说引分词器有打包负担 → `jtokkit` 已在 classpath
- `SheetAudit` 说"不引 Micrometer" → `micrometer-core` 已是 compile 依赖
- `JobWatchdog` 说"仓内无 `@EnableScheduling` 故自建" → 是自己没开

而前端自己的调研文档反而是诚实的：`docs/research/排查-A7A8A9-轮询歪门邪道与过度设计-2026-10-24.md:462` 明确写"语义是 throttle(trailing)，lodash/VueUse 有成熟实现（**本仓未引入 VueUse，属"自造"而非"误造"**）"，还顺手登记了单槽回调 + mermaid 计时器未清两个成本。

这说明问题不在"不知道有库"，而在**默认自研 + 事后补理由**。后果不是功能错，是维护面变大：同一能力仓内出现两份（退避算式 ×2、分布式锁 ×2、SSE 重连策略前后端各一套、剪贴板两条路径、`saveBlob`/`downloadBlob` 两份）。
