## 特别检查（逐条回答）

**1）`AiStateUnavailableException` 映射**：类型继承 `CodedIllegalStateException`（仍是 `IllegalStateException`，既有 catch 语义不变），`@ExceptionHandler` 按最具体类型由 Spring 选中 → 503；文案不泄内部信息，`messages_en/zh` 有 `error.AI_REDIS_UNAVAILABLE`，`ErrorBodyFactory.envelope` 按 code 本地化，非中文请求不会看到中文硬编码。**映射本身正确**。但测试只直接调用了 handler 方法，没有 MockMvc 证明“Spring 解析器优先选子类 handler”——属测试真实性小缺口（Minor 2）。

**2）`pendingRaw` 回滚会不会误删他人 claim**：当前代码**不会**。回滚只在本次 `HSETNX` 返回 true 时执行（`:1329-1339` / `:1361-1365`），而唯一会删单个 claim field 的代码就是 `rollbackClaim` 自己 —— 两个回滚不可能都 `won`。理论窗口只有一个：`deleteRun` 整键 `DEL` 之后、我们的 HDEL 之前，别的实例用同一 `(runId, toolCallId)` 重新认领；当前没有这样的路径（轮已删还在执行工具属于异常态）。若要做到绝对安全，改成 Lua CAS（值匹配 `epoch|instanceId` 才 HDEL）即可，属 Minor 3。

**3）degraded 读会不会卡死连接 / 漏错误帧**：**会，且这是本轮新引入的 IMPORTANT（N-2）**。详见下节。

**4）typed outcome 兼容**：`ResumeService.Outcome` 新增 `CANCEL_STATE_UNKNOWN`/`STATE_UNKNOWN`，`AiController.resume` 的 switch 显式列出并回 503、仍有 `default`，`isRefusal()` 也纳入；`StartupResumeRunner` 只记 `outcome().name()`。编译面与语义面都兼容。（唯一小瑕疵：503 body 只有 `code`/`reason`、没有 `message`，与其他 503 不同；前端按 code 兜底，不阻断。）

**5）测试是否真实**：真实为主 —— 断言的是行为与状态（真线程、真 watch/gate、真 fake store、计数增量、日志捕获），不是“方法被调过”；I-3 断言了“不调用后续键”，I-1 断言了 `-1`/`empty`/`degraded`，C1 断言了 claim 表内容。**但仍有三处实质空白**：(a) 没有 `terminal=true + degraded` 的回放用例（正好漏掉 N-2）；(b) 没有 `pendingRaw` Redis 读失败走 HTTP 的用例（漏掉 N-3）；(c) 异常→HTTP 映射只测 handler 本身。

## 新 Important（附修法）

### N-1. UNKNOWN 在“副作用最后闸”被记成**用户取消**，且不可再续跑

`SpToolCallingManager.java:749-762` 在 UNKNOWN 时抛 `StreamViolationException(CANCELLED, "取消状态未知…")`；`ResilientChatService.java:629` 只看 `code==CANCELLED` → 走 `cancelTerminal`；`:1096` 写 `AI_RUN_CANCELLED：本轮由用户取消`，前端显示“已停止”，续跑一律 `ALREADY_CANCELLED`。`SpToolCallingManagerGateArmTest:121-133` 把这个选择锁成了“只断言异常类型”。

后果：一次 Redis 读抖动 = 一轮被记成用户主动停止、无法续跑、日志/记忆里写的是错误的归因。C2 的“不产生错误终态”在这里只是把错误终态从“工具失败 + 卡悬挂”换成了“用户取消”。

**修法**：新增独立错误码（如 `ErrorCodes.AI_STATE_UNKNOWN`）走 `StreamViolationException`，`ResilientChatService` 的 `CANCELLED` 分支不动，让它走普通错误路径：`failed + code=AI_REDIS_UNAVAILABLE`（或 `retryable=true` 的 error 帧），前端按码显示“服务暂不可用，请重试”；同时把该用例的断言从“isInstanceOf”改成“code 不是 AI_RUN_CANCELLED”。这样 fail-closed 保留、归因正确、可重试。

### N-2. 终态轮 + 降级回放：SSE 永不 complete、客户端拿不到任何帧

`SseChatEmitter.java:609-640`：`plan.degraded()` 时只 `kickDrain`（仅当 `staged>0`）然后 return —— **没有** `completeOne`。而 `terminal=true` 时前面**没有**挂订阅（`:613-616` 只在 `!terminal` 挂），也没有 drain 被提交 ⇒ 对于 `staged==0` 的终态重挂，`emitter` 永远不 complete、不写任何帧，而 `AiController` 用的是不带状态的 `replayAndAttach`（`AiController.java:661`），degraded 被丢弃；`NO_TRANSPORT_DEADLINE = -1`（`:1712`）意味着服务端不设超时 → 连接/异步请求悬挂到客户端自己断。

可达性不是纯理论：`/events` 的预检只查 `lastSeqIfKnown`（XREVRANGE）；预检通过后 **XRANGE（A3）单独失败** 就会得到 `degraded + out 空`，终态轮即命中。此时归档里的 `done`/`error` 帧也不会补发（漏错误帧）。

**修法**：`replayAndAttachWithStatus` 的 degraded 分支区分终态：`terminal && plan.staged()==0` 时写一帧 typed error（`AI_REDIS_UNAVAILABLE`、`retryable=true`、`degraded=true`）后 `completeOne(sub)`；非终态且 `staged==0` 至少投一帧 `degraded` 通知（或让 controller 改用 `replayAndAttachWithStatus` 并在创建 emitter 前转 503）。补一条 `terminal=true + degraded` 的用例（现在完全空白）。

### N-3. I-2 的另一类问题：待决条目/快照写入仍是未 typed，决策接口会回 500 或 400

`RunStore.pendingRaw`（`:1055-1064`）把 `opsForHash().get` 放在 try **之外**，Redis 读失败抛的是原生 `RedisConnectionFailureException`（DataAccessException，无 code）→ `GlobalExceptionHandler.handleGeneral` → **500 INTERNAL**；`putPending`（`:950-958`）包成普通 `IllegalStateException` → `handleIllegalState` → **400 + ILLEGAL_STATE**（还带“无法写入待决条目 …”内部措辞）。路径是主决策链：`AiController.confirm`（无 Redis 预检）→ `ConfirmGate.pendingForWrite`（`:1069-1072`）→ `pendingRaw`；提交写回走 `putPending`。`readPendings` 非 lenient（`:984`）、`save`（`:631/:691`）同理。

**修法**：把 `pendingRaw` 的 get 纳入 try 并抛 `AiStateUnavailableException`（或至少包成同一 typed），`putPending`/`readPendings(false)`/`save` 的 Redis 失败也改 typed；`pendingRaw` 的 JSON 解析失败保持 `IllegalStateException`（那是数据损坏，不是基础设施）。补一条 `POST /confirm` 在 pending 读失败时 503 的 MockMvc 用例。

7. `isCancelled` 的 cause 取自共享字段 `lastReadFailure`，极端并发下可能挂到另一个 run 的异常（仅影响诊断）。
