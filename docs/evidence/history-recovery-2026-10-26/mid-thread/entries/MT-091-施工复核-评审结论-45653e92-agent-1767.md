### Critical（1 条，**非本批引入，但会阻断集群上线**）

**C1 · `chat:mem:` 双键 Lua 在原生 Cluster 必 `CROSSSLOT` → 前端"新建对话"500**

`RedisChatMemoryRepository.java:71-76` 的 `DELETE_WITH_INDEX` 用 `KEYS[1]=chat:mem:<convId>` + `KEYS[2]=chat:mem:__ids__`；调用点 `:171`，上层是 `AiController.java:1237 DELETE /api/ai/history/{sessionId}`（前端"新建对话"必走）。我独立算槽：`chat:mem:s-abc`→**6127**，`chat:mem:__ids__`→**8572**，不同槽 ⇒ 真集群 `EVAL` 直接 `CROSSSLOT`。类注释 `:55` 已自认这是"迁移 Cluster 前必须处理"的已知项，但两轮报告都只说"未触碰 `RedisFrameStore` 等"，**没有把这条列为集群阻断**。

修法（推荐后者）：
1. 不能简单加 tag —— 索引是全局 SET，给两个键加同一 tag 会把索引键变成 per-conversation，语义崩掉。
2. 拆成两条单键命令，顺序 SREM→DEL：并发 `SADD` 落在 `SREM` 之后只会留下"指向已删键的索引成员"，而 `messages()`（`:108-123`）本来就惰性剔除空会话，属良性；若担心"迟到的 SREM 抹掉他人 SADD"，可把顺序改为 DEL→SREM 并接受同样良性的窗口，或用 per-conversation 标记键（`chat:mem:used:{conv}`，同槽）承担"索引一致性"。

### Important（3 条）

**I1 · 取号外置新增"epoch 反转"窗口：晚到者用更小 epoch 占住租约，会让一轮永久写不进去（fail-closed 但卡死）**

`FENCED_SET`（`RunStore.java:225`）判据是 `fence > epoch ⇒ 拒写`，`tryClaimExecution`（`:1123`）同理。原设计 INCR+SET 在同一 EVAL 里，号与写入必然同序；现在 INCR 在 `:334`、EVAL 在 `:336`，中间可被 GC/调度/连接重排拉长。反例：A `INCR=10` 后被挂起 >30s（租约 TTL）→ B `INCR=11`、`SET 11|B`、写 fence=11 → B 崩、租约过期 → A 的 EVAL 终于落地，键已空 ⇒ `SET 10|A` 成功 ⇒ A 拿到 **10 < fence 11** 的租约：每次 `save` 都 `STALE_EPOCH` → 500；A 的续租又会一直钉着这把"写不进去的租约"，别人接不了管。

- 安全性没破（陈旧写永远进不去，不会脏写）；破的是**可用性**：需要人工删 fence 键才能恢复。
- 触发条件（延迟 > TTL=30s）概率低，但代价是"单轮永久卡死 + 无自愈"。

修法（二选一）：
1. **根治（推荐）**：把取号键搬进 run 的 tag —— `ai:epoch:{run:<runId>}`，脚本内 `INCR`+`SET` 回到同槽、同一原子步，`ai:lease:epoch` 降级为诊断计数。我已核实 **epoch 从不跨键比较**（只有 `FENCED_SET`/`tryClaimExecution` 的"同 run 内 fence vs epoch"，`ai:lock:*` 只做 token 等值比对），所以 per-run 计数器语义等价，还顺手去掉"`ai:lease:epoch` 必须 noeviction"这条运维约束。
2. **折中**：`acquire` 在 `created=true` 后回读 fence，若 `fence > epoch` 立即释放并返回 `UNAVAILABLE`/新枚举 —— 把"静默卡死"变成"可见失败 + 可重试"。

**I2 · 竞争场景零覆盖：没有"两实例争同一租约"的 cluster 用例**

`ClusterSlotTest` 9 例全为单线程顺序调用（我数过：9 个 `@Test`、59 条 assert，无空断言）。任务点名的"竞争下 epoch/fencing 正确性"没有对应用例，`created` 语义（同主双抢的败方不得释放）也没被断言。加一例如下即可：

```
twoInstancesRaceForTheSameLeaseUnderClusterMode():
  两位 LeaseService（owner=inst-a / inst-b）共享同一 FakeLeaseRedis（clusterMode=on）
  交错：a.fastPathGET→null, b.INCR, b.SET, a.INCR, a.EVAL
  断言：恰一个 created==true；另一个 HELD_ELSEWHERE；ai:lease:epoch 只增；
       fence 未被推回；败方 releaseIfHeld 不删胜方键
```

**I3 · 迁移方案自相矛盾：搬 fence 却没说 `ai:lease:epoch` 要预置**

报告 §六 的搬运清单是"12 键除 `ai:lease:run`"（即**搬 fence**），但 §五.2 又说"新键名下 fence 从 0 起算"。这两句不可能同时成立，而"搬 fence + 换到新集群"这一支是**会炸的**：新集群 `ai:lease:epoch` 从 1 起，搬过去的 fence 是旧集群的高位（可能几千）⇒ `fence > epoch` ⇒ 所有在途轮 `save` 恒 500、`claim` 恒 `STALE_FENCE`。

修法（写进硬闸，二选一）：
- **不搬 fence**（推荐）：旧实例已停，fence 的保护对象不存在了；新 fence 从新 epoch 起算即可，旧 fence 键 24h 自然过期。
- **搬 fence**：必须先 `SET ai:lease:epoch <max(所有 fence, 所有在途 lease epoch)>`，再起新版本。

同一处要补：`ai:seq` 与 `ai:xevents` **必须成对搬**。只搬 stream 不搬 seq ⇒ `nextSeq` 从 1 重发，新帧 `seq` 小于读者手里的 `afterSeq`，差量读会把它们全过滤掉（表现为"升级后新帧不出现"）。

## 四、迁移专题（逐问回答）

**1. 无双读时是否严禁滚动升级？——是，严禁，且理由比报告写的更硬。**
不只是"分叉导致重复续跑"：新实例的 `allRunIds()`（`RunStore.java:783-800`）对"快照键不存在"的成员执行 **`SREM ai:runs`**，也就是**写**。混版窗口里新实例第一次收到 `GET /api/ai/runs` 就会把旧实例的在途 runId 从索引里删掉，旧实例自己再启动扫描也找不回来。加上 lease/fence 键形也不同（同一 run 两把锁），混版等于"双驱动 + 索引自毁"。只能 `停旧 → 迁 → 起新`。

**2. drain vs 一次性迁移，谁可行？**
- **drain 不能当"最短停机"**：等人的路径**无上限**（`AiProperties.java:635-636` 明说 `confirm-timeout` 退役、`suspendWaitSeconds` 返回 null；只有前端工具 120s）。要压短只能逐轮 cancel，那是**有损**，且"驱动线程已死 ⇒ cancel 不生效"。
- **一次性离线迁移可行**，窗口由脚本时长决定（10 轮 ≈ 百来次往返，秒级）。但报告给的清单缺 C1/I3 两项硬闸（见上）。
- 代码里**没有 chat 级"停受理"开关**（报告结论正确），选 drain 就得临时靠代理层挡流量。

**3. 老租约键不搬是否合理？——合理，而且必须"不搬"。**
租约 30s 自过期，搬过去等于把死实例的租约**续命 30s**，反而挡住接管。而且 `ai:lease:epoch` 不搬（同键）没问题，只要不换 Redis 实例；**换到新集群就必须预置**（I3）。
