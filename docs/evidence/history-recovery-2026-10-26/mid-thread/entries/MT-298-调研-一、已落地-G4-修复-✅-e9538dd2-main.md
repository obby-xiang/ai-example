## 五、三份调研结论与对应的实施方案

**G5 双通道（64KB vs 8000）**：业界主流是「一份结果、两套呈现、各按各的预算、超限走引用不硬砍」——模型侧常见 10k–25k token（≈4 万字符，我们的 8000 偏保守），UI 侧 64KB 合理但应定义为「单帧上限」；两侧用统一截断字段契约（`truncated/strategy/originalChars/handle`），超大结果落存储、模型拿句柄+预览。→ **方案**：收敛为一个 `ToolResultLimits` 配置（两字段独立可调）、统一截断字段、模型侧阈值提为可配（默认 2 万字符档）。

**M-2b 僵尸卡**：业界主流（Camunda/Temporal/Step Functions）的答案不是「启动时自动补字段」（那是明确的反模式），而是**「降级可见 + 可取消」为必做基线**：旧挂起轮渲染成一张降级卡「此确认已随版本升级失效，可取消或等待过期」，加监控计数；一次性 backfill 只作为可选运维命令（dry-run+幂等+对账），不做 boot hook。→ **方案**：做基线（降级卡+计数+发布说明），backfill 不做。

**P1-5 resultView 契约**：业界没有统一标准，但主流共识非常清晰——**受控白名单 + 数据引用 + 版本降级**（A2UI/Adaptive Cards 思路的语义化子集），禁自由 HTML。→ **方案骨架**：`resultView = {version, kind: table|chart|form|text, data: {ref: JSON指针}, columns/chart/form, fallback}`，前端一个 `kind→渲染器` 注册表，未知 kind 走降级文本；v1 只允许后端确定性构造，按工具逐个迁移。这正好把 P1-4 的「拆双通道」也一并承载（reason 摘要进卡面、明细进 data）。

**G3 记忆窗口**（上轮调研结论）：改为 token 预算 32k–48k + 条数兜底 40–60 条 + 旧工具结果替换占位符（保留最近 3–5 个），摘要压缩留作兜底。
