## a. L-120 这个"自我保护"是什么 & 业界怎么做

**是什么**：`frontend/src/utils/markdown.ts` 里有个 24 毫秒的渲染耗时预算——某次 Markdown 渲染超过 24ms，就把一个**页签级全局开关**永久置位，之后这个页签里所有消息的代码块都走简化渲染（没边框、没高亮、没复制按钮），不弹任何提示，只有 F5 才恢复。代码注释里自己写着"页签级粘滞，刷新才归零"。

**业界主流怎么做**：调研结论是——**业界没有"测一次渲染耗时→自动降级且粘滞"这种做法**。主流方案是：

- 虚拟列表/窗口化（LobeChat 用 `react-virtuoso`，只渲染可视区消息）；
- 流式渲染节流（AI SDK 的 `throttle`，只降更新频率，不降渲染质量）；
- ChatGPT 甚至连虚拟列表都不用，宁可让 DOM 增长，也**不做**自适应降级。

业界存在的"降级"都是**确定性的、可逆的**：比如"超过 N 条/ N 字符就简化"、"加载更早"按钮、用户手动切换。我们这种"机器抖一下→这篇对话永久变丑"属于反模式——不可预测、不可恢复、用户会困惑。

**我的建议**：这条可以缩小成"保留复制按钮 + 给恢复入口"（半小时级），或者干脆评估把这个粘滞开关去掉、改成只对"单条超长消息"（>1 万字符）生效——这个长文短路逻辑代码里本来就有。你定。

## c. L-98 / L-99

**L-98 是什么**：现在模型的"思考过程"只推给前端思考卡片展示，**不落进对话记忆**——下一轮对话时模型看不到自己上轮怎么想的。查证发现：仓里有个补丁类 `ReasoningAwareOpenAiChatModel` 专门负责"多轮把思考回填给厂商 API"，但**全仓没有任何地方往里写数据，是死代码**；技术方案里记着：接 deepseek-v4-pro 这类推理模型且带工具调用时，缺回填会**稳定报 400**。

**业界口径**（三家不同，这点很关键）：

- **DeepSeek**：请求带 tools 时，历史所有轮的 `reasoning_content` **必须完整回传**，否则 400；不带 tools 则不用传。
- **Anthropic**：tool-use 链内必须原样回传 thinking blocks。
- **OpenAI**：从不返回原始推理，只给摘要/加密块，普通多轮不需要回传。

也就是说：**只要接推理型模型 + 工具调用，"存思考"就从体验题变成功能正确性题**。我们仓现在的断点正好是这条路径。

**L-99 现在有什么过滤**：查证后纠正一下表述——现在的输出闸**不是敏感词过滤**，是 9 条"高置信凭据"正则脱敏（API key、私钥、JDBC 连接串、`password=` 这类），命中就替换成 `[REDACTED:xxx]`，流式管道里带 128 字符尾窗。这正是你说的"业务定义的敏感信息"，厂商确实不管这个。而**思考帧完全绕过这道闸**（代码注释明写"DLP 对思考文本不设闸"），思考原文还会进 Redis 帧日志存 24 小时。

**业界做法**：厂商侧的通行做法是**根本不把原始思维链给调用方**（OpenAI/Azure 只给摘要，Anthropic 拦截时返回加密的 `redacted_thinking`）——所以"对思考再做一层业务脱敏"没有通行先例，更多产品选择不展示原始思考。我们仓是把原始思考展示给用户的少数派，那这道闸要不要覆盖思考，确实是你要拍的板。
