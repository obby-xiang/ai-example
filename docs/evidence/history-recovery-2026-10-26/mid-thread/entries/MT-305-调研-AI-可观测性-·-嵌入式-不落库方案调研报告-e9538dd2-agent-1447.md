## 2. 业界主流（官方来源）

### 2.1 四层数据模型已是事实标准

| 产品 | 模型 | 存什么 | 部署形态 | 本仓可用性 |
|---|---|---|---|---|
| **OTel GenAI semconv** | span 树 + metric + event | `invoke_agent` → `chat` → `execute_tool`；`gen_ai.request.model`、`gen_ai.usage.*`、`gen_ai.conversation.id`、`error.type`；内容为 **opt-in** | 纯标准 | ✅ 可直接做字段目标 |
| **Langfuse** | trace → observation（span/generation/event）+ session + score | 一条 observations 表，每行复制 trace 级属性（user/session/tags/metadata）；score 独立 | Web + Postgres + ClickHouse + worker | ❌ 服务端 |
| **LangSmith** | run → trace → thread → trajectory | run 类型（llm/tool/chain）、inputs/outputs、feedback（tag+score）；SaaS 保留 180 天 | SaaS / 自托管 | ❌ 服务端 |
| **Phoenix (Arize)** | span（OpenInference）+ project + eval | SpanKind：CHAIN/RETRIEVER/LLM/TOOL/AGENT…；attributes 为扁平 KV | 服务端 | ❌ 服务端；但 SpanKind 词汇可借用 |
| **Helicone** | 网关请求日志 | 请求/响应全量、成本、延迟；自托管 = Postgres + ClickHouse + MinIO + Web + Jawn | 代理型服务端 | ❌ 且是网关模式，与「不改调用链」冲突 |

来源：[OTel GenAI spans](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md) · [OTel GenAI metrics](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-metrics.md) · [Langfuse Data Model](https://langfuse.com/docs/tracing-data-model) · [LangSmith Observability Concepts](https://docs.langchain.com/langsmith/observability-concepts) · [Phoenix Tracing Concepts](https://docs.arize.com/phoenix/tracing/concepts-tracing) · [Helicone Self-Host](https://docs.helicone.ai/getting-started/self-host/manual)

**四层归纳**（各家叫法不同，结构一致）：`Trace（一次请求）→ Observation/Span（一步）→ Generation（一次模型调用）→ Score（评价）`，外加 `Session` 做多轮归组。本仓的 `runId` ≈ Trace，`sessionId` ≈ Session，`tool_call_*` ≈ execute_tool span，**缺的正是 Score 层与 span 的父子结构**。

### 2.2 「无服务端」的三种可行做法（按侵入排序）

1. **Micrometer → 日志/文件**：`LoggingMeterRegistry` 是 micrometer-core 自带类，定时把 meter 打到日志（[源码](https://github.com/micrometer-metrics/micrometer/blob/master/micrometer-core/src/main/java/io/micrometer/core/instrument/logging/LoggingMeterRegistry.java)）。零服务端、零新组件。
2. **OTel SDK → 进程内 exporter**：Java SDK 自带 `OtlpJsonLoggingSpanExporter` / `OtlpStdoutSpanExporter`（`opentelemetry-exporter-logging-otlp`，OTLP JSON 编码），可把 span 以 OTLP-JSON 打到日志/标准输出（[OTel Java SDK](https://opentelemetry.io/docs/languages/java/sdk/)）。**注意：Java 没有官方稳定的 FileSpanExporter**，要落文件得自己写 30 行 `SpanExporter`。
3. **OTel Collector `file` exporter**：把 pipeline 数据写成 newline-delimited OTLP JSON，支持轮转（`max_megabytes`/`max_days`/`max_backups`），还能用 `otlpjsonfilereceiver` 读回（[fileexporter README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/exporter/fileexporter/README.md)）。**但 Collector 是独立服务，不满足「纯嵌入式」**——只能作为「将来放开」的落点。

### 2.3 评估（eval）面的主流做法

主流不是「从生产日志重放内容」，而是 **dataset → experiment → score** 三段式：Langfuse 明确区分 online（对线上 trace 打分）与 offline（固定数据集跑实验），并提供 CI 回归动作（[Langfuse Evaluation](https://langfuse.com/docs/evaluation/overview)）；LangSmith 用 dataset + evaluator + feedback（[LangSmith](https://docs.langchain.com/langsmith/observability-concepts)）；OTel 侧对应事件是 `gen_ai.evaluation.result`（`gen_ai.evaluation.name/score.value/score.label`，[gen-ai-events.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-events.md)）。

对本仓的直接含义：**内容不落库 ⇒ 「生产 trace 内容回放」这条路在立法层面就是关的**。能做的只有「行为回放」（工具序列/重试/时延）+「CI 黄金集跑模型」。

## 3. 分层方案

### A. 现在就能做（零新组件，全部基于已有 classpath）

#### A1. 结构化事件 → 按天 NDJSON trace 流（推荐做，性价比最高）

- 在 `AiTrace.eventOn` 的同一处再吐一份 NDJSON（**同源，不做第二套埋点**），写 `backend/data/ai-traces/ai-trace-yyyy-MM-dd.ndjson`（`backend/data/` 已 gitignore）。
- 行形（`kv` 原样进 `attrs`）：

```json
{"ts":"2026-10-22T10:31:02.123+08:00","event":"turn_end","run_id":"...","session_id":"s-42",
 "turn_no":3,"attrs":{"status":"done","code":"none","totalMs":8421,"gateWaitMs":702,
 "toolCalls":2,"inputTokens":5120,"outputTokens":302,"est":false,"model":"..."}}
```

- 工程约束：`ArrayBlockingQueue(4096)` + 单写线程 + 满则丢并计数；**绝不阻塞 AI 主路径**（与「日志不许影响主流程」同一条纪律，`AiTrace.java` 类注释）。按天 + 大小双阈值轮转，保留天数可配。
- 成本：约 150 行 + 1 个配置项；无新依赖（Jackson 已有）。
- 收益：runId 聚合从「grep 文本」升级为「结构化可算」，`jq`/`awk`/未来 DuckDB 都能直接读；这就是 OTel 之前的「trace 落盘」。

#### A2. Micrometer 指标落日志（补 L-55 的 metrics 面）

- 新增 `AiMetrics`：`SimpleMeterRegistry` + 自建 60s 单线程 dump（仓内无 `@EnableScheduling`，`JobWatchdog.java:52` 已确立「自建单线程调度器」的先例）。
- 指标集直接复用 `turn_end` 字段，避免二次埋点：

| 指标 | 类型 | 来源 |
|---|---|---|
| `app.ai.turn.duration` | Timer（tag: status/model） | `turn_end.totalMs` |
| `app.ai.turn.ttfb` | Timer | `upstream_first_byte.ms` |
| `app.ai.tool.duration` | Timer（tag: tool/ok） | `tool_call_end.ms` |

- 输出：每 60s 一行一指标（`metric=... value=... tags=...`），比 `LoggingMeterRegistry` 全量打印更可控（后者会打全部 meter）。
- pom 里**显式声明** `io.micrometer:micrometer-core`（Boot BOM 管版本，artifact 已在 m2，离线可构建）。
- 明确不做 actuator：收益（`/actuator/metrics` 端点）与自建 dump 重叠，代价是联网拉包 + 新组件过库 + 暴露管理端点（安全面还要额外加固）。

#### A3. Redis「只读聚合」，零新增写入

- 不新增 key：用现有 `ai:runs`（索引）、`ai:run:*`（status）、`ai:pending:*`（待审批）在请求时算 gauge：活跃轮数、挂起轮数、按状态分布。

#### A4. 手册升级

在 `docs/AI对话日志链路追踪手册.md` 增「聚合查询」章：按天文件 + `jq` 菜谱（P95 时延、按 code 的失败分布、审批等待占比、工具 Top N）。半天工作量。

|---|---|---|
| NDJSON trace（仅 12 事件的元数据） | ✅ 允许 | 计数/计时/枚举/run 摘要 = 立法明列的「指标与元数据」 |
| NDJSON 写入 prompt/response/tool 入出参 | ❌ 禁止 | 明文禁区 |
| 导出 `ai:xevents` / `ai:run.messageJson` 到文件 | ❌ 禁止 | 那是正文，只是「现在恰好在 Redis」 |
| Micrometer 内存指标 + 60s 日志行 | ✅ 允许 | 纯计数/计时，无正文 |
| Redis 会话内聚合（TTL = session-ttl） | ✅ 允许 | 与会话同生共死，口径最干净 |
| Redis **跨会话**累计计数（无 runId/sessionId） | ⚠️ 需用户拍 | 仍属元数据，但越过「24h 严格共亡」（`决策看板.md:23`）的字面口径 |
| NDJSON 保留期 7 天 | ⚠️ 需用户拍 | 元数据可留，但与 24h 口径不一致；可选 24h 最保守 |
| Spring AI observation（内容开关全 false） | ✅ 允许 | 官方默认不导出 prompt/completion |
| OTel SDK + 自写 FileSpanExporter | ✅ 允许（若只导元数据） | 但当前无收益、需联网拉包 |
| OTel Collector / Langfuse / Phoenix | ❌ 现在不行 | 非嵌入式 + 自带 DB；且 Langfuse 需显式关内容捕获 |
| eval 基于 trace 的行为回归 | ✅ 允许 | 只用元数据 |
| eval 内容回放 | ❌ 禁止 | 需先推翻 🏛️，不是工程决策 |

## 5. 给用户的决策建议（三条）

1. **做 A1 + A2**（NDJSON trace sink + Micrometer 指标落日志）。理由：两者都**不引入任何新组件**（micrometer 已在 fat jar 里），直接补上 L-55 里 metrics 面的 70%，且把「日志面」升级成「可聚合的 trace 面」。预计 2.5–3 人日 + 1 人日测试。
2. **不引 actuator、不引 OTel SDK**。前者本地 m2 没有 3.5.x（离线构建会断）+ 新组件过库；后者在没有 collector 的情况下收益极低。把 `TraceSink` 接口和字段映射先留好，放开时再接。
3. **eval 只做「行为回归 + CI 黄金集」**，明确写下「内容回放不可做」的边界，避免后续被当成欠账。

需要用户拍板的**只有两个口径**（其余都能按上面执行）：
- trace 文件保留期：**7 天**（便于周对比）还是 **24h**（与共亡口径最一致）？
- 是否允许「无标识的跨会话累计计数」在 Redis 里活过 24h？（建议：不允许，先不做。）
