## 三、Important（附修法）

### I-1 规格缺口：启动校验没有把“+余量”变成约束，且接受“无工具超时”配置

证据：`AiProperties.java:256-262` 只做 `zombieAge.compareTo(legalSilence) <= 0` 抛错；`AiProperties.java:797` 缺省 180s 是“max+60s”，但 `verifyZombieAge` 不校验这 60s。`application.yml:238-240` 的注释也把约束写成“必须 > 两类合法静默”。后果：运维把 `zombie-age` 设为 `121s` 能正常启动，而工具执行上限是 120s，工具刚跑满上限就可能被判死接管——正是 R1-09 要消除的“同一轮双执行”。

另：`SpToolCallingManager.java:1167-1170` 把 `exec-timeout <= 0` 解释为“**无超时**”，而校验把它当成“合法静默下限 0”，于是一个工具永不超时 + `zombie-age=1s` 也能过启动校验。

修法：
```java
Duration margin = this.resume.getZombieMargin();            // 新键，缺省 60s
if (!zombieAge.minus(legalSilence).isPositive()
        || zombieAge.compareTo(legalSilence.plus(margin)) < 0) {
    throw new IllegalStateException("zombie-age 必须 ≥ max(exec-timeout, inter-event-timeout) + " + margin + "...");
}
if (execTimeout.isNegative() || execTimeout.isZero() || interEvent.isNegative() || interEvent.isZero()) {
    throw new IllegalStateException("exec-timeout / inter-event-timeout 必须 > 0：0 等于永不超时，合法静默无上界");
}
```
配套：`application.yml` 增加 `zombie-margin: 60s` 并把注释改为“≥ max + margin”；按本仓既有约定补 `AiResumeZombieAgeGuardTest`（参照 `AiPropertiesContextGuardTest`/`AiPropertiesLimitGuardTest` 的写法：等于/略低于/低于余量三条各断言抛错，合法值不抛）。若产品裁决“余量只是缺省取值、不是硬约束”，那至少要改成启动 WARN 并在注释里删掉“必须 + 余量”的表述——现状是规格与实现各说一半。

### I-2 键族一致性：`ai:activity` 没进 `SessionKeyRegistry`，而同类 `ai:beat` 进了；内存替身的删除语义与生产相反

证据：`SessionKeyRegistry.java:158` 把 `ai:beat` 登记为 `WRITE`，但 `RUN_KEYS`（`:130-160`）里没有 `ai:activity`；类注 `:40-46` 写“run 级登记 = 13 条”、`:59` 的裸前缀清单只列 `ai:beat`/`ai:cancel`；`SessionKeyRegistryTest.java:23` 锁 `entries()` 18 条。该表自述“新增会话同寿键只改这张表 / 分类而不遗漏”，现在两者都被打破了。报告把这件事列为“未做/可选”，但它不是纯可选：它让“键族唯一登记表”从事实变成部分事实。

另外 `InMemoryRunStore.deleteRun` 会 `businessActivity.remove(runId)`（`InMemoryRunStore.java:348`），却不删 `beats`；生产 `deleteRun` 刻意**都不删**（`RunStore.java:757-781` 注释明确 `ai:beat`/`ai:activity` 按 TTL 走）。测试替身与生产语义相反，会让“删轮后锚点仍在”这一真实行为永远测不到。

修法（二选一，推荐前者）：
1. 把 `ai:activity` 登记为 `Renewal.WRITE`：`new RunKey(RunStore.ACTIVITY_PREFIX, runId -> RunStore.ACTIVITY_PREFIX + runId, List.of(Renewal.WRITE), "业务活动锚点")`；同步 `RUN_KEY_COUNT` 注释 13→14、`SessionKeyRegistryTest` 18→19/13→14（HEARTBEAT/READ 面计数不变）、裸前缀清单补 `ai:activity`。
2. 若坚持不登记，就在 `SessionKeyRegistry` 的“显式不进本表”清单里加一条 `ai:activity` 及理由，别让它落在“没分类”的灰区。
同时把 `InMemoryRunStore.deleteRun` 改成与生产一致（不删 `businessActivity`），或加断言锁定“删轮不动锚点”。

### I-3 `touchBusinessActivity` 的“读-比-写”不是原子/单调的，且给流式热路径每次出帧加了 2 次 Redis 往返

证据：`RunStore.java:1638-1644` 是 `GET → 比较 → SET`（另有 `EXPIRE` 分支），两个实例并发时存在经典回拨窗口：A（旧帧 atMs=1000）读到 current=0，B（新帧 2000）先 SET 2000，A 再 SET 1000 → 锚点被回拨。注释 `:1628-1629` 写“读-比-写（防回拨）… 并发下轻微回拨由事件日志尾部 max 兜住”，但兜底只探尾 **16** 帧（`ACTIVITY_TAIL_PROBE`，`:189`）：若落后时钟的实例在尾部刷了 >16 条旧帧，2000 那一帧会滑出探测窗，锚点与尾部一起给出旧值。注释对“单调”的承诺强于实现。

同时这是**出帧锁内**的调用（`SseChatEmitter.java:1159` 的 `synchronized (emitLock)` → `:1196`），每个业务帧（含每个正文/思考 delta）多 2 次 Redis 往返；而该锁里原本已有 `nextSeq`(INCR) + `XADD` 两次。等于把 token 流路径的 Redis 调用翻倍，并延长锁持有时间（心跳、其他线程出帧都被它串行化）。

修法：把比较+写+续期收成一条 `EVAL`（本仓已有 `DefaultRedisScript` 用法），1 次往返且同键原子：
```lua
local cur = tonumber(redis.call('GET', KEYS[1]) or '0')
local new = tonumber(ARGV[1])
if new > cur then redis.call('SET', KEYS[1], ARGV[1], 'PX', ARGV[2])
else redis.call('PEXPIRE', KEYS[1], ARGV[2]) end
return 1
```
可选再加本地节流（每个 run 一个 `AtomicLong`，`atMs - last < 1000ms` 就跳过）：最坏滞后 1s，相对 180s 判死窗可忽略，能把热路径降到 ≤1 次/秒。跨实例时钟域问题 Lua 也解决不了（Minor M-2），但至少注释不再过度承诺。

### I-4 会话门的新分支没有测试，且既有用例的 stub 已失效

### I-5 测试真实性：安全网 `verifyZombieAge` 零测试；出帧测试只覆盖 `start/delta` 且用的是兼容构造器

## 四、Minor（不改也可验收，建议排期）

1. **第三类合法静默：续跑期上下文压缩**。首轮压缩发生在 `store.create` 之前（`ResilientChatService.java:400`），扫不到，安全；但续跑路径先把快照置 RUNNING 落库（`ResumeService.java:716-723`）再压缩（`:759`），而 L2 压缩是 **N 次串行摘要**，每次 60s 超时（`RollingSummarizer.java:132-140`，`AiProperties.java:1180`），期间既无业务帧也无心跳（心跳只在流式 `consume` 里发，`ResilientChatService.java:596-608`）。180s 判死窗仍可能被超越。正常情况下续跑者持有租约（`LEASE_HELD_ELSEWHERE` 会挡住接管），所以只在租约不可用/丢租时暴露。修法不动 SSE 格式：每完成一次 `summarizer.summarize(...)` 刷新一次业务锚点（包一层 `Summarizer` 即可），把单次静默压回 60s。
2. **跨节点时钟域**：锚点/帧 `atMs` 都是出帧节点的墙钟，判死用的是本节点 `now`；负偏的节点会让活轮提前“超龄”。属既有口径（旧 LIST 尾也是节点钟），但 R1-09 把它变成主判据，建议在部署要求里写明 NTP。
3. **`activeAgeMs` 对 SUSPENDED 的语义**：`activeAtMs` 现在只含业务活动，挂起等人三天的轮会显示 `activeAgeMs≈3天`，而同一条记录 `zombieRunning=false`；前端/运维若按该字段判断会误读。建议 SUSPENDED 时改报含心跳的年龄，或加 `activeAgeBasis` 字段。
4. **坏锚点值会卡住后续写入**：`Long.parseLong(raw)` 抛异常被外层 catch 吞掉，导致该 run 直到 TTL 都不再写锚点（读侧回落日志，不会误判，但锚点长期失效）。建议解析失败时直接覆盖。
5. **注释陈旧**：`RunStore.java:1515-1517` 仍写“改由 touchActivity 记一个轻量活动戳 —— 于是‘心跳提供活动证据’这一用途照旧”，与 R1-09 后“心跳只给会话门用、不给僵尸判据用”不一致；`InMemoryRunStore` 的删除语义（见 I-2）。
6. **验证产物口径**：1916 vs 1912、RED 8/7 vs 最终 10、报告“相关 67”无法从产物复现；diff 非任务隔离（混入其他任务 hunk）。这些不影响代码判断，但影响“报告即证据”的可审计性。
7. 会话门对“活着但丢租 + 心跳仍在 + 业务停滞 >180s”的轮现在会放行新会话（旧行为是 409）。方向与“丢租即允许接管”一致，但这是行为变化，值得在用例里写明（I-4 的第二个用例可顺带锁定）。
