## 3. 那个“断流期正文尾部”的现象、触发与修法

### 现象（用户在界面上看到什么）

用户正在看 AI 逐字回答，网络断了/页面刷新了，回来发现**回答的后半截没了**——工具卡、确认卡还在，但正文只到断线前那一截。

### 三个词分别指什么

- **delta 不入档**：从 T3a 起，流式输出的“增量文字帧”**不写进 Redis 归档**（设计卡 `docs/M2-T3-设计卡.md:51` 的 T3-2，后果注记在 `:57`）。归档里只留 `start/suspended/tool_*/message_start/message_end/done` 这类**状态帧**，没有正文。
- **断流期**：连接断开到重新连上/刷新之间。
- **正文尾部**：断线前已经显示、但还没到“轮末写回会话记忆”的那段文字（`ResilientChatService#convergeMemory` 只在轮末收敛）。

### 两种情形，结果完全不同

1. **轮已经结束**：刷新 → `loadHistory` 调 `GET /api/ai/history`，末条 ASSISTANT 正文就是本轮完整正文 → **尾部补回**。施工报告场景 A 实测：实收 delta 与历史正文完全相同，回放里没有 delta（`docs/evidence/M2-T3b-施工报告-DS-V4-Flash.md:450-462`）。
2. **挂起中 / 轮未结束**：历史里只有 USER 一条，没有 ASSISTANT（记忆未收敛）→ **尾部补不回**，界面只有 `streamInterrupted` 提示“连接中断，结果可能不完整……可刷新重试”（场景 B，`:464-476`；当前代码 `frontend/src/stores/ai.ts:1477-1480`）。

### 修法

**没有新增“前端兜底机制”。** 施工报告写得很直白：本项“只确认 + 登记，**无功能性改动**”（`:437-438`，A23 口径）。现有机制就是两条：

- **会话镜像**：`startMirror` 对 messages 深监听，流式 token 也 300ms 防抖写 `sessionStorage`（`frontend/src/stores/ai.ts:969-980`）；
- **历史加载**：`loadHistory` 先用镜像即时恢复，再与后端历史对账（`:1045`）；历史非空时**整体替换** messages（`:1141`）；
- **增量续收**：`resumeSnapshotStream` 只收 `seq > lastSeq` 的状态帧，不补正文（`:1444`）。

**改动面**：这一项 **0 个前端文件**。整个 T3b 批次是 **32 个文件**（25 个后端源码/测试 + 4 个文档 + CI/脚本 3 个），施工报告口径 23 改 + 8 新；报告自身 667 行。红队核对过分文件行数，但指出报告汇总“+1013”手算差 2（S2-1，后已勘误）。
