## 2. Enter / Shift+Enter / IME / 空内容 / 重复发送

事件链：

1. `@keydown.enter.exact.prevent="send"`（`AiPanel.vue:737`）。`.exact` 表示只有无修饰键的 Enter 被拦截并发送；Shift+Enter 不匹配，走浏览器默认换行。
2. `send()`（`:2584-2619`）：`trim()` → 空内容静默返回 → `!ai.canSend` 时 `noticeBusySend()` 并保留草稿 → `pinBottom()` → 编辑重跑分支 → `inputText=''` → `await ai.send(text)`。
3. store `send()`（`stores/ai.ts:1483-1573`）：再次 trim/空内容返回 → `loading` 守卫 → 记录用户消息、追加助手消息 → **同步置 `loading=true`**（`:1500`）→ 请求并内部 catch 错误（`:1554-1557`）→ finally 复位 loading（`:1558-1566`）。
4. `stop()`（`AiPanel.vue:2621-2623` → `stores/ai.ts:2326`）只负责 abort 与后端取消。

代码可见的缺陷落点：

- **IME 组合期 Enter**：`frontend/src` 与 `frontend/tests` 中 `isComposing` / `compositionstart` / `compositionend` / `keyCode === 229` **grep 0 命中**。组合期按 Enter 会进入 `send()` 并 `preventDefault`；Vue 的 v-model 会延迟组合文本同步，因此行为至少是“可能发送旧草稿/拦截候选确认”。这是明确的守卫缺口，但真实症状需浏览器复现，不能仅凭此断言根因。
- **发送后焦点回收**：全组件只有错误卡「改写后重发」会 `composerRef.focus()`（`:1150`）；发送路径没有 focus。发送后 `loading=true` 使 textarea 进入 `disabled`，浏览器会使禁用控件失焦，因此焦点丢失是结构性的。
- **发送失败草稿保留**：`inputText.value=''` 在 `await ai.send(text)` **之前**执行（`:2617`）；store 内部 catch 错误且 `send()` 返回 `void`，面板无法得知失败并恢复。因此“失败/断流后草稿丢失”从代码路径可直接看出。注意：busy 守卫（`:2590-2595`）反而会保留草稿，丢失发生在“已开始发送但失败”的路径。
- **空内容**：`canSubmit` 要求 `trim().length > 0`（`:1290`），`send()` 又双重 trim 拦截（`:2585-2589`），空内容/纯空白会静默无操作。
- **重复发送**：组件 `send()` 没有显式 in-flight 标志，但依赖“先同步清空 inputText”和 store 的 `loading` 守卫；从代码看没有明显可重复发送的窗口。未做浏览器事件序列验证，不建议把它列为已确认缺陷。

**重要依赖**：demo 的 Enter 缺陷②“发送后焦点回收”假设生成中 textarea 仍可编辑（勾位②“流式可编辑”）。当前生成中 textarea 被 `disabled`，发送后立即 focus 不可行；若不启用勾位②，只能退化为“本轮结束后再 focus”或“仅失败时 focus”。这需要在方案里明确。
