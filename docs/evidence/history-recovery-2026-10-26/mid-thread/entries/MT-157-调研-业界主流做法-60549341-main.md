## 业界主流做法

主流不是“AI 自己决定要不要继续”，而是宿主做分层治理：

1. **准入层**
   Schema、权限、scope、目标资源、前置状态、业务规则先校验。Gemini 官方也要求重大后果调用先验证/确认：[Function calling](https://cloud.google.com/vertex-ai/generative-ai/docs/multimodal/function-calling)。

2. **调度层**
   只读工具可以并行；有副作用、共享状态、顺序依赖的工具默认串行。Anthropic 明确建议副作用和共享状态工具串行，browser/computer 类还要求首错即停：[Parallel tool use](https://docs.anthropic.com/en/docs/agents-and-tools/tool-use/parallel-tool-use)。

3. **审批层**
   高风险工具在参数完整、前置条件通过后才让人确认；参数缺失或畸形时 fail closed。OpenAI Agents SDK 的 HITL/guardrail 就是这个方向：[Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)。

4. **执行与恢复层**
   副作用必须配幂等键、执行台账、资源锁、完成验证和补偿路径；超时或结局未知时先对账，不允许盲目重试。可参考 [Stripe idempotent requests](https://docs.stripe.com/api/idempotent_requests) 和 [Temporal Saga](https://docs.temporal.io/design-patterns/saga-pattern)。

## 当前项目的主要问题

这些问题比“模型是否并发”更实际：

- **当前不是首错即停**：前一个工具失败后，后续工具仍会继续执行。
- **scope 只校验上下文，不校验目标资源**：例如当前上下文在任务页时，`start_export(taskId=别的任务)` 也可能通过。
- **风险标签失真**：7 个 FRONTEND 工具都标 `READ`，但 `set_condition`、`confirm_step` 会写库，导航和下载也可能改变 UI/向导状态。
- **只有 `toolCallId` 级去重**：能防同一调用重放，不能防模型下一轮重新发起同一业务操作。
- **确认发生在前置校验之前**：用户可能先批准一个注定失败的 `start_*`，批准后业务校验才失败。
- **互斥粒度不够**：只有会话级锁；作业只按“同任务同类型”互斥，同任务的 `IMPORT` 和 `PUBLISH` 仍可能并发。
- **错误语义不可靠**：多处失败被包装成普通字符串并返回 `ok=true`，模型可能误以为成功并继续。
- **HITL 还有高风险竞态**：后置确认卡可能在 latch 登记前被点击，触发恢复流与原执行流并发。

## 建议的工具分类

| 类别 | 工具 | 默认策略 |
|---|---|---|
| **R 纯读** | `list_*`、`get_*`、`check_job_status`、`get_row_count` | 可并行、可重试，但要分页/限流/越权校验 |
| **W 创建写** | `create_task` | 业务幂等键，重复返回已有任务，不重复创建 |
| **J 异步作业** | `start_export`、`start_precheck`、`start_import` | 必须确认、按 `taskId` 串行、等待终态并验证 |
| **P 不可逆写** | `start_publish` | 每次确认、任务级全局串行、禁止盲重试、失败后人工/补偿 |
| **U UI/向导状态** | `navigate_to`、`select_definitions`、`set_condition`、`confirm_step`、打开编辑器 | 按会话/任务串行，带期望步骤或版本 |
| **F 文件/下载** | `download_export_files` | 按 artifact 幂等，重复返回同一结果，不重复下载 |
| **H 人工交互** | `generative_form`、确认门 | 单激活，同一会话只允许一个可操作交互 |

## “修复”应该怎么分流

不建议让 AI 自己猜怎么修。宿主应按错误类型路由：

| 情况 | 处理方式 |
|---|---|
| trim、大小写、去重、默认值等不改变语义的归一化 | 可以安全修复，但必须记录 |
| 参数格式或业务规则可修正 | 返回结构化错误给模型，限定重试次数 |
| 用户意图不清、范围扩大、不可逆操作 | 问用户，不自动补参数 |
| 越权、未知资源、类型错误、前置状态不满足 | 硬拒绝，不让模型绕过 |
| 超时、连接中断、副作用结局未知 | 先对账；确认未发生才允许重试 |
| 非法条件字段、未知 step/mode/page、跨任务 ID | 不自动修复，直接拒绝或要求澄清 |

尤其不能做这些“看起来聪明”的自动修复：

- 未知 `taskId` 自动换成当前任务；
- 非法条件字段丢弃后变成空条件、导出全量；
- `mode` 拼错自动当 `REPLACE`；
- 下载或 `start_*` 超时后自动重试；
- 某个工具失败后继续执行后续写操作；
- 自动批准 DANGER 工具。
