## 新 Important（附修法）

**I-4 `ITEM_OPEN` 门禁把 4 个 Runner 的“失败补偿写”变成空操作 → 作业 FAILED 而条目停在 COMPLETED**

本轮给 `finishIfJobStatusAllowed` 加了 `i.status IN ('PENDING','RUNNING')`，同时 `markItemFinal` 走同一门禁。但执行器的成功路径**先写条目 COMPLETED、再干会失败的事**，失败时靠 catch 里的 `finishItem(FAILED)`/`markItemFinal(FAILED)` 回退——现在这条回退恒为 0 行：

- `<REPO>/backend/src/main/java/com/example/configmgr/job/service/ExportJobRunner.java:170` 先 `finishItem(COMPLETED)`，`:174` 才 `excelWriter.write(...)`（写盘/权限/磁盘满失败），`:202` 的补偿 `finishItem(FAILED)` 被拒 → 条目留 COMPLETED 10/10，作业 FAILED，且无 Excel 产物。
- `PrecheckJobRunner.java:237` 之后 `:239 snapshot`、`:240 updateItemStatus`，异常落 `:255 finishItem(FAILED)` → 同样被拒。
- `ImportJobRunner.java:166` → `:167 updateItemStatus` 异常 → `:178 finishItem(FAILED)` 被拒。
- `PublishJobRunner.java:237` → `:239` 异常 → `PublishAbort` → `:301 markItemFinal(FAILED)` 被拒。

round0 下这四处是能生效的（当时无条目状态条件），所以是本轮引入的行为回归；`JobSideWriteGuardTest.markItemFinalAfterItemTerminalIsDropped` 还把“丢弃”写成了契约，但没同步调整执行器。影响：条目抽屉显示“已完成/满进度”，与作业 FAILED + 错误 issue 自相矛盾（`task_items` 仍被置 FAILED，只有 `job_items` 不一致），无数据损坏。

修法（二选一，均小改动）：
1. **推荐**：加一条“同轮补偿可降级”的仓库方法，仍用父作业在途做闸：
   `UPDATE JobItem i SET i.status=:failed, i.processed=:p, i.total=:t WHERE i.id=:id AND i.status IN ('PENDING','RUNNING','COMPLETED') AND EXISTS(parent IN ('PENDING','RUNNING'))`
   四个 catch 点改用它（只允许 COMPLETED→FAILED；CANCELLED 条目与已终态父作业仍不可翻写）。
2. 或**调整顺序**：把成功路径的 `finishItem(COMPLETED)` 移到本配置项全部动作之后（Export：移到 `:192` 之后），让 catch 的 FAILED 落在仍开放的条目上（顺带修掉“文件还没写出来条目已 100%”这个旧瑕疵）。
另补一条回归：作业在途 + 条目 COMPLETED → 补偿写 FAILED，断言最终状态（按选定语义固定下来）。
