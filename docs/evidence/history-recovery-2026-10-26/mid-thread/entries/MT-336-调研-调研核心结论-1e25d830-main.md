## 调研核心结论

1. **你的直觉就是业界主流**：「按时序混排」是有名字的设计模式（mid-stream tool call interleaving）。存储层证据最硬——**ChatGPT 导出就是一条有序消息数组**（assistant→tool→assistant 逐条排列）、**Kimi 服务端就是有序 blocks 数组**（think/text/tool 同级按序）、**DeepSeek 是有序 fragments**、Vercel AI SDK v5 干脆把 `content` 字符串废弃改成有序 `parts` 数组并定义为「用于渲染的唯一事实源」。**没有任何一家按类型分块存**——我们现在的 `content + toolRuns[] + pendingCall` 三桶模型是行业少数派。
2. **一个重要纠偏【静态阅读，落地前需实测】**：历史轮次**不是完全不可重建**——chat memory 里工具调用/工具结果本就是独立有序消息（`assistant(toolCalls) → tool → assistant(正文)`），丢失的只是**同一条 assistant 消息内部的正文↔工具交错**。这与 AG-UI 官方承认的损失**完全同类**，业界标准答案不是放弃混排，而是：历史与实时**共用同一渲染器**，显式声明这条上限（历史轮统一「工具组在前、正文在后」）。
3. **折叠/分组的通行规则**（LibreChat / VS Code / assistant-ui 三方一致，可直接照抄为验收标准）：折叠单位是**相邻连续块**（非类型桶）；进行中展开、完成后折叠；**用户手动展开过的组永不被自动收起**；**正文永不进折叠组**；单调用组不套壳直接展示。
4. **HITL 一张卡全生命周期**：确认区是工具卡的 `requires-action` 子区域，不是第二张卡（assistant-ui ToolFallback / LangChain 同一 call.id 就地更新）——从结构上消灭我们现在的双渲染；待决**默认展开**，决策后收成一行记录；待决项行业惯例是**复数**；超时不发自己的帧、靠轮终态帧收敛。

## 问题 4 设计终案（在一期方案上吸收调研校准）

- **消息模型**：`ChatMessage` 增有序 `parts[]`（TextPart/ToolPart/ReasoningPart，ToolPart 复用现有 `ToolRun` 形状+`requires-action` 态）；`toolRuns`/`pendingCall` 降级为**派生投影**（兼容存量调用点，逐步替换）；镜像带 parts。
- **实时轮**：纯前端重解释现有 15 类帧（每帧有 seq/atMs，帧序即真序），delta 遇到工具帧即封口成 text part——**零协议改动**；折叠/展开规则照抄上面第 3 条。
- **历史轮**：`GET /api/ai/history` 的有序消息喂**同一个 timeline reducer**（`assistant(toolCalls)`→text+tool parts、`TOOL`→回填结果、末尾 `ASSISTANT(正文)`→正文 part），声明上限=轮内正文↔工具顺序按「工具在前正文在后」呈现；「有 call 无 result」→重建为 `requires-action` 卡（HITL 可重新操作），叠加镜像已有的 expired 降级。
- **R-84 合并**：ToolPart 状态机（待决→执行→成功/失败/拒绝/超时/**结局未知**）一卡呈现，R-84 修单不再单独立项。
- **服务端**：一期不动；唯一候选增量=`textStart()` 的 CAS 从「每消息一段」改「每段一段+segmentId」（让协议层自带正文段边界），**建议放二期观察**，一期前端按 seq 切段已够。
