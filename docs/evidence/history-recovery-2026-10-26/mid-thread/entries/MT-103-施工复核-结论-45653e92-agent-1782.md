## 专项核查

### 1) 锁续租/释放是否可靠 — **设计可靠，停止粒度偏粗，缺测试**

- 获取：`SET ai:migrate:lock <uuid> PX 60000 NX`（`<REPO>/scripts/redis-run-migration.mjs:860`）。
- 续租：20s 定时，Lua `get == token` 才 `pexpire`（`:859-863`、`:880-890`）；token 不匹配返回 0 → 置 `lock.lost`；任何异常也置 `lost`（fail-closed）。
- 释放：`finally` 中 Lua `get == token` 才 `del`（`:899-910`）；释放失败由 60s TTL 兜底；**不会误删/误续他人锁**。
- 崩溃：最长 60s 自动过期；报告“最多 60s”准确。
- **粒度问题**：`assertLock` 只在 plan 前后、每个 run 前后、delete phase 1 前后/每个 DEL 前（`:943/945/978/981/845`）；**单个 run 内的 item/copy chunk 循环没有锁检查**。锁在 run 中途丢失时，当前 run 可以继续写到结束；报告/注释的“丢失停止写入”应改为“**在下一个检查点停止**”。
- **测试缺口**：没有续租测试（TTL 是否被延长、错 token 是否置 lost），也没有“丢失锁后停止写入”的测试；只有获取冲突、成功释放、异常路径释放。40/40 不能证明续租逻辑。
- 结论：**ADDRESSED（可靠性）**；**Minor** 级别的粒度/测试问题，不阻塞真实集群。

### 2) delete-source 两阶段是否“所有失败都不删” — **phase 1 是，phase 2 不是**

- Phase 1（`deleteVerifiedSources`，`:810-847`）：对所有候选做 `verifyEqual` + `ttlSufficient`；任一失败 `throw`，**此时一个源都没删**；测试 `:906` 两 run 一个 TTL 不足、`:926` delete 前目标被改/过期，均验证。
- Phase 2（`:849-856`）：仅 `assertLock`，然后逐个 `DEL`；**没有**再 `verifyEqual`/再读 TTL。若第 N 个 DEL 报错、或期间锁丢失触发 `assertLock`，前 N-1 个源已删除。每个已删源都刚通过 phase 1 的值+TTL 校验，**无数据丢失**，但“任一失败不删任何源”不成立；错误摘要应改为“**校验阶段失败不删；DEL 阶段失败可能部分删除（已删项均已校验）**”。
- **source/target=-1 语义**（`:382-420`）：`source=-1` 要求 `target=-1`；`source` 有限而 `target=-1` 视为安全；`target<=0` 拒绝；`-2` 拒绝；`target+1000 < source` 拒绝。与报告一致。**测试缺口**：只测了“source=-1/target 有限 → 拒删”，没测“source=-1/target=-1 → 允许”的接受路径。
- **新窗口**：phase 1→phase 2 之间没有逐项复验；若离线前提被破坏、旧进程在这段时间写入了**源键的新值**，phase 2 会把新值删掉而目标仍是旧值（旧实现是“逐项 verify→DEL”，窗口更小；两阶段为了 all-or-none 把早期候选的窗口拉长了）。离线窗口下不触发；建议 phase 2 每个 DEL 前再做一次轻量值+TTL 复验，缩小窗口。

### 3) 临时键 TTL 是否真防孤儿 — **不 100%**

- `writeViaTemp`（`:596-625`）：先 `del(temp)`；`write` 在**第一个 chunk 写成功后**调 `touch` → `PEXPIRE 1h`（`:603`）；最后按源 PTTL `PEXPIRE`，源 `-1` 则 `PERSIST`；失败 catch 清理；测试 `:954` 验证了“首个 chunk 之后”的 1h TTL、失败清理、源无 TTL 时 PERSIST。
- **不真防的情况**：
  1. **首个 chunk 写入成功 → PEXPIRE 之间**崩溃：临时键已存在但**没有 TTL**，这是**无界孤儿**；1h 安全 TTL 不覆盖这一段。报告第 75 行已承认“极小窗口仍可能残留无 TTL 临时键”。
  2. 复制耗时 **>1h**：1h 安全 TTL 到期后，后续 HSET/RPUSH/XADD 会**重建**临时键，而 `touch` 只在 `i===0` 触发一次，重建的键无 TTL；最终 `PEXPIRE/PERSIST` 前崩溃 → 无界孤儿。
- 修法：第一个 chunk 与 `PEXPIRE` 用 **`MULTI/EXEC`** 或 Lua 原子完成（同键同槽），保证临时键“要么不存在，要么有 TTL”；对超长复制按批次重新 `PEXPIRE`（或把安全 TTL 设得远大于单键复制时间）。这两点都是 Minor（泄漏，不是数据丢失）。

### 4) 是否有新数据丢失/误覆盖路径 — **离线前提下没有新 Critical；有两处 Minor 窗口**

- **误覆盖**：没有新增。STRING `SET NX`；HASH/LIST/STREAM 同槽临时键 + `RENAMENX`；目标存在时 `verifyEqual` 不一致即失败；锁 + token 防止两个迁移进程互删临时键/互删锁。rollback 旧裸键的“先查后写”TOCTOU 是上一轮已披露的既有边界，未恶化。
- **数据丢失**：
  - phase 1→phase 2 之间**源键被并发写入新值** → 新值被 DEL、目标仍是旧值。仅在离线前提被破坏时发生；两阶段把早期候选的窗口拉长（Minor，建议 phase 2 逐项复验）。
  - 目标 TTL 只比源短 ≤1s（`TTL_TOLERANCE_MS`）且 phase 1 耗时 >1s：目标可能在 DEL 前到期，源被删。属于临近过期数据，实际损失有限（Minor）。
  - phase 2 部分删除：每个已删源已校验，无数据丢失（表述问题，见 Important‑2）。
  - 锁在 run 中途丢失：当前 run 继续写，但所有数据写仍是 NX/RENAMENX，删源在全部 run 之后且逐项 `assertLock`；第二个进程最多造成冲突/部分目标，不会静默覆盖或丢源（Minor）。
- **结论：无新 Critical；无新的“静默覆盖”路径；新增的是两个受离线前提约束的窗口，均为 Minor。**
