## 六个重点专项

### 1. 临时键 hash tag 是否同槽 — **通过（构造上成立，但测试未钉住）**

`tempKeyFor(target) = target + ':__migrate_tmp__'`（`<REPO>/scripts/redis-run-migration.mjs:507`）。正向前缀形如 `ai:pending:{run:<runId>}`，临时键为 `ai:pending:{run:<runId>}:__migrate_tmp__`。Redis 只取第一个 `{...}` 作为 hash tag，两者都是 `run:<runId>`，**同槽**；`RENAMENX` 不会 CROSSSLOT。

但 fake cluster 完全不建模 CRC16/slot（`makeFakeCluster`，`<REPO>/scripts/redis-run-migration.test.mjs:351`），测试只断言 `renamenxCalls > 0`，**没有任何断言证明临时键与目标同槽**。当前代码是对的；这是一条测试证据缺口（I3）。

### 2. 目标已存在对账是否可靠 — **四类型值对账可靠；TTL 对账不可靠**

- 值对账本身可靠：STRING 直接比；HASH 用 `hgetall` 键集合+值；LIST 逐位比顺序；STREAM 逐 entry 比显式 ID 和字段顺序（`valuesEqual`，`:295`）。`verifyEqual` 先比 source/target 类型，再读全量值（`:326`）。
- **缺口**：`verifyEqual` 完全不比 PTTL；`planRun` 把“值相等”直接标 `identical`（`:463-470`），只把 `targetPttl` 记进报告。结合 `--delete-source`，会出现：目标值相同但 TTL 明显短于源（典型场景：上一次 apply 后旧进程继续心跳续了源 TTL，tagged 目标没有续），本次删源通过，目标提前过期 → 该 run 丢失。见 **I2**。
- STREAM 只比值/ID/字段，不比 `last-generated-id`、消费组等元数据；本仓无 `XGROUP/XREADGROUP`（已 grep 确认），风险低，但 `XADD` 显式 ID 后 `last-generated-id` 会重算，若历史上发生过尾部 `XDEL` 会改变后续自动 ID 语义。归 Minor（M8）。
- 二进制安全：`String(v)` 强制按 UTF-8 文本处理；本仓存 JSON 字符串，可接受，但需在文档里写清。

### 3. 冲突时写入/删除顺序是否安全 — **通过**

- 计划阶段发现任何 conflict（源类型不符、目标类型不符、目标值不一致）→ `runMigration` 在任何写入之前返回 `ok:false`，**所有 run 都不写**（`:757`）。
- apply 阶段若并发漂移导致 `copyItem` 抛错：异常向上抛，`deleteVerifiedSources` 根本不会执行，**源不会被删**；已写的目标保留，CLI 打印 partial results + `MIGRATION FAILED`。
- 删除阶段在**全部 run apply 完成之后**才进入（`:774`），且逐项 `verifyEqual` 后才 `DEL`（`:717-723`）。即使某项对账失败，已删的项都是刚刚验证过的，后续源保留；不会误删未对账的源。
- 唯一的顺序弱点：`deleteVerifiedSources` 是“逐项 verify→DEL”，不是“全部 verify 通过→统一 DEL”。某项失败时，前面已删的源不会回滚（但它们已验证）。若要求严格全有全无，改成两阶段（见 I2 修法）。

### 4. ROLLBACK 是否可能跨槽或误覆盖 — **不跨槽；有已披露的 TOCTOU 误覆盖窗口**

- rollback 目标是旧裸键，代码只发单键命令（`HSET/RPUSH/XADD/PEXPIRE/DEL`），**不涉及多键脚本或多键 DEL，不会 CROSSSLOT**。
- 误覆盖：`copyString` 仍用 `SET NX`；HASH/LIST/STREAM 因目标裸键与临时键无法同槽，退回“先查后写”（`supportsAtomicClaim` 为 false，`:512`、`:551/568/585`）。在“目标不存在”检查与首次写入之间若有人并发创建同类型目标，会 merge/append，不是原子拒绝。报告“已知边界”已明确披露，且要求离线窗口；**不构成 Critical**。
- 另一个作用域风险：`--rollback` 不带 `--run-id` 会扫到**所有** tagged run，包括新版本原生创建的 run；叠加 `--delete-source` 会删掉这些新键（warning 在删除之后打印）。见 M3。

### 5. SCAN / 参数 / RESP2 — **主路径正确；参数有一处真实作用域 bug**

- `scanPattern` 逐 master `SCAN cursor MATCH ... COUNT 1000`，循环到 `'0'`；`discoverRunIds` 遍历 10 个前缀，**从不调用 KEYS**；`--run-id` 时完全不扫描（`:165`、`:183`）。`ai:run:*` 不会误中 `ai:runs`。
- RESP2：`protocol: 2`、`disableClientInfo: true` 在 ioredis 6 源码中确实存在（`RedisOptions.js` 默认 `protocol: 3`、`disableClientInfo: false`；`event_handler.js` 有 RESP3 失败降级）。`SET NX` 返回 null、`RENAMENX` 返回 0 的处理与 RESP2 一致；Redis 5.0.14 不支持的 `HELLO/CLIENT SETINFO` 都被绕开。
- **I1**：`--run-id=` 和 `--run-id ,` 会得到 `runIds: []`，`parseArgs` 不报错，随后 `discoverRunIds` 走全库扫描。叠加 `--apply --delete-source` 就是“迁移并删除所有 run 的源键”。我已实测：

- Minor：`masterNodes` 在 `client.nodes('master')` 为空时回落 `[client]`，真实 Cluster 上若出现空 masters 会只扫一个随机节点并静默漏 run；建议 Cluster 下直接失败（M5）。

## Important（附修法）

### I1. `--run-id=` / `--run-id ,` 静默变成“全量”

**位置**：`<REPO>/scripts/redis-run-migration.mjs:874-884`。

**影响**：`--run-id="$RUN_ID"` 且变量为空是最常见的运维写法；当前会扫描所有 run。配合 `--apply --delete-source` 会迁移并删除所有源键。数据本身有对账保护，但**作用域被静默放大**，属于安全边界缺陷。

**修法**：

```js
} else if (arg === '--run-id') {
    const value = argv[++i];
    const ids = (value ?? '').split(',').map(s => s.trim()).filter(Boolean);
    if (ids.length === 0) throw new MigrationError('--run-id 缺少值');
    options.runIds.push(...ids);
} else if (arg.startsWith('--run-id=')) {
    const ids = arg.slice('--run-id='.length).split(',').map(s => s.trim()).filter(Boolean);
    if (ids.length === 0) throw new MigrationError('--run-id= 缺少值');
    options.runIds.push(...ids);
}
```

测试补三条：`parseArgs(['--run-id='])`、`parseArgs(['--run-id', ','])`、`parseArgs(['--run-id= , '])` 都抛错；再加一条“`--apply --delete-source --run-id=` 必须在连接/扫描前失败”（可只测 `parseArgs`）。

### I2. 删除源的“二次对账”不比 PTTL，存在目标提前过期导致丢 run 的路径

**位置**：`planRun` 的 `identical` 分支 `<REPO>/scripts/redis-run-migration.mjs:463-470`；`deleteVerifiedSources` `:717-723`。

**场景**：上一次 apply 已复制 tagged 目标，随后旧进程继续心跳续了源键 TTL、tagged 目标未续；本次重试值仍相等 → 标 `identical`；`--delete-source` 验证值相等后删源 → 目标剩余 TTL 很短，若新版本未及时续期就丢 run。当前测试 `<REPO>/scripts/redis-run-migration.test.mjs:533` 恰好构造了“目标 TTL 300s、源 TTL 600s”却只断言值，等于把该行为固化了。

**修法（最小安全版）**：
1. `planRun` 对 `identical` 项记录 `sourcePttl`/`targetPttl`；若 `targetPttl >= 0 && sourcePttl >= 0 && targetPttl + TTL_TOLERANCE < sourcePttl`，标记 `ttlShort`（不改变 `identical` 的 0 写语义，但禁止删源）。
2. `deleteVerifiedSources` 改成**两阶段**：先对所有候选源做 `verifyEqual` + TTL 充分性检查，全部通过后再统一 `DEL`；任一失败就整体不删。这样也顺带把“逐项 verify→DEL、前面已删后面失败”的顺序弱点收掉。
3. 判定：目标 PTTL 为 `-1` 视为不早于源（持久，安全）；目标 PTTL 短于源超过容差 → `MigrationError('拒绝删除源键：目标 PTTL 短于源 ...')`。
4. 测试：目标值相等但 `PEXPIRE` 1s、源 600s，`--apply --delete-source` 必须拒绝删源且源仍在；正向正常场景仍删 10 个。

若不想引入 TTL 容差，也可选择“值相等且目标 TTL 更短时，对目标 `PEXPIRE` 源的 PTTL 再删源”，但会打破“第二遍 0 写”的断言，需显式归类为 TTL 写，不推荐。

### I3. 测试对故障/竞态/分页/同槽/跨语言契约的覆盖不足

**位置**：`<REPO>/scripts/redis-run-migration.test.mjs`（fake 在 `:351`，SCAN 用例 `:465`，四类型 `:485`，冲突 `:554`，delete-source `:646`）。

**修法**：
1. 给 `FakeRedis` 加注入点（如 `beforeSet`、`beforeRenamenx`、`beforeDel`、`onCommand`），至少覆盖：
   - `SET NX` 返回 null（目标并发出现且相同/不同）；
   - `RENAMENX` 返回 0（同槽被并发认领）；
   - apply 中途抛错（例如第二次 HSET 抛 WRONGTYPE）→ 源全保留、`partialResults` 有前序 run；
   - delete-source 前目标被改/过期 → 不删源。
2. 大数据用例：stream 1200 条（跨 `STREAM_PAGE=500` 三页）、hash 1200 字段（跨 `HASH_BATCH=500`）、list 2500 条（跨 `LIST_BATCH=1000`）、SCAN 1500 个 key（跨 `SCAN_BATCH=1000`），断言值/顺序/ID 完整。
3. 同槽断言：加一个 `hashTag(key)` 帮助函数，断言 `hashTag(tempKeyFor(target)) === hashTag(target)`；或引入真实 CRC16-XMODEM 的 fake slot 检查（参考 Java `FakeLeaseRedis` 的 cluster 模式）。
4. 硬编码契约：对固定 `runId='r1'` 断言 `taggedKeyFor('ai:run:','r1') === 'ai:run:{run:r1}'`，10 个前缀全部写死；old 键同样写死 `ai:run:r1`。这样脚本与 Java `RunTag` 漂移会红。
5. 精确计数：首遍 apply `writes === 10`、非 STRING 族 `renamenxCalls === 8`；第二遍 `writes === 0`、`deleted === 0`。

## Minor（单列）

- **M1 临时键无 TTL，崩溃可永久残留**：`writeViaTemp` 先 `del(temp)` 再写，直到最后才 `pexpire`（`:516-535`）。崩溃在写 temp 中途且源之后过期，或 `RENAMENX` 返回 0 后、`del(temp)` 前崩溃，会留下无 TTL 的完整副本；重跑若目标已存在则不会走 copy 路径，也就不会清理。建议：首次写入后立即给 temp 一个安全 TTL（如 1h），最终用源 PTTL 覆盖；源无 TTL（`pttl=-1`）时 `PERSIST`。并修正报告“重跑会清理”的表述。
- **M2 无迁移锁**：并发两个 apply 会互相 `del(temp)` 并写出混合内容；虽然源保留、写后对账会报错，但会凭空造出一个 conflict 目标，需要人工清理。报告已把“单进程”列为边界；若 runbook 不能强制保证，建议加 `SET ai:migrate:lock <token> NX PX 60000`，finally 释放（或至少启动时 GET 检查）。
- **M3 rollback 全局作用域**：`--rollback` 不带 `--run-id` 会处理所有 tagged run，包括新版本原生 run；`--delete-source` 会删掉它们。建议 `--rollback --delete-source` 强制要求 `--run-id`，或删除前打印将删的 run 数并二次确认（当前 warning 在删除之后）。
- **M4 `--delete-source` 缺少 `--apply` 被静默忽略**：`runMigration` 在 `!apply` 时直接返回，dry-run 输出只说“no writes”，没说“delete-source 未生效”。建议打印 warning。
- **M5 `masterNodes` 回落 `[client]`**：真实 Cluster 上 `nodes('master')` 为空时只扫一个随机节点，会静默漏 run。建议：有 `nodes` 方法但返回空 → 抛 `MigrationError`；`[client]` 只留给非 Cluster/fake。
- **M6 stream 逐条 XADD**：每 run 最多约 6000 条（MAXLEN ~6000），串行 round-trip，多 run 时慢；可用 pipeline 分批（保持显式 ID、同键单槽）。
- **M7 报告元数据两处修正**：`SessionKeyRegistry` 13 键与 `deleteRun` 13 键的混用表述；“重跑会清理临时键”的绝对化表述。另把 `ai:activity:`、旧 `ai:resume:lock:`、`ai:ctx:*`、`ai:safety:*`、`ai:cfg:ver`、`ai:rate:*` 补进排除审计清单。
- **M8 STREAM 元数据/二进制**：不复制/校验 `last-generated-id`、消费组；不保留非 UTF-8 字节（`String(v)`）。本仓无消费组、只存 UTF-8 JSON，可接受，但应在“已知边界”写明。另测试 fake 的 `strlen` 用 JS UTF-16 长度、真实 Redis 是字节数，只影响计划里的 `count` 展示。
