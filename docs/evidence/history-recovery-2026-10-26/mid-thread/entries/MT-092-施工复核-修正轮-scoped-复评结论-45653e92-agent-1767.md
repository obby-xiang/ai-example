## 二、新发现问题

### Important（1 条）

**N-1 · 计数器与 fence 并非严格同寿，"不再需要 noeviction"属过度断言 —— 计数器先死就是 I-1 的变体（永久卡死）**

三条**只有 fence 有、计数器没有**的存活路径：

1. **写路径**：`save` → `fencedSet`（`RunStore.java:608-612`）每次都给 fence 续满 `session-ttl`；计数器只在 `ACQUIRE` 创建时和 READ 续期时被动到。⇒ 一个连续跑满 24h 的轮（有大量 save、没走 `touchActiveRun` 那 4 个读端点）会让 **fence 活着、计数器过期**。
2. **淘汰路径**：`volatile-*` / `allkeys-lru` 下按访问时间淘汰，fence 每笔 save 都刷新访问时间，计数器只在取号/读时被访问 ⇒ 内存压力下**计数器更可能先被淘汰**。这正是"运维约束放宽"不成立的地方：号源键不是"随 run 一起回收"，而是"比 fence 更容易先没"。
3. **重入路径**：`ACQUIRE` 命中现值时提前返回（`:140-143`），不做 `PEXPIRE`，也不重建已过期的计数器。

后果与 I-1 完全同型：计数器从 **1** 重来，残留 fence（比如 40）⇒ `fence > epoch` ⇒ 该轮**每次 save 都被 STALE_EPOCH 拒（500）**，而新租约还在被续租钉住，别人接不了管；要恢复只能手工删 fence 键。触发要"24h 无 READ"或"内存压力淘汰"，概率低，但代价是单轮**永久卡死**。

**修法（推荐 3 键自愈脚本，一次消掉本类全部入口）**：`ACQUIRE` 的 KEYS 变为 `[租约键, 计数器, fence]`（三者同 tag、同槽），脚本体：

```lua
local epoch = redis.call('INCR', KEYS[2])
local fence = redis.call('GET', KEYS[3])
if fence and tonumber(fence) >= epoch then epoch = tonumber(fence) + 1
   redis.call('SET', KEYS[2], epoch) end
redis.call('PEXPIRE', KEYS[2], ARGV[3])
redis.call('SET', KEYS[1], tostring(epoch)..'|'..ARGV[1], 'PX', ARGV[2])
return tostring(epoch)..'|'..ARGV[1]..'|1'
```

零额外往返、同槽、原子；命中分支也顺手补一次 `PEXPIRE`。收益：TTL 差、淘汰、重入、迁移（G2 的"若搬 fence 必须预置计数器"直接作废）**全都不再是问题**。折中方案（改动更小）：把计数器作为 `KEYS[3]` 加进 `FENCED_SET` 并 `PEXPIRE`，让两者共享 save 的刷新节奏——但仍挡不住"淘汰"。若不做任何代码改动，则必须在硬闸里把 **`maxmemory-policy=noeviction`（或 `volatile-ttl` + 长 TTL）** 从"可放宽"改回"必须"，并接受 24h 假设。

## 二、特别审：`有效租约 epoch >= fence` 是否可能误伤

**结论：判断本身不会误伤；但它是"一个字符之差"，而当前没有用例锁住这个字符（P-1）。**

**（1）为什么不会"留错"（该换却不换）**
`FENCED_SET` 的判据是 `fence > epoch ⇒ 拒写`（`RunStore.java:225` 脚本、`:1162` 认领）。所以 `epoch ≥ fence ⇔ 该持有人仍能写快照/认领执行`。保留它是正确的，**恰好 `epoch == fence` 是可写的最小边界** —— 作者用了 `>=` 而不是 `>`，这是对的；用 `>` 会把"正好等于 fence 的合法租约"判成陈旧。

**（2）为什么不会"换错"（不该换却换）**
要误换，必须存在"`epoch < fence` 但仍在写的持有人"。经过租约/认领两条路径都不可能：写快照要过 `fence > epoch`，认领要过同一个判据。唯一绕过点是 **E3 红线**（`heldRunEpoch == 0` 走 plain SET，不看 fence，`RunStore.java:550-557`）—— 但那是"进程内视图已丢、已经不持租"的态，与本次判断无关，属既有取舍。
副作用面也安全：陈旧持有人被换掉后，其 `renew` 因整值比对失败 → `renewTick` 摘视图并停续租（`:711-716`），不会误删新租约；已认领的工具仍由 `ai:claim` 的 `HSETNX` 挡住二次执行（换主语义与既有接管一致）。

**（3）P-1（Important）：`>=` 边界无用例锁定**
我把 6 个用例逐个走了 `>` 的假设：`staleLease…`（2<5，仍替换）、`counterExpiry…`（无租约，走 INCR 支）、`delayedAcquire…`（B 的租约到期后 A 走 INCR 支）、`twoInstancesRacing…`（fence=0，`1>0` 与 `1>=0` 同结果）、`reentrant…`（fence=0）、`missingFence…`（fence=0）。**把 `>=` 改成 `>`，6 条全绿**。而一旦真的回退成 `>`，后果是：`epoch == fence` 的**活租约被抢**，被抢方在 renew 失败前（≤1 个续租间隔）仍在自己视图里当自己是主人 → 双驱动窗口 + 一次无谓的 epoch 推进。

修法（8 行，直接钉住语义）：

```java
@Test
void aLeaseAtExactlyTheFenceIsValidAndIsNotStolen() {
    LeaseService.Lease held = this.storeA.tryAcquireRunLease(RUN_ID).orElseThrow();
    this.storeA.save(snapshot(RunSnapshot.RUNNING));           // fence == held.epoch()
    assertThat(this.fence()).isEqualTo(held.epoch());           // 语料前提
    LeaseService.AcquireResult other = newStore("inst-x").acquireRunLease(RUN_ID);
    assertThat(other.outcome()).isEqualTo(LeaseService.AcquireOutcome.HELD_ELSEWHERE);
    assertThat(this.fake.string(this.storeA.runLeaseKey(RUN_ID)))
        .as("epoch == fence 的活租约不得被替换").isEqualTo(held.epoch() + "|inst-a");
}
```

## 三、新增窗口审计（可用性 / 正确性）

**没有发现新的正确性窗口。** 我按下述路径逐一验过：

- 有效租约 vs 无租约 vs 陈旧租约三个分支互斥且都在同一 `EVAL` 内；两实例同时看到陈旧租约时，先落地者 `created=1`，后到者看到新值（`epoch>fence`）→ `HELD_ELSEWHERE`，不会双创建。
- 计数器**只会被抬高**：命中分支 `if counter < curEpoch` raise-only；取号分支 `epoch ≤ fence → fence+1` 也是抬；`INCR` 单调。不存在"把号推回"的路径。
- `save` 与 `acquire` 交错只有两种时序，两种都安全：`save` 先 → fence 变高，acquire 见到；`acquire` 先 → 新 epoch > 旧持有人 epoch，旧 `save` 被 `FENCED_SET` 拒。
- `fence`/`counter` 缺失按 0 处理（`tonumber(...) or 0`），`missingFenceAndCounterAreTreatedAsZero` 锁定"取号不写 fence"。
- Lua 无回滚导致 `SET` 失败时"号已推进"——只跳号（作者已注明）。

**Minor（不阻断，建议进 runbook 或 1 行加固）**

1. **fenceKey 传错 run 会静默降级**：三键脚本跨槽 → `CROSSSLOT` → 被 `catch` 折成 `UNAVAILABLE`（`LeaseService:461-465`）→ 该轮退化为进程内互斥。当前 3 个入口都传同 run 的 `fenceKey`，属编程错误面；建议在 Java 侧加一句 `tagOf(key).equals(tagOf(fenceKey))` 的断言（throw 放在 `try` 之外），把"静默降级"变成"启动/用例即红"。
2. **键类型损坏的爆炸半径变大**：`ai:fence:run:*` 或计数器被写成 HASH/LIST 时，`GET` 报 `WRONGTYPE` ⇒ **acquire** 失败（改动前只有 `save` 失败）。日志有 WARN 且带 key，可查；建议写进排障手册。
3. **超大 fence 值**（人工写入 > 2^63）会让 `fence+1` 变成浮点、写出 `1e+19|owner`，Java `parse` 失败 ⇒ `HELD_ELSEWHERE` 且该键滞留到 TTL。非数字已是 `or 0`，只有"巨数"没兜；可加 `if fence > 9007199254740992 then fence = 0 end`。
4. **`acquire(String,Duration,owner)` 仍公开**：未来的 run 租约调用方若误用它，会悄悄走**不自愈**的两键路径。建议 `@Deprecated` 或在 `epochKey != null && fenceKey == null` 时打一次显眼 WARN（现注释已说明，但注释不拦人）。
5. **`InMemoryRunStore` 仍用自己的 `epochSeq` 取号**（不走脚本），所以 conformance / gate 面捕获不到"自愈失效"的回归；这类回归只能靠 `LeaseEpochPerRunTest`。可接受，记录即可。
6. **类数口径**：报 132 类，我按 surefire XML 数 130 类（例数 830 完全一致）。
7. **交付依赖（非本批缺陷）**：共享工作树里 `ResilientChatServiceMemoryWriteTest.java:141` 是另一 agent 的新文件；是否真为"重载歧义"我**无法复现**（按要求不跑构建，且从 `ChatMemory.add(String,List<Message>)` 看该行应可解析）。结论只说事实：**它不属于本批文件集合**，但仓库级 `mvn test` 会卡在它上面，需其所有者收口后才能跑整门禁；本批 6/9/5 与相邻 830 是在隔离副本里验的。
