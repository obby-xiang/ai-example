## 五问结论

1. **Q1 全渲染 vs 逐卡**：不是二元，要分三层。**数据契约层**一律「一批一起送达」（同一模型 turn 的产物，AG-UI 明说没有 run 中途上行通道，做不出「发一张等一张」）；**布局层无任何规范**——同屏并列 / 队列逐卡 / 批摘要+下钻三派并存；**推进层**一致「整批齐备才续跑」。没有任何主流把「服务端只发第一个」当默认。
2. **Q2 客户端批量执行**：主流是客户端执行完整批、结果**一次性回灌**驱动下一轮。AG-UI 只能在下一 run 的 input 回传；AI SDK 靠 `lastAssistantMessageIsCompleteWith...` 整批齐才自动续跑；Anthropic 强制结果同一条消息。CopilotKit 是「每 call 一张卡、各自悬挂 Promise、各自 follow-up」。
3. **Q3 握手术语**：骨架统一为 `pending → 逐项决策 → 整批回执 → 恢复`，但帧名各异（`Command(resume=)` / `resume[]` / `RunState.approve` / `mcp_approval_response` / `tool-approval-response` / `respond()`）。幂等只有 AG-UI 明文要求（规则 5）。
4. **Q4 乱序防错配**：一律 id 绑定，不用位置。唯一位置耦合是 LangGraph 同 node 内多 `interrupt()` 的索引配对，官方专门写警告——反证位置绑定是错的。AG-UI 用「原子提交」抹平乱序；OpenAI 允许逐条决、未决再挂。OpenAI 还要求服务端持真相、拒收客户端替换参数。
5. **Q5 已知风险**：审批疲劳→橡皮图章（WorkOS 综述）；**批内夹带**已是命名攻击技术 ATR-2026-00118，对策是高风险项禁批量批准 + bulk/individual 分开审计；Claude Code #36983 并行组首个提示**未显示即静默拒绝**并谎报「用户拒绝」；AI SDK #10980 半批执行导致孤儿 `tool_use` → 400 **永久毒化会话**。

## 对本项目的建议（两条路线）

- **路线 A 维持串行逐卡**：改动最小、注意力集中，但单槽 UI 上「已批准未提交」无归属，必须另加 `decisions` map，否则退化成服务端半批推进（AG-UI 禁止、AI SDK 会毒化的形态）；且用户失去横向比较；若真「一张一 resume」就得让 gate 层拆分批量调用，改变模型可见的工具契约。
- **路线 B 并行渲染 + per-call 绑定**：与 AG-UI/LangGraph/OpenAI 同构、支持乱序；代价是前端单槽改多槽、要防误触「全部批准」、per-call 幂等与审计、卡片多了反而促批量批准。
- **推荐组合**：**B 的契约 + A 的默认视图**——状态层多槽 + `toolCallId` 绑定 + 整批齐备才续跑；呈现层默认折叠成「待确认 3 项」批次条、只展开第一张；`n≤2` 同屏、`n≥3` 走逐张向导；DANGER 级不进「全部批准」。并明确一条**半批禁区**：决策完成 ≠ 执行，执行只发生在整批 resolved 之后的续跑里。
