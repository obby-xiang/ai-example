## 工具编排调研结论

### 1. AI 一次调用多个 tool 是允许的

OpenAI、Anthropic、Gemini 都允许一次响应多个 tool calls：

- [OpenAI function calling](https://platform.openai.com/docs/guides/function-calling) 支持 `parallel_tool_calls=false` 来限制为 0 或 1 个。
- [Anthropic parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use) 默认允许多个，可用 `disable_parallel_tool_use` 关闭。
- [Gemini function calling](https://cloud.google.com/vertex-ai/generative-ai/docs/multimodal/function-calling) 也会一次返回多个 `functionCall`，但没有看到同等的并行开关。

**是否并发执行不是模型决定的，是宿主决定的。**模型只是提议一组调用，宿主可以串行、并行、限流或拒绝。

### 2. 顺序不是协议保证，配对才重要

主流协议都以 `toolCallId` / `tool_use_id` 配对结果，不把“按原顺序返回”当硬约束。Anthropic 还要求每个 `tool_use` 都必须有对应 `tool_result`。

[LangGraph ToolNode](https://github.com/langchain-ai/langgraph/blob/main/libs/prebuilt/langgraph/prebuilt/tool_node.py) 默认并发执行多个工具，但结果列表保持调用顺序；这再次说明“执行并发”和“展示顺序”是两件事。

### 3. HITL/GF 没有统一的“必须独占一批”标准

业界做法并不统一：

- AG-UI：一个 run 的所有 open interrupts 都处理完才恢复。
- OpenAI Agents SDK：允许先处理部分审批，其余继续挂起。
- LangGraph：多个 interrupt 按 ID 恢复，同一节点内更偏顺序语义。
- Power Automate：明确支持顺序审批和并行审批。
- AutoGen：单激活、整个人机回合阻塞。

所以“**HITL/GF 一批只能一个**”不是行业标准，但可以作为我们产品自己的安全策略。

## 当前项目审视结果

当前实现是**事实串行，不是显式互斥**：

- 后端按模型返回的 `tool_calls` 数组顺序逐个执行，见 `backend/src/main/java/com/example/configmgr/ai/gate/SpToolCallingManager.java:141`。
- 没有并发执行、依赖图、批次 ID 或互斥元数据。
- HITL/GF 挂起时会阻塞同批后续工具，但前序工具的副作用已经发生，批次不是原子审批。
- 后端可以保存多条 pending，但前端投影和操作入口基本是单一 pending，多张待决卡存在操作错位的风险。

最重要的新发现是一个 **Critical 竞态**：

- `suspended` 帧会提前把整批 pending 发给前端，见 `frontend/src/utils/parts.ts:498`。
- 如果确认卡排在后置工具，用户可能在后端 latch 登记前点击“确认执行”。
- 此时可能触发恢复流程，与原始执行流并发驱动同一个 `runId`，造成两次模型请求、历史或快照互相覆盖。

这比“是否允许并发 tool call”更紧迫，属于应先修的安全边界。

## 我建议的编排裁决方向

暂不改代码，建议形成一份“工具编排专项裁决”：

1. **拆开两个开关**
   `allow_parallel_tool_calls` 控制模型能否一次发多个；`max_tool_concurrency` 控制宿主如何执行，不能混为一个“并行开关”。

2. **给 18 个工具补编排元数据**
   至少包括：副作用、幂等、可并发、互斥组、资源键、顺序依赖、是否交互式、超时与取消策略。

3. **默认可并行范围收窄**
   纯只读、无共享状态的工具可并行；WRITE、DANGER、前端状态修改、任务启动、导航、表单、确认门默认串行。

4. **交互工具默认单激活**
   HITL/GF 不建议与其他交互工具同时可操作；可以允许同批存在，但只有一张进入“可交互”状态，其余显示等待。

5. **批次要有显式身份和顺序**
   增加 `batchId`、`callIndex`、`dependsOn`、批次状态；展示顺序与完成顺序分开记录。

6. **先修 Critical 竞态**
   在 latch 未武装前，确认卡不得可点击；恢复流程必须和原执行流互斥，并持有 session/run 级锁。

7. **取消、超时、部分恢复另行裁决**
   一个工具超时或拒绝时，同批其他工具是继续、取消还是等待，需要按工具类型定，不宜一刀切。
