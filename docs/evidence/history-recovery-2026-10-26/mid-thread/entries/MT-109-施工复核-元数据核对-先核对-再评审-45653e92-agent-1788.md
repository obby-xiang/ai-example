## Critical-1：V6 外键挡不住“取消后迟到写”，并发下仍会产生数据库孤儿

**结论：** 报告称“这类迟到 INSERT 由 V6 子表 FK 拒绝，删除后不会留下数据库孤儿行”，该结论在 H2 上**只在 INSERT 语句本身晚于删除提交时成立**。目标窗口恰恰是长事务 runner 的 INSERT 已在删除提交前发出、COMMIT 落在删除提交之后——H2 外键只在语句执行时校验，**提交时不复检**，该行会作为孤儿提交成功。

**证据（可复现，均在库副本上，未动原库）：**

1. 用真实 `tasks` / `task_files` 表 + V6 约束复现（`<LOCAL_WORK>/_r113-db-v6/RealSchemaRace.java`）：
   - runner 连接：`INSERT task_files(task_id=<T>)`（未提交）
   - 删除连接：`DELETE FROM task_files WHERE task_id=<T>` 影响 **0 行**（看不到未提交行）→ `DELETE FROM tasks WHERE id=<T>` 成功 → 提交
   - runner 随后 `COMMIT` **成功**，查询结果：`orphan task_files rows=1`；连续 2/2 次复现。
2. 合成表最小复现（`FkRaceProbe.java`）：`parent rows=0, orphan child rows=1`。
3. H2 语义探针（`FkSlockProbe.java`）：父行被 `FOR UPDATE` 锁住时，子表 INSERT **不阻塞**（2ms 返回）——H2 的 FK 检查不取父行共享锁，因此既没有“父行锁 → 提交期复检”的保护，也不会形成 task↔child 死锁。

**为什么这不是理论窗口：** `ImportJobRunner` 是整轮 `@Transactional`（`.../job/service/ImportJobRunner.java:60`），`stagingRowRepository.saveAll` 后紧跟 `dataRowRepository.findRow`、`progressService.*` 等查询，Hibernate 自动 flush 会把这些 INSERT 提前发到库；取消只改 job 行，runner 在分片边界 `break` 后**正常提交**（`ImportJobRunner.java:126-145` 一带）。`ExportJobRunner`/`PrecheckJobRunner` 同理，分别覆盖 `task_files` / `validation_issues`。因此“取消 → 立即删任务”正是规格允许的路径，也是产生孤儿的路径。

**与现有测试的关系：** `TaskDeleteInFlightGuardTest.lateCancelledRunnerWritesAreRejectedWithoutOrphans`（`.../task/service/TaskDeleteInFlightGuardTest.java:148-181`）是在删除**已提交之后**再 `saveAndFlush`，顺序场景必然通过，**没有覆盖本问题**；报告把该用例当作“迟到写被拒”的证据，证据强度不成立。

**修法（按推荐度）：**
- **A1（推荐，改动小）**：删除闸门从“job 状态”升级为“runner 是否仍活着”。取消提交后 runner 仍会跑，删除前检查该任务所有 job 的 runner lease/心跳（单实例用现有 `JobHeartbeatRegistry`，`finish` 已负责 `clear`；多实例用 Redis `runner-active:<jobId>`，分片边界续 TTL）。仍活 → 返回 409/423 + 可重试提示（“作业正在收尾，请稍后重试”），不进入级联。这样“无孤儿”变成确定性成立，代价是把“CANCELLED 立即可删”改成“取消后需等 runner 退出”（即报告第 3 条自己标注的语义变更，需要裁决，但不是可以省的）。
- **A2（若必须保持“立即删”）**：两阶段删除——先提交 `DELETING` 墓碑（任务行保留），列表/详情即时不可见；迟到写落在墓碑上（FK 合法），后台在 runner 租约到期后清理子表并物理删任务。工作量更大，但语义与“无孤儿”都成立。
- **无论选哪种**：补一个**双连接并发回归**（insert 未提交 → delete 提交 → insert 提交 → 断言 0 孤儿）。现在写这个测试应当是 RED，正好作为 C1 的 RED 证据。
- 附带：C1 也会让物理文件残留更严重（迟到 `task_files` 行落库成功 → 文件被孤儿行引用，删除路径再也扫不到它）。报告“物理文件残留”的限定需要随 C1 修正一起收紧。

**修法：** 产出任务级 diff（或按 hunk 标注归属），报告“改动文件”逐项写“本批 hunk / 他批 hunk”。代码本身没有过度改动——R1-13 的净改动（两个锁点 + 删除守卫 + V6 + 两个测试 + 前端错误拆分 + `DefinitionDeleteTest` 夹具）是相称的；`StaleJobRecoveryRunner` 的锁也属必要。

**I-2　V6 迁移对“目标库已有孤儿”没有防御，且不是幂等的。**
V6 是 5 条裸 `ALTER TABLE ... ADD CONSTRAINT`。只要某一个环境（同事库/历史 E2E 库/未来 MySQL）在这五张表里有孤儿，启动即失败；H2/MySQL 的 DDL 部分提交后，版本未记录、约束已存在，重跑会报“constraint already exists”，需要人工 repair。我已在 `backend/data` 库副本上验证：当前 0 孤儿、V6 可一次通过（flyway 历史仅 V1–V4），但这是**碰巧干净**，不是迁移自身保证的。
**修法：** 每条约束单独一个迁移文件；加 `DROP CONSTRAINT IF EXISTS` 前置；或在脚本前加一条会明确报错的孤儿计数检查（并注明“需先由人裁决清理”）；报告写明各环境上线前必须跑的五表孤儿核查 SQL。

**I-3　“所有相关路径统一 task → job”措辞过强，安全性依赖一个未固化的实现细节。**
逐路径核对（H2 上）：`delete`（task 锁→读 job→删子表/job）、`createAndStart`（task 锁→INSERT job）、`cancel`（读 job→task 锁→条件 UPDATE job）、`StaleJobRecoveryRunner`（task 锁→UPDATE job）都确实是 task→job，**无环**。但 `JobTerminalWriter.apply`（`.../job/service/JobTerminalWriter.java:103-113`）在同一个外层事务里先 `finish` 后 `applyJobOutcome`——它不形成环的**唯一原因**是 `JobProgressService.finish` 内部又开了一层 `REQUIRES_NEW` 并先行提交（`JobProgressService.java:132`），job 行锁在写 task 前已释放。若有人把 `finish` 改成 `REQUIRED`，就变成“持 job 行锁写 task”，与 delete 的 task→job 立即构成死锁。另外 `TaskService.updateStatus` / `applyJobOutcome` 直接写 task、不取 task 锁，也不在“统一先锁 task”的表述内。
**修法：** 在 `JobTerminalWriter` 外层事务写 task 前补 `taskService.lockForUpdate(taskId)`（此时无 job 锁，成本极低、安全），把不变量做成字面成立；或至少在 `finish` 上加注释+测试锁死“必须 REQUIRES_NEW”，并把报告改成“job→task 方向在 finish 先行提交的前提下不成立”。同时注明该结论是 H2 语义（FK 不取父行 S 锁）；若将来换 InnoDB，删除持 task X 锁 + 子表 INSERT 取父行 S 锁会形成真实环，需要重新评估。

**I-4　V6 让“合法写路径”在并发删除下从“造孤儿”变成“500”且未纳入契约。**
`TaskService.selectDefs`、`FileController.save/upload`、`updateItemStatus` 等子表写入路径都没有 task 锁：并发删除后，插入会被 FK 拒绝，以 `DataIntegrityViolationException` → 500 暴露（`FileController.save` 还会先写盘留下物理文件，报告只提了 upload，未提 PUT）。这比孤儿好，但属用户可见的错误契约变化，报告未说明。
**修法：** 在这些入口先做 task 存在性判定并统一映射为 404/409（或在 `GlobalExceptionHandler` 对 FK 冲突映射业务码）；`FileController` 的“先写盘后落行”要么改成先落行后写盘，要么把 PUT 也写进残留清单。
