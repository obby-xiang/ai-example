**我的设计：点击 = 跳转查看（复用现有 goStep 管道），不做独立查看面板**。规则：

- **回跳**（目标步 < 当前步）：自由放行，等价于连点「上一步」，各步空态/数据已有承载；
- **前跳**：按 `nextStep` 守卫逐站校验（未选配置项不得跳入查询/导出步；导入第 1 步必须先 `flushEditors` 落盘），点击远步 = 依次校验，任一不过则停在守卫点并提示原因；
- **运行中作业**：跳转不中断作业（与现有上一步/下一步行为一致），回来自有 watch/快照自愈；
- **数据加载**：点击进场走与按钮完全相同的按 index 加载钩子（`loadEditors`/`loadStaging`/`resumeJobs`），不新增第二条加载路径；

## 问题 4：对话界面按时序展示 —— 设计方案（待裁决，建议与 R-84 合并施工）

【实测】「拆开」的根因有两层：① 模板渲染顺序硬编码为 正文 → 工具卡 → 挂起卡，与帧到达顺序无关；② 同一 toolCallId 双渲染（store 对挂起类帧同时写 `pendingCall` 和 `toolRuns`，模板各出一张卡），且 `pendingCall` 单槽位互相覆盖。**时序数据在协议层是完备的**（每帧单调 `seq` + 服务端钟 `atMs`，单流单 emitter 锁内出帧），**但前端入库那一刻就被销毁**（delta 拼进一个字符串、消息模型无任何时间/序号字段）。**硬缺口**：服务端不落 delta 归档、chat:mem 把整轮正文合并成一条消息——**历史轮次的「正文↔工具」交错已不可重建**。

**我的设计（两期）：**

- **一期（前端为主，合并 R-84 工具卡语义修单）**：
  1. 消息模型引入**有序时间线**：每条 assistant 消息持 `timeline[]`，文本段（相邻工具事件之间的 delta 聚合）、工具卡、HITL 卡统一为带 `seq/atMs` 的时间线条目，渲染严格按 seq；
  2. **同一 toolCallId 一卡全生命周期**：待决 → 执行中 → 成功/失败/拒绝/超时，终结「一调用两卡」；顺手落地 R-84 的「结局未知/降级」卡片态（R-84 裁决点随施工报告一并呈你）；
  3. 镜像（sessionStorage）补时序字段，刷新不丢序；
  4. **历史轮次诚实降级**：服务端无法重建交错，历史按「正文块 + 工具卡列后」渲染（视觉与现状一致），仅新产生的轮次严格时序——不伪装时序。
- **二期（不建议做，除非你有强需求）**：后端正文段边界（一轮多对 message_start/end）+ delta 归档——存储成本上升、触及 Spring AI 记忆语义（影响模型上下文），收益只是把历史轮次也变时序。
