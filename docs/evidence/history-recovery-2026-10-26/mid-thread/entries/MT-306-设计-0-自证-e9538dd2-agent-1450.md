## 1 读路径事实（刷新后一张卡怎么长出/怎么消失）

刷新后前端串行读三个源，任何一个缺口都会表现为"卡没了"：

1. **本地镜像**（sessionStorage，含未收敛轮的实时产物）——`frontend/src/stores/ai.ts:1102` `loadHistory` 先读镜像并做 v1→v2 迁移、残留收口（`:555` `sanitizeMirrorResidues`：`requiresAction→false`、`pending→expired`）。
2. **后端历史** `GET /api/ai/history/{sessionId}` —— 读的是 Spring AI `ChatMemory`（`backend/.../web/AiController.java:927-940`，`:932`）。**关键**：记忆只在该轮**终态**时整体写入（`ResilientChatService.java:1030` `convergeMemory`，仅被 `:778/:922/:945` 三个 DONE/FAILED/CANCELLED 路径调用）。⇒ **挂起中的这一轮不在 history 里**；而 history 非空时前端把 `this.messages` **整体替换**（`stores/ai.ts:1201`）。所以刷新后，挂起轮的正文、已完成工具卡也一并不可见——**恢复卡是这一轮在界面上的唯一载体**，卡没有＝整轮从界面消失。
3. **挂起快照** `GET /api/ai/runs/current`（`AiController.java:713-765`）→ `restoreSuspendedSnapshot`（`stores/ai.ts:1418-1570`）。

恢复建卡三条判据（`stores/ai.ts:1458-1472`）：`PENDING` + `kind∈{CONFIRM,FRONTEND}` + **`req===true`**。而 `suspended`（禁用输入）只看"存在任意 PENDING"（`:1458-1463`）——**与 req 无关**。这就是"输入禁用 + 上方无卡"的直接成因。

`req` 的机制：独立 HASH `ai:req:<runId>`，HSETNX 首写者胜（`RunStore.java:129`、`:971` `markRequestEmitted`、`:977` `putIfAbsent`），由 `ConfirmGate` 在**发帧之前**置位（`ConfirmGate.java:435` `reserveRequestSlot`、`:709`）。`/runs/current` 已透出 `name/arguments/kind/req/reqAtMs/expiresAt/atMs/preflight`（`AiController.java:737-754`）——**重建卡片内容所需的字段一个不缺，唯一缺的是"这一帧到底发没发"这个位**。

卡面渲染需要段 `requiresAction=true`（`stores/ai.ts:1494-1503`），再分四支（`components/AiPanel/AiPanel.vue`）：CONFIRM 待决 `:515`；GF `:570`（还要 `activeForm` 被武装，`stores/ai.ts:1533`）；表格写预览 `:592`（还要 `stalePreviewToolCallId`，`:1510`）；上传交接 `:605`（还要 `activeUploadHandoff`，`:1514`）。

**为什么它是"僵尸"（不是一会儿就好）**：

- 启动扫描对"仍有 PENDING 外部条目"的轮直接 skip（`StartupResumeRunner.java:139-152`，reason=`PENDING_UNRESOLVED`；判据源 `ResumeService.java:243`、硬闸 `:544-551`）。⇒ 没有进程会再走到 `await` ⇒ `req` 永为 null。
- `/runs/current` 每次读都续期非终态快照（`AiController.java:729` → `RunStore.java:1524-1543`，24h 滑动）。⇒ **只要用户还打开页面，僵尸不会靠 TTL 自己烂掉**（这与挂账里"靠 TTL 收敛"的表述有出入，值得更正）。
- "停止"只写 Redis 取消标志（前端 `stores/ai.ts:3009-3019`；后端 `AiController.java:603-621` 只写标志），**没有等待者消费它** ⇒ 不会把该轮写成终态；本地 `suspended=false`，下次刷新又回到"禁用 + 无卡"。
- 决策路径本身不是死的：`ConfirmGate.java:1246` `maybeTriggerResume` + `:1453` `hasActiveLatch` 就是为"重启后外部输入刚到"设计的死卡兜底（重启后 `woke=false` → 抢租 → `ResumeService.resume`）。但见 §2 的多卡限制。

## 2 分卡型影响表（用户怀疑"不一定都受影响"——核实：确实只有一类受影响）

| 卡型 | 刷新后来源 | 受 `req=null` 影响 | 实际表现 | 缺什么 / 能否重建 |

| **已决回执卡**（门已批准/拒绝/超时；GF 已提交） | history（`toolCallStates` + decision/decidedAt/submittedValues，`stores/ai.ts:1254-1276`） | **否** | 正常渲染只读卡 | 无 |
| **普通工具结果卡**（已执行） | history（`toolCallStates` 的 status/outcome） | **否** | 正常渲染（旧载荷缺状态→占位 succeeded/UNKNOWN） | 无 |
| **BACKEND 待决条目** | — | 无关 | 从不建卡（kind 过滤），符合设计 | — |

一句话：**用户判断对——只有"等待动作的挂起卡"受 `req` 影响；工具结果卡、已决回执卡、已提交表单回执完全不受影响。** 但要注意第 6/7 行只覆盖"已收敛轮次"，挂起中的这一轮整体不在 history，所以该轮**所有**卡（含已执行工具卡）刷新后本来就不可见——这是既有的另一条挂账"回复过程中刷新"，与 `req` 无关。

**另外查到两条会影响方案选择的事实**：

- **同一形态不用升级也能复现**：`saveSuspended` 把整批 pending 一起落库、请求帧逐条发（`ConfirmGate.java:76-80`）。所以"多确认门批次执行到一半进程重启"→ 没发过帧的那几张 `req=null`，启动扫描 skip，同样是"无卡僵尸"。
- **多卡孤儿"批一张"不生效**：`ResumeService` 对"仍有 PENDING 外部条目"直接 `PENDING_UNRESOLVED`（`:544-551`）。只画一张卡、只批一张，续跑仍不启动，前端会停在"已提交，同步中…"（`stores/ai.ts:2053-2085` 的 `syncGateFromAuthority` 永远拿不到裁决）。中等方案必须"整批渲染 + 批量决策"或"未发帧条目一次性转终态"。

## 3 版本升级影响面（通性）

- 严格说 `req=null` 只来自 **L0（2026-10-21）之前**落库的挂起轮（`PendingToolCall.java:169`；出口 `Boolean.TRUE.equals` 缺键即 false，`AiController.java:745`）。
- 但"旧载荷缺新判据 ⇒ 卡消失"**不是一次性事件**：同形态在"多卡批次中途重启"就可达；history 路也已经踩过同族坑并各自打了补丁（`toolCallStates` 缺失→占位；`decision` 缺失→刷新回执卡不渲染，R-160 才修；镜像 v1→v2 迁移）。
- 根因是**结构性**的：恢复路径的门禁"只认新字段，缺字段就不渲染"；history 路径的口径是"缺字段就降级为占位/只读"。两路口径不一致，于是每加一个判据（未来的 `resultView` 版本、新 kind 值、新必填字段）都会再产生一批"凭空消失的卡"。
- 所以"版本兼容"的正解不是逐版本写迁移，而是定一条读路径规则：**不能证明可操作 ⇒ 渲染只读降级卡（带失效说明），而不是不渲染**；再加一个载荷版本戳（pending 条目带 `schemaVersion`，缺失/未知即 legacy），未来只需一处识别。

## 5 推荐：A+，理由

1. **直接消灭最差形态**：用户的核心诉求是"别一刷新就拉跨"。A+ 把"空白 + 输入禁用 + 停止也无效"变成"看得到一张说明清楚的失效卡 + 一键结束本轮"。
2. **老卡在语义上确实不可继续**：进程死了、模型调用链断了；多卡批次有 `PENDING_UNRESOLVED` 硬闸；provider 可能已变。B 把它包装成"还能批"，大概率换来"已提交，同步中…"这个更难受的第二种坑。
3. **成本/风险最低**：A 纯前端；A+ 只加一个读侧判据 + 一个端点，复用现成的 `cancelPendings` + 终态 `save()` 联动，不碰实时路径、不改 `req` 语义。
4. **有通性收益**：把"缺字段⇒不渲染"改成"缺字段⇒只读降级"，与 history 路既有口径统一，以后每次升级都不会再出现"卡凭空消失"；顺带修复 `blocks.ts:432` 对门卡 `expired` 显示"已超时"的语义错位。
5. **不与既有裁决冲突**：不去恢复 HITL 超时（守住 2026-10-20「审批/表单不限时」），也不动 24h 滑动 TTL；`orphan` 判的是"没人能推进这一轮"，不是"等太久"。

A+ 的两条硬性护栏（施工时必须写进验收）：① **活轮的 `req=false` 卡（卡 2/3）不得显示"已失效/结束本轮"**——判据必须用 `orphan`，不能只看 `req` 缺失；有活闸门时维持现状或给中性"等待前一步完成"只读卡。② **跨实例**：`hasActiveLatch` 只覆盖本进程，必须叠加 `ai:lease:run:<runId>` 持有判断；租约设施不可用时保守回退为"只读、不给结束按钮"。③ 发布口径兜底：若 A+ 赶不上本次发布，至少在发布说明里写"升级前请先结束挂起轮"，并把 `GET /api/ai/startup-resume` 的跳过原因暴露给运维。

**验证边界（如实申报）**：本次是只读源码勘察（含既有证据文档 `docs/evidence/补档-L0刷新恢复-施工报告.md` §7-5、`docs/任务看板.md:471`、`docs/决策看板.md:14`），未跑任何单测/E2E、未起服务；行号为本树实测，与施工报告里的旧行号已有漂移（报告写 :1297-1320，实测 :1458-1472）。§1 的"停止对孤儿轮不收敛""页面刷新续期 24h""多卡批次批一张不生效"三条是我从代码推出的结论，建议施工前用一次真实升级穿越 + 重启复现来锁定。
