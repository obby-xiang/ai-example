### 1.2 根因复核结论（一句话）

**issue 根因成立且可复现路径清晰（`watch(selectedDefs)` 不同步 workspace ⇒ `buildContext().extra.selectedDefs` 为空、`dataVersion` 不递增、面板无「工作区已同步」），但 issue 给出的"建议修复"不完整：它只修好了"AI 能读到页面选中集"，而系统提示词里那句权威的「已选配置项」来自后端 task items（手动勾选不落库、切步才落库），修复后会出现"任务行说旧集合 / 额外上下文说新集合"的对立，减选场景下模型仍可能答错。**

支撑证据（新发现，issue 未提）：

- `ContextBuilder.java:70-74`：
  ```java
  List<String> selectedDefs = task.getItems().stream().map(i -> i.getDefCode()).toList();
  if (!selectedDefs.isEmpty()) { sb.append("已选配置项: ").append(String.join(", ", selectedDefs)).append("\n"); }
  ```

## 3. 修复设计（阶段二施工蓝图；**尚未施工**）

### 3.1 核心设计判断：程序性恢复 vs 用户手动勾选 —— 用**幂等收敛 + 相等短路**区分

**方案（推荐）**：在页面内引入唯一收敛点，写入前与 `workspace.selectedDefs` 做**顺序敏感的逐项比较**，相等则**不写、不 touch**；不等才 `setSelectedDefs`。

```ts
// ExportWizardView.vue（锚点：类/组件级 helper，紧随 selectedDefs 声明区）
/** 选中集变化 → 收敛到 workspace（唯一写入口）。
 *  相等短路 ⇒ 程序性恢复（loadTask→enterPage 已同步）不会二次 touch / 误增版本；
 *  真实变化（手动勾选/减选、AI handler）才记动作，供 AI 侧 buildContext 感知。 */
function syncSelectedDefsToWorkspace(source: WorkspaceActionSource = '界面'): void {
  const codes = [...selectedDefs.value]
  const current = workspace.selectedDefs
  if (current.length === codes.length && current.every((code, i) => code === codes[i])) return
  workspace.setSelectedDefs(codes, 'REPLACE', source)
}
```

改动点（预期 4 处，均在 `ExportWizardView.vue`）：

1. `watch(selectedDefs)`（`:928`）末尾追加 `syncSelectedDefsToWorkspace()`（保留原 `draftModels` 补全逻辑）。
2. `persistStepData()`（`:437`）把裸 `workspace.setSelectedDefs([...selectedDefs.value])` 换成 `syncSelectedDefsToWorkspace()`（避免同一选中集被重复记两次动作）。
3. `registerPageHandler('export.selectDefs')`（`:786-793`）在写 ref 后显式 `syncSelectedDefsToWorkspace('AI')`——让"AI 驱动"这条路的动作来源保住 `'AI'`（面板 chip 与 `recentActions` 会显示来源，`AiPanel.vue:37`）。
4. 非本页：`frontend/src/stores/workspace.ts:175-182` `setSelectedDefs(codes, mode = 'REPLACE', source: WorkspaceActionSource = '界面')`，把 `source` 透传给 `:181 touch(summary, source)`（**附加可选参数，向后兼容**，现有 3 个调用点无需改动）。

**为什么"相等短路"能精确区分两类写入（关键论证）**：

- 程序性恢复：`loadTask` 的 `:298` 赋 ref 与 `:304` `enterPage` **在同一个同步块内、无 `await` 间隔**；Vue `watch` 默认 `flush: 'pre'`，回调必定在同步块结束后才跑 ⇒ 回调执行时 `workspace.selectedDefs` 已等于 ref（`enterPage` 是 `[...selectedDefs.value]`，同序）⇒ 短路，**不二次 touch**。跨任务改绑同理（旧任务选中集被 `enterPage` 覆盖后再比较）。【实测（代码级）+ 阶段二探针 s4/s7 断言版本增量恒为 1】
- 用户手动勾选/减选：`workspace.selectedDefs` 是上一状态（通常 `[]` 或上一任务集合）⇒ 不等 ⇒ 写入 + `touch` ⇒ `dataVersion` 递增 + `workspace_changed` 广播（面板「工作区已同步」chip）⇒ AI 下一轮 `buildContext()` 可见。**issue 期望的三件事（AI 答对 / 上下文 `selectedDefs` 更新 / 版本递增）由这一处同时满足。**
- AI handler 路径：handler 先显式以 `'AI'` 收敛，随后 watch 再比较时已相等 ⇒ 短路，不会产生第二条"来源：界面"的假动作。

**被否决的备选方案**：

- (B) `watch` 里无条件 `setSelectedDefs`：实现最短（issue 建议的形态），但恢复任务时**每个任务多一次 touch**（版本 +1、`recentActions` 多一条假"界面"动作、面板闪一次假 chip），正是任务书点名的"误触 AI 上下文刷新"。**否决**（除非把它仅当作降落伞——见下）。
- (C) 显式抑制标志（`let suppress = false`，程序性赋值前置位、`nextTick` 后释放）：能区分，但引入时序耦合（`applyTaskBinding` 内含 `await router.replace`，抑制窗口跨 await 后释放点脆弱），且 `resetTaskScopedState` 之类的后续改动容易破坏它。**只作备选**。
- (D) 只改 handler（AI 侧）或只改 watch（手动侧）：任一都留下另一条通路缺口（§2 #1/#2 是同因的两个入口）。**否决**。

## 1. K1–K10 逐项结论

### K1 相等短路正确性 —— **过（附 S4 理论面 R5）**

【实测代码实读】两向导的收敛点均为：

```ts
const codes = [...selectedDefs.value]
const current = new Set(workspace.selectedDefs)
if (current.size === codes.length && codes.every((code) => current.has(code))) return
```

- **空集 vs 从未同步**：短路判据只比集合，不区分「来源」，故与两态区分（后端职责）无耦合。空 ref vs 空 workspace：`0===0` 且 `every` 空真 ⇒ 短路，正确【实测 s4：恢复任务 recentActions 无「已选择配置项」】。
- **大小写**：比较是精确字符串相等（`has`），`'currency'` ≠ `'CURRENCY'` 会判不等 ⇒ 触发写入——正确行为（勾选编码大小写不同就是不同项），无假短路风险。
- **codes 含重复/脏值 ⇒ 假不等？**【推断，机制逐环确认】：`REPLACE` 模式（`this.selectedDefs = [...codes]`）不去重。若 AI handler 传入 `defCodes=['A','A']`（`ExportWizardView.vue` handler 的 REPLACE 分支直接 `codes` 赋 ref），则 ref/workspace 可含重复元素；此后每次相同调用 `current.size(1) !== codes.length(2)` ⇒ 恒不等 ⇒ 每次都 touch。**不构成 touch 风暴**：watcher → 收敛点 → workspace 写入不回馈页面 ref，无自触发环；每次 touch 对应一次显式 AI 调用，记账语义可辩护。`ADD` 模式与 `runUiEvent` 的 select_defs 各自既有去重/直传形态未变。定为 R5/S4（低危理论面，顺手修法：收敛点写入前 `Array.from(new Set(codes))`）。
- **顺序不敏感**（裁决⑤）：`Set` 比较 + `every has`，纯重排正确短路；导出顺序变化不进 `recentActions` 是施工报告 §6-7 已登记的已知取舍，维持。

### K2 恢复路径幂等（时序反例构造）—— **过，反例不可构造**

【实测代码实读 + 探针双证】恢复链：`onMounted` 的 `enterPage`（不带 `selectedDefs`，`ExportWizardView.vue:973`）→ `loadTask` 内 `selectedDefs.value = items.map(...)`（`:326`）与 `workspace.enterPage({... selectedDefs: [...selectedDefs.value]})`（`:332-340`）在 **同一个 await 之后的同步块**（ImportWizardView 同构：`:400` 与 `:408-417` 之间无 await）→ `watch(selectedDefs)`（默认 `flush:'pre'`，`:1029`）的回调在当前同步块结束后的微任务 flush 才执行 ⇒ 此时 `workspace.selectedDefs` 已等于页面值 ⇒ 短路。`watch` 在 `setup()` 顶层注册、先于 `onMounted` 生效，监听不缺位。

反例逐一尝试（均不成立）：
- 「flush 抢在 enterPage 前」：Vue 的 pre-watcher flush 由 `queueJob` 调度、只能在当前同步块让出控制权后运行，而 ref 赋值与 `enterPage` 之间无让出点——**时序上不可能**【推断：调度机制逐环确认】；
- 「watcher 回调读到旧值」：回调不使用参数快照，直接读 `selectedDefs.value` 最新值——同 tick 内用户/AI 再改 ref 也读到最新，无害；
- 「同 tick 多次写 ref」：pre-watcher 合并去重，只回调一次，读最新值；
