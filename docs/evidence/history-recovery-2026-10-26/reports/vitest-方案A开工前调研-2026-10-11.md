### 2.2 与本仓 Vite/Vue 大版本的兼容判定

| 候选组合 | 与 `vite 6.4.4` | 与 `vue 3.5.43` | 结论 |
|---|---|---|---|
| **vitest 4.1.11 + @vue/test-utils 2.5.1 + jsdom 30.1.2** | ✅ peer `^6.0.0` 覆盖 6.4.4 | ✅ test-utils peer 为 `vue: 3.x` | **推荐**（且是 CVE 修复地板，见 §2.4） |
| vitest 5.0.3 + 同三件套 | ✅ peer `^6.4.0` 覆盖 6.4.4 | ✅ | 可用，但属"大版本很新"路线（见 §2.3） |

【实测】两条 peer 区间均由 registry 原始 manifest 取得；本机 `node v22.23.2` 同时满足两者的 engines；`jsdom 30.1.2` 要求 `node >= 22.22.2`，本机 22.23.2 满足。

**4 vs 5 的取舍建议：选 4.1.11。** 理由（每条都有据）：
1. **它是安全地板且已被本仓实测**——前批可行性工程用 4.1.11 跑通 28/28；换成 5.x 需重跑验证，而收益只是"版本号更新"。
2. **5.0.0 发布于 2026-09-03**（迁移指南页面更新于 2026-09-28），距今约 5 周，属"新大版本"；其破坏性变更（`clearMocks` 默认改 `true`、`extends` 默认 `true`、benchmark API 重写、`.vitest` 工件目录统一、`test.sequential` 移除等）对本批"全新写测试"多数无感，但 `clearMocks: true` 默认值会改变 mock 调用历史的语义，属"现在踩不到、以后会咬人"的一类。
3. 5.x 的 peer 地板更紧（`vite >= 6.4.0`），而本仓 `package.json` 声明的是 `^6.0.7`——**声明区间比地板更宽**：一旦有人删掉 `yarn.lock` 重装，vite 可能落到 6.0.x~6.3.x，届时 5.x 的 peer 契约被违反。选 4.1.11 时该风险面更小。
来源：<https://vitest.dev/guide/migration/>、<https://vitest.dev/releases>

【推断】若选 5.x，建议同批把 `vite` 声明由 `^6.0.7` 收紧为 `^6.4.0`（或干脆不动、依赖 `--frozen-lockfile`）。本报告按 4.1.11 出草案。

### 2.3 jsdom vs happy-dom 的当前主流取舍

| 维度 | jsdom 30.1.2 | happy-dom 20.14.6 |

### 3.3 vitest 配置文件草案：独立 `vitest.config.ts`（建议）vs 与 vite 共资

**建议：新增独立 `frontend/vitest.config.ts`。** 理由与代价如下（两条已确立的事实支撑）：

1. **事实（必须先知道）**：一旦存在 `vitest.config.*`，vitest **不再读 `vite.config.ts`**。故 `@` 别名与 `@vitejs/plugin-vue` 必须在 `vitest.config.ts` 里重新声明，否则测试里所有 `@/...` 解析失败。【实测·前批已证】
2. **本仓 `vite.config.ts` 的默认导出是"函数"**（`({mode}) => ({...})`，内含 `loadEnv` 与 `/api` 代理）。这与 `mergeConfig`（要求对象配置）不直接相容——要走共资就得把现有函数包一层或改写导出形态，**等于动了正在正常工作的生产构建配置**。
3. 因此取舍是：**独立配置（生产构建配置零改动，重复声明 2 行：plugin + alias）** vs **把 `test` 段直接写进 `vite.config.ts`（单一事实源，但生产构建文件的 `defineConfig` 需从 `vite` 改为 `vitest/config`，即让生产构建依赖一个 devDependency 的导出）**。本仓文化偏"最小爆炸半径、不动已验证的路径"，故选前者。
4. 独立文件的"漂移风险"是**自曝型**而非静默型：若有人日后往 `vite.config.ts` 加别名/`define`/`dedupe` 而忘了同步，测试会立即大面积解析失败（红得很响），不会悄悄变绿。

草案（与既有 `vite.config.ts` 的 `@` 别名、`vue()` 插件逐字对齐）：

```ts
// frontend/vitest.config.ts（新增）
import { defineConfig } from 'vitest/config'
import vue from '@vitejs/plugin-vue'
import { fileURLToPath, URL } from 'node:url'

// 注意：本文件存在时 vitest 不再读 vite.config.ts，
// 故此处必须与 vite.config.ts 的 plugins / resolve.alias 保持同值（漂移会立即在测试里炸出来）。
export default defineConfig({
  plugins: [vue()],
  resolve: { alias: { '@': fileURLToPath(new URL('./src', import.meta.url)) } },
  test: {
    environment: 'jsdom',
    include: ['tests/**/*.spec.ts'],
    setupFiles: ['tests/setup.ts']
    // 不设 globals：显式 `import { describe, it, expect, vi } from 'vitest'`，
    // 免动 tsconfig 的 types 数组，也免引入全局符号。
  }
})
```

配套夹具（前批实测出的**必需**项）：

```ts
// frontend/tests/setup.ts（新增）
// jsdom 无 ResizeObserver：SpreadGrid.vue 在 onMounted 成功路径要 new ResizeObserver(...)，
// 缺失时异常会被 try/catch 吞成"引擎加载失败"的假象。
class ResizeObserverStub {
  observe(): void {}
  unobserve(): void {}
  disconnect(): void {}
}
;(globalThis as unknown as { ResizeObserver: unknown }).ResizeObserver = ResizeObserverStub
```

**备选（若更看重单一事实源）**：把 `test` 段并入 `frontend/vite.config.ts`，并把该文件第 1 行 `import { defineConfig, loadEnv } from 'vite'` 改为 `import { defineConfig, loadEnv } from 'vitest/config'`（`vitest/config` 的 `defineConfig` 是 Vite 的超集，兼容既有全部字段与函数式用法）。此时不需要 `vitest.config.ts`，别名/插件天然共资。代价：生产构建配置的导入源指向 devDependency，且 `vite.config.ts` 的 `include` 已在 tsconfig 中（会被 `yarn typecheck` 检查），必须确保类型干净。

### 3.6 CI 集成建议：**并入既有 `frontend` job（不新立 job）**

插入位置（`.github/workflows/ci.yml:73-79` 之间）：

```yaml
      - name: 类型检查（vue-tsc --noEmit）
        run: yarn typecheck

      # 新增：单测（阻断）。实测 28 用例 ~1.6s，job 上限 20 分钟，余量极大。
      - name: 单元测试（vitest run）
        run: yarn test

      - name: 生产构建（vue-tsc + vite build）
        run: yarn build
```

**建议并入的理由**：
1. **零额外成本**：同 `working-directory: frontend`、同 `cache: yarn`、同 `node-version: '22'`；独立 job 要重复一次 checkout + setup-node + `yarn install --frozen-lockfile`（约 +40~70s 与缓存重复占用），而测试本体只花 ~1.6s——**为 1.6 秒的工作再付一次完整安装成本不划算**。
2. **门禁语义更清晰**：`frontend` job 的定义就是"前端门禁"；把类型/单测/构建三件放在一起，读 Actions 界面即知全貌。
3. **超时无风险**：job 上限 20 分钟，冷缓存首次跑约 15 秒级（Windows 杀软影响），Linux runner 更短。
4. **失败归因已由 step 粒度解决**：Actions 界面能明确区分 `类型检查` / `单元测试` / `生产构建` 三步，不需要靠拆 job 来归因。

**顺序**：放在 `typecheck` 之后、`build` 之前——三者都是阻断项，顺序不改变 job 的成败判定，只改变"一次运行能看到哪些失败"；类型错误与逻辑失败都便宜（1.6s），放前面能避免在源码逻辑已坏时还去烧最重的构建。注意一个既有副作用：`build` 脚本本身也含 `vue-tsc --noEmit`，若 `typecheck` 或 `test` 失败则 `build` 步骤不执行（既有注释已说明此为有意设计）。

**反方意见（供指挥官取舍）**：若希望单测**不阻断**（夜间/观察制）或想把覆盖率产物单独上传 artifact，则应新立 job（`needs: frontend`、加 `continue-on-error: true`）。但这与本批"把欠账变成回归锁"的立项动因相冲——**建议阻断**；确实要观察制，也应另开一个 job 而不是把阻断项降级。另：`docs` job 的 6 条断言与 `scan-history` 均不受本批影响（见 §5）。
