# 「文本 / 工具调用 / HITL 混排展示」业界调研报告

## 0. 一个先要澄清的发现（会影响裁决）

你给的现状是「15 类帧」。但当前仓库 `<REPO_ROOT>` 里已经多了一组边界帧，语义与本次裁决直接相关：

- `SseChatEmitter.messageBoundary(phase, kind)` → 帧名 `message_start` / `message_end`，`kind ∈ {text, reasoning}`；`delta` 是中间的内容帧（`backend/src/main/java/com/example/configmgr/ai/run/SseChatEmitter.java:492-531`）。
- 该方法的注释原文就在说这件事：「一条 assistant 消息可能"先吐思考、再吐正文、中间夹工具调用"，而前端此前只有 content 帧 —— 无法判断两段文本属于同一条消息还是两条……边界帧 + `messageId` 让"哪几帧属于同一条消息"成为协议事实，而不是靠客户端猜。」
- 但 `textStart()` 用 `textSegmentOpen.compareAndSet` 做的是**每条消息只开一段**，整轮所有 delta 仍汇成同一段（`ResilientChatService.java:620-630`）；落定时 `finish()` 把整轮 text 作为**一条** `AssistantMessage` 追加（`ResilientChatService.java:447-479`）。

所以：**协议层已经为"时序混排"埋了一半基础设施，但"每轮正文一段"是把混排压平的那一半。** 这条建议你先确认现场基线，它决定了「改造面」是纯前端还是需要服务端配合。

### 1.1 AG-UI 事件模型（`<LOCAL_WORK>\agui-raw\md\`）

**消息/事件结构**【官方文档】

| 维度 | AG-UI 的做法 | 出处 |
|---|---|---|
| 文本 | `TEXT_MESSAGE_START(messageId, role)` → N×`TEXT_MESSAGE_CONTENT(delta)` → `TEXT_MESSAGE_END`；三段式 | `concepts_events.md:184-264` |
| 工具 | `TOOL_CALL_START(toolCallId, toolCallName, parentMessageId?)` → N×`TOOL_CALL_ARGS(delta)` → `TOOL_CALL_END` → `TOOL_CALL_RESULT` | `concepts_events.md:287-394` |
| 结果载体 | `TOOL_CALL_RESULT` **本身是一条消息**（`role:"tool"`，自己的 `messageId`），「does not reopen the call it answers」 | `spec_1.0_events_tool-calls.md:48-100` |
| 归属 | `parentMessageId` **可选**，「a tool call belongs to the message that carries it」 | `spec_1.0_events_tool-calls.md:34-40` |
| 边界语义 | 关闭的消息「closed, not sealed」——可用同 `messageId` 再发 `TEXT_MESSAGE_START` 续写，内容**追加**；工具调用同理可"重开"续写 args | `spec_1.0_events_text-messages.md:38`、`spec_1.0_events_tool-calls.md:56-62` |
| 消费约束 | `TOOL_CALL_END` 之前**不得**对 args 采取行动（此刻只是前缀） | `spec_1.0_events_tool-calls.md:48` |
| 消息模型 | `AssistantMessage { content?: string; toolCalls?: ToolCall[] }`——**两个并列字段，字段间无顺序信息** | `concepts_messages.md:130-143` |
| 历史同步 | `MESSAGES_SNAPSHOT` 整表替换，用于初始化/断连恢复；`reasoning`/`activity` 在快照里是 all-or-nothing | `concepts_events.md:489-515` |
| 中断（HITL） | 终局式：`RUN_FINISHED.outcome = {type:"interrupt", interrupts:[...]}`；客户端以**新一轮** `RunAgentInput.resume[]` 续跑；同 `threadId`、必须覆盖全部 open interrupt、`expiresAt` 过期即 `RunError` | `concepts_interrupts.md:9-49, 124-145` |
| 中断与工具的关系 | `reason:"tool_call"` + `toolCallId` 绑定到先前 `ToolCall*` 序列；**续跑那一轮不重发** `ToolCallStart/Args/End`，直接 `TOOL_CALL_RESULT` 打在原 id 上 | `concepts_interrupts.md:197-209` |
| 中断 UI 契约 | `message` 是人类可读兜底文案；`responseSchema` 描述期望载荷，`editedArgs` 的**存在本身**就是"允许改参数"的能力信号 | `concepts_interrupts.md:85-94, 211-231` |
| reason 分类 | 核心三值 `tool_call` / `input_required` / `confirmation`；未知 reason 客户端**不得报错**，用 `message`+`responseSchema` 兜底渲染 | `concepts_interrupts.md:171-196` |

**要点**：AG-UI 把「时序」放在**事件流**里，把「消息」做成粗粒度容器（content + toolCalls）。因此实时轮有序，**历史轮由实现方自己决定如何折叠**——这正是它的已知损失点（见 §2.3）。

**对前端渲染的指引**（AG-UI 明确"协议不规定呈现"）：`spec_1.0_events_text-messages.md:14-17`、`spec_1.0_events_tool-calls.md:12-15` 只说「typically rendered as a chat transcript」「surface a tool call as it streams — a card naming the tool, arguments filling in」，不规定卡片形态。

### 1.3 原始数据采样观察（`<LOCAL_WORK>\原始数据\`）

**ChatGPT（`chatgpt_6a98d463.json`，87 条 message）——最强证据：它就是一条时序数组**

- `messages` 是扁平**有序**数组；一条完整的工具轮形如：
  `assistant(recipient=web) → assistant(recipient=web.run) → tool(web.run) → tool(web.run) → assistant(content_type=thoughts) → assistant(content_type=reasoning_recap) → assistant(终答)`
- `recipient` 字段承担"这一步交给谁"的语义（`all` / `web` / `web.run`）；`author.role` 出现 `tool` 共 16 条，`author.name='web.run'`。
- 工具输出**不在 content.parts 里**，而在 metadata：`search_model_queries.queries[...]`、`search_result_groups`、`tool_icons:["globe"]`、`reasoning_title:"正在搜索…"`（即"工具调用 = 卡片元数据 + 一行标题"，正文里没有它的位置）。
- 思考是独立 content_type：`thoughts`（`summary` + `content` + `source_analysis_msg_id` 回指被解释的正文）与 `reasoning_recap`（`content:"思考了两秒"`, `reasoning_recap_type:"hide_all"`）。**recap 是"折叠后的一行摘要"这一范式的直接物证。**

**DeepSeek（`deepseek_56fb623a.json`）**：`content` 为 `null`，真实内容在 `fragments` 有序数组中；实测类型 `REQUEST / TIP / THINK / RESPONSE`，每段带 `id`（段级 id）、`stage_id`、`elapsed_secs`、`references`。→ **消息 = 有序 typed fragments**。

**Kimi（`kimi_ListMessages_服务端原始响应.json`，61 条）**：`blocks` 为有序数组，元素形如 `{'id','parentId','messageId', 'multiStage'|'stage'|'think'|'text'|'tool'}`，`parentId` 串成链；`tool` 块 = `{toolCallId, name, args, contents[], status:"STATUS_DONE"}`。一条实测顺序：`multiStage → stage → think → text → tool → multiStage → stage → think → text`。→ **服务端本来就按时序存 blocks，且工具块与文本块同级**。`kimi_1a02c52d.json` 是 `[{r, t, think, tools, summary}]` 的轮级形态。

**结论**：三家产品在存储层都是"有序 typed parts/blocks"，**没有任何一家是"按类型分块"存的**。我们的 `ChatMessage { content, toolRuns[], pendingCall }` 是行业里的少数派。

### 2.2 协议 / SDK 层的消息模型

**Vercel AI SDK v5：从 content 字符串改成有序 `parts` 数组**【官方文档】
- `UIMessage { id, role, metadata?, parts: UIMessagePart[] }` ——「The parts of the message. **Use this for rendering the message in the UI**」。
- part 类型：`text`（带 `state:'streaming'|'done'`）、`reasoning`、`tool-${name}`、`source-url`、`source-document`、`file`、`data-${name}`，以及 **`step-start`（多步 agent loop 的步边界）**。
- `ToolUIPart` 是一个显式状态机：`input-streaming → input-available → output-available | output-error`，全部挂在**同一个 `toolCallId`** 上。
- 出处：[UIMessage 参考](https://ai-sdk.dev/v5/docs/reference/ai-sdk-core/ui-message)、[v5 迁移指南](https://ai-sdk.dev/docs/migration-guides/migration-guide-5-0)。

**持久化语义**【官方文档 + 社区实践】：`UIMessage` 被明确定义为「source of truth for your application's state… it is what you persist」；历史还原靠 `originalMessages` + `onFinish` 存整个 parts 数组（[AI SDK 5 指南](https://www.matthewswong.com/en/blog/vercel-ai-sdk-5-guide/)、[vercel/ai discussion #7988](https://github.com/vercel/ai/discussions/7988)）。→ **只存最终文本 = 主动丢掉可回放性，业界把它当反模式。**

**Anthropic Messages API：content blocks 是有序数组**【官方文档】
- assistant 的 `content` 可以是 `[text, tool_use, tool_use, …]`，"Claude will often comment on what it's doing or respond naturally before invoking tools"，即**正文与工具块同列有序**。
- 但顺序有**API 合法性**硬约束：`tool_result` 必须紧跟在对应 `tool_use` 之后、必须在 user 消息 content 数组的**最前**，任何 text 只能排在其后（否则 400）。→ **这是给模型的格式约束，不是 UI 约束，但意味着"文本可以出现在工具调用之后"是被支持的。**
- 出处：[Implement tool use](https://docs.claude.com/en/docs/agents-and-tools/tool-use/implement-tool-use)。

**OpenAI Responses API：输出是 items 的有序数组**【官方文档 + 社区解析】
- 输出组织为 output items（message / function_call / reasoning），最终 `output` 数组**保留 announcement order**；流式用 `output_item.added / delta / done` 闭合每个 item。→ 与 parts 模型同构。
- 出处：[Responses API streaming 事件指南](https://community.openai.com/t/responses-api-streaming-the-simple-guide-to-events/1363122)、[output array 顺序讨论](https://github.com/ollama/ollama/issues/18798)。

**A2A：刻意不做单流全序**【官方规范】
- Task 生命周期流：`Task` → 交错 `TaskStatusUpdateEvent` / `TaskArtifactUpdateEvent` → 终态。工件的坐标是**「artifact ID + part 序号」二元组**，而不是单一序号；也就是「一条流无法干净描述一切」被显式接受，由消费方自己合账。
- 出处：[A2A 规范（流式）](https://a2aproject.github.io/A2A/latest/specification/)、[A2A Task Lifecycle 分析](https://jpcasabianca.com/journal/a2a-task-lifecycle/)。
- **对我们的意义**：单流全序（我们有 seq）其实是**比 A2A 更强的保证**，不该放弃它去换"分类数组"。

### 2.3 开源聊天 UI 组件库怎么渲染

| 项目 | 做法 | 关键细节 |
|---|---|---|
| **assistant-ui** | `MessagePrimitive.Parts` **按 parts 顺序逐个渲染**；`GroupedParts`/`groupPartByType` 做**相邻**分组（`reasoning` + `tool-call` → 一个 collapsible "chain of thought"） | 【官方文档】[Message 原语](https://www.assistant-ui.com/docs/primitives/message)、[Chain of Thought 指南](https://www.assistant-ui.com/docs/guides/chain-of-thought)。默认：`Text` 渲染 `<p>`+streaming 光标，**未注册 UI 的 tool call 什么都不渲染**（必须显式给 fallback） |
| assistant-ui + AG-UI 运行时 | 明确记录**回放损失**（见下） | 【官方文档】[AG-UI runtime options](https://www.assistant-ui.com/docs/runtimes/ag-ui/runtime-options) |
| **LibreChat** | 「Activity groups **collapse each contiguous block** of Agent reasoning and tool calls under a generated one-line header」；「**Loaded history uses the same grouping**」 | 见下，最完整的产品级答案 |
| **LangChain（前端 SDK）** | tool 卡**挂在 AI 消息下**、出现即渲染 pending 卡、**同一 `callId` 就地更新**（pending→completed/error） | 【官方文档】[Tool calling（JS）](https://docs.langchain.com/oss/javascript/langchain/frontend/tool-calling)；最佳实践含"Always handle all three states"、"**Keep cards compact. Tool cards sit inline with chat messages**"、"Provide a generic fallback（可折叠 JSON）" |
| Vercel AI Elements | `ChainOfThought` 是 **collapsible** 组件，"step-by-step reasoning with complete/active/pending 状态与进度指示" | 【官方文档】[Chain of Thought](https://elements.ai-sdk.dev/components/chain-of-thought) |

**assistant-ui 记录的两条"历史不可逆"损失（与我们处境完全同构）**【官方文档，价值最高】：

> 「An AG-UI assistant record carries `content` and `toolCalls` as separate fields **with no ordering between them**, so its text is **restored ahead of its tool calls whatever order the run streamed them in**.」
> 「Reasoning is restored ahead of the assistant record's own parts, so reasoning that arrived **between two blocks of one live message** comes back before both.」

以及它的三条应对：
- 用**多条 assistant record** 逼近时序：「A turn that spoke, called a tool, then answered sits on the wire as **three assistant records**」；
- 无结果的 tool call → 重建为 `requires-action`（HITL 卡**可重新操作**）；
- 中断态**必须由后端额外持久化**（`metadata.custom.agui.interrupts`），否则「interrupt state cannot be reconstructed」；
- 子 agent 嵌套「does not survive a reload」（只保结果与决策，不保嵌套）。

**LibreChat 的产品级规则（最贴合"混排"裁决的一套）**【官方文档，[Agents 文档](https://www.librechat.ai/docs/features/agents)】：

- 折叠单位是**连续块**，不是类型桶；每块头部是**生成的一行摘要**（可用便宜模型生成）。
- 「**Short progress text remains inside its parent phase. When the Agent begins a substantial answer, LibreChat closes the phase before that text so the user-facing result stays outside the collapsed summary.**」← 正文永远在折叠组之外，这是硬规则。
- 「Persisted phase boundaries are **rebased** when malformed or omitted content parts are compacted, so the grouping remains aligned after reload.」← 历史回放时分组边界可重算。
- 「**Stopped, cancelled, failed, and completed steps retain distinct statuses, including after a conversation reload.**」← 终态跨刷新保持。
- 工具卡生命周期分两段：**Preparing**（SDK 交付前，可能含审批等待）与 **Calling**（交付到结果）；完成卡两段都显示。
- 「a tool group that contains **a single call opens directly to that call's details**」← 单卡不留多余层级。
- 流式时展开面板跟随到底部，**用户向上滚动即暂停跟随**。

### 2.5 历史回放：交错是否保留、怎么存

- **保留，且与实时同一套分组**：LibreChat「Loaded history uses the same grouping」「Stopped/cancelled/failed/completed steps retain distinct statuses, including after a conversation reload」。
- **保留的代价是"持久化 parts"**：AI SDK 把 `UIMessage.parts` 定义为要持久化的东西；assistant-ui 的 history adapter 用 `fromAgUiMessages` 反序列化；**中断态必须单独持久化**否则不可重建。
- **哪些交错会丢（已知上限）**：AG-UI 线上只有 `content` + `toolCalls` 两个字段 → **同一条消息内部的正文↔工具顺序必然丢失**，还原时统一按"正文在前"处理；子 agent 嵌套不跨刷新保留。
- **服务端确实都存了时序**：ChatGPT 的导出文件就是有序 `messages` 数组（含 `tool` 角色消息）；Kimi 的服务端响应就是 `blocks` 有序数组 + `parentId` 链；DeepSeek 是 `fragments` 有序数组。→ **"历史轮次不可重建"在本行业不是常态，是省了存储的代价。**
- **折中做法参考**：LibreChat 只持久化**分组边界**（phase boundaries），回放时按 parts 重算/rebase，不追求逐 token 位置还原。

## 3. 对本场景的设计启示

### 3.0 先修正一个前提

我读了当前仓库，有一条与"历史完全不可重建"不符的证据（**建议你实测确认**）：

- 每轮的工具调用与工具结果**已经以独立消息落进 chat memory**：`SpToolCallingManager.java:198-203` 落定 `assistant(toolCalls)` + `ToolMessage(responses)`；(ResumeService 同构)
- `GET /api/ai/history/{sessionId}` 返回的是 **memory 里的有序消息列表**，每条带 `type/text/toolCalls/toolResponses/timestamp`（`AiController.java:500-524`）。
- 真正被压平的是**同一条 assistant 消息内部的正文**：`finish()` 把整轮 accumulator 的 text 作为**一条** assistant 消息追加（`ResilientChatService.java:447-479`）。

**所以准确的说法是**：历史轮次的「工具与工具之间的顺序保留，工具与正文之间的**轮内**顺序丢失」。这与 AG-UI 官方承认的损失**完全同类**——业界对此的标准答案不是"放弃混排"，而是：
1. 历史回放沿用与实时**同一套分组规则**；
2. 把"轮内正文↔工具"退化为**消息级边界**（assistant(带 toolCalls) → tool → assistant(正文)），显式声明这条上限；
3. HITL 待决态靠"**有 call 无 result**"重建（+ 你们镜像里已存的 `pendingCall`）。

### 3.1 渲染模型：一轮 = 一条 timeline，不是两个数组

**实时轮（可精确重建，零协议改动）**
- 你们已有 `seq` + 服务端 `atMs`，且 `tool_* / confirm_* / frontend_tool_* / delta` 都在同一把 emitter 锁内出帧 → **帧序即真序**。前端把每轮折叠成一个 `parts[]`：
  - 收到 `delta` → 追加到"当前末尾 text part"；
  - 收到 `tool_start` / `confirm_request` / `frontend_tool_request` → **封口当前 text part**，压入对应 tool part，再开一个新的 text part（即使服务端把文本合成了一段，前端也能按 seq 在正确位置切开）；
  - `tool_result` / 决策帧 / `frontend_tool_result` → **就地更新那个 tool part 的状态**，不新建 part。
- 这条路径**不需要服务端发新帧类型**，是对现有 15/17 类帧的纯前端重解释。

**分组与折叠（三方一致的默认值）**
- 单位是**相邻同类块**，不是类型桶：连续 `reasoning*` + `tool_*` parts 合成一个"活动组"（assistant-ui `GroupedParts`、LibreChat activity groups、VS Code 连续工具折叠三方一致）。
- 组头：**进行中用动词短语**（"正在搜索…"/"Preparing/Calling"），**完成后用一行摘要**（VS Code 用 AI 生成标题、LibreChat 用生成摘要、ChatGPT 用 `reasoning_recap`）。短期可先用工具名+参数摘要，模型摘要作为后续增强。
- 默认态：**进行中展开，完成后折叠**；但**用户手动展开过的组不得被后续帧强制收起**（LibreChat 明确规则）。
- 硬规则：**正文永远在组外**（LibreChat：「closes the phase before that text so the user-facing result stays outside the collapsed summary」）。
- 单调用的组直接展示该调用细节，不套一层壳（LibreChat）。

**HITL：确认是 tool part 的一个子区域，不是第三种块**
- 现状 `pendingCall` 是**单槽位**，行业通行是**复数**（多路并行工具/多中断）。parts 化后天然支持：每个待决 tool part 独立 `requires-action`。
- 卡片只有一张、生命周期一条：`待决 → 已决` 是同一 part 的状态迁移；**`confirm_decision` / `frontend_tool_result` 不得再造第二张卡**（你们现在 `hasDecidedPendingResidue` + 双守卫就是在对抗这个问题，parts 模型能从结构上消灭它）。
- 默认展开条件 = `requires-action`；决策后收起为一行（记录态）；若做输入框上方的审批面板，轮内卡退化为记录（LibreChat）。
- 超时/取消：按你们已有语义落地即可（`expired` / `rejected` / `cancelled`），并保证**跨刷新保留**（LibreChat）；超时时**别假设卡会自己变灰**——用轮终态帧收敛（Claude 实现的教训）。

**历史轮（近似重建）**
- 用 `GET /api/ai/history/{sessionId}` 的有序消息**喂给同一个 timeline reducer**：`ASSISTANT(toolCalls)` → 在 parts 里放 text part + tool parts；`TOOL(toolResponses)` → 回填对应 tool part；末尾 `ASSISTANT(text)` → 正文 part。**渲染器与实时轮共用**，这是最小代价的一致化。
- 明确的已知上限（要在 UI/文档里承认）：同一条 assistant 消息内部的正文↔工具顺序不可还原 → 历史轮统一按"工具在前、正文在后"或"工具组置于本轮正文之上"。这与 AG-UI 的处理完全一致。
- 挂起态：**有 call 无 result → `requires-action`**（assistant-ui 的做法），叠加你们镜像里已有的 `pendingCall` 与 `expired` 降级。
- 不建议为历史轮做"逐 token 位置"的还原：LibreChat 也只持久化分组边界并在回放时 rebase。

### 3.2 消息模型（timeline / parts）最小改造面

**前端（改动最小、收益最大）**

1. `frontend/src/types/ai.ts` 的 `ChatMessage` 增一个有序字段，例如：
   `parts: Array<TextPart | ToolPart | ReasoningPart>`（`TextPart{kind:'text', segmentId, text, streaming}`；`ToolPart` 直接复用现有 `ToolRun` 形状 + `requires-action` 状态）。
2. **保留 `toolRuns` / `pendingCall` 作为派生投影**（`computed`），不改现有调用点与 `AiSessionMirror` 之外的地方 —— 这样"按类型分块"的旧组件可以先并存，逐步替换。
3. 折叠逻辑集中在一处（`parts → blocks` 的纯函数）：相邻同类合并、分组头、默认展开态。**实时与历史共用这一个函数**。
4. `AiSessionMirror`（`types/ai.ts:228-234`）改为一起带 `parts`，刷新后不重排。

**服务端（只在需要"每段正文位置精确"时才动）**

- 需要动的一处：`SseChatEmitter.textStart()` 的 `textSegmentOpen` CAS 目前**每消息只开一段**（`SseChatEmitter.java:515-531`）。若希望"工具调用之后模型又说话"能作为**独立 text part** 落在协议里，则改为**每段开一次**并带 `segmentId`（或 `messageId + segmentIndex`），在每次 `tool_*` 边界前 `textEnd` 一次。`message_start/message_end` 帧结构已支持（`kind` 字段），是**增量**改动。
- 不建议新增帧类型；现有 `seq` 是比 A2A「artifact id + part 序号」更强的结构，保留它。

### 3.3 需要拍板的三点（我的倾向）

1. **历史轮是否值得为"轮内精确交错"付存储代价？** 业界（AG-UI/assistant-ui/LibreChat）一致答案：不值得逐 token，但要保 parts/边界；我倾向**只保 parts（消息级），不保 delta** —— 实时轮精确，历史轮近似，且两者共用同一渲染器。
2. **`pendingCall` 单槽位是否扩为复数？** 行业惯例是复数（并行工具 + 多中断 + 全部覆盖式 resume）。若短期不扩，就让 parts 支持复数、`pendingCall` 仅作"当前焦点"投影，渲染以 parts 为准。
3. **折叠默认态**：进行中展开 / 完成后折叠；用户展开过的组永不被自动收起；正文永不进折叠组。这三条在 LibreChat / VS Code / assistant-ui 三处都能找到对应规则，建议直接照抄作为验收标准。

|---|---|---|
| **Element Plus `el-steps`/`el-step`** | ❌ 不内置 | 官方 API 只有 `active`、`process-status`、`finish-status`、`status` 等**展示型**属性，没有 `onChange`/`clickable`/`disabled`，也没有任何点击示例。点击跳转必须自己挂 `@click` 再自行更新 `active` |
| **Ant Design Steps** | ✅ 传 `onChange` 即变为可点击 | 官方 demo 的 `onChange` 是**无条件** `setCurrent(value)`，组件不限制"只能点已完成步骤"；每个 `StepItem` 有 `disabled`（"禁用点击"）。维护者明确表态：能否点击因业务而异，"应该由业务自行实现" |
| **MUI Stepper** | ✅ `StepButton` | `linear` 模式自动把未到达步骤设为 `disabled`；`non-linear` 不自动 disable，任意点进入，**完成与否由实现方判断**。官方硬性无障碍要求：可点击 `StepButton` 必须有 `aria-controls` 指向内容区 |
| **Material Design 原规范**（m1/m2） | 规范层定义 | 步骤类型：**editable**（会话内可回改）/ **non-editable**（不可回改，适用于"用户之后无法编辑"或"允许编辑会分散完成表单的注意力"）；stepper 类型：**linear**（必须按序完成才能前进）/ **non-linear**（任意点进入）。另有 optional step、error state、stepper feedback（仅当步骤间有长延迟时使用） |
| **Vuetify `v-stepper`** | ✅ | 默认 **non-editable steps**（强制线性）；`editable` = 任意时刻可选中并导航过去；`linear` = 始终按定义路径走；`non-linear` = 用户自选顺序；另有 error state |
| **PatternFly（企业级）** | ✅ 侧栏可点 | **Visited step**："In most cases, people can select this step to return to an earlier point in the flow"；**Disabled step**："Later steps are usually disabled so the flow stays sequential"；"People can jump to an **enabled** step by selecting it in the sidebar"；**"After submit, hide the steps sidebar. People can no longer edit earlier steps."** |
| **USWDS Step Indicator（政府规范）** | ❌ 明确反对 | "The step indicator is designed to complement standard back/next navigation in a linear sequence, **not to be navigation of its own**"、"Provide navigation separately"、不适用于非线性流程；pending 段落"should still maintain accessible contrast and **not appear disabled**"；用 `aria-current="true"` 标当前步 |

关键结论（三条，都很重要）：
1. **没有任何一个主流组件库把"只能跳到已完成步骤"写进组件契约**。MUI 的 linear 是唯一"组件级自动禁用"的例子，且它是靠 `activeStep` 推导 disable，而不是"校验通过才解锁"。【官方文档】
2. 点击权限是**业务规则**：Ant Design 明确把这件事推给业务（官方 issue #15482 维护者原话："不同的业务场景下，Step 能否点击/点击效果可能都不一样，所以应该由业务自行实现"）；MUI non-linear 文档也写"完成与否由你自己实现判断"。【官方发布说明/维护者表态】
3. PatternFly 给出了最贴近本场景的成熟模型：**可点击 ⟺ 已访问（visited）且未禁用；后续步骤默认 disabled；提交完成后整条步骤栏隐藏、不得再编辑**。USWDS 则代表另一极：步骤条根本不是导航。【官方文档】

## 二、线性 vs 非线性：业界共识

**共识 1：命名体系已经统一。** linear（未到达步骤禁用）/ non-linear（全部可进）/ editable vs non-editable（能否回改）三组正交维度，在 MUI、Vuetify、Material 原规范里语义一致。【官方文档】

**共识 2：默认应是"线性 + 已访问可回跳"。** PatternFly 的原则化表述最接近共识：前向步骤默认 disabled 以保持顺序，**已访问过的步骤可以点回去**；USWDS 则直接要求用 Back/Next 按钮承载导航、步骤条不承担导航。【官方文档】

**共识 3：前跳需要逐站校验解锁，回跳一般无条件允许。** MUI linear 是组件级的"未到达即禁用"，属于最严格的一档；PatternFly 的 progressive wizard 允许"回到前两步重选、后续步骤随之更新"。【官方文档】

**共识 4：回看/回改必须预填，且改完不必重走全程。** GOV.UK「Check answers」：“每个 section 旁给 Change 链接（含 visually hidden 文本说明改哪一段）”，“用户返回上一个答案时，**必须预填已填内容，页面要和上次看起来一致**”，改完点 Continue **直接回到 check answers**，不需要重走整个流程。Baymard 的收银台研究同向：“多步流程要允许用户直接从 review 页修改前面信息，而不是强迫他们往回走完整个流程”。【官方设计系统 + 商业研究机构】

**共识 5：只有"用户不能一次性完成 / 需要自选顺序"时才用非线性。** GOV.UK Task list 的使用门槛写得很硬：只在有研究证据表明用户"不能或不想一次完成"且"需要能自己选顺序"时使用；**"不要用于必须按特定顺序完成的长流程"**。【官方设计系统】

## 三、工作流/流水线产品的步骤查看范式

| 产品 | 运行中任务 | 已结束任务 | 点击节点后看到什么 | 变更动作 |
|---|---|---|---|---|
| **GitHub Actions** | 可以进入 run 页 → Jobs 或可视化图 → 点 job，展开 step 与日志；社区讨论确认"每个 step 的输出在该 step 结束时就出现，直接打开 job 视图能看到部分更新"（本质是准实时日志，不是 SSE 式进度条） | 同一套 UI；run 概览显示 conclusion（success/failure/**canceled**/neutral）；失败步骤**自动展开**；可选行号取 permalink；日志可搜索（只搜已展开的步骤）、可下载 archive | **只读日志视图** | 重跑 workflow / 重跑失败 job（在 run 页操作） |

| **Argo Workflows** | 打开 workflow → 点节点 → 右侧 node details 面板；第三方文档："Selecting a step in the sidebar loads its logs"；3.6 起"能看到 pod 的 live logs" | 同面板，可看归档（archived）workflow 的节点信息 | **只读详情面板**（日志、输入输出、节点元信息；3.6 起 URL 变成可点链接） | 对单个 node 的 retry（3.6 起可在 UI 做，"即使 workflow 已经成功"）；历史上诉求"从失败节点重试而不是从头重跑"，早期只能 CLI（`argo retry --node-field-selector`） |

**归纳出的公共范式（跨 5 个产品一致）：**
1. **节点点击 = 查看，不是编辑。** 运行中给实时/准实时日志，已结束给归档日志，形态都是只读详情面板。
2. **所有变更动作（重跑/重试/取消/标记）是详情面板里受状态约束的显式按钮**，不存在"点节点即改状态"。
3. **失败节点默认被定位/自动展开**（GitHub 自动展开失败步骤、Blue Ocean 自动切到失败步骤日志）。
4. **失败后回看历史完全自由且只读**，重跑走"新一次执行（try / new run）"而不是就地改写历史——Airflow 的 try_number 历史、Argo 的单节点 retry、GitHub 的 re-run 都是这个模型。
5. 运行中 vs 已结束的差异体现在**可用动作集合**（cancel vs retry），而不是"节点能不能点"。

## 四、「只读查看模式」的交互范式

**业界更偏"快照/汇总面板"，而不是"整页 disabled 表单"。** 证据：
- GOV.UK Check answers：编辑态与查看态**分离**——查看态是一个 summary 列表（纯文本答案），每个 section 右侧挂 Change 链接进入编辑态。返回编辑态时数据预填、布局与上次一致。【官方】
- PatternFly：提交后**隐藏步骤栏、不允许再编辑早期步骤**；结果耗时长就用 progress 屏；"wizard 启动后台任务时，提供一个 monitor progress 链接或 Close 按钮"。对后台作业场景这句话几乎是为本场景写的。【官方】
- GitHub/Argo/Airflow/Blue Ocean 的已结束详情全部是"只读面板 + 日志 + 产物下载 + 重跑动作"。【官方文档】

**如果非要复用表单布局，控件选型的硬事实：**
- `disabled` 的控件**不可聚焦、不参与约束校验、不会被提交**——键盘与读屏用户在 Tab 序列里根本到不了它，也就无法读到/复制它的值。【官方：MDN】
- `readonly` 的控件**仍可聚焦、可选中复制、会随表单提交**，只是不可编辑；ARIA 层面 `aria-readonly`（不可编辑但仍可操作）与 `aria-disabled`（不可操作）语义不同。【官方/规范】
- 结论：**"展示历史值"应当用 readonly 语义或纯展示文本，不要用 disabled**；只有"该控件此刻确实不可用"时才用 disabled。【推断，但由 MDN 语义直接推出】
- 对比度：WCAG 1.4.3 明确豁免"属于 inactive（disabled）用户界面组件"的文字，因此 disabled 灰字（Ant Design `colorTextDisabled: rgba(0,0,0,0.25)`、Material inactive steps `38% black`，实际约 1.9–2.9:1）**在 WCAG 上合法但可读性很差**；业界的常见误用是把这个豁免套到"仍有信息价值的内容"上（此时既不合规也不好读）。【规范 + 第三方解读】
- 视觉上"不可点"也必须真的不可点，反之亦然：GOV.UK 的 "Cannot start yet" 是**灰字 + 整行不加链接**并明说"状态整行链接"是有意设计；其研究还指出用户会误把状态标签当按钮点，所以状态被重新设计得"不那么像按钮"。USWDS 则要求 pending 段落"保持可访问对比、**不能看起来像 disabled**"。【官方设计系统】

## 五、失败/取消状态的步骤条呈现

**组件库层面：** MUI 有独立 error step；Vuetify 有 error state（含 alternative label + error）；Ant Design 的 `status` 可取 `error`，且**状态可以在单个 Step 上覆盖由 `current` 推导出的状态** —— 也就是说"失败的是第 2 步、当前停在第 4 步"这种精确表达是组件原生支持的。Ant Design 的 `colorError = #ff4d4f` / `colorErrorBg` 是语义 token。【官方文档】

**产品层面的通行做法：**
- 失败步骤**默认被定位/自动展开**：GitHub Actions "Any failed steps are automatically expanded"；Blue Ocean "If a particular step during the run fails, this tab automatically defaults to showing the console log from the failed step"。
- 失败后**回看历史完全自由且只读**：Airflow 的 Task Instance History（每个 try 的日志）；GitHub 的 partial re-run 会保留前次 attempt 的日志 archive。
- 重试是**显式动作**，不是"点节点即重试"：GitLab 在 pipeline graph 上 retry failed jobs；Argo 3.6 起在 UI 里对单个 node retry；Airflow 点失败任务后点 Clear（并需选择作用范围）。
- 红色**只用于错误**：GOV.UK 明确"Do not use the red background colour for any status text except errors"，并要求能从源头即时纠错时就用 error summary + inline error 而非"存着一个错误状态"。【官方】

## 六、对本场景的设计启示

前提重述：3~4 步的导入/导出向导，步骤内含作业执行（SSE 进度、校验问题表、文件结果）；任务生命周期 = 进行中（ACTIVE / FAILED 均未终态）与已结束（COMPLETED / CANCELLED）。

### A. 进行中任务（ACTIVE，含作业在跑）
- **节点可点性（建议）**：当前步骤高亮但**点击无动作**；**已完成步骤可点 → 只读查看**；未到达步骤不可点且必须"看起来就不可点"。这正是 PatternFly 的 visited + enabled 模型【官方文档推荐】，也是 AntD/Vuetify/MUI 里最严格档与最宽松档之间的主流折中。不要采用 MUI 的完全 non-linear（任意跳）作为默认，除非有研究证据表明用户需要自选顺序（GOV.UK 的使用门槛）。
- **点击语义必须单一**：工作流产品全部是"点节点 = 查看"。若又想"点已完成步骤 = 跳回去改参数"，会出现节点语义二义（查看 vs 编辑）。建议：**节点点击一律 = 查看（抽屉/侧栏只读面板，SSE 进度实时流入）**，跳转/编辑走页脚动作按钮或面板内的显式"修改该步骤"按钮。这是从 GitHub/Argo/Airflow/BlueOcean 的一致范式推断出的取舍【推断】。
- **编辑正在进行中的步骤参数是危险动作**：平台必须先回答"该步骤的作业能否安全取消/重跑"。若不能，应该提供"取消本次作业"而不是"直接改参数后重建"。Ant Design 维护者与 MUI non-linear 都明确这类规则属于业务，组件不会兜底【官方表态】。
- **前跳 gating**：只允许跳到"已完成且校验通过"的步骤；失败步骤与当前步骤之间不允许跳过。回跳无限制。
- **SSE 与步骤条的衔接**：把 SSE 进度放在**步骤内的进度条**，而不是用步骤条本身当进度指示器（步骤条表达的是流程阶段，MUI 原规范里"stepper feedback"也只在步骤间有长延迟时才用）【官方文档 + 推断】。

### B. 已结束任务（COMPLETED / CANCELLED）
- **全部节点可点，但一律只读查看** —— 直接对标 PatternFly "After submit, hide the steps sidebar. People can no longer edit earlier steps."【官方文档推荐】，以及 GitHub/Argo/Airflow 的归档页范式。
- **只读呈现方式优先级（我的建议排序）**：
  1. **只读快照面板/汇总页**（结构化字段 + 校验问题表 + 文件结果列表 + 下载），对照组 GOV.UK Check answers 与各大工作流产品的详情面板【官方范式】；
  2. 若产品要求复用表单布局：字段用 **readonly 语义 + 视觉弱化但保持对比度**（可聚焦、可复制、读屏可读）；
  3. **不要整页 disabled**：Tab 序列会变空、读屏取不到值、灰字对比度低（虽然 WCAG 1.4.3 豁免）【规范推导】。
- **CANCELLED 的特殊处理**：必须区分"未执行/已跳过/已取消"，并展示取消人、取消时间、取消原因；状态文案用中性色，**不要用红色**（GOV.UK：红色只用于错误）。
- **"想改历史任务"的出口**：业界普遍做法是**复制为新任务/新 run**（Argo 的 resubmit、Airflow 的 trigger、GitHub 的 re-run），而不是就地编辑已完成记录。这样同时满足审计与一致性【官方产品范式 + 推断】。在导出场景下这通常正是用户真正想要的（用同一份配置再跑一次）。

### C. 失败任务（FAILED，未终态）
- **呈现**：失败步骤红色 + 明确文本"失败"（不能只靠颜色）；用 AntD `StepItem.status="error"` 这类**单步状态覆盖**能力精确表达"停在第 4 步、但第 2 步失败"【官方文档】。
- **默认视图**：进入任务详情时自动定位/展开失败步骤，把校验问题表作为该步骤详情内容（对标 GitHub 自动展开失败步骤、Blue Ocean 自动切失败日志）。
- **导航规则**：失败步骤及其之前的**所有步骤都可自由点开回看**（只读）；失败步骤之后的步骤保持不可点，并给出原因文案（"依赖前序步骤完成"），形态参考 GOV.UK "Cannot start yet"：灰字、整行不加链接、明确说明【官方】。
- **动作**：重试 / 继续 / 取消 作为失败节点详情里的显式按钮，且不同生命周期状态暴露不同动作集（对标 GitLab：运行中=cancel、失败=retry）【官方产品范式】。

### D. 可访问性注意点（跨三态）
1. **语义**：步骤条用有序列表，当前步加 `aria-current="true"`（USWDS 官方做法）；每个步骤的完成/失败/进行中状态用 **visually hidden 文本**说明，不能只靠颜色（USWDS 要求）。【官方】
2. **可点击节点必须是真按钮/链接**（可 Tab、可 Enter/Space），不要在 `div` 上挂 click；可点击节点若驱动内容区切换，需 `aria-controls` 指向内容区（MUI 官方硬性要求）。【官方】
3. **不可点击节点不要"可聚焦但点了没反应"**：要么用带 `aria-disabled` 的、在 Tab 顺序里合理降级处理的元素，要么纯文本呈现 + 相邻说明文案（GOV.UK 的"整行不加链接"就是这个思路）。【官方】
4. **只读态用 `readonly`/纯文本，不用 `disabled`**：disabled 不可聚焦、不参与校验、不随表单提交，键盘/读屏用户拿不到值（MDN 原文）。WCAG 1.4.3 对 disabled 文字的对比度豁免**不适用于仍有信息价值的内容**。【规范】
5. **禁用原因要可达**：`disabled` 元素本身不可聚焦，tooltip 若挂在 disabled 元素上键盘用户拿不到 —— 把原因放在外层可聚焦容器或紧邻文本/`aria-describedby` 上。【推断，依据 MDN 的 disabled 语义】
6. **避免"看起来可点但不可点"和"不可点却像按钮"**：USWDS 反向要求 pending 段落"不能看起来像 disabled"，GOV.UK 的研究发现用户会误把状态标签当按钮。开关状态与视觉必须一一对应。【官方设计系统研究】
