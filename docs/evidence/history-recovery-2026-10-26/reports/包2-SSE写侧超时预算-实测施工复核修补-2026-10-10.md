## 1. 结论一：写侧**没有按帧/按业务配置的预算**，只有一条由连接配置派生的 120s 兜底写超时（字节码 + 实测双向坐实）

> **2026-10-10 复核后更正（本节早期版本的机制判读被反证，结论方向不变）**：本节原文断言
> "`NioEndpoint` 从不 `setWriteTimeout` ⇒ 缺省 `-1` ⇒ 落 `writeLock.wait()` **无参**分支 =
> 无限期阻塞"。复核用**钉住的构件**（`target/config-mgr.jar` 里的
> `tomcat-embed-core-10.1.54.jar`）逐条反证：
> `NioEndpoint#setSocketOptions` **依次**调 `getConnectionTimeout() → setReadTimeout(long)` 与
> `getConnectionTimeout() → setWriteTimeout(long)`（字节码偏移 151/160）⇒ **NioEndpoint 确实设置写超时**；
> `SocketWrapperBase#setWriteTimeout(t) = t > 0 ? t : -1`，故本配置下 `writeTimeout = 120000`，
> **不是 -1**；`NioSocketWrapper#doWrite` 里 `writeLock.wait(J)`（带参）**与** `writeLock.wait()`
> （无参）**两个分支都存在**，无参分支仅在写超时 ≤ 0 时可达。
> jstack **无法区分** `wait()` 与 `wait(long)`，"无参分支"这一判定只能来自源码断言，而该断言为假。
> **更正后的口径**：写侧**没有按帧/按业务配置的预算**，但有 Tomcat 的**写超时兜底 = `connection-timeout`
> （本配置 120s）**，超时以 `SocketTimeoutException` 抛出（正是实测 ≈116s 释放的机制）；
> 上界"≈120s 且随配置漂移"的**量级结论因此更硬**——它字面上就等于连接的写超时。

- **源码（更正后）**：`SocketWrapperBase#doWrite` 的阻塞分支取 `getWriteTimeout()`，该字段由
  `NioEndpoint#setSocketOptions` 设为 `getConnectionTimeout()`；`NioSocketWrapper#doWrite` 的超时分支
  抛 `SocketTimeoutException`。全 jar 扫描 `setWriteTimeout` 引用类只有
  `NioEndpoint` / `Nio2Endpoint` / `SocketWrapperBase`（无任何协议类把它重置为 -1），且没有任何
  按帧的写预算 —— 即**能拦住一帧的只有这条 120s 的宽兜底**。

## 3. 结论三：阻塞**不自愈**（≥150s 观测窗）

`step0b`（驱动侧零超时，避免"驱动自己断开"污染结论）在 t=0 采到阻塞后持续观测：

**读法与修正**：

1. **没有"按帧"的释放机制**：100s 内两个请求持续停在内核写与监视器上，`SseEmitter(0L)` 的
   `AsyncContext#setTimeout(0)` 在 Tomcat 里被 `AbstractProcessor#timeoutAsync` 判为"无超时"
   （`if (asyncTimeout > 0)`），**不存在**按帧的自愈；连接层面的释放只有上面 §1 更正后的那条
   **120s 写超时**（`SocketTimeoutException`）；
2. **交付前必须修正审计的一处措辞**：审计 B-02/B1 写"可被挂住数小时""无上界"。实测表现为
   **~116–120s 后由连接器的写超时中止**（两次实验分别 116.8s/116.3s 与 ~115.7s，且吻合
   `server.tomcat.connection-timeout: 120000` —— 同一处 `setSocketOptions` 里的
   `setWriteTimeout(connectionTimeout)`，2026-10-10 复核按字节码更正）
   ——即本配置下 **上界 ≈ 120s**，不是小时级。**但它仍是有界内的完全阻塞**：
   120s 里该任务的 publish 全排队、调用线程 + 事务 + DB 连接全占住，且该上界**随配置漂移**
   （`connection-timeout` 调大即变长；换连接器/换实现是否仍有这条兜底无法保证）。
   故本包的修法不是"消除一个不存在的无限"，而是**把释放手段从"依赖容器/配置的兜底"换成
   写侧自己的 15s 预算**（并把 120s → 15s 的收紧一并落实），把"锁内写"改成"锁内只快照"。
3. 阻塞结束的原因是**连接器的写超时到点**（[8] 两次请求都在 ≈116s 以 500 收场）或**慢客户端断开**
   （[9] 2.5ms/200）；两次阻塞请求最终以 **500** 收场（阻塞写抛出的异常穿出 `publish` → 事务回滚 →
   全局异常处理器）——即"客户端侧的一次慢读"会变成"服务端一次 5xx + 一次事务回滚"。

## 4. 对 AI 通道（`SseChatEmitter`）的对应推断与证据边界

- `drain` 的 `sub.emitter.send(payload)`（`SseChatEmitter.java:838` 区）与任务通道是**同一条
  Spring/Tomcat 写出栈**，故写侧同样只有那条 **120s 容器写超时兜底**（源码同一处，无需重复实测）。
- 差别在**后果**：AI 通道的写出跑在**进程级共享有界投递池**（`app.ai.sse.delivery-pool-size=8`）上，
  所以慢连接占的不是"一把锁"而是"池工作线程"——**M ≥ 池容量（8）** 时同轮乃至全进程停投
  （T3-5 压测已给出该矩阵的实测结论，本次不重复压测）。
- AI 请求的两个 emitter 由 `AiController` 用 `budgetMillis()`（= `app.ai.resilience.total-budget`，
  300s）构造，即**已有一条整条流的生命周期超时**；它与本包新增的"单帧写预算"是两层不同语义，
  详见施工报告 §设计选型。注意 300s **晚于** 120s，故卡住的写一般先由写超时收场，生命周期超时
  只兜"流寿命"这一维。

- 缺陷**坐实**（写侧只有 120s 容器兜底写超时、没有按帧预算 + 持锁阻塞 + 120s 内不自愈），

## 2. 设计选型论证

### 2.1 为什么不能拿 `SseEmitter` 自带 timeout 当"写超时"（选型 A vs B）

| | `SseEmitter(timeout)`（自带） | 自定义写预算（本次采用） |
| --- | --- | --- |
| 语义 | **整条响应**的一次性 deadline（交给容器 `AsyncContext#setTimeout`）| **单帧写出**的时长上限 |
| 对"一帧卡住" | 无效：它按流寿命计时，不按帧计时 | 直接命中：单帧超预算即摘除 |
| 对"健康长流" | 会整条掐断（越短越频繁重连） | 无影响（健康帧毫秒级完成） |
| `0L` 的语义 | **无 async 超时**（Tomcat `AbstractProcessor#timeoutAsync`：`if (asyncTimeout > 0)`，0 不触发）—— 实测两次实验均在 0L 下无按帧释放 | —— |

即：两者不是替代关系而是**两层**。本次保留 emitter 生命周期超时承担"整条流寿命 + 卡死写的最终释放"，另建单帧预算。AI 通道的 emitter 本来就被 `AiController` 用 `budgetMillis()`（= `app.ai.resilience.total-budget`，300s）构造，本包不改其值。

### 2.2 为什么自己实现"看门狗"必须**换线程**（而不是 `complete()` 或中断）

三条实测/源码事实决定了唯一可行解：

1. `ResponseBodyEmitter#send` 与 `#complete` **同为 `synchronized`**（Spring 6.2 `ResponseBodyEmitter.java:186/248`；`SseEmitter#send(SseEventBuilder)` 另有一把 `ReentrantLock`，同样包住 `super.send`）⇒ 写卡住时**监视器被占**，任何别的线程 `complete()` 只会一起挂住 —— 这本身也是修复前的一条隐藏阻塞（出帧线程会在 `evict → complete()` 上挂住）；
2. **线程中断对 socket 写无效**：`NioEndpoint#doWrite` 捕获 `InterruptedException` 后 `// Continue` 继续等；
3. `SseEmitter.send` 无写超时（§1）。

⇒ 唯一出路是**把阻塞的写出搬到别处，让调用线程只等一段预算**。故 `SseWriteBudget` 的做法：`submit(send)` 到**弹性写出池**（`sse-write-*`，core=0 + `SynchronousQueue`，60s 回收），调用线程 `Future.get(budget)`。
反对的备选：把 T3-1 的投递池换成弹性池 —— 改动面大（一票既有测试锚定"投递池工作线程内写出"的语义），且仍不能把"卡住的写"从**调用线程**（任务通道的作业线程/HTTP 线程）上摘下来。

**配套机制（写在飞期间的收尾交接）**：既然写在飞时不能就地 `complete()`，`completeOne` 增加交接逻辑 —— `Subscription#writeInFlight` 为真时置 `completePending` 并返回，由写出线程在 `send` 返回/抛出后（监视器已释放）补做收尾；两侧都走到时由既有的 `completed` CAS 去重。这同时修掉了修复前"溢出摘除时出帧线程挂在 emitter 监视器上"的隐藏阻塞（单测 `overflowEvictionDuringAnInFlightWriteDoesNotBlockTheCallingThread` 锚定，修复前必红）。

### 2.3 超时的失败帧处置：**断开让前端重连**（不是丢弃+继续投）

- **丢弃不可取**：`delta` 帧按 T3-2 **不入归档**，静默丢一帧正文是"重挂也补不回来"的永久缺失；而断连有现成通道 —— AI 通道 `frontend/src/api/sse.ts` 的 onerror/onclose → 带 `lastSeq` 重挂（ADR-5，`replayAndAttach` 差量补发，seq 无洞）；任务通道 `openTaskEvents` 用 `EventSource`（断线按 retry 自动重连）+ `utils/job-watch.ts` 固定间隔快照轮询兜底。
- **与既有语义同口径**：S2-1 已确立"溢出摘除 = 主动断连，不静默丢帧"，本包沿用同一出口（摘表 + 清队列 + 计数 + WARN），并把写超时作为**第五个**摘除触发（溢出 / 写出失败 / 池拒绝 / 生命周回调 / 写超时）。
- **不在调用线程 complete**：见 §2.2；emitter 收尾交给"卡住的那次写返回时"的写出线程（AI 通道）；任务通道则移出推送表后由自身生命周期（客户端断开 / 5m 容器超时 → `onError/onTimeout` → 幂等 `remove`）收尾。

## 8. 遗留风险与【待裁决】

1. **[已知残留] 卡死的那一次写仍占 1 个弹性写出池线程**（每条订阅者至多 1 个，drain 独占保证），释放依赖客户端断开或 emitter 生命周期超时（AI 300s / 任务 5m）。相对修复前"无限 + 占共享池"已降为"有界 + 不占共享池且不影响他人"，但**不是零成本**。
2. **[待裁决] 调用线程的事务/DB 连接仍在预算期内未提交**（任务通道 `publish` 在 `@Transactional` 内被调用）。本包只把窗口从 ~120s 收到 15s；彻底解耦需按审计建议③把推送挪到"事务提交后 + 异步派发 + 有界队列 + 饱和丢进度帧"。是否要做（涉及 `JobService#cancel` 的取消通路语义）请裁决。

### 2-3 三处并发热点的对抗走读（重点）

**(a) `SseChatEmitter#completeOne` 写在飞交接 —— 无丢唤醒、无重复 complete**

两侧字段：`AtomicBoolean writeInFlight`（写侧 `set(false)`）与 `volatile boolean completePending`（收尾侧置真）。写侧程序序 = `W1: writeInFlight=false` → `R2: read completePending`；收尾侧 = `R1: read writeInFlight(true)` → `W2: completePending=true` → `R3: read writeInFlight`。
“置位→复查”是标准 Dekker 形态：若 `R3` 仍读到 `true`，说明 `W1` 在同步序上晚于 `R3`，而 `W2` 程序序早于 `R3` ⇒ `W2` 早于 `W1` ⇒ `R2`（晚于 `W1`）必见 `true` ⇒ 不可能出现"写侧漏看 pending 且收尾侧不补做"。反之 `R3` 读到 `false` 则收尾侧自己 `set false` 并就地 complete。两侧都走到时由既有 `completed` CAS 去重 ⇒ **既无丢唤醒也无二次 complete** ✅
写出返回后再 complete 的时机安全性：`SseEmitter.send(SseEventBuilder)` 在 `super.send` 外持 `writeLock`（javap 实证，见 §4-①），而 `send` 返回时该锁已释放 ⇒ 由写出线程补做 complete 不会自锁 ✅
`completeOne` 的调用点（`drain` finally / `evict` / `evictOnWriteTimeout` / `completeWhenDrained`）都在 `writeInFlight` 为真时让路；且 `writeFrame` 仅被 `drain` 调用（单订阅者 `draining` CAS 独占）⇒ **写在飞期间不存在第二个 drain** ✅
`evictOnWriteTimeout` 只做计数/日志/`closeSubscription`（摘表+清队列+计数归零），**不碰 emitter** ⇒ 不会挂在写线程持有的锁上 ✅

- 快照在 `synchronized(list)` 内 `new ArrayList<>(list)`，此后所有网络写在锁外 ⇒ 单条慢连接不再让同任务其它 publish 排队（`aStuckEmitterDoesNotBlockOtherPublishesForTheSameTask` 锚定，红轮实测 5.005s 挂住 ⇒ 判据为真）✅

## 2. 修 2：S3-② INTERRUPTED 静默丢帧收口

**实读 `evictOnWriteTimeout` 后的选型**：该路径 = `closeSubscription`（摘表 + 清队列 + 计数归零 +
复位标志）+ `EVICTED_TOTAL`/WARN + `completeOne`（写在飞则**交接**给写出线程），即"摘除 = 主动断连、
不碰 emitter 监视器"。既有通用出口 `evict(sub, reason)` 与之同形并多一个 `evicted` CAS 去重 ——
这正是复核 §4-② 建议的写法，且**回灌队列方案被否**：队列里的帧在中断标志已复位前重新投递会在
`future.get` 上立即再次 `InterruptedException` 自旋（且 `LinkedBlockingQueue` 只能回尾、破坏 FIFO），
故"摘除让前端 reattach 对账"是本包唯一自洽出口。

```java
// SseChatEmitter#writeFrame（改前 default 分支 → 改后显式 INTERRUPTED 分支）
- default -> {
-     log.debug("SSE 写出被中断 runId={}（帧留在队列，由补投接续）", this.runId);
-     return false;
- }
+ case INTERRUPTED -> {
+     evict(sub, "写出被中断（调用线程中断）");
+     yield false;
+ }
```

- 顺带把 `switch` **语句**改为 `switch` **表达式**（`return switch (result.outcome()) { … }`）：
  编译时发现 javac 对"枚举全常量覆盖的 switch **语句**"不视为 definite-return（`缺少返回语句`），
  改用仓库既有写法（`TaskSseService#sendFrame` 就是 `return switch`）后四路显式且无 `default`，
  新增 `Outcome` 常量会**编译期报错**而非静默落入某分支。
- **中断语义保持**：`SseWriteBudget#write` 仍在 `catch (InterruptedException)` 里
  `Thread.currentThread().interrupt()`；本分支不碰中断位，只改变"帧的处置"。
- 单测：`SseChatEmitterWriteBudgetTest#interruptedWriteEvictsTheSubscriberInsteadOfSilentlyDroppingTheFrame`
  （投递走本用例线程 `Runnable::run` 以便辅助线程精确打断 `future.get`；写预算 30s ⇒ 提前返回只可能
  来自中断）。断言：中断位已复位（`Thread.interrupted()` 为真且清除）、订阅表归零（摘除而非静默丢帧）、
  写仍在飞 ⇒ 不在调用线程 `complete`、`release()` 后由写出线程补做收尾。

## 3. 修 3：S4-⑨ emitterTimeout 守卫

`config/AppProperties.java` 新增（**沿用仓内既有配置校验风格**）：

```java
@PostConstruct
void verifyTaskSseEmitterTimeout() {
    Duration emitterTimeout = this.task.getSse().getEmitterTimeout();
    if (emitterTimeout == null || emitterTimeout.isZero() || emitterTimeout.isNegative()) {
        throw new IllegalStateException("app.task.sse.emitter-timeout 必须 > 0（当前 = " + emitterTimeout + "）…");
    }
}
```

- **为什么是 `@PostConstruct` 而不是 `@Min`/`@Positive` 注解**：仓内**有**校验先例且风格明确 ——
  `AiProperties#verifyBoundedElasticCapacityBudget`（`@PostConstruct`，委托 `AiPoolCapacityBudget`）
  + 其锚定测试 `AiPropertiesT35DefaultsTest` 用**最小 Spring 上下文实测"绑定值落进 bean"**。
  本项沿用同一风格（同样在 `@PostConstruct` 读**绑定后**的值；`ConfigurationPropertiesBindingPostProcessor`
  在 `@PostConstruct` 之前完成绑定）。另：`jakarta` 标准约束（`@Min`/`@Positive`）**不支持 `java.time.Duration`**
  （Hibernate Validator 无对应 validator，只有其专有的 `@DurationMin`），故未走注解路线。
- **fail-fast 而非只告警**：与容量联动校验（后果 = 性能降级，故只 WARN）不同，`emitter-timeout=0`
  直接废掉"每条流有终期"这一前提，故 `IllegalStateException` 让启动失败。
- 单测：`SseWriteBudgetTest#zeroTaskEmitterTimeoutFailsStartupWhileTheDefaultPasses`
  —— 先证缺省 5m 照常起（守卫不过严），再把绑定值改为 `0s`（`MapPropertySource` 覆盖 +
  `@EnableConfigurationProperties(AppProperties.class)` 最小上下文）断言 `refresh` 失败且**根因**是本守卫。
  另：全量测试中的 `@SpringBootTest` 上下文（如 `TaskCenterQueryTest`）正常启动，反证守卫不误伤现网配置。

真实 emitter 的首帧写**不落 socket**。因此红队 S3-2 描述的"客户端连上即死 ⇒ 首帧 HEARTBEAT 超时/失败
不摘除"在**当前代码路径上不可达**，且"滞留推送表最长达 5m"的量化后果亦随之不可达。本修单收口的是
**口径缺口**：契约声明"false ⇒ 摘除"而唯一调用方丢弃结论（写出真失败/超时、或该 emitter 已被并发收尾时，
现在按契约摘除），并消除未来首帧一旦落 socket 写就失效的隐患。**未按红队原话夸大后果**。
