## 二、五大攻击面

### A1. 即发即回真实性 —— 攻不破，主张成立

**攻击过程**：逐行核对执行器与下载链的每一跳，寻找「ack 之前藏 await」「ack 之后同步 click」「悬浮 promise」「卸载后回调触雷」四种破法。

**证据（均【实测】实读）**：

- 执行器 `ExportWizardView.vue:1113-1134`：`:1114` 仅 `await preflightDownload(call.args)`；`:1119-1130` 从读 `busy`/`requestedInFlight` 到 `startDownloadInBackground(defCode)` 到 `:1131` `return` ack 全程**无 await**（同步原子段）。
- `startDownloadInBackground`（:778-794）：`:779-780` 同步登记（set + `downloading`），`:781` 发起 `startDownload(code)` 后**不 await**。
- `startDownload`（:728-732）：第一个挂起点在 `await buildXlsx(code)`；`buildXlsx`（:706-716）同步前缀只读 `exportResults`/`gridRefs`，随后必经 `await grid.toXlsxBlob()`（:710）或 `await tasksApi.downloadFile(...)`（:715）——**至少一个异步跳**。
- `downloadBlob`（`excel.ts:839-848`）：同步 void，`link.click()` 在 `:845`，只有 `buildXlsx` 的 await 落地后才可能执行。
- 回灌侧 `stores/ai.ts:1490-1499`：`runFrontendTool` 等 `executeFrontendTool` 返回后才发回灌 POST。

**ack 是否真的先于 `link.click()`**：【推断-强】执行器 `return`（ack 文本构造完成）发生在调用 `startDownloadInBackground` 的同一同步 tick；而 `link.click()` 需等 `buildXlsx` 的 await 解析（至少一个微任务 + 一次 grid 导出或 HTTP 往返），任何交错下都晚于 ack 构造。且即便构造出病态交错（click 先于 POST 发出），ack 文案「已发起下载」仍为真——发起动作在 `:781` 已同步发生。**结论：不可攻破。**

**preflight 里有没有藏着网络级 await**：有，且是设计内的。`ensureTaskBoundForTool`（:917-954）在跨任务时走 `tasksApi.getTask`（:939）+ `applyTaskBinding`（:949 → `loadTask` → `getFiles` :364，可能还连带 `ensureGridLoaded` 的又一次 `downloadFile` :677）；同任务在途绑定时 `await pending.promise`（:923）。结果存在性检查 `:1001` 是**纯本地状态**（`exportResults.value.some`），不打后端。→ 「前置体检毫秒级」这个口径（任务卡背景语）在跨任务场景**不成立**，可达数秒甚至逼近 60s 执行器预算；但 `frontend-tools.ts:340-343` 的注释已如实登记「串行 HTTP 可以很长」，且预算计时器保证回灌不迟到（见观察项-5）。

**unhandledrejection**：后台链 `:781-793` 为 `startDownload().then().catch().finally()`——`buildXlsx` 内部同步 throw、`downloadBlob` throw（如 `createObjectURL` 失败）都会变成 async 函数的 rejection，被 `:785` 的 `.catch` 兜住；`.finally` 回调只做 `Set.delete` 与条件置 null，不抛。`goStep(2)`（:463-474）void 出发的 `persistStepData`/`syncStepToBackend`/`refreshResults` 三者内部全部自带 try-catch（:524-528、:490-494、:378-381/:683-688），不会产生未处理拒绝。【实测+推断】唯一理论残留：`.finally` 回调或 `ElMessage` 自身抛异常会让链条末端 promise 悬浮拒绝——两者无已知抛出路径，不计发现。

**卸载清理**：`onBeforeUnmount`（:1143-1151）注销执行器与 5 个 handler。在途 promise 的回调只触碰组件级 ref（`downloading`）、`Set`（`inFlightDownloads`）与全局 `ElMessage`——三者卸载后均安全（ref 是普通对象、ElMessage 全局单例），**不会炸**。【推断】卸载→重挂后新实例的 `Set` 为空，存在同码二次发起窗口（见观察项-3）。

### A2. 防重复（在途集合增删时机）—— 同实例内攻不破，跨任务有一个真实缺口

**攻击过程**：构造用户侧/AI 侧/重复投递三方并发时序，检查 check→add 原子性、finally 覆盖面、双轨状态不一致。

**同实例原子性（攻不破）**：
- `downloadOne`（:745-750）：`has` 检查 → `add` → `downloading=code` 全同步，无事件循环让出窗口；
- 执行器（:1119-1130）：`busy`/`requestedInFlight` 读取 → 分支 → `startDownloadInBackground`（内含 `add`）→ return，同样全同步；
- JS 单线程 + 每段无 await ⇒ 两次并发投递的后续段必然串行，第二次必然看到第一次的 `add` → 走分支②「本次未重复发起」。【推断-强】
- 异常路径：`downloadOne` 的 `finally`（:759-764）与 `startDownloadInBackground` 的 `.finally`（:788-793）无条件 `delete`，覆盖所有 rejection；`downloading` 复位带 `=== code` 守卫，不会误清他人。✅
- `busy===defCode` 而 Set 空的状态（分支②误选的入口）：分析所有交错（单发、双发覆写、打包与单发交叠、早退分支）均不可达——每次 `add` 都在同 tick 配对 `downloading=code`，每次删除都同 tick 条件复位。【推断】

**攻破的缺口（跨任务）**：`resetTaskScopedState`（:396-405）清空 `exportResults`/`checkedDefs`/`loadedGrids`，但**不清 `inFlightDownloads` 也不复位 `downloading`**。跨任务改绑（`applyTaskBinding` :441-459）后，旧任务在途的同码条目仍留在集合里 → 见发现清单 MINOR-1。

**双轨并行与哨兵值**：
- `downloading` 单值（:208）可被后发起的下载覆写（如用户在打包下载进行中又点了单文件下载，:801→:750），单文件先结束时 `downloading` 被置 null 而 zip 仍在构建 → 执行器分支③的前置（`busy !== null`）被绕过、走分支①并发起下载——**串行化意图被绕过但无谎言**（新下载确实发起了，ack 为真）。见观察项-1。
- 哨兵值 `'checked'`/`'all'`（:801/:828）与普通 defCode 碰撞的后果见观察项-2。

### A3. ack 文案三分支口径 —— 文案本身合规，选择条件在跨任务场景失真

**攻击过程**：逐字比对三分支措辞与注释纪律（:1108-1112），找成功/失败暗示、措辞串用、前置失败误当 ack。

**分支①（:1131-1133）**【实测】：「已发起下载：…（内容为在线编辑后的当前表格）。下载由浏览器执行——若弹出保存位置选择框或提示被拦截，请让用户在浏览器侧放行并确认；文件落盘以浏览器下载目录为准。本次调用到此结束，无需重试。」——只陈述「已发起」+ 浏览器侧不确定性 + 无需重试，**无「已下载完成/已成功」暗示**。措辞与 `startDownload` 实际行为一致（`buildXlsx` 优先取 grid 当前内容 :709-710）。

**分支②（:1122-1124）**：「页面上已有一次下载在进行中（…），本次未重复发起。…无需重试。」——同实例内为真；**跨任务改绑后为假**（在途的是旧任务的同码文件，本次请求的目标文件从未发起，却被告知「无需重试」）——同 A2 缺口，见 MINOR-1。

**分支③（:1127-1128）**：「本次未发起 X 的下载（页面正有 … 在进行中），可稍后重试本项。」——`busy !== null` 时选用；经所有交错分析，`downloading` 非空时确有下载指示在途（无持久性脏非空态）。多码并发时括号里的 `downloadingLabel(busy)` 只命名最新一个在途项（如 set={X,Y} 时标 Y），属措辞精度问题非谎言。

**前置校验失败会不会被误当 ack 成功**：不会。【实测】`preflightDownload` 失败经执行器 `throw`（:1115-1117）→ `runRegisteredTool` 的 catch（`frontend-tools.ts:842-847`）→ `ok:false, availability:'degraded'`，文案为「…执行失败：<原因>。请提示用户手动重试。」；`stores/ai.ts:1504` 据此落卡片 `status: 'failed'`。前置失败文本（:994/:999/:1004）自身均含「未下载/未触发下载」的确定性陈述，与成功 ack 不可混淆。

**分支②选择条件**：`requestedInFlight || busy === defCode`（:1121）。`busy ?? defCode`（:1123）的兜底分支（set 有码而 busy 为 null）经分析不可达，`downloadingLabel` 不会错标。

### A4. 文案回归锁有效性 —— 有效（含实证），负向断言有缺口

**攻击过程**：真跑测试、做两个变异体、审断言与实现的同源性。

**实测**：
1. 原版测试 3/3 通过（JUnit Platform 直跑，含 2s/3s/1s 真等待，走生产路径 `AiProperties.getHitl().setTimeout` → `awaitFrontendResult` → 生产等待循环 → `expire`，非伪造路径）；
2. **变异体①**（把 `ConfirmGate.java:311` 的 `timeoutSeconds` 硬编码为 `120`，编译于仓库外、置于 classpath 优先位）：两个参数化用例**当场失败**，报错正是 `[文案秒数必须等于注入的 app.ai.hitl.timeout（硬编码常量过不了两个用例）] expected: 2 / expected: 3` —— **「文案硬编码 120 而配置注入 2」防得住**；
3. **变异体②**（在 `:310` 确认门文案**末尾追加**「本次调用结局未知（不表示未发生）。」）：**3/3 全绿，漏网** —— 确认门分支只有正向 contains 断言（Test:118-120），没有 `doesNotContain("结局未知")` 类负向断言。

**同源性审查**：断言中的关键短语（「结局未知」「不表示未发生」「未获得数据」「回传执行结果」）必然与实现共用字面——这是回归锁的本性，不构成缺陷；关键防同源设计（正则 `SECONDS_IN_TEXT` Test:70 从**产出文本**读回秒数再与注入值比对，不拼串）已被变异体①实证有效。若实现改掉「未在 N 秒内收到前端回执」句式，`secondsInText` 的前置断言（Test:146-149）会让测试**响亮地失败**而非静默通过。✅

**确认门分支锁够不够**：整句替换式破坏（删掉「系统已自动取消该操作（工具未执行）」）会被 contains 断言抓住【推断，断言结构决定】；**追加式污染抓不住**【实测】。对称缺口：前端分支（Test:98-104）锁了不含「未获得数据」「回传执行结果」，但**未锁不含「工具未执行」**——若有人给前端超时文案追加「（工具未执行）」，与「不表示未发生」直接矛盾，测试不设防【推断】。见 MINOR-2。

**{2,3} 注入 vs 生产默认 120s**：文案生成全程配置驱动（`await`(:190) → `confirmTimeoutSeconds()` → `expire(timeoutSeconds)` :297-311），注入值与默认值走**同一条代码路径**，文本层面无 120 专属分支——**无覆盖盲区**。默认值 `120` 本身（`AiProperties.java:127`）是配置缺省而非文案逻辑，不属本锁职责。

### A5. workspace.ts 的 AbortController 60s（R-11 链路）—— 实现与注释相符，不产生批 A 同类「假失败」

**攻击过程**：核对锚点行号、验证「未写入任何文件」断言的真实性、审 abort 归因竞态、核对常量同值注释。

**锚点核对（全部【实测】吻合）**：`DOWNLOAD_FETCH_TIMEOUT_MS=60_000`（:327）、`case 'download'`（:434）、`AbortController`（:437）、`setTimeout abort`（:438）、`fetch+signal`（:440）、abort 归因（:446-450）、`clearTimeout` finally（:451-453）。

**60s 超时是否造成批 A 同类「假失败」**：**不会**。批 A 消灭的假失败形态是「文件已落盘、回执却说未获得数据」；本分支 abort 发生时 `saveBlob`（`http.ts:145-154`，仅在 `await response.blob()` 完整返回后同步执行）**尚未被调用**，fetch 已被真正中止——「下载失败：60 秒内未取回文件（已中止本次请求），**未写入任何文件**」(:448) 是**真失败 + 真陈述**。它确实会把「慢但会成功」的下载变成失败（可用性代价），但口径诚实、有界，且与 axios 全局 60s（所有其他拉字节请求同等待遇）一致——属设计取舍而非谎言。`saveBlob` 的 `link.click()` 同步即返回（不待保存框），成功分支「已触发下载」同样为真。【实测+推断】

**abort 归因竞态**：真实网络错误若恰在 ~60s 边界先于 abort 生效，`controller.signal.aborted`(:447) 为 true 时会被归因为超时文案、真实错误原因被吞——结局等价（fail、无文件），仅归因文本略失真，窗口毫秒级。反向（abort 已发、fetch 先 reject 非 Abort 错误）同路径。非 abort 错误 `throw error`(:450) → `runUiEvent` 外层 catch（:479-481）→ `fail('ui_event 处理失败：…')`，如实。**可接受**。

**常量注释声称与 `api/http.ts` 的 60000 同值**：【实测】`http.ts:85` `timeout: 60000`，**属实**；「两者都是拉字节类请求、延迟分布同类」的论证充分（axios 60s 覆盖头+体，fetch signal 同覆盖，量级一致）。

**遗留交互（本批新增面）**：`ui_event download` 经路由 3 进入时还套着执行器预算（`deriveFrontendToolBudgetMs(120)=60s`，`frontend-tools.ts:234-247`）——两个 60s 计时器同值竞速，预算先到则走 `timeoutOutcome` 的下载类文案「文件也许已经下载到浏览器的下载目录」（:417-419），而此刻 fetch 可能已被 abort、**并无文件**——该句在此形态下高估。此为既有文案族（本批前 fetch 无限挂起时同样存在此高估），本批的 abort 反而**收窄**了该窗口。见观察项-4。

## 三、发现清单

### MINOR-1 · 跨任务改绑不清在途集合，分支②「无需重试」失真 + 同码异任务误拦截

- **主锚**：`ExportWizardView.vue:396-405`（`resetTaskScopedState` 清 4 项状态但不清 `inFlightDownloads`/`downloading`）；受害面 `:745-747`（用户侧误拦）、`:1121-1124`（AI 侧分支②谎言）。
- **复现路径**【推断，由实读代码逐步推演】：① 任务 #1 在途下载 defCode=X（`startDownloadInBackground`，set={X}）；② AI 调 `download_export_file(X, taskId=#2)`，preflight 的 `ensureTaskBoundForTool`（:997→:949）触发 `applyTaskBinding(#2)` → `resetTaskScopedState` 清空页面态但 set 残留 X；③ 执行器读 `requestedInFlight=true` → 分支②回灌「已有一次下载在进行中（X 的下载），本次未重复发起…**无需重试**」——而在途的是**任务 #1** 的 X 文件；任务 #2 的 X 从未发起，模型被明确告知不要重试，用户最终拿到的是旧任务的同码文件（issue #2「张冠李戴」同族）。用户侧 `downloadOne(X)` 同窗口会被 `:745` 误拦为「已在进行中」。
- **评级理由**：触发窗口窄（在途下载通常秒级 + 需跨任务 + 需同码，而同码跨任务正是本代码库实证过的场景——issue #2 的 CURRENCY 例），且自愈（在途下载结束后可重试）；但它直接击穿批 A 主张的「在途防重复」在跨任务维度的正确性，且错误方向是**让模型放弃补发**。
- **处置建议**：`resetTaskScopedState` 一并清 `inFlightDownloads` 与 `downloading`（在途 promise 的 finally 守卫 `downloading.value === code` 已能容忍中途复位），或在分支②文案里去掉跨任务场景下的「无需重试」。

### MINOR-2 · 回归锁负向断言缺口：追加式措辞污染不设防

- **主锚**：`ConfirmGateFrontendTimeoutTextTest.java:118-120`（确认门仅正向 contains）、`:98-104`（前端分支未锁「工具未执行」不得出现）；被锁对象 `ConfirmGate.java:310-311`。
- **复现路径**：【实测】变异体②在 `:310` 确认门文案**末尾追加**「本次调用结局未知（不表示未发生）。」→ 测试 3/3 全绿。同理【推断】给 `:311` 前端文案追加「（工具未执行）」也不会被抓（无 `doesNotContain("工具未执行")`）。
- **评级理由**：整句替换式破坏已被正向断言锁死（含「系统已自动取消该操作（工具未执行）」整串），缺口仅在「保留旧句+追加矛盾措辞」的污染形态——危害是两个分支的语义界碑可被慢慢磨糊，与该测试「防措辞互相串用」的立意直接相关。
- **处置建议**：确认门分支补 `doesNotContain("结局未知")`；前端分支补 `doesNotContain("工具未执行")`。

### 观察项（不构成对本批主张的否定，建议登记）

1. **`downloading` 双轨覆写绕过分支③串行化**：用户在打包下载（`downloadChecked` :801 置 'checked'）进行中再点单文件下载（`downloadOne` :750 覆写），单文件先结束把 `downloading` 置 null 而 zip 仍在构建 → 此刻 AI 调用走分支①并发起并发下载。无谎言（ack 为真），仅绕过「页面有下载时不并发」的设计意图。主锚 :750/:761-763/:801。建议登记（与 MINOR-1 同根：双轨状态无单一事实源）。
2. **哨兵值碰撞**：defCode 字面量为 `'checked'` 或 `'all'` 时（配置定义编码是用户数据，无格式禁令），`busy === defCode`（:1121）会把「打包下载在途」误判为「该配置在途」走分支②。后果轻（打包通常恰好包含该配置的文件），但 `downloadingLabel` 会把它标成「勾选项打包下载」。主锚 :968-977/:1121。
3. **卸载重挂同码双发窗口**：`inFlightDownloads` 是组件实例级（:226），卸载→重挂后新实例集合为空，旧实例在途下载仍在 → 同码可再发起（两次保存框）。窗口=在途下载时长。主锚 :226/:1143-1151。
4. **ui_event download 路由的双 60s 竞速**：执行器预算 60s（`frontend-tools.ts:191`）与本批新增 fetch 60s（`workspace.ts:327`）同值竞速，预算先到时下载类超时文案「文件也许已经下载到浏览器的下载目录」（`frontend-tools.ts:418`）在 fetch 已 abort 的形态下高估（无文件）。属既有文案族，本批收窄而非扩大了该窗口。主锚 `frontend-tools.ts:416-419`、`workspace.ts:438`。
5. **「前置体检毫秒级」口径不实 + `exportResults` 本地缓存可能陈旧**：跨任务绑定的 preflight 含串行 HTTP（`ExportWizardView.vue:939/:949→:364`），可达数秒；同任务无 taskId 时不刷新文件列表（:920-935 早退），`exportResults` 陈旧时 `:1001` 会给出「任务 #N 里没有 X 的导出结果文件（该任务现有导出结果：（无））」这种**断言服务端事实实为本地缓存**的假阴性（与 open 执行器 :1079 同族的既有面，非本批引入）。文案含补救指引、失败方向安全（不触发下载），故仅登记。
6. **正面确认**（列举攻过且未破的面，留痕）：ack 先于 `link.click()`（A1）；同实例同码并发无双发窗口（A2）；三分支文案无成功/失败暗示、前置失败必落卡片 failed（A3）；回归锁真跑通过 + 硬编码 120 被抓（A4）；「未写入任何文件」为真陈述、常量同值注释属实（A5）；`submitFrontendResult` 对已决条目 DUPLICATE 幂等丢弃（`ConfirmGate.java:459-461`）支撑「不新增二次回灌通道」主张；`docs/requirements.md` 注记与实现一致（「只覆盖到已发起」的覆盖口径诚实）；`frontend-tools.ts`/`AiTools.java` 改动确为纯注释（diff 逐 hunk 核对）。

## 四、总结论

**带条件 PASS。**
