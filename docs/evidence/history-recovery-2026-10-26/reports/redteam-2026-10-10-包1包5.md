## 2. 关键判断点裁决（J1–J7）

### J1 语义回归：Promise.race 超时后迟到 settle —— 裁决：机制正确，有一处防御性结构缺口（降 S3）

**unhandledRejection 推演（本体逐路径验证）**：`runWithBudget` 的 race 输入是 `task.then(...)` 的派生 promise P1 与 `expired`。Promise.race 对两个输入都注册了 handler，因此：

- 超时赢之后 task 迟到 resolve：`task.then` 的 onFulfilled 执行、P1 settled、race 已定忽略——无泄漏、无拒绝；
- 超时赢之后 task reject：P1 的 rejection handler 已由 race 注册——**零 unhandledRejection**，成立；
- task 先 reject（race 未定）：`executeFrontendTool` reject → `runFrontendTool` 的 `await` 抛出 → 调用点 `ai.ts:1298` 的 `void this.runFrontendTool(...)` **无 catch** → unhandledRejection + 回灌不发 + toolRun 卡永停 pending + `suspended` 卡 true（1289 置 true 后只有 frontend_tool_result 帧能复位，回灌不发则帧不来）——**issue#6 同型病灶在"throw 而非 hang"形态下的复现**。
  静态核查该 reject 面是否可达：路由 1 `runRegisteredTool` try 包 executor；路由 3 `runUiEventAction` try 包 `dispatchUiEvent`，而 `dispatchUiEvent` 内 `runUiEvent` 的 try-catch 覆盖整个 switch（workspace.ts:449）、`emitWorkspaceEvent` 逐订阅者 try-catch（workspace.ts:330-338）、`workspace.touch` 为纯 store 写无抛面；路由 4 `runPageHandler` try 包 handler。**当前无可达 reject 路径**，"dispatchFrontendTool 按契约不 reject"的注释论断成立——但它是约定不是类型保证，`void` 调用点无兜底是结构缺口（见 S3-1）。

**用户可见矛盾（迟到成功）**：下载超时回灌"结局未知"后，`downloadOne` 的 `finally` 复位 `downloading`、`ElMessage.success` 弹出"已下载 xx"——用户先见超时卡、后见成功 toast。文案已预告"可能仍在后台继续"，属"迟到但有据"，不构成谎报（S4-1）。toolRun 卡 `status:'failed'` 与文本"结局未知"的状态语义不一致见 S3-3。

### J2 看门狗正确性 —— 裁决：不变量成立

- **快速失败→重连→再武装交错**：`connectTimer` 唯一赋值点在 `startConnect#508`，函数首句 `clearConnect()`，唯一调用点 `open#555` 紧随 `new EventSource` 同一同步回合——无双武装路径。清除点全覆盖：`settle:470`、`startIdle:484`（onopen/任一帧到达即让位，含"帧先于 onopen"的防御）、`scheduleReconnect:529`（退避期双清，消除 HEAD 版"旧 idleTimer 误杀新连接"既有缺陷）、`startConnect:507` 自清。`onerror` 全部出口返回时 connectTimer 必为 null；abort 与超时同帧竞争两个方向均由 `settled` 早退/已清闭合。
- **后台节流**：Chrome 后台 timer throttling（intensive throttling 对隐藏页面 1min 粒度）使各计时器**晚触发**——方向安全（晚结算不误杀活连接；EventSource 网络在后台不受节流，活连接的 onopen/帧会照常让位看门狗）。代价是后台 tab 下 48s 收口可能拉长到数分钟、90s 预算可能推迟到 120s 之后（见 S4-2）。
- **不误杀活连接**：`startIdle` 在 onopen 与每帧都执行（`onmessage` 首句），连接只要出数据看门狗就持续让位；心跳帧也在其列。
- M3 识别的极端异常序列（onReconnect 回调抛错、`new EventSource` 构造抛错 → reattach Promise 永不 settle / 首次构造抛错时违反"只 resolve 不 reject"注释）为**既有结构缺陷**，触发条件现实不可达（3 处 onReconnect 实现只写 notice；SSE_PATHS 生成固定合法 URL），归入 S3-2，不构成本次返工事由。

- 攻击场景：执行器恰在预算边缘 settle（或主线程阻塞后补触发）→ 90s 时回灌 POST 发出 → 网络拥塞/代理排队使 POST 耗时 31~60s → 到达时刻 121~150s > 服务端 120s 挂起上限 → 后端已判前端超时、回灌 409 拒收 → 模型与用户拿到"本次调用未获得数据"空结局——issue#6 的原始症状在极端网络下重现。
- 证据链：余量的数学保证要求 `budget ≤ serverTimeout − axiosTimeout`（120−60=60s）；现值 90s 只在 POST <30s 时成立。施工注释把"实测正常 <1s（POST 3.1ms）"外推成"慢网络也不至于迟到"，未覆盖 POST 自身上限。`elapsedMs` 与"已等待 N 秒"文案如实，属"迟到但不丢"口径的延伸，但注释以"保证"自居与事实不符。
- 缓办依据：触发需 POST 耗时 >30s 的极端网络（实测 3.1ms），且失败模式是幂等 409+notice 而非数据损坏。修复方向二选一：预算上界改取 `min(serverTimeoutMs − HEADROOM, serverTimeoutMs − 60000)`（120 场景即 60s），或注释如实改写为"POST 耗时 <30s 时保证不迟到；超过则迟到但不丢"并登记为已知窗口。

## 3. 修 2（S2-2）预算公式严格化

**落点**：`frontend/src/utils/frontend-tools.ts`

- 新折算式（唯一事实源）：
  ```ts
  const serverBudgetMs = typeof timeoutSeconds === 'number' && Number.isFinite(timeoutSeconds) && timeoutSeconds > 0
    ? timeoutSeconds * 1000
    : null
  if (serverBudgetMs === null || !Number.isFinite(serverBudgetMs)) {
    return FRONTEND_TOOL_TIMEOUT_BUDGET_MS
  }
  const usableMs = serverBudgetMs - FRONTEND_TOOL_RESULT_HEADROOM_MS
  const clampedMs = Math.max(MIN_FRONTEND_TOOL_TIMEOUT_BUDGET_MS, usableMs)
  return Math.min(clampedMs, serverBudgetMs)
  ```
  即 `budget = min(max(serverTimeoutMs − 60000, 5000), serverTimeoutMs)`。
- 常量：`FRONTEND_TOOL_TIMEOUT_BUDGET_MS = 60_000`（语义改为"帧未带合法 `timeoutSeconds` 时的**回落值**"，不再是折算的上界钳制 —— 因此 >120s 的上限随服务端平移：150s→90s、300s→240s）；`FRONTEND_TOOL_RESULT_HEADROOM_MS = 60_000`（语义改为"回灌 POST 的最坏耗时 = `api/http.ts:85` 的 axios 单请求上限"，单一事实源）。
- 注释：删掉"为什么是 90s / 30s 是慢网络也不至于迟到的保守余量"旧论证，改为如实数学口径（`预算 + 60000 ≤ 服务端上限`，对 `服务端上限 ≥ 65s` 全域成立）；病态区（≤65s）如实写成"保证必然失效、退化为到点即回灌 + 不倒挂"，保留原"宁可无余量也不倒挂"的取舍精神；并登记 S4-2 迟到源。
- **新增防线（必要，防修 2 引入新缺陷）**：`timeoutSeconds` 有限但 ×1000 溢出为 `Infinity` 的畸形输入（如 `1e307`）在新公式下会产出 `budget = Infinity`，而 `setTimeout(Infinity)` 被引擎钳到 ~1ms ⇒ **瞬间判超时（假超时）**。旧公式因有 `min(90_000, …)` 常量钳制而侥幸安全；故把"乘积非有限"并入非法判据，回落默认值 60s（红队 J4 的"1e307 → 90_000 ✅"在新公式下等价为"→ 60_000 ✅"）。

## 1. 修：`setTimeout` delay 上限（前后对照）

**修复前**（`normalizeBudgetMs`，第 249-254 行原样）：

**修复后**（新块在第 249-294 行，常量在 `frontend/src/utils/frontend-tools.ts:278`）：

```ts
/**
 * 计时器 delay 的可表示上限（毫秒）= `2^31 − 1` ≈ 24.86 天。
 * …（MDN "Maximum delay value" 出处 + Node 注 + 本机实测 + 可达路径 +
 *    "计时器是唯一超时判定源 ⇒ 收口后的值就是有效预算" + 病态配置"可接受退化"登记）
 */
const TIMER_MAX_DELAY_MS = 2_147_483_647

/** 预算归一：非法值一律回落默认值，并把上界收口到 {@link TIMER_MAX_DELAY_MS}。 */
function normalizeBudgetMs(value?: number): number {
  const requestedMs = typeof value === 'number' && Number.isFinite(value) && value > 0
    ? value
    : FRONTEND_TOOL_TIMEOUT_BUDGET_MS
  return Math.min(requestedMs, TIMER_MAX_DELAY_MS)
}
```

另在 `runWithBudget` 文档追加一段 "**计时器 delay 的上界**"（`frontend/src/utils/frontend-tools.ts:344-347`）并在 `setTimeout` 调用处留 2 行注释（`:356-357`），使读者在计时器现场就能看到约束来源。

**口径选择（如实说明为什么不"只钳计时器、不动预算"）**：`runWithBudget` 的 race 只有"执行器 settle"与"计时器到点"两支 ⇒ 计时器是**唯一**超时判定源，故钳制后**有效预算即 `2^31 − 1`**。因此把收口放在预算归一这一处（而非只钳 delay 实参），使 **计时器 delay 与超时文案里的"执行器预算"同源** —— 否则病态区会出现"已等待 2147484 秒 < 执行器预算 10000000 秒却判超时"的自相矛盾。收口只此一处（v4 有"钳制只此一处"断言，防日后双份钳制各自漂移）。

**可达性推演（不是凭空的畸形输入）**：预算随服务端上限平移（`deriveFrontendToolBudgetMs`，已不再被 60s 常量封顶），上限来自 `app.ai.hitl.timeout`（`Duration`），帧里的 `timeoutSeconds` 是 int（`ConfirmGate.java:169` `(int) Math.max(1, timeout.toSeconds())`）⇒ `timeoutSeconds = 3_000_000`（≈34.7 天）时预算 = `2_999_940_000` ms，**越界**。属病态配置（后端默认 120s，与该值差 5 个数量级），注释按"该场景超时判定实际退化为本次会话内不超时，由服务端上限判定兜底，属**可接受退化**"如实登记。
