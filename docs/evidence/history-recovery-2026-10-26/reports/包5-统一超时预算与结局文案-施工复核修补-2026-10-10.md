## 3. 超时预算设计

### 3.1 取值：默认 90s，且由服务端上限折算

```
FRONTEND_TOOL_TIMEOUT_BUDGET_MS   = 90_000   // 默认预算（= 120s − 30s 余量）
FRONTEND_TOOL_RESULT_HEADROOM_MS  = 30_000   // 回灌 + 后端受理判定的余量
MIN_FRONTEND_TOOL_TIMEOUT_BUDGET_MS = 5_000  // 折算下限
deriveFrontendToolBudgetMs(timeoutSeconds)   // clamp(服务端上限 − 30s, [5s, 90s])；缺省 90s
```

**为什么 90s（而不是别的值）**：
- **上界**：必须 **< 120s**。120s 是后端挂起等待上限（`app.ai.hitl.timeout`，确认门与前端工具共用），超时后后端直接以"前端超时、工具未执行"回填；前端预算若 ≥120s 就完全没有意义。90s 留 **30s 余量**给"超时结局 → 回灌 POST → 后端受理与判定"。实测该链路正常耗时合计 < 1s（页面侧 `anchor.click → POST` 3.1ms、后端受理回帧 25ms），30s 是"慢网络也不至于迟到"的保守值。
- **下界**：不能太小。预算不得把"慢但会成功"的执行掐掉 —— 实测最慢的一次**成功**回灌发生在 **30.6s**（issue#6 run3：宿主浏览器把下载链路拖住 30.1s 后才解析），90s 覆盖该类慢成功，同时把 issue 那两轮（120s 才收口）提前到 90s。
- **与服务端同源**：`frontend_tool_request` 帧恒带 `timeoutSeconds`（`:197` required），调用方用它折算 —— 后端改 `app.ai.hitl.timeout` 时前端预算自动跟随，且**不超过**服务端上限。折算表【实测，脚本 ⑤】：`120→90s`、`150→90s`、`60→30s`、`40→10s`、`10→5s`（下限）、`0/null/NaN→90s`。
  **归零勘误（两包复核 S2-1，已修）**：施工时点的这句原文写的是"恒**小于**服务端上限（无倒挂）"，但当时的折算只夹 `[5s, 90s]`：上限 ≤5s 时 5s 下限会**反超**上限（`timeoutSeconds=3` → 5000ms > 3000ms）。已由后续合并修补加上第二道"服务端上限"钳制（`min(折算结果, timeoutSeconds×1000)`，两者冲突时上限优先）改为如实口径 —— 非病态区（>5s）仍恒**小于**上限，病态区（≤5s）等于上限、无回灌余量。详见 `pkg5-reports/修补报告.md`。

### 3.2 机制

`executeFrontendTool(call)` → `Promise.race([dispatch(call), 预算计时器])`：
- 派发先给出结局 → **原样返回**（成功/失败/降级/不可用语义一律不变，未触碰任何工具原有成功路径）；
- 计时器先到 → `timeoutOutcome(...)` 产出 `{ ok: false, availability: 'degraded', result: <结局驱动文案> }`；
- `finally` 里 `clearTimeout`，胜者确定后不留悬挂计时器【实测，脚本 ⑥：预算 5s 的快结局不把进程挂住】。

**"回灌 POST 一定发出"如何成立**【实测，脚本 ②③⑦】：回灌是 `runFrontendTool` 里 `await executeFrontendTool(...)` 之后的一步，预算保证这个 await **最多等预算那么久**（异步挂起类），因此 POST 在预算时刻发出；超时分支**只依赖计时器**，不依赖执行器 settle/reject —— 这正好处理 `downloadOne` 吞异常（§4）。脚本 ③ 还验证了"慢成功（3× 预算后落地）不产生第二次回灌、不产生未处理拒绝"。

**范围刻意限定**：预算只包统一派发层，`generative_form` 不经此路径（帧 handler 特判 `openGenerativeForm`，等的是用户填写，自带帧时限），因此不存在"用户还在填表，前端预算先把工具判超时"的风险。

### 3.3 边界（代码注释与实证一致）

同步阻塞主线程的执行器（issue#6 的候选机制）下，宏任务计时器无法在阻塞期间触发。阻塞结束后的两条分支已在 node 侧逐条实证（§6.3 ⑧a/⑧b）：
- **⑧a**：执行器随即给出结局 → 微任务先于"已过期的宏任务" → 按**真实结局**回灌（慢成功仍报成功，刻意不谎报超时）；若阻塞在 120s 内结束，该回灌仍赶得及被后端受理；
- **⑧b**：仍未给出结局 → 过期计时器**立刻补触发** → 回灌超时结局（不丢结局、不悬挂）；此时文案里的"等待 N 秒"如实显示实际等待（> 预算），也是"主线程被长时间阻塞"的可观测信号。

## 4. `downloadOne` 吞异常的现状如何处理

现状【实测，代码锚点】：`ExportWizardView#downloadOne`（`:689-704`）把自身异常吃进 `ElMessage.error` 后 **void 返回、不 rethrow** ⇒ 注册的执行器（`:951-969`）**从不 reject**，于是当 `buildXlsx` 抛错/下载被浏览器拦截时，回灌给模型的仍是"已触发下载…"（**谎报成功**，即前序分析报告的 P1）。

本包的处理方式（与已裁决拒绝的 `void downloadOne().catch()` 落点完全无关）：
1. **超时分支不依赖执行器的 reject**：`runWithBudget` 的结论只由计时器给出；`timeoutOutcome` 不读异常、不读 settle 状态。故"执行器吞异常"对本预算没有影响 —— 这也是必须用计时器而非 `catch` 的原因，已写进 `runWithBudget` 与 `timeoutOutcome` 的注释。
2. **不把"下载失败却报成功"混进超时文案**：超时文案只声明"没拿到回执/结局未知"，不宣称下载失败；反之，"执行器在下载失败时回灌成功"（P1）**不在本预算职责内，本包未改**，作为【待裁决】项登记（§8），避免与"已裁决拒绝的 fire-and-forget"落点混为一谈。
3. **不改动 download 执行器本身**：`:967` 的 `await downloadOne(defCode)` 与 `downloadOne` 的实现均未触碰（脚本反向断言已锁定）。
