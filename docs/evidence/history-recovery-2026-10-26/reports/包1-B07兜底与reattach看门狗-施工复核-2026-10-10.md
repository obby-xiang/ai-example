## 1. 缺陷一：B-07（`SpreadGrid.vue`）

### 1.1 永不 settle 路径枚举【实测：读码 + 编译产物实跑】

**HEAD 的全部 settle 点（重读 `git show HEAD:frontend/src/components/SpreadGrid.vue`）**

| # | 位置（HEAD 行号） | 语义 |
|---|---|---|
| S1 | `SpreadGrid.vue:118` `readyResolve?.()`（`onMounted` 成功路径，且紧跟 `readyResolve = null`） | **唯一** settle 点（resolve） |
| — | 全仓 `grep readyPromise` 仅 2 处命中（`:87` 定义、`:203` `await`） | 无 reject 保存点、无超时 |

**消费点（await 点）**

- `SpreadGrid.vue:203` `loadFromJson` 内 `await readyPromise`（唯一的 await 点，`loadFromXlsx` 经它间接等待）。

**条件枚举：四类组合中只有一类会 settle**

| 组合 | 触发条件（实况可达性） | HEAD 行为 |
|---|---|---|
| ① 成功 | `loadSpreadCore()` 兑现 + `host.value` 非空 | settle（唯一绿路径） |
| ② `loadSpreadCore()` 拒绝 | 4.7MB `spreadjs` chunk 404 / CSP 拦截 / 离线 / 部署漏包（`utils/spreadjs.ts:45-66`）；`spreadCorePromise` 置 null 只影响**后续**调用，不打断在途 await | `catch`（`:132-135`）只置 `engineState='failed'`，**不 resolve、不 reject** ⇒ 永久悬挂；UI 显示"表格引擎加载失败"，工具链侧永久等待（**审计 B-07 ①**） |
| ③ 早退 | `onMounted` 的 `if (!host.value) return`（`:94-96`） | **不 resolve、不 reject**，`engineState` 停在 `'loading'`（UI 恒显示"表格引擎加载中…"，即审计所说"UI 在说谎"）（**审计 B-07 ②**） |
| ④ 引擎永不 settle | 动态 `import()`（chunk 请求）与 CSS `import`（Vite 注入 `<link>`）**都没有原生超时**：TCP 建了但资源响应挂起/被中间层黑洞时，既不 resolve 也不 reject | 连 `catch` 都进不去 ⇒ 永久悬挂（**本包新坐实的第三条路径**，审计未单列；也是 §1.2 看门狗要兜的那条） |

**关于审计触发条件②的实读纠正**：审计写"el-tabs 懒渲染场景下宿主尺寸为 0/未挂载"。实读 `SpreadGrid.vue:1-15` 与 Vue 3 模板 ref 语义：`host` 是**元素 ref**，组件已挂载时它必然非 null（尺寸 0 不会置 null）；懒渲染的场景是**组件整体未挂载**（此时 `onMounted` 根本不跑）。故 `!host.value` 的真实触发条件只有一种：**`await loadSpreadCore()` 期间组件被卸载**（`onBeforeUnmount` 后 Vue 把元素 ref 置 null）——正是排期表 `M2-排期计划.md:154`（RR1）描述的三重组合场景。§1.2 的兜底按此收敛，并在该分支补 `engineState='failed'` + 可读文案。

### 1.2 修复设计（`SpreadGrid.vue`）

新增一个"结算门闩"与一个看门狗，**四条路径全部经同一出口**：

| 兜底点 | 位置（工作树行号） | 说明 |
|---|---|---|
| `settleReady()` | `:104-112` | 清看门狗 + `readyResolve?.()` + 置 null；**成功（`:167`）/ 卸载（`:192`）** 走它 |
| `failReady(msg)` | `:121-125` | 置 `engineState='failed'` + `engineError=msg` + `settleReady()`；**早退（`:143`）、`catch`（`:182`）、卸载中未就绪（`:190`）** 走它 |
| `READY_TIMEOUT_MS = 60_000` 看门狗 | `:99` 常量、`:132-135` 与 promise 同点武装 | 覆盖组合④（以及任何未预见的"永不 settle"） |
| `waitForReady()` | `:261-266` | `await readyPromise` 后按**活体状态**（`workbook.value`/`spreadNs`）判定，未就绪则抛 `engineError` 原文或 `'表格引擎尚未就绪'`；`loadFromJson:270` 改用它 |

**为什么选 resolve 兜底而不是 reject（口径论证）**

1. **调用方对结果的用法**：两个消费点的形状完全一致 —— `ExportWizardView.vue:641-660#ensureGridLoaded` 与 `ImportWizardView.vue:553-581#loadEditors` 都是 `try { await grid.loadFromXlsx/loadFromJson(...) } catch (error) { ElMessage.error(error.message) }`，**没有任何一处依赖 promise 的 rejection 语义**，二者只依赖"最终抛出可读 Error"。故 settle 用 resolve 还是 reject 对调用方等价。
2. **与既有裁决口径一致**：排期表 `M2-排期计划.md:154`（RR1 去向）已定口径 —— "**早退分支补 `readyResolve?.()`**，让 `loadFromJson` 走既有「表格引擎尚未就绪」throw 后被 `ensureGridLoaded` 吞掉，链正常 settle"。本包采用同一机制（唤醒 + 由消费点抛错），只是把抛出的文本从固定文案升级为**引擎错误原文**（`engineError.value || '表格引擎尚未就绪'`），使回灌/提示具备可行动信息。
3. **避免新的未捕获异常面**：`readyPromise` 在 setup 点创建、可能**无人 await**（如用户直接关掉页签、`loadData` 路径）。若在 `catch`/早退里 reject，则这条无人消费的 rejected promise 会产生 `unhandledrejection`（浏览器控制台红字，且测试/监控会当异常上报）；resolve + 按需抛错没有这个副作用。
4. **可重试性**：`readyPromise` 只承担"等待结束"的**唤醒**语义，就绪与否按调用时实况判定 ⇒ 失败唤醒后若引擎后来补上（`utils/spreadjs.ts:59-63` 失败不缓存、可重试），后续 `loadFromJson` 仍能走通；若用一次性 reject，晚到的成功就永久不可用了。

**超时取值论证（60_000ms，对齐既有常量）**

- 该等待的实质是"同一条网络栈拉一个 ~4.7MB 的 `spreadjs` chunk（`vite.config.ts` 懒加载口径）+ 模块求值"，与一次 REST 请求同族，故取 `api/http.ts:85` 的 **axios 单请求上限 60s 同值**（既有常量，不新造数字）。
- 60s **明显小于**后端 `ConfirmGate` 的挂起超时 120s（审计 §5 口径：唯一时间边界），确保"前端先失败、先出可读错误"，不再退化成 issue#6 的"沉默 120s 才由后端收尾"。
- 该值同时是"误判活连接"的假阳性上界：正常的 chunk 拉取（含冷启动/TLS/代理首包）远在 60s 内完成。

**注释同步**：文件头新增"就绪等待契约（B-07）"一条（`:33-34`）；常量、`settleReady`、`failReady`、`waitForReady`、`onBeforeUnmount` 各处的行为变化点均带原因注释。

## 2. 缺陷二：R-03 / 前端篇 B-03（`sse.ts#reattach`）

### 2.1 永不复位路径枚举【实测：读码 + 打包真实模块实跑】

**HEAD 的 settle 出口清单（全在 `reattach` 的 Promise 执行体内，唯一出口是 `settle()`）**

| 调用点（HEAD 行号） | 触发条件 |
|---|---|
| `:438-440 onAbort` | 外部 `signal` abort（用户点停止） |
| `:444-452 startIdle` 的定时回调 | 帧间静默超过 `idleTimeoutMs`（90s） |
| `:459-465 scheduleReconnect` 的 aborted / 次数耗尽分支 | 重连退避中取消，或 `attempts >= maxReconnects` |
| `:493-495 source.onmessage` 收到终帧 | 正常收尾 |
| `:497-509 source.onerror` | 连接错误（含终态轮次正常关流） |

**关键缺口**：`startIdle()`（帧间看门狗）**只在 `source.onopen` 里被调用**（`:482-485`）；`open()`（`:478-484`）内除 `new EventSource(...)` 外**没有任何计时器**。

**条件枚举：`EventSource` 从构造到首个事件之间的三种结局**

| 结局 | 触发条件（现实可达） | HEAD 行为 |
|---|---|---|
| fire `onopen` | 正常建连 | 武装帧间看门狗 ⇒ 有界 |
| fire `onerror` | 连接被拒/断 | 走 `scheduleReconnect` ⇒ 有界 |
| **两者都不 fire** | TCP 已建但服务端迟迟不 commit 响应头（上游排队 / `SseEmitter` 未 commit）、中间代理黑洞、静默挂起 | **无任何计时器被武装**：`idleTimer` 从未创建、`scheduleReconnect` 无从触发、`settle` 无可达路径 ⇒ **promise 永久 pending**（浏览器对 `EventSource` 无原生命中；`vite.config.ts:34` 的 `proxyTimeout: 300000` 只在 dev 生效） |

**失效安全方向（代价）**：`reattach` 是"只 resolve 不 reject"的接口，三个调用点全部把状态复位放在 `finally` 里 ⇒ promise 不 settle 时 `finally` 不跑：

- `stores/ai.ts#send:703-717`：`loading` 永不复位 ⇒ `canSend` 恒 false ⇒ 输入区与发送按钮持续禁用（现场唯一自救是点"停止"，走 abort 可救，或刷新页面）；
- `stores/ai.ts#reattachActive:780-847`：同上，且 `busyConflict` 不被清；
- `stores/ai.ts#resumeSnapshotStream:580-624`：同上（`:583` 置 `loading=true`）。

### 2.2 修复设计（`sse.ts`）

| 改动点 | 位置（工作树行号） | 说明 |
|---|---|---|
| 常量 `DEFAULT_CONNECT_TIMEOUT_MS = 15_000` | `:43`（含取值论证注释 `:30-42`） | 建连预算，独立于 `DEFAULT_IDLE_TIMEOUT_MS` |
| `connectTimer` + `clearConnect()` | `:439`、`:457-462` | 新增看门狗句柄与清理器 |
| `startConnect()` | `:506-520` | `onopen` **之前**武装：超时后 `source.close()` → `scheduleReconnect('重挂连接建立超时（未收到 onopen）')` |
| `open()` 内 `startConnect()` | `:555`（紧接 `new EventSource(...)`） | 覆盖"构造 → `onopen`"这一唯一无计时器窗口（构造同步、事件只能在此后的任务里派发，故无事件丢失窗口） |
| 清除点 | `settle():470`、`startIdle():484`、`scheduleReconnect():529` | **不变量：任一时刻只武装一只看门狗**（`onopen`/首个帧让位给帧间看门狗；退避期间两只全清） |

**超时取值论证（15_000ms，对齐既有常量）**

- 落在审计建议区间（`blocking-audit/frontend.md` §S1-2 修法方向："`Promise.race` 连接超时 10~15s"）的**上界**，把"活但慢的连接被误判为死"的假阳性压到最低（一次 TCP/TLS 握手 + 代理首包 + 服务端线程池排队都放得下）。
- **三轮建连预算合计 15 + 1(退避) + 15 + 2(退避) + 15 = 48s `< DEFAULT_IDLE_TIMEOUT_MS`（90s）** —— 即整段 reattach 的"无进展等待"不超过既有"单条已建流允许的最长静默"这一上限，未引入新的量级（仓外实测：48.05s 收尾，§3.2）。
- 远小于 `api/http.ts` 的 axios 单请求上限（60s）与后端 `ConfirmGate` 挂起超时（120s）⇒ 前端先失败、先复位 `loading`、先出提示。
- 为什么不能直接复用 90s：建连失败（"根本没连上"）与帧间静默（"连上了但没数据"）证据强度不同，前者可以判得更早；沿用 90s 会让最坏等待退回 273s 量级（`90+1+90+2+90`），S1 的"界面假死"体验基本不变。

**错误呈现路径复用（未新增通道）**：超时后走既有 `scheduleReconnect` → 退避重试 → 次数耗尽 `settle(false, reason)` → `finish()` → `handlers.onClose(info)`；`stores/ai.ts` 三处调用点的既有 `onClose` 处理会置 `streamInterrupted=true` 并给出"连接中断，结果可能不完整（重挂连接建立超时（未收到 onopen）（重挂已尝试 2 次））…"的提示，`onReconnect` 公告也在退避时照常发出；`finally` 随之复位 `loading`。**`reattach` 仍只 resolve、不 reject**，调用方契约不变。

**副作用（顺带收口，同族）**：`scheduleReconnect()` 顶部原先只做 `settled` 守卫、不清任何计时器，HEAD 下 `onerror` 路径存在"退避期间上一只 `idleTimer` 残留"的隐患（其回调会再调一次 `scheduleReconnect`，造成次数重复计数/双连接）。本次在该函数顶部统一 `clearIdle() + clearConnect()`，两条看门狗互斥。（HEAD 的 B-04 —— 退避 `setTimeout` 句柄未纳入 `settle` 清理——**本包未动**，见 §7。）

**注释同步**：`reattach` 文档注释新增"两只看门狗（缺一不可）+ 只 resolve 不 reject"（`:410-423`）、常量注释（`:30-42`）、`clearConnect`/`startConnect`/`open` 行为注释。
