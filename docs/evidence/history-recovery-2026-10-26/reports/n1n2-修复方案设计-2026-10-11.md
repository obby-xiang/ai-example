## 3. N1 候选方案

### 3.1 候选 A：restore 内部自持对账（**推荐**）

**改动点（design-level diff，仅 `frontend/src/stores/ai.ts`，1 个函数 + 1 处 JSDoc）**

```
async restoreSuspendedSnapshot(): Promise<void> {
  const sid = this.sessionId            // ← 新增①：入口同步捕获（此刻与 :458 的 sid 同一 tick）
  let current: AiRunCurrent
  try {
    current = await aiApi.runsCurrent(sid)   // ← 改：显式用 sid（此刻等价，意图显式化）
  } catch {
    return
  }
  if (this.sessionId !== sid) {         // ← 新增②：唯一 await 之后、任何写回之前对账
    return
  }
  if (!current.found || !current.runId || !current.awaitingExternal) { return }
  …（:524-595 原样不动）
}
```

- **为什么"入口同步捕获"与"传入参数"等价**【实测】：`:458` 守卫与 `:471/:500` 的 `await this.restoreSuspendedSnapshot()` 之间**没有任何 await**（`:462-467` 与 `:496-499` 均为同步语句）⇒ restore 函数体首段执行发生在同一 tick，`this.sessionId` 与 loadHistory 的 `sid` 必然相等。
- **为什么必须放在 restore 内部**（直接否掉"只改 loadHistory 调用点"的朴素形态）【实测】：守卫 `:458` 已位于调用**之前**，而窗口产生于调用**内部**；`resumeSnapshotStream`（`:591`）虽自带 `isCurrentRound = currentAbort === controller`（`:614`）守卫，但那守的是"这条连接是否仍是当前轮"，**管不到 `:524-588` 的写回，也管不到 `suspended/loading/activeRunId` 被旧值覆盖**——故调用点侧无法补救。
- **JSDoc 同步**：`:427-430`（loadHistory 的守卫声明）与 `:503-507`（restore 的说明）各加一句"本函数内部自带一次 await，故入口自持身份、await 后二次对账；**本函数内任何新增 await 之后、写回之前都必须重新对账**"——把守卫口径固化成规则，避免后人再开窗口。

**竞态残余分析**

| 残余 | 是否被 A 覆盖 | 说明 |
|---|---|---|
| R1 会话身份在 `runsCurrent` await 期间变化（N1 本体） | ✅ **闭合** | 唯一 await 之后立即对账；写回段为同步块，JS 单线程保证无插队 |
| R2 await 期间**同会话**起了一轮新对话（`send()` 成功） | ❌ 未覆盖（**新发现，建议登记**） | 身份未变故守卫放行：`:588` 会用旧 runId 覆盖在跑轮的 `activeRunId`，`:617` `previous?.abort()` 会**掐断在跑轮自己的 SSE 连接**，其后 `resumeSnapshotStream` 的 `isCurrentRound` 因 `currentAbort` 被替换而恒 false ⇒ 在跑轮丢取消句柄、`loading` 永不复位（输入区长期禁用）。可达性【推断】：`AiPanel.onMounted` 只在 `onMounted` 调 `loadHistory`（`AiPanel.vue:726-733`），而输入区可用性 = `canSend = !loading`（`ai.ts:345-347`）⇒ 刷新后两次 RTT 窗口内用户可发出新消息。**与 N1 同族但不同轴（轮次身份 vs 会话身份）**，建议按 N1 同级新条目登记、由指挥官决定是否同批用"调用起点捕获 `currentAbort` 并在写回前比对"一并收口（本设计**不**把它塞进 N1，以保持 N1 的 MINOR 代价与可验收边界） |
| R3 同一会话两次并发 `loadHistory`（重入） | ❌ 未覆盖（现状不变） | 后到者赢、且 `resumeSnapshotStream` 会 abort 先到者的连接；触发面窄（`onMounted` 单次 + `!messages.length` 前置），登记即可 |
| R4 会话 id 复用导致守卫误判 | ✅ 无风险 | `createSessionId()` = `crypto.randomUUID()`（回落 `s-<base36 ts>-<8 随机>`，`:60-67`），`resetSession()` 每次都换新 id（`:1144/:1151`）⇒ `this.sessionId` 在页签生命周期内单调换新，**不可能回到旧值**，等值判定即身份判定【实测】 |

| 面 | 影响 | 依据 |
|---|---|---|
| 守卫族 | **不新增谓词种类**：新增的仍是 `this.sessionId !== sid`（族①「会话身份」）的第 4 个实例（`:449` / `:458` / 新增点）。族②`isCurrentRound = currentAbort === controller`（send `:686`、reattachActive `:832`、resumeSnapshotStream `:614`）与族③`resetSession` 的 F5 复合判据（`:1179`）**零改动** | 【实测】 |

### 3.3 逐项对比与推荐

| 维度 | 候选 A（restore 内自持对账） | 候选 B（await 上提 + 同步 apply） |
|---|---|---|

**推荐：候选 A**。理由（三条，按权重）：
1. **收益同构、代价差一个量级**：在当前代码形态下，两方案闭合的窗口集合完全一致（R1 闭合、R2/R3 同样残留），而 B 需要搬动 T2b-D#3 最密集的写回段——用 N1 的 **MINOR** 级收益去交换中等级别的回归面，不划算。

| 形态 | 成因 | 后果 | 是否已被惰性清理兜底 |
|---|---|---|---|
| ① stale 成员（**N2 本体**） | DEL 成功、SREM 前崩溃 | 索引多一个指向已删键的成员 | ✅ `findConversationIds` 会剔除（`:103-105`）；但 `removedFromIndex` 可能误报 `false`、索引键无 TTL 期间缓慢膨胀 |
| ② **丢失 SADD**（**N2-b，本次新发现**） | DELETE 的 `DEL` 与 `SREM` 之间，被**另一连接的** `saveAll`（`SADD`）插队 ⇒ 迟到的 `SREM` 抹掉刚加的成员（见 §6.3 推演） | **存活会话从索引消失**（数据键在、成员不在）⇒ `findConversationIds` 漏报（违反 SPI "列出全部存活 id"）、`isConversationIndexed=false`（`removedFromIndex` 误报 `true`） | ❌ **无兜底**（`findConversationIds` 只清"索引有、键无"，不补"键有、索引无"）；只能等该会话下一次 `saveAll` 的 `SADD` 自愈 |
| ③ 兄弟窗口：`saveAll` 自身四步非原子（`:132-142`：`DEL` → `RPUSH` → `EXPIRE` → `SADD`） | 崩在 `SADD` 之前 | 数据键在、索引无成员（同 ② 的终态） | ❌ 同 ②；但 `saveAll` 是每轮收尾的 `clear + add`（`ResilientChatService:576-592`）热路径，**下一轮写回即自愈** |

## 5. N2 候选方案与代价

### 5.1 候选 1：单次 Lua 脚本原子化（**推荐**）

```java
// 类内静态常量（无需改 AiModelConfig / 无需新 bean）
private static final RedisScript<Long> DELETE_WITH_INDEX = new DefaultRedisScript<>(
    "local removed = redis.call('DEL', KEYS[1]) " +
    "redis.call('SREM', KEYS[2], ARGV[1]) " +
    "return removed", Long.class);

@Override
public void deleteByConversationId(String conversationId) {
    this.redis.execute(DELETE_WITH_INDEX, List.of(key(conversationId), CONVERSATION_IDS_KEY), conversationId);
}
```

| 代价项 | 评估 |
|---|---|
| 代码量 | ~8 行常量 + 1 行调用 + 类 JSDoc「语义」节改写（`:45`）+ 键结构节补一句 | 【推断】 |
| 依赖/装配 | **零新增依赖**（`DefaultRedisScript` 属既有 `spring-data-redis`）、无需 bean、不改 `AiModelConfig` | 【实测：`RedisAvailability:86` 已在用 `redis.execute(RedisCallback)`，"执行脚本/回调"这条路本仓已开】 |
| 服务端要求 | `EVAL/EVALSHA` 为 Redis 核心命令，Memurai 兼容；【假设】需一次实跑确认（本机无 Redis 实跑，未验证） |
| 序列化一致性 | `StringRedisTemplate` 的 key/value 序列化器均为 String ⇒ `ARGV[1]` 是会话 id 原始字符串，与 `opsForSet().add(...)` 写入的成员字节一致（否则 `SREM` 会静默不匹配） | 【推断，必须实跑验证，见 §8.2 用例 3】 |
| 原子性边界（**如实**） | Lua 消除的是"**跨命令**窗口"：客户端（JVM）在任何时刻崩溃/断连，脚本要么整段未执行、要么整段在服务端执行完；同时消除与其它连接命令的交错。**但**：Lua 脚本内部不具回滚语义，Redis **服务端进程**在脚本执行中途崩溃仍可能只落前半（对持久化而言，与任何多命令序列同性质）——该面是本设计**不承诺**的 | 【推断】 |
| 集群约束 | 两 key 不同 hash slot，Redis **Cluster** 下 `EVAL` 多 key 会被拒（需 hash tag）。本仓为单实例 Memurai，**需在 JSDoc 写明该约束**，避免将来迁移踩坑 | 【推断】 |
| 测试改造 | 既有 `AiControllerHistoryDeleteTest` 的 F4 两例（`:224-261`）断言的是 `SISMEMBER`（`isConversationIndexed`），与 `deleteByConversationId` 实现无关 ⇒ **存量用例不受影响**（桩 `execute(...)` 未 stub 时返回 `null`，本方法忽略返回值）；新增 2 例即可（§8.1） | 【推断 + 实测】 |

### 5.2 候选 2：Redis 事务（MULTI/EXEC）

| 代价项 | 评估 |
|---|---|
| 实现形态 | `redis.execute((RedisCallback<Object>) conn -> { conn.multi(); conn.del(bytes); conn.sRem(idxBytes, idBytes); return conn.exec(); })` —— `RedisCallback` 是**字节级**连接 API，须手工序列化两个键（`stringSerializer.serialize(...)`），可读性差；或走 `SessionCallback` + `multi()`，同样需要裸连接判空 |
| 原子性 | 与 Lua **同效**（EXEC 内命令不交错；客户端崩溃于 EXEC 前 ⇒ 两条都不执行） |
| 语义陷阱 | 事务**不回滚**：脚本/命令级错误只在 `EXEC` 返回列表里体现，`exec()` 的返回值必须显式判别，否则失败静默 |
| 测试改造 | 单测断言从 `opsForSet()` 迁到 `execute(RedisCallback)`，比 Lua 的 `execute(RedisScript, keys, args)` 更难表达"这是一次原子操作"（可读性/可维护性劣势） |
| 结论 | 能力上可行，但**收益与候选 1 相同、代码与测试代价更高** ⇒ 不推荐（仅作为 LUA 被否时的备选） |

### 5.3 候选 3：显式接受现状 + 文档化

| 代价项 | 评估 |
|---|---|
| 代码 | 零改动 |
| 需要新增的文字 | `RedisChatMemoryRepository` 类 JSDoc「已知未覆盖」节（`:48-49`）补一条：**索引是数据键的从属投影，允许出现 stale 成员；权威存活判据永远是数据键的 `EXISTS`；`findConversationIds` 负责惰性收敛**；`AiController:610-612` 的"响应时点事实"口径与之呼应（已有） |
| 残余 | ① stale 成员（有兜底）、② 丢失 SADD（**无兜底**）、③ `saveAll` 窗口（下一轮自愈）**全部保留**；索引键无 TTL 的缓慢膨胀保留 |
| 何时可选 | 若指挥官认定"不动后端"（例如与批 B 的 job 侧改动隔离、避免同批触碰 AI 记忆面）⇒ 候选 3 + **必须同时登记 N2-b**（否则"已知代价"清单不完整，属如实性缺口） |

### 5.4 推荐：候选 1（Lua），并给出条件

**推荐理由**
1. **代价极低、收益成类**：~10 行、零依赖、零装配改动，一次性消除 ①② 两种失配（③ 属 `saveAll` 自身语义，见下）。
2. **N2 的性质已被本次实读升级**：不再是"仅崩溃窗口"（§4.2 ② 的丢失 SADD 是可并发复现的交错失配）⇒ "后果有界故不修"的原始理由被削弱；而 §5.3 的"接受"需要额外承担一条**无兜底**失配的登记成本。
3. **它让一条不变量变得可断言**：修后即可写"删除后 `key` 与 `__ids__` 成员同生共死"的结构性断言（§8.1），这正是本仓偏好"机器化锁"的验收风格（同 `AiControllerHistoryDeleteTest:224-241` 的单次 `SISMEMBER` 断言）。

**条件**：若本批的唯一目标是 N1（或明确"不碰后端"），则按 §5.3 接受 + 登记 N2-b；**不建议**在本批只做"半个修复"（例如仅把 `saveAll` 的 `SADD` 提前而不动 `deleteByConversationId`）。

**可选顺手项（超出 N2 字面范围，需单独裁决）**：`saveAll`（`:132-142`）把 `SADD` 提前到 `DEL/RPUSH` **之前**，可让 ③ 的崩溃终态从"存活会话无索引成员（无兜底）"变为"stale 成员（有兜底）"，属**零成本、纯恶化方向改善**的一行重排序；改动不影响非崩溃路径的最终状态。本设计**不把它并入 N1/N2 验收**，只登记为候选。

### 6.3 **N2-b（本次新增发现，建议登记）**：DEL 与 SREM 之间的交错可让**存活会话**从索引消失

【推断，推演链】
1. 线程 T1 走 `deleteByConversationId(id)`：执行 `①DEL`（此刻数据键已不在）→ 被调度切出。
2. 线程 T2 走 `saveAll(id, msgs)`（典型来源：在飞轮次的收尾 `convergeMemory` = `clear + add`，`ResilientChatService:576-592`；`AiController:551-557` 已把该并发路径文档化为"必然先于收盘重写"）：`DEL` → `RPUSH` → `EXPIRE` → **`SADD id`** ⇒ 索引此刻有 `id`、数据键也存在（一致）。
3. T1 恢复，执行 `②SREM id` ⇒ **索引成员被抹掉，而数据键仍在**。
4. 终态 = "存活会话无索引成员"：`findConversationIds()` 漏报该 id（违反 SPI 契约面）、`isConversationIndexed()` 返回 `false`（`removedFromIndex` 误报 `true`）；**惰性清理不覆盖该方向**，只能等该 id 的下一次 `saveAll` 自愈。
5. 交错的相反顺序（T2 的 `SADD` 落在 T1 的 `SREM` 之后）终态一致、无异常；只有上述顺序有害。

【推断】修复候选 1（Lua）可让第 1~3 步成为一个不可分割的执行单元 ⇒ 两种交错终态都变成"键与成员同生共死"，与 `AiController:551-557` 已登记的"旧键必被写回"代价自洽。
