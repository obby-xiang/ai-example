### 1.6 根因复核结论（一句话）

**契约违反成立（向导页把 `page` 设成标签空间外的 `'export'`/`'import'`，且 `enterPage` 的 `pageId→page` 回退使任何页面都必然如此），但它当前无任何可观测后果 —— 因为标签匹配是 OR、且全部 `page:tasks` 类工具都带 `task:*` 兜底、而 `page:export`/`page:import` 匹配不到任何工具（等价于"向导页不参与 page 披露"，恰与 `ToolScope.java` 的 `task:* — on any task wizard page` 心智模型一致）；issue 主张的"6 个工具被排除"有 4 个为误判、2 个是正确行为。故建议严重度由"高"降为"低（契约债务 + 后续误改诱因）"。**

## 3. 多挖缺口（issue 未提，需一并裁决）

- **G1【推断→需探针实证】冻结上下文导致"同轮内推进到最后一步后，启动类工具不可见"，这才是 issue 措辞所指的"冻结下工具不可见"的真身**：一轮内模型执行 `confirm_step`（前端 `ExportWizardView.vue:876-886` → `goStep` → `workspace.setStep` + `syncStepToBackend`）把 step 推到 `EXPORT`/`PRECHECK`/`IMPORT`/`PUBLISH` 后，冻结上下文仍是旧 step ⇒ `start_export`/`start_precheck`/`start_import`/`start_publish`/`open_export_file_editor`/`download_export_file` 既不在 `toolCallbacks`（`ResilientChatService:208`），即便模型硬调也会被防线③以 `SCOPE_NOT_DISCLOSED` 拦下（`SpToolCallingManager:177-179/232`）。**受害面 = 所有"最后一步才披露"的工具**，与 `page` 取值无关（B1/C2、D1 的差集即证据）。缓解现状：模型只能在同一轮结束后（下一次用户消息带上新上下文）再调用 ⇒ 表现为"AI 不能一口气跑到启动，需要用户再发一句"。**与 issue 的关系：机制真、归因错。**
- **G2【实测】`enterPage` 的 `pageId→page` 回退是系统性诱因**：任何新增页面（或忘记传 `page` 的旧页面）都会自动把 `page` 设成 `pageId`。若将来新增页面 id（例如 `reports`）而不加 `page:`，会产出 `page:reports` 标签（同样匹配不到任何 pattern ⇒ 等价于该页无 page 披露），但**若该页本意是 `page:tasks` 口径**（例如"任务工作台"变体），则 `page:tasks` 类工具会静默全失（此时才有真实症状）。⇒ 建议为回退加断言/守卫（§4 备选 B 的配套）。
- **G3【实测】`page:tasks` 依赖面全清单**：`list_tasks`、`create_task`、`start_export`、`start_precheck`、`select_definitions`、`set_condition`、`confirm_step`、`generative_form`（8 个，§1.4 表）。其中**只有 `list_tasks` 有 `*` 兜底**，其余 7 个在"仅剩 `page:tasks` 且无 task 维度"的上下文（任务中心）**完全靠这个标签存活** ⇒ 一旦有人按注释把向导的 `page` 也改成 `'tasks'`，这 7 个工具在向导内的披露范围全部被悄悄放宽（§2.2）。**反向告诫：`page:tasks` 目前承担"任务中心专属闸门"职责，而契约注释却把它描述成"page 的合法取值之一"，二者语义不对称。**
- **G4【实测】`workspace.leaveWizard()` 是死代码**：全仓无调用点（仅 `workspace.ts:152` 定义）。它声称"离开向导时清掉 task 维度"，实际由各页 `enterPage({taskType:null, step:null})` 完成 ⇒ 文档/实现轻微漂移（低危，登记）。
- **G5【实测（代码级）】提示词里的 `页面:` 文案是裸 id**：`ContextBuilder:67` 输出 `页面: export`（而空值时回落中文"任务中心"），与前端 `PAGE_LABELS`（`workspace.ts:48-54`）中文文案不一致。非本 issue 根因，但若采纳 §4 备选 B（文档对齐），建议顺手把该行改成"页面：<中文名>（<id>）"，避免模型面对裸 id。【低危】
- **G6【推断，需探针】`navigate_to` 后同轮可见性**：从任务中心一轮内 `navigate_to(export, taskId)` 后，冻结上下文仍是任务中心（`page:tasks`，无 task 维度）⇒ `start_export`/`select_definitions`/`set_condition`/`confirm_step` 在此轮**恰好都可见**（这正是 S4.4d 放宽 `page:tasks` 的目的），但 `open_export_file_editor`/`download_export_file`/`start_publish` 等到下一轮才可见；反向（向导内 `navigate_to` 回任务中心）则仍持有向导的工具集。**结论：跨界导航后同轮工具集与实际页面不匹配，方向利弊不对称**，建议一并纳入 §5 探针（s6）观察。
- **G7【实测】前端 `matchesScope` 的 `page:` 分支只做字面比较、且 `snapshot().page` 被当作 `page` 唯一来源**：若采纳"强制 `page='tasks'`"，则前端描述的 `page:` 级粒度在向导内也失效（与后端同向失效，不产生新的不一致）；**但若未来后端给某工具加 `page:export` 而前端仍按 `page` 比较**，两侧依然同源 ⇒ 无风险。登记即可。
