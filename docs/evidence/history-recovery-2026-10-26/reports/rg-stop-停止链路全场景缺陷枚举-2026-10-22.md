## 二、逐场景实证细节

### 场景 1：纯文本流式中途停止（`<LOCAL_WORK>/_rg-probe/stop/S1/`）
- 停止前：`msg-bubble-a-…:106`、`stream-caret=true`、`stopVisible=true`、镜像里助手段 `text len=0 / streaming=true`（防抖未落盘，与上一轮报告一致）。
- 点击后 +230ms：正文 `141`（**还在涨**——迟到帧仍被消费，见根因 #8），`stopVisible=false`、`notice=「已请求取消本轮对话」`、`caret` 仍 true。
- +1.2s：正文定格 141，`caret=false`，`notice` 仍在；无任何"已停止"标记（截图 `03-after-stop-1.2s.png`：正文以"…版本与生效范围"硬断，下方只有「继续」）。
- 后端：`/api/ai/runs/{runId}` → `status=CANCELLED`、`cancelled=true`、`error=AI_RUN_CANCELLED：本轮由用户取消（上游连接已断开，工具未再继续）`、`assistantContent=null`、`historyRoles=[SYSTEM,USER]`；归档末帧 `done{cancelled:true}`。
- 场景 1b（停止→刷新，`07-b-stopped-then-reload.png`）：DOM 只剩 `msg-bubble-history-0:54`；镜像只剩 user；**141 字的答案彻底没了，后端也没有**。
- **补充复核（`S1e/`）**：S1 首轮里曾出现"停止约 20s 后发新消息 → 正文（141 字）被 `history-0` 整替"，我一开始怀疑是"发送导致丢失"。用同一路径复测（停止 → 静置 20s → 发送）后：正文 109 字**稳定保留**，新轮正常，`performance.getEntriesByType('navigation')` 只有一条 `navigate`、`/history` 拉取 0 次 ⇒ **该次丢失是实测期间外部 HMR 整页重载所致，不是发送路径的缺陷**。真正的丢失路径只有"刷新/重载"（1b）。

### 场景 2：工具执行中途停止（`S2c/`、`S5/b1,b2`）
- 页内 10ms 探针在「调用中…」出现后 **1ms** 内点停止（`probe[0] detect` / `probe[1] click+0`，卡数 2、`st=["已成功","调用中…"]`）。
- +50ms / +200ms / +600ms / +2s / +5s 全部**仍是** `["已成功","调用中…"]`——**没有任何终态帧把它收口**。
- 镜像（`S2c/evidence.json` → `mirrorBrief`）把该段写成 `{"kind":"tool","name":"get_row_count","status":"running"}` ⇒ 脏态持久化。
- 归档（`S5/b-events.txt`）证实：`tool_start` 之后**没有** `tool_result`，直接 `done{cancelled:true}`。所以既不是前端丢帧，是后端就没发。
- 刷新（`S5/b2-tool-stop-after-reload.png`）：该卡**直接消失**（历史里没有这次调用），恢复成 2 张「已成功」；正文 79 字也没了。
- 对照 S2b：停止发生在"4 张卡全成功、模型收尾阶段"时，卡面 4×已成功 + 正文保留，`ledgerCounts={"get_row_count":6}`（含 2 次真失败 `RESOURCE_NOT_FOUND`，与取消无关，别误读为"取消导致失败"）。

### 场景 3：HITL 确认卡挂起中停止（`S3/`、`S3b/`、`S3c/`）
- 挂起时：`composer.taDisabled=true`、占位「挂起等待中：请先在上方处理确认/执行，或点「停止」结束本轮」、`gate=["拒绝","批准"]`；后端 `SUSPENDED`、`awaitingExternal=true`、`start_export/PENDING/req=true`。
- 点击停止 +2.5s（`S3b/01-after-stop-card-still-pending.png`，与 S3c 一致）：
  - 停止钮 **消失**（`stopVisible=false`，DOM 计数 0）；
  - 确认卡**仍是「待确认」**，`拒绝/批准` 仍可点；
  - 输入框**仍禁用**，占位文案还在教用户"点「停止」结束本轮"（自相矛盾的 UI）；
  - 顶部「已请求取消本轮对话」。
- 后端：`CANCELLED`；`/api/ai/pending/{runId}` → `status=CANCELLED`、`outcome=cancelled`、`code=RUN_CANCELLED`、`resultText="本轮对话已被用户取消，该工具未执行。"`、`resolvedAtMs` 与归档 `message_end` 同毫秒；`/runs/current` `found:false`。
- **旧洞复核结论：挂起等待者确实会消费取消标志（已修）**，代码侧对应 `ConfirmGate.java:474`（`onCancel(runId, latch::signal)` 加速唤醒）+ `:518`（心跳轮询 `isCancelled`）+ `:762`（`cancel()` 逐条落 CANCELLED）。**但这套"发裁决帧"的路径本次没走到**：
- 归档（`S3c/events.txt`，seq 52-56）：`suspended → tool_start → confirm_request → message_end → done{cancelled:true}`，**没有 `confirm_decision` 帧**。即整轮被 `ResilientChatService.cancelTerminal` 直接收尾，`RunStore.cancelPendings` 批量置 CANCELLED 而**不发帧**。
- 于是前端：既没有帧能收敛卡（重挂也回放不出来），`stop()` 又只清 `suspended` 不碰段 ⇒ `pendingToolCall` 恒非 null ⇒ 输入框死锁。
- 在死锁现场点「批准」（`S3b/02`）→ `POST /api/ai/confirm` **409**，横幅变成「该确认已提交过（幂等拒绝），正在与系统同步真实裁决…」→ 10s 后仍是「待确认 + 工作中…」，**仍死锁**。
- 刷新（`S3c/03-after-reload.png`）：输入框恢复、确认卡不再可交互、可发新消息。**刷新是唯一出路。**

### 场景 4：generative_form 挂起中停止（`S4b/`、`S4c/`）
- 挂起时：卡 `配置项筛选条件 / 待填写`、输入禁用、后端 `SUSPENDED`、`generative_form/PENDING/req=true`。
- 停止后：表单控件消失（`form=null`）、但**卡片仍显示「待填写」**、输入框**仍禁用**（与场景 3 同型）；后端 `CANCELLED`、条目清空。
- `S4b` 里 `page.fill` 超时 5s → 实证"发不出"。刷新（`S4c`）：可用，但只剩 `msg-bubble-history-0:52`，整条助手消息（表单卡与说明文字）消失。

### 场景 5：停止后立刻刷新
- 文本（场景 1b）：整条答案消失（最差）。
- 工具（场景 2 + `S5/b2`）：恢复成"更早的已完成态"，执行中的卡**消失**（没有"已取消"记录）。
- 挂起（场景 3b / 4b）：卡片不再可交互（历史态），输入恢复；同轮上下文部分丢失。
- 三种情况的 `/runs/current` 都是 `found:false`（取消后索引被清，`RunStore.java:463` 只在 SUSPENDED 写索引）⇒ 刷新后前端**没有任何入口**知道"刚刚那一轮被用户停掉了"。

### 场景 6：停止后立刻发新消息
- 文本：停后 600ms 发 → 200，新轮正常；停后 120ms → 200；停后 **10/30/50/70/100ms** → 全部 200（`S6d`）。**没有 409，也没有上一轮 E 场景的幻影气泡/草稿双份**（因为 `send()` 前 `loading` 已复位，`notice` 被清）。
- 工具中途停止后发 → 200，新轮正常，旧卡「调用中…」留在上方（视觉脏但可用）。
- 挂起态：**发不出**（输入框 disabled，属场景 3/4 的锁死）。
- 唯一瑕疵：停后 **1ms**（同一 tick）的回车被 keydown 守卫 `ai.loading` 吞掉，**无任何提示**（草稿保留，再按即可）。≥10ms 正常。

### 场景 7：连点两次停止 / 停止中的按钮态
- 页内 `btn.click(); btn.click()`（同 tick）→ **2 次** `POST /api/ai/cancel/{同 runId}`（均 200）；`/api/ai/cancel/{runId}` 返回 `alreadyCancelled` 但前端**不消费**该字段。
- 按钮态序列：`before(present=true,disabled=false)` → `after1` 仍 present → `after2` 仍 present → `t+30ms present=false`。即**首点后约 30ms 内按钮仍可点**，且永远不 disabled、无"停止中"文案。
- 结果无实害（run 一次 `CANCELLED`，后续发送正常），但**没有任何防重语义**。

## 四、根因（文件:行，锚点为上文 md5 快照）

1. **`stop()` 只清"挂起标志"，不收敛任何段/卡** — `frontend/src/stores/ai.ts:3244-3282`。
   - `:3257` `currentAbort?.abort()`（立刻断流，后端裁决帧再也收不到）；
   - `:3265-3268` 只 `dropActiveForm()`；
   - `:3272` `this.suspended = false`；
   - **全程没有** `expireResidueToolParts()` / `applyPendingTerminal()` / 把 `running`→`cancelled`。
2. **输入框禁用的判据包含 `pendingToolCall`，而它由段投影派生** — `AiPanel.vue:1520-1526`（`ai.pendingToolCall !== null`）+ `ai.ts:960-975`（getter 扫 `message.pendingCall.status==='pending'`）。停止清掉 `suspended` ⇒ 停止钮条件（`AiPanel.vue:896` 的 `v-if="ai.loading || ai.suspended"`）为假、钮消失；但段仍 pending ⇒ 输入框仍禁 ⇒ **既停不了也发不出**。
3. **后端取消终局不发裁决帧** — `ResilientChatService.java:984-1000`：`cancelTerminal()` 里 `store.cancelPendings(runId)`（`RunStore.java:1315-1327` 批量置 `CANCELLED`）**只改 Redis 条目，不 emit**。会 emit 的 `ConfirmGate.cancel()`（`ConfirmGate.java:762-785`，含 `out.confirmDecision(...)`）在本次实测里被 watchdog/上游中断抢先，未被执行（归档缺 `confirm_decision`）。
4. **取消路径被看门狗式"整轮收尾"抢走** — `StreamWatchdog.java:104`（`onCancel` → `fire(CANCELLED)`，当场断上游）与 `ConfirmGate.java:474` 竞争；前者赢则走 `cancelTerminal`，逐条 cancel 的语义丢失（挂起条目仍正确变 CANCELLED，但**没有帧**）。
5. **半截正文刻意不落记忆** — `ResilientChatService.java:986-987` 注释原文"**不**写入半截 assistant 正文（半条消息会污染下一轮记忆）"，`:992` `setAssistantContent(null)`。于是停止后正文只存在于浏览器内存。
6. **前端刷新用历史整体替换** — `ai.ts:1264` `this.messages = history.messages.flatMap(...)` ⇒ 历史里没有的半截答案被丢弃（与上一轮刷新报告 R3 同一条）。
7. **段级收口不认 `running`** — `ai.ts:581-593` `expireResidueToolParts` 只处理 `requiresAction`，把 `pending`→`expired`；对 `status==='running'` 的段无任何出口。所以即便 `stop()` 调它，「调用中…」也收不掉（D4 的直接原因）。
8. **abort 只断网络，不断"已到达的块"** — `api/sse.ts:316-317` 的读循环不检查 `signal.aborted`（只在 `catch` 里判 `:350`），一次 `reader.read()` 已返回的整块帧会被全部 `consumeFrame` 掉；`ai.ts` 侧只按 `currentAbort` 身份判"是否本轮"，而 `stop()` 不换 `currentAbort` ⇒ 停止瞬间在途块照写（D8）。
9. **停止钮无防重、无 stopping 态** — `AiPanel.vue:896-900`（无 `:disabled`、无"停止中"分支）；`ai.ts:3244` 无 `if (!this.loading && !this.suspended) return`；`AiController.java:648-667` 已返回 `alreadyCancelled` 但前端（`:3277`）只 `await aiApi.cancel(runId)` 后写一句 notice，不读返回体（D6）。
10. **可发现面缺失** — `RunStore.java:463-464` 只在 `status==SUSPENDED` 时写 session→current 索引；取消（CANCELLED）后 `/runs/current` 恒 `found:false`（S1/S3c 实测）。刷新后前端没有任何"这轮被停掉"的入口（D10，与上一轮报告 R1 同源）。
11. **停止无可见收口文案** — 只有 `done` 帧里才有 `notice='本轮已取消'`（`ai.ts` done 分支，快照内 `:3814` 起）；`stop()` 永远收不到这个帧，只写"已请求取消本轮对话"，消息上无标记（D5）。

## 五、修法方向（按"批G 必须成立"排序）

**必修 1：`stop()` 本地就地收敛（纯前端，改动最小、收益最大）**
- 在 `stop()` 里对**本轮宿主消息**的所有 `tool` 段：`requiresAction=false`；`status ∈ {pending, running}` → `'cancelled'`（配套把 `expireResidueToolParts` 的判据扩到 `running`，见根因 #7）；再 `deriveProjections`。
- 一并清 `activeForm/activePreview/stalePreviewToolCallId/suspended`，让 `pendingToolCall` 立刻变 null ⇒ 输入框解禁、确认卡/表单卡转为只读「已取消」。这一步直接把 D1 从"卡死"降为"可继续"。

**必修 2：给"停止"一个可观察的 stopping 态 + 防重**
- store 加 `stopping`（或复用 `stopped` 的显式阶段）：按钮 `:disabled="ai.stopping"`，文案/图标换"停止中…"；`stop()` 首行 `if (this.stopping || (!this.loading && !this.suspended)) return`；读 `cancel` 返回的 `alreadyCancelled` 只记一次。

**必修 3：停止要"看得见"**
- 被停止的助手消息打标记（`message=stopped` 或末段 `truncated:true`），正文尾部渲染「已停止」chip，与断流的「结果可能不完整」同一视觉族；`notice` 与「继续」入口二选一，别同时出现（D9）。
- 顺带把 done 帧才有的 `lastRoundOutcome='cancelled'` 语义在本地补上（现在已手动置位，但"继续"的含义要写清：继续=重发该问题，而不是续写被停的答案）。

**必修 4（跨刷新正确性）：让"停止后的答案"活下来**
- 短期（纯前端）：`stop()` 时立刻 `writeMirror`（含部分正文与已收敛的卡），并把 `done:true` 落镜像；`loadHistory` 改成"历史 + 未被历史覆盖的镜像在途/已停轮"合并（上一轮报告 R3 已列同一修法）。
- 中期（后端一行级）：`cancelTerminal` 允许写入带 `cancelled:true` 标记的半截 assistant（或新增 `stoppedText` 字段），至少让 `GET /history` 能返回"这轮被停止，内容如下"。当前"整条消失"是最糟的一种。

**必修 5（帧面）：取消时补裁决帧，或把结局塞进 done**
- `cancelTerminal` 对每个 `pending` 在 `cancelPendings` 前排空订阅者之前 emit `confirm_decision(decision=cancel)` / `frontend_tool_result(cancelled)`；或在 `done{cancelled:true}` 里带 `pendingOutcomes:[{toolCallId,status}]`，让**任何再连接的客户端**都能收敛（现在归档里查不到，重挂也救不回）。这样即便 D2 的"前端已断流"，刷新/重挂也有真值。

**必修 6（可发现面）**
- `RunStore.java:463` 的 `markSessionCurrent` 在 RUNNING 也写（终态再清），或 CANCELLED 保留短 TTL，让 `/runs/current` 在"停止后刷新"时能回答"上一轮被取消了"；前端据此渲染一条"上一轮已被停止（N 字）"的只读条，而不是让答案凭空消失。

**建议 7（迟到帧闸门）**
- `sse.ts` 的读循环每块前检查 `signal.aborted`；`stop()` 递增 `roundEpoch` 并把 `currentAbort` 置空后再 abort，配合 `handleFrame` 的代际判定，杜绝停止瞬间的迟到帧（D8）。
