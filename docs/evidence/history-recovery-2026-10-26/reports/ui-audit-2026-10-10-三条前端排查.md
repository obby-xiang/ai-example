## 0. 结论摘要

- 任务中心 4s 自刷（`stores/task.ts:187`）确实是**"有推送基建却用轮询"的设计债**：后端 `TaskSseService` 已按任务推送 `TASK_CHANGED` / `JOB_PROGRESS` / `JOB_DONE` 三类事件 **【实测】**，而任务中心页面**没有订阅任何 SSE 通道**，改用 4s 无条件全表轮询；前端 `types/sse.ts` 甚至已定义 `TASK_CHANGED` 类型但**全仓无任何消费方** **【实测】**。
- 该 4s 轮询是**无条件**的：与"是否有任务在跑"无关、与浏览器页签是否可见无关，只要任务中心页挂载就每 4s 打一次 `GET /api/tasks`。后端 `TaskController#toSummary` 对**每一行**再查一次 jobs + 一次 files（**N+1**，`TaskController.java:64-71`）**【实测】**，10 行/页 ≈ 20+ 次查询/4s/tab。
- 全前端周期性点共 **5 个**，其中 **3 个产生周期性网络请求**（任务中心 4s、job-watch 3s 兜底、waitForJobFinal 1s），2 个是本地节拍（AiPanel 倒计时 1s、页面就绪等待 50ms 有界）。
- **全仓 `frontend/src` 无任何 `visibilitychange` / `document.hidden` 处理** **【实测】**（grep 零命中）——即所有轮询在页签后台仍在跑。
- 事件驱动可行性结论（详见 §3）：**可以大幅降频，但不能完全取消列表拉取**。核心原因：任务中心是"分页 + 筛选的查询视图"，而 SSE 通道是**按 taskId 单任务**的（无全局任务通道、无事件序号、无断线回放），且 `JOB_DONE` 载荷只有 `{jobId, jobType, status, errors}`，不含行级所需字段。

### 1.2 机制描述【实测】

**刷什么**：`load()` 拉 `GET /api/tasks`（分页 10 条 + 筛选），整体替换 `items`/`total`，记录 `lastLoadedAt`。刷新的是**任务列表行**：任务状态、当前步骤、行级进度（`latestJob.progress/total`）、创建/更新时间。

**触发条件**：**无条件周期性**。`onMounted` 起表后每 4s 必然发一次请求，**不检查**：
- 列表里是否存在非终态作业（全部任务已完成/已失败/已取消时仍在拉）**——【实测】`startAutoRefresh` 与 `load()` 均无任何终态判断**；
- 浏览器页签是否可见（无 `visibilitychange`）**【实测】**；
- 是否已有在途请求（有 `if (!this.loading) return` 防重叠，但这只防重入，不降频）**【实测】**。

**停表路径**：只有一条 —— 组件卸载（`onBeforeUnmount` → `stopAutoRefresh`）**——【实测】**。路由无 `<keep-alive>`（`src/App.vue:28` 裸 `<router-view />`，全仓 grep `keep-alive` 零命中）**【实测】**，因此切换页面确实会停表，**这部分形态是好的**。
**另有一条隐性问题**：模块级 timer 与 store 实例解耦，`autoRefresh` 这个 state 字段**全仓无任何模板/组件消费**（grep 仅命中 store 内部自身赋值）**【实测】**，即"自动刷新开关"是**死状态**，用户无法关闭 4s 刷新。

**页面隐藏不停表**：`document.hidden === true` 时 `setInterval` 被浏览器节流到 ≥1000ms 但仍在跑；页面回到前台不会立即补拉，最坏情况下用户看到的是**最多 4s 前的陈旧数据**。

**详情抽屉**：`openTask()` → `refreshCurrent()` 是**一次性**拉取（`stores/task.ts:204-230`），抽屉打开期间**不订阅 SSE、也不再刷新** **【实测】** —— 即"列表在 4s 刷新，看着同一任务详情的抽屉却是静态快照"，进度展示存在口径分裂。

### 1.3 成本量化【实测 + 推断】

- 前端：每 4s 一次 `GET /api/tasks`，含 `loading` 遮罩（`v-loading`）→ **表格每 4s 闪一次遮罩**，是可见的体验问题（`TaskCenterView.vue:42`）。
- 后端：`TaskController#toSummary` 每行 2 次额外查询（`findByTaskIdOrderByCreatedAtDescIdDesc` + `findByTaskId(...).size()`）**【实测】**，`size=10` ⇒ 每次列表请求 ≈ **1（search）+ 10×2 = 21 次查询**；一个 tab 常开 ⇒ **每分钟 ~315 次查询**，且**与业务活跃度完全无关**。【推断】多 tab / 多用户时这是纯浪费，且把"任务中心页常开"变成持续的数据库负载源。
- 与 `FR-4.2`「运行中任务进度实时刷新」的对照：需求只要求"运行中任务"实时，**现状是对所有任务无条件全量刷新**，既非最优实时性（4s 延迟）也非最优成本。

### 1.4 "有推送基建却用轮询"的定性证据【实测】

代码里存在**三处自述矛盾的痕迹**，可直接作为设计债的硬证据：

1. `frontend/src/api/tasks.ts:99-104` 函数注释自述：
   > 「该通道帧形态与 AI 帧不同……且任务中心的进度口径按规格走 **4s 轮询**；本函数留给需要事件驱动的场景（如作业终态即时报）。」
   → 即：**基建已写好并注明"留给事件驱动"，而任务中心主动不用**。
2. `docs/technical-design.md:185-187` 自述：
   > 「后端已实现 SSE 推送；前端作业进度当前采用 1.5s 轮询 `GET /api/jobs/{id}`，二者并存，互不冲突」
   → 官方文档承认双轨并存。
3. `docs/03-技术方案文档-v2.1.md:49,55` ADR-10/DC-13 记载：任务中心自动刷新是**部件级吸收自 deepseek 前端**的特性；而同一 ADR 中"**SSE 进度通道替换轮询**"也写法吸收自 deepseek。
   → 即 4s 轮询是**蓝本搬运的惯性**（`stores/task.ts:4-5` 自述"形态来源：deepseek-v4-pro"），**不是本项目的设计选择**，在已自建 SSE 基建后失锚。

## 3. 事件驱动替代可行性结论

### 3.1 现有事件覆盖面【实测】

| 前端所需数据面（列表每行） | 现有事件能否覆盖 |
|---|---|
| `task.status` / `currentStep` / `updatedAt` | `TASK_CHANGED`（含 `taskId/version/currentStep/status/summary`）✅ 覆盖 |
| 任务增 / 删 | `TASK_CHANGED`（创建 `:90`、删除 `:267`）✅ 有事件 |
| `latestJob.status` | `JOB_PROGRESS`（隐含 RUNNING）+ `JOB_DONE`（终态）✅ 覆盖 |
| `latestJob.progress/total` | `JOB_PROGRESS` 带 `processed/total/pct`（字段名与列表的 `progress/total` 不同，需映射）⚠️ 部分覆盖 |
| `latestJob.errorCount/warningCount` | 仅 `JOB_DONE.errors`（且非全部 runner 同形）⚠️ 部分覆盖 |
| `latestJob.startedAt/finishedAt` | ❌ 无事件字段 |
| `latestJob.id/jobType` | ✅ 覆盖 |
| items 数 / files 数 / 分页 `totalElements` | ❌ 无事件（新增作业/文件不改这两个计数，但**新任务**会改 `total`） |
| 当前分页/筛选下"哪些行属于本页" | ❌ 事件流无法表达（查询视图语义） |

**已具备但闲置的能力**：`frontend/src/types/sse.ts:337-370` 已定义 `TaskEventType = 'HEARTBEAT' | 'TASK_CHANGED' | 'JOB_PROGRESS' | 'JOB_DONE'` 与 `TaskEventFrame`/`TaskChangedPayload`；`api/tasks.ts#openTaskEvents` 已实现客户端。**`TASK_CHANGED` 除类型定义与一处文档注释（`types/api.ts:125`）外，全仓无消费方** **【实测】**。`watchJob` 只处理 `JOB_PROGRESS`/`JOB_DONE`（`utils/job-watch.ts:61-73`），**丢弃 `TASK_CHANGED`**。

### 3.2 缺口清单（G1–G6）

| 缺口 | 内容 | 影响 | 关闭成本 |
|---|---|---|---|
| **G1** | 无**全局任务通道**（现有通道按 taskId 单任务；任务中心最多同时关心 N 个任务、且含"尚不存在订阅者"的新任务） | 事件驱动无法覆盖"列表里任意一行发生变化" | 中：后端加 `GET /api/tasks/events` 广播（`TaskSseService` 增加一个 taskId 通配的订阅列表即可复用现有 `publish`） |
| **G2** | `TASK_CHANGED` 前端零消费 | 任务状态变化无事件驱动的接线 | 小：在 `watchJob` 或新的 `watchTaskList` 中处理该帧 |
| **G3** | `JOB_DONE` 载荷过窄（`{jobId, jobType, status, errors}`） | 收到终态事件仍需一次快照拉取才能更新行 | 小：扩载荷（补 `processed/total/errorCount/warningCount/finishedAt`） |
| **G4** | 通道**无 seq / 无回放 / 无缓冲** | 断线期间的变更永久丢失 ⇒ 事件驱动**必须**配重连后全量对账，不能只靠事件 | 中：照抄 `RunStore`/`SseChatEmitter` 的 `seq + replayTo + lastSeq` 现成范式（`SseChatEmitter.java:322,363`）**【实测】基建同仓已有，可复用** |
| **G5** | `TaskSseService.emitters` 无订阅上限 / 无空闲回收（`SseEmitter(0L)` 无超时） | 与 P2 累积叠加会放大连接数 | 小-中 |
| **G6** | 列表行的 `items/files 计数`、`startedAt/finishedAt`、`updatedAt` 无事件字段 | 事件后仍需拉快照补全（与 G3 同类） | 小：同上扩载荷；否则接受"事件 → 触发一次拉取" |

### 3.3 可行性判定【推断，基于 §3.1/§3.2 证据】

- **可做**：把 4s **无条件固定轮询**换成 **「事件触发 + 低频兜底 + 前台才跑 + 有活才跑」**。这是收益最大且工程风险最低的形态，且**同仓已有完整范式可照抄**（`utils/job-watch.ts` 的"SSE 主通道 + 轮询兜底 + `onChannel` 显式降级"就是为这类场景写的）**【实测】**。
- **不可做（至少不该承诺）**：把列表**完全**改成事件驱动、删掉一切拉取。原因是 **G1 + "查询视图语义"**：分页/筛选/排序下的行集合只能由后端查询求值，新任务的插入位置、`totalElements`、跨页视图无法由事件流重建；且 **G4** 决定了断线后**必须**有一次全量对账。
- 因此正确表述是：**"事件用于决定何时刷新，而非用于代替刷新"**；轮询从"心跳"降级为"看门狗"（低频、条件化），而不是"换掉"。

## 0. 一句话结论

**放开是安全的，没有崩溃级风险点，但有 9 处 L2 级「空名/null 破相」消费点 + 4 处 L1 级退化点需要兜底。**

1. 后端**根本没有 Bean Validation 校验**：创建入口收的是裸 `Map<String,String>`，无 DTO、无 `@NotBlank`、无 `@Valid`（`backend/src/main/java/com/example/configmgr/task/controller/TaskController.java:73-79`）。所谓"必填"只存在于前端一行手写拦截 + DB 的 `NOT NULL` 列。

3. 唯一的硬阻塞是 `NULL`：`{"title":null}` 会穿透 `getOrDefault` 落到库上被拒 → 500。而"纯放开"若只允许空串（不允许 null），连这个都不存在。

- **一切面向机器的引用都走 id，不走名字**：AI 工具全部按 `taskId` 操作（`AiTools.java:148-166/265-320`、`navigate_to` `AiTools.java:362-368`、前端 `frontend-tools.ts:646/677/689` 的绑定判据也是 `taskId`）；SSE 按 taskId 订阅（`TaskSseService.java:23-33`）；导出/下载按 taskId（`FileController.java:196/272`）。⇒ **不存在"靠任务名选错对象"的功能性风险**。

4. `el-radio-group.css`：`.el-radio-group{flex-wrap:wrap;align-items:center;font-size:0;display:inline-flex}` → 两个 radio 各约 232 / 262px 宽，一行放不下 ⇒ 第 2 个折到下一行，**行距按 32px 盒子算**。

以第 1 个 radio 盒顶为 `T`：

- radio1 盒 `T … T+32`；label 内容 48px 居中 ⇒ 溢出为 `T−8 … T+40`，其中**说明文字行盒 `T+24 … T+40`**（16px）；
- radio2 盒 `T+32 … T+64`；label 内容同样溢出 ⇒ 首行行盒 `T+24 … T+56`。

⇒ 两个文本的**行盒在 `T+24 … T+40` 这一段完全重合（16px）**，按微软雅黑 14px/12px 的实际字身框折算，**字形墨迹交叠约 10px** —— 与截图所见一致。

补充说明（为什么以前没暴露）：`white-space:nowrap` 只保证说明文字不折行，本例说明文字比可用宽（约 306px）窄，所以**没有横向溢出**；问题纯粹是**纵向：32px 固定高度装 48px 内容**。任何在 `el-radio` 内放块级/多行内容的写法都会重现。

### 修法建议（EP + Tailwind，不写自定义 CSS）

**方案 A（推荐，最小改动，已在复现页验证）**——补 Tailwind 工具类，把固定高度与 nowrap 解开、并让选项竖排：

```vue
<el-radio-group v-model="createForm.type" class="flex flex-col items-start gap-1">
  <el-radio value="EXPORT" class="!h-auto !whitespace-normal !items-start !mr-0">
    导出配置
    <div class="text-xs text-[#909399] font-normal">选择配置项 → 设置查询条件 → 导出 Excel</div>
  </el-radio>
  <el-radio value="IMPORT" class="!h-auto !whitespace-normal !items-start !mr-0">
    导入配置
    <div class="text-xs text-[#909399] font-normal">上传/编辑 → 检查 → 导入暂存 → 发布生效</div>
  </el-radio>
</el-radio-group>
```

- `!h-auto` 解掉 `height:32px`（否则容器永远比内容矮 16px）；`!whitespace-normal` 解掉 nowrap（未来说明变长会自己折行，不再横向溢出）；`!items-start` 让单选圆点与首行对齐；`!mr-0` 去掉 `margin-right:30px`，竖排时不要右侧留白。
- 用 `!` 前缀与本仓既有习惯一致（`App.vue:11` 的 `class="!border-b-0"` 就是同一个用法）；不用 `!` 也能生效（`main.ts:12` 先引 EP 的 `element-plus/dist/index.css`、`:20` 后引 `src/styles/main.css`，同特异性后来者胜），但显式 `!` 不依赖 import 顺序，更稳。

**方案 B（结构性，最抗回归）**——说明文字**移出** `el-radio`，EP 的 radio 只承载单行标签（EP 的 radio 本来就不带描述插槽）：

```vue
<el-radio-group v-model="createForm.type" class="flex flex-col items-stretch gap-2 w-full">
  <div v-for="opt in TASK_TYPE_OPTIONS" :key="opt.value"
       class="px-3 py-2 rounded border border-solid border-[#e4e7ed]">
    <el-radio :value="opt.value" class="!mr-0">{{ opt.label }}</el-radio>
    <div class="pl-6 text-xs text-[#909399]">{{ opt.desc }}</div>
  </div>
</el-radio-group>
```

说明文字成为普通块级流，**结构上不可能再与单选项重叠**。

两种方案的实证：`<LOCAL_WORK>\ui-audit\shots\03-repro-before-after.png` 的 B 半幅就是方案 A 的类名组合（`el-radio-group` 加 `flex flex-col items-start`，`el-radio` 加 `h-auto whitespace-normal items-start mr-0`），渲染无重叠。

## ③ 总修法原则（EP + Tailwind 优先，禁自写 CSS）

1. **不要和 EP 的固定尺寸硬碰**：`el-radio`(32px/nowrap)、`el-checkbox`(32px)、`el-form-item__label`(32px)、`el-collapse-item__header`(48px line-height)、`el-button` 等都有写死的单一尺寸。往里塞**块级/多行**内容前，先用 Tailwind 解掉固定值（`!h-auto`、`!whitespace-normal`、`!items-start`），或把多行内容挪到 EP 组件**外面**。
2. **多行说明不要塞进单行控件**：需要“选项 + 描述”时，用 `el-radio-group` + 结构容器承载描述（方案 B），而不是往 `el-radio` 里放 `<div>`。
3. **宽度冲突优先用 EP 的布局开关**：`label-position="top"` / `label-width="auto"`（EP 原生，会把 label 高度改为 `auto`）；中文 label 不要写死在 `label-width` 边缘（≥5 字就会折行溢出）。
4. **覆盖 EP 用 Tailwind 工具类 + `!` 前缀**（本仓既有口径，见 `App.vue:11` 的 `!border-b-0`），不新增 `<style>`；`tailwind.config.js:5-7` 已关 preflight，Tailwind 不会污染 EP/SpreadJS。
5. **长文本/动态文本一律按会换行设计**：标题、label、`ElMessageBox` 文案都假设会折行，避免依赖单行假设；`\n` 想生效必须显式 `whitespace-pre-line`。
6. **回归建议**：改完后按 `http://localhost:5202/tasks` → 创建任务 → 目视两个选项与其说明互不遮挡；并把本报告 ②表中 P1（label 折行）纳入“以后加长中文 label 时的自检项”。
