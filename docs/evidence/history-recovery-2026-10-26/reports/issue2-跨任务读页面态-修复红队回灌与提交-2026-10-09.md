### 2.3 根因结论（以实际代码为准）

> 两个前端工具都声明了必填 `taskId`（`AiTools.java` 的 `@ToolParam(description="任务ID")`，`frontend/src/types/tools.ts` 里 `required: true`），但执行路径只用它做了**参数校验**：`open` 把它透传给页面 handler 后页面**不看**、`download` 连透传都没有。所有判定都落在页面本地状态上（`exportResults` / `gridRefs` / `loadedGrids`），而这三者只反映**当前绑定任务**。
>
> 于是同一个 bug 有**两个方向**：目标有文件而当前任务没有 ⇒ 假阴性（issue 现象）；当前任务有**同名 defCode** 的导出文件 ⇒ 假成功 + 把别的任务的字节当目标任务给出去（issue 未提及，实测复现）。
>
> 并且 —— 即使只补一句 `if (args.taskId !== taskId.value)`，也不够：绑定是一条**异步链路**（改路由 query → watch 同步 `setTaskId` → `loadTask()` → `loadExistingResults()`），不等它跑完就读 `exportResults`，得到的还是旧任务的列表（假阴性照旧）。

### 2.4 只加"判断 taskId 是否一致"为什么不够（三个必须一起处理的点）

1. **必须 await 加载完成**：绑定后 `exportResults` 要等 `GET /tasks/{id}` + `GET /tasks/{id}/files` 两个请求回来才可信（设计要求的第 2 条）。
2. **必须区分三类"没有文件"**：`任务不存在` / `文件列表读取失败` / `该任务确实没有这个文件`。旧代码把三者都归成同一句"暂无导出结果文件"，AI 拿到之后无法决定是换任务号、重试、还是先导出。
3. **必须清掉上一个任务的表格缓存**：`ensureGridLoaded` 用 `loadedGrids` 当"已加载"判据，跨任务遇到同名 defCode 会直接跳过加载 —— 编辑器里显示/下载的仍是**上一个任务**的字节（场景 C 修前的直接成因）。这也是"绑定切换"的一部分，不清理则修复不完整。

### 3.2 视图侧：一条绑定链路，两种触发（不另造第二套）

```ts
// ExportWizardView.vue#applyTaskBinding（:405，含 R1/R2/R3 回灌）
async function applyTaskBinding(id: number, preloaded?: Task): Promise<TaskLoadOutcome> {
  resetTaskScopedState()                                       // ① 清上一个任务的页面态（R2：脏表格先提醒）
  stopJobWatchForTaskSwitch()                                  // ② R3：停旧作业 watcher + 清作业面板
  taskId.value = id                                            // ③ 同步改绑（与 onMounted 同序）
  workspace.setTaskId(id, 'EXPORT', null)                      //     AI 侧"绑定完成"判据立刻成立
  const promise = (async () => {                               // ④ R1：把这次绑定登记为"在途"
    await router.replace({ name: 'export-wizard', query: { taskId: String(id) } })
    return await loadTask(preloaded)                            //    等详情 + 导出结果都加载完
  })()
  inFlightBinding = { taskId: id, promise }
  try { return await promise } finally { /* 只清自己那一次登记 */ }
}
```

- issue #1 的 `watch(() => route.query.taskId)` 现在只负责"从 query 推导目标 id"，随后调用同一个 `#applyTaskBinding`（:984-994）—— **两条触发路径共用一份实现**，不存在第二套任务切换逻辑。
- `#loadTask` 返回值从 `void` 改为 `{ taskOk, filesOk }`（:284），并支持 `preloaded`（跨任务门已经 `getTask` 过就不重复请求）；`#loadExistingResults` 从 `void` 改为 `boolean`（:323）。既有调用点（`onMounted`、`createAndBindTask`、`#refreshResults`）忽略返回值，行为不变。
- `#resetTaskScopedState`（:360）：清 `exportResults` / `checkedDefs` / `activeTab` / `loadedGrids`。对 issue #1 的 watch 路径同样生效 —— 这是**顺带变得更正确**的一点：换任务时不再短暂/失败后残留上一个任务的结果列表与表格缓存（数据丢失面见 §6 风险 1）。

### 3.3 跨任务门：三类失败互不相同（对 AI 可行动）

## 6. 遗留与风险

1. **换任务时的页面态清理对 issue #1 路径也生效（刻意的行为收紧）**：`#resetTaskScopedState` 在 watch 改绑时同样会清空 `exportResults`/表格缓存。方向上更正确（否则换任务后编辑器里是上一个任务的字节），但若有 E2E 断言"改绑后旧结果仍在页面上"，会看到差异。判定依据：旧结果属于**另一个任务**，保留它就是本 issue 的同源错误。若产品坚持"改绑瞬时保留旧结果"，把 `resetTaskScopedState()` 从 `#applyTaskBinding` 移到两个执行器的调用点即可（一处改）。
   **数据丢失面（红队 R2，v2 补披露 + 已缓解）**：清 `loadedGrids` 会连带丢弃**用户尚未保存的在线编辑**（`gridDirty=true` 时那批改动只存在于浏览器表格实例里）。这不是理论风险：`download`/`open` 的风险级是 **READ**，一次 AI 调用即可触发换任务 ⇒ 读操作造成数据丢失，超出其风险授权面【红队实测代码走查 + 本批探针复现：切换前 `gridDirty` 已置位（`recentActions` 有「导出结果表格内容已修改」），切换后无任何提示】。**本批最小修复**：切换前 `ElMessage.warning` 显式提醒（不阻断，见 §3.2b R2）。**仍存在的残余**：提醒只是"事后告知"，未保存内容**依然会丢失**（没有自动保存、没有"先保存再切"的强制路径）。是否要做成阻断/自动保存，见 §9 待裁决。
2. **`run_job` 的 taskId 只用于建作业、不切绑定**（§5）：AI 可对"未显示的任务"起作业，页面照旧显示当前任务。不同构、本次未动，建议单独登记裁决。
3. **失败文案仍走"执行失败：…。请提示用户手动重试。"的通用包装**：本次让三类失败都落到 `ok=false/availability=degraded`（AI 面板显示失败卡，不再谎报成功），但包装后缀"请提示用户手动重试"对"任务号错了"并不贴切（应核对任务号）。改这句需要动 `frontend-tools.ts` 的通用错误包装（影响所有前端工具），**未做**，登记为观察项。
4. **跨任务 open 会把目标任务推进一步**：`open` 成功分支里 `if (stepIndex !== 2) goStep(2)` 是既有逻辑，绑定到新任务后它打在新任务上（`PUT /tasks/{id}/step` + `persistStepData`），即"AI 让我看任务 1 的导出文件"会顺带把任务 1 推到 EXPORT 步。这与用户手点"导出配置"步等价，且是改动前就有的行为，本次只让它作用在**正确的任务**上；如需"只看不动"，需产品裁决。
5. **`loadTask` 仍无请求序号守卫**（issue #1 红队 S3 遗留 = 本批 R5）：本批新增 `inFlightBinding` 只解决"**同 id** 在途时动作先等它"，**不解决**"近并发两次改绑交错"（A 的 `loadTask` 可能晚于 B 落笔，写出混合态）。两条路径都收敛到 `#applyTaskBinding`、`router.replace` 同 query 不触发 watch，实测 12 个 v2 场景未见乱序；守卫仍**未做**（按裁决合并 issue #1 S3 排期）。
6. **跨任务调用比同任务多 3 个串行请求**（`GET /tasks/{id}` 探活 → `GET /tasks/{id}/files` → `GET /tasks/{id}/files/{code}`），且执行器**必须等它们回来**才能判定；后端慢时该工具调用的耗时随之上升（axios 单请求上限 60s，无额外超时兜底）。同任务路径零额外请求（实测 `newCalls=[]`），故日常路径不受影响。
7. **R2 的置零 `gridDirty`**（本批）：提醒后把 `gridDirty` 归零 —— 语义是"这批改动已被丢弃，不必再报一次"。副作用是：若用户在被丢弃前其实只想切走再切回（指望表格内容还在），不会再有第二次提醒（内容确实已经没了）。属于提醒语义的忠实实现，非缺陷。
8. **R3 的停表是"尽力而为"**：`stopWatchJob()` 停止轮询与 SSE，但如果旧作业的 `syncSnapshot` 回调**已经在途**，其 `onSnapshot/onFinal` 仍可能在改绑后落笔一次（把 `exportJob` 重新写回非空并触发 `refreshResults`）。本批未做"代际令牌"级别的收敛（与 R5 同族，属请求序号守卫范畴）；探针场景 N 实测 4.5s 窗口内未见回写。
