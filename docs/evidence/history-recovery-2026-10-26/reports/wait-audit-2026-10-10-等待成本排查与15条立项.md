## 2. 第 0 号案例（`download_export_file`）方案 A 落地要点

> 本节供后续施工卡直接引用。目标是"**即发即回**"：AI 侧只等那些**AI 真正需要、且失败即可确定未发生**的前置校验；浏览器下载链路的结局**不再回灌**。

### 2.1 执行体拆分点

执行体：`frontend/src/views/ExportWizardView.vue:981-999`（`registerFrontendToolExecutor('download_export_file', …)`）。

| 段 | 现态行号 | 处置 | 理由 |
|---|---|---|---|
| 参数校验（defCode 非空） | `:982-985` | **保留**（可下沉到 `frontend-tools.validateArgs` 的 FRONTEND_TOOLS 声明里，与其它工具统一） | AI 需要"参数错了"这一确定性失败 |
| 任务绑定闸门 `ensureTaskBoundForTool` | `:987-990` | **保留**（这才是 issue#2 修复的真实价值） | 绑定失败即确定未触发下载，可回灌确定性失败 |
| 结果存在性 `exportResults.some(...)` | `:991-993` | **保留** | 同上（`noResultMessage` 文案已可用） |
| `goStep(2)` 切页 | `:994-996` | **保留**（但同步失败面见 W-06/W-07） | 让用户看到下载发生的位置 |
| `await downloadOne(defCode)` | `:997` | **改即发即回**：换成 `startDownload(defCode)`（返回 promise，**不 await**），在 promise 上挂 `.then/.catch` 只更新页面态（`downloading` / `ElMessage`）与可选卡片态 | 浏览器下载链路耗时与结局 AI 都不消费 |
| 回灌文本 | `:998` | **改文案**（见 2.2） | 现文案"已触发下载…（在线编辑后的内容）"是对未来事件的断言 |

辅修 1：`downloadOne`（`:710-725`）改为返回结局 `type DownloadOutcome = { ok: true; fileName: string } | { ok: false; reason: string }`，**catch 分支 rethrow 或返回 `ok:false`**（去掉 W-02 的吞异常）；`Promise<void>` 的两个既有调用点（`:735` / `:759`）改 `const o = await downloadOne(...); if (!o.ok) …`（行为不变，仍 toast）。
辅修 2：把"前置校验"抽成纯函数 `preflightDownload(args): { ok: true; defCode } | { ok: false; message }`，执行器只调它 + 发下载 ⇒ 校验可被单测（配合 R-91 的前端测试框架裁决）。

### 2.2 ack 文案口径（生成式要点）

- **只陈述已发生的事**：任务号 + 配置编码 + "已发起下载"。
- **显式交代浏览器侧不确定性**：保存位置选择框 / 浏览器拦截 / 下载目录，落盘以浏览器为准。
- **明确禁止模型重试**：不要在 ack 里出现"若未成功请重试"这类暗示（避免重复触发同一文件）。
- 建议文本（可施工卡定稿）：
  > `已发起下载：任务 #<taskId> 的 <defCode> 导出文件（内容为在线编辑后的当前表格）。下载由浏览器执行 —— 若弹出保存位置选择框或提示被拦截，请让用户在浏览器侧放行并确认；文件落盘以浏览器下载目录为准。本次调用到此结束，无需重试。`
- 前置校验失败文本（确定性失败，保持既有口径）：`参数不合法…` / `任务 #N 无法加载…` / `任务 #N 里没有 <defCode> 的导出结果文件（该任务现有导出结果：…）` —— 三条均由 `frontend-tools.runRegisteredTool` / `:987-993` 现有分支产出，只需保证 `ok:false` 传递到卡片。

### 2.3 防重复触发

| 面 | 现状 | 方案 A 下的一致性 |
|---|---|---|
| 同一 `toolCallId` 重复回灌 | 后端幂等：`ConfirmGate#submitFrontendResult` 对非 PENDING 返回 `DUPLICATE` → `AiController.java:249-253` 409；前端 `stores/ai.ts:902-913` 按 409 收敛卡片 | 不变（仍有效） |
| 同一帧重复投递（reattach 回放） | 前端 `hasDecidedPendingResidue`（`stores/ai.ts:935-940`）挡住"已决 toolCallId 再挂起" | 不变 |
| **执行器被连点/重复调用** | 现由 `downloading` 单值挡住并发（`:715`） | 即发即回后**必须补**：① `downloading` 保留，且在途时 ack 改为"该文件的下载已在进行中，请勿重复触发"；② 模块级 `Set<string>`（在途 defCode）防"同 defCode 的两次工具调用"；③ ack 文案不含失败/重试暗示（2.2） |
| 迟到结局想二次回灌 | **无通道**：`ConfirmGate#submitFrontendResult` 对已决条目一律 `DUPLICATE`（`:448-450`）→ 409 幂等丢弃；设计上"结局帧为最终裁决" | **本批不新增二次回灌通道**（会牵动 pendingCall 终态单调性、409 语义与跨进程快照）。迟到结局只体现在**用户侧**（`ElMessage` / `downloading` 复位），AI 侧保持"已发起"语义。若日后要回灌迟到结局，须新立"post-hoc 结局帧"议题 |

### 2.4 卡片状态档位建议

现档位（`types/ai.ts` 的 `ToolRun.status`，前端 `stores/ai.ts:1231-1241` 写入）：`running / succeeded / failed / rejected / blocked / expired`。

- **最小改动档位方案**：不新增档位。
  - 前置校验失败 ⇒ `failed`（文案即原因）；
  - 已发起 ⇒ `succeeded`，但**卡片文案**必须写"已发起下载（浏览器侧结局不回传）"。为避免"已成功"三个字误导，可把该工具的 `ToolRun.reason` 或卡面标签特例化为"已发起"。
- **推荐档位方案（供施工卡裁决）**：新增一个语义精确的展示态 `started`（"已发起，结局由浏览器决定"），由 `executeFrontendTool`/`runRegisteredTool` 的结局结构承载（例如 `availability` 已有 `available|degraded|unavailable`，可再加"副作用已提交、结局未知"的结局类型）。
  - `started`：一切前置校验通过、下载已发起；
  - `failed`：前置校验失败（参数/绑定/结果缺失）或 `buildXlsx`/`toXlsxBlob` 同步失败（**这些在执行器返回前就已确定**）；
  - `unknown`：仅在保留"等回灌"的兼容档位下才可能出现（方案 A 落地后该类不再产生）。
- 与既有 R-84 的衔接：R-84 已立项"补『结局未知』卡片态"，本节的 `started`/`unknown` 建议**并入 R-84 的落点**，避免两次设计。

### 2.5 与后端 120s 挂起键的配套（方案 A 的必要收尾）

- 即发即回后，`download_export_file` 的后端等待只剩"回灌 POST 到达"（正常 <1s；实测自动化 Chromium 25~41ms —— 【旁证】`docs/M2-排期计划.md` R-93）。120s 对下载工具不再承载真实语义，只剩"前端整体崩掉"的兜底。
- 因此建议（两选一，属**配置与文案**面）：
  - **文案改实**：`ConfirmGate.java:298-300` 的前端超时文本"…未在 N 秒内回传执行结果（前端超时），本次调用未获得数据"中的"未获得数据"是**误导**（本工具即发即回后根本没有"要获得的数据"）；改为"未在 N 秒内收到前端回执，本次调用**结局未知**（不表示未发生）"。
  - **键拆分（建议）**：`app.ai.hitl.timeout` 现同时供"确认门"（等人点）与"前端工具挂起"（等回灌）使用 —— 场景不同（人的决策延迟 vs 机器回执延迟），建议拆出 `app.ai.hitl.frontend-tool-timeout`（默认远小于 120s，如 30~60s），并把前端预算折算 `deriveFrontendToolBudgetMs` 的输入改为该键随帧下发（前端已按帧 `timeoutSeconds` 折算，故只需后端改下发源）。该拆分是 §3 标出的"一刀切共用"键的第一处落地。
