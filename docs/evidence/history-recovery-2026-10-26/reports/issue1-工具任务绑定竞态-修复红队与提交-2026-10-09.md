### 2.2 【实测】复现矩阵（真实前端，非静态走查）

环境：`vite@6.4.4` dev server + 真实 `vue@3.5.43` / `vue-router@4.6.4` / `pinia@2.3.1` + 真实 `EXPORT_WIZARD`/`workspace`/`frontend-tools` 代码路径；用临时探针页在页面内调 `executeFrontendTool(...)`（探针已删，源码存档见 §4.2）。
**说明**：本机未启动后端，`/api/*` 全部 ECONNREFUSED（向导页只显示"后端服务不可用"的提示），但本 issue 的对象是**前端工作区状态机**（`workspace.taskId` 的绑定时序），不依赖后端数据。

| 场景 | 起点状态 | `navigate_to(export, taskId=1)` 结果 | 随后 `select_definitions(CURRENCY)` |
| --- | --- | --- | --- |
| A 控制组：从任务中心进入 | `/tasks`，向导未挂载 | ok=true，`workspace.taskId` **=1**（挂载即绑定） | **ok=true**（一次成功） |
| B issue 现场：向导已挂载但无任务 | `/export`（无 taskId），页面就绪、handler 已注册、`taskId=null` | ok=true，文案"…**（页面已就绪，可继续执行本页动作）**"，**`workspace.taskId` 仍为 null**（URL 已变 `/export?taskId=1`） | **ok=false / unavailable**：「选择配置项需要绑定任务：当前没有进行中的任务，请先在任务中心创建或打开一条任务。」 |

场景 B 即 issue 原文现象（文案完全一致）。补充实测：

- 【实测】场景 B 之后手工补一次绑定（探针里 `workspace.setTaskId(1)`，等价于用户点了向导空状态里的「创建导出任务并进入」或刷新页面），**同一条 `select_definitions` 立刻成功**——这就是 issue 里"第 3 次重试才成功"的解释：不是重试等到了绑定，而是**绑定被另一条路径（空状态建任务/刷新/重进）补上了**。
- 【实测】场景 B 的页面此时显示空状态"尚未绑定任务 / 创建导出任务并进入"，而地址栏已是 `/export?taskId=1`——**URL 与工作区状态自相矛盾**，是"`restore_task` 只改 query"的直接证据。

### 2.3 根因结论（以实际代码为准）

> **真实触发条件**：`restore_task` 只做 `router.push({name, query:{taskId}})`。当目标向导页**已经挂载**时（用户先点过顶栏「导出向导」，或上一轮 AI 调过不带 taskId 的 `navigate_to(export)`），同一条路由记录下的组件**不会重建**，`onMounted` 不再执行，而视图**没有** `route.query.taskId` 的 watcher ⇒ `workspace.taskId` 永远是 null。
> 此时 `waitForPageReady` 的判据（页面 id + handler）**早已满足**，于是 `navigate_to` 立刻回灌"页面已就绪"的**假成功**，紧随的 `select_definitions` 被 `needsTask` 判成"当前没有进行中的任务"。
>
> issue 的"现象/文案/复现率"100% 属实，但机制需修正为：**不是"绑定还没完成"，而是"绑定根本没被触发，且没有任何一方会发现"**。因此只做 issue 建议的"等待绑定"一半并不够——在场景 B 里等满 3 秒也不会绑上；必须同时让视图跟随 query 补绑定。

### 2.4 为什么"只加等待"不能单独修复

`waitForTaskBound` 单独上线时，场景 B 的结局是：等 3s → 页面就绪但未绑定 → 明确降级（比假成功好，但 issue 的业务目标"navigate_to 成功后 select_definitions 第一次即成功"仍不成立）。故本次实现两半同时落地（§3）。

### 3.2 `frontend-tools.ts`：完成判据升级为"页面就绪 **且** 任务已绑定"

```ts
/** "页面就绪 + 任务绑定"两个维度的等待结局（两维分开返回，供调用方给出不同的回灌文案）。 */
export interface TaskBindWaitResult {
  pageReady: boolean   // 页面 id 匹配且该页能力 handler 已注册
  taskBound: boolean   // workspace.taskId === expectedTaskId
}

// 超时口径与 waitForPageReady 完全一致：默认 PAGE_READY_TIMEOUT_MS(3000ms)、轮询 50ms、到点即返回
export async function waitForTaskBound(
  page: WorkspacePageId, expectedTaskId: number, timeoutMs = PAGE_READY_TIMEOUT_MS
): Promise<TaskBindWaitResult> { /* pageReady && taskBound 才提前返回；否则到 deadline 返回两维现状 */ }
```

`navigate_to` 的动作表新增 `bindsTask`，并把"该带哪个 taskId 才算恢复向导"的判定收敛到一份 `resolveNavigateIntent`，供 `toUiEvent`/`navigatesTo`/`bindsTask` 共用（避免事件映射与完成判据两份判断漂移）。原行为逐条保持：带 taskId 且目标为 export/import ⇒ `restore_task`；否则 ⇒ `open_page`；page 非法 ⇒ null。

`runWorkspaceAction` 的回灌分支（四结局）：

| 等待结局 | 回灌 | 说明 |
| --- | --- | --- |
| 页面就绪 + 任务已绑定 | `ok:true / available`，`…（页面已就绪，任务 #N 已绑定，可继续执行本页动作）` | 新的成功口径 |
| 页面就绪、任务未绑定 | `ok:false / degraded`，`…，但任务 #N 的绑定没有完成（向导页已就绪，未绑定该任务）。请核对任务 #N 是否存在，或提示用户手动在任务中心打开该任务后重试。` | **失败出口**：页面都就绪了还没绑上 ⇒ 不是"还在加载"，再等也不会变，明确降级、不谎报成功 |

### 3.3 视图侧：跟随 `route.query.taskId` 补绑定（真正的修复点）

两个向导视图各加一个 watcher（`ExportWizardView.vue:791-812`、`ImportWizardView.vue:993-1012`）：

```ts
watch(
  () => route.query.taskId,
  async (raw) => {
    const parsed = Number(raw)
    const id = Number.isFinite(parsed) && parsed > 0 ? parsed : null
    if (id === null || id === taskId.value) return   // query 变成无 taskId 时不动绑定（见下）
    taskId.value = id
    workspace.setTaskId(id, 'EXPORT', null)          // 与 onMounted 同序：先同步绑定
    await loadTask()                                 // 再拉详情（慢/失败时向导自己的空/错误态照旧）
  }
)
```

设计取舍：

- **先同步绑定**再拉 `/tasks/{id}`：AI 侧的等待判据因此立刻成立，不被详情请求的耗时/失败拖住（与 `onMounted` 里 `enterPage` 先于 `loadTask` 的既有顺序一致）。
- **query 变为无 taskId 时不动绑定**：顶栏「导出向导」菜单项 `push({name: export-wizard})` 不带 query，若把它当作"解绑"，用户在同页点导航反而会丢掉已打开的任务——这是本次刻意不做的事（保持既有行为），已在注释里写明。
- 只处理"正整数 id 且与当前不同"的变化，幂等、无回环（watcher 不写 route）。
