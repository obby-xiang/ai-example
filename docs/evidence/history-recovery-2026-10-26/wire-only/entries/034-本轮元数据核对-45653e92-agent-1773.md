## 三、特别检查结论

**1）转义无碰撞：成立。**
映射是单射：`%` 全部变成 `%25`，输出里的 `%` 只可能是转义起始，故解码唯一；`{`/`}` 不再出现在转义结果里 ⇒ tag = escapedId 恒非空 ⇒ final/staging tag 逐字相同。独立复算 CRC16 亦证实（`}x` → 两键同槽，round0 的 11550/9833 反例已消失）。测试覆盖 `}x/x}y/{a}b/%{x}%/a%b` 与 `{a}b ≠ %7Ba%7Db`。
仅一处命名空间级注意（Minor-9）：legacy 用**原始 id**，当旧版本曾接受 `{` 开头的敌意 id 时，`chat:mem:{x}` 既是 id `{x}` 的 legacy 键、也是 id `x` 的 tagged 键 —— 转义本身无碰撞，这是新旧键形重叠，仅旧键、仅敌意 id 可构造。

**2）索引旧成员不被误清：成立。**
`hasLiveMemory` = tagged 或 legacy 存活（`:233-236`）；`findConversationIds` 只在两者都不在时清（真实 Redis 上已验证 legacy 存活不被 SREM）。更强的性质也成立：保存路径上 **任意时刻至少一个键存在**（legacy 在 RENAME 成功后才删，tagged 始终由 RENAME 原子替换），所以惰性清理不会误杀活会话。唯一残留是已登记的 SADD/SREM 窄竞态（下次保存自愈）。

**3）RENAME 后 TTL 与失败窗口：正确，且比 round0 更严。**
TTL 由同一脚本 `PEXPIRE` 设到 staging，RENAME 继承；fake 精确断言、真 Redis 区间断言。失败窗口穷举：脚本失败 → finally 清 staging、旧 final 不动；RENAME 失败 → 同上；成功但响应丢失 → 数据已提交、跳过 legacy 清理与 SADD（索引自愈）。**未发现新的丢旧历史路径。**

**4）新数据丢失路径：未发现。** 新增的是三个“非丢失”边界态：
- 删除第二条 DEL（legacy）抛错时，tagged 已删、legacy 仍在 → 接口 500 但旧历史可经回退读到（迁移期、有 legacy 时；重试收敛）；
- legacy 若**无 TTL**（非旧版本正常写入形态）且 tagged 先过期，旧历史会复活；
- 脚本中途失败（如 OOM）时 Redis 不回滚，可能留下“已 RPUSH、未 PEXPIRE”的 staging（仅当 finally DEL 也失败才成永久孤儿）——替身把 `failExpire` 建模成“无数据”，比真语义乐观。

## 五、Important（1 项，含修法）

- **I-7 迁移期的“混合版本滚动发布”会历史分叉（发布门禁，非代码缺陷）。**
  旧版本只读 `chat:mem:<raw id>`，新版本优先 tagged 并**会删除 legacy**。滚动发布期间旧 pod 的写只落 legacy、且被新 pod 的下一次保存删掉；同一会话在两个 pod 间来回会看到两份互不可见的历史，最终态取决于最后写入者。legacy 回退只解决“新读旧”，不解决“旧写新”。
  **修法（选其一，均为发布流程）**：①对新写路径做整体切换（停旧实例→起新实例），禁止新旧混跑；②若必须分批，先在旧版本侧加双写（需要单独发版），否则不可滚动；③上线前用旧键清单做一次性 `saveAll` 迁移并停旧写。建议在发布清单里固定，并加一条启动/巡检 WARN（legacy 键数量）辅助确认切换完成。

## 六、Minor（单列，不阻断）

1. **SREM 失败 / legacy DEL 失败两条 WARN 分支无测试**：`FakeMemoryRedis` 没有 `failIndexRemove`；`failDelete=true` 会同时打掉 staging 清理，测不到 `deleteLegacyQuietly`。建议加 `failIndexRemove` + 两条用例（删除仍返回、WARN 含 cid）。
2. 生产常量 `STAGE_WRITE_MARK`（`:105`）无人引用（替身自带一份），属死代码；删除或注明仅供替身约定。
3. 注释漂移：`AiControllerHistoryDeleteTest` 的 F4 javadoc 仍写“删除只做单键 DEL、stale 由 findConversationIds 惰性清理”“两次单键往返”（实际 DEL+SREM、最多 3 次往返）；`AiController:1217/1320` 同样过期 —— 主会话修 `memoryKey` 时一并改。
4. **TTL 过期产生的索引成员仍无人清理**（生产仍无 `findConversationIds` 调用者），报告“避免无界增长”只对**删除路径**成立；建议加定时对账，或把措辞改为“删除路径不再增长”。
5. 删除两条 DEL 的顺序：建议 **legacy 先、tagged 后**，可把“500 但旧历史经回退复活”的迁移期窗口消掉（当前测试锁的是 tagged 先，需同步改断言）。
6. legacy 无 TTL + tagged 先过期 → 旧历史复活；建议迁移期给 legacy 补一次 `EXPIRE` 或一次性清理。
7. `STAGE_WRITE` 的保证应限定为“脚本执行完成即带 TTL”（中途报错不回滚）；建议注释收敛，避免“任何失败都无孤儿”的过度承诺。
8. `findByConversationId` 对空会话多一次 legacy `LRANGE`（每会话首轮多 1 次往返），可接受，建议注释说明。
9. legacy（原始 id）与 tagged（转义 id）命名空间在“旧 id 以 `{` 开头”时逐字重叠；建议迁移时跳过/清理“看起来像 tagged”的 legacy 键（`raw id` 含 `{`/`}`）。
10. 证据：RED 用的是较早测试修订，“同套件 RED”措辞宜放宽；真 Redis 迁移用例在 DB9 写了**无 TTL 的 legacy 键**，若用例中断会残留（仅测试库）。
11. `stagingTtlMillis` 对毫秒级 TTL（如 1ms）会让 RENAME 概率失败；V-c2 类实验需保证 TTL ≫ RTT。
12. 第 5 项遗留（未改，已按要求留后续）：`ResilientChatService` 的 `clear()+add()`、`AiController.memoryKey`（现在还需使用 `keyFor` 才含转义）、文档漂移；另外 `AiController` 的 `removedFromIndex` 注释仍写“单次 SISMEMBER”。
