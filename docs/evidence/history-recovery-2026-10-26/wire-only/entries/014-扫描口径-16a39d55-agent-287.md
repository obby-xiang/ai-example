## 4. `onerror` / `onmessage` / `onAbort` 与 `connectTimer` 的交互

- **`onerror`（`#571-583`）**：建连期（尚未 `onopen`）触发时 `connectTimer` **仍处武装态**（由 `open#555` 武装）。执行 `source?.close()` + `source = null`（580-581）→ `scheduleReconnect('重挂连接中断')` → `clearIdle#528` + `clearConnect#529`，随后或 `settle`（耗尽/已 abort，535/531）或经退避 `600`… 即 `#542` 重新武装。**onerror 的所有出口返回时 `connectTimer` 必为 null。** 唯一早退分支 `if (settled) return`（572-574）与"timer 已武装"不共存（settle 必清）。`state.terminal` 分支（575-579）走 `settle(true)` 亦清。
- **`onmessage`（`#560-570`）**：首句 `startIdle()`（561 → 481-494）先执行 `clearConnect#484`，故任何帧（含心跳）到达都会让建连看门狗让位，重启帧间看门狗；终帧再走 `settle`（567-569）。⇒ 帧到达时不存在"`connectTimer` 仍武装"的窗口。
- **`onAbort`（`#477-479`）**：`settle` → `clearConnect#470`；监听器在 `open()` 之前注册（`#590` `{once:true}`），预检在 `#586-589`。**若 Promise 因第 2 节 a 中两处异常序列悬挂，`#473` 的 `removeEventListener` 永不执行 ⇒ abort 监听器残留**（`once:true` 保证最多触发一次）。
- **附带顺序事实（`onopen`）**：`#556-559` 先 `handlers.onOpen?.()`（557）再 `startIdle()`（558）。若 `onOpen` 抛错，`startIdle` 不执行 ⇒ `connectTimer` 不被清除，15s 后触发并 `close()` 掉已建立的 source → `scheduleReconnect`。仓内无 `onOpen` 传入点（grep 只命中 `sse.ts:62/364/557`），当前不可达，但顺序事实成立。
