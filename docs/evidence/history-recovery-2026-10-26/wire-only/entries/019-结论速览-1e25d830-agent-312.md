- 对话界面只有一个组件：`frontend/src/components/AiPanel/AiPanel.vue`（右侧栏，`App.vue:34` 挂载）。没有任务执行视图内的第二套消息渲染。

**「拆开」的三处具体形态**

1. **正文永远在最上、工具卡永远在最下**：模板自上而下是 content → toolRuns → pendingCall，与 seq 顺序无关。模型如果「先工具、后正文」，渲染仍是「正文在上、工具卡在下」。
2. **同一个 toolCallId 渲染两张卡**：store 在 `confirm_request`（`stores/ai.ts:1244-1256`：`:1246` 写 `pendingCall`，`:1248-1254` 同时 `upsertToolRun(status:'pending')`）、`frontend_tool_request`（`:1282-1300`）、`suspended`（`:1337-1359`）三处都同时写两个投影 → 模板 `:151` 出一张工具卡、`:169` 又出一张挂起卡。
3. **挂起卡是单槽位、可被覆盖**：`ChatMessage.pendingCall: PendingToolCall | null`（`types/ai.ts:190`），同一条宿主消息上后续的 `confirm_request` 直接赋值覆盖（`:1246`、`:1290`、`:1349`）；`suspended` 帧里一批多个待决条目时只投影**第一个** CONFIRM/FRONTEND（`:1341-1357`）。宿主消息 = 本轮唯一那条 assistant 消息（`handleFrame(frame, assistant.id)`，`:1158-1166`）。

数据源链路：`ai.messages` ← SSE 帧 → `stores/ai.ts handleFrame`（`:1151-1399`）→ `AiPanel.vue` 模板。

## 4. 后端 SSE 事件流：类型清单与时序语义

### 4.1 事件类型
`frontend/src/types/sse.ts:59-75`（后端 15 类实测白名单，顺序即后端产出语义）：
`start, message_start, delta, message_end, tool_start, tool_result, confirm_request, confirm_decision, frontend_tool_request, frontend_tool_result, suspended, heartbeat, retry, done, error`
另有前向兼容 `reasoning`（`:80`、`:242-247`；后端当前不产出）。

### 4.2 时序字段（关键）
`SseFrameBase`（`types/sse.ts:82-98`）：
- **`seq?: number`** —— 单调业务序号，自 1 起、跨进程续号；心跳走独立 `heartbeatSeq` 不占业务号。后端：`SseChatEmitter#nextSeq`（`SseChatEmitter.java:700-720`），续号锚点 = `max(归档末帧, ai:seq:<runId>)`（`:704`），发放即登记 `RunStore#recordIssuedSeq`（`RunStore.java:624-632`）。
- **`atMs?: number`** —— 帧的**服务端构造时刻**（epoch ms）。**实时帧与归档帧同值**（T4-3 后半，即你提到的「atMs 前移帧构造」）：赋值点在帧构造器 `SseChatEmitter#frame`（`SseChatEmitter.java:677-682`，`frame.put("atMs", System.currentTimeMillis())`），`RunStore#appendEvent` 的 `putIfAbsent` 退化为兜底（`RunStore.java:573-592`，注释 `:561-564`）。相关提交：`727c503 feat(backend): 实时 SSE 帧 atMs 前移帧构造点，expiresAt 同钟取值`。
- 挂起类帧的 `expiresAt` 与同帧 `atMs` 同钟单点取值 ⇒ `expiresAt - atMs ≡ timeoutSeconds*1000`（`SseChatEmitter#expiresAtEpochMs` `:1067-1071`）。
- 消息身份：delta / message_* 带 `messageId = "assistant-" + runId`（`:199-200`、`:485-490`、`:505-513`）；工具帧带 `messageId = "tool-" + toolCallId`（`:1074-1076`）。

### 4.3 单流还是多流
**一条流、一个 emitter、多线程出帧**：
- `RunRegistry` 按 `runId` 一 emitter（`RunRegistry.java:84-89`），SseChatEmitter 内部多订阅者扇出（`SseChatEmitter#attach` `:313-315`、`emit` `:722-782`）。
- 出帧线程不唯一：运行线程（delta/start/done/error/heartbeat）、HTTP 线程（`ConfirmGate#submitDecision` `:413` → `confirm_decision`；`#submitFrontendResult` `:467`/`:502` → `frontend_tool_result`）、闸门等待线程（`ConfirmGate#await` `:198` `confirm_request`、`:201` `frontend_tool_request`、`:234` heartbeat）、工具循环线程（`SpToolCallingManager` `:163 suspended`、`:170 tool_start`、`:242/:318/:339/:351/:381 tool_result`）。
- **到达顺序 = seq 顺序**由 `emitLock` 保证（取号 → 落档 → 入队同一把锁，`SseChatEmitter.java:183-197`、`:726-781`）。心跳不占业务号、不落归档（`:731-746`）。

### 4.4 一轮内的产出顺序（生产代码路径）
`ResilientChatService#chat`（`:187-237`）：`out.start(sessionId)`（`:209`）→ `runAttempts`（`:287-370`）内 `consume`（`:613-631`：非空文本即 `out.textStart()` + `out.delta(text)`，`:627-630`）→ 工具调用由 Spring AI 官方循环内的 `SpToolCallingManager#executeToolCalls`（`:141-206`）处理：`saveSuspended` + `out.suspended`（`:162-163`）→ 逐条 `out.toolStart`（`:170`）→ 三分支结局帧（越 scope `:242`；前端通道结局在 `ConfirmGate` `:467`/`:502`；确认门 `:318`；后端执行 `:381`）→ 回填模型继续循环 → 终局 `out.textEnd + out.done/error`（`finish :477-478`、`emptyReply :510-511`、`cancelTerminal :541-542`、`fail :568-569`）。

**关键限制**：`textStart()` 由 `textSegmentOpen` CAS 幂等守卫（`SseChatEmitter.java:203`、`:516-522`），**一轮只发一对 message_start/message_end**。也就是说：
- 协议层**确实**保留了「delta 帧 vs 工具帧」的相对先后（靠 seq，`:627-630` 与 `SpToolCallingManager` 各帧的取号顺序，工具之后的模型续跳文本同样走同一 `consume`，见 `ResilientChatService` 的注释 `:613-631`）；
- 但**没有**「正文段 N / 正文段 N+1」的段边界，正文交错只能由帧序列本身表达。

## 6. 时序数据可得性结论

**能支撑严格时序合并的部分**
- 同一 run 内：`seq` 是全序（严格递增、无缺口、锁内取号，conformance 断言见 `backend/src/test/java/com/example/configmgr/ai/conformance/FrameContract.java:105-122`「仅业务帧占号」），且**每帧**带 `atMs`（毫秒，服务端单钟）。文本、工具、HITL 三类帧**在同一条流、同一个 emitter** 上产出（`SseChatEmitter`），因此「按 seq/atMs 合并输出与 tool/HITL」在协议层具备充分数据。
- 服务端还有独立的因果序不变量可复用：`FrameContract#orderingContract`（`:318-374`，`suspended < tool_start`、`confirm_request < confirm_decision < tool_result`、`frontend_tool_request < frontend_tool_result`）。
- 持久化侧：`ai:events` 保留了每帧 `seq/atMs`（放回放可用）、`ai:pending`/`ai:ledger` 保留毫秒时刻、历史消息保留 ISO `timestamp`。

**缺口（按严格时序合并展示所需的「全序键」逐条列）**
1. **前端消息模型没有任何时间/顺序字段**：`ChatMessage`/`ToolRun`/`PendingToolCall` 都无 `timestamp`/`seq`/`order`（`types/ai.ts:164-226`），镜像同样不带（`:229-234`）。要按时序合并，合并键在当前前端模型里**不存在**。
2. **到达即丢序**：`delta` 被拼进单一字符串 `content`（`stores/ai.ts:1205`），工具帧进独立数组 `toolRuns`（`:1213`、`:1468-1478`），挂起帧再进单槽 `pendingCall`（`:1246`/`:1290`/`:1349`）。帧一旦被 handler 处理即无留存，`seq` 只保 max 值（`:1168-1175`）。**同一条消息的正文与工具卡的相对先后在前端已不可恢复**。
3. **协议层没有正文段边界**：`textStart/textEnd` 由 CAS 保证一轮只一对（`SseChatEmitter.java:203`、`:516-531`），`message_start/message_end` 无法把「工具前的正文」与「工具后的正文」分成两个可排序的段；只能靠 delta 与工具帧各自 seq 的先后。
4. **服务端不持久化 delta**：`RunStore#appendEvent` 对 `delta`/`heartbeat` 直接 `return`（`:574-581`，T3-2）。后果：**任何既往轮次的「正文 vs 工具」交错在服务端无法重建**；且 `stageReplay` 也跳过 delta（`SseChatEmitter.java:441-443`）。回放只提供状态帧骨架。
5. **历史（chat:mem）粒度不足**：每轮正文被合并为**一条** assistant 消息、且**在 `finish` 时才追加以致排在所有工具消息之后**（`ResilientChatService.java:447-478`）；`tool` 消息与 `assistant(tool_calls)` 成对但无轮内偏移；前端 `loadHistory` 还丢弃 `timestamp`（`stores/ai.ts:454-474`），并把 `TOOL` 条目渲染为空助手气泡。
6. **`pendingCall` 单槽位**导致 HITL 与工具卡对同一 toolCallId 双渲染、且多个挂起互相覆盖（`stores/ai.ts:1246/1290/1349`，模板 `AiPanel.vue:151` 与 `:169`），这是当前「拆开」的直接成因之一。
7. **精度/host 归属**：`atMs` 是「帧构造时刻」，不是「用户可见事件时刻」（例如 confirm_decision 在 HTTP 线程构造、`suspended` 在工具批次开始时构造）；同一批次多个 `tool_start` 的 `atMs` 可能同毫秒，需靠 `seq` 定序——而 `seq` 在**前端不保留**。此外 `atMs`/`seq` 均为**可选字段**（旧格式帧/损坏数据缺失，`types/sse.ts:89-97`、`frameSeq` `:323-326`），合并逻辑必须设计缺失兜底。
