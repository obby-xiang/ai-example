### Important 1：检查与级联不是原子的，建作业并发仍可绕过守卫

证据：

- 删除侧先读作业（`TaskService.java:352`），再级联（`:375-383`）；两步之间没有任务行锁，`TaskRepository` 也没有 `findByIdForUpdate`（`TaskRepository.java:12`）。
- 建作业侧先检查任务/在途（`JobService.java:153-156`），再插入 PENDING 作业（`:158-162`）；同样没有任务行锁。
- 全表没有外键，`jobs.task_id` 只是普通列。

后果：

- 新作业在删除“读作业”之后、“deleteByTaskId”之前提交：会被一并删掉，但创建方已拿到 201，执行器随后可能对已删任务运行。
- 新作业在 `deleteByTaskId` 之后提交：留下孤儿 PENDING 作业，执行器可能继续写。
- 这正是 R1-13 要消除的孤儿数据类别，只是窗口比“删除时已有 RUNNING 作业”窄。

最小修法：

- 给 `TaskRepository` 增加 `@Lock(PESSIMISTIC_WRITE)` 的 `findByIdForUpdate`；在 `TaskService.delete` 和 `JobService.createAndStart` 都先锁同一 task 行，再读取/插入并保持到事务提交。这样两者串行：先建作业则删除看到 PENDING 返回 409；先删除则建作业拿到 404。
- 注意锁顺序：`JobTerminalWriter` 当前是“先条件更新 job 行，再 `applyJobOutcome` 更新 task 行”（`JobTerminalWriter.java:103-110`），与“task → job”的删除锁顺序相反，直接加锁可能引入死锁。需要让终态写入/僵尸恢复等任务态写路径也统一先锁 task，或改用统一的 task 级互斥方案；仅加半边锁不够。
- 加一个真正的并发测试（两线程/两事务 + CountDownLatch），验证“建作业与删除只有一方成功”，不要只靠顺序测试。

### Important 2：`CANCELLED` 并不等于执行器已停止，取消后立即删除仍会产生孤儿

证据：

- 代码注释称“CANCELLED 已落终态，执行器残余收尾不再回写业务数据”（`TaskService.java:345`），与 runner 实际行为不符。
- `ImportJobRunner` 在取消分支 `break` 后，仍会执行 `if (!stagingBatch.isEmpty()) stagingRowRepository.saveAll(...)`（`ImportJobRunner.java:157-164`）。
- `ExportJobRunner` 在最后一次取消检查之后仍会 `excelWriter.write`、`taskFileRepository.save`、`updateItemStatus`（`ExportJobRunner.java:170-192`）。
- `JobService.cancel` 只是把 job 条件更新为 CANCELLED 并提交（`JobService.java:365-384`），runner 的长事务仍在继续；删除侧看到 CANCELLED 就放行，runner 之后提交的 `task_files`/`config_staging_rows`/`validation_issues` 没有外键兜底，成为孤儿。
- 新测试的 CANCELLED 用例只是静态 seed 一个 CANCELLED 作业（`TaskDeleteInFlightGuardTest.java:101-119`），没有复现“取消提交后 runner 仍在写”的真实窗口。

结论：按“CANCELLED 即终态、可删”的产品口径，这是状态语义的必然残余；但如果验收目标是“删除后不产生孤儿数据”，本批没有关闭它。任务行锁也修不了，因为 runner 不持 task 行锁。

可选修法：

- 若允许改变“终态立即可删”的语义：给每个 job 增加 runner 停止/静默确认（DB 列或 Redis ack），只有确认后才允许删除 CANCELLED；删除时可短暂 409/重试。
- 若坚持“终态立即可删”：给 `task_files.task_id`、`config_staging_rows.task_id`、`validation_issues.job_id` 等加 FK（`ON DELETE CASCADE`），并补孤儿文件清理；runner 的迟到插入会因 FK 失败回滚，不再落孤儿行。迁移前要先清历史孤儿数据。
- 至少先修正 `TaskService.java:345` 的注释和报告“不再回写业务数据”的结论，避免把已知残余说成已解决；并补一个取消与删除交错的并发测试。

### Important 3（既有、非本批引入）：英文 API 实际仍回中文

报告的方向判断正确，我独立确认了机制：

- Spring Boot 3.5.14 的 `MessageSourceAutoConfiguration.ResourceBundleCondition` 只检查 `classpath*:messages.properties`（v3.5.14 源码 `getResources` 拼接 `target + ".properties"`），不是按 `Locale` 找 `messages_*.properties`。
- 本仓 `spring.messages.basename=messages`（`application.yml:19-26`），但只有 `messages_zh.properties`、`messages_en.properties`，没有基座 `messages.properties`，因此自动配置不启用；上下文里的 `MessageSource` 是 `DelegatingMessageSource`。
- `ErrorBodyFactory.message` 在非中文 locale 下查不到 `error.JOB_ALREADY_RUNNING`，回落调用方原文（`ErrorBodyFactory.java:58-67`）。所以真实 `Accept-Language: en-US` 的 409 会返回中文详细文案，而不是 `The job is already running`；`code`/HTTP 状态仍正确。
- 新测试 `errorCodeHasChineseAndEnglishMessages` 直接 new `ResourceBundleMessageSource`（`TaskDeleteInFlightGuardTest.java:128-137`），它能找到 `messages_en`，所以 6/6 通过；这恰好绕开了应用上下文，不能证明英文 API 生效。报告里“英文资源层测试通过”是事实，但“英文 API 通过”不成立。

正确最小修法（不在这批直接改）：

- 增加 `backend/src/main/resources/messages.properties` 基座文件（空文件/仅注释即可；也可复制 `messages_en` 作为默认英文）。这样 Boot 3.5 的条件匹配，`ResourceBundleMessageSource` 生成，en 查 `messages_en`，zh 继续短路用原文；`messages_zh/en` 的键集契约不变。
- 或者显式声明 `MessageSource` Bean（`ResourceBundleMessageSource`，basenames=`messages`，UTF-8，`fallbackToSystemLocale=false`），避免依赖自动配置；但要把 `application.yml` 的 encoding/cache 等设置一并复制，代码量比加基座文件大。
- 补一个 HTTP 级测试：MockMvc `DELETE /api/tasks/{id}` + `Accept-Language: en-US`，断言 409、`code=JOB_ALREADY_RUNNING`、`message="The job is already running"`。当前测试只锁资源束，建议保留但不要当作 API 英文验收。
- 注意：修好后英文会变成通用短句 `The job is already running`，丢失任务号/作业号/类型等细节；若英文也要可操作信息，需要给 `ConflictException`/handler 传 `args` 或增加模板键，属于更大的契约变更。

## Minor（单列）

1. **级联测试漏了 `job_items` / `validation_issues`**：`seed()` 只造 job/task_item/task_file/staging，终端删除断言只查 task/job/task_item/task_file/staging/物理文件（`TaskDeleteInFlightGuardTest.java:103-118`）；服务代码确实删了 job_items/issues（`TaskService.java:375-378`），但测试没有锁住这两条。建议在 `seed()` 各插一行并在“保留/清理”两侧都断言。
2. **前端 409 会额外触发“任务列表加载失败”横幅**：`taskStore.error` 同时是列表加载错误字段，`TaskCenterView.vue:33-40` 用它渲染 `views.tasks.loadFailed`。删除 409 时 store 写入该字段（`stores/task.ts:243-245`），页面会同时出现 `ElMessage.error` 和“任务列表加载失败：任务 #…仍有未结束作业…”的顶部 Alert。新测试甚至断言了 `store.error === message`，把这个行为锁死。建议拆分 `actionError`/`loadError`，或在 toast 后清空 `error`；至少不要让删除冲突显示成“加载失败”。
3. **报告 RED 描述与最终测试不一致**：报告称“英文/错误码用例：expected 409，actual 200”，但最终测试文件里没有 HTTP 英文 409 用例，只有资源束断言。建议修正报告，避免把资源层测试当作 RED/GREEN 的 HTTP 证据。
4. **其他写入口仍可制造同类孤儿**：删除入口本身只有 `TaskController.delete`（`:89-93`），没有 AI 删除工具，服务层守卫不可从别的删除路径绕过；但 `FileController.save`（`FileController.java:169-188`）不校验任务是否存在，删除后仍可插入 `task_files` 并写物理文件；`selectDefs`/上传等也有同类检查后写入窗口。它们不属于 R1-13 的作业守卫，但若目标是“删除后无孤儿”，需要一并加 task 行锁或 FK。另：H2 console 开启属于运维面绕过，不在应用入口范围。
5. **错误码语义略重载**：`JOB_ALREADY_RUNNING` 同时用于“不能启动作业”和“不能删除任务”。在“不新增码”约束下可接受；若未来前端要按码区分，需要靠 HTTP 方法/路径或另开码。
6. **E2E/清理脚本兼容性**：既有证据/脚本大量用 `DELETE /api/tasks/{id}` 做清理；若作业仍在跑，现在会 409。这是预期行为，但清理脚本应先取消/等待，否则会留下测试数据。建议在相关脚本中显式处理 409。
