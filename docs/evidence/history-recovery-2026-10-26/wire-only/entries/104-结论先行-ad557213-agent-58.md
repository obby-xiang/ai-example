## 结论先行

这一块的“手搓”总量很大，但**真正的重复造轮子集中在 4 处**：写超时预算（JDK 已有）、会话门分布式锁（Redisson 已有）、前端 SSE 解析/重连（npm 有现成库）、两套重复的退避算式（Spring Retry 有近似策略）。而 **SSE 通道本身没有重造 `SseEmitter`/`ResponseBodyEmitter`**，Redis 侧也已经用上了官方的 Stream 与 Spring Data Redis 的 `MessageListener`——这两点是加分项，不是问题点。

## 一、五个问题的直接回答

**Q1 SSE 形态**：MVC `SseEmitter` + `emitter.send(String)` 裸发 JSON，线上是标准 `data:` 帧（未命名事件）。**没有**重写 `ResponseBodyEmitter` 的线格式，但**在它之上重建了背压/收尾/超时语义**（每订阅者队列 + CAS drain + 投递池 + 写预算，`ai/run/SseChatEmitter.java:1303`/`:1539`/`:1575`）。流式上游用的是 Spring AI 官方 `Flux<ChatResponse>`（`ResilientChatService.java:445-460` 的 `.stream().chatResponse()`），但立刻被 `subscribe(...)` 降级成阻塞驱动（`:665-683`），再用 1s 节拍看门狗替代 Reactor 的 `timeout/retryWhen/doFinally`。
- **框架已给的**：`SseEmitter` 生命周期回调、`event().id()` + 规范里的 `id:`/`Last-Event-ID`、SSE `retry:` 字段、Tomcat 写超时、Reactor 的超时/重试/取消。
- **业务真需要的**：跨请求回放（POST 首轮 → GET 重挂在另一个 URL，`Last-Event-ID` 覆盖不了这条）、跨实例乱序去重用的 seq、挂起期心跳、慢订阅者摘除、单帧字节截断。
- **结论**：不是“重造 SseEmitter”，是“在 Servlet 阻塞栈上自建了一个 Reactor 级扇出引擎”。其中**慢订阅者隔离 + 写预算**在阻塞 socket 下框架确实给不了；但 **状态机复杂度**（drain 抢权、handoff/complete 二选一、liveQueued 计数）远超业务所需，用 `Sinks.Many.multicast().onBackpressureBuffer(256)` + `publishOn(boundedElastic)` 能收掉大半。

**Q2 重试/退避/熔断/超时/降级**：
- **模型调用重试 = 框架的**：`AiRetryConfig` 注册自有 `RetryTemplate` 顶掉 spring-ai autoconfigure 的 10 次默认值，`AiProviderRegistry.java:431` 传给 `OpenAiChatModel`。这是正确用法，不算手搓。
- **只有 BackOffPolicy 是自写**（`AiRetryDefaults.java:137-171`，30 行），且与 `RetryBackoff.java:26-92` 是**同一套算式写了两遍**。
- **流式断流重试是必要自研**（`ResilientChatService.java:645-752`）：判定条件是“未产出内容 + 无工具副作用 + 未超段预算”，Resilience4j/Spring Retry 都表达不了“已发内容就不许重试”。
- **熔断**：`CompactionFuse.java` 手写 closed/open/half_open 三态 —— Resilience4j `CircuitBreaker` 能力完全覆盖，但状态外置在 Redis（跨实例），替换要自定 `CircuitBreakerStateStore`。
- **超时**：首包/事件间/段预算/取消四合一由 `StreamWatchdog` 承担（`StreamWatchdog.java:138-192`），Reactor `Flux.timeout` 只能覆盖前两项（作者在 `:32-44` 已论证）。
- **降级**：各处 `catch → WARN + 放行/继续`，属业务策略，非轮子。

**Q3 限流器**：是**自写 Redis + Lua 滑动窗口（ZSET）**，`AiRateLimiter.java:79-102`。Redis+Lua 原子滑动窗口本身是业界推荐做法（代码注释也自引“不要新造设施”），Bucket4j 的 Redis 后端也是同思路但为令牌桶；Resilience4j `RateLimiter` **只有进程内**，多实例下不可用；Spring Cloud Gateway 的 `RedisRateLimiter` 需要整个网关依赖。**判定：合理自研**，非重复造轮子。

**Q4 Redis 复刻**：
- 帧日志 = **原生 Redis Stream**（`XADD ... MAXLEN ~` / `XRANGE`，`RedisFrameStore.java:305`/`:437`），没用 consumer group —— 这是**正确**的，多订阅者广播不需要 ack。
- 唤醒总线 = **Spring Data Redis `RedisMessageListenerContainer`**（`RedisFrameWakeBus.java:47-83`），不是自建 pub/sub。
- `ai:events` LIST 仅兼容只读残留；`ai:runs` SET 用惰性清理（`RunStore.java:971-1043`）。
- **唯一像“自建总线”的是取消**：跨实例取消靠 1s 轮询 Redis 键（`CancellationRegistry.java:255-265` + `StreamWatchdog` 每拍读），而同仓已有现成的 pub/sub 通道没用上。keyspace notification 也能做，但 pub/sub 丢消息需保留轮询兜底，改造收益有限。

**Q5 JSON / 时间 / 序列化**：没有手拼 JSON（`TruncationContract.java:151-156` 只有一行失败兜底拼串）；时间一律 `java.time`，无 `SimpleDateFormat`。`MessageJsonCodec` 是**必要自研**——Spring AI 1.1.7 没有公开的 `Message` JSON codec（JDBC/Neo4j memory 各自内联实现）。

## 二、确凿的重复造轮子

### 1. `SseWriteBudget`：用 150 行重建了 `Future.get(timeout)` + `newCachedThreadPool()`
- **证据**：`common/sse/SseWriteBudget.java:175` 的 `write()` 本质是 `executor.submit(task)` → `future.get(timeout, MILLIS)` → `future.cancel(true)`；`:132` 的 `sharedElasticWriterPool()` 是 `corePool=0 + SynchronousQueue + 60s keepAlive`，与 `Executors.newCachedThreadPool(daemonFactory)` **逐参数相同**。附带的 `Result`/`Outcome`/`WriteFailure` 是把 `ExecutionException` 拆回原异常。
- **本可用**：JDK `CompletableFuture.supplyAsync(...).get(15, SECONDS)`（或 `orTimeout`）+ `Executors.newCachedThreadPool`。零依赖。
- **判断**：**确实重复**，核心机制 100% 是 JDK 自带；只有“超时计数”“超时不碰 emitter”的注释结论是业务知识。
- **成本/风险**：**小改**，~30 行可等价替换；不丢功能。真正的价值在注释里的 Tomcat 写超时论证，那部分应保留为文档而非代码。

### 2. `SessionGate`：手写 Redis 分布式锁 + watchdog 续期
- **证据**：`ai/session/SessionGate.java:85` `setIfAbsent(key, runId, ttl)` 抢锁、`:159` 定时 `expire` 续期、释放时比对 runId；`:35-38` 明确“Redis 锁 + watchdog 续期”。这是 Redisson `RLock` 的标准语义（看门狗续租、可重入、只删自己的锁）。
- **本可用**：Redisson `RLock`（`tryLock(0, -1, unit)` 即开启看门狗）；或 Spring Integration Redis LockRegistry。
- **判断**：**确实重复**，功能级 1:1。
- **成本/风险**：**小改**（一个类），代价是引入 Redisson（含 netty，包体明显变大）。若坚持零新依赖，现状可接受 —— 但应把它记为“已知重复”而不是“必要自研”。

### 3. 前端 SSE 解析 + 重连退避整套自写
- **证据**：`frontend/src/api/sse.ts:217` 手切 `data:` 行（含 BOM 容忍、多行 data 拼接）、`:53` 自写 `1/2/4/8s ±25%` 退避、`:360-450` 自写 `getReader()` 流循环 + idle 计时器、`:585-711` 自写 connect/idle 双看门狗 + `EventSource` 重建。
- **本可用**：`@microsoft/fetch-event-source`（POST SSE + 可配置重试退避 + AbortController）、`eventsource-parser`（规范级解析，含 `id`/`retry` 字段）。
- **判断**：**确实重复**（解析与退避两部分）；但“挂起期不重连”“idle 45s 判死”“connect 15s 独立预算”是业务策略，库里没有。
- **成本/风险**：**中改**（前端一条通道 + 相关 vitest），可保留 watchdog 只换解析层。风险是换库后 `lastSeq` 接管逻辑要重写。

### 4. 退避算式写了两遍
- **证据**：`ai/run/RetryBackoff.java:29-79` 与 `ai/config/AiRetryDefaults.java:110-171` 都是 `500ms × 2^n，上限 5s，±25% 抖动`，各带一份 `clamp01`、一份 `baseMs`。
- **本可用**：Spring Retry 自带 `ExponentialBackOffPolicy`（multiplier/maxInterval）与 `ExponentialRandomBackOffPolicy`（乘数随机化 = 抖动）。缺口是“不能注入抖动样本”“不能表达退避总预算上界”。
- **判断**：**部分重复**（框架策略差两个能力，故自写有理由；但**两份自写**没有理由，应合并成一个）。
- **成本/风险**：**小改**（合并 + 单测收敛），零功能风险。

## 三、存疑（有理由，但值得复核）

### 5. seq 放在 JSON 里 + `?lastSeq`，而不是 SSE 的 `id:` + `Last-Event-ID`
- **证据**：`SseChatEmitter.java:1303-1349` 取号后塞进帧体；`AiController.java:661-683` 重挂读 query 参数 `lastSeq`；前端 `sse.ts:289` 自行维护 `state.lastSeq`。
- **本可用**：SSE 规范的 `id:` 字段 + `Last-Event-ID` 请求头（`EventSource` 重连时自动回带），Spring MVC 侧 `SseEmitter.event().id(seq)` 一行；服务端仍可自行查 Redis 回放。
- **判断**：**部分重复但有合理理由**——首轮是 POST（`EventSource` 不支持），POST→GET 换 URL 时浏览器不会带 `Last-Event-ID`；且 seq 还必须暴露给 UI 做“孤儿帧过滤”。
- **成本/风险**：**大改**（前后端协议 + 双端白名单 + E2E 取证脚本全动）。建议不动，仅在 GET 通道**兼容**读 `Last-Event-ID` 作为 `lastSeq` 的回退源即可（小改、零风险）。

### 6. `SseChatEmitter` 在阻塞栈上重建 Reactor 扇出语义
- **证据**：`SseChatEmitter.java:1303-1375`（emitLock 内取号/落档/入队）、`:1470-1513`（`liveQueued` 闸 + CAS drain）、`:1539-1600`（`finishDrain` 的 handoff/complete 二选一）。整套是为了保证“单订阅者 FIFO + 慢连接不阻塞整轮 + 队空才 complete”。
- **本可用**：reactor-core **已在 classpath**（`StreamWatchdog` 已 `import reactor.core.Disposable`）。`Sinks.Many.multicast().onBackpressureBuffer(256)` + `publishOn(boundedElastic, 256)` + `timeout` + `doFinally` 可表达大部分；`Flux.onBackpressureDrop` 对应溢出摘除。
- **判断**：**框架能力部分不足**——上游 `SpToolCallingManager` 是阻塞工具循环，写侧是 Tomcat 阻塞 socket，换 Reactor 也消不掉“写预算”；但 2000 行里至少一半是**手写状态机**，Reactor 能省掉。
- **成本/风险**：**大改**，且是当前最不容易回归的一块（注释里记录了 7 轮红队修复的竞态）。**不建议现在换**，建议只做“把 CAS drain 的语义抽成独立类 + 契约测试”。

### 7. 跨实例取消靠 1s 轮询，而同仓已有 pub/sub
- **证据**：`CancellationRegistry.java:28-36` 明确“跨进程靠轮询”；轮询点 = `StreamWatchdog` 每 1s（`StreamWatchdog.java:148`）与 `ConfirmGate` 每 2s。已有 `RedisFrameWakeBus` 的 `RedisMessageListenerContainer` 可复用。
- **本可用**：Redis pub/sub（同仓实现）/ keyspace notification；`CancellationRegistry` 的本地监听者集合已经是半个实现，只差跨实例那一段。
- **判断**：**部分重复**（轮子已有未复用），但**轮询作为兜底必须保留**（pub/sub at-most-once）。
- **成本/风险**：**小改**（加一条 `ai:cancel-evt:*` 频道 → 触发已有本地监听者），不丢功能；风险是容器多一个订阅连接。

### 8. `CompactionFuse` 手写三态熔断
- **证据**：`ai/context/CompactionFuse.java:26-79`：`allowsSummary/onSuccess/onFailure/halfOpen` + 连续失败阈值 + 冷却窗，状态存在 `ai:ctx:<sessionId>`。
- **本可用**：Resilience4j `CircuitBreaker`（COUNT_BASED 滑动窗口、half-open、`CallNotPermittedException`）。
- **判断**：**部分重复**——他们的判据是“连续失败 N 次 + 固定冷却”，不是失败率；且状态必须跨实例外置，Resilience4j 需自定义 store。替换收益不大。
- **成本/风险**：**中改**，收益低，建议不换，但在注释里登记“等价于 Resilience4j 的 X 配置”。

### 9. `ContextEstimator` 手算 token
- **证据**：`ai/context/ContextEstimator.java:29-31`，`cjk/1.7 + other/4`，注释明确“刻意不引分词器”。仅用于无 usage 时的回退与分项展示。
- **本可用**：`com.knuddels:jtokkit`（纯 Java BPE，tiktoken 兼容）/ `tiktoken-java`。
- **判断**：**合理自研**（真值以 API usage 为准，估算是粗判）；只有在需要把前端 `≈` 变成真值时才值得引库。
- **成本/风险**：**小改**（替换一个静态方法），但会引入词表体积与模型族对齐问题（不同 upstream 用不同 tokenizer，反而更不准）。

## 四、合理自研（明确不是轮子）

| 对象 | 为什么不算重复 | 依据 |
|---|---|---|
| `SseChatEmitter` 的**帧协议**（`type/seq/atMs/runId`） | `SseEmitter` 只给线格式，不给业务信封；16 种帧型是产品契约 | `SseChatEmitter.java:1277-1282` |

## 五、汇总（按建议动作排序）

| # | 发现 | 判断 | 成本 | 丢功能风险 |
