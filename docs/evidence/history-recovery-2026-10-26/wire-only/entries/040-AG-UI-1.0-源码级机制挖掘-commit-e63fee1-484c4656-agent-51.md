## 2. 状态同步

- `STATE_SNAPSHOT.snapshot` = **整替换**（客户端 `state = snapshot`，字面量，falsy/null 也照用）【已核实：`client/src/apply/default.ts:695-708`；conformance `state-falsy-snapshot-applies.json`、`state-null-snapshot-applies.json`】。
- `STATE_DELTA.delta` **就是 RFC 6902 JSON Patch**——`JsonPatch` = array of `JsonPatchOperation`，`oneOf` Add/Remove/Replace/Move/Copy/**Test**，判别式 `op`，字段 `path`/`value`/`from`；空数组是合法 no-op；operation 是**开放对象**（RFC 4 要求忽略多余成员），两条关系型规则（move 的 `from` 是 `path` 真前缀、指针不可解析）**schema 不校验、由 applier 拒绝**【已核实：`spec/1.0/schema.json` `$defs.JsonPatchOperation`】。客户端用 `jsonpatch.applyPatch(state, delta, true, false).newDocument`，**失败即警告并整体保留旧状态（不做部分应用）**，不失败 run【已核实：`client/src/apply/default.ts:726-740`；`conformance/streams/state-delta-unappliable-warns-and-keeps.json`】。
- 配合方式：先 snapshot 后 delta 增量修补（`state-delta-applies.json` 断言结果）。`ACTIVITY_*` 同套机制（`patch` 字段），`replace:false` 表示合并而非替换（`activity-replace-false-preserves.json`）。
- **有无 version/顺序保证：无**。没有任何 sequence/version/revision 字段；`timestamp` 明确"consumer **MUST NOT** 用它排序，到达顺序才是顺序"。跨 run 的可比性靠 `MESSAGES_SNAPSHOT` 按 id 对账（`messages-snapshot-reconciles-by-id.json`）与 `RUN_STARTED.protocolVersion` 协商。

## 3. HITL / 暂停-恢复

**Interrupt**（schema，required 仅 `id`、`reason`）：`id`、`reason`（开放字符串，非枚举）、`message`、`toolCallId`（工具审批时指向 `TOOL_CALL_START` 的 id）、`responseSchema`（object，不透明）、`expiresAt`（**刻意不设 date-time 格式**，约定 ISO 8601；非日期值会被按日期比较者视为"永不过期"）、`metadata`、继承 `subagentRunId`。
> **`paid` 之类的"付费属性"在 1.0 schema 中不存在**——全仓 grep `paid|payment|billing|price` 仅命中 `cacheWriteInputTokens` 的描述文字（"providers price a cache write differently"）。README-导读 第 56 行的表述有误，interrupt 的额外属性就是 `responseSchema`/`metadata`/`expiresAt`。【已核实：`spec/1.0/schema.json`】

**ResumeEntry**：`interruptId`(req)、`status`(req, enum **仅 `resolved`｜`cancelled`**)、`payload`(any JSON，非 null，`resolved` 时是答案本体)、`metadata`（信封信息如签名/路由）。拒绝语义表达在 payload 内（如 `{approved:false}`），**不是**第三种 status。【已核实：`spec/1.0/schema.json`、`fixtures/ResumeEntry/valid/{resolved,cancelled}.json`、`fixtures/ResumeEntry/invalid/unknown-status.json`】

**RunFinishedOutcome** = `oneOf` **success｜interrupt｜cancelled**——**没有 `error`**；失败只有 `RUN_ERROR` 一条路【已核实：`spec/1.0/schema.json` `$defs.RunFinishedOutcome`；`fixtures/RunFinishedEvent/invalid/` 含 `outcome-success-carrying-interrupts`、`outcome-interrupt-carrying-pending-tool-call-ids`、`outcome-interrupt-with-no-interrupts` 等互斥不变量】。
- `interrupt`：`interrupts[]` **minItems 1**，语义"run 暂停，resume = 启动一个**新 run**，其 resume 条目回答这些 interrupt"。
- `cancelled`：主动停止、非失败、无 result、无 interrupt，**后续 run 是普通新 run 而非 resume**。
- `success.pendingToolCallIds[]`：本 run **已 START 但无 TOOL_CALL_RESULT** 的调用 id，按发起顺序，供 application 在**下一轮 input 的 messages** 里回答；省略时 consumer 自行从流推导（客户端 `pendingToolCallIdsOf` 正是此逻辑，producer 给出则以 producer 为准）【已核实：`client/src/apply/default.ts:146-157`、`fixtures/RunFinishedEvent/valid/outcome-success-pending-tool-call-ids.json`】。

**客户端逻辑**（`sdks/typescript/packages/client/src/interrupts/index.ts`）：
- `getRunOutcome(event)` = 直接返回 `event.outcome`；
- `isInterruptExpired(interrupt, now?)`：无 `expiresAt` → false；否则 `new Date(expiresAt) <= now`（与"非日期=永不过期"一致）；
- `buildResumeArray(interrupts, responses)`：**要求 1:1**——缺条目抛 `missing responses for open interrupts`，多余 id 抛 `reference unknown interrupt ids`；`resolved` 且 payload 非 undefined 才写 payload，metadata 有才写。
- `AbstractAgent.onInitialize`【`agent/agent.ts:610-635`】：有 `pendingInterrupts` 时，resume 必须覆盖全部 id，否则抛 `Thread has N pending interrupt(s) not addressed by resume`；**过期的 interrupt 只允许用 `status:"cancelled"` 通过**（抛 `...expired at ... and can no longer be answered. Cancel it to continue the thread.`）。`pendingInterrupts` 在收到 interrupt outcome 的 `RUN_FINISHED` 时被赋值，其他 outcome 清空【`apply/default.ts:1120-1140`】。

**服务端恢复形态**：`RunAgentInput.resume?: ResumeEntry[]`——resume 就在**普通 run 请求体**里，**没有独立 resume 端点/事件**【已核实：`spec/1.0/schema.json $defs.RunAgentInput`；`client/src/agent/types.ts:50-54` `RunAgentParameters.resume`；`client/src/agent/http.ts` `requestInit` 仍是 `POST + application/json + Accept: text/event-stream`】。
服务端示例（Go）【`sdks/community/go/example/server/internal/agent/loop.go:64-150,588-593`】：`len(in.Resume)>0` 走 resume 分支，从暂停 run 存档（按 threadId/runId 为键，`deps.Store`）非破坏性 Load；失败分别 `RUN_ERROR`：找不到暂停 run / 条目不匹配任何 pending call / 未覆盖某 pending tool call / 被并发 resume 抢占；`approvalsFromResume` 只把 `status==resolved` 视为批准。

**结论（确切答案）**：AG-UI 的中断-恢复是 **"轮次终态化 + 新 run 携带 resume 决策"**，**不是连接内挂起**。证据链：outcome 附着在 `RUN_FINISHED` 上（终态事件）；`RunFinishedInterruptOutcome` 描述原文"Resuming means starting a new run"；客户端把 interrupt 记在 `pendingInterrupts` 这一**跨 run 的客户端字段**上；恢复请求即新的 `POST` 请求体。【已核实：`spec/1.0/schema.json`、`client/src/apply/default.ts`、`client/src/agent/agent.ts`】
（附实现细节：Go 示例的 resume **复用原 threadId/runId** 作为存档键，见 `loop.go:67` 注释——协议只要求 threadId 相同，runId 复用与否是服务端选择。）

## 4. 前端工具（客户端执行）

- 表达方式就是普通 `TOOL_CALL_START`/`ARGS`/`END`（无独立"客户端工具"事件、无 `ClientToolExecutor` 类）。生产者**MUST NOT** 发 `TOOL_CALL_RESULT`，它以 **success outcome + `pendingToolCallIds`** 结束 run；application 在**下一轮 `messages` 里放一条 `role:"tool"` 消息**（携带该 `toolCallId`）来回答，走普通消息循环。【已核实：schema `RunFinishedSuccessOutcome.pendingToolCallIds` 描述；`client/src/apply/default.ts`；Go `loop.go:230-245` "Hand-back: the server can't execute client-defined tools … Finish with a plain RUN_FINISHED so the client fulfills and starts Run B"】

## 5. SSE 线格式与内容协商

`sdks/typescript/packages/encoder/src/encoder.ts`：

```ts
encodeSSE(event) => `data: ${JSON.stringify(omitOptionalNulls(event, "Event"))}\n\n`
```

- **只有 `data:` 行，没有 `event:`／`id:`／`retry:`**；事件名只在 JSON 的 `type` 里。序列化前 `omitOptionalNulls(event,"Event")` 落实"缺值即省略，不发 null"。

## 7. Token 计量

- **只有 `TokenUsage[]`，只出现在 `RUN_FINISHED.usage` 与 `RUN_ERROR.usage`**（`RUN_STARTED` 没有）。字段全 optional：`provider`、`model`、`inputTokens`、`outputTokens`、`totalTokens`、`reasoningTokens`、`cachedInputTokens`、`cacheWriteInputTokens`（均为 integer，fixtures 中负数非法）。
- 记账模型："每个计数要么是总量、要么是某个总量的**具名部分**"——`inputTokens`/`outputTokens` 是总量，`reasoningTokens`/`cachedInputTokens`/`cacheWriteInputTokens` 是**其组成部分而非追加**；`totalTokens = inputTokens + outputTokens`。`cacheWriteInputTokens` 单独存在是因为"provider 对 cache write 与 cache read 定价不同，算成本的消费者少不了它"。
- 边界：**以 run 为单位，包含其 subagent 的调用**（subagent 事件自身不带 usage）；被当作独立 run 调用的 agent 由 `parentRunId` 命名并在自己的终态事件上报；父 run MUST NOT 计入。
- **`contextWindowUsage` 在 1.0 中不存在**——`spec/` 与 `sdks/` 全量 grep `contextWindow` 零命中。上下文窗口量只能走 `metadata`（保留键 `ag-ui`）或 `CUSTOM`。【已核实：`spec/1.0/schema.json $defs.TokenUsage`、`fixtures/RunFinishedEvent/valid/usage*.json`】

## 9. 去重与幂等

- **`EventEncoder` 没有 id 机制**：全仓无 `EventsEncoder` 符号，类名是 `EventEncoder`；`BaseEvent` **无 `id` 字段**，SSE 帧**不发 `id:`**，规范要求 consumer 忽略 `id:`，`Last-Event-ID` 不被使用、**没有流恢复**。故传输层**零去重、零重放保护**——重连只能换新 `runId` 起新 run 并重放 snapshot。
- id 生成是**调用方责任**：事件工厂 `core/src/event-factories.ts` 的 30 余个 `create*Event` 均不生成 id（只用 `uuidv4` 的地方是 `AbstractAgent` 铸 `runId`/`agentId`）。`TOOL_CALL_CHUNK`/`TEXT_MESSAGE_CHUNK` 走 `client/src/chunks/transform.ts` 展开为 START/ARGS/END：**首个 chunk 必须带 `messageId`（对 tool 还必须带 `toolCallName`），否则抛错**（`First TEXT_MESSAGE_CHUNK must have a messageId` / `First TOOL_CALL_CHUNK must have a toolCallName`）；后续 chunk 若 id 或 toolCallName 与已开启者**冲突**则**致命**（`does not match the open stream's toolCallName`），**完全重复则接受**。
- 匹配约定：`toolCallId` 绑定 `TOOL_CALL_*` → `TOOL_CALL_RESULT` → 相关 interrupt；`messageId` 在 thread 内**跨 run 必须唯一**（因为后续 run 的 snapshot 会按 id 复述消息），`runId` 在同一 thread 内 **MUST NOT** 复用；全部 id 是不透明字符串，consumer MUST NOT 解析其结构。去重靠 `MESSAGES_SNAPSHOT` 按 id 对账 + metadata 按键 last-write-wins 合并（`metadata-merges-last-write-wins.json`）【已核实：`client/src/apply/default.ts`、`conformance/streams/{first-chunk-missing-id-fatal,chunk-conflicting-role-fatal,chunk-repeat-identical-accepted,messages-snapshot-reconciles-by-id}.json`】。

## 10. RAW 与可观测面

- **不存在 `RUN_RAW_MODEL_CALL_EVENT`**（全仓 grep 零命中）。原生调用透传有两条路：`RAW` 事件 `{event:any, source?}`（"把 provider 原生事件未翻译地透出"），以及每个事件信封上的 `rawEvent`（"本事件翻译自的 provider 原生事件，逐字携带，consumer MUST NOT 由它推导协议行为"）。
- 内置观测面：① `RUN_STARTED.input` 回显整个 `RunAgentInput`（"让没发起请求的消费者也能看到 agent 被问了什么"）；② `RUN_STARTED.protocolVersion`（生产者自述版本，双方各自声明即构成协商，缺失＝1.0 之前的 producer）；③ 终态事件的 `usage`；④ `STEP_STARTED/FINISHED`（宏观进度）；⑤ `ACTIVITY_*`（结构化进度，`content` open-by-key，`replace=false` 合并，可作审批请求/预测状态载体）；⑥ `REASONING_ENCRYPTED_VALUE`（provider 加密思维，`entityId`+`entityType`）；⑦ `metadata` 保留键 `ag-ui`、`CUSTOM`；⑧ 客户端流不变量校验器 `client/src/verify/verify.ts`（首事件必须 `RUN_STARTED`、禁止嵌套 run、开放实体必须闭合、run 结束后除新 `RUN_STARTED` 外无事件等）。**没有** CPU/耗时/trace 这类系统指标字段。

## 与我方自定义 SSE 帧对齐时的注意点

我方现状：`start/text_delta/reasoning_delta/tool_start/tool_call/tool_result/confirm_request/ping/done/error`，POST+fetch，HITL = `ToolCallingManager` 阻塞挂起 + Redis 外置 + 跨进程续跑。

1. **最大结构性冲突是 HITL 模型**。AG-UI 的中断是**轮次终态**：必须在 `RUN_FINISHED.outcome.interrupts[]` 里交付，且 state/messages snapshot 要**先于**该 `RUN_FINISHED` 发出；resume 是**新请求体里的 `resume[]`**。我们的"连接内阻塞挂起 + 跨进程续跑"在协议上无对应物——若要对齐，`confirm_request` 要在 run 收尾时改由 `done` 携带 interrupt，且续跑请求必须带齐 `resume: [{interruptId,status,payload}]`。反之，若保留阻塞模型，就必须承认这是**非 AG-UI 的私有扩展**，别指望 AG-UI 客户端能消费。
2. **覆盖是强制的**：resume 必须 1:1 覆盖上一 run 全部 open interrupt，部分恢复被拒（客户端 `buildResumeArray` 直接抛错）；过期 interrupt 唯一出路是 `status:"cancelled"`。我们的 `confirm_request` 至少要携带 `id/reason/message/toolCallId/responseSchema/expiresAt` 六件套，尤其 `responseSchema`（前端建表单）与 `expiresAt`（必须有明确时钟语义，否则会被当成永不过期）。
3. **`error` 不该再表示"运行失败收尾"以外的语义**，且 outcome 里没有 `error` 值——失败只走 `RUN_ERROR(message, code, usage)`；`cancelled` 是独立的第三态（无 result、无 interrupt、后续是普通新 run），不能报成 success。
4. **`done` 需要携带 outcome**：若我方"前端工具"是客户端执行，正确形态是 run 以 **success + `pendingToolCallIds`** 结束、**不发 `tool_result`**，由下一次请求的 messages 里补 `role:"tool"` 消息回答。我们目前的"等待前端工具结果"若靠阻塞连接，与第 1 点同源问题。
5. **帧命名**：AG-UI 帧是纯 `data: {…"type":"…"}\n\n`，没有 `event:` 行；客户端会**忽略 event 名**。我们若想被 AG-UI 客户端直读，事件名必须进 JSON `type`（并在 `data:` 里），不能只放 SSE event 字段；`ping` 建议改成 SSE 注释行（`: keep-alive`）
——
`data:` 里塞非事件对象会被判为畸形。
6. **文本/推理增量缺括号**：我方 `text_delta`/`reasoning_delta` 是扁平增量，AG-UI 要求 `*_START`（带 `messageId`）→ `*_CONTENT(delta)` → `*_END`，且 `*_CHUNK` 展开时首个 chunk 必须带 id/名字、冲突即致命。缺 START 的 content（`content-without-start-fatal`）与 run 收尾时未闭合的消息（`open-message-at-run-finished-fatal`）都会被拒。
7. **tool_result 必须带 `messageId`**（不只是 `toolCallId`）：AG-UI 的 `TOOL_CALL_RESULT` 会"铸出"一条 tool 消息并插在发起调用的 assistant 消息之后，`messageId` 是该消息的身份；`content` 支持 string 或 parts（含 `{type:"document",source:{type:"file"|"url",…}}`，且 file handle 不透明、不得改写为 URL）。
8. **状态同步改用 RFC 6902**：我们若用自定义 delta 结构，前端换到 AG-UI 客户端就失效。注意两条实现细节：patch 不可应用时**整体保留旧状态并告警**（不得部分应用、不得失败 run）；空数组合法；`op` 判别，`add/replace/test` 必须带 `value`，`move/copy` 必须带 `from`。
9. **无断流恢复、无 `id:` 去重**：重连必须换新 `runId` 起新 run 并靠 `MESSAGES_SNAPSHOT`（按 `messageId` 对账）+ `STATE_SNAPSHOT` 重放；`messageId` 在 thread 内跨 run 必须唯一、`toolCallId` 必须贯穿 call→result→interrupt，"同一 `(threadId,interruptId,status,payload)` 可安全重放"这条幂等保证需要我们在 Redis 侧自己实现（协议只提出要求，不给机制）。
10. **顺序纪律**：首事件必须 `RUN_STARTED`，禁止嵌套 `RUN_STARTED`，`RUN_FINISHED` 之后除新 `RUN_STARTED` 外别无事件，`timestamp` 不可用于排序。我们若在 `done` 之后还补发 `ping`/尾帧，会直接违反。
11. **可直接复用的测试资产**：`spec/1.0/conformance/streams/*.json`（68 例，含 `kill` 变异说明与 `expect.request` 形状断言）+ `spec/1.0/fixtures/`（42 型 / 303 例 valid+invalid）；建议把 reducer 与帧序断言抽成语言无关的 runner，我们的 SSE 实现即可用同一份语料验收。

**未能核实项**：任务提到的 `contextWindowUsage`、`MEMORY` 事件、`agents` 字段、`MCP` schema、`paid` 属性 —— 在 `spec/1.0` 与已检出 `sdks/` 中**均不存在**（已在对应各题给出 grep 依据）；文档中大量"spec 正文 MUST"引述因 `spec/1.0/` 未含 prose 而无法在本地核实，其中一部分可由 `conformance/streams` 的 `specPage` + `kill` 间接佐证。
