## 必须修（P1）

### P1-1 `RunStore.get` 的 Redis 读失败仍是未 typed → `/events`、`/runs/current` 回 **500**，与本批“基础设施 → 503”的口径自相矛盾

`<REPO_ROOT>/backend/src/main/java/com/example/configmgr/ai/run/RunStore.java:795-806`

`String raw = this.redis.opsForValue().get(runKey(runId));` 在 `try` **之外**；连接失败抛原生 `RedisConnectionFailureException`（无 handler）→ `GlobalExceptionHandler.handleGeneral` → 500。调用点：

- `AiController.java:645`（`GET /api/ai/events/{runId}`，重挂主路径）——`lastSeqIfKnown` 的 503 预检在 `get` **之后**，永远走不到；
- `AiController.java:840`（`GET /api/ai/runs/current`）——同批刚为 `lastSeqIfKnown` 加了 503 用例，但 `get` 失败仍是 500；
- `ResumeService.java:250/333`（`/runs`、`/runs/{id}` 运维面）。

**为什么必须修**：同一批已经把“读失败”统一成 503（fence/guard/待决/B3），唯独最常用的快照读仍是 500；前端对 503 有 degraded 处理，对 500 没有，重挂路径在 Redis 抖动时表现为“服务端炸了”。

**修法**：把 `get` 的 Redis 读纳入 try，连接类失败抛 `AiStateUnavailableException`（JSON 解析失败保持 `IllegalStateException`）；顺带让 `listRuns`/`describe` 的 `ledger`/`ledgerCounts` 走非抛或 typed（见 P2）。

**可执行验证**：MockMvc：`when(runStore.get(runId)).thenThrow(new RedisConnectionFailureException("down"))`，断言 `GET /api/ai/events/{runId}` 与 `GET /api/ai/runs/current?sessionId=...` 返回 **503 + `AI_REDIS_UNAVAILABLE`**（当前树：500）。

### P1-2 runner-active 的“共享可见性”在两种非稳态下失效，破坏“A 的 runner 未退出 ⇒ B 409”

`<REPO_ROOT>/backend/src/main/java/com/example/configmgr/job/service/JobHeartbeatRegistry.java:53, 122-139, 235-244`

两个成因（同一不变量）：

1. **写失败被吞**：`beginRunner` → `renewRunnerActive`（`:235-244`）对 Redis 失败只 `log.warn`；`beat` 同样。若作业启动/心跳期间 Redis 写失败，恢复后共享键可能**从未存在**，而 runner 仍活着。此时另一实例 `TaskService.delete` 的 DB 在途检查已过（作业已终态），runner 闸门读不到键 → 放行级联删除（删除任务/作业/暂存/文件，`TaskService:426-445`），而 A 的 runner 可能仍在长事务里写子表——正是 C1 要消灭的“删在活 runner 上”。
2. **TTL 与配置脱钩**：`RUNNER_ACTIVE_TTL = 1h` 是硬编码；`app.job.max-execution-time` 可配（默认 30m，`AppProperties:96-131` 只校验正数与心跳关系，**不校验与该 TTL 的关系**）。把 `max-execution-time` 调到 >1h 时，键会在合法作业运行中过期 → 同样的跨实例误删窗口。

**为什么必须修**：类注释与测试都把“A 未退出 ⇒ B 409”当硬不变量，但当前只在“写成功 + 运行 <1h”时成立；删除是不可逆级联。

**修法**（二选一，建议都做）：
- `beginRunner` 在 redis 模式写键失败时**不让作业开跑**（有界重试后仍失败 ⇒ 作业落 FAILED，不执行 runner），或把“注册成功”作为执行前置；`beat` 的失败保留告警但至少由启动重试兜住。
- TTL 由 `app.job.max-execution-time` 派生（如 ×2 + margin），并在 `verifyJobWatchdogKeys` 里断言 `runner-active TTL > max-execution-time`；`memory` 模式在非 test profile 打 WARN。

**可执行验证**：
- 多实例用例（扩 `RunnerActiveMultiInstanceTest`）：`doThrow` on `valueOps.set` → `beginRunner` 后让 Redis “恢复”（`hasKey=false`）→ 在 A 的 runner 仍登记时，B 的 `taskService.delete` **必须仍 409**；当前实现会成功删除（红）。
- 配置用例：`max-execution-time=2h` 启动 → 断言 `RUNNER_ACTIVE_TTL ≥ 2h+margin`（或启动失败）；当前硬编码 1h（红）。
- 真机：两实例 + 真 Redis，`CLIENT PAUSE`/断网覆盖 begin 与 beat，恢复后立即在 B 删除（见下“边界”）。

## P2（不阻断，登记即可）

- `ResumeService.listRuns/describe` 的 `ledger`/`ledgerCounts` 仍是非抛外读（`:270`、`:348-349`）：Redis 读抖动时 `/api/ai/runs`、`/runs/{id}` 会 500（同页的 `pending` 已是 lenient，口径不一致）。
- 非终态降级回放会发 **terminal `error` 帧并关闭连接**（`SseChatEmitter:700-718`，用例 `nonTerminalDegradedReplayAlsoCompletesWithTypedError` 锁住该行为）。前端把任何 `error` 帧当本轮失败（`stores/ai.ts:2292-2298, 4732-4750`，`sawErrorTerminal` 后不重连），而服务端该轮仍在跑；用户需刷新/重建才恢复。建议产品确认；若要避免误报，非终态降级应收流但**不发终态 error**（或前端识别 `degraded=true` 自动重挂）。
- `TaskService.delete` 在持有 task 行锁的事务里做 N 次 Redis `hasKey`（2s 命令超时）：Redis 挂死时锁被占最多 2s×job 数，会拖住 `createAndStart`。建议加时间预算。
- `RunnerActiveKeyCleanupRunner` 启动时 `findAllIds()` 逐个 GET（jobs 表大时启动慢）；受守卫禁 SCAN 限制，可考虑只清“本机曾经运行过”的索引或异步化。
- `rollbackClaim` 对“`putIfAbsent` 已在服务端成功但响应超时”无法判定（`claimed==null` 不回滚），仍可能留 24h phantom claim；可在异常后 best-effort `HGET` 比对再决定。
- `runner-active-store=memory` 在生产误配时无告警（`JobHeartbeatRegistry:106-110`），跨实例闸门会静默消失。
