## 结论（先行）

1. **18 个工具全部返回 `String`**（`grep 'public String ' AiTools.java` 命中 18 个工具方法），没有一个是结构化返回；失败表达分四类：抛异常 4 个（`start_*`）、吞异常返回中文串 3 个、参数错误返回中文串 1 个、静默给"0 行"1 个、前端哨兵桩 7 个、无失败分支 2 个。
2. **最关键的事实（与仓库注释相反）**：Spring AI 1.1.8 的 `MethodToolCallback` 会把工具方法抛出的异常包成 `ToolExecutionException`，再由 `DefaultToolExecutionManager` 交给 `DefaultToolExecutionExceptionProcessor`（默认 `alwaysThrow=false`）**转成普通文本**返回。本仓用的是 `ToolCallingManager.builder().build()`（`SpToolCallingManager.java:123`），所以 **`start_*` 抛 `ConflictException` 在真实循环里仍然 `ok=true`**，`executeOnce` 的 catch（`:377`）几乎不触发。"T6 重抛面 ⇒ ok=false" 只在本仓测试的直调层成立，端到端不成立。
3. **帧面**：`tool_result` 已带 `ok/status/result`，但前端只用 `ok===false` 或 `status==='BLOCKED'` 判失败（`parts.ts:435-436`），于是"业务失败但 ok=true"的卡面显示为 **「已成功」+ 失败文案正文**（`blocks.ts:453-454`、`AiPanel.vue:394-402`）。
4. **模型回读面**：`ToolResponse` 只有 `id/name/responseData`，整个 `spring-ai-model-1.1.8.jar` 中 `isError` 出现 **0 次**；模型只能看到 `limiter.forModel(text)` 后的字符串（`SpToolCallingManager.java:211-212`）。
5. **前端其实已经有 `outcome`**（`frontend-tools.ts:100-116`、`types/tools.ts:124`），但回灌 POST 只发 `result` 文本（`stores/ai.ts:3230` → `:2173`），`FrontendToolResultRequest` 也没有 outcome 字段（`web/FrontendToolResultRequest.java:15`）。
6. **最小侵入方案**：在汇聚层统一包信封 + **1 行**把官方异常处理器改为 `alwaysThrow=true` + 改造 6 个"吞错"工具；**不要改 18 个工具返回值**（编译面与测试面都不划算，且覆盖不到挂起/拒绝/超时这些非工具路径）。

**为什么 `:377` 的 catch 基本不触发（决定性证据）**

- `MethodToolCallback.callMethod` 把方法异常包成 `ToolExecutionException`：`throw new ToolExecutionException(this.toolDefinition, ex.getCause())`（[MethodToolCallback.java v1.1.8](https://raw.githubusercontent.com/spring-projects/spring-ai/v1.1.8/spring-ai-model/src/main/java/org/springframework/ai/tool/method/MethodToolCallback.java) 的 `callMethod`）。
- `DefaultToolCallingManager.executeToolCall`：`catch (ToolExecutionException ex) { toolResult = this.toolExecutionExceptionProcessor.process(ex); }`（[DefaultToolCallingManager.java](https://raw.githubusercontent.com/spring-projects/spring-ai/v1.1.8/spring-ai-model/src/main/java/org/springframework/ai/model/tool/DefaultToolCallingManager.java)）。
- `DefaultToolExecutionExceptionProcessor` 默认 `alwaysThrow=false`，`process()` 返回 `exception.getMessage()`；只有 cause **不是** `RuntimeException`（如 `JsonProcessingException`）时才 rethrow（[源码](https://raw.githubusercontent.com/spring-projects/spring-ai/v1.1.8/spring-ai-model/src/main/java/org/springframework/ai/tool/execution/DefaultToolExecutionExceptionProcessor.java)）。
- 本仓未自定义处理器：`this.delegate = ToolCallingManager.builder().build()`（`SpToolCallingManager.java:123`），全仓库没有其他 `ToolExecutionExceptionProcessor` 定义（grep 仅命中注释）。

因此：`ConflictException`（RuntimeException）→ 变成 `ToolExecutionException.getMessage()`（= cause message）→ **ok=true**。`AiToolsInvocationTest:196-198` / `AiToolsThrowPathTest:20-29` 的注释断言与端到端行为不符。

### 6.3 为什么"汇聚层统一包"更省

- 覆盖 **6 条出口**（正常/异常/越 scope/拒绝/超时/前端回灌），而改 18 个工具只能覆盖第 1 条。
- 改 18 个工具会**编译级破坏**至少 8 个直接调用测试文件（见 §7），且 Spring AI 会把非 String 返回值用 `DefaultToolCallResultConverter` 序列化成 JSON——仍然要处理 limiter/截断/历史渲染，省不掉汇聚层。
- 唯一必须动工具的地方是"**吞错**"：不把吞掉的异常抛出来，汇聚层拿不到 `code`（这 5-6 处是真正的信息源头）。
- 1 行异常处理器改造是**前提**：不改它，`start_*` 的 `TASK_FINALIZED` 等码永远到不了汇聚层。

### 6.4 需要单独标出的协议面（P）

- `tool_result` 增字段/改 `ok` 语义 → **前端类型 + parts 派生 + 历史回放**三处同改。
- `suspended` 的 `toolCalls[]`（`PendingToolCall.asMap`）增 `outcome/code` → 重挂/续跑一致。
- `POST /api/ai/frontend-tool-result` 增 `outcome` → DTO + 前端调用同步。
- `GET /api/ai/history` 的 `toolCallStates` 增 outcome/code → 刷新后卡面真态。
- **不建议**把信封塞进现有 `result` 字符串字段（会让卡面、GF 提交值解析、历史渲染三处同时被 JSON 污染）。
