## 1. 总体判断

AI 工具执行器不应做成“模型调用函数，然后相信它成功”。更稳的做法是：

> **把每个有副作用的工具当成一个可持久化的工作流活动：先写意图与幂等键，再取资源租约，再审批/派发，等待完成，读回验证，失败按“确定未发生 / 确定已发生 / 结局未知”分流，最后补偿或升级人工。**

模型只负责“提议做什么”，**不能负责“是否已经做过”“要不要重试”“是否互斥”**。这些必须由执行器在模型之外强制。

## 2. 五个问题的官方模式

### 2.1 有副作用步骤如何等待完成并保证顺序

核心原则：**“调用返回”不等于“副作用完成”**。要等待的是完成事件、作业终态或外部回执。

| 模式 | 官方做法 | 对 AI 执行器的借鉴 |
|---|---|---|
| Durable Workflow + Activity | Temporal 的 Workflow 通过 Activity 执行副作用，结果回到 Workflow；Activity 有超时、重试、心跳、取消和异步完成；Event History 支持故障后重放 | `start_*` 不应只返回 jobId 就结束；执行器应进入 `WAIT_JOB`，用轮询/回调等待终态 |
| 长任务同步/回调 | AWS Step Functions 的 `.sync` 等待作业完成；`.waitForTaskToken` 暂停到外部回传 token；`HeartbeatSeconds` 防止永久挂起 | 作业型工具应返回 `handle`（jobId/taskToken），由执行器等待，而不是让模型自行决定何时查 |
| DAG 依赖与触发规则 | Airflow 用 upstream/downstream 表达顺序；默认 `all_success`，可用 `all_done` 做清理/收尾；Task Instance 有 `queued/running/success/failed/up_for_retry/deferred/awaiting_input` 等状态 | 导入/预检查/发布应显式建模为 DAG 或状态机，不能靠模型“记得先做什么” |
| 节点顺序与等待 | n8n 按连线执行；1.0+ 默认逐分支完成；有 Wait 节点、Execute Once | 前端动作应按“会话/任务”串行，而不是并发下发 |
| 并行汇合 | Power Automate 的并行分支要等所有并行步骤完成后才继续；Apply to each 默认顺序执行，可设 1–50 并发度 | 只有无依赖的只读查询可并行；有副作用步骤默认并发度 1 |
| 工具结果关联 | OpenAI 用 `call_id` 关联 function call 与 output；Anthropic 用 `tool_use` → `tool_result` 往返；MCP 用 `isError` 区分工具执行错误 | 执行器必须保存 `toolCallId + handle + 状态`，不能把“模型下一轮再说”当作完成 |

### 2.2 同资源 / 同任务互斥

互斥键应该是**业务资源**，不是工具名，也不是会话 ID。常见粒度：`taskId`、`defCode`、`scopeKey`、`artifactId`、`workspaceId`。

| 机制 | 官方要点 | 适用 |
|---|---|---|
| Workflow ID 唯一性 | Temporal 保证同一 Namespace 内同一 Workflow ID 最多一个 Open 执行；`WorkflowIdConflictPolicy` 可选 Fail / Use Existing / Terminate Existing | 用业务单号作为 Workflow ID，天然防重复发起 |
| 资源池槽位 | Airflow pool 用 slots 限制任意任务集合的并行度；`pool_slots=1` 等价于该资源互斥，拿不到槽位就排队 | 作业型工具按资源建池，而不是全局串行 |
| 循环并发度 | Power Automate Apply to each 默认顺序，可设 1–50；嵌套循环内层始终顺序 | UI/向导动作默认并发度 1 |
| 数据库行锁 / 咨询锁 | PostgreSQL `SELECT ... FOR UPDATE` 锁行；advisory lock 可表达应用级互斥；死锁靠一致加锁顺序规避；**不要在等待人工时长时间持有事务锁** | 任务状态推进、发布等强一致场景 |
| 乐观锁 | EF Core 用 concurrency token：更新时带版本条件，0 行受影响就抛 `DbUpdateConcurrencyException`，由应用重读/重试/提示冲突 | 向导步骤推进、任务版本更新 |
| 分布式锁 | Redis `SET key value NX PX ttl`，随机值 + 比较后删除；Redlock 多数派；官方明确建议 **fencing token**，并提示时钟漂移风险 | 跨实例互斥；必须配租约续期和 fencing |
| 唯一约束作为仲裁者 | Azure Idempotent Consumer：不要 check-then-set，直接用唯一索引/原子插入，让数据库裁决并发重复 | 创建任务、作业去重 |
| 会话级门 | 当前仓库 `SessionGate` 已做同 `sessionId` 单轮互斥，带 Redis 锁 + watchdog + 进程内降级 | 防止同一会话两轮并发，但不覆盖“两个会话操作同一 task” |

关键点：**锁要带租约、持有者标识、fencing token**；拿不到锁应返回 `BUSY/QUEUED`，而不是让模型“稍后重试”或直接执行。

### 2.3 失败时如何拒绝、重试、补偿，而不是盲目继续

先把失败分成三类：

1. **确定未发生**：连接未建立、请求被拒、前置校验失败 → 可安全重试或直接拒绝。
2. **确定已发生**：收到成功回执、读回状态一致 → 不重试，进入验证/完成。
3. **结局未知**：超时、连接中断、进程崩溃、只拿到 jobId 没拿到终态 → **不能当失败重试**，必须先对账/读回。

| 模式 | 官方要点 | 借鉴 |
|---|---|---|
| 重试策略 | Temporal 默认重试 Activity，支持指数退避、最大间隔、最大次数、`non-retryable` 错误；Azure Retry 强调只重试瞬态故障，且操作必须幂等 | 只有 `FAILED_NO_EFFECT` 且 `retryable=true` 才重试；参数/权限/业务规则错误直接失败 |
| 熔断 | Azure Circuit Breaker 的 Closed / Open / Half-Open 状态机；达到失败阈值后快速拒绝，恢复期放少量探测 | 下游持续失败时停止派发，保护资源并升级告警 |
| 错误分支 | Step Functions `Retry` + `Catch`；Dify 节点 `None / Default Value / Fail Branch`；n8n `Stop Workflow / Continue / Continue using error output`；Power Automate `Run after` + Scope try/catch | 失败不是“返回一段错误字符串继续”，而是进入显式失败分支 |
| Saga 补偿 | 每个本地事务配补偿事务；失败按**逆序**执行补偿；区分 compensable / pivot / retryable；补偿可能失败，需人工兜底 | 导入/发布这类跨步骤操作要有补偿或“不可补偿”声明 |
| 补偿注册时机 | Temporal 建议**在执行前注册补偿**，并让补偿幂等；补偿失败要记录并继续其余补偿，最终告警人工 | `start_import` 写暂存前就登记“清理暂存”；`start_publish` 若不可逆则明确标记为 pivot |
| 人工升级 | Temporal HITL 用 Signal + `wait_condition(timeout)` 等待审批，支持长时间无计算资源占用；Dify Human Input 有审批按钮和超时分支 | 审批/拒绝/超时是状态机的一等状态，不是异常日志 |

### 2.4 如何防止 AI 重复触发同一副作用

这是 AI 执行器最容易漏的一层。传统幂等键防的是“同一个 HTTP 请求重试”；AI 还会出现：

- 同一轮模型重复发出同一个 tool call；
- 下一轮模型“重新规划”后又发一次，`toolCallId` 变了；
- 并行工具调用同时打同一个资源；
- 工具超时，但副作用其实已经发生；
- 前端工具超时，文件已经落盘/表单已经提交。

| 机制 | 官方要点 | 借鉴 |
|---|---|---|
| Idempotency-Key | Stripe：客户端生成唯一 key，服务端保存首次响应；同 key 重试返回原响应；参数不一致报 `idempotency_error`；key 有保留期 | 为每次“逻辑操作”生成 key，而不是只为 HTTP 请求生成 |
| Idempotent Consumer | Azure：稳定去重键；去重标记与副作用同一事务；唯一约束做并发仲裁；外部调用用 `in-progress → completed` 两阶段；记录 TTL 要覆盖重投窗口 | 工具执行台账应保存 `in-progress/completed`，而不只是“执行过” |
| Transactional Outbox | 业务数据与待发消息同一数据库事务提交；中继可能重复发送，所以消费者必须幂等 | 先落“执行意图 + 幂等键 + 参数摘要”，再派发外部副作用 |
| Tool call 关联 | OpenAI `call_id`；Anthropic `tool_use` / `tool_result`；MCP `isError` | 同一 `toolCallId` 的重放可直接复用结果 |
| 关闭并行工具调用 | OpenAI `parallel_tool_calls=false` 保证一轮最多一个工具调用 | 有副作用的工具默认关闭并行；只读工具才允许并行 |
| MCP 注解 | `readOnlyHint`、`destructiveHint`、`idempotentHint`、`openWorldHint` 只是 **hints**；规范明确说客户端不应基于不可信服务器的注解做工具使用决策 | 注解可用于披露/排序，但**不能作为执行器唯一防线** |
| AI 中断的副作用规则 | LangGraph `interrupt()` 恢复时节点会从头重跑；官方明确要求 interrupt 之前的副作用必须幂等 | 审批前不要做不可逆写；把副作用放到 interrupt 之后或独立节点 |
| 人工审批作用域 | OpenAI Agents SDK 的审批按 `call_id` 作用域；`always_approve` 会粘滞；参数无法解析时 fail closed | 审批决定要绑定具体调用和参数，不能只按工具名放行 |

### 2.5 把“检查—执行—验证—修复/升级”做成状态机

建议的统一状态机（比当前 `PENDING/APPROVED/EXECUTED` 多出“派发后未知”和“验证/补偿”两段）：

```text
PROPOSED
  ├─ 前置检查失败 ──────────────→ REJECTED_PRE
  ├─ 需要人工 ─→ AWAITING_APPROVAL
  │                 ├─ 拒绝 ───→ REJECTED
  │                 ├─ 取消 ───→ CANCELLED
  │                 └─ 超时 ───→ EXPIRED
  └─ 自动/已批准 ─→ READY
READY
  ├─ 资源被占用 ───────────────→ BUSY / QUEUED
  └─ 取得租约 + 持久化意图/幂等键 → DISPATCHED
DISPATCHED
  ├─ 收到回执/handle ──────────→ RUNNING
  └─ 无回执/超时 ──────────────→ UNKNOWN_OUTCOME
RUNNING
  ├─ 终态成功 ─────────────────→ VERIFYING
  └─ 终态失败 ─────────────────→ FAILED
VERIFYING
  ├─ 读回一致 ─────────────────→ SUCCEEDED
  ├─ 可修复的不一致 ───────────→ REPAIRING → VERIFYING
  └─ 无法判定 ─────────────────→ RECONCILING
UNKNOWN_OUTCOME / RECONCILING
  ├─ 确认已成功 ───────────────→ SUCCEEDED
  ├─ 确认未发生 ───────────────→ READY（才允许重试）
  └─ 无法确认 ─────────────────→ MANUAL_ESCALATION
FAILED
  ├─ 确定未发生且可重试 ───────→ READY
  ├─ 确定未发生且不可重试 ─────→ FAILED_FINAL
  └─ 可能部分发生 ─────────────→ COMPENSATING
COMPENSATING
  ├─ 补偿成功 ─────────────────→ COMPENSATED
  └─ 补偿失败 ─────────────────→ MANUAL_ESCALATION
```

六条不变量：

1. **`DISPATCHED` 必须先于外部调用持久化**，且同一事务写入幂等键、参数摘要、资源键。
2. **`UNKNOWN_OUTCOME` 不是失败**，禁止直接重试；必须先按业务键对账/读回。
3. **只有 `FAILED_NO_EFFECT` 才可重试**；`FAILED` 若可能部分生效，只能补偿或升级。
4. **状态迁移用 CAS/版本号**，同一资源同一时刻只有一个 owner；跨实例用租约 + fencing token。
5. **补偿按 LIFO、幂等、可失败**；补偿失败是人工升级，不是静默吞掉。
6. **人工决策是一等状态**，要有 `APPROVED/REJECTED/CANCELLED/EXPIRED` 和审计记录。

建议工具结果契约至少包含：

```json
{
  "ok": true,
  "status": "SUCCEEDED | FAILED | UNKNOWN | REJECTED | EXPIRED | BUSY",
  "effect": "NONE | APPLIED | UNKNOWN",
  "retryable": false,
  "idempotencyKey": "task:45:publish:req-7f3a",
  "handle": { "jobId": 123, "taskId": 45, "version": 7 },
  "evidence": { "jobStatus": "COMPLETED", "fileExists": true }
}
```

模型看到 `effect=UNKNOWN` 时应停止，由执行器对账，而不是“再试一次”。

## 3. 成熟工程模式 vs AI 产品特有做法

| 能力 | 成熟工程模式 | AI 产品特有做法 | 结论 |
|---|---|---|---|
| 执行单元 | Workflow / Activity / DAG Task / State | 一轮对话、一次 tool call、agent loop | 把 tool call 映射为持久化 Activity，不要只存在上下文里 |
| 顺序 | DAG 边、trigger rule、run after | 模型自行决定下一步 | 顺序必须外置到执行器/状态机 |
| 互斥 | Workflow ID、pool slot、DB lock、advisory lock | session gate、per-call approval | 会话互斥不够，要补资源级互斥 |
| 幂等 | 业务幂等键、outbox、inbox、唯一约束 | `toolCallId`、`parallel_tool_calls` | 两者都要：`toolCallId` 防同轮重放，业务键防跨轮重复 |
| 人工 | Approval、HITL task、callback token | interruptions、RunState、elicitation | AI 的审批交互可以复用成熟状态机 |
| 验证 | 读回、断言、对账、补偿 | guardrails、output validation | guardrails 不能替代业务读回；输入 guardrail 默认并行时可能已执行工具 |
| 失败 | retry policy、circuit breaker、saga | 模型自我修复/重新规划 | 不能信任模型判断“是否需要重试” |
| 可观测 | Event History、task state、audit log | trace、tool call 日志 | 需要统一的执行台账和状态迁移审计 |

AI 产品真正新增的，不是“分布式事务”本身，而是：

- **不确定性入口**：模型可能重复、并行、误解结果、重新规划；
- **交互式暂停/恢复**：审批、表单、澄清；
- **自然语言参数**：同一意图可能生成不同参数，导致“业务上同一操作、技术上不同请求”；
- **工具描述影响行为**：schema 和 description 会改变模型是否/如何调用。

所以结论是：**底层用成熟工程模式，交互层用 AI 特有原语；不要把 AI 原语当成执行正确性的保证。**

## 4. 当前 18 工具可借鉴的分类模板

### 4.1 先纠正一个前提：不能按 `ToolRisk` 标签分类

`AiTools.java` 中 `ToolRisk` 只有 `READ / WRITE / DANGER`，`ToolChannel` 只有 `BACKEND / FRONTEND`（`ai/tool/ToolMeta.java:20`、`:29`）。但**前端通道的 7 个工具全部标了 `READ`**，真实行为却有明显副作用：

- `confirm_step` 会推进向导并落库；
- `download_export_files` 会触发浏览器下载/打包；
- `navigate_to` 会改变工作区路由；
- `select_definitions` / `set_condition` 会改向导表单状态；
- `open_export_file_editor` 会打开编辑器；
- `generative_form` 会挂起等待用户输入。

所以分类维度应是：**真实副作用 + 执行通道 + 是否可逆 + 是否需要人工 + 资源粒度**，而不是风险标签。

### 4.2 七类模板

| 类 | 判定标准 | 默认执行模式 | 互斥键 | 幂等/验证 | 18 工具 |
|---|---|---|---|---|---|
| **R 纯读** | 不改任何状态；只查数据库/作业状态 | 可并行；必要时限流 | 无 | 直接重试；只读结果可缓存 | `list_config_defs`、`get_config_def`、`list_tasks`、`get_workspace_state`、`check_job_status`、`get_row_count` |
| **W 创建写** | 插入一条业务记录，返回 id | 自动或低风险确认；按业务键去重 | `clientRequestId` 或 `(session,type,title)` | 唯一约束；重复返回已有 id；读回任务存在 | `create_task` |
| **J 异步作业** | 创建 Job 并异步执行，可能产生文件/暂存写 | 确认 + 单飞 + 等待终态 | `taskId:jobType` | 业务幂等键；查 Job 终态；验证产物/行数 | `start_export`、`start_precheck`、`start_import` |
| **P 不可逆生产写** | 写生产数据，失败可能无法回滚 | 确认 + 独占 + **禁止盲重试** | `scope/defCode` 或 `taskId:PUBLISH` | 读回生产结果；未知结局转人工；尽量设计补偿 | `start_publish` |
| **U 向导/UI 状态** | 改前端路由、选择、条件、步骤 | 按会话/任务串行 | `sessionId` 或 `taskId:wizard` | 目标状态幂等；读回当前页面/步骤/选择 | `navigate_to`、`select_definitions`、`set_condition`、`confirm_step`、`open_export_file_editor` |
| **F 文件/下载** | 触发浏览器下载或生成文件 | 按 artifact 单飞 | `taskId + defCodes + artifactVersion` | 验证文件存在/大小/校验和；重复返回同一 artifact | `download_export_files` |
| **H 人工输入** | 挂起等待用户填写/选择/取消 | 交互独占；不自动重试 | `sessionId/formId` | schema hash；accept/decline/cancel/timeout；不把超时当失败 | `generative_form` |

### 4.4 对当前实现的直接启示（只给模板，不施工）

当前仓库已经有不错的基础：

- `SpToolCallingManager.executeOnce` 已按 `toolCallId` 做跨进程台账与原子认领（`ai/gate/SpToolCallingManager.java:348`）；
- `ConfirmGate` 已有批准/拒绝/超时三结局；
- `SessionGate` 已做同会话单轮互斥；
- `JobService.createAndStart` 已有同任务同类型在途守卫 `JOB_ALREADY_RUNNING`（`job/service/JobService.java:124`、`:160`）。

但按上面的模板，仍有几个“位”需要补：

1. **`ToolRisk.READ` 不足以描述前端真实副作用**：建议增加正交的 `effectClass`（NONE / UI_STATE / ARTIFACT / JOB / PRODUCTION_WRITE），不要继续用 READ 覆盖。
2. **`toolCallId` 去重只覆盖“同一次调用重放”**：模型跨轮重新发起时 `toolCallId` 会变，需要业务幂等键 + 唯一约束/单飞。
3. **`start_*` 当前只返回 jobId 并提示“稍后查看”**：应在执行器侧增加 `DISPATCHED → WAIT_JOB → VERIFYING`，不能让模型自由决定何时查。
4. **`SessionGate` 是会话级，不是资源级**：两个会话操作同一 `taskId` 仍可能并发；应补 `taskId:jobType` 租约。`JobService` 的在途守卫是 check-then-act，并发窗口最好由唯一索引/行锁兜底。
5. **`PendingToolCall` 状态止于 `EXECUTED`**：建议增加 `DISPATCHED / UNKNOWN_OUTCOME / VERIFYING / COMPENSATING / MANUAL_ESCALATION`。
6. **前端工具超时的语义要保留**：当前注释已正确指出“前端超时只说明回执没回来，结局未知”；模板应把这一点固化为 `effect=UNKNOWN`，不要当失败重试。
7. **`start_publish` 应明确标为 pivot/不可逆**：确认、独占、禁止盲重试、读回生产、失败升级人工，不能与 `start_export` 同一套重试策略。
