## 3. convergeMemory（`ai/run/ResilientChatService.java`）

原文（`:572-609`）：

```java

594	/**
595	 * 窗口裁剪的配对保护（SM-01 的判据）：窗口首条不得是孤立的 {@code TOOL} 消息 ——
596	 * 它的 {@code assistant(tool_calls)} 若被裁掉，下一次请求会因"tool 没有对应的 tool_calls"
597	 * 被上游拒绝（400）。裁剪点从需要丢弃的位置起向后推到第一个非 {@code TOOL} 消息，
598	 * 即"tool 配对整体保留"。
599	 */
600	private List<Message> trimKeepingToolPairs(List<Message> messages, int maxMessages) {
601		if (maxMessages <= 0 || messages.size() <= maxMessages) {
602			return messages;
603		}
604		int drop = messages.size() - maxMessages;
605		while (drop < messages.size() && messages.get(drop).getMessageType() == MessageType.TOOL) {
606			drop++;
607		}
608		return new ArrayList<>(messages.subList(drop, messages.size()));
609	}
```

事实要点：

- **每轮整窗口重写**：是。`clear + add`（`:586-587`）经 `MessageWindowChatMemory` 落到仓储 `saveAll`，而 `saveAll` 的语义是 `DEL` + 批量 `RPUSH` + `EXPIRE` + `SADD`（`RedisChatMemoryRepository:156-167`），其 javadoc 自陈「整窗口覆盖写…与官方 2.0 实现 `saveAll`（内部 clear + add）的『整窗口覆盖写』语义一致」（`:43-45`）。`clear` 走 `deleteByConversationId`（Lua `DEL`+`SREM`）。
- **收敛时机**：`finish`（`:467`，先 `history.add(AssistantMessage.builder().content(text).build())` 再收敛）、`emptyReply`（`:508`）、`cancelTerminal`（`:530`）三处；**`fail()`（`:546-570`）不收敛记忆**（只改快照状态/error）。⇒ 取消终局也会把「本轮已落定的历史」写进记忆。
- **裁剪从头丢**：是。`drop = size - maxMessages` 后 `subList(drop, size)`（`:604`、`:608`），上界 = `app.ai.memory.max-messages: 40`（`application.yml:111`；默认值 `AiProperties.java:98`；`AiModelConfig:81-88` 把同一数字装进官方 `MessageWindowChatMemory`）。
- **是否保证不裸 TOOL**：保证**窗口首条不是 TOOL**（`:605-607` 把 drop 向后推）。推论性事实：若 `drop` 起至末尾全是 TOOL，`drop` 可推进到 `messages.size()`，返回空列表（该走查结论被文档引用：`docs/evidence/补档-CHATTIMELINE-批2-复核报告-GLM-5.3.md:78`「本仓 `convergeMemory` 的全 TOOL 尾裁剪产出空 `windowed` 的走查结论【推断】合理」）。注意该循环只保护「首条非 TOOL」，不做别的配对校验；`convergeMemory` 无异常外抛（`catch` 只 WARN，`:589-591`），收敛失败时记忆保持旧窗口。
- 记忆窗口上界实际叠加了两道：官方窗口（`maxMessages=40`）自身在每次 `add` 时也会裁剪（`docs/03-技术方案文档-v2.1.md:290-292`），本仓 `trimKeepingToolPairs` 是第二道。

## 事实性总结（不含建议）

1. HEAD = `4260651`（与草案预期一致）；工作树 6 改 4 新增，本报告全部证据取自 `git show HEAD:`。
2. 读取侧就是 `AiController:509-533` 的 25 行方法：把 `chatMemory.get(sessionId)` 的 Spring AI `Message` **逐条 1:1** 映射为 `Map`，无任何转换/合并/DTO，无鉴权、无 session 归属校验；TOOL 与 ASSISTANT 是各自独立的条目。
3. 存储层是「一 Message = 一个 Redis LIST 元素」，`type` 取自 `MessageType.name()`，编解码覆盖 SYSTEM/USER/ASSISTANT/TOOL 四值（记忆 LIST 被 `convergeMemory` 过滤掉 SYSTEM）；工具轮 ASSISTANT 的实测快照 `content` 为空串，但编解码层本身只做 `put("content", getText())`，不强制空串；`toolCalls` 为顶层数组 `{id,type,name,arguments}`。
4. `convergeMemory` 每次轮终态**整窗口覆盖写**（`clear + add` → 仓储 `DEL + RPUSH`），裁剪**从头丢**且首条不会是裸 TOOL（推进 drop 越过 TOOL）；`fail()` 不收敛记忆。
5. `SpToolCallingManager` 内不存在「只落 ASSISTANT(tool_calls) 不落 ToolResponse」的写点：assistant 仅与 `ToolResponseMessage` 成对写入（`:198-203` `settle`）；挂起期 assistant 只存 `assistantContent`/`inFlightToolCalls`（`:162`），取消/异常路径整对丢弃。
6. resume 追加 assistant 的唯一条件是 `inFlightToolCalls` 非空，且随后立刻补 `ToolResponseMessage`（`ResumeService:299-321`）；取消优先级最高、终态直接返回，均不追加；重试不追加任何 assistant 消息。**提交态代码中未发现「取消/中断后 resume 追加新 ASSISTANT 造成相邻 ASSISTANT 条目」的路径。**
7. 该历史端点的生产消费方**只有前端 `loadHistory`**（`stores/ai.ts:638`，`api/ai.ts:64`，类型 `types/ai.ts:133-150`）；其余消费方为前端测试桩、两个脚本（`verify-e2e.ps1` / `chat-panel-smoke.mjs`）与约 20 份文档，后端无内部消费方、无端点级测试（仅 DELETE 有测试）。
8. 后端没有历史 DTO/视图模型；载荷只携带 `type/text/toolCalls{id,type,name,arguments}/toolResponses{id,name,responseData}/timestamp`，配对键两侧同名为 `id`，且不含任何工具执行状态字段（该缺口已在 R-141②/R-144 登记）。
