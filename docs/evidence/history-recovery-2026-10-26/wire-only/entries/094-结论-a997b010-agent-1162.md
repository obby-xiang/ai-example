## 2. `maybeTriggerResume` 的完整判据

`ConfirmGate.java:564-596`：

| 顺序 | 判据 | 不满足时 outcome | 行号 |
|---|---|---|---|
| 1 | `woke == true`（本进程内该 toolCallId 的 latch 被 `signal` 成功） | `WOKE_IN_PROCESS_GATE` | `:565-567` |
| 2 | `!hasActiveLatch(runId)`：本进程内没有任何 `runId|` 前缀的 latch | `ACTIVE_LATCH_IN_PROCESS` | `:568-571`，实现 `:620-631` |
| 3 | 快照存在且 `status == SUSPENDED` | `SNAPSHOT_NOT_SUSPENDED` | `:572-576` |
| 4 | `resumeServiceProvider` 与 `resumeTriggerExecutor` 非空 | `NO_RESUME_SERVICE` | `:577-579` |
| 5 | `provider.getIfAvailable() != null` | `NO_RESUME_SERVICE` | `:580-582` |
| 6 | 投递到 `resumeTriggerExecutor` | `EXECUTOR_SATURATED` / `DISPATCH_FAILED` | `:583-595` |

**幂等性**：触发端**没有**任何 in-flight / 已派发去重判据，也没有“登记中”判据。每次 `ACCEPTED` 的外部输入且 `woke=false` 都可能再派发一次；去重完全依赖下游：
- `ResumeService` 的 runId 锁：第二个并发 resume 得到 `IN_PROGRESS`（`ResumeService.java:220-224`）；
- 状态判据：`DONE/FAILED/CANCELLED` → `ALREADY_DONE`（`:257-264`）、`RUNNING` → `ALREADY_RUNNING`（`:265-270`）、仍 `PENDING` 的外部项 → `PENDING_UNRESOLVED`（`:284-293`）。

这些都发生在**已经派发并进入锁之后**，不能阻止 `maybeTriggerResume` 把任务派出去，也不能区分“本进程正在挂起登记”与“真的无人等待”。

**关键缺陷**：判据 2+3 的组合把“刚 `saveSuspended`、latch 未登记”与“重启后无人等待的死卡”视为同一种状态。注释 `:548-550` 明确写了 R4③ 毫秒窗，但 `hasActiveLatch` 在 latch 尚未存在时只能返回 false，无法承担它声称的防护职责。

## 3. `claimExecution` 与 `ResumeService` 的 runId 锁

### 3.1 `claimExecution`（`RunStore.java:427-441`）

- 实现：对 `ai:claim:<runId>` HASH 做 `putIfAbsent(toolCallId, instanceId)`（`:428`，Redis HSETNX 语义），并续 `expire`（`:429`）。
- 认领成功（`:430-439`）后写入同一条目：`claimedAtMs=now`、`executed=true`、`executedBy=instanceId`。**认领发生在执行之前**。
- 保证的语义：**副作用跨实例最多一次**。`SpToolCallingManager.executeOnce` 先查台账复用（`:349-358`），再认领（`:360-370`），失败即不执行。
- 不保证的语义：
  - **不防重复“续跑/双驱动”**：它只保证工具体最多执行一次，不阻止两个驱动线程各自继续模型循环、各发帧、各写快照。
  - **不保证恰好一次（exactly once）**：认领后进程死亡，`executed=true` 已落库，`ResumeService.resolvePending` 不会补执行（`SpToolCallingManager.java:438-440`，`EXECUTED && !executed` 才执行），结果可能是“从未执行”。
  - 认领后的条目是用“读—改—写”整对象回写（`:432-437`），不参与决策状态机的事务。

### 3.2 `ResumeService` 的 runId 锁（`ResumeService.java:409-439`）

- 两层：进程内 `Map<String,Boolean> resuming` 的 `putIfAbsent`（`:410-412`），加 Redis `ai:resume:lock:<runId>` 的 `setIfAbsent(instanceId, ttl)`（`:415-420`）。
- **锁住了什么**：`resume()` 的入口到真正驱动结束——`acquire` 在 `:221`；正常交给 `suspendExecutor` 后，在驱动任务 `finally` 中释放（`:351-354`）；未交出去则在 `finally` 释放（`:368-372`）。因此 **resume 对 resume** 被串行化。
- **没锁住什么**：
  - **原进程正在跑的官方循环**：它从不获取这把锁；`AiController` 的 `SessionGate`（`AiController.java:178`）也不被 `ResumeService` 使用。F8 中 resume 与原循环可并行。
  - TTL = `app.ai.resilience.total-budget`（默认 300s，`application.yml:141`；`AiProperties.java:176`），**没有续期**；驱动超过 300s 后锁过期，理论上可出现第二个 resume（之后仍会被 `RUNNING` 状态挡住，除非 `forceTakeover`）。
  - 释放是 `get` 后 `delete` 的非原子组合（`:430-434`）；Redis 异常时降级为仅进程内锁（`:422-424`），跨实例保护消失。
  - 不锁 `StartupResumeRunner.scan` 的读取（`StartupResumeRunner.java:101`），只锁每个 `resume` 调用。

## 6. 最小修法候选

以下只列修改点与影响面，不写代码。

### 候选 a（推荐，本地确定性修复）：让闸门登记先于 `suspended` 帧

- **修改点**
  1. `ConfirmGate.java:203-206`：`await()` 改为复用已登记的 latch（例如 `computeIfAbsent`），而不是无条件 `new Latch()` 覆盖。
  2. `ConfirmGate.java:615-641` 附近新增 `arm(runId, toolCallIds)` / `disarm(...)`（或返回句柄）：为**仅 `KIND_CONFIRM`/`KIND_FRONTEND`** 的条目预登记 latch。
  3. `SpToolCallingManager.java:156-180`：在 `saveSuspended`（`:179`）之前（最迟在 `out.suspended` `:180` 之前）对整批需要等待的条目 `arm`；在 `executeToolCalls` 的异常/提前返回路径（如 `:194-196` 的 scope 拦截、`:186` 的取消抛出）与未被 `await` 消费的条目上 `disarm`，避免 latch 泄漏使 `hasActiveLatch` 永真。
- **影响面**
  - 窗口从“帧发出 → latch put”缩短为零：帧发出时 `hasActiveLatch(runId)` 已为 true，`maybeTriggerResume` 直接返回 `ACTIVE_LATCH_IN_PROCESS`。
  - 需要处理 `saveSuspended` 抛异常时的回滚（`RunStore.java:361-362` 会抛）。
  - 批内所有条目一次性受保护，消除“前一个 latch 已删、下一个未登记”的空档。
  - **测试影响**：
    - `ConfirmGateDeadlockResumeTest`：`awaitDecision` 直接调用的用例仍可走 `computeIfAbsent` 回退，①③④⑤⑥⑦⑧⑨预期不变；需新增“arm 后、await 前提交 → 不触发续跑”的用例。
    - `ConfirmGateWiringTest`：`ConfirmGate` 是 mock，新增 `arm` 应为 void 或提供默认空实现，否则 mock 返回 null 会导致 NPE；`saveSuspended`/`suspended` 的既有断言不受影响。
    - `ToolFrameSequenceConformanceTest` / `FrameContract`：帧序不变（`suspended` 仍在 `tool_start` 前），但必须确保 latch 在 `await` 结束后释放，否则后续用例或同轮第二个条目行为改变。
    - `ConfirmGateFrontendTimeoutTextTest`：直接 `awaitDecision`，回退路径不变。
  - 局限：只解决**同实例**的登记前点击；多实例下确认请求被路由到没有 latch 的实例时仍会误触发（见候选 c）。

### 候选 b（判据加宽）：给 `maybeTriggerResume` 增加“登记中 / 派发中”判据

- **修改点**
  1. `ConfirmGate.java:564-596`：在判据 2 之前增加“挂起登记进行中”判据（例如 `SpToolCallingManager` 在 `saveSuspended` 前设置 `runId` 级 marker，`await` 登记完成后清除；或使用 `snapshot.updatedAtMs` 的新鲜度宽限，要求 `now - updatedAtMs > 宽限` 才允许触发）。
  2. `ConfirmGate.java` 字段区（`:115-128`）增加派发去重/in-flight 集合，避免同一 run 连续派发多个 resume。
  3. `ConfirmGate.java:599-612` 的 `runResume` 在调用 `resume` 前再查一次 `hasActiveLatch`（只能缩小、不能消除竞争，但能吃掉“检查后立即登记”的常见调度）。
- **影响面**
  - 时间宽限方案会**延迟真实的死卡恢复**（仅外部输入触发的路径），且依赖时钟/调度，属于启发式；marker 方案在进程于 marker 设置后崩溃时会卡住恢复，必须带 TTL 或超时兜底。
  - 去重集合只能防 resume 重复，不能防“原循环 + resume”双驱动。
  - **测试影响**：
    - `ConfirmGateDeadlockResumeTest:96-112` 的 `snapshot()` 辅助（`:333-339`）没有设置 `updatedAtMs`（为 0），新鲜度判据会把它当“旧挂起”从而仍然触发；若采用 marker，需为死卡用例显式声明“无登记中标记”，并新增“登记中 → 不触发”的用例。
    - 其余用例的断言大多只关心 outcome，预计可保留；⑦⑧ 与派发去重可能冲突（同一测试内多次提交），需要隔离。

### 候选 c（更优，跨实例）：用“驱动存活租约”替代/补强进程内 latch 判据

- **思路**：`hasActiveLatch` 是**进程内**判据，既覆盖不了登记前窗口，也覆盖不了“确认 POST 落到另一实例”的分布式误判。可以引入一个跨进程的“该 run 仍有驱动”证据，`maybeTriggerResume` 见到它就跳过：
  - 方案 c1（复用现成设施）：读 `SessionGate` 的 Redis 锁 `ai:session:lock:<sessionId>`（`SessionGate.java:42,70-95`）。该锁由正在跑的轮持有、watchdog 每 30s 续期 10m TTL（`application.yml:154-157`），值就是 `runId`；轮终态才释放（`AiController.java:204,211`）。若锁值 == 当前 `runId`，说明原轮仍活着，禁止死卡兜底。需要把 `SessionGate`（或一个只读查询）注入 `ConfirmGate`，或在 `RunStore` 暴露只读方法；`ConfirmGate` 已能从快照取 `sessionId`（`:157-166`）。
  - 方案 c2（更精确、TTL 更短）：新增 `ai:driver:<runId>` 心跳租约，在 `saveSuspended` 前写入、在 `ConfirmGate.await` 的心跳拍（`:240-249`）续期、在 `settle`/终态清除；`maybeTriggerResume` 读到租约即跳过。这样连“登记前”也被覆盖，因为租约在帧发出前就已存在。
- **影响面**
  - **关闭两类缺口**：同实例登记前窗口 + 多实例确认请求误路由；且不依赖 latch 的进程内可见性。
  - c1 的代价：崩溃后会话锁最长残留 10m，外部输入触发的死卡恢复会被延迟到锁过期；`StartupResumeRunner` 路径不受影响（它不走 `maybeTriggerResume`）。
  - c2 的代价：新增一个 Redis 键与续期/清理生命周期；若驱动线程卡死但心跳仍续期，会抑制恢复，需要心跳停止条件与 TTL 兜底。
  - **测试影响**：
    - `ConfirmGate` 构造器/依赖变更会波及 `ConfirmGateDeadlockResumeTest`（`:82-83` 直接 `new ConfirmGate(...)`）、`ConfirmGateWiringTest` 的 mock 装配，以及任何直接构造 gate 的测试；需要补“锁/租约存在 → 不触发（`LIVE_DRIVER_ELSEWHERE`）”和“锁过期 → 触发”的用例。
    - 死卡用例 ② 需要显式让锁/租约不存在（mock 返回 null/false），否则会从“触发”变为“跳过”。
    - 无 `ResumeService` 测试类，无需改动其测试；`AiController` 测试若构造 gate 需同步依赖。

**优先级建议**：a 是成本最低、能确定性关闭本进程窗口的修复；c（尤其 c2）是唯一能同时覆盖“登记前”和“多实例误路由”的方案；b 单独使用只是缩小竞争面，不建议作为唯一修复。
