## B. 写点候选核验

**B4. `convergeMemory` 入参来源与 3 调用点可得状态源**（`ResilientChatService.java`）

- 定义 :576-592，签名 `convergeMemory(String sessionId, List<Message> history)` —— **只有 sessionId + history，拿不到 runId**；调用方持有 runId。收敛动作 = `chatMemory.clear(sessionId)` + `add(sessionId, windowed)`（:586-587），失败仅 WARN（:589-591）。
- 三调用点全部在 `if (snapshot != null)` 内，且**均在清空 in-flight 之后**收敛：
  - `finish:454-467`：`history = new ArrayList<>(codec.deserializeAll(snapshot.getMessageJson()))`（:457）+ 新追加一条无 metadata 的最终 assistant（:458）；:460 `setInFlightToolCalls(new ArrayList<>())`；:467 converge。
  - `emptyReply:496-508`：同源 deserialize（:498），不新增消息；:500 清 in-flight；:508 converge。
  - `cancelTerminal:520-530`：同源 deserialize（:522）；:523 清 in-flight；:530 converge；**:532 才 `store.cancelPendings(runId)`**（即收敛时点该轮条目在 Redis 里可能仍为 PENDING）。
- `RunSnapshot` **不存任何条目级 status**（字段仅 `messageJson / assistantContent / inFlightToolCalls / status / round / …`，:65-105；`inFlightToolCalls` 在三个终局分支均已清空）。最终 status 的真源 = Redis `ai:pending:<runId>` HASH（`RunStore.putPending:371-380`）；台账 `ledger` **无 status 字段**（`appendLedger:449-465` 只有 atMs/executedBy/toolCallId/name/kind/resultText）。
- 结论：**convergeMemory 本体拿不到 PendingToolCall 最终 status**；要写只能 (a) 由调用方把 `store.pendings(runId)` 的终态传入/嵌入，或 (b) 状态已随消息 metadata 预先落在 `messageJson` 里。cancelTerminal 分支若走 (a)，:530 早于 :532，本轮 PENDING 条目此刻不可靠。

**B5. settle 时点状态可知性 / settle 写 metadata 是否自然流入收敛**（`SpToolCallingManager.java`）

- `settle:459-470`，:464 `snapshot.setMessageJson(this.codec.serializeAll(history));`，:465 清 in-flight，:467 回 RUNNING。调用点 `:198-203`：`history = prompt.getInstructions() + assistant + toolMessage`（:200-202），**`pendings` 列表在该作用域内**。
- 状态可得性：BLOCKED（:235）、REJECTED_ARGUMENTS（:298）、BACKEND 的 EXECUTED（:377）都是**就地写在传入对象上**；而 CONFIRM/FRONTEND 走 `await*`，返回的是**从 Redis 读回的 fresh 副本**（`ConfirmGate:226-234` `fresh = this.store.pending(...); if (fresh.resolved()) return fresh;`），**外层 `pendings` 元素不会被回写** ⇒ 该列表对象对这两类可能过期，需 `store.pending(runId, id)` 复读（`RunStore:396`）。**「settle 前状态即已知」成立，但真源是 Redis 而非局部列表。**
- 同一份 List？`settle` 序列化进 `messageJson` 的就是随后交回官方循环继续跑的 `history`（:205 `conversationHistory(history)`）；终局三处都是 `deserializeAll(snapshot.getMessageJson())` 后再收敛（:457 / :498 / :522）⇒ **内容同源**（对象身份非同一，是再反序列化的副本），metadata 经序列化保真 ⇒ **settle 写 metadata 能自然流入 convergeMemory**。
- 未覆盖面：取消发生在工具执行中时 `checkCancelled` 在 :169/:192 抛异常，**:203 的 settle 不执行**；此时快照里的挂起轮仅以字段形式存在（`saveSuspended:354-369`：`assistantContent` 文本 + `inFlightToolCalls` + `messageJson = prompt.getInstructions()`），**messageJson 里没有那条 assistant(tool_calls) 消息对象**可挂 metadata。

**B6. 取消路径终态可知时点 / resume 重建路径状态**

- 整轮取消：`ConfirmGate.cancel:274-297` 在返回前 `setStatus(CANCELLED)`（:280，reason=RUN_CANCELLED）；轮级扫尾 `RunStore.cancelPendings:535-550`（仅改仍 PENDING 者，:538-541），调用点 `ResilientChatService.cancelTerminal:532`、`ResumeService:249`。
- 超时：`ConfirmGate.expire:310-325`（:318 TIMEOUT；CONFIRM_TIMEOUT / FRONTEND_TIMEOUT 靠 :319 区分）。
- 前端放弃：`ConfirmGate.dismiss:515-522`（:516 FRONTEND_CANCELLED）。
- 轮终态：`RunSnapshot.CANCELLED`（`:525`）、`DONE`（`:463`）、`FAILED`（`:503`/`:559`）。
- resume 重建（`ResumeService:295-326`）：:296 history 取自 `snapshot.messageJson`；:301-302 用 `rebuildAssistant(snapshot)` 重建 assistant —— `:395-405` **builder 不设 `properties(...)`**；:320 `ToolResponseMessage.builder().responses(...)` **不设 metadata**；逐条状态以 Redis 为准（:308 `fresh = this.store.pending(...)`），结算走 `resolvePending:419-431`（仅 APPROVED / PENDING+BACKEND / EXECUTED&&!executed 才执行）。
- 执行后的状态事实：`executeOnce:376-379` **仅 KIND_BACKEND 落 EXECUTED**；确认门放行的 DANGER 工具执行完仍是 `APPROVED`（靠 `executed=true` 表达），台账复用路径（:333-341）也只置 executed/executedBy/resultText，**不动 status**。再次挂起则回到 `saveSuspended` 新 PENDING 条目（同一 run 的 pending HASH 累积不清）。

**B7. 两候选写点的事实性优缺点（只列事实）**

| 事实维度 | convergeMemory 收尾统一写 | settle / 终态即时写 |
|---|---|---|
| 覆盖面 | 3 个终局路径（finish/emptyReply/cancelTerminal）统一；resume 后终局同样经 finish | settle 覆盖正常结算轮；**取消发生在执行中时 settle 不执行**（:169/:192 抛） |
| 时点状态可得性 | 需调用方额外取 `store.pendings(runId)`；cancel 路径 :530 早于 :532 | 状态就在同作用域（但 CONFIRM/FRONTEND 需复读 Redis，见 B5） |
| 与记忆落点的关系 | 直接写进即将 clear+add 的 history | 写进快照 messageJson，随后被终局 deserialize 复用 ⇒ 等价流入 |
| 消息对象可用性 | 有（deserialize 后的 List<Message>） | 同上；但挂起轮的 assistant(tool_calls) 此刻不在 messageJson，只在 assistantContent/inFlightToolCalls 字段 |
| 未覆盖路径 | — | resume 重建的 assistant/tool 消息由 :395-405 / :320 新建，**不带 metadata**（除非另加写点） |
| 冗余写风险 | 每轮在终局集中一次 | 每轮 settle 一次；advisor 另在 `ChatClient` 路径写记忆（`MessageChatMemoryAdvisor.before/after` 调 `ChatMemory.add`，字节码实证） |
| 可行 API | codec 读侧原样还原；写侧无 setter，只能就地改 Map 或重建消息 | 同左 |
