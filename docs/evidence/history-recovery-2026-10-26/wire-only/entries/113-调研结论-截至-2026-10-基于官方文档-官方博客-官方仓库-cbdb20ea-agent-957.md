## 调研结论（截至 2026-10，基于官方文档 / 官方博客 / 官方仓库 issue）

先给出总判断，再逐源给证据。

**一句话结论：** 在可查证的官方文档里，“审批卡已决”最主流的做法是**撤掉按钮 + 留一行决策收据（receipt）/结果行**，或**折叠成可展开的 tool-call 行**；“表单卡已决”最主流的做法是**整块锁定只读、已填值保留**。因此口径甲只对了一半（表单对、审批不对），口径乙也只对了一半（审批方向对、表单不对）。

## 1. CopilotKit（useCopilotAction / useHumanInTheLoop / useInterrupt）

**做法：默认“撤掉交互，换成一行摘要，或直接消失”，没有内建的“已决卡片”规范。**

- v1 `useHumanInTheLoop`（`useCopilotAction` + `renderAndWaitForResponse` 的后继）官方示例里，`render` 收到 `status`（`inProgress` / `executing` / `complete`）与 `respond`：
  - `executing` → 渲染带 Approve/Cancel 的卡片；
  - `complete` → 渲染一行灰字摘要：`result.confirmed ? "Items deleted" : "Deletion cancelled"`；
  - 其余 → `null`。
  “Complex Input Collection”示例在提交后直接 `return null`，表单整体消失。
  [useHumanInTheLoop（v1 reference）](https://docs.copilotkit.ai/reference/v1/hooks/useHumanInTheLoop)
- 官方 LangGraph + CopilotKit 教程里的 HITL 写法就是 `status !== "complete" ? <ProposalViewer .../> : null`——完成即隐藏。
  [Easily Build a UI for Your AI Agent (CopilotKit blog)](https://www.copilotkit.ai/blog/easily-build-a-ui-for-your-ai-agent-in-minutes-langgraph-copilotkit)
- v2 的 HITL 有两套：`useHumanInTheLoop`（tool-based）与 `useInterrupt`（LangGraph interrupt）。`useInterrupt` 提供 `resolve(payload)` 与**独立的 `cancel()`**；interrupt 过期（`expiresAt`）时“不 resume，记 error 并清空 pending state”。文档只讲“渲染待决 UI”，没有讲已决后保留成什么样。
  [HITL Overview](https://docs.copilotkit.ai/human-in-the-loop) · [useInterrupt (v2)](https://docs.copilotkit.ai/reference/v2/hooks/useInterrupt)

**判定：** 审批卡 → 摘要行/消失（偏乙）；表单卡 → 默认消失（甲、乙都不是）。CopilotKit 是“框架给你 render 自由，官方示例选最省事的摘要/隐藏”。

## 2. LangGraph interrupt / LangChain 前端 / LangSmith

**这是全场最明确的一条：默认已决即消失；若要保留，必须显式把“已决快照”写回消息，并整体只读渲染——这正是口径甲的形态（针对表单/富卡片）。**

- LangChain 前端 HITL 指南原话：

  > “When you resolve a plain interrupt, the card disappears the instant the interrupt clears and only the tool result comes back. That means a rich review card would vanish mid-run. To keep it on screen, resolve the interrupt **and** commit a message carrying the card to state … Snapshot the card with the decision baked in so it renders read-only.”

  代码即 `{ ...card, resolved: true, decision }`，塞进 `AIMessage.response_metadata.cards`，渲染时 `<InterruptForm card={card} readOnly />`；`InterruptCard` 类型本身就有 `resolved?: boolean` 与 `decision?: ReviewDecision` 字段。也就是说：**保留整张卡（含所有字段/已填值），只读锁定，并把 decision 烘进去**。
  [Human-in-the-Loop – Frontend (LangChain docs)](https://docs.langchain.com/oss/python/langchain/frontend/human-in-the-loop)
- 决策类型：`approve` / `reject`（可带 message，工具不执行，理由回给模型）/ `edit`（改参数后执行）/ `respond`（作为 tool result，不算拒绝）。**没有独立的 cancel 决策**；取消属于 run 级别，不属于 HITLResponse。
- 超时：LangGraph 明确“**waits indefinitely** until you resume”；前端指南只建议“Set timeouts thoughtfully… Consider showing how long the agent has been waiting”，即超时是应用层的事，框架不内建。
  [Interrupts (LangGraph docs)](https://docs.langchain.com/oss/javascript/langgraph/interrupts)
- LangSmith：官方 HITL 文档是 SDK 级（threads / runs / `Command(resume=...)`），**没有规定已决卡片怎么渲染**。参考客户端 Studio 只说明会把 `responseSchema` 渲染成 typed input fields（含 approval toggle），没有“已决卡片”规范。
  [Human-in-the-loop using server API (LangSmith docs)](https://docs.langchain.com/langsmith/add-human-in-the-loop) · [Interrupts – Using LangSmith Studio](https://docs.langchain.com/oss/javascript/langgraph/interrupts)

**判定：** 默认消失；显式保留时是“整卡只读 + 已决状态/decision”，不是一行摘要。这为口径甲的**表单部分**提供了最强证据，同时说明“保留”不是默认行为，需要额外做。

## 3. Vercel AI SDK + assistant-ui（框架层的“已决渲染”规范，值得单列）

**AI SDK**：tool part 有明确状态机 `approval-requested → approval-responded → output-available | output-denied`。官方 cookbook 的 UI 写法是：待决时渲染 Approve/Deny；批准后同一 part 改渲染结果行（`Weather in {city}: {output}`）；拒绝后渲染 `Weather request for {city} was denied.`。即**控件被替换成结果/拒绝摘要行**，原始审批内容不再作为卡片保留。
[Human-in-the-Loop with Next.js (AI SDK cookbook)](https://ai-sdk.dev/cookbook/next/human-in-the-loop)

**assistant-ui** 则把这条写成了设计原则，措辞非常接近“收据”：

> “**Leave a Receipt** — Once a user decides, the interactive surface should become a record of the decision, so scrolling back never shows a live control for a choice already made. … `ToolFallback` replaces settled approval controls with a receipt … 'Denied · Delete all project files', 'Answered · Staging'.”

细节：
- 审批：`approval.approved === false` → 渲染 `Denied: {reason}`；`approval.isAutomatic` → 渲染 “auto-approved” 徽标而不是按钮；`approval.approved === true` 且结果未到 → `Approved, running…`。
- **取消 / 过期是独立终态**：`approval.resolution: "cancelled" | "expired"`，明确“closes the gate without recording a deny”。
- 表单/问答：答案 “stay on `approval.answers` once it settles”；`OptionList` 用 committed answer 作为 `choice`；已答的 generative `prompt_user` **locks its controls**。
  [Tool UI (assistant-ui docs)](https://www.assistant-ui.com/docs/tools/tool-ui)

**判定：** 审批 → 收据行（乙）；表单/问答 → 锁定已填内容（甲）。这也是业界少有的、把两者分开规定的成文规范。

## 4. ChatGPT / Claude / Cursor / GitHub Copilot

### ChatGPT（Apps / agent）

- 官方帮助中心：动作执行前可能显示 **approval card**，描述 app 与拟执行动作；控件包括 **Deny/Decline、Allow/Allow once、Allow low-risk actions、Always allow**。没有 “Cancel” 语义，也没有超时/已决渲染的说明。
  [Managing app permissions in ChatGPT](https://help.openai.com/en/articles/20001495-managing-app-permissions-in-chatgpt)
- Apps SDK 文档从侧面说明“审批 UI 是宿主临时的门”：审批门控工具的 `toolInput` 在批准前可能为 `null`，**批准后**宿主才通过 `ui/notifications/tool-input` 下发参数；工具完成后用 `openai/toolInvocation/invoked`（≤64 字符的短状态文案）表示“已完成”。这更像是**状态文案**而非保留审批卡。
  [Plugins reference (OpenAI Developers)](https://developers.openai.com/plugins/reference)
- agent 模式只说明会 pause for confirmation / watch mode / take over browser，**没有**规定那条确认 UI 批准后如何留痕。
  [ChatGPT agent](https://help.openai.com/en/articles/11752874-chatgpt-agent)

**证据强度：弱（对“已决后怎么渲染”基本没有公开规范）。** 能确定的只有“审批是宿主渲染的卡、有 Deny/Allow 系列”，不能据此判定甲或乙。

### Claude（以 Claude Code 为代表）

- 权限提示：显示“Claude 将要做什么”，选项为 **Yes / Yes, and don't ask again / No, and tell Claude what to do differently**（官方 tools reference 对 WebFetch 的原话是 “No, and tell Claude what to do differently: rejects the fetch”）。选 No 还能按 Tab 附一条说明再提交——**拒绝可带 steering 反馈**，不是单纯 cancel。
  [Configure permissions](https://code.claude.com/docs/en/permissions) · [Tools reference](https://code.claude.com/docs/en/tools-reference)
- 超时：官方明确 **“permission prompts, including plan approval, never auto-resolve on idle”**——权限提示没有空闲超时；只有 `AskUserQuestion` 的多选题有倒计时（最后 20 秒显示，按键可重置），超时会按模型判断继续。
- 已决后：提示本身消失，对话里留下的是 tool call 与其结果（Claude Code 的 transcript 形态），**没有“审批卡保留态”**。另有 issue 指出 permission prompt 事件与用户选择不会写入 session jsonl，也印证它是瞬态 UI。
  [claude-code#58198](https://github.com/anthropics/claude-code/issues/58198)

**判定：** 控件消失、留 tool call + result；拒绝=带反馈的 reject；无超时。偏乙的“只剩记录”，但不是徽标行。

### Cursor

- 官方文档直接使用 “approval card” 一词：“The approval card shows the full path and why Cursor is asking. Click **Allow** to let the read through.” 说明卡内是完整上下文 + 单一 Allow。
  [Run Modes (Cursor docs)](https://cursor.com/docs/agent/security/run-modes)
- 终端审批的按钮（社区实测/论坛）：**Run once / Allow always / Skip**；“Skip” 是跳过该次调用并让 agent 继续，不是终止任务。
  [Cursor forum: Add “Explain” to shell command approval (Run once / Allow / Skip)](https://forum.cursor.com/t/add-explain-to-shell-command-approval-run-once-allow-skip/161730)
- 已决后：审批提示消失，命令作为 terminal 块在对话/终端中继续存在并显示输出；没有“已决卡片”概念，也没有文档化的超时。
  [Terminal (Cursor docs)](https://cursor.com/docs/agent/tools/terminal)

**证据强度：中。** 官方确认“approval card + Allow”，按钮语义与已决形态主要靠社区/实际 UI 佐证。

### GitHub Copilot（VS Code agent mode）

- 审批弹窗：显示 tool name + 输入参数，可选择 single use / session / workspace / always。
  [Manage approvals and permissions (VS Code docs)](https://code.visualstudio.com/docs/agents/run/approvals)
- 1.104 起明确三态：**Allow / Skip / Cancel**——“skip the tool call and let the agent continue. You can still cancel the request or enter a new request via the chat input box.”
  [VS Code v1.104 release notes](https://code.visualstudio.com/updates/v1_104)
- 已决后：弹窗消失，对话里留下 **collapsed 的 tool-call 行**（默认折叠，展开可看调用与输出）；自动批准时还会显示“命中了哪条 auto-approve 规则”的标签。
  [Use tools with agents (VS Code docs)](https://code.visualstudio.com/docs/agents/run/tools)

**判定：** 审批弹窗是瞬态的；留痕形态是“可展开的 tool-call 行 + 结果”，自动批准才有徽标/规则标签。偏乙的“记录”，但不是独立审批卡。

## 5. 审批/确认 UI 的“取消”态与超时

**取消 ≠ 拒绝，这一点在协议层是成立的，但各产品落地不一致。**

| 产品/框架 | 拒绝 | 取消 | 超时 |
|---|---|---|---|
| assistant-ui | `approved:false` / `Denied` | `resolution:"cancelled"`（另有 `expired`），不记 deny | 有 `expired` 终态；过期 gate 不可再 respond |
| CopilotKit v2 | `resolve({approved:false})` | 独立 `cancel()` | `expiresAt` 过期后不 resume，清 pending |
| VS Code Copilot | Skip（跳过并继续） | Cancel（终止本次请求） | 未文档化 |
| Claude Code | No + 可附反馈 | Esc / 关闭提示（等价拒绝并交回控制） | 权限提示**无**空闲超时；AskUserQuestion 有 20s 倒计时 |
| Cursor | Skip | 关闭提示 / 停止 run | 未文档化 |
| LangChain/LangGraph | `reject`（可带 message） | 无独立 cancel 决策；取消 run 在 HITL 之外 | interrupt 无限等待；超时由应用层做 |
| ChatGPT | Deny/Decline | 未文档化 | 未文档化 |

**归纳：** “取消/过期”通常被建模为**第三种终态**（cancelled / expired），与“拒绝”分开记；但**主流产品并不默认做审批超时**——Claude 明确不自动放行，LangGraph 无限等待，Cursor/VS Code 无文档化超时。真正内建超时的是框架层（CopilotKit `expiresAt`、assistant-ui `expired`），且过期表现为“门关闭、不产生 deny”，UI 上通常是清掉待决控件，而不是显示一个“已过期”的审批卡。

## 总结：与口径甲 / 口径乙的对照

| 维度 | 业界可查证的主流 | 口径甲 | 口径乙 |
|---|---|---|---|
| **审批卡已决** | 撤按钮 + **决策收据/结果行**（`Denied · 动作名`、`Approved, running…`、`Items deleted`），或折叠成可展开的 tool-call 行；默认常常直接消失 | ✗ 未找到“卡头徽标 + 内容区原样”的官方默认实现 | ✓ 方向一致，但“只剩徽标”太薄：主流收据通常保留**动作名/关键参数**，且可展开详情 |
| **表单卡已决** | **整块 UI 只读锁定、已填值保留**（LangChain `resolved` + `readOnly`；assistant-ui locks controls / committed answer） | ✓ 与主流一致 | ✗ 主流不是换成摘要 |

**逐条判定：**

1. **口径甲**：**表单半句成立，审批半句不成立。** LangChain 前端指南几乎是口径甲的原文实现（`resolved:true` + `decision` + `readOnly`，整卡保留）；assistant-ui 对表单/问答也是锁定控件。但审批卡方面，没有任何一个官方文档把“卡头状态徽标 + 内容原样”作为默认推荐；相反，assistant-ui 明确要求 “settled approval controls → receipt”，AI SDK 官方示例直接换成结果/拒绝行，CopilotKit 示例换成一行摘要或 `null`。
2. **口径乙**：**审批半句方向正确，表单半句不成立。** 审批的“摘要行”在 CopilotKit / AI SDK / assistant-ui 都能找到直接证据，但业界收据一般带动作标识（如 “Denied · Delete all project files”），而不是纯状态徽标；表单则相反，LangChain 与 assistant-ui 都选择保留已填内容并锁定。
3. **真正的主流不变量**（比甲/乙都更稳）：**已决后不得再出现可交互控件**（assistant-ui 的原话是 “scrolling back never shows a live control for a choice already made”），同时**决策必须可读**。至于保留多少内容，取决于该卡片是否是决策依据的唯一载体：审批卡通常有 tool call/结果兜底，所以可以收据化；表单卡的值没有别处可查，所以必须原样锁定。

**证据强度：**
- 审批卡：**强**（LangChain 明确写“默认消失/要保留就整卡只读”、assistant-ui 成文设计原则、AI SDK 官方 cookbook、VS Code/Claude/Cursor 的实际交互、CopilotKit 官方示例，方向高度一致）。
- 表单卡：**中强**（LangChain + assistant-ui 两条明确规范；CopilotKit 官方示例是反例——提交后 `null`，说明“锁定”并非所有框架默认，但在“保留”时业界选择锁定而非摘要）。
- ChatGPT：**弱**（官方只定义审批卡控件，不定义已决渲染；无法据此支持甲或乙）。
- 超时：**中**（协议/框架层有 expired/cancelled 建模；产品层普遍不超时，不能把“超时”当成主流渲染惯例）。

**给待验口径的建议：** 若必须二选一，应按卡片类型拆开——**审批卡走乙的收据化（但收据需含动作名/关键参数，可展开详情），表单卡走甲的整块只读锁定**。把两者统一成甲或统一成乙，都与可查证的业界惯例有偏差。
