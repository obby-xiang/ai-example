## 6. 帧序竞态三路 × unknown（重点）

### 6.0 先钉死"帧携带的是不是权威真相"（本点结论的基石）

`SseChatEmitter.java:613-623`：

```java
613  public void frontendToolResult(PendingToolCall pending, boolean ok, String result) {
614    Map<String, Object> frame = frame("frontend_tool_result");
617    frame.put("ok", ok);
619    frame.put("status", pending.getStatus());
```

`status` = 后端**挂起台账条目**的当前状态（= 跨窗口共享的权威裁决：他端提交/取消、后端超时、入参被安全闸拒、防线③拦截都在这里反映）。但 `ok` 不同：

- `ConfirmGate.java:484-491`（回灌成功路径）：`pending.setStatus(FRONTEND_RESULT)` 后 `frontendToolResult(pending, **true**, result)` —— **ok 是硬编码 `true`**，与前端执行器真实成败无关（`docs/M2-排期计划.md:289` 已登记为证据 N-6："`submitFrontendResult` 非取消回灌硬编码 `ok=true`"）。所以前端 `execution.ok=false`（含预算到期）时，帧仍是 `ok=true, status=FRONTEND_RESULT`。
- `ConfirmGate.java:515-531` `dismiss`：`FRONTEND_CANCELLED` + `ok=false` —— **他端取消**时才是独立真相。
- `ConfirmGate.java:310-336` `expire`：`TIMEOUT` + `ok=false`，文案"**结局未知（不表示未发生）**" —— **后端权威超时**，独立于前端提交。
- `ConfirmGate.java:274-297` `cancel`：仅当条目仍 `PENDING` 才置 `CANCELLED`，否则原样发帧。
- `SpToolCallingManager.java:296-308`：`REJECTED_ARGUMENTS` + `ok=false`。
- `SpToolCallingManager.java:235`：`BLOCKED`。

⇒ **判定：`FRONTEND_RESULT` 这一支的 `frontend_tool_result` 帧是"后端对前端已提交结果的回执确认"，不含比前端已知更多的真相**（`ok` 恒 true、`status` 只反映"回灌被受理"）；而 `FRONTEND_CANCELLED / CANCELLED / TIMEOUT / REJECTED_ARGUMENTS / BLOCKED` 五支**确实携带独立于本地提交的权威结局**（他端动作 / 后端超时 / 后端闸门）。这个混合性是本任务的关键：把一个**本地"结局未知"判断**交给帧去改写，只能被改写成 `FRONTEND_RESULT→'succeeded'`（假成功），而不会被改写成"未知"。

**`unknown` 是否应是不可改写的终态：是**。依据：① 语义上 unknown 是"未确认成功/失败"的**收尾判断**（types/ai.ts:162），任何后续"成功/失败"改写都在制造断言；② 唯一会改写它的帧支 `FRONTEND_RESULT` 恰恰**不携带结局真相**（ok 硬编码 true，后端根本没执行前端工具）；③ 携带独立真相的五支（cancel/timeout/reject/block）与 unknown **不冲突**——它们表达的都是"未执行/被取消/超时"，与"结局未知"同向或更弱，无需覆盖本地已下定的结论；④ 仓内既有 first-wins 单调口径（parts.ts:355-360 把"本地乐观 cancelled"也列入保护）与 R-84 的登记口径（预算到期 = 诚实终态）同向。

### 6.1 帧进入 `parts.ts:351-366` 的所有入口（代码锚点）

- 入口唯一：`handleFrame` → `case 'frontend_tool_result'`（`stores/ai.ts:1593-1612`）→ `applyFrameToParts(message, frame)`（`:1601`）。

三条竞态路径具体的可达形态：

**(a) 重投 / re-attach**

- 连接内自动重挂（`api/sse.ts:549-552`）：`const since = state.lastSeq ?? options.lastSeq` ⇒ **带 seq 的帧不会重发**（已消费帧被服务端按 `seq > since` 过滤），且即便重发也被 `alreadyApplied` 拦下 —— **同消息内不可能覆盖**。

- 帧不带 `seq`（旧格式）时 `state.lastSeq` 恒为 null（`api/sse.ts:170-173`）⇒ 即便同消息也**会**重新进入 `:351` 分支。

**(b) 回放 / replay（会话恢复 / snapshot 续收）**

- `restoreSuspendedSnapshot`（`:685-777`）→ `resumeSnapshotStream(current.runId, current.archiveMaxSeq, host.id)`（`:775`）。`archiveMaxSeq` 可为 `0`，而 `SSE_PATHS.events(runId, 0)`（`api/sse.ts:48-54`）会拼 `?lastSeq=0` ⇒ 服务端补发 `seq > 0` 的**全部归档帧**。

**(c) 续收快照（snapshot 已有 unknown 段）+ 活帧**

- 快照循环先处理 "非 PENDING" 条目（`:708-716`）：`mapped && hasDecidedPendingResidue(...)` 才调 `applyFrontendToolTerminal`。

### 6.2 三路 × (1)(2) 判定（含代码锚点的明确结论）

**先明确一个前提**：本任务问的"本地 `unknown` 段"目前**没有生产者**（第 1 点），下列结论是对"一旦引入 `unknown` 写入点"的**前瞻性竞态判定**，锚点均为现码。

| 路径 | (1) `unknown` **不**加入 `localTerminal` | (2) `unknown` 加入 `localTerminal` |
|---|---|---|
| **(a) 重投（同消息，无 seq / 重放）** | `localTerminal=false` ⇒ `fromFrame`（`FRONTEND_RESULT→'succeeded'`）**覆盖 unknown → succeeded**（parts.ts:361-364） | **本地胜**（parts.ts:362-363 取 `existing.status`），unknown 保留 |
| **(a') re-attach 新宿主消息**（:1008） | 新消息无该段 ⇒ 新建一张 `succeeded` 卡（重复卡），原 unknown 段仍在 | **仍失守**：`findToolPart` 是消息级（parts.ts:77, :357），保护不到另一条消息 ⇒ 依旧新建重复卡 |
| **(b) replay 到同一宿主消息**（:733-737 + `?lastSeq=0`） | 段命中、`localTerminal=false` ⇒ **unknown → succeeded** | **本地胜**，unknown 保留 |
| **(b') `loadHistory` 历史非空整体替换**（:631-663, :644） | 段被丢弃，新段 `succeeded` | **同样失守**（此路不经段级判定，直接换 messages） |
| **(c) 续收快照 PENDING 条目 + 活帧** | 守卫失效 ⇒ 段被写回 `pending`+`requiresAction=true`（:745-752）⇒ 活帧 `FRONTEND_RESULT` 再落 `succeeded`（**unknown → pending → succeeded**，两跳全失真） | 守卫命中 ⇒ `continue`（:725-727）⇒ 若这是唯一 PENDING 条目，`host` 保持 null ⇒ **不建续收连接**（:773）⇒ 无活帧，unknown 保留；若另有其它 PENDING 条目共享宿主，则帧仍可能落到**不含该段**的消息上并新建重复卡（同 a'） |

**⇒ 对第 6 点 (1)(2) 的直接回答**：
- (1) 若 `unknown` **不**加入 `localTerminal`：**三路都会把它翻成 `succeeded`/`failed`**（(a)(b) 由 `fromFrame` 直接覆盖；(c) 先复活成 pending 再落 succeeded）。翻成 `succeeded` 的具体来源见 6.0：帧 `status=FRONTEND_RESULT` + `ok=true`（`ConfirmGate.java:484-491` 硬编码）——**是假成功**。
- (2) 若 `unknown` **加入** `localTerminal`：**本地并非三路都稳赢**。三路里"同消息 + 段命中 + 帧再投递"这一情形稳赢；另外三种情形仍失守，且**根因不是终态集合，而是两个结构性缺口**：
  1. **段查找是消息级**（`parts.ts:77-80` / `:357`），而 first-wins 保护必然只在本消息内生效 ⇒ re-attach 新宿主（`ai.ts:1008`）、或帧落到不含该段的消息时，会**新建一张帧状态卡**（重复渲染 + 卡面矛盾）；
  2. **`loadHistory` 历史非空支整体替换**（`ai.ts:631-663`，工具段状态硬编码 `'succeeded'` `:644`），绕开所有段级终态口径。
  ⇒ 要让"`unknown` 不可改写"真正成立，除把 `unknown`（以及 `failed`）并入射界集合外，还必须：把段查找/终态判定提到**店级**（或让帧写路径先过 `hasDecidedPendingResidue`），以及让历史替换支的段状态不硬编码 `succeeded`。

## 7. 取消竞态 — 需修正（"乐观 cancelled 的唯一写点"比草案窄，且 unknown 与取消无覆盖关系）

`grep 'cancelled'` 结果（`frontend/src`）：

**唯一把段置为 `cancelled` 的本地路径** = GF 表单取消：

```ts
1296    async cancelGenerativeForm(auto = false): Promise<void> {
1297      const form = this.activeForm
1298      if (!form || form.status === 'cancelled' || form.status === 'submitted') { return }
1301      form.status = 'cancelled'
1302      // T2a-D#2（A2）：本地 cancel 仅乐观置位 —— 只收敛仍处 pending 的 pendingCall 投影；
1303      // 帧终态为最终裁决，后到帧可覆盖此乐观 cancelled（他端先提交时翻为 succeeded，不降级）
1304      this.applyPendingTerminal(form.toolCallId, 'cancelled')
1305      disarmFormExpiry()
1306      const outcome = await this.submitFrontendToolResult(form.toolCallId, '', 'http-post', true, form.runId)
```
→ `applyPendingTerminal`（`:1698-1710`）才是真正落段处，覆盖域是：

```ts
1704        if (part && part.kind === 'tool'
1705          && (part.status === 'pending' || part.status === 'cancelled' || part.requiresAction)) {
1706          item.parts.splice(index, 1, { ...part, requiresAction: false, status: mapped })
```

**次要点**：`openGenerativeForm` 的 schema 非法支先落 `failed`（`:1231`）再带 `cancelled:true` 回灌（`:1236`）——帧 `FRONTEND_CANCELLED` 到达时本地已是 `failed` ⇒ first-wins 保留 **`failed`**，不是 `cancelled`（本地乐观判断胜）。

**`stop()`（`:1317-1342`）不写任何 `cancelled` 段**：只 abort 连接 + `POST /api/ai/cancel`，段状态留给帧/收尾；`send` 的 finally（`:923-927`）只置 `message.done=true`，**不调 `expireResidueToolParts`** ⇒ 主动停止轮里 `requiresAction=true` 的段在**本会话内**会保持挂起语义（刷新后由 `sanitizeMirrorResidues:222-240` 在 done 消息上降级）。同族小缺口，供参考。

**first-wins 保留哪个（确认）**：用户取消后任何迟到的 `frontend_tool_result` 帧，`localTerminal` 含 `'cancelled'`（parts.ts:360）⇒ **保留 `cancelled`**；`parts.ts:355-356` 与 `ai.ts:360-369` 的注释、以及 `frontend-tool-result-terminal.spec.ts:195-211` 三条断言锁死了这一口径（cancelled 不被 `ok=false` 缺省帧 / `TIMEOUT` 帧改写；`succeeded` 不被 `CANCELLED` 帧改写）。

**"先 unknown（预算到期）后取消"能否覆盖**：**不能，且路径上根本不会尝试覆盖**，逐条给依据：

1. 通用 FRONTEND 工具**没有**"用户取消"这个动作：`cancelGenerativeForm` 只作用于 `activeForm`（GF），`stop()` 不写段 ⇒ 一个 `unknown` 的**通用**前端工具段，在其后取消整轮时，段状态不会被改写；后端条目若已是 `FRONTEND_RESULT`（非 PENDING），`ConfirmGate.cancel`（`java:279-286`）也**不改它**，只会走 `done{cancelled:true}`（`ai.ts:1653-1655` 只改 notice）⇒ 卡面 `unknown` 保留。
2. 只有 GF 段可能被 `applyPendingTerminal` 改写为 `cancelled`，而它的覆盖域是 `pending || cancelled || requiresAction`（`:1705`）。若 GF 段为 `unknown` 且 `requiresAction=false`，**`unknown` 不属于覆盖域 ⇒ 取消失败**（这是"unknown 终态不可改写"的应有表现，但注意它是**副作用式**成立，不是显式口径）；若同段 `requiresAction=true`，则**取消会覆盖 unknown → cancelled** ⇒ 同一状态两种结果，取决于 `requiresAction` 这个正交字段 —— **语义不一致，建议显式化**。
3. 时序上"先取消后 unknown"不可达（`unknown` 只可能来自 `runFrontendTool` 的预算到期结局，而该函数一旦开跑就不再回读取消）：`stop()` 之后在途的 `executeFrontendTool` 仍会返回并写段 + 回灌（`:1798-1818`），于是**已停止轮的段仍会被写成终态**，而 `send` 的 finally 只置 `done` —— 这是一条"停止后仍写段"的残留面（与第 6 点无关，单独登记）。
