## 0 结论速览

1. **你的记忆是对的**：实时路径上，同一批多张 HITL/表单卡**严格串行**——第 N 张的请求帧是在第 N-1 张决策之后才发。
2. **但"前一个有问题后面的都跳过"只对一半**：只有"执行后确定性失败（failed 且不可重试）"才跳；**用户拒绝（REJECTED）不跳**，后面的卡照常弹。
3. **孤儿轮（req=null）不能照搬这个模型**：缺的不是"顺序展示"，而是"发帧 + 等待"的那个**活线程**。刷新后的前端只能画卡，不能发帧；而 `ResumeService` 是"直接结算 in-flight 调用"，从不重新进入等待循环。
4. **重要修正**：单卡批次（一批只有 1 个 PENDING 外部条目）其实**今天就走得通**——批准后 `unresolved` 为空，续跑正常执行。你的方案只在**≥2 张卡**的孤儿批次上断掉，断点是 `PENDING_UNRESOLVED`（`ResumeService.java:548-554`）。

## 1 实时路径是否严格串行：是

**"整批落库、逐条发"到底怎么逐的**：

- 一次模型响应里的 N 个 toolCall 先全部建成 `PendingToolCall`（`SpToolCallingManager.java:270`、`:1212-1223`），**整批**写进 Redis 并置快照 SUSPENDED（`:353-359` `saveSuspended`，`RunStore.java:723-743`）。`suspended` 帧一次列出**全部**挂起条目（`:357-358`）。
- 然后进入**同一个 `for` 循环**（`SpToolCallingManager.java:363-448`），逐条执行：`out.toolStart` → `awaitConfirm` / `awaitFrontend`（`:414-415`）。
- 每条 `await` **自己发自己那张卡的请求帧**，然后 `completeSubscriptions()` 断流，再阻塞等人（`ConfirmGate.java:429` 起：`:466` `confirmRequest` / `:469` `frontendToolRequest`、`:487` `completeSubscriptions`、`:507-545` 阻塞循环）。原码注（`:482-486`）写得很直白：*"第 N 张卡的请求帧是在第 N-1 张卡决策之后、重新连上的订阅里发出的"*。
- 前端同一口径：`suspended` 帧 handler 只 `find` **第一个** CONFIRM/FRONTEND 建段（`stores/ai.ts:3501-3516`、`utils/parts.ts:768-786`）；第 2 张卡靠它自己的 `confirm_request` 帧 upsert 建段（`utils/parts.ts:603-620`）。

⇒ **帧层、卡层都严格串行；只有"条目层"是整批预落库的**——这正是 L0 那个洞的根源（条目存在 ≠ 卡已送达）。

**"后面都跳过"的真实判据**（这是需要纠正你印象的一处）：

| 触发 | 后续条目是否跳过 | 锚点 |
|---|---|---|
| 执行后 `outcome=failed` 且 `!retryable`，且类别 ∈ W/J/P | **是** → 剩余全部 `SKIPPED` | `haltsBatch` `:495-505`；跳过循环 `:364-367`；`skipAsUpstreamFailed` `:513-531` |
| **用户拒绝**（REJECTED） | **否**，循环继续，下一张卡照发 | `haltsBatch` 只认 `outcome==FAILED`（`:505`）；`awaitConfirm` 非 APPROVED 分支 `:746-748` |
| 预检不通过（PRECHECK_FAILED） | **否**（retryable=true，注释 `:375`） | `blockPreflight` `:599-616` |
| 越 scope（BLOCKED） | **否** | `blockOutOfScope` `:656-673` |
| 步数到顶 | **是**，剩余 `SKIPPED / TOOL_STEP_LIMIT` | `:540-558` |
| 用户取消整轮 | 整轮终止 | `checkCancelled` `:582`、`:372/:423` |

## 2 实时路径靠什么推进到第 2 张

**同一个线程、同一个 `for` 循环**，不经过 `ResumeService`：

1. 用户点批准 → `POST /api/ai/confirm`（`AiController.java:410-458`）→ `ConfirmGate.submitDecision`（`:891-896`）→ `doSubmitDecision`（`:921-971`）：抢决策 guard → `putPending` → 发 `confirm_decision` 回执帧 → `signal(runId, toolCallId)` 把 latch `countDown`（`:969`）。
2. 阻塞中的 `await` 被唤醒，`latch.await` 返回 true（`ConfirmGate.java:534`），下一圈读到 `fresh.resolved()`（`:514`），**交棒租约**后 `return fresh`（`:515-517`）。
3. 控制权回到 `SpToolCallingManager` 的 `for` 循环：`awaitConfirm` 里 APPROVED → `executeOnce`（`:741-745`）；然后 `responses.add(...)`、判 `haltsBatch`，**进入下一条 pending** → `toolStart` → 下一条 `await` → 发第 2 张卡的帧（`:409-447`）。
4. 前端在 `ai.confirm` 成功后立即 `reconnectSuspendedRun`（`stores/ai.ts:2199`、`:1655-1666`）带 `lastSeq` 重连，接住"决策 → tool_start → 第 2 张请求帧"。

**`PENDING_UNRESOLVED` 在这条路径上完全不起作用**——它只存在于 `ResumeService.resume()`（`:548-554`），而实时路径从不调用 resume。这条闸门的语义是"重启/死卡兜底时，还有人没决策就别驱动"，与"活线程边等边推进"是两套机制。

**明确结论**：

- **1 张卡的批次走得通**（批准后 `unresolved` 为空 → 续跑执行 → 模型继续）。这是今天就已具备的能力，只差"把卡画出来"。

## 4 让"串行重建、决一张出一张"成立的最小改动

要成立，必须补一个**能发帧、能阻塞等待的驱动者**，因为这份能力只存在于死掉的那条执行线程里。两档：

**D 档（贴合你的方案：重入执行循环）**

| 文件 | 改动 |
|---|---|
| `backend/.../ai/gate/SpToolCallingManager.java` | 复用现有批循环：新增可被 ResumeService 调用的入口（或直接 `executeToolCalls(prompt, chatResponse)`），由它重新 `arm` → 逐条 `await` → 逐条发帧 |
| `backend/.../ai/run/RunStore.java:723-733` | **前置必修**：`saveSuspended` 现在会用"全新全 PENDING 对象"覆写整批条目（`newPendings` `:1212-1223`），重入时会抹掉 `executed/resultText/outcome`（决策 guard 只救回 status）。加守卫：库内已非 PENDING 的条目**不覆盖** |
| `backend/.../ai/run/ResumeService.java:548-554` | `PENDING` 分支由"直接返回 409"改为"进入重入等待"，并把它放到专用线程（现有 `aiRunExecutor`，`poolSize=20`，长时间阻塞需评估） |
| `backend/.../ai/run/StartupResumeRunner.java:139-152` | 触发点：启动扫描遇到"PENDING 外部条目 + 无等待者"的孤儿轮，改走重入而不是 skip |
| 测试 | 新增：3 卡批次重启后逐张出卡 / 决策向后推进 / 已决条目不重复执行 / 多实例抢租只一个驱动 |

风险点（必须在验收里写死）：① `stepsUsed` 会按条重新自增，已结算条目要跳过计数（`:390-405`）；② 预检会对已挂起的 CONFIRM 重跑（`:288-320`，IMPORT 类要重算文件 hash，可能"卡已经给用户看了、预检结果却变了"）；③ 会重发 `suspended` 帧；④ 多实例必须靠 `ai:lease:run:` + `claimExecution` 双重兜底。

**工作量：3~4 人日。收益：真正实现"决一张出一张"，且对任何版本的旧轮都适用。**

**B 档（最小，但放弃"顺序呈现后半批"）**

把"从未发过帧"的 PENDING 条目在续跑前一次性结算成 `SKIPPED`（复用 `skipAsUpstreamFailed` 的语义与文案，`SpToolCallingManager.java:513-531`），`unresolved` 清空 → 续跑执行已批的那张。改动只碰 `ConfirmGate`/`ResumeService` + `RunStore` 一个新方法 + 测试，**1~2 人日**。代价：用户只看到第 1 张，后面的在 tool_result 里显示"未执行/已跳过"，模型接着往下走。

**取巧档（零后端改动）**：前端把 3 张卡一次全画出来，用户逐张批，前两次停在"已提交，同步中…"，第 3 次批准后整轮才动。技术上可行，但体验正是你不想看到的那种。

## 5 "跳过"后的终态与 history 呈现

- 写入：`status=SKIPPED`、`outcome=skipped`、`code=UPSTREAM_FAILED`（或 `TOOL_STEP_LIMIT`）、`executed=false`、`resultText="未执行：上游 X 失败（code），本调用已跳过"`（`SpToolCallingManager.java:513-531`、`:540-558`）。
- 实时：`toolResult` 帧 → 段 status `skipped` → 卡头标签"已跳过"（`utils/blocks.ts:486`），`reason/resultText` 进卡体。
- 刷新后：`toolCallStates.status=SKIPPED` → `historyToolCallStatus` 映射 `'skipped'`（`utils/parts.ts:310-311`）；`outcome='skipped'` → `outcomeStatus('skipped')='skipped'`（`:352-353`）⇒ 历史里**仍显示"已跳过"**，与实时一致。
- 前提：该轮已收敛进 ChatMemory（`ResilientChatService.java:1030`，仅终态调用）。**若该轮还停在 SUSPENDED，history 里根本没有这一轮**——上一轮已核实，这仍是"刷新后整轮不可见"的独立问题。

## 6 终判

- **你的方案可行，但不能只改前端**。判定：**"可行，但要改 X"**，X = 一个能重入等待循环的驱动（D 档），外加 `saveSuspended` 的覆写守卫；只改前端重建卡会稳定卡在 `PENDING_UNRESOLVED`。
- **如果这一批只有一张待决卡**（最常见），方案今天就能落地：只要把卡画出来，批准 → 续跑 → 执行，不需要任何新驱动。建议把 D 档按"多卡批次"立项，单卡批次先随 M-2b 的降级卡一起上。
- 我上一轮"必须整批渲染整批决策"的说法**在"零后端改动"前提下正确，但表述过强**：准确说法是"要么整批决策、要么补后端重入驱动"；串行重建不是不可行，而是需要后端配合。

**验证边界**：本轮全部为静态代码核实（未跑单测、未起服务）；行号为本树实测。第 3 节第 5 步的 `PROVIDER_GONE` 与第 7 步的"输入框恢复但会话仍占用"建议真机复现一次再定案。
