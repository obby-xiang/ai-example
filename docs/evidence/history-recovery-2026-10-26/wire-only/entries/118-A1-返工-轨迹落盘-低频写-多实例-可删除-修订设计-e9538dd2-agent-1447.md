# A1 返工：轨迹落盘（低频写 / 多实例 / 可删除）修订设计

> 只出设计，不写代码、不改仓库。上一版 A1 的核心错误是假设「**单文件追加（append）**」——在远程文件服务上这个假设不成立：对象存储没有 append（只能整对象覆写），NFS/SMB 并发 append 会交错或截断。修订后的写模型改为 **write-once 不可变对象**，从根上消除写冲突。

---

## 0. 结论先行

1. **写模型**：不再 append，改为「内存缓冲 → 每批一个不可变对象」。写频从「每事件 1 次」降到「每 5 分钟 1 次（且非空才写）」。
2. **多实例**：选 **a) 每实例独立对象名**，不做 Redis 缓冲、不做单写者选举。零冲突、零新 Redis 键、不碰 A-6。
3. **删除**：主路径交给**存储侧生命周期规则**（按 `dt=` 前缀），应用只留每日一次的幂等兜底清理；保留期建议 **7 天**（量级只有 MB 级，24h 太短；设 `retention-days: 1` 即可切到严格档）。

---

## 1. 修订后的 A1 完整设计

### 1.1 写模型（关键变更）

```
事件发生 → AiTrace.eventOn 同一处 → 有界队列 → 单写线程
   ├─ 触发条件：满 5 分钟 / 满 500 行 / 满 1 MB（三者先到先发）
   ├─ 序列化：按事件白名单取字段 → 一行一条 JSON
   └─ 落盘：写一个全新对象（write-once），不读、不改、不追加
```

三条硬纪律：

- **绝不 append**。对象存储不支持；NFS 并发 append 不可靠。
- **绝不阻塞 AI 主路径**。队列满即丢并计数（与现有「日志不许影响主流程」同一条纪律，`AiTrace.java` 类注释）。
- **绝不整对象重写**。避免 read-modify-write 带来的写放大与丢更新。

写入方式按存储类型二选一（配置 `atomic-write`）：挂载盘用「临时文件 + `ATOMIC_MOVE`」；对象存储用单次 PUT（天然原子）。

### 1.2 缓冲与 flush 参数（默认值 + 依据）

| 配置键 | 默认值 | 依据 |
|---|---|---|
| `app.ai.observe.trace.enabled` | `true` | 可一键关 |
| `app.ai.observe.trace.dir` | `./data/ai-traces` | **不复用** `app.file.storage-path`（业务文件区，`application.yml:379`），避免被业务清理逻辑扫到 |
| `app.ai.observe.trace.flush-interval` | `5m` | 5 分钟是「丢失窗口」与「对象数量」的平衡点；1m 对象翻 5 倍，15m 丢得太多 |
| `app.ai.observe.trace.flush-max-lines` | `500` | 500 行 ≈ 150–200 KB，单对象不至于过大；也是崩溃丢失的硬上界 |
| `app.ai.observe.trace.flush-max-bytes` | `1MB` | 防御超长 `reason` 等异常行 |
| `app.ai.observe.trace.queue-capacity` | `8192` | 约 2–3 MB 堆内存；满则丢最旧并计数 |
| `app.ai.observe.trace.shutdown-drain-timeout` | `5s` | 有界 drain，**远程存储卡住也不许拖住 JVM 退出** |
| `app.ai.observe.trace.retry-attempts` | `2`（200ms/1s 退避） | 失败即丢并计数，不堆积 |
| `app.ai.observe.trace.retention-days` | `7` | 见 §3 |
| `app.ai.observe.trace.cleanup-enabled` | `true` | 兜底清理开关 |
| `app.ai.observe.trace.atomic-write` | `rename` \| `put` | 按存储类型选 |

### 1.3 文件命名与目录布局

```
<dir>/dt=2026-10-22/instance=<instanceId>/part-103215-000017-a1b2c3.ndjson
```

- `dt=` 用 **UTC 日期**（存储侧生命周期规则按前缀删，避免时区歧义）。
- `instance` 取现有 `InstanceId.get()`（`ai/run/InstanceId.java:26`，形如 `instance-<host>-pid<pid>-<6hex>`）；文件名做一次字符白名单清洗（只留 `[A-Za-z0-9._-]`）。
- `part-<HHmmss>-<seq>-<rand>`：`seq` 为进程内单调序号，`rand` 6 位防同名；**重试复用同一名字** → 幂等（覆盖同内容对象，不产生重复）。
- 目录前缀是 Hive 风格，读取侧 `glob dt=*/instance=*/part-*.ndjson` 即可，未来 DuckDB/Spark 可直接按分区读。

### 1.4 轮转与删除

因为是 write-once，「轮转」退化为**命名分段**：

- **按天**：`dt=` 分区，天然跨日切分，不依赖时钟切文件。
- **按大小**：单对象 ≤ `flush-max-bytes`（1 MB），超出即分片。
- **删除（推荐三层）**：

| 层 | 做法 | 评价 |
|---|---|---|
| 主 | **存储侧生命周期规则**（对象存储 `Expiration: Days=7` on prefix `ai-traces/`；NFS 侧运维脚本 `find -mtime +7 -delete`） | ✅ 唯一不会漏、不占应用资源的方式，**首选** |
| 兜底 | 应用每日一次（本地记 `last-cleanup` 日期，避免每小时扫），列 `dt=` 前缀、删 `dt < today-7` | ✅ 幂等；多实例同时做也无害（DELETE 幂等） |
| 不做 | 写线程「顺便删」 | ❌ 让写路径依赖 LIST/DELETE，远程存储上 LIST 很贵，且放大写路径失败面 |

### 1.5 字段白名单（比上一版更严）

不整包序列化 `kv`，而是**按事件 allowlist**。理由：日志层有 `AiTrace.clean` 截断，但持久层应比日志更严。

- 允许：`ts / event / run_id / session_id / turn_no / instance / attrs{计数、耗时、状态码、枚举、工具名、模型名、token 数}`
- **剔除**：`turn_retry.reason`（自由文本，可能夹带上游异常原文）、任何 `chars` 之外的内容长度、任何工具入出参。
- 结果：一行约 300–400 B，比原设计小 ~30%。

### 1.6 崩溃丢失量级（给用户判断）

上界 = `min(5 分钟窗口的流量, 500 行)`。

| 场景 | 轮/日 | 行/轮 | 5 分钟内约 | 崩溃最坏丢失 |
|---|---|---|---|---|
| 轻度（内部配置工具） | 50 | 10 | < 1 轮 | **≤ 1 轮** |
| 常规 | 300 | 10–12 | 1–2 轮 | **≤ 2 轮** |
| 峰值/重工具链 | 1000 | 15–40 | ~10–33 轮 | **500 行封顶（约 10–33 轮）** |

**可接受性的关键论据**：轨迹是排障辅助，**真值仍在 Redis 24h**（`ai:run` 快照 + `ai:xevents` 帧流）。崩溃丢的那 5 分钟，在 24h 内还能从 Redis 找回；超过 24h 的那部分，本来就是「可丢的辅助数据」。

### 1.7 容量估算（回答「会不会堆积」）

按 300–400 B/行：

| 场景 | 每天 | 7 天 | 对象数/天（4 实例、5 分钟窗口） |
|---|---|---|---|
| 轻度 50 轮 | ~175 KB | ~1.2 MB | 十几 |
| 常规 300 轮 | ~1.2 MB | ~9 MB | 120–240 |
| 峰值 1000 轮（重工具） | 4–14 MB | 30–100 MB | 240–400 |

结论：**这不是容量问题，是口径/合规问题**。删除是为了「不留痕」，不是为了省空间——所以更应依赖存储侧规则，而不是写代码硬删。

### 1.8 失败与幂等

- 写失败：重试 2 次 → 丢批 + 计数 `observe.trace.dropped`，WARN 一行（不刷屏，按分钟限流）。
- 重试同名 → 覆盖同内容，不产生重复对象。
- 读取侧按 `ts` 排序，**不依赖文件顺序**（多实例时钟偏差只影响排序细节，不影响归属）。

## 2. 多实例方案对比

| | a) 每实例独立对象 | b) Redis 缓冲 + 单实例聚合落文件 | c) 纯 Redis（TTL=session-ttl） |
|---|---|---|---|
| 写放大（远程存储） | 每实例每 5 分钟 1 次 PUT；4 实例 = 4× 对象数，**总字节不变**（仅多每对象元数据开销） | 全局每窗口 1 次 PUT，**写放大最低**；但 Redis 侧每次 flush 一次批量写 | 0 次文件写 |
| 一致性/冲突风险 | **0**（名字唯一、write-once、删除幂等） | 中：写者租约过期 → 双写（需 fence）；缓冲 TTL 过期 → 丢批；跨实例顺序需自行保证 | 低（Redis 单点原子），但**数据 24h 后消失**，不满足「存轨迹」 |
| 复杂度 | **低**（约 150 行 + 1 个调度线程） | **高**（租约/续租/fence/断点续传/空窗补偿），与 B23L1 的租约设施耦合 | 低，但查询要 SCAN/索引，且要新增键族 |
| 与远程存储契合 | ✅ 对象存储 / NFS 都行，不依赖 append | ✅ 但要额外保证「写者唯一」 | — 不涉及 |
| 与 A-6 / 24h 共亡 | ✅ **零新 Redis 键**，完全不碰 A-6 | ⚠️ 新增全局缓冲键，A-6 冻结期属抢跑；且键的 TTL 语义要另立 | ⚠️ 必须新增 `ai:obs:*` 键族，**必须等 A-6**；且 24h 后轨迹即失 |
| 查询体验 | 多对象 glob 后按 `ts` 归并 | 单文件/少量对象，最顺 | 只能在 24h 窗口内查 |
| 结论 | **推荐** | 备选（仅当对象数真的成为问题时） | 不作主存；它其实**已经是**现有 24h 热层 |

**推荐 a**，三条理由：
1. 「写冲突」被命名规则从根上消除，不需要任何分布式协调——**最少的机制解决最多的问题**。
2. 不引入新 Redis 键，不抢跑 A-6（`docs/任务看板.md:479`，且 `:482` 明确「我说跑才能跑」）。
3. 对象数在真实量级下（每天几百个）完全不是问题；真到了「每天上万对象」再上 b 也不迟，届时 a 的数据格式可原样复用。

**b 的唯一适用条件**：需要「全局单一时序文件」给外部系统消费。当前没有这个需求，不建议为一个假想需求先付租约+双写的复杂度。

**c 的定位**：不是替代品，而是**已有的热层**。建议明确写成「Redis = 24h 热层（真值），文件 = 冷层（辅助）」，两层职责不再混。

## 3. 保留期建议（7 天 vs 24h）

**建议默认 7 天，理由三条**：

1. **量级支持**：常规场景 7 天约 9 MB，峰值也就 30–100 MB。为省这点空间牺牲可回溯性不划算。
2. **排障价值**：24h 意味着「周一查不了周五的事」。7 天正好覆盖一个工作周 + 一个周末。
3. **合规不冲突**：🏛️（`docs/决策看板.md:21`）允许持久层存「计数、计时、枚举、run 摘要」；这里存的就是 run 摘要（runId/sessionId + 时序 + 计数），**无正文、无工具入出参**。

**同时给严格档**：`retention-days: 1` 即退化为 24h 口径，其他参数全不变——把选择权留给用户，不写死。

需要用户拍板的只有一句：**7 天（推荐）还是 1 天（严格对齐共亡）**。

## 4. 若走 Redis 方案：与三条纪律的关系（本次不选，但先答清）

| 纪律 | 若新增 `ai:obs:*` 会怎样 |
|---|---|
| **A-6 冻结**（`任务看板.md:479`） | 键命名/结构/TTL 三面都要等 A-6 定调；现在起名 = 抢跑，后续大概率返工。这是不选 b/c 的**首要理由**。 |
| **SessionKeyRegistry 登记纪律**（`SessionKeyRegistry.java:118-140`） | 该表只有 `RUN` / `SESSION` 两种作用域，且注释明确「全局键/短命协调键**显式不进本表**」。缓冲键是全局键，只能进「显式排除」清单 → 等于同时改代码 + 改文档口径。另外 `RUN_KEY_COUNT=12` 有断言锁定（心跳面 5 条被用例锁定），加键必须同步改用例，属显式变更。 |
| **24h 共亡**（`决策看板.md:23`） | 缓冲键 TTL（如 10 分钟）**短于** session-ttl，不违反「不许活得更久」；但它仍是一次新的键族扩张，且引入「写者挂了谁来补偿」的新故障面。 |

结论：这些摩擦都是「选了 Redis 才付」的成本，选 a 则一分不付。

## 5. A2（Micrometer 指标）是否受影响

**不受影响，确认**。三条理由：

1. 指标是**进程内聚合**（Counter/Timer），只在内存里累加，不落文件、不跨实例协调。
2. 输出是**日志行**（走既有 stdout → 平台日志管道），不经过远程文件存储，因此不受「低频写」「写冲突」「删除」三条约束。
3. 每实例各自计数是**正常语义**（Prometheus 模型也是这样），跨实例求和交给日志平台，不需要应用层合并。

⚠️ 唯一 caveat：**不要把指标也落文件**。若将来有人想「指标也存一份到 data 目录」，它会立刻继承本设计的全部约束——所以 A2 明确写死走日志行。
