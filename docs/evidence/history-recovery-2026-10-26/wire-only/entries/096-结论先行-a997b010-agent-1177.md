## 结论先行

**选 a：服务端快照里确实有正文，丢的是前端恢复链路没读、没渲染。** 但要把“正文”拆成两处、并划一条边界：

| 快照字段 | 内容 | 是否在 Redis | 前端能否拿到 |
|---|---|---|---|
| `assistantContent` | **触发挂起的那一条 assistant 消息**的正文（不是整轮全部） | 是 | `/runs/{runId}` 有；`/runs/current` 没有；前端从不读 |
| `messageJson` | 挂起前模型看到的整串历史，含**此前各轮 assistant 正文** | 是 | 没有任何接口透出正文，`asMap` 只给 `messageCount` |
| `finalText` | 轮结束后的全文 | 是 | 轮结束后走 `/history`，不走快照 |

所以：**挂起态刷新，服务端有正文；前端只重建了工具卡，正文被“只有 USER 的历史”整体替换掉了。** 这不是 delta 没入档导致的“服务端没存”。

两个必须钉死的边界：

1. **`assistantContent` 不是“截至挂起已生成的全部正文”**，只是当前这条 assistant 消息；此前正文在 `messageJson`。而且纯工具调用轮的 assistant 正文通常为空（`RunSnapshot.java:84` 注释），所以“有没有正文”取决于模型在调工具前说没说话。
2. **如果是“还没挂起、模型正在流”的 RUNNING 刷新，服务端确实没有正在流的那段**——`assistantContent` 只在 `saveSuspended` 时写，delta 又跳过归档。这半边才是 b 的领域；T3b 场景 B 是挂起态，属 a。

**报告的问题**：场景 B 自己记录“挂起前实收 delta 拼接：`''`（模型还没产出正文）”（`docs/evidence/M2-T3b-施工报告-DS-V4-Flash.md:467`），等于这条用例**压根没有“正文尾部”可丢**；而且它只查了 `/history` 和 `/runs/current`，没查快照、没查 `/runs/{runId}`。所以不是代码后来变了，也不是确实没存，是**用例空转 + 根因漏了一条数据源**。

## 1) `saveSuspended` 到底存了什么

`RunStore.saveSuspended`（`backend/src/main/java/com/example/configmgr/ai/run/RunStore.java:354-369`）：

- `snapshot.setAssistantContent(assistantContent)`（`:364`）
- `snapshot.setMessageJson(codec.serializeAll(history))`（`:366`）
- `snapshot.setStatus(SUSPENDED)`（`:367`）
- `save(snapshot)`（`:368`）→ 整个快照序列化进 `ai:run:<runId>`（`RunStore.java:191-200`）

**谁传进来的**：`SpToolCallingManager.executeToolCalls` 在模型已经返回带 tool_calls 的 assistant 消息后调用：

```java
this.store.saveSuspended(runId, assistant.getText(), pendings, prompt.getInstructions(), this.codec);
```

（`backend/src/main/java/com/example/configmgr/ai/gate/SpToolCallingManager.java:188`；`assistant` 来自 `chatResponse.getResult().getOutput()`，见 `:142`）

所以：

- **`assistantContent` = 模型这一条 assistant 消息的正文**（`assistant.getText()`）。模型如果先说了“好的，我来启动发布”再调工具，这句话就在里面；纯工具调用轮则为空——`RunSnapshot.java:84` 的字段注释写得很直白：“通常为空串：工具轮的 assistant 正文就是空的”。
- **`messageJson` = `prompt.getInstructions()`**，即模型当时看到的 system/memory/user/此前 assistant/tool 消息；序列化时每条都存 `content`（`backend/src/main/java/com/example/configmgr/ai/memory/MessageJsonCodec.java:98-99`），因此**此前各轮 assistant 的正文也在里面**。

**反证它确实是权威正文**：续跑时 `ResumeService.rebuildAssistant` 把 `snapshot.getAssistantContent()` 写回 assistant(tool_calls) 的 `content`：

```java
.content(snapshot.getAssistantContent() == null ? "" : snapshot.getAssistantContent())
```

（`backend/src/main/java/com/example/configmgr/ai/run/ResumeService.java:394-405`，尤其 `:401-404`）

轮结束时，全文被追加进 `messageJson`，`assistantContent` 清空、`finalText` 置全文（`ResilientChatService.java:457-462`）。也就是说：**挂起时存在 `assistantContent` 的正文，续跑时会原样带回模型历史，不会丢。**

**时间线（排除“代码后来变了”）**：

- `assistantContent` 与 `assistant.getText()` 调用自 `b038e77`（2026-10-07 02:52）起就存在；`git blame -L 354,368 RunStore.java` 全指向该 commit；`git show b038e77:...SpToolCallingManager.java` 第 119 行就是同一句 `assistant.getText()`。
- T3b 施工是 2026-10-09 18:05，**晚于该字段两天**。

## 3) 前端刷新恢复路径到底读没读正文

### `restoreSuspendedSnapshot`（`frontend/src/stores/ai.ts:1342-1438`）

它只做三件事：

1. 拉 `runsCurrent(sid)`（`:1347`）；
2. 遍历 `current.pendingEntries`，只处理 `entryStatus === 'PENDING'` 的条目（`:1365-1432`）；
3. 找宿主消息（已有该工具段 → 最后一条 assistant → 都没有就**新建一条空 assistant**，`:1390-1399`），然后 `upsertToolPart` 写入挂起卡（`:1405-1413`）。

**全程没有读 `assistantContent`，也没有读任何正文。** 它只重建工具段。

### `loadHistory`（`frontend/src/stores/ai.ts:1045` 起）

- 先读 `sessionStorage` 镜像，镜像里有流式文字（`:1049-1076`；镜像写入是 messages 深监听 + 300ms 防抖，`:969-980`）。
- 然后拉 `/api/ai/history`。
- **历史非空时，直接整体替换**：

```ts
this.messages = history.messages.flatMap((item, index) => { ... })
```

（`:1141`）

- 替换完才调 `restoreSuspendedSnapshot()`（`:1323-1325`）。

而挂起轮的历史是什么样？T3b 报告场景 B 实测：`count=1`，只有一条 USER（`docs/evidence/M2-T3b-施工报告-DS-V4-Flash.md:468-469`）。因为记忆只在轮末收敛（`ResilientChatService#finish` 里才 `convergeMemory`，`:467`）。

**于是实际顺序是**：

1. 镜像里本来有流式正文；
2. `loadHistory` 用“只有 USER”的后端历史**整体替换**，镜像正文被丢掉；
3. `restoreSuspendedSnapshot` 发现没有 assistant 宿主，**新建一条空 assistant**（`:1396`），把工具卡挂上去；
4. 用户看到：USER + 空助手 + 确认卡，正文没了。

如果后端历史为空，镜像会被保留（`:1095-1109`），正文反而不会丢——但挂起轮的真实情况是历史里已有 USER，所以走的是替换分支。

**增量续收也不补正文**：`resumeSnapshotStream` 只收 `seq > lastSeq` 的状态帧（`:1444-1494`），断流提示仍是“结果可能不完整”（`:1477-1480`），没有补内容逻辑。

## 4) 报告判定 vs 现在的代码事实

报告场景 B（`docs/evidence/M2-T3b-施工报告-DS-V4-Flash.md:464-476`）的原始记录：

- `挂起前实收 delta 拼接：''（模型还没产出正文）`（`:467`）
- `/history`：`count=1`，只有 USER（`:468-469`）
- `runs/current`：`found:true / SUSPENDED / pendingEntries[...] / awaitingExternal:true / archiveMaxSeq:4`（`:470-472`）
- 结论：“此窗口内丢失的正文尾部**不可补齐**”（`:475`）

对照代码事实：

- **不是代码后来变了**：`assistantContent` 自 2026-10-07 就有；`/runs/current` 自 2026-10-09 09:54（`95b7eaa`）就有，但从未透出该字段；T3b 是 10-09 18:05。
- **不是确实没存**：`saveSuspended` 明确写 `assistantContent`（`RunStore.java:364`）和 `messageJson`（`:366`）；`ResumeService` 还把它当作权威正文重建历史（`:401-404`）。
- **报告判得对不对**：**结论“当前前端补不回”是对的；根因“记忆未收敛 + delta 不入档”不完整，漏了快照**。而且这条用例的 delta 是空的，**根本没有正文可丢**，所以它并没有真正验证“正文尾部”这件事。

还有一个报告没算到的点：**轮结束之后，正文会回到历史里**。

- 超时/批准后，`settle` 把 `prompt.getInstructions() + assistant + toolMessage` 写回 `messageJson`（`SpToolCallingManager.java:226-229`、`:505-516`），其中 `assistant` 就是带 `getText()` 的那条；
- 刷新后走续跑时，`ResumeService` 用 `assistantContent` 重建这条 assistant 再落库（`ResumeService.java:296-326`）；
- 轮末 `finish` 再把最终 assistant 全文追加进 `messageJson` 并 `convergeMemory`（`ResilientChatService.java:457-467`）。

所以“补不回”最多是**挂起期间的 UI 缺失**；等这一轮结束（确认、超时、取消后继续跑完），历史里会有完整正文，再刷新就能补回。它不是永久的数据丢失——除非快照在轮结束前过期/Redis 挂了。

## 5) 挂起等待期间后端还在不在生成新正文

**不在。挂起时刻，这一条 assistant 消息的正文已经“到顶”。**

- `executeToolCalls` 拿到的是模型已经结束的这一轮 assistant 消息（带 tool_calls），先 `saveSuspended`（`:188`），再进入工具执行；
- CONFIRM 走 `awaitConfirm` → `gate.awaitDecision` → `await()` 的阻塞循环：

```java
while (true) {
    ...
    boolean signalled = latch.await(Math.min(remain, HEARTBEAT_SECONDS * 1000L));
    if (!signalled) { beacon.pulse(...); ... out.heartbeat(...); }
}
```

（`backend/src/main/java/com/example/configmgr/ai/gate/ConfirmGate.java:254-256`、`:288-314`，`latch.await` 在 `:306`，心跳在 `:314`）

这里只有 Redis 读、闸门等待、心跳，**没有模型调用、没有新 delta**。

- 用户确认后，才 `executeOnce` 跑工具，把 `ToolResponseMessage` 加回历史（`SpToolCallingManager.java:207-229`），然后 Spring AI 发起**下一轮模型生成**；新正文从这时才开始。

所以：`assistantContent` 不是“半截还在长”的字段，挂起后就固定了；确认后产生的是**另一条** assistant 消息。说“到顶”只针对挂起时那条 assistant 消息，不是整轮回答。

## 6) 修法大小

**是 a 的小改，不需要 delta 入档。** 三条路，按改动面从小到大：

1. **纯前端（最小）**：`restoreSuspendedSnapshot` 里若 `found && snapshotStatus==='SUSPENDED'`，优先保留镜像里的 assistant 正文，别让 `loadHistory` 的历史替换把它冲掉；或先调已有但没人用的 `aiApi.run(runId)`（`frontend/src/api/ai.ts:104-106`），读 `snapshot.assistantContent` 渲染到宿主消息。约 1 个前端文件。
2. **前后端小改（更权威）**：给 `/runs/current` 加 `assistantContent`（后端 1 行 + 前端类型 1 行 + 渲染十几行）；若要把此前各轮正文也补全，再加一个从 `messageJson` 过滤出的“展示用 transcript”。仍然很小。
3. **delta 入档（中改，不推荐为这个场景做）**：会动 `SseChatEmitter`/`RunStore` 的归档、回放、seq、backlog（T3a 当初就是刻意让 delta 跳过归档，`RunStore.java:573-581`、设计卡 `docs/M2-T3-设计卡.md:51`）。它只在“**RUNNING 未挂起**时刷新、且希望回放补当前正在流的那段”这个子场景才必要；而且轮结束后历史仍会补回全文。

**仍然会丢的窗口（诚实边界）**：

- **RUNNING（还没挂起）刷新**：`assistantContent` 是 null，delta 不入档，回放只有状态帧；正在流的那段任何服务端存储都没有（只有 `messageJson` 里此前已 settle 的旧正文）。这半边确实是 b 的问题，但它是“运行中刷新”，不是 T3b 场景 B 的“挂起中”。
- **挂起但 `assistantContent` 为空**（纯工具调用、模型没说话）：没有当前轮正文可丢；此前的正文在 `messageJson`，但没接口透出，前端只能靠镜像。
- **挂起且有正文**：服务端有，前端不读——就是 a。

## 一句话给用户

你怀疑得对：**Redis 里有正文，丢的是前端的显示，不是服务端的存储。** T3b 报告场景 B 那次跑的是“模型一个字没说就调工具”的样本（delta 为空），所以它没有真正测到“正文尾部”；它又只看了 `/history` 和 `/runs/current`，没看快照的 `assistantContent`/`messageJson`。修法是把快照里已经有的正文接到前端恢复链路里（小改），不是把 delta 塞进归档（中改）。
