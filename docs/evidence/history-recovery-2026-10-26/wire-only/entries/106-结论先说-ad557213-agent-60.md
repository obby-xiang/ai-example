# 一、确凿：成熟组件直接覆盖，却手搓了

### 1. 作业元数据表 + 状态机 + 恢复扫描（JobRepository / JobExplorer 等价物）

- **手搓的是什么**：`jobs`/`job_items`/`validation_issues` 三张表当作业库，自写 5 态状态机、进度回写、条件终态、启动恢复。
- **证据**：`job/entity/Job.java:13-61`（`JobStatus{PENDING,RUNNING,COMPLETED,FAILED,CANCELLED}` + `progress/total/result_json`）；`job/repo/JobRepository.java:54-110` 用 6 条 `@Modifying` 条件 UPDATE 做"谁先到终态谁胜"；`JobProgressService.java:89-149` 每次分片边界开 `REQUIRES_NEW` 事务写进度；`StaleJobRecoveryRunner.java:52-103` 启动时 `findAll()` 扫 PENDING/RUNNING 直接判 FAILED。
- **本可用**：Spring Batch `JobRepository`（BATCH_JOB_EXECUTION / STEP_EXECUTION / EXECUTION_CONTEXT）、`JobExplorer.findRunningJobExecutions()`、`JobOperator.stop()`。映射关系：`jobs`≈`job_execution`、`job_items`≈`step_execution`、`result_json`≈`ExecutionContext`、`/jobs/{id}/issues`≈`step_execution` 的 exit message。
- **判断：核心一半是重复造轮子，一半是有意简化 —— 必须分开说。**

| 能力 | 自研是否等于 Batch | 说明 |
|---|---|---|
| 作业元数据持久化 | ✅ 重复 | 表结构与语义几乎 1:1 |
| 状态机 + 并发归宿 | ✅ 重复（但自研版实现得更好读） | Batch 也是乐观校验，本项目的条件 UPDATE 是正确做法 |
| 取消 | ✅ 重复 | Batch `JobOperator.stop()` 语义等价 |
| 重启/断点续跑 | ❌ **不是重复，是有意放弃** | Banner 明确"暂存/发布进度不可续，一律 FAILED，用户显式重跑"（`StaleJobRecoveryRunner` 类注）。Batch 的 restart 要求数据面按 step 切分才生效，本项目数据面不是 step 粒度 —— 换 Batch 也续不了 |
| 心跳判死 / 超时回收 | ❌ Batch 不提供 | 归到第三节"合理自研" |

- **替代成本与风险**：高。`jobs` 表已被任务中心 REST、AI 工具、前端 job-watch 直接消费；引入 Batch 要新增 6 张 `BATCH_*` 表 + 重写四类 Runner 为 Tasklet/Chunk，且**换不来断点续跑**（数据面不满足），收益主要是"少写元数据表"和"少写取消状态机"。**不建议换**；建议只在文档里承认这是 Batch 的等价物，避免后续再加第二套。

### 2. 整作业单事务 + 手搓分片（Spring Batch chunk 模型）

- **手搓的是什么**：一个作业从第一条到最后一行业务数据都在**同一个事务**里，靠 `batchSize=100` 攒 `List` 再 `saveAll` + `Thread.sleep(demo-delay)` 模拟分片。
- **证据**：`ImportJobRunner.java:60-61`（方法级 `@Transactional`）、`:140-155`（攒 100 行 `saveAll` 后 `Thread.sleep`）；`ExportJobRunner.java:75-76`、`:148-149`；`PrecheckJobRunner.java:65-66`；`PublishJobRunner.java:116` 单 `TransactionTemplate` 包整个发布。分片边界是纯装饰：进度写走 `REQUIRES_NEW` 旁路（`JobProgressService`），数据面仍是一笔巨大事务。
- **本可用**：Spring Batch chunk-oriented processing（`commit-interval=100` + 每 chunk 独立事务 + `ItemReader/ItemWriter`），或最小替代 `TransactionTemplate` 包 per-batch 提交。
- **判断：确实重复造轮子。** 这直接导致三个下游手搓：① 需要 `REQUIRES_NEW` 进度旁路；② 需要 `heartbeatRegistry.hold()` 给"无分片边界的慢临界段"开豁免（`ExportJobRunner.java:129/176`、`PublishJobRunner.java:87/97`）；③ 看门狗判死后线程仍在长事务里迟到写，于是要 runner 存活闸门。**换成 per-chunk 事务，这三处补丁大半可删。**
- **替代成本与风险**：中低（不引 Batch，只把循环体抽成 `TransactionTemplate.execute` 包一批）。风险：`@Transactional` 现在的"整批回滚"语义被 `PublishJobRunner` 文档明确依赖（`PublishJobRunner.java:45-56`），改成分片提交等于把"要么全成功要么全回滚"改成"部分成功"，**这是产品语义变更，需先裁决**。

### 3. Excel 读取全量进内存（三份拷贝）

- **手搓的是什么**：读 Excel 走"整文件 `byte[]` → `XSSFWorkbook`（全量 DOM）→ `List<Map>` 全量行"，三层都是全量。
- **证据**：`FileStorageService.java:49-51` `Files.readAllBytes`；`ImportJobRunner.java:106-107` 一次读字节再一次读成 `List<Map>`；`ExcelReader.java:32` `new XSSFWorkbook(new ByteArrayInputStream(fileBytes))`、`:56-73` 全表遍历收集。类注只对**指纹**做了流式（`FileStorageService.java:63-81`），读表没做。
- **本可用**：POI 自带 `XSSFReader` + `ReadOnlySharedStringsTable`（SAX 事件模型流式读）；EasyExcel/FastExcel 已封装成"监听器逐行回调"。
- **判断：确实重复造轮子（且是内存风险点）。** 百 MB 级 xlsx 在这里 ≈ 文件 + DOM（约 10–20×）+ 行 Map 三份堆占用；`spring.servlet.multipart.max-file-size: 5MB` 只是把上传口卡住，绕不过任务中心复用导出件（预检查 UPLOAD→EXPORT 回落）的路径。
- **替代成本与风险**：低-中。用 `XSSFReader` 改 `ExcelReader` 为 `Consumer<Map>` 回调，约 1 个文件改动；但会牵动三个 Runner 的 `rows.size()` 预知分母逻辑（`JobProgressTotals` 依赖"先知道总行数"，流式化后总数要改成"边读边涨"或预扫一次）。EasyExcel 引入新依赖，需评估 POI 5.5.1 版本兼容（EasyExcel 对 POI 版本较敏感）。

### 4. 导出写 Excel 用了 SXSSF，但收益被上游全额抵消

- **手搓的是什么**：写作侧正确用了 `SXSSFWorkbook(100)`，但调用方先把**全部过滤结果装进 `List<Map>`** 再写。
- **证据**：`ExcelWriter.java:31` `new SXSSFWorkbook(100)`、`:48-57` 逐行写、`:68` `dispose()`（用法规范）；`ExportJobRunner.java:128` `List<Map<String,Object>> filtered = new ArrayList<>()`、`:140-146` 全量 `add`、`:174` 才调 `excelWriter.write(def, filtered, ...)`；同时 `dataRowRepository.findByDefCodeOrderByRowKey(defCode)`（`:132`）又是一份全量实体。
- **本可用**：SXSSF 的价值来自"边取边写"，只需把 `List` 换成 `Consumer`/`ItemWriter` 分页流式（`Pageable` 或 `Stream<ConfigDataRow>`）。
- **判断：框架用对了、用法用错了 —— 属于"部分重复"，但结论是 SXSSF 当前形同虚设。**
- **风险**：改成流式写入后，`task_files.row_count` 与"取消时已写一半的文件"语义要重新定义（当前 `filtered.size()` 直接当 rowCount，`:189`）。

### 5. 打包下载：手写 zip + 全量 byte[] 响应 + 手写编码探测

- **手搓的是什么**：zip 用 `ByteArrayOutputStream` 拼完整包再回 `byte[]`；下载/单文件/模板包全部 `ResponseEntity<byte[]>`；解压时手写"UTF-8 乱码则回退 GBK"探测。
- **证据**：`FileController.java:272-284` `buildZip`（`ByteArrayOutputStream` + `fileStorage.read` 逐文件全读）；`:177-195` 单文件下载 `byte[]`；`:234-244` `download-all`；`:306-319` 模板 zip；`:154-173` `readZipEntries` 的 UTF-8/GBK 双解探测。
- **本可用**：Spring MVC `StreamingResponseBody`（流式响应，无整包内存）、`ResourceRegion`（Range 断点续传）、`ContentDisposition.attachment().filename(name, UTF_8)`（替代手写 `URLEncoder` + `filename*=UTF-8''`）；commons-compress 的 `ZipArchiveOutputStream` 可显式设编码，避免"先猜再重解"两遍 IO。
- **判断：确实重复造轮子（响应层）；zip 本身用 JDK `java.util.zip` 不算轮子。** 现场风险具体：`download-all` 对一个含 20 个导出件的任务会把全部 xlsx 读进堆再拼 zip（2× 峰值）。
- **替代成本与风险**：低。改返回 `StreamingResponseBody` 即可，但**会失去 Content-Length**，前端若依赖下载进度条需同步改。GBK 探测建议保留（`ZipInputStream` 设编码是 JDK 能力，commons-compress 也只是同一件事），属于真实兼容需求。

### 6. 带条件查询的"内存分页"

- **手搓的是什么**：无条件路径走 DB 分页（正确用 `Pageable`），有条件路径退化为"全表读 → Jackson 逐行反序列化 → 内存过滤 → `subList` 分页"。
- **证据**：`ConfigDataService.java:62-69` `findPagedFiltered`（`matched.subList(from,to)` + `new PageImpl<>`）；`:98-112` `filterRows`（`findByDefCodeOrderByRowKey` 全量 + 逐行 `readValue`）；`:72-74` `countFiltered` 同样是全量算长度；`DataController.java:79-81` 调它。
- **本可用**：Spring Data `Specification`/`Querydsl` 在无条件路径已证明可用（`ConfigDataRowRepository.java:34-42`）；有条件路径的根因是字段存在 `data_json CLOB`（`ConfigDataRow.java:31-32`），关系型 `Specification` 无法表达。
- **判断：分页机制本身确实重复造轮子（`Pageable` 就在旁边）；但"过滤只能内存做"是 schema 设计导致，属框架能力不足。** 两者要分开记账。
- **替代方案与成本**：H2 支持 JSON 函数（`JSON_VALUE`/`JSON_OBJECT`），可把常用条件编译成 native query 下推；成本中等、SQL 注入面要严管（当前 `ConditionEvaluator` 白名单是好的前置）。**当前实现对 300 行演示数据无痛，对 10 万行级别是 O(n) 全扫 + 全量反序列化。**

### 7. 发布"范围差集删除"逐行遍历 + 逐行 delete

- **手搓的是什么**：把本次导入覆盖范围的 rowKey 收进 `HashSet`，再遍历该范围所有已发布行逐个比对、逐个 `delete`。
- **证据**：`ConfigDataService.java:201-225` `deleteRowsOutOfRange`（`keptKeysByScope` 建表 → 外层 `findRowsInScope` → `entry.getValue().contains(rowKey)` → `dataRowRepository.delete(row)`）。
- **本可用**：单条 `DELETE FROM config_data_rows WHERE def_code=? AND scope_type=? AND scope_key=? AND row_key NOT IN (...) AND updated_at < ?`（`@Query` native 或 `JdbcTemplate.batchUpdate`）；H2/PG 也可 `MERGE`。
- **判断：确实重复造轮子（差集运算由数据库一行 SQL 完成）。** 注意并发保护条件（`updatedAt >= importedAt` 不删）可以原样放进 `WHERE`，用 `returning`/二次查询拿"被保护行"——语义不丢。
- **风险**：`NOT IN` 在 `rowKey` 数量上千时要分批（H2 参数上限）；`row_key` 是拼接字符串（`buildRowKey`，`ConfigDataService.java:151-159`），`|` 分隔存在**歧义键**隐患（`"a|b"+"c"` 与 `"a"+"b|c"` 同键），与本次替换无关但同表同键，值得一并登记。

### 8. 看门狗自建 `ScheduledExecutorService`（`@Scheduled` 就在 classpath）

- **手搓的是什么**：手工 new 单线程 daemon 调度器 + `scheduleWithFixedDelay` + 自己的 `@PostConstruct/@PreDestroy` 生命周期。
- **证据**：`JobWatchdog.java:114-134`（`Executors.newSingleThreadScheduledExecutor` + `thread.setDaemon(true)` + `shutdownNow`），类注 `:52-53` 明说"仓内无 `@EnableScheduling`，故自建"。
- **本可用**：`@EnableScheduling` + `@Scheduled(fixedDelayString=...)`（Spring 自带，默认单线程 `TaskScheduler`，与"不复用作业池"的诉求天然一致）；多实例互斥可用 ShedLock。
- **判断：确实重复造轮子，但**代码量小、行为等价。** 唯一实质差异：`@Scheduled` 默认调度器是共享的，本项目想彻底隔离观察者 —— 用 `@Scheduled` + 自定义 `TaskScheduler` bean 也能做到。
- **风险**：低。注意当前实现**每个实例都会扫**（多实例下同一僵尸作业会被两个实例判两次），`judgedJobIds` 只是进程内去重；换 `@Scheduled` 不改变这一点，需 ShedLock 才解决。

### 9. `spring-boot-starter-validation` 在 pom 里，代码零使用；请求体全是 `Map`

- **手搓的是什么**：所有写接口用 `@RequestBody Map<String,String>`，参数校验靠手写 if + `valueOf` 抛异常。
- **证据**：`pom.xml:62-66` 引入 validation；全仓 `@Valid`/`@NotBlank`/`ConstraintValidator` **0 命中**（grep 仅 `GlobalExceptionHandler.java:90-101` 处理 `MethodArgumentNotValidException`/`ConstraintViolationException`，即"留了出口没有入口"）；`TaskController.java:77` `Map<String,String> body` + `:78` `TaskType.valueOf`；`JobController.java:27-32` 同款；`TaskService.java:262-266` `setImportMode` 手写 `"MERGE".equals(mode) && "REPLACE".equals(mode)`；`TaskController.java:126-152` 手写 condition JSON 合法性校验。
- **本可用**：请求 DTO（record）+ `@Valid` + `@Pattern/@Max`；`TaskController.java:49` 的 `size` 无上限问题（`DataController.java:51-56` 注释里自己登记了这个缺口）一条 `@Max(100)` 就闭合。
- **判断：确实重复造轮子 —— 且是本清单里**性价比最高**的一处：依赖已在，出口已写，只缺 DTO 与注解。
- **风险**：极低。改 `Map` → DTO 会改变"未知字段是否报错"的行为（Jackson 默认忽略），需确认前端不依赖宽松入参。

### 10. `saveAll` + IDENTITY，且未配 JDBC 批处理

- **手搓的是什么**：以为 `saveAll(100 行)` 是批量，实际 Hibernate 对 `IDENTITY` 主键**默认禁用 JDBC batching**，仍是 100 条独立 INSERT。
- **证据**：`ImportJobRunner.java:141/158` `stagingRowRepository.saveAll(stagingBatch)`；`ConfigStagingRow`/`ConfigDataRow` 均 `GenerationType.IDENTITY`（`ConfigDataRow.java:16`）；`application.yml` 的 `spring.jpa` 只有 `ddl-auto/show-sql/open-in-view`，**无 `hibernate.jdbc.batch_size`/`order_inserts`**。
- **本可用**：JPA 自带（配 `batch_size` + 改 `SEQUENCE`/`TABLE` 生成器，或 `hibernate.jdbc.batch_size` 配合 `@GeneratedValue(SEQUENCE)`）；Spring Batch `JdbcBatchItemWriter`。
- **判断：确实重复造轮子（批量写）且当前实现无效。**
- **风险**：低-中。改主键策略会动 Flyway 迁移与既有数据；H2 上收益不如生产库明显，但代码意图与运行事实不符值得登记。

### 11. 导入逐行查 `baseVersion`（N+1）

- **手搓的是什么**：导入每一行都去已发布表查一次同键行拿版本号做乐观快照。
- **证据**：`ImportJobRunner.java:134-137`（循环体内 `dataRowRepository.findRow(defCode, scopeType, scopeKey, rowKey).map(getVersion)`）。
- **本可用**：Spring Data 一次 `findByDefCodeAndScopeTypeAndScopeKeyIn/RowKeyIn` 装 `Map<rowKey,version>`；或发布时用 `@Version` 冲突检测（已在 `upsertPublished` 用 `OPTIMISTIC_FORCE_INCREMENT`）。
- **判断：部分重复（查询方式手搓），但 `baseVersion` 快照这套语义 JDK/JPA 没有现成物 —— 语义合理。**
- **风险**：低。一次修复即把 1 万行导入的 1 万次查询降到 1 次 IN 查询。

# 二、存疑：有重复，但有可辩护的理由或替换不划算

### 13. Redis 租约/心跳（Redisson `RLock`、ShedLock 可覆盖一部分）

- **手搓**：`job:runner-active:<id>` 的 `SET + TTL + 续期` + 本机 PID 解析清理 + `isRunnerAlive` fail-closed。
- **证据**：`JobHeartbeatRegistry.java:166-184`（beginRunner 硬闸门）、`:294-303`（renew）、`:234-259`（`cleanupDeadLocalRunner` 用正则解析 `runner-<host>-pid<n>-xxxx` 再 `ProcessHandle.of(pid)`）。
- **本可用**：Redisson `RLock`（看门狗自动续期）、`RSemaphore`；或 `spring-integration-redis` 的 `RedisLockRegistry`；多实例定时任务互斥用 ShedLock。
- **判断：部分重复但有合理理由。** 他们要的语义是"**进程存活**"而非"临界区互斥"——锁会被 run 超时自动释放，反而误判 runner 已死。自研的 PID 校验是对"进程崩溃后 TTL 未到"这一真实窗口的补丁，Redisson 也给不了。**为该语义引 Redisson 不值。**
- **风险**：自研部分的可测性/运维心智成本是真实代价（类注 150 行里有 5 个"一致性边界"免责声明）。

### 14. 行级 upsert 手搓（且同一次发布查两遍同键）

- **手搓**：`findRow` → `em.lock(OPTIMISTIC_FORCE_INCREMENT)` → `save`。
- **证据**：`ConfigDataService.java:173-186`；`PublishJobRunner.java:189-203`（先 `findRow` 再做冲突判定，然后把它当参数传给 `upsertPublished` —— 查询本身是对的，但没有合并）。
- **本可用**：JPA `@Version` 已足够；批量场景用 `saveAll` + 正确 batch 配置。
- **判断：JPA 能力已用上（`@Version`/`OPTIMISTIC_FORCE_INCREMENT` 是框架原语），不算重复造轮子；真正的问题是 N+1 与两次查询。** 归为"部分重复"。
- **风险**：低。

### 15. 表头匹配 / `_meta` 模板协议

- **手搓**：`_meta` 隐藏 sheet 存 `def_code + 列映射`，无 meta 时按"标签去 `*` 归一"回退匹配，匹配不上记 `_unknown_N`。
- **证据**：`ExcelReader.java:84-101`（readMetaSheet）、`:121-141`（labelToCode 建表）、`:153-157`（`DataFormatter` → 全转 String）。
- **本可用**：EasyExcel `@ExcelProperty(value=..., index=...)` + 自定义 `Converter` 覆盖面映射与类型转换。
- **判断：列名/标签→code 的映射**是框架覆盖的（EasyExcel 按表头名读），但 `_meta` 隐藏 sheet 携带 `def_code` 做"模板错配 fail-fast"（`requireMetaDefCode:108-115`）是**本项目独有的数据治理协议**，EasyExcel 无对应物。**类型转换是真丢**：所有单元格变 `String`，`NUMBER`/`DATE`/`BOOLEAN` 语义在导入侧丢失（`getCellValue` 只 `formatCellValue().trim()`），下游只能靠字符串比较（`ConditionEvaluator.compareValues:138-150` 现场试 Date→Double→String 就是后果）。
- **风险**：如果只做"按 EasyExcel 读表头 + 保留 `_meta` 主校验"，改造约 1 个文件；但要同时补类型转换（`FieldType` → `Converter`），会改变 `data_json` 中的值类型，**影响已发布数据的历史形态** —— 需迁移考虑。

### 16. 时区处理口径不一致

- **手搓/隐患**：Jackson 固定 `Asia/Shanghai`，但看门狗把 `LocalDateTime` 转 `Instant` 用 `ZoneId.systemDefault()`。
- **证据**：`JacksonConfig.java:22-23`（`setTimeZone("Asia/Shanghai")`）vs `JobWatchdog.java:194`（`baseline.atZone(ZoneId.systemDefault())`）；`Job`/`ConfigDataRow` 全用无时区 `LocalDateTime`。
- **本可用**：`Instant`/`OffsetDateTime` + 统一 `Clock`（`JobWatchdog` 已经注入了 `Clock`，但只用于 `millis()`，转换仍取系统时区）。
- **判断：不是"框架缺失"，是自研时间处理的一致性缺口。** 当前单机 + 默认时区 = 巧合正确；容器 `TZ=UTC` 部署会让看门狗判超时偏移 8 小时（`max-execution-time` 判据直接失效）。
- **风险**：修一处 `Clock#getZone()` 即可，但 `Clock` 目前是包级私有构造注入，需扩到生产构造。

### 17. 死 schema：`config_dependencies` 表

- **证据**：`V1__schema.sql:50-56` 建表（含 `uq_dep` 唯一约束）；全仓 Java 0 引用 —— 依赖关系实际由 `ConfigField.refDefCode` 推导（`DependencyResolver.java:42-50`）。
- **判断**：不是轮子，是"建了轮子没用"。可删，或把 `DependencyResolver` 改为读该表以获得"显式声明依赖"能力。

### 18. 种子数据用 `ApplicationRunner` 手写幂等

- **手搓**：`regionRepository.count() > 0` 整体跳过；GLM 种子用逐定义 `existsByCode`。
- **证据**：`DataSeedRunner.java:33-38`；`GlmSeedService.java:41-47`。
- **本可用**：Flyway 已在（`flyway-core` + `db/migration` + `baseline-on-migrate`），种子可作为 `R__seed_*.sql`（repeatable migration）由 Flyway 保证只跑一次，且版本可追溯。
- **判断：部分重复。** 但 `DataSeedRunner` 要插的是**动态定义 + JSON 数据**（`ConfigField` 集合、`optionsJson`），写成 SQL 会很丑；且 `GlmSeedService` 有程序化数据生成（`valueOf`，260 行）。**归"合理"边缘**，主要问题是两套种子逻辑并存（7 个定义 vs 8 个定义）。

# 三、合理自研：框架确实不覆盖

| # | 自研点 | 证据 | 为什么框架给不了 |
|---|---|---|---|
| 19 | **心跳判死 + 绝对超时 + 慢临界段豁免** | `JobWatchdog.java:160-244`；`JobHeartbeatRegistry.hold/release:268-281` | Batch 只管执行记录不管存活；Quartz 的 misfire 是"触发器错过"，不是"运行中线程失联"；K8s liveness 管进程不管业务作业。这套"心跳 ×3 + 绝对上限 + 长事务 hold 豁免"是合理的自研 |
| 20 | **SSE 单帧写预算** | `common/sse/SseWriteBudget.java:175-224`（提交到弹性池 + `Future.get(15s)` + 超时摘订阅者） | Spring 的 `SseEmitter.timeout` 是**整条流寿命**，不是**单帧写**；Tomcat 只有 `connection-timeout` 派生的 120s 兜底。类注有实测依据（jstack + 字节码），是真问题真解法 |
| 21 | **动态查询条件语言** `ConditionEvaluator` | `data/service/ConditionEvaluator.java:60-150`；`QueryCondition.java` | 字段是 JSON in CLOB，无实体属性；JPA `Specification`/Querydsl 都表达不了。12 个操作符白名单 + 未知操作符抛错（`:131-134`）是正确的安全姿态 |
| 22 | **预检查三项校验** | `PrecheckJobRunner.java:157-173`（必填）、`:175-189`（主键重复）、`:209-233`（引用存在性） | **必须区分**：必填 = 单对象约束，可用 Hibernate Validator 自定义 `ConstraintValidator<RequiredForDef, Map>` 覆盖，但收益仅省 15 行；**主键重复**是文件级集合约束、**引用存在性**要跨表查询，都不是 Bean Validation 的语义范围（validator 内还是得写这段逻辑）。**"必填可迁移、另两项不可"** |
| 23 | **runner 存活闸门 + 条件 UPDATE 状态机** | `JobService.java:291-308`；`JobRepository.java:90-110` | Spring 没有"作业租约"原语；这套锁序（task→job）+ 条件 UPDATE 是分布式作业的正确写法，自研版注释密度远超框架文档 |
| 24 | **Excel 模板构建**（下拉校验/批注/隐藏 `_dict`） | `ExcelTemplateBuilder.java:69-118`（`XSSFDataValidationHelper` + `createFormulaListConstraint` + `_dict` 隐藏表） | EasyExcel 不做数据验证下拉；POI 原生写法是唯一路径。**纯 POI，不算轮子** |
| 25 | **i18n 出口** `ErrorBodyFactory` + 自定义 `LocaleResolver` | `WebI18nConfig.java:41-105`；`ErrorBodyFactory.java:59-107` | 已正确复用 Spring `MessageSource`；覆写 resolver 的理由（"头缺失会退到 JVM 默认 locale，CI 是 en-US"）是真实跨平台缺陷。是**配置/覆写**而非重造 |
| 26 | **无 DTO 映射层** | 全仓无 MapStruct/ModelMapper；controller 直接返回实体（`TaskController.java:60-65`、`DataController.java:72-85`），仅有 `TaskSummary` record（`TaskController.java:67-74`） | 没有"映射"可手搓，也没有该造的轮子。**真问题不是缺 MapStruct，而是缺 DTO 边界**（见 #9：实体直出导致 `data_json` 字符串直接暴露给前端、`@Valid` 无处可挂） |
| 27 | **错误码体系 + 双形态错误体** | `common/ErrorCodes.java`（325 行）、`ErrorBodyFactory.java:76-94`（信封 vs RFC 9457 按 `Accept` 切换） | 用 Spring `ProblemDetail` 原语组合，不是重写。合理 |

## 一句话优先级建议

按"改动小、收益大"排序：**#9（挂上 `@Valid` + DTO）→ #10（batch_size）→ #11（IN 查询）→ #12（删死代码）→ #5（StreamingResponseBody）→ #7（差集删除下推 SQL）→ #3/#4（Excel 流式，风险最高、收益也最大）**；**#1/#2 不建议引入 Spring Batch**（换不来断点续跑，且与现有前端/工具面强耦合）。
