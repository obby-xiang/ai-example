## 2. 代码面：delta 链路逐点核对

链路（`ResilientChatService.java:1268-1286`）：

```
Generation.getOutput().getText()  ← String
  → guard.feed(raw)               ← OutputGuard，纯 String
  → accumulator.accept(safe)      ← StringBuilder
  → out.delta(safe)               ← SseChatEmitter.java:707-712，frame.put("text", text)
  → FrameSizeLimiter.apply(...)   ← 仅超限时 takeChars 截断
  → frames.append(runId, frame)   ← RedisFrameStore Jackson → bytes
```

逐点排查结论：

1. **`SseChatEmitter.java:1114` `new String(payloadBytes, UTF_8)`** —— 这是本仓唯一在 delta 链路上的"字节→字符"解码。但它只用于**实时订阅者下发**，归档走的是 `frames.append(Map)`（:1103）。**归档帧本身就脏** ⇒ 排除。
2. **`FrameSizeLimiter.takeChars`（:247-266）** —— 有代理对保护（:262），且 `substring` 按 char 截断只会产生**孤立代理项**，Jackson 序列化时写成 `'?'`（0x3F）。实测字节是 `EF BF BD`，**不是 3F** ⇒ 排除"按 char 截断切断代理对"这一整类猜测。
3. **两条独立写路径都脏**（xevents 帧 + `ai:run` 的 `messageJson`/`finalText`），二者代码路径不同、序列化点不同 ⇒ 坏点在**进入本仓 `consume()` 之前的 Java String 里**。
4. **Spring AI 侧**（`javap` 实测 `OpenAiApi.chatCompletionStream` 用 `bodyToFlux(String.class)`）：SSE 由 `ServerSentEventHttpMessageReader` + `StringDecoder` 处理，`AbstractCharSequenceDecoder.decode(Publisher)` 是**先按行分隔符累积到 `LimitedDataBufferList`、拿完整行再 `decodeInternal`**（delimiter `\r\n`/`\n`），且解码器是 REPLACE 模式。也就是说：**跨 TCP 包切开的多字节字符会被拼回，不会被切坏**；但任何**行内非法字节**会被静默替换成 U+FFFD。
5. 前端 `frontend/src/api/sse.ts:322` 用 `decoder.decode(value, { stream: true })`，流式安全，且它影响不到 Redis 归档。

## 4. 乱码根因（含缺什么证据）

**根因：进入本仓 `consume()` 的那一份 String 里就已经是 `\uFFFD\uFFFD`。**

证据链：① 坏帧字节是两颗 `EF BF BD`（不是 `?`、不是孤立代理项）⇒ 只能由解码器的 REPLACE 产生；② 本仓 delta 链路全程 String，唯一的 `new String(bytes)`（:1114）只影响实时下发，而归档也脏 ⇒ 排除；③ 两条独立写路径同脏 ⇒ 坏点在 String 里；④ 前端流式解码 + spring-ai 降版均已排除。

**两次 U+FFFD 而非一次**，最贴合"3 字节字符被 2|1 切成两个非法子片段、各被 REPLACE 一次"的形状——但 Spring 的按行解码不会切字符，所以更可能是 provider 侧：要么 API 传了非法字节，要么**模型自身吐出了两个 `\uFFFD` token**（byte-level BPE 的半截 token 是已知故障形态，天然"换模型也一样"，因为它与模型家族/推理栈有关而与本仓无关）。

**缺的证据**：《上游原始字节》。我拿不到——provider key 只在 java 进程环境里（`keyRef: ENV`，用户/机器环境变量里没有），本仓也没有抓包/tee 通道。要钉死，需要给后端加一个本地 tee 代理（`AI_BASE_URL=http://127.0.0.1:18080` 转发并落原始字节），跑 1–2 轮出坏字，比对"上游 JSON 里是不是本来就是 `\uFFFD`"。另外当前只配了 1 个 provider / 1 个模型（`deepseek/deepseek-flash`），"换别的模型也一样"这句我也无法在此环境复核。

## 5. 断续：帧时间戳取证

今天 11 个 run 的全部 ≥1.5s 空档，**只有三种形状**：

| 形状 | 时长 | 例子 |
|---|---|---|
| `start → message_start`（首包/思考） | 2.0–7.0s | 15:59:49 我发的 run 7.0s |
| `tool_result → 下一帧`（工具轮后模型延迟） | 2.0–4.5s（最狠 8.7s） | 15:17:08 3.9s、15:26:04 4.5s |
| `frontend_tool_request → result`（HITL 人工等待） | 6.7 / 11.2 / 34.4s | 15:10 那轮 |

**`delta → delta` 空档今天最大只有 0.91s**，从未到"好几秒"。但"蹦长段"有硬证据：

- **379 个 ≥20 字的 delta，100.0% 以锚字符开头**；**40 个 ≥100 字的 delta 全部 ≤131 字**；
- 对照：2835 个 1–3 字 delta 只有 **9.2%** 以锚字符开头（随机水平）。

这个分布只有一种解释：**大块文本是 `OutputGuard` 累积后释放的**。

机制（`ai/gate/SafetyRules.java:166-178` + `ai/run/OutputGuard.java:61-139`）：

```
TAIL_WINDOW = 128                                   // SafetyRules:66
ANCHOR_CHARS = "sAkK-:jJbBpP@/"                    // SafetyRules:181
cut = holdFrom(buffer)  →  末尾 128 字里第一个锚字符的下标
        → 该锚之后全部扣住，直到它滑出 128 字窗口，才一次性吐出
```

锚字符集里 `-`（每个 Markdown 列表项）、`:`、以及 `s A k K b B p P j J` 这 8 个 ASCII 字母（出现在 `PROJECT`/`import`/`sk-`/`sx` 等每个英文标识符里）——**中文技术文几乎每段都命中**。

静态复现（用我实抓的一轮真实输出文本喂真实 `OutputGuard`，2 字一喂）：

```
step 0..77 : 2 2 2 2 ... 2      （纯中文段，逐字吐出）
step 78..121: 1 0 0 0 ... 0     ← 126 字完全静默
step 122   : 65                 ← 一次性蹦 65 字
```

**时长公式**：静默 = 128 字 ÷ 出字速率。实测 deepseek-flash ≈ 218 字/秒 ⇒ 0.44–0.91s（与我测到的 delta 空档吻合，所以这几轮只是"卡一下"）；**若是推理类或更慢的模型（30–50 字/秒）⇒ 2.5–4.3s，正好是"停住好几秒"**。

**与工具轮叠加才是完整形状**：工具结果回来后模型先静默 2–4.5s（最多 8.7s，这是模型侧延迟，非本仓），正文第一句往往以 `-` / 英文标识符开头 ⇒ 立刻再进 128 字静默 ⇒ 用户看到「工具卡 → 好几秒空白 → 蹦出一大段」。

**已排除的嫌疑**：`SseWriteBudget` 是 15s **写超时**不是限速器（`SseWriteBudget:87`）；投递池 8 线程、每订阅队列 256（`AiProperties:830/845`）；前端 75ms 防抖（`markdown.ts:458`）+ 1 万字降级（`markdown.ts:44`）；无 `turn_retry`（今天所有 run `attempts=1`）；前端 idle 超时 45s（`sse.ts:30`）不会把 6s 空档误判。

## 6. 最小修法建议（未改代码）

**断续（首选，改动最小）**：把 `SafetyRules.holdFrom` 的"任一锚字符"改为"**规则字面前缀匹配**"——只有当窗口尾部确实等于某条规则的起始若干字符（`-----BEGIN`、`sk-`、`AKIA`、`://`、`eyJ`、`postgres://`、`test_` 等）时才扣住，且扣住量 = 该前缀长度。这样 Markdown 的 `-`、`:` 与单字母 `s/A/k/b/p/J` 不再误扣，"攒满 128 字才吐"消失。次选（更保守）：保留窗口但加**时间上限**——缓冲被扣住超过 200ms 就只保留尾部 16–24 字、其余立即发出。注意：两种改法都会略微削弱"跨分片的模式识别"（只在真前缀处扣住），需要 `SafetyRulesTest` / `OutputGuardTest` 补"跨分片仍能命中"的用例。

**乱码**：
1. **先做可观测**（最小、零风险）：在 `ResilientChatService.consume` 入口 `if (raw.indexOf('\uFFFD') >= 0)` 打一条结构化 warn（runId/seq/长度/偏移，不放原文），并在 `done` 帧加 additive 计数。这能把"上游带入替换字符"从静默变成血证，也直接给下一步定位提供样本。
2. **若确认来自上游**：本仓无需改渲染；可选在 `textEnd` 后对含 U+FFFD 的段落做一次非流式重述（成本较高），或保持原样只做提示。
3. **不建议**现在改 Spring AI 的 SSE 解码链：实测它是**按行累积后再解码**，跨包不会切字符；改它属于"没有证据的试错"。
