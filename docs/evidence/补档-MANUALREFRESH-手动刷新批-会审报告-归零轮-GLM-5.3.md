## 逐条评议

**Z1 谓词假 ⇒ 停表 —— 采纳，附条件。** 现状核实：`polling.ts:106-108/177-183` 谓词假确仅降频（desiredIntervalMs 切 fallback），永不停表，卡描述属实。dormant（非 destroy）+ 事件/回可见/手动触发 re-arm 的设计正确。**条件**：dormant 态必须保持 `invoke()` 的 started/paused 双闸与 dirty 补发语义（:134-146），且 `setIntervals()` 在 dormant 下的行为要定义（job-watch 通道切换会调它）；refreshNow 在 dormant 仍须可用（补刷入口不变）。

**Z2 任务中心归零 —— 采纳。** 用户直裁在前，设计选择（纯事件驱动 + 回可见补刷 + 手动按钮）是对该裁决的忠实落地。验收"静止可见 ≥60s GET /api/tasks 恰好 0 次"可测。两点说明：①闲置任务（非在跑、无订阅）的行内变更将不再自动到达——属直裁接受的时效性折损，建议在 PR 描述里明示而非隐含；②该验收与 5m emitter 重连的一发 refreshNow（卡 1d 自认）存在口径张力，见 Z6。**注意**：Z2 的前提是 Z3 把事件通道补全，且必须一并解决 dead 通道任务问题（见 Z3），否则形成永久盲区。

**Z3 订阅池扩面 —— 有条件采纳（会审重点）。** 方向正确：归零后无事件通道的任务永不自动刷新确不可接受，全量订阅 RUNNING/PENDING 是与归零自洽的唯一主案。但卡漏了两个硬约束：
1. **F6 dead-set 死区（关键漏项）**：`task-events.ts:122-131` 现设计在 onerror 判死时 close 并 `dead.add(taskId)`，且 `plan()`（:138-146）**永久排除 dead 任务**，其兜底注释明写"走列表条件轮询兜底"——而 Z2 恰好把该兜底删了。即：SSE 一次抖动判死 ⇒ 该任务在任务中心**永无自动刷新**（只剩回可见/手动），比"第 4 个任务不订阅"更糟。修正案：dead 改为带退避的复活探测（如 sync 时对 dead 任务每 30~60s 允许重订一次），或 dead 任务回可见时强制补刷 + 重订。此项不解决，Z3 的"扩面"只是把盲区换了个位置。
2. **HTTP/1.1 同域 6 连接上限**：task-events 池头注释已论证 AI 通道用 fetch 不占 EventSource 名额，但 Z3 全量订阅 + 向导页 job-watch（≤3）+ `api/sse.ts` reattach（1 条 EventSource）并存时，在跑任务 ≥5 即可能顶满浏览器同源连接配额（HTTP/1.1 下 fetch 请求也占连接），饿死其它请求。备选"上限提到 8"**直接不可取**（8 > 6）。建议：全量订阅但设绝对上限（≤4~5，超限部分回可见补刷兜底），或先核实生产部署为 HTTP/2（多路复用下无此约束）再放开。"60s 慢速保底"兜底备选确违背归零精神，仅在上两项都不可行时考虑。
另：分页外（第 2 页）的在跑任务不在 getTargets 快照内，翻页 load → sync 会补订，可接受，无需改。

**Z4 job-watch 归零 —— 有条件采纳（会审重点）。** 通道语义正确：realtime ⇒ 0 周期、onerror/readyState 判死才降 3s、onopen 恢复回 0（job-watch.ts:140-149 现状可平滑改造）。但有一个卡未覆盖的可靠性缺口：**静默悬挂不可检出**——`/api/tasks/{id}/events` 无周期心跳（HEARTBEAT 仅订阅首帧），0 周期轮询 + 连接看似 OPEN 但被网络黑洞（代理空闲掐断、无 TCP FIN）时：无帧、无 onerror、服务端 5m emitter complete 也到不了客户端 ⇒ 进度条冻结且永不降级。修正案（二选一，施工卡须定）：a) 前端帧空闲看门狗——realtime 态下 N 秒（建议 60~90s）无任何帧即主动探活一次并重估通道；b) 服务端补周期心跳帧（如 30s 一发），使"无帧超时"成为可靠判据。另注意：5m emitter 到点 complete ⇒ 浏览器重连窗口会瞬时降 3s 再回 0，属预期行为但与"realtime ⇒ 0 周期请求"字面冲突（每 5 分钟边界数跳 3s GET），验收须容忍该窗口（见 Z6）。

**Z5 消灭 waitForJobFinal —— 采纳，附三条件。** `api/jobs.ts:73-91` 1s 裸轮询、`workspace.ts:452` void 调用无 AbortSignal 均实测属实。复用 watchJob（SSE 驱动）方向正确。条件：①**保留墙钟上限**——现实现 300s 超时会"提示恰好 1 次 + 保留现场"（task.ts:509-512 口径），纯事件驱动后作业悬挂（活 SSE + 永不终态）将无任何出口，新实现须带等价墙钟守卫；②F4 jobId 闸（task.ts:111-114，并发跟踪只认最后者）须移植到新路径；③明确 watcher 生命周期归属——watchPublishOutcome 从 workspace 触发、用户可能离开向导页，复用 job-watch 后须定谁持有/回收（job-watch 有同 kind 回收表），防泄漏或提前断流。若保留降级轮询，visibility + AbortSignal 要求正确。

**Z6 验收口径 —— 采纳，附三修正。** ①②③④⑤⑥方向均合理。修正：a) ①的 60s 窗口可能撞上 5m 重连触发的 refreshNow 一发（断链恢复性质，卡 1d 自认），须明确豁免条件（避开 5m 边界测，或口径改为"除重连补刷一发外恰好 0 次"）；b) 补一条 **dead 通道任务的兜底行为断言**（Z3 修正案的验收）；c) 若采纳 Z4 看门狗/心跳，③断链演练须补"静默悬挂"场景（连接 OPEN 但无帧 → 看门狗触发降级）；未采纳则须明示该场景不设防。
