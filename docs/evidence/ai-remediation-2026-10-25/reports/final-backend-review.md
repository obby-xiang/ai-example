## Cross-patch interactions examined (not just individual hunks)

1. **Park-exit lifecycle ↔ decision write (`ConfirmGate` 780-810, 1580-1610).** Both sides take `submitLock`; the park thread re-reads the pending entry inside the lock, so there are exactly two exits: settled → this thread drives (and the decision side's `woke=true` skip is then *true*), or unsettled → release lease **then** clear all latches (both inside the lock) → later signals must miss and the dead-card fallback dispatches. I checked the third-order race explicitly: signal is taken inside the same lock as `putPending`, so "signal hits a latch nobody awaits" is no longer constructible inside a JVM; across JVMs the signal always misses by construction and the lease (`acquireFenced`, epoch-scoped release) plus `claimExecution` decide the single driver. The lease-then-latch order is load-bearing and correctly justified (the reverse order lets a reentrant acquirer take the lease and then have it deleted).
2. **`switchParkedLifecycle` ↔ outer latch cleanup.** The new "settled" return leaves the latch in the map (no `finally` runs on that path), but `SpToolCallingManager:714` `disarm(runId, gateWaitIds)` is in the `finally` of the whole loop and the key is still in `armedKeys`, so the latch is removed on both the park throw and the handoff return. Verified this is not a new `hasActiveLatch` leak.
3. **Prefetched `tool_start` ↔ request frames ↔ resume settlement.** One emission point (`emitToolStartOnce` with a per-invocation `toolStarted` set) plus an archive-based idempotent backfill gives exactly one `start` per card on all three paths: first round (prefetch when park is on, loop when off), decision-side backfill for frontend cards (emitted under the same `submitLock`, *before* `frontend_tool_result`, so the frame cannot land after the result even if the decision wins the park race), and resume-side backfill for approved/backend cards (before `executeOnce`). Frame order `suspended → tool_start → request` is asserted, and the crash-between-backfill-and-result test proves no duplicate on retry.
4. **Per-subscriber `wakeFloor` ↔ replay / local fan-out / wake.** All three writers run under `emitLock`; the cursor is advanced only after a successful enqueue; the wake read lower bound is the min over live subscribers (fixes the F3 "another subscriber's replay starves me" case); the emitter-level `lastFanoutSeq` is now diagnostics only and is documented as such. Sync-bus self-wake remains single-delivery (the reentrant `onWake` delivers, then the local fan-out skips on the cursor) and the red-line test still pins it.
5. **Job convergence ↔ late `startItem` ↔ cancel ownership.** Job-terminal and item-terminal now commit in the same `REQUIRES_NEW` transaction (FAILED via `finish`, CANCELLED via `cancel`), COMPLETED is deliberately not converged, and cancel keeps the "item CANCELLED is written by the canceller" rule. `startItem` takes `SELECT … FOR UPDATE` on the parent row, which is the *same* lock the conditional terminal UPDATE takes, and the lock order (jobs → job_items) is identical in `startItem`, `finish` and `cancel` — no deadlock, and the two possible orders both leave zero open items. The pre-existing `markItemFinal`/`compensateItemFailure` insert branches already use the same parent-row lock, so the hole is closed at every insert site.
6. **Flyway lock ↔ DataSource wiring.** The lock wraps the whole `migrate()` (necessary: Flyway 11 creates the history table before `BEFORE_MIGRATE`); PG pins the lock connection via a `ThreadLocal` `PinnedDataSource`/non-closing proxy so `pg_advisory_lock` and the migration share one physical connection, unlock-false/SQLException aborts the physical connection and fails startup; H2 uses a separate pooled connection with `SET LOCK_TIMEOUT` + `FOR UPDATE` + holder-token re-verification, in a dedicated schema so Flyway still sees PUBLIC empty and migrates V1–V9. Hikari pool 10 in all multi-instance profiles ⇒ the second connection needed by the H2 path cannot self-deadlock.
7. **Drain gate ↔ graceful shutdown.** The gate listens to `ContextClosedEvent` and waits on the event thread; `AbstractApplicationContext.doClose` publishes the event *before* `lifecycleProcessor.onClose()` (which is where Tomcat's connector is paused), so the sleep really does delay connector stop. `ReadinessService.drainingSince` is a single volatile source of truth and terminal, and `check()` still short-circuits probes while draining (so the AI capability block cannot block a 503).
8. **Readiness ↔ AI.** The ledger ruling "Redis DOWN must not block whole-site ready" is intact: Redis remains `required=false` + `capability=ai`; draining is the only new reason for 503.
9. **File download ↔ per-file endpoint.** The new single-code branch reads the same `storage_path` with the same EXPORT→UPLOAD preference and the same xlsx header as `GET /files/{defCode}`, so the two download surfaces are now byte- and type-consistent; multi-code still zips one entry per requested code (previously a code present as both EXPORT and UPLOAD produced two same-named entries).
