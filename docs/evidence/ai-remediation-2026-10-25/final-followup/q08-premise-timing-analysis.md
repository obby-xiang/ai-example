## 1. 现象原文

- attempt 2 唯一失败行：`[FAIL] AIE2E-Q-08 [P1] 点即发与 409 的交互：历史条数不变（无幻影气泡） => 并发点发 HTTP 200，期望 409`。
- attempt 2 汇总：`结果：PASS=165 FAIL=1`（批① `129/130`）。
- attempt 1 同一用例通过，汇总 `结果：PASS=166 FAIL=0`。
- 结论方向：**同一提交、同一用例、同一断言，两次结果不同** ⇒ 先按「测试前提或时序竞态」查，不按「产品回归」直接定。

## 2. 断言做了什么（测试侧）

`scripts/verify-e2e.ps1:3993-4008`，用例体：

| 行 | 动作 |
|---|---|
| `:3993` | `Add-AiCase 'Q-08' 'P1' '点即发与 409 的交互：历史条数不变（无幻影气泡）'` |

## 3. 产品侧为什么给 200（两条落点）

### 3.1 409 的唯一来源 = 会话门被占

`backend/src/main/java/com/example/configmgr/ai/web/AiController.java`：

- `:412` `SessionGate.Busy busy = this.sessionGate.acquire(sessionId, runId);`
- `:416-423` 死轮放行分支（`isDeadRound` → `releaseDeadHeld` → 重新 `acquire`）
- `:425` 起 `if (busy != null)` ⇒ 组装 409 体；`:443-444` `deny(HttpStatus.CONFLICT, ErrorCodes.SESSION_BUSY, …)` + `return json(HttpStatus.CONFLICT, body)`。

即：**只有 `sessionGate.acquire` 返回非 null（门被别的轮占着）才会 409**；门空着就一定走正常受理（200 + SSE）。

### 3.2 挂起（park）后驱动线程退出并释放会话门

同文件 `:480-484`：

```java
finally {
    LocaleContextHolder.resetLocaleContext();
    this.sessionGate.release(sessionId, runId);
    this.runRegistry.close(runId);
}
```

`SessionGate` 类注释（`backend/src/main/java/com/example/configmgr/ai/session/SessionGate.java`，类头「锁归属 = 每次 acquire 的 token（I2）」段）把这件事写成了**设计意图**：`park 后由 ResumeService 用同一个 runId 重新取门`。也就是说，**挂起期间会话门并不被持有**，续跑时才重新取门（并按 token 精确匹配，避免首轮迟到的 `finally` 删掉续跑方的锁）。

⇒ 现行语义：**「挂起」≠「占会话门」**。Q-08 的 409 前提（「已挂起 ⇒ 同会话第二轮必被拒」）与现行语义相反。

### 3.3 竞态窗口在哪

`confirm_request` 帧由挂起路径发出，而 `sessionGate.release` 在 **`finally`** 里、线程退出时才执行。因此「发完挂起帧」与「门已释放」之间有窗口：

- 第二次请求落在 **`finally` 之前** ⇒ 门仍被第一轮持有 ⇒ **409**（attempt 1 的形态）；
- 第二次请求落在 **`finally` 之后** ⇒ 门已空 ⇒ **200**（attempt 2 的形态）。

`Read-Sse` 一旦收到 `confirm_request` 就返回并发第二条请求，**没有任何同步点等待 `finally` 完成** ⇒ 两次尝试落在窗口两侧，完全解释「同码不同果」。这是**时序竞态 + 过时前提**，不是稳定性好的产品缺陷证据。

## 4. 与同套件其它用例的口径对照（关键旁证）

同一 `scripts/verify-e2e.ps1` 里，「挂起态是否可以再发一轮」在别处是**按「可以」断言的**：

- attempt 1 日志：`[PASS] AIE2E-W-34 [P1] 挂起中停止不遮挡新轮：同会话下一轮可再挂起且 runs/current 指向新轮`
- attempt 1 日志：`[PASS] AIE2E-W-30 [P1] 前端工具挂起中停止：迟到回灌 409 + 同会话可发下一轮（不锁死）`

即「同会话可发下一轮」是套件里已被钉住的**预期行为**（针对停止路径），与 `SessionGate` 的 token/续跑设计一致。Q-08 要求「挂起中同会话必 409」是**另一套（更早的）语义**，且用例名与注释（`:3993`「点即发与 409 的交互」、`:4000`「409 前提不成立」）就是按旧语义写的。

> 限定：W-30 / W-34 覆盖的是「挂起**中停止**」路径，与 Q-08 的「挂起**中直接再发**」不完全同形；此对照只说明「现行语义并不要求挂起期间必须 409」，不构成产品一定正确的证明。

## 5. 两种处置方向（**均待用户裁决，本件不选**）

### 方向 A：按现行 park 语义改测试（只动 `scripts/verify-e2e.ps1`）

- 改法轮廓：把「第二次请求必须 409」换成「挂起期间允许同会话新轮，但**不得产生幻影气泡 / 历史不得被未开始的轮次污染 / 前端不得出现假提示**」；若确实要保留 409 面，则改为**可控时序**（在门确定被持有期间发请求，例如续跑派发窗口内），而不是「收到挂起帧就立刻发」。
- 代价：一处测试改动，产品零改动；风险是**弱化**了对「并发点发」的守卫 —— 必须把「历史条数不变」这条真正的防幻影断言保留并加强（当前它排在 409 之后，实际从未被执行到）。
- 前提判断（需裁决）：确认「挂起中允许同会话开新轮」是**有意的产品行为**，而不是没人想过的副作用。

### 方向 B：认定「挂起应继续占会话门」是产品缺陷（改 `AiController` / `SessionGate`）

- 改法轮廓：跨 park 持有会话门（不在 `:480-484` 的 `finally` 释放，改由续跑方/终态方释放），并处理与「死轮放行」「租约续期」「跨实例」的交叉。
- 代价明显更大：①与 `SessionGate` 现有 token 设计（park 后重新取门、迟到释放 no-op）直接冲突，需重写取门/释放路径；②与 W-30 / W-34 的「同会话可发下一轮」断言冲突，会连带改掉多条已绿用例；③挂起无上限（去超时口径）⇒ 门可能被长期占用，刷新/重挂/跨实例恢复路径都要重新证明；④影响面覆盖 `ResumeService` / `ConfirmGate` / `runRegistry`。
- 前提判断（需裁决）：确认「挂起期间另一个问题必须被拒绝」是**产品要求**，而不是测试的过时假设。

**两种方向都不能靠「放宽断言/加重试」收口**；也不能在未裁决前由本批替用户选路，或顺手改一处让 CI 变绿。
