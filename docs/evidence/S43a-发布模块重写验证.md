### 2.1 事务模型（本次重写的关键结构变化）

```
PublishJobRunner.run(job)            // 非 @Transactional：事务外编排
├─ job=RUNNING（独立事务）
├─ transactionTemplate.executeWithoutResult(status -> doPublish(job))   // 单事务：upsert+差集删除+状态推进
└─ catch RuntimeException → recordFailure(...)   // 回滚后独立事务补记：job FAILED + issue + item/task 状态
```

- **软冲突不是异常**：baseVersion 不一致 → 行级 issue、跳过该行、其余行照常提交（与 baseline B2.18"逐行语义"一致，作业终态 FAILED）。
- **硬错误是异常**：任一行解析/写入异常 → `PublishAbort` 冒泡 → 整个发布回滚；随后在新事务里写 FAILED 与 issue（否则"失败"这一事实会随事务消失）。

## 4. 与 glm 删建语义的差异与数值口径说明

① **`__id` 保留（Q14 有意差异）**：glm `ConfigDataService.publishStaged` = 逐范围 `delete` PUBLISHED + 提升 STAGED；本实现 = 逐行 upsert（同业务键行保留 id）+ 范围内差集删除。C2 实测：`HB|100` 由 id=1309 原地更新（版本 1→3），不做删建；glm 同场景会得到新 id（其 V2 证据 R1 旧 id 201/206/211 → 新 id 359/360）。业务语义等价，差异仅在行身份延续性与快照可延续性上，且这正是并发冲突检测能生效的前提。

② **版本递增幅度**：combined 机制是 `@Version` + `OPTIMISTIC_FORCE_INCREMENT` 双计 —— 内容有变化 +2（基线 B2.19 的 1→3、C3/C5 实测 1→3），内容零变化 +1（V5 证据的 1→2）。经导入链路的数据一律是字符串（Excel 往返），故"看起来零变化"的行其 `dataJson` 文本也已变化，实测普遍为 +2。C5 任务书写的"version+1"按此口径为**不精确表述**，记为【待裁决-3】。

③ **范围差集删除的执行条件**：本实现把它挂在导入模式上（MERGE 默认不删、REPLACE 删除范围内未覆盖行），依据见【待裁决-2】。glm 无模式开关、恒为范围内替换。

## 5. 遗留【待裁决】

1. **发布前终检（FR-3.5）在基座发布路径中不存在**：通读重写前的 `PublishJobRunner`（与 combined 分支逐字相同，重写前 `diff` 为空）确认发布前**没有**任何独立的终检/校验门禁；发布阶段唯一的检查是逐行 `baseVersion` 快照比对。规格 §1 表格"发布前终检｜保留基座既有终检"按现状是"无可保留"。若要求和 FR-3.5 一致（发布前重跑引用完整性等），需另立子任务实现，**本棒未擅自新增**。
2. **差集删除是否应无条件执行（与 C1 数值互斥）**：规格 §1 把"范围差集删除"列为发布语义，而 C1 要求重放 B2 的行数变化与基线一致（CURRENCY 5→7）。本实现在 **MERGE 模式不执行删除、REPLACE 模式执行**：若改为无条件删除，B2 场景（默认 MERGE）三个 GLOBAL 配置项都会删掉"未出现在导入数据中的旧行"，算术结果与基线全面不符 —— CURRENCY 5−3+2=**4**（基线 7）、APPROVE_ROLE 4−3+1=**2**（基线 5）、DOC_TYPE 5−4+1=**2**（基线 6）；PROJ_APPROVE 因覆盖范围（HE-P001 / NO_SUCH_PROJ）内本就 0 行而不变（3=3）。实测证据：C1 运行后 EUR/GBP/JPY 三行仍是 v1 且 `updatedAt` 仍为种子时刻（§3-C1 的 DB 查询），即基线口径下它们必须存活。因此两条要求**不可能同时成立**；本棒选择满足显式数值验收的 C1（MERGE 纯 upsert；"范围内替换"由 REPLACE 模式承载，V2/C2、C5 均用 REPLACE 复现）。请裁决：采纳本口径，或改判 C1 的对照目标。
3. **C5 的"version+1"口径**：实测 upsert 已存在行为 1→3（内容变化）而非 +1（见 §4-②）。若要求严格的 +1，需去掉 `OPTIMISTIC_FORCE_INCREMENT`（会破坏 V5 已实测的"内容零变化也递增"资产，并使快照比对失效）—— 不建议，请裁决是否维持 combined 原机制。
4. **C6 的"约束冲突"注入方式**：单线程重放下发布期 DB 约束冲突**不可达**（重复业务键先被 `baseVersion` 守卫拦下；同列宽约束使超长值在导入阶段即被拦下；唯一约束只在"并发插入同一新业务键"时才可能触发，线程时序不可复现）。故 C6 用"暂存数据损坏（非法 JSON）"作为确定性硬错误注入，注入手段是直连 H2 文件库 SQL（已记录原文）。若要求必须复现 DB 约束冲突，可采用"两任务并发导入同一新业务键后同时发布"的时序型实验（结果依赖提交先后，无确定性）。
5. **差集删除候选行的并发保护（本次新增语义）**：C4-2 证明，不做保护时 REPLACE 的差集删除会**静默删除**并发写入的行（该行不在本任务导入数据中，行级快照比对覆盖不到）。本实现在 `deleteRowsOutOfRange` 中加了保护：删除候选行若 `updated_at ≥ 本次导入时刻`（暂存行 `created_at` 最小值）则不删除，转而落 issue（新文案"…快照版本 无，当前版本 m），本次范围内替换未删除该行…"）。副作用：**同一任务重复发布**时，上次发布触及的行会被判为"导入后被修改"而免于删除（与 B4.8"重复发布必然冲突"的既有行为同向）。请裁决是否保留该保护与文案。
6. **任务删除不清理暂存行**：C6 等场景的任务被删除后，`config_staging_rows` 中对应行仍留存（`TaskService.delete` 只删 task_items/task_files/task），实测清理任务后库内仍为 `PUBLISHED 23 / FAILED 3 / STAGED 2`。属基座既有行为，本棒未改，供合流决策。
