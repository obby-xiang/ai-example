### 1.4 旧 AI 层处置说明（规格书第 9 条）

**处置方式：整体删除**（未新建 `ai/legacy/` 包）。判定依据与影响：

1. **为什么删而不是留 legacy**：规格 §1 目标是"把手工协议 AI 层**整包替换**为官方循环运行时"，§2 给出的目标包树没有 legacy 位置；基座旧层的语义锚点（进程内 Caffeine 会话、进程内 HITL future、ThreadLocal 发射器）在规格 §2 中都有**不同实现的新落点**（`session/AiSessionService` 走 Redis、`gate/ConfirmGate` 走 Redis 决策、`run/RunStore` 走外置挂起态），保留旧实现只会成为"看似可复用的死代码"。后续棒次的移植来源是规格点名的 spike（sp01ab/sp01c/sp01d/sp02）与 deepseek 分支，不是基座旧类。旧实现完整保留在 git 历史（`git show HEAD:<path>` 可取）。
2. **依赖切断情况**：业务服务层、种子、发布模块**零依赖** AI 包（`grep` 验证后删除，编译通过即证）。唯一被 AI 层反向依赖的是 `TaskService/DefinitionService/JobService/ConfigDataService`——由新 `AiTools` 继续按同一服务层调用（FR-5.4/D2 单一事实源）。
3. **保留的部分**：`ai/tool/{ToolMeta,ToolScope,ToolRisk,ToolRegistry}` 保留为**当前**设施（渐进披露标签与工具注册表不是"手工协议"，规格 §2 的 `tools/ToolScopeFilter` 是其演进形态，属后续棒次）。
4. **对前端的破坏（交接 S4.4，非本棒范围）**：基座前端 `frontend/src/api/ai.js`、`frontend/src/stores/ai.js` 依赖的旧端点已随本棒消失：
   `/ai/sessions`(POST)、`/ai/sessions/{sid}`(GET/DELETE)、`/ai/sessions/{sid}/context`(PUT)、
   `/ai/sessions/{sid}/runs`(POST SSE)、`/ai/sessions/{sid}/interactions/{iid}`(POST)、`/ai/health`(GET)。
   新契约 = `POST /api/ai/chat`（SSE：`start`→`delta`*→`done`/`error`）+ `GET /api/ai/history/{sessionId}`；
   会话 id 由前端生成并随请求携带（不再有"建会话"接口）。**这是规格 §2 端点重设计的必然结果，需 S4.4 适配前端。**

## 2. 本棒落成的集成形态（规格 §3 时序的子集）

```
POST /api/ai/chat
  └─ AiController：AiAvailability 判空（无 key → 503，开流之前返回）
       └─ 专用有界平台线程池（DC-12，饱和 → 503 AI_BUSY）
            └─ AiChatService：发 start 帧
                 └─ ChatClient(prompt).system(人设).system(工作区上下文).user(msg)
                      .advisors(param(ChatMemory.CONVERSATION_ID=sessionId))
                      .toolCallbacks(ToolRegistry.forContext(ctx) 披露子集)
                      .stream()  ← 官方循环（工具执行在 OpenAiChatModel 内部）
                 └─ delta* → done/error 终帧
       └─ 记忆：官方 MessageChatMemoryAdvisor → 官方 MessageWindowChatMemory(窗口 40)
                → 官方 ChatMemoryRepository SPI → RedisChatMemoryRepository（LIST + 滑动 TTL 6h）
```

未落成、留给后续棒次（本棒明确不碰）：`gate/*`（确认门）、`run/{RunStore,ResumeService,CancellationRegistry}`、
`session/SessionGate`、`tools/ToolScopeFilter`、`/confirm`、`/frontend-tool-result`、`/events/{runId}`、
断流重试三条件与双超时（ADR-6）。

## 4. 遇到的问题与解法

### 4.1 Q2 空 key 启动失败（规格 §4 明确要求修复）

- **现象**：不带 key 时后端启动中断，`OpenAiApi` 创建失败：`OpenAI API key must be set`（`Assert.hasText`）。
  根因：`spring-ai-autoconfigure-model-openai` 的**六个**自动配置类都是
  `matchIfMissing=true`，任一先把 `OpenAiApi` bean 建出来即断言失败；`spring.ai.chat.client.enabled` 默认 true 时
  `ChatClientAutoConfiguration.chatClientBuilder(ChatModel)` 还要求 `ChatModel` bean 存在。
- **解法**（全部走官方开关 + 条件装配，未改基座 Application 类）：
  1. `spring.ai.model.{chat,embedding,image,moderation,audio.speech,audio.transcription}=none` 关掉六类模型自动配置；
  2. `spring.ai.chat.client.enabled=false`，`ChatClient.Builder`/`ChatClient` 由 `AiModelConfig` 组装；
  3. `AiKeyPresentCondition`（按 `spring.ai.openai.api-key` 是否非空白）把 `OpenAiApi`/`ChatModel`/`ChatClient`/
     `AiChatService` 全部条件化；`AiAvailability` 恒在，端点据此 503。
- **验证**：§3.4 反证 + 修复后启动、业务 API 200、AI 503。

### 4.2 错误响应被 SSE 转换器吃掉（实测 500，已修）

`@PostMapping(produces = {text/event-stream, application/json})` 下，`Accept: */*` 时 Spring 选中
`text/event-stream` 作为响应类型，返回 `Map`/`ApiResponse` 体时抛
`No converter for [class java.util.ImmutableCollections$MapN] with preset Content-Type 'null'` → HTTP 500（而非 503）。
解法：错误分支统一走 `json(status, body)`，显式 `contentType(APPLICATION_JSON)`（见 `AiController`）。

### 4.3 反证实验的代码往返（确保交付物未被实验污染）

实验前 `cp AiModelConfig.java /tmp/s42p1/AiModelConfig.java.bak`；实验后 `cp` 还原并
`diff` 校验（输出 `diff: identical`），再重新 `mvn -DskipTests package` 并用**还原后的 jar** 重跑 V4/V5。
最终交付物 = 还原后的构建，`git status` 中不存在实验残留。

### 4.4 三条集成发现（四机制从未共存 ⇒ 本棒先撞上的边界）

1. **工具配对不进记忆窗口**：官方 `MessageChatMemoryAdvisor` 在流式路径上用 `ChatClientMessageAggregator`
   聚合整条流后再 `ChatMemory.add(...)`，而官方内部工具循环在 `returnDirect=false` 时**不把中间工具响应放进客户端流**
   （`OpenAiChatModel.internalStream`：仅递归新请求，不 emit 工具轮响应）。实测结果：Redis 中每轮只存
   `USER + ASSISTANT(最终文本)`，`toolCalls/toolResponses` **从不落记忆**（V2/V3 会话逐条核对）。代码级 SPI 往返能力仍在
   （`MessageJsonCodec` 支持两者，SP-01c 已验），只是官方 advisor 的写入内容里没有它们。
   ⇒ 对 SM-01/Q13 的影响：规格 §3 步骤 7 设想的"记忆窗口 saveAll 覆盖写 + 以完整历史一次性 saveAll 刷新记忆"
   **本路径无法提供含工具轮的完整历史**；工具配对的完整性只能来自 M3 的 RunStore 快照（与规格的"以 RunStore 为准"一致，
   但"续跑后以完整历史一次性 saveAll 刷新记忆"这一句需要后续棒次自行拼装消息再写入，不能依赖 advisor）。
2. **reasoning 回填值为空串**：见 §3.6——补丁在场只保证字段存在（`""`），非空思维链未被回填。
3. **客户端流看不到工具调用**：V3 五轮共 10 次上游请求，客户端 `tool_call` 事件数 = 0。故本棒删除了原先设计的
   `tool_call` 帧（避免死代码）；工具可见性/前端工具卡片必须由第二棒 `gate/SpToolCallingManager` 的钩子提供
   （与规格 §2 的"可见性钩子"分工一致）。
