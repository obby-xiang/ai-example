## 1 一句话结论

B1「挂起即断」把请求帧改成**逐条发**（`ConfirmGate.await` 发自己那张卡再断流），而 `saveSuspended` 仍把**整批**待决条目一起外置 —— 于是「条目存在」不再等于「卡已送达」。本批给待决条目加「请求帧已发」位（`req`），把刷新恢复的建卡口径收窄为 **`PENDING` + `kind∈{CONFIRM,FRONTEND}` + `req===true`**，并让后端在发帧前先看「是否已决」，已决则跳过发帧与断连、直接消费既有决策。实时路径零改动。**收口修（2026-10-21）**：无卡也要挂流（I-1）、置位后复判已决（M-1），并修正窗口/自愈的申报口径（§9）。

### B. pending 条目透出真实 kind 三值，前端按真值过滤

- 后端：`kind` 原本就是三值原文（无改动），本批加用例锁死（见 §5）。
- 前端：`frontend/src/stores/ai.ts` `restoreSuspendedSnapshot` 建卡循环 :1311-1317 —— `if (entry.kind !== 'CONFIRM' && entry.kind !== 'FRONTEND') continue`（类型随之收窄，`kind2` 不再靠三元兜底）。

### C. 发帧前先读 `resolved()`：已决则跳过请求帧与 `completeSubscriptions`

- `ConfirmGate.reserveRequestSlot` :444-461（javadoc :409-443，M-1 段在 :437-443）：`synchronized (this.submitLock)` 内 `store.pending(...)`；`fresh.resolved()` ⇒ 归还预登记闸门（`consumeDecided` :467-477，与 `await` 的 `finally` 同序）→ 返回该条目；未决则置位后再判一次（M-1）。
- `await` :313-316：返回非 null 即**不发帧、不 `completeSubscriptions`、不进心跳等待**，直接 `return fresh`；调用方（`SpToolCallingManager#awaitConfirm` / `awaitFrontend`）按既有语义消费：`APPROVED` → `executeOnce`（认领 + 台账 + `tool_result`）、`REJECTED` → 未执行回填、`FRONTEND_RESULT` → 用既有 `resultText`。
- 为什么在同一把锁：`submitDecision` / `submitFrontendResult` 的「落库 → 发回执帧 → 唤醒」也在 `submitLock` 内，因此这里读到的「已决」一定伴随着已经写出去的回执帧（S5c-6 口径不破）。

### D. 前端恢复：只为 `req=true` 的 CONFIRM/FRONTEND 建卡；`suspended` 不变

- `frontend/src/stores/ai.ts` :1297-1320：`pendingEntries = current.pendingEntries.filter(PENDING)`；`pendingEntries.length > 0` ⇒ `suspended = true` + `activeRunId = current.runId`（**与 req / kind 无关**，输入禁用语义不变）；建卡循环内三条 `continue`（kind 三值 → `req !== true` → 已决残留）。
- GF 武装同条件：GF 分支在过滤之后，`req=false` 的 GF 条目既不建段也不武装 `activeForm`（所以也提交不了）。
- 未发卡条目不渲染、不新增占位 UI：无段、无空卡、无"待执行"占位。**但无卡 ≠ 无后续帧**（I-1 收口修，见 §9）：挂起态下即使一张卡都重建不出来，也照常以 `archiveMaxSeq` 挂差量续收，宿主消息由首个到达的帧惰性取用（有则续写、无则创建，空转期不留空气泡）。
- 旧载荷（缺 `req` 键）按 `false` 处理：**宁可少一张卡，不可让用户点到未生效的卡**。适用范围与"旧挂起轮永无卡"的边界见 §7-5 与挂账 M-2b。
- 类型：`frontend/src/types/ai.ts` `AiRunCurrentEntry` :531-541 新增 `req?` / `reqAtMs?` 与口径注释。

## 7 偏差与取舍留痕

1. **`req` 用 `Boolean` 而非 `boolean`**：`null` = 本口径引入前的旧数据 / 从未发射，与"明确未发"分开；`/runs/current` 出口统一成 `false`（前端不区分两者，一律不建卡）。
2. **「有 PENDING 但一张 `req=true` 都没有」的窗口（I-1 之前为死胡同，收口修已挂流）**：刷新落在「卡 1 已决 → 后端正在执行卡 1 的工具 → 才轮到卡 2 发请求帧」这段里时，`suspended=true`（输入禁用）且一张卡都重建不出来。**窗口上界 = 前一张卡的工具执行时长**（导出/导入类可达数秒～数分钟，期间快照仍是 SUSPENDED、`unresolvedExternal` 仍非空），不是"毫秒级"。施工版此处**无自动自愈**：无卡 ⇒ 不建续收连接 ⇒ 卡 2 的请求帧只入归档，用户只能点「停止」或**再手动刷新一次**。**收口修（I-1）已改**：挂起态下即使零卡也照常以 `archiveMaxSeq` 挂差量续收，请求帧到达即按实时路径建卡（见 §9）。
3. **已决早退分支顺带归还预登记闸门**：裁决 C 未点名，但若不归还，`hasActiveLatch` 会在整批结算前恒真、挡住本进程死卡兜底（F8 同族缺陷），故按 `await` `finally` 同序（先摘闸门、后摘标记）一并处理。
4. **`PendingToolCall.asMap()` 也加 `req`/`reqAtMs`**：裁决只要求 `/runs/current` 透出，但 `/pending/{runId}` 是同一份条目快照的诊断面，同名字段避免两套口径；纯增量、无消费方受影响。
5. **旧载荷缺 `req` 一律不建卡**（严格口径）：这是"宁可少一张卡"的取舍，不引入"缺键即视为已发"的回退（那会把本批修掉的洞在新旧混跑期重新打开）。**适用范围要如实分开**：①**本轮仍在跑**的条目 —— 服务端走到它的 `await` 时会置位 `req`，刷新（含 I-1 挂流后到达的请求帧）即可恢复；②**升级穿越期的旧挂起轮**（升级前挂起、重启后无人等待）—— 没有进程会再走到它的 `await`，`req` **永为 `null`**，**任何次数刷新都不会建卡**，直到会话 TTL 到期或用户取消 ⇒ 见挂账 M-2b（`docs/任务看板.md`）。
6. **E2E 未加 `req` 断言**：本可加一行（TC23 拿到的条目必然是 `req=true`），但卡面明确「预期零改动」且本批不运行 E2E，加未验证断言有浪费主会话一整轮 CI 的风险 ⇒ 不改。**建议主会话下批顺手补**：TC23 在 `$entry23.kind` 断言后加 `if ($entry23.req -ne $true) { throw ... }`。
7. **本批未测的边界**（如实申报）：①多实例并发仍只靠进程内 `submitLock` 串行化 —— `markRequestEmitted` 是「读 → 判 → 写」**非原子**（无 Redis CAS / Lua）：**该守卫只覆盖"读时已决"**，**不覆盖"读后写前被另一实例决策"**，此时整对象 `HSET` 会把已决条目回写成 PENDING = **丢失决策**；单实例（DC-11）不可达，多实例属 B3 面，见挂账 M-2（收口修已在 `ConfirmGate` 内补"写后复判"，但那只缩小本实例的**发帧**误判，不解决跨实例 lost update）；②浏览器级真实刷新未跑（E2E 归主会话），本批的恢复口径证据全在单测层。
8. **`frontend/src/utils/parts.ts` 只动注释**：`toPendingCallProjection` 的「非 FRONTEND 按 CONFIRM」是**派生层**的展示映射（段 kind2 已是三值、且只有 CONFIRM/FRONTEND 能建段），不动逻辑；只把"与旧 restore 判定同口径"这句已过期的注释改成现行口径，避免下一位读者以为恢复路径仍二值化。
9. **`suspended` 前置置位的副产品（N-3）**：置位点从"循环内、建成卡之后"移到"循环外、存在任意 PENDING"，于是**全部条目都已是本地已决残留**的快照也会置位 `suspended`（旧行为不禁用输入）。裁决 D 字面即如此（"存在任意 PENDING"），代价是这类边缘现场多禁用一次输入，下一帧结局到达即由既有清理路径复位；不改。
