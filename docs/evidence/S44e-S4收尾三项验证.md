## 2 V2 ②：`create_task` 从零建任务 → 全链路零人工预置导出（真实模型 + 真实浏览器）

### 2.1 实现说明（裁决②）

- **工具**：`create_task(type: EXPORT|IMPORT, title?)`，BACKEND 通道，`WRITE` 风险；
- **落库机制与任务中心同源**：工具体直接调 `TaskService.create(TaskType, title)` —— 与 `POST /api/tasks`（`TaskController#create`）**同一条路径**（含 `currentStep` 初值 `SELECT_DEFS`/`UPLOAD`、标题缺省规则、任务变更事件），因此"AI 建的任务"与"手点建的任务"在库里没有差别；
- **返回 id + 下一步**：返回值形如 `已创建导出任务 #161（标题：…，当前步骤：SELECT_DEFS）。下一步：navigate_to(page="export", taskId=161) 打开向导，再用 select_definitions 勾选配置项。`（实测模型据此一次接上导航）；
- **披露范围**：`{"page:tasks", "task:EXPORT", "task:IMPORT"}` —— 任务中心（"没有任务时建任务"的现场）与两类向导页都披露；`definitions`/`data`/空上下文**不披露**（见 §5）；
- **不进确认门**：创建任务可逆（任务中心/REST 既有删除机制），不直接改业务数据；FR-5.3 的确认清单不含"创建任务"。

### 2.2 预置

- 库为 15 定义种子态（`GET /api/definitions` → 15）；**零人工预置任务**（无手工建任务、无 API 预置）。

## 3 V3 ③：`set_condition` 参数形态对齐前端契约（表单真实填充 + 落库一致）

### 3.1 实现说明（裁决③）

- 前端**只读两个键**：`frontend/src/utils/frontend-tools.ts#normalizeActionArgs` 的
  `case 'set_condition': return { defCode: args.defCode ?? '', conditions: args.conditions ?? {} }`
  → 扁平四参（`defCode/fieldCode/operator/value`）里的后三个会被**静默丢弃**，产生"调用成功、条件为空"的错误；
- 前端认得的形态是 `frontend/src/types/condition.ts#FieldQueryCondition`：
  `{ scopeKeys?: string[], fields?: [{ fieldCode, operator, value? }] }`（也是后端 `data/service/QueryCondition` 的形态）；
- 本棒把入参从 `Map<String,Object>` 收紧为**逐字段镜像前端契约的类型化 record**（`AiTools.FieldQueryCondition` / `FieldCondition`，字段名一字不改）。收益有两层：
  1. **Schema 长出内层结构**（`Map` 只能生成"无内层结构的 object"）：改造前 Schema（本棒开工前用临时探针实测，**原文未归档**）
     `"conditions": {"type":"object","description":"查询条件对象，形如 {\"fields\":[…]}"}`（内层靠描述文字猜）；
     改造后 `conditions.properties = {scopeKeys[], fields[].{fieldCode,operator,value}}`，
     `required=[fieldCode,operator]`、`value` 可选（EMPTY/NOT_EMPTY 不带值），并由单测逐项断言（§3.3）；
  2. 前端收到的仍是模型原始实参（`frontend_tool_request.args` 逐字节透传），后端只改"披露与 Schema"，**不改下发通道**（前端零改动）。

### 3.2 实测（真实模型，导出向导 QUERY_COND，任务 #162 由 AI 自建）

模型实参（`frontend_tool_request` 原文，`<EV>/raw/seq-v3.txt`）：

```json
{"defCode": "CURRENCY", "conditions": {"fields": [{"fieldCode": "code", "operator": "EQ", "value": "CNY"}]}}
```

前端回灌：`已设置 CURRENCY 的查询条件：code 等于 CNY`
（该文案来自页面 handler `export.setConditions`，即**条件已写进表单模型**；若是 ui_event 直连路径则文案无摘要 —— 二者可据此区分）。

**表单真实填充**（DOM 探针原文 `<EV>/raw/v3-condition-form-dom.json`）：

```json
{"cardTexts":["货币代码（code）\n等于\n添加条件\n不设置条件表示导出全部数据"],
 "inputValues":[...,"CNY"], "selectTexts":["货币代码（code）","等于","CNY"]}
```

截图 `<SHOTS>/04-v3-condition-form.png`：查询配置步骤的卡片显示 `货币代码（code） │ 等于 │ CNY`。

**落库一致性**：

| 时点 | `GET /api/tasks/162` 的 `items[0].conditionJson` |
|---|---|
| `set_condition` 刚回灌完 | `"{}"`（表单已填，但尚未落库 —— 见【待裁决】1） |
| `confirm_step` 推进步骤后（前端 `persistStepData`） | `{"fields":[{"fieldCode":"code","operator":"EQ","value":"CNY"}]}` |

与 AI 传入的条件**语义一致**（前端经"草案模型"往返：`draftModelFromCondition` → `buildQueryCondition`，`scopeKeys` 未给故不出现）。
语义有效性核验：`GET /api/data/CURRENCY/count` 无条件 = **5 行**；带该条件（URL 编码 conditions）= **1 行**。

### 3.3 Schema 回归锁（单测）

`ToolRegistryDisclosureTest#setConditionSchemaMirrorsFrontendContract`：解析 `inputSchema()` 断言
顶层仅 `defCode/conditions`、`conditions.properties = {scopeKeys, fields}`、`fields[].properties = {fieldCode, operator, value}`、
`fields[].required = [fieldCode, operator]`；并以契约实参调用工具回调，断言入参可绑定且仍只返回哨兵（`FRONTEND_STUB`）。

**结论（③）**：模型按前端契约传参时，前端正确接收并**真实填充条件表单**；`conditionJson` 落库与 AI 所给条件一致（落库发生在向导推进步骤时，见【待裁决】1）。

## 4 V4 ⑥：`start_export` / `start_precheck` / `start_import` 纳入确认门（三结局）

`claimExecution` **未被调用**、回填文本逐字进 `role:tool` 消息。`start_import` 的运行时三结局未单独跑（披露范围限定在

**结论（⑥）**：三工具（+既有 `start_publish`）在同一 `ConfirmGate` 下三结局行为一致：**放行 → 执行（作业完成）**、**拒绝 → 未执行 + 原因回填**、**超时 → 自动取消 + 未执行**。

## 6 遗留【待裁决】

| # | 项 | 现状与影响 | 建议 |
|---|---|---|---|
| 1 | **`set_condition` 不落库**（本次实测确认） | 页面 handler `export.setConditions` 只写表单模型（`draftModels`），**不调** `tasksApi.setCondition`；`conditionJson` 要等向导推进步骤（`goStep → persistStepData`）才写。V3 原文：设置后立即读 `conditionJson="{}"`，推进后才是条件 JSON。影响：AI 设完条件后若用户/模型不再推进步骤，库里条件仍是空 | 前端在 `setConditions` handler 内直接 `tasksApi.setCondition`（本棒**禁改前端**）；或后端在 `confirm_step` 前置校验"条件已落库"。当前业务上不致命（导出前必然推进步骤），但"设置即落库"更符合直觉 |
| 2 | **导入向导 `confirm_step` 报成功但步骤未推进**（前端缺陷，本次实测） | 无勾选配置项时 `flushEditors()` 返回 false → `goStep` 提前 return，而 handler `import.nextStep` **无条件**返回"已推进到导入向导步骤「预检查」"。AI 据此认为已推进，下一轮读任务仍是 UPLOAD。本棒为把 UI 置于 PRECHECK/IMPORT 上下文，改用 `PUT /api/tasks/163/step` 置位后重开向导（等价用户走到该步） | 前端 handler 应回传真实结果（`goStep` 返回 boolean）；`flushEditors` 的"未勾选即拒绝"应与"下一步"按钮的校验口径统一 |
| 3 | `TaskController#setCondition` 用 `body.get("condition").toString()` 落库 | 前端传字符串时正常；若经 ui_event 直连路径传**对象**，会把 Java `Map.toString()`（非法 JSON）写进 `conditionJson`，后续 `parseConditionJson` 读不出。本棒 AI 路径走表单→字符串，未触发 | 后端改 `objectMapper.writeValueAsString(...)`（属 `task/` 模块，不在本棒授权范围） |
| 4 | `set_condition` 入参类型化后的严格性 | 类型化嵌套 record 让 Schema 精确，但若模型把 `conditions` 传成 **JSON 字符串**，参数绑定会失败（旧 `Map` 形态同样会失败），失败是**可见**的（"工具执行失败"）而非静默空条件 | 本次实测 deepseek-flash 按契约传对象；若后续模型版本出现字符串传参，可加一层 `JsonDeserializer` 容错（先记观察项） |
| 5 | 确认门的"作业已完成"口径 | V2 的 `start_export` 放行后返回即"已启动"，作业完成是异步的（本轮实测 0.6s 跑完，模型靠 `check_job_status` 才看到 COMPLETED）；`start_precheck` 在无文件时也会创建作业（#130 COMPLETED 0/0 行） | 属既有设计（作业异步）；如需"发起后自动回填终态"，需在工具内等待作业终态（涉及超时预算），未做 |
| 6 | `start_import` 的运行时三结局未单独跑 | 披露范围限定 `task:IMPORT/IMPORT`，跑通需真实上传文件 + 预检查通过（本轮不含上传）；同源机制由 `ConfirmGateWiringTest` 锁定 | 若要运行时覆盖，需补一条"上传真实 xlsx → 预检查 → 导入（经确认门）"的端到端 |
| 7 | 挂起期 `heartbeat` 帧不进事件回放 | 活体 SSE 有 61 帧（120s 挂起），`GET /api/ai/events/{runId}` 回放里 0 帧 —— 与 S44d 同一现象。取证心跳必须用浏览器抓包 | 若希望离线回放也能证明"挂起期有帧"，需把 heartbeat 也写进事件存储（注意容量） |
| 8 | 自产任务未有 S44E 前缀 | `create_task` 的标题由**模型自选**（任务单给定的用户原话里没有前缀），本轮三张任务标题为「导出 CURRENCY 配置」「导出 CURRENCY 配置（code=CNY）」「导入配置任务」 | 清理按任务 id（161/162/163）执行并已核对库里 0 任务（见 §6.9）；后续若有"前缀识别"要求，需在提示词里约定命名 |
| 9 | `navigate_to` → 紧随动作的"页面就绪竞态"仍在（S44d 待裁决 4） | 本棒 V3 轮实测 3 次 `unavailable`：报错文案是**步骤不匹配**（"当前步骤为EXPORT，选择配置项只支持：SELECT_DEFS、UPLOAD。请先推进到可用步骤"），根因是 `navigate_to(export,162)` 返回时目标页尚未完成 `onMounted`/任务绑定，`workspace.step` 还是上一任务的 `EXPORT`（新任务 #162 的 `currentStep` 本是 `SELECT_DEFS`）；靠模型自愈（改走 `confirm_step(SELECT_DEFS)` 后 `select_definitions` 成功） | 前端让 `navigate_to`/`restore_task` 等到"路由 + 任务绑定 + 步骤"就绪再回灌结果（本棒禁改前端） |
| 10 | Redis 里的历史 run 快照未清理 | 本棒 14 轮 + 历史共 20+ 轮 `ai:run:*`/`ai:pending:*` 键仍在（只影响 AI 运行时键，不影响业务库；启动续跑扫描会跳过 PENDING） | 由后续棒决定是否加"按 TTL/终态清理"（本轮未动，避免影响既有续跑机制） |
| 11 | 前端注释里的风险等级表已过期 | `frontend/src/types/tools.ts` 顶部注释仍写 `start_export … WRITE`、`start_publish … DANGER`；前端**行为**完全数据驱动（按帧里的 `kind` 渲染），所以只是注释漂移 | 下次改前端时同步注释（本棒禁改前端） |
