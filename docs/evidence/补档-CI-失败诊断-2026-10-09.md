另两次的同条注解：

- job `113785134469`：`create --name dda457712df340fc98dc8619c4b3df0c_redis7_21832a … --maxmemory-policy noeviction … redis:7`（exit 125）
- job `113771058917`：`create --name 375db36d1ef74c9d8979dce3ecbfbd15_redis7_c8e136 … --maxmemory-policy noeviction … redis:7`（exit 125）

**A/B 对照【实测】**：成功 run 的 E2E job（`113753004081`）注解只有 2 条 warning（Node 20 弃用提示、无 artifact 提示）+ 1 条 notice，**没有 failure 注解**；三次失败 run 的另外两条 warning 与它逐字相同。即：同一条流水线、同一类 runner、同一天，**唯一差异就是 `docker create` 命令行里多出的 `--maxmemory-policy noeviction`**。

**runner 侧行为佐证【实测】**（公开源码 `actions/runner`）：
- `src/Runner.Worker/Container/DockerCommandManager.cs` 的 `DockerCreate()` 把 `container.ContainerCreateOptions`（即 workflow 的 `options:` 字符串）原样插入 `docker create` 参数列表，位置在**镜像名之前**，随后 `ExecuteDockerCommandAsync(..., requireExitCodeZero: true)` 执行 —— 非零退出即抛错并置该步骤为 failure。
- 同文件 `ExecuteDockerCommandAsync` 会先 `context.Command($"{DockerPath} {arg}")` 打印完整命令 —— 这正是注解中那行命令的来源，也是日志里可见的那行。

**「exit 125」含义【旁证】**：docker CLI 对**未知 flag / CLI 语法错误**返回 125，且表示「命令在容器内进程启动前就失败」。多个公开来源一致（如 [Komodor 退出码指南](https://komodor.com/learn/exit-codes-in-containers-and-kubernetes-the-complete-guide/)、[erroratlas](https://www.erroratlas.net/errors/docker-run-exit-code-125)、[Bamboo KB：`--password-stdin` unknown flag → exit 125](https://confluence.atlassian.com/bamkb/unable-to-docker-push-with-bamboo-as-the-docker-login-command-fails-with-exit-code-125-due-to-password-stdin-being-an-unknown-flag-1064086477.html)）。`docker create` 不存在 `--maxmemory-policy` 这个 flag（该名字属于 **Redis 服务端配置项**，[docker create 选项表](https://docs.docker.com/engine/reference/commandline/create/#options)中无此项）。

## 8. 根因推断分级

### A. 最可能（采信）
**`services.redis.options` 里放了 redis 服务端参数 `--maxmemory-policy noeviction`，导致 runner 执行 `docker create` 时被 docker CLI 判为未知 flag，exit 125，步骤「Initialize containers」直接失败，后续步骤全部 skipped。**

- 【实测】三次失败 run 的 check-runs failure 注解给出了完整 `docker create` 命令行，其中含 `--maxmemory-policy noeviction`，返回 exit 125。
- 【实测】成功 run（`749fa43`）的同 job 注解无 failure 注解；该 run 的 ci.yml 与该命令的唯一差别就是没有这一项。
- 【实测】该行由 `1113677` 于 10:05:56Z 引入（唯一功能性改动），10:06:01Z push，10:06:11Z 首次失败。
- 【实测】`actions/runner` 源码 `DockerCommandManager.DockerCreate()` 把 `options` 原样拼进 `docker create` 且 `requireExitCodeZero: true`。
- 【实测】`services.<id>.options` 官方定义即 `docker create` 选项；`--maxmemory-policy` 不在 docker 参数表中。
- 【旁证】docker CLI 对 unknown flag 返回 125。
- 残余不确定性（约 5%）：docker CLI 打到 stderr 的**具体文字**未能读取（日志 403）；理论上 exit 125 也可能由 `--health-cmd "redis-cli ping"` 的引号解析等其他 CLI 层原因造成，但该部分在成功 run 中已实证可用。**注：此残余不确定性不影响修复动作的确定性与安全性**（去掉该行即回到已验证成功的状态）。

## 9. 建议处置

> 所有修复均需仓库 owner 提交并推送（本次诊断按约束**未做任何 git 写操作**）。

### 选项 A（推荐·最小改动·立刻恢复）：从 `options` 删除该行

```yaml
        options: >-
          --health-cmd "redis-cli ping"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 12
```

- 利：回到 `749fa43` 已验证成功的配置；改动 1 行、风险最低、无需实测新语法。
- 弊：T3-9 在 **CI 内**的「显式声明 noeviction」口径丢失（注释也要同步改，否则文档与实现不符）。缓解论据：`noeviction` 本就是 Redis 的**默认** `maxmemory-policy`；CI 中未设 `maxmemory`（默认 0=不限制），淘汰策略在 CI 里实际不可能生效，因此该行在 CI 中更接近**声明性**而非功能性。本机 Memurai 的 `CONFIG SET` 口径不受影响。

### 选项 B（保留口径·语义正确）：改用 `services.redis.command`

```yaml
    services:
      redis:
        image: redis:7
        ports: ['6379:6379']
        command: --maxmemory-policy noeviction
        options: >-
          --health-cmd "redis-cli ping"
          --health-interval 5s
          --health-timeout 3s
          --health-retries 12
```

- 原理【实测】：`command` 的值会被 runner 追加在**镜像名之后**，成为 `docker create redis:7 --maxmemory-policy noeviction`；官方 redis 镜像的 `docker-entrypoint.sh` 对以 `-` 开头的首参有兜底 `set -- redis-server "$@"`（`redis/docker-library-redis` 的 entrypoint 源码实测可见），最终等价于 `redis-server --maxmemory-policy noeviction`。
- 利：保留 CI 内显式口径，且放到**语义正确**的位置（redis-server 参数）。
- 弊：依赖「官方 redis 镜像 entrypoint 的 `-` 兜底」这一行为；若哪天换成自建/非官方镜像则该兜底不存在。建议**一次 CI 实跑验证**（可加一步断言 `redis-cli CONFIG GET maxmemory-policy` 期望 `noeviction`），并确认 `services.command` 在当前平台确实可用（官方文档已列该字段，但**本仓尚未用过**，属未实测语法）。

### 选项 C（证据力最强·改动略大）：去掉 `options` 里的非法项 + 运行期断言

在 E2E 的既有步骤序列中（checkout 之后、运行 E2E 之前）增加一步：

```yaml
      - name: 断言 redis noeviction 生效（T3-9）
        run: |
          cid=$(docker ps -q --filter ancestor=redis:7 | head -n1)
          docker exec "$cid" redis-cli CONFIG SET maxmemory-policy noeviction
          docker exec "$cid" redis-cli CONFIG GET maxmemory-policy | grep -q noeviction
```

- 利：把「声明」升级为「实测断言」（与仓库现有的「环境坏 vs 用例坏」分离风格一致，如 `/api/ai/health` 就绪门）；不依赖镜像 entrypoint 行为。
- 弊：多一个步骤与一处对 service 容器名的隐式依赖（用 `--filter ancestor=redis:7` 规避取名字，但容器名生成规则若变化需再适配）；`CONFIG SET` 属运行期设置，非启动即生效。

**倾向**：先落 **A**（解封 CI，风险最低），把 **B/C 作为 T3-9 口径恢复的后续项**并在一次隔离 run 中验证；若团队认为 CI 内该口径必须保留，则直接上 **B + 一步 `CONFIG GET` 断言**（两者可叠加）。

### 「是否等自愈」
**不等**【实测 + 推断】。理由：根因是仓库内确定性配置错误（同一 commit、同一命令、跨 2 小时三次一致复现），与本仓业务与平台波动无关；githubstatus 在 10-08/10-09 无事故；截至 12:07Z 无新 run。**继续 push 任何内容都会以同一条 `docker create` 命令失败**，等待不会改变状态。修复前推送只会继续产生红灯 run（可用于验证，但不必等）。

### 「是否值得加 services 健康检查重试」
**不建议为本次故障加**【推断】。理由：
- 现有 `--health-cmd/interval/timeout/retries` 本身合法且在成功 run 中可用；本次失败**不是**健康检查失败，而是 job 级 `docker create` 崩溃。
- 健康检查重试把「容器起来了但不健康」的情况从「立刻红」拉长为「最多 60s 后红」，对**确定性非法参数**毫无帮助；若真加上重试，反而会把当前的 6s 快速失败拖延为约 60s，迟滞归因。
- GitHub Actions 没有原生 job 级自动重试能力，引入「重试」需第三方 action 或人工 re-run，成本与收益不匹配。
- **可考虑**的是反向动作：保持 fail-fast（当前行为已正确），并在 workflow 或文档中登记一条「services 容器初始化失败 ⇒ 优先检查 `options` 是否为合法 `docker create` 参数」的排障口径 —— 这能让下次同类错误在 1 分钟内被识别，而不是被误判为平台抖动。

### 附带建议（非本次故障，低成本）
- 顺手处理注解中的 `Node.js 20 is deprecated … actions/upload-artifact@v5`（属既有 warning，与本次无关）。
- 为 `ubuntu-latest → Ubuntu 26`（2026-10-19 起）预留观察位：切换后 E2E 的 pwsh、JDK、docker 版本均可能变化，建议切换后首个失败 run 优先按「镜像变更」而非「代码回归」排查。
