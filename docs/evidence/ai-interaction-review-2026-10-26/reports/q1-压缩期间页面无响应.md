# 问题1 只读分析：压缩上下文时页面卡死

## 一、结论先行（按证据强度分级）

| 级别 | 判断 | 依据强度 |
|---|---|---|
| **A｜代码实证** | **“压缩”这件事在代码里确实是一段“前端收不到任何帧、也没有任何界面反馈”的静默期**：压缩在 `out.start` 之前同步跑完，期间没有 start、没有 heartbeat；设计稿要求的压缩提示条（C-35）**从未施工**；`POST /chat` 这条裸 `fetch` **没有建连超时**。续跑路径还会撞上前端 45s 帧间看门狗，表现成“重连中→断流”。**这足以解释“页面像死了”，但本身不阻塞主线程。** | 强（代码 + 设计/施工报告 + 项目自己的调研结论） |
| **B｜代码实证、量级未测** | 长会话（正是需要压缩的那种会话）前端有 4 条持续主线程成本：全量消息列表每 token 重渲染、每张工具卡每次渲染多次 `JSON.parse`/全量字符串扫描、300ms 一次整会话 `JSON.stringify` 写 sessionStorage（**parts 与投影双份**）、`messages`/镜像**无任何上限**。 | 中强（代码位置确定；magnitude 无测量） |
| **C｜推测，需 profiling** | mermaid 同步渲染（`Promise.race` 3s **打断不了同步渲染**）、`loadHistory` 一次性全量渲染 + 逐条 `scrollHeight` 强制布局、GC/OOM。 | 弱（有代码气质，无证据） |
| **D｜排除/无法证明** | ①“压缩那一刻前端做超大 JSON 解析/深拷贝/递归循环”**没有找到任何代码**；②没有任何前端代码消费 `contextCompaction`（只写不读），压缩帧不会触发重渲染；③提供的运行日志里**没有一次真实压缩**（全部 `reason=under_threshold`，ratio 0.001–0.109），不能作为本问题的证据。 | 已核查 |

**最重要的一句话**：现有代码里 **“压缩”与“浏览器主线程卡死”之间没有直接的同步调用链**。最可能的情况是 **A（静默等待被感知为卡死）**；如果用户确实看到了 Chrome 的 “Page unresponsive” 对话框，那第二因（B）需要现场 performance profiling 才能定到具体位置，不能凭“压缩慢”反推。

## 二、实际链路（逐跳，含文件行号）

### A. 首轮发送（用户发消息，上下文已超阈值）

1. 前端 `send()`：立刻建乐观用户气泡 + 空助手气泡，置 `loading=true` —— `frontend/src/stores/ai.ts:2576-2582`。
2. `aiApi.chat(...)` 走**裸 fetch** `POST /api/ai/chat` —— `frontend/src/api/sse.ts:491-511`。**这里只有 `AbortSignal`，没有任何建连/首帧计时器**（45s 的 `DEFAULT_IDLE_TIMEOUT_MS` 要等 `response.body` 可用后才启动，见 `api/sse.ts:31`、`:371-390`）。
3. 后端 `AiController#chat` 先建 `SseEmitter(-1)`（**无传输死线**）并在 `aiRunExecutor` 异步跑本轮 —— `backend/.../ai/web/AiController.java:447-467`、`:1956`。
4. `ResilientChatService#chat` 在**发第一个帧之前**同步执行：
   - `compactBeforeRequest(...)` —— `backend/.../ai/run/ResilientChatService.java:471`；
   - 内部：`MemoryWindow.plan` → `codec.serializeAll(windowed)`（**每轮都把整段记忆序列化一遍**，不只压缩时）→ `ContextCompactor#compact` —— `ResilientChatService.java:2385-2405`；
   - L2 分支走 `RollingSummarizer.plan`：按 `chunk-tokens=8000` 分块，**串行 N 次摘要模型调用 + 递归合并**，每次硬上限 `summary-timeout=60s` —— `ai/context/ContextCompactor.java:262-290`、`ai/context/RollingSummarizer.java:160-190`、`ContextSummaryClient.java:142-160`；配置见 `backend/src/main/resources/application.yml:165-190`（`l1=70% / l2=80% / l3=95%`，128k 窗口 ⇒ L2 约 92k token 触发）。
   - 代码自己写明了这件事的代价：**“续跑路径在压缩期间既没有业务帧、也没有心跳：L2 的 N 次串行摘要每次最长 60s”** —— `ai/context/ContextCompactor.java:211`。
5. 压缩完才 `out.start(sessionId)`，随后发 `context` 帧 —— `ResilientChatService.java:495-497`、`ContextCompactor.java:178-190`（帧体很小，只有 level/before/after/turns/lostTokens 等，**不是大 JSON**）。
6. **heartbeat 只在“上游流式回调”里发**（`ResilientChatService.java:785-793`），也就是 `start` 之后。⇒ **压缩全程 0 帧、0 字节**；Spring 的 SSE 响应体通常在第一次 `send` 才提交，所以浏览器的 `fetch` 连 header 都拿不到。

### B. 续跑（确认卡批准 / 刷新恢复后）

1. 前端带 `lastSeq` 走 `GET /api/ai/events/{runId}`（EventSource）—— `stores/ai.ts:2436-2510`、`api/sse.ts:583+`。
2. 后端 `ResumeService` 同样是 **先 `MemoryWindow` → 再 `ContextCompactor.compact`（可含 L2 串行摘要）→ 才 `out.context(...)` → 才交棒** —— `backend/.../ai/run/ResumeService.java:993-1055`。
3. 前端 EventSource 有两个狗：建连 15s（`api/sse.ts:660-676`）、帧间 45s（`api/sse.ts:648-660`）。**压缩 >45s ⇒ 判定断流 → 退避重连 4 次（1/2/4/8s）→ 耗尽后 `loading=false` + “结果可能不完整”提示**，而此时后端还在压缩/续跑，用户看到的是“卡住/断了”。

### C. `context` 帧到达前端之后

- `case 'context'` 只写 `this.contextCompaction = {...}` —— `stores/ai.ts:5418-5432`；**全仓除 store 自身外没有任何读取方**（`grep contextCompaction` 仅 5 处，全在 store）。
- 因此压缩帧 **不会**触发列表重渲染、不会拉历史、不会重绘图表。
- `done` 帧才会刷新 pill（`contextUsage`），`popover` 打开时才拉 `/context` 分项 —— `stores/ai.ts:1685-1710`。

**没有“压缩导致历史刷新”的路径**：`loadHistory()` 只有两个入口 —— 面板挂载（`AiPanel.vue:3638`）和复制页签接手（`stores/ai.ts:5044`）。

## 三、根因候选（按证据分级，带文件行号）

### A 级：压缩静默期（能解释“卡死”观感，**不阻塞主线程**）

| # | 事实 | 位置 |

| A2 | L2 是 **N 次串行摘要**，N ≈ 前缀 token / 8000，单次上限 60s，且还有递归合并轮 | `RollingSummarizer.java:160-190`、`ContextCompactor.java:262-290`、`application.yml:184-186` |

## 四、为什么不能把“压缩慢”直接当“浏览器卡死”

1. **压缩慢 = 后端线程在跑 N 次摘要**，浏览器此时只是“等网络”。真正的前端症状应是**无反馈**，而不是 CPU 占满。
2. **Chrome 的 “Page Unresponsive” 需要渲染进程主线程连续阻塞数十秒**。代码里唯一可能与“压缩时机”重合的主线程成本是 B1–B6（长会话），但它们**与压缩动作没有因果**，只是**同一批会话同时命中**。
3. 反向也成立：如果用户是在**刷新后**第一次打开面板（历史重渲 + mermaid + 强制布局）时看到卡死，那与压缩只是时间上相邻。

## 六、最小修复方向（供你审，不施工）

**P0 · 消除“假死”观感（不动业务语义）**
1. **压缩期间发心跳**：`RollingSummarizer` 已支持 `onSummaryProgress` 回调（`ContextCompactor.java:217,468`，续跑路径已用），首轮路径（`ResilientChatService.java:471`）没有传；在每次摘要返回后发一个 `heartbeat{phase:"compacting"}`（帧集 16 类不变，但要过 `FrameTypeSetFrozenTest` 的 payload 断言）。
2. **落 C-35 提示条**：`contextCompaction` 状态已存在但无人读；`loading && !首帧` 时显示“正在压缩上下文…（已用 Ns）”，完成后由 pill 百分比下降作为完成标志（设计稿 §5.6 C-35、调研 #28）。
3. **给 `POST /chat` 补建连/首帧超时**（现在只有 body 开始后的 45s）；超时文案要能区分“压缩中”与“网络断”，不要把长压缩直接判成断流。

**P1 · 削主线程峰值（须先用 profiling 确认是这条）**
4. 卡片判据 memo（`hasBodyRows`/`paramRows`/`gateRows`/`conflictRows` 按 `ToolPart` 身份缓存），折叠体改 `v-if` 或 `content-visibility`；长列表按需渲染。
5. 镜像：去掉与 `parts` 重复的投影（或只在回滚模式下写）、降频、加体积上限与“配额击穿”可见提示。
6. 前端 `messages` 跟随后端记忆窗口裁剪（或只保留最近 N 轮 + 压缩摘要），避免页面越开越重。

**P2 · 其它**
7. mermaid 移出主线程（Worker 或分片 yield）；`loadHistory` 后分批渲染 / `requestIdleCallback`。

## 七、仍需 performance profiling 才能定论的点

1. **压缩窗口内是否真的出现 ≥5s 的 long task**：Chrome Performance 录制“点发送 → 首个字符”，看 Main 轨道是否有连续长任务。有 ⇒ B 级成立；没有 ⇒ 就是 A 级“静默等待”。
2. **每次 delta 的组件渲染耗时**：`performance.mark/measure` 包 `markdownHtml` + `onUpdated`，同时记录 `messages.length` / `parts` 总数。
3. **`writeMirror` 单次耗时与镜像体积**：`JSON.stringify` 前后 `performance.now()` + `sessionStorage` 该项的字节数；看是否已接近 5MB 配额（配额击穿后异常被吞，表现为“刷新丢现场”）。
4. **DOM 规模**：Performance Monitor 的 Nodes / JS heap / Layout 次数（`measureUserMsgOverflow` 与 `scrollBottom` 每帧强制布局）。
5. **压缩本身的后端耗时**：用日志时间差即可（`POST` 时刻 → `turn_start` 时刻；以及 `上下文压缩 … level=… summaryChars=…`），并确认 `level` 与摘要请求数——**这条不需要 profile，先确认用户那次到底有没有压缩**。

## 八、需要你确认的三点（否则结论会分叉）

1. 用户说的“浏览器提示无响应”，是 **Chrome 的 “Page Unresponsive/Aw, Snap” 对话框**，还是“页面完全没反应、转圈”的主观描述？这决定 A 级还是 B 级为主因。
2. 卡死发生在**发新消息后**，还是**批准确认卡（续跑）之后**？后者会额外叠加 45s 看门狗 → 重连 → 断流。
3. 复现时后端日志里是否出现 `上下文压缩 … level=L2`？若没有，就说明“压缩”只是用户对“等待”的归因，真正的病灶在别处。

**关于“引入提交”**（仅在有充分证据时给）：
- **`35a30ad`（2026-10-21，上下文批①）** 首次把 `compactBeforeRequest` 放在 `out.start` 之前 ⇒ 引入“压缩静默窗”；
- **`fe12250`（2026-10-21，批②③）** 引入 L2 递归摘要（N×60s）⇒ 把静默窗从毫秒级放大到分钟级，**这是“压缩慢”的直接来源**，但**不是“浏览器卡死”的证明**；
- **`5902cca`（2026-10-24，L-120）** 撤掉了 24ms 渲染预算 + 粘滞降级，使“慢渲染自动降级”这道保险消失（只剩 >10k 字符短路）——**若 profiling 证实主线程阻塞，它是最可疑的渲染侧变更，但目前证据不足以归因**；
- `636dd78` / `152b3a9`（10-26）只动 `awaitingInput` 与取消终态，**与压缩和渲染均无关，不能凭提交时间算回归**。
