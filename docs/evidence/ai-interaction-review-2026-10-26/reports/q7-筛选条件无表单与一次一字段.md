## 结论

真实场景“筛选条件没有表单”，首要原因不是 `FormRenderer` 坏了，而是**当前没有任何提示词/产品契约要求模型在自然筛选请求下必须出表单**：

- 系统提示词全篇没有 `generative_form`（`backend/src/main/java/com/example/configmgr/ai/run/ResilientChatService.java:159-207`）；
- 规则 7 让模型直接走向导勾配置项、设条件（`:178-180`）；
- 规则 18 明确把“筛选条件”列为可以用文字询问的开放信息（`:205-206`）；
- `set_condition` 与 `generative_form(FILTER)` 都能收筛选条件，但没有选择判据（审计已记录：`<LOCAL_WORK>/_a-audit-fragments/R3/S1-backend-tools.md:108-113`、`<LOCAL_WORK>/_a-audit-fragments/R4/S1-prompts-backend.md:590-600`）。

因此模型在真实场景选择“文字问一句”或“直接 `set_condition`”，是当前指令下的合理行为。测试通过只证明“桩点名让模型调表单后，产品链路能消费表单”，不证明“自然语言会触发表单”。

“一次只给一个字段”在现有 `visibleWhen/optionsFrom` 上只能做到**单张表单内的条件显隐**；做不到跨配置项、跨字段的真正逐步向导，因为表单 schema 是模型手写的一整张，渲染器没有分页/步骤。

## 为什么真实场景没有表单：归因

| 归因 | 判定 | 依据 |
|---|---|---|
| **提示词** | **主因，已证实** | `SYSTEM_PROMPT` 无 `generative_form`；规则 18 允许文字问筛选条件；工具描述只有一句“用于收集筛选条件”，没有“何时必须用、一次问几个” |
| **产品交互契约** | **主因，已证实** | `set_condition` 与 `generative_form` 语义重叠、无选择判据（R3-08）；研究稿要求“一屏 >5 字段或出现依赖 → 分步”，但生成式表单没有落地这条规则（`docs/research/调研-AI面板业界细则-2026-10-17.md:252`） |
| **前端能力** | **已证实限制，不是“零表单”的直接原因** | 渲染器把可见字段一次铺开；同一时刻只有一个 `activeForm`；多张表单同批到达时第一张会失去可填入口（`stores/ai.ts:1331`、`:3595-3606`；`AiPanel.vue:613-614`） |
| **模型行为** | **待证** | 真模型 G-01 历史数据 10/10 未出现可提交卡，但当时存在 `tool_start` 晚于 `frontend_tool_request` 的帧序缺陷；HEAD 已有防御（`utils/parts.ts:539-556`），尚无新的自然语言真模型证据 |
| **页面范围** | **已证实** | `generative_form` 只在 `page:tasks` / `task:*` 披露；配置定义页、数据浏览页**刻意不披露**（`AiTools.java:627`；`GenerativeFormDisclosureTest.java:70-90`）。用户若在数据页问筛选，代码层面就没有表单工具 |
| **长表单被拒** | **机制已证实，现场待证** | 字段 >20、序列化 >8000 字符直接拒，表单不下发（`GenerativeFormRules.java:151`、`:174`、`:253-257`、`:289-292`）；G-01 注释记录过真模型“先被入参闸门拒绝、再挂起一次”的实测（`11b-hgta.spec.ts:509-513`） |
| **旧帧序缺陷** | **已修正，不应继续归因** | `parts.ts:539-556` 已保证 `tool_start` 晚到不会把待填表单复位成只读；当前 HEAD 含该修复 |

可以明确分成两种“没有表单”：

1. **页面不对**：在配置定义/数据浏览页，`generative_form` 根本没披露，模型只能用文字或 `ui_*`。这是产品范围问题。
2. **页面对但模型不出**：在任务中心/导出向导，模型可以用规则 18 的文字询问，或直接 `set_condition`。这是提示词/交互契约问题，也是用户反馈最可能命中的场景。

## 已有联动/条件显示/字段来源能否支持“先选一个字段再给下一个”

**能支持的部分（单张表单内）**

- `visibleWhen` 可以让值输入框只在选定字段后出现；渲染器已有测试锁（`frontend/tests/gf-renderer.spec.ts:126-134`）。
- `optionsFrom.definition_fields` 可以按父字段（配置定义编码）返回该定义的字段列表；已有测试锁（`gf-renderer.spec.ts:188-205`）；数据源实现见 `FormOptionSource.java:56-78`。
- `defaultFrom` 可以按父值给静态默认值，适合“选 A 后 B 默认 X”。

**不能支持的部分**

- 不能按“当前选中的字段”动态改变值控件的类型：字段 `type` 是 schema 静态属性（`form-schema.ts:52-82`；后端结果复核也按静态 `type` 判，`GenerativeFormRules.java:1046` 起）。
- 不能按“当前选中的字段”动态返回该字段的枚举选项/引用选项：`optionsFrom.sourceId` 闭集只有 `definition_fields`，它返回的是“字段清单”，不是“某个字段的取值选项”（`GenerativeFormRules.java:140`；`FormOptionSource.java:33-37`）。
- 单张表单最多 20 个字段（`GenerativeFormRules.java:151`），要覆盖多个配置项的全部字段，很快触顶；触顶即整张表单被拒。
- 渲染器没有分页/步骤，只有 320px 内滚（`FormRenderer.vue:23-24`）；`FormSpec` 也没有 step 属性。
- 同一时刻只有一个 `activeForm`；模型一轮发两张表单时，第一张没有可填入口（G-01 实测注释：`11b-hgta.spec.ts:494-500`）。

**缺约束的层**：不是 `visibleWhen/optionsFrom` 原语，而是**提示/编排层**——没有“一次只问一个字段”的规则，也没有产品侧把 `ConfigField` 元数据转成单字段表单的桥；模型必须自己预声明所有候选字段和类型，成本高且容易超限。

## 最小交互与实现方向（供审，不改）

### 建议的最小交互

1. **判配置项**：若已选配置项只有 1 个，跳过；若多个，先用一个单枚举问“先筛选哪个配置项”。
2. **问字段**：只给一个字段选择控件（`enum`，选项来自 `definition_fields` 或 `get_config_def`）。
3. **问操作符**：仅在需要时问（数值/日期可默认 EQ，用户要区间再问）；不要和字段、值堆成三列长表单。
4. **问值**：只给一个与字段类型匹配的控件（text/number/date/enum/multi_select）。
5. **继续或结束**：用户要加第二个条件时重复 2–4；不要主动铺开多个字段。
6. **最终汇总**：把累积的多条字段条件一次 `set_condition`（AND），或按产品裁决每步落库；表单值本身不改变导出范围。

### 实现方向（按成本从低到高）

| 方案 | 改动面 | 能解决 | 主要风险/边界 |
|---|---|---|---|
| A. 提示词 + 工具描述 | `SYSTEM_PROMPT` 加 1–2 条规则；`generative_form` / `set_condition` 描述补“表单只收值，落条件必须 set_condition；一次一个字段” | 自然触发、一次一个 | 依赖模型服从；需真模型自然语言复测；不改变渲染器 |
| B. 单表单位联动 | 不改产品代码，模型用 `visibleWhen` + `optionsFrom` 把其他字段藏起来 | 视觉上一次只看到一个值控件 | 仍需预声明所有候选字段；20 字段上限；动态类型/枚举值选项不足；多配置项不可行 |
| C. 产品派生单字段表单 | 产品从 `ConfigField` 生成“字段选择 + 单值控件”，复用 `operatorsForFieldType` / `parseFieldOptions` | 稳定一次一个、类型/选项正确 | 工作量最大；需要产品裁决；不是当前最小改动 |
| D. 前端分步渲染 | `FormRenderer` 加分页/步骤 | 长表单展示 | 不解决“是否触发表单”；且现有产品原则已是“>5 字段分步”，可作为后续 UI 项，不宜先做 |

**供审建议**：先做 A，并补一条“自然语言筛选请求”的真模型用例；用结果决定是否需要 C。不要先做 D——它解决的是“表单太长”，不是“根本没有表单”。

### 建议补的验证（仅方向）

- 自然语言：“帮我导出 CURRENCY 里 code 为 CNY 的数据” → 是否出现表单，或是否直接 `set_condition`。
- 多配置项：“这几个配置项里先筛一个” → 是否先问配置项，而不是一次列全部。
- 单字段约束：表单可见控件数 ≤ 2（字段/值），且不出现其他配置项/字段。
- 编辑已有条件、取消、字段切换、多字段汇总各一条端到端。

## 需要保留的边界

| 边界 | 现状/证据 | 必须保留 |
|---|---|---|
| 编辑已有条件 | `set_condition` 是**整份替换**（`TaskService.java:163-168`）；模型上下文看不到已有 `conditionJson`（`ContextBuilder.java:61`） | 不能静默丢掉已有条件；要么提供读取/合并路径，要么明确提示“将替换现有条件”。当前是待裁决缺口 |
| 必填 | 后端只校验“可见且 required”的字段；隐藏字段不必填（`GenerativeFormRules.java:343-355`）；前端同样只校验可见字段（`form-schema.ts:747` 起） | 只让当前步骤的字段必填；不要把未来步骤/隐藏字段标成必填 |
| 取消 | `cancelled=true` 是明确终态，不获得数据（`ConfirmGate.java:1759-1790`）；前端取消清草稿 | 取消整个收集流程，不自动应用部分条件；已有条件保持不变 |
| 字段切换 | 向导条件表单切字段会清空值并重置操作符（`ConditionForm.vue:316-323`）；生成式表单会裁掉不再合法的级联值（`form-schema.ts:625-681`） | 切字段后旧值不得复用；依赖字段的值要级联清理 |
| 多字段最终汇总 | `set_condition.fields` 之间是 AND；导出逐条 `ConditionEvaluator.matches`（`ExportJobRunner.java:193`）；向导草案是“每字段一条”（`condition.ts:141-143`、`:169`） | 一次问一个，但最终要汇总成一份 `fields`；避免同字段重复条件（BETWEEN 展开为 GTE+LTE 是既有例外） |
| 配置项 vs 字段 | `select_definitions` 是勾配置项；`set_condition` 是设字段条件；`generative_form` 只收值，不选配置项 | 不能把表单提交值当成“已选配置项”；多配置项时必须先落 `defCode`，再落条件 |
| 空条件 | 空条件被 `WizardActionGuard` 拒绝（`:212-264`）；清空只能由用户在向导手动操作 | 不要把“清空所有条件”做成表单提交；空条件不等于“导出全部”的成功回执 |
| 单活动表单 | 前端同一时刻只有 `activeForm`（`stores/ai.ts:1331`）；同批两张表单第一张失去入口 | 逐步表单必须**串行**：一张决完再出下一张；模型不要在一轮里发多张 |
| 导出 vs 预检查 | 只有 `ExportJobRunner` 读 `conditionJson`（`:166`）；precheck/import 无 condition 消费点 | 不要让用户以为筛选条件会影响预检查/导入；FILTER 表单在导入上下文目前没有落地动作 |
| 页面范围 | `generative_form` 不在 `definitions/data` 披露（`GenerativeFormDisclosureTest.java:70-90`） | 若产品希望数据浏览页也能“问一句就出表单”，需要单独裁决披露范围；不要默认它已经可用 |
| 回灌形态 | 模型收到的是字段 key→值 JSON，不是 `FieldQueryCondition`；字段编码合法性由 `set_condition` 闸门复核（`WizardActionGuard.java:277-330`） | 表单 key 必须能映射回字段编码；多字段汇总时模型要自己组装 `fieldCode/operator/value`，不能把原始 JSON 直接当条件 |

## 仍需实测的待证项

1. **HEAD 上自然语言是否触发表单**：现有 G-01 是显式点名表单的提示词，且历史 10/10 受帧序缺陷污染；需要一条“不说‘请用表单’”的筛选请求。
2. **模型一轮是否只发一张表单**：G-01 实测过“一轮连发两张，第一张取消”，需要确认当前提示/后端是否会约束。
3. **长表单被拒是否是用户现场的直接原因**：机制确定（20 字段 / 8000 字符），但没有用户那次的 `FORM_SCHEMA_REJECTED` 日志。
4. **同一轮内连续两次 `generative_form` 是否可靠**：代码上可挂起/回灌，但前端单 `activeForm`；需要真机验证“第一张提交 → 第二张出现”。
5. **用户当时所在页面**：若在数据浏览/配置定义页，`generative_form` 未披露是确定事实；若在任务中心/导出向导，则主因是提示层。
6. **编辑已有条件的产品口径**：当前模型读不到已有 `conditionJson`，`set_condition` 又是整份替换；是否允许覆盖、是否需要读取入口，需要产品裁决。
