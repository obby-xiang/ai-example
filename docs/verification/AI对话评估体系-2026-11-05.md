# AI 对话独立评估体系（2026-11-05）

## 1. 目的与边界

本体系服务于“渐进式披露与知识库工具选择”复测，交付物为：

- `scripts/verification/ai-progressive-disclosure-eval.mjs`：通过公开 HTTP/SSE 执行小样本，保存逐案轨迹并计算机械指标。
- `scripts/verification/fixtures/ai-rag-eval.json`：`DIRECT/KNOWLEDGE/ACTION/MIXED` 小样本及工具、检索预期。
- `docs/verification/AI对话独立复测清单-2026-11-05.md` 的 PD-01～PD-08：需要浏览器、额外接口或身份对照的独立场景。

评估分两层：**协议与工具行为的机械统计**，以及**答案正确性、忠实度和引用的人工评分**。脚本不会因为出现某个字符串、工具调用或 `done` 帧就给出语义 PASS。

本文件只定义方法和后续执行方式，不代表已经调用真实模型或得到评估结论。

## 2. 隔离前提与强制门禁

1. 只对隔离后端、隔离 Redis、隔离 KB 小样本和隔离模型配置执行。不得读取或修改生产数据。`EVAL_ISOLATED_ENV=true` 是执行者对隔离环境的显式确认；随机 `sessionId/clientRequestId` 只用于轮次去重，不能证明环境隔离。
2. `BASE_URL` 必须显式提供，没有默认地址。只有 `localhost`、`127.0.0.1`、`::1` 按本机处理；任何其他主机还必须设置 `EVAL_CONFIRM_REMOTE=true`。门禁失败会在网络请求前拒绝运行。
3. 默认 fixture 含 `ACTION/MIXED`，必须设置 `EVAL_ALLOW_WRITES=true`。任何 `ACTION/MIXED` 或 `autoApprove` 确认写操作都有同一门禁；`confirm()` 也会防御性检查该许可。只含 DIRECT/KNOWLEDGE 的自定义只读 fixture 可不开启写入许可。
4. `ACTION/MIXED` 中的 `autoApprove=true` 会经公开 `/api/ai/confirm` 批准动作，可能真实创建任务或作业，只能在可清理的隔离环境运行。确认必须同时满足 HTTP 200、响应 `accepted=true` 和后续 `tool_result.outcome=ok`；否则记 `confirm_rejected`，未提供自动批准时记 `approval_required`，两者均属于 `NOT_RUN/HITL`，不是模型工具选择失败。
5. 身份必须显式由 `TENANT_ID`、`USER_ID` 环境变量传入。脚本不读取密钥文件，也不在命令中传模型密钥。
6. 只使用公开 HTTP/SSE。不得通过直接写库、内部接口或伪造帧补齐证据；接口无法证明的项目记 `unknown` 或“未覆盖”。
7. 在仓库根目录执行，每轮使用新的 `sessionId` 和 `clientRequestId`。正式对比至少 `ROUNDS=3`，不能只复用同一现场。
8. KB 小样本应包含“区域费率”的正式管理口径及可核对引用；不存在编号 `ZXQ-404-UNKNOWN` 和“区域收费细则”这一正式标题，并能对近似查询返回“可参考的标题”。未准备好对应语料时，相关用例应记阻塞或未覆盖，不得把环境缺口判成模型通过。
9. 两个 QUERY_COND 用例必须由执行者通过 `QUERY_COND_TASK_ID` 显式提供隔离真实任务。脚本先调用 `GET /api/tasks/{id}`，只在任务存在、`type=EXPORT`、`currentStep=QUERY_COND` 且条目含 `defCode=CURRENCY` 时注入并执行；未提供 ID、ID 非法或任一前置条件失败均记 `NOT_RUN/fixture`，不会请求模型，也不会硬编码任务 ID。
10. 脚本在 `finally` 中最佳努力清理本轮成功创建且已识别 ID 的资源：先以 `DELETE /api/jobs/{jobId}` 请求取消作业，再以 `DELETE /api/tasks/{taskId}` 删除本轮新建任务。创建 ID 优先取结构化 `createdTaskId/createdJobId`（含 `data` 内同名字段），正文解析仅作 fallback，并记录 `idSource`。复用任务和预先存在的上下文任务不由脚本删除。每个结果、HTTP 响应/异常及无法识别 ID 的 `trackingGaps` 均写入报告；任何清理失败或跟踪缺口都会令 `cleanup.status=incomplete` 并设置非零退出码，不得改写为已清理。

## 3. 小样本矩阵

| fixture ID | 类型 | 核心输入/上下文 | 机械预期 | 人工重点 |
|---|---|---|---|---|
| `direct-smalltalk` | DIRECT | 一句话自我介绍 | 不调用 `kb_search/kb_read_doc/kb_lookup_term` | 回答自然，不编造检索或引用 |
| `knowledge-region-tariff` | KNOWLEDGE | 查询区域费率正式口径并要求引用 | 至少一次 `kb_search`；至少一次 `ok/low_confidence` | 口径正确，引用能支持答案 |
| `action-create-export` | ACTION | “创建导出任务” | 选择 `create_task`；不调用 KB；出现确认流程 | 不省略确认，不伪称已启动导出 |
| `mixed-create-and-search` | MIXED | 先查区域费率，再创建导出任务 | 同时出现 `kb_search`、`create_task` | 两件事都完成且顺序、事实不混淆 |
| `knowledge-no-match-rewrite` | KNOWLEDGE | 不存在编号；无命中后仅用指定同义词再查一次 | 至少两次 `kb_search`，出现 `no_match` | 只改写一次，仍无结果时如实说明 |
| `knowledge-approximate-title` | KNOWLEDGE | 查询不存在的“区域收费细则” | `no_match` 且出现“可参考的标题” | 近似标题不得冒充正式命中或有效引用 |
| `query-cond-mixed` | MIXED | `EXPORT/QUERY_COND`；查 KB 并设置 `code EQ CNY` | 同时出现 `kb_search`、`set_condition` | 条件阶段不丢当前任务，参数与目标正确 |
| `query-cond-long-context` | MIXED | 同一条件阶段，含历史候选的消息重复 24 次 | 仍调用 `kb_search` | 长上下文中不省略检索，不串用旧候选 |

`expectedKbOutcome=any` 只表示该案例不预设 KB 结局，不等于有效命中。`requiredTools/forbiddenTools` 只约束工具选择，不证明工具参数、业务结果或答案语义正确。

默认 QUERY_COND fixture 只提供公开页面/任务类型/步骤，不包含 `taskSlots` 或任务 ID：槽位只由服务端生成，任务 ID 只能由执行者通过 `QUERY_COND_TASK_ID` 注入。执行者先按公开标准工作流准备隔离 EXPORT/CURRENCY 任务并进入 QUERY_COND，再把真实 ID 放到环境变量中；脚本完成存在性、类型、步骤和条目校验后才运行。长 Schema、任务槽位硬预算及跨身份回读拒绝还需按 PD-06～PD-08 单独取证。

## 4. SSE 与披露证据

脚本调用 `POST /api/ai/chat`，解析以下公开帧：

| 帧 | 保存内容 |
|---|---|
| `start` | `runId`；请求侧另存 `sessionId` |
| `delta` | 普通正文只拼入 `answer`；`kind=reasoning` 独立拼入 `reasoning`，并分别保留有序段，不混入答案 |
| `tool_start` | `toolCallId`、工具名、参数、相对开始时间 |
| `tool_result` / `frontend_tool_result` | 结果、`resultView/userTextCode`、`outcome/code/status/kind/executed`、表单提交原文、相对结果时间及截断字段 |
| `confirm_request` / `confirm_decision` | 对允许自动批准的用例调用公开确认接口；必须同时满足 HTTP 200、`accepted=true` 和后续 `tool_result.outcome=ok`，否则写 `confirm_rejected` 并记 `NOT_RUN/HITL`；另保存真实决策与状态 |
| `done` | 终帧及 `usage`；`transcriptDegraded=true`、`historyComplete=false` 或两个 transcript 错误码均按降级失败处理，不接受为健康完成 |
| `error` | 错误码和消息；执行失败案例的机械检查不得计为通过，transcript 降级单独分类 |

每个案例还保存 `id/kind/round/latencyMs/terminal/error` 和按 `toolCallId` 关联的调用轨迹。`stopAfter=approval` 的案例只在此前已批准的动作工具返回 `outcome=ok` 后停止读取，不会在 KB 只读调用成功后提前结束；因此这类案例可能没有 `done` 或 `usage`，应记未观测而不是补零。

正常读取到 EOF 时会先 flush `TextDecoder`，再把 `buffered` 中最后一个未遇空行的事件交给同一个 `parseSseBlock + processFrame` 逻辑处理，不能丢失末帧 `done/error` 或其工具结果。逐案 `eof.reached` 和 `eof.tail={present,chars,parsed,frameType}` 保存末帧证据；主动停止/提前批准成功后的取消不是 EOF，不把不完整残留伪装成完整事件。

### 同源 history/run 与持久化证据

- 每案 `reasoning` 独立于 `answer`；`orderedSegments` 只来自实际公开帧，按 assistant 消息合并连续同类 delta，并保留工具首次出现的位置，不伪造应用内帧。
- 终态后以相同 base URL 和租户/用户头读取公开 `GET /api/ai/history/{sessionId}`、`GET /api/ai/runs/{runId}`。history 以 `latest=100` 和真实 `nextCursor` 最多读取 20 页；读取顺序是最新页到更早页，合并时逐页前插以恢复全局时间顺序，页内原升序不变，不使用时间戳等字段猜造排序。
- `persistenceEvidence.history/run` 保存真实读取证据。只有终态存在、history 全部分页可读、run 存在且 `snapshot.runId/sessionId` 与本案一致时，后续内容 verdict 才能判 `PASS/FAIL`；否则保持 `NOT_RUN`。
- `persistenceEvidence.orderedSegments` 比较公开与同 run ASSISTANT `segments` 的 `kind/text/toolCallId` 顺序。`persistenceEvidence.tools` 还必须同时比较 TOOL `toolResponses[].id/name/responseData/resultView/userTextCode` 及相应截断证据，以及 ASSISTANT `toolCallStates[toolCallId]` 的 `status/outcome/code/kind/decision/submittedValues/preflight`；表单提交原文同时核对 TOOL 结果与 `submittedValues`，不能只比较工具锚点。
- 截断按 `FrameSizeLimiter` 语义分路：所有 `frame_truncated/frame_limit_unreached/model_view_truncated` 的 `originalChars/returnedChars` 必须是非负整数并满足 `returnedChars <= originalChars`。帧截断另要求公开 `truncated=true` 与合法 `head/noticeCode`，公开结果长度须等于 `returnedChars`，history 原文长度须等于 `originalChars`，不拿公开截短结果与 history 原文深相等；表单 `submittedValues` 则以 history TOOL 原文核验。公开或 history 任一侧为 `model_view_truncated` 时，该侧均须具有 `truncated=true`、合法 `head/tail/head_tail` 策略及合法计数，缺失、非法或同一路径内的双侧字段冲突均为 `FAIL`。仅未进入 `frame_truncated/frame_limit_unreached` 帧分支且公开侧为 `model_view_truncated` 时，才将公开 result 全文与 history 原文精确比较；公开 `frame_truncated` 与 history `model_view_truncated` 的混合场景不比较公开截短 result 与 history 原文，只分别核验公开帧截断事实、history 模型截断事实及各自字符计数。
- 工具状态中的合法 `PENDING/APPROVED → EXECUTED/BLOCKED` 投影只按公开帧的 `executed/outcome` 与同 run 真实 ledger 推导。缺失、额外、重复 TOOL 响应，或结果、表单提交内容、状态任一不一致，`tools.verdict=FAIL`，并阻断 `orderedSegments` 与 reasoning `toolHopVerdict` 的 `PASS`。空白提交严格按 Java `Character.isWhitespace/StringUtils.isBlank` 的显式集合判定：`\u0009-\u000D`、`\u001C-\u0020`、`\u1680`、`\u2000-\u2006`、`\u2008-\u200A`、`\u2028`、`\u2029`、`\u205F`、`\u3000`；仅空串或全由这些字符组成时才与 history 空白缺省的 `null` 等价。NBSP `\u00A0`、`\u2007`、`\u202F` 不属于空白，含这些字符或其他非空白内容的提交必须精确一致，不使用 JS `\s` 代替 Java 语义。
- 公开和持久化工具集合均为空时 `tools.verdict=NOT_RUN`、`applicable=false`，表示工具对账不适用而非通过。该空工具结果不得降低纯文本 `orderedSegments` 的 verdict；只有实际存在工具但证据不完整时，才阻断有序段 `PASS`。
- `persistenceEvidence.reasoning` 分别给出 `verdict/toolHopVerdict/visibilityVerdict` 及公开、持久化 reasoning 段。工具跳结论要求工具前 reasoning 与完整有序段均同源保留；可选 `REASONING_DISPLAY_ENABLED=true|false` 只声明并核对可见性，展示关闭时隐藏 reasoning 的持久化和工具跳仍为 `NOT_RUN`，不得仅凭 SSE 推断持久化。

### 执行阶段、错误分类与 NOT_RUN

每个 `error` 都保留 `stage/category` 及原始响应、帧或异常文本。`chat_http` 表示聊天接口没有返回 SSE，`fixture_validation` 表示任务前置校验，`confirm` 表示 HITL，`terminal` 表示上游错误帧，`execute` 表示脚本执行异常。分类口径：

- `infra`：HTTP、连接、脚本执行等基础设施失败；计入执行错误，不进入模型可评价分母。
- `fixture`：缺 `QUERY_COND_TASK_ID`、任务不存在、类型/步骤/条目不符；记 `NOT_RUN`，不请求模型。
- `hitl`：`approval_required` 或 `confirm_rejected`；记 `NOT_RUN`，不把未批准或未成功执行的动作算作模型选择失败。
- `transcript`：`transcriptDegraded=true`、`historyComplete=false`、`AI_TRANSCRIPT_INCOMPLETE` 或 `AI_TRANSCRIPT_WRITE_FAILED`，优先于其他 terminal 分类；计入执行错误和 `transcriptErrors`，不进入模型可评价分母，也不冒充 infra/model。
- `model`：错误码明确包含 `MODEL/UPSTREAM/PROVIDER/RATE_LIMIT/EMPTY_REPLY` 的 terminal 错误，以及执行成功后 required/forbidden 工具或检索行为不符合预期。通用 `INCOMPLETE` 不再单独作为模型分类依据；`modelBehaviorFailure` 单独标记行为失败，其他 terminal 错误保守归为 infra，不能拿 fixture/HITL/transcript/infra 错误冒充。

每个 HITL NOT_RUN 案例必须同时写案例顶层 `notRun=true` 和 `error.notRun=true`：前者是 mechanical、executionErrors、notRunByCategory、executable、modelEvaluable 的唯一分母判据，后者只负责保留详细原因，不能只在 error 内标记而污染分母。此类案例的机械 `pass` 为 `null`，不会伪造通过或失败；`executionErrors` 不包含这些案例。`notRunByCategory`、`infrastructureErrors`、`transcriptErrors`、`modelTerminalErrors`、`modelBehaviorErrors` 和去重后的 `realModelErrors` 分别汇总。

即使 confirm 已返回 `accepted=true`，流结束时仍无对应 `tool_result.outcome=ok`，也只能记 `confirm_rejected` 和“结局未证明”，不得仅凭 `create_task` 工具名或确认受理就机械通过；成功创建的工具结果仍按原路径参与资源清理。

### 披露事实的 `unknown/invalid` 规则

- 公开 SSE 中出现某工具，只能证明它被执行或请求，不能反推 system prompt、规则包或完整披露工具集合。
- 默认全局及逐案 `disclosure.status=unknown`。
- `DISCLOSURE_URL` 只接受同源 `/api/ai/tools`（可带 page/taskType/step/taskId 查询参数）。报告级证据只有在 HTTP 200、Content-Type 为 JSON，且响应满足真实结构时才为 `observed`：`success=true`，`data` 含非空 `context/definitionsVersion`、一致的 `count/registeredCount/toolNames/tools`，每个工具的名称顺序一致，并含 `displayName/titleKey/lang/riskLevel/channel/scopePatterns`。
- 非 200、请求异常或未配置接口为 `unknown`。错误 URL、200 HTML/非 JSON、健康检查或无关 JSON、字段缺失及计数不一致均为 `invalid`，不得因状态码 200 升为 `observed`。
- `/api/ai/tools` 只是按入参现算的工具披露投影，不等于每一轮实际 system prompt 或冻结上下文；即使获得报告级证据，也不能把它自动当成每一轮的完整披露证明。
- `read_tool_result` 的分页连续性、跨 run/身份拒绝若公开接口无法证明，按 PD-08 记 `unknown/未覆盖`。

## 5. 机械指标口径

以下按“案例 × 轮次”统计；`N` 为全部案例轮数，`R` 为 `expectRetrieval=true` 的案例轮数，`F` 为 `expectRetrieval=false` 的案例轮数。执行出错即该轮检索与工具选择检查不通过。

| 指标 | 公式/判定 | 报告字段 |
|---|---|---|
| 正确检索率 | 检索行为符合预期且无执行错误的轮数 ÷ `N` | `correctRetrieval/retrievalChecks`、`retrievalAccuracy` |
| 应检索触发率 | `R` 中至少调用一次 `kb_search` 且无执行错误的轮数 ÷ `R` | `retrievalRequiredPass/retrievalRequired`、`retrievalRecall` |
| 检索误触发率 | `F` 中至少调用一次 `kb_search` 的轮数 ÷ `F` | `falseTriggers/retrievalForbidden`、`falseTriggerRate` |
| 工具选择准确率 | 无执行错误、全部 `requiredTools` 出现且无任何 `forbiddenTools` 出现的轮数 ÷ `N` | `toolAccuracy.pass/total/ratio` |
| KB 有效命中率 | 返回 `状态: ok` 或 `状态: low_confidence` 的 `kb_search` 次数 ÷ 全部 KB 结局数（含 `unknown`） | `effectiveHits/kbOutcomeCount`、`effectiveHitRate` |
| KB 无命中率 | 返回 `状态: no_match` 的 `kb_search` 次数 ÷ 全部 KB 结局数（含 `unknown`） | `noHits/kbOutcomeCount`、`noHitRate` |
| 平均总工具调用数 | 各轮不同 `toolCallId` 对应的工具调用总数 ÷ `N` | `averageToolCalls` |
| 平均 KB 检索调用数 | 各轮 `kb_search` 调用总数 ÷ `N` | `averageKbSearchCalls` |

`retrievalRecall` 是“应检索场景的触发率”，不是相关文档排序召回率，也不替代 MRR、nDCG 等检索质量指标。`unknownKbOutcomes` 单独报告，不得并入有效命中或无命中。

同一组公式同时写入 `metrics.raw`、`metrics.executable` 和 `metrics.modelEvaluable`：

- `raw` 保留全部案例轮次，包括 `NOT_RUN` 和全部错误，兼容原报告顶层字段。
- `executable` 只排除 `NOT_RUN`，仍保留 infra/transcript/model 执行错误，因此不会被误读为纯模型成绩。
- `modelEvaluable` 排除 `NOT_RUN`、infra 和 transcript 错误，但保留模型错误帧及模型行为失败；不会通过删除真实模型错误抬高比例。

汇总另给 `executableCases/modelEvaluableCases/notRun/notRunByCategory/transcriptErrors/realModelErrors`，不得只选择较高的一项作为整体能力结论。平均调用数仍按全分母计算并包含失败轮，解释时应同时查看 `executionErrors` 和分类计数。

逐案另有 `outcomePass`、`minCallsPass`、`approximateTitlePass` 等辅助检查。“状态”“可参考的标题”仅用于协议统计；它们不证明答案正确、引用有效或近似标题可当作正式文档。

## 6. 人工评分与引用核对

每个案例的 `manual` 初始均为未评分：

- `answerCorrectness=null`：0 = 错误或未回答核心请求；1 = 部分正确但有遗漏/次要错误；2 = 核心请求完整正确。
- `faithfulness=null`：0 = 关键结论无依据或与证据矛盾；1 = 仅部分结论有依据；2 = 关键结论均由所引证据支持。
- `citations=[]`：审查者为每个关键引用追加 `{claim, source, verdict, note}`。
- `reviewer=null`、`notes=null`：填写审查者、适用性说明、失败原因和复现信息。

引用 `verdict` 只有四种：

| 值 | 含义 |
|---|---|
| `unchecked` | 尚未打开来源核对；不得计为通过 |
| `verified` | 来源真实且对应内容支持该结论 |
| `wrong_source` | 引用了错误文档、近似标题或无关片段 |
| `unsupported` | 来源本身存在，但不能支持该结论 |

正确性与忠实度分别评分：答案碰巧正确但引用不支持时，忠实度不能给 2 分。无引用必要的 DIRECT/ACTION 案例在 `notes` 说明“不适用”，不得虚构引用。人工评分完成前，报告只有机械结果，没有整体语义 PASS。

## 7. 使用方法与输出

在仓库根目录、隔离服务就绪后执行。默认 fixture 有写操作，命令必须显式包含隔离和写入许可：

非本机地址还必须追加 `EVAL_CONFIRM_REMOTE=true`。缺省 `BASE_URL`、隔离确认或所需写入许可时脚本默认拒绝；不要通过随机会话号绕过这些判断。

其他环境变量：

- `TIMEOUT_MS`：单次 HTTP/SSE/清理请求超时，默认 `120000`。
- `FIXTURE`：替代 fixture 路径，默认 `scripts/verification/fixtures/ai-rag-eval.json`。
- `QUERY_COND_TASK_ID`：QUERY_COND 用例的隔离真实任务 ID，必填于该组用例；必须对应存在、EXPORT、当前 QUERY_COND 且含 CURRENCY 条目的任务。缺失或校验失败仅将该组标为 `NOT_RUN/fixture`，其他独立用例仍可执行。
- `OUT_DIR`：报告目录，默认 `verification-results/ai-progressive-disclosure-eval`。
- `DISCLOSURE_URL`：可选的同源 `/api/ai/tools` 路径，例如 `DISCLOSURE_URL='/api/ai/tools?taskType=EXPORT&step=QUERY_COND'`；健康检查和其他接口不属于有效披露证据。
- `REASONING_DISPLAY_ENABLED`：可选 `true|false`，声明隔离服务实际 reasoning 展示开关并核对公开/history 可见性；缺省表示未声明。该开关不改变持久化证据门槛，隐藏 reasoning 不得由空投影推断为已保存。

输出为：

```text

```

`summary.metrics` 同时保留 raw/executable/modelEvaluable 三组指标及各自分母，另有 `notRunByCategory/transcriptErrors/realModelErrors`；不得只摘取其中一组夸大结论。`cleanup.jobs/tasks/trackingGaps/failures` 是环境清理证据，创建 ID 另记录 `idSource=structured-createdTaskId|text-fallback`；`cleanup.status` 为 `complete/incomplete/not_required`，已有终态作业、已不存在资源与真正失败分别记录，不能相互冒充。出现未捕获执行异常或清理不完整时报告仍尽量落盘，同时进程退出码非零。报告可能包含用户输入、工具结果和身份信息，应按评估证据管理，不得提交密钥或生产数据。
