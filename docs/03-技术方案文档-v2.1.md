## 1. 概述

### 1.1 目标

以需求冻结版 RD-001 v2.1 为范围，落地一套"元数据驱动的配置实施平台"：配置定义/数据/导出/导入（检查→暂存→发布）/任务中心/AI 对话助手/认证授权与审计/版本管理，并满足以下技术目标：

| 目标 | 口径 |
|---|---|
| 官方能力优先 | 循环、记忆、工具管理、认证、前端组件一律用现成能力（DC-05）；官方能力不存在时才在官方 SPI/扩展点上实现（ADR-3） |
| 单一服务层 | 界面 REST 与 AI 工具调用共用同一业务服务层、同一校验、同一权限切面（FR-5.5/D2、FR-5.4） |
| 多实例无状态 | JVM 内本地状态一律外置（DC-03），外置清单见 §9 |
| 可迁移 | Flyway 版本化迁移 + 本期 H2 文件库 → M2 MySQL（ADR-9） |
| 可回归 | 行为基线与故障注入全部自动化进 CI 门禁，门禁有效性经注入缺陷验证（ADR-12） |

性能与并发口径沿用冻结版：查询 P95 ≤ 500ms、万行检查 ≤ 60s、导出 5 万行 ≤ 90s、10 并发，均为**设计目标（非实测承诺）**（DC-09 A8/A9）。

### 1.2 范围

- 本期（M1）包含：§1.1 所列八项能力；审批流（FR-3.6）、脱敏规则引擎、敏感字段加密存储、AI 统计报表**均不在实现范围**，仅保留接口/元数据留口（DC-09 A1/A4/A5/A7）。
- 不在本期：配置运行时下发的业务通道、工作流引擎级多级审批、M2 的 MySQL 迁移与生产化（ADR-9）。

## 2. 总体架构

### 2.1 进程形态

| 进程/组件 | 形态 | 关键约束 |
|---|---|---|
| 浏览器 SPA | Vue 3 + TS 单页应用（静态资源部署） | 页签级 AI 会话（sessionStorage 存 sessionId）；不持有任何模型凭证；不含前端 Runtime（DC-06②③） |
| 后端应用 | Spring Boot 3.5.14 单体制、无状态多副本 | 业务 REST、SSE、AI Runtime、作业执行同进程；虚拟线程开启；实例内不留权威状态（DC-03） |
| 作业执行 | 进程内线程池/虚拟线程 + 事务后异步提交 | 权威状态落库；取消标志与进度事件外置 Redis（ADR-8、DC-03） |
| 数据层 | H2 文件库（本期）→ MySQL（M2）；Flyway 迁移 | 见 §3 |
| 共享协调层 | Redis（会话记忆 / 挂起态 / 锁 / 扇出 / 取消标志） | 不要求持久化（DC-02）；使用点见 §9 |
| 上游模型服务 | 任意 OpenAI 兼容服务（base-url/model/key 全配置化） | 密钥仅服务端环境变量注入（DC-01、DC-08） |
| 文件存储 | 后端本地目录（导出结果、上传文件、模板） | 路径可配置；多实例下需共享或粘性——见 §13【待裁决】11 |

### 2.2 多实例部署图（文字描述）

```
浏览器（N 用户）──HTTPS/REST + SSE（进度、AI 流式）──▶ 反向代理/负载均衡（无会话黏滞要求）
        ├─▶ 后端实例 #1 ：业务服务层（唯一） + AI Runtime（官方循环） + 作业执行器
        ├─▶ 后端实例 #2…#N：同构
        ├─▶ Redis（共享）：会话记忆 / 挂起态 / 锁 / pub-sub / 取消标志
        ├─▶ 数据库：本期 H2 文件库（单实例）→ M2 MySQL（多实例共享）
        └─▶ OpenAI 兼容上游：每实例各自出站，密钥经环境变量
```

要点：
1. **无状态化边界**：任一实例可处理任一请求；会话记忆、挂起态、锁、进度/事件扇出、取消标志全部在 Redis 上（DC-03、ADR-2/3/5/8）。**例外**：AI 轮的"挂起中"请求本身仍占用某实例的线程与 SSE 连接，故续跑协议必须把控制权外置（§5.3 硬性前置）。
2. **扇出**：进度事件与 AI 事件经 Redis pub/sub 跨实例广播（ADR-2/ADR-6 配套），订阅端为持有该 SSE 连接的实例。
3. **上游调用**：AI 与工具调用由实例直接出站，无中心网关；重试与超时策略在实例内按 §5.6 执行。

## 3. 数据层与迁移

### 3.1 Flyway 迁移规范（ADR-9）

| 规范项 | 内容 |
|---|---|
| 位置 | `backend/src/main/resources/db/migration` |
| 命名 | `V{n}__{描述}.sql`（顺序递增，编号不跳号、不复用） |
| 不可变 | 已入库的迁移文件禁止修改；任何结构变更以新增迁移表达 |
| 与 JPA 的关系 | `spring.jpa.hibernate.ddl-auto=validate`——实体映射必须与迁移结果一致，禁止 `update/create` |
| 启动校验 | 启动即执行迁移；校验失败视为启动失败，不得以内联改库绕过 |
| 环境一致性 | 测试库与演示库均由迁移生成，禁止手工建表（V9 三实验幂等结论） |

### 3.2 清库初始化纪律（Q1）

- **main-v2 一律清库初始化**：首次启动前清除旧数据文件/旧 schema，由 `V1` 起完整迁移。**禁止复用任何旧 H2 数据文件**。
- 原因（Q1 实测边界）：`baseline-on-migrate` 对"已有非空 schema 但无 Flyway 历史表"的旧库会**跳过 V1 迁移**，直接导致启动失败（缺表）。配置项保留，但纪律以清库为准。
- **切 MySQL 时迁移演练必须覆盖此场景**（非空 schema + 无历史表），演练结论作为 M2 出口条件之一。
- 回归用例：清库后连续两次启动成功、`ddl-auto=validate` 通过、`flyway_schema_history` 记录完整。

### 3.3 H2 → MySQL 演进路径

| 阶段 | 内容 | 出口标准 |
|---|---|---|
| 本期 M1 | H2 文件库；单库演示与自动化测试 | 清库两次启动、schema validate、E2E 全绿 |
| M2 切换 | 迁移脚本方言审查（标识符长度、`JSON/CLOB`、布尔与时间类型、自增/序列、唯一键与索引差异）；清库全量迁移演练（含 Q1 场景） | 全量迁移一次通过；回归套件在 MySQL 上全绿 |
| 切换后 | 多实例共享同一库；Redis 使用点不变 | 多实例并行用例通过 |

前置提示：ADR-9 的推翻条件为"M1 期间出现 H2 不支撑的需求（如多实例共享库）——届时提前切换 MySQL"。M1 演示的实例数口径与该条件的关系见 §13【待裁决】11。

## 4. 领域模型与业务机制

### 4.1 实体表（按冻结版 §3）

| 实体 | 说明 | 关键属性/约束 |
|---|---|---|
| ConfigDefinition | 配置项元数据 | 编码、名称、层级（GLOBAL/REGION/PROJECT）、字段集、依赖 DAG、状态、版本 |
| ConfigField | 字段定义 | 编码、7 种类型（文本/长文本/数字/布尔/日期/枚举/引用）、必填、枚举选项、引用目标、业务键标记、**sensitive 元数据标记（仅标记，不脱敏不加密）** |
| ConfigData | 已发布生效数据 | 定义编码、范围（地区/项目）、行数据（JSON）、版本号、状态（PUBLISHED）、生效时间；唯一性含范围维度（FR-1.3） |
| StagingData | 导入未发布草稿 | 按任务隔离，发布后清除 |
| ConfigVersion | 每次发布的快照 | 版本号、diff 摘要、发布人/时间；审批人字段预留（M1 留空）；回滚＝以快照为数据源重走导入发布通路，无回滚指针、无独立回滚审批（DC-09 A3） |
| Task | 一次导出/导入实施过程 | 任务号、类型、状态机、当前步骤、参数、创建人 |
| Job / JobItem | 任务内异步执行单元 | 类型（EXPORT/PRECHECK/IMPORT/PUBLISH）、状态、进度、逐项明细、行级校验问题 |
| AiSession | 页签级 AI 会话 | 会话 ID、页签绑定、**消息历史存 Redis（滑动 TTL 默认 6h）**、待确认交互、TTL（DC-09 D1） |
| AuditLog | 全量操作流水 | 操作人、动作、对象、前后值摘要、来源（界面/AI）、IP、时间；审计表 + 检索页，不建报表体系 |
| Approval | 发布审批（**本期仅实体与接口预留**） | M1 不启用；审批角色随 M2 另行定义（DC-09 A1/A2） |
| User/Role | 认证与 RBAC | 3 角色（操作员/管理员/只读审计）；数据权限按层级只读/可写两级（§8） |

### 4.2 发布语义（ADR-7）

| 机制 | 口径 |
|---|---|
| 替换范围 | **glm 范围内替换**：按"配置项 × 范围"替换 PUBLISHED 数据，多范围并存互不误伤（V2 双向对称实验逐字段比对） |
| 事务性 | 删除本次涉及范围 + 提升暂存为发布态在**同一事务内**完成；发布前终检 |
| 并发安全 | combined 的乐观锁冲突检测（`OPTIMISTIC_FORCE_INCREMENT` + baseVersion 快照比对）**原样保留叠加**；版本强制递增、提示文案沿用（V5） |
| 冲突处置纪律 | 冲突时**重写而非折中**（取新版本重做发布，不做字段级合并） |
| 冲突提示通路 | 现状形态为"异步作业 FAILED + issues 文案、POST 恒 201"（Q4）；前端**必须按异步通路**处理提示，该形态写入接口文档（Q4 处置） |
| 引用完整性 | 发布终检引用取值源 = 正式区 + 本批次拓扑序在前配置的暂存数据（FR-3.3 引用完整性规则） |
| 回滚 | 以 ConfigVersion 快照为数据源重新走"导入→发布"既有通路（DC-09 A3） |
| 回归用例 | V2 双范围发布实验、V5 并发发布冲突实验均转自动化 |

### 4.3 作业治理（ADR-8：继承 combined + 三项修正）

**继承**（combined 生产机制，35 次迭代淬炼，V5/V6 实测）：任务中心（统一列表、类型/状态过滤、服务端分页）、作业三层模型（Job/JobItem/ValidationIssue）、事务后异步提交（创建事务 afterCommit 后再提交线程池，修复"执行线程读不到未提交行"竞态）、同任务同 kind 幂等（存在 RUNNING 作业时拒绝重复提交并返回现有作业）、僵尸恢复、取消注册表、终态补发。

| 修正项 | 内容 | 出处 |
|---|---|---|
| ① 扫描范围 | `StaleJobRecoveryRunner` 扫描范围**必须含 PENDING**——崩溃残留实为 PENDING（RUNNING 从未提交），只扫 RUNNING 会漏 | Q6 |
| ② 恢复联动 | 恢复动作与任务状态联动策略**在 S4.3 定**（当前只改 jobs 表、不重排队、任务态长期不一致）；本文档不预设策略 | Q5 / §13【待裁决】7 |
| ③ 取消外置 | 取消标志 **Redis 化** + **取消请求必须路由到持有该流的实例**（多实例缺口实测：落错实例时 `isCancelled()` 恒 false）；无法路由时必须返回"未找到"，不得静默忽略 | SP-01d V-d3、DC-03 |

其他落地要求：
- 取消生效点＝**事件边界**；工具内按分片（≤1 个分片，实测 200ms 分片下 57ms 响应）协作式检查标志，值得推广到所有长工具（SP-01d §6.4）。
- 运行态按 **runId** 隔离（不按 sessionId），`cancel` 明确指定 runId（SP-01d §6.5）。
- 抑制 `SseEmitter.onCompletion` 置取消标志的写法（正常结束也会触发，产生竞态）；客户端断开由 `onError`/`onTimeout` 承载（SP-01d §5.5）。
- 回归用例：kill 恢复（含 PENDING 残留）、执行中取消（协作式/非协作式两种）。
- 事务后异步 + 幂等：AI 发起的作业启动走同一作业服务（FR-5.5）。

### 5.1 循环组装（ADR-1：官方 ChatClient 循环）

| 项 | 口径 |
|---|---|
| 决策 | A：Spring AI 官方循环（`ChatClient` + `ToolCallingManager`），【实测】V3 22/22 E2E + SP-01ab/c/d 三卡 + 独立复核一致 |

| 被否决 | B 自研手工协议循环（1145 行巨型类，模型行为变化时整片失效）→ 转化为**模型升级冒烟套件**回归；C 受控薄 Loop 为**预登记备选**，仅在 S4.2 出现 SP-01 三卡未覆盖且无法绕行的官方缺陷且有新实测证据时回退 |

启动可用性（Q2）：AI 相关 Bean 采用懒加载/可缺省装配，**空 api-key 时必须仍能启动**后端（业务功能不受影响），并补启动回归用例。

### 5.2 HITL 确认门与前端工具（ADR-2：ToolCallingManager 阻塞挂起）

`HooksToolCallingManager` 包装官方 `DefaultToolCallingManager`，承担四件事：

| 能力 | 实现口径 | 实测支撑 |
|---|---|---|
| 可见性 | 工具执行前后推 SSE `tool_start` / `tool_result`（含耗时、成败） | SP-01ab 时序留档 |
| HITL 确认门 | `needConfirm` 工具**执行前阻塞挂起**：批准→放行执行；拒绝/超时→以"未执行 + 原因"文本作为工具结果回填模型 | SP-01b 三结局 6/6、7/7、9/9 断言全过 |
| 前端工具 | 注册成普通 `@Tool` 以生成 Schema 下发（**只借 schema，不借执行**）；不委托执行，SSE 透出 `tool_call` → 阻塞等前端 `POST` 回灌 → 结果以官方 `ToolResponse` 交回循环 | SP-01a 非流式/流式各 11/11；哨兵桩计数 0 证明后端未执行 |
| 回灌幂等 | 自建 pending 注册表按 `toolCallId` 去重：重复回灌返回 `duplicate=true` 且不落消息、不推进轮次；未知 id 返回 409（官方循环对重复 `toolCallId` **不去重**，必须入口层处理） | SP-01d V-d2③ |

实现边界（必须写进规范）：
1. **挂起＝阻塞循环中执行工具的那条线程**，非一等公民暂停（1.1.8 无 suspend/resume）。流式路径用 `subscribeOn(boundedElastic)` 承载，**不得在 Tomcat 请求线程上直接挂起**（否则耗尽线程池）。
2. 挂起占用一个工作线程 + 一条 SSE 连接；并发挂起上限 = 线程池容量（压测口径见 §13【待裁决】2 相关项）。
3. 超时语义自定：前端工具超时→回填"前端未在 N 秒内回传，本次未获得数据"；确认门超时→回填"已取消、未执行"（FR-5.3）。
4. 心跳保活：挂起期按固定间隔（PoC 实测 2s）下发 `ping`，载荷暴露 `pending` 语义；实测挂起 30s 期间 15 帧心跳、连接未断。**心跳不得被用作超时续期**（见 §5.6 硬规范①）。
5. 结果文本形状归一：委托官方执行的结果为 JSON 序列化形态，自建 `ToolResponse` 为原文透传（SP-01ab §7.1）——前端卡片渲染前统一归一化。
6. 一条 assistant 消息可同时含文本与多个 `tool_call`，前端渲染（文本气泡 + 工具卡）必须容忍该混合（SP-01ab §7.3）。

### 5.3 挂起态 Redis 外置与续跑协议（**硬性前置**，Q10）

- **问题（实测反例）**：官方循环的挂起态仅存于进程内存。GLM 独立复核的 kill-during-suspend 反例证实：挂起期进程死亡后**已放行的人工决策也无声丢失**（前端拿到 404 unknown sessionId、工具计数归零、无任何痕迹），后果比"续跑不了"更重一档。
- **生产形态（ADR-2 定）**：挂起请求写入 Redis（**pending 状态 + TTL**）＋ **前端可感知的挂起态展示**（刷新/换实例后仍能看到待确认交互）＋ **实例恢复后的续跑协议**（以 SP-01ab §5 方案 B 为起点）。
- **纪律**：S4.2 落地时该外置为**硬性前置工作项，不得降级**（不得以"单实例内存挂起 + 会话黏滞"充当交付）。
- **前置补测**：SP-01ab §5 方案 B 属【推断，本次未实测】，落地前**必须补一次实测**（含消息序列合法性、不重放、不丢、流式续接）；结果记为【待裁决】1 的证据。
- **配套要求**：超时判定必须把"挂起期心跳"纳入输入，并对重放加幂等保护——否则长挂起（>超时阈值）会触发重放，导致同一工具调用被重复请求（SP-01ab §7.6【推断】）。
- 回归用例：挂起期重启续跑测试（含已放行未执行决策的恢复）。

### 5.4 会话记忆（ADR-3：官方 SPI + Redis LIST）

实现官方 `ChatMemoryRepository` 的 4 个方法（`findConversationIds` / `findByConversationId` / `saveAll` / `deleteByConversationId`），其余全部走官方（`MessageWindowChatMemory` + `MessageChatMemoryAdvisor`）。

| 项 | 口径 |
|---|---|
| 键结构 | `chat:mem:<conversationId>`：LIST，元素为 JSON 消息（`type`/`content`/`timestamp`/`metadata`，按需含 `toolCalls`/`toolResponses`）；`chat:mem:__ids__`：SET，会话 id 索引 |
| 写入语义 | `saveAll` = `DEL` + 批量 `RPUSH`（**整窗口覆盖写**）——官方 `MessageWindowChatMemory.add` 为"读全量→合并裁剪→全量回写"，实现成追加会使窗口裁剪失效（字节码核对） |
| TTL | 滑动 TTL，默认 **6h**（DC-09 D1）；**仅写操作刷新**，读不续期；到期键自行消失（"不持久化"语义成立） |
| 窗口裁剪 | 由官方 `MessageWindowChatMemory` 的 `maxMessages` 按**消息条数**裁剪（非 token）；这是防止 LIST 膨胀的第一道也是唯一一道闸门 |
| 索引清理 | 索引键不带 TTL，过期 id 在下次 `findConversationIds()` 时被惰性剔除 |
| 装配 | 显式声明 `chatMemoryRepository` / `chatMemory` Bean（官方自动配置带 `@ConditionalOnMissingBean`，自动让位）；**不要同时引入官方 Redis starter** |
| 被否决 | 官方 2.0 实现（需 RedisJSON + RediSearch，本机与生产基线均无，且引入 Jedis 双客户端）；H2 持久化（违反 DC-02）；JVM 内存（违反 DC-03，多实例断片） |
| 系统提示置顶 | `MessageChatMemoryAdvisor` 会把遇到的第一个 SystemMessage 移到索引 0（字节码 + 上游报文双证）——system 每轮置顶，不必在业务层重复插入 |
| 实测 | V-c1~V-c5 五项全过：多轮记忆、TTL 到期消失、多实例共享、重启恢复、7 轮带工具无 400；工具协议消息经 Redis 往返保真 |
| 升级条件 | 升级 Spring AI ≥2.0 且生产 Redis 具备 JSON/Search 模块时可切官方实现（接口不变，调用方无感）；升级评审须把"Redis 是否具备模块"作为前置条件 |
| 回归用例 | TTL 到期会话消失、双实例接续对话、工具消息往返保真、窗口裁剪上界 |

### 5.5 会话串行化（ADR-5：409 单值门 + 分布式锁）

| 项 | 口径 |
|---|---|
| 目标 | 同一 sessionId 的并发轮次串行化，杜绝静默数据损坏（Q11） |
| 机制 | 会话级**单值门**：同 sessionId 已有进行中的轮次时，第二轮直接返回 **409**；多实例下用 **Redis 分布式锁**（键按 sessionId，锁 TTL 覆盖单轮最长时间并大于最长工具耗时与确认门等待） |
| 证据 | 8 并发实测**必丢 1 条用户消息**且产生 7 USER/8 ASSISTANT 失配历史**永久驻留**（对用户不可见、无法自愈）；并发两轮回复文本互相拼接、runId 互相覆盖 |
| 与挂起的关系 | 409 单值门模型已实测**不影响挂起中的那一轮**（SP-01ab） |
| 体验影响 | 页签级会话（DC-06③）下 409 在正常单页签使用中不触发，体验无损 |
| 运行态隔离 | 运行态（terminal/content/attempts/取消注册）按 **runId** 隔离，禁止按 sessionId 共享可变状态 |
| 回归用例 | 同 sessionId 并发 8 路压测，**必须 0 丢消息**；挂起中再发一轮返回 409 且原轮不受影响 |
| 被否决 | 不控制（即上述丢消息）；队列化（改变即时响应语义、复杂度高） |

### 5.6 SSE 韧性策略（ADR-6：每轮重建请求 + 双超时 + 重试三条件）

自研策略、官方 API 组装（官方机制在流式场景已被实测证伪）。

| 机制 | 口径 | 实测依据 |
|---|---|---|
| 不重订阅 | **每次尝试重建整条请求**（新 advisor 链）：`chatClient.prompt()...stream()` | `ChatClient` 的 advisor 链一次性（`DefaultAroundAdvisorChain` 用 `Deque.pop()`），重订阅必抛 `IllegalStateException: No StreamAdvisors available to execute` 且**不发第二次请求** |
| 官方重试不覆盖流式 | 官方 `RetryTemplate` 只出现在非流式 `internalCall`；`stream()` 全程无 retry/timeout 算子 | 字节码实测 |
| 双超时 | `firstEventTimeout`（首包）与 `interEventTimeout`（事件间）分别可配 | 单值 `timeout` 亦可覆盖两层，拆开是为两个业务阈值可分别配置 |
| 重试三条件 | ① 剩余次数（默认 `max-attempts=2`）② 未超总时长预算 ③ **本轮未对客户端产出内容且未产生工具副作用** | 19 个 case + 独立复核反例 |
| 副作用判定 | 必须同时看**执行台账（已完成）**与**活动信标（已开始执行尚未返回）**——只看台账会在"工具被超时打断"时放行重试，导致工具重复执行 | SP-01d §5.4（第一版实现的真实缺陷） |
| 终态明确 | 成功 `done{terminal:OK}`；取消 `done{cancelled:true}`；失败 `error` 事件带 `code / attempts / partial / toolSideEffect / emittedChars / elapsedMs / rawReason`；三类互斥 | 故障矩阵全部 case |
| 错误码命名 | `UPSTREAM_SILENT_TIMEOUT` / `UPSTREAM_CONNECTION_BROKEN` / `UPSTREAM_STREAM_ERROR`，后缀 `_AFTER_PARTIAL` / `_AFTER_TOOL_SIDE_EFFECT` 标明不可重试原因 | 同上 |
| 取消 | `takeUntil` 在**事件边界**生效；工具内分片协作检查把等待压到 ≤1 个分片 | 协作式 776ms / 非协作式 2590ms 实测 |

**两条硬规范（随 ADR-6 生效，不得淡化）**：

1. **超时阈值必须大于最长工具耗时**（含 HITL 确认门等待）。原因：官方流式循环在工具执行期间**不向下游发送任何内容**（实测 8s 工具在 6s 超时处被误杀、台账 `longTask:OK:5999ms`），且给 SSE 客户端发的确认门心跳**不在 Reactor 流内**，无法续期超时。
2. **TCP 正常 FIN 的静默截断会被判 OK——必须落地完成帧校验**：首包必须为 `start` 事件、终帧必须为显式 `done`/`error` 事件，**缺失终帧一律按断流处理**（实测：内容产出 4 字符后正常 FIN → `terminal=OK`；8 个事件后正常 FIN、无正文 → `terminal=OK, emittedChars=0`，即空回复也被判成功）。

配套：错误/尝试记录、工具台账、取消与重试事件三类证据出口保留（§10）；参数取值见 §13【待裁决】2。回归：SP-01d 全部 **21 用例**入 CI。

### 5.7 模型接入与 reasoning 补丁（ADR-4）

| 项 | 口径 |
|---|---|
| 接入方式 | OpenAI 兼容协议，`base-url` / `model` / `api-key` **全部配置化**；代码与文档禁止笃定单一厂商（DC-01）；兼容服务路径差异（如 `/chat/completions` 与 `/v1/chat/completions`）由配置覆盖 |

### 5.8 渐进式工具披露（FR-5.2：三重防线）

| 防线 | 内容 |
|---|---|
| ① 工具过滤 | 请求时按 **page + step + 任务类型** 过滤 `ToolCallback` 子集（`@Tool` + `ToolRegistry` 元数据：风险级 `ToolRisk`、作用域 `ToolScope`、`needConfirm`、适用页面/步骤） |

### 5.9 AI 与人工同通路（FR-5.5 / D2）

- AI 工具调用与人工操作走**同一服务层、同一校验、同一权限切面**；AI 工具执行前强制携带操作人身份与权限上下文（DC-09 D2、ADR-11）。
- 审批机制在 M2 启用时，AI 通路**自动适用同一审批约束**，不做旁路（FR-3.6 接口预留先行）。
- 审计来源字段区分界面/AI（FR-6.1），两侧同源记录。

## 6. AI ↔ 工作区契约层（DC-06④）

### 6.1 形态（原样吸收 deepseek 契约层接口形态，ADR-10）

| 模块 | 职责 | 关键接口（保形态，TS 化后类型化） |
|---|---|---|
| workspaceBus | AI 面板与工作区之间的唯一通信媒介（事件总线 + 上下文提供者） | `on(topic, fn)` / `off` / `emit(topic, payload)` / `registerContextProvider(fn)` / `getContextSnapshot()` |
| workspaceContract | 唯一知道"AI `ui_event` ↔ 各 store/路由"映射关系的模块 | `initWorkspaceContract()`：注册上下文快照提供者；订阅 `ui_event`，逐个 `type` 分发到**与用户点击相同的 store action**；业务侧变更经 `emit('workspace_changed')` 通知 AI 面板 |
| workspace（抑制器） | AI 驱动的变更不触发"工作区已更新"用户提示 | `suppressWorkspaceEvents()` / `resumeWorkspaceEvents()` |

`ui_event` 已覆盖的语义（蓝本实测通路）：`open_page`、`goto_step`、`select_defs`、`set_conditions` 等；新增语义在契约层集中登记，不散落到视图组件。

### 6.2 双通路单一事实源

- **业务 → AI**：每次 chat / tool-result 请求携带工作区快照摘要（页面、步骤、任务、选择集、**数据版本**，FR-5.4）；细粒度状态由 AI 按需调用查询类工具拉取，避免上下文膨胀。
- **AI → 业务**：AI 动作经契约层分发到同一 Pinia store action，与人工点击路径一致——单一状态源，天然双向同步（FR-5.4）；快照携带数据版本，版本漂移的处置动作（重新拉取/拒执行）见 §13【待裁决】10。

### 6.3 裁剪性要求（硬要求）

| 裁剪 | 期望行为 |
|---|---|
| 去掉 AI 面板（不加载契约层） | 工作区各向导、任务中心**功能完整可用** |
| 去掉工作区（不注册上下文提供者） | AI 对话仍可完成全部操作（后端工具直接执行）；`getContextSnapshot()` 返回空而不报错 |
| 去掉契约层 | 前后端其余部分不受影响（契约层是唯一知晓映射的模块） |

回归用例：双向导走查 + AI 联动 + 裁剪性验证（去 AI 栏业务可用、去工作区 AI 可用）。

### 6.4 契约 bug 根治（Q3）

`isKey` / `key` 字段名不一致（前端发送 `isKey`、后端拒收并 500）在 TS 重写时以**共享类型定义 + 契约测试**根治：字段名以服务端契约为准，前端类型定义单一来源，新增/编辑定义通路纳入 E2E。

## 7. 前端架构（ADR-10）

### 7.1 决策与蓝本

- **选择**：B —— 按 deepseek 前端**功能蓝本** TS 重写（不选"整目录替换 + 原位 TS 化"，避免 JS→TS 混杂债；不选保留 combined 前端，其功能落后且带契约 bug）。

- 推翻条件：S4.4 评估重写工作量 **> 5 人日**时回退方案 A（整目录替换）并分期 TS 化。

### 7.2 目录结构建议（TS 化后）

```
frontend/src/
├─ api/            # 类型化 API 客户端（definitions/data/tasks/jobs/files/ai/audit）
├─ types/          # 与服务端契约对应的共享类型定义（含 isKey 等字段名单一来源）
```

### 7.3 状态管理与 SSE 客户端

| 项 | 口径 |
|---|---|
| 状态管理 | Pinia；"唯一状态源"在 store action，AI 与人工走同一 action（§6.2）；页面组件不直接调 axios |
| AI 流式客户端 | 请求走 `POST` + `fetch` 流式读取（需 POST 语义，`EventSource` 不适用）；按 §5.6 事件面渲染：`start`（首包）→ `text_delta` / `reasoning_delta` / `tool_start` / `tool_call` / `tool_result` / `confirm_request` / `ping` → 终帧 `done` / `error` |
| 完成帧校验（客户端侧） | 缺失首包 `start` 或终帧 `done`/`error` 时按断流处理并提示可重发，**不得渲染为成功**（与 §5.6 硬规范②同一口径） |
| 作业进度 | 独立 SSE 通道（`job_progress` / `job_item_update` / `job_end`），终态补发；轮询作为降级备份 |
| 渲染要求 | 工具卡与文本气泡可混排（一条消息可同时含文本与多个 `tool_call`）；确认卡展示工具名/参数/风险级与倒计时；思考链可折叠（FR-5.1） |
| 表格 | SpreadJS 17.1.5（导出结果在线编辑、单文件下载/打包，FR-2.3） |

### 7.4 页签会话语义（DC-06③ / DC-09 D1）

- `sessionStorage` 存 sessionId：**刷新不丢**、**新页签＝新会话**、**无长期留存**。
- 会话生命周期与 Redis 滑动 TTL（默认 6h）一致；TTL 内刷新/后端重启不丢。
- 不同页签并发对话对后端表现为不同 sessionId（不触发 §5.5 的 409）。
- 契约类型先行：先落 `types/` 与 `api/`，再落 store，最后落视图（Q9 处置）。

## 9. Redis 使用点汇总

五个使用点全部来自 DC-03 落地映射（决策卡附录）。键名凡有实测证据者按实测列出，其余为建议形态（键名与结构随 S4 实现定稿）。

| 用点 | 承载 ADR | 键/形态 | TTL | 说明 |
|---|---|---|---|---|
| AI 会话记忆 | ADR-3 | `chat:mem:<conversationId>`（LIST，JSON 消息）+ `chat:mem:__ids__`（SET 索引） | 主键滑动 6h（仅写刷新）；索引键**无 TTL**，靠惰性清理 | 实测形态；`saveAll` = `DEL`+`RPUSH` 整窗口覆盖写 |
| HITL/前端工具挂起态 | ADR-2 | pending 记录（含 sessionId/runId/toolCallId/状态/决策）+ 续跑所需消息序列 | TTL 覆盖"最长确认等待 + 续跑窗口" | 键名与结构 **S4.2 定稿**（硬性前置工作项，§5.3） |
| 会话并发串行化 | ADR-5 | 分布式锁（同 sessionId 单值门） | 锁 TTL 必须 > 最长工具耗时 + 最大确认门等待 | 建议 `SET key val NX PX ttl` + 唯一值校验释放 |
| SSE 事件/进度跨实例扇出 | ADR-2 / ADR-6 配套 | pub/sub（AI 事件、作业进度、终态补发） | 不适用（pub/sub 无键） | 订阅者离线期间的事件兜底（轮询/终态补发）细节见 §13【待裁决】 |
| 作业取消标志 | ADR-8 | 共享取消标记 + 实例路由信息 | TTL 覆盖作业最长执行时间 | 取消请求必须路由到持有流的实例，否则返回"未找到" |

**淘汰策略与容量（建议，标注【推断】）**：

- 在 `maxmemory` 约 16GiB 的部署背景下，本方案会话类键**全部带 TTL**，因此 `volatile-lru` 类策略可精确命中会话键，避免误淘汰非会话数据；代价是索引键 `chat:mem:__ids__` 不带 TTL、不会被该策略淘汰，可能短暂与主键失配（由惰性清理兜底）。
- `allkeys-lru` 的代价是索引键也可能被淘汰，导致 `findConversationIds()` 结果不全（该接口非业务关键路径）。
- 键数量级：1 会话 ≈ 2 个键（LIST + 索引成员），量级很小；真正的容量风险在**单条消息体大小**（见 §13【待裁决】6）。
- 实际策略与 Redis 自身高可用形态（单点/Sentinel/Cluster）见 §13【待裁决】5。
- 纪律：Redis 按"会话状态、TTL 即可、不要求持久化"定位（DC-02）——不得把任务/作业/审计等权威数据放 Redis。
