## 1. 问题清单（按致命程度排序）

### P1【致命】挂起态续跑协议是全方案多实例叙事的承重墙，却是唯一零实测的核心机制，且违反 Q10 自定的"S3 定案"时点

- **攻击路径**：S4.2 落地前按 §5.3 补测 SP-01ab §5 方案 B → 发现（a）eligibility-predicate 返回 false 意味着"循环续跑权收回业务侧"，与 ADR-1"官方循环"的决策直接冲突（SP-01ab §4 自己实测定位了这一点）；（b）`assistant(tool_calls)` + `role:tool` 消息序列在"重启后重建请求"路径下的合法性/不重放/流式续接任一环节不成立 → 方案 B 失败 → **ADR-2 没有预登记回退**（其推翻条件只写了"Spring AI 提供一等 suspend/resume API"）→ 只能触发 ADR-1 的推翻条件回退自研循环 C，而 C 的可用性证据是空的（见 P5：V7/V8 根本没测过 kimi-k3 的循环）。HITL 与前端工具是 FR-5.3/FR-5.2 的 P0 需求，此处失败即 AI Runtime 多实例形态不可交付。
- **依据**：SP-01ab §5 明文"方案 B【推断，本次未实测】"；§4 明文"若产品需求是……跨实例续跑、可持久化挂起态，官方 1.1.8 没有对应能力"；GLM-R 反例（kill-during-suspend，已放行决策无声丢失）；Q10 处置方向写的是"**S3 技术方案必须定案**：挂起态 Redis 化 + 续跑协议 + 前端可感知的挂起态外置"，而技术方案 §13.2-1 把"续跑协议**最终形态**"推迟到 S4.2 落地前——只定了方向（Redis 化），没定案（协议），与 Q 清单自定时点直接冲突。
- **最小修复建议**：S3 冻结前补一个最小 PoC 实测方案 B（消息序列合法性、不重放、流式续接三件套，工程量参照 SP-01 系列一天级）；给 ADR-2 补推翻条件"方案 B 实测不成立"并预登记回退（候选：`internalToolExecutionEnabled=false` 显式循环——SP-01d V-d2B 已实测该形态可暂停-回灌-恢复，但须先裁决它与 ADR-1"官方循环"口径的一致性并写入 ADR-1）。

### P2【致命】部署形态自相矛盾：§2.1/§2.2 宣称"无状态多副本、任一实例可处理任一请求"，ADR-9 本期却是 H2 单文件库；这一根本矛盾被踢到 S4.1/S4.3

- **攻击路径**：M1 按总体架构部署 2+ 实例 → H2 文件库被多进程并发打开，H2 文件锁直接拒绝后续实例启动（或库损坏）→ 多实例部署在本期物理不可能；退而单实例部署 → DC-03（多实例）不成立，§9 全部五类 Redis 机制（记忆共享、挂起外置、分布式锁、pub/sub 扇出、取消路由）在生产形态下**全部不可验证**，§3.3 出口标准"多实例并行用例通过"无法执行，§1.1 技术目标"多实例无状态"沦为纸面。两头都输。
- **依据**：DC-03（部署形态为分布式多实例，生效）；ADR-9 推翻条件自认"如多实例共享库——届时提前切换 MySQL"；技术方案 §2.1 同一张表内并列"实例内不留权威状态（DC-03）"与"H2 文件库（单实例）"；§13.2-11 把"M1 演示形态的实例数与数据库关系"留到 S4.1/S4.3；需求冻结版 §5 并发"多实例部署架构保留水平扩展能力"。
- **最小修复建议**：S3 内二选一并写死：① M1 明确"单实例部署 + 多实例机制作为 M2 生效的代码前置"，同步把 §1.1/§2.2 的"无状态多副本"改为目标态而非本期形态，多实例用例移入 M2 出口；② M1 直接切 MySQL（等于触发 ADR-9 推翻条件，需重排 §3.3 演进路径）。不允许架构图（§2.2）与数据层（§3）各说各话进入 S4。

### P3【高】多实例 SSE 扇出（Redis pub/sub）零实测，且"订阅者离线兜底"在待裁决清单里根本无对应项

- **攻击路径**：负载均衡下用户 SSE 连在实例 B，作业/AI 轮跑在实例 A → A 经 pub/sub 广播进度与 AI 事件 → B 与 Redis 之间一次短暂重连/抖动 → 事件永久丢失（pub/sub 是 fire-and-forget）→ 前端进度停滞或按 §5.6 完成帧校验判为断流，而客户端重连策略又未定（待裁决 12）→ 用户只能整轮重来。跨实例扇出没有任何 spike 覆盖（SP-01c 只测了记忆键共享；sp01ab/d 全部单实例）。
- **依据**：§2.2 要点 2 断言扇出形态；§9 表格 SSE 扇出行自认"订阅者离线期间的事件兜底（轮询/终态补发）细节见 §13【待裁决】"——**但 §13.2 的 12 项中没有任何一项对应 pub/sub 兜底**，违反技术方案自己的承诺"凡决策未覆盖者一律在 §13 标【待裁决】"（文档头注）。
- **最小修复建议**：§13.2 补登第 13 项"pub/sub 离线兜底机制"（终态轮询/补发 + 客户端重挂）；S4.2 前补双实例扇出 PoC（事件丢失率 + 兜底生效路径）。

### P4【高】ADR-5 的 409 单值门在"刷新/断线"场景形成用户死锁，锁 TTL 与实例崩溃/轮存活的相互作用未设计

- **攻击路径 A**：用户在 AI 轮进行中刷新页面（DC-06③：sessionStorage 保 sessionId，**刷新不丢**）→ 新页签发起下一轮 → 409 → 客户端重连/reattach 端点不存在（待裁决 12 未定），用户只能干等到轮结束或超时。§5.5"正常单页签使用下不触发"的断言恰恰漏掉了 DC-06③ 自己定义的刷新语义。
- **攻击路径 B**：实例崩溃/长工具/慢模型使一轮实际时长超过锁 TTL（锁 TTL 须 > 最长工具耗时 + 最大确认门等待，§11.1）→ 锁过期而轮未完 → 第二轮进入 → **Q11 的 8 并发丢消息场景以双请求形态复现**（静默数据损坏，7:8 失配历史永久驻留）。反向：轮已死但锁未过期 → 会话被锁到 TTL 自然耗尽。锁的续期（watchdog）、轮终态与锁释放的联动、"持锁者已死"的检测，方案均未提及。
- **依据**：§5.5、§11.1 配置表、Q11/GLM-R 反例、SP-01ab §2.4-6（409 已实测）、待裁决 12。
- **最小修复建议**：设计按 runId 的 SSE reattach 端点（409 响应携带进行中轮的 runId 供前端重挂）；锁增加续期与"轮终态 → 主动释放"联动；把"锁过期早于轮结束"列为 §12.2 回归用例（双请求交错压测 0 丢消息）。

### P5【高，证据诚实性】两处【实测】级引用与原始记录不符：ADR-1 备选 C 的"可用性佐证"是空的；ADR-8 的"V5/V6 实测"覆盖面远超实际核验范围

- **断言一（ADR-1）**："C 作为预登记备选——其可用性已由 **V7/V8** 佐证"。核对原始记录：**V8（kimi 作业幂等核验）明文"本核验项未发起任何 AI 请求"**——它测的是作业幂等，与 AI 循环无关；V7 是绕过后端直连 API 的补丁归因核验，同样没有运行过 kimi-k3 的受控薄 Loop。该备选路线的可用性证据**不存在**。若 S4.2 按 ADR-1 的推翻条件回退 C，是在无证据支撑下切换到一条未验证路线——且 C 恰是 P1 失败时唯一逃生通道。
- **断言二（ADR-8 / 技术方案 §4.3）**："继承（combined 生产机制，35 次迭代淬炼，**V5/V6 实测**）：任务中心、事务后异步、同任务同 kind 幂等、僵尸恢复、取消注册表、终态补发"。核对 V5/V6 原文：实测覆盖的只有乐观锁冲突（V5）、僵尸恢复含 PENDING 残留（V6）、单事务语义（V6 侧证）；**取消注册表**（SP-01d 测的是 spike 自建 CancellationRegistry，不是 combined 的）、**终态补发**（V1~V9 全部核验中零覆盖）、**任务中心/服务端分页**（无核验）三项不在 V5/V6 范围内。另外"35 次迭代淬炼"的出处（分支评价报告）在同一套 merge 文档里被明确定性为【推断】分数且"回归全靠人工"。
- **依据**：V8 §2 环境表 AI Key 行；V5/V6 全文（无"终态补发/任务中心/取消注册表"任何核验记录）；GLM-R 对 SP-01c 15 vs 25 的同类口径批评，说明计数/引用纪律是本体系的既知弱点。
- **最小修复建议**：ADR-1 删除 V7/V8 引用或降级为【推断】并补"备选 C 需先补 PoC 方可启用"前置；ADR-8/§4.3 把"V5/V6 实测"收窄为逐机制标注（实测/未测），对终态补发、取消注册表、任务中心补核验或标待验。

### P6【高】Redis 自身是新增单点，且其故障模式与 Q10 硬性前置同构，却未进入 §13.1 风险表

- **攻击路径**：Redis 重启（DC-02：不要求持久化、AOF 关闭）→ 会话记忆、**挂起态（含已放行未执行的人工决策）**、分布式锁、取消标志同时全灭——这正是 GLM kill-during-suspend 反例的 Redis 级重演：用户刚批准的删除操作决策无声消失，无任何痕迹。§5.3 把外置当作"决策不再丢"的答案，但外置目的地本身不持久化，问题的严重度只是从"实例死"扩大到"Redis 死"。Redis 抖动期间分布式锁失效还会让 P4 的并发丢消息复现。§13.1 风险表六条中**没有一条是 Redis 故障**；HA 形态（单点/Sentinel/Cluster）推迟到 S4.3（待裁决 5）。
- **依据**：DC-02（Memurai AOF 关闭实测）；§9 五个使用点全部压在 Redis 上；GLM-R 反例 1；§13.1 逐条对照。
- **最小修复建议**：§13.1 增补"Redis 故障/重启：会话与挂起态全丢、锁失效"风险条目，明确降级行为（前端可感知挂起丢失、决策可重做、锁失败-开放或失败-关闭二选一）；待裁决 5 的裁定时点提前到 S3/S4.1——它是 Q10 硬性前置成立的隐含前提。

### P7【中】AI 会话与 HITL 确认门没有会话所有权绑定设计——跨用户读会话/替他人批准破坏性操作

- **攻击路径**：sessionId 存 sessionStorage、无与认证主体的绑定设计；若按 spike 形态实现端点（`GET /api/chat/{sid}/history`、`POST /api/confirm`、`POST /api/frontend-tool-result`），任何登录用户可枚举/读取他人会话内容，并可**替他人批准确认门**——而确认门保护的恰是 `delete_config` 这类敏感操作。§8 权限切面只覆盖 Service 层业务操作，AI 会话端点的授权不在其内。"操作人"审计字段在"会话发起者 ≠ 确认者"时语义未定义。
- **依据**：§8.1（切面在 Service 层收口，未提会话所有权）；spike 三卡的端点形态；FR-5.3（破坏性操作必须经人确认——是"发起者本人"确认还是"任何操作员"确认，需求未定义，方案也未定义）。
- **最小修复建议**：§5.2/§8 增补"sessionId ↔ 认证用户"绑定与所有权校验；确认/回灌请求强制校验会话归属；§12.2 增加越权用例（他人 sessionId 读取/确认/回灌 100% 拒绝并审计）。

### P8【中】挂起的线程模型自相矛盾（虚拟线程 vs boundedElastic），且长确认门留在流式管道内，使断流发现延迟与确认门等待时长线性绑定

- **攻击路径 A**：§2.1 宣称"虚拟线程开启"，§5.2 却规定流式挂起用 `subscribeOn(boundedElastic)`（SP-01ab 实测写法）。boundedElastic 是固定容量调度器（默认 10×CPU 线程 + 有界队列），长确认门挂起每人占一线程：并发挂起到数十路即饱和排队，全部 AI 流式（含无关会话）被拖死。挂起并发上限压测被推迟（待裁决 2），且方案未认识到"开虚拟线程"与"boundedElastic 承载"是两套并行的线程模型。
- **攻击路径 B**：SP-01d §6.1 明确建议"若要支持人审等待远超 90s，**必须把确认门移出流式管道**"；技术方案选择了相反分支——确认门留在管道内、用"超时 > 最长确认等待"兜底。代价：真实断流的发现延迟 ≥ 最大确认门等待时长。若 hitl-timeout 配到分钟级（人审现实），一次上游挂死要等几分钟才报错，且重试预算被同步拉长。该取舍未在 §13.1 披露。
- **依据**：§2.1/§5.2/§11.1；SP-01ab §2.4-1/3；SP-01d §2.1④、§6.1。
- **最小修复建议**：S3/S4.2 明确挂起线程模型（虚拟线程承载阻塞挂起，或 boundedElastic + 容量规划 + 挂起上限三件套一起定）；把"确认门在管道内 vs 移出管道"的取舍写入 §13.1 并给出 hitl-timeout 上限约束（超过该值即转异步确认模式）。

### P9【中】ADR-8 修正③自相矛盾：取消标志 Redis 化（隐含轮询可见）与"取消请求必须路由到持有流的实例"两机制叠加且路由机制无设计、无实测

- **攻击路径**：实现者面对两条同时生效的要求——若取消标志已 Redis 化且持有实例在事件/分片边界检查（SP-01d 协作式模型），路由本无必要；若要低延迟直通知，则需实例注册表/定向通道，而"路由信息"（§9）只有四个字，无键结构、无实例存活检测、无路由失败降级。多实例取消（SP-01d V-d3 自认缺口）至今零实测。路由失败时返回"未找到"的要求，在实例崩溃瞬间会把用户的取消请求变成永久的"未找到"。
- **依据**：§4.3 修正③、§9 取消标志行、SP-01d §4.3。
- **最小修复建议**：二选一定死——"Redis 标志为准（轮询延迟 ≤1 分片）+ 直通知仅作加速、失败不视为错误"；补双实例取消 PoC。

### P10【低】SP-01d 用例计数口径三处不一致："21 用例"无法追溯到任何清单，实际附件为 23 个

- **攻击路径**：CI 门禁按字面实现"SP-01d 全部 21 用例入 CI"（ADR-6/ADR-12/§5.6 末/§12.2），而附件 B 实含 **19** 个 vd1 case（vd1-baseline…vd1-truncate-rst，逐一清点）、附件 C 2 个（vd2-spi-dup、vd2-fronttool）、附件 D 2 个（vd3-coop-cancel、vd3-hard-cancel），合计 **23**；同文档 §5.6 表内又写"19 个 case"。哪 21 个？无清单可查。鉴于 SP-01c 已发生过 15 vs 25 的同类问题（GLM-R §1.3-2 指出），这是系统性计数纪律缺陷，直接威胁"门禁有效性验证"（ADR-12）的可审计性。
- **最小修复建议**：以附件为准出一份 23 条编号清单，全文统一引用清单号。

### P11【低】被否决方案的坑 → 回归用例转换基本完整（12 张 ADR 主线全部落地），但有四处遗漏

## 5. 总结论

**不通过（暂缓 S3 冻结，限期整改后重审）。**

理由：两项致命问题均属"S3 必须定案而未定案"，不是"S4 实现细节"——

1. P1：方案的多实例核心（挂起态续跑协议）建立在未实测的【推断】上，无预登记回退，备选路线的证据引用是空的，且违反 Q10 自定的"S3 定案"时点；
2. P2：总体架构（无状态多副本）与数据层（H2 单文件库）在 M1 期间自相矛盾，被推到 S4 裁决。

重审通过条件（按序）：

- 【条件 1】补方案 B 最小 PoC（消息序列合法性/不重放/流式续接），结果回填 ADR-2，并为 ADR-2 补"方案 B 失败"推翻条件与预登记回退（对应 P1）；
- 【条件 2】S3 内裁决 M1 实例数与数据库口径，消除 §1.1/§2.2 与 ADR-9 的矛盾（对应 P2）；
- 【条件 3】修正 ADR-1（V7/V8 引用）与 ADR-8（V5/V6 覆盖面）的证据引用，按逐机制重标【实测/未测】（对应 P5）；
- 【条件 4】§13.2 调整：#1、#7、#11 提前到 S3，#5 的 HA 半项与 #12 的方向项给出 S3 级方向；补登 pub/sub 兜底项（对应 §2、P3）；
- 【条件 5】§13.1 风险表增补 Redis 故障条目（对应 P6）。

P3/P4/P7/P8/P9/P10/P11/P12 可随 S4 落地整改，但 P4（409/reattach）、P7（会话所有权）、P8（线程模型）须在 S4.2 开工前有设计文档。若五项条件在约定整改期内完成，本报告不反对基于整改后版本直接进入重审——该方案的证据工程化水准（V 记录 + spike 三卡 + 独立复核）远高于常见基线，问题集中在"最后一公里"的引用纪律与自定裁决时点的执行力上。
