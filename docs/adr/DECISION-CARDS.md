## ADR-1 AI Runtime 主循环：Spring AI 官方 ChatClient 循环

- **选项**：A. Spring AI 官方循环（ChatClient + ToolCallingManager）／B. 自研手工协议循环（main/combined 分支方式）／C. kimi-k3 受控薄 Loop
- **选择**：A
- **证据等级**：【实测】（V3 22/22 E2E、SP-01ab/c/d 三卡、GLM-R 复核一致）
- **理由**：官方循环在三条官方路径（call/stream/工具循环）上承载了前端工具与 HITL（SP-01ab 双路径各 11/11 断言）；ChatMemory/Advisor/工具管理均为官方抽象，符合 DC-05"官方能力优先"，框架升级成本最低；B（1145 行巨型类手工协议）与 C 的维护成本与升级风险已被评审确认（01 报告 §2.1/§2.6）。
- **被否决方案的坑**：B 手工拼 tool_calls 易在模型行为变化时整片失效（转化为回归用例：模型升级冒烟套件）；C 作为**预登记备选**——若官方循环在 S4.2 整合时出现 SP-01 未覆盖的硬阻断，回退 C（其可用性已由 V7/V8 佐证），本卡即触发推翻条件。
- **推翻条件**：S4.2 出现 SP-01 三卡未覆盖且无法绕行的官方循环缺陷（须有新实测证据）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-2 HITL 确认门与前端工具：ToolCallingManager 阻塞挂起 + 挂起态 Redis 外置

- **选项**：A. ToolCallingManager 扩展点阻塞挂起／B. Advisor/ChatClient 层拦截／C. ToolExecutionEligibilityPredicate 抑制
- **选择**：A（挂起实现）＋ 挂起态必须 Redis 外置（多实例前提）
- **证据等级**：【实测】（SP-01ab 三结局 6/6/7/7/9/9、挂起期 15 帧心跳；B/C 不可行为【推断】+依据，见 SP-01ab §4）
- **理由**：SP-01ab §4 卡点定位证明唯一可行落点是 ToolCallingManager；挂起期 SSE 心跳保活已实测。**但阻塞挂起态仅存于进程内存**（Q10）：GLM-R 反例证实挂起期进程死亡连已放行的人工决策都无声丢失。因此生产形态 = 挂起请求写入 Redis（pending 状态 + TTL）＋ 前端可感知的挂起态展示 ＋ 实例恢复后的续跑协议（SP-01ab §5 方案 B 为起点）。S4.2 落地时该外置为**硬性前置工作项**，不得降级。
- **被否决方案的坑**：纯内存挂起在多实例下会话黏滞、重启丢决策（GLM-R kill-during-suspend 实测）；转化为回归用例：挂起期重启续跑测试。
- **推翻条件**：Spring AI 后续版本提供一等 suspend/resume API 时重审（可简化实现）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-3 会话记忆：官方 SPI 自实现 RedisChatMemoryRepository（Redis LIST + 滑动 TTL）

- **选项**：A. 实现 1.1.8 官方 ChatMemoryRepository SPI（Redis LIST + EXPIRE 滑动 TTL）／B. 官方 2.0 RedisChatMemoryRepository backport／C. H2 持久化（deepseek 分支方式）／D. JVM 内存
- **选择**：A（TTL 默认 6h，maxMessages 窗口由官方 MessageWindowChatMemory 裁剪）
- **证据等级**：【实测】（SP-01c 五项全过 + GLM-R 复现一致；BOM/central 元数据证实 1.1.8 无官方实现；官方 2.0 需 RedisJSON/RediSearch 模块而本机与生产基线无此模块）
- **理由**：DC-02 已定 Redis 不持久化路线；官方 SPI 扩展不违反 DC-05（官方能力在 1.1.8 不存在）；SP-01c 实测多实例共享、TTL 到期消失、重启恢复、7 轮工具无 400；saveAll=整窗口覆盖写语义与官方 2.0 对齐。
- **被否决方案的坑**：B 引入模块依赖（Redis Stack）为生产新增运维约束且 backport 有升级漂移风险；C 违反 DC-02；D 多实例下会话漂移（DC-03）。回归用例：TTL 到期会话消失、双实例接续对话。
- **推翻条件**：升级 Spring AI ≥2.0 且生产 Redis 具备 JSON/Search 模块时，可切换官方实现（接口不变，调用方无感）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-4 模型接入：OpenAI 兼容协议全配置化 + reasoning 兼容补丁保留

- **选项**：A. Spring AI OpenAI 兼容接入（base-url/model/key 全配置）+ ReasoningAwareOpenAiChatModel 补丁／B. 锁定 DeepSeek 专用接入／C. 去掉补丁
- **选择**：A
- **证据等级**：【实测】（DC-01；V7 修正归因：deepseek-flash 不强制 reasoning_content 回填（57 次全 200），deepseek-v4-pro 稳定 400 且报错原文逐字吻合；补丁实现对 flash 无害）
- **理由**：DC-01 要求可接入任意 OpenAI 兼容服务；补丁是接入推理类模型（v4-pro 及未来同类）的必要保险，对非推理模型无副作用；kimi-k3 的补丁实现（同名包 Override 单方法）侵入面最小，升级后评审移除的约束写入 Javadoc。
- **被否决方案的坑**：B 违反 DC-01；C 在切换推理模型时直接 400（V7 报错原文存档）。回归用例：v4-pro 思考模式 7 轮工具调用（接入该模型时激活）。
- **推翻条件**：Spring AI 官方修复 reasoning_content 回填（评审补丁移除）；或确认永不接入推理类模型（业务方裁决）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-5 会话并发控制：同 sessionId 串行化（会话级单值门 + 分布式锁）

- **选项**：A. 会话级单值门（同 sessionId 并发第二轮返回 409）＋ Redis 分布式锁（多实例）／B. 不控制／C. 队列化并发请求
- **选择**：A
- **证据等级**：【实测】（Q11：GLM-R 反例——8 并发必丢 1 条消息且 7:8 失配历史永久驻留；sp01d 同 sessionId 并发两轮内容互相拼接；sp01ab 的 409 单值门模型已实测有效）
- **理由**：并发写丢消息对用户不可见且无法自愈，属静默数据损坏；409 模型在 SP-01ab 已验证不影响挂起中的那一轮；页签级会话（DC-06③）使 409 在正常单页签使用下不触发，体验无损。
- **被否决方案的坑**：B 即 GLM-R 实测的丢消息/串写；C 改变交互语义（用户期望即时响应）且实现复杂度高。回归用例：同 sessionId 并发 8 路压测（必须 0 丢消息）。
- **推翻条件**：产品确认需要同会话多端同时书写（转 C 并重新评估）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-6 SSE 韧性策略：每轮重建请求 + 双超时 + 重试三条件

- **选项**：A. 官方 RetryTemplate／B. Reactor .retry() 重订阅／C. 自研：每轮重建请求 + 双超时（首包/包间）+ 重试三条件（次数上限/总预算/未产出且无副作用）
- **选择**：C（官方 API 组装，策略自研——官方机制在流式场景已被实测证伪）
- **证据等级**：【实测】（SP-01d：A 只覆盖非流式；B 重订阅必抛 IllegalStateException 且不发第二次请求；ChatModel 层重订阅会重发已产出内容"我是我是"）
- **理由**：流式 advisor 链一次性（字节码+实测）；C 的三条件门禁经 SP-01d 全部故障注入用例与 GLM-R 反例（2s 超时误杀 5s 工具）验证，副作用信标可正确阻止误重试。**两条硬规范随本卡生效**：① 超时阈值必须大于最长工具耗时（工具执行期下游零事件）；② TCP 正常 FIN 的静默截断会被判 OK——必须落地完成帧校验（首包 start 事件 + 显式 done/error 终帧），缺失终帧一律按断流处理。
- **被否决方案的坑**：A/B 见上（实测证伪）；无完成帧校验 = 静默数据丢失。回归用例：SP-01d 全部 21 用例入 CI。
- **推翻条件**：Spring AI 官方支持流式断流重试语义时重审。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-7 发布语义：glm 范围内替换（重写 combined 整体替换）+ 乐观锁冲突检测保留

- **选项**：A. glm 范围内替换（按配置项×范围替换 PUBLISHED）／B. combined 按配置项整体替换／C. 两者折中
- **选择**：A；combined 的乐观锁冲突检测（OPTIMISTIC_FORCE_INCREMENT + baseVersion 快照比对）原样保留叠加
- **证据等级**：【实测】（V2 双向对称实验逐字段比对；V5 冲突提示文案逐字一致、版本强制递增）
- **理由**：多范围并存时整体替换有误伤风险（V2 实测范围内替换互不误伤）；冲突检测是发布安全底线（V5）；手册纪律：冲突时重写而非折中。
- **被否决方案的坑**：B 多地区/项目并存互伤（V2 反证）；折中方案语义含糊不可测试。回归用例：V2 双范围发布实验、V5 并发发布冲突实验，均转为自动化。
- **推翻条件**：业务确认配置项永远单范围生效（事实不成立，三层级是需求）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-8 作业治理：继承 combined 任务中心 + 三项修正

- **选项**：A. 整体继承 combined（任务中心/僵尸恢复/取消注册表）＋修正／B. 重建
- **选择**：A；修正项：① StaleJobRecoveryRunner 扫描范围必须含 PENDING（Q6：崩溃残留实为 PENDING 而非 RUNNING）；② 恢复动作与任务状态联动策略在 S4.3 定（Q5：当前只改 jobs 表，任务态长期不一致）；③ 取消标志 Redis 化 + 取消请求路由到持有流的实例（SP-01d V-d3 多实例缺口，DC-03）
- **证据等级**：【实测】（V5/V6、SP-01d V-d3、GLM-R）
- **理由**：combined 的生产机制（乐观锁/僵尸恢复/取消/事务后异步）经 35 次迭代淬炼且 V5/V6 实测符合；三项修正均有实测出处。
- **被否决方案的坑**：B 丢弃 35 次联调修复记录（01 报告：demo 与真实的分水岭即这些机制）。回归用例：kill 恢复（含 PENDING 残留）、执行中取消。
- **推翻条件**：S4.3 行为对照发现 combined 作业模型与新骨架不兼容度 >5%。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-9 数据层与迁移：Flyway + H2 文件库（本期）→ MySQL（M2）

- **选项**：A. Flyway 版本化迁移 + 本期 H2 文件库／B. ddl-auto／C. 本期直接 MySQL
- **选择**：A；MySQL 切换列 M2（S2 已裁剪范围）
- **证据等级**：【实测】（V9 三实验幂等；Q1 边界：已有非空 schema 无历史表时 baseline 跳迁移致启动失败——main-v2 一律清库初始化，切 MySQL 时迁移演练必须覆盖此场景）
- **理由**：Flyway 是六分支中唯一经实测的迁移治理能力（V9）；H2 文件库满足本期单库演示与测试，MySQL 在 M2 随生产化切换。
- **被否决方案的坑**：B 无版本治理不可进生产；C 把数据库切换风险叠加进 M1 合流（违反分层推进）。回归用例：清库两次启动、schema validate。
- **推翻条件**：M1 期间出现 H2 不支撑的需求（如多实例共享库——届时提前切换 MySQL）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-10 前端架构：Vue 3 + TS 重写（deepseek 前端为功能蓝本）

- **选项**：A. deepseek 前端整目录替换 + 原位 TS 化／B. 按 deepseek 功能蓝本 TS 重写／C. 保留 combined 前端
- **选择**：B（蓝本重写）；workspaceBus + workspaceContract 契约层原样吸收（双通路解耦，DC-06④）
- **证据等级**：【实测】（Q9：deepseek 前端纯 JS——10 js/0 ts/11 vue；DC-05 TS 约束；Q3：combined 前端与后端存在 isKey/key 契约 bug；V3 佐证 deepseek 前端功能通路完整）
- **理由**：DC-05 禁纯 JS，原位改写 11 个 vue + 10 个 js 的 TS 化成本与重写相当，重写可得干净类型设计；契约层是 DC-06④ 的载体，必须保留其接口形态；Q3 的契约 bug 在重写时以类型定义根治。
- **被否决方案的坑**：A 留下 JS→TS 混杂债；C 继承契约 bug 且功能落后（Q3/Q4）。回归用例：双向导走查 + AI 联动 + 裁剪性验证（去 AI 栏业务可用）。
- **推翻条件**：S4.4 评估重写工作量超阈值（>5 人日）时回退 A 并分期 TS 化。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-11 安全与审计：表单登录 + RBAC 3 角色 + 审计从简

- **选项**：按 DC-09 A2/A4/A6 执行（表单登录+BCrypt；操作员/管理员/只读审计；审计表+检索页）
- **选择**：同左；AI 工具调用强制携带操作人身份与权限上下文（FR-5.5/D2：AI 与人同通路同校验）
- **证据等级**：【推断】（DC-09 为业务方授权裁决；实现方案为常规 Spring Security 实践）
- **理由**：本期无 IdP 对接需求（A6）；三角色覆盖操作/管理/审计最小闭环；审计从简满足留痕底线（A4）；AI 通路越权拒绝是 FR-5.5 的 P0 要求，实现上 AI 工具执行前经同一权限切面。
- **被否决方案的坑**：OIDC 本期过度设计；五角色与细粒度数据权限无真实用户支撑。回归用例：越权访问（含 AI 通路）100% 拒绝并审计（§6-3 验收标准）。
- **推翻条件**：真实终端业务方提出 SSO/细粒度权限需求（触发 DC-09 重审）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-12 测试策略：glm 金字塔移植 + E2E 脚本 + 行为基线自动化 + 门禁注入验证

- **选项**：A. glm 38 JUnit 移植扩充 + deepseek 22 E2E 移植 + S4 行为基线转自动化／B. 只保 E2E／C. 只保单测
- **选择**：A；CI 门禁必须通过注入缺陷验证（S5：故意提交含已知缺陷的 PR 确认门禁能拦住）
- **证据等级**：【实测】（V1 38/38 全绿；V3 22/22 双轮；S0.5 全部行为基线文档化）
- **理由**：glm 套件是唯一可回归资产（V1）；E2E 脚本是唯一一键端到端（V3）；行为基线自动化是红线 3 的延续；门禁有效性验证防止"测试覆盖假象"（0.5 偏差预警）。
- **被否决方案的坑**：B 数据校验深度不足（V3 vs V1 对比结论）；C 无端到端保障。目标：≥80 JUnit + 25 E2E 进 CI（S5 出口）。
- **推翻条件**：无（测试投入只增不减）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06
