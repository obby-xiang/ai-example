## ADR-1 AI Runtime 主循环：Spring AI 官方 ChatClient 循环

- **选项**：A. Spring AI 官方循环（ChatClient + ToolCallingManager）／B. 自研手工协议循环（main/combined 分支方式）／C. kimi-k3 受控薄 Loop
- **选择**：A
- **证据等级**：【实测】（V3 22/22 E2E、SP-01ab/c/d 三卡、GLM-R 复核一致）
- **理由**：官方循环在三条官方路径（call/stream/工具循环）上承载了前端工具与 HITL（SP-01ab 双路径各 11/11 断言）；ChatMemory/Advisor/工具管理均为官方抽象，符合 DC-05"官方能力优先"，框架升级成本最低；B（1145 行巨型类手工协议）与 C 的维护成本与升级风险已被评审确认（01 报告 §2.1/§2.6）。
- **被否决方案的坑**：B 手工拼 tool_calls 易在模型行为变化时整片失效（转化为回归用例：模型升级冒烟套件）；C 为**预登记备选**——【修订：CH-P5】**C 的可用性目前无实测支撑**（V7 为直连 API 补丁归因核验、V8 核验记录明文"未发起任何 AI 请求"，均未运行过 kimi-k3 的 AI 循环；v2.1 原文"其可用性已由 V7/V8 佐证"为引用错配，已更正）。**启用 C 前必须先补其最小 PoC**，未补 PoC 不得作为回退启用。
- **推翻条件**：S4.2 出现 SP-01 三卡未覆盖且无法绕行的官方循环缺陷（须有新实测证据）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-2 HITL 确认门与前端工具：ToolCallingManager 阻塞挂起 + 挂起态 Redis 外置

- **选项**：A. ToolCallingManager 扩展点阻塞挂起／B. Advisor/ChatClient 层拦截／C. ToolExecutionEligibilityPredicate 抑制
- **选择**：A（挂起实现）＋ 挂起态必须 Redis 外置
- **证据等级**：【实测】（SP-01ab 三结局 6/6/7/7/9/9、挂起期 15 帧心跳；B/C 不可行为【推断】+依据，见 SP-01ab §4。**【SP-02 补测】** 挂起态外置 + 续跑协议三件套全部成立：E1 16/16、E2 8/8、E3 9/9、E4 5/5、E6 8/8 共 46/46 断言，全部 12 次模型请求零 400——见 `docs/spike/SP-02-决策卡.md`）
- **理由**：SP-01ab §4 卡点定位证明唯一可行落点是 ToolCallingManager；挂起期 SSE 心跳保活已实测。**但阻塞挂起态仅存于进程内存**（Q10）：GLM-R 反例证实挂起期进程死亡连已放行的人工决策都无声丢失。因此生产形态 = 挂起请求写入 Redis（pending 状态 + TTL）＋ 前端可感知的挂起态展示 ＋ 实例恢复后的续跑协议（SP-01ab §5 方案 B 为起点）。S4.2 落地时该外置为**硬性前置工作项**，不得降级。**【SP-02 实测】** 该协议成立且对两种循环形态均适用；**两条硬规范随之生效**：① **外置先于阻塞**（进入挂起前必须先写 Redis，含 `assistant(tool_calls)`；进程内等待对象只做唤醒）；② **续跑必须重建完整历史**（官方循环自身的"工具后续跑请求"只带 `assistant+tool`，会丢掉 system/user——SP-02 §7.1 字节码+报文双证）。
- **【修订：CH-P1】续跑协议实测前置（已完成）**：SP-02 最小 PoC 实测三件套（`assistant(tool_calls)`+`role:tool` 重建请求合法性／不重放／流式续接）**逐项成立**，条件 1 可关闭；未闭合项 = "续跑后再发起外部工具调用是否在新进程内再次挂起"（SP-02 §6.1，模型行为导致 4 次尝试均未构造成——前 3 次失败即停、第 4 次仅留档，建议转 S4 用例 `TC-AI-03b`）。
- **【修订：CH-P8】线程模型定案（再修订：DC-12；三重修订：重审 N1）**：**禁用虚拟线程**（DC-12）。长挂起统一由**专用有界平台线程池**承载（池容量 = 挂起并发上限，可配置；超限快速失败拒绝（503 SUSPEND_POOL_SATURATED，与 ADR-5 的 409 会话并发语义区分），为准入闸门）；**注意（重审 N1 实测纠正）**：BLOCKING 形态下每次挂起实际占用**专用池线程 1 条 + boundedElastic 线程 1 条**（Spring AI 1.1.8 `OpenAiChatModel.internalStream` 的工具执行分支硬编码 `subscribeOn(boundedElastic())`，无法移出——SP-02 §4.1 字节码证据），容量联动约束为"专用池容量 × 2 ≤ boundedElastic 容量"，压测范围须含此联动（§13.2 #2）。确认门保留在流式管道内，hitl-timeout 设上限约束，超过上限的场景转异步确认模式（M2）；断流发现延迟与确认门等待绑定的取舍记入风险表。
- **被否决方案的坑**：纯内存挂起在多实例下会话黏滞、重启丢决策（GLM-R kill-during-suspend 实测）；转化为回归用例：挂起期重启续跑测试。
- **推翻条件**：① Spring AI 后续版本提供一等 suspend/resume API 时重审；② 【修订：CH-P1/SP-02】**方案 B 实测成立**（未触发预登记回退）；原"方案 B 不成立时启用 `internalToolExecutionEnabled=false` 显式循环"改写为：**该形态与"自定义 predicate 对本轮返回 false"在同一个判定点、二者等价**（SP-02 §4.3 实测），从"回退选项"降级为"可选形态"；仅当出现 SP-02 §6.1 未测项实测失败、或需要"请求边界暂停/不占线程"时才启用，启用时须同步重审 ADR-1 口径（该形态与"官方循环"的关系写入 ADR-1）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-3 会话记忆：官方 SPI 自实现 RedisChatMemoryRepository（Redis LIST + 滑动 TTL）

- **选项**：A. 实现 1.1.8 官方 ChatMemoryRepository SPI（Redis LIST + EXPIRE 滑动 TTL）／B. 官方 2.0 RedisChatMemoryRepository backport／C. H2 持久化（deepseek 分支方式）／D. JVM 内存
- **选择**：A（TTL 默认 6h，maxMessages 窗口由官方 MessageWindowChatMemory 裁剪）
- **证据等级**：【实测】（SP-01c 五项全过 + GLM-R 复现一致；BOM/central 元数据证实 1.1.8 无官方实现；官方 2.0 需 RedisJSON/RediSearch 模块而本机与生产基线无此模块）
- **理由**：DC-02 已定 Redis 不持久化路线；官方 SPI 扩展不违反 DC-05（官方能力在 1.1.8 不存在）；SP-01c 实测多实例共享、TTL 到期消失、重启恢复、7 轮工具无 400；saveAll=整窗口覆盖写语义与官方 2.0 对齐。

- **推翻条件**：升级 Spring AI ≥2.0 且生产 Redis 具备 JSON/Search 模块时，可切换官方实现（接口不变，调用方无感）。

## ADR-4 模型接入：OpenAI 兼容协议全配置化 + reasoning 兼容补丁保留

- **选项**：A. Spring AI OpenAI 兼容接入（base-url/model/key 全配置）+ ReasoningAwareOpenAiChatModel 补丁／B. 锁定 DeepSeek 专用接入／C. 去掉补丁
- **选择**：A
- **证据等级**：【实测】（V7 修正归因：deepseek-flash 不强制 reasoning_content 回填（约 57 次全 200），deepseek-v4-pro 稳定 400 且报错原文逐字吻合——Challenger 抽-1 复核属实；补丁实现对 flash 无害）+【指令】DC-01

- **被否决方案的坑**：B 违反 DC-01；C 在切换推理模型时直接 400（V7 报错原文存档）。回归用例：v4-pro 思考模式 7 轮工具调用（接入该模型时激活）。

## ADR-5 会话并发控制：同 sessionId 串行化（会话级单值门 + 分布式锁）

- **选项**：A. 会话级单值门（同 sessionId 并发第二轮返回 409）＋ Redis 分布式锁（多实例）／B. 不控制／C. 队列化并发请求
- **选择**：A
- **证据等级**：【实测】（Q11：GLM-R 反例——8 并发必丢 1 条消息且 7:8 失配历史永久驻留；sp01d 同 sessionId 并发两轮内容互相拼接；sp01ab 的 409 单值门模型已实测有效）
- **理由**：并发写丢消息对用户不可见且无法自愈，属静默数据损坏；409 模型在 SP-01ab 已验证不影响挂起中的那一轮；页签级会话（DC-06③）使 409 在正常单页签使用下不触发，体验无损。
- **【修订：CH-P4】刷新/断线与锁生命周期**：① 409 响应必须携带进行中轮的 runId，并提供 **SSE reattach 端点**（前端按 runId 重挂进行中轮的流），解决 DC-06③"刷新不丢"与 409 的死锁（与技术方案 §13.2 #12 联动，方向 S3 已定、端点细化 S4.4）；② 分布式锁须带续期（watchdog），轮终态主动释放；"锁过期早于轮结束"列为回归用例（双请求交错压测 0 丢消息）。
- **被否决方案的坑**：B 即 GLM-R 实测的丢消息/串写；C 改变交互语义且实现复杂度高。回归用例：同 sessionId 并发 8 路压测（必须 0 丢消息）。
- **推翻条件**：产品确认需要同会话多端同时书写（转 C 并重新评估）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-6 SSE 韧性策略：每轮重建请求 + 双超时 + 重试三条件

- **选项**：A. 官方 RetryTemplate／B. Reactor .retry() 重订阅／C. 自研：每轮重建请求 + 双超时（首包/包间）+ 重试三条件（次数上限/总预算/未产出且无副作用）
- **选择**：C（官方 API 组装，策略自研——官方机制在流式场景已被实测证伪）
- **证据等级**：【实测】（SP-01d：A 只覆盖非流式；B 重订阅必抛 IllegalStateException 且不发第二次请求；ChatModel 层重订阅会重发已产出内容"我是我是"）
- **理由**：流式 advisor 链一次性（字节码+实测）；C 的三条件门禁经 SP-01d 全部故障注入用例与 GLM-R 反例（2s 超时误杀 5s 工具）验证，副作用信标可正确阻止误重试。**两条硬规范随本卡生效**：① 超时阈值必须大于最长工具耗时（工具执行期下游零事件）；② TCP 正常 FIN 的静默截断会被判 OK——必须落地完成帧校验（首包 start 事件 + 显式 done/error 终帧），缺失终帧一律按断流处理。
- **被否决方案的坑**：A/B 见上（实测证伪）；无完成帧校验 = 静默数据丢失。回归用例：SP-01d 全部 **23 用例**（vd1×19 + vd2×2 + vd3×2，以附件 B/C/D 清单为准——【修订：CH-P10】原"21 用例"计数无法追溯已更正）入 CI。
- **推翻条件**：Spring AI 官方支持流式断流重试语义时重审。

## ADR-7 发布语义：glm 范围内替换（重写 combined 整体替换）+ 乐观锁冲突检测保留

- **选项**：A. glm 范围内替换（按配置项×范围替换 PUBLISHED）／B. combined 按配置项整体替换／C. 两者折中
- **选择**：A；combined 的乐观锁冲突检测（OPTIMISTIC_FORCE_INCREMENT + baseVersion 快照比对）原样保留叠加
- **证据等级**：【实测】（V2 双向对称实验逐字段比对；V5 冲突提示文案逐字一致、版本强制递增——Challenger 抽-2 复核基本属实）
- **理由**：多范围并存时整体替换有误伤风险（V2 实测范围内替换互不误伤）；冲突检测是发布安全底线（V5）；手册纪律：冲突时重写而非折中。
- **【修订：CH-P11④】V5 边界披露**：V5 自认"真正同刻乐观锁竞争（ObjectOptimisticLockingFailureException）路径未取得直接观测"——快照守卫路径已实测，同刻竞争路径补并发发布回归用例（§12.2）。
- **【修订：Q14 定案（2026-10-07，指挥官裁决）】范围替换下的版本粒度**：glm 范围内替换是"事务内删同范围 PUBLISHED + 提升 STAGED"（删建行），而 combined 乐观锁基于行级 baseVersion 快照——删建行使行身份不延续，并发发布同范围时快照比对对象消失（组合未测，Q14）。**定案选 A：行级 upsert + 范围差集删除**——发布时按业务键匹配：已存在行更新（保留行 id 与 version 递增，baseVersion 语义完整延续 V5 实测机制）、新业务键行插入、范围内本次未覆盖的旧行删除（差集）。业务语义与 glm"范围内替换"等价（V2 不伤），冲突检测语义与 combined 一致（V5 不浪费）。被否决：B（引入范围级版本表 scope_version，新实体复杂度高）；C（发布串行互斥锁替代冲突检测，丢失精细度且与 V5 资产冲突）。S4.3 发布模块按此写码，行为对照必含"并发发布同范围"场景（快照比对在 upsert 路径下仍触发冲突提示）。
- **被否决方案的坑**：B 多地区/项目并存互伤（V2 反证）；折中方案语义含糊不可测试。回归用例：V2 双范围发布实验、V5 并发发布冲突实验（含同刻竞争），均转为自动化。
- **推翻条件**：业务确认配置项永远单范围生效（事实不成立，三层级是需求）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06

## ADR-11b 安全边界：无认证鉴权（demo 定位）+ 无主体操作流水

- **选项**：A. 保留 DC-09 的认证+RBAC／B. 完全无安全体系／C. 无认证鉴权但保留操作流水
- **选择**：C
- **证据等级**：【指令】（DC-10 业务方指令）
- **理由**：demo 无真实多用户，认证/RBAC/数据权限是纯成本（DC-10）；但操作流水的追溯价值独立于用户体系存在——保留"动作/对象/前后值摘要/来源（界面或 AI）/时间"的无主体记录（P2），AI 行为记录（token/工具序列）不受影响。安全边界显式声明：**仅限内网/本地受信环境**；HITL 确认门保留（交互安全，非权限体系）。
- **【修订：CH-P7】会话所有权**：sessionId 与认证主体绑定（防跨用户读会话/替他人批准）在无认证体系下无锚点——本期转为**已知风险接受**（受信环境前提，sessionId 为不可枚举的随机长 ID 即可）；转生产恢复 ADR-11 时，"sessionId ↔ 用户绑定 + 确认/回灌请求归属校验 + 越权用例"为一揽子前置工作项。
- **被否决方案的坑**：A 给 demo 背上登录/用户管理/权限切面三件套的的成本；B 丢失 AI 行为追溯能力。回归用例：操作流水写入与按来源过滤查询。
- **推翻条件**：转生产/真实多用户出现（恢复 ADR-11 原卡）。
- **主笔**：Kimi K3　**复核**：GLM-5.3（Challenger 通过）　**日期**：2026-10-06
