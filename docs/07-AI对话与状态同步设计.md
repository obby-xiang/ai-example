# AI 对话与状态同步设计

- 项目：ai-example-deepseek-v4-pro
- 版本：v1.0

> 本设计回应任务中的三个核心要求：**优先后端 AI Runtime**、**解决用户操作与 AI 对话状态同步**、**不同页面不同工具（渐进式披露）**。设计综合了业界主流实践（Microsoft Copilot Side-by-Side 模式、AG-UI 事件协议、OpenAI Function Calling 规范、参考项目 dataVersion 机制）与 DeepSeek 推理模型的实际行为。

## 1. 总体架构：后端 AI Runtime + 契约化双向同步

```
┌─────────────── 前端（Vue3 + Pinia）───────────────┐
│ 左：业务工作区（向导/表格/SpreadJS）   右：AI 对话栏  │
│   store action（用户点击 / AI ui_event 同源写入）   │
└───────────────┬──────────────────┬────────────────┘
       上下文快照（业务→AI）      ui_event（AI→业务）
                │                  │
┌───────────────▼──────────────────▼────────────────┐
│        后端 AI Runtime（Spring AI 1.1.8）          │
│  AiSessionStore（页签会话 + 影子状态 + pending）     │
│  Agent 循环：流式 → 工具调用 → 执行 → 回填 → 再流式   │
│  ToolRegistry（按页面披露 + confirm 确认门）         │
└──────────────────────┬─────────────────────────────┘
              OpenAiApi（DeepSeek OpenAI 兼容端点）
```

**为什么后端 Runtime？** ① API 密钥不出后端（安全）；② 工具直连业务服务层（导出/导入/数据全部在后端，无需前端再代理一遍）；③ 会话与工具权限可审计。前端 Runtime 的**思想**被借鉴：上下文快照、工具结果驱动 UI、状态同源。

## 2. 会话生命周期（页签唯一、不持久化）

| 决策 | 方案 | 理由 |
|---|---|---|
| 唯一性 | 前端 `sessionStorage` 存 UUID（首次进入生成） | sessionStorage 天然按页签隔离：新页签=新会话；同页签刷新仍在；关页签即销毁 |
| 存储 | 后端内存 Map + 空闲 30min 定时清理 | 满足“不持久化、不看历史”；避免持久化一致性问题 |
| 刷新恢复 | 前端启动时 `GET /api/ai/history?sessionId=` 恢复消息与工具卡片 | 同页签刷新后对话不丢（后端内存会话仍在期间）；后端重启后返回空列表，前端自动降级为新会话 |
| 跨页面 | 会话对象不随路由重建，页面切换仅更新上下文快照 | 对话连续，工具清单随页面切换（渐进披露） |
| 安全默认 | 未确认操作 + 新消息 → 自动视为拒绝 | AG-UI 超时安全原则：过期确认宁可拒绝 |

## 3. 状态同步：双向契约（本设计核心）

### 3.1 业务 → AI：上下文快照（摘要级）

每次发消息，前端把工作区状态压缩为摘要随请求上传（避免把整表数据塞进 prompt）：

```json
{
  "page": "export",
  "workspaceVersion": 12,
  "export": { "step": 2, "selectedDefs": ["SERVER_PARAM"], "conditions": {"SERVER_PARAM": {"env": {"op": "eq", "value": "生产"}}}, "taskId": 3 },
  "import": { "step": 1, "selectedDefs": [], "batchId": null }
}
```

后端把快照合并进会话的**影子状态**。工具在同一轮内连续调用（选配置→设条件→启动导出）时读写影子状态，不需要等前端往返——这是同步的第一层保证。

### 3.2 AI → 业务：ui_event 统一分发

工具执行结果附带 `ui_event` 指令，前端**统一分发器**把事件写入与用户点击完全相同的 store action：

```
用户路径：点击勾选框 → store.selectDefs([...])
AI 路径 ：select_export_defs 工具 → ui_event{type:"select_defs"} → store.selectDefs([...])
```

两侧走同一条状态变更路径 → 状态不可能分叉。事件类型与目标见 docs/03-实现方案.md §2.3。

### 3.3 竞态防护：workspaceVersion（借鉴 dataVersion 机制）

- 任何改变工作区的操作（用户点击、AI ui_event 应用）都递增版本号；
- 版本号随上下文快照上传；AI 挂起（等待确认）期间用户改了左栏 → 新快照覆盖影子状态 → 工具继续执行前可用 `get_ui_state` 复核；
- 相比事件流方案：只需首尾版本对比，成本极低，且保留“用户改完再确认”的合法路径。

### 3.4 同步的可视化（透明可审计）

对话流中展示：工具名+参数卡片、执行结果摘要、成功/失败着色、思考过程折叠、确认卡片。用户始终知道 AI 动了什么、为什么。

## 4. 渐进式披露：不同页面不同工具

- 工具定义声明 `pages` 白名单（导出页 6 个工具、导入页 9 个、定义页写工具、全局通用 3 个）；
- 每轮请求只把**当前页面可见工具**放入 tools 数组与系统提示词 → 模型视野收敛、token 节省、工具权限页面隔离；
- 页面切换不需要新会话：上下文快照变化 → 系统提示词重建 → 工具清单自动切换；
- 常见问题（“导出页为什么没有发布工具”）成为结构性的不可能，而不是靠提示词约束。

## 5. HITL：确认门（破坏性操作人审）

- `confirm=true` 的工具（导入/发布/写数据/改定义）在 Agent 循环中触发**暂停**：
  SSE 下发 `confirm_tool` 卡片 → 结束本轮流 → 用户点“确认执行/取消”；
- `POST /api/ai/confirm {approved}` 打开新 SSE 续跑：确认 → 执行工具并继续后续工具与模型轮次；拒绝 → 回填“用户拒绝”结果让模型收尾；
- 超时/新消息兜底：自动视为拒绝（宁可少做，不可错做）。

## 6. Agent 循环实现要点（Spring AI 1.1.8 实测）

1. `OpenAiApi.chatCompletionStream`（WebClient 流式）自动完成工具参数分片合并，finish_reason=tool_calls 时给出完整调用；
2. `parallel_tool_calls=false`（1.1.8 流式合并器单帧仅支持一个调用）；
3. 回填消息时 **reasoning_content 必须置空**（DeepSeek 对回传推理内容返回 400，官方文档明确警告）；推理过程仅流式展示给用户，不进入上下文；
4. 工具结果回灌前截断（4000 字符），会话消息窗口上限 40 条（system 常驻）；
5. 传输健壮性：读超时 180s（推理模型长输出）；429/5xx 中断 → error 事件（副作用最小原则：不自动重跑任务类工具）。

## 7. 设计权衡记录

| 议题 | 方案选择 | 取舍 |
|---|---|---|
| AI Runtime 位置 | 后端 | 安全/可审计/直连服务层；代价是后端需维护 SSE 循环 |
| 会话持久化 | 不持久化（页签级） | 符合需求且最简；历史对话为预留扩展点 |
| 状态同步 | 快照+影子状态+ui_event 同源写入 | 比事件流简单可靠；大数据场景靠 get_ui_state 现查兜底 |
| HITL 粒度 | 工具级确认门（仅破坏性） | 在“全自动”与“步步确认”之间取业务最优：读操作零摩擦，写操作可控 |
| 工具披露 | 页面级白名单 | 简单可预测；若未来页面内步骤级披露，扩 pages 为 page+step 矩阵即可 |
