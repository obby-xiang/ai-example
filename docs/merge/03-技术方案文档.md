# 技术方案文档 —— AI 辅助配置快速实施平台（生产落地版）

> 文档编号：TD-001　版本：v2.0　日期：2026-10-05
> 本方案融合 6 个 demo 分支的长板（来源标注为〔分支名〕），并补齐生产落地缺口。每条关键决策均给出备选与理由（ADR 方法采自〔kimi-k3〕）。

---

## 1. 总体架构

```
┌────────────────────────── 浏览器（Vue 3 SPA，页签级 AI 会话） ─────────────────────────┐
│  左侧业务工作区（任务中心 / 导出向导 / 导入向导 / 配置定义管理 / 审计）                     │
│  右侧常驻 AI 对话栏（消息流 + 工具卡片 + HITL 确认卡 + 上下文芯片）                        │
│  中间契约层 workspaceContract + workspaceBus〔deepseek〕：AI 操作与人工操作同源             │
└──────────────┬───────────────────────────────────────────┬───────────────────────────┘
               │ REST + SSE（作业进度/事件广播）             │ POST SSE（AI 流式）
               ▼                                           ▼
┌────────────────────────────── Spring Boot 后端（无状态多副本） ──────────────────────────┐
│  业务层：定义/数据/任务/作业/版本/审批/审计/权限服务（REST 与 AI 工具共用，单一事实源〔glm〕） │
│  AI Runtime：Spring AI 官方能力组合〔deepseek〕                                              │
│    @Tool 工具（Schema 自动生成）+ ChatClient 循环 + ToolCallingManager 扩展点（HITL 钩子）   │
│    + ChatMemory（DB 持久化）+ ReasoningAware 补丁〔kimi〕+ 断流重试/心跳〔deepseek〕          │
│  作业引擎：JobExecutor（线程池/虚拟线程）+ 拓扑排序 + 僵尸作业恢复〔claude+ds〕               │
│  数据层：MySQL 8（生产）+ Flyway 迁移〔claude〕+ Redis（会话/锁/进度热点）                   │
└───────────────────────────────────────────┬─────────────────────────────────────────────┘
                                            │ OpenAI 兼容协议（SSE）
                                            ▼
                              DeepSeek API（deepseek-flash，密钥仅后端持有）
```

关键原则：
1. **单一服务层**：界面 REST 与 AI 工具调用同一组业务服务，权限/校验/审计在 Service 层统一收口——AI 不可能绕过任何业务规则〔glm〕。
2. **能用框架能力绝不自造**〔deepseek/kimi〕：Agent 循环、工具 Schema、对话记忆全部使用 Spring AI 官方组件，仅在官方预留扩展点（ToolCallingManager）上做业务增强。
3. **服务端权威 + 事件驱动**〔main 调研结论〕：任务/作业/会话的权威状态在服务端，前后端经标准化事件流（SSE）同步。

## 3. 关键架构决策（ADR）

### ADR-1：AI Runtime 置于后端，不使用前端 Runtime

- **决策**：Agent Loop 在后端；前端只做事件渲染与工具结果回灌。
- **理由**：① API Key 不出后端；② 工具混排（后端数据工具 + 前端 UI 工具）需要服务端编排；③ 权限/审计必须在服务端强制〔main 调研结论与 kimi D1 一致〕。
- **否决项**：`ai-ui-vercel` 式前端 Runtime（Vercel AI SDK）——密钥代理注入仍可被滥用、工具权限无法服务端管控、审计断链。前端范式仅作为技术预研存档。

### ADR-2：工具体系 —— @Tool 注解 + 注册表元数据 + 渐进式披露

- **决策**：工具用 Spring AI `@Tool` 注解定义（JSON Schema 自动生成）〔deepseek/glm〕；另建 ToolRegistry 元数据表（名称、风险级 ToolRisk、作用域 ToolScope、needConfirm、适用页面/步骤）〔claude〕。
- **渐进式披露三重防线**〔kimi D4 + claude〕：① 请求时按 page+step+任务类型过滤 ToolCallback 子集；② 系统提示词声明当前场景可用动作与禁区；③ 工具方法内兜底校验上下文，不匹配返回错误结果给模型。
- **理由**：@Tool 省去手工 Schema（deepseek 分支实测删除数百行手工协议代码）；注册表保留风险/作用域元数据供 HITL 与披露策略使用。

### ADR-3：Agent 循环 —— ChatClient + ToolCallingManager 扩展点挂 HITL

- **决策**：循环与协议交给 Spring AI（OpenAiChatModel 内部循环）；实现 `HooksToolCallingManager` 包装官方 DefaultToolCallingManager〔deepseek〕，做两件事：① 工具执行前后推 SSE `tool_start/tool_result`（可见性）；② needConfirm 工具执行前挂起等待前端确认（批准→放行；拒绝/超时→以"用户取消"作为工具结果回填）。
- **前端 UI 工具**（navigate_to / select_config_defs 等）：`internalToolExecutionEnabled=false` 的受控执行开关由框架预留〔kimi D1〕，Loop 暂停、SSE 下发 tool_call、前端执行后 POST 回灌恢复。
- **理由**：全部走官方扩展点，框架升级无破坏性改动；HITL 语义（暂停-恢复-回填）官方循环无法直接表达，扩展点是框架认可的自控入口。

### ADR-4：DeepSeek 推理模型兼容性（实测结论，必须遵守）〔kimi，实测附报错原文〕

1. **deepseek-flash 为思考模式：回填历史 assistant 消息必须携带本轮 `reasoning_content`，缺失即 400**（"The `reasoning_content` in the thinking mode must be passed back to the API"）。注意：这与 deepseek-chat/deepseek-reasoner 的旧规则**相反**。
2. Spring AI 1.1.8 `OpenAiChatModel.createRequest` 将历史 reasoningContent 硬编码为 null → 需补丁 `ReasoningAwareOpenAiChatModel extends OpenAiChatModel` 仅 Override 该传播点（流式 chunk 与聚合 AssistantMessage 均以 metadata["reasoningContent"] 为键，闭环）；补丁类注明升级框架后评审移除。
3. `parallel_tool_calls=false`（1.1.8 流式合并器单帧仅支持单调用）。
4. 重试：429/5xx 整轮指数退避 ≤3 次；**已产出流式内容不重试**（Spring AI 官方重试只覆盖非流式）；上游断流 90s 自愈重试〔deepseek〕。
5. 工具结果截断 4000 字符回填；reasoning 回放上限 8000 字符〔kimi〕。

### ADR-5：会话生命周期与记忆

- **页签级会话**：sessionStorage 持有 sessionId，新页签=新会话〔deepseek/glm/kimi 一致〕。
- **记忆持久化**：ChatMemory 落库（MessageWindowChatMemory + 自定义 JdbcChatMemoryRepository）〔deepseek 用 H2，生产换 MySQL/Redis〕——刷新与后端重启均不丢；TTL 24h 滑动过期〔claude Caffeine 思路平移到 Redis〕。
- **中断恢复**〔main 调研 P3/P4〕：pending HITL 交互入库，刷新后重放确认卡；超时（10min）自动按"取消"回填，绝不无限悬挂；确认等待期间 SSE 心跳保活〔deepseek〕。

### ADR-6：AI ↔ 工作区状态同步 —— 请求时注入 + 契约层联动

- **业务 → AI**：每次 chat/tool-result 请求携带上下文快照摘要 `{page, step, taskId, selectedDefs, dataVersion}`；细粒度状态由 AI 调 `get_workspace_state` 工具按需拉取，避免上下文膨胀〔kimi D3〕。
- **AI → 业务**：AI 动作经 `workspaceContract`（契约层）+ `workspaceBus`（事件总线）分发〔deepseek〕，与人工点击走同一 Pinia store/同一服务层——单一状态源，天然双向同步；去掉 AI 通路业务完整可用（可裁剪）。
- **竞态防护**：快照携带 dataVersion/workspaceVersion〔deepseek/kimi〕，执行工具时版本比对，漂移则让模型重新拉取（解决 main 调研 P5 状态漂移）。

### ADR-7：作业引擎 —— 异步、持久化、可恢复、可取消

- Job/JobItem/ValidationIssue 三层模型〔claude〕：作业逐项（按配置项拓扑序）推进，行级校验问题落库。
- **事务边界**：作业在创建事务 afterCommit 后再提交线程池（修复"执行线程读不到未提交行"竞态）〔kimi/claude+ds 实测缺陷〕。
- **幂等**：同任务同 kind 存在 RUNNING 作业时拒绝重复提交并返回现有作业〔kimi〕；**工具调用级幂等**：tool-result 回灌按 tool_call_id 去重（已回灌的重复提交直接拒绝），审批接口按审批单号幂等，发布动作全局只生效一次。
- **取消**：JobCancellationRegistry + 执行检查点响应 AtomicBoolean，取消真正生效〔claude+ds〕。
- **恢复**：StaleJobRecoveryRunner 启动时扫描残留 RUNNING 作业，标记或续跑〔claude+ds〕。
- **进度**：SSE 推送（ProgressHub + 心跳 + 终态补发）〔deepseek/glm〕；轮询作为降级备份〔kimi 权衡〕。多副本时经 Redis Pub/Sub 广播。

### ADR-8：发布语义 —— 范围内替换 + 乐观锁 + 版本快照 + 审批

- **范围内替换**〔glm，业务正确性最高〕：事务内先删"本批次涉及配置项 × 涉及范围"的 PUBLISHED 数据，再将 STAGED 提升为 PUBLISHED；多范围并存互不误伤。**否决**按配置项整表替换〔deepseek 现状，多范围场景误伤〕。
- **并发安全**：发布携带版本号，`OPTIMISTIC_FORCE_INCREMENT` 强制版本递增〔claude+ds〕，冲突返回明确提示；同配置项发布经 Redis 分布式锁串行化。
- **版本快照**：发布生成 ConfigVersion（全量快照 + diff 摘要），支持审批、回滚〔需求 FR-3.6/3.7〕。
- **引用完整性**：发布终检时引用取值源 = 正式区 + 本批次拓扑序在前配置的暂存数据；REPLACE 模式下被覆盖配置以新数据为准〔kimi RefValueProvider UNION/REPLACE 模式〕。

### ADR-9：依赖处理

dependsOn 构成 DAG，作业创建时 Kahn 拓扑排序〔claude DependencyResolver〕；循环依赖报错；未选中依赖项以正式区数据为准；上游失败下游自动 SKIPPED 并注明原因〔kimi 实测行为〕。

### ADR-10：场景与工具的可配置演进

保留〔main〕的 YAML 场景/工具声明式注册思想作为**二期演进**：当业务场景从 2 类扩展到 N 类时，将工具分组、向导步骤、提示词模板收敛为 scenarios.yaml 配置驱动，新增场景零代码。一期场景固定，先硬编码保简单。

## 4. 数据模型（DDL 要点，MySQL）

核心表：`config_definition`、`config_field`、`config_data`（含 scope_region/scope_project/version/status）、`staging_config_data`（task_id 隔离）、`config_version`、`task`、`job`、`job_item`、`validation_issue`、`ai_session`、`ai_message`、`approval`、`audit_log`、`user/role/permission`。

关键约束：
- `config_data` 唯一键 = (def_code, scope_region, scope_project, business_key)；
- 全部业务表带 `version`（乐观锁）与审计四列（created_by/at, updated_by/at）；
- `job` 状态机：PENDING → RUNNING → SUCCESS/FAILED/CANCELLED；`task` 状态机独立于 job 状态机；
- `ai_message` 存 role/content/toolCalls/reasoningContent（回放必需，ADR-4）/token 用量。

## 5. API 与事件契约（摘要）

REST（`/api`，统一 `ApiResponse<T>{code,msg,data}`〔各分支一致〕）：
- 定义：`GET /api/definitions`、`GET /api/definitions/{code}`、字段编辑 `PUT /api/definitions/{code}/fields`
- 数据：`POST /api/data/query`（字段级条件）、`POST /api/data/count`
- 任务：`POST /api/tasks`、`GET /api/tasks`（分页/过滤）、`GET/PUT/DELETE /api/tasks/{id}`、`POST /api/tasks/{id}/cancel`
- 作业：`POST /api/jobs`（kind=EXPORT/PRECHECK/IMPORT/PUBLISH，幂等）、`GET /api/jobs/{id}`、`POST /api/jobs/{id}/cancel`
- 文件：模板下载（单/打包）、上传（xlsx/zip）、结果下载
- AI：`POST /api/ai/chat`（SSE）、`POST /api/ai/tool-result`、`POST /api/ai/cancel`、`GET /api/ai/history`、`GET /api/ai/tools`（调试）
- 审批/审计：`POST /api/approvals/{id}/approve|reject`、`GET /api/audit-logs`

SSE 事件契约（对齐 AG-UI 事件面〔claude/main 调研〕）：`run_start`（首包）→ `text_delta` / `reasoning_delta` / `tool_start` / `tool_call`(前端工具) / `tool_result` / `confirm_request` / `ping`（心跳）→ `run_end(finished|cancelled|error)`；进度通道：`job_progress` / `job_item_update` / `job_end`（终态补发）。

## 6. 安全设计

1. OIDC 登录 + JWT；Service 层统一权限切面（含数据权限）；**AI 工具方法第一参数强制注入操作人 SecurityContext**。
2. 密钥治理：`DEEPSEEK_API_KEY` 仅环境变量注入，pre-commit 钩子扫描密钥防入库〔各分支共识〕。
3. 敏感字段：定义级 `sensitive` 标记，查询/导出/进模型前按角色脱敏。
4. 审计：Service 层 AOP 记录操作流水，来源字段区分 UI/AI。
5. 前端不持有任何模型凭证；SSE 通道鉴权（一次性 ticket）。

## 7. 可观测与运维

- 指标：作业成功率/耗时、AI 轮次/token/成本/工具分布、SSE 连接数、发布冲突率。
- 日志：结构化 + TraceID 贯通（chat → 工具 → 作业）。
- 告警：作业失败率、模型 429 率、SSE 断连率阈值告警。
- 部署：Docker 双副本 + MySQL 主从 + Redis；`verify-e2e` 脚本纳入 CI 门禁〔deepseek〕。

## 8. 测试策略（详见《04-测试用例文档》）

金字塔：单元/切片测试（JUnit + Spring Boot Test，继承并扩充〔glm〕38 用例基线）→ API 集成测试 → E2E 脚本（继承〔deepseek〕verify-e2e 并迁移为可 CI 的 Playwright/curl 套件）→ AI 专项（真实模型冒烟 + 录制回放回归）→ 非功能（性能/并发/故障注入/安全越权）。

## 10. 风险与对策

| 风险 | 对策 |
|---|---|
| SpreadJS 商业授权成本/法务 | 尽早采购；隔离表格层接口，保留 Handsontable 降级方案 |
| DeepSeek 模型行为变更（如 reasoning 规则再变） | ADR-4 补丁点单一、升级评审机制；模型接入层抽象，可切换其他 OpenAI 兼容模型 |
| 大数据量校验/导出性能 | 流式读写（SXSSF）、分批校验、行数上限与审批 |
| AI 误操作业务数据 | HITL 确认门 + 权限切面 + 审计 + 版本回滚，四重兜底 |
| Spring AI 升级破坏补丁 | 补丁类单一职责 + 升级检查清单 + 兼容性测试用例库 |
