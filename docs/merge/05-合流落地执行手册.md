> 项目：AI 辅助配置快速实施平台（ai-example 六分支合流 + 生产化）
> 版本：v2.0　日期：2026-10-06

## 0. 防偏差体系（本版核心）

### 0.1 证据分级制度

本手册及所有产出文档中，每个事实性断言和决策必须带以下标签之一：

| 标签 | 含义 | 例子 | 处置规则 |
|---|---|---|---|
| 【实测】 | 有可复核的证据（代码/提交/日志/亲自运行的结果） | "glm-5.3 分支含 6 个 JUnit 测试类 38 个用例"（已读码确认存在） | 可直接作为行动依据 |
| 【推断】 | 基于证据的专业判断，但未经直接验证 | "38 个测试全部通过"（分支文档自述，未亲自运行） | 可用，但须在 S0.5 核验后才能作为搬运依据 |
| 【假设】 | 无证据，是填补空白的猜测 | "业务需要发布审批流""用户规模 50 并发" | **必须经人/业务方确认签字，否则对应工作不得开工** |

**写作纪律**：AI 模型产出任何文档时，提示词中必须要求"每个关键断言标注证据等级；不确定就标【假设】，禁止把猜测写成事实"。

### 0.2 三条红线（防大偏差的根本机制）

1. **未核验的声明不作为搬运依据**：分支文档自述的能力（"22 用例全绿""范围内替换正确"），在 S0.5 亲自运行核验前，一律视为【推断】。
2. **【假设】未签字不动工**：所有标【假设】的条目（主要是业务需求）汇总成一张表，业务方/负责人逐条确认或否决后，对应开发任务才启动。
3. **行为对照不过不算合流完成**：每搬运一层，先在**源分支**录制行为基线（输入→输出），搬运后在 main-v2 重放，输出一致才算该层完成——防止"代码搬过来了但行为变了"。

### 0.3 决策登记表（Decision Register）

所有决策集中登记在 `docs/adr/DECISION-REGISTER.md`，一决策一行：

| 字段 | 说明 |
|---|---|
| 编号/决策 | DC-XX + 一句话 |
| 证据等级 | 【实测】/【推断】/【假设】 |
| 证据来源 | 分支路径/提交号/日志/核验记录编号 |
| 提出/复核/签字 | 提出模型、复核模型（须异厂商）、签字人 |
| 推翻条件 | 什么情况发生必须重审此决策 |
| 状态 | 生效/待确认/已推翻 |

### 0.4 评分的正确用法

《01-分支评价报告》中的分数是【推断】，且相邻分支分差（83/81/80/79）在噪声范围内。**正确用法**：只取"梯队"（第一梯队：deepseek/combined/glm/kimi）和"长板清单"；**禁止**用 1–3 分的分差做任何取舍裁决。搬运层的选择依据是 S0.5 核验后的实测证据，不是总分。

### 0.5 偏差早期预警清单

出现以下任一信号，停下回到最近的签字节点复查，不要继续推进：

- 某层搬运后行为对照不一致率 > 5%；
- 门禁连续多次全绿但人工抽查发现行为错误（说明测试覆盖假象）；
- 决策登记表中【假设】类决策占比 > 30%（说明地基是猜的）；
- 任一模型连续 3 次产出被同一人驳回（说明提示词/分工错配，非模型问题）。

### 0.6 协作纪律（每一步都适用）

1. **门禁独立**：任何模型产出的代码必须过 CI；同一任务连续失败 2 次升级到上一档模型重做，并记录升级事件。
2. **决策卡流转**：所有架构取舍必须先有决策卡，下游执行者只执行、不重新裁决。
3. **跨厂商评审**：作者与评审者不得同厂商。
4. **反方审查（Challenger）制度化**：关键产出（需求冻结稿、技术方案 ADR、S1 各决策卡、S4 各层出口）必须经过一次异厂商模型的**专职反方审查**——评审者的任务不是"看看有没有问题"，而是"**设法推翻它**"（提示词模板见附录 E）；反方问题清零或被显式驳回后，该产出才算完成。
5. **资产入库**：提示词、决策卡、SKILL.md 全部存仓库，不锁死在任何 Harness 私有格式。
6. **时间套利**：DeepSeek 任务排闲时半价；批量任务走 Batch API；长 system prompt 固定前置吃缓存。

**通用提示词前缀（此后每个会话开头必贴，含证据纪律）**：

纪律：1) 代码须过 mvn test / yarn build；2) 不改已冻结领域名词；
3) 完成定义=对应 TC 用例绿且行为对照一致；4) 每个关键断言标注
【实测】/【推断】/【假设】，禁止把猜测写成事实；

**验收产物**：端点连通记录、`main-v2` 结构、CI 首次绿灯、决策登记表空表。
**通过标准**：6 个模型端点连通；CI 可跑通。
**异常与备选**：Kimi Code Desktop 异常 → 全程 CLI；某厂商端点不通 → 查 §9 降级映射，不阻塞。

## S0.5 分支声明核验 ★ 本版新增的关键关卡

**目标**：**把 6 个分支文档中的自述声明全部亲自运行核验一遍**，将【推断】升级为【实测】或证伪。这是纠正"评审只读了代码和文档、没跑过"这一根本缺陷的唯一手段。核验结果可能修正搬运层来源映射——这是正常的，正是本步骤的价值。

| 项 | 内容 |
|---|---|
| Harness/模型 | OpenCode + GLM-5.3-Flash / V4 Flash（执行核验脚本）；人抽验 20% |
| 输入 | 6 个分支 worktree、各分支自述的验证文档 |

**核验清单（逐分支）**：

| # | 声明 | 核验方法 | 期望 |
|---|---|---|---|
| V1 | glm-5.3：38 个 JUnit 全通过 | 该分支 `mvn test` | 38/38 绿；记录真实数字 |
| V2 | glm-5.3：范围内替换发布语义 | 造两地区数据，发布其一 | 另一地区数据不变 |
| V3 | deepseek-v4-pro：22 E2E 用例全绿 | 起服务跑 `verify-e2e.ps1` | 记录真实通过数 |
| V4 | deepseek：会话 H2 持久化（重启不丢） | 对话→重启后端→取历史 | 历史完整 |
| V5 | combined：乐观锁发布冲突检测 | 两会话并发改同配置发布 | 后者收到冲突提示 |
| V6 | combined：僵尸作业恢复 | 作业中 kill 后端→重启 | 残留作业被检测标记 |
| V7 | kimi-k3：reasoning_content 不回放则 400 | 直连 API 复现（去掉 reasoning） | 复现 400 报错原文 |
| V8 | kimi-k3：作业幂等（重复提交返回现有 id） | RUNNING 中重复 POST | 返回同 id |
| V9 | claude：Flyway 迁移可重复执行 | 清库重跑两次 | 幂等成功 |
| V10 | main：ai-ui-vercel 前端 Runtime 可用 | 起三服务走一遍导出 | 确认可用性及其局限 |

**提示词（核验执行）**：

```
在 /branches/{分支} 目录执行核验项 V{n}：{核验方法}。
记录：实际结果（数字/报错原文/截图）、与声明是否一致、环境差异。
禁止"应该能通过"式的臆断——只记录你实际观察到的东西。
输出追加到 docs/evidence/V{n}-{简述}.md，文末给出证据等级结论：
【实测-符合】/【实测-不符】/【环境受限未验】。
```

**验收产物**：`docs/evidence/V1–V10` 核验记录 + `docs/evidence/核验汇总表.md`（声明 vs 实测对照）。
**通过标准**：V1–V9 全部完成（V10 环境受限可缓）；**凡核验不符的声明，修正对应分支的"长板"定位与搬运映射**，并在决策登记表记录修正。
**异常与备选**：
- 分支跑不起来（依赖/环境）→ 记【环境受限未验】，该分支的对应长板降级为备选来源，改用已核验来源；
- 核验推翻关键声明（如 glm 测试实际不全绿）→ 这不是坏事：修正映射表后再进 S1，**此时修正成本最低**；
- 时间紧 → 最小核验集 = V1/V2/V3/V5/V7（覆盖 4 个搬运来源的核心声明），其余入 backlog。

## S1 风险验证 PoC 组 ★ 关卡步骤

**目标**：把合流最大的技术未知数拆成 **4 个相互独立的 PoC** 分别验证（吸收外部手册的拆分思路——比一个大复合 Spike 定位更准、单点失败不阻塞其他验证）。证据要求：结论必须全部【实测】。

| 子 PoC | 验证内容 | 通过条件 |
|---|---|---|
| SP-01a 前端工具 | 官方循环内前端工具暂停→SSE 下发→回灌→恢复 | 链路完整走通，Loop 正常结束 |
| SP-01b HITL 确认门 | HooksToolCallingManager 挂起→确认放行/拒绝回填/超时自动取消 | 三种结局行为正确；挂起期心跳保活 |
| SP-01c 状态与恢复 | 连续 7 轮工具调用不 400（reasoning 回放）；刷新/重启后会话与 pending 恢复 | 无 400；恢复完整 |
| SP-01d 幂等与故障 | tool-result 重复去重；断流 90s 有界重试；执行中取消 | 见 TC-F-04/TC-AI-14/15 预期 |

| 项 | 内容 |
|---|---|
| Harness/模型 | Kimi Code（CLI，Plan 模式）+ **Kimi K3**；**GLM-5.3 独立复现复核**（防单模型假象） |
| 输入 | S0.5 的 V4/V7 核验结果、deepseek 的 `ai/` 包、kimi-k3 的补丁与 AiChatService |
| 输出 | `docs/spike/SP-01a~d-*.md`（各一张决策卡，证据等级必填）+ spike 脚手架（`spike/`，不入主干） |

**提示词（每个子 PoC 分别发起，将{子项}替换为 SP-01a/b/c/d 的验证内容）**：

```
任务：技术可行性 PoC {子项编号}（不改主干代码，只产实测结论）。
验证范围：{子项验证内容与通过条件}。
背景：AI Runtime 拟采用 Spring AI 1.1.8 官方循环（ChatClient + ToolCallingManager），
关键参照：deepseek 分支 ai/HooksToolCallingManager.java（HITL 挂起）、
kimi-k3 分支受控薄 Loop 与 ReasoningAwareOpenAiChatModel（reasoning 回放补丁）。
已知约束：deepseek-flash 思考模式回填 assistant 必须携带 reasoning_content 否则 400
（证据见 docs/evidence/V7）。
流程：先输出验证计划，经我确认后在 spike/ 建最小工程实测。
产出决策卡：结论（可行/不可行/有条件可行）+ 每条结论的实测日志证据 +
被否决方案的回归风险。所有结论必须【实测】，不得外推。
```

**复核机制（防单模型偏差）**：K3 产出后，GLM-5.3 在干净环境中**独立按决策卡复现各子 PoC 的核心链路**，结论一致才算通过。

**验收产物**：SP-01a~d 四张决策卡（双模型一致结论 + 日志证据）、spike 代码、实现要点清单。
**通过标准**：4 个子 PoC 全部实测通过（单点失败只重做该子项，不连带返工）；双模型复现一致；人签字登记决策表。
**异常与备选**：
- **X1：SP-01a 或 01b 证明官方循环表达不了共存** → 备选：kimi-k3 受控薄 Loop（其可用性已由 S0.5-V7/V8 与该分支验证记录佐证）。推翻原决策，登记决策表（推翻条件触发），更新 ADR-3。
- **X2：可行但有边界** → 约束写入 ADR-4 并配测试，继续。
- 真实模型波动干扰 → 录制回放隔离变量：先验框架行为，再验模型行为。

## S4 M1 骨架合流 ★ 主体工程

**总原则（更新）**：基座拼装 + 定向移植；**每层先在源分支录行为基线，搬运后重放对照**（红线 3）；基座与移植来源以 **S0.5 核验后的映射表**为准（下表为默认，允许被核验结果修正）。

**基座策略**：`main-v2` 直接从 combined 分支切出（`git checkout -b main-v2 origin/claude-opus-5.5+deepseek-v4-pro`），保留其完整 git 历史（含继承自 claude 分支的 3 个提交与 35 次迭代修复记录），**不建空仓库**。然后做两个整包替换型 commit：① 前端整目录替换为 deepseek-v4-pro 前端；② 后端 `ai/` 包整包替换为 S1 裁决的 AI Runtime 方案。glm 的测试/发布语义/种子、kimi-k3 的补丁为定向移植。

| 模块 | 基座/来源（待核验确认） | 动作 | 前置核验 |
|---|---|---|---|

> 纪律：基座≠免检。combined 的 AI 层是要被替换的、发布语义是要被 glm 改写的——基座提供骨架与历史，S0.5 核验与红线条款对基座同样适用。

**行为对照方法（每层通用）**：
1. 搬运前：在源分支运行该层核心场景（如发布一次导入），记录"输入 → 关键输出/DB 状态"到 `docs/evidence/baseline-{层}.md`；
2. 搬运后：在 main-v2 用相同输入重放，逐条比对；
3. 不一致项逐个定性：有意改进（记决策卡）/ 搬运缺陷（修复）/ 源分支本身 bug（不修旧分支，直接在新基线修并补回归用例）。

### S4.1 后端骨架与数据层

模型：GLM-5.3-Flash 搬运 → 卡点升 K2.7 Code。提示词同 v1.0，追加："**逐文件列搬运清单（来源路径→目标路径→改动点）；字段差异一律以决策卡 DDL 为准并列出对照表。**"
验收：编译绿 + Flyway 迁移成功 + 8 配置种子落库 + **V9 基线重放一致**。

### S4.2 AI Runtime 合流 ★ 最高风险

模型：**Kimi K3** 主干；MiniMax M3 只读评审；GLM-5.3 复核关键结论。提示词同 v1.0，按 S1 最终架构（官方循环或受控薄 Loop）执行。
验收：TC-AI-01/02/03/05/13 绿 + **行为基线重放一致** + M3 评审问题清零。
异常：主干行为与 spike 不一致 → 回退备选架构（决策表已预登记）；设计层面争议回决策卡，执行模型不现改。

### S4.3 业务机制合流

模型：K2.7 Code 主力；GLM-5.3 负责发布模块。提示词同 v1.0，追加"**发布语义以 S0.5-V2 核验过的 glm 实现为准；冲突时重写而非折中**"。
验收：11 条对应用例绿 + 发布/冲突/僵尸恢复三个基线重放一致。

### S4.4 前端合流

模型：V4 Flash 组件搬运 + GLM-5.3-Flash 样式 + K2.7 Code 联调。提示词同 v1.0。
验收：构建绿 + 双向导走查 + AI 联动录屏 + 裁剪性验证（去 AI 栏业务可用）。

## S5 测试迁移与门禁建设（与 S4 并行）

同 v1.0（GLM-5.3 主力 JUnit、V4 Pro 闲时 E2E、Qwen CLI 批量反译缺陷清单、M3 找茬），追加两条防偏差要求：

1. **基线对照测试入库**：S4 各层的行为基线转为自动化用例（不只靠人工比对一次）；
2. **门禁有效性验证**：故意向 CI 提交一个含已知缺陷的 PR，确认门禁能拦住——门禁拦不住已知的坑，就不配拦未知的坑。

**验收产物**：≥80 JUnit + 25 E2E 进 CI、regression-backlog.md、门禁有效性验证记录。
**通过标准**：CI 连续 3 次全绿 + 门禁成功拦截至少 1 次注入缺陷。

## 9. 异常总表与备选速查（v2.0 增补）

| 异常 | 触发信号 | 备选方案 |
|---|---|---|
| Spike 推翻 AI Runtime 选型 | S1 链路 1 失败 | 受控薄 Loop（预登记决策） |

| **行为对照不一致率 >5%** | S4 各层比对 | 停线：逐条定性（改进/缺陷/旧 bug），查清再继续 |
| **【假设】占比 >30%** | 决策表统计 | 回 S2 补业务确认，不动工 |
| **门禁拦不住注入缺陷** | S5 验证失败 | 暂停合并权限，先补测试设计 |
| Kimi Code Desktop 不稳 | 崩溃/丢会话 | 全程 CLI |
| 厂商端点不可用 | 超时/限流 | K3→GLM-5.3；K2.7 Code→V4 Pro；GLM-Flash→V4 Flash→qwen3.7-flash；M3→GLM-5.3 评审 |
| 模型产出连续失败 | 同任务门禁 2 次红 | 升档重做；再败则人拆小任务 |
| 业务方不签字 | S2 迟迟无法完成 | 仅放行已确认 P0 子集 |
| E2E 抖动 | nightly 间歇红 | 降 nightly 观察稳定后再升门禁 |
| 模型行为变更 | TC-AI-13/14 突红 | 复核 ADR-4 补丁；录制回放隔离变量 |
| SpreadJS 授权未落地 | 采购超期 | Handsontable 降级（表格层已隔离） |
| 成本超标 | 周账单超 30% | 查 T0 占比（应 ≤10%）/档位误用/闲时调度 |
