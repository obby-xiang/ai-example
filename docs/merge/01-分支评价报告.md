# ai-example 多分支评价报告

> 评价对象：https://github.com/obby-xiang/ai-example 的 6 个分支（main、claude-opus-5.5、claude-opus-5.5+deepseek-v4-pro、deepseek-v4-pro、glm-5.3、kimi-k3）
> 评价视角：**以"指导真实业务需求落地"为第一视角**，辅以架构质量、工程质量、测试验证、文档交付、AI 能力设计五个视角。
> 评价日期：2026-10-05

---

## 1. 项目整体认知

### 1.1 项目是什么

ai-example 是一个"**AI 辅助配置快速实施平台**"的全栈演示项目：左侧为业务工作区（配置项导出/导入的多步骤向导，内嵌 SpreadJS 在线 Excel），右侧为常驻 AI 对话栏（Function Calling 驱动工作区、渐进式工具披露、HITL 人在回路确认、SSE 流式与状态同步）。统一技术底座为 Spring Boot 3.5.14 + JDK 21 + Spring AI 1.1.8（OpenAI 兼容协议接 DeepSeek）+ H2 文件库 + Vue 3 + Element Plus + GrapeCity SpreadJS 17.1.5。

### 1.2 各分支是什么关系

6 个分支是**同一命题下的 6 套独立实现**（分支名即实现所用的大模型）：

| 分支 | 提交数 | Java 行数 | 前端行数 | 自动化测试文件 | 文档规模 | 一句话定位 |
|---|---|---|---|---|---|---|
| main | 11 | 4,235 | 10,493（双前端） | 0 | 最大（含调研归档） | **基线版**：双 AI 运行时范式对比演示，4 业务场景 |
| claude-opus-5.5 | 3 | 4,644 | 2,826 | 0 | 中 | **单次成型版**：后端分层最规范的底稿 |
| claude-opus-5.5+deepseek-v4-pro | 35 | 5,763 | 3,350 | 0 | 大 | **迭代最深版**：功能最全、生产意识最强 |
| deepseek-v4-pro | 13 | 5,426 | 2,978 | 0（含 685 行 E2E 脚本） | 最大（8 篇） | **技术选型最优版**：Spring AI 官方能力用得最彻底 |
| glm-5.3 | 6 | 4,920 | 2,223 | **6（38 个 JUnit）** | 中 | **测试最扎实版**：唯一有真实自动化测试套件 |
| kimi-k3 | 10 | 3,921 | 2,710 | 0 | 中 | **工程权衡最清晰版**：ADR 与实测踩坑记录质量最高 |

## 2. 分支逐一评价

### 2.1 main（基线分支）—— 总分 64

**定位与内容**：项目的起源分支。最大特色是**双 AI 运行时范式并存**：`ai-ui`（后端 Spring AI Agent Loop，工具执行经 resumeToken 暂停-恢复）与 `ai-ui-vercel`（前端 Vercel AI SDK streamText，Promise 内暂停）两个前端共享同一后端业务 API。后端有 YAML 驱动的工具/场景发现（tools.yaml、scenarios.yaml + ToolDiscoveryService）、PlannerService（Plan-Execute 雏形）、AgentState 数据库状态机。业务覆盖 **4 个场景**（导出/导入/新增/修改），是各分支中最广的。

**亮点**：
1. **范式对比的实验价值独一无二**：《会话生命周期行业调研与方案评审》文档对标 AG-UI 协议、CopilotKit、LangGraph、Temporal/Restate durable execution，把 7 个真实痛点（刷新断连、pending 丢失、状态漂移等）映射到业界方案——这是其他分支都没有的**方法论资产**，对真实项目选型极具参考价值。
2. 场景/工具 YAML 化配置驱动，新增业务场景不改代码框架，扩展理念先进。
3. 最早识别并实践"前端工具暂停-恢复"这一 HITL 核心机制。

**落地差距**：
1. **零自动化测试**，验证依赖人工；对话归档类文档占文档总量一半以上，属于过程记录而非交付规格。
2. 两套前端并行维护（10,493 行），真实业务中维护成本翻倍，且 `ai-ui-vercel` 范式下密钥虽经代理注入，但 Agent Loop 前置到浏览器后，工具权限管控、审计都变难——调研文档自己也有结论，生产应收敛到后端 Runtime。
3. 无任务中心（历史任务不可管理）、无作业恢复、无发布冲突检测，业务闭环停留在"单次向导走完"层面。
4. AI 层为纯手工协议（自管 messages、自拼 tool_calls），1145 行的 AiService 巨型类，可维护性差。

**分项打分**：A=70（场景最多但每场景深度浅）｜B=72（双范式探索加分，工程结构一般）｜C=55（无迁移管理、无恢复机制）｜D=40（无自动化）｜E=75（调研文档深但不规格化）｜F=80（范式探索与暂停-恢复原创性强）

**落地建议**：不作为生产底座；其**调研结论**（服务端权威状态、事件驱动、会话三层模型）和 **YAML 场景驱动**思想应被吸收进最终方案。

### 2.2 claude-opus-5.5 —— 总分 74

**定位与内容**：3 个提交一次性成型的"底稿"分支。后端包结构是 6 个分支中**最规范的领域分层**（definition / data / job / task / ai / excel / file / masterdata 按域分包），引入 Flyway 迁移、Caffeine 会话缓存（TTL 30min）、虚拟线程 Agent 循环、AG-UI 风格事件协议（SseRunEmitter）、ToolRegistry 按 @ToolScope 渐进披露 + ToolRisk 风险分级、HITL 管理器，以及完整的 Job/JobItem/ValidationIssue 作业模型与 DependencyResolver 拓扑排序。

**亮点**：
1. **领域建模最工整**：Job（作业）/JobItem（逐项）/ValidationIssue（行级校验明细）三层模型直接可进生产；主数据（Region/Project）独立成域。
2. Flyway 版本化迁移是全部非 main 分支中独有的，数据库演进能力 = 生产必需品。
3. AG-UI 事件协议对齐业界标准，事件可审计、可重放。
4. 风险分级（ToolRisk）+ 作用域（ToolScope）双维度工具管控，比单一标志位精细。

**落地差距**：
1. **无任务中心**——历史任务看不见、恢复不了，业务闭环缺一块（这正是后续 combined 分支补的重点）。
2. 零自动化测试；验证全靠文档记录的 curl 结果。
3. 仅 3 个提交，没有经历"联调-修缺陷"迭代，代码未经过真实运行淬炼（combined 分支的 30+ 个 fix 提交就是证明）。

**分项打分**：A=72｜B=85（结构最佳）｜C=75（Flyway/虚拟线程/HITL）｜D=50｜E=80（五件套规格化）｜F=85

**落地建议**：**以其包结构与 Job 模型为骨架**；但必须叠加 combined 分支的功能补全与缺陷修复。

### 2.3 claude-opus-5.5+deepseek-v4-pro —— 总分 81

**定位与内容**：在 2.2 底稿上迭代 35 个提交的**功能最全版**。新增/修复覆盖：任务中心（统一历史任务列表、状态进度实时刷新、一键恢复向导）、服务端分页、字段级查询条件、导出子集打包下载 + ZIP 批量上传、导入模式（追加/替换）、**发布冲突检测 + OPTIMISTIC_FORCE_INCREMENT 乐观锁**、StaleJobRecoveryRunner **僵尸作业恢复**、JobCancellationRegistry 取消注册表、UI_COMMAND 前端指令协议、配置定义字段编辑 UI，以及 30 余项联调缺陷修复（Hibernate 6.6 集合映射、作业异步竞态、发布 NPE、_meta 列对齐等）。

**亮点**：
1. **生产意识最强**：乐观锁防并发发布、僵尸作业恢复、作业取消真正生效、创建事务提交后再异步执行——这四件事恰恰是 demo 与真实系统之间的分水岭，全部覆盖。
2. 缺陷修复记录本身就是最真实的"落地排雷清单"，每一条都对应一个真实业务中必然踩到的坑。
3. 验证文档记录了 20/20 API 用例 + 浏览器级实测，证据链完整。

**落地差距**：
1. **依然没有任何自动化测试代码**——35 次迭代的回归全靠人工，真实业务中不可持续。
2. AI 层维持自管 Agent Loop（手工协议），未享受到 Spring AI 官方能力红利，与 deepseek-v4-pro 分支形成鲜明反差（讽刺的是分支名里带着 deepseek-v4-pro，但 AI 层重构发生在另一个分支）。
3. 功能堆砌带来复杂度，部分机制（UI_COMMAND 指令协议）与 Spring AI 官方工具通路并存，真实落地需收敛。

**分项打分**：A=88（功能最全）｜B=84｜C=86（乐观锁/恢复/取消/事务）｜D=58｜E=82｜F=84

**落地建议**：**业务功能的集大成者**，最终方案的"任务中心 + 发布安全 + 作业治理"应整体采自该分支。

### 2.4 deepseek-v4-pro —— 总分 83

**定位与内容**：**AI 技术选型最优**的分支。核心重构是"AI 全链路改用 Spring AI 官方能力"：@Tool 注解定义工具（Schema 自动生成）、ChatClient + MessageChatMemoryAdvisor 驱动循环与记忆（H2 持久化，后端重启不丢）、**HooksToolCallingManager 经官方 ToolCallingManager 扩展点**实现 HITL 确认门与工具可见性钩子——删除全部手工协议与手工 Schema。韧性设计：上游断流 90s 自愈重试、确认门等待期间 SSE 心跳保活、SSE 首包 start 事件、平台线程池统一执行器。前端引入 workspaceBus 事件总线 + workspaceContract 契约层，AI 操作与用户点击走同一契约、可独立裁剪。配套 685 行 PowerShell E2E 脚本（22 用例），是**唯一可一键重复执行的端到端验证**。

**亮点**：
1. **"能用框架能力绝不自造"执行得最彻底**：ToolCallingManager 扩展点、ChatMemory Advisor、@Tool Schema 生成均为官方推荐用法，框架升级成本最低——这是真实业务落地时长期维护性的关键。
2. 韧性三件套（断流重试/确认门心跳/首包事件）直击 SSE 长连接在真实网络下的三类典型故障。
3. 文档最全（8 篇：需求/技术/实现/用例/验证/部署手册/AI 设计/接口文档），部署手册+接口文档是交付规格的标配。
4. AI 会话 H2 持久化（刷新+后端重启均不丢），会话连续性方案最完整。

**落地差距**：
1. 无单元/集成测试代码，22 用例脚本只覆盖 API 层"快乐路径+少量异常"，数据校验深度不如 glm 的 JUnit 套件。
2. 发布语义为按配置项整体替换，未实现 glm 的"范围内替换"（同范围数据精准替换），多范围并存场景有数据误伤风险。
3. 种子数据仅 4 个配置定义，业务覆盖演示面偏窄。

**分项打分**：A=82｜B=90（选型与韧性最佳）｜C=80｜D=72（唯一可重复 E2E）｜E=88（文档最全）｜F=90（扩展点用法最规范）

**落地建议**：**AI Runtime 架构应以本分支为准**（官方能力 + HooksToolCallingManager + 韧性三件套）。

### 2.5 glm-5.3 —— 总分 80

**定位与内容**：**测试最扎实**的分支。唯一提交真实自动化测试代码：6 个测试类 38 个 JUnit 用例（AiToolsTest、ImportFlowTest、ExportFlowTest、ConfigDataServiceTest、CatalogServiceTest + BaseIntegrationTest），覆盖"导入全流程（含依赖失败级联）/导出全流程/AI 工具/数据校验"，并配 10 个 E2E 场景记录。AI 层同样走 Spring AI 高层 API（ChatClient/ChatMemory/@Tool 按任务类型分三组披露）。运行时组件完整：EventPublisher 事件广播、SseHeartbeat 心跳、ProgressManager。发布语义为**范围内替换**（事务内先删同范围 PUBLISHED，再把 STAGED 提升为 PUBLISHED）。8 个种子配置覆盖全局/地区/项目三层级与全部字段类型。

**亮点**：
1. **38 个自动化测试 = 唯一可持续回归的资产**；真实业务落地第一优先级就是可回归性，该分支唯一达标。
2. "范围内替换"发布语义是 6 个分支中**业务正确性最高**的发布实现：多地区/多项目并存时互不误伤。
3. 种子数据设计最有业务演示价值（8 配置 × 三层级 × 全字段类型 × 跨配置依赖引用）。
4. REST 与 AI 工具共用同一服务层（单一事实源），"去掉任一方另一通路完整可用"的解耦验证思路严谨。

**落地差距**：
1. 前端规模最小（2,223 行），交互打磨与边界处理（步进条状态映射、分页等）不如 deepseek/combined 分支。
2. AI 会话为服务端内存记忆，后端重启即丢（其他分支已做到 H2 持久化）。
3. 迭代历史最短（6 提交），联调淬炼程度低；无部署手册与独立接口文档。

**分项打分**：A=80｜B=82｜C=76｜D=85（唯一自动化套件）｜E=78｜F=82

**落地建议**：**测试套件与发布语义应采自本分支**；测试金字塔策略（38 JUnit + E2E 场景）应直接继承并扩充。

### 2.6 kimi-k3 —— 总分 79

**定位与内容**：**架构决策记录（ADR）质量最高**的分支。技术方案文档含 7 条带权衡的 ADR（D1-D7），并留下两条高价值实测结论：① **deepseek-flash 思考模式回填 assistant 消息必须携带 reasoning_content，缺失即 400——与旧模型规则相反**（实测报错原文存档），为此以最小侵入方式实现框架补丁 ReasoningAwareOpenAiChatModel（同名包 Override 单一方法，Javadoc 注明升级后评审移除）；② `parallel_tool_calls=false` 的框架限制与 429/5xx 指数退避重试策略（流式已产出内容不重试）。工程细节：作业在事务 afterCommit 后异步触发（修复静默失效竞态）、同任务同 kind 作业幂等拒绝重复提交、依赖失败自动级联 SKIPPED、删除任务级联清理、navigate_to 等待页面就绪消除上下文竞态。验证记录完整（API 12/12 + AI SSE 7/7 + 浏览器 7/7）。

**亮点**：
1. **ADR 与踩坑记录 = 最真实的技术资产**：模型兼容性结论全部来自实测并附报错原文，真实业务接入推理模型时这类记录能省数天排查时间。
2. 幂等（重复提交返回现有作业）、级联跳过、事务后异步，三项工程细节处理到位。
3. 明确的权衡声明（如"轮询 vs SSE：本规模选轮询，后续可平滑升级"），决策可追溯。
4. 密钥治理完整（环境变量注入 + pre-commit 钩子 + 历史密钥移除提交）。

**落地差距**：
1. 零自动化测试代码，验证依赖一次性 curl/浏览器记录，不可重复回归。
2. AI 会话内存存储（TTL 不持久化），重启丢失；作业进度用轮询而非 SSE（虽有权衡声明，但实时性体验弱于 deepseek/glm 分支）。
3. 业务场景仅导出/导入两类，无配置定义编辑 UI；前端无 Tailwind 化前的样式债清理记录。

**分项打分**：A=78｜B=86（ADR 与兼容性补丁）｜C=80｜D=60｜E=85（API 契约独立成文）｜F=85

**落地建议**：**模型兼容性结论与 ADR 方法应全量吸收**；会话持久化与 SSE 进度需向 deepseek 分支看齐。
