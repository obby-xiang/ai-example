# AI Conversation Recovery and Content Remediation Design

日期：2026-11-08
依据：`docs/research/调研-AI对话重复恢复与导出内容治理-2026-11-08.md`
状态：推荐设计，施工前按 Task 0 证据确认根因；不代表已实施或已验证。

## 1. Intent

为普通终端用户修复创建导出流程中的重复回复、恢复分叉、断轮、过程卡泛滥和技术文案，同时建立“真实内容一致”而非“脚本自报成功”的验收门禁。

## 2. Goals

- 同一用户意图在同一 run 完成可完成的创建、配置、条件和启动确认。
- 实时、刷新、重连和 history 中的正文、卡片、顺序和状态一致。
- 重复事件、重复刷新和重复决策不增加消息、卡片或业务副作用。
- 用户只看到当前需要操作或有业务价值的信息。
- 审查者可以直接比较完整内容和证据，不依赖脚本绿色摘要。

## 3. Non-goals and anti-goals

- 不重写整个 AI 面板，不引入新事件框架、数据库、消息队列或依赖。
- 不把所有 UI 草稿、展开状态都改成事件溯源。
- 不靠继续堆长提示词代替确定性宿主流程。
- 不通过隐藏真实失败、删除用户草稿、清空镜像或降低断言制造通过。
- 不按特定中文话术、任务号、配置编码或当前模型名称硬编码生产分支。
- 不把“所有 AI 对话场景已覆盖”作为本专项可自动继承的结论。

## 4. Global constraints

- AI 会话及运行数据仍只在既有 Redis 边界；模型配置和用户反馈之外的 AI 数据不得访问数据库。
- Redis 数据遵守现有 24 小时滑动过期和跨实例节流；新增键不是本设计目标。
- 保持 OpenAI 通用协议、现有 SSE/history 兼容和多实例语义；新字段仅允许 additive。
- 优先复用 runId、entryId、segments、toolCallId、pending、ledger 和现有公开 API。
- 刷新只断开连接，不等于取消；显式停止继续走独立取消入口。
- 普通测试代码不因本专项新增或修改；独立验证脚本与测试文档按用户授权维护。
- 每次独立验证只执行一个场景/变体，复杂场景至少三个独立新会话。

## 5. Recovery design

### 5.1 Canonical identity

逻辑身份分两层：

```text
UI 助手消息：sessionId + runId + 既有 messageId（当前为 assistant-{runId}）
持久化 part：(entryId, segments[].seq)；工具：toolCallId
普通 SSE 幂等与续传：seq；既有压缩事件：eventId（仅此用途）
```

- 当前产品可以把同一 run 的多条持久化 ASSISTANT 条目投影为一个带有序 parts 的 UI 助手消息，不能再给同一 run 克隆第二个 UI 助手。
- 优先复用实时 SSE 已有的 `messageId` 和后端 entryId。history 当前未透出 entryId；若 Task 0 证明跨来源恢复需要它，必须通过 additive history 字段透出并同步 `AiHistoryMessage`，不得把它当作已经可消费字段。
- `history-数组下标` 和本地临时 ID 只可用于旧版展示，不得作为跨来源业务身份。
- 旧数据缺稳定身份时保留 legacy 展示路径，但不得凭旧 ID 克隆到权威历史。

### 5.2 Full reload versus incremental resume

**页面刷新/全量恢复：**

1. 读取权威 history/run/snapshot。
2. 同一 run 作为整体替换并重建有序 parts。
3. 再按最后已应用 seq 接续活动流。
4. 不追加一份未匹配的镜像助手。

**活动连接/增量恢复：**

1. 只处理 `seq > lastAppliedSeq` 的事件。
2. 普通 SSE 以 seq 幂等，工具以 toolCallId 幂等，既有压缩事件以 eventId 幂等；持久化 part 需要跨来源对账时使用 `(entryId, segments[].seq)`。
3. 旧 generation/revision 不得覆盖新现场。
4. 副作用由 pending/ledger/业务幂等单独保证，不能只靠 UI 去重。

### 5.3 Mirror role

sessionStorage 镜像仅是 last-good 缓存：

- 权威 history 可用时，不以镜像构造第二份事实。
- 镜像无法匹配时不得直接克隆插入。
- history 暂不可用时只保留一份镜像和真实恢复状态，不能显示两份互相矛盾的版本。
- 用户输入草稿、表单草稿与助手历史分开恢复，不能因清理镜像而丢失用户输入。

### 5.4 Single projection

实时、history 和镜像使用同一套有序 parts 规则：正文、reasoning、工具、表单、事件按稳定身份与顺序投影。禁止按“同 run + 位置相邻 + 文本前缀”猜测复制或合并。

## 6. Host workflow design

创建/导出常规流程由宿主根据真实步骤和缺口推进：

```text
create_task 确认
  → 批准后打开对应向导
  → 仅缺失时选择配置项
  → 仅缺失时收集筛选条件
  → start_export 确认
  → 批准后启动一次作业
```

规则：

- 明确创建意图直接出现创建确认，不先文字追问。
- 已知配置、条件、标题不重复询问；标题使用真实默认值。
- 创建、配置和启动属于同一原始意图，不要求第二次聊天输入。
- 导航、选择、确认步骤等自动成功过程只更新业务页面，不重复生成对话过程卡。
- HITL 是启动确认的唯一操作入口，正文不重复要求确认。
- 任务号、配置项、条件和结果只在一个合适的卡片或最终回复中表达一次。
- 模型负责语义理解和真实歧义，不负责机械步骤编排。

## 7. Copy and presentation design

- 用户侧统一使用“配置项”；“宿主、回灌、帧、影响面暂不可估、创建≠执行”等不得作为普通用户文案。
- 空白任务名、未决定条件等无行动价值字段不占位展示。
- 未知行数不阻碍导出时不显示模糊风险句；真正需要用户决策的未知必须给出具体、可行动说明。
- 创建和启动说明使用自然业务语言，例如“将导出 4 个配置项”。
- 相同条件紧凑表达，例如“4 项均不筛选，将导出全部数据”。
- 表单标题按 purpose 显示“选择配置项”“设置筛选条件”等，不共用“请填写以下信息”。
- 示例和业务名称来自真实定义，不编造配置、地区或项目示例。
- 所有动态文案同时审查中英文、空值、未知值、异常值和旧数据兜底。

## 8. Verification design

采用“流程阶段 × 事件边界 × 用户状态 × 恢复方式”矩阵，不用固定 sleep 代替边界：

- 输入草稿、首帧前、正文前、reasoning 边界。
- 工具/HITL/表单刚到达、未操作、提交在途、已受理未终帧。
- 工具结果已写入、后续正文未生成、DONE/history 落账交界。
- 连续刷新、关闭重开、重连、随机种子刷新和乱序 history。

每次保存并比较：

- 用户消息数量与原文。
- 完整助手正文、逻辑消息数、parts 和顺序。
- 卡片稳定 ID、类型、数量、状态、动态字段和按钮。
- 刷新前后实际 DOM 可见内容。
- history/run/SSE 与界面的一致性。
- 任务、作业、文件内容、Redis 键/TTL、日志和清理。

自然语言采用语义不变量，不要求逐字固定；但重复段落、内部术语、多余追问、缺失操作卡、重复事实均直接 FAIL。脚本 PASS 只限其声明范围，整项 PASS 必须有 API 内容、浏览器内容、业务副作用和恢复一致性证据。

## 9. Review design

每批必须有：

1. 根因和规格对照，逐文件逐 hunk 审查。
2. 关联调用链审查，覆盖实时、history、镜像、快照和业务副作用。
3. 独立审查者重新计算内容数量、顺序和哈希，不只阅读施工摘要。
4. 生产代码实际编译，脚本 `node --check`，Java 使用 IDEA 默认规则格式化。
5. 开发规范 ledger 与提交门禁；未通过不得提交推送。
6. 动态验证按单场景单变体执行，失败保留，NOT_RUN 不得写成 PASS。

## 10. Alternatives

- A：只改提示词、文案和局部去重。拒绝作为独立方案，因为身份和职责问题保留。
- B：采用本文现有链路收敛。保留基础设施，修复身份、恢复、流程、文案和验收。
- C：全事件驱动框架重写。当前不采用，因为现有 Redis/SSE/history/pending/ledger 已具备大部分基础，重写成本和回归风险过高。
