# create_task 结构化业务引用与确定性解析设计

日期：2026-11-25

## 背景与问题

真实模型在三个独立会话中接收“导出cny货币字典”，三轮 `create_task` 均缺少 `defCodes` 且 `conditions={}`，随后出现额外配置选择卡；其中一轮最终全量导出。历史同类场景曾成功。

回归点是 `67c20a3a` 删除 `completeCreateTaskArguments` 后，创建入口不再有任何“用户已明确的信息不得丢失”的保障。旧实现通过中文正则和关键词解析用户原文并改写工具参数，存在双意图引擎、多语言/否定/同名歧义和场景拟合问题，不能恢复。

当前链路中：

- 模型负责从自然语言生成 `defCodes/conditions`，可能因不知道内部编码而传空。
- 预检只检查载荷形状，缺 `defCodes` 与 `conditions={}` 均可通过。
- 创建遗漏纠正只检查是否调用 `create_task`，不覆盖“已调用但漏参”。
- 空槽位在创建后触发表单，把模型遗漏转嫁给用户。

## 目标

- 模型只负责提取用户明确表达的业务引用，不要求它知道内部配置编码或字段编码。
- 宿主只处理模型已经结构化的引用，确定性地解析为现有 `defCodes/conditions`。
- 用户已明确的配置和条件不得因“模型不会映射内部编码”而被省略或推迟到创建后。
- 无法唯一解析的信息在创建前集中收集；批准创建前不产生任务、条件或作业副作用。
- 保留下游候选草案、HITL、向导、条件物化、启动确认及转录协议。

## 非目标与禁止事项

- 不恢复 `TaskSlotParser`、`TaskIntent` 或任何用户原文正则/关键词/停用词解析。
- 不增加第二次模型纠正请求，不通过提示词重试掩盖结构问题。
- 不按模型、供应商、具体配置、字段、CNY 或测试话术增加特例。
- 不做模糊匹配、包含匹配、相似度匹配，不任意把值转为大写。
- 不新增依赖、不新增模型调用、不改变创建和启动的 HITL 边界。
- 不借业务任务、作业或配置表保存 AI 会话状态。

## 方案比较与选择

### 方案 A：结构化业务引用 + 宿主确定性解析（选择）

模型传配置/字段的编码或名称等结构化引用，宿主通过现有 `DefinitionCatalog` 唯一解析为内部编码。语义理解只发生在模型边界，宿主不再理解自然语言。

### 方案 B：允许创建前只读查询（不单独采用）

修改提示，允许模型用 `list_config_defs/get_config_def` 查询后再创建。修改较小，但仍完全依赖模型主动查询和正确续接，无法解决已调用但漏参。

### 方案 C：创建前追加一次模型复核（不采用）

不解析原文，但增加延迟、 token 和恢复分支；已有纠正链证明第二次请求仍可能不遵循，且会扩大正文与转录复杂度。

## 创建入口契约

模型可见的创建参数改为业务引用形态，示例：

```json
{
  "type": "EXPORT",
  "defCodes": ["货币字典"],
  "conditions": {
    "fields": [
      {"fieldCode": null, "operator": "EQ", "value": "CNY"}
    ]
  }
}
```

字段语义：

- `type/title/openWizard` 保持现有语义。
- `defCodes` 为必填数组；每项是配置编码或配置名称。空数组只表示用户没有提及配置，不表示模型不会解析。
- 用户提到配置但模型不知道内部编码时，必须传用户给出的名称或编码，不得省略。
- EXPORT 的 `conditions` 仍必传。单配置时，`{}` 只表示用户没有给出条件，不表示模型无法确定字段，也不表示明确全量。
- 多配置继续沿用现有契约：保留全部已知配置引用，创建载荷 `conditions={}` 仅表示逐项条件不在创建载荷中承载，后续由一次 `set_conditions(items)` 物化；该分支不解释为“用户未给条件”，本轮不重写多配置条件协议。
- 用户明确全量时，本轮继续走现有 `conditionMode=ALL` 条件收集与明确不设链，不新增第二种全量表达，也不把 `conditions={}` 自动解释为全量；是否减少该场景现有卡片不属于本批目标。
- `scopeKeys` 不属于本轮引用改造，保持现有结构化协议和校验，不根据 `fieldCode=null` 推断范围键，也不删除用户已明确给出的范围条件。
- 创建入口的 `fieldCode` 承载字段引用：可传字段编码、字段标签或 `null`。用户给了条件但字段未知时传 `null`，不得因此丢弃整个条件。
- `operator/value` 仍由模型按用户意图结构化；宿主不从原文补operator或值。
- IMPORT 不允许携带条件，现有限制不变。

为避免给 `create_task` 增加专用 Schema 对账豁免，模型侧与执行侧保留现有 `defCodes/conditions.fields.fieldCode` 字段名，仅扩展创建入口的值语义为“编码或名称引用”。canonical 化仍写回同名字段，因此只有一套 JSON 协议，下游历史展示、执行和持久化草案无需区分两种字段名。该调整只改变创建工具的值契约，不改变其他工具中这些字段的现有编码语义。

## 确定性解析规则

在 `SpToolCallingManager.bindPendingArguments` 的创建入口、预检和 HITL 之前完成一次解析。输入仅为结构化工具参数，不读取用户原文。

### 配置引用

- 复用 `DefinitionCatalog/SlotDefinition` 的 `code/name` 快照。
- 编码按现有大小写安全口径精确匹配；名称去首尾空白后精确匹配。
- 同一引用恰好命中一个定义时转换为权威 `defCode`。
- 多命中、零命中、空引用和目录不可用均为不同的安全失败原因，不得静默删除引用。
- 当前目录没有配置别名事实，不臆造别名匹配能力。

### 字段引用

- `fieldCode` 非空时，按字段 `code/label` 精确匹配；唯一命中才转换为权威 `fieldCode`。
- `fieldCode=null` 时，只允许在该配置恰好一个主键字段的情况下解析到该主键；否则保持未决并进入创建前收集。
- 多字段、多主键、字段零命中或多命中均不得猜测。
- 枚举字段存在 `optionValues` 时，值可按唯一精确或唯一大小写安全匹配归一到权威选项；无唯一匹配则未决。
- 非枚举字段保留模型给出的值，不做任意大小写转换、trim 之外的改写或数据内容猜测。

### canonical 输出与失败

- 全部可解析时，生成现有 `defCodes` 和 `conditions.fields.fieldCode`，再执行现有 `ToolPreflightService`。
- canonical 参数进入 pending、HITL、转录和 `RunContextRefresher`，下游无需理解 `defCodes/fieldCode`。
- 任一引用未决时，不得把未决项改成“未提及”、空对象或明确全量，不得进入创建确认或执行任务。
- 解析失败不得吞异常后沿用原参数；目录读取失败必须可观测并失败关闭。

## 创建前集中收集

复用现有宿主生成式表单和 park/resume 机制，新增一个通用的创建详情收集用途，而不是恢复创建后连续补卡：

- 只展示未决的配置引用、字段引用或枚举值；已解析项不回问。枚举值未决时使用该字段的权威 `optionValues` 提供选择，不允许自由文本绕过唯一匹配。
- 多未决项尽量由同一张创建详情卡收集，提交后对全部引用和值重新执行同一确定性解析和预检。
- 用户取消则不创建任务；用户提交非法或仍有歧义的值则保持未决并显示真实原因。
- 表单结果与原始 `type/title/openWizard` 绑定到同一 pending 和 run，沿用现有多实例、TTL、取消和恢复语义。
- 全部明确时只出现原有创建 HITL，不出现该收集卡。

“创建导出配置任务”这类用户确实未提供配置/条件的请求，仍可在创建后沿用现有向导收集；本设计只把“模型已经提取但宿主无法唯一解析的引用”前移，不把所有空槽位一律阻断创建。

## 提示与工具描述同步

- 将“无法唯一映射时省略 defCodes”改为“未提及时才传空；提及时传结构化引用，由宿主解析”。
- 将“无法确定字段时传 `{}`”改为“保留条件值并传 `fieldCode=null`，由宿主解析或收集”。
- 删除“需要确认编码也先创建、由宿主后续补充”与“已知槽位不得推迟”的冲突口径。
- 只读目录查询仍不是创建前置；解析由宿主基于结构化引用完成，不要求模型额外调用工具。

## 影响面

- 创建工具模型 Schema 与描述：`AiTools.java`、`tools.yaml` 及对应提示规则。
- 创建入口绑定：在 `SpToolCallingManager` 前增加单一引用解析组件，复用 `DefinitionCatalog`。
- 创建前未决收集：复用现有生成式表单、pending park/resume 和安全业务码/i18n。
- 既有测试中将“导出CNY货币字典保持空参数且预检通过”锁为预期的断言必须按新契约重写，不得保留回归行为。
- 下游 `ToolPreflightService` 的 canonical 校验、`RunContextRefresher`、向导和导出执行原则上不改；若施工发现必须改动，需重新记录原因和边界。

## 验收口径

只执行独立单点，不批量或循环跑普通测试；真实模型场景逐轮独立执行。

1. 结构化解析单点：编码、名称、字段标签、唯一主键、大小写安全枚举、零命中、多命中、目录失败、非枚举值不改写。
2. 创建入口单点：引用在 preflight 前 canonical 化；未决不进入创建 HITL、不产生任务；取消和恢复幂等。
3. 真实模型独立三轮逐字输入“导出cny货币字典”：每轮创建 HITL 前 canonical 参数必须为 `defCodes=["CURRENCY"]` 和 `code EQ CNY`；不得出现配置选择或条件补卡。
4. 每轮创建批准后只创建；启动批准前作业为零，启动批准后恰好一个 COMPLETED 作业；实际文件仅包含 CNY。
5. 对照场景：未提及配置、配置名称歧义、无条件、明确全量、多配置、字段无法唯一解析；不得把未决静默变成全量。
6. 每轮核对 run/history/工具卡和刷新一致性，无 `AI_TRANSCRIPT_INCOMPLETE`、工具卡丢失或错误“已停止”。

静态审查、单点测试、真实模型和浏览器证据分别记录；未执行项写 `NOT_RUN`，不得以历史成功记录代替本版验收。
