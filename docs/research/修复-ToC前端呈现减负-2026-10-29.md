## 二、逐项：根因与修法

### 2.1 同一事实只留一个提示面（项 1）

- **根因（提示面重复）**：面板顶部是**并列**的一排提示位（专属 Alert ×5 + 通知槽 + 回执位），
  各自独立判据；同一条事实被两条链路各写一次（池饱和：`poolSaturated` + `setNotice`；断流：
  `streamInterrupted` + `setNotice('ai.notice.interruptedKeep')`），于是同屏两句话。
- **根因（同步/回执双写）**：`workspace_changed`（人手动动作）与 `ui_event_result`（AI 驱动动作回执）
  是两条独立事件，用户既看到「工作区已同步：…」又看到「AI 驱动工作区：…」。
- **修法**：渲染层两张小表 —— `noticeCoveredByAlert`（只覆盖**同义**两条，避免误伤"取消/重试/反馈失败"
  等没有专属 Alert 的通知）与 `uiEventReceiptVisible`。**信息不丢**：断流的"已生成内容保留"在断流 Alert
  正文里；回执在同步反馈退场后照常显示。
- **R1 订正（I-1）**：首版让位判据不看 `handled` ⇒ 失败回执（`handled=false` 且**从不**广播
  `workspace_changed`）会被一条**别的**动作的「工作区已同步」永久压掉。改为「成功回执 **且** 有同步反馈
  才让位」；失败回执始终显示（同一提示面原则只针对**同一事实**，不针对"都有提示"）。
- **R1 订正（M-3）**：断流去重补 `interruptedKeepShort`（接管耗尽路径写的码）—— 两个码同义，必须一并覆盖。

### 2.2 挂载准备中出阶段条（项 2）

- **根因**：批次3「阶段条退场」把 `CompactionStatus` 从模板摘掉，store 侧的 `compactionPhase` /
  `preparingRun` 仍在维护 ⇒ **有状态、没出口**；恢复/挂载期用户只看到一条呼吸点，无法区分
  "在压缩上下文"与"服务端在建上下文"，也没有「准备中」的重试出口。
- **修法**：`stageBar` 计算属性只产出**进行中**两态（`compacting` / `preparing`），模板重新挂
  `CompactionStatus`；`done` 态不渲染（不与呼吸点重复报"压缩完成"）；`preparing` 的重试直接接
  既有 `ai.retryPreparing()`（store 不动）。

### 2.3 GF 提交后保留 submitting 只读态（项 3）

- **根因**：`liveForm` 只认 `filling / submitting`；提交成功立刻 `status='submitted'` ⇒ 表单从卡体消失，
  而段的 `requiresAction` 与 `pending/running` 要等结局帧才变 ⇒ 这段时间卡体**既不是表单也不是只读卡**。
- **修法**：新增纯函数 `isFormAwaitingOutcome(part)`（`utils/blocks.ts`）+ 呈现层 `readOnlyLike`。
  只读体分支改判 `readOnlyLike`：同一张表单（`cardFormSpec`）+ 段上的 `submittedValues` 回填，
  零操作按钮；`cardStatusOf` 在该期间返回 `submitted`（「✓ 已提交」）⇒ 提交前后与结局后**卡头状态同一字**。
- **边界（不声称）**：判据依赖段上有 `submittedValues`（`writeSubmittedValues` 写入）。他端提交 / 409 幂等
  这类"本地没有提交值"的现场**不伪造同值**，仍走原路径等结局帧。
- **R1 订正（I-2）**：回填判据原只认 `readOnlyStateOf === 'submitted'`，于是结局一落成 `failed` /
  `expired` / `rejected` / `notExecuted`，卡体就回落成 schema 默认空表单，而卡头摘要
  （`generativeFormSummary` 读同一份 `submittedValues`）还写着「导出范围 华北」—— 同一张卡自相矛盾，
  也违背本项"结局后形态不变"。改为「有 `submittedValues` 且非 `cancelled`」一律回填；
  `cancelled` 是唯一例外（F9：取消 = 从未提交，不得回填半成品值）。`expired` 是真实可达态
  （`frontend_tool_result` 丢失、done/error 先到 ⇒ `expireResidueToolParts` 把仍 pending 的段收成 expired）。

### 2.4 失效确认卡禁用决策（项 4）

- **根因**：`runExpiry` 到期只把「已失效」提示画出来，按钮判据里没有它 ⇒ 允许一次注定失败的提交。
- **修法**：`runExpired` 参与两钮与勾选框的禁用；**拒绝也一并禁用**（决策同样送不到），
  出口保持既有「刷新状态 / 新建会话」。未到期时两钮照旧（负例已锁）。
- **R1 订正（M-1）**：勾选框禁用后，紧邻的「请先勾选确认项」提示行成了照做不了的死指令 ⇒
  `v-if="gateNeedsAck(part) && !runExpired"`（未失效时提示行照旧，负例已锁）。

### 2.5 展开按本轮未终态（项 5）

- **根因**：`turnStillOpen` 只认 `ai.loading`。B1 之后等人决策的一轮是 `loading=false && suspended=true`；
  点批准那一拍段已切只读、连接尚未建立 ⇒ 卡瞬间折叠，重连后又展开（闪一下）。
- **修法**：判据换成「本轮未终态」= `loading || suspended` ∨ 决策在途 ∨ GF 提交在途，
  仍限定末条消息（历史卡不因新轮被展开）。手动折叠仍最高优先（既有三态语义不动）。
- **R1 订正（I-3）**：首版写 `runPhase ≠ idle`，把 `recovering` 也算进来 —— 而 `loadHistory` /
  `retryRestoreSnapshot` / `returnToActiveRun` 在 `restoringRecovery` 期间**同步**把镜像消息落屏，
  于是刷新/重新载入时末条消息里的已决只读卡先被强制展开、HTTP 回来再折叠（本批要消的那类闪动）。
  改为 `loading || suspended`（不含恢复中）；批准瞬间的闪动仍由「决策在途 / GF 提交在途」覆盖，
  不依赖 `recovering`。`partMemo` 的展开态依赖随之由 `runPhase` 换成 `suspended`（`loading` 本就在表内）。

### 2.6 不可提交表单字段只读（项 6）

- **修法**：`FormRenderer` 增 `locked`（与 `readonly` 分开：readonly = **已决回放**、零操作行；
  locked = **待决但此刻交不出去**）：字段 `disabled` 但按只读配色（值可读）、提交禁用、
  一行说明 `ai.gf.lockedHint`、**取消仍可用**（本地收口出口）。`AiPanel` 传 `:locked="runExpired"`。

### 2.7 技术词只进诊断（项 7）

- 删：首屏「会话 <id>」「数据版本 <n>」两段（收进 `panel-diagnostics` 折叠区，排障仍可取）；
  `contextSynced` 的 `v<n> · <source>` 括注（版本号/来源是机读词）；
  池饱和文案里的「挂起专用线程池容量 N」（改说"同时等待的对话已达上限"，数量不再当卖点）。
- 改：`ai.notice.redisUnavailable`（去 `（Redis）`）、`ai.notice.missingRunId`（去 `runId`，改说"这一轮已经
  不在进行中，结果没能送回"）、`ai.panel.toolResult.TOOL_ALREADY_CLAIMED`（去"执行实例"）。
- **R1 订正（M-2）**：漏了两条**未被抑制**的池饱和通知（`ai.notice.poolSaturated` /
  `poolSaturatedWithSize`）—— 503 无 JSON body 时走的就是前者 ⇒ 用户仍会读到「挂起池已饱和（容量 N）」。
  两条双语改写为「等待处理的对话较多 / 已达上限」；模板上已失效的 `{size}` 死参一并删除。
- 留：断流/降级/失效的人话说明、不可撤销的高危确认（`ai.hitl.irreversible` / `publishIrreversible`）一字未动。

### 2.8 硬编码走 locale（项 8）

- `UploadHandoffCard`：兜底入口名（原 `'上传 xlsx / zip'`）与三态说明（degraded / missing / unavailable）
  全部 `t()`；`reason` 仍是后端数据（数据不是文案），有就用、没有才回落本地人话。
- `ContextPopover`：`'上限未知'` → `t('ai.context.limitUnknown')`。
- 新增键全部**双语同批**（`i18n-bootstrap#B1/B3` 键集与占位符门禁已过）。

### 2.9 R1 另案两条（状态批 M-3 / 本批 M-4）

- **M-4（提交在途仍报「等待你操作」）**：`waitingForAction` 只看 `requiresAction`，而 GF「已提交、结局未到」
  这段人这一侧已经没有待办（卡头「✓ 已提交」、卡体只读表单、无 chevron）⇒ 排除 `isFormAwaitingOutcome`，
  该窗口归**既有**工作中语义（呼吸点），不新增任何状态或规格措辞。
- **状态批 M-3（回稿与恢复提示重复）**：**状态批的自动恢复真的接管了本条**时，面板不再把原稿塞回
  输入框（那会与恢复提示重复、并让用户以为消息没发出去）。判据落在既有回稿流程的最后一道守卫
  （`inputText !== ''` 之后），**三条件同时成立**才算"被自动恢复接管"：
  ① `ai.loading`（仍有连接在跑）；② `result.outcome === 'interrupted'`（接管/断流，不是真失败）；
  ③ `result.userMessageId != null && ai.messages` 里**找得到这条消息**（本条气泡仍在）。
  **为什么不能只写 `ai.loading`（终审 I-A 的返修）**：`loading` 只表示"**有任何一轮**在跑"，而两条
  真实可达分支恰恰不是"本条被接管"——
  · 409 `SESSION_BUSY` + 接管回滚（R-04）：本次乐观用户/助手气泡被一起删掉，`settleOutcome` 因轮次身份
    被换而返回 `interrupted`，接管方同时置 `loading=true` ⇒ 只按 `loading` 跳过回稿，等于把
    「草稿只留在输入框一处」变成"零处"（提示还说"这条消息没有发出去"）；
  · `not-sent`（`stopping` 等待期间被续收插队）：连用户气泡都没有，同样会被吞。
  收窄后：自动恢复接管且消息仍在 → 不回稿；409 回滚 / `not-sent`（`userMessageId=null`）→ **照旧回稿**；
  真失败（`error`，`loading` 本为假）→ 回稿/聚焦/编辑锚点一字不变（三条控制组单测已锁）。
  **有效前提（不声称）**：本条去重只在**状态批的"自动恢复接管"真正落地并保留本条气泡**时生效；
  本树目前首帧超时只写一条通知、`send()` 随后复位 `loading`，所以真实首帧超时路径仍走原回稿。
  （"输入框占位仍写「挂起等待中…」"属 M-4 同一窗口的第三块面，本批未动，登记后续。）

## 四、边界与不声称

- **真机未执行**：本批全部证据为 jsdom 单测；**没有任何真机/浏览器实测**（无真机环境），
  因此"批准时不再折叠再展开""提交后不再闪卡""阶段条不跳字"三件事都**只在单测层面成立**，
  像素级表现与真实 SSE 时序未取证。
- **`stores/ai.ts` 未改**：所有判据都是渲染层现算，因此**不含**任何状态机修正。
  （R1/M-4 之后 GF 提交在途不再报"等待你操作"，但那是 `waitingForAction` 的呈现判据，不是 store 状态。）
- **提示面抑制只覆盖同义两组**（池饱和 / 断流，断流含两个码）；其余"疑似重复"未做通用去重
  （避免误伤不同事实）。**失败回执从不因「工作区已同步」让位**（R1/I-1）。
- **项 3 依赖 `submittedValues`**：他端提交 / 409 幂等这类本地没有提交值的现场仍是"空档 → 结局帧"
  （不伪造同值），只是不再回落到普通工具卡（`requiresAction` 仍为真）。
- **项 3 的"非成功结局保留值"只锁到呈现层**（R1/I-2）：`expired` / `failed` / `rejected` / `notExecuted`
  都按段上的 `submittedValues` 回填；若上层在收尾时**清掉** `submittedValues`，本层无从回填（未加另一份缓存）。
- **项 7 只清 AI 面板面**：`app.footer.dataVersion`（全局页脚）与其它页面未动，属本批范围外。
- **项 6 的 `locked` 不带上传闸**：附件控件已因 `disabled` 一并锁死，但未区分"运行态失效"与"浏览器不支持"
  两种成因的说明（仍各自走原提示）。
- **M-5 未做（只登记）**：sheet-preview 的「应用」与 upload-handoff 的「选择/放弃」同样走
  `frontend_tool_result`，`runExpired` 未接入（`locked` 只给了 GF）。同一类"点了必然送不到"，本批按
  「不扩散」未改。
- **M-6 未改（口径取舍）**：被抑制的池饱和通知原是 `error`（红），承接它的 `alert-pool-saturated`
  是 `primary`（蓝）—— 严重度观感与"已经失败"不完全一致，属既有色族规则，本批不改色。
- **回稿跳过判据（状态批 M-3，终审 I-A 收窄后）的边界**：只有「`loading` + 结局 `interrupted` +
  本条 `userMessageId` 在 `ai.messages` 里仍找得到」三件同时成立才不回稿。**不声称**它覆盖所有"恢复中"
  的文案去重：409 接管回滚 / `not-sent` 明确按「回稿」处理（宁可草稿回到输入框，也不让它凭空消失）；
  `error` 路径 `loading` 本为假，回稿逻辑一字未动。
- 阶段条的秒数是"服务端 elapsed 折算锚点 + 本地流逝"，挂载后可能比 store 值多走 1 秒（用例按区间断言）。
