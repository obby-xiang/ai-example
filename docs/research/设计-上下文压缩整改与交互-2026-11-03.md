## 1. 目标与边界

### 目标

1. 压缩在真正需要时能够触发，不因状态机空操作或滞回永久失效。
2. 发给模型的工作上下文可以压缩，但用户可见/可审计的原始会话不得因此被静默删除。
3. 当前页面、刷新恢复、停止、异常和多实例场景对“是否压缩成功”有一致事实。
4. 压缩状态归属于具体助手回复，不用全局顶部阶段条代替消息状态；压缩完成事实落在该回复消息流的真实时序位置，不是回复属性或页脚标签。
5. 清理死状态、重复职责和无收益载荷，避免继续堆叠机制。

### 非目标

- 不重做 AI 面板整体视觉。
- 不新增“停止压缩”独立按钮、压缩设置页或默认展开的摘要详情。
- 不在首轮引入便宜摘要模型、分块并行等新配置面。
- 不把多实例、Redis Cluster、HITL、取消和身份隔离当成过度设计删除。

## 2. 当前状态与交互事实

### 消息级状态

当前助手消息元信息行主要有两种呼吸状态：

- `工作中…`：蓝色呼吸，正在生成、工具执行、提交后等待结局等。
- `等待中…`：琥珀色呼吸，存在需要用户处理的 HITL/表单/预览/上传交接卡。

完成或异常时还可能出现：`已停止`、`已截断`、时间戳、继续、重试本轮、错误卡等。继续/重试在主动停止轮中的缺陷由停止专项处理。

### 顶部阶段条

当前顶部还有两类独立阶段：

- `正在压缩上下文 · 已用 N 秒`：只有真实 L2 摘要调用出现；L1/L3 和 MemoryWindow 当前静默。
- `正在准备本轮回答 · 已用 N 秒`：已 start、快照未建的准备窗口，带“立即重试”。

顶部另有身份/恢复/断流/池饱和/通知、AI 页面操作条等。它们的保留、合并或退场属于独立“顶部提示专项”，本压缩交互只处理压缩阶段条，不顺带改其他提示。

### 当前压缩结果展示

- L2 历史摘要恢复后可能出现“较早的对话已压缩”灰色 synthetic 条。
- L1 刷新后可能把 `[工具结果已清除：…toolCallId=…]` 直接显示在工具卡。
- L3/窗口裁轮没有专属边界，旧轮可能直接消失。
- `CompactionStatus` 的绿色完成分支在 AiPanel 当前映射中不可达。
- 目标交互不再使用 synthetic 灰条或回复页脚 chip 表达压缩结果，而是在该消息的 parts 时序中放置流程事件节点；同一事实只表达一次。

## 3. 功能与数据整改清单

### 3.1 触发链与记忆窗口

1. **L1 空操作不得阻断升级**
   - 当前每次最多升一级，但 L1 无可清理时不推进状态，纯文本会话可长期停在 L1。
   - 拟改为：当前级没有实际工作时允许尝试下一级；每一级都以真实效果和成本决定是否执行。
2. **滞回不得永久锁死**
   - 当前压缩后可压缩历史仍 ≥60% 时可能一直不解锁，硬越窗也受抑制。
   - 拟改为：滞回只抑制无意义同级重复，不阻止级别升级；硬越窗必须有逃逸路径。
3. **合并 MemoryWindow 与 L1 的重复清理职责**
   - 当前 MemoryWindow 先清，Compactor 后判，导致重复计量、空操作和谱系不推进。
   - 拟统一工具结果清理的 mutator、pin、记账和归档语义。
4. **修正 MemoryWindow 默认死路径**
   - 默认 min=max=40 时 token 预算只能清工具结果，整轮淘汰不可达。
   - 需明确选择：预算只用于工具结果清理，或开放裁轮并补齐归档/展示边界；不得保留“宣称能裁、实际不能裁”的双口径。
5. **SYSTEM 计量口径一致**
   - 修正“预算包含 SYSTEM”的注释与实际估算跳过 SYSTEM 的偏差。

### 3.2 用户历史与模型工作上下文

1. **展示历史与 working context 分离**
   - 当前 `/history` 直接读被窗口/压缩改写的 ChatMemory，刷新后可能只剩 40 条、摘要或裁后内容。
   - 目标：模型读派生工作上下文；用户展示/审计读独立 transcript。短期可评估本机镜像只读前缀，但不能把镜像冒充审计存储。
2. **刷新前后一致**
   - 当前页面不得因后台压缩即时删气泡；刷新后也不得无声少掉旧轮。
3. **L1/L2/L3 的展示事实分别明确**
   - L1：工具结果省略不能暴露 toolCallId/token 估算。
   - L2：摘要正文默认不展示，只显示压缩边界；原始 transcript 仍可恢复。
   - L3/窗口裁轮：若会影响用户展示，必须有中性边界，不能无痕消失。
4. **归档可读性和键唯一性**
   - 当前压缩归档只写不读，且 turnNo 可能被下一轮复用。
   - 拟使用单调 compressionSeq/等价唯一标识；若归档没有受控回取价值，应删除无收益写入，而不是继续占 Redis。

### 3.3 摘要保真与安全

1. L2 不应先看到被 L1 清空的工具结果；需保留资源 ID、工具参数摘要、已执行不可逆动作、未决事项。
2. L1/L3 清理需保护同会话其他活跃 run，复用 protectedRunIds，不新增平行协议。
3. 审查摘要作为 UserMessage 的角色风险；保留不可信数据定界和系统规则，不直接提升为 SystemMessage。
4. synthetic 需要区分 compaction、step_limit、turn_budget、correction；非压缩内部指令不得显示成“较早对话已压缩”。
5. 摘要只处理达到目标所需的最小旧前缀，首轮不引入额外模型配置和并行复杂度。

### 3.4 计量、配置与提交一致性

1. ContextMeter 不得把压缩后合法下降的 prompt usage 当脏帧丢弃。
2. 有效预留需考虑实际 max_tokens/maxOutput；轮首和轮内越窗判据统一。
3. lostTokens 只表示 L2/L3 实际折叠/丢弃的量，不混入 L1 savedTokens。
4. ContextState 的 providerId/modelId 必须与本轮一致；已知模型缺 max_context 不得静默冒充 128K。
5. 圆环展示 used/limit 与触发 nextEst/(limit-reserve) 需明确区分，颜色档位不得误导。
6. 压缩状态/台账应在记忆 CAS 成功后提交；失败不得留下“已压缩但模型仍看原文”的状态。
7. 只有真实 L2 摘要成功才能关闭摘要熔断；L3 不得误关。

### 3.5 减法项

1. 删除 CompactionStatus 不可达 done 分支及对应无效词条。
2. contextCompaction、breakdown、context 帧字段要么有真实消费者，要么删除/按需返回。
3. 修正 context 帧 atMs、est 等恒空/硬编码字段。
4. 不为了假想详情页保留数据面。

## 4. 新交互提案：消息级压缩状态

> 用户提案：增加一种带呼吸但不同颜色的压缩状态；压缩完成后留下可见结果；不再使用顶部压缩提示。以下为主控细化，待审视。

### 4.1 状态归属

压缩状态归属于**触发这次压缩的助手消息/run**，不是会话全局状态，也不是顶部独立横幅。

建议消息级状态：

- `压缩中…`：呼吸动画与工作中相同，使用独立紫色系，区别于蓝色工作中、琥珀色等待中。
- 压缩期间仍沿用当前输入/停止规格：可输入草稿，不排队发送；停止按钮停止整轮，不新增“停止压缩”。
- HITL/表单真正需要用户操作时仍优先显示 `等待中…`，不与压缩状态同时抢同一状态位。
- 过程态占消息元信息行；结果事件不占该状态位，而是插入消息流 parts 的真实时序位置（见 §4.3）。

### 4.2 过程显示

- 真实开始压缩且尚未得出结果时显示 `压缩中…`。
- 过程态是该消息的**纯内存态**（`compactingStartedAtMs`）：只在当前页面内有效，心跳只保活、不归档，刷新/重连后不恢复紫色过程态、不重算秒表。
- 是否显示秒表可复用现有真实计时，但不显示伪造百分比/进度条。
- L1/L3 是本地短操作，原则上不应为一瞬闪现状态；只有实际进入可感知压缩阶段才展示过程态。若后续所有级别都需要可见，应至少保证不闪烁。
- 不再在顶部显示压缩阶段条；准备中、错误、恢复等顶部场景留给独立专项，不在本批顺带删除（交互 Demo 亦不再设准备中对照场景）。

### 4.3 完成事件节点

实际压缩提交成功后，在该助手消息的 **parts 时序**中插入全宽、轻量、无操作的流程分隔行：细线 + 居中灰字 `已压缩上下文`。

它是**事件节点**，不是回复属性：

- 不在回复页脚元信息行，不是 chip/tag/card，不弹 Toast。
- 不含摘要正文、toolCallId、token、秒表或级别。
- 不提供展开、按钮或正文入口。
- 不参与正文复制；复制仍只取 text parts。

只有**确实产生了已提交压缩结果**才插入：

- L1 实际清除了旧工具结果：插入。
- L2 实际生成并提交摘要：插入。
- L3 实际裁掉旧轮：插入。
- MemoryWindow 实际改变历史：需用同一“已整理”事实模型决定是否复用节点，不能无记录。
- 仅判断达阈值、无可清理、未触发、失败回滚：不插入。

位置规则：

- 压缩发生在首段正文前：节点位于本次回答开头。
- HITL/表单续跑：节点位于已决卡之后、后续正文之前。
- 提交后停止、没有后续正文：保留该节点。
- 刷新/重连/跨实例：按持久事件恢复原位置。

同一轮多次真实压缩按事件顺序各保留一个节点；同一事件被重放/刷新时按事件 id 去重，不重复渲染。

### 4.4 停止、异常与恢复矩阵

| 场景 | 过程态 | 结果事件节点 |
|---|---|---|
| 压缩成功，继续生成 | 压缩结束后回到工作中 | 保留 `已压缩上下文` 节点 |
| 压缩成功，本轮正常完成 | 不显示过程态 | 完成后节点仍在原时序位置 |
| 压缩成功后用户停止 | 过程态消失 | 若结果已提交，消息流保留节点 + 页脚既有已停止；不附带重试 |
| 压缩中用户停止，尚未提交 | 立即退出过程态 | 不插入成功节点；以后端最终提交事实为准 |
| 摘要失败，本轮继续 | 退出过程态并回工作中 | 不插入成功节点，不额外增加失败提示 |
| 摘要失败导致本轮失败 | 退出过程态 | 不插入成功节点；沿用本轮既有错误表达 |
| 无可清理/未达阈值/上限未知 | 不出现过程态 | 不出现结果节点 |
| HITL 等待 | 等待中优先 | 已提交的压缩节点仍保留在原时序位置 |
| 刷新/重连/跨实例恢复 | 过程态退场、不恢复：`compactingStartedAtMs` 纯内存、心跳不归档；按服务端现有恢复阶段显示工作中或既有准备态 | 从持久事实恢复节点与位置，按事件 id 去重 |
| 运行态过期 | 不伪造过程态 | 没有持久事实就不补节点；不得把未知当成功 |

### 4.5 持久化要求

压缩过程态和结果态必须分开：

- 过程态可由 heartbeat/真实阶段帧驱动，但**只存当前页面内存**（`compactingStartedAtMs`）：心跳帧不归档计时起点，刷新/重连/接管后过程态一律退场，不按服务端阶段重建「压缩中…」，也不重算秒表；恢复阶段只显示既有「工作中…」或既有准备态。
- 结果事件必须带稳定事件 id，来自已提交的 run/消息事实或可靠事件归档，刷新后仍能恢复原位置。
- 结果事件按事件 id 幂等：同一事件被重放、刷新或跨实例同步时不得重复渲染。
- 停止、断流、换实例不得把“开始过压缩”误记为“压缩成功”。
- synthetic 摘要灰条、页脚 chip 与新事件节点不得重复展示同一事实；目标只保留事件节点。

### 4.6 2026-11-03 用户明确与目标交互对齐（已落地）

用户已明确：**压缩后的摘要正文不给用户展示**。交互 Demo 按以下目标契约呈现，不是现状复刻：

1. **摘要正文不展示**：产品面板不出现摘要正文，也不提供正文入口。
2. **过程不占顶部**：压缩过程只出现在触发压缩的助手消息元信息行；紫色 `压缩中…`，呼吸节奏与 `工作中…` 相同但颜色不同；可显示真实秒表，不显示伪造百分比/进度。蓝色 `工作中…`、琥珀 `等待中…` 保持。
3. **结果持久**：实际压缩提交成功后，在该助手消息 parts 时序中插入全宽、轻量、无操作的流程分隔行 `已压缩上下文`；刷新/重连后仍保留原位置。它是历史事件节点，不是临时 Toast、页脚 chip 或 synthetic 灰色摘要条。
4. **过程/结果分开**：开始但未提交、失败、no-op 均不得显示成功；停止在提交前只有 `已停止`，停止在提交后为节点 + `已停止`；异常、刷新、跨实例按真实提交事实；同轮每次真实压缩各保留一个有序节点，同一事件按 id 去重。
5. **输入规格不变**：压缩中可输入草稿，普通 Enter 静默不发送，Shift+Enter 换行，停止停止整轮；不新增“停止压缩”；停止轮不出现重试/继续。
6. **本地操作与 L2 区分**：L1/L3/MemoryWindow 是本地瞬时操作，避免过程态闪烁；真实产生结果时可在消息流插入 `已压缩上下文` 流程行。L2 可展示 `压缩中…`。所有级别统一用户语义，不暴露级别/技术字段。
7. **展示历史与工作上下文分离**：用户原始展示历史保留，只有模型工作上下文被压缩；刷新后原文仍可见，不再沿用“刷新后旧原文消失/只剩摘要”。
8. **减法边界**：不展示技术占位符、预估行数；不重做其他顶部提示；不出现 synthetic 灰色摘要条或页脚 chip；准备中属于顶部提示专项，压缩 Demo 不设对照场景。

#### 事件节点规格

| 项目 | 目标 |
|---|---|
| 形态 | 全宽、轻量、无操作的流程分隔行：细线 + 居中灰字 `已压缩上下文`；不是 chip/tag/card |
| 位置 | 消息 parts 真实时序：首段正文前 → 回答开头；表单/HITL 续跑 → 已决卡之后、后续正文之前；提交后停止且无后续正文 → 保留 |
| 出现条件 | 仅实际提交成功；no-op、失败、未提交、结果未知不出现 |
| 多次压缩 | 每次真实提交产生一个节点，按事件顺序保留 |
| 幂等 | 同一事件 id 被重放/刷新不重复渲染 |
| 内容 | 不含摘要、toolCallId、token、秒表、级别；不提供展开/按钮/正文入口 |
| 复制 | 不参与正文复制；复制仍只取 text parts |
| 可访问性 | `role="separator"` + 可访问名称；可见文字不重复播报；不新增 live region；颜色不是唯一载体 |
| 过程态 | 紫色 `压缩中…` 仍在消息元信息行；提交后插入/保留节点；顶部压缩提示为零 |
| 与旧表达关系 | 不再同时出现 synthetic 灰条、页脚 chip；同一事实只保留事件节点 |

## 5. 施工顺序（B1–B5 已完成）

1. 触发链：L1 空操作升级、滞回逃逸、MemoryWindow 职责合并。
2. 历史契约：transcript 与 working context 分离，刷新/归档/边界统一。
3. 摘要保真、活跃 run 保护、usage/预留/状态提交。
4. 消息级 `压缩中…` 与消息流 `已压缩上下文` 事件节点，移除顶部压缩阶段条、synthetic 灰条与页脚 chip。
5. 清理 synthetic 误标、技术占位符、死状态和未消费载荷。

## 6. 保留的现有合理设计

- 真实 usage 优先、无 usage 才估算。
- 工具调用/结果配对不拆，按 Turn 裁切。
- 最近轮次、未决 HITL 和活跃 run 保护。
- 摘要失败保持原样，不静默退回更狠截断。
- 轮内工具循环不调用 L2 旁路摘要。
- 多实例 CAS、租户隔离、取消与恢复。
- 不显示摘要全文、不弹压缩成功 Toast、不把完成事实降级为回复页脚 chip。
