## 2. 总体结论

### 2.1 健康度判断（一页内读完）

**结论：Redis 数据面的「原语层」是全仓质量最高的一段，问题不在原语而在两处结构性缺口 ——「Cluster 形态从未被建模」与「多实例的实例归属从未被建模」。**

- **原语层（键生命周期 / 原子性 / fencing 语义）可以打高分**：全仓 38 个 key 模式 + 1 个 pub/sub 频道，`ai:*` 族的 TTL 与续期收敛成一张可断言的登记表（`SessionKeyRegistry`，三档续期面，心跳面「exactly 5」被用例锁定）；9 条 Lua 脚本**全部**通过 `KEYS[]` 传键、无硬编码键名；租约的「抢/续/放/校验」四动作全在 Lua 内完成值比对，fence 写做到「存储侧拒绝回退」（Kleppmann 正解），TTL 30s / 续租 10s 与 Redisson watchdog 默认值同构。这些是**明确值得保留**的资产（见 §5）。
- **缺口一（A-4）：9 条 Lua 里 4 条是多键脚本，且全部跨 hash slot，全仓零个 hash tag**。更严重的是失败模式不对称：`FENCED_SET`（快照写）**硬抛异常**、`IDEM_PUSH`（台账+索引）**在工具副作用已发生之后才炸**、`ACQUIRE`（抢租）被 `catch` 吞成 `UNAVAILABLE` ⇒ **上 Cluster 后租约体系静默失效**（不崩、不报错、只是跨实例互斥消失）。这三条互相掩护，形成「今天看不出问题、修好一条反而炸另一条」的错位。
- **缺口二（A-1）：业务作业域完全没有「实例归属 / 选主 / 状态 CAS」三个概念**。启动恢复把**所有** PENDING/RUNNING 当自己的残留、看门狗在**每个**实例全库判死、`Job` 既无 `@Version` 也无条件 UPDATE ⇒ **最普通的滚动发布就会杀掉别人正在跑的作业，并把「数据已发布」写成「作业 FAILED」**。AI 侧靠「每轮一个租约」勉强守住了这条路，作业侧没有任何对等物 —— **两条链的多实例成熟度相差一个量级**。
- **缺口三（A-1·AI 面）：租约与「这一轮还活着」的证据链之间是断的**。活动锚点在批① 之后只剩心跳帧（新落档口不刷 `ai:beat`），而 `zombie-age(60s) < inter-event-timeout(90s) < exec-timeout(120s)` ⇒ 跨实例会把「正在跑长工具 / AI 慢吐字」的活轮判成僵尸并接管，同一轮被执行两遍（`toolCallId` 不同，认领去重救不了）。
- **缺口四（A-6）：四个「只增不减」的数据结构与四个「大 value 无上限」的口子并存**。`ai:runs` 与 `chat:mem:__ids__` 两个索引键无 TTL 且唯一的惰性清理路径在生产不可达；`ai:xevents` 是「条数窗口 × 单帧 64KB」的乘积，理论上限 **≈384MB/轮**，而淘汰策略已钉成 `noeviction` ⇒ 触顶不是「丢最旧帧」而是**全线写失败**；`chat:mem` 的整窗口覆盖写是「先 DEL 再 RPUSH」，中间崩一次就**永久丢整段历史**（这是本报告唯一一条「现况就会丢用户数据」的 🔴）。

**一句话**：**这是一个「原语做得很正、拓扑假设很软」的系统** —— 单实例下几乎挑不出硬伤，一旦要上多实例或 Cluster，缺口集中在两处（实例归属、slot 合法性），且两处都因为「降级路径设计得很礼貌」而被掩盖成静默问题。

### 2.2 最重要的 5 条（按「该先动手」排序）

1. **🔴 R1-01 `ACQUIRE_SCRIPT` 跨 slot + 异常吞成 `UNAVAILABLE`**（`backend/src/main/java/com/example/configmgr/ai/run/LeaseService.java:98-108`、`:302`、`:317-321`）：Cluster 下每次抢租都 `CROSSSLOT` → 吞成「设施不可用」→ 按 I4 口径降级为进程内互斥 ⇒ 续跑互斥、fencing 写、资源锁三族**一起静默失效**。这是「越礼貌越危险」的典型。

#### 🔴 R1-01 `ACQUIRE_SCRIPT` 跨 slot，且失败被 `catch` 吞成「设施不可用 ⇒ fail-open」`【迁 Cluster】`

- **来源碎片**：S2（🔴 第 1 条）+ S5（E1，🔴）+ S1（🔵「多 key 原子脚本 5 处仅 1 处登记」的一份子）
- **位置**：`backend/src/main/java/com/example/configmgr/ai/run/LeaseService.java:98-108`（脚本）、`:302-303`（调用，两键）、`:82`（`EPOCH_KEY`）、`:317-321`（catch 吞异常）
- **现象**：抢租脚本一次操作两个键：`KEYS[1]` = 具体租约键（`ai:lease:run:<runId>` / `ai:lock:task:<taskId>` / `ai:lock:job:<taskId>:<TYPE>`），`KEYS[2]` = 全局常量 `ai:lease:epoch`。两者前缀不同、id 维度不同，实算 slot 不同（`ai:lease:run:r-1` = 3659 vs `ai:lease:epoch` = 4124）。脚本外层 `catch (Exception)` 把任何异常折成 `AcquireOutcome.UNAVAILABLE`，调用方按 I4 口径「设施不可用 ⇒ 走进程内互斥、放行」。
- **证据**（1-3 行关键）：
  ```lua
  local epoch = redis.call('INCR', KEYS[2])   -- LeaseService.java:104
  ```
  ```java
  String raw = this.redis.execute(ACQUIRE_SCRIPT, List.of(key, EPOCH_KEY), holder, ...);  // :302
  catch (Exception ex) { ... return new AcquireResult(AcquireOutcome.UNAVAILABLE, null); } // :317-321
  ```
- **判定**：Redis 对「KEYS 落在不同 slot 的 EVAL」一律回 `CROSSSLOT Keys in request don't hash to the same slot`，**客户端无法替脚本拆槽**。于是 Cluster 下的实际行为不是崩，而是：每次抢租都抛 → 吞成 `UNAVAILABLE` → 进程内视图永远为空 → `heldRunEpoch()==0` ⇒ ①续跑权互斥（`ResumeService` / `ConfirmGate` 的「只让一个实例驱动一轮」）整族失效；②fencing 写降级为 plain `SET`；③资源锁（`ai:lock:*`）退化成「每个实例各自放行」。**这是全仓最严重的一处：静默退化，日志只有 WARN，业务侧表现为重复驱动 / 重复副作用，且无法通过增加告警发现（因为口径本来就是「降级放行」）**。另外 epoch 是「全局单计数器」，结构性决定了它**不可能**与 N 个不同 runId 的租约同槽 —— hash tag 只能把全族压进同一 slot（牺牲分布），不能按 run 分散。
- **建议**：把取号从脚本里剥离（客户端先 `INCR ai:lease:epoch` 取号，再用单键 Lua 做 `SET NX PX` + 值比对），或给 `ai:lease:*` 全族加常量 hash tag 并接受单槽热点；两方案都要在 `SessionKeyRegistry` 里把「slot 约束」登记为键族属性（见 Y1-06）。同时**把 `UNAVAILABLE` 与「脚本错误」区分开**（后者应显式告警）。

#### 🔴 R1-02 `FENCED_SET` 跨 slot（`ai:run:` + `ai:fence:run:`），持租写快照会全线硬失败 `【迁 Cluster】`

- **来源碎片**：S2（🔴 第 2 条）+ S5（E2，🔴）
- **位置**：`backend/src/main/java/com/example/configmgr/ai/run/RunStore.java:217-226`（脚本）、`:511-512`（调用）、`:443-449`（`save()` 的失败分支）、`:515-517`（异常包装）
- **现象**：持租写快照时用一条脚本「You win or you don't」：`GET KEYS[2]`（fence）比对 epoch，然后 `SET KEYS[1]`（快照）+ `SET KEYS[2]`（fence）。两键前缀不同，实算落不同 slot（`ai:run:r-1` = 6530 vs `ai:fence:run:r-1` = 4210）。
- **证据**：
  ```lua
  local fence = redis.call('GET', KEYS[2])
  if fence and tonumber(fence) > tonumber(ARGV[2]) then return 0 end
  redis.call('SET', KEYS[1], ARGV[1], 'PX', ARGV[3])
  redis.call('SET', KEYS[2], ARGV[2], 'PX', ARGV[3])
  ```

- **判定**：Cluster 下这条脚本直接 CROSSSLOT。但**这条不走 catch 降级** —— `fencedSet` 把异常包成 `IllegalStateException("无法写入轮次快照")` 抛给 `save()`，即「持租状态下每一次快照写都会失败」。组合起来形成**危险的错位**：今天因为 ACQUIRE 先失效（R1-01），`epoch` 恒 0，永远走 plain `SET` 分支，所以表面上只是「fencing 静默缺失」；**一旦有人只修好 ACQUIRE（或换成「取号外置」方案让抢租成功）而忘了这条，写快照就会从「静默无 fencing」直接变成「全线 500」**。两处必须同批改造。

#### 🔴 R1-06 会话记忆是「整窗口非原子替换」：一次写失败即整段历史被清空 `【现况】`

- **来源碎片**：S4（🔴 第 1 条，孤例）
- **位置**：`backend/src/main/java/com/example/configmgr/ai/memory/RedisChatMemoryRepository.java:157`、`:162-166`、`:174-179`；`backend/src/main/java/com/example/configmgr/ai/run/ResilientChatService.java:1694-1705`（`writeBackMemory`）、`:1204-1210`（`convergeMemory` 同形）

- **证据**：
  ```java
  this.redis.delete(redisKey);
  this.redis.opsForList().rightPushAll(redisKey, this.codec.serializeAll(messages));   // :163-164
  ```
  ```java
  this.chatMemory.clear(sessionId);
  this.chatMemory.add(sessionId, messages);          // ResilientChatService.java:1699-1700
  } catch (RuntimeException ex) { log.warn("{}后记忆写回失败 ...", stage, sessionId, ex.getMessage()); }  // 只 WARN
  ```
- **判定**：这是**唯一**的会话历史持久面（`GET /api/ai/history/{sessionId}` 直接读它）。三种失败都会永久丢历史：① 进程在 `clear` 与 `add` 之间死；② `clear` 成功而 `add` 抛出（payload 大 + 2s 命令超时 + `noeviction` 下写失败，都是现实路径）—— 此时 `catch` 只 WARN，**记忆已被清空且不重试**；③ `DEL` 与 `RPUSH` 之间同样。上一轮及更早的轮次只存在这个键里（run 快照只有「本轮」的 `messageJson`），删掉即不可恢复。**这是本报告唯一一条「现况部署下就会永久丢用户数据」的 🔴。**

- **建议**：时间列改 `Instant` / `timestamp with time zone`，或至少把看门狗的比较改为不依赖 JVM 时区（统一 UTC）。

## 4. 做得对、值得保留（🚩 正面发现，30 条）

> 这一节的作用是给整改定「不要动的东西」。本仓 Redis 使用的正面项密度很高，**绝大多数整改不该顺手改掉它们**；特别提醒两条反面纪律：① 给单键脚本加 hash tag 只会牺牲分布、无收益；② 不要因为「统一风格」把 `ai:lock:*` 的 `created` 判据改成「epoch 变没变」。

### 4.1 租约与 fencing（5 条）

**P1-01 租约原语的 epoch + 「谁创建谁释放」+ 条件续/放（Lua 原子）** — 来源 S1 / S3 F-04 / S5
- 位置：`LeaseService.java:98-140`、`:291-322`、`:455-529`
- 现象：抢租用单段 Lua（`GET` 现值优先 → `INCR` 取号 → `SET PX`）；续租/释放都在 Lua 内「现值等于 `<epoch>|<owner>`」才 PEXPIRE/DEL；进程内视图按 `key\0owner` 记账；续租带「存活判据」（僵尸续租自停）；用 `created` 标志区分「创建者」与「重入者」——**用「epoch 变没变」去判创建者是错的**（并发同主双抢时两边同形），这一点代码注释已写透。
- 判定：这是全仓 Redis 使用时最扎实的一处 —— fencing 号、原子比对、明确降级（`UNAVAILABLE ≠ HELD_ELSEWHERE`）三件事都做到了。**值得保留**，并作为其它锁（Y1-04 会话锁）的整改模板。

**P1-02 fence 写「拒绝回退」= Kleppmann 式的存储侧校验，不是冗余** — 来源 S4 / S5 E12+B1
- 位置：`RunStore.java:217-226`（`fence > epoch` 则 `return 0`）、`:443-449`
- 现象：脚本先读 fence，若已有更高的号就拒写，否则写快照并把 fence 推到本次 epoch；`STALE_EPOCH` 拒写是「fencing 生效」的唯一可观测证据。
- 判定：与 Kleppmann「storage remembers the highest token」一字不差同构（`https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html`）。**这是全仓最重要的正确性设施之一**；文档里应把「fence 是存储侧校验，不是锁的替代」讲清楚。

**P1-03 台账 + 幂等索引用一条 Lua 原子写，且索引不复制大正文** — 来源 S1 / S4 / S5 E3
- 位置：`RunStore.java:249-257`、`:142-149`
- 现象：`LLEN` 取下标 + `RPUSH` + `HSETNX` + 两个 `PEXPIRE` 一个原子步；下标在脚本内现取（推入前的长度），避免与并发写者竞争；`HSETNX` 而非 `HSET` 保证「第一次是哪条记录」不被重放改写；索引值只存「哪一条台账记录」的指针，正文不复制。
- 判定：既消除了「台账有、索引没有 ⇒ 重复执行」的洞（注释 `:229-241` 把动机写清），又是**大 value 治理的正确姿势**（指针而非副本），可作为其余写口的模板。（唯一问题是它跨 slot —— 那是 A-4 的账，不是这条设计的错。）

**P1-04 记忆删除 `DEL + SREM` 合成一条 Lua** — 来源 S1
- 位置：`RedisChatMemoryRepository.java:71-74`

### 4.2 数据结构选型（4 条）

**P1-06 键生命周期治理：滑动 TTL + 三档登记表 + 取消标志与会话同寿** — 来源 S1 / S4
- 位置：`RunStore.java:1681-1693`、`SessionKeyRegistry.java:18-27`、`CancellationRegistry.java:244-257`
- 现象：run 级键全部随写整额续 24h；三档续期面（HEARTBEAT / READ / WRITE）显式分档，心跳面「exactly 5」被用例锁定（`RunStoreSlidingTtlTest`）；取消标志从「2×总预算=600s」改为「与会话同寿」。
- 判定：口径统一、有登记、有锁定用例 —— **Y1-01 / Y1-02 正是这张表边界没划全造成的，而不是思路错**。这张表本身是本仓最值得复制的机制。

**P1-07 限流用 ZSET 滑动窗口 + 单键 Lua + `PEXPIRE`** — 来源 S1 / S4 / S5 E11
- 位置：`AiRateLimiter.java:79-102`
- 现象：`ZREMRANGEBYSCORE` / `ZCARD` / `ZADD` / `PEXPIRE` 全在一个脚本里，窗口外成员当场回收、键随最后一次命中后 1 个窗口过期；用 Redis 自己的 `TIME`（多实例时钟漂移不切窗）。
- 判定：结构选型与访问模式完全匹配，没有「计数器永不过期」的问题；单键脚本天然 cluster-safe。

**P1-08 表单附件「单命令即原子」** — 来源 S1 / S4
- 位置：`RedisFormAttachmentStore.java:94-118`
- 现象：「一次性消费」以单条 `DEL` 的**返回值**作判定门（两个并发消费只有一个拿到 1），墓碑只是诊断面。
- 判定：遵守「限流 / 消费计数直接用 Redis 原语」的既定口径；「`DEL` 成功但 `SET` 墓碑失败」的崩溃窗只会少一条墓碑，**不会放行第二次消费**。

**P1-09 事件日志选 Stream + 显式 entry ID `<seq>-0`，读侧 O(差量)** — 来源 S4 / S2
- 位置：`RedisFrameStore.java:33-49`、`:225-235`、`:290-322`
- 现象：`XADD key MAXLEN ~ 6000 <seq>-0 seq <n> frame <json>` + `EXPIRE`；`XRANGE (afterSeq-0 +` 让重挂补帧从 O(窗口) 降到 O(差量)；显式 ID 被拒时退化为自动 ID，并在读侧按 `seq` 字段排序过滤（显式登记了「自动 ID 兜底会使物理序 ≠ seq 序」这一例外）。
- 判定：用 Stream 承载「有单调序号的事件日志」是正确选型（LIST 无法按 ID 区间读、LIST 头尾裁剪会让低号帧永久不可见）。**唯一缺口是「字节」这一维没治理**（R1-08）。

### 4.4 缓存模式与服务可用性（3 条）

**P1-15 KB cache-aside 的三件套齐了（版本号传播、单飞锁、stale-if-error）** — 来源 S4

- 位置：`RedisAvailability.java:40-53`；`application.yml:94-95`
- 判定：把「Redis 挂了 → 15s 才报错」压到 ≤2s 的 503，且失败侧结果缓存 5s 避免打爆。对「缓存设施不可用不该拖垮业务」的口径落实到位。

**P1-17 全仓生产路径没有 `KEYS *`、没有全库 `SCAN`，索引用自建 SET** — 来源 S2

**P1-18 启动恢复「三条安全边界 + 逐轮自抢租约」** — 来源 S3 F-19

### 5.1 Redis Cluster 多键操作与 hash tags

| 编号 | 业界事实 | 来源 | 与本仓的关系 |
|---|---|---|---|
| **A1** | 多键命令在 Cluster 下必须同 slot，hash tag 是唯一官方手段。Cluster 把键空间切成 **16384 个 slot**，一条命令只能由一个节点执行；`MGET/MSET/DEL/UNION 系/MULTI-WATCH/EVAL` 涉及多个键时键必须落在同一 slot，否则返回 `CROSSSLOT Keys in request don't hash to the same slot`。强制同 slot 的手段只有 hash tag：`{...}` 内的子串参与 CRC16，`user:{42}:profile` 与 `user:{42}:orders` 落同一 slot | `https://redis.io/docs/latest/develop/using-commands/multi-key-operations/`、`https://redis.io/docs/latest/operate/oss_and_stack/reference/cluster-spec/` | **这是硬约束，不是性能建议**。本仓 4 条多键脚本全踩（R1-01~04）。口径应是「先看有没有多键，再谈要不要迁 Cluster」 |
| **A2** | 官方多键行为表就是一份现成的迁移检查清单：在「OSS cluster enabled」下，`EXISTS`、`MGET`、`DEL`、`MSET`、`UNLINK`、`SUNION`、`WATCH`、`XREAD` 以及 **`MULTI/EXEC` 与 `EVAL/EVALSHA` 的键集合**一律 **single-slot**；只有 `DBSIZE/KEYS/SCAN/FLUSHALL` 是「当前分片」语义 | `https://redis.io/docs/latest/develop/using-commands/multi-key-operations/` | 可照抄成 checklist：① 所有 `EVAL` 的 `KEYS[]`；② 所有多键 `DEL/MGET/MSET`；③ 所有 `MULTI/EXEC`；④ `SCAN/KEYS` 的语义变化。本仓的 `deleteRun` 12 键 `DEL` 正好是第 ② 项（R1-05），而 e2e 的 `KEYS`+`FLUSHDB` 是第 ④ 项（Y3-01） |
| **A3** | hash tag 的代价是热 slot：同 tag 的键全部落到同一 slot ⇒ 同一节点。若 tag 取得过粗（如 `{ai}`、`{session}`），整个键族从一个「分散的集群」退化成「单节点热点」，分片收益归零；阿里云把这类现象归入「数据倾斜（大 Key / 热 Key）」。Stanza 的实践口径：「Use entity-level hash tags — Tag by user, tenant, or order ID rather than by category」 | `https://dev.to/deko39/redis-cluster-explained-hash-slots-crossslot-errors-lua-scripts-and-pipelining-3bi0`、`https://help.aliyun.com/zh/redis/user-guide/deal-with-data-skew-issues`、`https://www.stanza.dev/courses/redis-clustering/redis-cluster/redis-clustering-cluster-clients` | **这条直接决定「能不能用 hash tag 修本仓的 CROSSSLOT」**：用一个全局 tag 把所有 lease 键绑到一起 = 自废分片。tag 粒度必须取「业务实体 id」（runId / taskId），永不取「子系统名」。这也是 R1-01 / R1-04 为什么难修的根因 |
| **A4** | 迁 Cluster 不是改连接串：Spring Data Redis 的 Cluster 支持要显式给 `RedisClusterConfiguration`（`spring.redis.cluster.nodes` / `max-redirects`），且「初始配置只提供入口节点，集群拓扑变更只保留在原生 driver 里、不会写回配置」；**单机 Redis 不校验 slot，即使只有一个主节点的本地 Cluster 也会校验**，所以「本地跑得通」不能证明线上没问题 | `https://docs.spring.io/spring-data/redis/reference/redis/connection-modes.html`、`https://dev.to/deko39/redis-cluster-explained-hash-slots-crossslot-errors-lua-scripts-and-pipelining-3bi0` | 本仓 `application.yml` 只有 `spring.data.redis.host/port`（单机）。迁移前置条件应是「本地/CI 起一个 3 主 Cluster 跑全量用例」，而不是先改配置再救火（Y3-02） |
| **A5** | CROSSSLOT 是「设计问题」，客户端重试与代理都绕不过去。slot 不匹配是命令路由层的拒绝，重试无意义；BullMQ / Laravel queue 这类「多键 Lua」框架的修复方式都是**改键名加 hash tag**（Laravel 13.5 自动把队列三键包成同 tag），而不是加重试 | `https://hack1024.com/en/articles/redis-cluster-crossslot-multikey-lua`、`https://github.com/langwatch/langwatch/issues/1419`、`https://laravel-news.com/laravel-13-5-0` | 本仓 4 处多键脚本必须逐处改键形，没有「配一下就好」的捷径。建议把「每个 Lua 的键族前缀」做成一处常量，供 tag 化改造与用例断言共用（`LeaseKeys` 已是这种收口方式的正面样板） |

### 5.2 分布式租约 / fencing token

| 编号 | 业界事实 | 来源 | 与本仓的关系 |
|---|---|---|---|
| **B1** | 锁不够，必须配 fencing token 且由存储侧拒绝回退写。Kleppmann 指出「取锁 → 读 → 改 → 写」在 GC 停顿 / 网络延迟下必然出错，写前再查一次锁也没用（线程可能在检查与写之间被暂停）。唯一有效的补法是：锁服务每次授予锁时发一个**单调递增**的 token，随写请求带给存储，存储记住见过的最大值并拒绝更小的 token。原文：「you need to include a fencing token with every write request to the storage service… the storage server remembers that it has already processed a write with a higher token number (34), and so it rejects the request with token 33.」 | `https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html` | 本仓 `RunStore` 的 fence 写正是这一模式，**不是自创，属主流正解**（P1-02） |
| **B2** | token 的发放粒度：主流是「每把锁一个号」，不是「全局一个计数器」。Redisson 的锁类型表里只有 `Fenced Lock`（`RFencedLock`）带 fencing token，token 由 `lockAndGetToken()` 返回，语义是「这把锁的第 N 次授予」；普通 `RLock` 明确标注 **Fencing token ❌**。实现是在锁的 hash 里维护计数器，即 **per-lock**。表格行：「Fenced Lock \| Reentrant ✔️ \| Fair ❌ \| Fencing token ✔️ \| Pub/sub \| Guarding an external resource against a stale lock holder」 | `https://redisson.pro/docs/data-and-services/locks-and-synchronizers/` | per-lock 号是主流（也天然单调），但**跨锁不可比**。本仓要的是「跨键可比」（同一 run 的快照写要能压过任何后继者的号），因此选了全局号 —— 这是**有意的偏离**，代价是全局键成为热点与单点（R1-01）。建议在注释 / 设计稿里把「为什么不是 per-lock 号」写死，避免后续被「改成 Redisson 式」误改 |
| **B3** | ZooKeeper 方案对照：`zxid` / znode version 天生是 fencing token。ZK 的锁用 `EPHEMERAL_SEQUENTIAL` 临时顺序节点排队，会话断开即自动删节点（无需 TTL 续租来兜崩溃）；Kleppmann 原话「if you are using ZooKeeper as lock service, you can use the zxid or the znode version number as fencing token」；Curator `InterProcessMutex` 的 `internalLockLoop` 在锁目录下建 `EPHEMERAL_SEQUENTIAL` 节点并按序号排队 | `https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html`、`https://www.cnblogs.com/xifenglou/p/10497407.html` | ZK 的优势是「崩溃即释放 + 号天然单调」，代价是运维一套 ZK 集群、写入吞吐远低于 Redis。**对本仓不是划算的替换**（只需要「每轮一个号 + 存储侧校验」），但它是「全局单调号」这一思路的来源：ZK 的 zxid 就是全局的 |
| **B4** | 续租参数：**TTL 30s、每 10s 续一次**是业界默认值。Redisson watchdog 默认 `lockWatchdogTimeout = 30s`，续期周期 = `timeout / 3` = 10s；只有 `lock()`（不带 leaseTime）才启用 watchdog，显式 `leaseTime` 会关掉自动续期 | `https://redisson.pro/docs/data-and-services/locks-and-synchronizers/`、`https://juejin.cn/post/7639941743310946314` | 本仓 `app.ai.lease.ttl=30s` / `renew-interval=10s`（`AiProperties.java:980`、`:983`）与主流默认值**完全同构**，注释里「容忍两次连续续租失败」的理由也与 Redisson 的设计意图一致。**属正面项，不需要调** —— 但注意 Y4-01：实际实现是「单拍失败即弃视图」，与「容忍两拍」的注释不符 |
| **B5** | 「等待方持租」在主流的对应物是「运行所有权租约」，而不是「互斥锁」。主流锁用法是「临界区短、进出成对」（watchdog 假设持有者**正在执行**）；「等人」这类长等待，主流做法是把等待**状态化**（工作流引擎的 wait state / signal），执行权不占租约，因为空闲进程长期持租等于把「故障切换的恢复时间」拉长到「人什么时候点按钮」。Redisson 的描述：「prolongs lock expiration while lock holder Redisson instance is alive」—— 续租的前提是「实例活着」，**语义上并不区分「活着在干活」还是「活着在等人」** | `https://redisson.pro/docs/data-and-services/locks-and-synchronizers/`、`https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html` | 本仓把「运行所有权」做成租约（而非互斥锁），并用 I7 存活判据约束僵尸续租，**是自洽的**；但它属「所有权租约」这一族，不该拿「锁」的直觉去评价。建议命名与文档上把 `ai:lease:run:*` 明确称为「所有权租约（ownership lease）」，与 `ai:lock:*`（互斥锁）区分 —— 这个区分也解释了为什么 Y1-01「等人超过 TTL」是一个真问题 |
| **B6** | Redlock 已被官方判为 deprecated，本仓没走 Redlock 是对的。Redisson 官方文档把 `RedLock` 标为 deprecated：「The algorithm's safety guarantees are contested, and it adds significant operational cost… superseded by RLock together with replica-synchronization checking, and by RFencedLock」；「This object is deprecated. Superseded by RLock and RFencedLock objects.」；Kleppmann 的结论同样是「要正确性就别用 Redlock」 | `https://redisson.pro/docs/data-and-services/locks-and-synchronizers/`、`https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html` | 本仓「单 master + fencing」的路线避开了这个坑，**属正面选择**；如未来有人提议「上 Redlock 提高可靠性」，可直接用此条否决 |
| **B7** | 「epoch 全局发放」与 etcd 的全局 revision 同源，但与「任意键的原子抢租」在 Cluster 下互斥。全局单调号（ZK zxid、etcd revision）之所以能全局，是因为发号器本身是一个**单点共识对象**；Redis 里对应物就是「一个键 + `INCR`」。而「抢任意键的租约」要求脚本同时触碰「该键」和「发号键」—— 两者在 Cluster 下几乎必然不同 slot。官方多键表把 `EVAL/EVALSHA` 的键集合列为 single-slot；`INCR` 只能作用于单键 | `https://redis.io/docs/latest/develop/using-commands/multi-key-operations/`、`https://martin.kleppmann.com/2016/02/08/how-to-do-distributed-locking.html` | **这不是实现疏忽，是两个正确性要求的结构性冲突**：要么把所有租约键收进一个 slot（放弃分片），要么让全局号退化为「每次抢租两次往返 + 冲突重试」，要么改成 per-key 号（失去跨键可比）。本仓现状「单实例 + 全局号」语义最干净；迁移时必须显式选一条路（R1-01 的三选一） |
| **B8**（自 S5 C 组） | Spring Boot 的默认客户端是 Lettuce，且是「数据面」定位：「There is a `spring-boot-starter-data-redis` starter… By default, it uses Lettuce.」Lettuce 基于 Netty，单连接多路复用、支持 Cluster/Sentinel/异步/响应式；Jedis 是同步阻塞、连接池独占 | `https://docs.spring.io/spring-boot/reference/data/nosql.html`、`https://redis.io/blog/jedis-vs-lettuce-an-exploration/` | 本仓 `backend/pom.xml:75` 只引 `spring-boot-starter-data-redis`，即 Lettuce；这是 Spring 生态的默认与主流选择。**无需动作** |
| **B9**（自 S5 C 组） | Redisson 的定位是「分布式对象/锁」，业界常见组合是「Lettuce 管数据、Redisson 管锁」或二选一。Redisson 提供 RLock/RSemaphore/RMap 等开箱对象，自带看门狗与（可选的）副本同步检查；可直接替换 Spring Data Redis 的 ConnectionFactory，也可与 Lettuce 并存 | `https://redisson.pro/blog/feature-comparison-redisson-vs-spring-data-redis.html`、`https://blog.csdn.net/blsc886/article/details/148614237` | 本仓**没有**引 Redisson，锁是自研 Lua。这在本仓是可辩护的：需要「owner 维度（key+owner 记账）」与「全局 epoch 跨键可比」两点，Redisson 的 `RLock` 给不了（`RFencedLock` 的 token 是 per-lock），且引入第二套客户端会多一份连接与运维面。若未来只是想「省掉自研脚本」，Redisson 能替代的是 `ai:lock:*` 那一层（纯互斥），**不能**替代 `ai:lease:run:*` 那一层（所有权 + 全局号） |
| **B10**（自 S5 C 组） | 自研 Lua 的代价是「每个脚本都要自己做对」：Lua 在 Redis 内是单线程原子执行，但会阻塞整个实例（`lua-time-limit` 默认 5s），且脚本里不能动态决定键（Cluster 下必须预先在 `KEYS[]` 声明）。「You also can't reference keys dynamically determined inside the script if you're running…」；「Redis will kill scripts that exceed lua-time-limit (default 5 seconds)」 | `https://polariscode.net/articles/lua-in-redis-atomic-scripts-that-dont-lie` | 本仓所有脚本都很短（GET/INCR/SET/PEXPIRE/DEL 级别），键全部通过 `KEYS[]` 传入，符合脚本最佳实践；**风险不在脚本本身，而在键的 slot 分布**。建议保持「脚本只做几次 O(1) 操作」的口径，不要往脚本里塞循环或大批量裁剪 |

### 5.3 会话记忆 / 帧日志的容量治理

| 编号 | 业界事实 | 来源 | 与本仓的关系 |
|---|---|---|---|
| **D1** | 流式日志的通行治理是「条数窗口 + 近似裁剪 + TTL」三层：`XADD key MAXLEN \| MINID [= \| ~] threshold [LIMIT count] id …`；`=` 精确裁剪、`~` 近似裁剪「more efficient, may leave slightly more entries than the threshold」；**`MAXLEN` 只按条数，不按字节** | `https://redis.io/docs/latest/commands/xadd/` | 本仓 `RedisFrameStore` 用 `XADD … MAXLEN ~ 6000` + `EXPIRE`（`RedisFrameStore.java:227-232`），三层里占了两层（条数 + TTL），**缺「字节」这一维**（R1-08）。这不是配置写错，而是「治理维度少一维」 |
| **D2** | `noeviction` 与 `volatile-*` 的语义差异决定「哪些键可以丢」：`noeviction` 下内存满时**写命令直接报错**（读命令照常）；`volatile-lru/-ttl` 只在**带 TTL 的键**里淘汰，若没有键带 TTL 则退化为 `noeviction`；官方建议「if you make good use of key expiration, then you are less likely to run into the cache memory limit」。原文：「`noeviction`: Keys are not evicted but the server will return an error when you try to execute commands that cache new data」；「The `volatile-xxx` policies behave like `noeviction` if no keys have an associated expiration」 | `https://redis.io/docs/latest/develop/reference/eviction/` | 本仓把 `ai:lease:epoch` 归为「绝不能淘汰」。业界更常见的做法是**把不可丢的键与可丢的缓存分实例 / 分库**，而不是靠全局 `noeviction`（`noeviction` 会让「缓存写满」变成「业务写入全挂」）。建议：要么分实例，要么用 `volatile-*` + 保证所有可丢键都带 TTL、不可丢键不带 TTL（这样 volatile 策略天然不碰它们） |
| **D3** | 会话类数据的容量治理：TTL 之外还要「绝对上限」。vivo 推送平台的实践总结是四条：只存热数据、容量可预估、**尽量设过期时间**、**大 value 压缩后存储**；阿里云把「大 Key/热 Key/高消耗命令」列为数据倾斜的三类来源。原文：「存储内容尽量是热数据，并且容量是可预先评估的，最好设置过期时间。在存储设计时，合理使用对应数据结构，对于一些相对大的 value，可以压缩后存储。」 | `https://www.cnblogs.com/vivotech/p/15891343.html`、`https://help.aliyun.com/zh/redis/user-guide/deal-with-data-skew-issues` | 本仓会话记忆 `max-messages=40` + 24h 滑动 TTL 是「条数」治理；帧日志 6000 条 + 24h 也是「条数」治理。两者都是**滑动续期、无绝对寿命上限**（`AiProperties.java:29-34` 明确写了「整个会话维度，无绝对上限」），业内对此的常见补法是「滑动 TTL + 绝对 TTL 双限」（如 24h 滑动 + 7d 绝对）。这是有意的产品取舍（活跃会话不丢上下文），**不是缺陷**；但容量规划上必须知道「一个永不结束的会话会无限增长」 |
| **D4** | 帧/事件日志的压缩：Redis 不透明压缩 value，压缩必须在应用层做；流式日志的常见做法是「热窗口存原文、冷数据压缩或落对象存储」 | `https://www.cnblogs.com/vivotech/p/15891343.html`、`https://redis.io/docs/latest/commands/xadd/` | 本仓选择「单帧 64KB 硬截断 + 原文落档」（`AiProperties.java:938`），比压缩更简单且保住可读性，对「回放给前端」这个用途是合理的；代价是内存成本高（R1-08 的乘积估算）。如果要压，优先压「已确定不再被实时消费」的冷帧，而不是全量压（全量压会让回放路径多一次解压） |

### 5.4 S5 对本仓的三段判断（原文要旨，供裁决参考）

**第一段 · Cluster 迁移 —— 不建议现在迁；若一定要迁，成本集中在「键设计」而不是「客户端」。**
本仓的 Redis 用法有三个特征是 Cluster 不友好的：全局 epoch 计数器（`ai:lease:epoch`）、「一轮一个键族」（12 个前缀的键）、以及「全局会话索引」（`chat:mem:__ids__`）。4 处多键脚本 / 1 处多键命令在 Cluster 下全部 CROSSSLOT，其中 R1-02 会硬抛异常、R1-01 会**静默降级成进程内互斥**（最危险）。而 R1-01 和 R1-04 不是「加个 tag」能解决的：前者要求「全局发号键」与「任意租约键」同 slot（等于放弃分片），后者要求「全局索引」与「每会话数据键」同 slot（同样把全局键拖进热点）。可行的折中是：**R1-02/R1-03/R1-05 用 `{<runId>}` 一次性修好**（语义零变化、无热点代价，占改造量的 3/5），**R1-01 改成「先取号再 CAS 抢租」的两次往返 + 冲突重试**，**R1-04 改成「删除非原子 + 幂等清理」**。判断：**单实例部署下没有任何理由迁 Cluster**；若因容量 / HA 要迁，先做前三条，后两条单独立项并单独设计。

**第二段 · 租约与 fencing —— 语义是主流正解，参数与 Redisson 默认同构，但「全局号」是有意偏离主流的少数派。**
Kleppmann 的结论在本仓被完整实现（P1-02），TTL 30s / 续租 10s 与 Redisson watchdog 的默认值完全一致（B4）。偏离点只有两个：① 号是**全局**发（Redisson `RFencedLock` 是 per-lock），换来「跨键可比」；② 抢租与发号在**同一个脚本**里原子完成，换来「抢到即有号」。这两点合在一起才导致 R1-01 的 Cluster 冲突 —— **它们不是两个独立问题，是一个设计的两面**。反过来说，如果未来要把锁换成 Redisson，`ai:lock:*`（纯互斥）可以换、`ai:lease:run:*`（所有权 + 全局号）不能换。ZK 式方案（zxid 天然单调 + 临时节点崩溃即释放）在语义上更贴合「全局号」，但运维成本与本仓的部署形态不匹配，不建议引入。

**第三段 · 容量治理 —— 「条数 + TTL」够用但不完整，缺的是「字节维度」和「绝对上限」。**
业界通行的是四个维度：条数窗口、字节预算、滑动 TTL、绝对 TTL（外加冷数据压缩 / 外置）。本仓占了两个半，缺「每轮字节预算」和「绝对寿命上限」。这在「会话都短、帧都小」的现状下没问题，属可接受的取舍；但一旦出现「超长会话 + 大帧」的组合，最坏值 ~384MB/轮 是真实可达的，且当前**没有任何指标能看到**。建议的最小动作**不是改 TTL**，而是先加可观测项（每轮落档字节、在途会话数、索引 SET 基数），再决定要不要加硬上限。
