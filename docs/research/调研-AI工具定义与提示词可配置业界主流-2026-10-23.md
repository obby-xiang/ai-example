# 工具定义与提示词：可配置化的业界实践调研

调研日期 2026-10-23。对照仓：本仓（只读核查）。

---

## ① 结论先行

**工具定义：主流是「代码锚定 schema + 配置只覆盖模型侧文案」，注册表是治理面，不是定义面。**

业界没有把工具的参数 schema、handler 绑定搬进 DB 的主流做法。Spring AI 用 `@Tool`/`@ToolParam` 反射生成 schema（[Spring AI 参考](https://docs.spring.io/spring-ai/reference/api/tools.html)），LangChain 用 `@tool`，MCP server 用代码声明。真正被外置的是三类东西：description、title/显示名、usage examples——它们本质是**给模型看的提示词**，不是接口契约。MCP Registry 这类治理面存的是*元数据*（谁发布、版本、部署位置、认证方式），明确"不存工具本身"（[Kong](https://konghq.com/blog/learning-center/what-is-an-mcp-registry)）。

**提示词：主流是「代码内嵌 + Git」为默认，「专用平台」为规模化解法，终态多为混合。**

最强的反向信号来自 OpenAI 官方文档（2026 年版）：*"Store production prompts in your application code instead of creating reusable prompt objects. Code-managed prompts let you use typed inputs, code review, tests, and your normal deployment process"*，并宣布 **`v1/prompts` 于 2026-11-30 关停**（[OpenAI Prompt engineering](https://developers.openai.com/api/docs/guides/prompt-engineering)）。专用平台（LangSmith / Langfuse / MLflow Prompt Registry / Braintrust）解决的不是"版本控制"（Git 已经解决），而是**版本指针与环境晋升、版本↔trace↔eval 的联动、非工程角色编辑、RBAC**。

**本仓：维持现状是对的，且已踩在业界正确形状上。**

`tools.yaml` 只覆盖 title、schema/description 仍归注解——这正是"代码锚定 + 文案覆盖"；`ToolRegistry.forContext` 的按上下文收窄，正是 Anthropic 对工具规模化的推荐答案（[advanced tool use](https://www.anthropic.com/engineering/advanced-tool-use)）。`SYSTEM_PROMPT` 不建议外置 yaml：它的 22 条是"代码闸门的说明书"，且被 `SystemPromptUiSnapshotRulesTest` 逐字钉住，外置只会削弱"改提示词必须同步改测试"的耦合。工具定义 DB 化：不做，且有明确触发条件（见 ④）。

## ② 业界分层现状

### 2.1 工具定义面：五层，越往下越"治理"，越不碰 schema

| 层 | 承担什么 | 代表 | 何时需要 |
|---|---|---|---|
| L1 代码锚定 | schema、handler、类型、错误语义 | Spring AI `@Tool`、LangChain `@tool`、MCP server 代码 | 永远 |
| L2 文案覆盖 | description、title、examples | 本仓 `tools.yaml`；Anthropic `input_examples` | 有多角色编辑诉求时 |
| L3 运行时收窄 | 本轮披露哪些工具 | Anthropic Tool Search `defer_loading`、本仓 `forContext` | 工具 >10 个或定义 >10K tokens |
| L4 目录/注册表 | 发现、owner、审批、allowlist、环境分离、审计 | MCP Registry 官方 spec、Kong/JFrog/TrueFoundry 企业版 | 跨团队、跨供应商、外部 MCP server |
| L5 网关 | 鉴权、限流、成本、审计（在请求路径上） | Kong AI Gateway 等 | 与 L4 配套 |

关键事实与规模锚点：

- **注册表不解决问题本身，只解决发现**。官方 MCP Registry 是公开目录 + 私有 sub-registry 模型（[MCP 官方博客](https://blog.modelcontextprotocol.io/posts/2025-09-08-mcp-registry-preview/)）；第三方直说"registry 是 catalog 不是 control，它不在请求路径上，agent 查一次之后直连"（[LyZer](https://www.lyzr.ai/blog/what-is-an-mcp-server-registry/)）。企业要的是 registry + gateway 成对出现。
- **工具定义规模化后的主流解法是"检索"，不是"让运营改定义"**。Anthropic 实测：5 个 MCP server、58 个工具 ≈ 55K tokens，内部见过 134K tokens 的定义；Tool Search 把 8.7K tokens 起步、省 85%，Opus 4 的 MCP 评测从 49% → 74%。适用门槛写得很明确：**定义 >10K tokens 或工具数 10+**；少于 10 个工具反而得不偿失。
- **工具定义是"确定性系统与非确定性 agent 之间的契约"**，因此必须像代码一样测试：Anthropic 的流程是 prototype → 造 eval 任务 → 用 Claude Code 反复优化 description（[writing effective tools](https://www.anthropic.com/engineering/writing-tools-for-agents)）。
- **description 质量是系统性缺陷，不是文案问题**。对 103 个 MCP server、856 个工具的实证：**97.1% 至少有一处 smell，56% 未清楚说明用途**；补全描述后任务成功率中位数 +5.85pp、部分完成度 +15.12%，但执行步数 +67.46%、16.67% 的用例反而变差（[arXiv 2602.14878](https://arxiv.org/abs/2602.14878)）。这条直接支持"description 变更必须过 eval"。
- **"热更新"在工具面上是负资产**。tool poisoning / rug pull 的防线是**对整个 tool 对象做 hash pin，变了就隔离等人工重批**（[CSA 研究简报](https://labs.cloudsecurityalliance.org/research/csa-research-note-mcp-tool-poisoning-ai-agent-exfiltration-2/)）。这与"保存即生效"的配置化诉求正面冲突。
- **工具数量本身有上限经验值**：单 agent >100 tools 被列为反模式，建议 <20（[agentic-product-standard](https://github.com/Moai-Team-LLC/agentic-product-standard)）。

**结论**：工具定义不存在"代码 vs 配置"的二选一。业界形状是 **schema/handler 在代码，文案/示例可外置，规模化靠运行时收窄，组织化靠 registry+gateway**。

### 2.2 提示词面：四层形态，平台卖的是"联动"不是"版本"

- **L0 代码内嵌常量**：OpenAI 现在官方推荐；适合与测试强绑定、变更低频的行为规约。
- **L1 资源文件（classpath yaml/md）**：Agenta 归纳的 Pattern 1，"prompt 与代码同发布"；缺点是改动被绑到部署周期（[Agenta](https://agenta.ai/blog/git-vs-prompt-management-tools)）。
- **L2 独立 prompt 仓**：生命周期解耦，代价是双仓漂移——代码改了变量/结构，prompt 仓可能静默崩掉。
- **L3 专用平台 / prompt registry**：不可变版本 + 可变 label 指针 + 环境晋升 + trace 关联 + eval 门禁 + RBAC。

平台能力边界（都查了一手文档）：

| 平台 | 形态 | 独有边界 | 适合谁 |
|---|---|---|---|
| **LangSmith** | SaaS | commit 版本 + 保留标签 `staging`/`production` 做环境指针；`owners only` 限制谁能 promote；webhook 在 prompt commit 时触发 CI 或同步 GitHub（[docs](https://docs.langchain.com/langsmith/manage-prompts)） | LangChain/LangGraph 栈，需要"prompt 变更触发 CI" |
| **Langfuse** | MIT，可自托管 | "prompt 集中管理，SDK 客户端缓存，取值等同读内存"；label 做环境；版本↔trace 关联（[docs](https://langfuse.com/docs/prompt-management/overview)）；Thoughtworks Radar 列为 Trial（[Radar](https://www.thoughtworks.com/en-us/radar/platforms/langfuse)） | 数据驻留/自托管诉求 |
| **MLflow Prompt Registry** | Apache-2.0 | 不可变版本 + alias（`production`/`staging`）+ 血缘到 run/eval；Unity Catalog 实体（[Databricks 文档](https://docs.databricks.com/aws/en/mlflow3/genai/prompt-version-mgmt/prompt-registry/)） | 已在 MLflow/Databricks 上的团队 |
| **Braintrust** | SaaS + BYOC | GitHub Action 在每次 commit 跑 eval，指标回退即阻断；eval-gated deployment（[对比文](https://enricopiovano.com/blog/prompt-management-versioning-production)） | 工程成熟、要 eval 卡门禁 |
| **PromptLayer / Agenta / Maxim** | SaaS/OSS | 非工程角色可视化编辑、原生 A/B 流量切分、多轮模拟 | 产品/业务要直接改 prompt |

**两条容易被忽略的行业事实：**

1. **这个品类正在震荡**：2025 年中以来 Humanloop 关停、Helicone 被收购转维护模式、Promptfoo 被 OpenAI 收购、Vellum 转型、PromptHub 收摊（[2026 年实地指南](https://daily.dev/posts/best-prompt-management-tools-in-2026-the-honest-field-guide-7x0fipmhv)）。上平台 = 接受供应商存活风险，锁定成本真实存在。
2. **大多数团队连门禁都还没有**：LangChain 1,340 人调研，89% 有 observability，只有 52% 跑离线 eval（[State of Agent Engineering](https://www.langchain.com/state-of-agent-engineering)）。先上 prompt 平台、后补 eval，是把顺序做反了——平台的价值恰恰来自 eval 联动。

**何时值得上平台**（可直接引用的判据，来自 Agenta 的决策框架 + 上面的事实）：非工程角色需要直接编辑；prompt 数 >5 或需要多变体；一天内要试多个版本；需要"版本↔生产 trace"定位事故；需要环境晋升/回滚。反之（2-3 个工程师、<5 条 prompt、<每周一次变更、只有工程角色）Git 足够。

## ③ 决策框架

### 3.1 该不该可配置

| 应可配置（低风险、可热更） | 不应可配置（或无门禁不可配） |
|---|---|
| 模型、温度、top_p、max_tokens | 工具参数 schema 与 handler 的绑定 |
| 功能开关、披露开关、阈值 | 工具的风险等级、确认语义、权限判定 |
| 路由策略、token 预算、超时 | 与测试断言一一对应的提示词条款 |
| 工具显示名、UI 标题、非模型侧文案 | 安全不变量（"权限在代码里，不在提示词里"） |
| 提示词的**变量与拼装顺序** | 提示词中承载业务规则/权限边界的句子 |

判断标准只有一条：**改错它的后果，是"体验变差"还是"越权/数据损坏/契约破裂"**。前者可配置，后者必须与代码同源、同评审。

### 3.2 变更门禁的共识

共识不是"提示词要不要评审"，而是**"评审判据必须换"**：

- **提示词 / 工具描述变更 = 代码变更**：PR + review + eval + 部署（OpenAI 官方措辞即如此）。Braintrust 把它工程化成了 CI 阻断。
- **文本 diff 不够**：Git diff 只告诉你字变了，不告诉你输出变了（[Agenta](https://agenta.ai/blog/git-vs-prompt-management-tools)）。所以门禁的判据是 eval 分数与 trace，不是 review 通过。
- **禁止"保存即生效"**：不可变版本 + label 指针是行业统一形状（LangSmith / Langfuse / MLflow 三家一致）；缺 label 时 fail-fast，不静默回落。
- **约束必须落在代码**：Replit 2025-07 的删库事件里，提示词明确写了 "code freeze"，agent 仍删了生产库（经 [agentic-product-standard](https://github.com/Moai-Team-LLC/agentic-product-standard) 转引 Fortune）。提示词是"说明书"，不是"闸门"。
- **工具定义要 pin**：对 tool 对象做 hash，变更需重新审批——这条同时是安全要求，也是"不要做热更新"的论据。

## ④ 本仓对照与建议

### 4.1 现状核查（已读代码）

- `backend/src/main/resources/ai/tools.yaml`：70 行、22 个工具，**只有 `title`/`titleKey`**；文件头明确"注解是缺省，本文件是可选覆盖"，写了 `inputSchema` 就与反射 schema 对账、漂移即启动失败；并注明"改 description 会击穿 prompt 缓存，必须发新 version 并留痕，禁止保存即生效"。
- `ResilientChatService.java:132`：`SYSTEM_PROMPT` 22 条；`:300` 处拼接 `kbPromptSection` 后缀，注释明确"不改人设原文（最长稳定前缀不被击穿）"——这已经是模块化 prompt 的正确做法。
- `SystemPromptUiSnapshotRulesTest`：逐字断言第 20/21/22 条、第 10 条的收紧句、编号顺序，并写了"证红"说明。
- `ToolRegistry.forContext`（`:210`）：按上下文标签裁剪披露面；另有 `ToolSchemaReconciler`、`SheetWriteGuard`、`FrontendToolGuard` 等代码侧闸门。
- `docs/research/设计-i18n与工具可配置专项-2026-10-21.md` D5：DB 化 = 不可变版本表 + 标签指针表，缺 `production` 标签 fail-fast，读路径零 DB；已裁决定"现网无 DB 源无种子，空表期会打红全量测试"。

**对照结论**：本仓形状与业界 L1+L2+L3 完全一致，且比多数团队更严谨（schema 对账、fail-fast、读路径零 DB、披露收窄）。差距不在架构，在**规模**——22 个工具、单实例、单语言、单团队。

### 4.2 三档建议

**A. 维持（现在就应该定下来的）**

1. `tools.yaml` 保持"只覆盖文案"的边界，**不要把 `inputSchema` 真正用起来**。文件里允许写 schema 是逃生门，不是常规路径。
2. `SYSTEM_PROMPT` 留在 `ResilientChatService`，不迁 yaml。理由不是"懒得改"，而是：22 条里第 20/21/22/10 条是**代码闸门的说明书**（快照闸、披露收窄、确认卡），它们与被它们描述的实现同生共死；外置后测试只能读外部文件，`contains("未快照过的 ref 会被直接拒绝执行")` 这类"改实现必须改说明书"的强制力会松掉。
3. 工具定义 DB 化：维持"不做"。业界证据三条都指向同一结论——registry 不存工具本体、工具定义要 hash pin 而非热更新、规模化靠检索而非可编辑。
4. 模型侧 description 单语（C5 红线）与业界一致：工具描述是模型侧的 prompt 工程产物，不是 UI 文案，不应进 locales。

**B. 小步增强（低成本、随时可做，建议排期）**

1. **把 22 条拆成具名常量块再拼**（`RULES_CORE` / `RULES_DISCLOSURE` / `RULES_UI_SNAPSHOT` / `RULES_SAFETY`），字符串内容一字不改，测试仍按整串断言。收益：diff 局部化、评审时能一眼看出动了哪一类、为将来"按模型/场景裁剪规则"留接口。这与已有的 `kbPromptSection` 后缀是同一手法。
2. **给 `SYSTEM_PROMPT` 加显式版本号 + 一行变更理由**（注释或相邻常量），与 `tools.yaml` 的 `version: 2026-10-21.1` 对齐。不改变加载方式，只是让"这次为什么改"可追溯——业界 platform 的 commit message 干的就是这件事，一张表就能替代。
3. **给 `tools.yaml` 的 `version` 加一条 CI 校验**：version 变了但 `title`/`description` 未变（或反之）时告警。低成本防"改了忘升版本"，等价于业界的 immutable-version 约束。
4. **补一份工具描述 eval 的最小集**（哪怕 10 条真实用户话术 → 期望工具名），在改 description 时手动跑。这是 Anthropic 流程的最小可用版；当前仓里 description 在注解、改动必然过代码评审，缺的只是"改了之后模型还选得对"的证据。

**C. 立项改造（现在不做，写明触发条件）**

| 触发信号（出现任一条才立项） | 该做什么 | 不该做什么 |
|---|---|---|
| 工具数 >30，或工具定义 tokens >10K，或线上出现"选错工具/参数错"且无法用现有收窄解决 | 先加强 `forContext` 的检索能力（关键词/BM25），对齐 Anthropic Tool Search 的阈值 | 不要先做 DB |
| 提示词改动频率 >1 次/周，且每次都要跑全量回归 | 把 `SYSTEM_PROMPT` 拆为 classpath 资源 + 版本号，**仍走 Git**；测试改为"读资源 + 断言条款存在" | 不要直接上外部平台 |
| 出现非工程角色（产品/业务）必须改工具描述且不能提 PR | 才考虑 DB 表或平台；**前置条件：eval 门禁 + trace 已就绪**（否则是给没有刹车的车加油） | 不要在无 eval 时开放编辑 |
| 多实例/多租户/多环境需要不同工具集或不同 prompt 版本 | 版本表 + label 指针（`production`/`staging`），缺标签 fail-fast | 不要做定时轮询热更新 |
| 接入第一个外部 MCP server | **立即**做 tool 定义 hash pin + server allowlist（安全项，不是配置项） | 不要只按工具名放行 |

顺序仍然是仓里已钉的那条：DDL → DB 源 → 种子 → 测试 → fail-fast。业界只是给了它一个更强的理由：**fail-fast 的"缺标签不回落"正是 platform 三家的共同形状**，不是本仓的洁癖。

**一句话红线**：不要因为"想配置化"让改描述绕过 eval 与审批，也不要因为"要治理"把 schema 搬离代码。前者制造不可观测的行为漂移，后者制造契约破裂。
