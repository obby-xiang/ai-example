## 二、多实例 / Redis Cluster（F1–F12）

### 2.0 总判断（原文）

**核心状态面在 Redis Cluster 下基本成立**：一轮的 13 个 run 级键都带 `{tenantId:userId:run:runId}` hash tag，三条多键 Lua（`FENCED_SET` / `IDEM_PUSH` / 租约 `ACQUIRE`）与 `deleteRun` 的 13 键 `DEL` 全部同槽；序号是「一个脚本里定号 + XADD」，分配序 = 归档序 = 交付序；认领/决策/幂等索引都是 `HSETNX`；会话锁、限流、附件登记、销毁台账都是单键原子。键命名、身份作用域、TTL 续期面集中且有登记表，没有 `KEYS`/`FLUSHDB`/`SELECT`/`MULTI`/`WATCH`，唯一的跨键 `RENAME` 也确认同槽。

### 2.2 确认问题 F1–F4（逐项）

#### F1 跨实例重挂后没有心跳：连接在静默阶段必然被判死

- **调用链**：`TurnKeepalive` / `ConfirmGate.await` → `SseChatEmitter.emitInternal` → 心跳分支（不取 seq、只写 `ai:beat`、只做本地扇出）→ `requestWakePublish(0)` 直接 `return`。
- **证据**：`ai/run/SseChatEmitter.java:2216-2236`（心跳分支 + 只扇出本地订阅者）；`:2511-2516`（心跳不发布唤醒）；`:931-1010`（重挂只走归档回放，不产生合成帧）；测试把「心跳不发唤醒」钉死：`backend/src/test/java/com/example/configmgr/ai/run/SseChatEmitterFrameStoreTest.java:76-100`。
- **影响**：驱动在 A、客户端重挂到 B（三实例网是非粘滞代理，`cluster-3node.yml` 明说「任意实例可 reattach」）。若此刻 A 处于压缩（L2 摘要最长 60s/次）、慢工具或上游静默，B 的连接收不到任何帧 ⇒ 前端 30s 首帧看门狗（reattach 用 `DEFAULT_FIRST_FRAME_TIMEOUT_MS`）或 45s 帧间看门狗触发（`frontend/src/api/sse.ts:34`、`:83`、`:894-900`），4 次重连后给用户报错，而服务端这一轮其实正常在跑。
- **报告最小修复**：在「本实例不是驱动方」的写出器上，为每个已 attach 订阅者启动**本地**、无 seq 的保活节拍（或读 `ai:beat` 后本地合成 `heartbeat`），条件是该 run 非终态且本进程无驱动登记；心跳仍不入档、不占 seq；或扩展 wake 载荷（心跳专用频道/上界 0 的唤醒）。

#### F2 park 后前端工具的到期收敛只在原实例进程内成立

- **调用链**：`ConfirmGate.await` → park 退出 → `scheduleParkedFrontendExpiry`（`retryScheduler.schedule`）→ 到点 `expireFrontend` + `triggerResume`。
- **证据**：`ai/gate/ConfirmGate.java:715-733`、`:1192-1233`；到期信息已持久化在 `PendingToolCall.expiresAt`（`ai/run/PendingToolCall.java:167-170`），但**没有任何读侧用它做收敛**：重挂（`AiController.events`）、启动扫描（`StartupResumeRunner.discoveryOf`）都只按 `PENDING` 跳过；`ai/run/StartupResumeRunner.java:651-661`（`PENDING_UNRESOLVED` 直接跳过）。
- **影响**：实例 A park 后被杀，或被调度到 B 重挂；120s 到期的即时类前端工具（`navigate_to` 等）永远停在 `PENDING`，该轮永久 `SUSPENDED`、没有终帧、没有驱动方；用户不主动点/提交就一直挂着。确认门本身「无上限」是设计，不受影响。
- **报告最小修复**：把到期判定做成**任何实例可做**的收敛——在 `/events` attach、`/api/ai/confirms` 列表/决策入口或运行期扫描里，按 `expiresAt < now && status=PENDING && kind=FRONTEND` 调既有 `expireFrontend` + `tryRecordDecision`/CAS（决策 guard 已保证多实例只赢一次），不需要新设施。

#### F3（最高）取消的终结路径全是进程内触发；驱动进程已死时永不落终态，并连带把会话销毁永久卡死

- **调用链**：①`POST /api/ai/cancel/{runId}` 只写 Redis 旗标（`ai/web/AiController.java:1379-1412` → `ai/run/CancellationRegistry.java:160-175`）；②真正的终结（快照 `CANCELLED` + `done{cancelled:true}`）只有两个进程内触发：`ResilientChatService` 写门失败交棒（`:549`）与 `ConfirmGate` park 退出交棒（`:1104`）→ `CancelledRunFinalizer.handOff` → `ResumeService.cancelConfirmed`（`ai/run/ResumeService.java:2541-2640`），**没有启动/运行期扫描或重挂路径调用它**；③启动/运行期扫描对「已取消但非终态」显式跳过（`ai/run/StartupResumeRunner.java:651-661`，`cancelled → Discovery.CANCELLED`）。
- **影响**：
  - 运行中轮次的驱动进程被杀（`kill -9`/Pod 重启）+ 用户随后取消 ⇒ 该轮永远 `RUNNING`（或 `SUSPENDED`）且带取消旗标，没人写终态、没人发 `done`；重挂连接会一直保持直到前端看门狗耗尽。
  - 更严重：会话销毁 `AiSessionPurgeService.executeDeletion` 先 `cancelActiveRuns` 再 `awaitTerminal`（`:841-890`），仍非终态则 `deleteOrDefer` 记 `deferred`（`:1166-1190`），`complete=false` 永远重试；`ai:purge:pending` 无 TTL、`SessionPurgeGuard.isArmed` 同时看 pending（`ai/session/SessionPurgeGuard.java:120-132`）⇒ **该会话永久 410 GONE 且删不掉**。
- **报告最小修复**：扫描发现 `cancelFlag=set && status 非终态` 时不跳过，走 `cancelConfirmed`（自己会抢租约、校验取消事实、幂等按归档终帧）；或 `/cancel` 端点发现「本进程无该轮驱动/无等待闸门」时直接 `handOff`；`cancelActiveRuns` 对「已取消但未终态」的 run 应调 `cancelConfirmed` 而非只等。

#### F4 `LeaseService.isHeld` 的吞异常与调用点的 fail-closed 契约相反

- **调用链**：`AiController.isDeadRound`（会话门判死放行）与 `StartupResumeRunner.deadWithoutDriver`（运行期扫描判死接管）都在 try/catch 里认为「租约读不出来 ⇒ 抛异常 ⇒ 按可能有人持有处理」。
- **证据**：调用点 `ai/web/AiController.java:1334-1352`、`ai/run/StartupResumeRunner.java:599-620`；被调方实际**吞掉异常返回 false**：`ai/run/LeaseService.java:1090-1101`（注释明确这是给对账用的 fail-open 口径）。
- **影响**：`hasKey` 失败（单节点故障、MOVED/TRYAGAIN 超时、集群抖动）而快照/活动锚点仍可读时，一个**仍有租约的活轮**会被判死：会话门被 `releaseDeadHeld` 强释放，同一会话可在本实例再起一轮（配合 `SessionGate` 降级进程内门就真并发）；运行期扫描也可能提前接管。概率不高，但错误方向正是「双驱动」。
- **报告最小修复**：新增 `isHeldStrict(key)`（异常上抛）或三态返回，供 `isDeadRound`/`deadWithoutDriver` 使用；原 `isHeld` 保留给 `ToolUnknownReconciler`。

### 2.3 风险 / 测试缺口 F5–F12（逐项）

#### F5（风险）写门 `NEVER_HELD` 分支仍允许非持租实例 plain `SET`

- **证据**：`ai/run/RunStore.java:1136-1197`（`epoch==0` 分支，`:1183-1195` 为 plain `SET`）；`ai/run/LeaseService.java:832-848`（`NEVER_HELD` 判定）。
- **影响**：当前生产调用图里非终态快照写基本都在驱动线程（持租）或「新建轮次」路径（`ResilientChatService.chat` 先 `create` 后 `takeDriveOwnership`，`:717-746`），尚未看到活的越权覆盖；但写门**无法区分**「我正在创建这一轮」与「这一轮已被别人持租，只是我没租约」。一旦以后有跨实例写快照的新入口（取消收尾、修数据、重跑优化），它会静默 plain `SET` 覆盖新主人的快照，fencing 失效。取消态写（`CANCELLED` 不受守卫）同理可覆盖 DONE（配合 F11）。
- **报告最小修复**：给「已存在快照 + NEVER_HELD」改成 fail-closed（`EXISTS` 命中即拒写，或先抢租约再写第一笔），只对「新建（键不存在）」保留 plain `SET`。

#### F6（测试缺口）没有真实 Redis Cluster 的端到端门禁

- **证据**：三实例网启动的是**单节点** `redis:7.2.16`（`scripts/ci/cluster3-run.sh:355-362`）；`cluster-3node.yml:8` 声称验证「跨实例」，但槽/重定向面不在覆盖内；双实例 harness 同样单节点，脚本自承认只做客户端算槽的静态证明（`scripts/b23l1-dual-instance.ps1:630-633`）；唯一「真集群」是 `scripts/redis5-cluster-smoke.sh`（只跑 `redis-cli`/`XRANGE` 级冒烟）；`ClusterSlotTest` 用 `FakeLeaseRedis` 模拟 16384 槽（`backend/src/test/java/com/example/configmgr/ai/run/ClusterSlotTest.java:1-160`）；静态守卫只禁 `KEYS/SCAN/FLUSH/SELECT/排他 ID`，**不检查**多键调用/脚本的 tag 一致性（`scripts/ci/forbid-redis-cluster-unsafe.mjs:56-115`）。
- **影响**：真实的 `CROSSSLOT`、resharding 期间 MOVED/ASK、跨节点 pub/sub 窗口、Lua 长阻塞都无门禁；新增一个 `delete(List.of(...))` 或新脚本混入未打 tag 的键，CI 全绿。
- **报告最小修复**：把 `b23l1-dual-instance` 的 Redis 换成 3 主 Cluster（或至少加一条「真 Cluster 起两实例跑 suspend/reattach/decision」），并把「多键调用键集合同槽」做成静态规则（解析 `List.of(...)` 实参的键构造器）。

#### F7（风险）单槽热键：`ai:runs` 与 `ai:purge:retry:queue`

`ai:runs` 是无 TTL 的全局 SET，`create` 路径会节流执行 `SMEMBERS + 逐成员 EXISTS`（`ai/run/RunStore.java:2360-2420`），启动扫描也全量读；`ai:purge:retry:queue` 是单 LIST（`ai/session/SessionPurgePendingStore.java:71`）。单节点上只是慢；Cluster 下这些键永远落在**同一个 master**，所有实例的发现/清理流量集中到一个分片，`SMEMBERS` 大集合会阻塞该节点。不影响正确性，属扩容风险。**建议**：索引按 `tenantId % N` 分桶（成员仍带完整身份），或至少把 prune 改成 `SSCAN` 游标 + 抽样。

#### F8（风险）TTL 登记表漏项：`ai:xtrim`（以及 `observed/ledger/idem/claim` 只随写续期）

`SessionKeyRegistry` 的 HEARTBEAT/READ/WRITE 三面登记（`ai/run/SessionKeyRegistry.java:129-158`）不含 `ai:xtrim`；其 TTL 只在真实裁剪时写入（`ai/run/RedisFrameStore.java:396-410`）。影响：长时间 park（24h 级，其余键被心跳续着）后 `ai:xtrim` 先过期而 `ai:xevents` 还活着 ⇒ 重挂时无法得知「归档被裁过」，`truncated=false`，前端把不可恢复的缺口当完整回放（不丢已存帧，只错误报告完整性）。同类：`ai:ledger/ai:idem/ai:claim` 过期后仍能靠 pending 的 `executed/resultText` 判定，属降级；`ai:observed` 过期理论上允许 24h 后再发一条 `tool_call_end`。**最小修复**：把 `ai:xtrim` 加入 `Renewal.READ`（或随 `xevents` 续期），`ai:observed` 加入 READ 面。

#### F9（风险）文件/附件字节在本地盘，「多实例闸门」只校验绝对路径

上传落盘 `ai/form/GenerativeFormAttachmentController.java:178-200` → `file/FileStorageService.java:69-90`（`baseDir` 是本地目录）；登记在 Redis（跨实例可见）`ai/form/RedisFormAttachmentStore.java:126-160`；多实例闸门只要求绝对路径 `file/FileStorageMultiInstanceGuard.java:10-40`、`:83-130`；会话销毁只删**本机**文件 `ai/session/AiSessionPurgeService.java:1362-1390`。`app.file.multi-instance=true` + 绝对路径（如每 Pod 本地卷 `/var/app/files`）能通过启动闸门，但 A 上传的附件在 B 上不存在：表单提交/工具读取报「文件不存在」，销毁时也可能漏删另一台盘上的副本。**最小修复**：启动期做「写入-读回」探针，或在复用指南里把它列为硬前提（对象存储更彻底）。当前 CI 三实例网正是共享目录，因此不会红。

#### F10（风险）限流 IP 维度默认退化为「代理 IP」

`ClientIpResolver` 默认 `trusted-proxies: []` ⇒ 只认 `RemoteAddr`（`config/ClientIpResolver.java:23-30`、`backend/src/main/resources/application.yml:492-501`）。三实例网前面有 HAProxy（非粘滞），若部署不配可信网段，所有用户共用 `ai:rate:ip:<LB-IP>`（60/分），一个用户刷满即全员 429；会话维度仍按身份分桶，表现为「限流看起来生效但不合理」。**最小修复**：沿用 `FileStorageMultiInstanceGuard` 的做法，在多实例 profile 下要求 `app.web.trusted-proxies` 非空，否则启动失败。

#### F11（风险/自述未实现）跨实例「终帧恰好一条」没有原子位

`SseChatEmitter` 自己在 `beginDrive` 注释里承认：「跨实例并发下终帧恰好一条仍需要原子终帧位（与 fence 同事务的条件写），本批**未做**」——`ai/run/SseChatEmitter.java:1100-1101`。可达形态：A 正在收尾（写 DONE → 准备发 `done`），B 收到取消并走 `cancelConfirmed`，其「归档终帧」检查（`ResumeService.java:2590-2600`）与 A 的落档之间存在窗口；A 先落 `done` 后 B 仍可能写 `CANCELLED` 快照并再发一条 `done{cancelled}`，表现为两条终帧 + DONE→CANCELLED 覆盖（快照与归档不一致）。**最小修复**：在 `ai:decided` 同级增加 per-run 终帧位（`HSETNX`/Lua CAS，key 用同一 tag），`done`/`error` 落档前先抢位；或把终态写与终帧落档合成一个带 fence 的 Lua。

#### F12（风险）每次快照写都在 Lua 里 `cjson.decode` 整份快照

`TERMINAL_SET_IF_NOT_CANCELLED` / `FENCED_TERMINAL_SET` 在脚本内解析当前快照全文判断 `status/cancelled`（`ai/run/RunStore.java:355-386`）。`messageJson` 是整窗历史，可达数百 KB 甚至更多；脚本串行执行期间会**阻塞持有该槽的整个节点**。单 Redis 上只是全局卡顿；Cluster 下同一节点承载大量无关槽，爆炸半径变大。**建议**：把「是否取消」抽到一个小键（如 `ai:cancelstate:{tag}`，或复用 `ai:cancel`），守卫只读小键。

### 3.3 D1（确认缺陷，当前生产路径不可达）：SSE 写出器在「无身份构造」时永久钉死 legacy 键族

- **证据**：`SseChatEmitter.java:566-568` 构造时抓 hints；`:2758-2795` 中当 `hint == null` 时跳过读记录，直接 `identityResolved = true`、`deliveryIdentity = null`；随后 `identityUnconfirmable` 只在 `readFailure` 为真时拦（`:2812-2817`），所以**帧会照常写 legacy 键、发 legacy 频道**。`RunRegistry.java:174` 又按 `LocalRunKey.of(runId)`（当前线程身份）缓存写出器。
- **影响**：若某入口在无身份线程上首次 `registry.of(runId)`（而记录其实带身份），该写出器的帧/序号/活动锚点全部写进 `ai:events:{run:<id>}`、唤醒发到 `ai:wake:<runId>`；驱动侧（带身份）写的是身份键族——同一轮出现**两个帧命名空间**，重挂回放看不到另一份，跨实例唤醒分叉。现有测试把这一行为「固化」为期望（`SseChatEmitterIdentityTest.java:91-105` 只断言「不 adopt 池线程身份」，没断言「不写 legacy」）。
- **报告最小修复**：`deliveryIdentityOutcome` 在 `hint == null && store != null` 时**不置** `identityResolved`（本拍按 `readFailure=true` 明确失败/跳过，或抛给调用方），或把 `SseChatEmitter` 构造改为必须显式传 `TenantUser`（`RunRegistry.of` 在无身份线程直接抛而不是静默建 legacy 写出器）。单测加一条：「记录有身份 + 构造无线程身份 ⇒ 不得写 legacy 键」。
- **可达性**：三个前置（无身份线程首次 `registry.of`）在现有调用点（`AiController.java:461/1032`、`ResumeService.java:1182/1999`、`ConfirmGate.java:549/636/1134/1759`、`SpToolCallingManager.java:723/1148`、`HostForm.java:180`）均**不成立**，故标「潜伏」。

### 3.4 D2（范围缺口）：租户上下文已传到工具线程，但工具体完全不使用

- **证据**：`ai/tools/AiTools.java` 及其依赖的 `task/definition/data` 全包 `RequestContextUtils|TenantUser|tenantId` 0 命中；业务实体无租户列；`SpToolCallingManager` 把身份传到了工具执行线程（`:708`、`:2632`）却无任何工具消费。
- **影响**：AI 的「租户/用户」只隔离对话数据（会话/run/记忆/附件/上下文/反馈），**不隔离业务副作用**——租户 A 的模型可以让工具读写租户 B 任务/定义/数据（只要知道 id）。若产品口径是「AI 租户 = 仅对话数据」，应显式登记为不承诺项；否则这是隔离缺口。
- **报告最小修复**：在 `ToolRegistry` 调用前注入 `TenantUser`，工具层对业务查询加租户/用户维度（需业务表加列），或在架构文档/`/health` 明确「业务数据不参与租户隔离」。
- **报告判据**：以实体/服务层 grep（`tenant` 0 命中）与 `AiTools` 无身份引用为依据；若业务数据本身不分区，这是**不承诺项**而非缺陷，**需产品口径确认**。

### 3.5 R1–R7（逐项）

#### R1（风险，中）身份读取异常时静默丢帧（含终帧）

- **证据**：`SseChatEmitter.java:2096-2112`——`deliveryIdentityOutcome()` 读记录抛异常且无提示时直接 `return`（不落档、不入队、不投递），只 WARN/DEBUG；注释说「下一拍重试」，但**该帧本身不会重试**。写路径同型（`:2991-2999` 直接摘连接）。
- **影响**：若 `done`/`error` 恰在此刻被跳过，归档里没有终帧、客户端只收到 EOF；重挂回放也补不回，前端只能等自己的看门狗。不是身份泄漏，但违反「每轮必有终态」的对外契约。
- **报告最小修复**：终帧（`done`/`error`）在身份不可确认时进「待重发」队列（或用已确认的提示身份重试 N 次），或在 `complete()` 前补一次「终帧是否已落档」检查并按 `unconfirmed` 语义收尾。

#### R2（风险，低-中）`ResumeService` 三处「先读快照、后开记录身份作用域」

- **证据**：`ResumeService.java:1056-1062`（仅模型步重跑）、`:1532-1539`（续跑）、`:2558-2563`（取消收尾）。注释都声称「身份只从记录恢复」，但**首次读用的是调用线程身份**。
- **影响**：今天所有调用方都带记录身份（HTTP/触发池/交棒/扫描），行为正确；一旦新增无身份入口（或 TTL 装饰被调整），首读会静默返回 `null` → `NOT_FOUND`/`NO_RUN`，表现为「轮次不存在」而不是「身份缺失」，排障会走错方向。
- **报告最小修复**：首读改成显式读口 `store.get(runId, tenantId, userId)`（身份由调用方以参数传入，扫描已有 `IndexRef`），或至少在方法入口 `require()` 断言身份并标注来源。

#### R3（风险，低-中）`driveResumed` 的身份同样来自「先读快照」

- **证据**：`ResilientChatService.java:878-884`：`snapshot = resumeSnapshot(runId)`（`:1205-1214`，线程身份读）→ 再 `RunIdentityScope.open(snapshot...)`；快照读不到时打开的是 **denied 作用域**，整轮会在「空身份」下跑（帧/台账/记忆写 legacy）。
- **影响**：依赖 `ResumeService` 先 `withRunIdentity` 再提交（现在确实如此）。任何「直接调用 `driveResumed`」的新入口都会静默落到 legacy 命名空间。
- **报告最小修复**：`driveResumed` 增加显式 `tenantId/userId`（或 `RunSnapshot`）重载，由 `ResumeService` 直接传，不再二次读；保留旧签名做兼容但内部 `require()`。

#### R4（风险，低）取消交棒的去重键与清理键不同源

- **证据**：`CancelledRunFinalizer.java:183-184` 用**交棒时刻记录身份**拼键；`:257-262` 的 `forget(runId)` 用**当前线程身份**拼 `LocalRunKey.of(runId)`（`:342-345` 直接 remove）。
- **影响**：若终态清理发生在与交棒身份不同的线程（当前所有调用点都带记录身份：driver / cancel-finalizer scope / HTTP），`inFlight` 与 `attempts` 不会释放 → 同一 run 后续 `handOff` 永远返回 `false`（「已在交棒中」）⇒「已取消但没有终帧」。
- **报告最小修复**：`forget` 增加身份参数（或按 runId 扫描 `inFlight` 前缀删除），由 `clearTerminalRunState` 传入记录身份。

#### R5（风险，低）启动扫描不校验 `TenantUserDirectory`，可驱动 HTTP 面已不可达的身份

- **证据**：`StartupResumeRunner.java:212-226` 只用 `RunIdentityScope.usable(tenantId, userId)`（`:91-93`：只要 `tenantId>0` 且 `userId>0` 或 `-1`）；HTTP 面要求 `TenantUserDirectory.exists`（`TenantIdentityFilter.java:144-147`），而目录是硬编码 4 个组合（`TenantUserDirectory.java:38-41`）。
- **影响**：目录里被移除的身份（或未来由系统路径写入的 `userId=-1` 记录）**用户永远读不到**，但后台扫描/运行期扫描照样会续跑它（发起模型调用、执行工具副作用）。属「系统路径比用户路径更宽」的不对称。
- **报告最小修复**：扫描续跑前加 `TenantUserDirectory.exists`（或可配置的允许清单）校验；`-1` 只允许来自显式系统来源（记录带 `createdBy=system` 标记）。

#### R6（风险，低）`/api/ai/kb/**` 被身份边界覆盖，但前端注释说不纳入

- **证据**：`TenantIdentityFilter.java:100-113` 不排除 `kb`；`ai/kb/AiKbController.java:29` 映射 `/api/ai/kb`；前端注释却写「模型配置 / provider / KB / 审计 … 不纳入」（`frontend/src/api/http.ts:143-145`），而 `isAiConversationPath` 实际不给 KB 例外（`utils/ai-identity.ts:204-235`）。前端目前没有调用 KB（`grep '/ai/kb'` 0 命中）。
- **影响**：一旦设置页/运维脚本在「未选 AI 身份」时调用 KB，会得到 400 `TENANT_IDENTITY_REQUIRED`（全局数据被要求租户身份）。当前无 UI 影响。
- **报告最小修复**：二选一并同步三处（后端排除表、前端排除表、注释）：要么把 `/api/ai/kb` 加入精确排除，要么删掉注释里的「KB」。

#### R7（风险，低-中）前端 `/confirm`、`/frontend-tool-result` 无显式身份头，切身份窗口可丢决策

- **证据**：`frontend/src/api/ai.ts:51-58` 两个写入口都不带 `headers`；拦截器在**微任务**里按 `currentAiIdentity()` 补头（`api/http.ts:154-170`）；调用方只在**回包后**用 `identityAtDecision/identityAtSubmit` 判定丢弃（`stores/ai.ts:6207-6216, 6347-6351`）。取消入口则显式带旧身份（`:7827-7829`），说明同类窗口已知。
- **影响**：切身份发生在「捕获身份 → axios 拦截器执行」之间时，决策会以**新身份**发出 → 后端在自己键族里找不到条目 → 409 `UNKNOWN_TOOL_CALL` → 前端按 `stillLive=false` 丢弃。旧轮的决策静默丢失；`switchIdentity` 只对 `activeRunId` 做 best-effort cancel（`:8199-8203`），`activeRunId` 为空（例如刷新恢复的挂起卡未设 activeRunId）时不兜底。
- **报告最小修复**：与 cancel 同口径——`api/ai.ts` 的 confirm/frontendToolResult 接受 `headers`，调用方用 `identityHeaders(identityAtDecision)` 显式传；或拦截器改为「同步捕获一次身份快照」而不是微任务现读。

### 3.6 上下文测试缺口（原文 §三，7 条）

1. **D1**：没有「记录有身份、写出器构造时无身份 ⇒ 不得写 legacy 键/频道」的用例（现有用例把 legacy 行为当期望，`SseChatEmitterIdentityTest.java:91-105`）。
2. **R2/R3**：没有「无身份线程调用 `ResumeService.cancelConfirmed/retryModelStep` 或 `driveResumed` 必须 fail-closed 且给出可区分结局」的守卫用例。

4. **R5**：`StartupResumeLegacyNoIdentityTest` 只覆盖 0/0；缺「目录外身份（如已撤销用户）不被系统扫描续跑」的用例。

6. **R7**：缺「切身份与 `/confirm` 并发 ⇒ 不得以新身份发出旧轮决策」的前端用例（现有只测回包丢弃）。
