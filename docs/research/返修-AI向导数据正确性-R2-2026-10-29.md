## R2-1：`set_condition` 先校验后写

### 根因

`export.setConditions` 的顺序是"先落状态、后校验"（实际是**根本不校验**）：转草案 → 写
`draftModels` / `touchedConditions` / `counts` → 直接 `PUT` 原样条件 → 回「已设置…并落库」。
`IN []` / 值算子空串这类输入 `buildConditionOutcome` 判 `invalid`，但只有到 `confirm_step`
（`persistStepData` 的 `assertConditionBuildable`）才被拦 —— 结果是"AI 说已设置"、服务端已被
写了一份非法条件、随后一步才失败。

### 修改（`frontend/src/views/ExportWizardView.vue`）

```ts
const model = draftModelFromCondition(condition)
const verdict = buildConditionOutcome(model)      // 与 persistStepData 同一判据
if (verdict.status === 'invalid') {
  return { ok: false, reason: `${describeConditionInputIssues(verdict.issues)} 本次未设置 …（未落库、未改动页面条件）…` }
}
// 校验通过后才写：draftModels / touchedConditions / counts / PUT(原样) / workspace.setQueryConditions
```

要点：

- **零写**：失败分支在写任何状态或发请求之前返回；草案、`touchedConditions`、`counts`、
  工作区与任务项都不动（后续 `confirm_step` 也不会补写它）。
- **可行动**：文案复用既有 `views.export.conditionInput.*`（"请补上值或改用「为空 / 不为空」"）
  再补三条具体指引（值算子必须填值 / IN 至少一个值 / 空值判断用 `EMPTY`·`NOT_EMPTY`）。
- **合法复杂条件原样落库**：校验只读不重建，`stringifyCondition(condition)` 仍是调用方给的原始
  条件（同字段多条件、含逗号 IN 都逐字保留）。

## R2-3：导入侧定义就绪等待 / 恢复

### 根因（精确）

- `loadDefinitions` 只有一次挂载调用、**无单飞、无重试**；`selectedDefs` 的 watch 会在定义到达前
  触发 `loadEditors()`，此时 `editorDefs` 为空 ⇒ 一次什么都没载入就结束。
- 纯"定义请求慢但最终成功"的**挂载路径**其实由 `onMounted` 末尾那次 `await loadEditors()`
  兜住（`Promise.all` 含 `loadDefinitions`）；但**首轮定义失败**（服务或网络抖动）后，任何后续
  触发（换任务 `bindTask → loadTask → watch → loadEditors`、AI 工具、`ensureStepLoaded`）都
  只会在空 `defs` 上再空跑一次，**没有任何补请求 / 恢复钩子** ⇒ 编辑区永久空白。
  这就是"定义不可用窗口"在导入侧真实可达的形态（与导出侧同类）。

### 修改（`frontend/src/views/ImportWizardView.vue`）

- `DEFINITIONS_READY_TIMEOUT_MS = 10_000`、`defsLoaded`、`defsInFlight`：`loadDefinitions` 单飞并
  返回真实结局；成功后 `void recoverEditorsAfterDefinitions()`。
- `awaitDefinitionsReady()`：在途时有界等待（不无限等）。
- `ensureDefinitionsForEditors()`：编辑区真要载入时 —— 定义已有 ⇒ 直接过；在途 ⇒ 等；**首轮失败
  过** ⇒ 补一次请求；成功读到空列表 ⇒ 不再重复。
- `loadEditorsNow`：在 `await nextTick()` 之后、计算 targets 之前，若选中项有定义缺失且 `defs`
  为空 ⇒ `await ensureDefinitionsForEditors()`（代次复检），再按真实定义算 targets。
- `recoverEditorsAfterDefinitions`：第 1 步、有任务、有选中项时 `await loadEditors()`（只补未载入的）。
- 失败路径不变：定义仍不可用 ⇒ `editorDefs` 为空 ⇒ 不按 0 字段载入、`editorState` 不置位 ⇒
  写回闸（`flushEditors` / `flushDirtyDefs`）不放行。

## 边界与不声称

- 定义等待上限 10s 为常量（非配置项）；`ensureDefinitionsForEditors` 的"补一次"只在
  `!defsLoaded` 时发生 —— 定义服务持续不可用时，每次编辑区载入都会再试一次（无缓存、无退避），
  这是可接受的用户/AI 触发频率，但**不是**自动轮询。
- 导入侧仍无「重试定义」的可见入口；服务恢复后的补载靠下一次编辑区载入或换任务触发。
- `set_condition` 的校验只覆盖"条件本身可提交"（与 `persistStepData` 同口径）；服务端仍可能因
  未知算子/字段不存在等 400 拒绝 —— 那条路径保持原有"落库失败"如实回执，不并入本地校验。
- 定义列表读空（服务健康但确实没有定义）时，导入编辑区同样不载入、写回不放行（fail-closed）。
- 真机 E2E、真实后端定义服务（慢响应/失败率分布）未验。
