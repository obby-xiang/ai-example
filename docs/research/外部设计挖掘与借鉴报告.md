## 1. HITL：确认门 / 中断-恢复形态

### 1.1 三方机制要点

| 家 | 机制 | 源码核实 |
|---|---|---|
| AG-UI | `Interrupt` 六件套 `id/reason/message/toolCallId/responseSchema/expiresAt`（+metadata）；`ResumeEntry` 仅 `resolved｜cancelled` 两态，拒绝语义表达在 payload 内；resume 必须 **1:1 覆盖**全部 open interrupt（缺/多皆抛错）；**过期 interrupt 唯一出路是 `cancelled`**；outcome = `success｜interrupt｜cancelled`（无 error，失败只走 `RUN_ERROR`）；success 可带 `pendingToolCallIds`（已 START 无 RESULT 的调用，交下一轮 messages 回答） | `spec/1.0/schema.json`、`fixtures/ResumeEntry/{valid,invalid}`、`sdks/typescript/packages/client/src/interrupts/index.ts` |
| CopilotKit | `ɵInterruptState` 统一 legacy/standard 两态；`respond` 前先 `agent.addMessage(role:"tool")` 再 `runAgent({resume})`；服务端把每条 ResumeEntry 合成 tool-result 再调模型一次；HITL 工具以 `interrupt` 标记，服务端不执行不发 `TOOL_CALL_RESULT` | `packages/core/src/interrupt-state.ts`、`packages/react-core/src/v2/hooks/use-interrupt.tsx:233-360`、`packages/runtime/src/agent/index.ts:1314-1362,1934,2051` |

### 1.2 我方现状（经 `AI/` 源码核实）

`confirm_request{toolCallId,name,args,summary,timeoutSeconds,callback}` + `confirm_decision{decision:approve|reject|timeout|cancel}` 两帧；`ConfirmGate` 状态机 `PENDING→APPROVED/REJECTED/TIMEOUT/FRONTEND_RESULT/CANCELLED/EXECUTED`（`AI/gate/ConfirmGate.java`、`AI/run/PendingToolCall.java:21-39`）；挂起期 2s 心跳带 `suspendKind/toolCallId/waitedSeconds/timeoutSeconds`；决策先写 Redis 再唤醒进程内 latch；执行由 `RunStore.claimExecution`（HSETNX 原子认领）保证恰好一次。

### 1.3 差距

1. `confirm_request` 无 `responseSchema`（前端确认卡无法结构化收集拒绝理由等复杂应答）与显式 `expiresAt` 时钟语义（仅有 timeoutSeconds 倒计时）；【实测-源码核实（对照），推断（影响）】
2. 一次 run 多个 toolCall 并发挂起时，无"决策必须 1:1 全覆盖"的协议级语义（我方按 toolCallId 逐个独立处理）；【推断】
3. confirm 请求无防伪：`POST /confirm` 只凭 `runId+toolCallId`，任何人可替他人批准/注入结果（P11② 已识别，无用户体系下无归属锚点，ADR-11b 已知风险接受）；【实测-源码核实：`AI/web/AiController.java`】
4. ADR-2 已预告"确认门超上限场景转异步确认模式（M2）"，该形态恰为三家的轮次终态化模型，当前帧协议未预留。

### 1.4 借鉴建议

| # | 建议 | 出处 | 我方现状/差距 | 借鉴价值 | 落地 | 证据等级 |
|---|---|---|---|---|---|---|
| R1-1 | `confirm_request` 增补 `responseSchema`（可选，声明期望的决策应答结构，默认 null）与 `expiresAt`（绝对时间戳） | AG-UI `Interrupt` 六件套 | 见差距 1 | 前端确认卡可按 schema 渲染表单（如"拒绝必须填原因"）；绝对时钟消除多端时钟漂移 | **当前微调**（帧向后兼容加字段，S4.4 前端同步） | 【实测-源码核实】 |

## 11. 其他维度

### 11.1 token 计量

- 三方：AG-UI `TokenUsage[]`（provider/model 维度，input/output 总量 + reasoning/cachedInput/cacheWriteInput 组成部分，仅挂终态事件）；CopilotKit `aggregateRunUsage` 按 provider+model 分组求和；Vercel UI 流协议**无 usage**（靠 messageMetadata/data part 外挂）。【实测-源码核实：`spec/1.0/schema.json`、`<RESEARCH_SRC>/copilotkit/packages/runtime/src/agent/converters/usage.ts`、`<RESEARCH_SRC>/vercel-ai/packages/ai/src/ui-message-stream/ui-message-chunks.ts`】
- 我方：`done.usage{promptTokens,completionTokens,totalTokens}`（依赖 stream-usage:true），无持久化、无 cached/reasoning 维度。
- 建议：**R11-1（当前微调）** usage 字段对齐 AG-UI 字段模型（加 cachedTokens/reasoningTokens 等可选字段，为成本核算留口）；**R11-2（M2）** usage 入库（与 R7-1 同一落点，FR-5.6/§8.3 既有要求）。证据等级【实测-源码核实】。

### 11.2 多模态

- 三家均有 Image/Audio/Video/Document 输入与工具结果 parts；我方明确不做（`ReasoningAwareOpenAiChatModel` 显式简化为纯文本）。**不采纳**（范围外，DC 层无需求）。【实测-源码核实】

### 11.3 MCP 兼容性

- AG-UI 1.0 无 MCP 概念；CopilotKit 以 MCP middleware 挂外部工具（`mcpClients/mcpServers`，merge 保重名不互相覆盖）。【实测-源码核实：`spec/1.0/schema.json` grep、`packages/runtime/src/agent/index.ts` mergeMCPTools】
- 建议：**R11-3（M2+ 观察）**——若未来要接 MCP server（如接入企业工具生态），CopilotKit 的 merge 策略（重名不覆盖 + 服务端注册）可参考；M1 我方 16 工具自有注册足够。**不采纳（M1）**。

### 11.4 Agent 间协议

- AG-UI 的 `SUBAGENT_*` 事件 + `Attributable.subagentRunId` 归属 + `AgentCapabilities.multiAgent`；我方单 agent 单 run。**不采纳**（范围外）。【实测-源码核实】

### 11.5 错误与终态语义

- AG-UI：outcome 三分 `success/interrupt/cancelled` + `RUN_ERROR` 独立（error 不是 outcome）；我方 `done{cancelled}/error` 二分 + 错误码后缀体系（`_AFTER_PARTIAL/_AFTER_TOOL_SIDE_EFFECT`）——**我方错误码语义粒度优于三家**（记录为优势）；三分语义在 M2 异步模式时随 R1-4 一并对齐。【实测-源码核实】

### 11.6 前端状态机

- Vercel Chat 状态机：`SerialJobExecutor` 串行化 chunk 应用、messages 节流渲染而 status/error 直通、`isCurrentRequest()` 丢弃过期 resume。**R11-4（当前微调，S4.4 设计输入）**：Vue 侧 `shallowRef` + 串行队列 + 节流的三件套形态可直接平移（思想可移植，组件不可）。【实测-源码核实】

## 13. 我方优势清单（防为新而新；均经源码核实）

1. **挂起外置 + 跨进程续跑 + 台账恰好一次**：RunStore 快照 + `ai:claim` HSETNX 原子认领 + `ai:ledger` 对账（`AI/run/RunStore.java:267,289`）。三家均无对应：AG-UI 无恢复、Vercel 靠外部 workflow 运行时、CopilotKit 靠外部 Intelligence 服务。
2. **服务端帧外置 + reattach 回放**：`ai:events` Redis LIST + `/events/{runId}` 回放（终态即 complete）。AG-UI 明文无流恢复；Vercel resumable-stream 流内容在进程内存（单进程）；CopilotKit /connect 依赖服务端 thread 存储。
3. **心跳带 pending 语义载荷**（suspendKind/waitedSeconds/timeoutSeconds，`ConfirmGate.java:213`）：三家心跳要么没有（AG-UI）、要么纯保活注释帧（Vercel keepAliveMs 默认关）。
4. **服务端持有权威消息历史**：无用户体系 + 多实例下天然防"前端篡改历史/结果注入"（三家客户端持史重发模型是注入面）。
5. **单轮内阻塞续接**：审批后同一次模型调用续流（省一次往返）；三家全部需二次请求（CopilotKit 递归 runAgent、Vercel 重发对话、AG-UI 新 run）。
6. **会话级 409 串行化 + Redis 锁 + watchdog**（`AI/session/SessionGate.java`）：三家协议层均不管并发写（Q11 实测的丢消息静默损坏在他们形态下靠"客户端持史"掩盖）。
7. **韧性三条件重试 + 完成帧校验 + 错误码后缀体系**（`_AFTER_PARTIAL/_AFTER_TOOL_SIDE_EFFECT`）：三家无应用层断流重试语义；AG-UI/Vercel 均无"缺终帧=断流"的硬规范。
8. **渐进披露三重防线**（补齐防线③后）：CopilotKit 只有 skills 元工具 + 客户端过滤，无场景级 scope 体系；AG-UI 协议层无披露。
9. **异步作业 + 轮询工具 = 天然引用回指**（start_export→check_job_status）：大结果不进上下文，是三家用 document parts 做的事的更彻底形态。
10. **错误码语义粒度**（七类违规 + 后缀标注可重试性）优于三家通用 error message。

## 14. 不适用清单（三家机制 × 我方约束）

| 三家机制 | 我方约束 | 不适用原因 |
|---|---|---|
