## 1. 结论速览

| 缺陷 | 修法 | 证据 |
| --- | --- | --- |
| 递归合并「缩不小」时 `partials.get(0)` 只取第一段，其余段静默丢弃 | 停下时**保留全部段**按原顺序拼接；且不再为"单段即超预算"的分组重发合并请求 | 单测 5 条（两超大段/多段/不能继续合并/部分合并/生产装配） |
| 多段拼接后仍可能超 `chunk-tokens` | 不截断、不丢段，改为**如实记账**（`summarySegments` / `summaryOverBudgetTokens`），台账与产物一致 | 单测 1 条（内容完整性 + 台账） |
| 任一分块摘要为空时，该段旧轮无任何产物覆盖却仍落摘要 | 空白分块/合并产物 ⇒ 整次摘要 `summary_failed`，历史逐字不变 | 单测 1 条（反向路径） |

真机（真实模型 + 真实窗口）本轮**未执行**：环境未提供可用的模型端点与会话，见 §5。

## 2. 根因

`RollingSummarizer.plan` 的递归合并（修复前）：

```java
while (partials.size() > 1) {
    List<List<String>> mergeGroups = group(partials, bodyBudget);
    List<String> merged = new ArrayList<>(mergeGroups.size());
    for (List<String> group : mergeGroups) {
        merged.add(summarizer.summarize(..., mergeUserPrompt(group), runtime));
        requests++;
    }
    boolean shrank = merged.size() < partials.size();
    partials = merged;
    if (!shrank) {
        break;          // 每段摘要自身就超过 chunk 预算：停在这里（不截断）
    }
}
summary = partials.isEmpty() ? "" : partials.get(0);   // ← 丢段
```

两个缺陷叠在一起：

1. **停下的时机太晚**：`group()` 对"单条即超预算"的输入会把它单独成组，于是 `mergeGroups.size()`
   与 `partials.size()` 相同 —— 这一轮合并**不可能**变小，请求体也必然超过 `chunk - 96` 的正文预算，
   却仍然发出了 N 次合并请求（纯浪费，且每次都可能重写/丢失已有要点）。
2. **停下之后只取第一段**：`partials.get(0)` 把其余段整段扔掉。它们没有任何别的产物覆盖，
   落库摘要"看着成功"（`changed=true`、`reason=l2_turn_window_summary`），实际丢掉了旧轮的历史。

触发条件在生产里并不罕见：分块摘要本身可能接近或超过 `chunk-tokens`（分词器与中英混排差异、
模型不遵守"Aim for at most N tokens"都会导致），一旦两段都超预算，第二段之后全部丢失。

## 3. 修法

### 3.1 合并只在"确实能变小"时发生

```java
while (partials.size() > 1) {
    List<List<String>> mergeGroups = group(partials, bodyBudget);
    if (mergeGroups.size() >= partials.size()) {
        break;      // 每段自身就超预算：再合并不会更小，请求体也必然越窗
    }
    ...
    for (List<String> mergeGroup : mergeGroups) {
        if (mergeGroup.size() == 1) {
            merged.add(mergeGroup.get(0));   // 单段组原样带过，不重发请求
            continue;
        }
        ...
    }
    partials = merged;
}
```

- 每轮都严格减少段数（`merged.size() == mergeGroups.size() < partials.size()`），必然终止。
- 单段组不重发"合并"请求：既缩不小，还会让模型把同一段摘要重写一遍（细节损耗）。
- 每个请求的正文仍不超过 `chunk - PROMPT_RESERVE_TOKENS`：**不会再为了合并而越窗**。

### 3.2 保留全部段（不静默丢历史）

```java
keptSegments = partials.size();
summary = partials.isEmpty() ? "" : joinPartials(partials);
```

`joinPartials` 把剩余段按原顺序以空行拼接；`partials.size() == 1` 时逐字返回原产物。
摘要消息仍是**一条**带 `[上下文压缩摘要]` 前缀的 `UserMessage`，正文仍闭合在一个
`<conversation_summary>` 定界内（多段正文里的同名标签照旧被中和为全角形态）。

### 3.3 预算如实记账，不装作在预算内

拼接后正文可能超过 `chunk-tokens`。这里刻意**不截断**（截断就是另一种静默丢信息），改为在摘要消息
metadata 里如实记账，供日志/前端/排查解释：

| metadata 键 | 含义 |
| --- | --- |
| `summarySegments` | 落库摘要由多少段保留拼接而成（1 = 一次摘要完成；>1 = 已无法继续合并） |
| `summaryOverBudgetTokens` | 摘要正文估算**超出** `chunk-tokens` 的量（0 = 在目标预算内），不截断正文 |

台账一致性：`Plan.summaryChars()` = 落库摘要正文的字符数（多段时为拼接后全长），
`Plan.summarizedTurns()` = 实际被摘要替代的前缀轮数，`META_LOST` = `Plan.lostTokens()`，
三者都取自同一次真实产物，不虚报覆盖范围。`lostTokens` 仍以 0 为下限：摘要比原前缀还大时
不谎报负数（该情形已由 `summaryOverBudgetTokens` 单独记录，编排层的 `savedTokens` 另算）。

### 3.4 空白分块/合并产物 = 失败（反向路径）

任一分块或合并产物为 null/空白 ⇒ `changed=false`、`reason=summary_failed`、历史逐字保持不变。
理由：那一小段旧轮没有任何产物覆盖，拼进摘要看不到、跳过又等于静默丢段；而"判失败 + 熔断计数 +
历史原样"是可解释且可回滚的。生产装配里 `ContextSummaryClient.requireClosedSummary` 已经拒绝空正文，
本改动把注入式 `Summarizer`（单测/其它装配）的同一个洞也堵上。

## 6. 取舍与残余风险

1. **多段拼接后正文可能超过目标预算**（`summaryOverBudgetTokens > 0`）。这是有意的：可选的替代是
   丢掉超出的段（本缺陷）或截断正文（静默丢信息），两者都比"如实超长 + 记账"更差。
   代价是这一次 L2 省下的 token 变少，甚至可能为 0（`lostTokens` 下限 0）；下一次压缩/更小的
   `chunk-tokens` 仍会继续尝试。
2. **多段摘要里的重复段落**：每段都带六项保留清单，拼接后会出现重复小节标题。信息不丢，
   但模型阅读时会有冗余；如果后续观察到模型被重复小节干扰，可再加"段内去重/结构化合并"的提示词，
   但那属于摘要质量优化，不应以丢段换整洁。
3. **段数口径**：`summarySegments` 记的是"最终保留的段数"（合并过的多段会先并成一段），
   不等于最初分块数；最初分块数仍看 `Plan.requests()` 与日志里的请求数。
4. **单段超大**（只有一段分块摘要且超预算）不是本缺陷：那一段就是全部旧轮的覆盖，落库时
   `summaryOverBudgetTokens > 0`，同样不截断。
5. `PROMPT_RESERVE_TOKENS = 96` 仍按常数预留；`summaryOverBudgetTokens` 以 `chunk-tokens` 为目标口径
   （提示词里的"Aim for at most N tokens"），不是请求体预算（`chunk - 96`），两者差 96，
   排查时不要混用。
