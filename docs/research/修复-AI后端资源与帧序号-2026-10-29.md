## 1. 缺陷形态（四条，互相独立）

### 1.1 取号修复是"读末号 + 无条件 SET + INCR"，并发下会复用已发 seq

`RedisFrameStore#nextSeq` 的号回退修复（M-1）原本是三步：

1. `INCR ai:seq:<runId>` → `issued`；
2. 若 `issued == 1`（键原本不存在：过期 / 被 `deleteRun` / 降级后恢复），读归档末号 `anchor`；
3. `SET ai:seq = anchor`，再 `INCR` 一次。

第 2、3 步之间是**真实可交错窗口**，而第 3 步的 `SET` 是**无条件写**。并发下只有"拿到 1 号"的线程
会去修复，同一瞬间拿到 2..N 的线程**已经把这些号交给出帧方并返回**；随后那次 `SET` 把计数器压回
`anchor`，`INCR` 再发一次同一个号。若归档里正好有 2..N，那一轮就**复用了已发（已落档）的号**：
订阅者收到两帧同 `seq`，前端 `lastSeq` 去重与归档侧 `mergeBySeq` 各丢一帧 —— 正是 M-1 要消灭的形态。

> 同一轮里"先改成 `INCRBY` 增量抬号"只解决了"把计数器压回去"，没有解决"窗口里已经交出去的低号"。
> 本批实测：把 `INCR + 抬号` 拆成两条命令时，`8 线程 × 4 次` 在键丢失后仍拿到 `2..5`（已落档号），
> 见 §4 的 RED 记录。

### 1.2 per-run 进程内簿记只增不减

`RedisFrameStore` 为每轮记四份进程内状态：降级号、本轮观察到的最大帧载荷、三个"每轮一次"的告警位。
它们按 `runId` 无界增长，只有进程重启才释放 —— 长跑实例上**每轮一条、永不回收**
（`RunStoreFrameStore` 的本地号锚同理）。终态出口（`RunRegistry#close`）不认识它们。

### 1.3 SSE 写出池"弹性"到无界

`SseWriteBudget` 的共享写出池是 `maximumPoolSize = Integer.MAX_VALUE` + `SynchronousQueue`（`AbortPolicy` 形同虚设）。
每条卡住的写要占一个线程，直到：客户端断开 / 容器 120s 写超时（由 `server.tomcat.connection-timeout` 派生）
/ 单帧 15s 预算三者先到。而"并发订阅者数"没有硬界（多实例 + 多连接 + 客户端不读也不断开）——
线程峰值因此可被外部拉高（每线程默认栈 1MB）。原类注把上界推导成"≈ 并发订阅者数"，
在被外部拉高的场景里不成立。

### 1.4 `emitLock` 内做唤醒侧的 Redis I/O

`SseChatEmitter` 的临界区（`emitLock`）里做了两类与正确性无关、时长不可控的 Redis I/O：

- 唤醒订阅的生命周期 `subscribe/unsubscribe`：背后是 `(P)SUBSCRIBE` / `(P)UNSUBSCRIBE`（容器 + 连接建立）；
- 唤醒发布 `PUBLISH`（一次网络往返）。

"最后一个订阅者离开"恰恰发生在锁内（`closeSubscription` 的调用点几乎都在临界区里），
于是一次退订慢下来，就把**同一轮的所有出帧**（含心跳、含其它订阅者的帧）一起顶在锁后面。
`delta` 帧更糟：`emitDeltaText` 在自己的外层临界区里连发多片，每片都会在锁内 PUBLISH 一次。

## 2. 修复口径

### 2.1 取号收敛为一次原子脚本（`RedisFrameStore`）

`nextSeq` 改成**单条 `EVAL`**（`AI_SEQ_NEXT` v1，`KEYS = [ai:seq, ai:xevents, ai:events]`，
三键同属 `{run:<runId>}` 同槽 ⇒ Cluster 下多键脚本合法）：

```
INCR ai:seq
若 (cur == 1) 或 (cur <= 本进程降级号)：
    anchor = max(降级号, XREVRANGE 末尾 16 条里最大的 seq, 兼容期 LIST 末帧 seq)
    若 anchor >= cur: cur = INCRBY(anchor + 1 - cur)
EXPIRE ai:seq session-ttl
返回 {cur, degraded}
```

要点：

- **Redis 串行执行脚本** ⇒ 并发（含跨实例）调用被串行化：后到者看到的必然是已抬高的计数器，
  不会再把已发号发第二遍。`INCR` 先于锚点读取，因此抬号永远是"加法"，**只能单调增**。
- **常规路径更便宜**：脚本只在"键刚重建/号落后于降级号"时读归档；平常就是 `INCR + EXPIRE`，
  并且把原来的两次往返（`INCR`、`EXPIRE`）合成一次。
- **降级语义保留**：末号读不出（`WRONGTYPE` / 读失败）时脚本用 `pcall` 包住读数，不抬号、
  返回 `degraded=1`，由 Java 侧每轮 WARN 一次（与 A4"末号未知不得按 0 锚定"同口径）；
  脚本整体不可用（Redis 抖动 / 脚本被禁用）时退回进程内单调计数（既有口径）。
- **降级号锚点补了 `ai:seq`**：首次降级时锚点取 `max(归档末号, ai:seq 当前值)`。
  只按归档末号锚定会把降级期的第一个号发成"已发出但还没落档"的那个号（出帧与落档本就不是原子的）。
- **不引入"SET 绝对值"**：抬号只用加法，因此任何并发下都不会把计数器压回去。

> 取号路径上的 `ai:seq` 仍是唯一号源；`lastSeq` / `readFrom` / 窗口治理都不变。

### 2.2 per-run 簿记收成一条 + 两条界（`RedisFrameStore` / `FrameStore#forget`）

- 四张 Map/Set 合并成一条 `RunState`（降级号、观察到的最大载荷、三个告警位、最后触达时刻）。
- **终态释放**：`FrameStore#forget(runId)`（默认 no-op；`RedisFrameStore` / `RunStoreFrameStore` 覆盖）
  由终态出口 `RunRegistry#close` 调用 —— "谁结束谁释放"。
- **到期清理 + 硬上限**：`state(runId)` 触达时按 `SWEEP_INTERVAL_MS = 60s` 节流做一次清理：
  ①清掉"最后触达早于 session TTL"的簿记（归档键已过期 ⇒ 簿记没有读者）；
  ②仍超过 `MAX_TRACKED_RUNS = 4096` 时按最后触达时刻从旧到新淘汰。
  清理只影响进程内兜底，取号锚点始终在 Redis（归档 + `ai:seq`），被清掉的轮下一帧按归档末号重锚。
  清理用 `lastSweepMs` 的 CAS 保证只一拍执行，绝不把写路径串行化。
- 测试可注入时钟（包内构造器），因此"24h 之后"是确定性的，不靠 sleep。

### 2.3 写出池设硬上限；饱和按"慢订阅者摘除"处置（`SseWriteBudget`）

- 池形：`core = 0`（空闲 60s 回收）+ `max = DEFAULT_MAX_WRITER_THREADS = 256` +
  `SynchronousQueue`（不排队：排队的写等于"卡住的写继续占调用线程"）+ `AbortPolicy`。
- 取值 256 = 投递池缺省（8）的 32 倍：正常负载下"同时在写的订阅者"远小于它（写是毫秒级，
  15s 预算只用来筛停读客户端）。
- 提交被拒 ⇒ 新结果 `Outcome.SATURATED`（不再是语义误导的 `FAILED`），`WRITE_SATURATIONS` 计数 + WARN；
  调用方（`SseChatEmitter#writeFrame`）据此**摘除触发本次写出的订阅者**（前端 `onerror/onclose` 带
  `lastSeq` 重挂差量补发）。任务通道（`TaskSseService`）同口径：饱和 ⇒ 该连接视为不可用、摘除
  （EventSource 重连 + 快照轮询自愈），日志与超时分开记。
- 可观测面（`SseChatEmitter.deliveryPoolMetrics()` 纯增量键）：`writePoolMaxThreads`、`writeSaturations`。

### 2.4 `emitLock` 内不做唤醒侧 I/O（`SseChatEmitter`）

- 锁内只**置位/累计**：`wakeSyncPending`（要不要同步订阅）与 `pendingWakeSeq`（要发布的最大上界）。
- 最外层锁出口（13 处 `try/finally` → `flushWakeSyncIfUnlocked()`）在**锁外**执行：
  ①`flushWakePublish()`（`PUBLISH`）；②`applyWakeSync()`（`register`/`unregister`）。
- 目标状态按"**当前**订阅表 / 当前最大上界"收敛（`applyWakeSync` 幂等），因此**事件顺序不变**：
  登记仍早于回放读、退订仍只在最后一个订阅者离开之后、发布仍在落档之后。
- I-1 得以保持并更严格：`replayAndAttachWithStatus` 在**取锁之前**调 `ensureWakeSubscribed()`，
  顺序变成「登记（锁外）→ 挂订阅 + 回放读（锁内）」—— 回读与登记之间落档的帧仍能被唤醒补到，
  而"建立订阅"的时长不再落在 `emitLock` 上。
- **仍留在锁内的 I/O 只有两类，且都是正确性必需**（如实登记，本批不改）：
  ①取号/落档（与入队同锁才有"队列顺序 = seq 顺序"）；
  ②`onWake` 的差量读（读取下界必须与入队同拍计算，否则"读到 5..7、其间本地已投 7"会让 5/6 排在 7 之后 = 乱序）。
  `touchActivity/touchBusinessActivity` 同理（注释口径：僵尸判定的输入不能随投递延迟漂移）。

#### 契约变化（唯一一处，已同步用例）

出帧流水由「取号 → 落档 → **发布唤醒** → 本地扇出」变为「取号 → 落档 → 本地扇出 → **发布唤醒**」。
原因：本地扇出必须与取号/落档同锁（FIFO 与 seq 同序），而 PUBLISH 必须在锁外 —— 二者相加只能是这个顺序。
不变的部分是真正有语义的那条：**落档永远早于发布**（否则被唤醒者读不到该帧），唤醒仍只带上界 seq。
用例 `SseChatEmitterFrameStoreTest#emitAppendsThenFansOutThenPublishes` 按新顺序断言，并写明原因。

## 6. 风险与后续（concerns）

1. **Lua 脚本的实机面未验证**：脚本正确性目前只有"替身镜像 + 逻辑审阅"两重保障。若目标 Redis
   禁止 `EVAL`（极少数托管形态），取号会退回进程内降级号并 WARN（跨实例不重号承诺失效）——
   上线前建议在 5.0.14 真集群跑一次双实例取号对账（`b23l1-dual-instance.ps1`）。
2. **写出池硬上限 256 是常量，不可配**：饱和时牺牲"新写"（摘除挤不进来的订阅者）。
   若某部署的并发出帧订阅者确实可能接近 256，需要把上限做成 `app.ai.sse.write-pool-size`（本批未做，
   因为新增配置键要连带改配置示例与启动期守卫，属独立批次）。
3. **`emitLock` 内仍有取号/落档与 `onWake` 的差量读**：本批只移出"订阅/退订 + PUBLISH"。
   继续外移这两类会改变"队列顺序 = seq 顺序"或引入乱序，需要协议层配合（例如按订阅者的乱序缓冲），
   不在本批范围。
4. **饱和摘除的策略是"断连让前端重挂"**：与既有 S2-1"溢出摘除 = 主动断连，不静默丢帧"同口径；
   若前端重挂风暴与慢连接同时出现，摘除会放大重连压力 —— 既有 `?lastSeq` 差量补发是它的对冲，
   但未做真机压测。
5. **`FrameStore#forget` 是新增接口方法（default no-op）**：实现方漏覆盖就回到"只增不减"，
