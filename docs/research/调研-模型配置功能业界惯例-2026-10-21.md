# 调研：AI 应用内「模型配置功能」的业界主流形态

- 日期：2026-10-21
- 范围：LobeChat/LobeHub、LibreChat、Cherry Studio、Open WebUI、NextChat、Dify、AnythingLLM、Cline、Continue，另加 LiteLLM 网关作对照
- 方法：优先官方文档原文（引用清单中的 URL 为实际抓取页），二手来源在正文标注；未逐项核实者集中在第 5 节
- 目标项目：本仓（Spring Boot + Vue3 + Element Plus 配置管理平台，`configmgr` 包，Spring AI 1.x，OpenAI 兼容协议，`AI_API_KEY/AI_BASE_URL/AI_MODEL`）

---

## 0. 结论速览

1. **「多提供商 + 自定义 OpenAI 兼容端点」是绝对主流**，单提供商单模型（本项目现状）在 2026 年已属少数派；Open WebUI 甚至明确以「协议」而非「厂商」为设计中心。
2. **服务端配置 / 客户端自带 key 是两条分明的产品线**：Web 协作型（Open WebUI、LibreChat、Dify、AnythingLLM）key 一律服务端保存、UI 不回显；桌面/IDE 型（Cherry、NextChat、Cline、Continue）key 在本地。浏览器 localStorage 存 key 只作为 opt-in 实验特性存在，且出过 CVE。
3. **模型列表 = 拉 `/models` 为主 + allowlist 收口 + 手填兜底**，没有一家把「纯手填」当推荐路径，也没有一家把「纯拉取」当唯一路径。
4. **参数分层是三层**：全局默认 → 会话/助手级 → 单轮；普通用户默认只见 temperature / max_tokens / top_p，streaming 与 penalties 折叠或不下放。
5. **系统提示词与生成参数同面板、但不同归属**：UI 上常并列（Open WebUI 的 Chat Controls），语义上属「助手/会话配置」而非「provider 配置」。
6. **健康检查是「保存时验证一次」，不是持续探测**；且业界明确区分「验证失败 ≠ 不可用」（`/models` 缺失不代表 chat 不可用）。
7. 对本项目：**DB 存 provider/model（key 加密）+ env 作首次启动种子 + 独立「AI 设置」页 + 对话面板只留模型选择器与折叠参数**，是风险最低且与现有 `AiModelConfig`/`AiAvailability` 结构最贴合的路线。

| **（对照）LiteLLM 网关** | 独立代理 | 100+ provider 聚合 | 本身就是「OpenAI 兼容端点」 | 网关维护 model_list | 服务端 DB；虚拟 key 签发 | `drop_params`、模型别名、fallback | 虚拟 key 绑模型白名单/预算/限流；spend 按 key/user/team 记账，可作审计层 |

**一句话读表**：越偏「团队/Web 协作」，越倾向「管理员配 provider + 用户只选模型」；越偏「个人/桌面/IDE」，越倾向「用户自己填 key」。两类产品的**参数面几乎一致**（temperature/max_tokens/top_p 在前，其余折叠）。

## 2. 五问结论

### 2.1 主流形态：多提供商是默认，单提供商是特例

- **provider 预设 + 自定义兼容端点**是标准组合：预设负责「开箱可用」（Cherry 30+、LobeChat 30+、Cline/Continue 一大堆），自定义端点负责「长尾/内网/中转站」（LibreChat `endpoints.custom`、Open WebUI 连接、Cline "OpenAI Compatible"、Cherry "Add Provider"、Continue `apiBase`）。
- **配置位置分两派**：
  - **文件/环境变量派**：LibreChat（YAML + `.env`）、Continue（`config.yaml`）、NextChat（env + 前端设置）、AnythingLLM（env 兜底）。优点是密钥天然不进 DB、可 GitOps；缺点是改配置要重启、非技术管理员不可用。
  - **DB/UI 派**：Open WebUI、Dify、LobeChat 服务端模式、Cherry 桌面端。优点是自助、可审计；缺点是要处理密钥加密与迁移。
- **模型列表三种实现都有，但组合起来才是主流**：
  1. 拉取：`GET {base}/models`（Open WebUI Verify/自动发现、Cherry「获取模型列表」、LibreChat `models.fetch: true`）；
  2. allowlist：拉回来也只是一堆 ID，需勾选「启用哪些」（Open WebUI 的 Model IDs、LibreChat 的 `models.default`、LobeChat `-all,+xxx`）；
  3. 手填兜底：`/models` 不实现的端点必须能手填（Open WebUI 给了明确的厂商清单，DeepSeek 属「支持自动发现」一类）。
- **key 展示口径高度一致**：**永不回显完整值**。UI 上要么只显示「已配置」，要么显示末 4 位；编辑时输入框留空 = 保持原值。LibreChat/Continue 这类文件派则干脆不在 UI 出现 key。
- **不该抄的地方**：NextChat 的「单端点 + `CUSTOM_MODELS` 字符串」是历史包袱（改模型要记语法、无法表达 provider 级差异）；LibreChat 的「自定义端点只能改 YAML」对非技术管理员不友好。

### 2.2 参数配置面：三层 + 折叠

| 参数 | 是否面向普通用户 | 业界做法 |
|---|---|---|
| `temperature` | 是 | 主面板滑杆，带默认值与「重置」 |
| `max_tokens` / max output | 是（但常标注「留空=模型默认」） | 主面板数字框；上限受模型能力约束 |
| `top_p` | 是（次要） | 与 temperature 并列或同组；有的产品提示「二者取其一」 |
| penalties / seed / stop | 否 | 折叠进「高级」；LibreChat 允许端点级 `dropParams` 直接不发 |
| `streaming` | 否 | 端点级/全局开关（AnythingLLM `GENERIC_OPENAI_STREAMING_DISABLED`），不交给普通用户 |
| 系统提示词 | 视产品 | Open WebUI 当作 Chat Controls 的一项（与参数同受 RBAC）；Dify 放在应用/节点 prompt；Continue 用 `rules` 注入 system message |

分层（业界收敛为三层，最多四层）：

1. **全局默认**：LobeChat `DEFAULT_AGENT_CONFIG`、Dify「Default Models」、Open WebUI 模型级默认参数、AnythingLLM 工作区设置；
2. **会话/助手级**：Open WebUI 每个对话的 chat controls、LobeChat 每个 assistant 的 model+params、Dify 每个应用的 LLM 节点；
3. **单轮覆盖**：Open WebUI 每次发送前可改参数；LibreChat 会话内参数面板；
4. （可选）**管理员设边界**：Open WebUI 用 RBAC 决定「能不能改」，Dify 用工作区角色。

**系统提示词的归属**：主流把它当「助手/会话配置」，与模型配置**共面板但不共存储**。理由很实际：提示词影响输出语义，provider/key 影响「能不能连上」，二者生命周期与权限不同。

### 2.3 多模型运行时：路由、能力、健康检查

- **路由粒度 = 会话级选模型**（几乎所有产品）。管理员决定「可见集合」，用户在集合内自由切：
  - Open WebUI：模型访问控制 + 用户组；模型选择器里只出现被授权的；
  - Dify：工作区 provider + Default Models，应用内再选；
  - LibreChat：`modelSpecs` 把「端点+模型+instructions+temperature」打包成一个个「规格」，用户在规格间切（这其实是「预设」思路，值得借鉴）；
  - AnythingLLM：**工作区级**绑定 chat model（不是每个会话），更粗。
- **能力差异的处理是「标记 + 参数裁剪 + 降级」，不是「假设都一样」**：
  - 标记：LobeChat 在模型清单里写 `<fc:vision:reasoning:search:file>`；Continue 用 `capabilities: [tool_use, image_input]`；Cline 在模型配置里勾 "Computer Use / Image Support"；
  - 裁剪：LibreChat `dropParams` 按端点删掉不支持的字段（否则 400）；
  - 降级：AnythingLLM 用 `PROVIDER_DISABLE_NATIVE_TOOL_CALLING` 回退到 prompt-based 工具调用；
  - 对「工具调用」这一项，行业共识是**显式能力位**，因为它是「能不能进 Agent 模式」的硬门槛（Continue 文档直言 `tool_use` 是 Agent 模式必需）。
- **健康检查**：
  - 保存时验证一次：Open WebUI `Verify Connection`（调 `/models`）、Cherry「检查」、Cline `Verify`、Dify Setup 时校验 key；
  - **不持续轮询**；连接上提供 enable/disable 开关代替删除；
  - 明确文案「验证失败 ≠ 不可用」（`/models` 缺失/鉴权方式非标时仍可 chat），并给出「手填模型 ID」的下一步；
  - 规模化后把健康检查/fallback/限流外置到网关（LiteLLM 的 `/health`、fallback、虚拟 key）。

### 2.4 安全与权限

- **「key 不落前端 localStorage」是 Web 协作型产品的硬共识**。反例只有两类：
  1. 桌面/IDE 单用户产品（Cherry、NextChat、Cline、Continue）——本地存储是产品前提；
  2. Open WebUI 的 `ENABLE_DIRECT_CONNECTIONS`——**默认关闭、标注 experimental、文档明说 key 存 localStorage**，并且历史上因该路径的 SSE 处理不当出过 **CVE-2025-64496**（外部模型服务可注入 JS，进而读 localStorage 的 JWT）。这条应作为「我们不做浏览器存 key」的反面教材。
- **权限分层**（Open WebUI 是最完整的参考）：
  - 管理员：连接 CRUD、模型可见性、默认参数、是否允许用户改参数/系统提示词；
  - 普通用户：选模型 + 被授权范围内的参数；`Allow Chat Params` / `Allow Chat System Prompt` 是独立开关；
  - 权限是「加法」（任一组授权即生效），因此推荐「默认最小 + 按组授予」。
- **审计**：
  - 应用层普遍只记「谁在何时改了配置」，**不记 key 值**；能记到「key 末 4 位 + 操作类型」就算合格；
  - 真正的调用审计/成本审计放在网关层：LiteLLM 虚拟 key 可按 key/user/team 记 spend 与模型访问，企业版才有 audit logs；
  - 结论：应用侧做「配置变更审计」，调用侧审计不要自己做（接入网关或只记 usage）。

## 3. 对本项目的建议

### 3.0 现状锚点（已核对代码）

- `backend/src/main/resources/application.yml:86-100`：`spring.ai.openai.api-key: ${AI_API_KEY:${DEEPSEEK_API_KEY:}}`、`base-url: ${AI_BASE_URL:https://api.deepseek.com}`、`chat.options.model: ${AI_MODEL:deepseek-flash}`、`temperature: 0.2`、`max-tokens: 4096`、`completions-path: /chat/completions`；
- `ai/config/AiModelConfig.java`：手工装配 `OpenAiChatModel`（含 `ReasoningAwareOpenAiChatModel` 补丁、`SpToolCallingManager`）+ 单个 `ChatClient`（挂 `MessageChatMemoryAdvisor`），**启动期一次成型**；
- `ai/config/AiKeyPresentCondition.java`：无 key 则整条模型链路不装配；
- `ai/config/AiAvailability.java`：无 key 时 AI 端点返回 503 `AI_UNAVAILABLE`；
- 前端 `frontend/src/views/`：已有 Definitions / DataBrowser / ExportWizard / ImportWizard / TaskCenter / AiFeedback，**尚无设置页**。

改造点因此非常清晰：把「一个 ChatModel + 一个 ChatClient」改成「provider 注册表 + 按请求选模型」，把「key 存不存在」的布尔判断升级为「provider 可用性」。

### 3.1 推荐路线（R1）：DB 为真源 + env 作种子 + 独立 AI 设置页

**a) 存储：DB 主存，Redis 只做缓存，env 只做种子**

| 数据 | 存放 | 理由 |
|---|---|---|
| provider（name/base_url/completions_path/协议） | DB 表 `ai_provider` | 需 UI 增删改、需审计 |
| key | DB `key_cipher`（AES-GCM，KEK 来自环境变量 `AI_SECRET_KEK`）+ `key_last4` + `key_fingerprint`(SHA-256) | 不回显、可判断「是否同一把 key」、KEK 不进库 |
| 模型清单 | DB 表 `ai_model`（provider_id, model_id, display_name, capabilities, max_context, max_output, enabled, sort） | 需要 allowlist 与能力位 |
| 参数默认值/会话覆盖 | DB `ai_setting(scope, scope_id, key, value_json)`；会话级可落 Redis（已有 Redis 与 `RedisAvailability` 模式） | 复用现有基础设施 |
| 运行时读取 | Redis 缓存 provider+model 快照，变更即失效 | 避免每轮请求查库 |

**优先级（推荐）**：`内置默认 < 环境变量 < DB 全局默认 < 会话覆盖 < 单轮请求`。理由：

- DB 为空时行为与今天**完全一致**（零迁移风险，CI/无 key 环境照旧 503）；
- 环境变量作为「首次启动种子/兜底」，运维仍可用 env 快速起一个可用实例；
- 若将来要「托管方强制锁定」，再加显式开关 `app.ai.config.env-wins=true`（默认 false），而不是靠隐式规则。

**b) 运行时装配：provider 注册表 + 按请求 options**

- 保留现有默认 `ChatModel`/`ChatClient` bean 不动（改为「默认 provider 的实例」），新增 `ProviderRegistry`：
  - `key = providerId + ":" + keyFingerprint + ":" + baseUrl + ":" + completionsPath`，缓存 `OpenAiApi` + `OpenAiChatModel` + `ChatClient`（`ChatClient` 共享同一个 `MessageChatMemoryAdvisor`，记忆仍按 `CONVERSATION_ID` 隔离）；
  - key/base-url 变更 → 指纹变化 → 自动重建该 provider 实例并关闭旧实例（无需重启）；
  - 保留 `ReasoningAwareOpenAiChatModel` 与 `SpToolCallingManager` 包装（这是本项目 HITL 的核心，不能丢）。
- **模型切换不必重建实例**：`chatClient.prompt().options(OpenAiChatOptions.builder().model(id).temperature(t).maxTokens(n).topP(p).build())` 即可逐请求覆盖；只有 **provider 级**（base-url/key）切换才需要换实例。
- 可用性：把 `AiKeyPresentCondition` 从「env 有 key」扩展为「存在任一 enabled 且 key 非空的 provider」；`AiAvailability` 输出 `{available, defaultProviderId, providers:[{id,status,lastCheckAt,latencyMs,error}]}`，全不可用时仍返回 503（保持现有契约）。

**c) 管理界面：独立设置页 + 面板内轻量入口**

- 新增 `设置 → AI 模型`（管理员可见），三段式：
  1. **提供商卡片列表**：名称、协议（OpenAI 兼容 / 预留）、Base URL、completions path、key（`sk-****abcd` + 「更新密钥」按钮，更新时输入框为空 = 不改）、启用开关、`测试连接`、`来源` 标签（ENV/DB/默认）；
  2. **模型表**：`拉取模型` 按钮 + 可搜索多选（勾选=启用）+ 手填一行 + 每行能力勾选（工具调用/视觉/推理/流式）+ 上下文与最大输出；
  3. **默认参数**：temperature / top_p / max_tokens + 「允许普通用户调整」开关 + 取值范围（借鉴 Open WebUI 的 RBAC 思路）。
- **对话面板内**只放：模型选择器（仅 enabled 且被授权的模型）+「参数」popover（temperature/top_p/max_tokens，其余折叠）。理由：provider/key 是低频高危操作，混进对话面板必然误触；模型/参数是高频操作，必须就地可改。
- 工具调用能力位必须**硬约束**：本项目是重工具 + HITL 的 Agent，`tool_calling=false` 的模型若被选中，应默认禁止进入工具模式并明确提示「该模型不支持工具调用，已退化为纯问答」，而不是发出去等 400。

**d) 模型列表裁决：拉取 + allowlist + 手填兜底（默认「自动拉取但需勾选启用」）**

- 保存 provider 时**不阻塞**于拉取；`测试连接` 与 `拉取模型` 分离；
- 拉取：`GET {base}{modelsPath}`，超时 5s，失败给三条明确文案（未实现 `/models` / 鉴权失败 / 网络不可达），并直接把用户引到「手填模型 ID」；
- 拉取结果进 Redis 缓存（TTL 10min，可手动刷新），勾选结果落 `ai_model`；
- 当前默认 provider 是 DeepSeek，其 `/models` 属「可自动发现」一档，所以主路径能跑通；自建网关/中转站大概率不支持，手填兜底是必需项而非 nice-to-have。
- URL 校验：仅 http/https；默认禁止私网与云元数据地址，需要内网模型时用 `app.ai.allow-private-endpoints=true`（对应 LobeChat 的 `SSRF_ALLOW_PRIVATE_IP_ADDRESS` 取舍）。

**e) 权限与审计**

- provider/key 的增删改：仅管理员；普通用户：选模型 +（被允许时）调参数；
- 审计表 `ai_config_audit(actor, action, target_type, target_id, diff_json, at)`，`diff_json` 对 key 只写 `{"key":"updated","last4":"ab12"}`，永不写密文或明文；
- 前端接口**永不返回** `key_cipher`；DTO 用 `keyConfigured: bool` + `keyLast4`。

### 3.2 备选路线

- **R2（最小改动，约 1 天）**：只做「多套 env + Spring profile」（`AI_PROVIDER=deepseek|qwen|...` 映射到不同 `spring.ai.openai.*`），前端只加只读的「当前模型」展示与模型切换下拉（切换 = 改会话级 model 名，不改 base-url）。适合先验证需求真伪，但满足不了「用户在界面上配 provider/key」的原始诉求。
- **R3（规模化演进，推荐作为 R1 之后的方向）**：接入 LiteLLM 之类网关，应用只保留一个 base-url/key，多 provider、模型别名、虚拟 key、预算、fallback、spend 审计全部外置。好处是 Spring AI 侧几乎零改动，且拿到了真正的调用审计；代价是多一个需要运维的组件，且「在管理界面配 provider」变成「在网关配」，需产品侧确认是否接受。
- **不推荐**：把 provider/key 塞进浏览器（localStorage/sessionStorage）。Open WebUI 的 Direct Connections + CVE-2025-64496 已经把代价演示过一遍；本项目有 HITL 破坏性工具，XSS 后果比纯聊天应用更重。

### 3.3 分阶段落地建议

1. **P1（表 + 读路径）**：`ai_provider`/`ai_model` 建表与迁移；`ProviderRegistry` 读 DB（空表回落 env）；`AiAvailability` 升级为 provider 级；行为与今天完全等价（建立回归基线）。
2. **P2（写路径 + 安全）**：key 加密/掩码/审计；`测试连接` + `拉取模型`；管理员设置页（Element Plus 表单 + 表格）。
3. **P3（对话面板）**：模型选择器 + 参数 popover + 会话级覆盖；能力位驱动的工具模式降级提示。
4. **P4（可选）**：网关化 / 多 key 负载均衡 / 用量与成本看板。

- **Cherry Studio 键的具体存储介质**（IndexedDB / Electron store / 系统钥匙串）未见官方一句话说明，表中按「桌面端本地」表述。
