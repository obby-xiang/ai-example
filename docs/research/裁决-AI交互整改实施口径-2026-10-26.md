## 2. 逐项裁决

### AR-01 历史保存范围、保留期、DLP 与失败现场

**裁决**

1. **不扩大历史 DB 范围**：`ai_chat_message` 及其子表维持现状——不新增列、不新增表、不把帧面已有而 DB 面没有的东西搬进 DB（含 `errorCard`/`code`、工具响应原文、`reasoningContent` 之外的思考展示字段）。
2. **两类保留期必须分开写，禁止混成一句**：
   - **Redis 运行态 / 记忆 = 24h 滑动 TTL**（维持原值：**不加**绝对上限、**不延长**、**不缩短**、**不引入**按轮独立保留期）；24h 到期的处理见 AR-10（只可见化）。
   - **既有完整历史 DB 无 TTL**：`ai_chat_message` 现状**就是无保留期**，本裁**维持现状、不新增保留期、也不补清理 runner**；"保留期"一词不得被用来暗示"DB 也 24h 到期"。这两条方向的共同约束只有一条：**不扩大**。
3. **不恢复 DLP**：`InputDlp` / `OutputGuard` / `SafetyRules` 三件套维持删除（10-24 裁定"过度设计"），不因"失败现场要展示原文"而复活任何一个；`ExcerptGuard`（反馈摘录守卫）去留另挂，不在本裁决范围。
4. **失败现场先走两条轻路径**：①**Redis 快照/帧日志**（run 级键族，24h 内可逐帧还原）；②**浏览器镜像**（`types/ai.ts` 镜像 schema 扩展携带 `errorCard`/`code`，兼容旧镜像）。DB 面**不新增失败写入**。
5. **synthetic 过滤可做**：展示通道复用既有 synthetic 判据——系统级压缩提示按"系统消息"呈现，不冒充用户原话、不显示内部配置键；该过滤是**展示层**行为，不改变模型记忆里的既有结构。

**理由**

- 扩 DB 范围=新建不可回收面（且 `ai_chat_message` 无 TTL，扩字段即扩永久留存），与 10-21 🏛️「AI 对话数据不落库」的距离只会更远，而收益（失败现场可查）已由 Redis 24h + 镜像覆盖。
- 改 TTL 会同时牵动多实例续跑、挂起卡可达性、`RunStore` 键族语义与既有"24h 严格共亡"口径，代价远大于收益。
- 恢复 DLP 与 10-24 用户裁定直接冲突，且 DLP 从未解决"失败现场要展示什么"这个问题。
- 合并稿 §3 A 段已认定"F1 失败现场的缺口在镜像/视图，不在 DB"；把缺口的 90% 用两条轻路径补上，代价最小。

**代价**

- **超过 24h 的失败现场不可恢复**（Redis 运行态 / 记忆侧 24h 到期后归零，如实登记为限制）；跨天排障只能依赖日志与 frame archive 之外的审计面；**DB 侧本来就没有失败写入，故不存在"DB 里能补查到失败现场"这条路**。
- **"历史面与帧面不同源"这条边界保留**：刷新后回看到的失败轮仍是"DB 里那半截 + 镜像里的错误卡"的组合，不等于逐帧一致。
- synthetic 过滤只作用于展示，**模型侧仍按既有 synthetic 结构携带**——"摘要不冒充用户"只对人类读者成立，不能据此说模型看到的也不同。

**影响任务**

- **Task 4 Step 3**（不依赖裁决的部分）：镜像升级照做，携带 `errorCard`/`code`，兼容旧镜像。
- **Task 4 Step 4**：**只剩**"synthetic 展示通道 + 读侧未完成标识"两件事；**明文禁止**新增 DB 写入、新增列、**给 DB 补保留期或清理 runner**，也**不得**顺手改 Redis 侧 TTL；"持久化失败半截"一句作废（不再实施）。
- **Task 3 Step 4**：空态保存文案必须**同时准确描述三类载体**，不得写成"不落库"：①**浏览器镜像**（本地镜像，供刷新恢复，配额失败要可见）；②**Redis 运行态 / 记忆**（24h 滑动 TTL）；③**DB 完整历史**（`ai_chat_message`，**无 TTL、维持现状**）。同时删掉"关闭页签即结束"这类与实现相反的表述。

### AR-02 确认卡知情面：三字段，且 supersede 只到这三项

**裁决**

Supersede 2026-10-20「撤预检区」裁决，**范围严格限定为三个字段**：

1. **影响面**（`impact`，后端已下发，前端现在明确不渲染）；
2. **条件摘要**（结构化条件的可读摘要，由后端在预检 payload 内补，不由前端反解文本）；
3. **权威发布模式**（取宿主 `publishMode` 枚举，**模型文本不得作为权威来源**）。

三项以**只读摘要行**呈现在确认卡内（可折叠、默认收起），**不恢复**旧预检区的五段式版式，**不恢复**"查看详情"抽屉，**不新增**第二张卡。

**理由**

- 三项的共同特征是"信息已经算好、只是没上屏"——这是呈现面缺口，不是能力面缺口，恢复成本极低。
- 其余旧预检区字段（报告原文、逐项检查明细等）在 10-20 被撤的理由（噪音、挤占决策位、重复披露）**仍然成立**，故不随本条复活。
- 发布模式必须由宿主权威给出：把模型文本当权威会造成"模型说 MERGE、实际 REPLACE"的致命误解。

**代价**

- 后端 payload 增两字段（additive，16 帧冻结不破），但**必须在预检阶段算好并缓存**，否则前端会二次请求。
- 前端需要一块新的只读渲染位与两条新 i18n 键（中英），并保持"最小决策集"原则：摘要可折叠、默认不展开。
- 卡面信息量上升，"批准"按钮的注意力竞争略有上升（用默认折叠对冲）。

**影响任务**

- **Task 6 Step 5**：**从"阻塞于 supersede 裁决"改为"已解锁，按 AR-02 实施"**；实现面 = 后端 `ToolPreflightService` 补条件摘要与发布模式两字段 + 前端渲染影响面与两项摘要；**不得**恢复旧预检区其余部分。
- **Task 6 Step 3/4**（6a）不变，仍可独立交付。

### AR-03 `create_task`：DANGER 确认门 + 宿主幂等 + 单轮 1

**裁决**

1. **形态 = DANGER 确认门**（进 `ToolPreflightService` 与既有确认卡链路），**不取**"软确认 / 事后回执"方案。
2. **宿主幂等**：幂等键 = 规范化 `name` + `parentId` + 稳定参数哈希（**不得以标题为唯一依据**）；命中已有键时**复用结果或返回明确冲突**，绝不二次创建。
3. **单轮上限 1**：同一轮内第二次 `create_task` 调用**直接拒绝创建**并给出可读原因（不是静默丢弃）。
4. 拒绝/取消语义沿用 DANGER 既有三态（批准 / 拒绝 / 取消），不新造按钮。

**理由**

- 既有 2B 裁决已要求"软确认或进门"，二者选一时，**DANGER 与 `start_*` 同族**：共用同一套确认、拒绝、取消、回执、超时与刷新恢复语义，前端零新形态、测试零新框架。
- 软确认（先创建后回执）的问题在于"创建"本身就是有后果动作（占任务号、进列表、可被后续引用），事后撤销不是等价的。
- 幂等 + 单轮上限是**防重复创建的硬闸**，不依赖模型服从——模型重试、并发调用、用户重复确认都收敛到同一结果。

**代价**

- **多一次人工点击**（创建任务频次低，可接受）。

### AR-05 失败后重跑粒度：只允许"仅模型步重跑"，不做半截自动替换

2. 重跑**只重跑模型步**：已结算的工具**零重执行**、**不追加用户消息**、不跨模型、不改本轮 fixed history。

**代价**

### AR-07 同批两张表单：单活动队列

**裁决**

### AR-09 "继续" / "重试本轮" / "regenerate" 三动作拆分 + 编辑后果提示

**裁决**

1. **继续**（append-drive）：在当前轮之后追加驱动，**不删历史、不追加用户气泡**。
2. **重试本轮**（retry-turn）：**仅零产出**（零正文、零思考、零副作用）时可用；语义是**替换本轮**，不追加用户消息。
3. **消息级 regenerate**：语义上替换该轮 assistant 输出、**保留用户消息**，与"继续"是不同动作、**不得复用同一按钮**；但**本批不实现普通已完成 / 有半截内容的 regenerate**（需要分支 / 失效替换协议）—— 入口整体隐藏、错误卡不得跳到假动作，**由 AR-17 收口**。本批实际只提供 AR-05 条件（已失败、零产出、无半截、归属可证明）的「重试本轮」。
4. **编辑用户消息前必须提示后果**："编辑将删除此后 N 条消息"，需用户确认后才执行；N 为实测条数（不是固定文案）。
5. 错误卡的"重试"**不得**再发送"继续"伪用户消息（F8 现状缺陷）。

**理由**

- 三者语义不同（追加 / 替换本轮 / 替换该轮回复），现状把它们混成一个"继续"，直接导致 F8 的伪用户消息与 A7 的 regenerate 缺项。
- 编辑删除后续消息是**不可逆**动作，按既有 HITL 口径必须有后果告知（与 10-23"不可撤销动作加确认"同源）。

**代价**

- 前端新增 2 个入口 + 1 个删除确认；按钮组密度上升，需要收敛排布。
- "替换本轮"与取消/终态 CAS 存在竞争面（替换前该轮可能已被取消）⇒ 必须复用 AR 的取消优先守卫，不得另写判定。
- 编辑删除的消息**不可恢复**（无回收站，接受；靠提示与确认兜底）。

**影响任务**

- **Task 4 Step 5**：按 AR-09 拆分动作；**普通 regenerate 不在本批实现**（AR-17），只落「继续」与 AR-05 条件的「重试本轮」；不得保留禁用 / unsupported 的假入口。
- **Task 3 Step 4**：错误卡两层文案（用户向 + 诊断）+ 编辑后果提示落点。

### AR-16 建作业的旧 runner 守卫：只探测非终态作业（2026-10-26 批次 1D 后追加）

**裁决**

1. `JobService.assertNoRunnerInFlight(taskId)` 的扫描面**收窄为同任务的非终态作业**（`PENDING` / `RUNNING`）：终态作业（`COMPLETED` / `FAILED` / `CANCELLED`）**不再逐条**调用 `JobHeartbeatRegistry.isRunnerAlive`（即不再逐条 `hasKey` 打 Redis）。
2. **两条硬约束不动**：①守卫仍在 **task 行锁 / 建作业事务内**执行（`createAndStart` 的 `taskService.lockForUpdate` 之后、作业落库之前）；②Redis **读失败仍 fail-closed 409 `JOB_ALREADY_RUNNING`**（"旧作业收尾状态无法确认（Redis 不可用）"），**绝不**把"查不到"当"没有 runner"。
3. **拒绝语义不变**：命中存活 runner ⇒ 409 `JOB_ALREADY_RUNNING`（"正在收尾，请稍后重试"），且被拒请求**不落 PENDING 行**。
4. **supersede 旧口径（历史文本保留）**："旧 runner 守卫**含终态未退**"这一表述（2026-10-24 规格回写批登在 `docs/任务看板.md` 与 `docs/决策看板.md` 的「runner-active 共享闸」行内）**只作为历史事实保留原文、不回改**；**自本条起不再作为实现口径**，后续引用（施工卡、看板、评审）一律以 `AR-16` 为准。旧描述的对照语义 = "含终态未退的 runner 也阻断新建"，新口径 = "只对非终态作业探测 runner 存活"。
5. **边界**：本条**只**改建作业守卫的扫描面；`JobWatchdog`、`StaleJobRecoveryRunner`、`TaskService.delete` 的活性判据**均不改**（删除闸门仍按"本地 runner / 心跳 / 共享 runner 键"判活，**不按作业状态过滤**）。

**理由**

1. **终态数据事务已提交**（本条的第一安全前提）：作业终态写发生在执行器**数据面事务提交之后**——`JobProgressService.finish` 类注释明写"由执行器在数据面事务提交后调用，保证'快照说完成时数据已落库'"，`JobTerminalWriter.complete` 走 `afterCommit`。作业到终态时 runner **已不再写暂存行 / 文件**，此后只剩 `endRunner` 清理，**不构成第二个数据面写者**。
2. **任务终态守卫仍在**（第二安全前提）：`createAndStart` 先跑 `assertTaskNotFinalized`——`CANCELLED` 任务恒拒，`COMPLETED` 任务按其**最终作业**（IMPORT→PUBLISH、EXPORT→EXPORT）核成功作业。生产上"取消后仍有活 runner"这条最需要拦截的形态**走不到** runner 守卫：取消作业必然联动任务 CANCELLED。
3. **成本是实测口径上的真问题**：旧实现按"任务**全部历史**作业"逐条打 Redis，且全程持 task 行锁 ⇒ **N 次同步命令**、延迟随历史作业数单调增长，Redis 抖动时把停顿放大到删除 / 并发建作业（`FA3-N7` / `BZ-34`，S3；旧注释"runner 可能仍在长事务里写暂存/文件"是**未量化假设**，与本条理由 1 的既有契约冲突）。
4. **探测历史作业不能提升拦截率**：真正的"僵尸仍在写"由看门狗判死（判死成功即 `revokeRunner` 清共享键，**即使探测也读不到**），而活跃写者必然处于 PENDING/RUNNING。

**代价**

1. **已接受的能力收窄**：终态作业的 runner 在"终态写已提交、`endRunner` 尚未执行"的**极小时窗**内不再被这条守卫看见。该窗口内 runner 不再写数据面（理由 1），故损失限于"最后一个清理动作与新建作业重叠"，**不产生数据面双写**。
2. **安全前提是有条件的，必须随执行器演进复核**：若将来有执行器把数据面写入放到终态写**之后**（例如新增收尾落盘、终态后回写结果），本条前提失效，**必须先**改回状态无关扫描或改为"终态 + 近期窗口"双条件，**再**上新执行器。
3. **测试面变化（口径变化，非放宽安全断言）**：`RunnerActiveMultiInstanceTest` 原用例以"任务 ACTIVE + CANCELLED 作业 + 活 runner"断言阻断；该夹具有悖于理由 2 的生产形态，在新口径下不再成立，已改写为"**异类型在途作业 + 活 runner**"仍阻断、`endRunner` 后放行，并新增"**终态作业的 runner 键一次都不被读**"的用例；另把"Redis 读失败 fail-closed"用例的夹具改为在途作业（终态作业已不触发共享态读取）。
4. **文档面代价**：旧"含终态未退"表述与两份看板的历史行**保持原样**，读者需按本条做口径切换；本追注与看板新行即为该切换的唯一准据。

**影响任务**

- **Task 2 Step 4**（`JobService` 的非终态查询）**落地为本条口径**：只扫 PENDING/RUNNING；**task 行锁与 Redis fail-closed 不得动**；**不得**顺手改删除闸门、看门狗判死判据、恢复扫描面。

### AR-17 普通消息级 regenerate：本批不做（入口隐藏，A7 保留缺项）

**裁决**

1. **本批不实现普通消息级 regenerate**：不替换普通已完成回答、不替换有半截正文 / 半截思考的回答；**不提供**"禁用按钮 + unsupported 提示"这类**假入口 / 死 UI**。
2. **入口整体隐藏**：助手消息操作行不再出现 regenerate 按钮；错误卡的「稍后重试」只在**归属可证明且符合 AR-05 条件**的零产出失败轮上出现（走真实窄入口「重试本轮」）；其余情形该动作**直接隐藏**，不得跳到"重新生成不可用"的空动作。
3. **三动作语义仍然分开**（与 AR-09 一致）：**继续** = 追加驱动、不删历史、不追加用户气泡；**重试本轮** = 仅 AR-05 条件的失败轮（失败 / 无在途 / 待决全结算 / 工具轮配对 / 无半截 / 同模型 / 同固定历史）且仅模型步重跑；**普通 regenerate** = 本批不做。
4. **A7 保留缺项**：审视矩阵 `A7`（无消息级 regenerate）**继续登记为缺项**，不因本裁决销记；后续若要做，须先设计独立协议。

**理由**

1. **普通 regenerate 不是"再发一次请求"**：它要处理"已有半截正文 / 半截思考 / 已执行工具"的**失效替换**——旧半截如何作废、`seq` 如何续号、重连如何对齐、历史与台账如何不出现两份结果，需要新的分支 / 失效替换协议。本批的窄入口只重跑模型步（工具零重执行、历史切片不改），两者不是同一件事。
2. **假入口比没有入口更糟**：禁用按钮或点击后只弹"暂不支持"会让用户以为功能存在、只是暂时不可用，既增加心智负担，也会诱导后续实现绕过协议。按 AR-05 / AR-17 的口径，**能证明条件不满足就不出入口**。
3. **风险不对称**：本地截断后 `send` 会重建上下文、可能重放工具，属于**危险假实现**；隐藏入口的代价只是"暂无此功能"，可由「继续」「编辑后重发」「新开一轮」覆盖主路径。

**代价**

1. **普通已完成回答不能一键重生成**：用户需改写入输入框后重发，或新开一轮；有半截内容的失败轮只给中性「状态未确认」视图 + 重新载入 / 新开一轮。
2. **A7 缺项继续存在**：能力缺口明确登记，不把"隐藏入口"包装成"已修复"。
3. **未来实现成本前置**：先补协议（半截作废 / 失效替换 / seq 续号 / 重连对齐），再做 UI；不得以本批隐藏入口为由跳过协议设计。
