## ② 结论

**Q1 计量**
- 三条路：官方 usage 字段（唯一"账单一致"口径）> 厂商 `count_tokens` 端点（发请求前预检）> 本地 tokenizer 估算（唯一能实时、按字段拆分，但与账单有偏差：role 框架、工具 schema、CJK/代码都会漂）。
- 上下文占用应取"下一次请求的 prompt_tokens"，它天然包含 system+tools+history+tool results，是唯一正确的分母口径；`completion_tokens` 只影响下一轮占用增量。
- 流式场景是最大的工程坑：OpenAI 规范要求 `stream_options.include_usage=true` 时**最后一个 chunk** `choices:[]` + `usage`；但兼容网关普遍不守规矩——有的完全不发 usage chunk，有的**每个 chunk 都重复 usage**（Cline/Roo 因此把 token 数放大到 1.7M）。必须"取最后一个、去重、缺失则回退估算并标注为估算值"。
- 展示口径主流是"百分比 + 已用/上限"（Cursor 明文 `80.1K/200K`），辅以按类目拆分（Claude Code、Cursor 2026 都已做）；"剩余可轮次"无人做主指标（不可预测），只在提示文案里做预警。
- 时机：每轮结束落一次 usage（准确）；流式中只显示"本轮输出 token"这种廉价增量（Claude Code 的做法）；上下文占用条不需要逐 token 跳动。

**Q2 压缩谱系（从轻到重）**
1. 工具结果清除（最轻、ROI 最高）：Anthropic `clear_tool_uses_20250919`，`trigger: input_tokens` + `keep: N tool_uses`，服务端换成占位符；官方 100 轮检索任务省 84% token。
2. 滑窗/硬截断：按 Turn 边界丢最旧轮（Spring AI `TurnWindowCompactionStrategy`、`MessageWindowChatMemory` 默认 20 条）；不做摘要、最便宜、最容易"失忆"。
3. 摘要压缩（主流）：Claude Code auto-compact、Cline Auto Compact、Aider 递归摘要（弱模型+后台线程）、Cursor `/summarize`、Spring AI `RecursiveSummarizationCompactionStrategy`（合成一对 user/assistant 消息滚到窗口最前，滚动叠加）。
4. 服务端托管压缩（2026 新趋势）：Anthropic 按需 compaction（保留最近轮次逐字、后台压缩、保留 thinking）+ 阈值模式（默认 150K）；OpenAI Responses 的 opaque compaction item。
5. 语义压缩（LLMLingua 族，最高 20×）：小模型逐 token 打分剪枝，但非确定性、需 GPU、对结构化内容（工具 schema/JSON）效果差——生产对话产品几乎不用，只在 RAG/离线场景。
6. 记忆外置：MemGPT/Letta 的 core/recall/archival 分页、structured notes（NOTES.md）、子代理只回 1–2K 摘要、对全量事件日志开一个 `conversation_search` 工具让模型"翻旧账"（Spring AI Session 已内建此招）。
- 用户可感知形态：Claude Code 显示 "Compacted" 提示 + `/context` 可查；Cline 把摘要做成一条可见 tool call，可 checkpoint 回滚；Cursor 摘要进入独立分桶。共识是**必须可见 + 可回溯**。

**Q3 坑与防法**
- **工具对孤儿化**：裁剪点落在 `tool_use` 与其 `tool_result` 之间 → 400 `tool_use ids were found without tool_result blocks`。防法：以 Turn 为最小裁剪单位（一个 Turn = 一条 UserMessage 起、到下一 UserMessage 止的全部级联事件）；发送前跑一遍配对校验/修复（丢弃无主的 result、为缺失 result 的调用补占位）；并行调用保持 id 原样，绝不重铸。
- **摘要丢关键决策**：真实投诉形态 = "压缩后完全忘了之前上下文、重做已完成的任务"、"`.claude/project-context.md` 指令被抹掉"。防法：摘要 prompt 显式保留"目标/已做决策/未解决错误/待审批项/关键 ID"，先用真实 trace 调 recall 再调 precision；允许用户 `/compact 关注…` 指定重点；原始日志不删（只改"喂给模型的那份"）。
- **压缩中途失败/静默降级**：有开源实现把失败 catch 成 `"Summary unavailable...older messages truncated"` 直接替换用户消息，不可逆且无上报。防法：压缩写成原子操作（新历史+摘要一次事务落库，原文存 `session:{id}:archive`），失败则**保持原状重试**，绝不静默截断。
- **压缩自身成本与缓存**：压缩请求要读完整会话，是一次大请求且必然 cache miss；Claude Code 在 `/usage` 里把它单列为 "expected rebuild"。压缩后前缀被重写，缓存从头重建——这是"压缩后那一轮特别贵/慢"的根因。
- **计量与现实不一致**：Cursor 用户报告 `/summarize` 后圆环与分桶百分比对不上。压缩后必须重置计量基线（把摘要的 token 数作为新起点重新累计）。

**Q4 对本项目的建议**

统计（推荐路线）
1. 计量源以**流式 usage 为主、本地估算为兜底**：请求带 `stream_options.include_usage=true`；解析时"取最后一个 usage chunk、丢弃重复、校验单调性"；拿不到就本地估算并在 UI 标 `≈`。把 system prompt + 工具 schema 的固定开销算一次缓存起来，按模型族选 tokenizer（中文按字符/1.6~1.8 兜底）。
2. 记账粒度：`chat_session_usage`（session_id, turn_no, model, prompt_tokens, completion_tokens, cached_tokens, est_flag, ts），既支撑展示也支撑成本归因；TTL 与会话同为 24h 滑动。
3. 展示位（最小侵入）：输入框下方一个 pill `上下文 42% · 84k/200k`，点击展开分桶（系统提示/工具定义/记忆/历史消息/工具结果/剩余），70%/85%/95% 三档换色与文案；不要在每个气泡上标 token。流式中只显示"本轮已生成 N tokens"。
备选：只做 hover 百分比 + `/context` 式弹层（成本最低，Cursor 早期形态）。

压缩（推荐路线）
分层，全部对齐 Turn 边界：
- L0 每轮：工具结果超过 N KB 就截断并注明"已截断，可让 AI 重取"（治本，从源头少产生 token）。
- L1 70–75%：清最旧工具结果，换占位符 `[tool_result 已清理: 4.2k tokens]`，保留最近 3–5 对。（本仓文案已于 2026-10-22 改版为 `[工具结果已清除：<name> · ≈<n> tokens · toolCallId=<id>]`，见设计稿 §L1 —— 此行保留调研当时的建议形态、不回改。）
- L2 80–85%：滚动摘要（保留最近 6–8 轮逐字 + 摘要置顶），摘要 prompt 固定保留：用户目标、已确认的配置变更、未解决报错、**当前待审批项**、关键资源 ID。
- L3 95%：硬截断兜底 + 明确提示条。
- 触发用"下一轮预估占用"而非历史长度；加滞回（压缩到 60% 以下才允许再次触发），避免抖动把缓存打穿。
- 与 HITL 的交互（关键）：**挂起态所在 Turn 永不参与压缩**，`tool_call` 与 `tool_result` 必须成对保留；恢复时把待审批项逐字重挂到消息尾部，并在 UI 提示"会话已压缩，待审批内容未变"；挂起期间禁止后台压缩（或只允许 L1）。
- 与 24h 滑动 TTL 的交互：压缩产物（摘要消息带 `compactedFrom/lostTokens` 元数据）与原始归档日志同 TTL、同滑动续期；用户刷新页面时先读摘要+元数据渲染"已压缩 N 轮"提示条，展开才读归档。
- 压缩执行方式：同步（下一轮请求前，前端显示"整理上下文中…"，设置超时→回退 L3）比后台异步简单，符合配置平台的交互预期；备选是学 Anthropic 后台压缩 + 事后替换。
- 缓存协同：system prompt / 工具定义严格静态在前，动态内容在后；**不要每轮做小裁剪**（每轮改前缀 = 每轮 cache miss，比偶尔一次大压缩更贵）。

**Q5 官方指导（2025–2026）**
- Anthropic《Effective context engineering for AI agents》（2025-09）：context rot / attention budget；三板斧 compaction、structured note-taking、sub-agent；最轻的压缩是 tool result clearing；压缩 prompt 要"先最大化 recall 再提 precision"。
- Anthropic compaction 文档（beta）：按需压缩（`compact-2026-09-04`，保留最近轮次、可后台、保留 thinking）与阈值压缩（默认 150K）两形态；context editing 为规则型（`clear_tool_uses_20250919` / `clear_thinking_20251015`，beta `context-management-2025-06-27`）。
- OpenAI Responses compaction：`compact_threshold` 服务端压缩 + `/responses/compact`；压缩项不透明、不可人工解读，需原样回传。
- Prompt caching 与压缩：缓存是**前缀精确匹配**（OpenAI 自动、≥1024 tokens 起、TTL 5–10 min，读取约 0.1×；Anthropic 显式 `cache_control`，5 min/1 h）。任何裁剪/压缩都会让缓存从改写点失效；反过来缓存让"多留历史"比账面便宜，所以应"少动、动则大动"，并把压缩后的首轮成本预期告知运维。
