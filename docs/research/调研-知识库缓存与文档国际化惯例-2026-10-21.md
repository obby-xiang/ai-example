# 上章 · 远端文档缓存层业界惯例

- 课题：服务从远端 HTTP 源拉取文档/知识语料时的缓存层怎么做
- 场景口径：Java 21 + Spring Boot 3 + Redis；只读、读多写少、写只来自远端的文档语料（几十到几百篇 markdown，MB 级）

## 1. HTTP 层：validator 优先，没有 validator 才退回 TTL + 哈希

对每篇文档保存 `ETag` / `Last-Modified`，刷新时发送 `If-None-Match` / `If-Modified-Since`；源返回 **304** 就只推进本地 `fresh-until`，不重新下载正文（RFC 9111 §4.3 的校验语义，字段定义见 RFC 9110 §8.8）。

`Cache-Control: max-age=…, stale-while-revalidate=…` 用来声明新鲜期，但**作为客户端缓存需要自己解释这些指令**；源没有 validator 时，退回 TTL 加内容哈希比较。

<https://www.rfc-editor.org/rfc/rfc9111.html>

## 2. 缓存模式：cache-aside + SWR + stale-if-error

只读、读多写少、写只来自远端的文档语料适用 **cache-aside**（应用负责 load 与 invalidate，缓存的 TTL 按访问模式设定）；配合 **SWR**（先返旧值、后台异步 revalidate）与 **stale-if-error**（源 5xx/超时时继续供旧语料）。

官方定义见 RFC 5861 §3/§4。

<https://learn.microsoft.com/en-us/azure/architecture/patterns/cache-aside>、<https://www.rfc-editor.org/rfc/rfc5861.html>

## 3. 惊群：进程内 singleflight，跨实例 SET NX 锁，TTL 加 jitter

- **进程内**用 singleflight 合并同一 key 的并发刷新（`Do`/`DoChan`，同 key 只有一个 in-flight，其余等结果）。
- **Caffeine 的 `refreshAfterWrite`** 是「到期后**首次被查询**才异步刷新、旧值继续返回、刷新的 key 去重、刷新异常保留旧值」——这正是文档语料要的行为。
- **跨实例**抢刷新权用 `SET lock token NX PX 30000` 加 Lua 比对 token 删除（Redis 官方自述此模式较粗，强保证场景用 Redlock / Redisson `RLock` 带 watchdog）。
- 所有 TTL 加约 **±10% jitter**，防止批量同刻过期。

<https://pkg.go.dev/golang.org/x/sync/singleflight>、<https://github.com/ben-manes/caffeine/wiki/Refresh>、<https://redis.io/docs/latest/commands/set/>

## 4. 拓扑：单 leader 拉取写 Redis，其余只读；版本号为主、pub/sub 为辅

单 leader 拉取写 Redis、其余只读最常见。失效通知两条路：

- **pub/sub**：fire-and-forget、不保证投递，必须靠 TTL 兜底；
- **版本号轮询**（`INCR manifest:version`，各实例周期性比对）——天然自愈。

文档场景建议**版本号为主、pub/sub 为辅**。

Redis 存什么：**MB 级语料（几十~几百篇 markdown）存全文完全合理**，远低于「单条 ~100KB 以上才考虑外置」的经验线；只存元数据的边界在 GB 级或大二进制/附件场景。

<https://github.com/cache-invalidation-org/cacheinvalidation.org/blob/main/content/advanced-cache-invalidation-patterns-synchronization/pubsub-routing-for-cross-service-invalidation/implementing-redis-pubsub-for-real-time-cache-invalidation/index.md>、<https://oneuptime.com/blog/post/2026-03-31-redis-why-not-store-large-blobs/view>

## 5. 索引与缓存的关系：索引是派生产物，缓存是源的物化快照

索引是派生产物，**远端源是真相**，缓存是源的物化快照。业内（Lucene/ES）把「取源/缓存」与「建索引」解耦，索引可随时重建，切换靠 alias 原子换指针或重开 `IndexSearcher`（Lucene 段不可变 + NRT）。

**从缓存重建优于从源拉取**：避免远端部分失败造成半成品索引，且多实例看到同一份字节；代价是缓存必须带 manifest/版本校验完整性。

<https://www.elastic.co/docs/manage-data/data-store/aliases>、<https://blog.mikemccandless.com/2011/06/lucenes-near-real-time-search-is-fast.html>

## 6. 一致性与 staleness：明确写出可接受上限

三种做法：

1. **各实例各拉各建**——最简单，N 个实例 N 次拉取，MB 级可接受；
2. **版本号轮询**——推荐；
3. **事件推送**——最快但需兜底。

惯例是**明确写出可接受 staleness**，例如「文档内容相对源端延迟 ≤ 轮询间隔 + 重建耗时（如 5 分钟）」，并以 TTL 作为事件丢失时的最终保障；满足该表述即可，不强求 read-after-write。

<https://dev.to/jessica_patel_472897dd43c/designing-cache-invalidation-at-scale-with-spring-boot-redis-and-aws-elasticache-36cp>、<https://www.controlled-rollout-systems.com/backend-evaluation-server-side-sdks/distributed-caching-for-flag-evaluations/cache-invalidation-strategies-for-flag-updates/>

## 7. Java/Spring 生态：`@Cacheable` 不适合本场景，主流是手写 cache-aside

`@Cacheable` + `RedisCacheManager` 适合单条 KV 读写与 per-cache TTL，但对「整批语料装载 / 异步刷新 / 单飞 / 条目级版本」支持很弱，且其可选锁是 **cache 级而非 entry 级**，不适合当分布式刷新锁。

主流生产做法是**手写 cache-aside（`RedisTemplate`）+ Caffeine L1**，L1 靠 pub/sub 或版本号失效（Spring 自身无 L1 + L2 组合，只有第三方 near-cache starter）。

<https://docs.spring.io/spring-data/redis/reference/redis/redis-cache.html>、<https://github.com/seokkim95/caffeinated-redis>

## 本场景推荐组合

手写 cache-aside；**Caffeine L1 常驻全部语料**（MB 级直接全量）+ **Redis L2** 按 `doc:{id}` 存 markdown 与 `doc:{id}:meta`（etag/hash/updatedAt）+ `manifest:version`；

启动时与固定间隔（如 **5 min**）用 `If-None-Match` 拉 manifest 比对版本；版本变化时先 `SET NX PX` 抢刷新权（单飞），把变更文档拉取后写 Redis 再 `INCR` 版本，各实例看到版本变化后**从 Redis 重建索引并原子替换 `IndexSearcher`**；远端故障走 stale-if-error 继续供旧语料；所有 TTL 加 jitter，并在文档/配置里写明可接受 staleness 上限。

# 下章 · 知识文档国际化业界惯例

- 课题：知识文档要不要做多语言版本、怎么做；检索与答案两侧的语言策略

## 1. 语料侧：三种模式并存，按「对外/对内」选

- **① 单语料 + LLM 按用户语言作答**：Intercom Fin 默认先在「提问所用语言」的内容里找，开了 real-time translation 后只维护一种语言正文，也能按客户 locale 回答 — [Fin 多语言](https://fin.ai/help/en/articles/10840651-use-fin-ai-agent-in-multiple-languages)
- **② 翻译副本**（同一文章挂多语言变体）：Intercom 每篇文章按语言一个版本、结构共用、按浏览器语言切换 — [Intercom](https://www.intercom.com/help/en/articles/3107388-support-multiple-languages-in-your-help-center)；Zendesk 同一 article 下多 translation、另有 `/hc/<locale>/` 路径 — [Zendesk API](https://developer.zendesk.com/api-reference/help_center/help-center-api/translations/)；Microsoft Learn 是 `/en-us/` 与 `/zh-cn/` 同路径镜像、英文为源 — [en-us](https://learn.microsoft.com/en-us/contribute/) / [zh-cn](https://learn.microsoft.com/zh-cn/contribute/)
- **③ 混语单库**：Notion 没有 locale 变体，实践中靠多语言子页或按需 AI 翻译，本质是混语，只适合内部低治理场景 — [Notion 翻译](https://www.notion.com/product/ai/use-cases/translate-your-content)

**结论**：对外公开 KB 用 ②；助手/问答型用 ①；③ 只当过渡。

## 2. 检索侧：单索引多字段可行，但中日文别混

- 单索引 + 语言后缀字段（`title.zh` / `title.en`）+ 每字段独立 analyzer，仅在字段语言严格分离、文档量不大时成立（Meilisearch 给的适用线约 **<1M docs**）；更大规模或强语言差异用**多索引**，按语言设 stopword/分词器后并行检索合并 — [Meilisearch](https://www.meilisearch.com/docs/capabilities/indexing/how_to/handle_multilingual_data)
- 中文：ES 核心没有 `chinese` analyzer；`cjk` 是 bigram，`smartcn` 是 Lucene 概率分词（简中），`standard` 对汉字基本单字切。**BM25 下必须显式指定，默认 analyzer 会毁掉中文相关性** — [语言分析器列表](https://www.elastic.co/guide/en/elasticsearch/reference/current/analysis-lang-analyzer.html)、[smartcn](https://www.elastic.co/guide/en/elasticsearch/plugins/current/analysis-smartcn.html)
- 查询侧：**显式 UI locale 优先于自动语言检测**（短查询检测不可靠）；「全字段并查」只在字段严格按语言分离时安全，否则跨语言互相污染 IDF。

## 3. 无向量 RAG：翻译查询是必需桥，不是优化项

- CLIR 标准做法是 **query translation**：译成语料语言再跑 BM25；实践上原查询与译后查询都检索、结果并集/RRF，并对翻译质量设门（如 COMET 阈值），低置信回退 — [CLIR baseline](https://arxiv.org/html/2304.01019v1)、[实践蓝图](https://dev.to/kuldeep_paul/how-to-improve-cross-lingual-retrieval-accuracy-in-bilingual-rag-chatbots-2mk1)
- **BM25 边界很硬**：词项不重叠 = 零召回；跨脚本且 tokenizer 不处理 CJK（按空格切）时英文查询直接 **0 命中**，有项目实测融合分掉约 **30%** — [issue](https://github.com/CortexReach/memory-lancedb-pro/issues/271)
- 译名锁术语表，产品名/制度名保留原文，避免一次一译。

## 4. 答案侧：语言跟用户，引用跟源文档

- 回答语言按用户 locale（Fin 明确如此）；但**模型常守不住回答语言**，需 prompt + 评测显式约束（XRAG 结论） — [dev.to](https://dev.to/kuldeep_paul/how-to-improve-cross-lingual-retrieval-accuracy-in-bilingual-rag-chatbots-2mk1)
- 引用锚到稳定 `doc_id` + 章节/段落 anchor，展示原文标题与原文片段再附译文；**不要为英文答案造英文 `doc_id`**，否则引用与治理都断裂。
- 术语一致性靠 glossary/termbase：Slack 明确决定哪些英文词不译 — [Slack](https://slack.com/blog/collaboration/how-we-localize-slack)；Microsoft 用 `no-loc` 标记不可翻译串 — [Markdown reference](https://learn.microsoft.com/en-us/contribute/content/markdown-reference)

## 5. 治理：翻译副本一定会漂移

- 源文改一句、译文滞后数月是常态；做法是 **single source of truth + 字符串级增量同步 + 翻译记忆**（只重译改动句），译文标注「基于源文 vX / 最后同步日期」，过期即标注或回落源语言 — [Crowdin](https://crowdin.com/blog/multilingual-knowledge-base)
- **不值得翻译**：代码/配置/API 名/错误码（no-loc）、内部制度流程（读者就是中文员工）、低频长尾文章；内部文档可纯 AI 直译甚至不译。

## 6. 成本门槛：没有统一数字，按头部/长尾算 ROI

- 通行判断：少数头部文章贡献多数流量与工单减免，**先译头部**；ROI = 翻译 + 维护成本 vs 单张工单成本；语料变更越频繁，翻译副本 TCO 越高。常见起步是 **top 20–50 篇**再按数据扩 — [Translated](https://translated.com/resources/prioritize-support-content-translated-first)
- 需求侧看目标语言用户占比与当地搜索量；占比低且用户能接受「母语提问 + 母语作答」时，模式 ① 明显更划算。

## 本场景推荐口径

**不建翻译副本**——中文制度库作唯一源，英文提问先经术语表约束的 EN→ZH 查询翻译，原查询 + 译后查询**双路 BM25 后 RRF 合并**（Lucene 侧用 `smartcn` 作 zh 字段分析器，另建只放英文术语别名的 `aliases_en` 字段做低成本桥接），答案按 UI 语言生成，引用固定锚到中文 `doc_id` + 章节并附中文原标题；只有英文用户占比/英文工单过阈值时，才翻译 **top 20–50 篇**对外制度摘要并标注同步版本，**内部制度永不翻译**。
