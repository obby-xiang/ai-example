## 1 终态 / 取消：per-run 监视器覆盖「判取消 → 写终态 → 发终帧」

**现状**：取消收尾（`cancelTerminal`）与成功/失败收尾原本各自写快照、各自发帧；`fail` / `emptyReply` 只把"写终态"放进取消优先守卫，**终帧仍在守卫之外发出** ⇒ 取消的 `done{cancelled:true}` 可以插在"写完 FAILED"与"锁外 `error`"之间，一轮出现两条终帧。

| 件 | 语义 | 锚点 |
|---|---|---|
| `CancelledRunFinalizer#finalizeMonitor` | **per-run 监视器**（`MONITOR_STRIPES = 64` 条带，同一 run 恒返回同一个对象；不同 run 可能落同条带 ⇒ 最坏只是多等，不影响正确性）；取消收尾、成功终局、失败出口、环外异常、续跑失败**共用这一把** | `CancelledRunFinalizer.java:96` / `:133` |
| `ResilientChatService#finalizeMonitor` | 对外统一取锁入口；`null` = 未注入交棒器（轻装配 / 直接 `new` 的单测）⇒ 维持单线程语义 | `ResilientChatService.java:383` |
| `fail` / `emptyReply` | 整段"判取消 → 写终态 → 发 `error`"进监视器（`failLocked` / `emptyReplyLocked`）；`synchronized` 可重入 ⇒ 内部再进 `cancelTerminal` 安全 | `:2223` / `:1758` |
| `failRunUnlessCancelled` | 读侧判据 + 写侧 CAS 同锁；**快照为 `null`（压缩窗口）也先查取消登记表** | `:1703` / `:1712` / `:1719` |
| `emptyReply` 的 null 取消 | 快照尚未建立且取消已成立 ⇒ 不发 `error`，改走 `cancelTerminal`（终态与终帧归取消收尾） | `:1768` / `:1779` |
| 首轮压缩后复查 | 压缩是最长的零帧窗口；命中 **确定 `CANCELLED`** ⇒ 不建快照、不发起模型调用，直接 `cancelTerminal`（只发唯一终帧） | `:530` / `:536`、`cancellationRequested` `:1508` |
| 首轮交棒前复查 | 覆盖"压缩之后、快照建立/历史落库期间"的窗口；命中 ⇒ 就地取消收尾，不发起任何模型调用 | `:597` / `:601` |
| 环外异常收尾 | `AiController#writeOutsideTurnFailure` 在**同一把**监视器内"写 FAILED + 发 `error`"，并顺手做终态清理 | `AiController.java:529` / `:545` / `:552` |
| 续跑失败收尾 | `markDriveFailure` 全段进锁；取消已先到（快照取消态 / 守卫拒写）⇒ **连 `error` 也不发**；`convergeProviderGone` 同型 | `ResumeService.java:1709` / `:1727` / `:2195` |
| `pendings` 去重 | 取消收尾只 `cancelPendings` 一次、读一次（`cancelledPendings`），同一清单喂给"补发裁决帧"与"park 结算"；三参 `emitCancelOutcomes` 保留旧语义（自己收敛、自己读）供既有调用 | `ResilientChatService.java:2050` / `:2090` / `:2095` |
| `idemFor` | 台账读口两跳：`idemFor`（O(1) 索引）优先，未命中回落 `ledgerFor`（全表 / 旧数据）；"台账才是判据"仍只有一个出口 | `:2465` / `:2438` |

**边界**：`cancellationRequested` **只认确定的 `CANCELLED`**；`UNKNOWN` / 读异常按未取消继续（这两处都还没有不可逆动作，与既有 C2 退避口径同源）。`clearTerminalRunState` 只清进程内表，**不碰** `LeaseService` 的 ended/epoch、Redis 帧册与快照 —— 终态的权威事实仍是 Redis 那一份。

## 2 会话活跃索引、终态进程内清理、工具池饱和、精确数值比较

**会话→活跃轮索引（N1）**：终态后 `clearSessionCurrent` 要回指"同会话仍活跃的最新一轮"，旧口径先 `SMEMBERS ai:session:runs:<sid>` 再逐个反序列化**整份快照**（每轮终态 O(N) 次大 JSON）。

- 新键 `ai:session:active:<sessionId>`（ZSET，score = 最近一次活跃毫秒）：`SESSION_ACTIVE_PREFIX` `RunStore.java:246`、`markActiveRun` `:1074`（随 session→current 写入）、`forgetActiveRun` `:1092`、`newestActive` `:1301`、`pickActive` `:1327`。
- 语义不变：仍是"最新且仍活跃"（`updatedAtMs` 最大；同毫秒平手 `SUSPENDED` 优先），**是否活跃仍以快照复读为准**（stale 成员顺手摘掉）；索引不可用/为空 ⇒ 一次性回退 `SMEMBERS + 逐个快照`，命中活跃轮后**回填索引**。`deleteRun` 同步摘成员。
- 取舍：索引只服务"回指候选排序"，写失败只降级、不影响正确性；老会话首次仍付一次全扫。

**终态进程内清理（N5）**：三处按 `runId` 常驻的进程内表在终态后没人再读，统一由 `ResilientChatService#clearTerminalRunState:1443` 幂等清理（失败只 WARN，不改变已发出的终态/终帧）：

| 清理项 | 只动什么 | 锚点 |
|---|---|---|
| 确认门**重派发计数** | `dispatchRetries` 一个计数 | `ConfirmGate#clearRunState:2166` |
| 取消交棒**去重位 + 重试预算** | `inFlight` / `attempts`；`Error` 路径下 `attempt` 也先 `finish` 再上抛 | `CancelledRunFinalizer#forget:194` / `:201` |
| 工具**活动锚点** | 只清 `lastActivityAtMs`（不扩 `clear`：它刻意保留锚点） | `ToolActivityBeacon#clearRun:304` |

调用点 = 四个成功/失败/空回复/取消出口（`:1427` / `:1807` / `:2115` / `:2257`）+ `AiController` 环外失败 + `ResumeService` 两处续跑终态。

**工具池饱和（N3）**：超时监视线程池容量改为**按配置派生**（`app.ai.suspend.pool-size`，缺省 20）并按容量共享执行器（`TOOL_TIMEOUT_EXECUTORS`，`SpToolCallingManager.java:196` / `:208` / `:211` / `:406`）。

- 旧行为：`SynchronousQueue + AbortPolicy` 饱和时**退化为同步执行、无超时** —— 恰好在最忙时让"到点收口"失效，并让工具脱离超时笼在调用线程上跑完。
- 新行为：饱和抛 `ToolExecutorSaturatedException`（`:2193`，文案保留 `EXECUTOR_SATURATED` 可检索词）⇒ 按既有 `timeout / TOOL_TIMEOUT` 口径结算成**未执行**（`executed=false`、不写台账、轮继续）：超时与饱和共用同一个 `settleAsUnexecuted` 标志位（`:1951` / `:2000`），由 `settleToolTimeout`（`:2133`）出结局帧并回填模型。

**精确数值比较（N10）**：表单 `min/max` 与回灌值不再经 `double` 中转 —— 整数按 `BigInteger`、其余按 `BigDecimal#compareTo`（`GenerativeFormRules.java:1077` / `:1092` / `:1106`），覆盖 `min > max` 判定、取值范围、整数判定（`2.0` 算整数、`2.2` 不算）、枚举值相等、区间比较五处；**不引入 epsilon**（小数相等仍是严格相等），非有限数（`1e999`）退回严格 `double` 比较并照旧判类型错误。

## 8 边界与不声称

- **只做原子性收口，不改语义**：终态仍只有 `DONE` / `FAILED` / `CANCELLED` 三种权威结果；`CANCELLED` 依旧是"终帧归取消侧发"的唯一终态，`DONE` / `FAILED` 维持旧口径（写终态失败仍照发 `error`）。
- **不加帧、不加字段、不加配置键**：SSE 帧类型集与 `tool_result` / `frontend_tool_result` 键集不变；新增的只是一个 Redis 键族（`ai:session:active:`，与会话同寿、失败降级）与前端常量模块。
- **活跃索引是优化不是判据**：索引只决定"先看谁"，活跃与否仍以快照复读为准；索引缺失/损坏只会退回旧口径（更慢，不会更错）。
- **工具池饱和的取舍**：宁可让模型知道"这一拍没跑"（`executed=false`），也不让一次调用脱离超时笼；容量仍由既有 `app.ai.suspend.pool-size` 派生，未新增独立开关。
- **`appliedSeqs` / `runSeq` 有界 = 丢最旧**：重投窗口远小于 64 / 16，超窗丢最旧的语义变化已在代码注释登记；若将来回放窗口变大，须同步调窗口而不是取消上限。
- **前端身份判据的边界**：`RoundGuard.runId` 只在读得到当前 run 时生效（读不到时以会话 + 纪元为准），故"同会话同纪元但 runId 已换且前端未更新 `activeRunId`"这一假阴性窗口**不在覆盖范围**。
- **未做全量门禁**：本件与两份看板的门禁只有 `check-docs`；产品测试、构建、E2E、主 CI 的真实结论须以对应施工批的 CI 回执为准。
