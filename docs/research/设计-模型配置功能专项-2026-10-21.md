# 设计 · 模型配置功能专项（多提供商 + 自定义 OpenAI 兼容端点）

- 日期：2026-10-21
- 依据：`docs/research/调研-模型配置功能业界惯例-2026-10-21.md` §0 结论 7 / §3.1 路线 R1（索引第 32 件）；`docs/决策看板.md` 10-21「代裁授权与队列四件立项依据」行；`docs/任务看板.md` 10-21「批·模型配置功能」行
- 口径（范围裁决，非本稿自拟）：多提供商并存 + 自定义 OpenAI 兼容端点；**DB 存 provider/model（key 加密）为真源**；**env 只作首次种子**；独立「AI 设置」页；对话面板**只留模型选择器与折叠参数**
- 本稿性质：**设计与测试矩阵，不构成施工承诺**；§10 待裁项需指挥官/用户裁决后方可进入施工

## 1. 范围

**做**：
- DB 侧：`ai_provider` / `ai_model` / `ai_setting`（+ P2 的 `ai_config_audit`）建表与 Flyway V4 迁移；key 加密列与掩码列；
- 运行时：`ProviderRegistry`（provider 级实例注册表，热生效）+ 每请求 model/params 覆盖 + 可用性动态化；
- 种子：启动期"表空才写"的 env 种子（`AI_API_KEY`/`DEEPSEEK_API_KEY`、`AI_BASE_URL`、`AI_MODEL`）；
- 接口：provider CRUD、测试连接、拉取模型、模型 allowlist、全局默认参数、`/health` 扩展；
- 前端：新「AI 设置」页（三段式）+ 对话面板模型选择器/参数 popover；
- 测试：后端单测/契约测试、前端 vitest、E2E 增 1 条主用例、stub 上游扩展。

**不做**（本专项边界）：
- 多 key 负载均衡、成本/额度看板、调用审计外置（LiteLLM 网关路线 = 调研 §3.2 R3，后置）；
- Anthropic/Gemini 等非 OpenAI 兼容协议适配（表里留 `protocol` 列，值只实现 `OPENAI_COMPAT`）；
- 会话级记忆/压缩策略（上下文统计专项）；多语言文案抽取（i18n 专项）；
- KEK 轮换自动化（P1 只支持单 kid，§9 挂账）；spike/ 目录下的历史样例不动。

### 2.6 现状结论（本专项要动的五条硬障碍）

1. **装配闸**：`AiKeyPresentCondition` 是"env 有 key"的单源判据 ⇒ DB 里有 key 但 env 清空 = 整条链路消失；
2. **单实例**：`OpenAiApi`/`ChatModel`/`ChatClient` 都是单例冻结 ⇒ 无 provider 维度；
3. **无模型身份**：`RunSnapshot` 缺 provider/model ⇒ 续跑不能保证"同一轮同一模型"；
4. **无密钥托管**：无加密设施、无 KEK 约定、无掩码列；
5. **前端无配置面**：设置页只有只读的反馈列表，面板无模型/参数入口。

## 3. 核心设计

### 3.1 数据模型（V4__ai_provider_config.sql）

**ai_provider**（provider 主档，一行 = 一个 OpenAI 兼容端点）

| 列 | 类型 | 说明 |
|---|---|---|
| `id` | BIGINT IDENTITY PK | |
| `code` | VARCHAR(64) UNIQUE NOT NULL | 稳定机读名（`deepseek` / `custom-<n>`），种子写 `deepseek` |
| `display_name` | VARCHAR(128) NOT NULL | 卡片标题 |
| `protocol` | VARCHAR(32) NOT NULL DEFAULT `OPENAI_COMPAT` | 预留列，本期只此一值 |
| `base_url` | VARCHAR(512) NOT NULL | 仅 http/https，见 §3.5 URL 闸 |

**ai_setting**（全局默认参数，单行键值）

`setting_key VARCHAR(64) PK` / `value_json VARCHAR(2048)` / `updated_at`。首期键：
`default.modelId`、`default.temperature`、`default.topP`、`default.maxTokens`、`allow.userParams`（布尔，对标 Open WebUI 的 `Allow Chat Params`）、`config.version`（P1 的版本号落点，见 §3.4）。

**ai_config_audit**（P2）：`id / actor / action / target_type / target_id / diff_json / at`；`diff_json` 对 key 只写 `{"key":"updated","last4":"ab12"}` —— 永不写密文或明文（调研 §3.1e）。

**不建表的东西**：拉取到的远端模型清单（Redis 缓存 TTL 10min，见 §3.5）、会话级参数（前端 sessionStorage）、provider 健康态（内存 + `/health` 现算）。

### 3.2 key 加密（净新增 `AiKeyCipher`）

- **算法**：AES-256-GCM（JDK `javax.crypto`，**零新依赖**），12B 随机 IV，128bit tag，AAD = `provider.code + "|" + keyRef`（防跨行搬运密文）。
- **信封**：`v1.<kid>.<iv_b64url>.<ct_with_tag_b64url>` 单列自描述，便于将来轮换（`kid` 标识 KEK 版本）。
- **KEK 来源**：env `AI_SECRET_KEK`（base64 的 32 字节）。裁决：**fail-closed** —— KEK 缺失时"保存/更新 key"直接 400 `AI_SECRET_KEK_MISSING`；不允许明文降级、不允许默认 KEK、不允许自动生成后落盘。
- **不可解密**（KEK 换了/错了）：该 provider 判 `KEY_UNREADABLE`，`/health` 与设置页明示；**绝不**静默回落到 env key（否则"为什么突然用错 key"无从排查）。
- **泄漏面三条硬约束**（进测试矩阵）：
  1. 实体 `@Data` 的 `toString()` 会带 `key_cipher` ⇒ 必须 `@ToString.Exclude`（或 `@Getter(AccessLevel.NONE)` + 显式 getter），并加日志捕获用例；
  2. API DTO 只有 `keyConfigured` / `keyLast4` / `keyRef`，**无任何 `key`/`cipher` 字段**；
  3. 审计/日志只写 `last4` + 动作。
- **为什么不选 Jasypt**：它解决"配置文件里的 ENC()"，本需求是**字段级**加密 + 指纹 + last4 + kid 轮换，Jasypt 仍要自己包一层；且默认 PBE 算法族弱、引入新依赖（本仓有"依赖引入需显式裁决"的历史约束，见 `docs/M2-排期计划.md` R-91）。A/B 见 §10-1。

### 3.3 env 首次种子（`AiConfigSeeder`，仅当表为空）

- **触发点**：`ApplicationRunner`（在 Flyway 迁移完成、Web 容器就绪后）。**不能**放进 `Condition` —— 条件求值早于 Flyway，首次启动时表还不存在。
- **触发条件**：`ai_provider` 计数 == 0 **且** env key 非空（`spring.ai.openai.api-key`，即 `AI_API_KEY` 或 `DEEPSEEK_API_KEY`）。
- **写入内容**（单事务）：1 行 provider（`code=deepseek`、`display_name=DeepSeek`、`base_url=${AI_BASE_URL}`、`completions_path=/chat/completions`、`source=ENV_SEED`、`key_ref=ENV`、`key_cipher=NULL`、`key_last4` 取 env key 末 4 位）+ 1 行 model（`model_id=${AI_MODEL}`、`is_default=true`、`max_context=128000`（占位，UI 可改）、`supports_tool_calling=true`）。
- **env key 不落库**（裁决建议，§10-5）：种子只记 `key_ref=ENV`，运行时从进程环境读 key。理由：把运维手里的 env 复制进 DB 等于扩大泄露面，且与"env 只作种子"一致。用户在设置页"更新密钥"后才写密文并置 `key_ref=DB`。
- **幂等**：`count==0` 判据 + `code` 唯一约束兜底；多实例同时启动时捕获 `DataIntegrityViolationException` 视为"别人已种子"，记 INFO 不报错。
- **strict seed**：表非空 ⇒ **env 完全不参与**（不覆盖、不追加、不做"env 兜底"）。否则运维改 env 会静默改变线上行为，与"DB 为真源"自相矛盾。需要重灌时用 `app.ai.config.seed-force=true`（默认 false，显式运维动作）。
- **无 env、空表**：不写任何行，`/health` 仍返回 503 `AI_UNAVAILABLE`（`AiController.java:794-797` 的现契约不变），前端降级提示不变 —— 这是"零迁移风险"的基线。

### 3.4 运行时：`ProviderRegistry` + 版本号热生效

**快照与版本**
- `AiConfigService` 持有 `ConfigSnapshot{ver, providers, models, defaults, globalParams}`。
- 版本号 = `ai_setting['config.version']`（DB 真源）+ Redis `ai:cfg:ver`（跨实例失效信号，键族与 B23L1 的 `ai:lease:` / `ai:lock:` / `ai:xevents:` 命名对齐）。写路径：DB `UPDATE ... version=version+1` 后 `INCR ai:cfg:ver`。
- 读路径：每实例本地 `lastCheckMs` ≥ 1000ms 才比对一次版本（稳态 = 1 次 Redis GET/秒/实例，**不在 chat 热路径上同步打 DB**）；版本变化 → 重载快照 + 淘汰 registry 中已不存在/指纹变化的 runtime。Redis 不可用 ⇒ 退化为本地版本（单实例正确；多实例留"改配置只有本实例生效"的洞，登记为风险，§9）。

**registry 与实例重建**
- 缓存键 `RuntimeKey = providerId | keyFingerprint | baseUrl | completionsPath`。
- `ProviderRuntime{ OpenAiApi api, ReasoningAwareOpenAiChatModel model, ChatClient client }`；`ChatClient = ChatClient.builder(model).defaultAdvisors(messageChatMemoryAdvisor).build()`，记忆 advisor **与今天同一个 bean**（`AiModelConfig.java:90-94`），记忆仍按 `CONVERSATION_ID` 隔离。
- 复用今天的两件包装：`SpToolCallingManager`（bean 单例，无状态，跨 runtime 共享）、`RetryTemplate`/`ObservationRegistry` 走 `ObjectProvider`（同 `AiModelConfig.java:129-137`）。
- **热生效口径**：
  - 改 base-url / key / completions-path ⇒ `RuntimeKey` 变 ⇒ **下次取用时重建实例**，在飞请求持有旧引用继续跑完（语义正确），**无需重启**；
  - 改 model 名 / 参数 ⇒ **不重建实例**，只改逐请求 `OpenAiChatOptions`（`setModel` + `setTemperature/setMaxTokens/setTopP`，并**必须保留 `streamUsage=true`**，否则上下文统计专项的 usage 计量源断供）；
  - 改种子 ⇒ **需重启**（种子只在启动跑，刻意如此）；
  - 换 KEK ⇒ **需重启**（P1 单 kid，轮换挂账）。
- 无连接池可关：`OpenAiChatModel` 不持有长连接，旧实例交给 GC；设计上只保证"不再被新请求取到"。

**可用性（`AiAvailability` 改造）**
- 判据从"构造期 env key 非空"改为"**存在 ≥1 个 enabled 且 key 可解析的 provider**"（每次调用问 registry，O(1) 读快照）；`isAvailable()/code()/reason()` 签名保留 ⇒ `AiController.java:174/543/759/795` 四处调用点零改动。
- `reason()` 分三档文案 + 机器码：无 provider（`AI_UNAVAILABLE`）/ key 缺失（`AI_KEY_MISSING`）/ key 不可解（`KEY_UNREADABLE`）；默认码仍是 `AI_UNAVAILABLE`（前端兼容，`types/ai.ts:101`）。

**装配闸的处置（关键裁决，§10-6）**
- 推荐 **A：移除 `@Conditional(AiKeyPresentCondition.class)`**，四个类改为无条件装配，可用性完全由 `AiAvailability` 动态判定。
  - 理由：`Condition` 无法可靠读 DB（早于 Flyway），"env OR DB" 的判据只能靠 try/catch 猜表存在性；而"无条件装配 + 动态判空"语义更直白，且 `AiController` 已经用 `ObjectProvider` + `availability` 双门（`:173-176`、`:542-545`），无 key 时的对外行为**完全不变**（503 + 原 code/原文案）。
  - 必须补的两处：`StartupResumeRunner` 启动扫描前自检 availability，不可用直接跳过（不得因无 provider 报错）；`/api/ai/startup-resume` 在 runner 非空但不可用时也要给出 `reason=AI_UNAVAILABLE`（`AiController.java:395-403` 的现文案分支要跟着调整）。
  - 影响面：`AiModelConfig` 不再产出 `ChatClient`/`ChatModel` 单例 ⇒ `ResilientChatService` 构造签名由 `(ChatClient, ChatModel, ...)` 变为 `(ProviderRegistry, ...)`，**3 个直接构造它的测试文件要改**（见 §5 回归面）。
- 备选 **B：保留 conditional、判据扩为"env 有 key 或 DB 有可用 provider"** —— 少改测试，但条件里读库（表不存在即异常）是脆弱设计，且"DB 改了但进程没重启"时条件已固化，等于把热生效挡在门外。**不建议**。

**每请求解析与 option 组装**
- 解析顺序（模型）：请求体 `modelId` > `ai_model.is_default` > `ai_setting['default.modelId']` > env `AI_MODEL`。
- 参数三层（调研 §2.2）：单轮请求 > 会话级（前端 sessionStorage，随请求带） > 全局默认（`ai_setting`） > 模型/环境缺省。`allow.userParams=false` 时后端忽略单轮/会话参数（只认全局），并在响应里标 `paramsLocked=true`（i18n 文案键）。
- 能力位硬约束：选中模型 `supports_tool_calling=false` ⇒ `toolCallbacks` 不下发、`internalToolExecutionEnabled=false`，本轮退化为纯问答；提示由**前端**按能力位先置灰/黄条（不新增 SSE 帧类型，见 §4）。
- 续跑一致性：`RunSnapshot` 增 `providerId` / `modelId`（additive，旧快照缺省 null ⇒ 用当前默认并 WARN 一次）；`buildResumedPrompt`/`driveResumed` 从快照取；provider 已删/停用 ⇒ `POST /api/ai/runs/{runId}/resume` 返回 **409 `PROVIDER_GONE`**（不静默换模型续跑，否则历史被污染、`done.model` 也会说谎）。

## 9. 风险与边界

- **KEK 单点**：KEK 丢失 = 所有 DB key 不可用（fail-closed，不明文降级）。缓解：README 强制备份 + `/health` 显式报 `KEY_UNREADABLE`。轮换（多 kid）挂账。
- **多实例配置一致性**：版本号走 Redis；Redis 不可用时退化为本地版本 ⇒ 多实例下可能出现"实例 A 已换模型、实例 B 仍用旧模型"。登记为**知悉风险**，由 B23L1 批③ 的 Redis 设施收口。
- **strict seed 的运维惊讶**：表非空后改 env 无效，是**刻意设计**；README + 设置页「来源」标签 + `/health` 的 `source` 三处明示，避免"我改了 env 怎么没用"的排障泥潭。
- **能力位靠人工录入**：`supports_tool_calling` 手填错了，会导致"该带工具却没带/不该带却带"。缓解：默认 true（保守于"能用"），UI 标注"错误标注会导致工具调用失败或 400"；不做自动探测（探测本身要发真实请求，成本与副作用不可控）。
- **SSRF 与合规**：允许管理员填任意 URL 本质上是"让应用去打内网"；默认禁私网 + 显式开关 + 只允许 http/https，是取舍而非根治。若将来对外网开放部署，需加白名单（登记为后置项）。
- **H2 并发**：配置写路径是低频人工操作，不涉及并发优化；但**读路径每请求只读内存快照**，不得退化成"每轮查两张表"（否则 AI 热路径多 2 次 DB 往返）。
- **`AiAvailability` 语义扩展**：从"env 有 key"变成"有可用 provider"，`reason()` 文案与 code 可能变化 ⇒ 前端降级提示与 E2E 断言要同步（`types/ai.ts:101` 的 code 注释、`AiController.java:830-832`）。
- **不做**：多 provider 故障转移（一个模型挂了自动切另一个）—— HITL 场景下静默换模型等于换掉"谁在决策"，明确不做。

## 10. 待裁选项（A/B + 建议）

| # | 议题 | A | B | 建议 | 理由 |
|---|---|---|---|---|---|
| 1 | 加密方案 | Jasypt（`jasypt-spring-boot-starter`，`ENC()`） | 自管 AES-256-GCM（JDK 内置） | **B** | 需求是字段级 + 指纹 + last4 + kid，Jasypt 仍要包一层；零新依赖，避免依赖裁决；算法可控、AAD 可绑行 |
| 2 | 生效方式 | 启动期读 DB（改配置需重启） | 运行时快照 + 版本号热生效 | **B**（种子/KEK 除外，见 §3.4） | 调研 §3.1b 已定"改 provider 无需重启"；重启成本对本项目是真实痛点（会话/挂起轮在飞） |
| 3 | 模型列表来源 | 硬编码清单 | 拉 `/models` + allowlist + 手填兜底 | **B** | 业界三家组合才是主流（调研 §0-3）；DeepSeek 可自动发现，自建网关大概率不支持 ⇒ 手填是必需项 |
| 4 | provider 并存 | 多 provider 同时 enabled，各自模型都可选 | 单活跃（全局只允许一个 provider 启用） | **A** | 并存是"自定义端点 + 官方端点"共存的唯一表达方式；"单活跃"只是 A 的一个配置特例（其余 disable），不需要单列模型 |
| 5 | env key 是否落库 | 种子时把 env key 加密落库（DB 自洽） | 种子只记 `key_ref=ENV`，不落密文 | **B** | 不把运维手里的 env 复制进 DB，泄露面更小；"env 只作种子"语义自洽；用户在 UI 更新密钥后才 `key_ref=DB` |
| 6 | 装配闸处置 | 移除 conditional，无条件装配 + 动态 availability | 保留 conditional，判据扩为 "env OR DB" | **A** | 条件求值早于 Flyway，读库不可靠；A 的对外行为与今天 503 完全一致，只是把判空挪到调用时 |
| 7 | 续跑遇到 provider 已删 | 跟随快照，provider 没了就 409 | 静默用当前默认模型续跑 | **A** | 静默换模型会污染历史与 `done.model`，HITL 场景不可接受 |
| 8 | key 指纹算法 | 裸 SHA-256(key) | HMAC-SHA256(KEK, key) 截断 | **B** | 指纹是运行时缓存键，不能变成"无 KEK 也能做离线字典"的口子 |
