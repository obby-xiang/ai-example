## 1 N2：上游错误正文的日志收敛（敏感隐去 + 单行限长）

**问题**：`describeForLog` 对 `WebClientResponseException` 直接拼 `getResponseBodyAsString()` —— 上游 401 的 body 里常带完整 key，400 的 body 可能是任意长度的多行 JSON。该文本只进日志/台账（用户面走白名单短句），但**日志本身**就是暴露面：凭据泄进日志、`\n` 让一条错误日志伪造出多行、超长正文把日志撑爆。

**根因**：body 进日志是**逐点拼接**，没有统一收敛点 —— 想加隐去/限长就得在每处调用点重复实现，很容易漏；且「先截断再判敏感」会让落在 1024 之后的凭据漏网。

**修改**（`ResilientChatService.java:3388`–`:3437`）：

```java
private static final int LOG_BODY_MAX_CHARS = 1024;
...
return "上游返回 HTTP " + upstream.getStatusCode().value() + "："
        + loggableBody(upstream.getResponseBodyAsString());

private static String loggableBody(String body) {
    if (body == null || body.isEmpty()) { return ""; }
    if (ExcerptGuard.sensitive(body)) {
        return "[敏感正文已隐去，原长 " + body.length() + " 字符]";
    }
    String singleLine = body.replaceAll("\\R", " ");
    if (singleLine.length() <= LOG_BODY_MAX_CHARS) { return singleLine; }
    return singleLine.substring(0, LOG_BODY_MAX_CHARS)
            + "…(截断，原正文 " + body.length() + " 字符)";
}
```

| 件 | 语义 | 锚点 |
|---|---|---|
| 判定顺序 | **先对完整原文**判敏感，**再**折行/截断 —— 反过来会让尾部凭据逃过判定 | `:3429`（`sensitive(body)`）、`:3432`（`replaceAll("\\R", " ")`） |
| 命中即整段隐去 | 只留 `body.length()` 的字符数，**正文一个片段都不落**（不逐处掩码、不保留前后文） | `:3430`–`:3431` |
| 未命中则单行 + 限长 | `\R` ⇒ 空格（消灭换行伪造日志行）；超 1024 截断并标 **`原正文 N 字符`**（原长取截断前） | `:3432`–`:3436` |
| HTTP 状态保留 | 状态码在 `describeForLog` 拼接处，与 body 收敛互不影响 —— 隐去/截断都不丢状态 | `:3407`–`:3409` |
| 唯一收敛点 | 未命中调用的路径一律走这里：失败日志 `failLocked` 的 `log.error` 直接调 `describeForLog`（`:2253`）；尝试/重试链在 `:1018` 经 `asViolation`（`:1249`–`:1254`）把**同一份** `describeForLog` 文本挂到 `StreamViolationException` 上 ⇒ 失败与重试**同源**、无第二个 body 落地点 | `:3402`、`:3409`、`:2253`、`:1018` |

**边界**（连读）：

- **不恢复 DLP**：复用既有 `ExcerptGuard.sensitive`（只服务"反馈摘录能否原样入库"的冻结规则快照），**不是**那条已按用户裁定整套删除的输入/输出 DLP 管道；本组只借用它的"命中/未命中"一个判据。
- **只动日志面**：不改模型输出、不改用户错误文案（用户面仍 `messageFor(code)` 白名单）、不改 `StreamViolationException` 的 `code`、不改快照字段 —— `:2253` 的 `describeForLog(violation)` 与 `asViolation` 挂的诊断文本**只进日志/台账**。
- 隐去是**整段级别**（有/无两态）：命中即整条 body 不落，不做逐段脱敏；字符数保留只为可诊断"上游回了多长"。
- 1024 是**正文**上限（不含 `上游返回 HTTP nnn：` 前缀与截断标记），故整行实际长度略超 1024，仍远有界。

## 2 MI1 + MI2：`session→current` 的写与续期改为单键 Lua

**问题**（两处同形竞态）：

- `clearSessionCurrent`：读 current 判"是不是自己" → 算回退（可能要 `SMEMBERS` + 逐个反序列化快照）→ 最终 `DELETE` 或 `SET fallback`。这段窗口里同会话新轮可能已经把 current 换成自己 ⇒ **过期读** 会让终态轮删掉/覆盖**新轮的** current（新轮从此不被索引看到）。
- `renewSessionCurrent`：`GET` 读到是自己的旧值 → `EXPIRE`。中间 current 被新轮接管时，旧轮的心跳**把新轮的 TTL 续着**，索引寿命被已结束的轮拖着走。

**根因**：`GET → 比较 → 写`（或 `EXPIRE`）是三个往返，Redis 的串行语义只覆盖单条命令；比较结果在发出写命令时已经可能过期。**写侧判据必须是 Redis 内的原子读-比-写**，不能是 Java 侧算完再发。

**修改**（`RunStore.java:479`–`:545`、`:1274`–`:1400`）：三个单键脚本 + 三个私有包装，写入路径全部改走它们。

| 件 | 语义 | 锚点 |
|---|---|---|
| `SESSION_CURRENT_CAS_DELETE` | `GET == ARGV[1]` 才 `DEL`，返回 1/0 | 脚本 `:494`；包装 `deleteSessionCurrentIfOwned` `:1381` |
| `SESSION_CURRENT_CAS_SET` | `GET == ARGV[1]` 才 `SET KEYS[1] ARGV[2] PX ARGV[3]`，返回 1/0 —— **SET 自带 TTL**（`app.ai.session-ttl`），不额外发 `EXPIRE` | 脚本 `:516`；包装 `setSessionCurrentIfOwned` `:1392` |
| `SESSION_CURRENT_CAS_PEXPIRE` | `GET == ARGV[1]` 才 `PEXPIRE`，返回 1/0 | 脚本 `:537` |
| MI1 fast-path | 老会话回退命中 / 未命中后：无回退 ⇒ CAS-DELETE（`:1330`）；有回退 ⇒ CAS-SET（`:1333`） | `clearSessionCurrent` `:1314` |
| MI1 老会话回退 | 旧口径 `SMEMBERS + 逐个快照`得出 fallback 后同样走 CAS-DELETE / CAS-SET；**只有 CAS-SET 真的写成功**（返回 true）才 `markActiveRun` 回填活跃索引 | `:1362`、`:1364`–`:1368` |
| MI2 续期 | 保留前面那次 `GET` 作**快路径**（值明显不是自己就不发脚本），正确性由脚本内的比较兜底 | `renewSessionCurrent` `:1282`–`:1294` |

**为什么这样切**（连读）：

- **只碰 current 单键**：活跃 ZSET 不放进同一脚本 —— 键不带同槽 tag，Cluster 下会 `CROSSSLOT`；**多实例强一致不在本修范围**，本组只保证"current 这一个键的读-比-写原子"。
- **GET 只用于跳过昂贵计算 / 提前返回**，不作为写入判据：CAS 失败（返回 0）即"current 已归新轮"，**什么都不写**。
- CAS 失败时**不回填活跃索引**（`:1364`）：否则等于替一条已经不是 current 的轮记活跃。
- `renewSessionCurrent` 的异常降级不变：`catch (Exception)` 后只 `log.debug`，续期失败不影响本轮（租约/心跳的既有降级口径未动）。

## 3 N5：`/confirm` 的 `reason` 先归一化、再按归一后长度过闸

**问题**：`reason` 的 1024 长度闸量的是**原文**，而落进 pending、并**原样回灌模型**的是原文。两个后果：①用户粘了带零宽/全角填充的长文本（归一后完全合规）被判 400；②原文与会话里归一化后的文本口径不一致 —— 同一条自由文本在 `/chat` 归一、在 `/confirm` 不归一。

**根因**：闸门在归一化**之前**，且提交给确认门的是 `request.reason()` 原文 —— "被量长度的那份"与"真正落库/回灌的那份"不是同一个字符串。

**修改**（`AiController.java:634`–`:649`、`:669`–`:670`）：

| 件 | 语义 | 锚点 |
|---|---|---|
| 先归一 | `InputSanitizer.Result sanitizedReason = this.inputSanitizer.sanitize(request.reason())`（与 `/chat` 同一个 bean） | `:638` |
| 观测日志 | `changed()` 时只记 **长度差 + 剥离的格式/控制字符计数**，**不打印原因原文**（原因可能含敏感数据） | `:639`–`:644` |
| 空 / 纯不可见 | `StringUtils.hasText(...) ? text : null` ⇒ 交给确认门走其默认「用户在确认门中批准/拒绝」文案 | `:645` |
| 闸门 | 量的是 `reason`（**归一后**）；超长回 `REASON_TOO_LONG` + `length`（归一后长度）+ `limit` | `:646`–`:648`、`:1588`–`:1590` |
| 统一口径 | `confirmGate.submitDecision(..., reason)` 传归一后文本 ⇒ 存储 / 响应 / 模型回灌同一份 | `:669`–`:670` |

**连带注释同步**：`InputSanitizer` 的「作用域与 fail-closed 边界」由"只处理 message"改为"处理自由文本：`/chat` 的 `message` 与 `/confirm` 的 `reason`"，并写明 `/frontend-tool-result` 载荷**仍无**归一化（`InputSanitizer.java:30`、`:44`–`:48`）；`ConfirmRequest` 的 `reason` 参数注释由"会原样回填"改为"经输入归一化后回填"（`ConfirmRequest.java:9`）。

**边界**（连读）：

- **不改 `ConfirmGate`**：三态判定、默认文案、`REASON_TOO_LONG` 的 400 形状都不在改动面；本组只改"进去之前"的文本。
- 归一 = `InputSanitizer` 既有口径（NFKC + 剥格式/控制字符 + 收敛到不动点），**未新增规则**；`/frontend-tool-result` 仍未归一化，本类存在**不代表**全入口已受控。
- 归一后变空（原文只有零宽/空白）⇒ `null`，**不是**空串落库；下游按"无原因"处理。
- 归一化会让**部分**超长原文变成合规（这是本组的意图），但归一后仍超长的一律按**归一后长度**拒绝（不会因归一化放宽上限）。
