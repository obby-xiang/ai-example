# 一、上下文压缩 / 摘要

## 1.1 CLI / IDE 编程 agent：压缩是标配，且是分层的

**事实（★★★）** Claude Code 官方把 auto-compact 定义为可配置窗口：`/autocompact 500k`、`autoCompactWindow` 设置、`--autocompact` 标志、`CLAUDE_CODE_AUTO_COMPACT_WINDOW`，取值范围 100K–1M。默认阈值**按模型而定**，不是一个固定百分比：

| 会话形态 | 压缩触发点 |
|---|---|
| 原生 1M 窗口模型（Fable、Sonnet 5+、Haiku 5.5、Opus 4.7+） | 约 **967K** 默认（≈96.7%） |
| Sonnet 4.6 / Opus 4.6 未开扩展上下文 | **200K 边界** |
| 云会话 | 接近模型上限时 |
| 不认识的 model ID（网关别名） | Claude Code 假定的窗口 |
| 关掉 auto-compact | 到 200K 直接以 context-limit error 停止 |

来源：[Model configuration — Default auto-compact thresholds](https://code.claude.com/docs/en/model-config)

**事实（★★★）** 压缩本身是"摘要替换历史 + 部分内容从磁盘重新注入"。官方列出压后存活表：系统提示与 output style 仍生效；项目根 `CLAUDE.md`、auto memory、plan 从磁盘重注；`paths:` 作用域规则和子目录 CLAUDE.md 按需重载；**最近读/改过的文件重读最多 5 个**（单文件超 5,000 tokens 只留路径引用）；skill 正文重注有 5,000/25,000 tokens 上限，超了从最旧的开始丢；hook 加的内容跟会话一起被摘要掉。来源：[Explore the context window](https://code.claude.com/docs/en/context-window)

**事实（★★）** 源码解剖类论文给出了更硬的数字：Claude Code 在"进入模型有效窗口以下 13,000 token 缓冲"时触发（`AUTOCOMPACT_BUFFER_TOKENS = 13 000`），流程是剥图 → 按 API round 分组 → LLM 摘要 → 插入 `SystemCompactBoundaryMessage`；压后恢复最多 5 个文件、预算 `POST_COMPACT_TOKEN_BUDGET = 50 000`，skill 截到每 skill 25,000。同一篇把七家 harness 的阈值横向列出：Gemini CLI **50%**（保留最近 30% 原文 + 双遍自检）、Hermes 50%−max_tokens（64K 下限）、Pi 窗口−16,384、Codex 走 `model_auto_compact_token_limit`、OpenCode 拖到接近上限。来源：[Anatomy, Architecture, and Evolution of Coding Agents (arXiv 2609.00006)](https://arxiv.org/html/2609.00006)

**事实（★★）** Codex 侧：官方支持服务端 compaction（`POST /v1/responses/compact`，客户端拿到不可读的加密 blob；Responses API 也可设阈值自动压）。`model_auto_compact_token_limit` 未设置时**按窗口的 90% 派生**，且用户设的值超过 90% 会被静默 clamp 到 90%。来源：[OpenAI Compaction guide](https://developers.openai.com/api/docs/guides/compaction)、[arXiv 2609.32961 引用 Codex config reference](https://arxiv.org/html/2609.32961v1)、[codexinsider: model_auto_compact_token_limit](https://codexinsider.com/config/model-auto-compact-token-limit/)（★）

**事实（★★★+★）** Kimi Code CLI：官方文档只说"对话变长时在上下文接近窗口上限时自动压缩历史消息"，支持 `/compact` 并可附带指引（`/compact 保留与数据库迁移相关的讨论`），另有 `/clear`、`/fork`。来源：[Kimi Code CLI 会话与上下文](https://moonshotai.github.io/kimi-code/zh/guides/sessions.html)。第三方源码分析给出具体参数：`compaction_trigger_ratio` 默认 **0.85**（0.5–0.99）、`reserved_context_size` 默认 **50 000**、通常保留最近 2 条：来源 [kimi-cli 演进全景](https://blog.gitcode.com/62f87083aca26098c3f31aa700453497.html)（★）

**事实（★★★）** API 层面，Anthropic 把上下文治理拆成四种原语，阈值全部可配：`clear_tool_uses_20250919`（**默认 trigger 100,000 input tokens**、默认保留最近 **3** 组 tool use、`clear_at_least` 保证每次至少清够、`exclude_tools` 白名单、`clear_tool_inputs`）、`clear_thinking_20251015`、服务端 `compact_20260112`、SDK 端客户端 compaction（默认 `context_token_threshold = 100,000`，摘要模板含 Task Overview / Current State / Important Discoveries / Next Steps / Context to Preserve）。来源：[Context editing](https://platform.claude.com/docs/en/build-with-claude/context-editing)、[Compaction at a token threshold](https://platform.claude.com/docs/en/build-with-claude/compaction-threshold)

**事实（★★★）** Anthropic 官方给出的长时域三件套：**compaction（摘要重开）+ structured note-taking（窗口外文件记忆）+ sub-agent 架构（各自独立窗口，只回 1–2K tokens 结论）**，并明确"context rot"（token 越多，召回越差）是压缩的根本理由。来源：[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)

## 1.2 滑动窗口 vs 摘要式 vs 混合

**事实（★，但分类学本身有用）** 一篇中文综述把业界做法拆成八类：A 工具输出剪枝、B 明文 LLM 交接摘要、C 服务端加密 compact、D 训练式自摘要（Cursor Composer）、E 结构化状态快照（Gemini CLI 七段强制字段 + probe）、G 非破坏隐藏 + 结构回注（Roo condensation，可 rewind）、H 事件存储型擦除（OpenHands）、F 隔离与外置（子 agent / 新会话 / 文件记忆）。**主流是"主路径 + 辅路径"，多数产品叠用 2–3 种**。来源：[长会话一压就失忆？先分清这八种上下文压缩](https://www.51cto.com/article/852012.html)

**推断** "纯滑动窗口截断"已经不是主流主路径，只剩降级/failure fallback（Gemini CLI 快照失败退截断、Roo 失败退滑动截断，见上）。主流是**混合**：先无 LLM 剪枝（便宜）→ 再 LLM 摘要（贵，留到最后）→ 保留近期原文尾巴 → 压后回注文件/结构。

## 1.3 触发阈值惯例：纠正一个常见误解

**推断（基于上述官方数据）** 题目里"92%/95% 容量"的传闻**不成立于官方文档**。官方口径是**按模型/配置定的 token 边界**（Claude Code 1M 窗口 967K；Codex 90%；Sonnet/Opus 4.6 是 200K 边界）。真实分布比"95%"宽得多：

| 触发点 | 产品 |
|---|---|
| ~50% | Gemini CLI、Hermes |
| ~80% | Copilot CLI（★二手） |
| ~85% | Kimi CLI（`compaction_trigger_ratio`） |
| ~86–92% | Roo Code（★） |
| 90% | Codex（未配置时的派生值）|
| 96–99% | OpenCode |
| ~96.7% | Claude Code 1M 窗口 |

同时**社区共识是"别等那么晚"**：多篇社区文章主张在 50–60% 主动 `/compact`，理由是 90%+ 才压，摘要在噪声里找重点、质量更差。来源：[mindstudio.ai](https://www.mindstudio.ai/blog/claude-code-compact-command-context-management)、[Level Up Coding](https://levelup.gitconnected.com/why-i-compact-my-ai-coding-agent-at-20-not-90-1a665c0c4e5d)（★）。反面成本：全文摘要会打碎 KV cache，一次约 12.5 万 token 的压缩约等于 20 多次暖缓存跟轮，所以"50% 就狂压"会把缓存红利吐回去（[51CTO](https://www.51cto.com/article/852012.html)，★）。

**事实（★★）** ACP（Agent Client Protocol）已在 **2026-06-05 把 session usage 定为 Completed 并稳定**：agent 通过 `session/update` 推送 `usage_update{used, size, cost?}`，明确"客户端自行算 remaining/percentage""cached tokens 也算占位""没有意义的窗口就干脆不发"。**这就是业界"向后端/前端暴露 usage"的事实标准**，并且它给了推荐分档：

| 使用率 | 建议行为 |
|---|---|
| <75% | 正常 |
| 75–90% | 黄色指示，提示"context 快满了" |
| 90–95% | 橙色，建议"开新会话或摘要" |
| >95% | 红色，警告"下一条可能失败，建议交接" |

来源：[ACP RFD — Session Context Size and Cost](https://agentclientprotocol.com/rfds/session-usage)

## 2.2 消费级网页产品：基本不暴露

**事实（★★）** ChatGPT 网页不显示 token 用量或上下文余量；只有社区持续提 feature request 要求"接近上限前给警告""加进度条"，说明**当时并不存在**。来源：[请在上限前警告用户](https://community.openai.com/t/please-warn-users-before-a-long-chatgpt-conversation-reaches-its-context-limit/1400941)、[上下文容量指示器与新会话接力](https://community.openai.com/t/feature-request-conversation-context-capacity-indicator-and-seamless-handoff-to-a-new-chat/1401664)、[加进度条](https://community.openai.com/t/add-a-context-limit-progress-indicator-in-chatgpt/1384047)。Claude 网页同理，需要第三方扩展才能看到"上下文表"（★ [ai-toolbox 的 context window meter](https://www.ai-toolbox.co/ai-toolbox-claude-features/claude-context-window-meter-2026)）。

**事实（★★★）** 网页端**有**的是"记忆层"的可视化，不是"上下文层"：ChatGPT 的 Memory summary / Saved memories 可在设置里读、改、删，回答下方可显示 **Sources**（哪条过去会话/记忆/文件影响了这次回答）；Claude 的 Settings → Memory 列出 Topics，可编辑删除，检索过去的会话时显示**引用出处**并可跳回原对话。来源：[Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)、[Use Claude's chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)

## 2.3 API 侧惯例

**事实（★★）** `usage` 对象（input/output/缓存读写）是通例，但流式下**不一定默认给**：OpenAI 形状需要 `stream_options: {"include_usage": true}`，用量落在最后一块；Anthropic 在 `message_start` / `message_delta` 报；Anthropic 另有免费的 `count_tokens` 端点可预览"压缩后会剩多少 token"。来源：[Streaming Responses（Requesty 文档）](https://docs.requesty.ai/features/streaming)、[Tracking token usage across OpenAI, Anthropic, and Gemini](https://dev.to/spanlens/tracking-token-usage-across-openai-anthropic-and-gemini-every-streaming-gotcha-i-hit-4mf3)、[Context editing 文档中的 token counting 一节](https://platform.claude.com/docs/en/build-with-claude/context-editing)

# 三、记忆分层

**事实（★★★）** Anthropic 官方给的分层命名最清晰，可当通用骨架：

1. **窗口内（短期）** = compaction 摘要，只服务当前对话连续性；
2. **窗口外文件（工作/长期）** = structured note-taking / memory tool，agent 自己写、按需读回；memory tool 是**客户端文件协议**（view / create / replace / insert / delete），存储归你；
3. **跨会话检索（长期）** = RAG 式检索历史会话；
4. **隔离** = sub-agent 用干净窗口，只回摘要（严格说不是压缩，是"别让历史挤进这一窗"）。

来源：[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)、[Memory tool](https://platform.claude.com/docs/en/agents-and-tools/tool-use/memory-tool)

**事实（★★★）ChatGPT memory 是"两套机制 + 多来源"**：
- **Saved memories**：显式条目，可搜索、排序、自动优先级、版本历史；删了原对话不会自动删这条记忆；
- **Reference chat history**：隐式，ChatGPT 自己从历史里挑，会随上下文变化（**没有单独的存储上限**）；关掉后 30 天内清除；
- 还有 custom instructions、Library 文件、连接应用（如 Gmail）；
- **Project-only memory**：可把记忆限定在某项目内，项目外互不可见（企业/健康版默认关闭）；
- 临时对话（temporary chat）不创建也不更新记忆。

来源：[Memory in ChatGPT](https://help.openai.com/en/articles/8590148-memory-in-chatgpt)

**事实（★★★）Claude memory 是"主题化 + 项目隔离 + 统一到 Cowork"**：新版是**边聊边存 Topic**（不是会话结束后总结），可"remember this"显式写入，改一个 topic 会在之后所有会话生效；**每个 Project 有独立记忆空间和项目摘要**；chat 与 Cowork 共用一份记忆；过去的会话检索走 RAG 并以 tool call 形式出现在对话里；有 incognito chat 和"单聊关闭 memory"两种排除方式。旧版描述里是"每 24 小时合成一次记忆摘要"。来源：[Claude 帮助中心 · chat search and memory](https://support.claude.com/en/articles/11817273-use-claude-s-chat-search-and-memory-to-build-on-previous-context)

**事实（★★★）** Claude Code 明确分成**"人写的" vs "Claude 自己写的"**两套并存记忆：`CLAUDE.md`（你写，项目/用户/组织多级作用域，建议 <200 行，>4MiB 跳过）与 **auto memory**（Claude 自己记四类：user / feedback / project / reference，存在 `~/.claude/projects/<project>/memory/`，`MEMORY.md` 作索引，**每次会话只加载前 200 行或 25KB**，话题文件按需读）。关键一点：**两者都不进系统提示**，是作为 user message 注入的"上下文而非强制配置"。来源：[How Claude remembers your project](https://code.claude.com/docs/en/memory)

**事实（★★）** 源码研究给出的横向对比很有信息量：Codex 是**最自主**的（后台两阶段从 rollout 抽取结构化记忆 → consolidate 到 `~/.codex/memories/`，由沙箱内 sub-agent 做，带引用追踪与使用频次排序）；Gemini CLI 反向走**人类审核 inbox**（抽取后产出 patch 到 `.inbox/`，用户 `/memory` 审阅应用）；Hermes 故意做得极小（`MEMORY.md` 2,200 字符 + `USER.md` 1,375 字符，**冻结快照**以免破坏 prompt cache），跨会话靠 SQLite FTS5 的确定性检索，"全程无 LLM 调用"；**整份语料约 400 万行代码里，没有任何 agent runtime 用向量嵌入检索代码**。来源：[Anatomy, Architecture, and Evolution of Coding Agents (arXiv 2609.00006)](https://arxiv.org/html/2609.00006)

**推断** 业界的"记忆分层"实际是两轴，不是三轴：**轴一 = 谁在写（人 / 模型 / 模型+人审）**，**轴二 = 何时进上下文（每次加载 / 按需读 / 检索命中）**。"短期/长期/工作记忆"这种教科书三分并不对应产品实现。

# 四、长对话体验标配（用户可见行为）

| 产品 | 接近上限时用户看到什么 | 证据 |
|---|---|---|
| **Claude Code / Codex / Kimi CLI / Gemini CLI** | 可见用量或百分比 → 到阈值自动压缩（可能无提示）→ 可手动 `/compact`；关掉自动压缩则报 context-limit error 并提示 `/compact or /clear` | ★★★ / ★★ |
| **Claude 网页版** | 到了长度上限直接报错（"Claude hit the maximum length for this conversation"），必须开新对话；**没有**上下文余量指示；Projects 让每个新对话都带 fresh 200K + project knowledge + project memory | ★★（[Reddit 实测帖](https://www.reddit.com/r/ClaudeAI/comments/1jfrym1/the_max_conversation_length_on_claudeai_is_less/)、[Claude hit the maximum length 修复指南](https://limitededitionjonathan.substack.com/p/ultimate-guide-fixing-claude-hit)、★[gigarag](https://gigarag.com/blog/claude-maximum-length-conversation-fix)） |
| **ChatGPT 网页版** | 单条过长报 "Message too long"；整段过长时模型"忘掉"早期内容（静默丢 oldest），到点提示开新会话；**无**剩余量指示 | ★★（[HackerNoon 解释](https://hackernoon.com/ai-tokens-how-they-work-how-to-count-them-and-how-to-stop-wasting-them)、[Community 请求加警告](https://community.openai.com/t/please-warn-users-before-a-long-chatgpt-conversation-reaches-its-context-limit/1400941)）；"静默丢最早消息"具体机制为**推断** |
| **Kimi 网页版** | 差异化做法：输入时可显式选**「对话长度：超长」**（K3 的 100 万 token 上下文，需最高档会员）；上下文过长会提示并建议新建对话 | ★★★ [Kimi 会话常见问题](https://www.kimi.com/help/others/chat-issues)、[Kimi Claw 对话限制](https://www.kimi.com/help/kimi-claw/conversation-limits) |
| **DeepSeek 网页版** | 有"对话长度超限"的官方/半官方说明与用户绕行方案（让 AI 先总结，再贴进新会话），未见可见余量指示 | ★（[太平洋电脑网](http://g.pconline.com.cn/x/1906/19061197.html)、[CSDN](https://blog.csdn.net/wei741094234/article/details/156359738)）证据弱 |
| **Gemini / Copilot / Cursor** | IDE/CLI 有指示（见 §2.1）；网页端与 ChatGPT 类似，无上下文仪表 | ★★ |

**推断（较强的模式总结）** 长对话的"标配"分界非常清楚：

- **凡是 agent/CLI/IDE 场景 → 用量可见 + 自动压缩 + 手动压缩**，因为用户是专业人士、且上下文爆炸会直接烧钱；
- **凡是消费级对话场景 → 不给余量指示，只在失败时报错并建议开新会话**，唯一例外是 Kimi 把"对话长度"做成显式选项（把复杂度交给用户主动选择）；
- **共同点是"静默降级"不存在于合规敏感场景**：Anthropic/OpenAI 在 API 文档里都强调摘要是有损的（"任务需要精确回忆早期细节时不适合 compaction"）。

# 五、主流聊天产品功能标配清单

**事实（★★，含官方/一手描述）** 一篇 UX 综述给出聊天产品的**最小必需集**：重新生成（regenerate）、编辑用户消息并重发（edit & resend）、**undo 或 branch 二者之一**；并给出现状对比：ChatGPT 有 regenerate-with-model-choice 与编辑，主界面**无**分支；Claude.ai 的 regenerate 是"1 of N"分页器（保留之前的回答），有编辑，主界面**无**分支；Cursor 的 agent 模式把分支做成一等公民。来源：[Regenerate, Undo, Branch — Conversation Mechanics](https://thepromptbench.com/ai-product-ux/regenerate-undo-branch-conversation-mechanics/)

**事实（★★）** 分支在消费级产品里是**隐式存在、显式缺失**：ChatWidget/ChatTree 这类扩展的卖点正是"ChatGPT / Claude / DeepSeek / Kimi 每次编辑或重新生成都产生新分支，但界面只给你 `< 1/2 >` 箭头"。来源：[ChatTree（Chrome 商店）](https://chromewebstore.google.com/detail/chattree/jpgdlfibomodhhhlgmojinojgelikidc)

**事实（★）** 2026-03 起 ChatGPT 把"编辑任意消息"收紧为**只能编辑最后一条用户消息、只能重试最后一个回答**（无公告）。来源：[ChatGPT Quietly Restricts Message Editing](https://aiproductivity.ai/news/chatgpt-restricts-message-editing-retry/)

### 标配 vs 分化项（推断 + 上列证据）

| 功能 | 判定 | 说明 |
|---|---|---|
| 重新生成 | **标配** | 所有主流产品都有；差异只在"旧回答是否保留"（Claude 用分页器，ChatGPT 直接替换） |
| 编辑并重发 | **标配** | 但"能编辑多早的消息"在分化（ChatGPT 2026 收紧到只允许最后一条） |
| 点赞/点踩反馈 | **标配** | ChatGPT / Claude / Gemini 三家的 UI 都有 |
| 会话列表 + 搜索 | **标配** | 消费级产品都有 |
| 导出 | **标配** | 消费级走"数据导出"；CLI 侧 Kimi 有 `/export-md`、`kimi export` ZIP |
| 停止生成 / 复制 / 流式 | **标配** | — |
| 隐式分支分页（`< 1/2 >`） | **准标配** | ChatGPT / Claude / DeepSeek / Kimi 都有，但都没有树视图 |
| 真分支树 / fork | **分化项** | Cursor agent、Pi（`/tree` + `fork` + `clone`）、Kimi CLI `/fork` 有；ChatGPT/Claude 主界面没有 |
| 撤销 / 回退 | **分化项** | Roo 可 rewind、Claude Code `/rewind`、Mistral Vibe checkpoint；多数消费级产品**没有** undo（Prompt Bench 明确指出"大多数产品跳过了 undo，但不该跳过"） |
| token 用量 / 上下文剩余指示 | **分化项（按场景）** | CLI/IDE ≈ 标配；消费级网页 ≈ 普遍没有 |
| 手动压缩入口（`/compact`） | **分化项** | CLI 普遍有；消费级网页几乎没有 |
| 记忆管理 UI | **分化项** | ChatGPT / Claude 有完整查看-编辑-删除；DeepSeek / Kimi 侧弱或没有 |
| 跨会话检索 | **分化项** | Claude（search past chats，RAG + 引用）、ChatGPT（reference chat history）有；其余少见 |
| 重新生成时换模型 | **分化项** | ChatGPT 支持；Claude.ai 历史上没有 |

# 六、对一个"内网 AI 辅助配置平台（页签即会话、关页签即弃）"最值得借鉴的 5 条

> 以下 5 条**全部是推断**（基于上述事实做的迁移设计建议，不是任何厂商的官方主张）。

1. **把"页签生命周期"直接绑定到 token 预算，并把用量做成可见的一等 UI。** 既然没有跨会话持久记忆，"页签内的上下文"就是用户唯一的记忆载体，静默降级等于丢工作。建议直接采用 ACP 的分档着色（75% 黄 / 90% 橙 / 95% 红 + 建议动作），并把 `used/size/cost` 作为会话级字段暴露给后端——这套契约已被协议标准化，且不与任何厂商绑定。依据：§2.1 ACP RFD；§4 消费级"无指示→到点报错"是最被诟病的体验。

2. **压缩走"阶梯"，不要一上来就全文摘要。** 顺序：① 清/截断陈旧工具输出与日志（无 LLM 成本）→ ② 保留最近 k 轮原文尾巴 → ③ 全文结构摘要（带 focus/hint 参数）。Anthropic 的 `clear_tool_uses` 默认参数（trigger 100K、keep 3、exclude_tools 白名单）可以直接照搬为默认值。依据：§1.1 Claude Code microcompact→full compact 的两层结构、arXiv 源码研究的七家对照。

3. **默认阈值调早（建议 80%±5，且允许用户调），并给一个"现在就压缩"按钮。** 官方默认值（Claude Code 967K/Codex 90%/OpenCode 96–99%）被社区一致认为"压晚了"；但也不要 50% 就狂压——全文摘要会打碎 prompt cache。Gemini CLI 的 50%、Kimi 的 0.85 是这个区间的两端参考。依据：§1.3 阈值分布表 + 缓存成本。

4. **把"关页签"从"丢弃"改造成"留下最小可恢复状态"。** 内网平台不该指望用户自己复制交接文档。可选做法：接近上限或即将关闭时自动生成一段**交接摘要**（进度 / 改动面 / 坑 / 下一步），并允许用户一键把它作为新页签的首条消息回填；技术上等价于 Codex/Mistral Vibe 的 "compaction envelope 重注原始目标" 与 Roo 的非破坏隐藏（原文保留、可恢复）。依据：§1.2 G/H 类做法；§4 消费级"开新会话 + 手贴总结"是当前最普遍的土办法（DeepSeek 用户社区的做法）。

5. **重生成 / 编辑重发 / 撤销（或分支）三件套一起上，缺一个用户就会死在一句没写好的提示上。** 这是 Prompt Bench 给出的"最小编辑机制集"，且成本不对称：regenerate 最便宜（前缀缓存仍有效），编辑越靠前的消息越贵。对一个"页签即会话"的平台，**undo 比 branch 更划算**（实现只需保留一份前一状态），branch 可作为高级手势后置。依据：§5 编辑机制成本模型 + Cursor/Pi 的分支实践。

**一条附带的架构提示（推断）**：如果将来要加跨页签记忆，优先选**文本/文件式记忆**（`CLAUDE.md` + `MEMORY.md` 索引那一套：人写的规则和模型自己记的笔记分开放、限制载入体积、可读可编辑），**不要先上向量库**——400 万行生产 harness 代码的研究结论是那里没有任何一家用向量嵌入做检索，跨会话召回普遍用 SQLite FTS5 这类确定性检索。依据：[arXiv 2609.00006](https://arxiv.org/html/2609.00006)、[Claude Code memory 文档](https://code.claude.com/docs/en/memory)。
