## 1. 结论先行

当前代码可以静态证明一条跨来源身份断裂链：

1. 实时 SSE 使用稳定的 `messageId = assistant-{runId}`。
2. 后端 transcript 已有稳定 `entryId` 和带归档 `seq` 的 `segments`，但 `/api/ai/history/{sessionId}` 当前没有把 `entryId` 透出，前端 `AiHistoryMessage` 也没有该字段。
3. 历史展示消息改用 `history-{数组下标}`；在空白条目处理和 tool/TOOL 配对闸通过后，同 run 的连续 ASSISTANT 才合并为一个 UI 消息。
4. `mergeMirrorInFlightRound` 只用消息 `id` 和 `toolCallId` 匹配镜像助手；纯文本助手没有工具强身份可供回退匹配。
5. 未匹配的镜像助手会被克隆并插入历史结果。

因此，**同 run 的权威历史已经合成一条，而镜像仍保留多条或不同进度版本时，存在整轮重复且两个版本内容不同的静态可证风险**。这不是“已经动态确认的唯一根因”。后端重复落账、SSE 重放、快照重复重建、DOM 投影以及它们与镜像合并的组合，仍需同一故障会话的四层证据排除。

### 2.2 代码事实

本文第 3～5 节列出的类、方法、字段、条件分支和调用顺序均直接来自当前工作树源码。静态阅读可以证明“某条路径存在、某字段未映射、某分支会克隆”，不能证明某次用户故障实际走过了该分支。

### 2.3 静态可证缺陷

- **身份传输缺口**：后端 `TranscriptEntry.entryId` 已存在，但 history API 映射遗漏它，前端类型也未声明，见第 3.2 节。

## 3. 恢复链逐项核对

### 3.1 实时 SSE：`assistant-{runId}`

`SseChatEmitter` 在构造时设置：

```text
assistantMessageId = "assistant-" + runId
```

依据：`backend/src/main/java/com/example/configmgr/ai/run/SseChatEmitter.java:664-667`、`:793-825`。该值写入正文 delta 和 `message_start/message_end`，见同文件 `:2823-2860`、`:2902-2922`。

前端 `ChatMessage` 另有 `messageId?: string` 字段，注释明确它接收 SSE 的服务端消息身份，见 `frontend/src/types/ai.ts:457-470`；`parts.ts` 在消息边界帧中写入该字段，见 `frontend/src/utils/parts.ts:859-875`。

需要避免一个概念混淆：前端本地新建消息时的 `ChatMessage.id` 仍可为 `a-{时间}-{随机}`，见 `frontend/src/stores/ai.ts:11984-12000`。因此 `assistant-{runId}` 是**实时协议及逻辑 UI 助手身份**，不能笼统声称当前所有 `ChatMessage.id` 都已等于它。

### 3.2 后端 entryId 已存在，但 history 当前未透出

`TranscriptEntry` 明确定义稳定 `entryId`，且 `segments[].seq` 是该段首帧的归档序号，见：

- `backend/src/main/java/com/example/configmgr/ai/history/TranscriptEntry.java:15-37`
- `backend/src/main/java/com/example/configmgr/ai/history/TranscriptEntry.java:115-124`

entryId 的现有生成形态包括：

```text
用户：{runId}:user
有工具 assistant：{runId}:assistant:{首个 toolCallId}
无工具多段 assistant：{runId}:assistant:text-{历史下标}
tool：{runId}:tool:{toolCallId}
```

依据：`backend/src/main/java/com/example/configmgr/ai/history/TranscriptEntries.java:159-184`、`:487-510`。

但是，`AiController.transcriptItem` 当前只放入 `type/text/runId/timestamp`，再按类型加入工具、段和状态字段，没有 `item.put("entryId", ...)`，见 `backend/src/main/java/com/example/configmgr/ai/web/AiController.java:2375-2409`。前端 `AiHistoryMessage` 同样只有 `type/text/segments/.../runId`，没有 `entryId`，见 `frontend/src/types/ai.ts:265-368`。

**结论：`(entryId, segments[].seq)` 是后端已经具备的持久化 part 身份素材，但不是当前前端 history 已可消费的身份。后续若用于跨来源对账，必须 additive 透出并同步类型，不能把它写成现有 API 能力。**

### 3.3 历史 UI：`history-{数组下标}` 与同 run 合并

`buildHistoryMessages` 为每个可见条目生成：

```text
id = history-{idBase + index}
```

并明确“不消费后端 messageId 作展示 id”，见 `frontend/src/stores/ai.ts:5458-5477`。该下标是原始历史数组下标；TOOL 条目虽被跳过，仍保留下标空洞。

随后，后置 pass **在空白条目处理和 tool/TOOL 配对闸通过后**，才把**同一非空 runId 的连续 ASSISTANT** 合并，见 `frontend/src/stores/ai.ts:5486-5591`。无正文、无思考且无失败事实的空白 ASSISTANT 会丢弃并断窗；带工具条目的每个 toolCall 必须在历史窗口内存在可配对的 TOOL 响应，任一项悬空则不合并、不吞掉该条目，也不开合并窗。遇 USER/SYSTEM、runId 缺失或变化同样断窗。满足这些条件并合并时：

- 保留首条的 `history-{首条原始 index}`；
- 将各成员 parts 顺次拼接并重排本地 `seg`；
- 工具仍靠各自 `toolCallId` 保持身份；
- 得到的是一个 UI 助手，而不是每个持久化 ASSISTANT 各一个 UI 助手。

因此，历史侧“满足合并条件的多个持久化条目 → 一个同 run UI 助手”是现有明确行为，不应被误读为后端只可能有一条 ASSISTANT，也不应忽略空白丢弃、断窗和 tool/TOOL 配对闸。

### 3.4 `mergeMirrorInFlightRound`：匹配与未匹配克隆

`loadHistoryInner` 先读取并归一镜像，再请求 history，构建历史消息后调用 `mergeMirrorInFlightRound`，见 `frontend/src/stores/ai.ts:4923-5023`、`:5079-5135`。

匹配合并的关键事实：

1. 只处理镜像在途轮，或需要保留的停止轮，见 `frontend/src/stores/ai.ts:5758-5778`。
2. 从镜像**最后一条 USER 之后**切片并筛选同 run 助手构成 `mirrorAssistants`；没有 USER 时 `mirrorUserIndex=-1`，即从镜像开头 `slice(0)` 筛选。历史同 run 助手构成 `roundTargets`，见 `:5771-5794`。
3. 首选 `message.id === source.id`；未命中再按 `toolCallId` 反查，见 `:5795-5816`。
4. 工具反查只遍历 tool parts；没有工具段时直接返回 `null`，见 `:3384-3410`。
5. 未匹配且 `seenIds` 不含该本地 ID 时，执行 `cloneMessage(source)` 并 `merged.splice(...)` 插入，见 `:5875-5915`。

### 3.5 为什么存在“整轮重复且版本不同”的风险

以下是一种**静态可达的风险组合**，不是本轮动态复现步骤：

1. 镜像在同一 run 下保留多条助手，或保留了比 history 更新/更旧的一组正文和工具卡。
2. 满足上述合并条件时，history 将同 run 的多个 ASSISTANT 合并为一个 `history-*` UI 消息。
3. 镜像消息的 `id` 与 `history-*` 不同；纯文本镜像助手又没有 `toolCallId` 可用于反查。
4. 一个或多个镜像助手因此未匹配，被克隆插入历史结果。
5. 最终同 run 同时存在“历史合并版”和“镜像克隆版”。两者来源进度不同，正文与卡片数量自然可能不同，而非简单逐字双份。

`seenIds` 只防止相同本地 ID 的重复插入，不能证明两个不同 ID 不是同一逻辑 run 的两份内容。`hasHistoryCoveredMirrorRound` 还使用正文/reasoning 前缀和工具 ID 判断覆盖，见 `frontend/src/stores/ai.ts:3341-3350`；它不能替代稳定 entry/part 身份，也不能证明非前缀正文关系。

### 3.6 普通 SSE 有序号防重，不能反推动态无重放问题

后端业务帧通过 `FrameStore.appendAndAllocateSeq` 取号并归档，再把真实 `seq` 写入帧，见 `backend/src/main/java/com/example/configmgr/ai/run/SseChatEmitter.java:3885-3915`、`:3961-3986`。

前端 `handleFrame` 对同 run 已记录的 `seq` 进行只增不减守卫，并对消息已应用 seq 去重，见 `frontend/src/stores/ai.ts:12149-12165`。这证明现有普通 SSE 幂等机制是 `seq`，不是 `eventId` 或正文前缀；但真实故障是否有跨宿主、全量恢复或快照路径绕过，仍为 **NOT_RUN**。

## 4. 现有身份公式与用途清单

| 对象 | 当前公式/字段 | 当前用途与边界 |
|---|---|---|
| 实时/逻辑 UI 助手 | `messageId = assistant-{runId}`；会话内还需 sessionId/runId 界定归属 | 实时 message_start/end 与 delta 的稳定消息身份；不要与本地 `ChatMessage.id` 混为一谈 |
| 持久化条目 | `TranscriptEntry.entryId` | 后端同 entryId 更新保持稳定；history 当前未透出 |
| 持久化 part | `(entryId, segments[].seq)` | `seq` 是段首帧归档序号，可表达同 entry 内段身份和顺序；前端当前拿不到 entryId |
| 历史展示 ID | `history-{idBase + index}` | 当前数组下标展示 ID，只适合 legacy 展示，不应作为跨实时/镜像/history 的业务身份 |
| 工具调用/工具 part | `toolCallId` | 历史 call/response 配对、实时工具段更新和镜像工具反查；缺稳定 ID 的调用不合成替代身份 |
| 普通 SSE 帧 | `seq`，按 runId 单调递增 | `lastSeq` 差量续传、同 run 与消息级重复帧幂等；心跳另有 heartbeatSeq |
| 已提交压缩事件 | `eventId` | 仅用于既有压缩事实幂等和排序；实时与 history 插入同 eventId 不重复 |
| 压缩事件生成形态 | `{runId}:c:{plan.atMs()}:{16 位 SHA-256 前缀}` | 当前生成见 `ContextCompactor.java:673-683`；应作为稳定 opaque ID 消费，不与普通 SSE seq 混用 |

压缩事件的前端去重直接检查 `part.eventId === event.eventId`，见 `frontend/src/utils/parts.ts:502-542`；实时 context 和 history events 都复用该机制，见 `frontend/src/stores/ai.ts:5594-5634`、`:12400-12421`。

## 6. 启动确认可复用的现有机制

静态调用链支持复用 `ToolPreflightService + HostForm.shouldPark + ConfirmGate.publishRequestsForParkedBatch`，不需要新事件框架。

### 6.1 预检

`ToolPreflightService.inspect(toolName, argumentsJson, context)` 是只读预检；`start_export` 属于支持范围。EXPORT 分支会检查任务存在、类型、在途作业、配置项、目标一致、权威 EXPORT 步骤和条件，见 `backend/src/main/java/com/example/configmgr/ai/gate/ToolPreflightService.java:260-352`。

后续宿主应以 `{"taskId":...}` 调用预检，只有 `report.pass()` 才可创建确认 pending。业务任务/作业/配置的只读预检属于业务边界，不等于把 AI 会话状态写入数据库。

### 6.2 pending 的必要形状

后续 `ExportStartForm` 创建条目时必须至少满足：

```text
toolCallId = host-start-export-{runId}-{taskId}
name = start_export
type = function
kind = CONFIRM
arguments = {"taskId":...}
status = PENDING（PendingToolCall 默认值）
pending.setPreflight(report.asMap())
```

`PendingToolCall` 的 `type/status` 默认值和 preflight 写口见 `backend/src/main/java/com/example/configmgr/ai/run/PendingToolCall.java:109-153`、`:258-317`。确定性 ID 还应配合 `hasIssued` 与既有 pending/ledger 防重。

**不得写 `KIND_BACKEND`。** `KIND_BACKEND` 表示后端直接执行而非确认挂起，见同文件 `:109-119`；`ConfirmGate.publishRequestsForParkedBatch` 也只发布 CONFIRM/FRONTEND，BACKEND 会被跳过，见 `backend/src/main/java/com/example/configmgr/ai/gate/ConfirmGate.java:659-689`。把启动条目写成 BACKEND 既不会形成所需确认卡，也破坏“批准前不得启动”的语义。

### 6.3 既有挂起和发布顺序

`HostForm.shouldPark` 复用 `shouldParkAll`，顺序为：

```text
saveSuspended
→ suspended 帧
→ ConfirmGate.publishRequestsForParkedBatch
→ completeSubscriptions
```

见 `backend/src/main/java/com/example/configmgr/ai/form/HostForm.java:133-213`。`ConfirmGate` 对 CONFIRM 调 `out.confirmRequest(pending)`，对 FRONTEND 调 `frontendToolRequest`，并先置请求已发标记，见 `ConfirmGate.java:659-689`。

因此，启动宿主只需构造正确的 CONFIRM pending 并调用 `shouldPark`，不应另写一套 SSE、恢复或决策 API。批准后仍必须复用既有后端执行、预检指纹复核和幂等台账；预检失败、拒绝、取消和未知结局不得启动或下载。
