## 0. 结论先行

1. **发射点密度很高，但全部是「运行态外置态」，不是「观测态」**。`ai:` 键族 27 个前缀（`RunStore:95-179`、`RedisFrameStore:63`、`FrameWakeBus:20`、`LeaseKeys:35`、`CancellationRegistry:45`、`AiRateLimiter:50`、`AiSessionService:36`、`SessionGate:42`、`AiConfigService:61`、`AiModelCatalog:34`）构成了一套**事实上的、围绕 run 的轨迹模型**（帧事件日志 + 工具台账 + 决策 WAL + 计量真值），但它只服务三个目的：重挂回放、续跑正确性、防重复执行。**没有任何一处是为「事后审计 / 成本 / 性能分析」设计的**：没有统一 trace id、没有保留策略分层、没有落库、没有指标导出。
2. **一次 run 在 24h 内可以被相当完整地还原**（帧序列 + 工具入出参 + 审批决策时刻与理由 + usage + 上下文计量），还原入口是 `GET /api/ai/events/{runId}`（回放）与 `GET /api/ai/runs/{runId}`（台账/待决/键表）。**24h 之后一切归零**：`app.ai.session-ttl: 24h`（`application.yml:138`）是全部 run 级键的滑动 TTL（`RunStore:1683`），H2 里没有任何 run/trace 表。
3. **指标面为零**：`pom.xml` 无 `spring-boot-starter-actuator`、无 micrometer registry、无 otel、无 prometheus；`/api/ai/health` 里的是**手写 `AtomicLong` 快照**（`SecurityEvents:77-88`、`SseChatEmitter:392-400`、jobWatchdog）。Spring AI 的 observation 钩子存在但**解析成 NOOP**（`AiProviderRegistry:60,217`，`getIfAvailable(() -> ObservationRegistry.NOOP)`）。
4. **日志面是「排障日志」，不是「审计日志」**：只有 `logging.level`（`application.yml:298-302`），无 logback-spring.xml、无文件 appender、无 JSON 编码、无 MDC（`traceId` 只出现在错误响应体，`GlobalExceptionHandler:107,132`）。轮次开始是 **DEBUG**（`ResilientChatService:295`），成功收尾**没有任何 INFO 日志**（只在 usage 脏帧时 WARN，`ResilientChatService:1452`）。
5. **最值钱的缺口不在「记录得不够」，而在「记录的东西不可被查询、不可被聚合、不可被长期保留」**：帧是「按 seq 的流水」，没有「按 run 的摘要」，没有「按会话/按模型/按工具的成本与耗时视图」，没有「失败分类的跨轮统计」。

#### 1.1.1 三类「事件条目」的字段级形态（轨迹词汇表的一半）

| 上游原始错误体 | 不能（只在日志 `describe()` 里，且不落盘） | 日志 |

### 2.2 缺什么

1. **没有「run 摘要对象」**：要回答「这一轮用了多少 token、几次工具、几次审批、等了多久、为什么慢」，必须自己把 6000 帧流水读一遍并逐帧聚合。`/runs/{runId}` 给的是**原料**（`ledger`/`pending`/`snapshot`），不是**摘要**。
2. **没有保留分层**：所有 run 级键同一 TTL（24h 滑动）。终态之后不再写就最后一笔写后 24h 全部消失；`ai:runs` SET 无 TTL，但成员指向的快照已过期（`allRunIds:694-714` 惰性剔除）。
3. **没有跨进程 trace 关联**：`instanceId` 只回答「哪个进程写的」，没有 `traceId/spanId`；日志里没有 MDC，无法把「一条 HTTP 请求 → 一轮 run → N 次工具 → 若干次 Redis 写」串成一条链（`ErrorBodyFactory` 的 `traceId` 取自 servlet 属性，`GlobalExceptionHandler:132-135`，与 AI 轨迹无关联）。
4. **帧窗口会吃掉早段**：`MAXLEN ~ 6000` + delta 入档会导致长回答/多工具轮的**开头帧被挤掉**（`FrameStore` 注释自述 B1 遗留风险；`RedisFrameStore:65-66`）。轨迹的「完整性」依赖「跑得短」。
5. **帧未落盘**：全仓 `ai/` 包内**没有任何 `Files./FileOutputStream/FileWriter`**（已 grep 确认）。进程外的证据只有「Redis 里有什么」。
6. **思考过程不进帧**：见上表最后两行。
7. **`FrameSizeLimiter` 的截断是有损且只留标记**：`truncated/truncatedReason`（`FrameSizeLimiter:45-47,86-107`），保留 `text/result` 前缀，**没有「全文另存」**（台账里 `resultText` 是全文，可救工具结果；正文 `text` 被截断即不可救）。

## 7. 缺口排序（建议专项从这里切）

### 最值钱的三处

1. **缺「run 摘要」这一层，导致所有轨迹数据都不可查询**。现状是「原料齐全、成品为零」：任何「这一轮为什么慢/为什么贵/为什么重试」的问题都要人工回放 6000 帧。建议的最小成品 = 每轮落一行结构化摘要（`runId, sessionId, providerId/modelId, 起止时刻, attempts, 工具次数与耗时, 审批次数与等待, prompt/completion/cached tokens, 压缩级别, 终态与错误码`），落点可选 H2 新表（与 `ai_config_audit` 同姿态）或 `ai:runsummary:<runId>` 键 + 一份可导出的 NDJSON。**它同时解决「24h 后归零」**（摘要可长留，原始帧仍 24h）。
2. **缺「统一关联 id」，导致三处证据串不起来**。`runId` 只在 Redis 键与部分日志里；日志无 MDC、无固定 `runId=` 前缀、无 traceId；`/health` 的 `instanceId` 只解决「哪个进程」。建议：给每轮分配 `traceId`（= runId 亦可），在 `AiController.chat` 入口与挂起/续跑线程入口装配 MDC，日志 pattern 加 `%X{traceId}`；把 `instanceId/epoch` 一并进 pattern。**这是「能不能用日志替代回放」的分水岭**。
3. **指标面为零（无 actuator / 无 MeterRegistry）**。当前 `/health` 的 7 个 `AtomicLong` 是手写的、进程内的、不可聚合的；双实例部署下 `security.scope=process`（`SecurityEvents:18,79`）意味着运维必须手工相加。建议：引 actuator + micrometer（prometheus registry 可选），把已有计数（`SecurityEvents`、`evicted`、`redisPolls`、`jobWatchdog`）迁成 `Counter`，并补四个最缺的计时器：上游首包、轮总耗时、工具执行、审批等待。**注意**：本轮勘察**不建议**把 SSE 帧量做成 metric（基数/音量都会爆），它属于 event log。

### 次一级（按性价比）

4. **`ai:xevents:` 窗口与保留策略不匹配「审计」用途**（delta 入档 + `MAXLEN ~ 6000`）：长轮早段会丢。若要审计，需要「按 run 的不可变归档」（落盘/DLQ/对象存储），而不是继续加大窗口。
5. **`start` 帧不带 `providerId/modelId`**（挂账 L-24）：在飞轮的「用了哪个模型」无法从帧断言，只能等 `done` 或读快照。
6. **thinking/reasoning 不进帧**：metadata 里有（`MessageJsonCodec:29-30`），但没有任何导出面；排查「模型为什么这么答」时只能读 `ai:run.messageJson`。
7. **成功路径无 INFO 行**：一轮正常结束在日志里几乎无痕（只有 DEBUG 开始行）。排查「用户说刚才那轮不对」时，如果没有 runId，日志里找不到入口。
8. **降级事件只有 WARN 没有计数**：`RedisAvailability`、`leaseOk`、`SseChatEmitter` 写超时摘除、`AiRateLimiter` 降级放行 —— 都是「发生了但只进日志」，无法做「降级率」看板。
