# 一、主流产品渲染面

## 1.1 ChatGPT（事实）

- **正文 Markdown 渲染**：标题、列表、链接、加粗等直接渲染；代码单独放 code block，带语言标签（Python/JavaScript/HTML）、复制、直接编辑、全屏、Code/Preview 切换。来源：[OpenAI 帮助中心《ChatGPT 中的写作与代码块》](https://help.openai.com/en/articles/20001246)。该页还写明"新编辑器"（写作块）支持 Bold/Italic、标题、链接、有序无序列表、清单。
- **图表是否原生渲染 Mermaid：不是「自动内联」，而是「点 Preview 预览」**。官方支持回复（2026-09-06）明确："Supported Mermaid code blocks can now be previewed inside ChatGPT—select Preview when it's available. Actions vary by device and account"；同一帖中 2025-01 的请求、2025-10 / 2026-02 / 2026-04 的追加吐槽说明在此之前长期不支持。来源：[OpenAI Developer Community《Rendering support for Mermaid code》](https://community.openai.com/t/rendering-support-for-mermaid-code/1085642)。
- **Preview 的受支持类型**：HTML 页面、React 组件、SVG、**Mermaid 图**、Vega/Vega-Lite 图表；"如果 Preview 不出现，说明该代码块不支持预览"；预览/执行在**沙箱环境**，需要外部资源时会请求授权。来源同上帮助中心页。
- **数学**：ChatGPT 渲染 LaTeX 数学（需用 `\( \)` 行内、`$$`/`\[ \]` 块级的定界符习惯），社区经验是"常要提示词明确要求用哪种定界符"；ChatGPT 也能输出 MathJax/MathML。第三方扩展（KaTeX/MathJax 复制类）大量面向 ChatGPT/DeepSeek，反向印证其用 KaTeX/MathJax 渲染。来源：[GenAI StackExchange《How does ChatGPT render math》](https://genai.stackexchange.com/questions/386/how-does-chatgpt-render-math-in-markdown-output)、[OpenAI 社区帖](https://community.openai.com/t/new-feature-properly-shown-mathematical-equations/73833)、[Copy LaTeX 扩展说明](https://www.chajianxw.com/product-tool/116533.html)。
- 推断（无公开文档）：code block 具体高亮库未公开；从"语言标签 + 主题化高亮"看是自研或 Shiki/Prism 一类，**不可断定**。

## 1.2 Claude（事实为主）

## 1.3 DeepSeek（事实 + 推断）

## 1.4 Kimi（事实，且信息质量最高）

- **官方文档明确**："Web 聊天支持 Mermaid 图表——助手回复中的 `mermaid` 代码块会在内置 web UI 中渲染为图表；**KaTeX 数学公式与 Mermaid 的解析改到 Web Worker 执行，流式输出时界面更跟手**"。来源：[Kimi Code 官方文档《最新动态》](https://www.kimi.com/code/docs/kimi-code/whats-new.html)。

## 1.5 Gemini（事实：Markdown 渲染存在但不稳定；推断：无 Mermaid）

# 三、流式渲染约束（含业界共识）

**问题定性（事实）**：逐 token 到达时，Markdown 天然处于"语法半成品"状态——这就是核心难点（未闭合代码围栏会吞掉后续所有内容、半截表格、未闭合加粗等）。来源：[Dayward AI《D2 Streaming Without Jank》](https://zhurilab.com/en/learn/frontend-agent-ux-7days/day-02)、[ProjectCOZY《Streaming LLM Responses》](https://projectcozy.me/blog/streaming-and-server-sent-events)。

**共识一：全量重解析是主要性能瓶颈（O(n²)）**
- "每个 token 触发整段累积文本的全量 re-parse"= 工作量随长度平方增长。来源：[DEV《I Made Streaming Markdown 300x Faster》](https://dev.to/jvoltci/i-made-streaming-markdown-300x-faster-heres-the-architecture-4a9f)、[《How To Build a Performant AI Markdown Renderer》](https://tigerabrodi.blog/how-to-build-a-performant-ai-markdown-renderer)、[前端架构文](https://ranjankumar.in/frontend-architecture-for-genai-why-your-react-patterns-dont-work-anymore)。
- **业界共识做法 = 分块 + 块级 memo**：AI SDK 官方 cookbook 明确推荐"把流式 Markdown 切成离散块，并对每块 memo，避免每个 token 重解析已完成内容"（[ai-sdk.dev cookbook](https://ai-sdk.dev/v5/cookbook/next/markdown-chatbot-with-memoization)、[ai-elements issue #9 引用该推荐](https://github.com/vercel/ai-elements/issues/9)）；Streamdown 把这条做成库能力：组件级 `React.memo` + **块级 memo，只有内容变化的块重渲染，已完成块保持稳定**（[Streamdown 官方 Memoization 文档](https://streamdown.ai/docs/memoization)）。

**共识二：未闭合块的处理——两种路线并存**
- **路线 A（保守）**：流式期间先纯文本，"done" 后再整体渲染 Markdown；或**检测到闭合围栏才渲染代码块**。来源：[Prasad《Building a ChatGPT-style streaming chat from scratch》](https://prasad.tech/blog/streaming-chat-from-scratch/)、[AI Tool Pipelines](https://www.aitoolpipelines.com/articles/nextjs-streaming-chat-ui-local-llm)、[The Front Kit《AI Chat UI Best Practices 2026》](https://thefrontkit.com/blogs/ai-chat-ui-best-practices)。
- **路线 B（增量修复/自动闭合）**：解析器在每一帧自动闭合未闭合标记，未闭合 ``` 渲染成"仍在填充的代码块"而不是字面反引号。来源：[mdstitch（crate 说明："runs before pulldown-cmark on each accumulated chunk and closes unterminated markers"）](https://lib.rs/crates/mdstitch)、[PanelUI《Response》："已上屏的字不能消失"原则](https://panelui.dev/docs/ai-components/response)、[Streamdown 未闭合块解析](https://reactscript.com/render-streaming-ai-markdown/)。
- **不必过度优化（反共识噪音）**：LangChain 给出量化口径——`marked` 约 1 MB/s，5 KB 聊天消息 <5 ms；"对典型聊天消息，每个 token 全量重解析已足够，只在很长（>50 KB）且观察到卡顿时再上 `requestAnimationFrame` 节流/增量解析"。来源：[LangChain《Markdown messages》](https://docs.langchain.com/oss/python/langchain/frontend/markdown-messages)。

**共识三：重型渲染器（KaTeX / Mermaid / 高亮）不能每帧跑**
- 数学：每个 chunk 全量跑 KaTeX 会浪费算力并造成可见闪烁，应增量或仅处理已完成块。来源：[ReLU.chat《KaTeX vs MathJax》](https://relu.chat/blog/katex-vs-mathjax-math-rendering/)。
- Mermaid：Streamdown 官方明确"**不要在每 chunk 重渲染 Mermaid**，否则慢且闪"，给出 `useIsCodeFenceIncomplete()` 钩子——未闭合时显示占位，**闭合 ` ``` ` 后立刻渲染**（不等整条消息结束），并用 `isAnimating` 禁用流式期交互。来源：[Streamdown Mermaid 插件文档](https://streamdown.ai/docs/plugins/mermaid)。VS Code Copilot Chat 正是踩了"每 token 重渲染 Mermaid"这个坑：[vscode issue #319248](https://github.com/microsoft/vscode/issues/319248)。
- open-webui 同款策略：**只有 code fence 已闭合才渲染**（`(token?.raw ?? '').slice(-4).includes('```')`）。来源：[open-webui CodeBlock.svelte](https://raw.githubusercontent.com/open-webui/open-webui/main/src/lib/components/chat/Messages/CodeBlock.svelte)。
- 另一个被验证有效的做法：**把 KaTeX/Mermaid 的解析挪到 Web Worker**（Kimi Code 官方），"流式输出时界面更跟手"。[Kimi Code 文档](https://www.kimi.com/code/docs/kimi-code/whats-new.html)

# 四、安全面：AI 输出渲染的 XSS 惯例

**事实：这不是假想风险，已有两个 AI 聊天框被同一手法打穿。** Escape 的安全团队在两个互不相关的公司发现同一类**存储型 XSS**，根因是 Markdown 栈装配为 `react-markdown + remark-gfm + rehype-raw`，**没有任何 sanitizer**；并用 `<iframe srcdoc="...">` 绕过 react-markdown 默认的"URL scheme 白名单"（`srcdoc` 不在 URL 属性清单里，React 会原样写入 DOM，浏览器按新文档解析）。来源：[Escape《Escape found the same XSS in two AI chatboxes》](https://escape.tech/blog/escape-found-the-same-vulnerability-in-two-ai-chatboxes/)。同文还引用了两个 CVE：

- **CVE-2026-17496**（NoteGen）：markdown-it 配 `html: true` + `dangerouslySetInnerHTML` + CSP 置空 → 恶意 skill 的 `REFERENCE.md` 让模型输出 `img onerror`，在 Tauri webview 内执行。
- **CVE-2026-32308**（OneUptime）：Mermaid 以 `securityLevel: "loose"` 渲染后把 SVG 用 `innerHTML` 注入，Mermaid 的 `click` 指令变成执行原语，波及所有渲染 Markdown 的字段。

**惯例清单（事实 + 一致推荐）**：
1. **首选不渲染 raw HTML**。`react-markdown` 默认把 raw HTML 转成纯文本（安全默认）；"对多数团队就是删掉 rehype-raw"，且"表格、链接、代码块都还能用"。来源：[Escape](https://escape.tech/blog/escape-found-the-same-vulnerability-in-two-ai-chatboxes/)、[Strapi 指南](https://strapi.io/blog/react-markdown-complete-guide-security-styling)、[MacMD 指南](https://macmdviewer.com/blog/react-markdown-guide)（"Raw HTML in the markdown source is stripped by default; if you enable raw HTML via rehype-raw, add rehype-sanitize to whitelist allowed tags"）。
2. **若必须开 raw HTML：`rehype-sanitize` 必须排在 `rehype-raw` 之后**（顺序反了等于没做，因为节点还是未解析的 raw node），用默认 schema 白名单而非黑名单，**逐属性枚举**（`srcdoc`/`on*`/`src`/`action`），iframe 若保留必须 `sandbox` 且**不给 `allow-same-origin`**，并上 CSP（无 `unsafe-inline`，含 `img-src`/`form-action`/`frame-src`）。来源：[Escape](https://escape.tech/blog/escape-found-the-same-vulnerability-in-two-ai-chatboxes/)。
3. **KaTeX 与 sanitize 的顺序**：若信任 KaTeX，`rehype-katex` 要跑在 `rehype-sanitize` **之后**（官方包 README 原文警告）。来源：[@deancureton/rehype-katex README](https://www.npmjs.com/package/@deancureton/rehype-katex)。
4. **"每个渲染扩展都是第二个 HTML 生成器"**：语法高亮、KaTeX、Mermaid 一旦把结果送进 `innerHTML`，就重新打开了刚关上的风险面；典型反模式是"sanitizer 放在这些插件之后会把它们的产物剥掉，于是被挪到前面，最后停在 rehype-raw 前面形同虚设"。来源：[Escape](https://escape.tech/blog/escape-found-the-same-vulnerability-in-two-ai-chatboxes/)。
5. **工业级默认值参考（Streamdown）**：默认 `rehype-sanitize`（GitHub schema，扩展 `tel:`）+ `rehype-harden`（协议/链接域名/图片来源白名单，可关 base64 图防追踪与 CSRF），提供 `allowedProtocols`/`allowedLinkPrefixes`/`allowedImagePrefixes`/`skipHtml`/`allowedTags`/`urlTransform`，并明确"覆盖 `rehypePlugins` 时必须带上 `defaultRehypePlugins.sanitize`，否则 XSS 防护失效"。来源：[Streamdown Security 文档](https://streamdown.ai/docs/security)。
6. **流式会让"只检查成品"的 sanitizer 失效**（浏览器已被分片渲染过）；同一输出可能出现在多个渲染面（工单看板、客服回放、Slack 展开、PDF 导出），要**逐个渲染点加固**。来源：[Escape](https://escape.tech/blog/escape-found-the-same-vulnerability-in-two-ai-chatboxes/)。
7. **链接的属性惯例**：Markdown 标准本身无法表达 `target`，行业惯例是自定义 link 组件对站外链接加 `target="_blank"` + `rel="noopener noreferrer"`（且 `noopener` 与 `noreferrer` 一起用），或干脆不加 `target`；站内链接走路由组件。来源：[Python Guides《Custom Component Mapping in React Markdown》](https://pythonguides.com/react-markdown-custom-component/)、[Markdown Links 指南](https://edtr.md/blog/markdown-links-guide)、[SEO Checkup 建议](https://seositecheckup.com/seo-audit/kernal-automation.com)。Streamdown 走另一条路——用 `linkSafety`/`allowedLinkPrefixes` 限制可达域，不安全链接渲染为 `[blocked]`，而非依赖 `target/rel`（[Streamdown Security](https://streamdown.ai/docs/security)）。
8. **现实提醒：开源实现经常覆盖不全**。open-webui 的公开安全公告显示其 **23 处 `{@html}` 只有 9 处（39%）经过 DOMPurify**，其中 `MarkdownInlineTokens.svelte:130` 是安全写法（`DOMPurify.sanitize(token.text, {ADD_ATTR:['target']})`），但存在未覆盖的"防御传播缺口"。来源：[GHSA-hcwp-82g6-8wxc / CVE-2026-45318](https://github.com/advisories/GHSA-hcwp-82g6-8wxc)。（源码侧同样可见 DOMPurify 只用在 `MarkdownInlineTokens`/`HTMLToken`：[open-webui 源码](https://raw.githubusercontent.com/open-webui/open-webui/main/src/lib/components/chat/Messages/Markdown/MarkdownInlineTokens.svelte)、[HTMLToken.svelte](https://raw.githubusercontent.com/open-webui/open-webui/main/src/lib/components/chat/Messages/Markdown/HTMLToken.svelte)）
9. **反例（不要照抄）**：open-webui 当前用 `securityLevel: 'loose'` 初始化 Mermaid（[utils/index.ts `initMermaid`](https://raw.githubusercontent.com/open-webui/open-webui/main/src/lib/utils/index.ts)）——正是 CVE-2026-32308 出事的配置档位；对比 Streamdown 插件默认 `securityLevel: 'strict'`（[Streamdown Mermaid](https://streamdown.ai/docs/plugins/mermaid)）与 Mermaid 官方默认 `strict`（[Mermaid 官方 Usage/securityLevel](https://mermaid.js.org/config/usage.html)）。

# 五、Mermaid 的工程代价

**体积（事实，含实测）**
- 官方 `mermaid@11.12` 的 `dist/mermaid.min.js` = **2684.6 KB（约 2.6 MB，未 gzip）**；同版本 `dist/mermaid.esm.min.mjs` 入口仅 **25.6 KB**（ESM 分片壳）。实测来源：[jsDelivr 包文件清单](https://data.jsdelivr.com/v1/packages/npm/mermaid@11.12.0?structure=flat)。
- gzip 后量级：第三方实测 **约 315 KB gzip（v11.14）**，且**"不可有效 tree-shake"**——图解析器在模块初始化时注册进 registry，"import mermaid 就得到全部图类型"，因此"**绝不要把 mermaid 放进全局 app shell**，按路由 code-split 或首次需要时 dynamic import"。来源：[Towards AI《Floundering with Mermaid?》](https://pub.towardsai.net/floundering-with-mermaid-1f6b2d7b6500)。
- 其他口径：核心 + 懒加载图 chunk **约 480 KB**、渲染 **50–200 ms/图**（第三方技能页）；某项目实测懒 chunk **约 620 KB**。来源：[skillsadd 汇总页](https://skillsadd.com/curiositech/some_claude_skills/mermaid-graph-renderer)、[Loomcycle 博文](https://loomcycle.dev/blog/the-document-viewer-grows-images-diagrams-colors-and-edit-controls.html)。
- **Tiny build**：官方提供约半体积的精简版，**不含 Mindmap、Architecture、KaTeX 渲染、lazy loading、ELK**（"tiny build 从未包含 ELK"）。来源：[Mermaid 官方 Usage 文档](https://mermaid.js.org/config/usage.html)。

**懒加载惯例（事实）**
- 模式统一：**先探测页面/消息里是否真的有 mermaid 块，再 dynamic import**——open-webui 在第一个 mermaid 围栏时才 `await import('mermaid')`（[源码](https://raw.githubusercontent.com/open-webui/open-webui/main/src/lib/utils/index.ts)）；Loomcycle 用 `import("mermaid")` 懒 chunk（[博文](https://loomcycle.dev/blog/the-document-viewer-grows-images-diagrams-colors-and-edit-controls.html)）；Streamdown 用 **viewport-based lazy loading**（进入视口才渲染）。来源：[Streamdown CHANGELOG](https://github.com/vercel/streamdown/blob/main/packages/streamdown/CHANGELOG.md)。
- 也有规模化反例供警惕：某站点把 mermaid 包成"约 3 MB minified"的 IIFE，按图类型分两个引擎懒 chunk，只在页面真的需要时加载。来源：[trip2g 技术说明](https://trip2g.com/dev/mermaid)。

**失败回退惯例（事实）**
- **源码块兜底 + 手动/条件渲染**：传统做法是"渲染成代码块 + 一个 render 按钮"；Streamdown 默认 `suppressErrorRendering: true`（避免半成品渲染），提供自定义 error 组件（`error`/`chart`/`retry` 三参，含"Try Again"重试），并保留源码可复制/下载 `.mmd`。来源：[Streamdown Mermaid 插件文档](https://streamdown.ai/docs/plugins/mermaid)、[toolify 功能页](https://www.toolify.ai/tool/streamdown)。
- **产品侧回退范式**：ChatGPT 用"**Preview 按钮**"，不支持就不显示 Preview（[帮助中心](https://help.openai.com/en/articles/20001246)）；Kimi Code 提供**全局开关**关掉 mermaid（`mermaid = "off"`，[文档](https://www.kimi.com/code/docs/kimi-code/whats-new.html)）；Qwen Code 明确"**原始源码始终可访问**"，提供 `render`/`raw` 两种模式（[文档](https://qwenlm.github.io/qwen-code-docs/zh/users/features/markdown-rendering/)）；open-webui 渲染失败 `console.error` 并退回代码块（[源码](https://raw.githubusercontent.com/open-webui/open-webui/main/src/lib/components/chat/Messages/CodeBlock.svelte)）。
- **安全档位**：Mermaid 官方默认 `securityLevel: 'strict'`（HTML 标签编码、禁用 click），`sandbox` 用 iframe 隔离，"site owner 需自行判断用户可信度"。来源：[Mermaid 官方 Usage](https://mermaid.js.org/config/usage.html)。

# 七、给本次裁决的要点（推断，非来源结论）

1. **Markdown 渲染已是行业默认，不是可选项**：调研到的所有面向用户的对话产品都渲染 Markdown（含代码块/表格/列表），差别只在"覆盖面与稳定性"。若本产品不渲染，会明显低于基线体验。
2. **Mermaid 是分层的、不是统一的**：ChatGPT 用"Preview 按钮"门控、Claude 用 Artifacts 容器、GitHub Copilot（web）干脆不在聊天里渲染、DeepSeek 至今只高亮。**"原生自动内联渲染"反而是少数派**——这说明"先只做代码块 + 可选预览/渲染按钮"是完全站得住的落地形态。
3. **若做 Mermaid，三个工程约束是硬约束**：①必须 dynamic import（≥0.3 MB gzip、不可 tree-shake）；②必须"围栏闭合才渲染"，绝不每 token 重渲染（VS Code 已给出反面案例）；③失败必须回落到源码块 + 重试/关闭开关。
4. **安全上是"不做比做错好"**：不开 raw HTML 是成本最低、收益最高的默认；一旦开了 raw HTML 或引入 Mermaid/highlight 这类"第二 HTML 生成器"，sanitizer 的顺序与属性白名单才是关键，而现实中的开源实现（open-webui）覆盖率只有 39%。
5. **流式不必一开始就上增量解析器**：LangChain 的量化口径支持"先整段重解析 + 块级 memo"，只有在长回答/多图/高 TPS 时才需要更重的方案（Streamdown 式未闭合块解析、Web Worker 卸载 KaTeX/Mermaid）。

**证据薄弱处（请在裁决时留出余量）**：Claude 正文渲染明细与数学实现、Gemini 的 mermaid 能力、Cursor 的渲染实现、通义/文心的具体渲染栈，均缺一手文档；这些条目我已在文中标注为推断或弱证据。
