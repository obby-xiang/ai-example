# 调研 · 多实例 SSE 扇出与 HITL 业界架构 · 2026-10-20

> 调研问题：AI 流式推送（SSE）在多实例部署下怎么扇出？「等人」（HITL 挂起）与「跑着的循环」跨实例怎么归属，才能既不丢帧也不重复执行？本件分四问：Q1 扇出方案选型 / Q2 sticky 是不是多数团队的答案 / Q3 分布式 HITL 如何做到不重复执行与不丢帧 / Q4 等待中的人与执行循环的跨实例归属。
> 来源：AWS Builder Center、Redis、Socket.IO、NGINX、ingress-nginx、AWS 网络最佳实践、LangGraph / LangSmith、Temporal、Camunda 8、CopilotKit、Ably 的官方文档与官方博客；访问日期 2026-10-20。厂商未公开的细节不臆测。
> 结论：业界主流**不是「长连接 + sticky」**，而是把三件事拆开 —— 帧变成**可重放的事件日志**（seq / Last-Event-ID，连接只是视图）、执行变成**外置状态机 + 无名执行者**（谁都能捡起来跑）、决策变成**一次幂等事件追加**且由**唯一领取者用租约 / 围栏令牌**续跑。sticky 只是「让旧连接别迁移」的止痛药，而 HITL 的等待时长（几十分钟到几天）远大于连接寿命，原理上救不了这个场景。
> 边界：本件是调研稿；§7「三条建议」与 §6 的修法是研究方向，不构成施工排期或接口契约。§6 的「我们」指本仓现状（Spring + SSE + Redis）。
> 脱敏：无账号显示名、无本机绝对路径、无密钥、无原始会话内容、无本仓代码行号；第三方与官方 URL 原样保留。

## 1. 一句话结论

业界主流不是「长连接 + sticky」，而是**把三件事拆开**：

1. **帧**——变成可重放的事件日志（有 seq / Last-Event-ID），连接只是「视图」；
2. **执行**——外置状态机 + 无名执行者（task queue / consumer group），**谁都能捡起来跑**；
3. **决策**——一次幂等的事件追加，由**唯一领取者**用**租约/围栏令牌**续跑，落点无关。

sticky session 只是「让旧连接别迁移」的止痛药，而 HITL 的等待时长（几十分钟到几天）远大于连接寿命，所以它在原理上救不了这个场景。

## 2. Q1：SSE/WebSocket 多实例扇出，业界主流选哪个

| 方案 | 采用度 | 适用 | 主要坑（有据可查） |
|---|---|---|---|
| **Redis Pub/Sub** | 事实标准，Spring/Node 小中型系统最常见 | pod 数 ≤ 十几、帧小、不需要历史回放 | **at-most-once**，订阅者掉线即永久丢消息；无背压；Redis 抖动 = 全体丢帧；Cluster 下普通 `PUBLISH` 会经 cluster bus 广播到所有节点，高吞吐成热点（用 Redis 7 `SSUBSCRIBE` 分片频道缓解） |
| **Redis Streams** | 中大型、需要 `Last-Event-ID` 补偿时 | 断线重放、每会话游标 | 要自己管 `MAXLEN` 裁剪；消费者组语义是「分摊」不是「广播」，不能直接套用 |
| **Kafka** | 大型 / 已有 Kafka 的团队 | 连接层与业务层彻底解耦（Shopify BFCM 模式：SSE 网关只持连接，业务逻辑无状态在后） | 小 payload 延迟高；「每用户一个 topic」不现实；运维重 |
| **专用/托管推送网关** | Node 生态默认 Socket.IO + Redis adapter；商业侧 Ably / Pusher / CopilotKit Intelligence | 多设备、企业代理穿透、不想自建 replay | 成本、数据出境、鉴权模型、厂商锁定 |
| **sticky session** | 大量团队的「默认止痛药」 | 只解决「同一连接内多请求落到不同 pod」 | 不是扇出方案，是**回避**扇出 |

关键证据：

- SSE 横向扩展的标准做法就是「连接层无状态 + 共享 pub/sub 扇出」：*"When multiple SSE server instances sit behind a load balancer, a client may reconnect to a different server. A shared pub/sub layer (Redis Pub/Sub, Kafka, NATS) ensures every server instance receives every event"* —— [Resilience Considerations for Implementing SSE over HTTP(S)](https://builder.aws.com/content/37s4EKZEFScKfd0lxYkfLnGZpHn/resilience-considerations-for-implementing-server-sent-events-over-https)
- Redis Pub/Sub 的投递语义原文：*"at-most-once ... if the subscriber is unable to handle the message ... the message is forever lost. If your application requires stronger delivery guarantees, you may want to learn about Redis Streams"* —— [Redis Pub/Sub](https://redis.io/docs/latest/develop/pubsub/)
- Socket.IO 的 Redis adapter 就是「把包 publish 到频道，其他节点收到后推给自己本地连接」，且明确说 **Redis 里的消息不签名不加密**，Redis 必须视为可信内网 —— [Redis adapter](https://socket.io/docs/v4/redis-adapter/)
- 扇出拓扑的完整权衡（广播并过滤 / 按需订阅 / 分片频道 / presence registry）与「Redis Pub/Sub at-most-once 不能回答『离线期间错过了什么』」—— [Scaling WebSockets: Fanout Across Servers](https://formation.dev/blog/websocket-fanout-presence-registry)
- Spring 生态的落地样板就是 `SseEmitter` + Redis Pub/Sub，且强调「所有实例（含自己）都订阅同一 topic，自己也不特殊处理」—— [Distributed SSE with Spring SseEmitter and Redis Pub/Sub](https://www.geekyhacker.com/distributed-sse-with-spring-sseemitter-and-redis-pub-sub/)

**判断**：不存在「一个赢家」，存在**分层共识**——小规模用 Redis Pub/Sub 做「唤醒通知」，大数据/回放放 Redis Streams 或 Kafka；帧本身不靠总线传，靠**可读的事件存储**。托管网关是「不想运维 replay/多设备/代理穿透」时的正确答案。

## 3. Q2：sticky session 派，是不是大多数团队的答案？

**不是。** 而且对「HITL 等人」这个场景，它几乎零收益。

原理层面的三个事实：

1. **SSE 是单次长响应**，不像 Socket.IO 的 HTTP long-polling 那样「一个会话多次请求」。所以 SSE **不靠 sticky 保证正确性**，重连落到哪个 pod 都合法——只要你还能拿到帧。反过来，sticky 只保证「连接不迁移」，不保证「新连接拿得到旧帧」。**连接迁移 = 断流，而断流本来就是常态**（滚动发布、HPA 缩容、ALB 空闲超时）。
2. **HITL 的等待时间远大于连接寿命**：用户 20 分钟后回来点批准时，SSE 连接早断了，sticky 的绑定对象已经不存在。此时唯一的救命稻草是 `Last-Event-ID` + 服务端事件缓冲。
3. **sticky 把正确性绑在 LB 上**，而 LB 恰恰是 K8s 里最容易被替换/最不透明的一环。

实践与坑（均有文档依据）：

- NGINX 开源版只有 `ip_hash` / `hash $remote_addr consistent`；`sticky cookie` 属商业订阅。`ip_hash` 用前三段 IPv4 做 key，NAT/公司出口/移动网络会**大量用户聚到同一 pod**；且 *"requests from the same client will always be passed to the same server except when this server is unavailable"*——pod 不可用即强制迁移 —— [ngx_http_upstream_module](https://nginx.org/en/docs/http/ngx_http_upstream_module.html)
- ingress-nginx 的 cookie affinity 有 `balanced`（扩容时重分配部分会话）与 `persistent`（最大粘性）两档；`session-cookie-change-on-failure=true` 时亲和会**在失败后自动失效**；且「Service 指向多个 Ingress 时只有第一个的 affinity 生效」—— [Ingress-nginx cookie affinity](https://kubernetes.github.io/ingress-nginx/examples/affinity/cookie/)
- AWS ALB 默认 **idle timeout 60s**，长连接必须上调，否则空闲即被切 —— [AWS Networking Best Practices: Load Balancing](https://aws.github.io/aws-networking-best-practices/application-networking/load-balancing/)
- 长连接在**建立时**才做均衡，所以「新发布的 pod 长期偏空、老 pod 堆满连接」；部分重启后连接数会长期倾斜；sticky 改善的是局部性，**替代不了跨进程路由** —— [Formation](https://formation.dev/blog/websocket-fanout-presence-registry)
- Socket.IO 是少数**真的必须** sticky 的场景（long-polling 握手 + 会话在进程内），且官方说「用 Redis adapter 也仍要开 sticky，否则 HTTP 400」；同时给了「关掉 polling、只用 WebSocket 就不需要 sticky」的出口 —— [Using multiple nodes](https://socket.io/docs/v4/using-multiple-nodes/)、[Redis adapter](https://socket.io/docs/v4/redis-adapter/)

**结论**：*"SSE can be load-balanced without stickiness"*（[Hybrid SSE](https://martinuke0.github.io/posts/2026-03-31-hybrid-serversent-events-combining-realtime-push-with-fallback-strategies/)）——sticky 对 SSE 是**可选优化**，对 HITL 是**无关变量**。把它当架构答案，等于把「pod 重启」写进 SLA。

## 4. Q3：AI agent 平台的分布式 HITL，怎么做到不重复执行、不丢帧

四家代表，两种范式：

| 平台 | HITL 原语 | 落点无关怎么保证 | 帧怎么不丢 |
|---|---|---|---|
| **LangGraph** | `interrupt()` + checkpointer + `thread_id`；`Command(resume=...)` | 恢复只需 **同一个 `thread_id`**，任何进程 `invoke` 都能恢复；状态在 checkpointer（生产用数据库），不在内存 | `stream_resumable=true` + `Last-Event-ID` 重放；`POST /threads/{tid}/runs/{rid}/stream` 可从任意节点「join」一个**已在跑**的 run；`cancel_on_disconnect` **默认 false**（断连不杀 run） |
| **CopilotKit** | AG-UI 事件流（SSE）+ `useHumanInTheLoop` 审批卡 | run 是服务端对象，`/connect` 用于「重连后恢复流」；Intelligence 模式下 run/connect **不返回流**，只返回 `{threadId, runId, joinToken, realtime:{clientUrl, topic}}`，事件走独立实时平面 | 托管实时平面负责顺序/恢复；线程事件可 `GET /threads/{tid}/events` 回读 |
| **Temporal** | `@workflow.signal` + `workflow.wait_condition()` | 审批作为 `WorkflowExecutionSignaled` **事件写入 history**；workflow task 由 server 串行调度，崩溃后 replay 到原状态，**不需要重新审批** | 不是「帧」问题——客户端只是订阅者，状态由 history 决定 |
| **Camunda 8 / Zeebe** | user task / job worker | *"Zeebe ensures each job is sent to only one of the workers"*；超时重派 + **job lease（围栏令牌）**：过期的 completion 被 `INVALID_STATE` 拒绝 | 同样：流程状态在引擎，UI 只是查询/订阅 |

要点：

- LangGraph 的官方措辞就是「run 是资源、stream 是视图」：*"Join and rejoin lets you disconnect from a running agent stream without stopping the agent... you pick up the stream exactly where you left off"*，且专门区分 `disconnect()`（不取消）与 `stop()`（取消）——[Join & rejoin streams](https://docs.langchain.com/oss/python/langchain/frontend/join-rejoin)、[Join Run Stream API](https://docs.langchain.com/langsmith/agent-server-api/thread-runs/join-run-stream)
- LangGraph `interrupt` 的两条硬规则，正好对应你们的 bug：**恢复时整个节点从头重跑**，所以「`interrupt` 之前的副作用必须幂等」；resume 值按**下标**匹配，不能条件性跳过 interrupt —— [Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)
- Temporal 的说法：审批写入 event history 后，*"If the website crashes after approval, the workflow resumes with the approval already recorded"*，且 waiting 时**不占 CPU**（不是轮询循环）—— [Durable HITL tutorial](https://learn.temporal.io/tutorials/ai/building-durable-ai-applications/human-in-the-loop/)
- Camunda 的 job leasing 段落是「决策落到非原执行者」的教科书答案：没有 lease 时，*"if worker A's stale approval reaches Zeebe first, it wins"*；有 lease 时*"Zeebe rejects it regardless of arrival order"*；同时明确 Zeebe 是 **at-least-once**，worker 必须幂等 —— [Job workers](https://docs.camunda.io/docs/components/concepts/job-workers/)

**回答「durable execution 是不是主流答案」**：是**重型场景**的主流答案（长等待、跨天、必须审计）；轻量场景的主流是「**外置状态机 + 幂等 + 单写者租约**」，本质上是 durable execution 的手工缩小版。两者共同点是：**没人试图让「原来那个进程」活着**。

## 5. Q4：「等待中的人」与「跑着的循环」的跨实例归属

**主流是「循环跑在哪个 pod 不重要、状态全外置、谁都能捡起来跑」（share-nothing + 外置状态机）。「原 pod 续跑」只是性能优化，且被明确设计成可降级。**

- Temporal 的 sticky execution 页面写得最直白：*"Any Worker that polls that Task Queue is eligible to accept the Task and begin executing the Workflow."* 粘性只是**缓存优化**；如果 worker 5 秒内没接走 sticky 队列里的任务，*"the Temporal Service disables stickiness ... allowing any Worker to pick it up"*；任务失败则把 workflow 从缓存移除、打回原队列 —— [Sticky Execution](https://docs.temporal.io/sticky-execution)
- durable execution 的定义就是「执行被虚拟化到一串进程上，每个进程可能在不同机器」—— [The definitive guide to Durable Execution](https://temporal.io/blog/what-is-durable-execution)
- Camunda：job 由 **worker 主动拉取**（或 stream 推送），*"Many workers can request the same job type to scale up processing. In this scenario, Zeebe ensures each job is sent to only one of the workers."*；worker 全挂也不丢——*"Zeebe queues all jobs during any job worker outages"* —— [Job workers](https://docs.camunda.io/docs/components/concepts/job-workers/)
- 长连接侧同理：连接会**故意**设 TTL（如 1 小时）来「自然再平衡」，服务端在关闭前发「please reconnect」并 drain —— [AWS SSE resilience](https://builder.aws.com/content/37s4EKZEFScKfd0lxYkfLnGZpHn/resilience-considerations-for-implementing-server-sent-events-over-https)

所以 workflow 引擎的答案是：**「原 pod」这个概念不存在**。存在的是「流程实例 ID + 事件历史 + 可被任意执行者领取的下一步」。**重复执行不是靠避免，而是靠「单写者租约 + 幂等」使其无害。**

## 6. 映射到我们的系统（Spring + SSE + Redis）

现状 → 业界对应物：

| 我们的现状 | 业界对应 | 差距性质 |
|---|---|---|
| 决策经 Redis 中转 | 决策 = append 事件（幂等键 `decisionId`） | ✅ 方向对，补幂等键即可 |
| 副作用 Redis 认领 | lease / fencing token | ✅ 方向对，缺**单调 epoch** |
| SSE 帧扇出在进程内 | 缺共享事件日志 | ❌ 结构性缺陷 |
| 决策落到非原 pod 触发续跑竞态 | 缺「单写者」约束 | ❌ 结构性缺陷（不是窗口大小问题） |

两个缺陷的业界修法，注意措辞差异：

1. **不丢帧**：不是「广播给所有 pod」，而是「**帧先落事件日志，再通知**」。`conv:{id}` 的帧带单调 `seq`；pod 收到 pub/sub 通知后从 Stream/DB 读 `>lastSentSeq` 推给本地连接。Redis Pub/Sub 只做**唤醒**，丢了也无所谓——客户端重连带 `Last-Event-ID` 补。这与 LangGraph 的 `stream_resumable` + `Last-Event-ID`、AWS 的「事件缓冲 + 有界 replay window」是同一件事。
2. **不误续跑**：把「决策投递」和「续跑触发」解耦。决策端点只做 `XADD decision`（幂等）；**续跑**由一个「领取者」用 `SET lease:{conv} <epoch> NX PX ttl` 抢占，epoch 单调递增，续跑写回时带 epoch，过期即被拒（Camunda job lease 的 `INVALID_STATE` 语义）。这样「落点」不再有语义——任何 pod 都能处理决策，但只有一个能续跑。
3. 附带一条安全提醒：Redis Pub/Sub 的消息**不签名不加密**（Socket.IO 官方文档明确警告），如果帧开始走 Redis，Redis 就是信任边界的一部分，需要 ACL/TLS/独立实例。

## 7. 三条建议（分别给单实例 / 多实例的最小路径）

### 建议一：把「帧」定义成可重放的事件，而不是一次 socket 写

无论今天几个实例，先把契约定死：`{conversationId, seq, type, payload}`，客户端支持 `Last-Event-ID`。

- **如果单实例（最小）**：`SseEmitter` + 每会话**内存环形缓冲**（保留最近 N 条 / T 分钟）+ 单调 seq + 心跳 comment（15–30s）+ `spring.mvc.async.request-timeout` 放大。断线重连从 ring buffer 补。**不引入 Redis。** 这一步只是把「缓冲区」抽象成一个接口（`FrameStore`），为多实例留门。
- **如果多实例（最小）**：`FrameStore` 换成 Redis Stream（每会话一个 key，`XADD` + `MAXLEN ~`）。所有 pod 订阅一个/少量 pub/sub 频道做「有新帧」的**唤醒通知**（不传帧体）；连接所在 pod 读 Stream 增量下发。**不要**用「每 pod 订阅每会话」的朴素广播——pod 数 × 会话数会爆，按连接 `SUBSCRIBE`/`UNSUBSCRIBE` 或分片频道。

### 建议二：把「续跑权」变成带围栏令牌的租约，而不是「谁收到决策谁跑」

- **如果单实例（最小）**：仍然加「单写者」约束——每会话一个 `AtomicReference<RunState>` / 单线程 executor，`tryStart(convId)` 返回 false 就丢弃重复触发。**现在就把幂等键和 `runEpoch` 写进代码**，成本几乎为零，是将来多实例唯一不用重写的地方。
- **如果多实例（最小）**：Redis `SET lease:{conv} {epoch} NX PX 30s` + 定期续租；所有「续跑」写入都带 epoch 校验（Lua 或 `WATCH`），epoch 小则拒。同时承认 at-least-once：续跑的**第一个副作用**必须是幂等的（Camunda 原文：*"worker code must be idempotent"*）。不要试图用「锁住让竞态不发生」——要让它「发生了也没事」。

### 建议三：不要用 sticky 当架构；真要粘，就按 `conversationId` 粘，且必须可 replay

- **如果单实例**：不需要 sticky，也不需要会话亲和。把 LB 的 idle timeout 调大即可（ALB 默认 60s 会切流）。
- **如果多实例**：优先「不粘」。如果因为成本/工期必须粘，用**一致性哈希按 `conversationId`（header/query）**而不是按 IP——IP 哈希在 NAT 下会热点，且 HITL 等待期连接早断了，粘不住「人」。任何 sticky 方案都必须叠加建议一（否则 pod 一重启就是丢帧事故）。
- **什么时候该上重型武器**：如果 HITL 等待跨越部署窗口/跨天、且「不重复执行」是合规要求，直接引入 Temporal（Java SDK 成熟）或 Camunda 8（Spring 生态、有 job lease 开箱），SSE 退化为纯视图。判据来自 Ably 的分界线：响应 >30s、多设备、企业代理、**HITL 是核心需求** → 该用 durable session/durable execution；否则 Redis 缓冲够用 —— [AI chat stream resumption](https://ably.com/blog/ai-chat-stream-resumption)。

> 后续口径（入库时注记）：本件 §6 指出的两条结构性缺陷（缺共享事件日志、缺单写者约束）与 §7 建议一 / 二，**已由 2026-10-20 架构方向裁决收口为三段计划** —— **B1 挂起即断 SSE 连接**（传输层不再靠长连接挂住等人，恢复走重连 + 补帧）→ **B2 pub-sub 扇出**（帧先落可重放事件日志，总线只做唤醒）→ **B3 fencing 租约**（续跑权用单调 epoch 租约，落点无关）；口径「**B2 完成前生产只能单实例**」「多窗口实时同步降级为操作 / 刷新时同步」，状态 = 已裁决待设计稿（裁决行见 `docs/决策看板.md` 10-20，任务行见 `docs/任务看板.md` 10-20「批·多实例架构专项（B1/B2/B3）」）。本件正文保留调研时点原貌、不回头修订。

## 8. 三个反直觉的点

1. **sticky 对 HITL 是无效药**：它绑定的是「连接」，而 HITL 等的是「人」，两者寿命差一个数量级。
2. **「不重复执行」的正确姿势不是加锁**，是**围栏令牌 + 幂等副作用**。加锁只是把竞态窗口变小；fencing 让过期写入被确定性拒绝（Camunda 的 lease 就是这么设计的）。
3. **Redis Pub/Sub 不适合承载帧**，只适合承载「有帧了」这个信号。它是 at-most-once 且无回放——把帧体放进去，等于把「不丢帧」这个需求交给了一个明确不保证的功能。
