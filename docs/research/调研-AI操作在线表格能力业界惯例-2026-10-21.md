## 0. 结论先行

**「AI 操作在线 Excel 的能力」在本仓不是完全缺失，而是"通道齐备、内容面为零"。**

精确判定（按 18 个 `@Tool` 逐个对账，见 §②）：

| 层 | 现状 | 判定 |
|---|---|---|
| **流程驱动**（建任务、选配置、设条件、推步骤、发起导出/预检/导入/发布） | 11 个后端工具 + 4 个工作区动作，含确认门与 DANGER 分级 | **已有，且比多数业界产品更严** |
| **文件通道**（打开在线编辑器、下载/打包 xlsx） | `open_export_file_editor` / `download_export_files` 两个前端工具 | **已有，但是"递交文件"，不是"操作文件"** |
| **表格内容**（读行、读单元格、写单元格、列映射、聚合、diff） | **零工具**。`get_row_count` 只回一个行数；`check_job_status` 只回 `errorCount` | **完全缺失** |

一句话：今天的 AI 是**"按钮的代按者"**（把用户想做的流程按下去），不是**"表格的操作者"**（看数据、改数据、解释数据）。业界主流产品的重心恰恰在后者，而且 2025–2026 的演进方向是"先给计划/预览，再落，再可撤销"——本仓已有确认门与暂存区这两块地基，缺的是"把数据面接进模型"的那一层契约。

### 三条跨产品共性（比逐家细节更重要）

1. **写操作一律"先说后做"**：Copilot 的计划模式、Gemini 的 Action preview card、Airtable 的 prompt 预览、Notion 的建库预览、ChatGPT/Claude 插件的"改前请求许可"。**没有一家把"AI 直接静默改一批单元格"当卖点**。
2. **可核对性优先于智能度**：单元格级引用（Claude/ChatGPT）、绿标签与高亮（Excel）、"Show code"（Gemini）、"改动摘要"（Agent 模式）——用户要能回答"它到底改了什么、依据哪格"。
3. **数据口径三者并用**：**范围选择**（Gemini 选 tab、Airtable 选字段、Notion 只用本行）× **聚合/抽样**（Airtable 词数上限、ChatGPT 文件过大只分析部分）× **不回训 + 权限裁剪**（M365 租户边界、Airtable 按协作者权限、OpenAI 企业默认不回训）。这三条正对应本仓第二份调研（数据最小化）要落的接口。

### 2.2 数据面事实

- **导出确实有 Excel**：`data/files/6c03e7f8-….xlsx` 落盘；后端 `excel/ExcelWriter.java`；前端 `SpreadGrid#toXlsxBlob` 自产 OOXML（`frontend/src/components/SpreadGrid.vue:333`，注释写明"不用 ExcelIO 保存，避免评估版水印表被后端当数据表读"）。
- **导入确实有 Excel 输入面**：`ImportWizardView` 上传 → `SpreadGrid#loadFromXlsx`（`:302`）→ 本地校验 → `PUT /tasks/{id}/files/{defCode}` → `ExcelReader` 解析 → 预检 → 暂存 → 发布。
- **列映射是"精确匹配"，不是"映射建议"**：`excel/ExcelReader.java:89-109` 只认 `label`（去掉 `*`）与 `code` 两种写法，匹配不上就变成 `_unknown_<col>` 后被 `:56` 静默跳过。前端只在 `missingHeaders.length>0` 时弹一条 warning（`ImportWizardView.vue:622-624`）。
- **服务端预检只查三族规则**：必填（`PrecheckJobRunner.java:153-169`）、主键重复（`:171-185`）、引用值存在（`:203-229`），**全部 ERROR，`rowWarnings` 从未自增**；类型/枚举/日期格式服务端不校验（前端 `utils/excel.ts:119 validateCell` 有）。
- **暂存区有行级操作类型、无字段级差异**：`ConfigStagingRow.opType` = `UPSERT/DELETE`（`data/entity/ConfigStagingRow.java:24`）；`ImportWizardView.vue:149-172` 的核查表只展示"操作=写入/删除"与暂存值，**不给 old→new**，且只显示前 100 行。
- **数据读取服务层已具备条件查询**：`ConfigDataService.findPagedFiltered`（`:59`）、`countFiltered`（`:69`）、`filterRows`（`:95`）；REST 侧 `DataController:71`（分页 + `conditions`）与 `:92`（count）——**能力在服务层，只是没接工具**。
- **模型侧的数据入口只有"行数"**：`ContextBuilder.buildContextMessage`（`ai/tool/ContextBuilder.java:75-112`）给的是页面/任务/步骤/已选配置项，**不含任何数据行内容**。

### 2.3 缺失面清单（逐条对照现有工具）

| # | 缺失 | 对照现有工具 | 造成的可观测后果 |
|---|---|---|---|
| M1 | **读不到数据行** | 只有 `get_row_count`；`DataController` 的分页+conditions 未接工具 | 用户问"XN 地区 CNY 的记录长什么样"，AI 只能回"共有 N 行" |
| M2 | **读不到单元格/工作簿内容** | `open_export_file_editor` 无读写参数；`SpreadGrid#collectRows`（`:314`）只在前端内存 | AI 无法核对"导出文件里到底写了什么" |
| M3 | **写不了单元格/行** | 无 `set_cell`/`patch_rows`；SpreadGrid 可编辑但只由人手 | 任何"修订"都只能靠人 |
| M4 | **看不到预检明细** | `ValidationIssue` 已落库（def/field/row/message/severity），但无读取工具；`check_job_status` 只给 `errorCount` | "为什么这批导不进去"答不出，只能让人自己翻界面 |
| M5 | **无聚合/摘要能力** | 无 group by / 去重数 / 空值率 / 异常值 | 无法在不搬全表的前提下回答"分布如何" |
| M6 | **无导入列映射诊断** | `ExcelReader` 精确匹配 + 静默丢弃未知列 | 用户拿到"缺列"提示，但不知道"这一列该映射到哪个字段" |
| M7 | **无字段级 diff / 预览** | 暂存只有 `opType` + 前 100 行 | 发布前看不到"这个值从 A 改成 B" |
| M8 | **无公式生成/解释** | — | 结构性不需要（列由字段定义驱动），见 §③ 明确不做 |
| M9 | **无图表/透视** | — | 导出到 Excel 后由用户自己做，见 §③ |
| M10 | **无"AI 编辑"的撤销/版本** | 有 staging + 行 `version` 字段 + 发布，但不是"一次 AI 编辑会话"的可撤销单元 | 若将来做 M3，必须先补这一层 |

### 2.4 数据口径现状（与第二份调研的接口位置）

- 唯一硬约束：`app.ai.tool-result.max-rows: 200` / `max-chars: 8000`（`application.yml:155-160`），由 `ai/tool/ToolResultLimiter.java` 在**回填 `role:tool` 前**施加；前端帧与 Redis 台账始终是全文（两条通道分离）。`ToolResultLimiter` 会加截断标记。
- 先例口径：`list_tasks` 固定 20 条并在超出时**显式告知**总数（`AiTools.java:158-176`，注释要求"值、描述、告知三者同改"）。
- 现状的"好处"：因为 AI 根本看不到数据，本仓天然接近**数据最小化**。任何新增读数工具都是**净新增的数据出仓面**，必须自带范围选择 + 投影 + 上限 + 告知四件事。
- **与第二份调研（数据最小化）的接口**（`docs/research/调研-AI上下文数据最小化业界惯例-2026-10-21.md`，§4.1/§4.2，同一工作树内由并行调研产出）：
  - 该稿把本仓数据分五档 **D0 契约 / D1 元数据 / D2 业务数据行 / D3 PII / D4 全量数据集**，并判定现状 18 工具**全部只回 D0/D1**（无一返回业务数据行）——与本节判定互相印证。
  - 其 **R3** 给出本类工具的硬阈值：**默认 0 行；确需样本 ≤20 行、总长 ≤2000 字符，且必须回"共 N 条"**；**R8** 规定 D2 超 20 行或 D4 任意规模**禁止走上下文**，只能走服务端聚合或产出文件，并要求"新增 `get_*_rows` 类工具须附 D2 授权记录"。
  - 结论：本稿 §③ 的所有读数类场景**必须按 R3/R8 收敛**（20 行而非 200 行；200 行只是 `ToolResultLimiter` 的外层兜底），`aggregate` 动作是首选形态（走 P2 聚合，不碰 D2）。

## ③ 场景识别与取舍建议

前提：本仓是**配置管理工具**（配置定义 → 数据行 → 导出/预检/导入/发布），不是通用电子表格。场景必须落在"配置数据的导入/预检/导出/修订"这条线上；通用表格能力（公式引擎、图表、协作编辑）不在产品面内。

### 3.1 建议做（按优先级）

| 优先级 | 场景 | 形态 | 理由与依据 |
|---|---|---|---|
| **P0** | **预检问题可读**：`get_precheck_issues(jobId, defCode?, severity?, offset, limit)` | 后端只读；返回"按 配置/字段/规则族 聚合的计数 + 前 N 条明细 + 分页游标" | ① 业界把"异常检测/摘要"当表格 AI 的基座能力（Gemini 的 insights、Pulse 的离群叙述、Airtable 的"出错的单元格"分档）；② 本仓 `ValidationIssue` 表已存在、字段齐全，只差一个读口（M4）；③ 这是"AI 解释为什么导不进去"的唯一闭环，且**零写入风险**；④ 落地成本最低：服务层已有 repository，按 `jobId` 查询即可 |
| **P0** | **数据行可查（带投影与上限）**：`query_data_rows(defCode, scopeKey?, conditions?, fields?, offset, limit)` | 后端只读，复用 `ConfigDataService.findPagedFiltered` / `countFiltered`；**强制字段投影**（默认只回主键 + 3 列），**默认 20 行、硬上限 20 行**（D2/最小化 R3），总长 ≤2000 字符，超出给"共 N 行，已回 M 行 + nextOffset" | ① 业界没有任何产品把整表塞进模型：Gemini 让用户选 tab、Airtable 按引用字段+词数上限、ChatGPT 明说大文件只分析一部分；② 本仓 `get_row_count` 是"半成品"（M1），服务层条件查询已具备（`ConfigDataService:59/69`）；③ 没有它，"AI 解释预检问题"只能停在规则层，无法指认具体行；④ 阈值不是拍脑袋：D2 取样口径取兄弟调研的 R3（≤20 行/2000 字符/"共 N 条"），**200 行只是 `ToolResultLimiter` 的外层兜底** |
| **P1** | **聚合/摘要**：并入 `query_data_rows` 的 `aggregate` 动作（按字段 group by 计数、去重数、空值率、min/max） | 后端只读，返回小结果集 | ① 这是"数据最小化"与"可解释"的交点：先把数据缩成统计量再进模型；② 业界对应 Gemini 的"Identify trends"、Airtable 的批量分类/摘要；③ 成本低（一条 SQL/内存聚合），收益是让"有多少/分布如何"不再依赖搬行 |
| **P1** | **导入映射诊断**：`inspect_import_file(taskId, defCode)` | 后端只读；读已上传 xlsx 的表头与 `_meta`，输出：已匹配列 / 缺失字段 / 多余列 / **疑似映射（列名→字段，含理由与置信）**；**只给建议，不改文件、不改定义** | ① "导入映射（文件→表结构）"是业界公认的一等场景（飞书"AI 粘贴录入"自动识别字段结构、Airtable 附件抽取→字段、Notion AI 建库）；② 本仓现状是精确匹配 + 静默丢弃（M6、`ExcelReader:89-109`），用户拿到的是"缺列"而不是"该怎么映射"；③ 风险可控：只读诊断，落库仍需人工改文件或后续确认流程 |
| **P2** | **修订建议（写前预览）**：`propose_row_patch` → 生成"字段级 old→new 变更集" → 确认门 → 由既有作业写入**暂存区**（不直接写生产） | 后端 WRITE/DANGER + 前端 diff 卡（可复用 `generative_form` 的白名单表单与确认门） | ① 业界铁律是"先说后做 + 可核对"：Excel 计划模式/绿标签、Gemini 预览卡、ChatGPT/Claude 改前许可、Airtable 永不覆盖人工格；② 本仓已有 staging（`UPSERT/DELETE`）与发布分离，天然是"落暂存→人复核→发布"的形态；③ **必须后置**：它依赖 M7（字段级 diff）与 §2.4 的数据口径先定，否则会变成"AI 盲改" |

> P2 的边界写死：**AI 只能写暂存区**，`start_publish` 仍是独立的人确认动作（FR-5.3 确认清单不动）。

### 3.2 可做可不做（有价值但不构成"能力缺口"）

| 场景 | 判断 | 理由 |
|---|---|---|
| **NL → 结构化条件的回读**（模型产出 `conditions` 后，把"将按 X=Y 过滤"回显成一张卡再执行） | 可做（低成本） | `set_condition` 已能用 `FieldQueryCondition` 结构化表达（`AiTools.java:447-482`），缺的只是"回读确认"这一步。业界依据：ServiceNow 的 NL 查询会把条件落成**可见可编辑的 filter**，而非黑箱结果 |
| **预检问题 → 修复建议**（按 issue 族给"批量填 X / 改引用 Y"的建议文案） | 可做 | 只产出建议、不动数据；与 P0 的 `get_precheck_issues` 是同一数据源。价值中等，因为很多错误必须人判断业务值 |
| **由 Excel 反推配置定义草案** | 可做（P3，且必须人工确认） | 业界有先例（Notion AI 建库、飞书智能搭建、钉钉一句话建表），但本仓的定义是**受控结构**（字段类型/必填/主键/引用/枚举），反推易错且下游引用需人工。真要做得限定为"草案 + 逐字段确认"，绝不自动落库 |
| **导出后分析口径建议**（"导出后建议按 region 做透视"这类文本） | 可做 | 成本近零（纯生成），但价值有限：用户拿到 xlsx 后用什么工具分析与本仓无关 |

### 3.3 明确不做

| 不做 | 理由与依据 |
|---|---|
| **AI 直接改单元格并落库（无预览、无确认的内联编辑）** | 与 FR-5.3 的确认清单与"单一事实源"口径冲突；业界 2025–2026 全部在往"计划/预览 + 撤销"收（Excel Plan Mode、Gemini preview card、ChatGPT for Excel 改前许可、Airtable 不覆盖人工格）。做它等于逆着行业走 |
| **整表/整个 xlsx 进 prompt** | 与 `tool-result.max-rows=200`/`max-chars=8000` 的既有预算直接冲突，也与上下文统计专项的 L1 工具结果清除策略冲突；数据最小化上不可接受 |
| **AI 自动建/改配置定义 schema（DDL 级）** | 定义是全局结构，改它会波及引用、导出模板、预检规则；连 Notion 都只允许"AI 新建库"而**不允许编辑已有库**。本仓连"新建"也应走人工 |
| **通用公式引擎 / 内嵌图表 / 多人协作编辑** | 不是本仓产品面：列由字段定义驱动，没有自由公式的位置；图表属于导出文件的下游（用户拿到 xlsx 用 Excel 做） |
| **AI 自动排版/美化工作表** | 收益低、样式面在 SpreadJS 里，且会与"导出模板由 `ExcelTemplateBuilder` 单点生成"的口径打架 |
| **自然语言直接发布/绕过预检** | 已有 `start_precheck`/`start_publish` 的 DANGER 门禁，任何"跳过预检"的捷径都是在削弱它 |

## ④ 与队列内四件的依赖关系

队列四件指：模型配置功能、上下文统计与压缩、i18n 与工具可配置、多实例与资源治理（依据：`docs/决策看板.md` 10-21 行、`docs/任务看板.md` 10-21 行）。

### 4.1 上下文统计与压缩专项（最强依赖）

- **每一件新增读数工具都是"往上下文里倒东西"的新入口**。必须复用 `ToolResultLimiter`（`ai/tool/ToolResultLimiter.java`）+ `app.ai.tool-result.max-rows|max-chars`，并按 `list_tasks` 的先例写死"默认条数 + 超出告知"的数字规格（`AiTools.java:158-176` 的注释要求值/描述/告知三者同改）。
- **L1「工具结果清除」会改写本类工具的设计前提**：压缩一旦清掉上一轮的工具结果，模型就"忘掉"了上一轮读到的行。因此：读数工具必须**幂等且参数可复述**（同样的 `defCode/conditions/offset` 能重放出同样结果），**不能依赖"模型记住刚才那 20 行"**；跨轮引用只允许引用"聚合摘要"或"游标"。
- **建议的接口**：新增工具声明 `maxRows` 与结果形状（纯文本/表格/JSON），交给压缩谱系决定"这条结果可被整块清除还是必须保留"（例如 `get_precheck_issues` 的聚合计数值得保留，明细行可清）。
- 依据：`docs/research/设计-上下文统计与压缩专项-2026-10-21.md` §1（L1→L2→L3 三级、reserve=13000、压缩只改"喂给模型的那一份"）与 §2.5（现状只有字符/条数裁剪，与 token 无关）。

### 4.1b 数据最小化调研（D 分级 / R1–R9）是"闸门"不是"参考"

- §③ 的 P0 读数工具与 P2 写工具都要过 `调研-AI上下文数据最小化业界惯例-2026-10-21.md` §4.2 的判据：
  - **R3**（D2 取样 ≤20 行 / ≤2000 字符 / 必须回总数）是**产品阈值**，优先于 `ToolResultLimiter` 的 200 行兜底；
  - **R8**（D2 超 20 行或 D4 一律不走上下文）意味着：**不排期"整表预览"「全 xlsx 问答」这类场景**，因为它们只能走服务端聚合或产出文件；
  - **R8 的"新增 `get_*_rows` 类工具须附 D2 授权记录"** 是本稿 P0 场景落地的前置流程件（谁批准、在哪登记），建议随批 1 一起补一份 D2 授权记录。
- 与之配套：`aggregate`（P2 聚合）应作为**默认**回答形态，"给我看几行"是例外路径（需显式理由 + 20 行上限）。

### 4.2 模型配置功能专项

- **分母/预算接口**：读数工具的"一次最多看多少行"应由 `ContextLimitResolver`（该专项为 DB `ai_model.max_context` 留的接缝）推导，而不是各工具自己拍数字；否则换模型后上限失真。
- **能力差异**：`inspect_import_file` 的映射质量依赖模型的结构化输出与长上下文能力；`propose_row_patch` 需要严格 JSON 输出。模型配置的 allowlist 应能标注"是否允许承担表格类工具"。
- **配置面**：可在「AI 设置」页加两个开关——"允许 AI 读取配置数据行"（默认关/按环境）、"允许 AI 生成修订建议"（默认关）。这与 Airtable 的"企业管理员可整体关闭 AI、但不支持字段级排除"是同一取舍。
- 依据：`docs/research/设计-模型配置功能专项-2026-10-21.md` §1（provider/model DB 为真源、每请求覆盖、provider 注册表）与 §2.4（上下文上限现状为空）。

### 4.3 i18n 与工具可配置专项

- 新增工具的 `name` / `description` / 每个 `@ToolParam` 的描述都是**模型可见文案**，必须进该专项的文案抽取面（否则中文描述漏抽，英文环境里模型看到的是中文）。
- 工具开关：`propose_row_patch` 这类写工具应默认关闭、按环境开启，配置粒度与该专项的"工具可配置"一致。

### 4.4 多实例与资源治理专项（B23L1）

- 读数与聚合是 DB/CPU 密集面：多实例下要限流（参照作业并发口径），且**分页游标必须无状态**（不能存实例内存，否则跨实例翻页丢游标）；优先用 `offset/limit` + 稳定排序（主键），不要服务端快照游标。
- `propose_row_patch` 的落库必须走**既有作业 + 租约**（不要在请求线程里做长事务），复用 `JobService.createAndStart` 的形态；否则多实例下会出现双写。
- 依据：`docs/research/设计-B23L1多实例与资源治理专项-2026-10-21.md`；本仓已有 `JobHeartbeatRegistry`、`LeaseService` 等基座。

## ⑤ 落地批次切分（若用户批准）

> 原则：**先只读、再诊断、最后写**；每批都能独立验收、独立回滚；不改 FR-5.3 的确认清单（新增 DANGER 工具须单独裁决）。

### 批 1 · 让 AI 看得见（只读）

- 范围：`get_precheck_issues` + `query_data_rows`（含 `aggregate` 动作）。
- 范围外：任何写入、任何前端新组件、任何 schema 变更。
- 验收口径草案：
  1. 三条问句走通：①"这个任务的预检为什么失败？"→ 回聚合 + 至少一条可定位明细（配置/字段/行号）；②"XN 地区 CURRENCY 有多少行？"→ 与 `DataController:92` 的 count 一致；③"给我看前 5 行 CNY"→ 只回投影字段且 ≤5 行。
  2. 双层上限都要可断言：**数据行层**按最小化 R3（≤20 行 / ≤2000 字符 / 必回"共 N 条"）；**通道层**仍受 `max-rows=200` / `max-chars=8000` 与 `ToolResultLimiter` 截断标记兜底。两层都要有单测（构造 25 行结果：模型只看到 20 行 + 总数告知）。
  3. 空集、非法 `defCode`、非法 `conditions` 三种边界各有单测；非法参数走 `ConflictException(CODE_ILLEGAL_ARGUMENT)`，不以字符串伪造成功。
  4. 工具描述含"最多返回 N 条"的字样，且与实现常量同源（防"描述说 20、实现 200"）。
  5. 前端零改动（走既有工具卡）；E2E 增 1 条主用例（任务中心提问 → 看到预检聚合 → 追问一行明细）。

### 批 2 · 导入映射诊断（只读）

- 范围：`inspect_import_file`；输出"已匹配/缺失/多余/疑似映射（含理由与置信）"。
- 验收口径草案：
  1. 用仓内样例 `data/files/6c03e7f8-….xlsx` 与一份"列名被改过"的副本各跑一次：前者应 100% 匹配，后者应给出疑似映射而不是"缺列"一句话。
  2. 未知列不再静默：诊断结果里必须逐列列出（对齐 `ExcelReader:106` 的 `_unknown_` 现状，但把"静默"变成"可见"）。
  3. 不写库、不改文件、不改定义（可用"调用前后文件 hash 一致 + 定义字段数一致"作为断言）。
  4. 诊断结果同样受 max-rows/max-chars 约束；列数 > 上限时给"仅显示前 M 列"告知。

### 批 3 · 修订建议与预览确认（写，仅暂存）

- 范围：`propose_row_patch`（生成字段级 old→new 变更集）+ 前端 diff 预览卡（复用白名单表单/确认门）+ 由作业写入暂存。
- 验收口径草案：
  1. **拒绝即不写**：确认门拒绝后，暂存区行数与 `opType` 分布不变（前后对账）。
  2. **批准只写暂存**：生产表 `config_data_rows`（`ConfigDataRow`，`@Table` 见 `data/entity/ConfigDataRow.java:11`）的 `version` 不变；`start_publish` 仍需单独确认。
  3. **预览可见**：卡片逐条展示 `rowKey` + 字段 + old→new + 变更理由；**单次提案 ≤20 行**（D2/R3：old 值是业务数据，进模型即出域），超出必须拆批并告知"本次仅处理 M / 共 N 行"；卡片本身是人看的 UI，不受 token 预算约束。
  4. **幂等**：同一变更集重复批准不产生重复暂存行（按 `rowKey` 去重）。
  5. **审计**：每次 AI 发起的修订建议在作业/日志里留"来源=AI + 提案 id"，便于回溯（对应业界的"绿标签/Show Changes"）。

### 批 4 · 可选增强

- `set_condition` 的条件回读卡（"将按 region=XN 且 code=CNY 过滤，共 N 行"）。
- 预检问题的"修复建议文案"（只读建议，不落数据）。
- 明确**不排期**：图表/透视、公式引擎、schema 反推（除非用户另立专项）。

### 风险与前置

- **新增 DANGER 工具需裁决**：批 3 若引入新的写工具，必须回到"确认清单"层面确认它属于既有四类（导出/检查/导入/发布）之外的第五类，还是并入"导入"语义。

- **二手来源边界**：本稿中 Excel Plan Mode 细节、Claude for Excel、钉钉 AI 表格的确认粒度均来自二手，**不足以为硬性设计依据**；凡引用处已在表 B 标注。官方可直连的依据是 Microsoft Learn 架构页、Google Workspace 帮助、Airtable Support、Notion 帮助、飞书帮助、OpenAI Help/公告。

### 6.1 场景分类学：8 族 / 44 个子场景

族划分不是自拟：**SheetCopilot（NeurIPS 2023）** 从 SuperUser 约 1.3 万条表格问答中过滤后，用 LLM 打标聚出六类 —— `Entry and Manipulation / Management / Formatting / Charts / Pivot Tables / Formulas`（[论文](https://proceedings.neurips.cc/paper_files/paper/2023/file/0ff30c4bf31db0119a6219e0d250e037-Paper-Conference.pdf)）。本节把"管理/录入"细化为**行列表结构、条件修改、数据质量**三族（因为这三类在本仓语境下命运完全不同），并补上"查找替换"与"结构"两族（教程与官方文档都单列的能力面）。

#### F1 查找替换族（6 个）

> 证据（A）：InvisibleMentor 的 20 人观察研究里，**"反复用查找替换去归一化分类值（如性别）"是被点到次数最多的低效工作流**（P2/P11/P19），且这正是该研究改进建议的主打场景（[arXiv 2509.26557](https://arxiv.org/abs/2509.26557)）。证据（B）：Excel 的查找替换支持通配符 `?/*/~`、Sheet/Workbook 范围、按行/按列、Match case、Match entire cell contents，且**带格式替换**（Find 可用格式当条件，Replace 只支持 Formulas）（[Microsoft 支持](https://support.microsoft.com/en-us/excel/get-started/find-or-replace-text-and-numbers-on-a-worksheet)）。

### 6.3 从谱系反推工具参数模型

#### 6.3.1 五元组：selector × predicate × operation × value × preview/commit

一个"AI 改表"工具族的统一形参，不建议按场景各造一套：

| 槽位 | 取值域 | 为什么必须单独建模 | 本仓落地 |
|---|---|---|---|
| `scope` | `sheet`（整表）/ `columns`（列集合）/ `rows`（行号区间）/ `rowKeys`（业务键集合）/ `selection`（当前选区） | 44 个子场景里，**歧义 80% 出在"范围"**（"这列"是哪列？"这些行"是哪几行？） | 前端可用 `getSelections()` 拿真实选区；后端只有 `rowKey` 语义，**不接受表行号**（行号会因排序/筛选漂移） |
| `predicate` | 复用 `FieldQueryCondition{scopeKeys, fields[{fieldCode, operator, value}]}` | 条件更新的核心；**本仓已有前后端同源契约**（`ai/tools/AiTools.java:466`、`types/condition.ts`） | **不要再造 DSL**：让模型直接产出既有结构，前端原样回显（"将按 region=XN 且 status=OLD 过滤"） |
| `match` | `exact / contains / prefix / wildcard(*,?) / regex / wholeCell / ignoreCase` | F1 的 6 个子场景全靠它区分；`contains` 与 `exact` 混淆会误改 | SpreadJS `SearchFlags` 只有 `ignoreCase/exactMatch/useWildCards/blockRange`，**无 regex**（`gc.spread.sheets.d.ts:43203-43227`）→ 正则必须在应用层实现 |
| `operation` | `replace / set / fillDown / fillSeries / fillBlank / normalize(trim·case·width·number·date) / format / deleteRows / mark(conditionalFormat) / addComment` | 粒度决定模型能否一次说对 | 见 6.3.3 的"细粒度优于整合式"证据 |
| `value` | 字面量 / 模板（`${a}-${b}`）/ 引用其他字段 / 枚举选项 | "改成什么"经常依赖其他列 | 枚举型字段应带 `options` 校验（定义里已有 `optionsJson`） |
| `preview` | `count`（影响面）/ `sample-diff`（前 N 条 old→new）/ `full-diff`（全量，仅前端卡） | 决定"人能不能在落之前看懂" | 见 6.3.4 三档 + 与最小化 R3/R8 的换算 |
| `commit` | `auto`（只读）/ `confirm`（DANGER 门）/ `staging`（写暂存） | 只读、改暂存、改生产是三种风险 | 复用既有 `@ToolRisk` 三档（READ/WRITE/DANGER）与 `ConfirmGate`，**不新增机制** |

#### 6.3.2 用户口语 → 参数的五个真实歧义（决定"何时必须反问"）

| 用户原话 | 歧义 | 正确处置 |
|---|---|---|
| "把空格去掉" | 是去掉**首尾**空格，还是把**所有**空格（含词中）删掉？ | 默认 trim；若命中含词中空格的值，先回"这 3 个值中间有空格，是否一并删？" |
| "把这一行删了" | "这一行"是**当前选区**、**第 N 行**、还是**某个 rowKey**？ | 有选区则用 `selection` 并回显 rowKey；无选区则必须反问 |
| "日期统一一下" | `01/02/2026` 是 1 月 2 日还是 2 月 1 日？`20260105` 是日期还是数字？ | 列出**歧义样本**（≤5 条）+ 两种解释，让人选；不许猜 |
| "状态改成已发布" | 改**全部行**、**筛选中的行**、还是**选中的行**？ | 用 `count` 预览说出影响面（"将改 1,240 行"），差异大时强制反问 |
| "把重复的删掉" | 按**整行**判重还是**按主键**判重？保留第一条还是最后一条？ | 本仓按定义的主键字段判重（`buildRowKey`），并把"保留规则"写进预览 |

这五条正好落在既有 `generative_form(scenario=CLARIFY)` 的能力面内（`AiTools.java:543`），**不需要为澄清新造一套 UI**。

#### 6.3.3 单工具还是工具族？——细粒度胜出的实验证据

SheetCopilot 的消融实验直接比较了"整合式动作"与"细粒度动作"：把 `SetFormat` 拆成更细的格式动作后，`Exec@1`/`Pass@1` 明显提升；反之把图表属性塞进一个 `CreateChart` 则显著变差（论文 Table 4）。原因是**参数一多，模型就猜不准**。

对本仓的直接推论：
- **不要**做一个 `edit_sheet(sheet, range, operation, value, ...)` 万能工具；
- 按族拆成 3~5 个工具即可覆盖 80% 场景：`replace_values`（scope+match+value）、`update_rows`（predicate+set）、`normalize_column`（column+rule）、`delete_rows`（predicate）、`mark_rows`（predicate+style）；
- 每个工具的 `operation` 用**枚举**而不是自由文本，枚举值同时就是模型可见的 Schema（延续 AI 仓既有"类型化入参让 Schema 自带形状"的手法，见 `AiTools.java:429-482`）。

#### 6.3.4 预览颗粒度三档（与数据最小化 R3/R8 的换算）

| 档 | 给人看什么 | 进模型的数据量 | 适用 | 依据 |
|---|---|---|---|---|
| **P0 计数级** | "将影响 **N 行 / M 格**，分布：region=XN 812 行、region=SH 428 行" | **0 行业务数据**（只有计数与分组） | 默认档；所有写操作都先出这一档 | 走最小化调研的聚合通道（P2 聚合），不触 D2 |
| **P1 采样 diff** | "前 20 条：`rowKey=CNY/Xn`，`status: OLD→NEW`" | ≤20 行 / ≤2000 字符 | 人要求"给我看看"时 | 最小化 **R3**（`调研-AI上下文数据最小化业界惯例-2026-10-21.md` §4.2） |
| **P2 全量 diff（仅前端）** | 前端 diff 卡逐行渲染，可筛选/翻页 | **0 行**（数据不经模型，走 `frontend_tool` 通道） | 大批量、要逐条核 | 本仓已有"前端帧/台账全文 vs 模型侧裁剪"的双通道（`ToolResultLimiter` 注释） |

关键设计点：**P2 的存在让"大批量修订"不必违反 R3**——模型不必看见 3 万行，它只需要签一张"变更集 id"，把渲染交给前端。这与 Excel 的"绿标签 + 高亮格 + 变更摘要"、Claude 的"改后高亮所有改动格"是同一思路的仓库版实现。

### 6.4 与 SpreadJS 的 API 映射（逐族核过 `node_modules` 的 d.ts）

核对源：`frontend/node_modules/@grapecity/spread-sheets/dist/gc.spread.sheets.d.ts`（本仓已安装版本），避免抄网文写错 API。

| 族 | 能力 | SpreadJS API（已核） | 缺口/注意 |
|---|---|---|---|
| F1 查找替换 | 查找 | `spread.search(SearchCondition)` / `sheet.search(...)`，`SearchFlags` = `ignoreCase=1 / exactMatch=2 / useWildCards=4 / blockRange=8`（d.ts:43203-43227） | **无 replace API、无 regex flag** → 替换=先 `search` 拿命中格，再 `setValue`；正则在应用层用 `RegExp` |
| F1 | 只替换格式 | `getCell(r,c).formatter()` / 样式对象 | 需先读命中格再写样式，逐格成本高 |
| F2 行列 | 插入/删除行列 | `addRows/deleteRows/addColumns/deleteColumns`（d.ts:23924/24222） | 本仓**禁止**插删列（破坏 `_meta` 列序） |
| F2 | 隐藏/冻结 | `setColumnVisible(col,bool)`、`frozenRowCount(n,topRow)` | 纯展示，导出前需还原可见性 |
| F2 | 排序 | `sortRange(row,col,rowCount,colCount,byRows,sortInfo)`（d.ts:25009） | 排序后行号漂移 → 写操作一律用 rowKey 定位 |
| F2 | 筛选/只改可见行 | `rowFilter(new GC.Spread.Sheets.Filter.HideRowFilter(range))`（d.ts:25599） | 可见行集合要显式取，不能"假设筛选生效" |
| F2 | 转置/复制 | `copyTo(..., CopyToOptions)` + `pasteSpecialOptions.transpose`（d.ts:32107） | 本仓不做转置 |
| F2 | 拆分/合并列 | **无 TextToColumns API**（全库无该符号） | 只能"读整列→改造→写回"，天然适合应用层/服务端做 |
| F2 | 去重 | **无 dedupe API**；有 `UniqueRule/DuplicateRule` 条件格式 | 去重=读列→建索引→删行，必须给预览 |
| F2 | 填充 | `fillAuto(startRange, wholeRange, {fillType, series, direction})`（d.ts:24280） | 序列填充可托付引擎；"按例填充"（Flash Fill 式）引擎没有，需模型生成值再写 |
| F3 条件修改 | 条件格式标记 | `sheet.conditionalFormats.addRule(rule)`（d.ts:23660） | 规则可导出到 xlsx（`ExcelWriter` 是否保留需另验） |
| F4 单元格 | 取值/赋值 | `getValue/setValue`、批量 `getArray/setArray`（d.ts:24449） | 批量读写**必须**用 array 版本，逐格调用在大表上会卡主线程 |
| F4 | 选区 | `getSelections(): Range[]`（d.ts:24996） | 这是"显式选区"槽位的唯一可靠来源 |
| F4 | 批注 | `sheet.comments.add(row,col,text)`、`comments.clear(range)` | 不进业务数据 |
| F4 | 数据校验 | `setDataValidator(row,col,dv)`，整列用 `setDataValidator(-1,col,...)`（d.ts:17874） | 与 `utils/excel.ts:221 applyColumnsToSheet` 的现有做法一致，可复用 |
| F5 公式 | 读写公式 | `setFormula/getFormula`、`getArray(..., getFormula=true)` | 本仓不做公式列 |
| 通用 | 撤销 | `spread.undoManager()`（d.ts:23558） | **AI 操作用户能否一键撤销，取决于是否走同一 undo 事务**——这是 P2 阶段必须先验的技术点 |
| 通用 | 合并单元格 | `addSpan/removeSpan`（d.ts:20160）、`getSpans` | 拆合并单元格=读 span→逐格写值→removeSpan |

**一条硬结论（写进 §⑦ 的"明确不做"）**：因为 `ExcelReader` 是**按列号对齐 `_meta` 给的 fieldCodes**（`ExcelReader.java:31-34,54-62`），**插列/删列/转置会让列与字段错位而系统毫无察觉**。所以"AI 改表结构"不是"风险高"，而是**在本仓当前映射实现下会静默读错数据**——必须明确不做，直到映射改成"按表头名匹配"。

### 6.5 本节对"AI 适配度"的两条经验规则（从 44 条里归纳）

1. **"值变换"比"结构变换"适配度高一个数量级**：F1/F6 的子场景几乎都能用"读→算→写回+预览"闭环；F2/F7 的结构操作要么动 schema（禁），要么动行号（漂移），要么依赖引擎缺失的 API。
2. **"能算出正确答案"不等于"能安全落库"**：F3 的 4 个子场景模型都能算对，但**删除/批量更新**必须先过 preview + 确认门；这也是为什么 44 条里只有 6 条能进"建议做"（§⑦）。

### 7.4 三档变动一览（给裁决用的一句话）

- **降 2 项**：Excel 反推定义（P3→P4）、导出后分析建议（→不做）。
- **不变 10 项**：其余条目原样生效（建议做 3、可做可不做 1、明确不做 6）。
- **判断依据的边界**：升/增的排序依据是"证据 A（E1/E2/E3）+ 本仓相关性（配置字典表）"，不是"通用表格里最常见"。例如 F5 公式族在通用场景证据很强（E4），但在本仓判"不做"——这正是"配置管理工具 ≠ 通用表格"的分界线。
