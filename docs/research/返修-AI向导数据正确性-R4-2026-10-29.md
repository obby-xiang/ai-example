## R4-1（Critical）：主 handler 统一走 `validateConditionPayload`

### 根因

`export.setConditions` 此前只靠 `parseConditionJson` 的 `null` 判断"清空"：

```ts
const condition = parseConditionJson(typeof payload.conditions === 'string'
  ? payload.conditions : JSON.stringify(payload.conditions ?? {}))
// 空串 / 坏 JSON / [1,2] / {fields:"oops"} 全部 parseConditionJson → null
// → draftModelFromCondition(null) → buildConditionOutcome === 'cleared'
// → draftModels/touched/counts 写入 → PUT "{}" → 回「已设置 … 并落库：全部数据（无条件）」
```

于是四类坏载荷被静默解释成"清空条件"（= 无条件 = 导出全部），且网络/状态都已写。R3 只修了
契约层兜底，页面主 handler 漏了。

### 修改（`frontend/src/views/ExportWizardView.vue`）

```ts
const verdict = validateConditionPayload(payload.conditions)
if (!verdict.ok) {
  const reason = verdict.issues?.length
    ? `${describeConditionInputIssues(verdict.issues)} 本次未设置 …`   // 非法空值走本地化成文
    : verdict.reason                                                   // 解析/结构错误用判据自带文案
  return { ok: false, reason }
}
// 之后才写 draftModels / touchedConditions / counts，PUT 用 verdict.serialized
```

- 四类坏载荷（空串 / 坏 JSON / 非对象 / 结构坏）**在写入之前**失败：零 `setCondition`、
  零 `workspace.queryConditions` 变动、零草案/touched/counts 变动。
- `PUT` 用 `verdict.serialized`（清空恒为 `"{}"`；合法复杂条件为规范化后的内容，逐字保留
  同字段多条件、含逗号 IN）。
- 只有**显式 `{}`** 才清空；`{"fields":[]}` 这类"有结构没内容"的载荷按坏载荷拒绝（见下）。

### 配套收紧：`validateConditionPayload` 的清空口径

`cleared` 仅在载荷是**空对象**（`Object.keys(parsed).length === 0`）时放行；否则拒绝并提示
"如需清空条件请显式传 {}"。这同时把契约层与页面收成同一条规则（R3 时 `{"fields":[]}` 曾按清空处理，
自 R4 起拒绝）。

### 测试（精确单点，逐条 RED → GREEN）

`frontend/tests/export-wizard-set-condition-validation.spec.ts`（本文件共 11 条；R4 新增 6 条）：

## R4-2：清空不写 `defCode` 占位

### 根因

清空时 `workspace.setQueryConditions(defCode, null)` 会留下 `{ [defCode]: null }`：
`buildContext().extra.queryConditions` 与 `get_workspace_state` 会把它报成"已设置过条件"，
模型据此以为还有筛选（实际是无条件）。

### 修改

- `frontend/src/stores/workspace.ts` 新增 `clearQueryConditions(defCode)`：删键（不存在则不动），
  记一条「清空 X 的查询条件」动作；
- 契约层 `set_conditions` 与页面 `export.setConditions` 在 `condition === null` 时统一调用它，
  非空才 `setQueryConditions`。

### 测试

- `workspace-ui-set-conditions-guard` 的 `显式 {} ⇒ 按"清空条件"落库（PUT "{}"），工作区不留该配置项占位`
  —— RED 实测 `expected { CURRENCY: null } to not have property "CURRENCY"` → GREEN；
- `export-wizard-set-condition-validation` 的同名页面用例同样 RED → GREEN（`PUT "{}"` 不变）。

## R4-3：冷却期失败的可行动成因

### 根因

导入侧冷却期（R3）让 `loadEditors` 快速失败，但 `sheet.current` 在无编辑区时返回
"`X` 的编辑区表格未挂载（请重开该标签页后重试）"、`ensureEditorLoaded` 返回"编辑区表格未能
载入（请重试…）" —— 模型读不出"定义列表读不到 / 正在冷却"，只会原地重试并继续撞冷却。

### 修改（`frontend/src/views/ImportWizardView.vue`）

新增 `definitionsUnavailableHint()`：

- 冷却中 ⇒ `配置定义列表最近一次读取失败，N 秒内不再自动重试（冷却中）`；
- 成功读到空列表 ⇒ `配置定义列表为空（服务端没有任何配置定义）`；
- 其他 ⇒ `配置定义列表尚未就绪（加载中或读取失败）`。

`sheet.current` 在"表格未挂载"检查**之前**先返回该成因（并说明编辑区未按 0 字段载入、
给出"稍后重试 / 让用户刷新"的下一步）；`ensureEditorLoaded` 的失败文案也带同一成因。

### 测试

`import-wizard-defs-readiness` 新增 `冷却期内 sheet.current 的失败文案给出可行动成因（定义不可用 / 冷却）`：

- RED：`expected 'CURRENCY 的编辑区表格未挂载（请重开该标签页后重试）。' to contain '配置定义'`；
- GREEN：文案含「配置定义」与「冷却」，仍零载入。

## 边界与不声称

- `validateConditionPayload` 的"清空"判定 = **空对象 `{}`**；`{"scopeKeys":[],"fields":[]}` 这类
  显式空数组同样被拒（提示显式传 `{}`）—— 这是 R4 的收紧口径，若上游协议需要"空数组即清空"，
  需另行裁决。
- 结构校验仍只覆盖 `scopeKeys`/`fields` 基本形状与条目必填键；算子白名单、字段是否存在由后端判
  （400 走原有"落库失败"如实回执）。
- 页面 handler 在 `taskId === null` 时仍只写表单草案（不落库），文案不变；该分支在校验通过后才写。
- 导入侧冷却 5s 为常量、页面无可见"重试定义"入口（R3 边界不变）；R4 只补失败文案成因。
