## 二、确认需要修改：高优先级

### P1-01 恢复扫描重复读取全局索引，并对每个 run 做 N+1 详情读取

- **根因**：系统线程的 `ResumeService.listRuns()` 先走 `allRunRecords()`，随后又走 `allRunIds()`，导致全局 `ai:runs` 被读取两次；`allRunRecords()` 还逐成员 `EXISTS`。每个存活 run 的 `listRun()` 再读取完整快照、3 组 pending HASH、完整 ledger、activity、heartbeat、cancel，约 9–11 次命令。
- **证据**：`backend/src/main/java/com/example/configmgr/ai/run/ResumeService.java:468`、`:512`；`RunStore.java:2305`、`:2357`、`:3152`。
- **放大条件**：候选是 24h TTL 内所有 run，包括 DONE/FAILED/CANCELLED，不只是活跃 run；再乘服务实例数与扫描周期。
- **方案**：增加“未完成 run”发现面，并在创建/终态状态维护链中同步更新、保留对账兜底；系统恢复使用轻量投影，与运维列表详情解耦；恢复路径移除 ledgerCounts、messageCount 等非必要读取；同槽小字段批量读取，禁止为优化引入跨槽 Lua。

### P1-02 多实例启动/运行扫描惊群，固定顺序与固定预算会饿死后续 run

- **根因**：每实例按同一周期完整扫描，无分布式单飞、无 jitter；候选固定按 runId 排序，失败结果也占用 `resumed` 预算，前面的永久失败项会让后续 run 长期得不到处理。
- **证据**：`backend/src/main/java/com/example/configmgr/ai/run/StartupResumeRunner.java:147`、`:423`、`:533`、`:548`、`:592`。
- **方案**：启动、定时、手工强制扫描共用带续租的分布式单飞；启动加 jitter；用轮转游标保证公平，同时保留每拍尝试上限。手工 `scan(force=true)` 同样接单飞和限频。

### P1-03 会话销毁包含多轮全量扫描、无关身份读取和重复快照读取

- **根因**：会话索引不完整时 `enumerate()` 读取全局 SET；`residualRuns()` 无条件再读一次。全局成员未先按复合成员里的 tenant/user 过滤，导致无关 run 也进入归属读取。staging/archive 最多 4 次全集群 SCAN；同一 run 在枚举、状态刷新、删除判断和 `deleteRun` 中重复完整读取。
- **证据**：`backend/src/main/java/com/example/configmgr/ai/session/AiSessionPurgeService.java:480`、`:583`、`:627`、`:669`、`:684`、`:960`、`:1118`、`:1126`、`:1186`、`:1227`；`RunStore.java:2048`。
- **方案**：五处全局 `SMEMBERS` 统一分批 `SSCAN`，包括 `residualRuns()`；先按索引成员身份过滤再读归属；复用枚举得到的 staging 列表和快照；同步预算耗尽时转现有 pending/retry，并保留台账，不能走首次枚举失败即撤销 pending 的旧路径。
- **不采用**：`GETRANGE + 假定 sessionId 位于固定字段位置`，该方案依赖 JSON 字段顺序，脆弱且不具备通用性。

### P1-04 状态写 Lua 在 Redis 内解析完整快照

- **根因**：两条取消优先状态脚本为读取 `status/cancelled`，对包含全部 `messageJson` 的快照执行 `cjson.decode`；快照越大，Redis 单线程解析越重。
- **证据**：`backend/src/main/java/com/example/configmgr/ai/run/RunStore.java:354`、`:370`。
- **方案**：增加与快照同 hash tag 的轻量状态键，在原状态写 Lua 内同步维护；取消判断改读轻量状态。删除、TTL、续租、回滚/滚动读取必须同时覆盖。

### P1-05 `activeRunIds()` 在记忆写/压缩热路径逐个完整读取快照

- **根因**：每个候选调用 `get(runId)`，读取并反序列化完整消息历史只为判断终态；stale ZSET 成员会放大 N。
- **证据**：`backend/src/main/java/com/example/configmgr/ai/run/RunStore.java:1463`；`backend/src/main/java/com/example/configmgr/ai/memory/RedisChatMemoryRepository.java:655`。
- **方案**：复用 P1-04 的轻量状态键并批量读取；同拍清理终态/失效 ZSET 成员；Redis 故障时 fail-fast，避免 N 个候选分别等待单命令超时。

### P1-06 SSE 回放无分页，内存随重挂连接数乘性放大

- **根因**：`stageReplay()` 一次读取整窗并逐帧放入无界 `LinkedBlockingQueue`，回放明确绕过实时容量闸；读取和入队处于 `emitLock` 范围，会延迟同 run 的实时帧/终帧。
- **证据**：`backend/src/main/java/com/example/configmgr/ai/run/SseChatEmitter.java:1553`、`:1565`。
- **方案**：按“帧数 + 字节数”分页读取、分批入队；用 `lastSeq` 续读剩余帧，不能直接截断丢弃；缩短持锁范围。

### P1-07 慢订阅者可以长期独占投递线程

- **根因**：投递池任务是一整个 `drain()` 循环，只有队空或写失败才退出；少量慢连接即可长期占满默认 8 条线程，最终影响健康 run。
- **证据**：`backend/src/main/java/com/example/configmgr/ai/run/SseChatEmitter.java:3134`、`:3186`。
- **方案**：每拍限制处理帧数或时间片，到点通过现有 `finishDrain/kickDrain` 重新排队，保持 FIFO、CAS 和收尾语义。

### P1-08 本地取消位可能被重注册覆盖

- **根因**：`CancellationRegistry.register()` 用 `put(false)`；Redis 写取消失败后，同 run 重驱动会清掉唯一的本地取消事实。
- **证据**：`backend/src/main/java/com/example/configmgr/ai/run/CancellationRegistry.java:101`、`:167`。
- **方案**：`register` 改 `computeIfAbsent` 保留已置位事实；`cancel()` 对未注册 run 不再创建永久本地孤儿条目。

### P1-09 身份不可确认时出帧直接丢弃，注释承诺的重试不存在

- **根因**：`emit()` 在身份读失败且无提示时直接 return，没有保存或重试该帧；与投递侧的“保留队列、主动断连重挂”不是同一语义。
- **证据**：`backend/src/main/java/com/example/configmgr/ai/run/SseChatEmitter.java:2380`。
- **方案**：写出器创建时必须带已验证的记录身份；暂时性读取失败使用有界重试/收流恢复，不能直接丢正文或终帧；同步修正注释。

## 五、误报、设计权衡与禁止的“优化”

1. **静态池未关闭 ≠ 运行期内存泄漏**：主要是优雅停机与多 Spring Context 隔离问题，应统一生命周期，不应按无界增长处理。
2. **固定静态 `ObjectMapper` 不是泄漏**：无需为统一实例扩散修改。
3. **`LeaseService.ended` 不能清理**：它是防止丢租实例重新获得写权限的 fencing 依据。
4. **记忆写路径不能直接截断 `LRANGE 0 -1`**：摘要、pinned run、其他 run 块可能在头部，截断会破坏合并语义。
5. **KB `HGETALL` 不应机械改 `HSCAN`**：调用方本来就需要完整文档内容。
6. **全局 epoch 单键无 TTL 不是容量问题**。
7. **`FrameWakeListener` 锁内没有 Redis I/O**；相关 Issue 描述属于误报。
8. **取消轮询**在流式期约 1 秒、挂起 park 后已有立即派发收敛，不建议为取消延迟单独增加一套 pub/sub。
9. **共享写池、限流降级**属于需要生产数据支撑的权衡，先观测，不直接拆池或新增复杂限流机制。
10. **NTP 时钟前提**保留为部署条件，不能靠代码猜测消除跨节点墙钟偏差。
11. **`ToolActivityBeacon` 与 `dispatchRetries`**已有终态清理，不应把“只覆盖活跃到终态的正常生命周期”写成必然泄漏。
12. **不能因 `SSCAN` 就放宽 prune 频率**：总遍历量与逐成员 `EXISTS` 并未减少。

## 六、建议施工顺序（仅为审查建议，未获施工批准）

1. **批次 A：直接小修**——取消位覆盖/孤儿、Locale 传播、确定清理出口、冗余 EXPIRE。
2. **批次 B：SSE 背压与生命周期**——drain 时间片、回放分页、Pub/Sub 有界派发与关闭、共享池优雅停机。
3. **批次 C：扫描与销毁**——全局 SSCAN、身份预过滤、销毁复用读取、扫描单飞与公平游标。
4. **批次 D：轻量状态与发现面**——同槽 run 状态键、未完成索引、`activeRunIds`/恢复投影切换；这是关联面最大的批次，必须独立完成。
5. **批次 E：心跳与记忆写降放**——续期分档、附件批量续期、记忆 staging 多值写入。
6. **批次 F：部署守卫和低优先级项**——trusted-proxies 守卫、降级内存表、前端畸形流上限等。

每个批次均应只修改对应代码与精确用例；多键 Redis 优化必须维持同槽、身份隔离、取消优先、fencing、终帧与重挂语义。
