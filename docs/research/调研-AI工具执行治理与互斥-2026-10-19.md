# 调研 · AI 工具执行治理与互斥 · 2026-10-19

> 调研问题：当模型输出的是"工具调用提议"而不是"命令"时，宿主执行器应如何在**准入、互斥、审批、执行、验证、失败分流**六个环节建立可审计、可恢复、恰好一次的治理链？本件结合本仓当前代码与业界官方资料，给出分层口径、18 工具分类矩阵、失败/修复分流表与建议状态机。
> 代码时点：本仓 `HEAD 0900cf0`（2026-10-19）。文中行号以该提交为准；引用一律使用仓库相对路径，不写本机盘符绝对路径。
> 来源：OpenAI、Anthropic、Google、Model Context Protocol、LangChain/LangGraph、Temporal、Stripe 的官方文档与官方博客；访问日期 2026-10-19。厂商未公开的细节不臆测，二手材料不进入结论。
> 结论：**模型只负责"提议"，宿主必须负责"成为事实"。** 本仓已有可用的 HITL 挂起/恢复骨架（Redis 外置、确认门、前端回灌、`toolCallId` 认领、台账），但治理链仍有九处实质性缺口：批内首错不停、scope 只验上下文不验目标资源、FRONTEND 工具的 READ 标签失真、仅按 `toolCallId` 去重而缺业务幂等、确认先于 preflight、会话锁而非资源锁、错误字符串可能以 `ok=true` 呈现、挂起帧早于等待闸门登记导致提前点击可触发并发续跑、以及多闸门时前端只有单槽投影。上述缺口不影响"能跑"，但影响"跑错时能否知道、能否止住、能否对账"。
> 边界：本件是研究稿，不是施工卡；文中的"建议 / P0 / P1"不构成施工排期、接口契约或验收承诺。是否立项、何时施工、如何分批，由后续裁决决定。
> 脱敏：无账号显示名、无本机绝对路径、无密钥、无原始会话内容；官方 URL 原样保留。

## 1. 执行摘要与适用范围

### 1.1 核心口径

模型返回的 `tool_calls` 是**外部输入**，不是宿主进程内的命令。它可能来自幻觉、提示注入、上游缓存了旧工具列表、协议截断或模型对参数的错误推断。宿主执行器必须把这串输入当成"未受信任的提议"，逐层回答六个问题：

1. **准入**：这个工具名是否已登记、是否在当前上下文被披露、调用者是否有权使用它？
2. **互斥**：它要动的资源（任务、配置项、文件、作业、浏览器页签）当前是否已被别的执行占用？同一业务动作是否已在途？
3. **审批**：这次调用的风险等级、影响面、可逆性是否达到人工确认门槛？审批人看到的是否是"将被执行的那一份"提议？
4. **执行**：由谁执行（后端 / 前端 / 异步作业）？执行前是否已原子认领、是否已分配幂等键、是否已持久化"将要执行"的状态？
5. **验证**：执行返回的字符串是否等于事实？是否读取了权威状态（作业行、任务行、文件、暂存区、页面绑定）来确认结果？
6. **失败分流**：失败是"确定未执行"、"确定已执行但结果不对"、还是"不知道执行没执行"？分别进入回模型、问用户、硬拒绝、先对账、补偿人工中的哪条路径？

只有第六问被认真回答，"重试"才不会变成"重复副作用"。

### 1.2 六条治理原则

| # | 原则 | 含义 | 反面 |
|---|---|---|---|
| G1 | 提议与执行分离 | 模型只能生成 `PROPOSED` 记录；宿主是唯一能改变外部状态的主体 | 把模型输出直接当函数调用执行 |
| G2 | 先写后做 | 任何外部副作用之前，先把"将要做什么、谁批准、幂等键是什么"持久化 | 先执行、后补记录 |
| G3 | 一资源一租约 | 互斥的粒度是目标资源，不是会话、不是进程 | 只锁 `sessionId` |
| G4 | 业务幂等优先 | 幂等键由宿主按"业务动作 + 目标 + 参数 + 期望版本"生成，不依赖模型给的 `toolCallId` | 换一轮对话就重复建作业 |
| G5 | 验证读权威态 | 成功与否看作业行/任务行/文件/页面绑定，不看工具返回的自然语言 | `"已启动"` 字符串即成功 |
| G6 | 未知不等于失败 | `UNKNOWN` 是独立终态，必须先对账，禁止自动重试 | 超时即重发 |

### 1.3 本仓执行链现状（一句话版）

`AiController` 接收会话请求 → `ResilientChatService` 组装带 `runId` 的 `toolContext` → Spring AI 官方循环 → `SpToolCallingManager.executeToolCalls` 在每次工具执行处插入"可见性帧、scope 复查、确认门、前端挂起" → `kindOf` 按通道/风险分三路（FRONTEND / CONFIRM / BACKEND）→ 后端路径经 `executeOnce` 认领与记账，前端路径经 `ConfirmGate` 挂起等回灌 → `settle` 重建完整历史。骨架的关键位置见 `backend/src/main/java/com/example/configmgr/ai/gate/SpToolCallingManager.java:141`、`:198`、`:465`。

这条链已经解决了"挂起态外置、跨进程续跑、恰好一次认领、确认帧先于后果帧"四个硬问题；本件的重点不是否定它，而是指出它在**治理语义**上的剩余缺口。

### 1.4 适用范围

**适用**：

- 本仓当前这 18 个 `@Tool` 工具，以及同构的"单宿主 + 内网 + 单用户/小用户量"配置管理场景；
- 后端同步工具、后端异步作业、浏览器侧前端工具、生成式表单四类执行面；
- 需要 HITL 审批、失败恢复、审计留痕的工具调用链。

**不适用**：

- 多租户强隔离、跨组织授权、零信任网络身份体系的设计（本件只指出"审批人与目标资源必须服务端校验"，不展开身份协议）；
- 模型训练期的工具选择偏好、提示词注入防御的完整分类；
- 前端视觉与交互细则（由 `docs/research/裁决-HITL型谱与问题2方案-2026-10-17.md` 系列件负责）；
- 任何具体施工排期与接口冻结。

### 1.5 术语

| 术语 | 含义 |
|---|---|
| 提议（proposal） | 模型给出的一次工具调用：工具名、参数原文、`toolCallId`、所属 `runId` |
| 准入（admission） | 工具名已登记、上下文已披露、调用者有权、参数可解析 |
| 预检（preflight） | 只读地检查目标资源存在性、归属、类型、状态、版本、在途作业、前置条件 |
| 资源租约（lease） | 以目标资源为键、带 TTL 与 owner 的互斥占位；不是数据库事务锁 |
| 幂等键（idempotency key） | 宿主生成的业务动作唯一键；同键重放返回首次结果，不重复执行 |
| 对账（reconciliation） | 在结果未知时，读取权威状态判断"到底执行了没有" |
| 补偿（compensation） | 对已发生副作用的反向动作；必须幂等，且能处理"可能没发生" |

## 2. 业界分层：从 Schema 到补偿

业界并没有一个叫"AI 工具执行治理"的统一标准，但 OpenAI、Anthropic、Google、MCP、LangGraph、Temporal、Stripe 分别在协议、审批、状态机、幂等、补偿上给出了可组合的官方口径。下面按八层归纳，并在每层末尾给出对本仓的映射。

### 2.1 分层总表

| 层 | 要解决的问题 | 业界代表机制 | 本仓对应 | 主要差距 |
|---|---|---|---|---|
| L1 Schema | 参数形状是否可解析、是否可约束 | OpenAI `strict` JSON Schema；MCP `inputSchema` / `outputSchema`；Anthropic `input_schema` | Spring AI 由方法签名生成 Schema；`GenerativeFormRules` 白名单 | 未开 strict；无输出 Schema；前端工具参数原文直达前端 |
| L2 权限 scope | 这个调用者/上下文能不能用这个工具 | OpenAI `allowed_tools` / `tool_choice`；MCP OAuth scope 最小化 | `@ToolScope` 标签 + `ToolRegistry.forContext` | scope 只表达"页面/步骤"，不表达"资源/租户/操作" |
| L3 目标资源 | 这次调用要动哪一个对象，是否归它管 | 服务端按 ID 重新解析并鉴权；MCP 反 confused deputy | 参数里的 `taskId` / `defCode` / `step` | 宿主不复核参数目标与上下文目标是否一致 |
| L4 前置状态 | 目标当前是否允许这个动作 | 状态机 + DB 守卫；LangGraph checkpointer；Temporal Activity 状态 | `JobService.assert*` 守卫 | 守卫在审批之后才跑；预检未成为独立状态 |
| L5 风险审批 | 哪些动作必须人批、批什么、批多久 | OpenAI `needs_approval` + `RunState`；LangGraph `interrupt()`；MCP HITL SHOULD | `@ToolRisk(DANGER)` + `ConfirmGate` | FRONTEND 工具 READ 标签失真；多闸门单槽；早点击竞态 |
| L6 资源锁 | 同一资源能否被两个执行同时动 | DB 唯一约束/行锁、租约、Temporal Workflow ID | `SessionGate` 会话锁；`claimExecution` 调用级认领；作业同类在途查询 | 无资源租约；作业守卫是 check-then-act，且只覆盖同任务同类型 |
| L7 幂等台账 | 重放会不会重复副作用；如何证明只执行一次 | Stripe `Idempotency-Key`；Temporal Activity 幂等 | `ai:ledger:<runId>` + `toolCallId` 认领 | 只有调用级去重，没有业务幂等键；台账无参数/审批/证据 |
| L8 审计补偿 | 出了事能否追责、能否回退 | Temporal Saga 补偿；MCP 安全最佳实践 | 台账有 `executedBy` / `resultText` | 无审批人、无参数快照、无补偿登记、无 UNKNOWN 对账 |

### 2.2 L1 Schema：约束形状，不约束意图

OpenAI 的 function calling 文档把流程定义为"模型返回 `function_call`，应用执行，再把 `function_call_output` 按 `call_id` 回填"，并明确"响应可能包含零个、一个或多个调用，最好按多个处理"；`strict: true` 要求每个对象 `additionalProperties: false`、所有字段 `required`，用于把"尽力而为"变成"可靠符合 Schema"（[Function calling](https://platform.openai.com/docs/guides/function-calling)）。Anthropic 的 `input_schema` 与 `tool_use.id` 也是同一思路：Schema 负责形状，`id` 负责配对（[Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)）。MCP 的 `tools/list` 用 `inputSchema` 描述入参，可选的 `outputSchema` 描述出参，工具执行错误用 `isError: true` 表达（[Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)）。

**本仓映射**：Spring AI 从方法签名生成 JSON Schema，`AiTools` 的 record 让嵌套条件与表单字段形状可见（`backend/src/main/java/com/example/configmgr/ai/tools/AiTools.java:438`、`:536`）。但 Schema 只保证"能绑定"，不保证"业务上允许"：`create_task(type="EXPORT")` 能过 Schema，不代表调用者有权建任务；`start_export(taskId=999)` 能过 Schema，不代表 999 是当前任务。**Schema 是准入门槛，不是授权结论。**

### 2.3 L2 权限 scope：披露范围不等于执行权限

OpenAI 用 `allowed_tools` 在不改动工具清单的情况下限制本轮可调用子集；MCP 安全最佳实践把"scope 最小化"列为独立攻击面，要求令牌只带完成当前任务所需的最小权限（[Security Best Practices](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices)）。这两者的共同点是：**权限判定在服务端/宿主侧完成，不能只靠"没把工具告诉模型"**。MCP 还明确"客户端必须把工具注解视为不可信，除非来自可信服务器"（[Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)），这直接对应本仓"模型可能返回未披露工具名"的防线③。

**本仓映射**：`ToolRegistry.forContext` 按 `page:` / `task:` 标签裁剪披露集（`backend/src/main/java/com/example/configmgr/ai/tool/ToolRegistry.java:81`），`matchesContext` 在执行前复查同一份标签（`:122`）。这是正确的"两处同源"设计。但标签只来自 `AiContext` 的 `page/taskType/step`（`:152`），`taskId` 完全不参与（`backend/src/main/java/com/example/configmgr/ai/tool/AiContext.java:21` 有字段，但 `buildTags` 没用）。因此当前 scope 是**上下文可用性**，不是**资源授权**。

### 2.4 L3 目标资源：服务端重新解析，不信任参数

OpenAI 的 HITL 文档在"长时审批"一节给出了与工具参数同构的要求：审批请求到达服务端时，必须①用应用会话认证审批人，不能从请求体取身份；②授权该审批人对该 run 与待决项动作；③用服务端保存的待决项校验提交的决策 ID 与布尔值，**不接受客户端替换工具调用、参数或审批记录**；④以原子、owner-checked 的状态转移消费待决项，避免并发/重放把同一快照恢复两次（[Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)）。MCP 的 confused deputy 条目则说明：代理不能在缺少 per-client consent 的情况下把请求转发给第三方（[Security Best Practices](https://modelcontextprotocol.io/specification/2025-06-18/basic/security_best_practices)）。

把这两条平移到工具执行：**模型给的 `taskId`、`defCode`、`step` 只是"它想动的资源"，宿主必须用当前会话/用户/上下文重新解析并确认"它能不能动这一个"。** 参数合法性与资源授权是两件事。

**本仓映射**：`start_export` / `start_precheck` / `start_import` / `start_publish` 直接把模型给的 `taskId` 传给 `jobService.createAndStart`（`backend/src/main/java/com/example/configmgr/ai/tools/AiTools.java:291`、`:308`、`:323`、`:333`），没有与 `AiContext.taskId` 比对，也没有把"当前页面绑定的任务"作为允许集合。`navigate_to` 更是 `@ToolScope("*")` 且 `taskId` 任意（`:383`、`:388`）。`select_definitions` 的 `codes`、`set_condition` 的 `defCode/conditions`、`confirm_step` 的 `step` 同样没有在宿主侧做目标解析。前端只做了部分兜底：`needsTask` 只检查"有没有绑定任务"，不检查"是不是这个任务"（`frontend/src/utils/frontend-tools.ts:799`）；`navigate_to` 会把任意 `taskId` 绑定为目标（`:716`）。`open_export_file_editor` 是少数做了目标校验的：它先 `ensureTaskBoundForTool(payload.taskId)`，再检查该 `defCode` 是否在导出结果里（`frontend/src/views/ExportWizardView.vue:1329`）。

### 2.5 L4 前置状态：审批前先预检，执行前再复核

LangGraph 的 `interrupt()` 在节点内暂停，靠 checkpointer 保存完整图状态，恢复时用 `Command(resume=...)` 把外部输入送回 `interrupt()` 的返回值；官方同时要求"在 interrupt 之前调用的副作用必须幂等"，并禁止把 `interrupt()` 包在 try/except 里、禁止在节点内重排 interrupt 调用（[Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)）。OpenAI 的 `RunState` 同样把"待决工具调用、参数、审批决定"序列化，恢复时从服务端保存的快照继续（[Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)）。Temporal 的 Activity 则明确"每次重试都从初始状态开始，除非用 Heartbeat detail 做检查点"（[Activities](https://docs.temporal.io/activities)）。三者共同说明：**前置状态必须持久化，恢复必须从持久化状态重建，不能靠内存里的"应该没问题"。**

**本仓映射**：`JobService.createAndStart` 内确实有较强的业务守卫：任务终态 `TASK_FINALIZED`（`backend/src/main/java/com/example/configmgr/job/service/JobService.java:72`）、同任务同类型在途 `JOB_ALREADY_RUNNING`（`:160`）、导入/发布前预检查通过 `PRECHECK_NOT_PASSED`（`:186`）、导入件指纹 `PRECHECK_STALE`（`:222`）。问题是这些守卫都在**审批之后**、`createAndStart` 内才跑；用户在确认卡上看到的是 `taskId`，不是"这个任务当前能否执行、是否已预检查、是否已有在途作业"。这不是"没有守卫"，而是"审批信息与审批时机错位"。

### 2.6 L5 风险审批：按调用声明，按 run 汇总，按服务端裁决

OpenAI Agents SDK 的 HITL 把审批做成 `needs_approval`（布尔或按调用判定的回调），回调收到 run context、解析后的参数、`tool_call_id`；**参数缺失、空、全空白、非法 JSON、不是对象、含 `NaN/Infinity` 时，回调不执行，直接要求人工审批**（fail-closed）。暂停后 `RunResult.interruptions` 暴露 `ToolApprovalItem`，转成 `RunState` 后 `approve/reject`，再 `Runner.run(agent, state)` 恢复（[Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)）。LangGraph 用 `interrupt()` + checkpointer 做同样的事；MCP 则用 SHOULD 级语言要求"始终保留人类拒绝工具调用的能力，并向用户呈现确认提示"（[Tools](https://modelcontextprotocol.io/specification/2025-06-18/server/tools)）。

**本仓映射**：`@ToolRisk` 三级（READ/WRITE/DANGER）经 `ToolRegistry.riskOf` 读取（`backend/src/main/java/com/example/configmgr/ai/tool/ToolRegistry.java:138`），`SpToolCallingManager.kindOf` 把 DANGER 映射为 `KIND_CONFIRM`（`backend/src/main/java/com/example/configmgr/ai/gate/SpToolCallingManager.java:465`），`ConfirmGate` 负责三结局（放行/拒绝/超时）与 Redis 外置（`backend/src/main/java/com/example/configmgr/ai/gate/ConfirmGate.java:414`）。骨架是对的；缺口在**风险标注的语义**与**多闸门的身份**，见 §3.4、§3.9。

### 2.7 L6 资源锁：锁资源，不锁会话

Stripe 的幂等键不是锁，但它解决的是同一类问题：客户端生成高熵唯一键，服务端用键识别重试，重试返回首次保存的状态码与响应体；参数必须与首次请求一致，否则报错；v1 的键至少保留 24 小时（[Idempotent requests](https://docs.stripe.com/api/idempotent_requests)）。Temporal 用 Workflow ID 唯一性 + Activity 重试策略 + Heartbeat 检查点来保证"同一业务执行不被并发拉起"；补偿动作则要求能处理"前一步可能已执行、也可能没执行"（[Saga compensating actions](https://temporal.io/blog/compensating-actions-part-of-a-complete-breakfast-with-sagas)）。

**本仓映射**：`SessionGate` 的锁键是 `ai:session:lock:<sessionId>`（`backend/src/main/java/com/example/configmgr/ai/session/SessionGate.java:42`），语义是"一个会话同时只允许一轮在跑"（`:70`）。它不阻止两个会话/两个页签同时对同一 `taskId` 发起导出或发布。`RunStore.claimExecution` 的键是 `runId + toolCallId`（`backend/src/main/java/com/example/configmgr/ai/run/RunStore.java:427`），只保证"同一次工具调用不被两个实例各执行一次"，不保证"同一业务动作不被两次调用各执行一次"。作业层的同任务同类型在途查询（`JobService.java:160`）是资源级判据，但它是 check-then-act，且只覆盖同类型；文件里也如实登记了 TOCTOU 观察项（`JobService.java:68`、`:219`）。

### 2.8 L7 幂等台账：键要来自业务，不来自模型

Stripe 的关键细节是"键由客户端生成、服务端保存首次结果、重试返回同一结果、参数不同则报错、只有端点开始执行后才保存结果"（[Idempotent requests](https://docs.stripe.com/api/idempotent_requests)）。Temporal 的 Activity 也建议幂等，使重试不产生重复副作用（[Activities](https://docs.temporal.io/activities)）。这两条对 AI 工具的直接启示是：

- 幂等键不能只用 `toolCallId`，因为模型换一轮就会生成新 ID；
- 幂等键不能完全信任模型提供，因为模型可以复制/伪造；宿主应按"工具 + 规范化目标 + 规范化参数 + 期望资源版本"生成；
- 同键不同参必须报错，而不是"以新参数再执行一次"；
- 结果要在执行开始后写入，重放返回已保存的结果，而不是重新执行。

**本仓映射**：`RunStore.appendLedger` 的记录字段是 `atMs / at / executedBy / toolCallId / name / kind / resultText`（`backend/src/main/java/com/example/configmgr/ai/run/RunStore.java:449`），没有参数、没有目标资源、没有幂等键、没有审批人、没有验证证据。`ledgerFor` 只按 `toolCallId` 匹配（`:486`）。`claimExecution` 只按 `toolCallId` 认领（`:427`）。因此当前只能证明"这个调用没被重放"，不能证明"这个业务动作没被重复"。

### 2.9 L8 审计补偿：补偿要能处理"可能没发生"

Temporal 的 Saga 文章把补偿的两个硬点讲得很清楚：①补偿方法与正向步骤一样要幂等；②补偿必须假设"要补偿的那一步可能已经执行，也可能没有执行"，所以方法名常写成 `putBowlAwayIfPresent` 这类带存在性判断的形式；③补偿顺序要与正向顺序相反，且超时/崩溃/取消都可能留下"已执行但未记录"的窗口（[Saga compensating actions](https://temporal.io/blog/compensating-actions-part-of-a-complete-breakfast-with-sagas)）。这正好对应本仓的 `FRONTEND_TIMEOUT`：前端工具超时"不表示未发生"（`backend/src/main/java/com/example/configmgr/ai/tools/AiTools.java:504`、`ConfirmGate.java:305`）。

**本仓映射**：目前只有"执行台账"，没有"补偿台账"；只有"结果文本"，没有"证据快照"；只有"用户拒绝/超时"的 reason，没有"审批人、审批时看到的目标版本、批准后的资源版本"。对于 `start_publish` 这类不可逆写，没有登记补偿动作（例如回滚到上一版发布快照），也没有在 `UNKNOWN` 时强制人工对账的字段。

### 2.10 协议对照：并行调用与"首错"语义

| 维度 | OpenAI | Anthropic | Gemini | MCP |
|---|---|---|---|---|
| 一次响应多个调用 | 支持；文档建议按多个处理；可用 `parallel_tool_calls=false` 禁止 | 支持多个 `tool_use` 块；执行顺序由调用方决定 | 支持并行与组合式 function calling | `tools/call` 是单次调用；批量由客户端编排 |
| 结果配对 | `call_id` | `tool_use_id`，每个 `tool_use` 必须有一个 `tool_result` | `functionResponse` 与调用配对 | 请求 `id` 配对 |
| 副作用批处理 | 文档未规定顺序；由宿主决定 | 官方明确：只读可并行；有副作用/共享状态/顺序要求宜串行；跳过未执行的调用也要返回 `is_error: true`；computer/browser 批量动作按序执行并在首个失败停止 | 文档强调组合调用需按依赖顺序 | 由客户端决定；协议只提供调用与错误表达 |
| 错误表达 | `function_call_output` 字符串，格式自定 | `tool_result.is_error` | `functionResponse` 内容 | `isError: true` |

这张表直接支撑 §3.2 的判定：**"批内首错不停"对只读工具是优点，对有副作用/有顺序依赖的工具是风险。** Anthropic 对 computer/browser 批量动作给出的口径是"按序执行、首个失败停止"，并给未执行调用补 `is_error`；这比"全部继续、失败只写字符串"更适合写链。

### 3.2 F1：批内首错不停

**现象**：`executeToolCalls` 对模型一次返回的所有 `tool_calls` 建 `pendings`，然后 `for (PendingToolCall pending : pendings)` 逐个执行（`backend/src/main/java/com/example/configmgr/ai/gate/SpToolCallingManager.java:183`）。每个工具的执行包在 `try/catch` 里，异常只把该次结果置为 `"工具执行失败：..."` 并继续下一个（`:377`）。只有取消（`StreamViolationException.CANCELLED`）会终止整轮（`:186`、`:209`）。

**后果**：模型若在同一轮发出 `start_precheck` + `start_import`，前者失败（例如文件缺失）不会阻止后者被尝试；若发出两个不同任务的 `start_export`，第一个失败不会阻止第二个。对于有依赖的写链，这会产生"部分成功"：模型看到两条结果，但没有人给出"这一批到底完成了几步、下一步该不该继续"的统一结论。

**业界对照**：Anthropic 明确说只读操作可并行，有副作用/共享状态/顺序要求的工具宜串行；对 computer/browser 的批量动作更是"按序执行、首个失败停止"，并给未执行调用补 `is_error`（[Parallel tool use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use)）。本仓是串行执行但"首错不停"，比"并行写"安全，但仍缺少"写链失败即停"的批策略。

**判定**：不应一刀切改成"所有工具首错即停"——只读查询继续执行是有价值的。应按分类定批策略：R/H 可继续；U 看是否同一向导的依赖动作；W/J/P 应按序遇到确定性失败即停，并为未执行项返回结构化 `SKIPPED`（不是空字符串，也不是成功）。

### 3.3 F2：scope 只验 context，不验 args 目标资源

**现象**：`ToolRegistry.matchesContext(name, ctx)` 只做两件事：取工具的 `scopePatterns`，用 `buildTags(ctx)` 生成 `*` / `page:<page>` / `task:<type>` / `task:<type>/<step>` 标签，然后做集合匹配（`backend/src/main/java/com/example/configmgr/ai/tool/ToolRegistry.java:122`、`:152`）。`AiContext.taskId` 从未进入标签（`ToolScope.java:9` 的注释也只列 page/task/step）。执行前的防线③因此只能回答"这个工具在这个页面/步骤该不该出现"，不能回答"这个工具要动的 `taskId` 是不是当前任务"。

**后果**（举三个真实可发生的场景）：

1. 上下文 `page=tasks, taskId=1`，模型调用 `start_export(taskId=999)`。`@ToolScope({"page:tasks","task:EXPORT/EXPORT"})` 通过（`AiTools.java:284`），确认卡显示 `taskId=999`，用户可能没注意就批准；`JobService` 只校验 999 是否存在/是否终态/是否有同类在途，不校验"999 是不是当前会话的任务"。
2. 上下文 `page=tasks, taskId=1`，模型调用 `navigate_to(page="export", taskId=999)`。`@ToolScope("*")` 必过（`:383`），前端 `resolveNavigateIntent` 接受任意正整数 `taskId`（`frontend-tools.ts:716`），直接把工作区绑定到 999。
3. 上下文 `page=tasks, taskId=1`，模型调用 `select_definitions(codes=["NO_SUCH_DEF"])`。`@ToolScope({"page:tasks","task:EXPORT","task:IMPORT"})` 通过（`:393`），前端 `export.selectDefs` 直接把 `codes` 写进 `selectedDefs`，不校验定义是否存在（`frontend/src/views/ExportWizardView.vue:1273`）。

**业界对照**：OpenAI HITL 要求服务端用保存的待决项校验提交的决策 ID，不接受客户端替换参数；MCP 反 confused deputy 要求 per-client consent。二者都指向"参数目标必须由服务端重新解析并授权"，而不是"Schema 通过即放行"。

**判定**：`@ToolScope` 应保留为"上下文披露"维度；新增独立的"目标资源解析"层：从 args 提取 `taskId/defCode/step`，按工具类型解析为资源引用，再与 `AiContext`、当前用户/租户、资源状态做比对。两者不能互相替代。

### 3.4 F3：FRONTEND 工具的 READ 标签失真

**现象**：`ToolMeta.RiskLevel` 的注释把 READ 定义为"auto-execute, no side effects"（`backend/src/main/java/com/example/configmgr/ai/tool/ToolMeta.java:20`）。但 7 个 FRONTEND 工具全部标 `@ToolRisk(READ)`：

| 工具 | 行号 | 实际副作用 |
|---|---|---|
| `open_export_file_editor` | `AiTools.java:349` | 切页、绑定任务、加载 SpreadJS 编辑器 |
| `download_export_files` | `:368` | 触发浏览器下载（单文件或 zip） |
| `navigate_to` | `:384` | 改路由、绑定任务、改变工作区上下文 |
| `select_definitions` | `:394` | 改向导选中项、同步 workspace、后续影响导出范围 |
| `set_condition` | `:422` | 写表单模型并**立即落库**（`ExportWizardView.vue:1299`） |
| `confirm_step` | `:458` | 推进步骤、持久化步骤数据，可能触发后续动作 |
| `generative_form` | `:517` | 下发交互卡、挂起等待用户输入 |

**为什么现在没出事**：`SpToolCallingManager.kindOf` 先看通道（`channelOf == FRONTEND` → `KIND_FRONTEND`），再看风险（`SpToolCallingManager.java:465`）。所以 READ 不会让它们"自动执行"，它们仍然会挂起等前端回灌。**但标签仍然是错的**：它进入诊断端点、风险矩阵、审计文案和 2B 的"18 工具风险标注重审"；一旦后续有人按 `riskOf` 做审批或按 READ 做"无需审计"的优化，就会漏掉这些前端副作用。

**判定**：风险等级应表达"副作用的性质与可逆性"，而不是"执行通道"。建议至少把这些工具从 READ 改为 WRITE 或新增 `FRONTEND_WRITE` 语义；`generative_form` 可保留 READ（无外部副作用）但应标为"阻塞式交互"，与普通 READ 区分。具体定级属 2B 的"逐个重审"范围（`docs/research/裁决-HITL型谱与问题2方案-2026-10-17.md:69`），本件只给分类事实。

### 3.5 F4：仅按 `toolCallId` 去重，缺业务幂等

**现象**：`RunStore.claimExecution(runId, toolCallId, executedBy)` 用 Redis `HSETNX` 语义按 `runId + toolCallId` 原子认领（`backend/src/main/java/com/example/configmgr/ai/run/RunStore.java:427`）；`ledgerFor` 只按 `toolCallId` 查台账（`:486`）。这套机制解决的是"同一次模型调用在跨进程续跑时不被两个实例各执行一次"，不是"同一个业务动作不被两次模型调用各执行一次"。

**后果**：

- `create_task` 每次调用都 `taskService.create`，没有唯一键（`backend/src/main/java/com/example/configmgr/task/service/TaskService.java:91`）。模型重试/换轮/用户重复说"建一个导出任务"会建出多条任务。
- `start_export` 的业务守卫是"同任务同类型在途"（`JobService.java:160`）。如果第一次作业已经完成，第二次调用会合法地再建一个作业；如果两次调用几乎同时到达，守卫是 check-then-act，两个事务都可能看到"无在途"（`JobService.java:68` 已登记该 TOCTOU 观察项）。
- `download_export_files` 没有去重；同一 `taskId + defCodes` 的重复调用会重复触发浏览器下载。
- `select_definitions` / `set_condition` 的重复调用在效果上往往是幂等的（REPLACE / 覆盖），但台账没有记录"这是同一次业务动作的重放"，审计上仍看不出。

**业界对照**：Stripe 的幂等键是"业务动作级"的，重试返回首次结果，参数不同则报错（[Idempotent requests](https://docs.stripe.com/api/idempotent_requests)）；Temporal 的 Activity 也要求幂等以承受重试（[Activities](https://docs.temporal.io/activities)）。`toolCallId` 是协议级关联 ID，不是业务幂等键。

**判定**：新增宿主生成的业务幂等键，建议组成 `hash(toolName, canonicalTarget, canonicalArgs, expectedResourceVersion)`；对 `create_task` 还要加"同一会话/同一请求窗口内同类型同标题"的软去重；对 `start_*` 用"taskId + jobType + taskVersion/precheckFingerprint"；对下载用"taskId + sorted(defCodes) + 导出文件版本"。同键不同参必须硬拒绝并回模型，不能"按新参数再执行"。

### 3.6 F5：确认先于 preflight

**现象**：`ConfirmGate.submitDecision` 只做四件事：找到 `PENDING` 条目、把状态改成 `APPROVED/REJECTED`、写 reason、落库并发帧/唤醒（`backend/src/main/java/com/example/configmgr/ai/gate/ConfirmGate.java:414`）。它不检查任务是否存在、是否终态、是否已预检查、是否已有在途作业、文件指纹是否新鲜。确认卡帧只带 `args` 与 `summary`（`summary` 直接等于 `args`，见 `backend/src/main/java/com/example/configmgr/ai/run/SseChatEmitter.java:579`）。真正的业务守卫在批准之后、`JobService.createAndStart` 内才运行（`JobService.java:124`）。

**后果**：

- 用户在不知道"这个任务当前不可执行"的情况下批准了一个不可执行的动作；随后收到 `TASK_FINALIZED` / `PRECHECK_NOT_PASSED` / `JOB_ALREADY_RUNNING` 的 409。审批记录是"已批准"，执行结果是"失败"，审计上需要解释这个矛盾。
- 审批与执行之间资源状态可能变化（文件被替换、别人先发了作业、任务被取消）。执行前的守卫会重新检查，但审批人看到的版本已经过期；当前没有"审批绑定资源版本/指纹"的字段。
- 确认卡没有"影响面摘要"：`start_publish` 只显示 `taskId`，不显示将发布哪些配置项、多少行、当前暂存状态、是否已有成功发布。2D 的"预检 diff 摘要"仍是候选缓办（`docs/research/裁决-HITL型谱与问题2方案-2026-10-17.md:79`），但即使不做 2D，至少应把只读 preflight 的结论放进 H1 卡。

**业界对照**：OpenAI HITL 的 `RunState` 把待决工具调用与参数一起保存，审批人看到的是服务端保存的那一份；恢复时从同一份状态继续，不接受客户端替换。LangGraph 的 `interrupt()` 也要求"中断前副作用幂等"，因为恢复可能重复进入节点。二者都支持"先预检、再审批、再执行"的顺序，而不是"先审批、再发现不能做"。

**判定**：在 `APPROVAL` 之前增加只读 `PRE_CHECK`，产出 `PRE_CHECK_REPORT`（目标存在/归属/类型/状态/版本/在途/前置条件/影响面摘要）；确认卡展示该报告的关键字段；批准时把 `reportHash` 与 `resourceVersion` 写入审批记录；`READY` 阶段再做一次轻量复核，闭合审批到执行之间的漂移。

### 3.7 F6：会话锁而非资源锁

**现象**：`SessionGate.acquire` 的键是 `ai:session:lock:<sessionId>`（`backend/src/main/java/com/example/configmgr/ai/session/SessionGate.java:42`、`:77`），语义是"同一会话同时只允许一轮"，冲突返回 409 + 进行中的 `runId`（`:70`）。它不感知 `taskId`、`defCode`、`jobId`。`RunStore.claimExecution` 是调用级认领（`RunStore.java:427`），不是资源租约。`JobService.assertNoJobInFlight` 是资源级判据，但只覆盖"同任务 + 同类型 + PENDING/RUNNING"，且是查询后插入，不是原子锁（`JobService.java:160`）。

**后果**：

- 两个浏览器页签（不同 `sessionId`）可以同时对同一 `taskId` 发起 `start_export`；若时间错开，第一个作业已在途时第二个会被 409 挡住；若几乎同时，两个事务都可能通过 check，留下两个 PENDING 作业（取决于数据库隔离级别与唯一约束；当前 `backend/src/main/java/com/example/configmgr/job/repo/JobRepository.java:13` 只有查询方法，没有"同任务同类型在途唯一"的约束）。
- 同一任务的不同类型作业（EXPORT vs PRECHECK vs IMPORT/PUBLISH）之间没有互斥查询；它们可能并发写同一 `task_files` / 暂存区 / 任务状态。
- `create_task`、`select_definitions`、`set_condition`、`confirm_step` 没有资源锁；两个会话可以同时改同一任务的选中项/条件/步骤。

**业界对照**：Stripe 用幂等键把"重复请求"收敛为同一结果；Temporal 用 Workflow ID 唯一性 + Activity 串行化保证同一业务执行不被并发拉起；Saga 文章则强调补偿要能处理"另一服务/事务也可能已经改过同一数据"（[Saga compensating actions](https://temporal.io/blog/compensating-actions-part-of-a-complete-breakfast-with-sagas)）。资源锁与幂等键是两件事：锁防并发，幂等防重放；本仓目前两者都只做到"会话/调用"级。

**判定**：引入资源租约（键如 `lock:task:<taskId>`、`lock:def:<taskId>:<defCode>`、`lock:job:<taskId>:<jobType>`），带 TTL、owner、可续期、终态释放；同时给作业表加"同任务同类型在途"的部分唯一索引或数据库级约束，作为租约失效时的最后一道。租约不是事务锁，不能替代业务守卫；它只保证"同一资源同一时刻只有一个执行者"。

### 3.8 F7：错误字符串可能 `ok=true`

这是本件最容易被低估的一条，因为它同时出现在后端、前端和模型三面。

**后端同步工具**：`executeOnce` 把 `ok` 初始化为 `true`（`backend/src/main/java/com/example/configmgr/ai/gate/SpToolCallingManager.java:373`），只有抛异常才置 `false`（`:377`）。但多个工具在业务失败时**返回字符串而不是抛异常**：

- `getConfigDef` 找不到定义 → `"未找到配置定义: ..."`（`AiTools.java:126`）
- `getWorkspaceState` 任务不存在 → `"任务 #... 不存在或无法访问"`（`:181`）
- `createTask` 类型非法 → `"任务类型不合法：..."`（`:253`）
- `delegateSingle` 找不到对应 `toolCallId` 的响应 → `.orElse("")`（`SpToolCallingManager.java:417`），空字符串也会以 `ok=true` 回填

**前端工具**：`ConfirmGate.submitFrontendResult` 在通过安全闸后无条件 `frontendToolResult(pending, true, result)`（`ConfirmGate.java:491`）。前端执行器其实有 `failed` / `unknown` 三态（`frontend/src/stores/ai.ts:3147`），但回灌时只 POST `execution.result` 文本（`:3163`），没有把 `outcome` 一起带回。页面 handler 的字符串返回值被解释为成功（`frontend/src/utils/frontend-tools.ts:1023`），例如 `set_condition` 落库失败时返回 `"已设置 ... 但落库失败：..."`（`frontend/src/views/ExportWizardView.vue:1310`），这串文字会被当成功回灌，后端再以 `ok=true` 发给前端/台账。

**模型面**：`ToolResponseMessage.ToolResponse` 只有 `id/name/responseData`（`SpToolCallingManager.java:211`），没有 `isError` 字段；`ok` 只存在于 SSE `tool_result` 帧（`SseChatEmitter.java:560`）。模型看到的是自然语言，无法可靠区分"成功"与"失败但返回了说明"。

**后果**：UI 可能显示成功徽标而正文写失败；台账记录 `ok=true`；模型可能基于"成功"继续下一步（例如条件没落库却继续 `start_export`，导出全量）。这与 MCP 的 `isError` 规范、Anthropic 的 `tool_result.is_error` 直接相悖。

**判定**：统一结果信封，至少包含 `{ok, code, outcome, retryable, target, evidence, message}`；后端工具的业务失败要么抛结构化异常，要么返回 `ok=false` 的信封；前端回灌必须带 `outcome`；模型侧 `ToolResponse` 的 `responseData` 用该信封序列化，SSE 帧与台账共用同一份事实，而不是各自解释字符串。

### 3.9 F8：挂起帧早于闸门登记，提前点击可并发续跑；多闸门单槽

**A. 提前点击竞态**

任务口径中的"HITL 后置确认卡提前点击"，在本仓对应的是：确认卡由 `suspended` 帧渲染，而该帧早于等待闸门的 `latches.put` 登记。执行顺序是：

1. `saveSuspended` 先把 `assistant(tool_calls)` 与所有 `PENDING` 条目写入 Redis，把快照置 `SUSPENDED`（`SpToolCallingManager.java:179`）；
2. `out.suspended(...)` 发帧（`:180`），前端据此渲染确认卡；
3. 循环进入 `awaitConfirm` → `gate.awaitDecision` → `await(...)`，**到这里才** `latches.put(key, latch)` 登记进程内闸门（`ConfirmGate.java:206`）。

在 2 与 3 之间有一个真实窗口（Redis 往返 + 帧传输 + 前端渲染 + 用户点击）。若用户在这个窗口点击"确认"：

- `submitDecision` 把条目改成 `APPROVED`，`woke = signal(...)` 返回 `false`（闸门还没登记）；
- `maybeTriggerResume` 检查：`woke=false`、本进程没有活跃 latch、快照仍是 `SUSPENDED` → 触发 `ResumeService.resume(runId)`（`ConfirmGate.java:564`；代码注释自己承认这个"毫秒窗"，见 `:549`）；
- `ResumeService.resume` 只把 `RUNNING` 当作"已在跑"（`backend/src/main/java/com/example/configmgr/ai/run/ResumeService.java:265`），`SUSPENDED` 会继续；此时 `PENDING` 外部项已经变成 `APPROVED`，`unresolved` 为空（`:284`），于是它重建历史、`resolvePending` 执行、并驱动一次新的模型循环；
- 原循环随后到达 `awaitDecision`，读到 `APPROVED`，也会执行 `executeOnce` 并 `settle`。

`claimExecution` 能保证**副作用最多一次**（`RunStore.java:427`），所以不会重复发布；但两个驱动者都可能 `settle` 快照、发 `tool_result` 帧、继续请求模型，产生重复续跑/重复帧/历史分叉。`ResumeService` 的 runId 级互斥锁只防"resume 对 resume"（`ResumeService.java:409`），不防"resume 对原循环"。这就是"提前点击可触发并发续跑"的准确机制。

**B. 多闸门单槽**

`newPendings` 会为一次 `assistant` 消息里的每个 `tool_call` 建条目（`SpToolCallingManager.java:451`），循环里每个 CONFIRM 都会发一张 `confirm_request`。但前端：

- `deriveProjections` 遍历消息内所有工具段时，`pending` 变量被后一个 `requiresAction` 段覆盖，因此同一条消息内只保留**最后一条** `pendingCall`（`frontend/src/utils/parts.ts:203`、`:210`、`:217`）；`pendingToolCall` getter 再从后向前找第一条 `status === 'pending'` 的消息投影（`frontend/src/stores/ai.ts:885`）；
- `confirm()` 用的是这个单槽 `pendingToolCall`，不是按钮所在卡片的 `toolCallId`（`:2012`）；
- `AiPanel` 的每个确认按钮都调用无参 `decide(true/false)`（`frontend/src/components/AiPanel/AiPanel.vue:506`、`:512`、`:2913`）。

若模型同一轮发出两个 DANGER 调用（例如对两个任务各发一次 `start_export`），前端会渲染两张卡，但无论点哪张卡，提交的都是同一个单槽 `toolCallId`（通常是最后一条）：点非最后一张卡时批准了另一个目标，点最后一张卡时其余项仍 `PENDING` 直到超时。更糟的是用户以为批准了 B，实际批准了 A。这不是 UI 细节，而是**审批身份（approval identity）错误**。

**业界对照**：OpenAI HITL 的 `interruptions` 是逐项的 `ToolApprovalItem`，每项带 `tool_name/arguments`，`state.approve(interruption)` 逐项处理；未处理完的项会继续留在 `interruptions` 并再次暂停（[Human-in-the-loop](https://openai.github.io/openai-agents-python/human_in_the_loop/)）。本仓 2C 的"批量中断支持"要做的正是这件事；当前单槽投影与逐项审批语义不兼容。

**判定**：① 在 `suspended` 帧发出之前登记闸门，或把"latch 登记"与"saveSuspended"做成同一个不可分割的准备阶段；② `maybeTriggerResume` 在 `woke=false` 时必须再等一个"闸门登记宽限"或检查 `snapshot.inFlightToolCalls` 是否仍有 `PENDING`，不能仅凭"无 latch + SUSPENDED"就续跑；③ 确认请求必须按卡片所在 `toolCallId` 提交（API 已带该字段，缺的是前端按钮没有把卡片 ID 传下去），store 不得使用单槽投影；④ 多闸门要么逐项审批，要么明确"一次批准全部"并显示全部条目，不能隐式只批第一个。

### 3.10 F9：元数据/运行上下文缺失时 fail-open

**现象**：

- `ToolRegistry.matchesContext` 对未登记工具返回 `true`（`backend/src/main/java/com/example/configmgr/ai/tool/ToolRegistry.java:124`）；`riskOf` 对未登记工具返回 `READ`（`:138`）；`channelOf` 返回 `BACKEND`（`:147`）。注释的理由是"元数据缺失不是越权证据"，但这在治理上是 fail-open。
- `SpToolCallingManager.executeToolCalls` 在拿不到 `runId` 或 Redis 快照时，直接 `return this.delegate.executeToolCalls(prompt, chatResponse)`（`SpToolCallingManager.java:149`）。这条路径会绕过 scope 复查、确认门、前端挂起，直接走官方执行。对于 FRONTEND 工具，后端方法体是哨兵桩，会返回 `FRONTEND_STUB_SHOULD_NOT_RUN`（`AiTools.java:345`）；对于 DANGER 工具，则会**在没有审批的情况下执行**。
- 正常路径（`ResilientChatService` 首轮与续跑）都显式设置了 `toolContext` 的 `runId`（`backend/src/main/java/com/example/configmgr/ai/run/ResilientChatService.java:227`、`:281`），所以这不是当前主路径的常态；但它是明确的 fail-open 分支，且注释把它当作"诚实回落"。

**后果**：一旦上游调用方漏传 `runId`（新入口、测试、未来编排层、第三方集成），高风险工具会静默跳过 HITL；前端工具会执行哨兵桩并把哨兵字符串当结果回填，模型可能据此编造"已打开"。这比"挂起但不可恢复"更危险，因为它没有留下"未执行"的明确信号。

**判定**：fail-open 只应保留给 READ；对 WRITE/J/P 与所有 FRONTEND 工具，拿不到 `runId`/快照时应 fail-closed：不执行、返回结构化 `HOST_CONTEXT_MISSING`，并提示调用方补上下文。未知工具名应直接 `UNKNOWN_TOOL` 拒绝，而不是按 READ/BACKEND 放行。

### 4.3 重点工具逐项

#### 4.3.1 `create_task`（W）

- **现状**：`@ToolRisk(WRITE)`，不进确认门（`AiTools.java:239`）；`TaskService.create` 只做 `save`（`TaskService.java:91`），没有唯一键或幂等。返回文本里带任务 id 与下一步建议（`AiTools.java:248`）。
- **风险**：静默建库、重复建库、标题/类型由模型决定但用户未确认。2B 已明确要"软确认或进门，不得静默建库"（`docs/research/裁决-HITL型谱与问题2方案-2026-10-17.md:68`）。
- **默认策略**：`PRE_CHECK` 校验 type 枚举、标题长度、当前是否已有同类型未完成任务；展示"将创建：类型 + 标题 + 初始步骤"；用户软确认（H1 的轻量形态或 H2 选择）后执行；宿主按"会话 + type + normalized title + 时间窗"生成幂等键，重复提议返回已存在任务而不是再建一条；单轮最多创建一个任务。
- **验证**：读回任务行（id/type/title/currentStep/status），不是只看返回字符串。

#### 4.3.2 四个 `start_*`（J/J/J/P）

四个工具都标 DANGER，都经确认门（`AiTools.java:285`、`:304`、`:319`、`:329`）。它们的差别在业务前置条件与可逆性：

| 工具 | 业务前置（应进 PRE_CHECK） | 审批强度 | 资源锁 | 幂等键 | 验证 | 补偿 |
|---|---|---|---|---|---|---|
| `start_export` | 任务存在、类型 EXPORT、非 CANCELLED、无同类在途、导出步骤/配置项就绪 | H1 标准 | `lock:task:<id>` + `job:EXPORT` | `taskId + EXPORT + taskVersion` | 作业行 PENDING/RUNNING；文件生成后可校验 | 删除导出文件/取消作业（可逆） |
| `start_precheck` | 任务存在、类型 IMPORT、上传件存在、无同类在途 | H1 标准 | `lock:task:<id>` + `job:PRECHECK` | `taskId + PRECHECK + uploadFingerprint` | 作业行 + `errorCount` | 取消/重跑（可逆） |
| `start_import` | 预检查 COMPLETED 且 `errorCount=0`、UPLOAD 指纹新鲜、无同类在途 | H1 标准 | `lock:task:<id>` + `job:IMPORT` | `taskId + IMPORT + precheckFingerprint` | 暂存行数/状态；作业行 | 清空/重导暂存（受控） |
| `start_publish` | 预检查通过、暂存存在、无同类在途、影响面可计算 | H1 + 影响面摘要 | `lock:task:<id>` + `job:PUBLISH` | `taskId + PUBLISH + stagingVersion` | 生产行/发布结果；作业行 | 人工回滚到上一版快照；禁止自动回滚 |

**关键点**：`JobService` 的守卫（`TASK_FINALIZED` / `JOB_ALREADY_RUNNING` / `PRECHECK_NOT_PASSED` / `PRECHECK_STALE`）已经覆盖了大部分业务前置，**应把它们前移到 `PRE_CHECK` 并以只读方式调用**，而不是在批准后才发现 409。执行时仍需再跑一遍（闭合 TOCTOU），但这次是"复核"，不是"首次告知"。

#### 4.3.3 `navigate_to`（U）

- **现状**：`@ToolScope("*")`、READ、FRONTEND（`AiTools.java:382`）。前端 `resolveNavigateIntent` 只校验 `page` 是否在 `tasks/export/import/definitions/data`，`taskId` 只要求正整数；带 `taskId` 且目标是 export/import 时直接 `restore_task`（`frontend-tools.ts:716`）。
- **风险**：可以把工作区绑定到任意任务；不校验任务类型与目标页是否匹配（IMPORT 任务可以打开 export 页）；`page=tasks` 时 `taskId` 被忽略，模型可能误以为已绑定。
- **默认策略**：页面枚举 + `taskId` 存在性 + 任务类型匹配（export 页只接受 EXPORT 任务，import 页只接受 IMPORT 任务）+ 目标页白名单；执行后验证 `workspace.pageId === page && workspace.taskId === expected`；无副作用，不需要审批；重复调用幂等。
- **标签**：应改为 U/W 类，不再是 READ。

#### 4.3.4 `select_definitions` / `set_condition` / `confirm_step`（U）

这三个是"向导驱动动作"，当前全部 READ + FRONTEND，但都会改变工作区/持久状态。

**`select_definitions`**

- **现状**：`@ToolScope({"page:tasks","task:EXPORT","task:IMPORT"})`（`AiTools.java:393`）。前端 `normalizeActionArgs` 把 `mode` 归一为 `args.mode === 'ADD' ? 'ADD' : 'REPLACE'`（`frontend-tools.ts:874`）。`export.selectDefs` 直接把 `codes` 写进 `selectedDefs`，不校验定义是否存在（`ExportWizardView.vue:1273`）。
- **明确缺陷**：`mode` 拼错（例如 `"add"`、`"APPEND"`、`"REPLACE "`）会被**静默当成 REPLACE**，可能把用户已选的配置项整批替换掉。这正是任务口径中"禁止把 mode 拼错当 REPLACE"的实例。
- **默认策略**：`mode` 严格枚举 `REPLACE/ADD`，大小写与空白只做**无损**归一（`trim` + 大写），其他值硬拒绝并回模型；`codes` 逐个校验存在且可导出；REPLACE 必须显式（缺省是否 REPLACE 要由工具契约写明，不能靠前端 `?:`）；执行后读回 `workspace.selectedDefs` 验证；按 `taskId + sorted(codes) + mode` 幂等。

**`set_condition`**

- **现状**：`@ToolScope({"page:tasks","task:EXPORT"})`（`AiTools.java:421`）。前端 handler 解析 `conditions` 后**立即** `tasksApi.setCondition` 落库（`ExportWizardView.vue:1299`）；失败时返回字符串 `"已设置 ... 但落库失败：..."`（`:1310`），该字符串会被当成功（`frontend-tools.ts:1023`）。
- **风险**：条件字段/操作符/值类型未在宿主侧校验；`parseConditionJson` 可能容忍未知字段；落库失败仍可能显示成功；条件写错会导致导出范围错误（少导/多导）。
- **默认策略**：校验 `defCode` 已在 `selectedDefs`、字段属于该定义、操作符在交集白名单、值类型与操作符匹配（`EMPTY/NOT_EMPTY` 不带值、`IN` 为数组）；落库失败必须返回结构化 `ok=false`；执行后读回 `task.conditionJson` 比对；按 `taskId + defCode + conditionHash` 幂等。

**`confirm_step`**

- **现状**：`@ToolScope({"page:tasks","task:EXPORT","task:IMPORT"})`（`AiTools.java:457`），`step` 参数 `required=false`（`:461`）。前端 `allowSteps: []`（不限制步骤），`toUiEvent` 在 `step` 为空时返回 `null` 并报缺参（`frontend-tools.ts:696`、`:751`）。后端 `TaskService.goToStep` 有任务终态守卫与步骤白名单（`TaskService.java:159`）。
- **风险**：模型省略 `step` 时得到的是"参数不完整"而不是"推进到下一步"；`allowSteps` 为空意味着前端动作表不做步骤级限制，依赖页面 handler 的 `goToStep` 校验；步骤推进可能持久化当前步骤数据，属于 U 类中的"有写"。
- **默认策略**：`step` 明确枚举 + 目标步骤必须是从当前步骤可达的合法转移；只读态拒绝；已在目标步则返回幂等成功；执行后读回 `task.currentStep`；进入 EXECUTE/PUBLISH 等执行步时，若该步会触发作业，应按 J/P 规则加审批或至少加"下一步将启动作业"的提示。

#### 4.3.5 `generative_form`（H）

- **现状**：READ + FRONTEND + `@ToolScope({"page:tasks","task:*"})`（`AiTools.java:516`）。`GenerativeFormGuard` 做 schema 白名单与回灌类型复核（`backend/src/main/java/com/example/configmgr/ai/form/GenerativeFormGuard.java:39`、`:57`）；schema 规则在 `GenerativeFormRules`。超时是 `FRONTEND_TIMEOUT`，语义是"结局未知"（`AiTools.java:504`），不是"未提交"。
- **风险**：表单是阻塞式交互，多个表单同时挂起会让前端 `liveForm` 单槽（`AiPanel.vue:524` 只渲染宿主表单）；用户关闭/取消要落 `FRONTEND_CANCELLED`；超时不能自动重试，否则可能重复收集/重复提交。
- **默认策略**：H 类自动放行 + schema 白名单；单轮最多一个活动表单；回灌按 schema 逐字段复核；用户取消是明确终态；超时进入 `UNKNOWN`，先检查前端是否已提交（`frontend_tool_result` 是否已到）再决定是否重新询问；禁止自动重发同一表单。

#### 4.3.6 `open_export_file_editor` / `download_export_files`（U/F）

**`open_export_file_editor`**

- **现状**：READ + FRONTEND + `task:EXPORT/EXPORT`（`AiTools.java:347`）。前端先 `ensureTaskBoundForTool(payload.taskId)`，再检查 `exportResults` 中是否有该 `defCode`，然后切到导出结果步并 `ensureGridLoaded`（`ExportWizardView.vue:1329`）。这是本仓前端工具里少见的"目标校验 + 结果验证"做得较好的例子。
- **默认策略**：U 类；保留目标校验；执行后验证 `activeTab === defCode` 且编辑器已加载；READ 标签应改；失败返回结构化 `ok=false`，不要只返回字符串。

**`download_export_files`**

- **现状**：READ + FRONTEND + `task:EXPORT/EXPORT`（`AiTools.java:366`）。1 个码直出 xlsx，≥2 个码打包 zip；码不在可导出清单时整体失败并回执可用码（`AiTools.java:357` 注释）。前端有 60s 预算，超时产出"结局未知"（`frontend-tools.ts:235`）。
- **默认策略**：F 类；校验 `taskId` 绑定与 `defCodes` 全部在可导出清单；按 `taskId + sorted(defCodes) + 导出文件版本/内容哈希` 去重；执行后验证浏览器下载记录或让用户确认；超时 `UNKNOWN`，先对账（是否已下载/是否已回灌），禁止自动重试；READ 标签应改。

## 5. 失败/修复分流表

### 5.1 结局分类

不要用"成功/失败"二元。至少区分：

| 结局 | 含义 | 是否已产生副作用 | 默认去向 |
|---|---|---|---|
| `SUCCEEDED` | 权威状态确认目标达成 | 是（预期） | 结束 |
| `FAILED_DETERMINISTIC` | 确定未执行，或执行了但确定失败且可判定 | 否/是但可判定 | 回模型或硬拒绝 |
| `FAILED_PRECONDITION` | 前置条件不满足，未执行 | 否 | 回模型/问用户 |
| `DENIED` | 策略/权限/审批拒绝，未执行 | 否 | 硬拒绝 |
| `DUPLICATE` | 同幂等键已执行，返回首次结果 | 是（首次） | 返回首次结果 |
| `PARTIAL` | 多步中部分成功 | 是（部分） | 补偿人工/继续受控步骤 |
| `UNKNOWN` | 已派发但无法确认是否执行/结果 | 未知 | **先对账**，禁止自动重试 |
| `SKIPPED` | 因前序失败/策略主动未执行 | 否 | 回模型，明确 `is_error` 语义 |

### 5.2 分流表

| 症状/判据 | 分类 | 分流 | 允许动作 | 禁止动作 |
|---|---|---|---|---|
| JSON 不合法、未知字段、类型不符、枚举拼写错 | 安全归一 / 回模型 | 若可**无损**归一（trim、大小写、明确别名）则归一；否则回模型并给出字段级原因 | 记录原始参数与归一后参数；返回 `INVALID_ARGUMENT` + 原因清单 | 猜测缺失目标、把 `"add"` 改成 `REPLACE`、丢弃未知字段后继续 |
| 工具名未登记 / 上下文未披露 | 硬拒绝 / 回模型 | 不执行，返回 `UNKNOWN_TOOL` / `SCOPE_DENIED`；审计 | 提示当前可用工具；让用户切页面/任务 | 按 READ/BACKEND 默认放行；静默换一个工具执行 |
| 参数目标与上下文目标不一致 | 回模型 / 问用户 | 若目标明确且用户有权，问用户"是要操作任务 A 还是 B"；否则拒绝 | 展示两个目标；让用户选择 | 自动改成当前任务；忽略 `taskId` 用上下文任务 |
| 目标不存在/类型不符/已终态 | 回模型 | 返回 `TARGET_INVALID` / `TARGET_FINALIZED`；不执行 | 提示正确目标或新建任务 | 自动创建替代任务；自动切到"最近一个任务" |
| 前置条件不满足（未预检查、指纹过期、有在途作业） | 回模型 / 问用户 | 返回具体 409 码；让用户先完成前置动作或等待/取消 | 展示前置条件与下一步 | 自动跳过预检查；自动取消在途作业；自动重试 |
| 审批被拒/超时 | 硬拒绝 | 不执行；返回"用户拒绝/超时"；结束该调用 | 记录审批人/时间/原因 | 自动批准；用同一工具的下一次调用"重试"绕过拒绝 |
| 执行前连接失败/池饱和 | 可重试（仅当未派发） | 若 `DISPATCHED` 未写、幂等键未消费，可重试一次 | 返回 `RETRYABLE` + 退避 | 无幂等证明的重试；在 `DISPATCHED` 后重试 |
| 执行超时/进程崩溃/回执丢失 | **先对账** | 读台账、作业行、任务行、文件/暂存、页面绑定；判定 `SUCCEEDED/FAILED/UNKNOWN` | 返回 `UNKNOWN` + 对账证据；必要时问用户 | 直接重发；把超时当失败；把超时当成功 |
| 工具返回错误字符串但 `ok=true` | 安全归一 / 回模型 | 统一信封；按 `code` 分类；未知码转 `UNKNOWN` | 记录原始文本与结构化码 | 以字符串包含"失败"猜结局；以 `ok=true` 当成功 |
| 多步中部分成功 | **补偿人工** | 停止后续依赖步骤；列出已完成/未完成；给出补偿建议 | 人工确认后补偿或继续 | 自动回滚生产数据；自动重跑整个链 |
| 发布后验证失败 | **补偿人工** | 不自动重发；保留证据；人工决定回滚/修复 | 回滚到上一版快照（人工） | 自动再次发布；删除证据 |
| 重复幂等键 | 先对账 | 返回首次结果；若参数不同，硬拒绝 | 展示首次参数与本次参数差异 | 以新参数执行；静默覆盖首次结果 |

### 5.3 明确禁止的自动修复

以下行为在"模型提议 + 宿主执行"的治理链中一律禁止，无论实现起来多方便：

1. **未知 `taskId` 换成当前任务**：这是最危险的"善意猜测"，会把操作打到用户没指定的对象上。
2. **非法条件丢弃后按全量导出**：空条件等于"导出全部"，是范围的实质扩大。
3. **`mode` 拼错当 `REPLACE`**：当前前端已有此行为（`frontend-tools.ts:874`），必须改成严格枚举。
4. **超时自动重试**：超时可能已经执行；重试可能重复发布/重复下载/重复建作业。
5. **自动批准 / 对同一工具"永久批准"**：审批必须绑定单次提议的目标与参数；sticky approval 只能用于明确低风险且用户显式选择的场景。
6. **把空字符串/未知结果当成功**：`delegateSingle` 的 `.orElse("")` 与前端字符串失败都是实例。
7. **把失败的 `defCode` 换成第一个可用项**：这是"替用户做业务决定"。
8. **静默截断 `codes` / 行数 / 结果**：截断必须 in-band 告知，且不能改变业务范围。
9. **为了让工具可用而自动切页面/切任务**：上下文不匹配应回模型/问用户，不应由宿主"帮忙凑条件"。
10. **在 `DISPATCHED` 之后无幂等证明地重试**：先对账，再决定。
11. **自动回滚生产发布**：补偿是人工决策；自动回滚可能覆盖别人的新数据。
12. **把 scope 拒绝改写成"换个工具试试"**：换工具可能绕过同一策略，必须回模型并保留拒绝记录。
13. **把模型提供的幂等键当作唯一权威**：模型可复用/伪造；宿主必须自己生成或校验。
14. **前端工具超时后自动重发同一表单/下载**：用户可能已经提交/下载。

### 5.4 先对账的顺序

当结局是 `UNKNOWN` 或工具返回文本与 `ok` 矛盾时，按以下顺序读权威状态，读到足够判定即停：

1. **台账**：按业务幂等键 / `toolCallId` 查 `ai:ledger:<runId>`，看是否有执行完成记录（`RunStore.java:449`）。
2. **执行认领**：查 `ai:claim:<runId>` 是否有 owner（`RunStore.java:427`）；有 owner 无台账 = "可能执行中/执行后崩溃"。
3. **作业行**：按 `taskId + jobType` 查最近作业与在途作业（`JobRepository.findTopByTaskIdAndJobTypeOrderByCreatedAtDescIdDesc`、`findFirstByTaskIdAndJobTypeAndStatusInOrderByIdDesc`）。
4. **任务行**：`TaskService.findById` 看 `currentStep/status/items`。
5. **文件/暂存/生产**：导出文件是否存在、暂存行数、发布结果/快照。
6. **前端/工作区**：`workspace.pageId/taskId/selectedDefs/step` 与表单回灌是否已到。
7. **外部回执**：浏览器下载记录、用户确认。

判定规则：有"已完成"证据 → `SUCCEEDED`；有"确定未开始"证据 → `FAILED_DETERMINISTIC` 可重试；两者都无 → `UNKNOWN`，转人工或等待一个对账窗口，禁止自动重发。

## 6. 建议状态机

### 6.1 状态定义

| 状态 | 含义 | 必须持久化 | 允许的下一状态 |
|---|---|---|---|
| `PROPOSED` | 已接收模型提议，尚未做任何检查 | `runId`、`toolCallId`、工具名、参数原文、上下文快照 hash、提议时间 | `PRE_CHECK` |
| `PRE_CHECK` | 只读预检：schema、scope、目标解析、前置状态、风险分级、影响面 | 归一后参数、目标资源引用、预检报告、报告 hash、资源版本 | `APPROVAL` / `READY` / `FAILED` / `MANUAL` |
| `APPROVAL` | 等待人工决策（仅需审批的调用） | 审批人、审批时间、批准/拒绝、审批时报告 hash、过期时间 | `READY` / `FAILED` / `MANUAL` |
| `READY` | 已获准，等待派发；已拿租约、已分配幂等键 | 租约 owner/TTL、幂等键、执行通道、派发前复核结果 | `DISPATCHED` / `FAILED` / `MANUAL` |
| `DISPATCHED` | 已把执行交给后端/前端/作业，**不确定性从此开始** | 派发时间、执行者、尝试号、请求摘要 | `RUNNING` / `UNKNOWN` / `FAILED` |
| `RUNNING` | 执行中（同步工具/前端动作/异步作业） | 心跳、进度、可取消标记 | `VERIFYING` / `UNKNOWN` / `FAILED` |
| `VERIFYING` | 读权威状态确认结果 | 证据（作业行/任务行/文件/页面）、验证时间 | `SUCCEEDED` / `FAILED` / `UNKNOWN` |
| `SUCCEEDED` | 权威状态确认达成 | 结果摘要、证据引用 | 终态 |
| `FAILED` | 确定失败且可判定 | 错误码、是否可重试、证据 | `REPAIR` / `COMPENSATE` / `MANUAL` |
| `UNKNOWN` | 无法确认是否执行/结果 | 对账记录、已查来源、待查来源 | `REPAIR` / `COMPENSATE` / `MANUAL` |
| `REPAIR` | 受控重试/修复 | 原幂等键、尝试号、修复动作 | `READY` / `MANUAL` |
| `COMPENSATE` | 补偿中/待补偿 | 补偿动作、补偿幂等键、执行者 | `SUCCEEDED` / `FAILED` / `MANUAL` |
| `MANUAL` | 需人工介入 | 原因、建议动作、证据 | 终态 / `READY`（人工放行后） |

### 6.2 关键转移

```text
PROPOSED
  └─> PRE_CHECK ──┬─> APPROVAL ──┬─> READY ──> DISPATCHED ──> RUNNING ──> VERIFYING
                  │              ├─> FAILED (拒绝/超时)
                  │              └─> MANUAL (需要补充信息)
                  ├─> READY (无需审批)
                  ├─> FAILED (参数/目标/前置/策略拒绝)
                  └─> MANUAL (目标歧义)

VERIFYING ──┬─> SUCCEEDED
            ├─> FAILED ──┬─> REPAIR ──> READY (同幂等键、新尝试号)
            │            ├─> COMPENSATE
            │            └─> MANUAL
            └─> UNKNOWN ─┬─> REPAIR (对账确认未执行)
                         ├─> COMPENSATE (对账确认已执行但结果不对)
                         └─> MANUAL (无法判定)
```

### 6.3 不变量

1. **提议不可变**：`PROPOSED` 的参数原文、目标引用、上下文 hash 一旦写入不得改写；后续所有状态引用同一 `proposalId`。
2. **无 READY 不执行**：任何外部副作用之前必须经过 `READY`；`READY` 之前不得调用工具、不得创建作业、不得触发下载。
3. **审批绑定摘要**：审批记录绑定 `reportHash + resourceVersion`；审批后资源版本变化，`READY` 复核必须发现并回到 `PRE_CHECK` 或 `MANUAL`。
4. **一幂等键一执行**：同一幂等键最多一个 `DISPATCHED`；重复派发返回首次结果或 `DUPLICATE`。
5. **UNKNOWN 不等于失败**：`UNKNOWN` 不得直接进入 `FAILED` 或自动 `REPAIR`；必须先对账。
6. **验证读权威态**：`SUCCEEDED` 必须有至少一个权威证据（作业行/任务行/文件/页面绑定），不能只凭工具返回文本。
7. **写前落库**：每次状态转移先持久化，再产生外部效果；崩溃恢复从最后持久化状态继续。
8. **取消在边界**：`DISPATCHED` 之后取消，必须先对账再决定终态；不能直接标"未执行"。
9. **补偿幂等**：补偿动作必须能处理"原步骤可能已执行/可能未执行"，且重复调用不产生二次副作用。
10. **审计可重建**：从 `PROPOSED → ... → SUCCEEDED/FAILED/UNKNOWN` 的记录应能重建"谁提议、谁批准、执行了什么、证据是什么、补偿是什么"。

### 6.4 实施优先级（建议，不构成承诺）

**P0（正确性与诚实性，先做）**

1. **统一结果信封**：后端/前端/SSE/台账共用 `{ok, code, outcome, retryable, target, evidence, message}`；前端回灌带 `outcome`；模型侧 `ToolResponse` 序列化该信封。
2. **PRE_CHECK 前移**：把 `JobService` 的只读守卫与 `create_task` 的 type/title 校验前移到审批之前；确认卡展示预检摘要。
3. **多闸门身份修复**：确认提交必须使用卡片所在 `toolCallId`（API 已带字段；前端 store 不得使用单槽投影）；按钮显式传参，禁止无参 `decide()`。
4. **早点击竞态修复**：闸门登记先于/等同于 `saveSuspended`；`maybeTriggerResume` 增加"仍有 PENDING in-flight"或"闸门登记宽限"判据。
5. **FRONTEND 风险重标**：按 2B 的"18 工具逐个重审"把下载/选择/条件/步骤/导航从 READ 改为能表达副作用的等级。
6. **目标资源校验**：从 args 解析 `taskId/defCode/step`，与上下文/用户/资源类型比对；`start_*` 必须校验任务类型与当前绑定。

**P1（互斥与恢复）**

7. **资源租约**：`lock:task:<id>` / `lock:def:<taskId>:<defCode>` / `lock:job:<taskId>:<jobType>`，TTL + owner + 续期 + 终态释放；作业表补同任务同类型在途的唯一约束。
8. **业务幂等键**：宿主生成、台账保存、同键重放返回首次结果、同键不同参硬拒绝。
9. **UNKNOWN 对账器**：按 §5.4 顺序读权威状态；对账结果写入台账；未对账前禁止重试。
10. **批策略**：R/H 可继续；U 按依赖；W/J/P 首错即停并为未执行项返回 `SKIPPED`。
11. **`mode` 严格枚举**：禁止 `ADD` 之外的任何值静默变 `REPLACE`；未知值回模型。

**P2（审计与补偿）**

12. **审批审计**：审批人、审批时间、审批时报告 hash、资源版本、拒绝原因进入台账/回执。
13. **补偿登记**：每个 P/J 工具声明补偿动作与幂等键；发布类只允许人工触发。
14. **指标**：审批延迟、拒绝率、UNKNOWN 率、对账耗时、重复幂等键命中率、按工具的错误码分布。

## 7. 与问题 2B / 2C 及后续工具编排专项的关系

### 7.1 与 2B 的关系

2B 的范围是"H1 定型 + `create_task` 收编 + 18 工具风险标注重审"（`docs/research/裁决-HITL型谱与问题2方案-2026-10-17.md:77`）。本件对 2B 的直接输入是：

- **风险矩阵**：§4.2 的 18 行分类与"现标注"列，可作为"逐个重审"的事实底稿；特别是 7 个 FRONTEND 工具的 READ 标签。
- **`create_task` 的默认策略**：§4.3.1 的"软确认/门 + 宿主幂等 + 单轮上限"与 2B 的"不得静默建库"同向。
- **H1 卡的信息面**：§3.6 的"确认卡只有 args、没有 preflight"说明 2B 的 H1 卡在施工时应至少展示预检摘要；否则 H1 只是"把参数再给用户看一遍"。
- **审批身份**：§3.9 的多闸门单槽是 2B 的 H1 卡在"多 DANGER 调用"场景下的直接缺陷；2B 即使不做 2C 的批量中断，也应先保证"按钮提交的 `toolCallId` 与卡片一致"。

本件不改变 2B 的型谱（H1/H2/H3/GF 的边界），只补充"审批前要有 preflight、审批要绑定目标与版本"的治理要求。

### 7.2 与 2C 的关系

2C 的范围是"H2/H3 新卡型 + 步进 + SSE 与后端批量中断支持 + `FormRenderer` 扩展 + combobox"（同上 `:78`）。本件对 2C 的直接输入是：

- **批量中断的协议面**：当前 `suspended` 帧带全部 `pendings`，但前端只有单槽 `pendingToolCall`（`ai.ts:885`）；2C 的"批量中断支持"必须定义逐项 `toolCallId`、逐项状态、逐项决策的帧与恢复语义。
- **"全部处理完才恢复运行"**：2C 的步进语义（`docs/research/裁决-HITL型谱与问题2方案-2026-10-17.md:47`）与本件状态机的 `APPROVAL → READY` 只在"所有待决项都解决"后发生一致；不能一项批准就恢复整轮。
- **H2/H3 的失败分流**：选择/输入类交互的取消、超时、非法值，应落 `FRONTEND_CANCELLED` / `UNKNOWN` / `REJECTED_ARGUMENTS`，不能都折成 `ok=true` 的文本。
- **表单单槽**：`generative_form` 的 `liveForm` 单槽（`AiPanel.vue:524`）与 2C 的多步表单/多问组合需要重新设计；否则同一轮多个表单会互相覆盖。

### 7.3 与后续工具编排专项的关系

后续若做"多工具编排"（并行调用、依赖 DAG、批处理、跨工具事务），本件的八层与状态机是地基：

- **并行**：只读可并行；有副作用/共享状态/顺序要求的调用必须串行或按 DAG 拓扑执行；每个节点仍有独立的 `PROPOSED → ...` 生命周期。
- **依赖**：上游 `SUCCEEDED` 才允许下游 `READY`；上游 `UNKNOWN` 必须阻塞下游，先对账。
- **批处理**：批级状态机 + 项级状态机；批级 `PARTIAL` 必须能列出每项状态与补偿建议。
- **跨工具事务**：Saga 式补偿；每个正向动作登记补偿；补偿必须幂等并能处理"可能没发生"。
- **取消**：取消是批级信号，但每个已在 `DISPATCHED/RUNNING` 的项要先对账再收尾。

这些是方向性输入，不是施工承诺；具体协议、帧格式、SDK 选型由后续专项裁决。

### 7.4 本件不做什么

- 不提出新的 HITL 型谱，不改变 H1/H2/H3/GF 的边界；
- 不设计多租户身份/授权协议；
- 不承诺任何接口、帧字段、数据库表结构或排期；
- 不评价具体模型的工具选择能力；
- 不把"建议"写成"已决"。
