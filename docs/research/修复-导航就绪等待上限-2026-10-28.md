## 1 问题

导航类前端工具（`navigate_to` / `restore_task` / `ui_event` 的导航分支）在派发后要等目标现场齐备才回灌。NAV2（第 81 件）把「成功判据」从**一维**升级到**三维**：

- **页面**：`workspace.pageId` 已切到目标页，且该页的**能力 handler** 已注册（`registerPageHandler` 发生在 `onMounted`，是"页面真的挂上了"的可靠口径，见 `frontend/src/utils/frontend-tools.ts:784`–`:797`）；
- **绑定**：`workspace.taskId === 期望任务号`（`restore_task` / 同页绑定只**同步**写这一位）；
- **详情**：页面自报「详情已应用」的只读探针返回 `true`（选中集 / 条件草案 / 步骤 / 状态已由 `loadTask` 恢复，见 `TASK_DETAIL_READY_PROBES`，`:829`–`:845`）。

判据扩了，**等待预算没扩**：`PAGE_READY_TIMEOUT_MS` 仍是页就绪时代的 **3 000 ms**（`:800`）。于是出现这样一类现场 —— 页面挂载与任务绑定**先**完成（挂载与 `workspace.taskId` 都是短路径），详情（一次 `GET /tasks/{id}` 加应用）在 **3–8 秒之间**才落地：

- 旧上界在 3 s 到点 ⇒ 三维里 `detailReady=false` ⇒ 回执走 `taskDetailNotReady`（`:1016`–`:1028`）：`failed` + `degraded` + `UI_PAGE_NOT_READY`，文案「页面已打开、任务 #N 已绑定，但任务详情在等待上界内仍未应用」。
- 模型读到的是一句**失败**：本轮不要再推进；用户看到的却是页面**几秒后就好了**。同一句回执既可能是"这台机器慢"，也可能是"详情真的读坏了"，**施工侧与模型都分不开**。

## 2 根因

**根因：判据与被判据的等待窗不同源。**

1. 这个常量是**四个等待函数共用的默认参数**，不是导航专用：
   - `waitForPageReady(page, timeoutMs = PAGE_READY_TIMEOUT_MS)`（`:812`）；
   - `waitForTaskDetailApplied(page, timeoutMs = PAGE_READY_TIMEOUT_MS)`（`:874`–`:877`）；
   - `waitForTaskBound(page, expectedTaskId, timeoutMs = PAGE_READY_TIMEOUT_MS)`（`:916`–`:920`）；
   - `waitForTaskOpened(expectedTaskId, timeoutMs = PAGE_READY_TIMEOUT_MS)`（`:953`–`:956`）。
   3 s 这个值成形于「只需等页面挂上」的年代（`PAGE_READY_PROBES` 一维）；NAV2 把**异步详情**并进成功判据后，等于让一次网络读 + 应用去挤一个为"挂载"准备的窗口。
2. 到点的语义是**硬失败**：`Date.now() >= deadline` 时返回**当时的三维真值**（`:932`–`:934`、`:968`–`:970`），调用方按维数分流出不同回执。这是对的（不无限等），但意味着**上界选小了 = 正常现场被稳定判失败**。
3. 上界偏小的代价不对称：判晚了只是这一轮少省几秒；判早了会让模型**放弃本可走通的一步**（并可能触发不必要的重试 / 让用户手动打开）。旧上界与「慢但正常」的区间重叠 ⇒ 属**系统性误判**、不是偶发（真实耗时分布未实测，见 §5 第 1 条）。

## 3 修改

**唯一生产改动 = 一个常量的一行取值**（`frontend/src/utils/frontend-tools.ts:800`，注释 `:799` 未动）：

```ts
/** 页面就绪等待上限（毫秒）：超过即如实告知"仍在加载"，不无限等。 */
export const PAGE_READY_TIMEOUT_MS = 8_000   // 旧值 3_000
```

**随之自动生效的四处**（都读默认参数，无第二处硬编码）：`waitForPageReady` / `waitForTaskDetailApplied` / `waitForTaskBound` / `waitForTaskOpened`。调用方**没有**传自定义超时的路径，故不存在"改了一处、漏了另一处"。

**明确不动的部分（逐条）**：

| 面 | 现状 | 本批 |
|---|---|---|
| 轮询方式 | 条件轮询，判据成立立即返回；间隔 `delay(50)` | 不动 |
| 就绪判据 | `pageId` 匹配 + 能力 handler 已注册（`PAGE_READY_PROBES`，`:784`–`:797`） | 不动 |
| 详情判据 | 只读探针返回布尔；**探针缺席视为该维不适用**（不替页面判假）；探针抛异常按 `false`（`:847`–`:867`） | 不动 |
| 到点语义 | 返回三维真值、由调用方分流；不退化成无限等 | 不动 |
| 回执面 | `taskDetailNotReady`（`:1016`–`:1028`）/ 页面未就绪（`:1091`–`:1101`、`:1714`–`:1726`）的 `code`、`outcome`、`availability` 与文案 | 不动 |
| NAV2 两维 | `opened` / `detailReady` 分开返回 + `opened-detail-pending` 态（`:1632`–`:1684`） | 不动 |
| 路由 | 不重推、不回退；导航成功静默不写回执位 | 不动 |
| HITL / 风险 | 风险分级、确认门三态、通道（`DANGER ⇒ BACKEND` 等） | 不动 |
| 帧 / 字段 / 配置键 | 16 帧冻结 | 不动；8 s 仍**不是配置项**（代码常量） |

**为什么是 8 000 而不是更大**（取值口径，**不是实测分布**）：上界必须显著大于「一次任务详情读 + 应用」的慢尾，又必须远小于外层预算，否则等待会被外层计时器先打断（见 §5 第 3 条）。生产预算 = 服务端挂起上限折算出的 `FRONTEND_TOOL_TIMEOUT_BUDGET_MS`（默认 **60 000 ms** = 挂起上限 120 s − 回灌 POST 上限 60 s，`:316`、`:57`；帧侧由 `deriveFrontendToolBudgetMs(frame.timeoutSeconds)` 给出，`frontend/src/stores/ai.ts:7778`）。8 s 约占该预算的 **13%**，既留够慢尾，又不会把一次导航拖成"半分钟没反应"。

## 4 测试

### 4.1 新增边界用例（本批的核心证据）

`frontend/tests/frontend-tool-restore-task.spec.ts:325` —— `详情在 3–8 秒之间完成：旧 3s 上界会降级、8s 上界应成功；超过 8s 仍 UI_PAGE_NOT_READY`。

- **夹具**：`registerPageHandler('export.taskDetailReady', () => detailReady)`（`:328`），`api.getTask` 返回 `{ id, type: 'EXPORT', status: 'ACTIVE', items: [], currentStep: 'EXPORT' }`（`:331`、`:347`）—— **`status` 统一 `ACTIVE`**（`TaskStatus` 四值 `ACTIVE | COMPLETED | CANCELLED | FAILED`，`frontend/src/types/task.ts:12`，`IN_PROGRESS` 不在枚举内）；两个边界各用独立 `id`，`budgetMs: 20_000`（`:335`、`:351`）把等待窗与预算分开，测的是上界而不是预算。
- **边界一（~5 s 完成）**：`advanceTimersByTimeAsync(4_950)` 后断言详情仍未应用（`:338`，即旧 3 s 上界此时**早已到点**）⇒ 置 `detailReady = true` ⇒ 再推进 `100` ⇒ `outcome === 'ok'`，回执含「可继续执行本页动作」（`:343`）。
- **边界二（超过 8 s）**：详情始终不应用 ⇒ `advanceTimersByTimeAsync(8_100)` ⇒ `outcome === 'failed'`、`availability === 'degraded'`、`code === 'UI_PAGE_NOT_READY'`（`:353`–`:357`）。
- **RED / GREEN**：**旧 3 s 下边界一红**（同一条用例在 3 s 上界上，5 s 才完成 ⇒ 拿到 `failed` + `degraded`）→ **改 8 s 后绿**；边界二在两种上界下**结论一致**（都判 `failed` + `UI_PAGE_NOT_READY`）—— 它是**硬上界仍在**的守卫：上界变大也不许退化成"永远等"。

## 5 边界（连读才可引用）

1. **真实度边界**：所有证据都在 jsdom + `vi.useFakeTimers()` 下取得 ⇒ 证明的是**判据与上界的数学关系**（3 s 到点会失败、5 s 完成能成功、8.1 s 仍失败），**不证明**真实浏览器里「路由解析 + `onMounted` + `GET /tasks/{id}` + 应用」的实际耗时分布，也不证明 8 s 对真实慢尾足够。**真实浏览器未验**。
2. **8 s 是上界，不是目标**：判据一成立就返回，正常现场仍是毫秒级；上界只影响"最坏等多久"。慢过 8 s 的现场**仍**会拿到 `taskDetailNotReady`（`failed` + `degraded`），本批**不重试、不换路、不改路由**。
3. **外层预算先到者胜**：`executeFrontendTool` 用计时器包住执行体（`:442`–`:449`），预算到点即产 `timeoutOutcome`（`:564` 起），并置 `lifetime.abandoned = true`（`:497`）。因此 **`budgetMs` < 8 s 的调用等不到「上界到点」那一支结局**（该支必然在 8 s 才产出）—— 它先拿到的是「前端超时」：`UI_PAGE_NOT_READY` / `taskDetailNotReady` 要等满上界才产出，而参数不完整、类型未知、绑定未完成这些**短路径失败**仍会正常返回。生产默认预算 60 s 不受影响（8 s ≪ 60 s）；受影响的只有把预算压到 5–8 s 的调用方（本批的测试夹具正是这一类，故 §4.3 上调）。预算下限仍是 `MIN_FRONTEND_TOOL_TIMEOUT_BUDGET_MS = 5_000`（`:335`）。
4. **代价 = 最坏多等 5 秒**：单次导航类调用最坏占用工具槽位由 ~3 s 变成 ~8 s（同一轮前端工具串行 ⇒ 一条链路可能叠加）。可预见的上界是"预算 60 s 内最多约 7 次这样的等待"，本批**未**为此新增并发、取消或退避语义。
5. **等待循环不读 `lifetime.abandoned`**：它只轮询只读探针、不产生写。外层超时后这条被抛弃的续体仍会跑完自己的 deadline（最多到 8 s），期间只多几个 `delay(50)` 定时器；那条晚到的结局**不会**进同参去重表（`if (!lifetime.abandoned) rememberSameCall(...)`，`:617`–`:619`），故不会把"超时后的晚到成功"毒化成"本轮已执行过"。这一点本批**未改**，只是把窗口从 3 s 拉长到 8 s。
6. **口径 supersede（只 supersede 一句边界声明，不改裁决）**：第 81 件（`docs/research/修复-创建导航与步骤推进-2026-10-27.md:123`）把「**不改等待上界**」写成了当时的边界；本批**正是**改这个上界 ⇒ 该句自本批起失效，引用时以本件为准，**旧件原文不改**。**不新增决策、不 supersede 任何 `AR` 条**（3 s → 8 s 是实现取值，不是新的规格裁决）。
7. **本批不动的判据仍然最硬**：详情未应用就不放行（否则紧随的 `confirm_step` 会拿空选中集推进并向服务端落库）——放宽的只是**等多久**，不是**等什么**。`isTaskDetailReady` 的"探针缺席 = 该维不适用"也一字未改（`:847`–`:867`），所以页面上没挂探针时不等于被本维判死。
8. **未改的相邻面**（供后续批对齐）：`UI_PAGE_NOT_READY` 仍是「页面未就绪」与「详情未应用」共用的 code，只能靠文案区分；轮询间隔仍是 50 ms（无退避）；上界仍不可配置。
