## 0. 总体判断

用户连续指出的不是 12 个互不相干的小样式问题，而是三类结构性偏差：

1. **展示与事实脱钩**：阶段心跳被画成「压缩」，局部挂起被画成整轮「等待确认」，轮次未完却出现完成时间。
2. **为机器流程增加 C 端心智负担**：复制页签、知情摘要、层级字段、创建任务的多轮编排都让用户理解内部机制。
3. **派生状态没有单一事实源**：`loading`、`suspended`、`pendingToolCall`、`runPhase`、`streaming` 和阶段条各自决定一块 UI，交界产生禁用、假等待、状态消失。

因此方向应是减少展示、减少状态、减少用户必须理解的步骤，而不是继续加提示和补丁。

## 1. 用户提出的 12 项

### 1. 新会话立即显示「上下文压缩」

- **代码事实**：每轮都在真正判断压缩前发出 `heartbeat{phase=compacting}`：`backend/src/main/java/com/example/configmgr/ai/run/ResilientChatService.java:499-503`；续跑同构：`ResumeService.java:1505-1511`。真正压缩结果只决定是否发 `context` 帧：`ResilientChatService.java:2597-2612`。
- **前端误判**：`frontend/src/stores/ai.ts:7166-7189` 将阶段切换当成压缩完成，阶段组件再显示「已压缩」。
- **结论**：这是**假压缩提示**，不是新会话真的发生了上下文压缩。已核引入提交为 `c6734b7`。
- **收敛建议**：删除面向用户的压缩阶段条；保活属于内部机制，不应映射成业务事实。

### 2. 工具 / HITL 期间输入框被禁用

- **代码事实**：`frontend/src/components/AiPanel/AiPanel.vue:2293-2301` 将健康异常、`ai.suspended`、`pendingToolCall` 合并为硬禁用，作用于输入框和发送按钮（`:1226`、`:1267`）。
- **恢复放大**：`frontend/src/stores/ai.ts:3272-3279` 对任何 PENDING 条目都置 `suspended`，包括无需用户操作的后端项或 `req=false` 项；自动前端工具也会触发挂起。
- **结论**：偏离原规格「允许继续输入，只是不响应回车发送；用户可停止后再发送」。等待用户操作与系统正在执行被错误合并。
- **收敛建议**：不要给现有布尔再补条件；区分「可编辑」与「可发送」，只保留用户原规格所需的一条发送闸。

### 3. HITL 变成静态「等待你的确认」，呼吸效果消失

- **代码事实**：`AiPanel.vue:948-962` 优先渲染静态等待文案和静态圆点；真正呼吸在 `v-else-if` 分支。`waitingKind()` 在 park 时取代原「工作中」（`:2582-2602`），`isBreathing()` 又显式排除 waiting、unconfirmed、compacting、preparing（`:2616-2624`）。
- **结论**：已核由 `0ede5cc` 引入。它不是单纯文案变化，而是同时删除活动感，违背用户明确要求的既有体验。
- **收敛建议**：不叠加第二套状态条；保留轮次仍活跃时的「工作中 + 呼吸」，确认卡自身已经表达需要用户操作。

### 4. 「已在新页签开始新会话；原页签的对话不受影响」

- **代码事实**：复制页签后清理 `sessionStorage`、采用新会话并弹通知：`frontend/src/stores/ai.ts:6594-6611`。通知是全局单槽（`:1796-1830`），会被后续提示或新一轮清掉；不支持 Web Locks 时甚至不进入该告知路径（`:6577-6580`）。
- **体验矛盾**：提示称原页签不受影响，但副本又可能在原页签关闭后静默接手原会话；用户需要理解页签所有权这一内部机制。
- **结论**：这是开发 / 测试视角提示，不应暴露给 C 端用户。
- **收敛建议**：优先静默处理；不在提示体系里继续解释页签、会话和接管关系。

### 5. 思考区仍显示字数和展开操作

- **代码事实**：`frontend/src/components/AiPanel/ReasoningHeader.vue:74-77` 固定拼接「N 字 · 展开/收起」；`:95-111` 同时渲染「思考过程」、字数操作、独立计时和箭头。整个卡头是 button（`:85-112`）。
- **计时已经存在**：`:61-72` 根据进行中 / 已结束选择计时文案，但界面又叠加标题、字数和展开操作。
- **结论**：问题不是思考 Markdown 渲染，而是**信息层级与用户指定格式不符**。
- **目标口径**：进行中只显示「思考中 + 计时」；结束后只显示「思考过程 + 耗时」。删除字数和「点击展开」提示，不再增加新标签。

### 6. 输出光标一直在底部，不能跟随文字

- **代码事实**：Markdown 正文块 `AiPanel.vue:330-338` 是块级 div，光标是它后面的兄弟节点（`:351-355`）；因此光标天然落在整个块之后，而非最后一个字符后。
- **结论**：这是 DOM 结构决定的稳定错位，不是动画参数问题。
- **用户口径**：直接去掉光标，保留一个轮次级活动状态即可。

### 7. 启动导出作业只能选已有任务，不能新建

- **代码事实**：`create_task` 虽存在，但只创建「类型 + 标题」的空任务，且明确「创建≠执行」：`backend/src/main/java/com/example/configmgr/ai/tools/AiTools.java:296-325`。流程被拆成 create → navigate → select → confirm → start，多轮继续。
- **披露限制**：`create_task` 只在任务中心和任务上下文披露（`:298`）；新建空任务还会被作业预检拒绝，无法直接启动。
- **结论**：当前具备的是「分步创建空壳」，不是用户要求的「在 AI 对话中新建并完成导出配置后启动」。不能仅用「已有 create_task」否定该缺口。
- **收敛建议**：后续若施工，应收成一条用户任务链，而不是再向用户暴露更多内部步骤；这涉及既有 `AR-03` 与流程规格，须单独裁决。

### 8. 「知情摘要」新增概念

- **代码事实**：确认卡把影响面、条件、发布模式放入 `gateFactsRows`，模板为可折叠行：`AiPanel.vue:501-522`、`:725-745`；`gateFactsExpanded` 初始为空，故默认收起（`:4801-4805`）。
- **后果**：关键 REPLACE 等影响在确认前默认不可见，用户还要学习「知情摘要」这一新名词。
- **结论**：字段虽已存在，但新增折叠概念没有降低心智负担，反而隐藏关键后果。
- **收敛建议**：删除独立概念和折叠交互；确认卡只保留作出决定必需的信息，关键后果不得默认藏起来。

### 9. 「选择要导出的配置项」出现层级选项

- **代码事实**：生成式表单工具说明直接支持并推荐 `definitions` 的「层级 → 定义」数据源：`backend/src/main/java/com/example/configmgr/ai/tools/AiTools.java:654`、`:765`；`backend/src/main/java/com/example/configmgr/ai/form/FormOptionSource.java:87-88` 将 GLOBAL/REGION/PROJECT 父值映射为该层级的配置定义。
- **结论**：这里指**导出选择表单的层级字段**，不是卡片视觉层级。它是批次 4 数据源扩展把内部配置层级带入用户流程。
- **收敛建议**：导出只让用户选配置项，删除层级前置选择；内部定义层级不应成为必填心智步骤。

### 10. HITL / 表单结束后，轮次未完却在底部出现日期时间

- **代码事实**：元信息行按互斥分支显示：等待 → 呼吸 → 时间戳（`AiPanel.vue:947-966`）。时间戳分支没有独立检查「本轮是否仍在运行」。确认结束后等待分支退出，即使本轮后续还在生成，只要宿主 `streaming` 已收口，就会落到时间戳。
- **恢复缺口**：`frontend/src/stores/ai.ts:3680-3689` 重建待决卡时将宿主 `streaming=false`；后续恢复路径并未在所有分支统一回置，进一步让未完成轮次看起来像已完成。
- **结论**：时间戳被当成互斥分支的兜底，而不是「整轮完成」的结果。
- **收敛建议**：时间只由整轮终态触发；未完成时绝不显示完成时间。镜像缺 `timestamp` 是另一个数据一致性缺口，不能替代本项根因。

### 11. 回复过程中「工作中」不显示

- **代码事实**：`isBreathing()` 除要求 `message.streaming` 外，还排除等待、未确认和准备 / 压缩阶段（`AiPanel.vue:2616-2624`）；阶段条又与其互斥。恢复宿主被置为非 streaming 时也会消失。
- **结论**：活动状态不是一个连续事实，而被多个局部状态切碎；用户看到的就是回复仍在继续但「工作中」消失。
- **收敛建议**：只保留一个轮次级活动指示，从用户发轮到整轮终态连续成立；HITL、表单、工具都是轮内事件，不应各自撤掉它。

### 12. 启动导出作业后直接开始下载

- **代码事实**：任务 COMPLETED 后，后端不再披露 `start_export`，明确引导模型改走 `download_export_files`：`backend/src/main/java/com/example/configmgr/ai/tool/ToolRegistry.java:427-439`；系统提示也直接这样要求：`ResilientChatService.java:227`。
- **自动副作用**：下载工具是 READ 风险，无确认门：`AiTools.java:454-461`；执行器挂载在导出向导页，前置校验后直接调用 `startDownloadInBackground()`：`frontend/src/views/ExportWizardView.vue:2239-2241`、`:2278`。底层 `saveBlob()` 直接 `link.click()`：`frontend/src/api/http.ts:206-214`。
- **状态 / 建议不一致**：终态收窄与提示词在任务完成后自动把「启动导出」语义切到「下载旧结果」；建议 chip 又可能不检查同一任务状态。
- **结论**：这是当前代码可证明的自动下载链，不是「没有执行器」；用户质疑成立。启动新作业与下载既有结果被混为一个对话意图。
- **收敛建议**：把「启动作业」和「下载结果」拆成明确且最小的动作边界；未经用户明确下载意图，不得由任务状态变化自动替用户选择下载。

## 2. 补充代码发现（9 项）

以下均为静态代码结论；涉及时序的项目未复现，只登记风险。

### S1. 终态 runner 与新作业可能双写（风险）

建作业守卫 `backend/src/main/java/com/example/configmgr/job/service/JobService.java:302-320` 只扫描非终态作业；删除守卫 `TaskService.java:555-580` 却承认终态作业的 runner 可能仍活着。看门狗将旧作业置 FAILED 后，在新任务创建窗口内可能放过旧 runner 与新 runner 并发写。收窄引入为 `d704e8c`。实际落库窗口仍需专项核实，不能写成已复现。

### S2. `retryModelStep` 可能全量回放旧 error（风险）

`frontend/src/stores/ai.ts:3573-3577` 在缺少序号锚点时回退为 0，重挂会从头回放旧 `error`；202 分支虽清 `errorCard`，但旧帧回放可重新写入。应禁止无锚点全量回放，而不是继续补清理逻辑。引入为 `0ede5cc`。

### S3. 新作业运行时可能下载旧批次（风险）

`frontend/src/views/ExportWizardView.vue` 的 `jobBatch/resultsBatch` 主要影响标签与旧结果判定；下载字节守卫只绑任务和任务代次，没有绑结果批次（`:1427-1435`、`:1515-1519`）。批次标签与实际字节可能错位，窗口未实机复现。

### S4. 自动前端工具也显示「等待确认」

恢复将任何 PENDING 条目置 `suspended`，但可重建卡仅覆盖特定 FRONTEND/CONFIRM 项；`waitingKind()` 最后又把无待决段的最后宿主兜底成 `confirm`（`AiPanel.vue:2601`）。于是自动执行、无需用户决策的工具也可能显示「等待确认」并锁输入。

### S5. `suspended` 清场依赖结果帧

历史加载失败时 `frontend/src/stores/ai.ts:2645-2658` 直接返回；`sealRecovery()` 不统一重置挂起（`:3428-3457`）。只有特定 leftover 路径或结果帧才清场，恢复失败可留下输入禁用和假等待。不能靠新增轮询掩盖，应先减少可残留的派生状态。

### S6. 长文降级提示按 `history-N` 跨会话串用

`AiPanel.vue:2757-2783` 的 `degradeNotices` 以消息 id 为键；历史消息 id 是 `history-${index}`（`frontend/src/stores/ai.ts:2845`）。每个会话都复用相同位置 id，且该表换会话不清空，提示会串会话。引入为 `a373663`。

### S7. 建议 chip 与实际任务 / 可用状态不一致

空态建议恒渲染，仅靠 disabled；每轮建议另有一套可见性判据（`AiPanel.vue:251-264`、`:2244-2266`）。这些判据没有统一使用 health、任务终态和可执行动作同一事实源，出现「看起来能点，实际禁用」或建议动作与当前状态不符。

### S8. `streamMdCache` 没有容量上限

`AiPanel.vue:2790` 是裸 Map，写入 / 删除在 `:2852-2874`，只在组件卸载时整体清空（`:5052`）。换会话、重试和停止并不保证逐块删除；历史缓存有预算而流式缓存没有。量级未 profile，但生命周期缺口成立。

### S9. 英文界面的工具结果仍可能硬编码中文

`backend/src/main/java/com/example/configmgr/ai/tool/ToolResultUserText.java:37-58` 直接存中文摘要，`SseChatEmitter.java:1304`、`:1388` 写入结果，前端 `AiPanel.vue:609-617` 原样展示。卡头走本地词表、卡体走后端中文，语言不一致。

## 3. 减法收敛建议

### 3.1 先冻结新增展示与派生状态

暂停新增提示条、徽标、折叠区、阶段条、组件缓存和状态布尔。对现有问题只做三类处理：删除、接回唯一事实源、修复数据正确性。禁止「再加一个提示解释上一个提示」。

### 3.2 C 端只保留四种轮次观感

建议对外只保留：**生成中 / 等待用户操作 / 已完成 / 失败**。内部阶段、压缩、工具状态、恢复缺口留在诊断层，不再分别抢占主界面。

- 生成中与等待用户操作都应有连续活动感，具体文案遵循用户对 HITL 的既有口径。
- 等待操作必须有一张真实可操作的卡；没有卡就不能显示「等待你的确认」。
- 只有整轮终态才显示完成时间。

### 3.3 优先删除用户无感的内部概念

优先评估删除：压缩阶段条、复制页签提示、打字光标、思考字数与展开提示、知情摘要折叠概念、导出配置的层级前置选择。判断标准是「删掉后用户能否更直接完成任务」，不是「已有代码是否还能复用」。

### 3.4 数据正确性修复单独保留，不与 UX 扩张捆绑

runner 双写、重试旧帧回放、下载批次错位、跨会话缓存键、无界缓存、英文界面中文属于正确性或资源生命周期问题，应独立收敛。不能借修这些问题再新增展示面。

### 3.5 每个后续施工项必须回答三个问题

1. 删除了什么旧展示、旧状态或旧分支？
2. 用户可见事实的唯一来源是什么？
3. 是否减少了用户必须理解的步骤？

答不出来就不施工。不要继续按 21 个表象逐个打补丁，应按「轮次状态、确认与表单、导出动作、缓存生命周期」四条链整体做减法。
