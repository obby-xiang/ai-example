## 1 问题根因

**多重写入点。** 裁决前同一份查询条件至少有四条能写业务库的路径：

| # | 写入点 | 裁决前 | 现在 |
|---|---|---|---|
| ① | `create_task(conditions)` 的候选 | 结构化条件先进 `extra.createTaskConditions`，再由宿主 `ConditionsForm#applyCreateTaskConditions` 走 `TaskService#setCondition` 落库 | **已改为草案下发**：`dispatchCreateTaskCandidates` 用同一份 `WizardActionGuard` 复核后经前端 `set_condition` 生成页面草案，**零业务库写入** |
| ② | 前端 `export.setConditions` handler | 裁决前"设置即落库"（`PUT`） | **已改为只写草案**（`draftModels`/workspace，不再发写请求） |
| ③ | 向导推进 `persistStepData` | 每步 `confirm_step`/下一步提交一次 | **保留，且是唯一提交函数**（由 `goStep` 与 `startExport` 两处调用） |
| ④ | 宿主条件表回灌后的补写 | 回灌非空文本后由宿主/模型补一次 `set_condition` | **已改为模型解析成 `set_condition` 草案**；留空时后端**不再代写** `{}` |

**后端只认 `conditionJson`。** 导出作业、`start_export` 预检与条件三态（`SET` / `EXPLICIT_UNSET` / `UNDECIDED`）都只读任务 `conditionJson`。写入点一多，"对话里已设"与"库里真有"就会出现时序裂缝：工具调用成功但条件为空、旧任务候选覆盖新任务、同一条件被写两次、或用户还没走到下一步库里已经有半条数据。

**提示词把实现事实写成了行为规范。** 描述里"立即落库""先落库再 `confirm_step`""条件已知但未落库会被拒绝"让模型把可回滚的草案说成既成事实，回执与正文也随之失真。

**一个独立缺陷（同批修复）。** `ResilientChatService` 的失败/重试门把"快照 `SUSPENDED`"当成"挂起工具轮"，普通续跑遇到异常时被宽判据吞掉：静默交还、无 `error` 终帧、不写 `FAILED`、不重试。现在普通失败门只认**已持久化的挂起工具轮**（`SUSPENDED` + in-flight 非空）；单纯 `SUSPENDED` 只在 `correcting`（导出收尾纠正）判据里参与，且纠正轮不占重试预算、也不得进失败重试（否则在"纠正 + 重试"间无限打转）。

## 2 用户裁决（本批依据）

1. AI 对话内的条件候选**只存 Redis**（会话作用域，随会话过期），**允许**；不写业务条目。
2. **禁止**在创建任务或"设置条件"时提前写业务数据库：`create_task.defCodes/conditions` 只是候选。
3. `select_definitions` / `set_condition` **只形成前端草案**；业务数据库只在下一步或启动作业前由前端 `persistStepData` 提交。
4. **已知条件**由宿主通过前端 `set_condition` 形成草案，**不弹条件表**；**未知条件**才由宿主给一次非必填表单，**留空 = 明确不设**，在下一步提交 `{}`。
5. `confirm_step` 认可本轮**已结算**的结构化草案 / 留空决定；`start_export` 预检仍检查**最终业务库条件**。
6. `create_task` 的页面适用范围恢复为"任务中心、已有任务或已完成任务页面都适用"。

## 3 状态流（当前实现）

| 阶段 | 谁写 | 落在哪 | 回执/正文要求 |
|---|---|---|---|
| `create_task(defCodes, conditions)` | 后端候选 | 会话/快照候选（Redis `extra.createTaskConditions` + `createTaskTaskId` + `createTaskRequestedAtMs`），**不写**任务条目与 `conditionJson` | 明说"只是候选、未提交业务库" |
| `select_definitions` | 前端草案 | 向导勾选态 | 不称"已落任务项" |
| `set_condition`（模型或宿主下发） | 前端草案 + Redis 待决条目 | 草案层（`draftModels`/workspace + `pending`） | 不得称"已落库/已生效" |
| 未知条件表单 | 宿主发放一次 | 回灌值（Redis 待决条目） | 留空 = 明确不设（下一步提交 `{}`） |
| `confirm_step` | 前端 `persistStepData` | **业务库 `conditionJson`** | 认可已结算草案/留空决定 |
| `start_export` | 后端预检 | 只读业务库 `conditionJson` | 仍是唯一事实源 |

## 6 验收要求（主控在浏览器执行；本节列出的是**待执行**场景，不是已通过记录）

1. **A 已知条件**：任务中心说"导出 CURRENCY 里 code = CNY 的数据" → `create_task` 确认卡 → 向导 `SELECT_DEFS`（**不弹条件表**）→ 勾选 → 下一步 → `QUERY_COND` **不弹条件表**；`set_condition` 后业务库 `conditionJson` **仍为空/旧值**，再"下一步"后才出现该条件；`start_export` 预检放行并读到该条件。
2. **B 未知条件**：只说"导出一份配置" → `QUERY_COND` 由宿主弹**一次**非必填表 → 留空 → 下一步提交 `{}`，业务库为 `{}`；不重复弹表、不用文字追问。
3. **C 回灌非空文本**：表单填 `code = CNY` → 模型 `set_condition` → 只形成草案 → 下一步**只写一次**业务库；无第二次写入、无第二张表。
4. **D 提前关闭/刷新**：未到下一步就关闭或刷新 → 业务库**没有**提前写入；对话内候选按会话有效期失效，不出现半条业务数据。
5. 每场景留证：业务库条件字段读数、Redis 候选键、工具回执原文、是否弹表。
