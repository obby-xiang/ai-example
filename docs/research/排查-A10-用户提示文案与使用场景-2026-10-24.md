## 1. 总体结论

### 1.1 健康度判断

**文案面的"表"已经做好了，"口"没收住。** 一句话：*键表是 A 级的，出口是 C 级的。*

- **做对了的硬底子**：两份 locale 各 914 叶键、键集合与键序**逐键对称**、占位符**零漂移**、键名风格统一（167 个下划线键全部是工具 id / 错误码 / 枚举这类外部协议标识）；后端 90 条错误码在「枚举 / 前端镜像 / 中英 properties」**四方零差集**，契约测试双向断言，加码忘了补文案 CI 立红。这两层是同类项目里少见的自觉。
- **没做对的是"最后一公里"**：i18n 只落在"模板 + locale 表"，**模板之外的层（组件脚本、utils、api、store、后端调用点）大面积漏网**。结果是英文界面下不是"翻译腔"，而是**中英混排**——一个英文句子里嵌着中文整句、中文全角括号、中文机器码。
- **更值得警惕的是第二类**：真正到达用户眼前的**不是**那 90 条精心维护的兜底文案，而是**调用方原文**——上游 HTTP 报文、`getMessage()` 的异常串、配置键名 `app.ai.sheet.read-enabled`、Java 类名 `ContextBreakdownService`、机器码后缀 `_AFTER_TOOL_PARTIAL`。**文案治理的产能，几乎全部没有作用在最高频的失败路径上。**

- **判定**：这一族对话框专用于"取消作业/删除任务"这类终态操作，用户点了没反应会反复点或以为页面卡死。AI 侧同款确认卡是有提示的（`AiPanel.vue:560-565` 的 `gate-ack-hint`："请先勾选上方确认项"）——**两处口径不一致**。
- **建议**：未勾选时把「确定」置灰，或在对话框内常驻一行"请先勾选确认项"（与 AI 侧同文案）。

##### Y-63 定义页/数据页加载失败只剩一次性 toast，表格回落"暂无数据"，容易被读成"系统里没有数据"
- **来源**：S4-§2⑭｜**位置**：`frontend/src/views/DefinitionsView.vue:328-344`、`:72-74`；`frontend/src/views/DataBrowserView.vue:252-279`、`:118-120`

- **建议**：两页各补一个常驻错误条（复用 `views.*.msg.loadFailed`），与任务中心同形态。

##### Y-64 任务列表的"继续任务"入口是任务标题本身，且操作列只有取消/删除两个负向动作
- **来源**：S4-§2⑮｜**位置**：`frontend/src/views/TaskCenterView.vue:46-48`、`:88-101`
- **现象**：恢复向导（`restoreWizard`）绑在标题的 `el-button link` 上，没有任何"打开/继续"字样或图标；右侧操作列只有「取消」「删除」。

- **建议**：操作列补「打开/继续」按钮（或给标题加"继续编辑 →"提示）。

##### Y-65 历史加载失败静默：刷新后按"空会话/本地镜像"渲染，既无提示也无重试
- **来源**：S4-§2⑯｜**位置**：`frontend/src/stores/ai.ts:1457-1466`；面板 `frontend/src/components/AiPanel/AiPanel.vue:166-174`
- **现象**：`aiApi.history()` 抛错时只置 `historyLoaded = true` 后 return（注释写"后端不可达：保留镜像展示"），界面没有任何"历史可能不全"的痕迹。

#### 2.2.5 汇总级补充发现（非碎片结论，本轮按 S5 检查表新增）

##### Y-66 中文第二人称「你 / 您」在同屏混用
- **来源**：**汇总级补充**（S5 checklist 第 31 条驱动；S1–S4 均未报告，本轮独立扫描发现）
- **位置**：`frontend/src/locales/zh-CN.json`（`ai.panel.greeting`、`ai.panel.welcome1`、`ai.panel.confirmTitle`、`ai.uploadHandoff.pickFile`、`ai.uploadHandoff.acceptHint`、`ai.notice.uploadPickerCancelled`）
- **现象**：全文「你」4 处、「您」2 处，且**空态同屏混用**：
  - 用「您」：`ai.panel.greeting`「**您**好，我是实施助手」、`ai.panel.welcome1`「我可以帮**您**查询配置项与字段…」
  - 用「你」：`ai.panel.confirmTitle`「待**你**确认：{business}」、`ai.uploadHandoff.pickFile`「需要**你**在左侧选择一个文件」、`ai.notice.uploadPickerCancelled`「**你**取消了文件选择，可以重试」

- **建议**：全仓二选一（面向配置管理员建议用「你」，与英文 `you` 的平等语气档一致），并加一条 locale 级检查。

> **口径说明**：S5 的严重度表示该准则在业界共识中的**约束力与审计权重**，不是本仓缺陷等级：🔴 = 多数标准/大厂规范明确要求，可直接判不合规；🟡 = 强建议，允许有解释的例外；🔵 = 情境化做法或存在合理分歧。**S5 未扫描仓库任何文件**，其"本仓映射"段是基于调研结论的场景假设，本报告的"对应发现"列是本轮汇总时做的实际映射。

### 5.1 四条最硬的共识（可直接当判据）

#### ① 错误消息三段式：说清"发生了什么 / 为什么 / 怎么办"（🔴）
- **来源**：<https://www.eleken.co/blog-posts/error-message-ui>、<https://www.nngroup.com/articles/error-message-guidelines/>
- **结论**：业界把合格错误消息拆成三件事——确认出事了、指出具体是什么问题、给出下一步动作；缺任一项用户就停摆。NN/g 直接挂在 Nielsen 启发式第 9 条"帮助用户识别、诊断、恢复"上。
- **原文**：*"The most helpful error messages do three things at once. It confirms that something went wrong... It names what went wrong... It points to what to do next."*；*Bad: "Error 500" / Good: "We couldn't save your file. Check your connection and try again."*
- **→ 本仓对应**：R-08 / R-13 / Y-24 / Y-30 全部违反；Y-29 的"下载失败"类文案缺后两段。

#### ② 描述用户视角，而不是描述系统做了什么（🔴）
- **来源**：<https://www.eleken.co/blog-posts/error-message-ui>
- **结论**：*"The biggest mistake in error copy is describing the system. A message like 'Authentication failed due to invalid credentials' is accurate from the server's point of view, but to the person reading it, credentials is jargon and failed is a dead end."* 中文技术产品里"鉴权失败/令牌失效/参数校验不通过/请求异常"均属此类。
- **→ 本仓对应**：R-11 / R-12 / R-14 / R-16 / Y-11 / Y-43 / Y-44 是教科书级样本（连"Spring bean 类名""配置键名""base36 nonce"都进了用户文案）。

#### ③ 技术细节降级但可获取：错误码折叠、可复制的诊断信息（🔴）
- **来源**：<https://www.nngroup.com/articles/error-message-guidelines/>、<https://documentation.five9.com/bundle/admin-console/page/admin-console/intro/troubleshooting.htm>
- **结论**：*"Hide or minimize the use of obscure error codes or abbreviations; show them for technical diagnostic purposes only."* 通行解 = 面向用户的话在前，技术细节收进可展开区或"复制详情"；直接暴露 traceback / 异常类名 / 请求体即不合规。
- **→ 本仓对应**：R-09（`{code}` 在第一屏）与 R-14/R-15（原始 JSON 直接当正文/hover）违反；**正确样板在本仓已存在**——P-24/P-25（`args`/`traceId` additive、长度类错误只回数字）。

#### ④ 按钮与破坏性操作：动词+宾语、命名对象、说清后果、确认键用动词（🔴）
- **来源**：<https://vaadin.com/docs/latest/components/button>、<https://uiuxatlas.com/lessons/content-design/button-label-and-cta-copy-conventions/>、<https://uxpatternsguide.com/patterns/confirmation-dialog/>、<https://www.marmoui.com/docs/foundation/voice-and-tone>、<https://business-dev.autohisab.com/custom-app/development-docs>、<https://www.jianshu.com/p/39f8bdd10a33>
- **结论**：*"A label should describe the action, preferably using active verbs... such as 'Save Changes' instead of 'Save'"*；*"Name the resource in the title — 'Delete Q3 report?'... State what is lost and whether it is recoverable... Label the confirm button with the verb — 'Delete', not 'OK'."*；*"Avoid OK, Yes, No, and Cancel-only button pairs when they force users to reinterpret the question."*；中文规范同向："避免使用「Yes 是」或「No 否」"。**双面判据**：*"Do not confirm ordinary save, archive, dismiss, filter, navigation, or low-risk edits."* —— 过度确认同样是问题。
- **→ 本仓对应**：R-07（写死"确定/取消"）、Y-27（四套动词）、Y-35（标题用页面名）、Y-62（点确定无反应）；反向问题 = Y-53（**该确认的发布没有确认**）。

## 6. 统一最小修复面清单（S2 × S3 的"错误文案出口"合并）

> **为什么要合并**：S2 从"界面层"看错误文案（`ElMessage`、兜底常量），S3 从"后端层"看（码表、调用点原文）。两条线独立发现了同一件事——**错误文案的真正出口不是 locale，而是 5 个"透传点" + 3 个"硬编码兜底"**。把它们合成一张表，是因为修法完全相同：**先定"谁负责把人话写出来"，再改出口**。

> **设计原则（一张图）**：
> ```
> 后端调用点 ──(code + args)──► 前端/后端统一文案表 ──► 用户

> ```
