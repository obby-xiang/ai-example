- 一句话：**先把"已用多少 / 上限多少 / 花在哪"变成真值与契约，再按"清工具结果 → 按 Turn 滑窗 → 递归摘要"逐级压缩，并留 13K 预留缓冲与连续失败熔断**；压缩只改"喂给模型的那一份"，原文进归档可回溯。

## 1. 范围

**做**
- 计量口径落地：流式 usage **取最后一个非空帧 + 去重 + 单调校验**，缺失回退估算并标注 `≈`；
- 分母口径落地：展示分母 = **下一次请求的 `prompt_tokens`**（上限来自单一取数点 `ContextLimitResolver`）；
- 展示：**百分比 + 已用/上限 + 类目拆分**（六项，含 tools 与 free），轮末更新、流式中不跳动；
- 压缩谱系三级逐级触发：**L1 工具结果清除 → L2 按 Turn 滑窗 / 递归摘要 → L3 硬截断兜底**，触发点留 `reserve=13000` 缓冲、加滞回、连续失败熔断；
- 压缩可见 + 可回溯：压缩事件进 `context` 帧 + 日志 + 台账，原文进 `ai:ctx:archive:` 归档；
- 度量自身的观测面：`ai:ctx:<sessionId>`（真值）+ `ai:ctx:ledger:`（事件）+ 端点。

**不做**
- 不接厂商服务端压缩（Anthropic compaction beta / OpenAI Responses `compact_threshold`）——本仓模型路径是 OpenAI 兼容 chat/completions，无该通道；
- 不做语义压缩（LLMLingua 族），不做向量检索记忆；
- 不改 24h 滑动 TTL 与 `app.ai.session-ttl` 语义；
- 不把「剩余可轮次」做主指标（业界无人做，不可预测）；
- 不做用户手动 `/compact`、用户级"钉住消息"（当前仓内无该能力，见 §7 D5 候选）；
- 不改 HITL 确认门/表单的等待语义（去超时裁决保持不变）。

## 3. 核心设计

### 3.1 计量：`ContextMeter`（取最后一帧去重）

新类 `ai/context/ContextMeter.java`（纯函数 + 小状态，单测友好），替换 `Accumulator.usage()` 的直读逻辑：

| 规则 | 内容 |
|---|---|
| R1 采集 | 每个 `ChatResponse` 取 `(prompt, completion, total)` + `UsageDetails.enrich` 的可选维度；`total<=0 && prompt<=0 && completion<=0` 记为**空帧**，不参与 |
| R2 去重 | 与"上一条已采纳"三维全等的 candidate 只计一次（治"每 chunk 重复 usage"） |
| R3 取最后 | 采纳**最后一个非空** candidate 作为本轮真值（治"末帧 0/0/0"） |
| R4 单调 | 若新 candidate 的 `promptTokens` 小于已采纳值 ⇒ 判脏帧、保留已采纳值、`dirty++`（不回退、不抛错） |
| R5 回退 | 全轮无有效 candidate ⇒ `est=true`，走 `ContextEstimator` 估算，UI 标 `≈` |
| R6 作用域 | 每次 attempt 新建 Accumulator ⇒ 重试天然不串值；跨 attempt 取"最后一次**成功**尝试"的值 |

输出契约（`done.usage` 增量键，既有三维不动）：`est`(bool) · `source`(`stream`/`estimate`) · `frames`(采集帧数) · `dirty`(污染帧数) · `promptTokens/completionTokens/totalTokens`（既有）· `cachedTokens/reasoningTokens`（既有可选）。

**估算器** `ContextEstimator`：`estimate(text) = ceil(cjkChars / 1.7 + otherChars / 4.0)`（调研给的"中文按字符/1.6~1.8 兜底"取中值），仅用于兜底与分项拆分，不替代真值。

### 3.2 分母与触发：`ContextLimitResolver` + 预估式

**上限（分母）单点取数**：`ContextLimitResolver.resolve(model) → limitTokens`
1. 模型配置专项的 DB 值（`ai_model.max_context`）——未落地时跳过；
2. `app.ai.context.limit-tokens`（本专项过渡键）；
3. `0`/未知 ⇒ **降级态**：端点 `limitTokens:null`，前端只显示已用不显示百分比，压缩只走"绝对阈值兜底"（L1 的 keepPairs + L3 的 keepTurns）。

**已用量与预估值分开**（这是本设计的核心口径，避免"展示用预测值"的漂移）：

```
usedNow   = 最后一次成功请求的 usage.promptTokens        // 展示用（真值，压缩后先置 est 再等下一次真值回填）
nextEst   = usedNow + lastCompletionTokens                // 触发用（"下一次请求的 prompt"预测）
            + estimate(本轮新输入)
            + Σ(该次请求之后新增的工具结果估算)
ratio     = nextEst / (limitTokens − reserveTokens)       // reserve=13000，先扣缓冲再取比
```

- 阈值（对 `limit − reserve` 取比，等价于"有效窗口 − 13K 后按比例"）：L1 ≥70%、L2 ≥80%、L3 ≥95%；
- 每次最多升一级（避免一次跳到 L2 把前缀全改写、缓存整段重建）；
- 滞回：压缩完成后 `usedNow/limit < 60%` 才解锁下一次触发；
- **压缩后重置基线**（调研 Q3 的"计量与现实不一致"）：压缩成功即把 `usedNow` 置为"压缩后规模估算"并标 `est=true`，下一次请求回填真值。
- 取值自洽性检查（写进注释、进 NUMSPEC 依据列）：128K 下 `limit−reserve=115K`，L3@95% 剩 `0.05×115K=5.75K > max-tokens 4096` ⇒ 触发线不会把输出空间吃掉。

### 3.3 类目拆分 taxonomy（六项，两级）

| key | 内容 | 来源 |
|---|---|---|
| `system` | 人设 + 工作区快照（`SYSTEM_PROMPT` + `ContextBuilder.buildContextMessage`） | 组装点 1 的 SystemMessage |
| `tools` | 本轮披露的工具 schema（`toolRegistry.forContext(context)` 的 `ToolDefinition` JSON） | 披露时的定义集 |
| `history` | 历史 user/assistant 正文（不含 tool 消息） | memory / 重建 history |
| `toolResults` | `role:tool` 的 `responseData`（含已清理占位符） | `ToolResponseMessage` |
| `summary` | 压缩摘要消息（**单独成项**，不并入 history） | metadata `compacted=true` 的消息 |
| `input` | 本轮用户输入 | 最后一条 `UserMessage` |
| `free` | `limit − used`（可为负 ⇒ "已超"） | 派生 |

**守恒规则**（`ContextBreakdown.normalizeTo(used)`，纯函数）：
`v_i` 为各分项估算；`S=Σv_i`；`scaled_i = floor(v_i × used / S)`；差额 `used − Σscaled_i` 补给 `argmax(v_i)` ⇒ **恒有 `Σ分项 == used`**。`used` 取真值（usage）时同样走比例归一，于是"拆分是估算、总量是账单"这一事实不产生加总矛盾。

### 3.5 压缩三级

统一入口 `ai/context/ContextCompactor.java`，**请求前同步执行**（D2 建议 A），两个调用点必须同源（否则首轮/续跑口径分叉）：

- 首轮：`ResilientChatService.chat` 在 `memory = chatMemory.get(sessionId)` 之后、构造 `instructions` 之前；
- 续跑：`ResumeService.resume` 在从快照重建 history 之后（`ResumeService.java:455` 附近）。

**pin（保留集）规则** —— "压缩不丢关键信息"的可执行定义：

| # | 规则 |
|---|---|
| P1 | 系统消息**永不参与**压缩（system 每轮由请求侧重建，本就不在历史里） |
| P2 | 本轮输入（最后一条 `UserMessage`）永不动 |
| P3 | 全部**未决 HITL 条目所在 Turn** 永不动，且该 Turn 的 `assistant(tool_calls)` 与 `tool` 必须成对完整保留（`pendings` 中 `PENDING`/`APPROVED && !executed` 反查 toolCallId） |
| P4 | 最近 `keep-recent-turns=6` 轮逐字保留 |
| P5 | 最近 `keep-tool-pairs=5` 对工具结果不清理 |
| P6 | 摘要必须原文携带六项：用户目标 / 已确认的工作区与页面操作 / 已执行且不可回滚的动作与资源 ID（taskId、jobId、defCode、文件名）/ 未解决报错与下一步 / **当前待审批项清单（toolCallId + 名称 + 参数摘要）** / 已完成勿重做清单 |
| P7 | 挂起期间（`snapshot.status == SUSPENDED` 且有外部未决项）**只允许 L1**，禁用 L2/L3 |

**L1 工具结果清除**（最轻、ROI 最高）
- 判据：`ratio ≥ 70%`；
- 动作：把最旧的、非 pin 的 `ToolResponseMessage` 的 `responseData` 换成 `[tool_result 已清理: <name> · ≈<n> tokens · 原文见台账 ai:ledger:<runId>]`；
- **不删消息、不改 id、不动 `assistant(tool_calls)`**（保留配对骨架，从构造上消除孤儿对）；
- 原文不丢：台账 `ai:ledger:<runId>` 本就是全文（`RunStore.appendLedger`），占位符给出回取路径。

**L2 按 Turn 滑窗 + 递归摘要**
- 判据：L1 后 `ratio ≥ 80%`；
- Turn 切分：一条 `UserMessage` 起、到下一条 `UserMessage` 止（与 Spring AI `TurnWindow` 口径一致），**裁剪单位 = Turn**；
- 递归摘要：取最旧非 pin 段，按 `chunk-tokens=8000` 分块 → 逐块摘要 → 递归合并，直到被摘要段落到目标预算；
- 产物：合成 `UserMessage`（metadata：`compacted=true`、`compactedFrom=<n turns>`、`lostTokens=<n>`、`atMs`）+ `AssistantMessage`（摘要正文）置于窗口最前；前端据此渲染提示条；
- 摘要模型：`app.ai.context.summary-model` 空 = 主模型（D3）。

**L3 硬截断兜底**
- 判据：L2 后 `ratio ≥ 95%` 或 L2 失败/超时；
- 动作：按 Turn 丢最旧（`trimKeepingToolPairs` 的 Turn 化版本），pin 集不动；最多丢到 pin 集下限，**丢完仍超就照发请求并让上游如实报错**（映射为 `CONTEXT_OVERFLOW`），绝不静默截断；
- `level=L3` 必须同时出现在 `context` 帧与提示条。

**原子性与失败口径**（对齐调研 Q3 的"绝不静默截断"）
1. 先写归档 `ai:ctx:archive:<sessionId>:<turnNo>` = 压缩前全量 `messageJson`（TTL 同会话）；
2. 再 `RunStore.save(snapshot)`（唯一写口、fenced）；
3. 最后 `chatMemory.clear + add`（沿用 `convergeMemory` 通道）。
任一步失败 ⇒ 记 ERROR + 熔断计数 +1 + **保持原状继续本轮请求**（本轮可能偏大，但不失真）。

**熔断**（`ai/context/CompactionFuse.java`，状态在 `ai:ctx:<sessionId>` 的 `fails/circuit/openUntilMs`）
- 只被"压缩尝试"驱动：L2/L3 失败（摘要请求异常 / 超时 / 产物不可用）⇒ `fails++`；任一成功 ⇒ `fails=0`；
- `fails >= 3` ⇒ `circuit=open`、`openUntilMs = now + 10min`，期间跳过 L2/L3、**只保留 L1**（可用性优先），并在 `done.context.circuit` 暴露；
- 到点**半开**：放一次 L2，成功清零，失败重新计数再开 10 分钟（不升指数，避免长尾锁死）；
- 熔断/恢复各写一行 WARN/INFO 日志 + 台账事件。

## 8. 风险与边界

- **估算偏差**：`ratio` 用估算触发，`≈` 标注只在回退时出现；若网关长期不发 usage，压缩会在估算基础上提前触发（可接受，L1 可逆且原文在台账）。
- **缓存打穿**：每次压缩都会改写前缀、必然 cache miss（调研 Q3）。故"每次最多升一级 + 滞回 60% + 不做每轮小裁剪"是硬约束，任何"每轮清一点"的实现都视为打红。
- **首轮无租约**：`chat()` 路径压缩写快照时 `heldRunEpoch == 0`，走 `RunStore.save` 的 E3 plain SET 分支（会有 `warnIfFenceIsAhead` 旁路观测）。同 session 并发两轮本身已被前端会话锁 + 会话锁参数约束，本专项不新增互斥；登记为边界。
- **快照与记忆双写**：压缩后的历史必须同时进 `ai:run:` 快照与 `chat:mem:`，否则续跑与下一轮的"模型看到的"分叉（SM-01 同族）。原子三步是本条的落地保证。
- **帧类型集扩张**：15→16 会让旧客户端遇到未知帧——`stores/ai.ts` 的 `default` 分支已静默忽略未知帧，前向兼容成立；但 conformance 白名单必须同批改，否则契约用例红。
- **归档体积**：`ai:ctx:archive:` 只在真压缩时写、TTL 同会话，最坏情况 = 会话内压缩次数 × 单轮历史体积；Redis 内存前提 `noeviction`（B23L1 已登记）。
- **`max-tokens` 与分母的自洽**：L3@95% 必须仍留得下 `max-tokens 4096`（128K 下剩 5.75K），换更小窗口模型时须重算——写进配置注释与 NUMSPEC 依据列。
