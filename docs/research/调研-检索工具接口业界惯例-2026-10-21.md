## 一、结论先行

### 1.1 对草稿四工具的裁决

| 草稿工具 | 裁决 | 核心理由 | 必改点 |
|---|---|---|---|
| `kb_search(query, topK?)` | 保留 | 与 OpenAI `file_search`、Anthropic `web_search`、MCP 各检索 server 的主流形态一致：一个自然语言 query 入参 | `topK` 改为可选 `top_k`，默认 5、上限 10；不向模型暴露原始 BM25 分数；返回增加 `doc_id/title/section/updated_at` 与明确的状态位 |
| `kb_read_doc(doc_id, section?)` | 保留，但必须收窄 | 业界普遍是 search/read 分离（MCP filesystem、memory，Claude Code 的 WebSearch/WebFetch）；但整篇读取会瞬间打爆上下文 | `section` 建议必填或「缺省时先返回目录 + 前 1200 字」；增加 `max_chars`/`offset`，默认 4000 字、上限 8000 字；`doc_id` 用可读 slug 而非 UUID |
| `kb_list_topics()` | 删（作为模型工具） | Anthropic 明确建议「用 `search_contacts` 而不是 `list_contacts`」；list 类工具会被模型当成「先浏览再搜」的捷径，浪费上下文 | 目录改为启动时注入 system prompt 的静态附录（主题 → 文档标题，控制在 2–4k token）；若业务确需「知识库有什么」的问答，再保留一个只返回主题级（≤30 行）的 `kb_outline` |
| `kb_lookup_policy(口径词)` | 改（条件保留） | 与 search 功能重叠是工具混淆的最大来源；只有在「术语表由业务维护、需要精确匹配与稳定答案」时才值得独立 | 改名 `kb_lookup_term`；只做精确/规范化匹配，未命中返回 `found=false` + `next="use kb_search"`；返回 `source_doc/section/updated_at`；禁止模糊兜底静默返回近义词 |

最终建议暴露给模型的工具数：**3 个**（`kb_search`、`kb_read_doc`、`kb_lookup_term`）。若术语表很小或更新不频繁，进一步合并为 **2 个**（把术语表作为文档纳入 BM25 索引），这是最稳的形态。

### 1.2 一句话定稿

**一个「返回带定位信息片段」的 search，加一个「按章节读取、带硬截断」的 read；分数只留给后端做阈值和 UI，不给模型看；空结果返回结构化的 `no_match` 文本而不是异常；system prompt 用「必须先检索 + 未命中必须说不知道 + 句末标注 `[doc_id §章节]`」三句话兜底。**

## 二、逐项调研

### 1. OpenAI file_search（hosted tool）

**接口形态**：`file_search` 是 Responses API 的托管工具。开发者侧配置 `vector_store_ids`、`max_num_results`、`filters`（metadata 过滤）、`ranking_options`（ranker、`score_threshold`、hybrid 权重）。模型侧不填这些参数，只产生一个 `file_search_call`，其中 `queries` 是数组，说明模型可在一次调用里发多条查询；`search_results` 默认 `null`，要拿详细结果需在请求里加 `include=["file_search_call.results"]`。

**模型看到什么**：检索出的 chunk 文本 + 最终回答上的 `file_citation` 注解；注解字段为 `{type:"file_citation", index, file_id, filename}`，`index` 是回答文本里的字符偏移。**分数不进入模型可见上下文**，只在开发者用 `include` 拉取时可见。旧 Assistants API 会在正文里插入 `【4:10†foo】` 这类内联标记，客户端再替换成角标；Responses API 不再暴露该标记，只给结构化 annotation。

**默认值（很值得抄）**：`file_search` 工具默认最多 **20 个 chunk**（gpt-4*/o 系列），并受 **16,000 token** 检索预算约束，可能少于 `max_num_results`；`score_threshold` 默认 0；底层 vector store search API 默认返回 **10 条、最多 50 条**。

**多轮里如何「先搜」**：托管工具没有强制的「先搜」语义，靠三件事——工具描述、`instructions`（官方示例就是「Use your knowledge base to answer questions about audited financial statements.」）、以及需要时用 `tool_choice` 强制。模型每轮自行决定是否再搜。

出处：
- https://platform.openai.com/docs/guides/tools-file-search
- https://platform.openai.com/docs/guides/retrieval
- https://platform.openai.com/docs/assistants/tools/file-search
- 内联标记 `【4:10†foo】` 的说明与 Responses API 差异：https://developer.mamezou-tech.com/en/blogs/2025/03/19/openai-responses-api-filesearch/
- annotation 字段（`file_id/filename/index`）：https://github.com/vercel/ai/issues/8079

**对我们的启示**：托管工具把「检索参数」留给开发者、把「查什么」留给模型，这个分工是对的。`top_k` 不该是模型每次都思考的东西；默认值和硬上限由后端定。

### 2. Anthropic

#### 2.1 Tool use 官方工具设计指南

- 工具描述是性能第一因素，建议每个工具 **3–4 句以上**：做什么、何时用、何时不要用、每个参数的含义、有什么不返回/限制。
- 参数名要无歧义：用 `user_id` 而不是 `user`。
- 错误返回用 `tool_result` + `is_error: true`，错误文本要具体可行动（例如「Error: Missing required 'location' parameter」），不要只给错误码或堆栈；模型通常会自行重试 **2–3 次**。
- 空 `tool_result` 是合法的；也可返回一段纯文本说明结果为空。
- `tool_choice` 支持 `auto/any/tool/none`；`any`/`tool` 会预填 assistant 消息，模型不会先说话再调工具；extended thinking 下不支持强制。
- 并行工具调用：独立操作鼓励并行；系统提示可用 `<use_parallel_tool_calls>` 段强化。

出处：https://docs.claude.com/en/docs/agents-and-tools/tool-use/implement-tool-use

#### 2.2 工具该给一个 search，还是 search + read

Anthropic 没有统一的「RAG 必须两个工具」规定，但官方示例与产品形态都指向 **search 返回「可引用的结果块」，read 是可选补充**：

- 官方 RAG 示例只定义一个 `search_knowledge_base(query)`，返回若干 `search_result` 块；每块自带 `source/title/content`，Claude 直接引用。
- 内置 `web_search` 是单工具，返回 `url/title/page_age` + 加密正文，搜索与取正文合并在一个工具里。
- Claude Code 则把 `WebSearch` 与 `WebFetch` 分开，这是「搜索 + 按 URL 读取」的典型分离。

结论：**一个 search 就能跑通；「read 全文/按章节读」只在 snippet 不足以回答、或文档很长时才需要，且必须作为第二个工具单独暴露。** 不要把 read 合并进 search 的返回（一次返回整篇会打爆上下文）。

出处：
- https://www.anthropic.com/engineering/writing-tools-for-agents
- https://platform.claude.com/docs/en/build-with-claude/search-results
- https://docs.claude.com/en/docs/agents-and-tools/tool-use/web-search-tool
- Contextual Retrieval（BM25 + embedding 混合、chunk 上下文前置，不改变工具形态）：https://www.anthropic.com/news/contextual-retrieval

#### 2.3 Citation 特性与官方推荐做法

- 普通文档：`document` block + `citations.enabled=true`；纯文本按句切分，引用给字符区间；PDF 给页码；`custom content` 按你提供的 block 切分，最适合 RAG chunk。
- RAG 工具：返回 `search_result` block，字段 `source`（可用 `kb://article-1234` 这类内部标识）、`title`、`content`（text block 数组）、`citations.enabled`。引用回传 `search_result_location`，含 `cited_text`、`source`、`title`、`search_result_index`、`start_block_index/end_block_index`。
- **切得越细，引用边界越细**：想把引用精确到「条款级」，就把每个条款放进独立 text block。
- **空结果官方写法**：搜索失败或无结果时返回一个普通 text block 说明结果（例如 `"No results found."`），不要抛错；这样 Claude 会向用户解释空结果，对话继续。
- 引用默认关闭，必须显式 `citations.enabled=true`；`cited_text` 不计输出 token。

出处：
- https://docs.anthropic.com/en/docs/build-with-claude/citations
- https://platform.claude.com/docs/en/build-with-claude/search-results

**对我们的启示**：不用 Anthropic 原生 citation 也能抄它「块级可引用」的思想——每条检索结果必须有稳定的 `source/doc_id` 和 `title`，正文按章节切块，而不是把 5 条结果拼成一大段。

### 3. MCP 生态检索类 server 的工具划分

| Server | search | read | list | 关键约定 |
|---|---|---|---|---|
| `server-filesystem` | `search_files(path, pattern, excludePatterns)`，只返回匹配的**完整路径** | `read_text_file(path, head?, tail?)`、`read_multiple_files(paths[])` | `list_directory`、`directory_tree`、`list_allowed_directories` | search 不返回内容，read 才返回内容；read 用 `head/tail` 限行；`directory_tree` 返回 JSON 树 |
| `server-memory` | `search_nodes(query)`，跨实体名/类型/观测内容搜 | `open_nodes(names[])` 按名取指定节点及其关系 | `read_graph()` 全图 | 典型 search / get-by-id / list-all 三件套；不存在的节点静默跳过 |
| `brave-search-mcp-server` | 按垂直域拆：`brave_web_search`、`brave_news_search`、`brave_video_search`、`brave_image_search`、`brave_place_search`、`brave_llm_context` | 无独立 read（`brave_llm_context` 直接返回正文） | 无 | `query` 必填（≤400 字符/50 词）；`count` 1–20 默认 10；`offset` 最大 9；`freshness` 过滤；`extra_snippets` 可选 |

**参数命名**：工具名统一 snake_case（`read_text_file`、`search_nodes`、`brave_web_search`）；参数在 TS server 里多为 camelCase（`excludePatterns`、`sortBy`），这是实现语言习惯，不是协议要求。对我们（Java 后端）建议统一 snake_case，避免模型在 `topK`/`top_k` 之间摇摆。

**分页/截断**：
- MCP 协议层对 `tools/list`、`resources/list` 等使用**不透明 cursor**：响应带 `nextCursor`，客户端不得假设页大小、不得解析 cursor、不得跨会话持久化。
- 检索类工具本身多用 `count + offset`（Brave：count 上限 20、offset 上限 9）或 `head/tail`（filesystem）。共同点是**服务端定硬上限，模型只能在小范围内调**。

出处：
- https://github.com/modelcontextprotocol/servers/blob/main/src/filesystem/README.md
- https://github.com/modelcontextprotocol/servers/blob/main/src/memory/README.md
- https://github.com/brave/brave-search-mcp-server/blob/main/README.md
- https://modelcontextprotocol.io/specification/2025-06-18/server/utilities/pagination

**对我们的启示**：search 只回片段和定位，read 才回正文；read 必须有行/字符上限；分页用 `offset` 而不是页码；上限写死在服务端。

### 4. LangChain / LlamaIndex 的 retriever tool 契约

**LangChain `create_retriever_tool`**。入参 schema 只有一个字段：

```python
class RetrieverInput(BaseModel):
    query: str = Field(description="query to look up in retriever")
```

工具名和描述由调用方提供；返回是 `document_separator`（默认 `"\n\n"`）拼接的文档文本，默认模板只有 `{page_content}`，**不带 metadata**；需要保留原始 Document 时用 `response_format="content_and_artifact"`。即默认契约是「单 query 入、纯文本拼接出」，要标题/来源/分数得自己定制 `document_prompt`。

**LlamaIndex `QueryEngineTool`**。入参是单个 `input` 字符串；默认描述是「Useful for running a natural language query against a knowledge base and get back a natural language response.」；返回 `str(response)`，即 **query engine 已合成过的自然语言答案，不是 chunk**。这对引用不友好：来源信息在合成阶段就丢了。做知识问答应优先用 retriever 级工具或自定义 `ToolOutput`，而非默认 QueryEngineTool。

**Agentic RAG 教程里 search 与 read 是否合并**：LangChain 官方 Agentic RAG 示例只给一个 `fetch_url` 工具，system prompt 要求「引用相关片段」；文档明确说 agent 只需要「一个或多个能取外部知识的工具」。另一个 Deep Agents 教程则把检索到的 chunk 卸载到文件系统，再由子 agent 读取——这是「search 返回片段、需要时再 read」的另一种实现。

**工具描述模板（可直接借用）**：名称 = 动词_对象（`fetch_documentation`、`search_knowledge_base`）；描述 = 一句话说明取什么 + 返回值形态 + 何时必须用 + 禁止什么（例如只允许特定域名）；system prompt 里再补「不确定就必须查」的硬约束。

出处：
- https://github.com/langchain-ai/langchain/blob/master/libs/core/langchain_core/tools/retriever.py
- https://github.com/run-llama/llama_index/blob/main/llama-index-core/llama_index/core/tools/query_engine.py
- https://docs.langchain.com/oss/python/langchain/retrieval

### 5. Amazon Bedrock KB / Azure AI Search 的 retrieve API

**Bedrock `Retrieve`**：
- 请求：`retrievalQuery.text`；`vectorSearchConfiguration.numberOfResults`；`rerankingConfiguration`（`bedrockRerankingConfiguration.numberOfRerankedResults`、rerank 模型 ARN）；`filter`；`nextToken` 分页；支持 `userContext.userId` 做文档级权限过滤。
- 响应：`retrievalResults[]`，每条含 `content.text`（或 row/audio/video）、`documentId`、`location`（s3/sharepoint/confluence/web 等 URI）、`metadata`（任意 JSON）、`score`；`nextToken`。
- **重排是请求侧配置，分数回传给调用方**；模型是否看到分数由调用方决定。

出处：https://docs.aws.amazon.com/bedrock/latest/APIReference/API_agent-runtime_Retrieve.html

**Azure AI Search `retrieve`（2025-11-01-preview）**：
- 请求：`messages`（对话式输入）、`outputMode`（`answerSynthesis` 或 `extractiveData`）、`maxOutputSize`、`maxRuntimeInSeconds`、`retrievalReasoningEffort`（minimal/low/medium）、`knowledgeSourceParams[].rerankerThreshold`、`includeReferences`、`includeReferenceSourceData`。
- 响应：`response[].content[].text`（合成答案或抽取片段）、`references[]`（`type/id/sourceData/rerankerScore/docKey`）、`activity[]`（查询规划、每次检索的 query/filter/耗时、答案合成的 token 数）。
- **重排阈值是服务端参数**；`rerankerScore` 语义是 **0–4**（4 最相关），和 BM25 的 `@search.score` 不是一个尺度，不能混用。

出处：
- https://learn.microsoft.com/en-us/rest/api/searchservice/knowledge-retrieval/retrieve?view=rest-searchservice-2025-11-01-preview
- https://learn.microsoft.com/en-us/azure/search/semantic-answers

**对我们的启示**：
1. 检索参数（topN、阈值、重排）属于「调用方/后端配置」，不属于模型每次调用要填的参数。
2. 返回给调用方的结构里保留 score 和 locator；给模型的那一层只保留排序、片段、来源。
3. 如果以后加权限过滤，参考 Bedrock 的 `userContext`：权限在检索层做，不靠 prompt。

### 6. 工具数量之争：单 search vs search/read/list vs 按域分

**权威论述**：
- Anthropic《Writing effective tools for agents》：「More tools don't always lead to better outcomes」「Too many tools or overlapping tools can also distract agents from pursuing efficient strategies」；并给出合并示例——不要 `list_users` + `list_events` + `create_event`，而要一个 `schedule_event`；不要 `read_logs`，而要只返回相关行及上下文的 `search_logs`。
- Anthropic《Tool search tool》文档给出量化：工具超过 **30–50 个**后选择准确率开始下降；**5 个 MCP server 的工具定义可占约 55k token**。其解法是延迟加载 + 按需搜索工具，而不是继续加工具。
- 学术侧：RAG-MCP 在 MCP 压力测试中，把工具描述先检索再注入，prompt token 减少 **50% 以上**，工具选择准确率从 **13.62% 提升到 43.13%**。这说明「工具太多」本身就是准确率问题。

**主流形态**：

| 形态 | 代表 | 适用 |
|---|---|---|
| 单 search 工具 | OpenAI `file_search`、Anthropic `web_search` | 语料同质、回答只需片段 |
| search + read | MCP filesystem、memory、Claude Code WebSearch/WebFetch | 文档长、需要精确到章节、需要引用 |
| 按域分工具 | Brave（web/news/video/image/place）、Anthropic 建议的 `asana_projects_search`/`asana_users_search` 命名空间 | 域之间词汇和权限差异大，用户会明确说「查合同/查产品」 |
| list 单独成工具 | MCP filesystem `list_directory`、memory `read_graph` | 浏览文件系统/全图是真实高频需求；知识库问答里通常不是 |

**结论**：几十到几百篇同质业务文档，**2–3 个工具是甜点区**；不要按文档类型拆 5 个 search；不要给 list 工具；只有当「制度/产品/合同」等域的检索字段、权限、排序策略确实不同，才按域拆，并用统一前缀命名空间。

出处：
- https://www.anthropic.com/engineering/writing-tools-for-agents
- https://docs.claude.com/en/docs/agents-and-tools/tool-use/tool-search-tool
- https://arxiv.org/abs/2505.03275

### 7. 返回格式：纯文本 vs 结构化；字段；分数；空结果

**纯文本拼接 vs 结构化**：
- LangChain 默认纯文本拼接，最简单，但来源/定位信息容易丢。
- Anthropic 明确说 XML/JSON/Markdown 没有一刀切答案，取决于模型与任务，要用 eval 选；其自身 RAG 用结构化 `search_result` block（source/title/content）。
- OpenAI 官方「合成回答」示例把结果格式化成 `<result file_id="..." file_name="..."><content>...</content></result>` 再交给模型。
- 结论：**结构化的「轻量信封」优于裸拼接**；但不必上完整 JSON（转义、token 开销、模型可读性都更差）。推荐「每条结果一行头部 + 片段正文」的混合格式。

**每条结果带什么**：必备 `doc_id`（稳定、可读）、`title`、`section`（标题路径）、`snippet`、`updated_at`；可选 `rank`、`match`（high/medium/low）、`locator`（行号/字符区间）、`truncated`。**不要带** UUID、MIME、内部 URL、索引分片号、调试字段——Anthropic 明确说低层技术标识符会降低检索精度、增加幻觉，建议把 UUID 解析成自然语言名或 0 基序号。

**score 给不给模型看**：
- OpenAI `file_search`：模型侧看不到 score；开发者用 `include` 才能拿到；阈值 `score_threshold` 是开发者参数。
- Anthropic `web_search`：结果只有 `url/title/page_age`，没有 score。
- Bedrock/Azure：score 回传给调用方，但是否进模型上下文由调用方决定；Azure 还专门用 `rerankerThreshold` 在服务端先筛。
- BM25 原始分**不可跨查询比较**（受查询长度、词频、集合统计影响），把它当「置信度」给模型看会误导。
- 结论：**原始分不进模型上下文**。需要让模型区分强弱时，用服务端算好的 `match: high|medium|low`，或干脆用「是否低于阈值」决定返回 0 条 / 2 条 / 5 条。

**空结果 / 低质**：
- Anthropic 官方：无结果时返回普通文本 `"No results found."`，不要抛错；工具失败时返回可行动的错误说明。
- Perplexity 的系统提示写「若搜索结果为空或无用，用已有知识尽量回答」——这对开放域搜索合理，但**企业制度问答不能照抄**，必须改成「明确说未找到，不得编造」。
- 建议三态：`no_match`（0 条）、`low_confidence`（有结果但低于阈值，最多 2 条并标注）、`error`（服务异常）。三者都要给模型一句「下一步怎么做」的提示。

**截断**：Anthropic 对 Claude Code 的工具响应默认限制 **25,000 token**；OpenAI 检索预算 **16,000 token**。我们的 read 工具按字符截断更直观：默认 **4,000 字**，上限 **8,000 字**，返回 `truncated=true` 和 `next_offset`；截断时在正文末尾加一句「已截断，可用 offset=... 继续读取」。

### 8. 系统提示词配套：先查再答与引用格式

**「必须先查」的写法**，公开可参考三类：

1. LangChain Agentic RAG 示例：`If a user asks a question you're unsure about—or one that likely involves API usage, behavior, or configuration—you MUST use the fetch_documentation tool...`；并明确「取数失败要告诉用户，再用你的专业理解继续」。
2. Perplexity 逆向提示：引用必须紧跟句子；`[index]` 对应搜索结果序号；每句最多 3 个来源；不设参考文献列表；搜索为空时允许用已有知识（开放域）。
3. Anthropic `search_result`：引用由 API 自动附着到 text block，不需要在 prompt 里教格式；但需要显式 `citations.enabled=true`。

**引用格式惯例**：

- 数字角标 `[1]`：适合 UI 有来源列表、由前端映射；Perplexity 是典型。
- 脚注/文档名：适合长文报告。
- `[doc_id §章节]` 内联：**最适合企业内部知识库**——稳定、可点击、模型不易编造；缺点是比较长，需要 prompt 明确「只写 doc_id 和章节，不要写标题全文」。
- OpenAI 的做法是「正文不带标记，annotation 单独给字符偏移」；如果前端能消费结构化引用，这是最干净的方案；否则用内联 `[doc_id §章节]`。

**建议的 system prompt 骨架（可直接落地）**：

```text
你是企业内部知识助手，只回答与公司制度、流程、产品、业务口径相关的问题。

检索义务：
1. 回答任何涉及上述内容的问题前，必须先调用 kb_search。不得凭模型记忆、常识或训练数据回答。
2. 首次检索用用户原词；若结果不足，换 2-3 个同义词/缩写/全称并行检索。
3. 若 snippet 不足以回答，调用 kb_read_doc 读取对应章节；不要凭 snippet 推测上下文或条款编号。

引用：
4. 每个结论句末标注来源，格式 [doc_id §章节]，多个来源并列：[hr/leave-policy §3.2][hr/attendance §2.1]。
5. 只引用你实际检索或读取到的内容；不得引用未返回的文档，不得编造章节号。

无结果与冲突：
6. 若 kb_search 返回 status=no_match 或 low_confidence，明确回答“知识库中未找到相关规定”，列出已检索的关键词，并建议联系对应负责人或提交工单；不得编造条款、数字、日期、审批层级。
7. 多篇文档冲突时，以 updated_at 较新、层级更高的文档为准，并在回答中说明存在冲突。

风格：
8. 不向用户展示工具名、原始相关度分数、检索调试信息。
9. 不确定时先问澄清问题，不要猜。
```

**是否强制第一次工具调用**：可用 `tool_choice` 在首轮强制 `kb_search`（Anthropic 支持 `{type:"tool", name:"kb_search"}`，OpenAI 支持 `tool_choice` 指定函数），但**不要每轮强制**；后续轮次应允许模型直接回答追问。Anthropic 也提醒 `tool_choice: any/tool` 会预填 assistant 消息，模型不会先说「我来查一下」。

**并行检索**：鼓励模型在一次回复里发多个 `kb_search`（同义词、缩写展开），而不是串行试错；Anthropic 有专门的 `<use_parallel_tool_calls>` 提示模板可借用。

- https://github.com/jujumilk3/leaked-system-prompts/blob/main/perplexity.ai_20250112.md
- https://platform.claude.com/docs/en/build-with-claude/search-results

### 9. FAQ / 预制答案通道与 search 并存

**风险**：两个工具都能「回答业务问题」，模型会混用——开放性问题走 lookup 拿到一个近义词的预制答案；或精确术语问题走 search 拿到一堆无关片段。Anthropic 把这类问题归为「overlapping tools / vague purpose」，会直接降低工具选择准确率。

**降低混用的做法**：

1. **名字先分开**：`kb_lookup_term` vs `kb_search`，不要叫 `kb_lookup_policy`（policy 太宽，和「制度问答」重叠）。
2. **描述写死边界**，用「用我 / 不要用我」句式：
   - `kb_lookup_term`：「查询已登记的标准术语/口径的权威定义。仅当用户询问一个明确的术语、缩写、指标口径时使用。不要用于开放性问题、多条件问题、流程步骤问题；这些一律用 kb_search。只做精确匹配，未命中会返回 found=false，此时必须改用 kb_search。」
   - `kb_search`：「在企业知识库中检索相关片段。适用于所有制度、流程、产品、口径类问题；也适用于 lookup 未命中的情况。不返回完整文档，需要原文时用 kb_read_doc。」
3. **行为上不给模糊兜底**：lookup 未命中就返回 `found=false`，不要静默返回最相近的词条，否则模型会以为「查到了」。
4. **单一事实源优先**：若术语表不大、更新不频繁，直接把术语表作为普通文档进 BM25 索引，删掉 lookup 工具——两个通道维护两份内容，迟早不一致。
5. **顺序提示**：若确实保留两者，在 system prompt 里写清「术语/缩写/口径定义类问题，先 lookup；未命中再 search；其他问题直接 search」，只对「术语类」问题生效，不要写成全局顺序。

出处：
- https://www.anthropic.com/engineering/writing-tools-for-agents
- https://docs.claude.com/en/docs/agents-and-tools/tool-use/implement-tool-use

## 三、定稿建议（可直接给后端/前端实现）

### 3.1 `kb_search`

**入参**

```json
{
  "query": "string, 必填, 自然语言或关键词，建议不超过 200 字",
  "top_k": "integer, 可选, 默认 5, 范围 1-10, 服务端强制 clamp"
}
```

不加 `scope`/`domain`，除非域边界真实存在且用户会明确说。不要用 `topK` 这种驼峰。

**返回（模型可见，建议 Markdown 风格头部 + 片段）**

```text
status=ok query="年假 几天" returned=5

[1] doc_id=hr/leave-policy | 员工请假管理制度 | §3.2 年假 | 更新 2026-03-01
年假天数按司龄计算：入职满 1 年不满 10 年的，每年 5 天；满 10 年不满 20 年的，每年 10 天……

[2] doc_id=hr/attendance | 考勤管理办法 | §2.1 假期类型 | 更新 2025-11-20
……
```

**字段约定**
- 必有：`doc_id`（slug，如 `hr/leave-policy`）、`title`、`section`（标题路径，用 `§` 或 `>` 连接）、`snippet`、`updated_at`。
- 可选：`match`（high/medium/low，由后端按阈值映射）、`locator`（行号或字符区间）、`truncated`。
- 不给模型：原始 BM25 score、内部索引 id、文件路径、MIME。

**预算**：单条 snippet 建议 **200–400 字**；总返回控制在 **3,000–5,000 字**（约 2–3k token），最多 5 条。超出时优先减条数，不要减到每条只剩一句话。

### 3.2 `kb_read_doc`

**入参**

```json
{
  "doc_id": "string, 必填, 必须是 kb_search 返回的 doc_id",
  "section": "string, 可选, 章节标题或锚点；省略时返回目录 + 前 1200 字",
  "offset": "integer, 可选, 默认 0, 字符偏移",
  "max_chars": "integer, 可选, 默认 4000, 上限 8000"
}
```

**返回**

```text
status=ok doc_id=hr/leave-policy | 员工请假管理制度 | §3.2 年假 | 更新 2026-03-01
offset=0 max_chars=4000 truncated=false next_offset=null

（正文）
```

**约定**
- `doc_id` 不存在：`status=not_found`，附 3 个最相近的 doc_id，提示「是否要查这些」；不要抛异常。
- `section` 不存在：`status=section_not_found`，返回该文档的章节目录，让模型重选。
- 截断：正文末尾加「已截断，继续读取请传 offset=NNNN」。
- 单次读取超过 8000 字一律截断，**不提供「读全文」的开关**。

### 3.3 `kb_lookup_term`（条件保留）

**入参**：`{ "term": "string, 必填, 术语/缩写/指标口径原文" }`

**返回**

```text
status=ok term="ARPU" found=true | 口径来源：finance/metrics-glossary §1.3 | 更新 2026-02-10
定义：每用户平均收入，按自然月统计，含订阅与增值服务收入，不含一次性项目。
同义词：每用户平均收入、单用户收入
```

未命中：

```text
status=no_match term="离职补偿 N+1" found=false
next=请改用 kb_search 检索相关制度文档。
```

**禁止**：模糊匹配后静默返回一个近义词条；返回与 search 相同的片段列表。

### 3.4 空结果 / 低分处理约定

| 情况 | 工具返回 | 模型应说 |
|---|---|---|
| 0 条 | `status=no_match`，附 `searched_terms` 与 2–3 个 `near_miss` 标题 | 「知识库中未找到与『X』相关的规定。已检索：…。建议换用『Y』或联系 Z。」不得编造 |
| 有结果但最高分低于阈值 | `status=low_confidence`，最多 2 条，`match=low` | 「找到若干相关度较低的内容，可能不适用：…如需准确答案，建议…」 |
| 服务异常 | `status=error`，`message` 写可行动信息（超时/索引不可用），不堆栈 | 「检索服务暂时不可用，请稍后重试。」不得用记忆回答 |
| 读取越界 | `status=section_not_found` + 目录 | 让模型重选章节，不要瞎猜 |

阈值建议在服务端用一组离线标注 query 校准，不要拍脑袋；BM25 的绝对分不可跨查询比较，阈值应结合「命中词数/覆盖率」或归一化后再定。

### 3.5 提示词配套要点（浓缩版）

1. 开头一句硬约束：「涉及制度/流程/产品/口径的问题，回答前必须先调用 `kb_search`。」
2. 写明检索策略：原词 → 同义词并行 → snippet 不足再 `kb_read_doc`。
3. 写明引用格式：`[doc_id §章节]`，句末，多个并列；只引用实际返回的内容。
4. 写明无结果行为：明确说未找到 + 给出已检索词 + 建议下一步；禁止编造条款/数字/日期。
5. 写明冲突处理：以 `updated_at` 新、层级高者为准，并说明冲突。
6. 写明不要暴露工具名、分数、调试信息。
7. 可选：首轮用 `tool_choice` 强制一次 `kb_search`；后续不强制。
8. 可选：鼓励一次发多个并行 `kb_search`（同义词/缩写展开）。

## 四、与草稿的差异清单

| 项 | 草稿 | 建议 |
|---|---|---|
| 工具数 | 4 | 3（删 `kb_list_topics`；`kb_lookup_policy` 条件保留） |
