## 1 组一：HITL 执行信封恢复 + 启动不变量 + 执行前复核 + `kind=null`

### 1.1 本轮权威执行信封（新文件）

`backend/src/main/java/com/example/configmgr/ai/gate/ToolExecutionEnvelope.java`（**新增，319 行**）是不可变值对象，`TOOL_CONTEXT_KEY = "executionEnvelope"`（`:36`）是写入方与读取方共用的唯一键名。

- **两个口**：`fromSnapshot(RunSnapshot, Long)`（`:92`，请求边界的生产构造口；`snapshot == null` 或 `runId` 空 ⇒ 返回 `null`，**不造无主信封**）与 `fromToolContext(Map)`（`:110`，执行点读取口）。后者兼容"本类实例"与"同名键 Map"两种承载形态，任何缺字段 / 类型不可解析 ⇒ 返回 `null` 且**不抛异常**（一个坏信封不能打断整轮工具执行）。
- **三条信任边界（类注释 `:19-28` 逐条写明）**：
  1. **只由本实例创建者消费** —— `restorableBy(expectedRunId, instanceId)`（`:233`）：`runId` 对得上 **且** `createdBy` 等于 `RunStore#instanceId()`；别的实例的信封不构成"这一轮归我驱动"的证据。
  2. **只恢复运行事实** —— `toSnapshot()`（`:155`）刻意**不带** `messageJson` / `inFlightToolCalls` / 任何条目的审批·认领·台账状态，状态写 `RUNNING`，于是"恢复"在结构上**不可能伪造审批**。
  3. **不重置序号 / 预算 / 步数** —— `round` / `toolSteps` / `budgetArmedAtMs` / `budgetSkippedBatches` 原值带回；`createdAtMs` **原值写回**（`:168-171`，旧信封缺该字段时才落当前钟 —— 恢复不是"新建一轮"，不拿当前钟冒充），`updatedAtMs` 才是本次落库时刻；`seqFloor` 只作**下界证据**，信封自身**不写** `ai:seq`。
- **写入点**：`ResilientChatService#toolContext(...)`（`:869`）把 `runId` / `sessionId` 原样保留后追加信封；首轮在 `chatClient...toolContext(...)` 处使用 **`store.create(...)` 的返回值** `executionSnapshot`（不是稍后可能被改写的读回值），续跑在 `buildResumedPrompt(...)`（`:841`）同构带上，`seqFloor` 取 `out.lastIssuedSeq()`（新方法 `SseChatEmitter#lastIssuedSeq()`，`:545`）。
- **读取点**：`SpToolCallingManager#executeToolCalls(...)`（`:388`）在"`runId == null || snapshot == null`"分支改为两步 —— 先 `recoverSnapshot(...)`，仍不可用才 `executeWithoutSnapshot(...)`（见 1.2）。

### 1.2 恢复路径与失败关闭

`SpToolCallingManager#recoverSnapshot(ToolExecutionEnvelope, String)`（`:2501`）：

1. 信封不可信（`restorableBy` 为 false）⇒ WARN + `null`；
2. **落库前复读**：并发中已有快照 ⇒ **直接用那一份**（不用较旧的信封覆盖更新的状态）；
3. `store.save(restored)` 后**必须复读确认真的落库** —— 写权不在本实例时 `save` 只 WARN 不抛，不复读会让后续 `saveSuspended` 以"找不到快照"把整轮打穿 ⇒ 这里宁可判成不可恢复；
4. **再抬序号下界**：`store.ensureIssuedSeqAtLeast(runId, envelope.seqFloor())`，随后校验 `lastIssuedSeq(...) >= seqFloor`，抬不上去 ⇒ `null`（**不发出会重号的帧**）；
5. 预算口径跨 park / 恢复不重置：`beacon.restoreBudgetArmed(...)` / `restoreBudgetSkippedBatches(...)` 按信封原值重新点亮。

`SpToolCallingManager#executeWithoutSnapshot(...)`（`:2557`）：恢复不了时 **READ + BACKEND 放行**（仍走官方执行器，纯只读无副作用），**危险 / 前端通道一律拒绝**，回 `blocked / TOOL_KIND_MISMATCH`（文本常量 `UNRECOVERABLE_EXECUTION_TEXT`，`:1683`），且**不弹卡、不认领、不写台账、不发帧**；历史形状保持"完整 `assistant(tool_calls)` + 全量 tool 响应"，官方循环下一跳不会丢消息。

### 1.3 风险 / 通道启动不变量

`ToolRegistry#init()`（`:65`）尾部新增 `assertRiskChannelInvariant()`（`:194`）：

- `DANGER ⇒ BACKEND`：`DANGER + FRONTEND` 会让后端按 `kind=CONFIRM` 挂起等确认、前端却按通道等回灌 —— **两条路径互相等，直接死卡**；
- `BACKEND ⇒ READ 或 DANGER`：`WRITE + BACKEND` 会被 `kindOf` 判成后端直执行 —— **可逆写静默绕过确认门**；
- 违反即 `IllegalStateException` **启动中止**并点名到工具（运行期只能二选一：死卡或绕过确认，没有安全默认）。

### 1.4 `reportHash` 执行前复核

`SpToolCallingManager#verifyApprovedReport(runId, pending, context)`（`:2624`），调用位置 = `executeOnce(...)` 的 **①.5**（台账重放之后、目标资源校验之前）：

- 只在"**确认门条目** + `ToolPreflightService.supports(name)` + 卡上**确实带过** `reportHash`"三条件齐备时生效；旧数据没有预检报告 ⇒ 无指纹可比 ⇒ 保持既有行为；
- 重跑一次**只读**预检：指纹相同 ⇒ 放行；不同 ⇒ `settleBlocked(PRECHECK_STALE, PRECHECK_STALE_TEXT)`（`:1668`，语义"确认卡上的预检报告与执行时的状态不一致，请重新发起并重新确认"）；
- 重跑自身抛异常或返回 `null` ⇒ 同样**不执行**（`PRECHECK_UNAVAILABLE` + `PRECHECK_REVERIFY_UNAVAILABLE_TEXT`，`:1672`）。

**口径**：卡上那份报告是批准的依据；执行时状态已变（文件被替换 / 有在途作业 / 任务改了步骤）**必须让人看新报告再决定**，旧报告不是执行授权。

### 1.5 `kind=null` 一律拒绝（旧兼容口径废止）

- `ConfirmGate#kindMismatch(...)`（`:1472`）：`kind` 缺失由"WARN + 放行"改为 **WARN + 返回 `true`**，调用方回 `TOOL_KIND_MISMATCH`，**条目一个字节不改**；`submitDecision` 与 `submitFrontendResult` 两条入口同口径（`cancelled=true` 也拦 —— 它同样会改写状态）。
- `SpToolCallingManager#executeOnce(...)` 新增 **⓪-a 硬闸**（`:1733` 起）：`!pending.hasKind()` ⇒ `settleBlocked(..., KIND_UNKNOWN_TEXT)`（`:1658`），**在台账重放与认领之前**。
- `SpToolCallingManager#resolvePending(...)`（`:2307`）续跑侧：只拦"本来会执行"的三态（`APPROVED` / `PENDING` / `EXECUTED` 但 `executed=false`）；**已结算的历史条目仍复用 `resultText`，绝不改写既有结局**。
- 机器码沿用 `TOOL_KIND_MISMATCH`（"这个调用不能在后端直执行通道上跑"），措辞明写"没弹卡、没执行，请重新发起"。

### 1.6 `seq` 只升：单键 Lua + 契约方法

- `RunStore#RAISE_SEQ_SCRIPT`（`:451`）：**单键** Lua，`floor > current` 才 `SET ... PX`，否则只 `PEXPIRE` —— 并发的更大号不会被回拨。**为什么必须是 Lua**：Java 侧 `GET → 比较 → SET` 会把并发发放的新号回拨。
- `RunStore#ensureIssuedSeqAtLeast(runId, floor)`（`:2732`）：`floor <= 0` 直接返回；写权走 `permittedToWrite(...)`（**丢租 / 换主后不得再推进号空间**）；异常只 WARN（恢复侧由 `recoverSnapshot` 复读校验兜住失败关闭）。
- 测试替身 `InMemoryRunStore#ensureIssuedSeqAtLeast` 用 `issuedSeqs.merge(runId, floor, Math::max)`，语义与生产一致（只升不降）。
- **为什么必须抬号**：快照与 `ai:seq` 可能同时丢失；不抬号会让恢复后的 `suspended` / `confirm_request` 从 1 重发，前端带 `lastSeq` 重挂时把这些帧当孤儿丢掉 —— **确认卡正好在这批帧里，卡就消失**。

**边界（本组）**：`RAISE_SEQ_SCRIPT` **未在真实 Redis 上实跑**（本笔零服务起停）；跨实例 / Cluster 语义、脚本在 `EVALSHA` 失败回退等形态均未验证；`recoverSnapshot` 的"并发已有快照优先"与"save 后复读"两个窗口只做了代码级推理，未做并发压测。

## 2 组二：断流、`!sideEffect` 与"零文字但工具已结算"

### 2.1 后端：重试判据**未改**

`ResilientChatService#runAttempts(...)`：

- `boolean sideEffect = this.beacon.startedCount(runId) > beaconBefore`（`:977`）**原样保留**；
- `boolean retryable = outcome.retryable() && !emitted && !sideEffect && hasNext && !overBudget`（`:982`）**原样保留**。

因此本批的语义是"**保留普通 `!sideEffect` 这条重试通道**"：本次尝试里**一次工具都没开始**（纯上游断流）时 `sideEffect=false`，仍按既有整轮重试路径走；一旦有工具开始（不论读写，`beacon.enter` 在执行前统一调用），`sideEffect=true` ⇒ **不自动重试**，整轮落失败终态，界面改由**用户动作**接手。

### 2.2 前端：工具段不再算"产出"

`frontend/src/components/AiPanel/AiPanel.vue`：

- `turnHasOutput` → **`hasTextOrReasoning(message)`**（`:1745`）：只认"非空正文 / 非空思考"，**工具段不再计入**；
- `showContinue(message)`（`:4389`）= 失败轮 **且有文字/思考** ⇒ 出「继续」（append-drive，不删历史、不加用户气泡）；
- `showRetryTurn(message)`（`:4393`）= 失败轮 **且零文字零思考** 且归属可证明（`ai.retryRunIdFor(message) !== null`）⇒ 出「重试本轮」，走**既有** `retryModelStep`（批次 2 建立的"仅模型步重跑"窄入口，本批**不新增入口、不改后端**）。
- 同一轮两按钮互斥；错误卡「稍后重试」同样只落在这类轮上，否则动作**直接隐藏**（不做禁用 / `unsupported` 假 UI）。

**修的是哪类轮**：工具已结算（例如 `list_tasks` 成功返回）但模型还没写出任何正文就断流 —— 旧判据把这轮算成"有产出"，只出「继续」；但这类轮**没有可承接的半截答案**，续写的正确动作是"仅模型步重跑"。

### 2.3 失败日志：`silenceMs` / `toolIdleMs`

`ResilientChatService` 失败日志（`:1011`）新增两个字段：

- `silenceMs = failedAt - watchdog.lastUpstreamAtMs()`（**最后一条上游事件到失败**的静默时长）；
- `toolIdleMs = toolActivityIdleMs(runId, failedAtMs)`（`:1112`）：只读 `ToolActivityBeacon#lastActivityAtMs(String)`（工具开始 / 落定 / 被动活动锚点），**无锚点或读取异常 ⇒ `-1`**。

两者都**不含正文**，只用于区分"上游一直静默"与"工具刚跑完就失败"。

**边界（本组）**：**断流的上游根因未证** —— 本批只加观测与前端动作分派，**不改上游处理、不做自动半截替换**；`silenceMs` / `toolIdleMs` 的实际取值形态未在真实断流下采过样；`sideEffect` 是"工具开始过"的口径（含只读工具），"无副作用"≠"只读"，引用时不要混用。

## 6 组六：思考默认不展示、但保留回填

- `AiProperties.Reasoning`（`:1565`）：`displayEnabled = false`（默认）、`persistContent = true`（默认）；`application.yml` 显式落两键（`:134-135`）。
- **展示侧**：`ResilientChatService` 分片处 `if (properties.getReasoning().isDisplayEnabled()) out.reasoningDelta(reasoning)`（`:2409`）—— 默认**不发思考帧**；`AiController` 历史透出加同一道门（`:1717`）—— 默认**不透 `reasoningContent`**（`metadata` 仍照旧落库）。
- **持久化侧**：`storedReasoning(reasoning)`（`:1782`）在 `persistContent=false` 时返回空串（`assistantMessage` / `stoppedMetadata` 据此不写该键）；默认 `true` 时思考全文照旧累计进 assistant 消息 `metadata`，供下一轮 `ReasoningAwareOpenAiChatModel` 回填。

**边界（本组）**：**帧类型集仍 16**，只是默认不发该帧（不是删帧类型）；历史"不展示"≠"不落库"；未跑测试，未验证真实模型下"关闭展示"是否影响推理质量。

## 7 组七：`navigate_to` 权威类型、两页静默纠正、任务详情就绪、成功导航静默

### 7.1 权威任务类型（查不到就不导航）

- `frontend/src/utils/frontend-tools.ts#resolveAuthoritativeTaskType(taskId)`（`:953`）单点收口到 `taskStore.ensureTaskType(taskId)`：**缓存优先、未命中拉一次 `GET`、查不到返回 `null`**。
- `runNavigateTo(...)`（`:1075`）：带 `taskId` 时**必须**拿到类型；`null` ⇒ `taskTypeUnknown(...)` 回执并**不导航**（fail-closed）。已知类型优先于模型写的 `page`（模型写 `export` 而任务是导入 ⇒ 实际进导入向导，回执说明修正）。
- 契约层 `frontend/src/stores/workspace.ts` 的 `restore_task`（`:544`）：优先用事件里带的**权威值** `event.taskType`，没有就当场 `ensureTaskType`；`null` ⇒ `fail("无法确认任务 #N 的类型…，未导航")` —— **不再按列表兜底成 `EXPORT`**（"冷缓存下导入任务被送进导出向导"的根因）。
- `toUiEvent('restore_task')` 只透传合法 `taskType`（`IMPORT` / `EXPORT`），非法值退化为不带；`WORKSPACE_ACTION_REQUIRED_ARGS` 增 `restore_task`（`:1266`），参数不完整时给统一可读提示。

### 7.2 两页静默纠正

- `ExportWizardView#loadTask(...)`：`loaded.type === 'IMPORT'` ⇒ `taskDetailReady=false` + `router.replace({ name: 'import-wizard', query: { taskId } })`，**不弹提示、不回灌"打开失败"**；
- `ImportWizardView#loadTask()`：`loaded.type === 'EXPORT'` ⇒ 同样静默 `replace` 到 `export-wizard`；
- 理由：类型相反说明"本页不是它的向导"，继续按本页形态恢复会把导入任务的选中集 / 上传清单套到导出页（或反之）。

### 7.3 `taskDetailReady`：最小就绪（含幂等）

- `frontend-tools.ts` 新增 `TASK_DETAIL_READY_PROBES`（`:809`，只覆盖两个向导页；任务中心"详情"就是列表行，其余页无任务详情）、`isTaskDetailReady(page)`（`:823`，只读探针、不发请求）、`waitForTaskDetailApplied(page, timeoutMs)`（`:844`）、统一回执 `taskDetailNotReady(label, taskId)`（`:975`，`failed` + `UI_PAGE_NOT_READY`，明写"此时页面上的勾选集为空，本轮不要再设置条件或推进步骤"）。
- `waitForTaskBound(...)`（`:886`）由两维扩为**三维**：`pageReady` / `taskBound` / `detailReady`，三者齐备才 `ok`；`TaskBindWaitResult` 同步加字段。`waitForTaskOpened(...)` 同样纳入详情维度。
- **幂等早退也要等详情**：`runNavigateTo` 的"同页同任务直接返回"与 `runRestoreTask` 的"同页同任务直接返回"分支，都先 `await waitForTaskDetailApplied(page)`，未就绪 ⇒ `taskDetailNotReady`（**不再回 `UI_ALREADY_ON_PAGE` 替一次未恢复的页面背书**）。
- 页面侧：两向导各增 `const taskDetailReady = ref(false)`，**只在 `enterPage` 之后置 `true`**；`loadTask` 起飞、读取失败、类型纠正、换任务（`resetTaskScopedState`）都置 `false`；探针 `export.taskDetailReady` / `import.taskDetailReady` 与页面其它 handler 在**同一处 `registerHandlers()`** 注册。
- **"最小"就绪的定义**：`pageReady`（页面挂载 + 能力 handler 已注册）+ `taskBound`（`workspace.taskId` 已绑）+ `detailReady`（选中集 / 条件草案 / 步骤 / 状态已按服务端事实恢复并 `enterPage`）；**明确不等**定义列表 / 结果文件 / 作业恢复 / SpreadJS / 编辑器。
- 探针缺席视为"该维度不适用"（页面没挂载时由 `pageReady` 兜住）—— 这条是**设计上的最小化取舍**，也是本组最需要留意的口子（见 §9）。

### 7.4 成功导航静默、失败与作业通道保留

`frontend/src/stores/ai.ts` 新增 `SILENT_SUCCESS_UI_EVENTS`（`:450`）：`open_page` / `restore_task` / `goto_step` / `refresh_defs` / `refresh_data` / `refresh_tasks` 六类，`record.handled === true` 时**不写** `lastUiEventResult`（`:2500`），且**不抹掉槽里已有的失败事实**；`send` 开新轮时清槽（`:4021`，回执位属"轮次现场"）。

- **不在此列的一律保留**（失败永远保留）：`run_job` / `cancel_job` / `download` / `select_defs` / `set_conditions` / `set_import_mode` / `export_started` / `import_batch` / `import_action` —— 这些的成功意味着后端已落副作用（建作业、取文件、改数据），**必须有一条可见回执**。
- **底层不动**：`workspace.touch` / `recentActions` / `workspace_changed` chip / `dispatchUiEvent` 广播全部照旧；本表只决定 **AI 面板回执位**写不写。

**边界（本组）**：`UI_PAGE_NOT_READY` 复用既有码（未新增错误码）；"静默纠正"= 不弹 `ElMessage`，但**路由确实会 `replace`**（两页互为反向，是否可能形成纠正往返未实测）；详情维度靠页面自报，**探针若漏注册该维度会静默通过**（代码注释声明与 `PAGE_READY_PROBES` 同处注册，但本笔未验证）；`ensureTaskType` 的 `GET` 增加了一次冷缓存请求，**未测其耗时对导航回执时延的影响**。

## 9 边界与未验（连读才可引用）
