## 0. 结论先行

「导出CNY货币字典」这一轮的特征是**帧密**：`start` → 文本增量 → 工具卡 → 确认门挂起
（`loading=false && suspended=true`）→ 用户批准 → 重连收流 → 结局帧 → 收口。整屏闪不是某一帧画错，
而是**呈现层在每次轮次现场翻转时做了一遍不该做的全量工作**，共三处：

| # | 根因 | 可观测症状 |
|---|---|---|
| 1 | 每条消息的 `v-memo` 依赖里并进了 `ai.loading` / `ai.runPhase` / `ai.activeRunId` / 末条消息 id 这类**全局现场** | 任一全局开关翻转（收流开始 / 收流结束 / 挂起 / 恢复 / 换轮）都会让**整列**消息行一起失效：历史正文重跑 markdown、卡片派生（标题 / 摘要 / 状态 / 字段表）整批重算 + 全列表 patch |
| 2 | 已决只读卡的「回合未结束仍展开」判据含 `loading`，但**恢复期 `restoringRecovery` 也会置 `loading`** | 刷新 / 重新载入 / 回到进行中的回答时，末条消息里的已决只读卡先被强制展开、HTTP 回来再折 —— 一次"展开→折叠"的换形 |
| 3 | 钉底挂在**含状态位的滚动指纹**上，且 `watch` 与 `ResizeObserver` **各钉一次**，浏览器原生滚动锚定再补一次 | ①状态变（工具段 status、`pendingCall.status`）也把视线拽回底部；②一次内容变化最多写两次 `scrollTop`（实测 2 次），叠加原生锚定即"来回抖 / 视觉闪" |

修复后口径：**全局现场只以"本消息/本卡的判定结果"进入 memo**；已决卡只在
`suspended || (loading && (!restoringRecovery || 恢复期进入时采样为真))` ∨ 决策/GF 在途时展开；
滚动由**measured size 变化**驱动、单一调度合并、上翻即释放，且**只在跟随态**关掉原生锚定。

## 2. 口径（逐条对应要求）

### 2.1 memo：全局现场不入，判定结果入

- **消息行**：`v-memo` 依赖 = 本消息字段（id / role / parts / streaming / done / stopped / truncated /
  synthetic / timestamp / pendingCall / recoveryGap / errorCard 各字段）+ 渲染期判定结果（元信息行、时间戳、
  等待/呼吸/淡出、继续/重试、反馈与复制、长消息折叠、降级提示、相邻发送者间距）+ 逐块 `partMemo`。
- **段（文本块 / 工具卡）**：`partMemo` 依赖 = 段自身字段 + 该块展开态判定结果 `isBlockExpanded(block)`
  + 卡片会读的**卡粒度** store 切片（门卡提交态/勾选态、撤销、表格已应用摘要、上传交接、
  表格预览、运行态到期、本卡 applied 摘要）。
- **GF 卡（复审 M-1 返修）**：`liveForm` 现场只属于"当前宿主那张卡"——只有
  `liveForm.toolCallId === part.toolCallId && formHostMessageId === block.messageId` 时才把
  `liveForm.value` / `values` 等并入依赖；历史 GF 卡的渲染不读它，因此不会被"用户每敲一个字"拖着重渲。
  队列面只入标量（本卡位次 + `queuedForms.length`），不再入整个数组身份。
- 关键点：这些"判定结果"函数本身在**父组件 render 里求值**，所以 `ai.loading` / `ai.suspended` 等
  依然会被父组件订阅（父组件照常重渲一次），只是**不再让每一条历史消息一起失效**：
  结果没变 ⇒ 该行 v-memo 命中、子树上零 patch（连 `v-html` 的 markdown 都不再生成）；结果变了 ⇒ 该行照常更新。
- 因此"loading 变化历史不失效、当前消息必要更新仍生效"是同一套机制的两面（回归锁第 1 条）。

### 2.2 确认卡：终态 + 在途事实，稳定展开、不卸载

- 卡壳、key、类型、testid 体系一律不动（`rocard` / `hitl-receipt` / `pending-card-*` 的判定仍是
  `readOnlyLike` / `requiresAction`，本批未改）。
- 展开判据（现行原文）：**`ai.suspended || (ai.loading && (!ai.restoringRecovery || 恢复期采样为真))`**
  ∨ 决策在途（`gateSubmissions` 有值）∨ GF 提交在途（`isFormAwaitingOutcome`），
  且要求该卡属于末条消息；用户手动展开（`expandedBlocks` 显式值）永远优先；失效禁用（`runExpired`）不动。
- **恢复期按"进入那一刻"是否仍在收流来判**（复审 I-1′ 返修）：`restoringRecovery` 由假变真时，用
  `flush:'sync'` 的 watch 采样当时的 `ai.loading`（挂载时已处于恢复期 ⇒ 不采样，默认 `false`）：
  - 采样为真（流中手动重载 / 自动恢复 attempt）⇒ 整个恢复窗口按"仍在收流"处理，**保持展开**；
    attempt 之间标志复位、`loading` 仍真，也不会折 —— 不再有"折一次→展开"的往返（最多两轮）；
  - 采样为假（刷新首屏 / 轮已收口后的重新载入）⇒ 恢复期**不展开**（原目标：不对过去的镜像做实时渲染），
    期间即使 `loading` 变真也不展开（采样是快照，不实时读）；
  - 恢复结束即清采样，下一次恢复重新取现场。
- `restoringRecovery` 的置位点 = `loadHistory` / `retryPreparing` / `retryRestoreSnapshot` / `reattachBusyRun`
  四个手动包装层 + 两条**自动恢复** attempt（preparing / first-frame，§7 I-1）。它是普通布尔、不是
  ref-count —— 嵌套/并发恢复可能提前清位；面板的采样机制不依赖"标志是否连续"，只依赖每一次
  假→真迁移（§5 保留该属性登记）。
- 「回合结束才收」语义不变：本轮真正收口（既没收流也没挂起、也没有在途决策）后才收成卡头行。

### 2.3 滚动：尺寸驱动的 stick-to-bottom

1. **跟随态**仍由用户的滚动事件维护（`followBottom`，32px 闸 + 32/160 浮钮滞回 + 钉底静默期回声闸，本批未动）。
2. **只有 measured size 变化才钉底**：RO（正文 / 卡片 / 确认门 / 表单插入）+ 「内容形态变过」证据 +
   「测到的高度比上次高」三者任一 ⇒ 尺寸变过；**状态位变化（工具段 status、`pendingCall.status`）不产生任何滚动**。
3. **用户上翻立即释放**：`followBottom=false` 时统一调度直接返回，不强制拉回；回到底部附近由既有闸自动恢复。
4. **合并重复触发**：`watch` 的补丁后复测与 RO 回调都汇入 `scheduleStickToBottom()`（一帧一个
   `nextTick` 任务），`pinBottomTo()` 再按"是否已在底部"去重 ⇒ 一次内容变化**只写一次** `scrollTop`。
5. **不与原生锚定打架**：滚动容器 `overflow-anchor: none` **只在跟着底部时挂**（`followBottom ? '[overflow-anchor:none]' : ''`）；
   上翻阅读时我们不做补偿，此时浏览器锚定是唯一的"保位置"手段，必须交还给它。
6. **不是"只有新正文才跟随"**：卡片展开 / 确认门与表单插入 / 用户长消息折叠都改尺寸，同一条路径钉底。
7. **已知时序（复审 M-3，接受项）**：RO 回调只置标志 + `nextTick`，补偿落在 paint 之后，比 BASE
   （RO 回调内同步写 `scrollTop`）可能**晚一帧**。真机若能看到"最新一行晚约 16ms 出现"，再按
   `onContentResized()` 内同步补偿处理（`pinBottomTo` 已贴底时早退，不会双写）。

## 3. 业界依据

- **`v-memo` 的语义就是"依赖数组逐项相等就跳过整棵子树更新"**，因此依赖必须恰好等于该子树渲染
  真实读取的值；把与子树无关的全局状态塞进依赖，只会把局部更新放大成全列表更新
  （Vue 官方 `v-memo` 文档：<https://vuejs.org/api/built-in-directives.html#v-memo>）。
- **AI 聊天场景的 stick-to-bottom 主流实现是"ResizeObserver + 用户滚动释放"**，而非"按状态变化滚"：
  `use-stick-to-bottom` 的 README 明确写它「用 ResizeObserver 侦测内容尺寸变化」「正确处理滚动锚定」
  「用户上翻随时取消跟随」「区分用户滚动与程序化滚动的 scroll 事件」
  （<https://github.com/stackblitz-labs/use-stick-to-bottom>；npm 页面同述
  <https://www.npmjs.com/package/use-stick-to-bottom>）。
- **浏览器原生滚动锚定默认开启**：内容在视口上方变化时浏览器会自行调整 `scrollTop`，`overflow-anchor: none`
  用于退出这一行为（MDN：<https://developer.mozilla.org/en-US/docs/Web/CSS/overflow-anchor>、
  机制总览：<https://developer.mozilla.org/en-US/docs/Web/CSS/Guides/Scroll_anchoring/Overview>）。
  自己接管滚动补偿的场景下必须显式关掉，否则"浏览器补一次 + 我们补一次"就是重复补偿与抖动。
- **经典的"钉底"做法本身就是"检测内容变化再滚"**，而不是监听业务状态
  （CSS-Tricks《Pin Scrolling to Bottom》：<https://css-tricks.com/books/greatest-css-tricks/pin-scrolling-to-bottom/>）。
- 本仓既有调研《业界滚动调研-2026-10-13》的结论（`StickToBottom` + ResizeObserver 全覆盖 +
  只认用户意图脱离）本批继续沿用，只补上"合并重复触发 / 关原生锚定 / 状态变化不滚"三条。

## 5. 未验证项（**真机未执行**）

- **未在浏览器真机复现/验收**「你说『导出CNY货币字典』→ 挂起 → 批准 → 重连 → 完成」这条链路；
  本批全部证据来自 jsdom 单测（DOM 断言 + `scrollTop` 写入计数 + markdown 生成计数 + GF 卡渲染计数）。
- **未做 Performance / Rendering 面板录制**：没有真机帧率、Layout / Paint 耗时、长任务数据；
  "整屏闪"是否 100% 消失只能由真机肉眼 + 录制复核。
- **恢复期不再折形只在单测层证明（复审 I-1′ 已消除，真机未验证）**：流中手动重载
  （`重新载入 / 刷新状态 / retryRestoreSnapshot`）与自动恢复两次 attempt 之间的已决只读卡**保持展开**
  由"进入恢复那一刻的 `loading` 采样"保证；单测覆盖进入/间隙/首次历史恢复三面，
  **没有真机观察**这条 1~1.5s 失败恢复窗口的视觉表现。
- **RO 补偿可能晚一帧（复审 M-3，接受项）**：RO 回调只置标志 + `nextTick`，补偿落在 paint 之后
  （BASE 是回调内同步写 `scrollTop`）。真机需确认"最新一行是否晚约 16ms 出现"，
  再决定是否改为回调内同步补偿（`pinBottomTo` 已贴底时早退，不会双写）。
- **`restoringRecovery` 不是 ref-count**：嵌套/并发恢复可能提前清位（既有实现属性，本批未改）；
  面板的采样机制只依赖"假→真迁移"，不依赖标志连续，但 store 侧"并发置位计数"仍未验证。
- **未验证跨浏览器锚定行为**：`overflow-anchor` 在 Safari 的支持历来不稳（`use-stick-to-bottom`
  正是为此改用 ResizeObserver），本批只按 MDN 口径声明；Safari / Firefox 未实测，
  "上翻时交回浏览器锚定"的真机效果也未验证。
- **未跑 e2e / Playwright 套件，也未跑全量 `vitest run` 与 CI**：按派工口径只允许"明确文件 + 单测试名"。
- **未做长会话压力验证**（>200 条消息、含 mermaid / 图片 / 大表的会话）：memo 收窄后的重渲染收益
  没有量化数据（只验证了"历史正文不再重渲、历史 GF 卡不再随输入重渲"）。
- **未覆盖"用户在流式中途上翻、随后自行回到底部"的真机手感**：`followBottom` 的滞回与回声闸沿用旧口径，
  jsdom 无法验证滚动惯性/触控板的连续 scroll 事件。

## 6. 边界与风险

- 本批**没有**引入虚拟列表、没有改消息 key / 组件层级、没有动后端；`stores/ai.ts` 只有 I-1 的
  两处 attempt 包裹（不触碰恢复分支、不触碰工具链、不新增 store 状态）。
- memo 依赖收窄的代价：父组件每次 `loading` / `suspended` / 恢复态翻转仍会重渲一次（这是 Vue 的
  `v-memo` 机制决定的），但每行的依赖比较结果不变 ⇒ 子树零 patch。若后续新增"渲染期读取的全局现场"，
  必须把它以**判定结果**的形式加进 `messageMemo` / `partMemo`，否则会出现"值变了但界面不动"。
- 滚动侧新增的唯一状态是组件内私有基线（`lastMeasuredScrollHeight` / `stickShape` / 两个本帧标志），
  随 `attachMessageViewObservers` / `resetStickBaseline` 重建；收起/展开、换会话不会带着旧基线走。
- `gfCardRenders` 是**只读调试计数**（经 `__batch7aDebug` 暴露，零 UI 影响），仅 GF 卡自增，
  随组件实例存活。
