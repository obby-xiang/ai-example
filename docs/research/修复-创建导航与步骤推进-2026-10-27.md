## 1 提示词：批准 → 同轮单点导航 → 结束本轮

**问题**：旧口径写"`create_task` 返回任务 id 后**下一轮**用 `navigate_to` 打开"与"引导用户回复继续指令"。两条叠加后，模型把「批准 → 建任务 → 打开向导」拆成三段，并在任务**已经存在**的前提下再要一次批准、再要一句"继续"，甚至重建任务。

**做法（三处规则一并收口）**：

| 规则 | 语义 | 锚点 |
|---|---|---|
| 第 8 条 | `create_task` 回执给出**真实 `taskId`** 后，**同一轮立即单独**调用 `navigate_to(page, taskId)`；**禁止**与 `create_task` 放进**同一批并行调用**；`page` 按任务类型取对应向导（导出任务=导出向导、导入任务=导入向导）；**导航前**不要调 `select_definitions` / `confirm_step` | `ResilientChatService.java:189`–`:192` |
| 第 10 条 | 披露按轮生效的口径保留（同一轮不调刚解锁的工具），但**收窄**为：确实要等下一轮才披露时可简短说明下一步，**允许用户给出下一步指令即可，不要机械套用"请回复继续"**；下一轮按原始意图自动接续；导航成功即结束本轮、同一目标页不重复导航；**例外** = `create_task` 已批准或已创建成功时任务已存在，**不得**再要批准 / 要"继续" / 重建 | `:200`–`:206` |
| 第 24 条 | **只有确认卡确实待决时**才提示"请在卡片上批准"；拒绝 / 取消即不创建；同轮最多一次、不换标题重试；**已批准且创建成功即"任务已存在"**，不得再索要批准、不得要求回复继续、不得重建或重复创建；拿到真实 `taskId` 后按第 8 条同轮立即（**单点、不并批**）导航，导航成功结束本轮，失败则如实说明失败原因与当前状态 | `:235`–`:241` |

**走法**：把"任务是否已存在"当成**事实分流**而不是语气问题 —— 批准后只剩"导航"一个动作，导航完成后本轮就该结束；需要下一轮披露时，用户输入是**继续条件**、不是**必须念的咒语**。

**边界**：这是**提示词软约束**，宿主侧只硬保证 `create_task` 的 DANGER 通道、单轮上限与幂等；**本批未新增"禁止并批"的宿主硬闸** —— 模型若仍并批，`navigate_to` 这一侧会因为拿不到真实 `taskId` 而按既有参数校验走 `failed`（不猜任务号、不兜底类型）。

## 2 选择配置后默认前进一步，不主动问筛选

**问题**：`select_definitions` 成功后，模型习惯追问"要筛选还是跳过"，用户还要多答一轮；同时会把"跳过筛选"实现成传 `step` 直接跳步，绕过当前步骤校验。

| 件 | 语义 | 锚点 |
|---|---|---|
| 第 28 条 | 勾选成功后**不要主动追问**"要筛选还是跳过"；**默认直接调用 `confirm_step` 且不传 `step`**，只前进一步；**只有用户主动提出筛选需求**才用 `set_condition`，没提就不展开询问；不设条件即**全量**导出，推进时如实说明"未设筛选，将导出全部"；`step` 仅在用户**点名目标步骤**或**明确要求跳过筛选**时传；查询条件**始终可选**、不强制填写 | `ResilientChatService.java:253`–`:256` |
| `confirm_step` 描述 | 同一口径写进模型侧工具描述（默认不传 `step`；`step` 只在点名目标 / 明确跳过滤镜时传） | `AiTools.java:586` / `tools.yaml:75` |

**边界**：`set_condition` **空值语义未动** —— 本批只规定"用户没提就不要问、不要设"，注解里"空 = 全量"仍依赖既有实现；"不传 `step`"也不改前端校验（当前步骤校验不过仍然推不动，前端才是判据）。

## 4 导航去重：只缓存"可复用"的结局（NAV3）

**问题（毒化）**：旧实现按"同 run + 同参"直接缓存**任何**结局。一次 `failed` / `timeout` / 降级成功被记进表后，同参重试命中它、直接回"本轮已执行过" —— 模型据此判定这条路走不通，而现场可能早已可执行（详情加载完 / 页面恢复）。

| 件 | 语义 | 锚点 |
|---|---|---|
| `rememberSameCall` | 只收 **`outcome === 'ok'` 且 `availability === 'available'`**；其余（失败 / 超时 / 结局未知 / 降级）**一律不记** | `frontend-tools.ts:694` / `:707` |
| 幂等表达 | 幂等与否由 `outcome` 说，**不按文案猜**；`UI_ALREADY_ON_PAGE` 这类幂等直返本身是 `ok`，照常进表 | 同上 |
| 作用域 | 键的构成（run 作用域 + 同参）与清理时机**未改**，本批只改"哪些结局可复用" | `:603` / `:618` |

**后果**：失败一次不再是**一次性的行业判决** —— 同参重试会真执行；而真正的幂等成功仍然挡住重复导航（第二次回"本轮已执行过"，`push` 次数不增）。

## 5 `ensureTaskType` 有限退避（NAV3 同批）

**问题**：`restore_task` / 带任务的导航**只**认服务端任务类型；一次瞬时读取失败就 `null` ⇒ fail-closed 不导航。用户看到的是"点了没反应"，实际只是网关抖了一下。

| 件 | 语义 | 锚点 |
|---|---|---|
| `isTransientTaskReadFailure` | **瞬时** = 网络未到达（`status === 0`）/ `408` / `429` / `5xx` ⇒ 可重试；**确定性 4xx（含 `404`）⇒ 不重试**，立刻 fail-closed；**非 `ApiError`** 的意外异常按"不知道是不是瞬时"给一次机会 | `stores/task.ts:199` |
| `ensureTaskType` | 首发 + `200ms` + `400ms`，**共 3 次**，**不轮询、不延长上界**；每次重试前**重查缓存**（退避窗口里列表加载 / 事件分发可能已把类型钉住，命中即零请求返回） | `:618` / `:624` |
| 失败口径 | 仍返回 `null`、**不兜底成 `EXPORT`**（"导入跳导出"的根因）；调用方仍按 `taskTypeUnknown` 出可行动回执 | `:646` |

**边界**：退避只加在"读任务类型"这一处，不改缓存的权威性与缓存优先次序；`404` 不重试是刻意的 —— 重试同一条不会把"没有这条"变成"有"。

## 6 详情未就绪 ≠ 未跳转（NAV2）

**问题**：导航成功判据是"页面 + 绑定 + **详情已应用**"三维（防 `confirm_step` 拿空选中集落库）。三维只折成一个布尔值时，"页已打开、详情还在加载"与"页根本没打开"挤进同一个 `false`，回执只能瞎猜一侧 —— 被写成"导航未执行 / 打开失败"，模型据此**重新导航**：页面再挂一次、真正的等待窗口被重新计时。

**做法**：维度分开 + 文案照实 + 路由不动。

| 件 | 语义 | 锚点 |
|---|---|---|
| `waitForTaskOpened` | 返回 `{ opened, detailReady }`：`opened` = 落在某个向导页且任务已绑定；`detailReady` = 详情已应用。**只读现场，不加等待时长** | `frontend-tools.ts:953` |
| `taskDetailNotReady(label \| null, taskId)` | 统一回执："**页面已打开、任务 #N 已绑定**，但任务详情在等待上界内仍未应用"，理由补"**路由已经落位，无需重新导航**"，下一步仍是"本轮不要设置条件或推进步骤"。未带类型时 `label = null` 走通用主语"任务向导"（类型归服务端，页名不可猜） | `:1016` |
| `UiEventNavigationWait` | 四态 `none` / `ready` / **`opened-detail-pending`** / `not-ready`；后者才允许说"未就绪" | `:1632` |
| `waitForUiEventNavigation` | `restore_task` 按"页面 + 绑定 + 详情"三维判；三维缺详情 ⇒ `opened-detail-pending`（带 label），页都没挂上 ⇒ `not-ready` | `:1651` |
| `runUiEventAction` | `opened-detail-pending` 复用 `taskDetailNotReady`；三条导航路径（`navigate_to` / `restore_task` / ui_event 导航）**同一口径** | `:1711` |

**刻意不改的三件事**：

1. **仍判 `failed` + `degraded`**，不放行成 `ok` —— 详情没应用时放行，紧随的 `confirm_step` 就会拿空选中集推进并落库（"AI 说按勾选导出、实际导出全量"）。
2. **不改路由**：不重推、不回退，也不清已落位的 `pageId` / `taskId`。
3. **成功仍静默**：`ok` 路径只回结果文本、不写回执位（沿既有口径），本批只改失败 / 降级一侧的措辞与去重准入。

## 8 边界与不声称

- **提示词 ≠ 硬闸**：第 1 组的"同轮单点导航""不并批"是模型侧纪律；宿主侧没有新增"检测并批即拒"的校验。真正的硬保证只有 `create_task` 的 DANGER 通道 / 单轮上限 / 幂等，以及 `navigate_to` 侧"拿不到真实 `taskId` 就按参数校验失败"。
- **去重表只改准入**：作用域键、清理时机与"第二次回执文案"都没动，所以"成功仍被去重"这一既有行为**照旧**（这正是本批要保留的一半）。
- **退避不是重试机制**：`ensureTaskType` 的 3 次上限是"跨过一次瞬时抖动"，不是轮询；`404` 一步不重试；读不到仍 fail-closed、不猜类型、不兜底 `EXPORT`。
- **`taskDetailNotReady` 仍是失败**：只把"哪一维没齐"说清楚，不改变"详情未应用就不许推进步骤"这条硬判据；也不改等待上界。
- **本批不触碰**：帧契约、工具风险分级、确认门三态、`set_condition` 的空值语义、`restore_task` 的"类型以服务端为准"口径。
