## 概念裁决（2026-10-16 用户直裁）：HITL ≠ 生成式表单

分界线=这次交互是否在授权一个后果：

- 生成式表单=把信息结构化送进流程（填完只是业务步骤、错可改、无立即外部副作用）。本项目 GF（FILTER/CLARIFY）与拟增的单选/多选询问卡均属表单系，不是 HITL。
- HITL=副作用发生前的人为闸门（不可逆/外部可见/花钱/改权限/合规敏感）。本项目确认门（start_export/import/publish/precheck）属 HITL。
- 口诀：填了只是「进入流程」用生成式表单；填了/点了就会「改变外部世界、花钱、授权或难以撤回」用 HITL。
- 混合场景：查票选座=表单、出票支付=HITL；生成 SQL=表单、执行到生产库=HITL。
- 修正前指挥官错误口径「GF ⊂ HITL 采集轴」（2026-10-16 用户纠正）。

## 一、三种监督姿态：HITL / HOTL / HOOTL（来源：Redis）

- **Human-in-the-loop（HITL）**：人做决定、AI 给建议；**关键动作不获得人类输入不继续**。适合高风险、低频、不可逆动作。Redis 把它与 HOTL/HOOTL 并列区分：HITL 通常要**同步 interrupt-and-resume**。
- **Human-on-the-loop（HOTL）**：AI 自主执行，人看 dashboard、告警，保留介入/熔断权；适合大批量、错误可恢复的场景。
- **Human-out-of-the-loop（HOOTL）**：边界内全自动，只在设计期设边界；高风险场景一般避免。

对项目含义：本项目确认门 = HITL；单据流程内的字段采集 = 表单系（既非 HITL 也非「弱 HITL」，见置顶裁决）。

## 二、运行时的五类「打断 / 询问」交互（来源：CopilotKit）

CopilotKit 把 agent 暂停后的交互归纳为五种，基本覆盖了「审批？询问？」这一问法：

| # | 形态 | 含义 | 例 |
|---|---|---|---|
| 1 | **Approve / reject** | 批准或拒绝一个完整动作 | 「是否发这封退款确认邮件」 |
| 2 | **Edit, then continue** | 人先改提案再执行，**执行的是编辑后版本** | AI 拟退 $500，人改成 $50 后批准 |
| 3 | **Choose among options** | 给多个方案让人选 | 三条行程、两种架构方案 |
| 4 | **Provide missing input** | 缺只有人知道的事实时暂停 | 「这张发票挂哪个成本中心」 |
| 5 | **Retry with guidance** | 拒绝并说明原因，让 agent 带反馈重试 | 「语气太随意，改正式」 |

## 三、工程落地的四种架构模式（来源：Dataiku / Permit 类文章，可组合）

| 模式 | 做法 | 代价 / 风险 |
|---|---|---|
| **Interrupt & resume** | 预定义 checkpoint 暂停，支持批准/修改/拒绝，留下审计点 | 延迟；适合高 stakes、低频 |
| **Human-as-a-tool** | 把人当成 agent 可调用的工具，遇不确定主动问 | agent 校准不好会问太多或太少 |
| **Approval flows** | 基于策略/角色的审批（RBAC/ReBAC、policy-as-code） | 审计更可辩护，但策略设计复杂，易瓶颈或漏审 |
| **Fallback escalation** | 低置信/失败/越权时**异步**升级到 Slack/邮件/看板 | 省人力，但**不可逆动作最好仍用同步阻断** |

## 四、审批策略的细分玩法（来源：StackAI）

可复用的审批工作流：**工具调用级 gate** / 内容草稿审批 / 双人规则 / 风险抽样 / 例外触发。
其中 **exception-only review** 是成熟后的方向：默认自动通过，只在低置信、敏感数据、异常参数、高风险分触发人审；**但若校验与日志不强，会变成「控制幻觉」**。

## 五、同步 vs 异步（来源：galileo.ai / Auth0）

- **同步审批**：适用于转账超阈值、删数据、改账户、公开发布等不可逆动作；核心是**可 checkpoint/恢复**，**执行前 gate 而不是事后补审**。
- **异步确认**：agent 发起授权后不必空等，人通过推送/邮件/短信后续批准；改善体验与吞吐，**但 compromise 时仍不能绕过显式批准**。

## 六、训练期 HITL vs 运行期 HITL（来源：StackAI）

- **训练期**：标注、纠错、偏好反馈 / RLHF —— 目标是改模型。
- **运行期**：防止当下动作造成真实影响 —— 强调「**谁批准了什么、为何批准**」的可追溯。

对项目含义：本项目全部落点是运行期 HITL（确认门）+ 表单系采集；不涉及训练期口径。

## 选型一句话（来源原文）

**外部可见/花钱/删改/不可回撤 → 同步 action gate，最好支持 edit；缺事实或歧义 → human-as-tool/提问；受合规/权限约束 → policy approval + 双人规则；规模化后 → confidence/risk 触发 fallback，低风险抽样或 exception-only，并持续看 approval latency、override rate、escalation volume 三个指标。**

## HITL vs 生成式表单：会话原表六维度对照（来源：分享会话第三轮）

| 维度 | 生成式表单 | HITL |
|---|---|---|
| 目标 | 把人脑里的信息变成结构化字段 | 在风险/不确定/责任节点上批准、修改、拒绝、补事实 |
| 发起方 | 通常是流程或用户主动发起 | 通常是 agent 执行到 checkpoint，被策略/置信度/风险规则暂停 |
| 没有这份输入时 | 表单没填完，流程不推进；但和「是否允许执行」未必有关 | **不该继续**：继续会产生外部副作用或违反授权边界 |
| 数据回传 | `form.submit(fields)` | interrupt outcome：approve / reject / edit / choose / provide / retry-guidance，并带审计上下文 |
| 关键约束 | 校验、默认值、动态字段、必填规则 | 原子性、幂等、并发锁、不可绕过、可恢复、可审计、决策归属 |
| 典型形态 | 问卷、录入页、动态生成的字段集 | 审批卡、工具调用 gate、Slack/邮件异步确认、dashboard veto |
| 责任含义 | 「你提供了这些信息」 | 「你批准/修改/拒绝了这次动作，因此副作用由该决策授权」 |

会话原口诀：**如果系统没有这个输入也能安全继续，那更像生成式表单；如果没有人类决策就不应/不能继续，那才是 HITL。**（与置顶用户直裁同向，用户直裁进一步把判据收紧为「是否在授权一个后果」。）

会话补充：五类里**补充缺失信息、选择方案、编辑后继续**经常长得像生成式表单，但本质是 agent 被暂停后等待一个可审计的 `resume/abort` 决策；**批准/拒绝、带反馈重试**常不是表单，只是决策按钮 + 理由。成熟做法是**把生成式表单当作 HITL 的一种 UI 承载，而不是把两者混成一个概念**——本仓按置顶裁决采纳更严的一半（表单系独立成轴，不算 HITL）。

## 对项目的落地修正

1. **徽章 / 状态语义分裂为两套**（本裁决最直接的施工面）
   - **表单系**（GF 的 FILTER/CLARIFY，及拟增的单选/多选询问卡）：`已提交` / `已取消`。「取消」= 用户没提交，语义是「没进流程」，**不是否决**。
   - **HITL 系**（确认门 start_export / import / publish / precheck）：`已批准` / `已不执行`。「不执行」是闸门裁决，带授权归属与审计责任。
   - 现状基线（HEAD a7b9ea7 实查）：回执徽标实词为 `✓ 已确认 / ✗ 已拒绝 / ! 已超时（作废）/ 已取消 / 执行中 / 执行失败`（`frontend/src/components/AiPanel/AiPanel.vue:2527` `hitlReceiptLabel`），工具卡九态词表为 `等待确认 / 调用中… / 已成功 / 执行失败 / 已拒绝 / 超出当前范围 / 已超时作废 / 会话已失效 / 已取消 / 结局未知`（同文件 `:2323` `toolStatusLabel`），表单族仅一处兜底文案 `表单已提交`（同文件 `:2584`）—— **两族词面尚未分裂**（门卡族吃「已确认/已拒绝」，正是需要改掉的那一半）。本裁决要求 S6 应用批按上表分裂，并同步改 demo 与断言。
2. **超时语义也分裂为两套：表单超时 ≠ 否决。**
   - 表单系超时 = 未提交，流程不推进，**无授权语义**，不得写「已拒绝 / 已不执行」；现有文案「已超时，表单不可再提交」（`frontend/src/components/AiPanel/FormRenderer.vue:151`）方向正确。
   - HITL 系超时 = 闸门未开 = 按**不执行**收尾（不可绕过），须与「用户主动不执行」区分展示；现实现「已超时作废」（本地倒计时归零 + 权威校正仍无结局）保留，归入 HITL 系超时族。
3. **demo 分组标注改「HITL 系 vs 表单系」**：`docs/demo/chat-ux/r165-chat-ui-v7.9.html` 场景清单等处现按「HITL 待批卡 / generative_form 表单卡」并列，改为两轴分组标注（**仅改标注，不改形态与量值**），下一轮 demo 修订随批。
4. **选型指引（新增门卡/询问卡的准入判据）**：外部可见 / 花钱 / 删改 / 不可回撤 → **同步 action gate，最好支持 edit**；缺事实或歧义 → **表单系提问**（GF FILTER/CLARIFY 或单选/多选询问卡），**不得升级成 HITL 门**；受合规 / 权限约束 → policy approval + 双人规则；规模化后 → exception-only（confidence / risk 触发）。
5. **挂账观察：三指标**（approval latency / override rate / escalation volume）—— 本项目当前无埋点，等规模化后接入；本件只登记口径，不本批施工。
