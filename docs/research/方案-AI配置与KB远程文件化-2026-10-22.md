# 方案 · AI 配置与知识库远程文件化（生产无表形态）

- 日期：2026-10-22
- 性质：**方案沉淀**。零代码改动、零 commit、零服务起停；**不构成施工承诺**，施工需用户另行发令
- 读码基点：`HEAD = 7b3db93`（= `origin/main`）；本件所有行号以此为准，不随码回头修订
- 自证（自身 wire `profile.bind`，`<KIMI_HOME>/sessions/<SESSION_ID>/agents/agent-1525/wire.jsonl`）：
  `{"type":"profile.bind","agentId":"agent-1525","modelAlias":"DeepSeek/deepseek-flash","profileName":"coder","thinkingEffort":"high"}`
  ⇒ model = `DeepSeek/deepseek-flash`、profile = `coder`、thinking = `high`
- 证据等级：**A** = 本仓代码/配置实读；**B** = 从代码推断但未实测（逐处显式标注）；**C** = 本件设计取舍
- 服务边界：全程未起停后端 8081 / 前端 5202，未占用两端口；只写本件与 `docs/research/README.md`

## 0. 背景与口径

### 0.1 需求原文（用户 2026-10-22）

> 「这次上生产没办法带上 AI 服务配置表结构（其他业务表不涉及），配置要放文件；知识问答的文档也放文件；文件是远程文件（需提供接口模拟远程）；不删既有 DB 方案，DB 模式继续可用。」

补充口径（同日）：

> 远程文件要**懒加载、可缓存（内存或 Redis）、能热更新**；可加一个更新文件的接口，但真实场景该接口在外部、我方无法得知文件何时更新，**只能定时检测**。

### 0.2 四条边界（本方案的全部前提）

| # | 边界 | 方案含义 |
|---|---|---|
| B1 | **不删既有 DB 方案**，DB 模式继续可用 | 文件源是**并列的第二实现**，不是替换。默认值仍是 `db`；file 模式的任何改动不得改变 db 模式的行为与既有测试断言 |
| B2 | **只有 AI 配置表带不上**，其他业务表不涉及 | 只处理 `ai_provider` / `ai_model` / `ai_setting` / `ai_config_audit` 四张表；其余表照常由 Flyway 建。**不**做"全库文件化" |
| B3 | 远程文件要**懒加载 + 可缓存 + 能热更** | 首次用到才拉；进程内快照即缓存；定时检测变化后走既有 `reload()` 通道生效。冷启动不因远端不可达而失败 |
| B4 | 更新接口**仅模拟** | 真实场景的文件更新方在外部，我方无法得知更新时机 ⇒ **定时轮询是唯一可靠的热更手段**；我方提供的 `PUT` 只是本地联调/演示用的影子端点，默认关闭 |

### 0.3 现状盘点（代码实读，A）

| 面 | 今天的样子 | 与目标的差距 |
|---|---|---|
| AI 配置真源 | `ai_setting['config.version']` 为版本真源，跨实例信号 `ai:cfg:ver`（`backend/src/main/java/com/example/configmgr/ai/config/AiConfigService.java:61`、`:197`） | 无文件源；无表即**无法启动**（JPA `validate` + Flyway V4） |
| 配置读取 | `AiConfigService.current()` 按 `app.ai.config.reload-interval`（缺省 1s）比对版本后 `load()` 全量读三张表（`:134`、`:236`） | 读取路径已是一个**可替换的装载缝**（返回 `ConfigSnapshot`），文件源可复用它 |
| 运行态重建 | `AiProviderRegistry.runtimeFor()` 以 `RuntimeKey = providerId \| keyFingerprint \| baseUrl \| completionsPath` 判等，真变化才重建连接（`AiProviderRegistry.java:119`、`AiConfigService.java:840`） | 机制**现成**，文件源只需产出正确的 `ResolvedProvider` |
| 写路径 | `AiConfigWriter` 一次写 = 数据行 + `config.version`+1 + 审计行，提交后 `INCR ai:cfg:ver` 并 `reload()`（`AiConfigWriter.java:60` 类注） | 文件模式下无表可写，写端点必须整体关闭或转只读 |
| KB 知识源 | `app.ai.kb.source=local\|http`（`backend/src/main/resources/application.yml:266`），`HttpKbSource` 已实现 ETag/`If-None-Match`/304（`ai/kb/HttpKbSource.java:31`） | **基本现成**：只需把 `base-url` 指向我方模拟端点 |
| KB 缓存 | `CachedKbSource` = Redis cache-aside + `SET NX PX` 单飞 + 版本号轮询（`ai/kb/CachedKbSource.java` 类注、`KbConfig.java:26`） | 现成，无需改 |
| KB 热更 | `KbService` 按 `refresh-interval`（缺省 10m）定时刷新 + `POST /api/ai/kb/reload` 手动重载（`KbService.java:142`、`AiKbController.java:43`） | 现成 |
| 模拟远端 | 无 | 需新增端点 |
| KB 表 | **零 DB 表**（KB 只有文件 + Lucene + Redis） | 无差距 |

结论：**KB 一侧是"换个 URL"的工作量，AI 配置一侧才是真工程**。本方案的重心在 §3.1 与 §4-B/§4-C。

### 1.6 KB：20 篇 Markdown + `manifest.json`

事实源：`docs/kb-samples/`（20 个 `.md` + `manifest.json`）、`ai/kb/KbManifest.java:18`、`KbDocMeta.java:31`、`KbTerm.java:20`。

`docs[]` 每项 **10 个字段**（全 20 篇齐备）：

| 字段 | 作用 | 备注 |
|---|---|---|
| `id` | 可读 slug，引用锚 | `kb_read_doc` 的入参；**引用格式 `[doc_id §章节]` 的左侧** |
| `title` | 标题 | 索引与目录 |

| `aliases` | 口头叫法/同义词 | 高权重召回，`kb_lookup_term` 也认 |
| `sha` | 正文 sha256 | 增量重建的唯一判据（"变了才重建该篇"） |

> 口径强调：**manifest 不只是文件清单**。`summary` / `tags` / `aliases` / `aliases_en` 直接决定召回与提示词目录，`terms` 是术语直答的答案源。把 manifest 当成"文件名表格"实现，会丢掉知识问答的一半能力。
>

### 1.8 KB 与 DB 的关系

**零 DB 表**。KB 全链路 = 文件（源）+ Lucene（索引，可再生）+ Redis（缓存，可再生）。这正是"知识问答的文档放文件"能低成本成立的原因——它本来就不在库里。

## 2. 目标形态

### 2.1 两个开关（互不耦合）

```yaml
app:
  ai:
    config:
      source: db            # db（默认，现行为不变） | remote-file
    kb:
      source: local         # local（默认） | http（指向任一符合 §2.2 契约的服务）
```

- 两个开关**独立**：可以 AI 配置走文件而 KB 走本地目录，反之亦然。
- 默认值保持 `db` / `local` ⇒ 合入后现网行为**零变化**，这是 B1 的硬约束。

### 2.2 远程文件契约（复用《知识库维护手册》§8.2，不新造协议）

事实源：`docs/知识库维护手册.md:150`（§8.2 服务端契约），四条原文口径：

1. `GET {base-url}/manifest.json` 返回清单 JSON，**建议带 `ETag`**；
2. `GET {base-url}/{file}` 返回 UTF-8 Markdown；
3. 支持 `If-None-Match`：未变化返回 **304**（不带 body），应用据此跳过整轮重建；
4. 鉴权头：应用把环境变量 `KB_HTTP_AUTH` 的值整段作为 `Authorization` 头发送。

本方案对 AI 配置文件沿用同一套 HTTP 语义（`ETag` + `If-None-Match` + 304），因为：

- `HttpKbSource` 已按此实现（`HttpKbSource.java:89`–`:95`），AI 配置侧照抄可共用一套联调脚本与桩；
- 真实外部文件服务通常只保证"能 GET"，**不保证**支持条件请求 ⇒ 方案必须同时准备 `sha256` 比对回退（见 §3.1）。

**文件布局（模拟远端根）**

```
<app.ai.files.root>/            # 缺省 ./data/ai-files，与上传件的 ./data/files 分开
  ai-config.json                # AI 配置（provider + 内嵌 model + settings）
  kb/
    manifest.json               # 即 docs/kb-samples/manifest.json 的同构件
    01-region-tariff.md
    ...                         # 20 篇
```

`<app.ai.kb.http.base-url>` 指向 `<模拟服务>/api/ai/files/kb` 即可直接复用现有 http 源。

**`ai-config.json` 形态（示意，字段与 §1 一一对应）**

```json
{
```

三条硬口径：

- 内嵌 `models[]` 只是 DB `provider_id` 外键的文件化表达，字段一个不少。

### 2.3 模拟远端服务：`GET /api/ai/files/{*path}`

挂在既有后端进程内（**不新开端口**），根目录 `app.ai.files.root`：

| 关注点 | 口径 |
|---|---|
| 路径变量 | Spring `{*path}` 捕获多级相对路径（`kb/manifest.json` 也能走同一端点） |
| 越界闸 | 解析后 `normalize()` 必须仍在 root 之下，`../`、绝对路径、盘符一律 404（与 `LocalDirKbSource.java` 的路径闸同口径） |
| ETag | 强 ETag = `"` + 内容 sha256 + `"`，由内容现算（不依赖 mtime，避免"内容没变但 mtime 变了"的假变更） |
| 条件请求 | `If-None-Match` 命中 ⇒ `304` + 空 body + 同一 `ETag` |
| Content-Type | `.json` → `application/json;charset=UTF-8`；`.md` → `text/markdown;charset=UTF-8`；其余按扩展名兜底 `application/octet-stream` |
| 缓存头 | `Cache-Control: no-cache`（可缓存但必须验证），`ETag` 恒在 |
| 存在性 | 目录、隐藏文件、非白名单扩展名一律 404（不列目录） |

### 2.4 更新接口：`PUT /api/ai/files/{*path}`（仅模拟）

| 关注点 | 口径 |
|---|---|
| 开关 | `app.ai.files.write-enabled`，**默认 false**；关闭时端点不注册（404，不暴露存在性） |
| 用途 | 仅在本地联调/演示里"假装外部系统更新了文件"，用来验证热更链路 |
| 写语义 | 同目录临时文件 + `ATOMIC_MOVE` 整体换入，杜绝"半份 JSON 被读到" |
| 校验 | 写前必须能按 §1 的结构解析成功，否则 400 且不落盘（防止把坏文件喂给热更链路） |
| 回执 | 返回新 `ETag` 与新旧 `version`，便于联调脚本直接断言"下一拍会变" |
| 与真实场景的关系 | **真实外部服务不会有这个端点**。它的存在不改变"只能定时检测"这一结论 |

## 3. 懒加载 / 缓存 / 热更设计

### 3.1 AI 配置：`RemoteFileAiConfigSource`

**装载缝**：`AiConfigService.load()`（`AiConfigService.java:236`）今天做三件事——查 provider、查 model、读 settings，然后拼 `ConfigSnapshot(version, providers, models, settings)`。文件源要产出的就是**同一个 `ConfigSnapshot`**，于是 `resolveDefault()` / `availability()` / `AiProviderRegistry` / `/health` / 设置页读取全部无需改动。

落地形态二选一（实现细节，不改结论）：

- (a) 在 `load()` 内按 `app.ai.config.source` 分派；
- (b) 抽出 `AiConfigSnapshotLoader` 接口 + `Db...` / `RemoteFile...` 两实现，`AiConfigService` 只依赖接口。

**时相（懒加载 + 内存缓存 + 定时热更）**

| 时相 | 行为 |
|---|---|
| 启动 | **不拉远端**、不碰 DB（file 模式）。应用照常起来；`/health` 首次被问到时才触发 |
| 首次 `current()` | 触发一次同步拉取（带 `app.ai.config.file.timeout`），成功则写进程内 `snapshot`；失败则 `snapshot` 为空 ⇒ 沿用今天的语义：`/health` 503 `AI_UNAVAILABLE`、聊天端点前置拒 |
| 稳态读 | 直接返回 `snapshot` 引用，**零 IO**；这就是"进程内快照即内存缓存" |
| 变化检测 | 单线程调度器每 `app.ai.config.poll-interval`（**建议 60s**，可配）比对一次：优先 `If-None-Match`（304 = 未变）；对方不支持条件请求时退化为**拉全文算 sha256** 与上次比对 |
| 检测到变化 | 走**既有** `reload()` 通道（`AiConfigService.java:154`）：解析 → 校验 → `applyLoad()` 原子换快照。失败保留上一份好快照并 WARN（与 DB 侧读库失败同姿态） |
| 连接重建 | 不新增逻辑：`AiProviderRegistry.runtimeFor()`（`:119`）以 `RuntimeKey` 判等，**只有 `keyFingerprint` / `baseUrl` / `completionsPath` 真变才重建**；只改 temperature 之类的 settings 不会重连 |
| 多实例 | 各拉各的，无广播、无租约、无共享缓存；允许最多一个轮询周期的漂移 |
| `ai:cfg:ver` | **文件模式停用**：不读、不写、不比对。`app.ai.config.reload-interval`（1s 的 DB 版本比对）同样不参与——文件模式的节拍由 `poll-interval` 单独决定 |
| 远端不可用 | 冷启动 = 不可用（空快照）；已有一份好快照 = **stale-if-error**，继续供旧配置 + WARN，不清空 |

**`version` 的来源**：优先文件里的 `version` 字段（单调递增由出具方保证）；缺失时用内容 sha256 的高位派生一个 `long`。它只用于"变了没变"的诊断显示，**不再**承担跨实例失效信号。

**`providerId` 与 `RuntimeKey` 的一处坑（B 级推断，施工必测）**：`runtimeKeyOf()` 对 `providerId == null` 一律拼成字面量 `"env"`（`AiConfigService.java:840`）。若文件模式的每个 provider 都拿 `null`，那么"换 provider 但 baseUrl/completionsPath 相同、key 指纹相同"就**不会**触发重建。处置：给文件模式的每个 provider 一个**按 `code` 稳定的合成 id**（如 `-(index+1)` 或 `code.hashCode()` 的稳定映射），使指纹仍能区分。这是实现注意点，不变更 §3.1 的结论。

### 3.2 KB：现成链路，零设计

| 环节 | 现成实现 | 切到模拟远端后的行为 |
|---|---|---|
| 拉清单 | `HttpKbSource` 带 `If-None-Match`，304 ⇒ `notModified` | 整份未变不重建索引 |
| 拉正文 | 按 manifest `sha` 判断哪篇要重拉 | 只重建变化的那篇 |
| 缓存 | `CachedKbSource`：cache-aside + `SET NX PX 30s` 单飞 + `kb:cache:manifest:version` 轮询 + stale-if-error | 多实例共享同一份字节；Redis 不可用降级直连 |
| 热更 | `KbService` 每 `refresh-interval`（缺省 10m）+ `POST /api/ai/kb/reload` 强制 | 改远端文件后，最迟一个周期生效；联调时可手动触发 |
| 鉴权 | `Authorization` 头只从 `KB_HTTP_AUTH` 读，不进日志 | 模拟端点可留空（内网回环） |
| 播种 | `LocalDirKbSource.prepare()` → `KbSampleSeeder.seedIfAbsent()` | http 源**不会播种**（无本地目录），符合预期 |

唯一需要新增的是"把 `docs/kb-samples/` 的 20 篇 + manifest 放进模拟远端根"这一件运维动作（§4-A-③），**代码零改动**。

## 6. 风险

### 6.1 两条启动崩溃面（**B 级：未经实测的推断**，施工前必须实跑）

| # | 面 | 推断 | 为什么现在无法实测 |
|---|---|---|---|
| R1 | `ddl-auto: validate` | file 模式下四张 AI 表不存在 ⇒ Hibernate 启动期 `SchemaManagementException`，应用起不来。必须靠 `ddl-auto: none`（profile 覆盖）或保留一份"空表占位" | 需在空库上起一次服务；本批禁止起停 |
| R2 | Flyway history | 三种组合行为不同：<br>(a) 空库 + 有 DDL 权限 ⇒ V1–V4 全建，AI 表被建出来（与"带不上表结构"的诉求冲突）；<br>(b) 空库 + 无 DDL 权限 ⇒ V4 失败，启动失败；<br>(c) 已应用 V4 的库切 file 模式 ⇒ 忽略 V4 会产生 `ignoreMigrationPatterns` 与 history 的交互（是否告警/是否要求 `outOfOrder`）需实测 | 同上 |

**处置建议**：施工第一步就做"空库 + 只读账号 + 已应用 V4"三态启动矩阵，结果回灌本件；在实测出结论前，**不要**把 `ignore-migration-patterns` 当成既定方案写进 yml。

### 6.2 文件模式多实例无广播（**知悉风险，非缺陷**）

各实例独立轮询 ⇒ 最多 `poll-interval` 的配置漂移；同一时刻两台实例可能用不同参数。`ai:cfg:ver` 停用后没有任何跨实例通知。这是 B4（外部更新、只能定时检测）的必然结果，**本方案不试图消除**，只要求：漂移窗口写进运维手册、诊断端点显示本实例的 `lastFetchedAt` 与 `version`，便于排障时判断"是不是还没轮到"。

### 6.3 其他

| # | 风险 | 说明 / 缓解 |
|---|---|---|
| R3 | 冷启动远端不可达 | 空快照 ⇒ AI 不可用但**应用可启动**（与今天"无 key"等价）。若要求"起得来还能用"，需在部署侧保证远端可达 |
| R4 | 真实外部服务不支持条件请求 | 已设计 sha 回退；但回退 = 每拍拉全文，配置文件大时成本上升。建议配置文件控制在 100KB 以内 |
| R5 | 文件泄漏面 | 文件只含 `key_ref: ENV`，**不含 key 任何形态**；仍需 `./data/ai-files` 不进版本库、不打进镜像层、日志不打印全文（只打印 version/sha 前缀） |
| R6 | KB manifest 与正文不同步 | 既有语义：`LocalDirKbSource` 实算 sha 与声明不符只 WARN 并以实算覆盖（`LocalDirKbSource.java` 类注）。http 源同理，靠 `sha` 判断增量 ⇒ 忘记更新 manifest 会导致"该重建的没重建"。运维手册需固化"改正文必改 sha" |
| R7 | 模拟端点与真实端点契约漂移 | 模拟端点支持 ETag/304，真实服务可能不支持。联调必须**两个分支都测**（有 ETag / 无 ETag） |
| R8 | 端口与服务纪律 | 模拟端点挂在既有后端进程内，**不新开端口**；本地联调一律走 8081，不占用前端 5202 |
| R9 | db 模式回归 | 所有条件装配必须默认"不存在该键即 db 行为"，否则会出现"没配新键反而变了行为"的隐性回归 |
