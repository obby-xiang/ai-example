# 上章 · 九项现值逐项对照

每项格式 = 本仓现值 → 业界现状（附出处）→ 评价 → 建议。

## 1. 一轮总预算 300s

**业界**：OpenAI / Anthropic SDK 对单次调用默认给 **600s** 超时（连接超时 5s），并没有「轮」的概念；Vercel AI SDK 提供 `totalMs` / `stepMs`，但**默认不启用**；Claude Code 不设回合上限，只设单工具 **120s / 600s** 超时；LangGraph 用**步数**（`recursion_limit`，长期默认 **25**，1.x 可调至万级）而非时间限制。

**评价**：**过严**。含 3~8 次工具往返的 agent 回合，常见耗时 5~15 分钟；300s 会频繁在中途被截断。

**建议**：将该上限提高到 **600~900s**，并补一层 `stepMs = 60~120s` 的单步限制，超出时降级为「收尾/部分完成」，不要直接判定整轮失败。

出处：[openai _constants.py](https://github.com/openai/openai-python/blob/main/src/openai/_constants.py) · [AI SDK streamText](https://ai-sdk.dev/docs/reference/ai-sdk-core/stream-text) · [Claude Code env-vars](https://code.claude.com/docs/en/env-vars)

## 2. 首字节 30s / 静默 90s / 重试 1 次且零退避

**业界**：两家 SDK 均为 **2 次重试（共 3 次尝试）+ 短指数退避**；Azure 官方答复建议客户端超时不低于 **600s**。健康 TTFT：非推理模型 P50 约 **0.3~2s**、P95 约 **2~3 倍 P50**（GPT-4o 实测 p95 **0.5s**）；推理模型 TTFT 可被 thinking 拉高 **5~30 倍**（**10~60s+**）。

**评价**：首字节 30s 对普通模型**过松**（是 P95 的数十倍），对推理模型**过严**；重试 1 次 + 零退避是**反模式**（零退避会放大重试风暴）。

**建议**：首字节 30s 按模型分档（普通 **15s** / 推理 **120s**）；重试 **2 次 + 0.5s/1s 指数退避 + jitter**，并在总预算内收缩。

出处：[anthropic _constants.py](https://github.com/anthropics/anthropic-sdk-python/blob/main/src/anthropic/_constants.py) · [Azure 默认超时问答](https://learn.microsoft.com/en-us/answers/questions/5552338/what-is-the-default-azure-openai-rest-api-timeout) · [llm-stats GPT-4o TTFT](https://llm-stats.com/models/gpt-4o-2024-08-06)

## 3. 流式无 socket read timeout（靠看门狗）

**业界**：SDK 的 600s 是 **httpx 的 per-read timeout**（每读一块重新计时），等价于容忍 600s 静默，并非总时长；生产惯例是「**细粒度 idle 看门狗 + 15s keepalive**」。AI SDK 已把它拆成 `firstChunkMs` / `chunkMs` 两档。

**评价**：**方向合理**，但只有「总静默 90s」一档，缺少首字节与帧间两档区分。

**建议**：补 `firstChunkMs ≈ 30s`、`chunkMs ≈ 90s`；socket 层保留 **300~600s** 兜底，用于回收半开连接。

出处：[AI SDK streamText](https://ai-sdk.dev/docs/reference/ai-sdk-core/stream-text) · [SSE 规范（keepalive）](https://html.spec.whatwg.org/multipage/server-sent-events.html)

## 4. 后端工具执行无独立超时

**业界**：MCP TypeScript SDK 硬默认 **60s**（`DEFAULT_REQUEST_TIMEOUT_MSEC=60000`），Python SDK 无默认（社区视为缺陷）；Claude Code Bash 默认 **120s**、模型可调到 **600s**；AI SDK 提供 `toolMs` 逐工具覆盖。

**评价**：**过松** —— 单个工具可吃掉全部 300s，且没有「工具卡死」的独立信号。

**建议**：默认 **60~120s**，长任务显式 opt-in（≤600s 或转后台异步任务 + 回执）。

出处：[MCP 60s 默认](https://www.codegateway.dev/en/blog/claude-mcp-tool-call-timeout) · [MCP Python 无默认超时](https://github.com/modelcontextprotocol/python-sdk/issues/1374)

## 5. HITL 人工审批无上限

**业界**：LangGraph 文档原文「**waits indefinitely** until you resume」；Step Functions `.waitForTaskToken` 最长可等 **1 年**（Standard 工作流配额），官方要求显式设 `TimeoutSeconds`；Temporal 支持无限期 durable wait，但建议显式超时；LangGraph 平台 checkpointer TTL 默认 **30 天**。

**评价**：**合理，且属主流**。「永不超时 + 持久化保底」正是业界做法；真正偏短的是 **24h 会话 TTL** —— 审批常跨天/周末。

**建议**：保留不超时；把「待审批态」的持久化寿命提到 **≥7 天**，另设可选 per-approval 过期（**24~72h**）做业务兜底。

出处：[LangGraph interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts) · [Step Functions（1 年）](https://docs.aws.amazon.com/step-functions/latest/dg/welcome.html) · [LangGraph TTL 30 天](https://dev.to/sudarshangouda/ai-agent-memory-part-2-the-case-for-intelligent-forgetting-4i48)

## 6. 前端工具 60s + 后端回执 120s

**业界**：MCP 60s、Claude Code 120s、AI SDK 逐工具 `toolMs` —— 60s 执行 + 120s 回执（2 倍余量）落在惯例区间内。

**评价**：**合理**。

**建议**：无需调整；若后端工具超时改为 60s，回执 120s 仍够，可把差值用于网络/序列化。

## 7. SSE 单帧 15s / 前端静默 90s 重挂 / 重连 2 次

**业界**：SSE 规范建议「**每 15 秒左右**发一行注释做 keepalive」（与 15s 完全一致）；但 nginx `proxy_read_timeout` 与 AWS ALB idle timeout 默认都是 **60s**，Cloudflare 约 **100s**；浏览器 `EventSource` 默认约 **3s 无限重试**，自研客户端惯例 **3~5 次**。

**评价**：15s 帧写 = 标准；**90s 静默判死与代理层不匹配**（先被 60s 掐断，成为死区）；重连 2 次**偏少**，易在一次抖动后彻底放弃。

**建议**：心跳保持 15s；静默阈值降到 **45~50s**（<60s 代理默认）；重连 **3~5 次、1/2/4/8s 退避 + jitter**，并配 `Last-Event-ID` 续传。

出处：[SSE 规范](https://html.spec.whatwg.org/multipage/server-sent-events.html) · [nginx/ALB 60s 默认](https://blog.authon.dev/why-your-llm-sse-stream-dies-after-60-seconds-and-how-to-actually-fix-it)

## 8. 取消标志 TTL 600s

**业界**：**无统一惯例**。可类比：Kubernetes 租约默认 **15s** 且**必须续期**；幂等键/回执缓存常 **24h**；通用经验法则 **TTL ≥ 1.5~2 倍最坏端到端墙钟**。

**评价**：**边界偏紧** —— 300s × 2 次尝试 + 排队/重连即可越过 600s，产生「取消已过期但执行仍在跑」的幽灵任务。

**建议**：提到 **900~1800s**，或改成「带心跳续期的租约」（执行中每 60s 续），正常结束/失败时显式删除。

出处：[Kubernetes Leases](https://kubernetes.io/docs/concepts/architecture/leases/)

## 9. 摘要 60s + Spring Retry 3 次无退避

**业界**：Spring Retry 的 `SimpleRetryPolicy` 默认正是 **3 次尝试、无退避**（项目与框架默认一致）；但业界共识是**指数退避 + jitter**（AWS Builders' Library），两家 LLM SDK 也是 2 次带退避。

**评价**：**60s 合理**（短摘要足够，远宽松于 SDK 的 600s）；**无退避是反模式**，3 次瞬时重试遇 429 会加剧限流。

**建议**：保留 60s；改 **2~3 次 + ExponentialBackOff**（0.5~1s 起、×2、上限 5s、加 jitter），并约束摘要重试总时长 ≤ 父预算的 **20%**。

出处：[SimpleRetryPolicy 默认 3 次](https://docs.spring.io/spring-retry/docs/current/apidocs/org/springframework/retry/policy/SimpleRetryPolicy.html) · [AWS: Timeouts, retries and backoff with jitter](https://aws.amazon.com/builders-library/timeouts-retries-and-backoff-with-jitter/)

**上章一句话结论**：9 项里 **6 项与业界一致或更保守**（1、4、8、9 的「时长」偏松/偏紧各半）—— 真正需要动的排序是：② 重试策略零退避（反模式）、① 总预算 300s（过严）、④ 工具无独立超时（过松）、⑦ 静默 90s 与代理 60s 死区、⑧ 取消 TTL 边界紧。⑤⑥ 属于业界标准做法，不必改（只需放宽 24h 会话 TTL 对「待审批」的约束）。

# 下章 · 挂起计时口径与取消信号保留期

证据类型标注：[文档] = 官方文档原文，[源码] = 源码实现，[推导] = 基于文档定义的必要推论。

## Q1 挂起后计时口径：逐对象

- **LangGraph**：只有步数预算，没有 wall-clock。`recursion_limit` 表示单次执行可跑的超步（super-step）上限，**默认 1000**；`invoke` 没有 timeout 参数。恢复后**不重置**，因为步数计数器保存在 checkpoint metadata 中，恢复时按 `step = saved.metadata.get("step", -1) + 1` 继续累计。[文档](https://docs.langchain.com/oss/python/langgraph/graph-api) + [源码 pregel/main.py](https://github.com/langchain-ai/langgraph/blob/main/libs/langgraph/langgraph/pregel/main.py) [源码]
- **Temporal**：分三级。`WorkflowTaskTimeout` 仅覆盖「worker 执行一个 Workflow Task」（默认 **10s**），SDK 注释明确写道「**this timeout is not related to the overall Workflow duration in any way**」—— 等待 signal 时没有 task 在跑，因此 task 计时不走；`WorkflowRunTimeout` / `WorkflowExecutionTimeout` 则是整段 run / 整条链的日历时长（后者「includes run retries and continue as new」），而 Open 状态的定义本身包含「waiting on something」，所以**等待期照样累计**。官方还反对用它做业务超时，建议用 Timer。[timeouts](https://docs.temporal.io/develop/python/workflows/timeouts) + [sdk-go](https://raw.githubusercontent.com/temporalio/sdk-go/master/internal/workflow.go) + [workflow-execution](https://docs.temporal.io/workflow-execution) [文档+源码]
- **AWS Step Functions**：`TimeoutSeconds` 从 `TaskStarted` 开始计时，原文是「Step Functions waits for a success or failure response ... within the specified TimeoutSeconds」；callback token 的等待发生在 TaskStarted 之后，因此**算在内**（默认 **99,999,999s**）。若没有设置 state 超时，则回调任务会一直等到 execution 上限 **1 年**，原文是「will wait until the execution reaches the one year service quota」。idle time 也是 1 年，并明确写着「constrained by maximum execution time」。[state-task](https://docs.aws.amazon.com/step-functions/latest/dg/state-task.html) + [connect-to-resource](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html) + [limits](https://docs.aws.amazon.com/step-functions/latest/dg/limits-overview.html) [文档]
- **Vercel AI SDK**：`totalMs` 表示「整个 call 含所有 steps」；`stepMs` 表示「每个完整 step，含模型生成、重试与 local tool 执行」，并且这两个预算「remain active across retries and local tool execution」—— **都算，不豁免**。二者都属于 per-call 的 RequestOptions（abort），而人工审批的挂起/恢复由 `WorkflowAgent` 的 durable suspend/resume 承担（「approvals suspend and resume durable workflow execution」）；也就是说，暂停期间没有任何 call 在计时，**恢复即是新调用、新时钟**（推导）。[settings](https://ai-sdk.dev/docs/ai-sdk-core/settings) + [tool-approvals](https://ai-sdk.dev/docs/agents/tool-approvals) + [AI SDK 7](https://vercel.com/blog/ai-sdk-7) [文档，最后半句为推导]
- **Claude Code**：只有 `--max-turns`（仅限 print 模式，默认无限制）和 `--max-budget-usd`（金额预算），没有轮级 wall-clock；权限确认没有时钟可停，因此不存在「重置」问题。[cli-reference](https://docs.claude.com/en/docs/claude-code/cli-reference) [文档]
- **OpenAI Agents SDK**：`max_turns` 按步数计算（`None` 表示不限）；`ModelSettings.timeout` 只作用于单次 model call（`ModelTimeoutError`），工具超时是独立的 `ToolTimeoutError`。HITL 暂停后从 `RunState` 再次调用 `Runner.run` 属于新一次 run，没有跨暂停的墙钟。[running_agents](https://openai.github.io/openai-agents-python/running_agents/) [文档]
- **CrewAI**：只有 `max_execution_time`（秒，墙钟）/ `max_iter`（轮数），文档没有给出「HITL 等待是否扣除」的口径，实际按墙钟计 —— 包括 `human_input` 阻塞等待在内。[concepts/agents](https://docs.crewai.com/en/concepts/agents) [文档]
- **AutoGen**：终止条件是消息数/文本（`MaxMessageTermination`、`TextMentionTermination` 等），没有轮级墙钟预算。[termination](https://microsoft.github.io/autogen/stable/user-guide/agentchat-user-guide/tutorial/termination.html) [文档]
- **旁证（明确选「停表」的一类）**：Inngest 原文「A wait does not keep a worker running, and your compute will entirely pause during the wait」，超时靠 `waitForEvent` 的显式 timeout 表达。[inngest](https://www.inngest.com/docs/learn/how-functions-are-executed) [文档]

**有无共识**：**没有**。业界分成两派，而且分界清晰 ——

- (a) **编排/持久化引擎**（Temporal、Step Functions、Inngest）：总时长按墙钟累计，挂起不「停表」，靠显式的业务 deadline（Timer、`waitForEvent` timeout、`HeartbeatSeconds`）来兜，并且都劝告你别把总超时当业务超时用；
- (b) **调用/轮次型 SDK**（AI SDK、OpenAI Agents SDK、Claude Code、AutoGen）：根本没有跨暂停的墙钟，只有单次调用预算或步数预算，恢复即新时钟。

**唯一真正无争议的是步数类预算**（LangGraph `recursion_limit`、`max_turns`）：**一律继续累计，绝不重置**。

## Q2 取消信号 / 标志的保留期

- **gRPC / HTTP**：说法成立。cancel 是调用/流级的一次性信号（deadline 到期或 I/O 错误也会触发），服务端 handler 必须自己周期性检查「cancelled?」并停止；它既不落盘，也没有 TTL 概念，流/连接结束即消失。[grpc.io cancellation](https://grpc.io/docs/guides/cancellation/) [文档]
- **Temporal**：取消不是「标志」，而是往 Event History 写一条 **`WorkflowExecutionCancelRequested`** 事件，永久可查；terminate 写 `WorkflowExecutionTerminated`。取消请求是持久的，且可以被 workflow 代码处理。[workflows/cancellation](https://docs.temporal.io/develop/python/workflows/cancellation) [文档]
- **AWS Step Functions**：`StopExecution` 后执行关闭，**执行历史保留 90 天**（可申请缩到 30 天），过期后「you can no longer retrieve or view the execution history」；redrive 窗口为 **14 天**。即：取消状态终态可查，但有期限。[limits](https://docs.aws.amazon.com/step-functions/latest/dg/limits-overview.html) [文档]
- **Kubernetes**：删除是 `deletionTimestamp` + grace period（`terminationGracePeriodSeconds` 默认 **30s**），finalizer 挂住对象直到清理完成；Lease 用 `leaseDurationSeconds` / `renewTime` 表达 TTL，apiserver 的过期 Lease「garbage collected ... after 1 hour」。[pod-lifecycle](https://kubernetes.io/docs/concepts/workloads/pods/pod-lifecycle/) + [leases](https://kubernetes.io/docs/concepts/architecture/leases/) [文档]
- **Tombstone 保留期的权威表述**：Cassandra 的 `gc_grace_seconds`（默认 **864000s = 10 天**），tombstone 必须活过「所有副本可能失联/未 repair」的窗口 ——「If a node remains down or disconnected for longer than gc_grace_seconds, its deleted data will be repaired back ... and reappear」，即删除会被复活。[cassandra tombstones](https://cassandra.apache.org/doc/latest/cassandra/managing/operating/compaction/tombstones.html) [文档]
- **AWS Builders' Library（最接近「要活到所有引用者消亡」的原文）**：「it's impractical to retain that knowledge indefinitely ... We have found that, for EC2 instances, it works to **limit the time period to the lifetime of the resource, plus an interval after which it is reasonable to assume that any late arriving requests would either have arrived or would no longer be valid.**」[builders-library](https://aws.amazon.com/builders-library/making-retries-safe-with-idempotent-APIs/) [文档]
- **幂等键对照**：Stripe API v1 幂等键「you can remove keys ... after they're at least **24 hours** old」，清除后复用同一个 key 被视为新请求；Redis 用 `SET key val NX EX <seconds>` 的显式 TTL 是同一套惯例。[stripe](https://docs.stripe.com/api/idempotent_requests) + [redis SET](https://redis.io/docs/latest/commands/set/) [文档]
- **LangGraph / LangSmith**：run 与 thread 状态本身持久，保留期由 `checkpointer.ttl` 配置（示例 **43200 分钟 = 30 天**），「**If omitted, threads do not expire by default**」，且 `delete` 策略「does not refresh with activity」（取消后的 thread 不会被后续活动续命）。[configure-ttl](https://docs.langchain.com/langsmith/configure-ttl) [文档]

**有无共识**：**有，而且分两层**。

- **传输层**的 cancel 是瞬时、连接/流级的信号，从不落盘，因此没有「保留期」（gRPC 的口径可确认为行业默认）。
- **编排层**的 cancel 一定落成一条永久事件或终态记录（Temporal 事件、SFN 执行历史、LangGraph thread 状态），保留期由产品策略给定：SFN **90 天**、LangGraph 默认**不过期**（可配 30 天）。
- 「防止复活」的那类标志（tombstone / 幂等键 / Lease）的保留期公式是公认的：**资源寿命 + 最大迟到请求窗口** —— Stripe 取 **24h**、Cassandra 取 **10 天**、K8s Lease 取 **~1h** 级、AWS 的说法是「resource lifetime plus a reasonable late-arrival interval」。类比到 Agent 的取消标志，业界落点就在 **24h–30d** 这个区间，往 24h 靠是「重试语义」取向，往 30d 靠是「审计/可追溯」取向。

**未覆盖 / 存疑**：Temporal 的「run timeout 是否把等 signal 的时间算进去」没有找到一句逐字原文，上面的结论由三处官方定义合成（Run 时长定义 + Open 状态含 waiting + task timeout 与总时长无关），属于强推导而非原句引用；CrewAI 的 HITL 是否扣除等待时间属于文档空白（按实现是墙钟），若要写进设计文档建议标注为「框架未定义」。

## 下章对本仓的直接含义（整理者归纳，非原文结论）

1. **步数类预算不重置是有共识的**（LangGraph / `max_turns` 一律累计）⇒ 步数上限必须跨挂起累计，不能随段重置。
2. **时间类预算在「调用型」架构里恢复即新时钟**（AI SDK 的 durable suspend/resume 语义）⇒ 段级重置在业界有先例，属可采纳路线，但必须与「步数不重置」配对，否则挂起可被用来无限续命。
3. **传输层取消信号本就不落盘、无 TTL**（gRPC 口径）⇒ 取消标志随连接/会话消亡符合传输层惯例；若要「取消后不可复活」，则须落成永久事件或终态记录（编排层惯例），二者是不同取向，不能只说一半。
