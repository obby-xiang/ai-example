性质：只读代码分析、用户提供的真实界面样本与官方资料调研；未复现、未修改生产代码、未执行新测试。

## 1. 输入与证据边界

用户提供了同一“创建导出配置任务”流程的两组界面样本，包含以下事实：

- 一条用户指令后出现重复的文字追问、重复助手内容和大批过程卡。
- 第二组样本中，整段流程出现两个版本；两个版本不仅重复，而且卡片和部分正文数量不同。
- 最终出现启动确认，但正文又重复询问“请确认是否启动导出”。
- 卡面出现“筛选条件未决定，由宿主收集一次”“将导出 4 个配置定义 · 影响面暂不可估”等文案。
- 多张不同用途表单均显示“请填写以下信息”；同时出现“跳转页面”“确认步骤”等过程卡。

本文把结论分为三类：

1. **界面事实**：用户样本直接可见。
2. **代码事实**：当前工作树可定位的实现。
3. **待证根因**：由代码路径推导，必须取得同一故障会话的镜像、history、SSE 和 DOM 后才能确认。

没有故障会话的原始 session/run 证据，因此本文不把“镜像合并”宣称为已经动态证实的唯一根因，也不排除后端重复落账、SSE 重放或快照重复重建。

## 2. 问题总账

| 类别 | 界面事实 | 影响 |
|---|---|---|
| 重复与分叉 | 整轮内容重复，两个版本的正文和卡片数量不同 | 用户无法判断哪份是真实流程，属于正确性问题，不只是视觉瑕疵 |
| 创建入口 | 明确创建指令后先反复文字追问配置、条件和标题 | 违反直接创建确认和一轮闭环规格 |
| 流程呈现 | 文字询问、表单、过程卡、正文汇总重复承载同一事实 | 对话被切碎，增加心智负担 |
| 内部过程泄露 | 导航、步骤推进、宿主收集、影响面未知等实现概念上屏 | ToC 用户读到开发/编排语言 |
| 动态文案 | 空字段、未知值、公式化说明和中英技术词混用 | 信息价值低，模糊担忧增加 |
| 确认渠道 | 正文要求确认，HITL 卡又要求确认 | 用户不知道应回复文字还是点击按钮 |
| 刷新恢复 | 用户实际样本显示恢复后内容重复且版本不一致 | 现有刷新回归没有有效覆盖该故障形态 |
| 验收方法 | 部分脚本有 PASS，但真实浏览器内容仍有明显错误 | 状态/退出码不能替代内容和界面验收 |

## 3. 代码链路分析

### 3.1 镜像与历史使用不同的身份和粒度

代码事实：

- 实时 SSE 已携带稳定 `messageId = "assistant-" + runId`，见 `backend/src/main/java/com/example/configmgr/ai/run/SseChatEmitter.java:663-667`、`:824`。
- 历史展示消息 ID 却由 `history-${idBase + index}` 生成，且明确不消费后端 `messageId`：`frontend/src/stores/ai.ts:5458-5462`。
- 同 run 的连续 ASSISTANT 会在历史构建后置 pass 中合并：`frontend/src/stores/ai.ts:5486-5591`。
- 镜像恢复以 runId、消息 ID 和 toolCallId 匹配：`frontend/src/stores/ai.ts:5758-5816`。
- 镜像助手找不到目标时，会按镜像顺序克隆并插入：`frontend/src/stores/ai.ts:5875-5915`。
- 匹配工具只读取 toolCallId；没有工具段的纯文本助手无法靠该强身份匹配：`frontend/src/stores/ai.ts:3389-3409`。

**待证根因 H1：**本地镜像可能有多条同 run 助手，而历史侧已合并成一条或重新分配了 `history-*` ID；当部分镜像助手无法匹配时，克隆插入会形成第二份流程。两个来源包含的进度不同，可解释“重复且版本不同”。

需要验证的反证/替代根因：

- history 本身已含重复 ASSISTANT；
- 实时帧与快照恢复重复建卡；
- SSE 全量重放未清空同 run 旧现场；
- DOM 分组或 key 导致同一消息重复渲染。

### 3.2 恢复语义同时存在缓存与第二事实源风险

`loadHistoryInner` 先物化镜像，再读取 history，并调用 `mergeMirrorInFlightRound`：`frontend/src/stores/ai.ts:4923-5023`、`:5117-5126`。

设计上镜像是 last-good 缓存，但未匹配内容又可插回权威历史结果，这使镜像实际上参与构造第二份事实。当前代码还使用正文前缀、同 run、位置等启发式关系判断覆盖与合并，身份规则并不单一。

### 3.3 创建规则存在，但模型行为仍越界

`backend/src/main/resources/ai/tools.yaml:131-150` 已明确：

- 创建时直接调用 `create_task`；
- 不先追问配置项、筛选条件或标题；
- 未明确限制后续时默认完整续接；
- 在同一 run 完成配置、条件和启动确认。

`PromptRulePacks.java:31-48` 也有同类规则。

**代码事实结论：**继续堆叠同类提示词不能构成可靠修复。必须保存实际模型请求、披露工具和首次输出，判断是规则未进入请求、工具未披露、模型未遵守，还是前后续状态误导。

### 3.4 自动过程卡的可见性过宽

`frontend/src/components/AiPanel/AiPanel.vue:3499-3510` 的 `shouldShowToolPart` 主要过滤系统拒绝幻影、部分 skipped/blocked 状态。普通成功的 `navigate_to`、`select_definitions`、`confirm_step` 没有统一的静默呈现规则。

`SILENT_SUCCESS_UI_EVENTS` 只静默工作区回执，不等于隐藏对话工具卡，不能混用两个概念。

### 3.5 动态垃圾文案有直接代码来源

- `ToolPreflightService.java:643`：固定生成“筛选条件未决定，由宿主收集一次”及英文对应句。
- `ToolPreflightService.java:218`：固定 `IMPACT_UNKNOWN = "影响面暂不可估"`。
- `ToolPreflightService.java:1290-1295`：导出影响面拼接“将导出 N 个配置定义 · 影响面暂不可估”。
- `ToolPreflightService.java:670-674`：仍存在“创建≠执行，不启动作业”。
- `frontend/src/locales/zh-CN.json:384`：通用表单标题“请填写以下信息”。
- `AiPanel.vue:3952-3959`：表单卡头可回落到该通用标题。

因此，这部分不是模型自由发挥，而是后端/前端正式文案和兜底设计失误。

### 3.6 测试文档不等于执行覆盖

`docs/verification/AI对话独立复测清单-2026-11-05.md:500` 标明 C-111～C-129 全部 NOT_RUN。已有刷新场景覆盖流式、表单、HITL、连续刷新和历史乱序，但：

- 没有形成“创建导出完整流程 × 每个事件边界 × 任意刷新时机”的矩阵。
- 没有要求每次都比较完整正文、消息数、卡片数、顺序、动态字段和 DOM。
- 没有逐工具、逐动态字段枚举空值、未知值和中英文兜底文案。
- 脚本的 `PUBLIC_API_SSE_ONLY` 范围不能外推为浏览器整项通过。

## 4. 业界官方调研

### 4.1 稳定身份和完整 UI 消息持久化

Vercel AI SDK 的[消息持久化文档](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-message-persistence)指出：需要持久化时，应使用在存储前已经稳定的 ID，避免恢复后的 ID 冲突；推荐保存包含工具及自定义 parts 的 UI 消息，并在处理前验证。

**对本项目的启示：**不能用本地临时 ID、传输 ID 或数组下标承担跨实时/镜像/history 的身份；优先复用 runId、entryId、segments 和 toolCallId。

### 4.2 全量重放与增量续传必须分清

Vercel 的[可恢复流文档](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-resume-streams)说明：默认全量重放会在 start 时重置被中断的回答并重建，避免 text、reasoning 和 step parts 重复；只有明确增量续传时才保留旧现场。刷新与显式停止也应分开。

**对本项目的启示：**刷新后的全量恢复与活连接的 seq 增量续传不能混成“镜像和历史双向猜测合并”。

### 4.3 幂等键、顺序和副作用

Azure 的[Idempotent Consumer](https://learn.microsoft.com/en-us/azure/architecture/patterns/idempotent-consumer)要求使用跨重投稳定的逻辑消息标识，不能用共享 correlationId、传输 ID 或接收时间代替；去重不保证顺序，还需 sequence/version；重复处理不得产生额外副作用。

**对本项目的启示：**runId 只是轮次边界，不足以唯一标识多条助手和段落；UI 幂等与工具/任务/作业副作用幂等必须分别验证。

### 4.4 Agent checkpoint 与完整事件历史不是同一需求

[LangGraph Checkpointers](https://docs.langchain.com/oss/python/langgraph/checkpointers)在步骤边界保存状态，支持中断、人工介入和故障恢复。[Temporal Event History](https://docs.temporal.io/encyclopedia/event-history)以完整有序历史 replay 持久工作流。

这些是长流程 Agent/工作流的主流做法，但普通聊天 UI 不必把所有草稿、展开状态和按钮都事件化。全量重写不是本项目当前必需。

### 4.5 用户内容与渐进披露

[Testing Library](https://testing-library.com/docs/)强调测试应接近用户实际看到和操作的界面，而不是内部实现状态。

Nielsen Norman Group 的[渐进披露](https://www.nngroup.com/articles/progressive-disclosure/)要求首屏只呈现当前任务必需的信息；[简洁、可扫描、客观文案研究](https://www.nngroup.com/articles/concise-scannable-and-objective-how-to-write-for-the-web/)支持减少无价值、宣传式或冗长内容。

**对本项目的启示：**自动成功过程通常应静默；文案和卡片是否必要必须经真实界面内容验收，而不是只检查 run=DONE。

## 5. 方案比较与结论

| 方案 | 内容 | 优点 | 风险/缺点 | 结论 |
|---|---|---|---|---|
| A 表面修补 | 改提示词、几句文案、再加一个去重条件 | 快、局部 | 根因和身份体系仍在，容易在其他流程和刷新时机复发 | 不单独采用 |
| B 现有链路收敛 | 统一身份、全量/增量恢复、宿主流程、动态文案和内容门禁 | 复用现有 Redis/SSE/history/parts，范围可控 | 需要认真迁移镜像兼容和关联审查 | **推荐** |
| C 全事件驱动重写 | 命令、事件日志、投影、快照全部重建 | 长期一致性强 | 协议、迁移、测试 blast radius 大，不符合稳定节制 | 当前不采用 |

方案 B 的批次：

1. 证据确认：同会话保存 history/run/SSE、脱敏镜像、DOM 和真实模型请求。
2. 恢复收敛：稳定 entry/part 身份；全量重建与 seq 增量幂等；镜像只做缓存。
3. 流程收敛：宿主确定性推进，已知信息不问，自动成功过程静默，同轮启动确认。
4. 文案收敛：按工具、用途和 locale 集中治理动态文案、空值和未知值。
5. 验收收敛：刷新事件矩阵、完整内容对账、业务副作用和独立审查证据。

## 6. 审查结论

后续审查必须同时回答：

- 代码为什么这样改，根因证据是什么；
- 同一消息/段落/工具在实时、镜像、history 中如何保持同一身份；
- 未匹配镜像为什么不会复制或丢失整轮；
- 同一事实由哪个界面元素表达，其他重复表达是否删除；
- 用户是否仍需第二次聊天输入完成本可一轮完成的流程；
- 所有动态文案、空值和兜底是否符合 ToC；
- 审查者是否亲自比较了实际内容，而非只读 summary.status；
- 哪些场景仍然 NOT_RUN，是否被错误外推为 PASS。
