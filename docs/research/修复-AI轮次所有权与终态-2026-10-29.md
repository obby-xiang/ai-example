## 二、口径与判据（为什么这样改）

### 2.1 首轮为什么要「与续跑一致的」所有权与心跳

- **同一条租约键**：`ai:lease:run:{run:<runId>}` + 同一个 fence 键（三键同槽脚本，`LeaseService#ACQUIRE_SCRIPT`）。
  首轮与续跑若各用一套，写回权限（`RunStore#persist` 的 fence 写）与出帧/认领/台账的写门（`RunStore#permittedToWrite`）
  就会对首轮静默退化成 plain SET —— 而 plain SET 正是「换主后的旧驱动能覆盖新主人终态」的入口。
  **注意**：首笔快照本身仍是 plain SET —— 租约在 `store.create` **之后**才取（`ResilientChatService.java:657` vs
  `:536`），只有其后的写才带 fence。首轮持租**不改变**首笔快照的写入口径。
- **同一条心跳**：`LeaseService#markDriving(lease, alive)`，`alive = 本进程仍登记着这一轮的驱动方 && 快照非终态`。
  于是驱动线程异常退出/轮次收尾后，下一拍即停续租并还租 —— 不会留下永远续租的僵尸租约；
  而长预检/首包等待期间租约始终有效 ⇒ 跨实例判活看到 `leaseHeld=true`，**不会**判死接管。
- **「抢不到就不驱动」**：`HELD_ELSEWHERE` 说明这一轮已被别的实例持有；本线程继续跑就是双驱动。
  终态与终帧归持有方。（**如实**：本分支返回后 `AiController` 的 `finally` 仍会 `runRegistry.close(runId)` 收掉本连接，
  它并不是"照常收流"；该 runId 为全新 UUID 时此分支实际不可达 —— 复审 M-3，本批未改，见 §七。）
- **「谁创建谁释放，重入不释放」**：`releaseDriveOwnership` 只在 `created==true` 且本进程 epoch 仍等于该租约时还租。
  终态写与 park 交棒都已还过租，那之后租约可能属于**下一任**，无条件还就会删掉别人的续跑权
  （与 `LeaseService.AcquireResult#created` 的既有裁决一致）。

### 2.2 接管复核为什么必须"抢租前 + 与 fresh 绑定"

租约拦得住**跨实例**，拦不住**同实例**：`LeaseService` 的抢租对同一 owner 是可重入的（`created=false`），
运行期扫描/启动扫描拿到的就是首轮/确认门持有的那一任。`ResumeService.resuming` 只覆盖续跑驱动方，
首轮没有对应登记 —— 本批补的就是首轮那一份登记（`drivingRuns`），并作为复核的第一条证据；
第二条证据是**业务活动锚点**（心跳不算业务活动，R1-09 既有口径）。

**但"拒绝"本身也要看是谁夺的租**（复审 M-1）：

- 抢租成功会把 fence 推到新 epoch（`fresh=true`，`created` 来自 Lua 返回位）。此时若再"拒绝 + 还租"，
  净结果是「fence 已推进 + 租约被删 + 无人驱动」—— 原驱动的写从此被它自己的丢租判据挡住，
  而也没有别人在推这一轮。这比"不接管"更糟。
- 所以复核拆成两层：**抢租前初检**（活驱动 + 仍持租 / 业务仍前进 ⇒ 什么都不动地拒绝，
  `takeoverPreCheck`）；**抢租后复核**只对 `!fresh`（同主重入）拒绝 —— 那时租约属于活着的驱动方，
  拒绝不改任何状态。
- **同实例的 `fresh` 也不能接管**（返修 R2，推翻 R1 的"fresh 一律接管"）：同一进程内两个驱动方共享
  同一份租约视图（`key+owner` 记账），新起接管驱动抢到的新 epoch 会把<b>旧驱动后续的写一起放行</b> ——
  等于双驱动。故 `isDriving && lease != null` 时改为<b>重挂租约</b>：不新起驱动，
  `stopDriving` 摘掉可能仍是旧 epoch 的续租任务后再 `markDriving(lease, 旧驱动存活判据)`，
  返回 `ALREADY_RUNNING + leaseRearmed`，后处理<b>不得还租</b>。
- **跨实例（`isDriving=false`）的 `fresh` 规则不变**：fence 能真正隔开两个进程，fresh 抢到的驱动
  接管，旧进程的写被 fence 拒绝。

### 2.3 终帧判据：按驱动分段；并**不**声称跨实例原子

**口径（本批实际做到的）**：同一 runId 可能被驱动多次（`retry-model-step` 把 FAILED 轮改回 RUNNING 再驱动，
归档不清理、也不追加代次）。因此失败出口的幂等判据必须是「**本次驱动**入口之后的终帧」：
`chat` / `driveResumed` 入口调 `beginDrive()` 记一次归档末号作为下界，失败出口只认 `seq > 下界` 的 done/error。
=> 挡的是：
1. **同一驱动内的顺序重复**（先落了终帧，随后另一条失败出口又想补一条）；
2. **同一 runId 的相邻驱动之间**的误判（上一次的 error 不再吞掉这一次的失败终帧）。

**本批**不**做到的（如实，不声称根治）**：
- **跨实例并发**下"终帧恰好一条"仍<b>没有</b>保证。判据是"读 → 判 → 发"，不是与归档同事务的 CAS；
  两个实例可以同时读到"没有终帧"并各发一条（窗口窄但存在）。
- 既有的写门（租约 / fence）在"终态写已还租"之后对<b>终帧这一笔</b>不设防
  （`persist` 在终态分支先 `releaseRunLease`，之后 `heldRunEpoch == 0` ⇒ `permittedToWrite` 直接放行、
  不读 fence；成功归还还会清掉墓碑 ⇒ `authority = NEVER_HELD`）。因此本批的注释与文档<b>不</b>把
  "写门会再拦一次"当兜底，也不写"跨实例恰好一条"。
- 要把跨实例做实：需要**原子终帧位**（与 fence 同事务的条件写，例如把"终帧已落"并入 fence Lua，
  或 `HSETNX` 式终帧占位）。本批<b>未实现</b>，登记为后续协议项（见 §七）。
- **取消收尾**仍按"整轮归档有没有终帧"判幂等（`terminalFrameArchived()`）：同类"跨代次误判"在同一路径上
  理论上仍存在（重试后取消），本批未改（避免扩散），登记为已知残余。

## 七、边界与不声称

- **未跑**：后端全量（`mvn -o test`）、前端任何命令、E2E（`scripts/verify-e2e.ps1`）、主 CI。
  本文所有 GREEN 都是**精确单点**（§四）或**点名类回归**（§五）的结果，不构成「后端全绿」；
  回归面不当单点证据用。
- **文档门禁**：`node scripts/ci/check-docs.mjs` 在**提交前对暂存区**跑过并通过 **6/6**（本轮返修后再次通过）；
  它只覆盖文档一致性/命名纪律，**不覆盖**代码正确性。
- **跨实例"终帧恰好一条"未做**：判据是"读 → 判 → 发"，不是原子协议；要拿这个不变量必须做原子终帧位
  （与 fence 同事务的条件写 / `HSETNX` 式占位）。本批**未实现**，见 §2.3。
- **同实例"重挂租约"的语义边界（R2）**：重挂只保证"不新起驱动、不还租、续租交给仍在跑的旧驱动"；
  它**不**保证旧驱动一定跑得完 —— 驱动线程若已卡死，存活判据（`isDriving`）会一直为真直到线程退出，
  这一轮要等线程结束（或进程重启）后由扫描接管。这是刻意的方向选择：宁可晚一拍，也不制造双驱动。
- **公开带租重载**（`resume(runId, forceTakeover, lease)`）不替调用方还租、也不重挂；
  同一 (key, owner) 的 `markDriving` 由 `computeIfAbsent` 保证幂等，不会起第二个心跳。
- **取消收尾仍按整轮归档判幂等**：重试后再取消的跨代次误判理论上仍在，本批未改（不扩散）。
- **未做双实例/真机演练**：1a/1b/M-1 的跨实例时序（旧主人还在驱动、新主人已抢到）只有单测级证据
  （两个 `LeaseService` 视图 + 可控 `FakeRenewScheduler`），**不是**真进程级证据。
- **驱动登记只在首轮 `chat` 登记**：续跑驱动方仍靠 `ResumeService.resuming`（既有），本批未改动。
  `isDriving` 表示"线程还在"，因此初检额外要求"仍持租"——只看登记会把"丢了租的僵线程"当成活主人。
- **`RunStore.create` 的显式判定只落在生产实现**：`InMemoryRunStore`（测试替身）的 `create` 未同步抛错
  —— 替身是夹具，若同步会让大量既有用例改变语义；生产路径唯一。走替身的首轮用例因此发现不了该语义回归。
- **失败出口的归档读**：`terminalFrameArchivedSinceDriveStart()` 是**差量读**（`afterSeq = 下界`），
  比"整轮全量读"小；取消收尾仍用整轮读（`terminalFrameArchived()`）。读降级时失败出口各打一条 WARN。
- **`PerDriveTerminalFrameTest` 走的是"真实 `RunStore` + `ai:events:` LIST 兼容口径"**（`RunRegistry` 三参构造
  → `RunStoreFrameStore`）。生产装配的 **Redis Stream 读路径（`RedisFrameStore`）没有在本批单测里跑**：
  两条路径的 `readFrom(afterSeq)` 语义同源（都按 `seq > afterSeq` 差量），但"生产 Stream 实现未被本批用例覆盖"
  这一事实必须如实登记（真机 RM-05 是它的验证面）。
- **首轮持租的行为变化（需知）**：首笔快照仍是 plain SET；**租约取得之后**的写走 fence（与续跑一致）。
  租约设施不可确认时首轮会转只读（写口 `UNAVAILABLE`）；**没有租约设施**（单测/降级装配）时写口是
  `NEVER_HELD` ⇒ **放行**，此时本批的 fencing 语义不参与（不能说"写口 fail-closed"）。
- **新增的只有 body 键**：`resume` 的拒绝仍复用 `Outcome.ALREADY_RUNNING`（对外 409 语义不变），
  新增 `reason=DRIVER_ALIVE_IN_PROCESS` / `ACTIVITY_ADVANCED` 与 `driverAlive`。
- **复审 M-3（未改）**：`chat()` 的 `HELD_ELSEWHERE` 分支注释原写"本连接照常收流"，实际 `AiController`
  的 `finally` 会 `runRegistry.close(runId)` 收掉连接；该分支对全新 UUID runId 基本不可达。本批只订正本文
  与注释口径（§2.1），**代码行为未改**（不在本轮授权面内）。
- **共享方案文档未改**（`docs/决策看板.md` / `docs/任务看板.md` / 设计稿）；本文与 `docs/research/README.md`
  索引为唯二文档改动。

  `ConfirmGate` 的失败出口（它的失败是 park/取消语义，本批未动）。
