## 0. 结论先行

### 0.1 三问三答

**问一「本项目目前 AI 可视可操作的方案是什么？」**
是一套**「注册式语义动作 + 引用式通用原语」的混合方案**：后端 34 个 `@Tool` 里有 23 个走前端通道，其中 7 个是通用界面原语（`ui_snapshot` + `ui_click` / `ui_fill` / `ui_select` / `ui_scroll` / `ui_highlight` / `ui_request_upload`），其余是业务流程动作（`navigate_to` / `select_definitions` / `set_condition` / `confirm_step` / `generative_form` 等）与 9 个表格域工具。AI「看见」页面的方式是**结构化工作区状态 + 区域化 DOM 行快照**（无截图、无无障碍树、无 console）；「操作」的方式是 `frontend_tool_request` 帧下发 → 浏览器内四路由派发 → `frontend_tool_result` 回灌，全程**零新增 SSE 帧**。安全靠三道围栏（区域 → 上下文 → 元素）+ 风险分级，其中 `data-ai-risk="consequential"` 的元素**一次都不点**（拒执并指路注册动作），上传走用户手势交接卡。但**标注面只落了导入向导第 1 步的上传区**：全前端 `data-ai-ref` 仅 3 处、可操作区域仅 1 个，其余页面 `ui_snapshot` 恒回「区域 0 个 / 共 0 个元素」。

**问二「是业界主流吗？」**
**路线是主流，成熟度不是。** 对「自有 Web 应用内嵌 copilot」这一类场景，「注册式语义动作 + 少量引用式通用原语」正是业界收敛出来的形态（第 41 件已论证，本件用 2026-10 一手来源复核仍成立：AG-UI 把前端工具定义为客户端注入、AI SDK 把前端工具与审批态做进 SDK、CopilotKit 的 HITL 就是"前端工具悬挂 Promise"、M365 声明式代理的动作=插件操作、Anthropic 2026 年新增的 `browser_toolset` 也是"结构语义 + ref"）。**偏离点在成熟度四件事**：① 主流用**无障碍树自动抽取**生成 ref，本仓靠**人工标注**（覆盖率因此 = 1 个区域）；② 主流把确认做成**三档（自动 / 确认 / 拒绝）**，本仓是**二值（本地可逆免确认 / 后果性一律拒执）**；③ 主流把失败做成**结构化结局**（`error` 字段 / `output-error` / `output-denied` / "未执行"批量语义），本仓主力回执是「结局未知」这种**不可判定态**；④ 主流工具集**整轮可用**，本仓按页面/步骤**冻结披露**，于是"推进后下一轮才生效"要靠系统提示补丁（`SYSTEM_PROMPT` 第 10 条）兜。

**问三「跟业界主流对比有啥差距和遗漏点？」**
一句话：**方向对、护栏硬、覆盖薄、失败面糙。** 十条差距见 §5（注册面覆盖率 / 页面状态感知 / 确认档位 / 失败重试与幂等 / 跨页导航与披露冻结 / 可观测性 / 选择器稳定性与标注治理 / 能力发现与工具面成本 / 撤销与写侧预演 / 富组件与批量等待）。最要紧的三条：**注册面 1/5 页面**（AI 在 4 个页面里"看得见工具、看不见目标"）；**没有文本/视觉兜底**（只能读 24 字符 label，读不到页面内容，canvas 永久不可见）；**"结局未知" + 无退避/无幂等**（实测同一轮 5 次重复导航）。

### 0.2 归类判定（一句话）

> 本仓属于业界**路线 C/D（应用内注册式动作 + 引用式原语）**，且是其中**安全边界最保守**的一档；它与主流的差距不在路线选择，而在**语义抽取的自动化程度、确认档位、失败语义与可观测性**这四处工程成熟度。

### 2.3 AI 如何「看见」页面

三条来源，**全是文本，且都是「已经结构化好的」**：

1. **工作区状态**（每轮注入）：`context` 严格 5 键 + `extra.recentActions`（页面 / 任务 / 步骤 / 选中项 / 数据版本 / 最近动作），由 `stores/workspace.ts#buildContext` 组装；
2. **区域化 DOM 行快照**（模型显式调 `ui_snapshot`）：每行 `[ref] role "label" state=… [fill=allow] [value="…"]`，默认 20 行 / 硬顶 40 行 / 硬顶 2000 字符 / 单行 120 字符 / label 24 字符（`ai-dom-tools.ts:36-53`）；
3. **工具结果与页面 handler 回执**（业务态）。

**明确没有的**：截图 / 像素坐标 / 无障碍树 / 页面正文文本 / 控制台与网络 / iframe 内文档 / canvas 内部。`ai-dom-tools.ts` 与 `types/tools.ts` 对 `screenshot|canvas|toDataURL` 零命中（A 级：本棒实读）。

### 2.4 AI 如何「操作」

链路：模型工具调用 → 后端哨兵桩（`FRONTEND_STUB`）→ 挂起 + `frontend_tool_request` 帧 → 前端四路由派发（登记表 / 工作区动作表 / `ui_event` / 页面 handler）→ 结局经 `makeExecution` 单点推导 → `POST /api/ai/frontend-tool-result` → `frontend_tool_result` 唤醒续跑。

原语侧的三道围栏顺序固定（`ai-dom-tools.ts:555` `checkFences`）：
① **区域围栏**：`ref` 必须能解析到已注册区域（解析失败给"不在当前页面/请重新快照"）；
② **上下文围栏**：区域 `page` 必须等于 `workspace.pageId`，`allowSteps` / `needsTask` 同口径；
③ **元素围栏**：`epoch` 必须等于当前 `epoch`（`<6 位 base36 nonce>-<counter>`，nonce 在模块加载期随机 ⇒ 刷新必变）、`isConnected` 必须为真、`data-ai-deny` 拒绝、动词白名单。

写动词底座：单轮配额 12 次、串行节流 80ms、用户「停止」后一律拒执（已执行不回滚）、撤销深度 1（`ai-dom-tools.ts:612` `acquireWriteSlot`）。

## 3. 业界主流（2026-10 一手来源复核）

### 3.1 路线 B：无障碍树 + `ref`（结构化语义，不用视觉模型）

- **Playwright MCP（Microsoft 官方）**：明确「operates on the page's accessibility tree, not pixels」「no vision models required」；`browser_snapshot` 返回 YAML 化语义树，节点带 `ref=e5`，后续 `browser_click/type` 按 ref 操作（[A](https://playwright.dev/docs/getting-started-mcp)）。同一页还给出两条与本文直接相关的边界：`browser_run_code_unsafe` 属 **RCE-equivalent**、只对可信客户端开启；实验性 **WebMCP** 会把页面自注册的工具以 `webmcp_<tool>` 暴露，"工具名/描述/schema/结果由页面提供 ⇒ 一律按不可信输入处理"。
- **Anthropic `browser_toolset_20260801`（2026 新增）**：默认 **27 个成员工具**（`navigate` / `read_page` / `left_click` / `screenshot` …），明确「works with the page both through its structure (the accessibility tree, elements, forms, and tabs) and through screenshots and viewport coordinates」；`read_page` 的结果是**每个元素带引用的文本**（[A](https://platform.claude.com/docs/en/agents-and-tools/tool-use/browser-use-tool)）。这条最关键：**业界头部把"结构 + 视觉"做成同一套工具集的两条腿**，而不是二选一。
- **Playwright 定位器指南**：推荐顺序是 role → label → text → testid →（最差）CSS/XPath；role 定位「reflects how users and assistive technology perceive the page」，testid「最抗变化但不是用户视角」（[A](https://playwright.dev/docs/locators)）。

**对本仓的意义**：我们的 `ref` 与 Playwright 的 `ref` **同构**（不透明键 + 每轮重取 + 逐字比对），差别在 ref 的**来源**——他们从无障碍树自动生成，我们从人工标注生成。

### 3.2 路线 B′：自动 DOM 抽取 + 可交互元素索引

- **browser-use**：`use_vision` 默认 `True`（`auto` 只在需要时用截图）；`max_actions_per_step=5`（一步可输出多个动作，**执行到页面变化为止**）；`max_failures=5`（步骤出错重试上限，到顶后强制一次"中间结论"式最终答复）；`step_timeout=180s`；另有 `fallback_llm`（主模型重试约 5 次指数退避后才切换）（[A](https://docs.browser-use.com/customize/agent/all-parameters)）。
  ⇒ 业界把「**重试上限 + 退避 + 兜底模型 + 超时**」作为**框架默认能力**，而不是留给模型自觉。

### 3.3 路线 A：纯视觉（截图 + 坐标）

- **Claude computer use**：`computer_toolset_20260801` 共 17 个成员（`screenshot` / `zoom` / 各类点击 / `type` / `key` / `scroll` / `wait` …）；工具集定义本身约 **4,500 input tokens**，每张截图约 **1,000–1,800 tokens**；单请求 >20 张图后收紧单边限制；批量动作**顺序执行、遇首错即停**，其余回「Not executed: an earlier computer action in this turn failed.」（[A](https://platform.claude.com/docs/en/agents-and-tools/tool-use/computer-use-tool)）。
  同一页还有两条与「确认」直接相关的硬要求：**若应用要求人对后果性动作确认，必须在每个 block 执行前确认**（一个 batch 能在一轮内完成多步动作）；官方自陈的限制包括坐标幻觉、滚动不可靠、**表格交互常需多次尝试**、注入可经网页/图片进入（官方另挂分类器自动扫描工具返回内容）。
- **OpenAI CUA / Operator**：纯像素感知 + 虚拟鼠标键盘；OSWorld 38.1%（人类 72.4%）、WebArena 58.1%、WebVoyager 87%；安全侧三条与本仓可对照：**外部副作用动作先求确认**、**高敏任务拒做**（银行类）、**敏感站点强制 watch mode**（[A](https://openai.com/index/computer-using-agent/)）。

**对本仓的意义**：纯视觉是「界面不是自己的」和「无 DOM」场景的兜底；但它也提供了两条可借的做法——**批量遇错即停的语义**与**执行前逐块确认**。

### 3.4 路线 C：应用内嵌 copilot 的动作注册（与本仓最相关）

| 框架 | 机制（一手） | 与本仓的对照点 |
|---|---|---|
| **AG-UI** | 前端工具由**客户端**在 `RunAgentInput.tools` 里注入（"frontend determines what capabilities are available"）；调用生命周期 `ToolCallStart/Args/End` → `ToolCallResult`；**失败必须带 `error` 字段**（"Without it, a tool that failed is indistinguishable from one that succeeded"）；HITL 就是"前端工具请求人输入"（[A](https://docs.ag-ui.com/concepts/tools)） | 我们的 `frontend_tool_request/result` 帧与之同构；但我们的失败态**多一个 `unknown`**，且没有等价的"error 必填"约束 |
| **CopilotKit** | `useHumanInTheLoop`：注册即"让 agent 暂停"，`render` 里拿到 `respond`，调用前状态 `InProgress → Executing → Complete`；实现上是 `useFrontendTool` + 一个**等 `respond` 才 resolve 的 handler**（[A](https://docs.copilotkit.ai/reference/hooks/useHumanInTheLoop)） | 我们的 `ui_request_upload` 是同一形态（悬挂 + 等人），但只此一个；`ui_click` 等写原语**没有**这条通道 |
| **Vercel AI SDK** | 三类工具：服务端自动执行 / 客户端自动执行（`onToolCall` + `addToolOutput`）/ **需用户交互**；后者用 `toolApproval: {name:'user-approval'}` 声明，前端出现 `approval-requested / approval-responded / output-denied` 三态并可带 `requestReason`；信任边界上另给 `experimental_toolApprovalSecret` 防"客户端伪造批准"；`sendAutomaticallyWhen` 负责批准后自动续跑（[A](https://ai-sdk.dev/docs/ai-sdk-ui/chatbot-tool-usage)） | 我们的确认门只服务 `DANGER` 后端工具，且**无"批准可伪造"的等价防护讨论**（前端回灌本身即信任边界） |
| **OpenAI Apps SDK / MCP Apps** | 组件跑在 iframe 里，经 `ui/*` JSON-RPC 桥与宿交互，**组件可反向调工具**（`tools/call`，兼容别名 `window.openai.callTool`）；规范强调"**保持工具在无 UI 时也有用**"，UI 只用于"inspect, compare, edit, confirm, or navigate"（[A](https://developers.openai.com/apps-sdk/build/chatgpt-ui)） | 我们的"工具在无 UI 时也有用"已成立（回灌是纯文本）；缺的是"组件侧可发起动作"这一层 |
| **Microsoft 365 声明式代理** | 代理 = 指令 + **动作（actions）** + 知识；动作由插件（OpenAPI 操作）承载，可挂多个插件（[A](https://learn.microsoft.com/en-us/microsoft-365-copilot/extensibility/overview-declarative-agent)） | 与我们"注册式语义动作"同构；差别是他们**没有**通用 DOM 原语这一层 |

### 3.5 正在成型的标准：页面自注册工具（WebMCP）

Chrome 149 起进入 Origin Trial：页面可用**命令式 API** 声明工具，或对**标准 HTML 表单做注解**（declarative），工具带 JSON Schema 与"当前可用状态"；权限策略 `tools` 默认 `self`（跨域 iframe 需 `allow="tools"`）；官方动机正是"与其让 agent 猜 HTML 元素的意图，不如网站直接告诉 agent 这个元素/工具是干什么的"（[A](https://developer.chrome.com/docs/ai/webmcp)）。

**对本仓的意义**：这条标准把「**应用侧声明能力**」从框架私约抬成浏览器级协议——本仓 `registerAiRegion` + `data-ai-*` 的方向被独立验证；但标准形态是「**页面注册工具（带 schema）**」，不是「元素带 ref 供通用动词点」。二者是同一哲学的两级抽象：**工具级声明**（粗、稳、可校验）vs **元素级声明**（细、覆盖长尾、需要护栏）。

### 3.6 标注机制四路对比

| 机制 | 代表 | 稳定性来源 | 覆盖率成本 | 语义强度 | 主要风险 |
|---|---|---|---|---|---|
| 人工 `data-*` 标注（本仓） | 本仓 `data-ai-ref`；测试界 `data-testid` | 显式契约，与文案/locale 无关 | **每加一个可操作元素都要改代码** | 中（ref 是私有语义，模型只知 label/role） | 漏标 = 永不可见；标注质量 = 信任根 |
| 无障碍树自动抽取 | Playwright MCP、Anthropic `browser_toolset`、browser-use | role + accessible name（W3C/ARIA） | 零标注成本，全页覆盖 | 高（就是给辅助技术看的那套语义） | 语义取决于页面 a11y 质量；自绘组件/`div` 按钮会缺失 |
| 视觉 + 坐标 | Claude computer use、OpenAI CUA | 像素（与 DOM 无关） | 零标注，但每步付图像 token | 低（模型自己"看图猜"） | 坐标幻觉、滚动不可靠、注入面更大 |
| 页面注册工具（schema） | WebMCP、MCP Apps、AG-UI 前端工具 | 工具名 + JSON Schema + 描述 | 每能力一次声明（比元素级粗） | 最高（模型按工具语义选，不猜元素） | 工具数增长会抬高选择成本与 schema token |

**选择器稳定性**这一维度本仓实际是**领先**的：`ref` 不拼 selector、`epoch` 含加载期 nonce（刷新必失效）、`isConnected` 判卸载、i18n 下 ref 不变（有专测 `frontend/tests/ai-ref-i18n-stable.spec.ts`）。业界的 `data-testid` 只解决"抗变化"，不解决"页面变了还拿旧句柄"——本仓用 `epoch` 补上了这一层。

## 4. 对比结论：同构点与偏离点

| 维度 | 本仓 | 业界主流 | 判定 |
|---|---|---|---|
| 路线选择 | 注册式动作 + 引用式原语 | 自有应用内嵌 copilot 同一形态 | **同构**（41 件结论复现） |
| 感知原语 | 结构化工作区态 + 区域化行快照 | 无障碍树快照（全页）+ 可选截图 | **偏离**：覆盖窄、无视觉兜底 |
| ref 生命周期 | epoch(nonce+counter) + isConnected + 逐字比对 | ref 每轮重取、页面变化失效 | **同构且更严** |
| 动作集 | 6 个受控动词 + 1 个交接 | click/type/select/scroll/key/tabs…（Playwright MCP 40+，browser_toolset 27） | **偏窄**：无键盘、无 tab、无等待、无批量 |
| 确认模型 | 二值：本地可逆免确认 / 后果性拒执 | 三档：自动 / 确认（可带理由、可改参数）/ 拒绝 | **偏离（保守方向）** |
| 失败语义 | `ok/failed/unknown` 三态，`unknown` 为超时兜底 | `error` 必填 / `output-error` / `output-denied` / 批量"未执行" | **偏离**：`unknown` 不可判定 |
| 重试与幂等 | 无框架级重试；`max-tool-steps=25` 兜底 | `max_failures=5` + 退避 + fallback 模型 + step timeout | **偏离**：成本全压在模型自觉 |
| 跨页导航 | `navigate_to` + 3s 就绪等待；工具披露按请求冻结 | 工具整轮可用，页面上下文运行期校验；或 dynamic tools | **偏离（架构级）** |
| 可观测性 | recentActions + 通用 `tool_call_end` | 动作级可审计（官方要求"review and verify actions and logs"） | **偏离** |
| 上传 | 手势交接卡（唯一等人工具） | 同为浏览器手势边界，业界亦无"AI 代选文件" | **同构**（且实现完整） |
| 页面自注册 | 私有 `data-ai-*` 约定 | WebMCP / MCP Apps 标准化 | **方向同、形态不同** |
| 工具成本意识 | 7 个原语 + 说明"不做第 8/9 个" | 明确量化工具集/截图 token 成本 | **同构** |

## 5. 差距与遗漏点清单

> 每项四列：现状（带锚点）/ 主流做法（带来源）/ 差距 / 建议方向（**候选，不构成施工承诺**）。

### D1 注册面覆盖率（最要紧）

| | |
|---|---|
| **现状** | `data-ai-ref` 3 处、区域 1 个（`ImportWizardView.vue:42/53/57`、`:1290`）；其余四页零区域；`ui_snapshot` 在这些页面恒回 0 元素（R1/R2 实测）。挂账 L-36/L-37 已登记「页面标注扩面待批②」 |
| **主流** | 无障碍树自动覆盖全页（Playwright MCP `browser_snapshot`、Anthropic `read_page`）；browser-use 自动抽可交互元素索引；WebMCP 允许页面用注解声明表单 |
| **差距** | 覆盖率差 1~2 个数量级；AI 在 4/5 页面上"有工具没目标"，用户感知为"这个 AI 只能聊天" |
| **建议方向** | ① 短期按 L-36 扩面（导入选配置/模式/表格视口 → 导出向导 → 任务中心）；② 中期补"**自动补全**"：对注册区域内做 role+accessible-name 的只读快照，仅 `read`/`mutate-local` 生效、ref 为临时键（41 件 §7.3 的 C 方案，42 件列为待评估）；③ 长期对齐 WebMCP 形态：把"区域"升级为"页面注册工具" |

### D2 页面状态感知方式

| | |
|---|---|
| **现状** | 只有工作区 5 键 + 标注元素的一行文字（label ≤24 字符）；无正文文本、无截图、无 console/network、无 iframe、无 canvas |
| **主流** | 结构（a11y 树）**与**截图两条腿（Anthropic `browser_toolset` 明确两者并用）；browser-use `use_vision=auto` 需要时补图；Playwright MCP 亦提供 `browser_take_screenshot` 供"视觉核验" |
| **差距** | ① 读不到页面内容（"这个页面现在显示什么"只能靠业务工具）；② 自绘组件（SpreadJS canvas）结构性不可见；③ 无"动作后视觉核验"这一环 |
| **建议方向** | ① 先加**只读文本快照**（区域内可见文本 / 表头 / 校验错误文案，带字数闸），成本低、收益最高；② 再评估**按需截图**（仅用户显式请求或失败诊断，1 张起、限尺寸）；③ canvas 面继续走领域工具（表格专项），不要试图用原语点格子 |

### D3 操作确认 / HITL

| | |
|---|---|
| **现状** | 二值：`consequential` 零点击拒执（`ai-dom-tools.ts:673`），`mutate-local` 免确认直接执行；`ui_*` 因通道优先（`SpToolCallingManager.java:1456`）**永进不了确认门**；撤销深度 1 且不持久化 |
| **主流** | 三档：自动 / **确认后执行（可展示参数、可带理由、可改参数）** / 拒绝（AI SDK `toolApproval` + `output-denied`；CopilotKit `respond`；AG-UI interrupt；CUA"外部副作用前求确认"；computer use"每个 block 前确认"）；另有"批准不可伪造"的信任边界讨论 |
| **差距** | ① 缺少"批准后执行"这一档 ⇒ 用户说"帮我下载模板"时 AI 只能说"请你自己点"，能力损失；② 无"逐次批准"的审计留痕；③ 无参数可编辑（改完再批准） |
| **建议方向** | ① 把「后果性拒执」升级为**可配置两档**：`deny`（现状）/ `approve`（走既有确认门 + 卡片显示 ref/label/risk，批准后续跑）；② 确认卡上补"这次要动的具体元素"与"预期后果"（人话摘要）；③ 保留"本地可逆免确认"以避免确认疲劳（42 件 §8.5 的理由仍成立） |

### D4 失败重试与幂等

| | |
|---|---|
| **现状** | 无退避/无抖动/无断路器/无同参去重/无业务幂等键；`outcome='unknown'` 作为超时兜底文案；`max-tool-steps=25` 是唯一硬顶；R2 实测同页导航同轮 5 次重试 |
| **主流** | `max_failures=5` + 指数退避 + `fallback_llm`（browser-use）；失败必须 `error`（AG-UI）；`output-error` / `output-denied` 分态（AI SDK）；批量"遇首错即停 + 其余标未执行"（computer use） |
| **差距** | ① "结局未知"没有可行动出口（模型只能重试，因为不知道还能做什么）；② 重复调用无代价 ⇒ 风暴靠步数兜底；③ 无幂等键 ⇒ 同一 `ui_fill` 重复执行会覆盖用户的手改 |
| **建议方向** | ① 回执补**确定性收敛提示**（"已在目标页，无需重复导航" / "该动作已执行过，请勿重复"）；② 引入**同工具同参数短窗去重**（同一 `toolCallId` 之外的重复调用直接回"已做过"）；③ 写动词带**幂等键/前置条件**（`epoch`+`ref`+原值三元组，原值已变则拒执）；④ 前端工具增加**指数退避重试白名单**（仅幂等读工具） |

### D5 跨页导航与披露冻结

| | |
|---|---|
| **现状** | `navigate_to` 后等页面就绪（3s 上界）；**工具披露按请求冻结** ⇒ 目标页新解锁的工具本轮拿不到，靠 `SYSTEM_PROMPT` 第 10 条要求模型"下一轮再调"（`ResilientChatService.java:156`）；同页导航无"已在目标页"直返 |
| **主流** | 工具集在**整轮/整 run** 可用，页面上下文以运行期校验拦截（AG-UI 前端工具、AI SDK 动态工具）；browser-use 一步可发多个动作并按"页面是否变化"推进 |
| **差距** | ① 跨页多步任务被强制拆成多轮对话，用户要多说一句"继续"；② 披露冻结让"导航→动作"同一轮必然失败，是设计性摩擦；③ 同页导航回执不确定（R2 现场） |
| **建议方向** | ① 同页导航直接回「已在目标页」（一行收敛）；② 评估"**导航后同一轮内二次披露**"（或对白名单工具放宽 step 级 scope）；③ 若维持冻结，至少在提示里给模型一条"导航成功即结束本轮"的明确口令（现已有第 10 条，可再收紧） |

### D6 可观测性

| | |
|---|---|
| **现状** | 动作只进 `workspace.recentActions`（容量截断的尾部窗口）+ 通用 `tool_call_end`；无结构化动作台账（ref / verb / risk / epoch / 结果 / 耗时 / 是否拒执）；无指标；无回放 |
| **主流** | 官方要求"review and verify the model's actions and logs"（computer use）；Apps SDK / AG-UI 都有工具调用事件流；可观测性件（索引第 43/44 件）指出**逐帧 span 无主流做法**，通行是"一条 generation + 首帧 + 帧数/字节"聚合 |
| **差距** | 出问题时无法回答"AI 到底点了什么、点了几次、为什么被拒"；告警与复盘都缺数据 |
| **建议方向** | ① 复用既有 `ai:safety:` 台账与 12 事件，加 `kind=ui_action`（字段白名单：ref / verb / risk / 结果码 / 耗时；**不含 value 原文**）；② 指标只做四件：动作数、拒执数、`unknown` 数、P95 耗时；③ 明确不做"逐动作 span"（与 43 件结论一致） |

### D7 选择器稳定性与标注治理

| | |
|---|---|
| **现状** | ref 逐字比对 + epoch nonce + isConnected ⇒ 稳定性领先；但**标注质量是信任根**，且无标注审计（挂账 L-40 只登记"由批⑤ 承接"）；元素级风险低于区域时无 DEV 告警 |
| **主流** | role/label 优先（Playwright），testid 为"最抗变化但非用户视角"；WebMCP 把"页面声明的工具语义"作为契约 |
| **差距** | ① 无"标注清单导出 + 人工过一遍"的机制 ⇒ 误标（把危险按钮标 `read`）无法被系统发现；② ref 与 a11y 完全脱钩 ⇒ 本可用于无障碍的语义被浪费 |
| **建议方向** | ① 标注审计做成**一次导出 + 每次新增区域必过**的清单（ref/risk/verbs/label/所属页面）；② 标注时强制要求可访问名（`aria-label` 或 `data-ai-label`），让 ref 与 a11y 同源；③ 加 DEV 期告警：元素风险低于区域、ref 重复、label 缺失 |

### D8 能力发现与工具面成本

| | |
|---|---|
| **现状** | 7 个 `ui_*` 的 scope = `*`，**所有页面都披露**；但 4/5 页面 0 目标 ⇒ 每轮付 schema token 换零可用性；`SYSTEM_PROMPT` 16 条规则里**没有一条讲何时用 `ui_snapshot`**（只靠工具描述自我说明） |
| **主流** | 工具成本被显式计量（computer use 工具集 ≈4,500 tokens、截图 1,000–1,800 tokens/张）；M365 生态对单插件函数数量有上限（B 级，转引 41 件）；AG-UI 主张"前端决定能力集合"，即**按上下文收窄** |
| **差距** | ① 披露与可达面倒挂（工具在、目标不在）；② 模型缺少"先快照再动手"的行为约束，R1 实测只有在用户明确要求时才快照 |
| **建议方向** | ① 把 `ui_*` 的披露从 `*` 改为**按区域存在性动态披露**（前端上报"本页有 N 个已注册区域"→ 后端过滤工具集）；② 系统提示补一条：**需要点界面元素前必须先 `ui_snapshot` 取 ref，不得凭猜测或旧快照操作**；③ 快照头行已带区域数，可再补"若为 0 请不要尝试 ui_*" |

### D9 撤销与写侧预演

| | |
|---|---|
| **现状** | 撤销深度 1、不持久化、只给用户（模型无 `ui_undo`）；写原语直接落 DOM，无"预览→确认→应用" |
| **主流** | 浏览器 agent 普遍不承诺 undo；但**应用内 copilot 的写动作**主流走"预览 + 人确认 + 应用"（本仓表格工具已是这个形态，`replace_values` 走预览卡） |
| **差距** | 同仓两套写侧哲学：表格写"先预览再应用"，界面原语写"直接改" |
| **建议方向** | ① 把表格的"预览三档"思路下移到**复合写**（多字段 fill / 表单式改动）；② 单字段 fill 保持直写（预览会成为负担）；③ 撤销深度维持 1（与 42 件裁决一致），但补"撤销失败如实说"的既有行为（已具备） |

### D10 富组件、iframe 与自绘面

| | |
|---|---|
| **现状** | canvas（SpreadJS）不可见；跨文档 iframe 在注册期拒绝；Element Plus 弹层靠 `[data-ai-option]` 全局兜住 |
| **主流** | Playwright 定位器默认穿透 Shadow DOM（XPath 不穿透、closed shadow 不支持）；Anthropic 明确"表格交互即便细粒度鼠标动作也常需多次尝试"；Apps SDK 用 iframe + postMessage 桥把"组件内动作"标准化 |
| **差距** | ① Shadow DOM 未处理（未来组件库升级即失效）；② iframe 面完全放弃（当前无此需求，属已知边界）；③ canvas 无兜底（正确，但要有"明确说做不到"的话术） |
| **建议方向** | ① 快照遍历补 Shadow DOM 穿透（`open` 模式即可）；② 保持 canvas 不做，但在工具描述里**明说**"表格内容请用表格工具"；③ iframe 维持拒绝（同源跨文档也无必要） |

### D11 多步批量与等待判据

| | |
|---|---|
| **现状** | 一次工具调用一个动作；写动词串行 80ms 节流；动作后靠"回读"确认；无 `wait_for`（等待文本/网络/元素出现） |
| **主流** | computer use：一轮可发**批量动作**，顺序执行、首错即停；browser-use `max_actions_per_step=5`；Playwright 有 `browser_wait_for`（文本/网络稳定） |
| **差距** | ① 多字段填写要 N 次工具调用（每次一轮模型往返）⇒ 慢且贵；② 无"等异步渲染完成"的判据 ⇒ 回读失败会被误报为"值未生效" |
| **建议方向** | ① 评估"**批量原语**"（一次调用带动作数组，顺序执行、首错即停、其余回"未执行"）——注意 42 件明确"不做第 8/9 工具"，需重新裁决；② 给 `ui_select` / `ui_click` 补**短等待**（等弹层出现/等 DOM 稳定，≤500ms），而不是靠失败重试 |

## 6. 不建议照抄的三件事（先划边界）

1. **纯像素路线**（截图 + 坐标点击）：成本（工具集 ≈4,500 tokens + 每步 1,000–1,800 tokens/张）、可靠性（官方自陈坐标幻觉、滚动不可靠）、注入面（页面内容直接驱动点击）三项全劣，且自有应用有 DOM 可用。业界把它用于"别人的界面"和隔离环境，不作为自有 copilot 默认架构。
2. **让模型产 selector / HTML**：等于把注入面变成执行面。本仓用 `UiPrimitiveGuard` 的 10 个禁键把这条口子钉死，应保持。
3. **全站自动扫描 + 无围栏通用点击**：会把"可被注入驱使的面"从几十个显式声明的控件扩大到全站。若要提覆盖率，应走"**区域内自动补全**"（有围栏的自动抽取），而不是全域开放。

## 7. 若要做：分层建议（候选，不构成施工承诺）

| 层 | 内容 | 依赖 | 收益/成本比 |
|---|---|---|---|
| **P0 收敛（小改）** | 同页导航直返「已在目标页」；系统提示补"先快照再操作"；`ui_*` 按区域存在性动态披露；快照 0 区域时给"请勿尝试"话术 | 无新设施 | 高（直接消 R2 的重试风暴与 token 浪费） |
| **P1 覆盖（批② 原计划）** | `data-ai-*` 扩到导入选配置/模式/表格视口 → 导出向导 → 任务中心；`setters` 页面注册点；标注审计清单 | L-36/L-37 | 高（覆盖率是天花板） |
| **P1.5 感知补强** | 只读文本快照（区域内可见文案/表头/错误提示，带字数闸）；写动词前置条件（原值三元组） | 无 | 中高 |
| **P2 治理** | `ui_action` 台账（字段白名单）+ 四指标；确认档位从二值扩到"拒执 / 批准后执行"两档可配 | 复用 `ai:safety:` 与确认门 | 中 |
| **P3 架构级** | 披露解冻（导航后同轮二次披露）或 dynamic tools；批量原语；按需截图诊断 | 帧契约与披露机制改造 | 低（需先裁决） |

排序理由：P0/P1 是"让今天的能力真的可用"，P2 是"出问题能查"，P3 才动架构。与 42 件 §10 的批次切分不冲突——本文只调整了优先级依据（用 R1/R2 实测的覆盖率与重试现场作为依据）。

## 9. 一句话收口

本仓的可视可操作方案**选对了路线**（应用内注册式 + 引用式原语，与 2026-10 的业界基线一致），**护栏做得比主流更硬**（区域围栏 + epoch + consequential 零点击 + 上传手势边界），但**可用性面还停在样板间**：1 个区域、看不到页面正文、后果性动作只能拒不能批、失败回执含"结局未知"、动作没有台账。补齐顺序应是**扩面（P1）→ 收敛失败与发现（P0）→ 治理（P2）→ 架构（P3）**，而不是先换路线。
