# 调研 · 临时会话有效期业界惯例 · 2026-10-20

> 调研问题：一个**页签级、非鉴权**的临时会话（业务工作区右侧 AI 面板）该给多长有效期？滑动续期与绝对上限各自防的是什么，业界默认值落在哪个区间？本件扫 **AI 聊天产品的临时会话留存、通用 Web 会话（cookie 与框架默认）、匿名会话与购物车、客服聊天** 四类。
> 来源：OpenAI / Anthropic / Google / Microsoft / Perplexity 官方帮助与隐私页，OWASP Session Management Cheat Sheet、NIST SP 800-63B、MDN，Keycloak / Auth0 / Django / Spring / Intercom / Zendesk / Adobe Commerce 官方文档；访问日期 2026-10-20。官方页 403 的 3 项采用二手转述并逐条标注（见 §8）。
> 结论：**「滑动」是默认动作，「绝对上限」是必须同时存在的第二道闸** —— 二者防的是不同威胁（idle 防「无人看管的终端被顺手使用」，absolute 防「会话被窃取后无限续命」）；但**临时会话的产品化 TTL（24h~30 天）约束的是服务端留存 / 合规，不是 UI 空闲超时**，且没有任何一家用滑动续期管理临时会话。只有滑动、没有绝对，理论上可无限续命。
> 边界：本件是调研稿；§6「建议一~三」是研究方向，不构成接口契约或验收承诺。件内 6h / 6h 是调研时点的本仓取值（其后已变更，见 §6 末注记）。
> 脱敏：无账号显示名、无本机绝对路径、无密钥、无原始会话内容；官方 URL 原样保留。

---

## 1. 结论速览

| 场景 | 业界常见值 | 性质 |
|---|---|---|
| AI 产品「临时/隐身会话」留存 | ChatGPT 30 天、Claude 30 天、Gemini 72 小时、Perplexity 24 小时 | 服务端留存上限，不是 UI 会话 TTL |
| AI 产品「普通会话」 | 永久保存直到用户删除；删除后 30 天内清完 | 账户级、跨设备 |
| 通用登录会话 idle | 15–30 分钟（低风险）、2–5 分钟（高价值） | 滑动 |
| 通用登录会话 absolute | 4–8 小时（办公全天）、12 小时（NIST AAL2）、10 小时（Keycloak 默认） | 绝对 |
| 匿名/游客会话 | 14 天（Perplexity 未登录线程）、购物车 30 天 | 绝对为主 |
| 客服聊天 | Intercom cookie 1 周、活跃自动 +1 小时；Zendesk 断线 5 分钟 | 混合 |
| 内部后台 | 30 分钟 idle + 8–12 小时 absolute 是主流组合 | 双时钟 |

一句话：**「滑动」是默认动作，「绝对上限」是必须同时存在的第二道闸**；只有消费级「保持登录」才会出现 30 天这类长绝对窗口。

## 2. 主流 AI 聊天产品的会话留存

### 2.1 普通会话：事实上的永久

- **ChatGPT**：常规与归档会话一直保留，直到用户删除或工作区保留策略清除；删除后 30 天内从系统彻底删除。[OpenAI Help: Chat and file retention](https://help.openai.com/en/articles/8983778-chat-and-file-retention-in-chatgpt)
- **Claude**：会话由用户控制，可随时删除；若开启模型改进，去标识化数据可在训练管线中保留最长 5 年。[Anthropic Privacy Center](https://privacy.claude.com/en/articles/10023548-how-long-do-you-store-my-data)
- **Gemini**：默认「Keep Activity」开启，历史进入账户 Activity。
- **Copilot / Perplexity**：同样以账户历史为默认，删除才消失。

要点：这些产品的「会话」是**账户级持久对象**，没有 tab 级 TTL 概念。它们的「临时」是另一种东西——一份不进入历史、只做短期安全留存的旁路记录。

### 2.2 临时会话：留存窗口 24 小时 ~ 30 天

| 产品 | 功能名 | 行为 | 留存上限 |
|---|---|---|---|
| ChatGPT | Temporary chat | 不进历史、不写 memory、不用于训练；可事后「保存为常规会话」；保存后按常规规则走 | **30 天**（安全用途副本）[OpenAI Help](https://help.openai.com/en/articles/8914046-temporary-chat-in-chatgpt) |
| Claude | Incognito | 不进历史、不进 memory、不参与训练、不被历史搜索命中 | **30 天**（消费级；团队/企业可按组织策略更长）[Anthropic](https://privacy.claude.com/en/articles/10023548-how-long-do-you-store-my-data) |
| Gemini | Temporary Chat | 不出现在最近会话与 Activity、不用于个性化/训练 | **72 小时**（官方原文："retained with your account for 72 hours"）[Google Privacy Hub](https://support.google.com/gemini/answer/13594961?hl=en)、[Google 公告](https://blog.google/products-and-platforms/products/gemini/temporary-chats-privacy-controls/) |
| Copilot | Temporary chat | 不写入个人历史与 memory | 受租户 Purview 保留策略约束，典型 **30 天**（消费级 Copilot 对话亦约 30 天）[Microsoft Learn](https://learn.microsoft.com/en-us/purview/retention-policies-copilot) |
| Perplexity | Incognito | 不入 Library、memory 与历史关闭 | **24 小时**过期；未登录匿名线程 **14 天**（官方帮助页口径，经二手来源转述）[Coupler.io 汇总](https://blog.coupler.io/ai-data-security/) |

观察：
1. **临时会话的 TTL 普遍远长于「一次对话」**（24h–30d），因为它约束的是**服务端留存/合规**，不是用户界面的空闲超时。用户关掉页面，临时会话就不可再打开（ChatGPT 明确：不保存就无法从历史重新打开）。
2. **没有任何一家用「滑动续期」管理临时会话**——它们都是从创建/最后写入起算的绝对窗口。滑动的对象是「登录态」，不是「对话记录」。
3. 30 天是「删除后彻底清完」的行业事实标准（OpenAI、Anthropic、Perplexity 账户删除均为 30 天）；72 小时是「为服务可用性保留」的下限（Google 明确说是为了 system failure 时可恢复）；24 小时是「短命隐身」的激进值（Perplexity）。

## 3. 通用 Web / 匿名会话 / 购物车 / 客服的 TTL 惯例

### 3.1 Session Cookie 与框架默认值

- **浏览器会话 cookie**：不设 `Expires`/`Max-Age` 时，浏览器关闭即忘；OWASP 建议会话 cookie 就应省略这两个属性（即浏览器会话级）。[MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Authentication/Session_management)、[OWASP](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)
- **ASP.NET / ASP.NET Core**：Session 默认 **20 分钟 idle、滑动**（每次请求续期）；Forms 身份验证默认 30 分钟滑动；常见企业包把「20 分钟 idle + 8 小时 absolute」作为默认组合。[SANS](https://www.sans.org/blog/session-attacks-and-asp-net-part-2)、[Recrovit 包文档](https://libraries.io/nuget/Recrovit.AspNetCore.Authentication.OpenIdConnect)
- **Spring Boot / Tomcat**：`server.servlet.session.timeout` 默认 **30 分钟**（idle）。[CodeJava](https://www.codejava.net/frameworks/spring-boot/change-session-timeout)
- **Django**：`SESSION_COOKIE_AGE` 默认 **2 周**（1209600 秒），且 `SESSION_EXPIRE_AT_BROWSER_CLOSE` 默认 **False**——即默认是持久 cookie，不是浏览器会话 cookie。[Django docs](https://docs.djangoproject.com/en/6.1/topics/http/sessions/)
- **Keycloak**：SSO Session Idle 默认 **30 分钟**，SSO Session Max 默认 **10 小时**；Remember Me 为 30 天 idle / 365 天 max。[Skycloak](https://skycloak.io/blog/session-management-in-keycloak-from-refresh-to-idle-timeouts/)、[Phase Two](https://phasetwo.io/tutorials/sessions/timeouts/)
- **Auth0（refresh token）**：开启轮换后默认 **30 天**绝对过期，可配置到 1 年；每次轮换只换新令牌，绝对窗口不重置。[Auth0 Docs](https://auth0.com/docs/secure/tokens/refresh-tokens/configure-refresh-token-rotation)

### 3.2 匿名 token / 游客会话

- Perplexity **未登录匿名线程 14 天**后过期且不可恢复（官方帮助页口径，见上）。
- 电商购物车：Magento 2 **quote lifetime 默认 30 天**；持久购物车 cookie 上限 **34,560,000 秒（400 天）**。[Adobe Commerce](https://experienceleague.adobe.com/en/docs/commerce-admin/config/customers/persistent-shopping-cart)、[Meetanshi](https://meetanshi.com/blog/configure-magento-2-quote-lifetime/)
- 规律：**匿名态越"低价值"，TTL 越长**（14 天、30 天、400 天），因为丢失成本只是重填；而登录态越敏感，TTL 越短（分钟级）。

### 3.3 客服聊天（Intercom / Zendesk / Ada）

- **Intercom**：跨子域维持会话的 cookie **1 周**过期；用户活跃使用 Messenger 时**自动延长 1 小时**；`session_duration` 只能配置得比后台设置**更短**，不能更长。官方明确建议「把 Messenger 会话长度对齐你应用自身的会话长度」。[Intercom Help](https://www.intercom.com/help/en/articles/16845-how-do-i-end-a-session)
- **Zendesk**：坐席结束聊天会把「断线超时」重置为 **5 分钟**；访客断线 1 小时；Messaging 会话约 **10 分钟**无活动转为 inactive。[Zendesk](https://support.zendesk.com/hc/en-us/articles/11005634190874-When-do-chats-time-out)、[Zendesk Messaging](https://support.zendesk.com/hc/en-us/articles/7043034053658-Automatically-releasing-agent-capacity-for-inactive-messaging-conversations)
- **Ada**：作为 AI 客服，其会话边界跟随宿主渠道（Zendesk 等），没有独立的「AI 会话 TTL」概念。

观察：客服场景是**最短**的一档（分钟级），因为它们模拟「实时在场」，且共享设备上的对话泄漏风险高（Intercom 专门警告共用电脑能看到上一个人的会话）。

## 4. 滑动过期 vs 绝对过期：惯例与适用场景

### 4.1 业界定义（OWASP 原文）

- **Idle timeout**：必须实现；「session 在最后一次 HTTP 请求后经过定义的空闲期即失效」。
- **Absolute timeout**：也必须实现，「无论会话活动如何」，从会话**最初创建**起算，到点即失效并强制重新认证。
- 典型值：idle **2–5 分钟**（高价值应用）/ **15–30 分钟**（低风险应用）；absolute 「若面向办公人员全天使用，合适区间为 **4–8 小时**」。
- 强制要求：**超时必须在服务端执行**；若靠客户端时间戳，攻击者可篡改延长会话。

来源：[OWASP Session Management Cheat Sheet](https://cheatsheetseries.owasp.org/cheatsheets/Session_Management_Cheat_Sheet.html)

### 4.2 为什么必须两个都要

OWASP 的理由很直接：idle timeout **不能限制攻击者的行为**，因为攻击者可以周期性制造活动让会话永不过期。绝对上限约束的是「会话被窃取后的最大暴露窗口」，idle 约束的是「无人看管的终端被顺手使用」。二者防的是不同威胁，不能互相替代。[BuilderProof 对 OWASP 原文的梳理](https://www.builderproof.org/benchmarks/can-you-actually-log-someone-out-session-lifetime-axis-september-2026)

### 4.3 各栈的默认行为对照

| 栈 | idle（滑动） | absolute | 备注 |
|---|---|---|---|
| ASP.NET Core Session | 20 分钟，默认滑动续期 | 无内置 | 需自行加 `created_at` 校验 |
| ASP.NET Cookie Auth | 20–30 分钟滑动 | 常见 8 小时 | 企业模板常显式加 absolute |
| Spring Boot / Tomcat | 30 分钟滑动 | 无内置 | 靠 `HttpSessionListener` 或网关补 |
| Keycloak | 30 分钟 | **10 小时** | 双时钟原生支持，最接近「标准答案」 |
| NIST 800-63B AAL2 | 30 分钟无活动须重认证 | **12 小时** | AAL3 为 15 分钟 / 12 小时 |
| Auth0 Refresh Token | 每次轮换重置单 token | **30 天**（默认） | 绝对窗口不随轮换延长 |
| Redis 原生 TTL | `EXPIRE` 每次写重置（天然滑动） | 无 | 绝对上限需另存 `created_at` 字段 |

NIST 来源：[NIST SP 800-63B](https://pages.nist.gov/800-63-3/sp800-63b.html)（AAL2：inactivity 30 分钟、extended usage 12 小时；AAL3：15 分钟 / 12 小时）

### 4.4 绝对上限的典型取值与选用逻辑

- **8 小时**：覆盖一个工作日，OWASP 对办公场景的建议上限。适合内部工具、后台。
- **10 小时**：Keycloak 默认，略宽于一个工作日，容忍加班。
- **12 小时**：NIST AAL2/AAL3 的强制重认证周期，合规场景的事实标准。
- **24 小时**：面向消费者的「一天一登录」，或短命匿名态。
- **30 天 / 365 天**：仅用于「保持登录」类消费产品，且必须配合轮换 token + 重用检测 + 设备撤销。

安全侧的核心逻辑：绝对上限的价值 = **把「被盗会话可被无限续命」压缩成「最多 N 小时」**。所以它通常与「敏感操作二次认证（step-up）」配套，而不是单独使用。

## 5. 内部工具 / 管理后台的典型取值

- **OWASP**：低风险内部应用 idle 15–30 分钟、absolute 4–8 小时；高价值（管理后台、财务、生产环境）idle 2–5 分钟。
- **Keycloak 部署实践**：30 分钟 idle + 10 小时 max 是最常见的出厂组合，几乎被各类「内部 SSO 接入指南」直接抄用（Valtimo、Emergence 等文档均如此建议）。[Valtimo](https://docs.valtimo.nl/valtimo-docs-v3/running-valtimo/application-configuration/configuring-keycloak)
- **真实工程取舍案例**：某管理后台把 idle 从 30 分钟提到 4 小时，理由是「长文写作被登出」，但同时保留 absolute 上限——说明**放宽的永远是 idle，不是 absolute**。[提交记录](https://git.erg.school/PostERG/xamxam/commit/554ba3ee8d77ec4ee13c518675f007a1e8170d5f)
- **企业 SSO 惯例**：管理后台 15–30 分钟 idle + 8 小时 absolute；特权操作再叠加 step-up（重新输密码/MFA）。

## 6. 对我们（页签级临时会话 + 6h 滑动 + run 键 6h 绝对）的建议

**先校准定位**：我们的是「页签级 UI 会话」，不是登录态。它不授予权限、不携带凭证，泄漏后果是「别人看到这段对话」，量级接近 Intercom 的 Messenger 会话（1 周 + 活跃 +1 小时），而不是 auth session（30 分钟）。因此 6h 的 idle 并不离谱——真正的问题是**它只有滑动、没有绝对**，理论上一个每天开着的页签可以无限续命。

### 建议一：保留 6h 滑动，补 12h 绝对上限（服务端 `created_at` 判定）

- 滑动 6h 继续负责「关掉页签半天后回来还能接上」，符合页签级临时语义。
- 新增 `absolute_expires_at = created_at + 12h`，与 `idle_expires_at` 分开存储；每次读取取两者最小值。Redis 侧用 `EXPIRE` 管滑动，用记录里的 `created_at` 管绝对（Redis 本身没有绝对 TTL 概念）。
- 12h 的取值依据：NIST AAL2 的 12 小时重认证周期 + Keycloak 10 小时默认 + OWASP 4–8 小时办公上限。对内部工具取 12h 属于「宽但仍有界」，不会出现「周一开的页签周五还活着」。若安全评审要求更紧，8h 是可辩护的下一档。
- 为什么不是 24h：24h 会让「绝对上限」在实际使用中几乎不触发（用户一天内基本会关浏览器），失去约束意义。

### 建议二：run 级键的 6h 绝对上限保留，但要让 tab 的绝对窗口严格大于它

- run 键 6h 绝对是对的：单次生成/工具调用不可能合法跑 6 小时以上，这是「防僵死」而非「防泄漏」，无需滑动。
- 但要保证 `tab_absolute ≥ 2 × run_absolute`（12h ≥ 2×6h），否则会出现「run 还在跑，所属 tab 会话先被绝对上限掐掉」的孤儿状态。当前 6h/6h 是临界相等，属于风险点。
- run 完成后可把该 run 键的 TTL 主动降到 1h（结果已落库的前提下），减少 Redis 驻留。

### 建议三：过期要做「软过期 + 可观测」，并且鉴权会话必须另开一套

- 会话过期不要直接 404：返回 `410`/结构化错误 `{expired_reason: "idle" | "absolute"}`，服务端保留只读 transcript 摘要一段时间（建议 24h，对齐 Perplexity 的短命线程），前端提示「会话已过期，已为你保留最近记录」并给「继续为新会话」入口。这比静默新建会话更符合 ChatGPT/Claude 的「临时会话不落历史但可保存」心智。
- 前端 `sessionStorage` 只存 session id 和最小 UI 状态即可（它天然是页签级：MDN 明确 `sessionStorage` 按 tab 隔离、仅在 tab 内 iframe 间共享，关 tab 即清）。**TTL 判定永远在服务端**，这是 OWASP 的硬要求。
- 如果侧栏未来要执行工具/读写文件，那属于「授权动作」，必须使用独立的 auth 会话（30 分钟 idle + 8 小时 absolute + 敏感操作 step-up），**不要复用这个 6h 聊天会话**。两者混用会让「聊天上下文还在」被误当成「权限还在」。

> 后续口径（入库时注记）：本件 §6 **建议一「补 12h 绝对上限」与建议二「run 级键保留 6h 绝对」均未被采纳** —— 2026-10-20 用户直裁会话 TTL = **24h 滑动、活跃即续期、整个会话维度、无绝对上限**（`docs/决策看板.md` 10-20 行已留痕「明确否掉 OWASP 绝对超时建议」，理由 = 本仓为内网受信环境 DC-10、人机等待不设上限）：绝对封顶、`EXPIRED_RENEWAL` 与 `RunStoreTtlAbsoluteCapTest` 整体退役，run 级键也统一走同一整额 `session-ttl`（`RunStore.ttlFor` 单点）。建议三的两条口径（**TTL 判定永远在服务端**、**鉴权会话必须另开一套**）不受该裁决影响，仍然成立。本件正文保留调研时点原貌、不回头修订。
