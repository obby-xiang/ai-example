# 排查 · Kimi Code 交接提示词与信息遗失（2026-10-26）

> **性质**：本件回答一个具体问题——**“为什么后来接手的人（含新会话）不知道真实模型配置/服务口径/纪律？”**。它把同批 7 份交接审计稿（`handoff-01`~`handoff-07`）收成一条可追溯的事实链。
> **边界（硬）**：**仓外交接原文不入库**。本件只写“哪类信息在哪个环节丢失/变化/本来没写/没执行”，**不复制交接档正文**，不复制任何密钥，不写密钥的尾号或片段；密钥只写“存在/缺失/变量名”。
> **路径别名**：`<KIMI_SESSIONS>`＝本机 Kimi Code 会话库根；`<KIMI_SESSION>`＝本次核查所在会话目录；`<仓外交接档目录>`＝仓外交接档目录；`<仓外当前交接快照>`＝当前在用的仓外交接快照文件；`<仓外本地配置>`＝含真实模型配置的仓外本地 env 文件；`<LOCAL_WORK>`＝本机工作根。
> **不改历史**：37 份仓外交接档、会话 wire、压缩摘要**一律未改**；本件只做判定与引用。

## 0. 方法与口径

- 判定分四类：**A 真丢失**（旧档有、新档无、也无替代）｜**B 明确变更**（后续有理由地改了口径）｜**C 原本没写**（旧档也没有，不能算丢失）｜**D 仍在但易被忽略/没被读取或遵守**。
- 只统计 `type=turn.prompt` 且来源为用户的记录；`origin.clientMetadata.doc` 只是同一文本的富文本副本，不重复计数；工具结果是工具输出，压缩摘要是模型生成物，单列不混计。
- 时间均为本机本地时间（由 wire 毫秒时间戳换算）。
- **一条纪律**：不能把“摘要层缺失”说成“用户原话被压缩删了”——压缩摘要明确会尽量逐字保留用户消息，实测 `keptUserMessageCount` 与用户消息条数吻合。

### 3.2 压缩面

- 本会话（`c5a94a62`）压缩 **8 次**（4 自动 / 4 手动），摘要逐次累积改写。用户原话基本按条逐字保留（实测保留条数略高于此前用户消息数），**被摘要覆盖的主要是助手与工具过程**。
- **最后一次摘要早于“本地启动 / 真模型 / 原数据 / 8081·5202”这一串事件**：这些新要求没有进入任何摘要，只存在于逐字消息与后来写入的快照里 ⇒ **新会话如果只拿摘要，必然拿不到它们**（不是“被摘要删掉”，而是“摘要之后才发生”）。
- 5 个早期 K3 会话的“首稿 vs 摘要”保留矩阵（`handoff-06`）结论：**丢失集中在三类可执行约束**——①执行环境面（端口/构建/密钥注入）②用户审批边界（授权/充值/锁屏/标签组）③git 门禁（钩子放行/署名/锚定纪律）；叙事与待办反而保留完好（五份摘要都能完整复述“做了什么、下一步是谁”）。五份里**没有零缺失**；相对最好的是“铁律层几乎全保”和“交接动作层全保但主仓禁令整段丢失”两档；会话中途压缩的那份丢失面最宽。
- 共同缺陷：**待办列表与正文不一致，且朝旧状态滞后**（会把已完成项标成在途，照它续跑会重做）。
- 一个易犯的对比错误：**不能把“存档里现在有”当成“摘要补回了”**——同一天存在两份不同文档（一份 88KB/147 行的单体档与一份 67KB/203 行的当前态档），端口信息只出现在后者。

## 5. 核心事实：真实模型信息**曾在旧档**，但**入口没继承**

> 这一节是本件的结论核心。四层原因**叠加**，缺一不可；且要把“没继承”与“从未存在”“被压缩删掉”严格分开。

### 5.1 旧档里到底有没有

- **有，而且很早**：10-13 热档 `§H5-5` 就记了“供应商 base url + 模型名 + 端点路径”这一层；10-17 起各棒都以“**引用 §H5-5、不抄值**”的方式携带；10-22 当前态档首次在本档明文重列；10-24 当前态档把它写成“**真 key 值在 10-13 热档第 143 行**（脚本现取现注入，不打印不落盘）”，并单独写了“**产品侧模型配置与 harness 子智能体模型分属两层，不要动产品侧**”。
- ⇒ 因此不能把“模型信息缺失”说成“旧档从来没写”。**旧档写得很完整，问题在传递。**

### 5.2 链条在哪一环断

| 环 | 保留了什么 | 丢了什么 |
| --- | --- | --- |
| 10-24 会话的压缩摘要 | 子智能体必须显式指定模型并区分“主会话最终新对话按用户要求换模型”这一分层；端口值；密钥纪律（不得打印/读取/写入文档）；运行产物不提交；不改历史；头部/CI 事实；`mvn clean` 会锁 jar | **整段“环境注入层”**：三件套变量名、`key_ref=ENV`、“重启必须带这三个”、密钥落点指针（“10-13”“交接提示词”“存档”这些词在摘要里 **0 命中**）、启动命令/PID/监听面/cwd、自建端口段、“产品侧配置属另一层”、“子代理自证 profile”、“继续/可以不算批准”、“真机手工触发”——**逐项 0 命中核实** |
| 主会话自拟的交接约束 | 头部/CI/测试数字、三个重点、九册总纲、集群边界、挂账数、“子 agent 必须显式指定模型” | 把**唯一事实入口**指定为那份快照文件；约束压成“**8081/5202 不动**”；**无“交接档目录”字样**；无 env/cwd/密钥落点/产品侧分层 |
| 交接件（17 行） | 同上，并补充“先读快照文件获取事实” | 同上；另新增一条**单向**密钥纪律（只禁读禁写，**没写“起后端必须注入三个变量，否则报缺 key”**） |
| 交接时刻的“快照文件”（105 行，纯 10-24 快照） | 只有一句“未起停 8081/5202”与一句“测试环境密钥未透传 → 配置报缺 key”的旁证 | **没有任何** key/base-url/model、没有 `key_ref`、没有 cwd |
| 10-26 快照（当前） | **模型/密钥层被补回**：三变量与 base url、端点路径；`key_ref=ENV`、必须注入否则报缺 key、勿接测试桩、勿清空原库、备份位置；cwd 指向 `backend` 以沿用原库；前端代理地址 | 仍**无存档入口**；端口仍是“不动”（**没有**“勿起停/勿占用（重启须带 env 三件套）”原句）；无 PID/jar/监听面；无“继续/可以不算批准”；无“自建端口段” |

### 5.3 四层原因（缺一不可）

1. **入口单点**：交接件只写“先读那份快照文件获取事实”；主会话给子 agent 的指令同样只指定它。接手方**没有理由、也不被鼓励**去翻交接档目录。
2. **当时那份快照里确实没有**：交接时刻的快照是 105 行纯历史快照，逐行核对无模型段、无 cwd。
3. **纪律反向劝退**：交接件写“不读写或泄露任何密钥”——真正需要的是“**要起后端必须注入三个 env**”这半句，它丢了，只剩“别碰密钥”这半句。
4. **模型信息本身是两层**：harness 子 agent 口径其实**活下来了**（摘要 → 交接件 → 快照）；真正丢的是**产品侧**配置（模型名、`key_ref=ENV`、三件套注入）。
   ⇒ 所以“没看到模型信息”**不是“模型名丢了”，而是“产品后端靠什么模型、怎么注入、怎么起”这一层整段没了**。

### 5.4 一个反例：Maven 为什么没丢

同一份交接里 Maven 反而保留得很好：原交接**根本没写** IDEA 自带 Maven（接手方主动问“提示词里面丢了吗”），助手承认“是我漏用了”，随后找到完整路径；**此后 8 份摘要全部保留该路径**，并反复强调禁止 `clean`。
⇒ 这说明摘要链并非“必然丢细节”——**只要某条信息在丢失前被反复强调并与一个具体路径绑定，它就能活下来**。模型配置恰好相反：它被压缩成“不读写密钥”这一句禁令。

### 5.5 必须同时声明的两点

- **10-26 的模型信息是当日用户重新提供的**（快照自述“2026-10-26 用户提供的真实模型配置”“用户明确要求写入交接”）⇒ **属事后补写，不能倒填成“旧摘要/旧交接早已包含”**。
- **“从未存在”与“未继承”要分清**：本次会话第一条交接稿（L12，934 字符）本身也没有模型配置、没有 Maven、没有本地启动方案——它是“按快照执行”的短指令，**不是**模型信息的载体。把“缺失”全部归给压缩，是错误归因（会话内曾有一次助手在思考中认为“摘要漏了模型信息”，而全量扫描显示**任何摘要里都没有该信息可漏**）。

## 6. “勿起停、勿占用”如何被压成“不动”（四跳链路）

| 跳 | 落点 | 写法 | 丢什么 |
| --- | --- | --- | --- |
| 0 | 交接档 | “勿起停、勿占用；E2E/测试自建端口段”+“重启须带 env 三件套” | — |
| 1 | 压缩摘要 | 正文是准确形“不得起停或占用”；但“交接文本应包含”一节写成“**8081/5202 不动**” | “占用（绑端口）”与“重启须带三件套” |
| 2 | 主会话自拟交接约束 | “约束：8081/5202 不动” | 同上 |
| 3 | 交接件 | “8081/5202 不动” | 同上 |
| 4 | 接手方自述 | “不动 8081/5202” | 同上 |
| 5 | 10-26 快照 | “8081/5202 不动” | 同上（另有一句“本地预览使用原端口 + 用户检查时暂停开发”在语境上补了“别打扰”的意思，但句子本身仍是“不动”） |

**为什么这个歧义有害**：原意是**运行面三条禁令**（不许起、不许停、不许占）；“不动”可被读成“别改代码/别改配置”。最危险的两种误读——为跑测试把预览后端停掉重启、或另起一个实例绑同一端口——在“不动”的字面下**都不算违规**。而 env 三件套的绑定也随之脱落：“别动”能推出“别重启”，却推不出“万一重启必须带三个变量”。

**当前准确含义（建议一次性定死）**：这是**用户正在看的预览服务**：只读使用、**勿起停、勿占用**；需要验证时**自建端口段**；万一必须重启，**必须带 env 三件套**。另外“PID 必须实测、不能照抄”这一点没有进任何红线（历史档里记的进程号早已过期）。

## 8. 结论与给主控的建议（按优先级）

1. **最该立刻补的一条**：在常驻纪律里恢复“**新会话第一动作 = 读交接档目录的最新交接档；存档不提交 git**”。它是 10-11 就有的用户规定，热冷分离后失传，是本轮“只读一份快照”的**结构性原因**。
2. **最该立刻纠的一条**：10-24 档的后端启动命令**缺 `cd backend`**，与“原数据库在 `backend/data/`、根目录那份早已停更”的实测事实冲突（两个库并存：根目录一份**约 1MB**、最后写入 10-24 已停更；`backend/data` 一份**审计时为 MB 级、明显大于根目录旧库**、最后写入 10-26 ⇒ 后者在用）。建议在旧档上标“此命令作废”。（两库大小只作**相对量级**对比，不写固定字节数——库会随使用增长。）
3. **最该立刻统一的一条**：端口口径一句话定死（见 §6），并补“PID 必须实测”。
4. **最该防的一条**：用“第 143 行”当密钥锚点应改回“§H5-5”（一插行即指错）；同时把“禁读任何 `.env`”补回（当前快照指向了本地配置备份，两者存在被误读的空间）。
5. **最该保留的一条**：`C` 类信息不要当“丢失”处理——例如“IDE 自带 Maven + 禁 clean”“九册流程”“关闭页签是否继续跑”等本来就只在最新快照里，**要求旧档补是错的**，应把它们并进常驻纪律。
6. **确认项（不能替用户裁）**：主会话模型的两个名称是否同一物；“产品模型保持通用 OpenAI 兼容”与“产品侧配置为某具体模型”的层级关系。
7. **不确定、不要填补的三项**：①热档里三条挂账在 10-22 之后检索不到，无法判断已销项还是漏搬（看板在仓内，本批未查仓）；②10-24 某批“31 改 / 10 不改 / 3 待裁”是否已获用户最终点头，快照未交代；③热档拍棒链在 10-22/10-24 之后未再追加，无法确认这两棒是否按惯例更新过热档（其基线内容停在 10-21）。
