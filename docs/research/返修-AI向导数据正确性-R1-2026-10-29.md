## R1-1（Critical）：按字段合并

### 根因

首轮的 `verbatim` 是**整份**原始条件；`ConditionForm` 编辑任何一行都会 emit 一份**不带
`verbatim`** 的模型，`onConditionChange` 只能整份丢弃 ⇒ 其它未编辑字段（同字段多条件、
取值含逗号等表单表达不了的原条件）被按有损草案重写：

```
原始: code EQ CNY + code NE USD + amount EQ 100
用户改 amount=200 后落库: code EQ CNY + amount EQ 200   ← NE USD 丢失
```

### 修改

`frontend/src/types/condition.ts`：

- `draftFieldsChanged(previous, next)`：逐字段比对，得到被改/新增/删除的编码；
- `dropVerbatimFields(condition, codes)`：从原条件里摘掉这些字段（其余原样，摘空返回 null）；
- `applyDraftEdit(previous, next)`：`next` + 裁剪后的 `verbatim`（未编辑字段继续携带，可继续编辑）；
- `buildConditionOutcome`：**先** `expandFields` 校验草案（非法即 `invalid`），**再**按字段合并 ——
  `verbatim` 里仍有草案行的字段用原条件，其余用草案展开（`mergeVerbatimFields`）。

`frontend/src/views/ExportWizardView.vue#onConditionChange`：统一走 `applyDraftEdit`；内容确实没变
（显示回写）时不记 `touchedConditions`。`persistStepData` 的"未改动且带 `verbatim` ⇒ 不覆盖"保留；
改过之后按合并结果落库。

## R1-4：定义慢加载的等待与自动恢复

### 根因

挂载时 `loadDefinitions()` 与 `loadTask()` 并行；任务先回来就触发 `loadExistingResults →
ensureGridLoaded → loadGrid`，此刻 `defs` 还是 `[]` ⇒ 按"0 字段"失败；定义到达后无人重试 ⇒ 结果页空白。

### 修改（`frontend/src/views/ExportWizardView.vue`）

- `defsInFlight`（单飞）+ `defsLoaded` + `DEFINITIONS_READY_TIMEOUT_MS = 10_000`；
- `awaitDefinitionsReady()`：在途就等（有界），无在途按当前事实判；
- `loadGrid`：字段不可用且该码不在列表、且有在途定义请求 ⇒ 先等，再重判（代次复检）；
  到点 / 加载失败 / 列表仍无该码 ⇒ 原 fail-closed（不载入、不下载、不置位）；
- `recoverGridsAfterDefinitions()`：定义成功后，导出步且已有结果时自动重载当前激活标签（已载入跳过）；
- `retryLoadLists()`：同时 `await loadDefinitions()`（定义是字段可用性的唯一来源），使
  "首轮定义失败"有出口。

## 边界与不声称

- 不做整文件 / 全量测试断言；`npm run build` 在本机受 highlight.js 环境问题阻塞，不作为绿证据。
- 契约层兜底每笔 `select_defs` 会多一次 `GET /api/definitions`（页面未挂载时才走该分支；
  没有缓存，未新增跨请求状态）。
- 定义等待上限 10s：到点仍未就绪按 fail-closed 失败（不无限等）；该常量不是配置项。
- `recoverGridsAfterDefinitions` 只恢复**当前激活标签**（不整批重载所有标签，避免覆盖用户正在编辑的表）。
- 按字段合并依赖 `onConditionChange` 作为唯一编辑入口；其它地方直接改 `draftModels` 的代码
  （如 AI `setConditions`）会整份替换模型 —— 那是"AI 给出新条件"的语义，不参与合并。
- 真机 E2E、真实后端定义服务（503/慢响应真实分布）未验。
