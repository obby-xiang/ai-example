## 二、设计要点提炼（10 条）

1. **「清空对话」要拆成两个语义不同的动作，并且都不要做成静默销毁。**
   业界现状是：**删除会话**（有确认、不可恢复）与 **归档会话**（无确认、可恢复）是两件事；而「清空当前对话但保留会话条目」几乎没人做成一等按钮。VS Code 的 `/clear` 给了一个干净的语义模板：**「清空 = 开一个新会话 + 把旧的归档」**。建议本项目把主按钮定义为「新建对话（并把当前对话归档）」，把「删除」降级到会话列表的 `⋮` 菜单里、带确认。

2. **副作用前设门，且审批框里必须显示真实解析后的目标。**
   确认门的价值在位置：**在执行前**，而不是执行后让用户善后。规则要可配置、要有优先级（deny > ask > allow），要说清「哪个工具、什么参数、影响什么」。GhostApproval 这类事故的根因是**审批框显示的路径与程序实际解析的路径不一致**——确认门一旦"说一套做一套"，等于没有门。

3. **「手动确认模式」不等于每次写操作都弹窗，必须把粒度写清楚。**
   VS Code 官方都专门提示「Manual permissions does not ask for confirmation for every file edit」。所以要么明确"哪些操作必然要确认"（并让用户能一键放宽/收紧），要么给会话级的"本次全部允许/全部拒绝"，不要含糊地宣称"全部确认"。

4. **等待输入 / 等待审批是一种需要外显的状态。**
   VS Code 的应用徽标把「**正在等你输入**」和「有未读结果」分开计数，**仍在生成中的不算**。对带 HITL 的产品，这正是最该被看见的信号——面板标题、会话列表项、应用图标三处都应该能看出"有一个审批卡在你这儿"。

5. **生成中要支持停止，停止后要保住已生成的内容，并给出明确的下一步。**
   停止生成是全行业 100% 覆盖的能力。关键在细节：Send 变 Stop（同一个控件位置）、Stop 结束立刻隐藏、**部分输出不清空**、并给 `继续` / `重新生成` 两个动作。同时输入框要接受"边生成边排队的下一条"，并允许删除或排序队列项。

6. **上下文要可见、可压、可重置，且三者要分开。**
   工具向产品的标配是「用量指示器 + 自动/手动压缩 + 开新会话」。指示器要能看出**是什么在占满上下文**（不只是百分比），压缩要能带保留指令（"重点保留数据库 schema 决策"），重置要有明确指引——VS Code 官方一句「要完全重置上下文，就开一个新会话」就是最好的文案模板。

7. **效率动作要成对出现：每个高频操作都配一个快捷键，且可发现。**
   `新建会话`（本项目建议 `Ctrl/Cmd+Shift+O` 或 `Ctrl+N`）、`切换/搜索会话`、`聚焦输入框` 是最需要的三个。空态里把快捷键提示出来，比写在帮助文档里有用得多。自定义快捷键要避开浏览器与系统的既有绑定。

8. **消息级操作条保持 4–5 个图标：复制、重新生成、点赞、点踩、（+1 个产品特有）。**
   业界实测的共识区间就是 4–5 个；超过这个数量反而降低使用率。反馈优先还是复制优先有分歧（GitHub Copilot 把反馈放最前、Claude 把 Copy 放最前），但**编辑历史消息并重发、从某条消息分支出新会话**这两个"重来"动作值得保留——它们比"再问一遍"更省事，也需要明确告知用户"这会覆盖此后的所有消息"。

9. **空态和错误态决定了第一印象，按"八状态"逐一设计并纳入验收。**
   空态要有 3–6 个基于用户真实上下文的起始任务 + 光标就位 + 快捷键提示；错误态要禁止使用通用的 "出错了"，而要说清发生了什么、保留了什么、**只给一个主恢复动作**，并且**失败时不清空输入框**。"停止/中断/压缩/审批中/额度耗尽"这些中间状态都要能被主动触发来验收。

10. **流式的可访问性策略要显式定下来：不要逐 token 播报。**
    流式期间把播报区域设为 `aria-live="off"`，回答结束后再 `polite` 播报（或只播报"回答开始/回答结束"两个事件）。这一条在厂商官方文档里基本找不到，属于需要团队自己写进规范的部分；同时"重新生成"要让屏幕阅读器知道有新版本产生，而不是静默替换。
