## 1 取消优先：整批工具 settle 之后再查一次权威取消标志

**问题**：一批工具全部结算（`settle`：历史进快照、in-flight 清空、`round` +1）之后，代码只判 `budget.overflow()` 就 `return ToolExecutionResult.conversationHistory(history)`。若取消标志恰在这个窗口内变为**已取消**，本轮仍会把「助手消息 + 工具结果」交回 Spring AI 驱动**下一跳模型调用** —— 用户已经点了停止，系统却还多发一次上游请求。

**根因**：该路径上的取消检查点都在**批次循环内** —— 每个工具执行前（事件边界，`:614`）与执行后（等待期间可能被取消，`:714`）；`settle` 之后到 `return` 之间**没有检查点**（只有越窗失败会提前 `throw`）。即"取消"与"落定 + 交棒"之间缺一道读口，取消能否生效取决于它落在循环里还是落在收尾窗口里。

**修改**（`:780`–`:783`）：

```java
settle(runId, history);
// 取消优先：settle 之后、把历史交回 Spring AI 之前再查一次权威标志 —— 命中即终止本轮，
// 不再返回可驱动下一跳的历史（工具结果与历史已先落定，已发生的副作用不撤回）。
checkCancelled(runId);
if (budget.overflow()) { ... }
return ToolExecutionResult.builder().conversationHistory(history).build();
```

| 件 | 语义 | 锚点 |
|---|---|---|
| 调用点位置 | 在 `settle(...)` **之后**、`budget.overflow()` 判定与 `return` **之前**；顺序即优先级 = **取消 > 越窗失败 > 正常交棒** | `SpToolCallingManager.java:780`、`:783` |
| 复用的读口 | 不新造判据，直接复用既有 `checkCancelled`：`CANCELLED` ⇒ 抛 `StreamViolationException.CANCELLED`（交由 `ResilientChatService` 以取消收尾）；`UNKNOWN`（Redis 读失败）⇒ 仍抛 **`STATE_UNAVAILABLE`**，不折成用户取消 | `:1425`–`:1437` |
| 落定顺序 | `settle` 在前 ⇒ 工具结果与历史**先落定**（快照里已有 `c-1`、in-flight 已清空、`round` 已 +1），取消穿越不撤回已发生的副作用 | `:2521`（`settle` 实现） |

**走法**：把"取消"当成**优先级最高的事实**而不是"循环内顺带看一眼"。收尾窗口里读到取消，本轮就该结束——历史已落定，无需也不该再驱动一跳模型。

**边界**（连读）：

- 本组**只堵"多余下一跳"**，**不撤回已执行的工具**：工具结果、台账、帧都已产生，副作用照旧生效。
- 该读口会**多一次 `cancelState` 读**（每次工具批收尾一次）；`CancellationRegistry#cancelState` 先看进程内本地标志（命中即不再读 Redis），正常路径开销是一次本地命中或一次 Redis 读。
- **新增了一个失败面（如实登记）**：该窗口内若 `cancelState` 返回 `UNKNOWN`（Redis 读失败 / 降级退避期），旧代码会照常交棒，新代码抛 `STATE_UNAVAILABLE` ⇒ 本轮按"基础设施不可用"失败而非继续。这是 **fail-closed 的有意选择**（与 `:1425` 段的 N-1 口径一致：UNKNOWN 不得当作"未取消"），但它改变的是"Redis 抖动时的这一窗口行为"，不是取消语义本身。
- 不改 `settle` 的内容与时机、不改 `budget.overflow()` 判据、不改帧契约。

## 2 决策 guard 时间戳解析：段式兼容

**问题**：读侧把 guard 值合成到待决条目时（WAL 收敛），结算时刻 `resolvedAtMs` 对**两段式**形态 `status|atMs` 恒为 `0`（时间丢失）；只有三段式 `status|atMs|instanceId` 能取到时间。

**根因**：旧实现写死"**必须存在第二个 `|`**"：

```java
long atMs = Long.parseLong(raw.substring(sep + 1, raw.indexOf('|', sep + 1)));
```

两段式时 `raw.indexOf('|', sep + 1)` 返回 `-1` ⇒ `substring(v, -1)` 抛 `StringIndexOutOfBoundsException` ⇒ 被同一个 `catch (RuntimeException)` 吞掉 ⇒ **结论保留、时间缺席**（`resolvedAtMs` 保持默认 0）。裸 `status` 也走同一条异常路径（虽然结果"对"，但靠的是抛异常而不是明文分支）。

**修改**（`:2153`–`:2168`）：

| 件 | 语义 | 锚点 |
|---|---|---|
| 段式判定 | 先 `if (sep >= 0)`：**裸状态根本不进解析**（不再依赖抛异常兜底） | `RunStore.java:2156` |
| 取时间片 | `end = raw.indexOf('|', sep + 1)`；`end < 0` ⇒ 取**余段** `substring(sep + 1)`（两段式），否则取**中间段** `substring(sep + 1, end)`（三段式 / 更多段只认第二段） | `:2158`–`:2159` |
| 值域 | 仍要求 `atMs > 0` 才写入（`0` / 负数 = 缺省）；`空值 / 非数字` 走 `catch`，**只缺时间、不改已成立的状态** | `:2160`–`:2166` |
| 状态门槛 | `mergeableDecisionStatus` 未动：仍只合并 `REJECTED` / `FRONTEND_CANCELLED` / `CANCELLED`；`APPROVED` / `FRONTEND_RESULT` 保持 PENDING（缺载荷，裸状态会让卡"已决但没有内容"） | `:2133`、`:2172` |

**写侧不变**：`tryRecordDecision` 仍写三段式 `status|atMs|instanceId`（`:3169`–`:3170`）。本组只是让**读侧**读得懂旧写者 / 灰度期的两段式与裸状态，便于滚动升级期与历史 WAL 收敛，**不引入新格式、不改写侧、不回填旧值**。

**边界**（连读）：

- **只读侧收敛**：不写任何条目、不改 guard 值，`applyDecisionMarker` 仍是纯合并（`:2126`）。
- 时间**只用于展示与对账**（`resolvedAtMs`），不参与任何终态判定；时间缺席不等于结论缺席。
- 多于三段的形态只读第二段（`instanceId` 及之后一律忽略）；两段式的第二段若为空（`status|`）⇒ 非数字 ⇒ 只缺时间。
- 不改 `decisionOf` / `decidedStatus` 的既有口径（`:3191`、`:3205` 一带仍按第一个 `|` 切状态）。

## 4 边界与不声称

- **不改取消语义**：本批只**加一个检查点**，取消仍由 `CancellationRegistry` 的权威标志决定，`UNKNOWN` 仍 `STATE_UNAVAILABLE`（不折成用户取消）；不改取消收尾链路、不改终态种类。
- **不撤回副作用**：收尾窗口里的取消只终止本轮交棒，已执行的工具结果、台账、帧一律保留（"取消 ≠ 回滚"）。
- **不改 WAL 格式**：`ai:decided:<runId>` 写侧仍是 `status|atMs|instanceId`；读侧兼容是被动读旧形态，**不回填、不升级历史数据**。
- **不改合并门槛**：哪些结论可由 guard 重建（`REJECTED` / `FRONTEND_CANCELLED` / `CANCELLED`）一条未动。
- **本批不触碰**：帧契约（帧类型集与键集）、工具风险分级、确认门三态、`budget` 判据、快照字段集合；`UNKNOWN` 新增失败面带已在 §1 如实登记，未做额外稀释。
