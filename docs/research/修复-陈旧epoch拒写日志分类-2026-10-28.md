## 0 结论速览

| 面 | 问题 | 一句话做法 |
|---|---|---|
| 拒写日志分类 | 取消优先守卫拒写后，日志把「fence 陈旧」与「当前快照已是取消态」并列成一句，运维无法按关键字把「换主」与「取消」分开 | 拒写**冷路径**上补一次单键 `GET` 复核 fence：**fence > 本次 epoch** 则改打含 `STALE_EPOCH` 与**实际 fence 值**的日志；否则原句保留；读不出来按 `null` 回退原句 |

## 1 问题

`RunStore#persist` 在「持租（`epoch > 0`）+ 非取消状态」这条路径上走取消优先守卫；守卫拒写时只返回 `false`，日志侧原本只有一句**合并口径**：

```
{status} 拒写轮次快照 runId=… epoch=…（fence 陈旧或当前快照已是取消态：不覆盖 CANCELLED，也不改会话索引/租约）
```

两个含义完全不同的运维事件被压进同一句：

- **fence 陈旧** = 另一实例已接管本轮续跑权，本实例的写回作废（多实例正常换主，属预期行为）；
- **当前快照已是取消态** = 本轮已被用户/上游取消，非取消状态不得转出 CANCELLED（属状态机守卫）。

同一 runId 在换主窗口里会两种都可出现。合并日志既不能按关键字做告警分类（`STALE_EPOCH` 在多实例运维里是既有约定关键字，见下文「非守卫分支」），也不带 fence 的实际值，排查时还得再回 Redis 手工比对。

既有精确用例 `RunStoreFencedWriteTest#staleEpochWriteIsRejectedAndTheStoredValueIsUntouched` 早就把「拒绝必须可观测（`STALE_EPOCH`）」写成断言（`backend/src/test/java/com/example/configmgr/ai/run/RunStoreFencedWriteTest.java:115`–`:116`，该断言自 `c2f8b2f` 起就在、本批未改测试），但守卫分支的日志里没有这个关键字 —— 于是该用例在陈旧 epoch 场景下**恒红**。

**这是一次口径回归，不是新需求**：`c2f8b2f`（2026-10-24）时代该分支无条件打 `STALE_EPOCH 拒写轮次快照 …`；`152b3a9`（2026-10-26）把「取消优先」守卫**只加到 `DONE`** 上、把 `DONE` 的拒写改成合并句；`0ede5cc`（2026-10-26）再把守卫**扩到全部非取消状态**（含本用例写的 `FAILED`）并把该分支统一成合并句 —— 从此本用例用 `FAILED` 写的那一笔不再出现 `STALE_EPOCH`。本批把「fence 已前进」这一支的日志恢复成带 `STALE_EPOCH` 的分类口径，同时**不退回**「取消态也打 STALE_EPOCH」的旧错。

## 2 根因

拒写原因**在写路径上不可分辨**：取消优先守卫把两处判据合成同一个返回码。

```lua
-- FENCED_TERMINAL_SET
local fence = redis.call('GET', KEYS[2])
if fence and tonumber(fence) > tonumber(ARGV[2]) then
  return 0                                  -- 判据一：fence 陈旧
end
local current = redis.call('GET', KEYS[1])
if current then
  ... if snapshot.status == 'CANCELLED' or snapshot.cancelled == true then
    return 0                                -- 判据二：已是取消态
  end
end
```

（`RunStore.java:362`–`:379`。）Java 侧只看到 `written = false`，两个 `return 0` 无法区分。**修复前**：要让日志带原因，只有两条路 —— ①改 Lua 返回不同错误码；②在 Lua 之外再读一次。本批选 ②，因为改 Lua 的返回码会牵动所有调用点对 `0/1` 的解释，属改契约；而"事后复核"只服务诊断，不动写入语义。

## 3 修改

### 3.1 拒写分支按复核结果分流（`RunStore.java:941`–`:951`）

```java
if (!written) {
    if (guardedStatus) {
        Long fence = fenceAheadOf(runId, epoch);
        if (fence != null) {
            log.warn("STALE_EPOCH 拒写轮次快照 runId={} status={} epoch={} fence={}（fence 已推进到更高 "
                    + "epoch：另一实例已接管本轮的续跑权，本实例的写回作废）", runId, snapshot.getStatus(),
                    epoch, fence);
        }
        else {
            log.warn("{} 拒写轮次快照 runId={} epoch={}（fence 陈旧或当前快照已是取消态："
                    + "不覆盖 CANCELLED，也不改会话索引/租约）", snapshot.getStatus(), runId, epoch);
        }
    }
    ...
    return false;
}
```

`else` 分支保留原文**一字不改** —— 取消态拒写仍走原句（此处 fence 未前进，复核必然返回 `null`，不会把取消误报成换主）。

### 3.2 新增只读复核 `fenceAheadOf`（`RunStore.java:1016`–`:1039`）

```java
private Long fenceAheadOf(String runId, long epoch) {
    try {
        String raw = this.redis.opsForValue().get(fenceKey(runId));
        if (raw == null) {
            return null;
        }
        long fence = Long.parseLong(raw);
        return fence > epoch ? Long.valueOf(fence) : null;
    }
    catch (Exception ex) {
        return null;
    }
}
```

| 件 | 语义 | 锚点 |
|---|---|---|
| 触发面 | **只在拒写冷路径**上调用（守卫拒写之后），成功写入与 `epoch = 0` 分支都不进 | `:942` |
| 判据来源 | 单键 `GET ai:fence:run:<runId>`（`fenceKey`，`:756`），与 Lua 脚本 `KEYS[2]` 同一个键 | `:1029` |
| 判定 | `fence > epoch` ⇒ 返回该值；键缺失 / 值 ≤ epoch ⇒ `null` | `:1030`–`:1034` |
| 失败姿态 | **`null`**（回退原合并日志）：读失败 / 非法数字一律不抛、不记 WARN、不改「这一笔被拒」的结论 | `:1036`–`:1038` |
| 刻意不复用 | 不走 `fenceEpoch`（认领侧读口，读失败 **fail-closed 抛异常**并记 WARN，语义是"取号必须成功"，与这里纯诊断不同） | `:1024`–`:1025` |
| 非守卫分支 | `epoch > 0` 但状态可写时的 `STALE_EPOCH` 日志、`epoch = 0` 的 `warnIfFenceIsAhead` 旁路观测**均未动** | `:953`–`:956`、`:961`、`:1052`–`:1075` |

**不改**：Lua 脚本（`FENCED_SET` / `FENCED_TERMINAL_SET` 一行未动）、任何数据写入（成功/失败路径的 Redis 命令集合、TTL、fence 推进、会话索引与租约释放）、状态机（守卫判据与拒写结论不变）、对外接口（`save` 签名、返回值、异常面）。

## 5 边界（连读才可引用）

- **只改日志，不改行为**：拒写结论、落库值、fence 推进、租约与会话索引的副作用**全部不变**；本批的安全性来自"没有动写入"。
- **仍有一处不可分辨**：`fence <= epoch` 但快照已是 `CANCELLED` 时，日志仍是原来那句合并话术 —— 拒写码在 Lua 里合并，Java 侧**无法**进一步区分。本批只把「fence 已前进」这一支单独分类，**不声称**日志已能穷尽分类所有拒写原因。
- **复核值有时点差**：`GET` 不在 Lua 原子段内，读到的是**复核时点**的 fence；极端情况下在拒写与复核之间 fence 又被推进，日志记录的是更晚的值。这只影响日志里的数字，不影响「被拒」与「拒写原因属于陈旧 epoch」这个结论（fence 只会单调前进）。
- **多一次读**：仅拒写冷路径（守卫拒写之后）一次单键 `GET`，不进正常写入路径，不影响写延迟与 Lua 原子性。
- **失败姿态是本批的硬约束**：读失败 ⇒ `null` ⇒ 原合并日志；**不引入新异常、不把诊断失败升级成写失败**（守卫拒写已经发生，诊断不得再改变结果）。
- **真实 Redis 未验**：单点证据来自 `FakeLeaseRedis`（`backend/src/test/java/com/example/configmgr/ai/run/FakeLeaseRedis.java`），`GET` 与 `Long.parseLong` 的语义在真实 Redis / Cluster 上**未实跑**；按单键设计，无跨槽面。
- **主控只读 diff 验收、未执行任何测试**：上表 RED/GREEN 为施工侧单点回执，**不构成后端定向整类 / 后端全量 / 前端 / E2E / 主 CI 通过**；本笔文档 agent 未跑产品测试、未起停服务、未触碰代码。
- 不新增帧 / 字段 / 指标 / 配置键；日志级别仍是 `warn`，不引入采样或节流（拒写本身已由守卫判定，频次上限 = 每笔拒写一次）。
