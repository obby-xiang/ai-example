## 一、结论先行

**一句话结论**：在本约束下，业界成熟且成本最低的组合不是「简化版 RAG」，而是 **「启动期把 Markdown 知识编译成结构化的 BM25 索引（Lucene 内嵌）→ 用 Spring AI 的 Tool Calling 把检索与读取暴露给模型 → 模型自己决定查什么、查几次」**，再用 **FAQ/口径表的精确直答** 与 **小规模全量注入** 作为两端兜底。三者都不需要向量、不需要新表、不需要新服务。

**三条主证据链**：

1. **全量注入的门槛是明确的**：Anthropic 在 Contextual Retrieval 中直接给出「知识库小于 200,000 tokens（约 500 页材料）时，可以直接把整个知识库放进 prompt，不需要 RAG 或类似方法」，并指出 prompt caching 让这条路「更快更便宜」（<https://www.anthropic.com/news/contextual-retrieval>）。
2. **关键词检索不是退而求其次**：BEIR 基准结论是「BM25 是一个稳健的基线（robust baseline）」，稠密检索在跨域零样本上经常打不过它（<https://arxiv.org/abs/2104.08663>）；Anthropic 的 Contextual Retrieval 也把 BM25 当作与 embedding 并列的一路召回，BM25 负责 embedding 会漏掉的精确串（错误码、专有名词）。
3. **业界正从「预先建索引的管道」转向「给模型工具、让它现场查」**：Anthropic 明确写团队用「just in time」策略——不预先把所有数据处理好，只保留轻量标识（文件路径、查询、链接），运行时用工具动态加载；Claude Code 即「CLAUDE.md 直接进上下文 + glob/grep 现场检索」的混合模式，可「绕开索引过期和复杂语法树的问题」（<https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents>）。LangGraph 的 agentic RAG 教程给的是同一套骨架：retriever 包成 tool，模型决定调不调、调几次，再加「文档相关性打分 → 不合格就改写问题重查」回路（<https://docs.langchain.com/oss/python/langgraph/agentic-rag>）。

**Top3 推荐（按优先级）**

| 排名 | 方案 | 一句话理由 | 对本约束的适配 |
|---|---|---|---|
| 1 | 内嵌 Lucene BM25 + Spring AI `@Tool` 检索/读取（agentic loop） | Java 原生、零服务、零新表；BM25 是跨域稳健基线；工具化让模型自己控制检索次数与粒度 | 索引是文件目录，不碰 H2；Lucene 10 要求 JDK 21，正好匹配 |
| 2 | FAQ/口径表「精确或别名命中直答 + 未命中转 LLM」两级 | 高频问题答案 100% 可控、可引用、零检索误差；成本几乎为零 | 一份 YAML/Markdown 维护，不需要表 |
| 3 | 小规模全量注入 + prompt caching（v0 或兜底） | 官方明确支持 <200K tokens 直接塞；实现成本最低，一天可上线 | 只在知识总量低于阈值时启用；超出即降级到方案 1 |

**不推荐**：Elasticsearch/OpenSearch（运维成本与规模不匹配）、H2 自带全文检索（会建系统表，且 FullTextLucene 与 Lucene 10 不兼容）、GraphRAG/LightRAG（索引成本高一个数量级，且检索分支仍依赖向量存储）。

## 二、先把「规模」算清楚（决定选型的唯一硬指标）

中文 token 保守换算：1 个汉字约 0.6–0.7 token，**按 1 字 = 1 token 做上限估算**最安全。

| 场景 | 文档量 | 单篇字数 | 总字数 | 估算 token（上限口径） | 可否全量注入 |
|---|---|---|---|---|---|
| 下限 | 50 篇 | 800 字 | 4 万字 | 约 4 万 | 可以，且很宽裕 |
| 中位 | 150 篇 | 2000 字 | 30 万字 | 约 30 万 | 临界，需分主题注入 |
| 上限 | 400 篇 | 3000 字 | 120 万字 | 约 120 万 | 不可以，必须检索 |

对照 Anthropic 的 200K tokens 门槛（<https://www.anthropic.com/news/contextual-retrieval>）：

- 总字数 **≤ 15 万字**：全量注入可行，优先做方案 3；
- 总字数 **15 万–30 万字**：全量注入只适合「按主题域切片后注入子集」，主路径应上检索；
- 总字数 **> 30 万字**：必须检索，且要考虑分块与索引更新。

**结论**：本项目按「几十到几百篇、几百到几千字」描述，大概率落在 15 万–60 万字区间，**不能把全量注入当主方案**，但可作为「单主题问答」快路径。

## 三、逐项调研

### 1. Agentic Retrieval / Tool-use 检索

**做法**：不构建「query → 检索 → 拼 prompt → 生成」的固定管道，而把检索能力做成模型可调用工具（`search`/`read`/`list`），由模型在多轮循环中自行决定检索词、次数、是否换词重查、是否读全文。检索器本身可以是关键词/BM25/grep/目录树，不要求向量。

**关键出处与要点**：

- Anthropic《Effective context engineering for AI agents》：明确描述从「pre-inference time retrieval」向「just in time」的转向；agent 维护文件路径、存储的查询、链接等轻量标识，运行时用工具加载；Claude Code 采用混合策略（CLAUDE.md 预加载 + glob/grep 现场检索），好处是「绕开索引过期与复杂语法树」。代价：运行时探索比预计算检索慢，需要好的工具设计与启发式，否则 agent 会浪费上下文、追死胡同。<https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents>
- 同文提出「context rot」：上下文 token 越多，模型准确召回能力越下降；上下文是有限资源，应追求「最小的高信号 token 集合」——这是「不要无脑全量塞」的正文依据。
- Anthropic《Contextual Retrieval》：即便走 RAG 也建议 BM25 + embedding 双路召回再做 rank fusion；纯 BM25 场景可直接借鉴「contextual BM25」——索引前给每个 chunk 前置 50–100 token 的上下文说明。<https://www.anthropic.com/news/contextual-retrieval>
- LangGraph《Build a custom RAG agent》：标准骨架 = `generate_query_or_respond`（决定是否调 retriever tool）→ `retrieve` → `grade_documents`（LLM 二分类判相关性）→ 不合格则 `rewrite_question` 回起点；这套「检索—自评—改写」回路是 agentic RAG 的最小实现。<https://docs.langchain.com/oss/python/langgraph/agentic-rag>
- LlamaIndex《Agentic strategies》：把 agentic 能力分「路由 / query transformation / sub-question / 完整 agent loop」四档——不一定要上完整 agent，路由与查询改写本身即带来大部分收益。<https://docs.llamaindex.ai/en/v0.12.15/optimizing/agentic_strategies/agentic_strategies/>

**没有向量时的检索器选型**：

| 检索器 | 说明 | 出处/证据 |
|---|---|---|
| grep/ripgrep 全文扫描 | Claude Code 的做法；语料在几 MB 级时延迟可接受 | 上述 Anthropic 文；另有工程实践总结称 Claude Code「无预计算索引、无 embedding、无后台索引进程」，靠 Glob/Grep/Read 现场探索 <https://zylos.ai/research/2026-04-19-codebase-intelligence-repository-understanding-ai-agents/> |
| 目录树 + 文件读取 | 先给模型一份「目录/主题清单」，再按 id 读全文（progressive disclosure） | 同上 Anthropic 文 |
| BM25/倒排索引 | 语料变大后 grep 的替代；排序质量显著优于纯扫描 | 见第 2 节 |

**适用条件**：知识条目有稳定 id/标题/章节结构；单次问答允许 1–3 次工具往返（延迟 +1–3 秒）；模型具备可靠工具调用能力。**不适用**：需严格单次低延迟、或模型工具调用能力弱。

**对本项目的含义**：业务文档天然有「标题 + 章节」，非常适合「先列主题、再读章节」的渐进式披露；工具数量控制在 3–4 个，避免 Anthropic 警告的「工具集膨胀导致选择歧义」。

### 2. BM25 无向量落地方案

**先明确一个事实**：BM25 是排序函数，不是数据库特性。凡提供「分词 + 倒排 + BM25 打分」的组件都能用；差别在部署形态、中文分词质量、与现有技术栈的耦合度。

#### 2.1 各选项横向对比

| 选项 | 形态 | BM25 | 中文分词 | 与「H2 + 文件系统」的侵入 | 结论 |
|---|---|---|---|---|---|
| **Apache Lucene 直接内嵌** | Java 库，索引是磁盘目录或内存 | 原生 `BM25Similarity`（Lucene 8.0 起为默认相似度） | `SmartChineseAnalyzer`（smartcn）或 `CJKAnalyzer`（二元组） | 最小：一个依赖 + 一个索引目录，不碰数据库 | **首选** |
| Hibernate Search + Lucene 后端 | ORM 集成，Lucene 后端可内嵌 | 是 | 同上 | 中：需给实体加注解/映射，而知识不在 H2 表里，属「为了用框架而造实体」 | 不匹配 |
| SQLite FTS5 | 独立嵌入式数据库文件 | 内置 `bm25()` 辅助函数 | 默认 `unicode61` 按单字切；需 `tokenize='trigram'`，但 **trigram 至少 3 字才命中** | 中：等于在 H2 之外再引一个存储引擎 | 次选（若允许再加一个嵌入式库） |
| H2 自带全文检索 | 库内实现 | 无 BM25 排序 | 无 | **不可行**：native FullText 的实现是「在数据库里建特殊表存索引」，直接违反「不新增表」；FullTextLucene 依赖老版 Lucene | 排除 |
| PostgreSQL `tsvector` | 需要 PG 实例 | **不是 BM25**：`ts_rank` 不使用全局 IDF | 依赖词典 | 需换/加数据库 | 排除 |
| MongoDB text index | 需要 Mongo | 经典 text index 只有 `textScore`，非 BM25；BM25 在 Atlas Search（Lucene）里，且仅 Atlas | 有限 | 需换/加数据库 | 排除 |
| Elasticsearch / OpenSearch / Solr | 独立服务 | 是 | 需装分词插件 | 大：新增服务、JVM 堆、运维、集群 | 规模不匹配 |
| 手写内存 BM25 | 纯 Java，约 100–200 行 | 自己实现 | 自己切词（二元组即可） | 零依赖 | 兜底方案，几百到几千 chunk 足够 |

#### 2.2 Lucene 内嵌的关键事实（决定它能落地）

- **版本与 JDK 对齐**：Lucene 10.0 起要求 JDK 21 或更高（<https://lucene.apache.org/core/corenews.html>；Elastic 年度总结同样确认 <https://www.elastic.co/search-labs/blog/apache-lucene-wrapped-2024>）。本项目 Java 21，正好是 Lucene 10 的目标运行时。
- **BM25 开箱即用**：`BM25Similarity` 是核心相似度实现，含 k1/b 参数与文档长度归一化（<https://lucene.apache.org/core/9_12_1/core/org/apache/lucene/search/similarities/BM25Similarity.html>）。
- **中文分词三种官方选择**（Lucene 10.1 smartcn 文档原文）：`StandardAnalyzer` 中文按**单字**索引；`CJKAnalyzer`（analyzers/cjk）按**二元组（bigram）**索引；`SmartChineseAnalyzer`（analyzers/smartcn）基于概率模型做**词级**切分，官方标注该 API 为 **experimental**。<https://lucene.apache.org/core/10_1_0/analysis/smartcn/org/apache/lucene/analysis/cn/smart/package-summary.html>
- **工程建议（推断，依据充分）**：业务文档专有名词、产品名、内部术语多，词表切分容易切错；**二元组召回更稳**，代价是索引变大、需配停用词与同义词。可用「标题/章节路径字段用 smartcn，正文字段用 bigram」的双字段策略，查询时两路 RRF 融合。
- **索引形态**：`ByteBuffersDirectory`（纯内存，启动重建）或 `MMapDirectory`（落盘目录，重启免重建），两者都不需要数据库表。

#### 2.3 SQLite FTS5（若团队愿意接受第二个嵌入式库）

- `bm25()` 是 FTS5 内置辅助函数，**返回值越小越相关**（与常见 BM25 直觉相反，排序要 `ORDER BY bm25(t) ASC`）——官方文档 <https://sqlite.org/fts5.html>。
- 中文：默认 `unicode61` 把 CJK 按单字切，短语匹配会失效；`tokenize='trigram'` 按三字符窗口索引，天然支持 CJK 子串匹配，但**少于 3 字查不到**（需回退 `LIKE`）——实践总结 <https://zenn.dev/kanseilink/articles/kanseilink-fts5-trigram-cjk-20260507>、<https://inys.cc/post/sqlite-fts5-trigram>。
- 结论：技术可行，但对 Java 项目意味着多一个 JDBC 驱动、多一个数据文件、多一套备份策略，收益不如 Lucene。

#### 2.4 为什么「H2 自带全文检索」不可用（重要，避免踩坑）

- H2 native FullText 的实现方式是「把索引数据存在数据库的特殊表里」（H2 官方文档原文：the native implementation stores the index data in special tables in the database），直接违反「不新增表」。索引文档：<http://www.h2database.com/h2.pdf>
- H2 的 `FullTextLucene` 与 Lucene 10 不兼容，官方 changelog 明确记录：`Issue #4225: Incompatibility in FullTextLucene with Lucene version 10.x onward`（2.4.240，2025-09-22）。<http://www.h2database.com/html/changelog.html>
- 所以「在 H2 里做全文检索」这条路在 2026 年已经堵死，不要再评估。

#### 2.5 中文场景的补丁：没有向量，如何补「词不达意」

纯 BM25 最大风险是词汇鸿沟（用户说「怎么退款」，文档写「资金原路退回」）。不依赖向量的三种补法：

1. **查询改写/扩展**：让 LLM 把用户问题改写成 2–4 个检索式（含同义说法、业务术语），分别检索后 RRF 融合；LangGraph 的 `rewrite_question` 节点即此模式（<https://docs.langchain.com/oss/python/langgraph/agentic-rag>）。
2. **同义词表**：维护业务同义词/别名 YAML，索引与查询两侧都过 `SynonymGraphFilter`；FAQ 的 `aliases` 字段可复用这份表。
3. **结构化加权**：标题、章节路径、文档标签作为独立字段并 Boost——BM25F 的思想即「标题命中比正文命中更值钱」（综述说明见 <https://dataaspirant.com/blog/bm25-explained/>）。

### 3. 全文塞入 / 长上下文直读

**官方立场**：Anthropic 明确写「知识库 < 200,000 tokens（约 500 页）时，直接把整个知识库放进 prompt，不需要 RAG」，并说 prompt caching 使这条路「延迟降低 2 倍以上、成本降低最多 90%」。<https://www.anthropic.com/news/contextual-retrieval>

**成本机制（两家官方文档）**：

| 厂商 | 触发条件 | 计费 | TTL | 备注 |
|---|---|---|---|---|
| Anthropic | 需显式 `cache_control`；最小可缓存长度 1024 tokens（Sonnet/Opus 4 系），Haiku 3.5 为 2048，Haiku 4.5 为 4096 | 写入 1.25x（5m）/2x（1h）；读取 0.1x | 5 分钟，每次命中自动续期；另有 1 小时档 | 缓存以 `tools → system → messages` 前缀分层，任一层变更使其后全部失效；最多 4 个断点，回看窗口 20 个 block |
| OpenAI | 自动，无需改代码；prompt ≥ 1024 tokens | 无写入费；缓存 token 折扣随模型不同（官方称输入成本最多降 90%） | 内存态 5–10 分钟（最长 1 小时）；部分模型支持 24h 延长保留 | 前缀精确匹配、128-token 粒度；`prompt_cache_key` 可提高命中率；同前缀 >15 req/min 会溢出到其他机器 |

出处：Anthropic <https://docs.claude.com/en/docs/build-with-claude/prompt-caching>；OpenAI <https://platform.openai.com/docs/guides/prompt-caching>

**算一笔账（Claude Sonnet 4.5 官方价：输入 $3/MTok，缓存读 $0.30/MTok）**：

| 知识规模 | 首次写入成本 | 每次提问的缓存读成本 | 评价 |
|---|---|---|---|
| 5 万 tokens | $0.19 | $0.015 | 可忽略 |
| 20 万 tokens | $0.75 | $0.06 | 仍可忽略，但已到官方建议上限 |
| 60 万 tokens | $2.25 | $0.18 | 单次不贵，但多数模型上下文装不下，且质量下降 |

**质量侧硬约束**：Anthropic 的「context rot」与 Liu et al. 2023 的「Lost in the Middle」（信息在长上下文中间时召回显著下降，<https://arxiv.org/abs/2307.03172>）共同说明——**全量注入不是免费的，它把「检索失败」换成了「注意力稀释」**；工程表现为答案漏掉中段某条口径，或把两份文档的规则混在一起。

**判断规则**：

- 总知识 ≤ 15 万字且问题多为「单点事实」：全量注入 + 缓存，最省事；
- 总知识 15 万–30 万字：按主题域切片，只注入命中主题的子集（相当于「粗检索」退化成「选目录」）；
- 总知识 > 30 万字：不要全量，改检索；
- 任何规模下，**系统提示词与工具定义都应放在最前并缓存**，这是零成本优化。

### 4. 结构化知识直答（FAQ 对 / 口径表）

**模式 A：两级问答（精确匹配直答 + 未命中转生成）**

客服/FAQ 机器人的经典结构，行业范式是「retrieval intent + response selector」：FAQ 建成「意图/问题 → 预制回复」候选集，命中高置信度直出预制答案，低置信度才走生成或转人工。Rasa 的 `ResponseSelector` 是代表实现，官方博客描述其为「多个 retrieval intent 对应多个 retrieval action」。<https://rasa.com/blog/response-retrieval-models>

对本项目的具体化（无需向量）：

1. **精确层**：问题归一化（去标点/空格/全半角、繁简统一）后做**哈希精确匹配**，或匹配 FAQ 的 `aliases` 列表；
2. **近邻层**：BM25 取 top1，若分数 ≥ 阈值（用 golden set 校准）且与 top2 有明显间隔，视为命中，直接返回预制答案；
3. **生成层**：未命中进入检索 + LLM 生成，并要求模型标注来源；
4. **回写**：把生成层的高频问题（相同问题出现 N 次）沉淀为新 FAQ，形成闭环。

价值：高频问题（通常占询问量 **60%–80%**）的答案完全可控、可审计、零延迟、零 token；同时天然满足「口径必须一字不差」的合规要求。

**模式 B：把知识做成工具（`lookup_policy(topic)` 返回预制答案）**

不是「检索语料让模型总结」，而是「模型调用一个返回结构化答案的函数」，适合口径表、费率表、时效表这类**字段化知识**。

- Anthropic《Writing effective tools for agents》原则：工具应自包含、对错误健壮、用途极其清晰；参数要有描述性；**最常见失败模式是工具集臃肿、职责重叠导致模型选错工具**。<https://www.anthropic.com/engineering/writing-tools-for-agents>
- Spring AI 侧实现即 `@Tool` + `@ToolParam`，框架自动生成 JSON Schema；官方文档把工具用途直接分为「信息检索（数据库、Web 服务、文件系统、搜索引擎）」与「采取行动」两类。<https://docs.spring.io/spring-ai/reference/api/tools.html>
- 设计要点（综合上述两文）：一个工具只做一件事；返回值 token 经济（返回结构化字段而非整篇文档）；错误返回「未找到 + 可用主题列表」而非抛异常，让模型能自我纠正。

**A 与 B 的关系**：A 是「入口拦截」，B 是「精确字段查询」，二者共用同一份知识源（Markdown 里的 FAQ 段与口径表），只是暴露方式不同；建议同时做，成本很低。

### 5. GraphRAG / LightRAG 类

**结论：本场景不值得做，且「无向量分支」并不成熟。**

- **Microsoft GraphRAG**：索引期要做 LLM 实体/关系抽取 + 社区摘要，成本比向量 RAG 高一个数量级。第三方汇总典型数字是「500 页语料索引 $50–200、约 45 分钟」，而向量 RAG 同规模「低于 $5」；官方仓库自己提示「从小规模开始」以避免意外账单。<https://www.paperclipped.de/en/blog/graph-rag-production/>、<https://github.com/microsoft/graphrag/discussions/1817>
- **LightRAG**：定位「更便宜的图检索」，用 dual-level 关键词（high-level 概念 / low-level 实体）+ 图遍历替代社区摘要遍历，索引成本显著低于 GraphRAG；但其 `local/global/hybrid/mix` 模式在检索实体与关系时**仍查向量存储**，`naive` 模式则退化为普通 chunk 向量检索。<https://github.com/hkuds/lightrag>
- **LazyGraphRAG**：方向对——索引期不做 LLM 抽取与摘要，只用 NLP 名词短语 + 图统计，把所有 LLM 开销推迟到查询期；微软研究院声称其索引成本「与向量 RAG 相同、约为完整 GraphRAG 的 0.1%」。但它主要解决「全局主题总结」，且未作为独立开源件普遍可用。<https://www.datastudios.org/post/microsoft-graphrag-indexing-community-summaries-global-search-and-token-costs>
- **效果侧现实**：有汇总引用 WildGraphBench 数字——BM25 26.9%、naive 向量 RAG 46.2%、GraphRAG local 46.2%、Fast-GraphRAG 50.0%（真实「野生」语料平均准确率）。即便采信，图检索相对向量 RAG 的增益也远小于其成本增幅。<https://dev.to/nikhil_ramank_152ca48266/-graphrag-the-end-to-end-guide-to-reducing-hallucination-and-automating-complex-workflows-44a5>

**何时才考虑图**：问题类型是「跨文档多跳关系」（A 的条款影响 B 的流程、B 又引用 C 的口径）、实体关系是核心资产、且有持续预算做索引维护。**业务 FAQ/口径说明不属于这一类**——它们是「离散事实」，不是「关系网络」。

### 6. 重排序（rerank）的无向量做法

**做法**：BM25 粗排取 top 20–30 → LLM 做一次 listwise 精排（输出重排后 id 列表）→ 取 top 5 进上下文。

**依据**：

- RankGPT（EMNLP 2023）证明零样本 LLM listwise 重排可达到甚至超过有监督的 monoT5-3B；代价是上下文长度与延迟——候选一多就要滑动窗口分批。<https://arxiv.org/abs/2304.09542>
- Anthropic 实验中检索 top-150 再重排到 top-20，把 top-20 失败率从 **2.9% 降到 1.9%**（相对基线 5.7% 降 67%）；注意这个 67% 是「contextual embedding + contextual BM25 + rerank」的合计效果，不是纯 BM25+rerank。<https://www.anthropic.com/news/contextual-retrieval>
- 也有「预算受限重排」研究（EcoRank），说明重排收益随候选数与调用次数递减，需设预算上限。<https://aclanthology.org/2024.findings-acl.773.pdf>

**成本（推断，按公开价目表）**：20 个候选 × 每段 300 tokens ≈ 6K 输入 tokens，输出 300 tokens；按 Sonnet 4.5 计价约 **$0.02/次**；用便宜模型或只在「低置信度查询」触发，成本可再降一个量级。

**什么时候值得做**：

- 检索结果 top1 经常「沾边但不回答」→ 值得；
- 知识条目少（<100 段）、BM25 本身能排准 → 不值得，直接 top3；
- 延迟敏感（首字 <1s）→ 不值得，改用「多查询改写 + RRF」这种零 LLM 调用的融合。

**更便宜的无向量替代（推荐先试）**：①字段加权（标题 3x、章节路径 2x、正文 1x）；②多查询改写 + RRF 融合（零额外模型调用，只多一次 BM25）；③规则过滤（按 `status=active`、`effective_to` 过滤过期文档）。

### 7. 知识保鲜与治理

#### 7.1 「知识作为代码」vs「运营后台编辑」

| 维度 | 知识作为代码（Markdown + Git） | 运营后台编辑（CMS） |
|---|---|---|
| 谁改 | 研发/产品，走 PR | 运营/客服，非技术 |
| 审计 | Git 历史天然完整，可 diff、可回滚 | 需自建审计表（违反「不加表」） |
| 发布 | 合并即生效，可走 CI 校验 | 需要发布流程与权限模型 |
| 时效 | 与代码同节奏，可能成为瓶颈 | 运营自助，响应快 |
| 本约束适配 | **v1 首选**：零基础设施 | v2 若必须，后台写同一份 Markdown 到挂载目录并触发重建，不引入表 |

「文档像代码一样管理」是成熟实践：纯文本 Markdown、版本控制、PR 评审、自动构建发布——Write the Docs 将其定义为 Docs as Code 的核心。<https://www.writethedocs.org/guide/docs-as-code/>

**折中方案（推荐）**：文件系统是唯一事实源，运营后台只是「文件的编辑器」——后台保存时写 `content/knowledge/*.md`，同时写一份 `audit.log`（追加式文本文件），索引服务监听文件变更重建；既不新增表，也不牺牲运营效率。

#### 7.2 元数据惯例

治理通行做法是「每篇有 owner、有复审周期、有状态」：指派具名负责人、按类别设季度复审、用元数据标记最后复审时间。<https://knowledge-base.software/guides/knowledge-base-governance-framework/>、<https://www.archbee.com/blog/knowledge-base-management>

落到 Markdown 的 YAML front matter（front matter 是静态站点/文档工具的通用约定，<https://markdific.com/docs/markdown/front-matter/>）：

```yaml
---
id: refund-policy            # 稳定标识，引用与评估都用它
title: 退款政策
version: 3
status: active               # draft | active | deprecated
effective_from: 2026-07-01
effective_to:                # 空表示长期有效
supersedes: refund-policy-v2
owner: 客服运营组
review_due: 2027-01-01
source:  《退款管理办法（2026 修订）》第 4 条
tags: [退款, 资金, 售后]
aliases: [怎么退款, 退款多久到账, 退款规则]
---
```

**关键规则**：

- `id` 一经分配不复用；改标题不改 id；
- `effective_from/to` 在**索引期**过滤：未生效与已过期文档不进索引（或降权并标注）；
- `supersedes` 形成版本链，旧版保留但 `status: deprecated`，用于回答「以前是怎么规定的」；
- 索引重建时把 `id + version + effective_from` 写进索引的 stored field，问答时可直接回显「依据：退款政策 v3（2026-07-01 生效）」。

#### 7.3 引用来源（citation）的主流做法

三种层次，成本从低到高：

1. **提示词级引用（推荐起点）**：检索工具返回的每段都带 `[doc_id §章节]` 前缀，系统提示要求「每个结论后标注来源 id，未在资料中出现的内容必须说不知道」。成本为零，但模型可能编造 id → 需**后置校验**（正则抽 id，与索引 id 集合比对，不合法则重答或降级为「未找到依据」）。
2. **API 级引用**：Anthropic 的 Citations API 让模型对每个论断返回原文片段级引用（`char_location` / `page_location` 等），前提是把文档作为 `document` 内容块传入并开启 `citations`（会修改系统提示，从而影响缓存）。<https://simonwillison.net/2025/Jan/24/anthropics-new-citations-api/>
3. **UI 级引用**：前端把 `doc_id §section` 渲染成可点击来源卡片，点开定位原文段落——这是「可验证」体验的关键，成本主要在前端。

对本项目：**第 1 层 + 第 3 层**即可满足绝大多数业务诉求；第 2 层只在「必须逐句给出原文依据」的合规场景才需要，且它要求把全文作为 document block 传入，与「检索后只传片段」的模式需重新权衡。

### 8. 评估

**业界轻量评估的共识结构**：

- **先建 golden set，再谈优化**。规模建议：20–50 条起步、80–150 条可获得稳定信号、超过 400 条收益递减；低于 80 条时 LLM judge 方差会淹没真实差异；按主题分层，每个主要文档类别至少 5 条。<https://www.mintlify.com/Helicone/helicone/guides/evaluation-with-ragas>、<https://callsphere.ai/blog/production-rag-agents-langchain-ragas-eval-2026>
- **检索与生成分开评**：检索侧 recall@k / hit@k / MRR；生成侧 faithfulness（答案是否只依据给定上下文）、answer relevance。<https://www.javacodegeeks.com/2026/04/rag-architecture-on-the-jvm-building-a-production-ready-pipeline-with-langchain4j.html>
- **LLM-as-judge 必须人工校准**：季度抽 50–100 条让人评、算与 judge 的相关性，低于阈值就改 rubric 或换 judge；judge 与生成不要同族模型（自偏好偏差）；judge 模型版本要钉死，升级视为基线重置。<https://www.qdrant.tech/documentation/search-evaluation/pipeline-output-quality/>、<https://myengineeringpath.dev/genai-engineer/rag-evaluation/>

**针对本项目的落地建议**：

| 指标 | 定义 | 计算方式 | 阈值建议 |
|---|---|---|---|
| 检索命中率 hit@5 | 期望文档 id 是否出现在 top5 | 规则，零成本 | ≥ 0.9 |
| 答案正确率 | 关键事实是否与标准答案一致 | LLM judge 0/1 | ≥ 0.85 |
| 引用合法率 | 回答中引用的 id 是否真实存在 | 规则（id 集合比对） | = 1.0 |
| 拒答正确率 | 知识库没有的问题是否明确说不知道 | LLM judge | ≥ 0.9 |
| 平均工具调用次数 | agent 效率 | 埋点 | ≤ 2.5 |

**成本**：60 题 × 约 2K 输入 + 300 输出 ≈ **14 万 tokens/轮**，按 Sonnet 4.5 约 **$0.5/轮**，用便宜模型约 **$0.05/轮**。适合每次改提示词/改索引策略后跑一次，以及每日夜间回归。

**注意**：不要用「同一批题反复调参」——golden set 要留 **20%** 作为 holdout，否则指标虚高。

## 四、候选方案谱系（总表）

评分说明：5 = 完全满足约束且性价比最高；4 = 满足约束但有明显取舍；3 = 需额外组件或运维；2 = 引入较重依赖；1 = 与约束冲突。

| # | 方案 | 原理 | 依赖 | 知识规模上限 | 适用性 |
|---|---|---|---|---|---|
| A | 全量注入 + prompt caching | 整库进 system，缓存前缀复用 | 仅模型 API | ≤ 20 万 tokens（官方建议） | 4（小规模最优，大规模失效） |
| B | Agentic 工具检索（grep/目录 + 读取） | 模型自己探索，无预建索引 | 无（文件系统） | 几 MB 文本（grep 延迟可接受） | 4（实现极简，排序质量弱） |
| C | **内嵌 Lucene BM25 + 工具化** | 倒排索引 + BM25 排序，工具返回片段 | lucene-core + analyzers（+ smartcn） | 数万～数十万 chunk | **5** |
| D | SQLite FTS5 | 嵌入式全文库，`bm25()` 排序 | sqlite-jdbc + 数据文件 | 数万 chunk | 3（多一个存储引擎；中文需 trigram 且 3 字起） |
| E | H2 自带 FullText | 库内倒排表 | 无 | — | 1（建系统表 + Lucene 10 不兼容） |
| F | PostgreSQL tsvector | GIN 倒排 + ts_rank | 换/加 PG | 大 | 2（要换库；ts_rank 非 BM25） |
| G | MongoDB text / Atlas Search | text index 或 Lucene BM25 | 换/加 Mongo | 大 | 2（要换库；经典 text index 非 BM25） |
| H | Elasticsearch / OpenSearch | 独立搜索引擎 | 新服务 + 运维 | 很大 | 2（规模不匹配，运维成本高） |
| I | 结构化 FAQ 直答 + 工具化口径 | 精确/别名/近邻命中返回预制答案 | 无 | 数千条 FAQ | **5**（与 C 互补） |
| J | GraphRAG / LightRAG | 实体关系图 + 社区/关键词检索 | 图存储 + 向量存储 + LLM 抽取 | 大 | 1（成本高一个量级，且仍依赖向量） |

## 五、推荐架构（可直接落地）

### 5.1 分层结构

```
                    ┌──────────────────────────────┐
用户提问 ──► 入口层  │ 1) FAQ 精确/别名命中 → 直答   │
                    │ 2) 口径表字段查询 → 直答      │
                    └──────────────┬───────────────┘
                                   │ 未命中
                    ┌──────────────▼───────────────┐
                    │ Agent 层（Spring AI ChatClient）│
                    │  工具：                        │
                    │   list_topics()  目录/主题树    │
                    │   search(query,k) BM25 检索     │
                    │   read_doc(id,§)  读章节全文    │
                    │   lookup_policy(topic) 预制口径 │
                    └──────────────┬───────────────┘
                                   │
                    ┌──────────────▼───────────────┐
                    │ 索引层（启动期构建，文件监听重建）│
                    │  Markdown + YAML front matter  │
                    │  → 结构感知切分（按标题）       │
                    │  → 前置「标题 > 章节路径」       │
                    │  → Lucene（BM25 + 中文分析器）  │
                    └──────────────────────────────┘
```

### 5.2 索引构建（关键细节）

1. **切分按结构，不按字数**：以 Markdown 标题为边界，一段一个 chunk；超过 800 字的段落再按句号切。论文 MDKeyChunker 在 18 篇 Markdown、30 个查询上实测「BM25 + 结构感知切分」Recall@5 = **1.000**、MRR = **0.911**，而稠密检索全流程 Recall@5 = **0.867**——小语料上结构比语义模型更重要。<https://arxiv.org/abs/2603.23533>
2. **前置上下文用「标题 > 章节路径」即可，不必 LLM 生成**：Anthropic 的 contextual retrieval 用 LLM 生成 50–100 token 说明，但同方向后续研究发现——在 BM25/混合检索下「免费的章节路径前缀」与「每 chunk 一次 LLM 调用」没有显著差异（同上论文摘要与结论），直接省掉索引期 LLM 成本。
3. **字段设计**：`doc_id`（stored，用于引用）/ `title`（indexed + stored，Boost 3.0）/ `path`（章节路径，indexed，Boost 2.0）/ `body`（indexed，Boost 1.0）/ `tags`（indexed，Boost 1.5）/ `version` + `effective_from`（stored，用于回显与过滤）/ `status`（过滤：只索引 active）。
4. **分析器**：正文用 `CJKAnalyzer`（二元组）或 `SmartChineseAnalyzer`（词级，官方标 experimental）；建议先二元组，召回优先，再用同义词表补精度。
5. **重建策略**：启动时全量构建（几百篇秒级）；运行期 `WatchService` 监听目录，增量更新受影响 doc_id（先 delete by term 再 add）；提供 `POST /admin/knowledge/reindex` 手动触发；索引目录带 `schema_version`，不兼容时自动重建。
6. **不碰 H2**：索引是文件目录（`data/knowledge-index/`），元数据在 front matter 里，运行态缓存放 Redis（已有组件）。

### 5.3 工具契约（建议直接照此实现）

```java
// 只读、幂等、返回 token 经济
@Tool(description = "按关键词检索业务知识库，返回最相关的片段。用户问业务规则、流程、口径时先调用它。")
SearchResult search(
    @ToolParam(description = "检索词，使用业务术语；可多次调用换词") String query,
    @ToolParam(description = "返回条数，默认 5，最大 10") int topK);

@Tool(description = "读取指定文档的完整章节。当检索片段不足以回答时使用。")
DocSection readDoc(
    @ToolParam(description = "文档 id，来自 search 结果") String docId,
    @ToolParam(description = "章节路径，可选；不传返回目录") String section);

@Tool(description = "查询已标准化的业务口径（费率、时效、限额等）。命中返回权威表述，未命中返回相近主题列表。")
PolicyAnswer lookupPolicy(@ToolParam(description = "口径主题，如 refund_window") String topic);

@Tool(description = "列出知识库的主题目录。不知道该查什么时先调用。")
List<Topic> listTopics();
```

**返回格式建议**（控制 token 且利于引用）：

```
[refund-policy §3.2 退款时效] (v3, 2026-07-01 生效)
收到退货后 3 个工作日内原路退回……
---
[refund-policy §3.3 特殊情形] ...
```

### 5.4 系统提示要点

- 「回答业务问题前，先调用 `search` 或 `lookupPolicy`；不要凭记忆回答。」
- 「只能依据工具返回的内容作答；资料中没有的，明确说不知道，并建议咨询渠道。」
- 「每个结论后用 `[doc_id §章节]` 标注来源；不得编造 id。」
- 「若首次检索结果不相关，换用同义业务术语再检索一次，最多 2 次。」
- 「涉及金额、时限、比例时，逐字引用原文数字，不做换算。」

### 5.5 降级路径

| 故障 | 降级 |
|---|---|
| 检索无结果 | 返回「未找到依据 + 主题目录 + 人工入口」，不让模型自由发挥 |
| 工具调用失败/超时 | 回退到「全量注入（若总量允许）」或纯 FAQ 直答 |
| 引用 id 非法 | 后置校验拦截，重答一次；仍失败则去掉引用并提示「请以原文为准」 |
| 索引构建失败 | 保留上一版索引目录，健康检查置 degraded，不影响已有问答 |

## 六、实施顺序（建议 3 步走）

**第 1 步（1–2 天）：FAQ 直答 + 全量注入兜底**——最高频 30–50 条 FAQ 做成 YAML（问题、aliases、答案、来源、生效日）；入口做归一化精确/别名匹配；未命中时把「全部 FAQ + 核心文档」放进 system prompt（若 ≤ 15 万字），开启 prompt caching。产出 = 可用问答能力 + 一份真实提问日志（用于建 golden set）。

**第 2 步（3–5 天）：Lucene BM25 索引 + 3 个工具**——索引构建（结构切分、字段 Boost、中文分析器）；`search` / `readDoc` / `listTopics`；接 Spring AI `@Tool`，系统提示改为「先检索再回答」；加引用后置校验。产出 = 可回答长尾问题，且答案带来源。

**第 3 步（2–3 天）：评估与调优**——从日志抽 60 题建 golden set（含 10 题「知识库没有」负样本）；跑 hit@5 / 正确率 / 引用合法率 / 拒答正确率；按失败样本调同义词表、字段 Boost、切分粒度、是否加 LLM 精排。产出 = 可回归基线。

## 七、风险与反模式

| 风险 | 表现 | 缓解 |
|---|---|---|
| 词汇鸿沟 | 用户口语 vs 文档书面语，BM25 召不回 | 查询改写 + 同义词表 + FAQ aliases；把「用户原话」沉淀进 aliases |
| 中文分词切错专名 | 产品名被切断，检索不到 | 二元组召回 + 自定义词表/同义词；标题字段单独加权 |
| 模型不调用工具 | 直接凭记忆编答案 | 系统提示强约束 + 工具描述写清「何时必须调用」+ 评估里加「是否调用」埋点 |
| 工具调用过多 | 延迟高、token 浪费 | 限制最多 2 轮检索；`search` 返回精简片段；提示「信息足够就回答」 |
| 知识过期 | 答旧口径 | front matter 的 `effective_to` 在索引期过滤；回答回显版本与生效日 |
| 引用编造 | 回答里出现不存在的 id | 后置正则抽取 + id 集合校验，失败即重答 |
| 全量注入的注意力稀释 | 答漏中段条款 | 只在 ≤15 万字时用；按主题切片；关键口径走 `lookupPolicy` 直答 |
| 索引与源文件不一致 | 改了文档没生效 | 文件监听 + 手动 reindex 接口 + 索引里存 `content_hash`，健康检查比对 |

**明确不要做**：

- 不要为了「以后可能上向量」而先抽象一层通用 retriever——本约束下这层抽象只会增加复杂度；
- 不要把 BM25 的 top-k 设成 20 再全塞进上下文（context rot + 成本）；
- 不要让模型自由发挥「根据你的理解总结一下政策」——业务口径必须逐字可追溯；
- 不要用 H2 的全文检索（建表 + Lucene 版本不兼容，双重坑）。

## 十、留给决策者的三个问题

1. **知识总量到底是 15 万字还是 60 万字？** 这一个数字决定「先做全量注入」还是「直接做索引」；建议先统计现有文档的字数分布，不要凭感觉。
2. **口径类问题占比多少？** 若超过 **40%**，`lookupPolicy` 直答的收益会大于检索优化，应优先做。
3. **谁维护知识？** 若运营必须自助编辑，第 1 步之前就要把「后台写文件」的目录约定定下来，否则会返工。
