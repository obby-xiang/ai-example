## 一、组件库层面：步骤节点的点击语义

| 组件库 | 是否内置点击 | 官方语义与限制 |
|---|---|---|
| **Element Plus `el-steps`/`el-step`** | ❌ 不内置 | 官方 API 只有 `active`、`process-status`、`finish-status`、`status` 等**展示型**属性，没有 `onChange`/`clickable`/`disabled`，也没有任何点击示例。点击跳转必须自己挂 `@click` 再自行更新 `active` |
| **Ant Design Steps** | ✅ 传 `onChange` 即变为可点击 | 官方 demo 的 `onChange` 是**无条件** `setCurrent(value)`，组件不限制"只能点已完成步骤"；每个 `StepItem` 有 `disabled`（"禁用点击"）。维护者明确表态：能否点击因业务而异，"应该由业务自行实现" |
| **MUI Stepper** | ✅ `StepButton` | `linear` 模式自动把未到达步骤设为 `disabled`；`non-linear` 不自动 disable，任意点进入，**完成与否由实现方判断**。官方硬性无障碍要求：可点击 `StepButton` 必须有 `aria-controls` 指向内容区 |
| **Material Design 原规范**（m1/m2） | 规范层定义 | 步骤类型：**editable**（会话内可回改）/ **non-editable**（不可回改，适用于"用户之后无法编辑"或"允许编辑会分散完成表单的注意力"）；stepper 类型：**linear**（必须按序完成才能前进）/ **non-linear**（任意点进入）。另有 optional step、error state、stepper feedback（仅当步骤间有长延迟时使用） |
| **Vuetify `v-stepper`** | ✅ | 默认 **non-editable steps**（强制线性）；`editable` = 任意时刻可选中并导航过去；`linear` = 始终按定义路径走；`non-linear` = 用户自选顺序；另有 error state |
| **PatternFly（企业级）** | ✅ 侧栏可点 | **Visited step**："In most cases, people can select this step to return to an earlier point in the flow"；**Disabled step**："Later steps are usually disabled so the flow stays sequential"；"People can jump to an **enabled** step by selecting it in the sidebar"；**"After submit, hide the steps sidebar. People can no longer edit earlier steps."** |
| **USWDS Step Indicator（政府规范）** | ❌ 明确反对 | "The step indicator is designed to complement standard back/next navigation in a linear sequence, **not to be navigation of its own**"、"Provide navigation separately"、不适用于非线性流程；pending 段落"should still maintain accessible contrast and **not appear disabled**"；用 `aria-current="true"` 标当前步 |

关键结论（三条，都很重要）：
1. **没有任何一个主流组件库把"只能跳到已完成步骤"写进组件契约**。MUI 的 linear 是唯一"组件级自动禁用"的例子，且它是靠 `activeStep` 推导 disable，而不是"校验通过才解锁"。【官方文档】
2. 点击权限是**业务规则**：Ant Design 明确把这件事推给业务（官方 issue #15482 维护者原话："不同的业务场景下，Step 能否点击/点击效果可能都不一样，所以应该由业务自行实现"）；MUI non-linear 文档也写"完成与否由你自己实现判断"。【官方发布说明/维护者表态】
3. PatternFly 给出了最贴近本场景的成熟模型：**可点击 ⟺ 已访问（visited）且未禁用；后续步骤默认 disabled；提交完成后整条步骤栏隐藏、不得再编辑**。USWDS 则代表另一极：步骤条根本不是导航。【官方文档】

## 二、线性 vs 非线性：业界共识

**共识 1：命名体系已经统一。** linear（未到达步骤禁用）/ non-linear（全部可进）/ editable vs non-editable（能否回改）三组正交维度，在 MUI、Vuetify、Material 原规范里语义一致。【官方文档】

**共识 2：默认应是"线性 + 已访问可回跳"。** PatternFly 的原则化表述最接近共识：前向步骤默认 disabled 以保持顺序，**已访问过的步骤可以点回去**；USWDS 则直接要求用 Back/Next 按钮承载导航、步骤条不承担导航。【官方文档】

**共识 3：前跳需要逐站校验解锁，回跳一般无条件允许。** MUI linear 是组件级的"未到达即禁用"，属于最严格的一档；PatternFly 的 progressive wizard 允许"回到前两步重选、后续步骤随之更新"。【官方文档】

**共识 4：回看/回改必须预填，且改完不必重走全程。** GOV.UK「Check answers」：“每个 section 旁给 Change 链接（含 visually hidden 文本说明改哪一段）”，“用户返回上一个答案时，**必须预填已填内容，页面要和上次看起来一致**”，改完点 Continue **直接回到 check answers**，不需要重走整个流程。Baymard 的收银台研究同向：“多步流程要允许用户直接从 review 页修改前面信息，而不是强迫他们往回走完整个流程”。【官方设计系统 + 商业研究机构】

**共识 5：只有"用户不能一次性完成 / 需要自选顺序"时才用非线性。** GOV.UK Task list 的使用门槛写得很硬：只在有研究证据表明用户"不能或不想一次完成"且"需要能自己选顺序"时使用；**"不要用于必须按特定顺序完成的长流程"**。【官方设计系统】

## 三、工作流/流水线产品的步骤查看范式

| 产品 | 运行中任务 | 已结束任务 | 点击节点后看到什么 | 变更动作 |
|---|---|---|---|---|
| **GitHub Actions** | 可以进入 run 页 → Jobs 或可视化图 → 点 job，展开 step 与日志；社区讨论确认"每个 step 的输出在该 step 结束时就出现，直接打开 job 视图能看到部分更新"（本质是准实时日志，不是 SSE 式进度条） | 同一套 UI；run 概览显示 conclusion（success/failure/**canceled**/neutral）；失败步骤**自动展开**；可选行号取 permalink；日志可搜索（只搜已展开的步骤）、可下载 archive | **只读日志视图** | 重跑 workflow / 重跑失败 job（在 run 页操作） |
| **Jenkins Blue Ocean** | Pipeline Run Details 的 Pipeline 标签直接展示 stage / 并行分支 / steps 及 console output | 同页只读；另有 Changes / Tests / Artifacts 三个只读标签 | console 输出；**某步失败时该标签自动默认展示失败步骤的日志** | 视图允许 edit / replay（重跑）该 run |
| **GitLab CI** | Pipeline details 页展示全部 job 的 graph；可 cancel 运行中的 pipeline；manual job 在 graph 上直接给 Run(play) 按钮；hover job 会高亮其前置依赖 | 同一 graph 只读；可 retry failed jobs、可 delete pipeline | job 详情/日志 | 动作**随状态变化**：运行中=cancel，失败=retry |
| **Argo Workflows** | 打开 workflow → 点节点 → 右侧 node details 面板；第三方文档："Selecting a step in the sidebar loads its logs"；3.6 起"能看到 pod 的 live logs" | 同面板，可看归档（archived）workflow 的节点信息 | **只读详情面板**（日志、输入输出、节点元信息；3.6 起 URL 变成可点链接） | 对单个 node 的 retry（3.6 起可在 UI 做，"即使 workflow 已经成功"）；历史上诉求"从失败节点重试而不是从头重跑"，早期只能 CLI（`argo retry --node-field-selector`） |
| **Airflow** | Grid/Graph/Tree 里点 task cell → 看日志，也能 mark success/failed/clear；失败与重试任务用**颜色 + tooltip**区分 | Task Instance 详情页**保留历史**（重试/clear 记录），每个 try 的日志都可查；DAG run 终态由叶子节点决定 | 日志 + 任务实例历史（只读） | clear（重跑）、mark success/failed；clear 必须显式选择作用范围（Past/Future/Upstream/Downstream/Recursive/Failed） |

**归纳出的公共范式（跨 5 个产品一致）：**
1. **节点点击 = 查看，不是编辑。** 运行中给实时/准实时日志，已结束给归档日志，形态都是只读详情面板。
2. **所有变更动作（重跑/重试/取消/标记）是详情面板里受状态约束的显式按钮**，不存在"点节点即改状态"。
3. **失败节点默认被定位/自动展开**（GitHub 自动展开失败步骤、Blue Ocean 自动切到失败步骤日志）。
4. **失败后回看历史完全自由且只读**，重跑走"新一次执行（try / new run）"而不是就地改写历史——Airflow 的 try_number 历史、Argo 的单节点 retry、GitHub 的 re-run 都是这个模型。
5. 运行中 vs 已结束的差异体现在**可用动作集合**（cancel vs retry），而不是"节点能不能点"。

## 四、「只读查看模式」的交互范式

**业界更偏"快照/汇总面板"，而不是"整页 disabled 表单"。** 证据：
- GOV.UK Check answers：编辑态与查看态**分离**——查看态是一个 summary 列表（纯文本答案），每个 section 右侧挂 Change 链接进入编辑态。返回编辑态时数据预填、布局与上次一致。【官方】
- PatternFly：提交后**隐藏步骤栏、不允许再编辑早期步骤**；结果耗时长就用 progress 屏；"wizard 启动后台任务时，提供一个 monitor progress 链接或 Close 按钮"。对后台作业场景这句话几乎是为本场景写的。【官方】
- GitHub/Argo/Airflow/Blue Ocean 的已结束详情全部是"只读面板 + 日志 + 产物下载 + 重跑动作"。【官方文档】

**如果非要复用表单布局，控件选型的硬事实：**
- `disabled` 的控件**不可聚焦、不参与约束校验、不会被提交**——键盘与读屏用户在 Tab 序列里根本到不了它，也就无法读到/复制它的值。【官方：MDN】
- `readonly` 的控件**仍可聚焦、可选中复制、会随表单提交**，只是不可编辑；ARIA 层面 `aria-readonly`（不可编辑但仍可操作）与 `aria-disabled`（不可操作）语义不同。【官方/规范】
- 结论：**"展示历史值"应当用 readonly 语义或纯展示文本，不要用 disabled**；只有"该控件此刻确实不可用"时才用 disabled。【推断，但由 MDN 语义直接推出】
- 对比度：WCAG 1.4.3 明确豁免"属于 inactive（disabled）用户界面组件"的文字，因此 disabled 灰字（Ant Design `colorTextDisabled: rgba(0,0,0,0.25)`、Material inactive steps `38% black`，实际约 1.9–2.9:1）**在 WCAG 上合法但可读性很差**；业界的常见误用是把这个豁免套到"仍有信息价值的内容"上（此时既不合规也不好读）。【规范 + 第三方解读】
- 视觉上"不可点"也必须真的不可点，反之亦然：GOV.UK 的 "Cannot start yet" 是**灰字 + 整行不加链接**并明说"状态整行链接"是有意设计；其研究还指出用户会误把状态标签当按钮点，所以状态被重新设计得"不那么像按钮"。USWDS 则要求 pending 段落"保持可访问对比、**不能看起来像 disabled**"。【官方设计系统】

## 五、失败/取消状态的步骤条呈现

**组件库层面：** MUI 有独立 error step；Vuetify 有 error state（含 alternative label + error）；Ant Design 的 `status` 可取 `error`，且**状态可以在单个 Step 上覆盖由 `current` 推导出的状态** —— 也就是说"失败的是第 2 步、当前停在第 4 步"这种精确表达是组件原生支持的。Ant Design 的 `colorError = #ff4d4f` / `colorErrorBg` 是语义 token。【官方文档】

**产品层面的通行做法：**
- 失败步骤**默认被定位/自动展开**：GitHub Actions "Any failed steps are automatically expanded"；Blue Ocean "If a particular step during the run fails, this tab automatically defaults to showing the console log from the failed step"。
- 失败后**回看历史完全自由且只读**：Airflow 的 Task Instance History（每个 try 的日志）；GitHub 的 partial re-run 会保留前次 attempt 的日志 archive。
- 重试是**显式动作**，不是"点节点即重试"：GitLab 在 pipeline graph 上 retry failed jobs；Argo 3.6 起在 UI 里对单个 node retry；Airflow 点失败任务后点 Clear（并需选择作用范围）。
- 红色**只用于错误**：GOV.UK 明确"Do not use the red background colour for any status text except errors"，并要求能从源头即时纠错时就用 error summary + inline error 而非"存着一个错误状态"。【官方】

## 六、对本场景的设计启示

前提重述：3~4 步的导入/导出向导，步骤内含作业执行（SSE 进度、校验问题表、文件结果）；任务生命周期 = 进行中（ACTIVE / FAILED 均未终态）与已结束（COMPLETED / CANCELLED）。

### A. 进行中任务（ACTIVE，含作业在跑）
- **节点可点性（建议）**：当前步骤高亮但**点击无动作**；**已完成步骤可点 → 只读查看**；未到达步骤不可点且必须"看起来就不可点"。这正是 PatternFly 的 visited + enabled 模型【官方文档推荐】，也是 AntD/Vuetify/MUI 里最严格档与最宽松档之间的主流折中。不要采用 MUI 的完全 non-linear（任意跳）作为默认，除非有研究证据表明用户需要自选顺序（GOV.UK 的使用门槛）。
- **点击语义必须单一**：工作流产品全部是"点节点 = 查看"。若又想"点已完成步骤 = 跳回去改参数"，会出现节点语义二义（查看 vs 编辑）。建议：**节点点击一律 = 查看（抽屉/侧栏只读面板，SSE 进度实时流入）**，跳转/编辑走页脚动作按钮或面板内的显式"修改该步骤"按钮。这是从 GitHub/Argo/Airflow/BlueOcean 的一致范式推断出的取舍【推断】。
- **编辑正在进行中的步骤参数是危险动作**：平台必须先回答"该步骤的作业能否安全取消/重跑"。若不能，应该提供"取消本次作业"而不是"直接改参数后重建"。Ant Design 维护者与 MUI non-linear 都明确这类规则属于业务，组件不会兜底【官方表态】。
- **前跳 gating**：只允许跳到"已完成且校验通过"的步骤；失败步骤与当前步骤之间不允许跳过。回跳无限制。
- **SSE 与步骤条的衔接**：把 SSE 进度放在**步骤内的进度条**，而不是用步骤条本身当进度指示器（步骤条表达的是流程阶段，MUI 原规范里"stepper feedback"也只在步骤间有长延迟时才用）【官方文档 + 推断】。

### B. 已结束任务（COMPLETED / CANCELLED）
- **全部节点可点，但一律只读查看** —— 直接对标 PatternFly "After submit, hide the steps sidebar. People can no longer edit earlier steps."【官方文档推荐】，以及 GitHub/Argo/Airflow 的归档页范式。
- **只读呈现方式优先级（我的建议排序）**：
  1. **只读快照面板/汇总页**（结构化字段 + 校验问题表 + 文件结果列表 + 下载），对照组 GOV.UK Check answers 与各大工作流产品的详情面板【官方范式】；
  2. 若产品要求复用表单布局：字段用 **readonly 语义 + 视觉弱化但保持对比度**（可聚焦、可复制、读屏可读）；
  3. **不要整页 disabled**：Tab 序列会变空、读屏取不到值、灰字对比度低（虽然 WCAG 1.4.3 豁免）【规范推导】。
- **CANCELLED 的特殊处理**：必须区分"未执行/已跳过/已取消"，并展示取消人、取消时间、取消原因；状态文案用中性色，**不要用红色**（GOV.UK：红色只用于错误）。
- **"想改历史任务"的出口**：业界普遍做法是**复制为新任务/新 run**（Argo 的 resubmit、Airflow 的 trigger、GitHub 的 re-run），而不是就地编辑已完成记录。这样同时满足审计与一致性【官方产品范式 + 推断】。在导出场景下这通常正是用户真正想要的（用同一份配置再跑一次）。

### C. 失败任务（FAILED，未终态）
- **呈现**：失败步骤红色 + 明确文本"失败"（不能只靠颜色）；用 AntD `StepItem.status="error"` 这类**单步状态覆盖**能力精确表达"停在第 4 步、但第 2 步失败"【官方文档】。
- **默认视图**：进入任务详情时自动定位/展开失败步骤，把校验问题表作为该步骤详情内容（对标 GitHub 自动展开失败步骤、Blue Ocean 自动切失败日志）。
- **导航规则**：失败步骤及其之前的**所有步骤都可自由点开回看**（只读）；失败步骤之后的步骤保持不可点，并给出原因文案（"依赖前序步骤完成"），形态参考 GOV.UK "Cannot start yet"：灰字、整行不加链接、明确说明【官方】。
- **动作**：重试 / 继续 / 取消 作为失败节点详情里的显式按钮，且不同生命周期状态暴露不同动作集（对标 GitLab：运行中=cancel、失败=retry）【官方产品范式】。

### D. 可访问性注意点（跨三态）
1. **语义**：步骤条用有序列表，当前步加 `aria-current="true"`（USWDS 官方做法）；每个步骤的完成/失败/进行中状态用 **visually hidden 文本**说明，不能只靠颜色（USWDS 要求）。【官方】
2. **可点击节点必须是真按钮/链接**（可 Tab、可 Enter/Space），不要在 `div` 上挂 click；可点击节点若驱动内容区切换，需 `aria-controls` 指向内容区（MUI 官方硬性要求）。【官方】
3. **不可点击节点不要"可聚焦但点了没反应"**：要么用带 `aria-disabled` 的、在 Tab 顺序里合理降级处理的元素，要么纯文本呈现 + 相邻说明文案（GOV.UK 的"整行不加链接"就是这个思路）。【官方】
4. **只读态用 `readonly`/纯文本，不用 `disabled`**：disabled 不可聚焦、不参与校验、不随表单提交，键盘/读屏用户拿不到值（MDN 原文）。WCAG 1.4.3 对 disabled 文字的对比度豁免**不适用于仍有信息价值的内容**。【规范】
5. **禁用原因要可达**：`disabled` 元素本身不可聚焦，tooltip 若挂在 disabled 元素上键盘用户拿不到 —— 把原因放在外层可聚焦容器或紧邻文本/`aria-describedby` 上。【推断，依据 MDN 的 disabled 语义】
6. **避免"看起来可点但不可点"和"不可点却像按钮"**：USWDS 反向要求 pending 段落"不能看起来像 disabled"，GOV.UK 的研究发现用户会误把状态标签当按钮。开关状态与视觉必须一一对应。【官方设计系统研究】
