## Task 1：`select_definitions` 必须按当前定义列表校验编码

### 根因

两个向导的 `selectDefs` 页面能力（`export.selectDefs` / `import.selectDefs`）把模型传来的 `codes`
**照单全收**：直接写本页 `selectedDefs`、收敛进工作区（`extra.selectedDefs` 的唯一来源），
回执统一是「已选择配置项：…」。编码拼错 / 幻觉 / 指向已删除定义时：

1. 回执是**成功语义**（字符串 ⇒ `interpretHandlerOutcome` 按 ok 解读），模型据此以为勾选生效；
2. 工作区 `extra.selectedDefs` 与后续 `persistStepData`（`POST /tasks/{id}/select-defs`）都带上了
   不存在的配置项 —— 任务项落成一个不可导出的集合，错误要到预检查/导出才以别的面貌爆出来；
3. 定义列表**不可用**（加载失败 / 尚未返回）时，旧实现同样"成功"，等于把"没法校验"说成"已选好"。

真机 E2E `12b` 的 `E2E-L11` 恰好把缺陷锁成了期望：旧断言只要求回执文本**包含** `NOT_A_DEF`
—— 而旧实现回的是「已选择配置项：APPROVE_ROLE、NOT_A_DEF」（字符串成功），弱断言照样通过。

### 修改

- `frontend/src/views/ExportWizardView.vue:472`、`frontend/src/views/ImportWizardView.vue:494`
  新增 `selectDefsProblem(codes)`：以**当前 `defs`** 为唯一判据。
  - 定义列表为空 ⇒ 失败，文案说明"列表仍在加载 / 不可用"并给出可用编码（不得当成"没有可用编码"）；
  - 任一编码不在列表 ⇒ 失败，点名**无效编码** + **可用编码清单**；
  - 失败时零副作用（本页选中集 / 工作区 / 任务项都不动，不"部分成功"）。
- 两个 handler（`ExportWizardView.vue:2257`、`ImportWizardView.vue:2182`）在校验通过前不写任何状态；
  `codes` 为空也返回结构化失败（`codes` 必填非空，`WORKSPACE_ACTION_REQUIRED_ARGS` 同口径）。
- 校验只在 handler 分支生效：`runPageHandler` 收到 `{ok:false, reason}` 即落 `failed`（不再被字符串兼容支折成成功）。

## Task 2：条件草案逆映射必须无损（AI `set_condition` 不被改写换义）

### 根因

AI `set_condition` 的落库链路是两段：先按**原始条件** `PUT /tasks/{id}/items/{code}/condition`，
再把它转成表单草案（`draftModelFromCondition`）。随后 `confirm_step` → `goStep` →
`persistStepData` 用**草案重建**的条件再 PUT 一次。问题是逆映射有损：

- `draftModelFromCondition` 按 `fieldCode` 分组，**同字段只留第一条**（GTE+LTE 合并 BETWEEN 除外）；
- IN 的数组值经 `draftValue` 被 `join(',')` 压成字符串，而 `expandFields` 又把该字符串原样当 IN 的
  `value` —— 后端 `ConditionEvaluator.matchesOp` 的 `IN` 分支只在 `value` 是 `List` 时逐项比对，
  字符串则退化成"整串等于行值" ⇒ `IN ["CNY","USD"]` 变成 `IN "CNY,USD"`，**命中从 N 行变成 0 行**。

两者都是"含义被重写"（不是顺序/格式差异），且发生在 AI 已经说过"已设置条件"之后。

### 修改

`frontend/src/types/condition.ts`：

1. `ConditionDraftModel` 增加 `verbatim?: FieldQueryCondition`（`:165`）：草案无法无损表达时，
   原始条件原样挂在模型上 —— **逆映射因此无损**（模型本身说得出那份条件）。
2. `draftModelFromCondition`（`:622`）构建后立即做一次**往返等价判定**；不等价才挂 `verbatim`
   （等价的不挂，避免把正常条件全变成"不可覆盖"）。
3. `conditionsEquivalent`（`:572`）：落库前的"能不能用这份覆盖那份"判据。`scopeKeys` 按集合、
   字段条件按**多重集**、取值按后端字符串比较口径归一（`100` 与 `"100"` 同值；IN 数组视为无序集合）。
   类型变化（数组 → 逗号串）、条目丢失都会判不等价。
4. `buildConditionOutcome`（`:299`）：**先校验草案，再按字段合并 `verbatim`** —— 草案行的
   空值 / IN 空列表一律 `invalid`（原条件不能给非法草案背书）；可提交时，`verbatim` 里仍有草案行
   的字段原条件原样保留、其余字段按草案展开（R1 返修，见 §R1-1/§R1-6）。
5. `expandFields` 的 `IN` 分支（`:256`）把表单的逗号串**拆回数组**（空列表仍判 `EMPTY_IN`）：
   这同时修掉了"用户在表单里填多选 IN，落库却是一个整串"的既有缺陷。
6. `draftContentEqual`（`:606`）：比较草案**内容**（scopeKeys + fields），忽略 `verbatim` 这类元信息。
7. R1 新增：`draftFieldsChanged` / `dropVerbatimFields` / `applyDraftEdit`（`:612` 起）——
   编辑只摘掉被改字段的原条件，未编辑字段的原条件继续携带（支持连续编辑；scope 变化不丢字段原条件）。

`frontend/src/components/wizard/ConditionForm.vue:250`：回填时的"是否回写"判据从 JSON 全等改为
`draftContentEqual` —— 否则父级模型带 `verbatim` 时子组件会把（行重建的）模型 emit 回去，
把用户没动过的原条件丢掉。

`frontend/src/views/ExportWizardView.vue`：

- `persistStepData`（`:1020`）：未真正改动过（`touchedConditions` 不含该码）且模型带 `verbatim` ⇒
  **跳过写入**（不等价禁止覆盖）。改过的草案按 `applyDraftEdit` 合并后的条件落库。
- `onConditionChange`（`:1073`）：统一走 `applyDraftEdit` —— 未编辑字段逐字保留原条件、
  编辑/删除字段只按新草案处理；内容确实没变（显示回写）时不记 `touchedConditions`。

## Task 3：定义列表不可用 / 字段为空时，载入与产出必须 fail-closed

### 根因

`fieldsOf(code)` 在"定义列表未加载 / 加载失败 / 该定义没有字段"时返回 `[]`，而
`SpreadGrid.loadFromXlsx(blob, [])` / `loadFromJson(json, [])` 会**成功**载入一张 0 列的表
（`applyColumnsToSheet` 被跳过），页面随即把它当成"已载入"：

- 导出向导 `loadedGrids` 置位 ⇒ `toXlsxBlob()` 产出**空工作簿** ⇒ AI `download_export_files`
  下载一个空 xlsx；`saveEdits` 用空文件 `PUT` 覆盖服务端真实导出结果；
- 导入向导 `editorState` 置位（`source: 'template' | 'file'`）⇒ 离开第 1 步的整表写回
  （`PUT /tasks/{id}/files/{code}`）用空文件覆盖用户上传的真实文件，预检查/导入读到的就是这个空文件；
- `sheet.current` 交出一个 0 字段适配器 ⇒ 表格工具把表读成 0 行、写进不存在的列。

`0 字段` 的含义是"**不知道**列映射"，不是"一张空表"：两者在字节层不可区分，只能按前者 fail-closed。

### 修改

导出向导 `frontend/src/views/ExportWizardView.vue`：

- 新增 `fieldsUnavailableReason(code)`（`:493`）：定义不在列表 / 定义无字段两种原因分开成文。
- `loadGrid`（`:1422`）：字段不可用 ⇒ **不下载、不载入、不置位 `loadedGrids`**，返回结构化失败
  （附"按 0 字段载入会产出空文件"）。**R1 返修**：字段不可用且定义列表在途时，先等它就绪
  （有界 `DEFINITIONS_READY_TIMEOUT_MS = 10s`）再判定；定义到达后自动重载当前标签
  （`recoverGridsAfterDefinitions`），不再初始化空白；加载失败/到点仍 fail-closed。
- `buildXlsx`（`:1519`）：字段不可用 ⇒ 直接 throw（取字节的**唯一**出口，服务端回落支同样不产出空文件）。
- `preflightDownload`：AI 下载的前置校验里逐码检查字段，**确定性失败**（"…本次未触发下载"），
  不再出现"回执说已发起、浏览器收到空文件"。
- `saveEdits`（`:1884`）：写回前再查一次字段，命中记 `unsupported`（与"未载入"的 `skipped` 分开成文），
  结局 `ok:false`、零 PUT。**R1 返修**：`retryLoadLists` 同时重读定义列表，使"先载入过、后定义丢失"
  这条路径真实可达并被直接用例覆盖（见 R1-5）。
- `sheet.current`（`:2355`）：字段不可用即拒绝交出表格能力。

导入向导 `frontend/src/views/ImportWizardView.vue`：

- 新增 `fieldsUnavailableReason(code)`（`:515`）。
- `loadEditorsNow`（`:1062`）：字段不可用 ⇒ 不载入、不置 `editorState`（写回闸因此也不会放行）。
- `flushEditors`（`:1213`）/ `flushDirtyDefs`（`:1318`）：字段不可用 ⇒ 零 `saveFile`，
  原因与"未载入""来源不明"分开成文。
- `sheet.current`（`:2084`）：字段不可用即拒绝。

  首轮未加校验，**R1 已闭合**（权威定义服务校验 + 定义不可用零写，见 §R1-2）。

- 条件无损只覆盖**前端草案往返**：`IN` 取值本身含逗号时无法用表单串表达，会走 `verbatim`（未被

- `verbatim` 保存在页面内存（`draftModels`），刷新后由任务 `conditionJson` 重新解析得到同样结论；
  服务端 `conditionJson` 的字节形态未在本批加去重/规范化。
- **R1 之后的已知行为变化**：草案行非法（值空 / `IN []`）时，即使用户只改别的字段，`confirm_step`
  也会按 `InvalidConditionInputError` 阻断（`buildConditionOutcome` 先校验草案）。这是 reviewer 要求的
  fail-closed 方向（原条件不给非法草案背书），代价是"AI 先落了一个空值条件、用户不改它就没法推进"。
