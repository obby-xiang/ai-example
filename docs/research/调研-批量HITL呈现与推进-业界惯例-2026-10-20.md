## 0. 一句话结论

**协议层高度一致，呈现层几乎没有规范。** 所有主流协议都把"一批调用"当成**一次快照、一次恢复**：用 `toolCallId` / `interruptId` / `approvalId` 逐项绑定，并且要求**整批齐备**才允许续跑；但**布局（同屏并列 vs 队列逐卡）没有任何规范约束**，由应用自己决定——终端类产品事实上是队列式，Web 框架把决定权交给应用。

没有任何主流框架把"服务端只发第一张卡、等回执再发第二张"作为**协议默认**。这做不到，因为它需要"在挂起态上再挂起"，而 AG-UI 明确写了"协议没有 run 中途的 consumer→producer 通道"。

## 2. 核心问题结论

### Q1 全渲染 vs 串行逐卡

**先纠正问题里的隐含假设**：这不是一个二元选择，业界实际有**三个层次**，而且"数据契约"和"布局"是分开的。

1. **数据契约层（有规范、且一致）**：一批调用**一起送达**。因为它们是模型**同一个 turn 的产物**，服务端没有"分批投递"的原语——AG-UI 甚至明说"协议没有 run 中途的 consumer→producer 通道"。所以"只发第一个、等回执再发第二个"在协议上要么做不出，要么得靠应用层把 `interrupts[]` 切成 N 次 run（等于每次只让模型 raise 一个，代价是 N 次模型调用）。
2. **布局层（无规范、三派并存）**：
   - **同屏并列**：AG-UI / LangGraph 的语义天然支持（一次给 N 条，要求一次覆盖），LangGraph Studio 把多个 interrupt 的 schema 都渲染成输入字段。
   - **队列逐卡**：终端/单焦点 UI 的必然选择（Claude Code），一次一个模态，避免抢焦点。
   - **批摘要 + 逐项展开**：CI/CD 与 diff 审批的常见形态（一次看全、可下钻）。
3. **推进层（有规范、且一致）**：**整批齐备才允许续跑**。AG-UI 规则 3/4 最硬：部分 resume 不合法、有 pending 时新输入必须带 resume；Anthropic 要求所有 `tool_result` 放进同一条 user message；AI SDK 的 `sendAutomaticallyWhen` 只在"整批结果齐全"时触发。

**代表理由（原文口径）**：
- AG-UI：把 N 条放进一个 `RUN_FINISHED`，是因为"一个没有任何东西要回答的 interrupt outcome 会让 consumer 无事可做"（`interrupts` **min 1**），且 resume 的完整性只能由 consumer 判断——所以必须让它一次看到全集。
- LangGraph：并行分支天然会同时 interrupt，官方给的解法是 `resume_map`，而不是"逐个唤醒"。
- OpenAI Agents SDK 是唯一明确允许"部分处理"的：*"If you rerun after approving or rejecting only some items, those resolved calls can continue while unresolved ones remain in `interruptions` and pause the run again."* ——注意这**不是**"发下一个"，而是"未决的继续挂着"。

### Q2 客户端工具的批量执行

**主流是"客户端执行完整批、结果一次性回灌"。** 不是"执行一个就回一个驱动下一步"。

- **AG-UI frontend tools**：agent 提议、application 执行；结果**只能跨 run 边界**回传（无 mid-run 上行通道）。一个 run 可留多个未答调用，应用**一并回答**；要继续的线程**必须先回答全部**。
- **AI SDK**：客户端逐个 `addToolResult`，然后**再调一次模型**；`sendAutomaticallyWhen: lastAssistantMessageIsCompleteWithToolCalls/WithApprovalResponses` 就是"整批齐才自动续跑"的开关。
- **Anthropic**：执行顺序自由（可 `Promise.all`），但结果**必须一条 user message 里全给**；并且*"If you choose not to run a particular call ... still return a `tool_result` for it with `is_error: true`"*。
- **混合批的真实行为**（很关键）：AI SDK 里"一个自动执行工具 + 一个待审批工具"同批时，**自动工具立刻执行，待审批的停在 `approval-requested`**。这就是**半批执行**——也正是 issue #10980 的毒化源头（见 Q5）。

**CopilotKit 的多 action 同批行为**：`useHumanInTheLoop` / `useCopilotAction(renderAndWaitForResponse)` 都是**每个 tool call 一张卡、各自一个悬挂 Promise**，`respond()` 只在该卡 `executing` 态可用；本质是"多张卡各自独立释放"，释放后各自触发 follow-up run（源码有 `MAX_FOLLOW_UP_DEPTH` 断路器）。但 v1 的 `useRenderToolCall` 有一个**只渲染首个工具卡**的已知缺陷（issue #3041，官方 workaround 是人为在工具调用之间插入 `TEXT_MESSAGE` 边界把一批拆成多条消息）。**注意**：该 issue 针对的是 v1 渲染路径，v2 HITL 卡是否受同一限制，本轮**未取到直接证据**。

### Q3 信号/ack 模式：术语与帧

存在成体系的握手，但**术语不统一，帧不统一**；共同骨架是 `pending → 逐项决策 → 整批回执 → 恢复`。

| 体系 | 暂停帧 | 回执帧 | 齐批约束 | 幂等 |
|---|---|---|---|---|
| LangGraph | `stream.interrupts`（N 个 `Interrupt`，带 `id`） | `Command(resume={id: value})` | 可分批；同 node 内按索引配对 | 由 checkpointer 决定 |
| AG-UI interrupts | `RUN_FINISHED{outcome:{type:"interrupt",interrupts[]}}` | `RunAgentInput{resume:[{interruptId,status,payload}]}` | **必须全覆盖**；partial → `RunError` | **规则 5 明文**：同 `(threadId,interruptId,status,payload)` 重放安全 |
| AG-UI frontend tools | `RUN_FINISHED` success + `pendingToolCallIds[]` | `messages` 里逐条 tool message（键 `toolCallId`） | 必须先回答全部 | — |
| OpenAI Agents | `RunResult.interruptions` | `RunState.approve/reject` → `Runner.run(state)` | 可部分；未决再挂 | `RunState` 序列化可跨进程 |
| OpenAI function calling | 无（直接吐 `function_call`） | `function_call_output{call_id}` 同轮齐发 | 一轮齐发 | — |
| OpenAI MCP | `mcp_approval_request{id}` | `mcp_approval_response{approval_request_id}` | 每条一个 response | — |
| MCP elicitation | `elicitation/create`（JSON-RPC id） | result `{action: accept/decline/cancel}` | 无批概念 | — |
| AI SDK | `tool-approval-request` part（`approvalId`） | `tool-approval-response` part + 再调模型 | 整批齐才自动续跑 | — |
| CopilotKit 链 A | 悬挂 Promise | `respond()` | 每卡独立 | — |

**统一术语建议（对本仓）**：`suspended`（一批）→ `decision`（逐项，带 `toolCallId`）→ `resume`（整批）→ `resolved`/`cancelled`。这正好接上仓内既有结论（`调研-CopilotKit-HITL实现-2026-10-17.md` 已建议"用 `resolved`/`cancelled` 取代分散的 `APPROVED/REJECTED/TIMEOUT/...`"）。

### Q4 乱序决策：怎么防"点 B 卡批准 A"

**业界一律用 id 绑定，不用位置。**

- 所有协议帧都带稳定 id：`tool_use_id`（Anthropic）、`call_id`（OpenAI）、`interrupt.id` 且**同时带 `toolCallId` 指回具体调用**（AG-UI）、`approvalId`（AI SDK）、`approval_request_id`（OpenAI MCP）。
- **唯一的"位置耦合"反例**：LangGraph 同一 node 内多个 `interrupt()` 是**严格按索引**匹配 resume 值，官方因此明令 *"Do not reorder `interrupt` calls within a node"*、不得条件跳过。这不是推荐做法，而是需要在文档里写警告的坑——恰好说明**位置绑定是错的**。
- **乱序允许与否，两派**：
  - AG-UI：**最终提交必须原子**（一次 resume 覆盖全部），但每条可以有**不同 status**（官方示例：批 2 条、取消 1 条）。乱序在"最终提交"层面被抹平成一次原子写，天然免疫乱序错配。
  - OpenAI Agents SDK：**允许逐条决**，已决的继续跑、未决的再挂。UI 可以一张张点，id 由 `ToolApprovalItem` 对象本身携带（`state.approve(interruption)` 传的是**那个对象**，不是 id 字符串）。
- **防错配的工程手段（有第一手依据）**：
  1. **服务端持有真相**：OpenAI 明确要求服务端 *"Load the server-owned snapshot and obtain the pending items with `state.get_interruptions()`; do not accept replacement tool calls, arguments, approval records, or serialized state from the client"*。
  2. **按钮闭包绑自己的 id**，不靠"当前选中卡"这种 UI 状态。
  3. **提交前做集合校验**：id ∉ 服务端 pending 集合 → 拒绝（AG-UI：consumer **MUST** 在 run 开始前拒绝未覆盖/未关联的 resume；producer **MUST NOT** 凭缺失条目执行被中断的动作）。
  4. **审计轨迹逐项**：AG-UI 的 tool-bound interrupt 设计要求"工具调用及其解决横跨两个 run"，可完整追溯 `interruptId ↔ toolCallId`。
- **一条硬安全约束（直接可用）**：AG-UI 原文——执行有副作用的工具前 SHOULD 取得同意，且 *"**MUST NOT** 在未获同意时把调用呈现为已获用户批准"*。

### Q5 「并行渲染多审批卡」的已知风险论述

1. **审批疲劳 → 橡皮图章**。WorkOS 的综述最贴切：*"The first request, a person reads carefully. The tenth, they skim. Somewhere past that, they are clicking approve before finishing the sentence"*；并纠正了流行的"决策疲劳=意志力耗尽"解释，指向**高频低差异负载下形成"批准"启发式**（引 CHI 2020 cookie consent、2025 Communications Psychology 的 null 结果）。[workos.com/blog/approval-fatigue-agent-governance](https://workos.com/blog/approval-fatigue-agent-governance)
2. **批内夹带是已命名的攻击技术**。Agent Threat Rules `ATR-2026-00118`「Human Approval Fatigue Exploitation」三种手法，第三条正是本主题的核心风险：*"bundles one risky operation into a batch alongside many benign ones, betting the human approves the whole batch at once rather than reviewing each item"*。对策原文：高风险项**不得**被批量批准覆盖；批量 vs 逐项批准要**分开审计**。[netzilo ATR 页](https://www.netzilo.com/threats/atr-human-approval-fatigue-exploitation)、[规则原文](https://agentthreatrule.org/en/rules/ATR-2026-00118)
3. **"显示不出来就自动拒绝"是真实事故形态**。Claude Code #36983：并行 5 个 Agent 调用，**第一个从未显示审批提示就被静默拒绝**，错误信息还谎称"用户不想继续"，其余 4 个正常弹出。报告者的判断很关键：*"permission prompts that can't be displayed to the user are auto-denied rather than queued"*。[issue #36983](https://github.com/anthropics/claude-code/issues/36983)
4. **半批执行会毒化会话历史**。AI SDK #10980：待审批工具与自动工具同批，批准已记录但**未续跑**（用户抢先发新消息 / 页面刷新）→ 该 `tool_use` 永远没有 `tool_result` → Anthropic 400 `tool_use ids were found without tool_result blocks`，且 *"From here the conversation is permanently poisoned"*。[issue #10980](https://github.com/vercel/ai/issues/10980)
5. **协议作者自己承认"批"是攻击面**：AG-UI 称工具调用为"协议最大的攻击面"，要求参数当不可信输入校验、结果文本不得当携带用户权威的指令。

## 3. 对本项目的建议

**现状（引自仓内既有调研，不重复取证）**：`suspended` 帧**已经带全部 `pendings`**，但前端只有**单槽** `pendingToolCall`（`ai.ts:885`），执行是"逐 tool call 阻塞"；`调研-CopilotKit-HITL实现-2026-10-17.md` 已判"若一次挂起多个待决，**必须齐备才放行**，否则会出现'等一个、跑一个'的半批执行"。

结论：**协议/状态层没有"串行逐卡"这个选项，只有"呈现层串行"。** 两条路线的真实差别不是"要不要多槽"，而是"多槽对用户暴露多少"。

### 路线 A：维持串行逐卡（一次只呈现一个）

- **做法**：服务端把 `pendings` 队列化；前端只投影队首；用户决策后回传，推进到下一张；**全部决策完才续跑**。
- **代价**：
  1. 需要**额外一层"决策暂存"**：单槽 UI 上"已批准但未提交"的项没有归属，必须引入 `decisions: Map<toolCallId, Decision>`；否则会退化成"逐项提交 + 服务端半批推进"，而这正是 AG-UI 禁止、AI SDK 会毒化的形态。
  2. 用户**失去横向比较**：三个待批的导出/发布操作，金额、目标、参数不能并排看，误批概率未必更低。
  3. 若真的"决策一张就 resume 一次"，就必须**每次只 raise 一个 interrupt**，即 gate 层要主动拆分批量调用（或直接拒绝并发 DANGER 调用）——这会改变模型可见的工具契约。
- **好处**：注意力集中；前端改动最小（单槽状态机可留）；与当前"逐 tool call 阻塞"的实现距离最近；审计串行、易解释。

### 路线 B：并行渲染 + per-call 绑定（协议原生）

- **做法**：`pendings[]` 全量进前端多槽；**每张卡的按钮闭包携带自己的 `toolCallId`**；本地维护 `decisions` map；提交时**一次性**提交（AG-UI 语义）或允许部分（OpenAI Agents 语义，未决项保持挂起）；**全部 resolved 才允许续跑**；高风险项禁用"全部批准"。
- **代价**：
  1. 前端从单槽改多槽状态机（渲染、高度、滚动、焦点、无障碍）；
  2. 需要 `全部批准 / 全部拒绝` 的**防误触**设计（二次确认、逐项回显、风险分级着色）；
  3. **per-call 幂等与重放**（AG-UI 规则 5）：同一 `(sessionId, toolCallId, decision)` 重复提交必须安全；
  4. 审计要能区分"批量批准"与"逐项批准"（ATR 明确要求）；
  5. 卡片一多就有**视觉噪声**，反而促进"全部批准"。
- **好处**：与 AG-UI / LangGraph / OpenAI 语义**同构**，不用为协议打架；支持乱序；用户可比较；未来接 `useInterrupt` 时不用二次改造。

### 推荐：**B 的契约 + A 的默认视图**（渐进披露）

1. **状态层按 B 做，不妥协**：多槽 + `toolCallId` 绑定 + 整批齐备才续跑 + per-call 幂等。这是协议要求，也是唯一能同时兼容"逐项决"与"原子提交"的形状。
2. **呈现层默认折叠成"批次条"**：一条 `待确认 3 项`，默认只展开**第一张**（视觉上接近串行），其余折叠可点开；用户主动展开才并列。
3. **数量阈值**：`n ≤ 2` 同屏并列；`n ≥ 3` 走"批次条 + 逐张向导"，并显示 `2/3` 进度。
4. **防错配三条硬约束**（对应 Q4）：
   - 按钮闭包绑定本卡 `toolCallId`，禁止读"当前选中卡"；
   - 提交前校验 `toolCallId ∈` 服务端 pending 集合，越界即 `RunError`；
   - 服务端**不接受**客户端提交的替换参数/替换工具名（只接受 `{toolCallId, decision, note?, editedArgs?}`）。
5. **半批禁区**：**决策完成 ≠ 执行**。执行只能发生在"整批 resolved 之后的续跑"里；任何"已批准但未续跑"的中间态都要能被重放修复（对应 AI SDK #10980 的毒化场景）。
6. **高风险项单独记账**：`DANGER` 级调用不进"全部批准"的覆盖范围，必须逐项确认；审计里单独记 `bulk` vs `individual`。

**如果只能做一件事**：先把"按钮提交的 `toolCallId` 必须等于该卡自己的 `toolCallId`"落到服务端校验（既有 `调研-AI工具执行治理与互斥-2026-10-19.md` §3.9 已把这条列为 2B 的 H1 缺陷）。呈现是产品选择，**身份绑定不是**。

## 附：串行 vs 并行双层的业界分布 · 2026-10-20 补

> **触发问题**：业界主流里，有没有像本仓这样「同批多个 tool_call **串行逐个执行** + 审批/前端工具**逐卡呈现推进**」的真实例子？
> **结论先行**：**A 层（执行）并行是默认**，串行要么靠配置要么自己写；**B 层（呈现/审批）逐卡串行是常态**，但原因是**编码 agent 的调用本身串行/依赖驱动**，不是"审批队列"设计出来的。两层同时"既批量又串行"的形态，业界几乎没有直接先例。

### A. 执行层：并行是默认，串行要显式做

| 框架 / 运行时 | 同一 step 内多个 tool_call 的执行语义 | 能否改成串行 | 依据 |
|---|---|---|---|
| **Vercel AI SDK** | **并行**：`ai@7.0.116` 对一步内的调用是 `Promise.all`，**不保证模型给的顺序**（示例：模型先 `sleep` 后 `read`，实际 `read` 先结束） | 当前**不能**；`parallelToolCalls:false` 只约束模型"能发几个"，不约束 SDK"怎么跑"。社区 issue 请求加 `toolCallConcurrency:1` 或 per-tool `concurrencySafe` | [vercel/ai #22125](https://github.com/vercel/ai/issues/22125) |
| **LangGraph `ToolNode`** | **并行**：官方 reference 把 "Parallel execution of multiple tool calls for efficiency" 列为设计目标；docstring 称 "handles parallel tool execution" | 可以，但要自己写节点。langgraphjs 有 issue 请求串行选项；有论文直接自造 `ExecutorToolNode` 改成串行，理由是"任一失败即中止后续，避免对过时设备状态继续操作" | [workflows-agents](https://docs.langchain.com/oss/python/langgraph/workflows-agents)、[langgraphjs #861](https://github.com/langchain-ai/langgraphjs/issues/861)、[arXiv 2602.07787](https://arxiv.org/pdf/2602.07787) |
| **Anthropic API** | **由宿主决定**：*"The API doesn't prescribe an execution order: you can run the calls concurrently, sequentially ... or any combination"* | 可以，且官方建议有副作用/共享状态/顺序要求时串行；**computer/browser 批量动作强制按序 + 首个失败即停** | [parallel-tool-use](https://platform.claude.com/docs/en/agents-and-tools/tool-use/parallel-tool-use) |
| **OpenAI API** | **不规定**；文档只要求"assume there are several"并把结果齐发 | 可以（官方 cookbook/生态示例给的是 `ThreadPoolExecutor` / `asyncio.gather`） | [function-calling](https://platform.openai.com/docs/guides/function-calling) |
| **OpenAI Agents SDK** | **未取到直接文档**（`_run_impl` 源码路径本轮 404，未读到 `gather`） | 未知 | — |
| **AG-UI** | **完全不管**：前端工具由 application 执行，协议只规定"结果跨 run 边界回传" | 应用自定 | [spec/1.0/events/tool-calls](https://docs.ag-ui.com/spec/1.0/events/tool-calls) |
| **pydantic-ai** | 默认**并发**（asyncio tasks），per-tool `sequential=True` 可强制串行 | 有原生开关 | 二手归纳 [codepointer.dev](https://codepointer.dev/p/what-actually-runs-when-you-start) |
| **buzz-agent / pi** | buzz 有 `max_parallel_tools`（并发但按模型原顺序入历史）；pi 直接**串行** | — | 同上（二手） |
| **Cline / Roo Code / Zoo Code** | 不是"同批并行/串行"问题：系统提示硬性要求 **"use one tool at a time per message"**、*"ALWAYS wait for user confirmation after each tool use before proceeding"*；Zoo-Code 自述 *"strictly serial — one task at a time, one tool at a time"* | 结构上就是串行 | [Cline system prompt 摘录](https://gist.github.com/maoxiaoke/cd960ac88e11b08cbb4fa697439ebc68)、[Zoo-Code #355](https://github.com/Zoo-Code-Org/Zoo-Code/issues/355) |

**A 层结论**：主流是**并行执行**，串行是"特殊情况的显式选择"。业界把串行限制在三种动机上：①**有副作用/共享状态**（Anthropic 官方口径，也是本仓最接近的动机）；②**运行时状态必须线性**（终端/设备自动化）；③**产品只允许一步一个动作**（Cline 类，靠提示词与架构约束，不是执行器选择）。

### B. 呈现/审批层：逐卡串行是常态，但"逐卡"≠"逐批投递"

| 产品 | 一批待批怎么出现 | 能否看到队列全貌 | 依据 |
|---|---|---|---|
| **Claude Code（CLI）** | 权限提示是**阻塞式模态，一次一个**；并行工具/子代理会同时产生多个待批，用户只能逐个答 | **看不到**。社区明确在要这个能力：*"Present all queued approvals together when the user returns. This alone would eliminate most idle time"*、*"Batch permission triage UI for multiple pending tool-approval prompts"* | [permissions](https://code.claude.com/docs/en/permissions)、[#55769](https://github.com/anthropics/claude-code/issues/55769)、[#58247](https://github.com/anthropics/claude-code/issues/58247)、[#102336](https://github.com/anthropics/claude-code/issues/102336) |
| **Claude Code 的官方应对** | 不是把审批做得更快，而是**减少提问**：auto mode 用分类器代判 | — | *"Claude Code users approve 93% of permission prompts"* —— [Anthropic Engineering: auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode) |
| **VS Code Copilot agent mode** | **每个 tool call 一个确认**：*"Review each tool call as the agent works. If an approval prompt appears, expand the tool details ... select Allow"*；聊天里工具卡默认**折叠/分组**（`chat.agent.thinking.collapsedTools`） | 可逐条展开；会话级"Allow all"是逃生阀 | [Use tools with agents](https://code.visualstudio.com/docs/agents/run/tools) |
| **Cursor** | 终端命令**默认需批准**，提示发生在命令**将要运行时**（执行前一刻）；Run Modes = Auto-review（默认）/ Allowlist / Run Everything | 逐步出现，无预先整批列表 | [Agent Security](https://cursor.com/docs/agent/security)、[Terminal integration](https://cursor.com/help/ai-features/terminal) |
| **Cline / Roo Code** | 聊天流里**逐张工具卡** Approve/Reject；auto-approve 可关掉 | 串行可见（一条一条冒出来） | 同上 A 层 Cline 提示词 |
| **Aider** | 不是多工具 agent：一次多文件编辑产出**一个 diff**，整体审阅/应用；有 issue 请求"每个原子改动都确认"（说明现状是整批） | 一次看全（但只有 diff，没有"待批工具"概念） | [aider #649](https://github.com/Aider-AI/aider/issues/649) |

**B 层结论**：
1. **"一次只出一个审批、答完才出下一个"在编码 agent 里确实是常态**，而且是最主流形态。
2. 但它几乎总是**执行模型本身串行/依赖驱动**的副产品：agent 读文件 → 改 → 跑测试，后一步依赖前一步结果，模型**压根不会一批发多个**。所以"审批逐卡"不需要额外设计。
3. **"整批列出逐个勾"在编码 agent 里少见**，主要出现在两类场景：**CI 门禁的多人审批**（GitHub environment approvals）、**批量 diff 审阅**（Aider、Cursor 多文件 review 的 "Accept all"）。
4. 真正"一批**独立**动作 + 逐卡审批"几乎只有 Claude Code 的并行工具/子代理场景，而它在这个场景出过事故（#36983：并行组首个提示未显示即静默拒绝）。

### C. 「队列逐卡」vs「整批平铺」的公开讨论：有，但不是对照实验

**没有找到严谨的 UX 对照研究**（同任务、同风险下两种布局的误批率/决策时延比较）。有的证据是三类，方向不完全一致：

1. **产品 issue 层（用户侧的痛点是"阻塞/空转"，不是"看不到全部"）**
   - Claude Code #55769：*"Present all queued approvals together when the user returns. This alone would eliminate most idle time"* —— 诉求是**别在我离开时干等**。
   - #102336：*"Action approval queue for unattended agents ... approvals that do not block, reviewed later in one batch"* —— 诉求是**非阻塞 + 事后批量分诊**（queue，而不是同屏平铺）。
   - #58247：*"Batch permission triage UI for multiple pending tool-approval prompts"* —— 诉求明确是**分诊（triage）**：先看清单、再逐项处理。
   - 三者共同点：要的是**"队列 + 全貌 + 可事后处理"**，不是"一屏平铺 + 一键全批"。

2. **安全研究层（明确反对"批量一键"）**
   - ATR-2026-00118：批内夹带是攻击手法，*"betting the human approves the whole batch at once rather than reviewing each item"*；对策是高风险项禁批量覆盖、bulk vs individual 分开审计。
   - NCC Group 的编码 agent 白皮书：HITL *"user fatigue is a major concern in which users may approve requests without reading them due to excessive prompting"*，并指出厂商的对策是沙箱与自动分类器（[NCC Group whitepaper](https://www.nccgroup.com/media/jtepwx1t/nccgroup_codingagentswhitepaper.pdf)）。

3. **厂商取舍层（业界实际选了"减少提示"，不是"优化布局"）**
   - Anthropic：93% 的提示被批准 → 说明提示本身已失去区分度；解法是 auto mode 分类器，而不是把审批 UI 做得更顺手（[auto mode](https://www.anthropic.com/engineering/claude-code-auto-mode)）。
   - Gartner / WorkOS：均匀审批队列本身就是失效根源，要按后果与可逆性分级（[WorkOS](https://workos.com/blog/approval-fatigue-agent-governance)）。

**C 层结论**：公开讨论的落点不是"队列 vs 平铺"，而是**"提示量"**。在这个前提下：
- **队列逐卡**的代价是**空转与注意力切换**（用户被绑在终端前，离开就卡住）——可用"非阻塞 + 事后分诊"缓解，不需要改成平铺。
- **整批平铺**的代价是**橡皮图章 + 夹带**（安全侧明确反对一键全批）。
- 折中形态是**"队列 + 全貌 + 逐项绑定"**：看得见还有几项、能跳着处理、但每项决策独立记账。

### D. 对本仓的含义（补充结论）

本仓的组合是「**同批多调用（模型一次吐多个）+ 串行执行 + 逐卡审批推进**」。对照下来：

1. **没有直接同构的先例**。业界要么"调用串行 + 审批逐卡"（Cline、Claude Code 的常态路径），要么"调用并行 + 无审批"（只读批量），要么"调用并行 + 一次整批回执"（AG-UI 并行 interrupt / OpenAI interruption 列表）。
2. **我们落在没人趟过的区间**：批量来自模型（不是我们拆的），串行来自执行策略（有副作用的正确选择），逐卡来自呈现（产品选择）。三者拼在一起，业界没有现成范式可抄。
3. 因此有三件事必须自己承担，不能指望"业界惯例"兜底：
   - **队列全貌可见性**：Claude Code 的教训是"看不到队列 ⇒ 用户不知道还剩几项 ⇒ 空转或盲点"；至少要有 `待确认 2/3` 这类计数。
   - **未决项持久化**：离开/刷新后未决的卡要能恢复（AG-UI 的 `interrupts[]` + `resume` 语义正好承载）。
   - **身份绑定**：`toolCallId` 必须与卡片一一对应并由服务端校验（本件 §2 Q4 已列三条硬约束）。
4. **最像我们的三个产品及其形态**（按接近程度排序）：
   - **Claude Code**——并行工具批 + 权限模态逐卡；**但**队列不可见、且出过"未显示即静默拒绝"事故，属于"同一问题域的反面教材"。
   - **Cline / Roo Code**——逐卡 Approve/Reject + 严格串行；**但**串行是架构约束（一次一个 tool），不是"批量后串行执行"。
   - **VS Code Copilot agent mode**——每个 tool call 一个确认、工具卡折叠分组、会话级 Allow all 逃生阀；这是"逐卡 + 可批量豁免"的最完整产品形态。
