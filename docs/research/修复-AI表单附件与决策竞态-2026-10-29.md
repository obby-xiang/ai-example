# 修复：AI 表单附件与决策竞态（2026-10-29）

> 范围：后端 `ai/form`（生成式表单附件）、`ai/gate/ConfirmGate`（决策写入口）。前端、共享方案文档未改。
> 基线：`2439c4e`（M08 重连通告文案批）。本件只登记本批的缺陷、口径与验证证据。

## 0. 一句话结论

四条缺陷同源：**"校验"与"消费/写入"混在同一个时点**，以及**"读到的副本"被当成"写时的真相"**。
本批把两件事拆开——校验只读、消费只在决策落库之后；写 guard 之后必须复读条目——并为上传口补上
"按表单的件数/总量预算"与"归属权威值"，同时用同一把尺（`app.ai.session-ttl`）对齐附件登记寿命，
在表单收口处回收没被提交的件。

## 1. 缺陷与根因

| # | 现象 | 根因（修复前） | 影响面 |
| --- | --- | --- | --- |
| 1 | 多附件提交失败后"可重试"是假话：用户手里的 fileId 已作废 | `GenerativeFormGuard#inspectResult` 在**值校验通过后立刻** `consume` + 删盘；该调用发生在 `ConfirmGate` **抢决策 guard / 落库之前**。同一份回灌里第 2 件消费失败 ⇒ 第 1 件已删，但整单被回 `RESULT_REJECTED`（文案"可修正后重试"） | 生成式表单附件（G-E） |
| 2 | 同一张卡出现两帧、两个互相矛盾的结论 | `ConfirmGate#dismiss` 的 `pending` 是**抢 guard 之前**读到的副本；抢到 guard 后未复读，直接用副本写 `FRONTEND_CANCELLED` 并 `frontendToolResult`。中间若有"不带 guard 的写者"（前端超时收敛、整轮取消）已落库，结局被覆盖 | 所有前端通道工具（表单、表格写、UI 原语） |
| 3 | 负数 `maxLength`/`maxItems` 的表单照样下发，用户填什么都过不了闸 | `GenerativeFormRules#constraintIssues` 只校验 `minLength < 0`、`minItems < 0`；`maxLength` 只判"超硬顶"，`maxItems` 完全没有负数判据 | 生成式表单 schema 白名单 |
| 4 | 上传口可被用来挂文件到别的会话、无限占盘、指向不存在的字段 | ①`sessionId` 直接取请求参数并写进"会话 → 附件"索引；②没有件数/总量上限（5MB × 无限件）；③不校验目标 attachment 字段；④`file.getInputStream()` 未关闭 | `POST /api/ai/form/attachments` |
| 5 | 等超过 2 小时的表单必然 `ATTACHMENT_NOT_FOUND`；失效文件无人回收 | 附件登记 TTL 写死 2h，而 `generative_form` 自 2026-10-20 起**无等待上限**（待决条目 TTL = `app.ai.session-ttl`，默认 24h 且挂起期随心跳续期）；登记先于卡失效，文件成孤儿 | 附件生命周期 |

## 2. 修复口径

### 2.1 校验与消费分离（对应缺陷 1）

- `FrontendToolGuard` 新增两个决策后钩子（默认空实现，其它复核器零改动）：
  `settleAcceptedResult(runId, toolCallId, argumentsJson, resultJson)` 与 `settleDiscardedResult(runId, toolCallId)`。
  契约定死：**只在结论已落库之后调用**；实现方失败不得抛出、不得改写结论。
- `GenerativeFormGuard#inspectResult` 变为**纯只读**：存在（`find`）/ 归属（`runId + toolCallId`）/ 形状
  （`GenerativeFormRules` 的 `att_` 正则）三段校验，多附件**全部**过一遍，一件不合格即整单拒绝，零副作用。
- 消费挪到 `settleAcceptedResult`：**先全部 `find` 取元数据/物理路径，再逐件 `consume`**；单件失败只告警
  （该件保留到 TTL，安全方向是多留不漏删）。用户放弃走 `settleDiscardedResult` 回收。
- `ConfirmGate#doSubmitFrontendResult` 在 `putPending → 结局帧 → 唤醒` 之后（`submitLock` 之外）调接受钩子；
  `dismiss` 在结局帧与唤醒之后调放弃钩子。锁外是刻意的：消费是 Redis + 删盘往返，不占实例级 `submitLock`。

### 2.2 dismiss 抢到 guard 后复读（对应缺陷 2）

`dismiss` 与 `doSubmitDecision` 对齐：`tryRecordDecision` 抢到后 `pendingForWrite` **复读**，`null ⇒ NOT_FOUND`、
非 `PENDING ⇒ DUPLICATE`（不覆盖、不发帧、不跑回收钩子）。复读出来是新副本，故入口已过白名单的
`sheetMeta` 要在新副本上再落一次（否则审计计数 `writePlans/writeCancelled` 随旧对象丢掉 —— 这一点由既有
`ParkSettlementAuditTest#parkedDismissSettlesCancelledWriteOnce` 当场抓到，本批已修）。

### 2.3 负数上界在 schema 阶段拒绝（对应缺陷 3）

`maxLength < 0 ⇒ FIELD_LENGTH_BOUND_INVALID`、`maxItems < 0 ⇒ FIELD_ITEMS_BOUND_INVALID`。
`0` 仍是合法边界（只接受空串/空选），不被负数判据误伤。这类"死约束"若下发，用户填什么都过不了值校验，
挂起只能等到放弃 —— schema 阶段拒绝是零副作用的，模型改一次即可用。

### 2.4 上传口预算与归属（对应缺陷 4）

- **件数** = 表单 schema 里的 attachment 字段数（每个字段只装一个 fileId）；在册件数达上限即拒（400）。
  判据来自新索引 `ai:form:att:form:<runId>:<toolCallId>`（`FormAttachmentStore#findByForm`，读失败抛出，不按空表）。
  **单附件字段的例外**：前端"重新选择文件"= 再上传一次（没有删除接口），所以单字段表单在满位时**顶掉旧件**
  （在册数仍 ≤ 1）。顶替的次序是"先存新件 + 登记成功，再删旧件"：反过来的话，存档/登记一失败，
  用户就同时失去旧证据与新文件。多字段表单不猜"替换的是哪个字段"（猜错会删掉另一个字段正在用的件），
  一律拒绝，并给出**真能照做**的指引：提交当前表单，或取消表单后重新发起（不存在"按 fieldKey 替换"）。
- **总量** = `MAX_TOTAL_ATTACHMENT_BYTES`（20MB/表）；`在册字节 + 本次 > 上限` 即拒。
  两者一起把"一张表单能占多少盘"变成有界量。
- **fieldKey**（可选参数）：**只做字段白名单校验** —— 带了就必须是这张表单 schema 里的 attachment 字段，
  否则 400（非法字段的坏请求必须在任何"顶掉旧件/落盘"之前被挡下）。它<b>不是</b>替换开关：登记簿没有
  字段归属映射，不能凭它判断"这次替换的是哪一件"，因此也不提供"按字段精确替换"。
- **sessionId**：请求参数**不再采信**，只取轮次快照的 `sessionId`（待决条目属于这一轮）；快照缺失/读取失败
  一律 **fail-closed**（503，不落盘、不登记），绝不回落到请求参数 —— 没有归属的登记不进会话索引，
  会话销毁时看不见它，文件就是孤儿。
- **输入流**：`try (InputStream in = file.getInputStream())` —— 容器流不关会漏到连接池/临时文件。
- 索引失败回滚：数据键 + 两个索引成员一起回滚（与会话索引同一口径），上传端点照旧删已落盘文件。

### 2.5 登记寿命与孤儿回收（对应缺陷 5）

- **TTL 同一把尺 + 同一条续期链**：`RedisFormAttachmentStore` 注入 `AiProperties`，登记/墓碑/两个索引的 TTL
  全部取 `app.ai.session-ttl`（默认 24h），不再是写死的 2h；新增 `FormAttachmentStore#touch(runId, toolCallId)`
  （续数据键 + 表单索引 + 会话索引），由 `FrontendToolGuard#touchSuspension` 接到 `ConfirmGate` 的挂起续期点
  （与 `renewSuspensionTtl` 同拍），只对仍 `PENDING` 的条目调用。于是"卡活着 ⇒ 附件登记活着"：
  表单等超过 24h 仍可提交（见 §4 的 25 小时用例）。park 模式下不跑心跳，待决条目与附件登记同样不续期，
  两者寿命仍然一致，不会出现"卡还在、附件先过期"。
- **表单收口回收**：决策接受（`settleAcceptedResult`）与用户放弃（`settleDiscardedResult`）后，按表单索引
  删掉"传了但没提交"的登记与落盘文件（用户重传后放弃的旧件、只提交一部分字段的其余件）。
  这一步同时给"件数上限"兜住了重复上传的残留。
- **会话销毁**：既有 `AiSessionPurgeService`（`findBySessionId`）不变，仍是整会话回收面。

### 2.6 第一轮返修闭项（I1–I5 + 附带项）

| 项 | 缺陷 | 现在 |
| --- | --- | --- |
| I1 | 单字段重传**先删旧件再存新件**：store/register 失败会连旧证据一起丢 | 次序反转为"存新件 → 登记成功 → 才删旧登记/旧文件"；失败只删新件，旧件原样保留。既有磁盘失败、登记失败、以及"登记先于删除"的次序断言三条用例 |
| I2 | 多字段满位时文案叫用户"带 fieldKey 重传"，但系统根本没有字段归属映射 —— 死路指引 | 文案改为可行动：**提交当前表单，或取消表单后重新发起**，并明说"当前无法替换"；`fieldKey` 退回白名单校验的唯一职责；文档不再宣称支持精确替换 |
| I3 | 消费失败的件随后被"表单收口回收"删掉，违背"保留到 TTL" | `keep` = 本次回灌**提交的全部附件**（无论消费成功与否）；回收只清"没被提交"的件。用例用生产登记簿（Redis 实现的进程内路径）+ 只对 `consume` 注入故障，`findByForm` 是真实语义（不是默认空表） |
| I4 | 登记 24h 一次性 TTL 不随挂起心跳续期：表单等 > 24h 仍 `ATTACHMENT_NOT_FOUND`、文件孤儿 | `FormAttachmentStore#touch`（数据键 + 表单索引 + 会话索引）接入 `ConfirmGate` 挂起续期点（同拍 `renewSuspensionTtl`，只续 `PENDING` 条目）；用例走**真实确认门**跑 23h→心跳→25h 后仍可提交，并附"不续期即过期"的对照 |
| I5 | `consume` 先删数据键再写墓碑：墓碑失败 = 登记已删 + 无墓碑 + 文件孤儿 | 次序改为**墓碑先写 → 再删数据键 → 清索引**；墓碑写失败直接抛出、数据键原样保留。故障注入用例断言"墓碑失败时数据键一次都没被删" |
| 附带 | 快照无 sessionId 时上传仍"成功"（无索引）；解析失败日志打印整段入参；空 `storagePath` 直接删盘；接口文档把消费钩子写成"唤醒/续跑之前" | 归属不可用 ⇒ **fail-closed 503**（不落盘不登记）；日志只记 runId/toolCallId/长度；空路径一律跳过（收口回收/顶替/消费三处）；接口文档改成与实际一致的"落库 → 结局帧 → 唤醒 → park 结算 → 续跑派发之前" |

## 3. 残留边界（如实登记）

1. **无上限等待 vs 有限 TTL**：登记寿命已与待决条目同链续期（`touch`），非 park 等待下"等多久都不会
   先过期"。仍存在的残留是**整条链一起断**的形态：进程在挂起期全部消失（park 模式本就没有心跳线程），
   且会话此后不再被销毁 —— 待决条目与附件登记在同一时刻过期；此时平台已无法判定"这张卡还有人要"，
   文件只能等人工清理。彻底兜底需要把索引成员扩成 `fileId|storagePath` 并配扫描器，本批不做。
2. **按字段的占用 / 替换**：登记簿不记录 `fieldKey`，"同一个字段被重复上传"按两件占位；满位后多字段表单
   只能提交或取消重来。**不宣称支持按字段精确替换**：要支持需在登记里加字段归属列（并让前端传 `fieldKey`），
   本批不做（避免扩 Redis 值格式），拒绝文案也不拿 `fieldKey` 当指引。
3. **消费失败的安全方向**：决策已落库后的消费失败（Redis 抖动）保留登记到 TTL，不重试、不回滚结论。
   这是刻意的：结论已定，重试只会产生第二条写入口。
4. `generative_form` 的 `inspectResult` 两参重载（无 `runId/toolCallId`）不做归属校验，只做形状校验 —— 与既有
   兼容口径一致，生产路径永远走四参版本。
