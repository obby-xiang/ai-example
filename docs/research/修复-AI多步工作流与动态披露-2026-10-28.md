## 1 提示词与工具描述：导航不再是终点，页面级动作分批串行

**问题**：旧规则 10 写「披露按轮生效 → 同一轮里不要接着调用刚解锁的工具 → 导航类调用成功后即结束本轮」；规则 24 写「导航成功后结束本轮」。模型照做 ⇒ 一条「新建导出并发起导出」的意图被切成**多个轮次**：导航一轮结束、下一轮才选配置、再下一轮才推进，用户每轮都要补一句（旧口径还允许「可简短说明下一步将做什么，并允许用户给出下一步指令」）。

**根因**：这条旧口径**对当时的实现是正确描述** —— 披露面在请求边界按当时 `AiContext` 算一次（`ToolRegistry#forContext`），执行期 scope 复查用的也是本轮快照冻结的那一份，所以「同轮里刚解锁的工具」确实拿不到。**提示词只是照抄了实现限制**，因此要支持多步必须**两边同时改**：实现侧补上「批间上下文推进 + 下一跳重算」（本件 §2/§3），提示词侧才敢写「导航成功不要结束本轮」。

**修改**（`ResilientChatService.java:200`–`:210`、`:241`–`:245`）：

```text
10. 页面级动作（navigate_to / select_definitions / confirm_step / set_condition）按批次串行接续：
    同一批工具调用共享该批开始前冻结的披露集，跨批才按最新页面与步骤重新披露。导航成功后
    不要结束本轮：下一批按最新披露的工具列表继续，顺序为
    navigate_to → select_definitions → confirm_step → set_condition，一批只做一步；…
    不要要求用户给出下一步指令，下一轮按原始意图自动接续，不要求用户重复原始意图。
    页面级动作失败即停：… 同一目标页不要重复导航。披露不等于授权：… 
    create_task 与 start_* 仍必须由各自确认卡承接（见第 9、17、24 条）。
24. … 导航成功后不要结束本轮，按第 10 条在下一批继续勾选配置项/上传文件；导航失败即停并如实说明…
```

## 2 `RunContextRefresher`：只吃成功结算、只写权威值

**问题**：`navigate_to` 成功后，同一次运行里的下一跳仍然看不到向导工具 —— 而「模型自己把意图走完」要求同一运行内也能换页面、换步骤。

**根因**：披露面由 `AiContext`（`page` / `taskType` / `step` / `taskId` / `taskStatus` / `extra`）决定，而这份上下文是**请求边界**算一次、随快照冻结的；工具结果本身**不会被翻译回上下文**。缺的就是这一个翻译层。

**修改**：新增 `RunContextRefresher`（`backend/src/main/java/com/example/configmgr/ai/gate/RunContextRefresher.java`，单构造注入 `TaskService`，不新增持久面、不新增帧类型）。

| 件 | 语义 | 锚点 |
|---|---|---|
| 只认三个工具 | `supports(name)` = `navigate_to` / `create_task` / `confirm_step` | `:53`、`:56`、`:59`、`:73` |
| 双闸门 | 必须 `resolved()` **且** `effectiveOutcome() == OK` —— 「只有前端真的做了 / 后端真的建了」才算页面事实；失败、超时、结局未知一律 `empty` | `:92`–`:94` |
| 无变化不写 | 结果与入参上下文 `equals` ⇒ `Optional.empty()`（调用方据此跳过 `save`） | `:106` |
| 导航 | `page`/`taskId` 取**入参**；有 `taskId` 时 `type`/`step`/`status` 取**任务权威值**；`page` 缺失时按任务类型推出 | `:110`–`:129` |
| 无任务导航 | **清掉** `taskId` / `taskType` / `step` / `taskStatus`（否则新页面仍带着旧任务的披露面） | `:114`–`:120` |
| 创建 | 任务号**只能从回执里取**（`#123`）；取不到 ⇒ **不编造 ID、不动上下文**，只 WARN | `:132`–`:145`、`:245` |
| 步骤推进 | **只读 `TaskService` 的权威 `currentStep`**，`args.step` **一律忽略** —— 步骤是 `start_export` 等工具的披露判据，照抄入参等于把「模型以为到了 EXPORT」变成「确实给了假入口」 | `:147`–`:174` |
| 任务定位（推进） | 入参带 `taskId` 就用，否则沿用**当前上下文**的；两者都没有 ⇒ 不动上下文 + WARN | `:160`–`:168` |
| 读任务 | `TaskService#findByIdRaw`（披露只要三个标量，不为一次刷新水合整份任务条目） | `:201`–`:219` |
| 失败口径 | 读不到 / 读取异常 ⇒ **抛** `IllegalStateException`，由调用方保留旧上下文并 WARN；**绝不拿猜出来的 type/step 替换权威值** | `:212`–`:218` |
| 换页删区域数 | 只在**真的换页**时改写 `page` 并 `extra.remove("uiRegionCount")`；**删键而不是写 0** | `:190`–`:199` |

**为什么是「删 `uiRegionCount`」而不是「写 0」**：`ToolRegistry#uiRegionsPresent` 把**缺失**当「存在」（`ToolRegistry.java:563`–`:575`，fail-open：旧客户端 / 桩不带该键时工具不得静默消失）；写 0 会变成确定的「本页没有 AI 区域」，等于拿旧页的数字冒充新页的事实。

**边界**（连读）：

- **只做上下文翻译**：不改 `TaskService`、不改任务状态机、不写回执位、不产生任何用户可见文案。
- 刷新是**增强不是授权**：拿到的只是"下一步更准"的披露面，能否执行仍由防线③（scope 复查）与各确认门决定。
- **页面事实按入参采信、任务事实按库采信**：`navigate_to` 的 `page` 不会去库里校验（页面是前端事实）；`type/step/status` 一律以 `TaskService` 为准。

## 3 `SpToolCallingManager`：批间刷新 / 每跳重算 / 执行期补齐 / 失败回落

**问题**（两处接缝）：

- **披露面不重算**：`resolveToolDefinitions` 原样委托给官方 `DefaultToolCallingManager`，返回的就是请求边界那份 callbacks ⇒ 下一跳看到还是旧工具集；
- **执行侧解析不到新工具**：官方执行单个调用时只从 `prompt.getOptions()` 的 callbacks 里按名字找，而下一跳重算把 `check_job_status` 之类的新工具给了模型，旧 options 里没有它 ⇒ **「看得见、点不动」**。

**根因**：披露面与执行面**各自冻结在请求边界**，中间没有「按当前运行事实重算」的接缝；而这两件事**必须分开处理** —— 披露面可以随上下文变，授权面不能跟着变。

**修改**（`SpToolCallingManager.java`）：

| 件 | 语义 | 锚点 |
|---|---|---|
| 可选注入 | `@Autowired(required = false) setContextRefresher(...)`；**构造签名不动**，缺失即不刷新（轻装配面 / 单测行为一字不变） | `:377`–`:383` |
| 批后刷新调用点 | 在**逐条成功结算之后**（`ToolCallEndTrace.emitOnce` 之后、组装模型回填之前）调 `refreshRunContext(runId, source)` | `:928`–`:934` |
| `refreshRunContext` | 读快照 → 交给 `RunContextRefresher#next` → 有变化才 `setContext` + `save`；**只改外置快照**，执行循环里那份 `context` 变量一字不动（同批 scope 仍按批首判） | `:2726`–`:2755` |
| 失败不打断 | 任何异常（读/算/写）只 `WARN` 并保留旧上下文，工具轮照常返回 | `:2751`–`:2754` |
| 每跳重算 | `resolveToolDefinitions` 先取委托结果，再按**当前快照**的上下文 `ToolRegistry#forContext` 重算，`mergeDisclosed` 合并后返回 `ToolDefinition` | `:456`–`:493` |
| 合并口径 | **名字**对齐（不用对象身份）：冻结集合的**顺序优先**（上下文没变时结果与旧口径逐字一致，不击穿 prompt 缓存）；已不在当前披露面的裁掉；新披露的**追加在后** | `:501`–`:526` |
| 执行期补齐 | `executionPrompt(prompt, toolName)`：本次调用的 callbacks 副本按同一口径合并；**只在「冻结里没有、合并后能解析到」时**才复制 options（名字序列相同即不复制），并打 INFO | `:554`–`:599`、调用点 `:2508` |
| 回落（八条） | 无 options / callbacks 为空 / `toolNames` 非空（名字面在本类之外解析不了）/ 无 `runId` / 无快照 / 重算结果为空 / 合并为空 / 任何异常 ⇒ **原样返回委托结果** | `:457`–`:492` |
| 回落的**关键一条** | 「callbacks 为空」回落，是因为那可能表示「本轮不下发任何工具」（模型不支持工具调用）—— 换成 registry 全集就是**静默扩大授权面** | `:462`–`:465` |
| 回执解析同源 | `taskIdFromText` 改为委派 `RunContextRefresher.taskIdFromText`（同一份回执、同一个号、唯一实现） | `:1164` |
| `runIdOf(Map)` | 抽出静态读口，供披露重算与执行补全共用；取不到按「不可判定」回落 | `:2765`–`:2771` |

**三层口径（本批的核心约束）**：

1. **批内冻结**：`executeToolCalls` 一进来读成一份 `context`，同批所有调用的预检 / 防线③ / 目标校验都用它 ⇒ 「导航成功后**同批**立刻选配置」仍被 `SCOPE_NOT_DISCLOSED` 拒绝（`SCOPE_VIOLATION_CODE`，`:172`）—— **一批工具不允许自我扩权**；
2. **批间刷新**：逐条成功结算后写回**外置快照**上下文，**下一批**（又一次 `executeToolCalls`）才按新上下文判；
3. **执行期补齐只解决可解析性**：补进去的 callbacks **不构成授权** —— 能不能执行仍由防线③（`matchesContext` 按快照上下文复查）与各工具确认门 / HITL 决定。

**边界**（连读）：

- **不改 HITL / 风险分级 / 通道**：`create_task` 与四条 `start_*` 的 DANGER + 确认门、`BACKEND`/`FRONTEND` 通道、`reportHash` 复核、`kind` 三态一律未动；本批只让「被披露」更准。
- **不改官方循环的返回结构**：执行期补齐只替换送进官方委托的那一个 `Prompt` 的 options 副本，不看也不改 `ToolExecutionResult`。
- **不加帧 / 字段 / 配置键**：唯一元数据变更 = `tools.yaml` 的 `version` 升位（因改描述必升）。
- **每次成功结算多一次快照读 + 一次任务读 +（有变化时）一次快照写**：只对三个页面级工具触发，任务读走 `findByIdRaw` 不水合。
- **缓存友好是有意为之**：上下文没变时 `mergeDisclosed` 的名字序列与冻结集合一致，`resolveToolDefinitions` 不会重排、执行期不会复制 options。

**测试构造要点（防假绿）**：

- 动态披露类用**真实 `ToolRegistry`**（注解 `@ToolScope` 参与判定），只有领域侧 `TaskService` 与存储侧 `RunStore` 是替身；替身快照 `get` 给**副本**、`save` **覆盖** ⇒ 上下文没写回去在下一跳必然丢（不是靠断言同一对象）。
- 「同批冻结」用**同一份** `ToolCallingChatOptions`（请求边界那份）贯穿全流程，因此「下一跳能看到新工具」只能是 `resolveToolDefinitions` 重算的结果，不可能是换了 options。
- 「不采信自报 step」是**双条件**构造：前端回执成功（`OK`）+ 权威步骤未动，断言上下文停在权威值。
- 无任务导航那条显式断言 `findByIdRaw` **从未被调用**，防"清字段"被顺手读库掩盖。

**不声称**：上文"1/1 通过"**只针对那九个方法**，不等同后端定向整类 / 后端全量 / 前端全量 / 构建 / E2E / 主 CI 通过；**真实模型多跳未验**（提示词与模型是否真按批串行只能实机看）、**真实浏览器未验**（前端动作表 `allowPages`/`allowSteps` 兜底未在本批实测）、**真实 Redis / 多实例未验**（快照读写与租约面走既有替身）、**真实 Task 落库时序未验**。

## 5 边界与不声称

- **不新增 HITL**：`create_task` 与四条 `start_*` 的确认门、`DANGER` 分级、`BACKEND` 通道、`reportHash` 复核、`kind` 三态**一律未动**；本批只让披露更准，**披露不等于授权**。
- **同批仍是冻结的**：「导航 + 选配置」放进**同一批**仍会被 `SCOPE_NOT_DISCLOSED` 拒绝 —— 这是**有意设计**（一批工具不许自我扩权），不是缺陷；模型只有按批串行才能继续。
- **`confirm_step` 依赖「前端先落库再回执」**：刷新读的是 `TaskService` 的权威 `currentStep`。若前端回执早于落库，刷新会读到**旧步骤** ⇒ 结果是「不前进」而不是「跳步」（安全侧），但披露面要再等一批才变。**该时序本批未在真机验证**，登记为边界。
- **信封恢复可能回退请求边界的 context**：恢复路径按 `ToolExecutionEnvelope` 重建快照，其 `context` 可能回到请求边界那一份（本批**未改恢复路径**）⇒ 批间刷新的成果在恢复后可能被回退到边界值。影响面 = 恢复后**多等一批**，不是越权。
- **回落口径的方向是「宁可少，不可多」**：callbacks 为空就是空、无快照就不重算、名字面（`toolNames`）非空就不重算 —— 绝不把「没有工具」变成「全部工具」。
- **执行期补齐不是授权**：它保证官方委托能按名字解析到 callback；能否执行仍由防线③与确认门决定，`No ToolCallback found` 仍是"该工具现在本来就不该被披露"时的如实失败。
- **`tools.yaml` 只升 version**：改描述必升 version（破 prompt 缓存），本批 `2026-10-27.1 → 2026-10-27.2`；`create_task` / 四条 `start_*` 的描述与已发布版本**未动**。
- **门禁只跑文档门禁**：`node scripts/ci/check-docs.mjs` 是文档结构/脱敏检查，**不是产品测试**，其通过不代表任何代码正确性。
