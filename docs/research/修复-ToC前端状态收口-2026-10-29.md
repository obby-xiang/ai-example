## 二、口径与判据（为什么这样改）

### 2.1 准备中的自动恢复为什么是"探快照"，不是"重发"

`preparing` 是"已 start、快照未建"（后端压缩/建上下文阶段）。这一刻后端**已经有这一轮**了，
重发 `/chat` 就是第二次真实副作用。唯一安全且可达的动作是重跑既有恢复链
`runs/current → （202 preparing 则保持准备中 / 200 则重挂 / 空态则封口）`。
所以自动恢复链 = `restoreSnapshotGuarded()`，判成功 = `preparingRun === null`。

预算耗尽时不封口（准备中仍可恢复），而是落 `currentError`（`code=PREPARING_TIMEOUT`）——
面板的恢复错误条与「重试恢复」钮是**既有**出口，本批不新增 UI、也不依赖不存在的按钮。

### 2.2 断流封口与"待决卡保留"的分界

断流（`!terminal && !suspended && !preparing`）= 这条连接到此为止，**但不是这一轮**到此为止：
确认卡 / 表单仍等人动作（刷新由 `restoreSuspendedSnapshot` 续上）。所以封口只作用于**消息**
（`streaming/done/段`），不动 `requiresAction`、不置 `recoveryGap`、不出错误卡。
`done` 帧的既有路径会在之后正常收口卡片；`suspended` 收流（挂起即断）与准备中**不封口**。

**R1（M-4）封口只封本轮宿主**：命中顺序 = 显式 `hostMessageId` → `activeRoundHostId` →
"最后一条未收尾且 `runId` 与本轮相同"的助手消息。第三级必须带 run 判据：没有宿主 id 的续收
（`resumeSnapshotStream` 的无卡挂流，`activeRoundHostId = null`）若回落到"最后一条未收尾"，
会封到**另一轮**的半截回答上 —— 那会凭空结束一条与本次断流无关的回答。

### 2.3 停止后表单草稿的**实际**清点（R1 订正）

`stop()` 之后 `activeForm` / `queuedForms` 已置空，**但草稿键仍在**（这是本批意图）。由此：

| 动作 | 是否清掉"停止留下的"草稿 |
|---|---|
| 轮终态帧（`done` / `error` → `cleanupTerminalInteractionState` → `dropActiveForm`） | **不清** —— 单例已为空，没有 toolCallId 可清；这里只清**仍在场**的表单草稿 |
| 明确放弃那张表单（`cancelGenerativeForm` / `cancelQueuedForm`） | 清（前提是它仍在场；停止后它已不在场，用户也就无从"放弃"） |
| 同 toolCallId 表单被快照恢复重建后再提交 | 清（`settleActiveForm`） |
| 换会话 / 接手会话（`adoptFreshSession` / `takeOverSession` → `pruneOrphanFormDrafts`） | 清（前缀 + 在场白名单，孤儿键在此回收） |

也就是说：**停止后失去引用的草稿会一直留在 sessionStorage，直到下一次换会话/接手会话（或用户
手动清站）**。这是有意的（刷新恢复重建同一张表单时还能回填），**不是**"轮终态即清"。本批不把
`pruneOrphanFormDrafts` 挂到 `dropActiveForm`：那会把停止后等待回填的草稿一起删掉，与本批意图相反。

### 2.4 共用有界自动恢复的四条纪律

1. **零副作用才允许自动**：读快照（`GET /runs/current`）、读历史（`GET /history`）、
   把既有轮接回来（`GET /events/{runId}`）、给新会话做一次对账。**绝不**重发用户消息、
   绝不重放工具、绝不重复写。
2. **有界**：`AUTO_RECOVERY_MAX_ATTEMPTS = 2`、`AUTO_RECOVERY_DELAY_MS = 400`，按类别计预算；
   同类同时只跑一条链（`autoRecoveryInFlight`），同类只排一个计时器。
3. **延时启动**：先排后跑（400ms），让人和其它入口先有机会动手 —— 自动动作不抢先。
4. **可整体作废**：换会话（`adoptFreshSession`）/ 停止（`stop`）/ 新发送（`send`）推进版本号并
   清计时器与等待者；用户手动重试（`retryLoadHistory` / `retryRestoreSnapshot` / `retryPreparing`）
   只作废**该类**（手动出口接管）。

三类接线的判据：

| 面 | 何时触发 | 恢复动作 | 成功判据 | 耗尽后（既有手动出口） |
|---|---|---|---|---|
| 首帧超时 | `send` 的 `onClose({timeoutStage:'first-frame'})` 且**一帧都没收到**（`sawAnyFrame === false`） | `restoreSnapshotGuarded()`：把既有轮接回续收；这一帧周期内 `finally` **让位**（不复位 `loading`、不封口宿主，否则刚接上的续收被判成结束） | **R1（M-2）真接回**：`activeStreamRunId !== null` 或 `activeStreamParked` 或 `preparingRun !== null`（**不是** `loading`：驱动预算不足/陈旧 runId 都会只置 `loading` 而无连接） | `onExhausted` 结构性收尾：`loading=false` + 封口本轮宿主；首帧超时提示保留（+ 面板失败回稿） |
| 历史读取失败 | `loadHistoryInner` 的 history catch | `loadHistory()`（纯 GET） | `historyError === null` | `historyError` + 错误条「重新载入历史」+ 恢复缺口入口 |
| 410 已换会话 | `send` 的 `SESSION_PURGED` 分支（已 `adoptFreshSession`） | `loadHistory()`：给**新会话**做一次对账 | `historyError === null` | 面板失败回稿（原稿留在输入框一处） |

**关于 410 为什么只对账、不复发**：既有裁决与 `tests/session-purged-recovery.spec.ts` 明确锁着
"不自动重发"（`api.chat` 只调 1 次、`outcome='error'`、原稿回输入框）。复发既会与面板回稿叠成
重复文本，也是**第二次真实副作用**。故本批的 410 自动恢复只到"新会话对账"这一步，手动出口不变。

## 五、未验证项 / 边界（如实）

1. **真机一律未执行**：没有浏览器 + 后端环境。以下都需要真机复验（尤其 1/2/8）：
   - 服务端长时间压缩（快照久不建）下，自动恢复是否在 2 次探活内接管，耗尽后错误条是否可点；
   - 真实断网（拔网线 / 代理 502）后重挂断流：气泡光标是否立即封口、待决卡是否仍可点；
   - 首帧超时后自动接管：**必须**确认没有产生第二条 run（后端归档里该 session 只有一条 run）；
   - 410 场景：换 id 后自动对账不报错、原稿仍在输入框、不会出现重复气泡。
2. **准备中耗尽后的观感未在真机确认**：`loading` 保持为真（输入禁用）+ 错误条重试 —— 这与
   "可恢复阶段"的语义一致，但禁用时长是否可接受要真机看。
3. **自动恢复的时延**（400ms × 2）为主观取值：本批与 `PRE_STREAM_RETRY_DELAY_MS` 对齐，未做真机手感调优。
4. **`readActionRecord` 的 `source` 口径**：仍是两值闭集（`AI`/`界面`）。闭集外/缺失回落「界面」——
   这是既有默认，本批不新增第三个值、也不改 locale（面板 chip 的 `source` 文案仍是中文原值，另案）。
5. **本批不动**：`v-memo` / 滚动跟随 / 整屏闪 / `AiPanel.vue` / `locales` / 类型层。
   复审 M-3（首帧超时"恢复成功"与面板回稿叠成重复文本）**归呈现批**：本批按要求不改面板，
   store 侧也不新增"已排自动恢复"字段；在面板修好前，真机可能出现"气泡在续写 + 输入框仍有原稿"，
   这是已知的**跨批交接面**，不计入本批修复范围。
6. 本机为跑测试给 `frontend/node_modules` 建了一个指向兄弟工作树的 **junction**（已被 `.gitignore` 覆盖，
   未入库）；删它会导致本工作树无法直接跑前端测试。
7. **停止后草稿的寿命**（R1 订正，见 §2.3）：停止留下的草稿会一直活到换会话/接手会话；轮终态帧、
   以及"停止后再放弃表单"都清不到它（表单单例已空）。这是有意保留（刷新重建同 toolCallId 时可回填），
   但意味着 sessionStorage 里可能长期存在一条不再可达的草稿键 —— 未做额外回收，属已知边界。
