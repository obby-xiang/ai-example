## 1. 六问逐项结论

### Q1 压缩上下文时页面“卡死”

**结论**：代码里“压缩”与“浏览器主线程阻塞”之间**没有直接同步调用链**（D 级排除）；最可能的真实症状是**压缩静默期被感知为卡死**（A 级），其次是**长会话的主线程成本**（B 级，量级未测）。

**A 级：压缩静默期（能解释“像死了”，但不阻塞主线程）**

1. 压缩在 `out.start` **之前**同步跑完：`compactBeforeRequest` → `MemoryWindow.plan` → `codec.serializeAll` → `ContextCompactor.compact`，压缩完才发 `start` 与 `context` 帧。
2. **L2 是 N 次串行摘要**（`chunk-tokens=8000` 分块 + 递归合并），单次硬上限 `summary-timeout=60s`；L2 触发点约 80% 窗口（128k ⇒ 约 92k token）。代码自述：“续跑路径在压缩期间既没有业务帧、也没有心跳：L2 的 N 次串行摘要每次最长 60s”。
3. **心跳只在“上游流式回调”里发**，即 `start` 之后 ⇒ 压缩全程 **0 帧、0 字节**；Spring 的 SSE 响应体通常在第一次 `send` 才提交，浏览器连响应头都拿不到。
4. 前端 `POST /chat` 走裸 fetch，**没有建连/首帧超时**（45s 的帧间静默判死要等 `response.body` 可用才启动）；服务端 `SseEmitter(-1)` 也**没有传输死线** ⇒ 首轮压缩期间可以无限等。
5. 设计稿把“压缩提示条”列为验收项，**从未施工**；`contextCompaction` 状态全仓**只写不读**；用户能看到“活着”的唯一信号是 CSS 呼吸点。
6. 项目自己的业界调研判据已写明：“压缩期间显示状态行 + 已用时间；不能静默 10–30 秒（用户会以为崩了）”。
7. 续跑路径同型：`ResumeService` 也是先压缩再 `out.context`；前端 EventSource 有建连 15s + 帧间 45s 两个狗 ⇒ **压缩 >45s 即判断流** → 退避 4 次（1/2/4/8s ±25%）→ 耗尽后提示“结果可能不完整”，而后端可能仍在压缩。

**B 级：长会话主线程成本（机制确定，量级未测）**

- 消息列表无虚拟化、无 `v-memo`、无上限；工具卡/只读卡/门卡字段表一律 `v-show`，DOM 恒在。
- 每张工具卡每次渲染多次 `JSON.parse(args)`（`paramRows/argRows`、`hasBodyRows`、`gateRows`、`toolSummary`、`outputByView` 各走一遍），只有表单 spec 做了 WeakMap 缓存。
- 每个 delta 只做 O(1) 段内追加，但会触发**整个面板**重渲染；面板常驻 `App.vue` ⇒ **面板一卡，整页卡**。
- 镜像 300ms 一次**整会话 `JSON.stringify`**，且 `parts` 与内容投影**双份写入**，异常被完全吞掉；镜像 `mdCache` 为 128 条 **FIFO 非 LRU**，流式每帧写入新键会挤掉历史块 ⇒ 长会话进入“每帧重算若干历史块”的稳态（每块含 markdown 解析 + 高亮 + DOMPurify 全量净化）。
- 在输入框打字、鼠标移入/移出输入区**同样触发整面板重渲**；每帧还有 2–3 个“读-写-读”强制布局回合（滚动指纹 watch、逐条 `scrollHeight` 测量、`pinBottom`）。
- 审计已登记同类风险并注明“未测量”。

**C 级（弱，需 profile）**：`loadHistory` 全量渲染 + 逐条强制布局；mermaid 同步渲染（`Promise.race` 3s **打断不了同步渲染**）；mermaid/前缀/markdown 缓存 + DOM 全量带来的内存与 GC 压力。

**D 级（已排除）**：

- `context` 帧载荷很小，不会引起大 JSON 解析；`contextCompaction` 无任何 UI 消费方；`loadHistory` 只有“面板挂载”“复制页签接手”两个入口 ⇒ 不存在“压缩→递归刷新历史”的环。
- 前端无 compact 按钮、无手动 `/compact` 端点。
- 提供的后端日志里**没有一次真实压缩**（全部 `reason=under_threshold`，ratio 0.001–0.109），因此该日志**不能**作为本问题的证据。

**提交归因（有条件，不能当因果）**：批①首次把压缩放在 `start` 之前（引入静默窗）；批②③引入 L2 递归摘要（把静默窗放大到分钟级，这是“压缩慢”的直接来源，但**不是**“浏览器卡死”的证明）；10-24 的渲染性能批撤掉“页签级 24ms 粘滞降级”，使“慢渲染自动降级”这道保险消失（若 profile 证实主线程阻塞，这是最可疑的渲染侧变更，但证据不足以归因）；10-26 两个提交只动 `awaitingInput` 与取消终态，**不能凭时间算回归**。

**要先答的三件事（否则结论会分叉）**：①用户说的“无响应”是 Chrome 的 “Page Unresponsive” 对话框，还是主观“页面没反应”；②卡死发生在**发新消息后**还是**批准续跑后**（后者会叠加 45s 看门狗→重连→断流）；③复现时后端日志里**有没有** `level=L2`。

### Q2 思考块只显示“共 N 字 · 点击展开”，应显示“思考中”并计时

**结论**：这不是产品决策，而是 2026-10-15 视觉重做时的“**无数据替代方案**”：蓝本写“已用 3 秒 · 点击展开”，本仓当时既没有思考帧、也没读帧时间，于是用 `text.length` 补位，注释里明确写“不伪造时长”。**但这句注释今天已不成立**——每帧都带 `atMs`，思考段的起止边界也齐备。

- 现状：段为空不出卡；卡头是 `<button>` + 圆环 + “思考过程” + 摘要位（`共 N 字 · 点击展开/收起`）+ chevron；展开体 `v-show` + 内滚限高；**思考卡头没有 `aria-expanded`**（工具卡头有）；`part.streaming` 在模板里**完全没被消费**。
- 数据面：`atMs`（服务端钟）在**每一帧**上，实时帧与归档帧都带，且进归档；但段写入时 `atMs` 与 `message_end.chars` **被直接丢弃**（`message_start` 只记首帧时间到消息级，`message_end` 只封口）。进行中计时在仓内没有任何 JS 秒表（“工作中…”是 CSS 动画）。
- **四条路径纯前端可做、后端零改动**：实时、续跑（决策后/工具轮后再思考，每段各有独立起止 ⇒ 天然“一段一张卡、一段一份耗时”）、断线重连（补发的是带原始 `atMs` 的 delta）、刷新恢复在途轮（清段 + `lastSeq=0` 全量重放）。**例外**：轮次帧数超归档窗口（6000 帧，且按字节再收窄）时起点可能已被裁掉 ⇒ 只能显示“≥N 秒”或不显示，**不得回落到“从当前时刻起算”**（会假报 0）。
- **唯一真缺数据的路径是历史回放/已完成轮刷新**：`/history` 返回里**不含思考内容、不含段级时间**，前端历史只建 text + tool 段 ⇒ 现状是**刷新后思考卡整块消失**（不是“没耗时但有正文”）。要在这条路显示思考卡与耗时，必须后端新增暴露字段（文本可复用已存的 `metadata.reasoningContent`；段起止需新持久化），属新需求。
- 续跑时新 emitter 的“思考段未开”状态 ⇒ 会**再发一条 `message_start(kind=reasoning)`** ⇒ 同一条消息出现多张思考卡（现状即如此）。
- 测试绑定面：唯一断言“共 N 字 · 点击展开”的用例、摘要节点的 `nth-child(3)` 位置断言、i18n 键双向对齐 + 中文硬编码残留棘轮（`AiPanel.vue` 基线只许下调）——改文案必须同步，否则 CI 红。

**方案（供审，未施工）**：推荐纯前端方案 A —— 给思考段加 `startedAt/endedAt/lastFrameAt`（均取服务端 `atMs`），文案改“思考中 · N 秒”/“已用 N 秒”，**无起点时不显示耗时**（不伪造），保留卡头开合、补 `aria-expanded`；注意 `AiPanel.vue` 是约 3,700 行单组件，面板级 1s tick 会每秒重渲整棵树，应抽卡头子组件自持计时器。后端加 `durationMs` 的方案 B 只在“历史回放也要耗时”时才是必须。

**待裁决 8 项**：①“不要点击展开”是删动作词还是连正文开合一起删；②“思考中”与耗时是否同屏；③耗时格式；④多思考段口径（每卡各自 vs 同消息汇总）；⑤进行中是否自动展开；⑥历史回放是否必须有耗时；⑦截断角标 hover 里的字数算不算“字数统计”；⑧无障碍等价（是否补 sr-only）。

### Q3 “AI 返回中断，请重试”为什么总是一句话

**结论**：用户看到的三个片段是**同一条后端 `error` 终帧**拆出的三段（标题/详情/引导），对应错误码只有 `UPSTREAM_STREAM_INCOMPLETE` 及其两个派生码；**中文路径永远只用基础码的白名单短句**，所以三态共用一个标题、一句引导。

**调用链（A 级，逐跳可对上）**：流“安静”结束且整轮没收到带 `finishReason` 的终帧 ⇒ `StreamViolationException.INCOMPLETE` → 分类器直接映射 `UPSTREAM_STREAM_INCOMPLETE`（retryable=true）→ 重试闸门（`maxAttempts=2`）→ 不重试则 `fail()` → 码加现场后缀 → `messageFor` → 白名单 `SAFE_FAILURE_MESSAGES`（“AI 返回中断，请重试。”）→ `out.error(code,message)` → `emitTurnEnd(...,"failed",code,...)` → 前端 `case 'error'` → 错误卡映射 → 中文文案 key → 内联渲染在出错的助手消息上。

**为什么只看到一句（A 级）**：

1. 后端 `messageFor` 先取 `baseCode()`，**中文分支直接 return zhFallback，从不查 `messages_zh.properties`**；而该文件里明明已为派生码写好“已显示的内容不完整 / 且本轮已有工具执行”三句 —— **中文用户看不到**（英文分支才按完整码查 `messages_en.properties`）。
2. 前端错误卡同样把三个派生码削回基础码再查表，只配了一条 title/guide；只有 `detail` 逐字透传，而 detail 恰好就是第 1 条那句常量。
3. 另有两条**近似**文案走完全不同的组件（通知槽、顶部 Alert），三条都在说“断了/内容留着/重试”，肉眼极易合并成“总是同一句”。

**频次反证（日志实证，D 级）**：给定后端日志（单实例 30 分钟、单会话、1012 行）中该码 **0 次**；`turn_end status=done` **15/15**、`attempts=1` 15/15；重试事件 0、`AI 轮次失败` 0、`UPSTREAM_*` 0、取消/断流 0；目标时段 10:52 与 10:53 两轮均正常 `done`；`upstream_first_byte` 15 次（656–903ms）；关流 `reason=完成订阅者` 27/27 正常。ERROR 级 50 行全是 25 条聚合器异常，**异常类型全部是挂起设计路径的自造异常，不是上游/协议错误，不能当失败计数**。⇒ **“经常”在这份日志里既不能证实也不能证伪**（覆盖太窄）；能确证的是“这段时间该实例从未判定过断流”。

**C 级弱线索（真实存在，但症状不是这张卡）**：挂起路径上“订阅在**挂起请求帧发出之前**就关闭”，随后走“死卡兜底续跑”；前端若没收到卡面请求帧，会按断流提示——但产出的是**通知槽/顶部 Alert**，不是这张错误卡。该区域正是 10-25/10-26 反复在动的“终帧重连与投递收尾竞态”带，但日志里没有一条能对应到断流码，**不能据此说回归**。

**最小方向（供审）**：①只改文案精度不动判定——让中文分支也走按完整码取文案的路径（三句已就位）；②把错误卡的 `code` 显示在次要位置或仅在 `?debug` 下，便于下次取证；③**不建议**加长超时、把断流一概改写成“网络异常”、或为消除提示而关重试（会把真故障藏起来，且与本次证据相反）；④独立议题：帧唤醒“订阅已关 → 挂起帧才发”的时序值得单独审（日志里 13 次死卡兜底说明挂起/续跑在正常路径上经常依赖兜底，观感是“卡住”）。

**要定论需要抓的三样（当前全空）**：后端 `本轮尝试失败|AI 轮次失败|event=turn_retry`、所有非 `done` 的 `turn_end`（含 code）、非挂起类型的聚合异常；再加前端该次 `error` 帧原文（code/message/seq）与是否刚发生 reattach。

### Q4 已终态任务重复导出 + 卡面“已批准 · 执行失败”

**结论**：三个现象要分开——“已完成不能再导出”是**既有且正确的业务约束**；“卡面显示已批准但没批准过”是**产品缺陷（UI 语义失真，且被测试锁死）**；“已完成仍披露开始导出”是**披露面不看任务终态**。

- **取证的硬边界**：给定日志里**没有**截图所述的会话号（唯一出现的是同一路径的另一次复现，任务/作业号 673，构建与 HEAD 一致）。因此**该截图会话的归因仍属待证**；下列“机理 A”是同一代码路径的**可复现机理**，不是对该截图的直接取证。
- **正确约束**：CANCELLED 恒拒；COMPLETED 按类型核最终作业（导出→存在成功导出作业）⇒ 409 `TASK_FINALIZED`；预检复用同一判据，失败文案为“任务 #N 已 COMPLETED，不可再发起导出作业”。测试已锁（守卫生效有；预检侧只有发布用例）。
- **机理 A（最强、与日志形态一致）**：预检不通过时**不进确认门、不发确认请求、不弹卡**，只结算一条 `PRECHECK_FAILED` 失败帧；但该帧的类型是“确认类 + 失败”，前端据此建**确认卡**且 `requiresAction=false` ⇒ 命中“已决只读卡”判据 ⇒ 在“无决策 + 失败”时返回“失败”态 ⇒ 文案渲染成 **“已批准 · 执行失败”**。这个“冒充已批准”还被测试锁死（一条断言无决策失败即 `failed`；另一条只断言含“执行失败”，放过了“已批准”前缀）。后端注释自述“前端零改动即可显示失败 + 完整原因”——该假设对确认类卡并不成立。
- **机理 B（待证）**：预检与执行之间存在 TOCTOU 窗口（代码自己登记为观察项）；若卡片停留期间上一笔导出作业收尾、任务转 COMPLETED，批准后创建作业会抛终态冲突，此时“已批准 · 执行失败”是**如实**标签。判别方法：日志出现“预检未通过…start_export”⇒ A；出现“approval_decided…APPROVED”且随后终态冲突 ⇒ B。**本日志只有 A 的形态**。
- **披露面**：工具披露只按 页面/任务类型/步骤/ui 打标签，**完全不看任务状态**（任务状态根本不进上下文，属结构性）⇒ COMPLETED 且停在导出步时，“开始导出”与“下载导出文件”同时披露，没有“终态只读”收窄。而“终态只读”判据只用于前端 UI 事件通道，与 `start_*` 不是同一道闸。
- **模型侧信息缺口**：`get_workspace_state` 只回 标题/类型/步骤/状态/配置项，不含“最近作业、导出文件清单”；`check_job_status` 必须给 jobId。要下载只能靠 `download_export_files(taskId, defCodes)`。系统提示里**没有任何“已完成→改下载”的引导**，第 7/17 条反而强推“直接发起工具、确认卡承接”。
- **模型行为（复现可证）**：说“让我查看工作区状态”那一轮 `toolCalls=0`，真正调用发生在后续用户轮。
- **“AI 返回中断”与导出被拒是两条独立错误**；本日志 15/15 正常 `done`，未发生中断（唯一相关异常是任务事件流的 SSE 超时，与 AI 流无关）。
- **测试缺口**：“已完成导出任务 → 再导出被预检拦 → 卡面文案不含‘已批准’ → 引导下载并成功”这条整链**没有任何端到端/集成用例**。
- **最小方向（供审）**：①对“未进门的终态”在落库时打显式标记，只读态新增一支（如“未批准 · 未执行（预检未通过）”，中性色），**不要复用“超出披露范围”那个态**；同步收紧两条测试断言。②上下文增 `taskStatus`（进白名单），披露标签在“COMPLETED + 最终作业成功”时收窄 `start_export`（执行侧同步，避免分叉）；系统提示补一条“已完成且导出成功 ⇒ 用下载工具，不要重复开始导出”。③批准→执行前再判一次终态冲突，失败返回专用码并附“可下载已导出文件”的下一步。④`get_workspace_state` 增“最近作业（类型/状态/ID）+ 已生成导出文件条目”。⑤补一条全链用例。
- **仍需补的证据**：该会话的 run 日志（键：`预检未通过.*start_export`、`approval_decided.*start_export`、`Starting job .* taskId=<该号>`、`TASK_FINALIZED`、`event=turn_end.*runId=`）、该轮帧册、以及若坐实机理 B 时两个事件的先后时间。

### Q5 创建任务没有确认卡

**结论**：不是确认门漏拦截、也不是卡片渲染 bug——`create_task` 在当前代码里被**显式定义为 WRITE（自动执行、可逆副作用）**，而确认门只对 DANGER 生效；但这也**不是“本来就该这样”**：2026-10-17 用户直裁明确要求“`create_task` 不得静默建库，改为软确认或进门”，归属批 2B，而 2B 至今**待开工**。⇒ **已定稿未施工的实现缺口**，不是新需求、也不是 bug。

**链路（A 级）**：工具标注 WRITE → 挂起种类判定（前端通道→前端工具；DANGER→确认门；其余→后端直接执行）→ 预检只认四个 `start_*`（按工具名，不按风险档），`create_task` 天然跳过 → 目标校验器也明写“不在本类校验面内” → 前端只有一张普通工具卡。

**日志实证**：`page:tasks` 披露集含该工具；两次调用均 `kind=BACKEND approval=false` → `ok=true executed=true`（约 38ms / 115–160 字符），**全程没有任何确认请求**；同会话 `start_export` 的确认卡正常弹出并在 4 秒内被批准执行 ⇒ **排除**“模型没调”“调用失败”“卡渲染丢了”。

**已定稿未施工的证据链**：裁决卡“改为软确认或进门（不得静默建库）”归批 2B；决策看板同条注明“裁决已定稿，非施工完成：2A ✅ / 2B·2C 待开工”；任务看板该行仍为 📋；研究稿把要求写得更细（预检 type/标题、展示“将创建：类型+标题+初始步骤”、宿主幂等键、单轮最多一个）。时间线也说明不是“先有实现后有需求”：工具 10-07 落地（WRITE），裁决在 10-17。

**文档口径互打（需一次性对齐）**：10-23 的真机 E2E 设计（L-05）与 10-24 的审计（P-02）把“WRITE 无门”当成**现行正确**，而 10-17 裁决要求改掉它；两份看板从未把 2B 标为完成。写文档/验收时必须声明哪一条优先。

**附带缺陷（同一场景的另一半）**：

1. 新建**导入**任务后会被导到**导出**向导：`restore_task` 只带 taskId，前端路由兜底**同步**写死 `'EXPORT'`，不查后端（异步版会查任务类型）；AI 新建的任务不在前端任务列表里 ⇒ 必然走兜底。本次日志恰好是导出，所以没暴露。
2. 任务中心列表**不自动刷新**：挂载只拉一次、无任务级事件订阅（只有右上角手动刷新）；`refresh_tasks` 只是前端事件名，**后端没有同名工具** ⇒ 模型无法主动让列表刷新。AI 建的任务在“仍停留在任务中心”的视图里不可见。
3. 无幂等、无单轮上限（审计已登记，2B 计划内有、未实现）：日志中 15 分钟内两次 `create_task`、只产生一个作业 ⇒ 第二次很可能是空任务（**未查 DB，属推断**）。

**方案（供审）**：①升 DANGER（最小、与 2B“进门”同向）——须同批改系统提示（第 8 条、第 17/18 条）、两处测试与若干文档；代价是每次建任务多一次点击、`create_task`+`navigate_to` 同批时多一次往返。②软确认（2B 本体，需新增非阻塞提议卡/可编辑标题后再确认的通路，等于新增机制，需裁决）。③零行为变更只消除歧义（提示词要求回复明确“已创建任务 #N”，文档把 2B“待开工”显式标为已知偏差）。

### Q6a 创建任务后只文字询问、不出表单（选配置项）

**结论**：**不是渲染或披露故障**。真因是两条叠加：①系统提示词第 18 条把“**选择配置项**”逐字列为允许文字询问的开放信息，且全篇从不点名生成式表单；②表单能力本身不覆盖“选配置项”这个场景（场景白名单只有筛选/澄清两类，唯一选项数据源以“配置定义编码”为父值返回字段，**不能枚举全部配置定义**）。模型按现有契约选文字询问，是**被允许的行为**。

- **排除项**：工具未披露（披露测试断言任务中心与导出/导入各步都披露；S44e 的运行时披露原文也含选配置项工具）；前端未渲染（七型表单真机用例在）；状态不同步（存在但不是“不出表单”的充分原因——`create_task` 不写任务项、前端不绑定任务、续跑上下文在请求边界冻结；这会让“后续选配置”打空，而不是“不显示表单”）。
- **结构性要点**：即使用户在表单里勾了配置项，**表单值也不会自动写进任务**——模型还要再调一次“选定义”动作。表单只是“收值”通道，不是“选配置项”的动作本体。
- **主因的归因提交**：10-22 新增提示词第 17/18 条是近期**唯一**改变“该不该出表单”的提示词面；工具描述与披露自 10-07 引入后**至今未改**。
- **产品侧诱因（推断，未实测）**：任务中心每轮建议里有“新建一个导出任务”chip；从该 chip 触发时用户没有给配置项，模型先建任务，随后在“规则 18 允许文字询问 + 无表单指引”的契约下直接文字问，是最省事路径。
- **测试盲区**：真机套件只有 4 条且不含本链路；表单 E2E 全部是“提示词点名 + 桩强制”（桩按 `scenario=` 关键字命中、另有强制工具通道）⇒ 这些绿只证明“下发→渲染→回填→续跑”管道通；单测只锁半条链（断言 `create_task` 返回文本含跳转引导，不锁表单路径）；真模型服从率无法由 CI 证明。
- **方案（供审）**：A 提示词最小改动（补“结构化选择优先表单”，并在工具返回文本补“若用户未指定配置项：先列定义、再用表单勾选、再选定义”）；风险：系统提示是编译期常量，改字即击穿 prompt 缓存前缀，且表单选项需模型硬编码（≤50 项）。B 新增选项数据源（需裁决：场景闭集只有筛选/澄清，“选配置项”不在授权范围，要么复用“澄清”语义、要么新增场景）。C 改为进向导选择器（最贴合现有产品，但“自动导航”是新行为，且与“导航后结束本轮”的规则冲突）。D 后端增“任务项非空”校验（审计 E-01，防“作业成功、零文件”的假成功）。
- **必配验证**：新增 1 条真模型采样用例（提示词只说“帮我新建一个导出任务”，不点名配置项、不点名工具），统计三种结局（出表单/进向导让用户勾/纯文字问）；**不要用桩补这条证据**。
- **尚不能断言**：没有该次 run 的帧/快照/日志，无法排除“模型试过表单但 schema 被白名单拒绝（不下发、前端看不到）”或“前端解析失败被静默收敛”两条支路，也无法区分模型是主动问还是被“导航后结束本轮”要求用文字收尾。

### Q6b 筛选条件没有表单 / 是否应“一次只给一个字段”

**结论**：首要原因同 Q6a——**没有任何提示词/产品契约要求模型在自然筛选请求下必须出表单**；系统提示全篇不含表单工具名，规则 7 让模型直接走向导勾配置项/设条件，规则 18 明确把“筛选条件”列为可文字询问；而“设条件”与“表单（筛选场景）”语义重叠、**没有选择判据**。测试通过只证明“桩点名让模型调表单后链路能消费表单”。

- **两种“没有表单”要分开**：①**页面不对**——在配置定义页/数据浏览页，表单工具**刻意不披露**（产品范围问题，代码层面就没有该工具）；②**页面对但模型不出**——任务中心/导出向导，模型可用规则 18 文字问或直接设条件（提示词/契约问题，用户最可能命中这条）。
- **模型看不到的上下文**：字段清单与已有条件 JSON 都不在上下文里；表单是模型**手写**的一整张 spec，产品不会按已选配置项自动生成。
- **“一次只给一个字段”的能力边界**：能做单张表单内的条件显隐（`visibleWhen/requiredWhen/disabledWhen`、`optionsFrom.map/sourceId`、`defaultFrom`，联动深度上限 2）；**做不到**按当前选中字段动态改值控件类型（字段 type 是 schema 静态属性）、做不到动态返回某字段的取值枚举（唯一选项源返回的是“字段清单”而非“某字段取值选项”）、单表最多 20 字段、序列化超 8000 字符整张被拒、渲染器无分页/步骤（只有卡内内滚）、同一时刻只有一个活动表单（一轮发两张时第一张失去可填入口）。缺的不是联动原语，而是**提示/编排层**：没有“一次只问一个字段”的规则，也没有“把字段元数据转成单字段表单”的桥。
- **桩为什么掩盖**：桩自认不是模型行为替身（CI 全绿只证明产品消费了桩给的表单）；路由只在提示词含 `scenario=` 时命中；固定返回 5 字段（导致“单字段”用例实际没验证）；解析器只检查 key 在不在；上次真机 0/10 的结论受帧序缺陷污染；未触发按 SKIP 处理 ⇒“模型不出表单”被记成模型行为，不会作为产品缺陷暴露。
- **重要异议（外部研究给出，且与“一次一个字段”方案方向相反）**：GOV.UK 的一屏一问面向**服务问答**而非探索性筛选；NN/g 明确 staged disclosure 在“步骤相互依赖、用户需来回修改”时有害，而筛选往往正是这种场景；LangGraph“一次一个中断 + 条件边重问”适合“缺一个关键字段”，不适合“十个相互影响的筛选条件”。更稳的对照是“**常用筛选一屏 + 实时结果 + 高级条件渐进披露**”，只有首次引导/长尾条件才逐项问。⇒ 该交互应作为**待裁决的产品选择**，不宜直接写进验收。
- **建议的最小交互（若采纳逐项收集）**：判配置项（>1 时先问先筛哪个）→ 只给一个字段选择控件 → 需要时问操作符 → 只给一个与字段类型匹配的值控件 → 继续或结束（重复）→ 最终汇总成一条多字段条件（AND）。
- **必须保留的边界 10 条**：编辑已有条件是**整份替换**且模型看不到现值（当前是待裁决缺口）；必填只校验“可见且必填”；取消是明确终态、不自动应用部分条件；切字段要清值并级联裁剪；多字段最终要汇总成一份 AND；配置项与字段不能混（表单值≠已选配置项）；空条件被守卫拒（不要把“清空全部条件”做成表单提交）；同一时刻只能一张表单（必须串行）；只有导出作业读条件 JSON（预检查/导入不读）⇒ 不要让用户以为筛选会影响预检/导入；回灌是“字段 key→值 JSON”不是条件对象。
- **仍需实测 6 项**：HEAD 上自然语言是否触发表单；模型一轮是否只发一张；长表单被拒是否就是用户现场的直接原因（机制确定、无该次日志）；同一轮连续两次表单是否可靠；用户当时所在页面；编辑已有条件的产品口径。

**规格/口径冲突 12 条（按风险排序，均 A 级）**

1. **全量历史落库 vs “AI 对话数据不落库”**：后者是 🏛️ 级立法（“对话内容/工具入出参/决策元数据/取消记录只在 Redis、随会话共亡，不落任何持久层”）；前者建表并声明“不随窗口裁剪、不复用运行态 TTL、不做 24h 过期”，两者正面冲突，且看板无 supersede 行。**授权面见 §7 补正**：功能级授权存在，“无 TTL”属授权范围不明；**规格冲突不因有授权而消失**。
2. **冻结需求仍写“6 小时 / 无长期留存”**：02 无追加注记；03 正文多处仍写 6h，只在末尾追加注记改 24h；README 仍写 6h ⇒ 对外引用会拿到三个不同答案。
3. **“审批卡一直等” vs “24h 严格共亡”**：两句都“对”，但用户看到的是第三件事——卡面没有倒计时，离开超过 24h 后数据消失、提交才失败；park 生产路径没有心跳线程续期，只有读侧 touch 才续，而前端挂起期不轮询。
4. **DLP 删除 + 全量持久化**：两次单独批准，组合后“用户粘贴的密钥/口令原文永久入库”没有任何裁决或缓解（反馈摘录守卫只保护摘录，不保护聊天正文）。
5. **摘要模型：设计说可切，代码说不可切**：设计稿仍列“可切”能力，代码注释明确“没有独立分支”，yml 键成哑键且无退役告警。
6. **03 正文仍写“确认门有上限、超限转异步”**：同一文档两套口径，靠“追加注记优先”维持，外部读者极易误引。
7. **看板的状态列不能当“未施工”**：多条 10-21/10-22 裁决仍为 📌，但对应批次已 ✅、代码也已落地 ⇒“批准却没做”必须逐条对代码。
8. **轮内预算的“本轮结束”跨挂起不成立**：注释说 armed 后直到本轮结束都不执行工具，实际 armed 与跳过计数都在进程内信标，park 后丢失 ⇒ 续跑后模型可以继续产生新副作用。
9. **披露面“结构上无法分叉”不成立**：空 scope 数组在披露侧通常不披露、在执行侧被视为“不限”而放行；当前 37 个工具都显式声明 scope，无现发实例，但这是启动不变量缺失。
10. **渲染规格“围栏 key 全局唯一”不成立**：实际是“每次渲染内唯一”，且该属性在净化白名单里，模型可用原生 HTML 写同名属性劫持图表槽位。
11. **park 与“完整历史”两条 10-25 用户裁决只在代码/计划里**：yml 写“用户裁决 2026-10-25”、SDD 计划说“已批准”，但决策看板无行 ⇒ **决策登记表不是完整事实源**。
12. **实时多卡 vs 恢复多卡的呈现不一致**：实时一次把同批所有待决条目落成卡；刷新恢复只建第一张、其余进队列串行补 ⇒ 用户看到“刷新后卡变少了/要一张张处理”。

### 3.1 自动续传与失败语义（来源 `review-02`）

**三档边界（代码事实，非建议）**

| 档 | 现状 | 是否自动 |
| --- | --- | --- |
| 安全的自动续传 | 首包前失败重试 1 次；断流自动重挂 4 次；刷新静默续收；park 决策后自动重建 + 派发退避 15 次；启动扫描 + 僵尸接管；重挂“已决无驱动方”自愈 | 已有 |
| 只能整轮重跑（当前只剩人工） | 中途断流（已产出正文或思考）、工具已执行后失败、超预算、内容过滤、空回复 → 失败终态 + 错误卡 + 「继续」 | 无 |
| 必须由人决定 | 上下文越窗、鉴权失败、4xx 拒绝、provider 被删、内容过滤、取消后仍待决的卡 | 无（有意为之） |

**四个直接问题的答案**：①**已有半截不能自动续写/替换**——后端从不在“已产出”后重试（`emittedAny()` 把 reasoning 也算已产出），失败终局**不落半截、不收敛记忆**，而取消路径会落 ⇒ “同一个半截，取消能活过刷新，失败不能”；前端是 append 语义，无替换原语。②**工具成功后失败“只重跑模型步”的机制已写好，但入口没有**——续跑路径能按台账复用已结算工具、用同一份固定历史重建 Prompt，这正是“只重跑模型步”的正确形态，但只对挂起轮可达；失败是终态，直接拒。③**“并非完全没有自动恢复”成立**（列 5 条）。④**绝不能引入的 7 类自动重放**：已产出后整轮重跑（思考叠加、正文重复、违反帧序）、工具已执行后整轮重跑（重复副作用，且从记忆重建会丢工具轮，实测请求退化为“系统+用户+用户”）、把挂起工具轮当空轮重试（真事故已封，不能回退）、对失败/取消自动 resume（覆盖终态、双写历史）、静默换模型续跑（有红线）、同一轮开第二条连接、读侧 touch 刷新进行中轮的业务锚点（会把卡死轮越读越年轻）。

**真问题（按源件严重度）**

- **F1（重要）中途断流后的半截正文“服务端无落点”**：刷新后错误卡消失、半截看起来像完整答案。依据：失败路径不落半截、不收敛记忆；前端镜像**不含错误卡**；刷新时镜像消息一律归一为“已完成”；终态轮已清“当前轮”索引 ⇒ 刷新走“无在途轮”分支，不会重挂补错误帧。用户后果：点「继续」时模型内存里**既没有半截答案、也没有工具轮**。**不是近期引入**（形态可追到 S4.2 批），但 park 批让“工具轮在 DB、内存在缺失”的不对称更常见。
- **F2（重要）“工具成功后模型失败”没有安全的重跑入口**，而能力其实已写好（见上）。不是近期引入；10-26 的 W-21 修复是**刻意收窄**（挂起轮不得重试），方向正确。
- **F3（中）失败码缺“已产出/已副作用”的组合**：已登记的码组合只有 8 组，多个带后缀的组合未登记 ⇒ 组合未登记就退回基础码；测试直接印证“有半截 + 500”拿到的是基础码而非“已有半截”码 ⇒ 用户看不到“已显示内容不完整”。
- **F4（中）集群运行期的进行中死轮没有自动接管**：只有启动扫描带强制接管、运维端点不带、无周期扫描；重挂自愈只覆盖“挂起且条目全决”。用户侧：断流 → 重挂 4 次耗尽 → 通用提示；180s 内点「继续」→ 409 → 前端只显示“这条消息没有发出去”。部分近期（“死轮放行新发送”是新改进，“接管旧轮”仍只挂启动路径）。
- **F5（小）`chat()` 环外异常只发 error 帧、不写失败快照**：快照停在“进行中”且索引不清 ⇒ 之后每次刷新都静默重挂这个已死轮。
- **F6（小）开流前瞬时失败（503/网络）不自动重试**：这类零副作用请求最适合有限自动重试，却是纯手工。
- **F7（边界）超长轮的全量回放可能撞窗口缺口**：归档窗口 6000 帧且按字节再收窄，游标早于幸存窗口时回放侧补错误帧收尾 ⇒ “极长回答 + 刷新”可能显示“服务暂不可用”而非答案。
- **F8（小）错误卡「稍后重试」发的是新的“继续”消息**：在“什么都没产出”的 429/5xx 场景，语义上应重发同一请求，而不是往对话里塞一条“继续”（会多一条用户气泡，模型也可能重复自问）。

**外部两个断言的核验结论（重要，防止把别人结论当事实）**：①“重试闸门使重试几乎永远不触发”**部分成立、措辞过强**——“首包前”整类都会重试且有单测锁定（500 两次、IO 两次、429+Retry-After 两次、仅 `tool_calls` 无产出两次）；真正失效面是中途断流，且是**有意**的。另需澄清：**所用 Spring AI 版本内部没有第二层流式重试**（反编译核实：`retryTemplate` 只在非流式调用生效）。②“配置 2 次实际仅 1 次”**是算术事实但归因错**——配置语义是“总尝试次数＝2”，即最多 1 次重试；对中途断流确实只 1 次，对首包前实打实 2 次。③真正值得记的窄点是：**reasoning 一吐就算“已产出”**，推理模型几乎第一个 token 就失去重试资格（为避免重复思考段的有意取舍）。

**最小方向（供审）**：①让失败也留下可解释现场（有半截时把“半截 + 已结算工具轮”写入快照/DB 历史，镜像携带错误卡与码；先只做持久面与展示面，不改重试语义）。②窄入口“仅模型步重跑”（仅在“失败 + 无在途 + 全部待决已结算 + 末段是配对的工具轮 + 无半截正文”时允许一次有界重建；**不重执行工具、不追加用户消息、不跨模型**；有半截的情形必须另有“截断替换”语义才可谈自动化）。③补码面/文案（登记缺失组合，或让取文案时在码带后缀时追加“已显示内容不完整/已有工具执行”）。④死轮兜底（受租约与僵尸年龄约束的低频扫描，与现存活跃判据同源；**不要放宽僵尸窗口**）。⑤开流前有限自动重试。⑥环外异常补终态。

**上下文三级的用户可见性**：轮内 L1 不发光上下文帧 ⇒ 同一张工具卡“实时看是全文、刷新后是占位符”；L3/记忆淘汰无任何“更早内容已压缩/不可见”的说明，上下文帧被 store 收下但不渲染（排批④）⇒ **在批④落地前，三级的用户可见性等于零**，这是“规格变化带来 UX 回归”的主因。

### 3.4 前端渲染性能（来源 `review-05`）

**一个重要的负面结论**：**未发现**“AI token 流导致表格引擎/任务页/向导页重渲或强制布局”的链路；两个向导对 AI store 只有命令式调用。但跨页唯一桥梁是工作区**数据版本自增**，而面板模板直接读该版本 ⇒ **用户在向导里改一格表格，就会触发一次整面板重渲**。

| 级 | 项 | 证据要点 |
| --- | --- | --- |
| P0-1 | **长会话下 Markdown 缓存反复失效**：缓存 128 条、**FIFO 非 LRU**、命中不刷新位置；流式每帧写入新键（长度变化）⇒ 每帧挤掉一个历史块 ⇒ 块数超过 128 后进入“每帧重算约 (N−128)…N/2 个历史块”的稳态（每块 = 解析 + 表格/围栏包装 + 高亮 + **净化全量**）。触发面不只流式：**在输入框打字**、鼠标移入/移出输入区同样触发整面板重渲 | 缓存容量与会话规模脱钩，且未随 10-24 性能批调整（该批只动渲染模块内部） |
| P0-2 | **单体渲染域 + 全量卡片派生计算**：全面板一个渲染 effect，无 per-message 子组件、无 `v-memo`、无虚拟化；每帧对每张卡多次 `JSON.parse(args)`、多次归一化（含 parse + stringify + 两次编码）；卡片体 `v-show` ⇒ 全部历史卡片永久留在 DOM | 量级示例：100 张卡、每卡 3 次参数解析 ≈ 300 次 `JSON.parse`/帧；参数是大表格时单帧即数十 ms |
| P0-3 | **每帧多次强制同步布局**：滚动指纹 watch 每 token 执行（`nextTick` 后再次滚动）、逐条测量所有用户消息 `scrollHeight`、`pinBottom` 读写、内容层 RO 每帧触发 | 净效果：每帧 2–3 个“读-写-读”布局回合，与 P0-1/P0-2 脚本时间叠加 |
| P1① | **10-24 渲染规格变更的两面性**：删掉的是**页签级粘滞降级**（覆盖长会话整体负载的保险），新增前缀缓存只在多顶层块生效、单块形态零收益且多一次 parse；阈值从“页签级”收窄为“单条 >1 万字符”；被降级的条只是不高亮，**净化与结构渲染照旧全量**；“18.65ms→1.15ms/帧”是单块实测，仓内性能用例**没有耗时断言**（无回归闸）⇒ **“删降级是否更差”两面都成立，必须真实浏览器 A/B**。附带语义回退：高亮收窄到 15 语言，其余语言一律退化为纯文本 | 同上 |

## 7. 规格复核补正（**本条覆盖初稿的相反结论**）

> 本批存在一份“规格变化初稿”（`review-06`）与一份**后续复核补正**（`supplement-219`）。两者在“授权”一项上结论相反；**以补正为准**，初稿的不同表述作为历史留痕保留，不回改、但也不得再被引用为结论。

### 7.1 全量历史落库的授权：**有用户授权（功能级）；“无 TTL”属授权范围不明**

- **有直接授权（转述，不回显原文）**：会话记录中助手列出待批 5 项，其中第 2 项是“**完整历史独立存储与分页**”（并说明第 41 条起会从用户历史里真正消失、需要把完整历史与 40 条模型记忆分开、不是简单调大窗口）；随后用户答复的语义是：**第 1、2、3、5 项按业界主流由助手作最佳裁决并直接实施，第 4 项挂起、先登记、暂不实施**。第 2 项即完整历史 ⇒ **功能级授权存在**，且时间上早于实现提交；助手随后确认按此执行。
- **授权范围边界**：用户另有一处约定的是**删除范围**（会话销毁时应把该会话相关的 AI 数据一并删除，业务数据不受影响）——这是“删什么”的约定，**不是**对“永久保存/不设 TTL”的批准。检索到的用户表述中**没有**“永久保存 / 不做过期 / 保留期 N 天 / 不设 TTL”这类明确内容；保留期是用户交给助手按“业界主流/最佳裁决”决定的 ⇒ **保留期属授权范围不明**。
- **原文不在本仓**：上述两句的用户原文只存在于会话记录与仓外交接快照中，按本批口径**不入库、不复制**；本件只保留“授权存在/范围不明”的判定与定位方式。
- **“看板未登记 ≠ 未经授权”**：看板缺席只能证明没有回写，不能证明未授权；初稿把“看板没有登记”写成“没有用户授权”，该结论**撤回**。
- **规格冲突仍然成立**（与授权是两件事）：10-21 的 🏛️ 级裁决“对话内容/工具入出参/决策元数据/取消记录只在 Redis、随会话共亡，不落任何持久层”仍在看板上、无 supersede 行；而建表声明“不随窗口裁剪、不做 24h 过期、删会话才物理删”。冲突在“旧裁决未废止 / 新裁决未登记”这一层，**不取决于用户是否授权功能**。附带基线冲突：02 仍写“默认 6 小时、无长期留存”；03 正文多处仍写 6h，仅末尾追加注记改 24h。

### 7.2 `set_condition` 空值 / `IN []` 的语义反转：完整链（**结论与直觉相反**）

**判定**：存在完整静态链路，**代码可证、未运行验证**；但机制**不是**“`EQ ""` 本身等于全量”，而是“后端闸门接受 → 前端草案把空值当未填 → 落库时用空对象覆盖 → 后端把空条件对每行返回真”。

1. **后端闸门接受空值**：只拒绝 `null`，`""` 不是 null ⇒ 通过；`IN` 只拒绝“非数组”，空数组是数组 ⇒ 通过；“为空/非空”算子直接通过；字段校验只查“是否属于该定义”，**没有重复检测**；只有在“没有任何被接受的字段且无范围键”时才整体拒绝。⇒ 空串、`CONTAINS ""`、`IN []` 都能过闸。
2. **页面 handler 先按原样落库**：解析 AI 传来的条件 → 生成表单草案 → **把原始条件再落库**（不是压平后的结果）⇒ 此刻服务端可能是 `EQ ""`。
3. **前端压平丢弃空值**：带值算子的值 `trim()` 后为空 ⇒ 该字段被丢弃；`IN []` 经草案变成空串，同样被丢弃；没有范围键、没有字段 ⇒ 返回 `null`；序列化 `null` 得到 `"{}"`。
4. **开始导出/推进步骤用 `{}` 覆盖**：落库函数对每个已选配置重新按表单模型构造条件并写回 ⇒ 只要 AI 先设条件、随后开始导出或用户点“下一步/开始导出”，服务端条件会被覆盖成 `"{}"`。
5. **后端把 `{}` 当“无条件”**：`"{}"` 不是空白 ⇒ 解析为非 null 的空条件；求值器对“无范围键、无字段”返回真 ⇒ 逐行全通过；导出作业用同一解析 ⇒ **导出全量**。

**按算子区分（关键在最后一列）**

| 输入 | 闸门 | 原样落库后的后端语义 | 经前端压平后 |
| --- | --- | --- | --- |
| `EQ ""` | 接受 | 只匹配**值为空字符串**的行 | 字段被丢弃 → `{}` → **全量** |
| `CONTAINS ""` / `LIKE ""` / `STARTS_WITH ""` | 接受 | 对非 null 值通常恒真 | 字段被丢弃 → 全量 |
| `GT/GTE/LT/LTE ""` | 接受 | 字符串比较，结果依数据而定 | 字段被丢弃 → 全量 |
| `IN []` | 接受（数组） | 恒 false ⇒ **0 行** | 被丢弃 → `{}` → **全量（0 行反转为全量）** |
| `IN` 非数组 | 拒绝 | — | — |
| `BETWEEN` | 拒绝（不在允许算子集） | 后端无此算子 | 表单层展开为“大于等于 + 小于等于”，AI 直接传会被拒 |
| 同字段重复 `fieldCode` | 接受（无去重） | 原样落库时两条都在 | 按字段分组：大于等于+小于等于合并为 BETWEEN，否则**只取第一条** ⇒ 后一条被静默丢弃；只有“保留下来的第一条也是空值”时才落到全量 |

**精确结论**：①`EQ ""` 本身**不是**全量，全量来自“前端把它当未填 → 丢弃 → 覆盖为 `{}`”；②`IN []` 更直接，**原样落库是 0 行、压平后反而变成全量，属语义反转**；③重复字段单独不必然全量，通常表现为“后一条被静默丢弃”；④**只有在没有范围键时才是全量**——若 AI 同时给了非空范围键，结果是“该范围内不筛字段”，不是整表；⑤该路径标“确定（代码可证）”，**不是“已实测复现”**（本批未运行）。
