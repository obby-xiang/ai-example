## 2. 逐条方案

### 2.1 M-17 历史重载的轮次守卫（`stores/ai.ts:2803`、`:2883`）

**根因**：`loadHistoryInner` 只对账会话身份（`sessionId`），不检查"这段时间里是否已经起了新一轮"。
`/runs/current` 失败落 `currentError` → 用户点错误条"重试" → 重试期间又发出新一轮（`send()` 递增
`roundEpoch` 并换 `currentAbort`）→ 历史回来时 `this.messages = mergeMirrorInFlightRound(...)`
**整体替换**，在途轮的宿主与半截正文被顶掉；后续帧按兜底 `currentAssistantMessage()` 新建第二条气泡
（同一轮两条气泡），并把错位现场写进镜像。

**修法**：入口捕获 `epochAtEntry = roundEpoch` / `abortAtEntry = currentAbort`；`await aiApi.history`
返回并通过会话对账后**再对轮次对账**：

```ts
if (roundEpoch !== epochAtEntry || currentAbort !== abortAtEntry) {
  this.historyLoaded = true
  return          // 只对账不替换：保留屏上在途现场（镜像 + 实时帧）
}
```

`historyLoaded` 仍落定（对账已结束 ⇒ 镜像写入恢复常态、骨架屏不误挂）。守卫放在空历史分支**之前**，
所以"后端历史为空就把待决段就地过期降级"也不会打到一个还在跑的卡上（反向用例锁住这一点）。

**取舍**：这份历史被整体丢弃，不尝试与在途现场拼接 —— 拼接需要按 runId 逐段对齐历史与实时帧，
收益（历史里更早的轮次）远不及风险（错位/重复气泡）；下一次显式重试或下一轮结束后的对账会补回来。

### 2.2 M-18 建卡失败 + 回灌失败的挂起收口（`stores/ai.ts` 4 个落点）

**根因**：`frontend_tool_request` / `suspended` 帧先把 `suspended` 置 true，随后建卡。建卡失败时
段被写成 `failed`/`rejected` + `requiresAction=false` —— 屏上**没有可点的卡**，但 `suspended` 仍是
true；随后 `submitFrontendToolResult` 的回灌若失败只写一条 notice 并返回 `{ok:false}`，不补
`clearSuspendedIfNoOtherConfirms`。结果是输入区与发送闸永久锁死，唯一出口是底部「停止」。

**修法**：在**所有"不建卡"的落点**写完段终态后同步收口（回灌成功与否都不影响这个结论）：

1. `openGenerativeForm` schema 不可渲染（原 `void submitFrontendToolResult(...cancelled)` 之前）；
2. `openWritePreview` 的 `fail()`；
3. `openUploadHandoff` 的 `fail()`；
4. `openUploadHandoff` 的 `ref 不在本轮快照`（`rejected` + `UI_REF_NOT_SNAPSHOTTED`）。

只清**这一张卡**的挂起语义：`clearSuspendedIfNoOtherConfirms(toolCallId)` 会把同轮其它待人卡
（确认门 / 另一张前端卡 / 恢复队列 / 排队表单）算进去，因此"保留其它卡"是既有判据的自然结果，
而不是新写的分支（反向用例专门锁住"另一张还是待决 ⇒ 挂起态保持"）。

### 2.3 M-19 start 帧之前停止的意愿落地（`stores/ai.ts`）

**根因**：runId 只由 start 帧（或下一条消息的 409 响应体）给出。`stop()` 的 `if (runId)` 决定是否
POST cancel —— runId 为空时只做本地收敛，**后端那一轮继续跑**（工具副作用、记忆写入）；下一条消息
撞 409 时又因 `stoppedRunId === null` 被判成"上一轮仍在进行中"，与用户"已经停了"的认知相反。

**修法**（有界、可归属、不误伤）：

- `stop()` 在 `runId === null` 时 `noteStopIntent()`：记 `{ hostMessageId: activeRoundHostId, at: now }`；
- `cancelRunIfStopIntended(runId, hostMessageId?)`：
  - 意向为空 ⇒ 不动作；
  - 超过 `STOP_INTENT_TTL_MS = 60s` ⇒ 作废（绝不拿久远意向取消后来的新轮）；
  - 传了 `hostMessageId` 且与意向宿主不同 ⇒ 属于**另一轮**，不取消、不消耗意向；
  - 命中 ⇒ 消耗意向、`stoppedRunId = runId`、撤 `busyRun` 指针，`void cancelStoppedRun(runId)`；
- 两个消费点：
  1. `send()` 的 `onFrame`：`frame.type === 'start' && isCurrentRound()` 时**先于** `handleFrame` 消费
     （停止闸门会丢弃非终态帧，这一帧可能根本不被处理）；
  2. `send()` 的 409 分支：`cancelRunIfStopIntended(busy.runId)` 命中则按"已停止"登记，不再把这条 409
     当成"上一轮仍在进行中"；
- `adoptFreshSession()`（换会话）：意向随旧会话现场清空。

**取舍**：TTL 之内如果用户"停止 → 又真发了一条新消息"，新消息的 409 会把被停的那一轮取消掉——
这正是期望结果（409 指向的就是它）；超过 60s 的意向一律作废，宁可少取消一次也不误杀后来的轮。

### 2.4 M-15 发送闸与健康探针解耦（`AiPanel.vue:2117`）

**根因**：`chipsAvailable = ai.available && ai.canSend && ...`。`available` 来自 `/api/ai/health`，
一次网络抖动 / 代理 502 / 体形态不符就把 `health` 打成 `null`（`healthError` 记原因），发送钮、Enter、
空态 chips 一起禁用；而程序化 `ai.send` 不被拦（UI 与 store 语义分叉）。

**修法**：

```ts
const healthBlocksSend = computed(() => ai.health !== null && ai.available === false)
const chipsAvailable  = computed(() => !healthBlocksSend.value && ai.canSend && !ai.suspended && ai.pendingToolCall === null)
```

- **探针失败 / 尚未探测**（`health === null`）⇒ 只作提示（状态胶囊 + `healthError` 文案），发送闸只看
  真实轮次（`loading`）与挂起（`suspended` / 待决卡）；
- **探针成功且明确不可用**（`health !== null && available === false`，如 `AI_KEY_UNREADABLE`）⇒ 仍按
  降级限制。这一档是既有规格（`tests/ai-panel-parts-render.spec.ts` 的"health 明确不可用"用例），
  本批不动：真实不可用的表达应由后端错误码与降级条承担，但"已明确关掉 AI"时保留入口只会让用户反复
  撞同一个失败。

**既有用例改判（2 条）**：`composer v2 health 未知` 与 `composer v2 healthError` 原本断言"发送钮禁用"，
正是本批要改掉的行为，已按其意图改写为"发送钮不被探针失败禁用（Enter 照常发送）"。

### 2.5 M-16 编辑重跑的失败还原（`AiPanel.vue:4535` 起）

**根因**：「编辑后重跑」是**先删后发**：`target.parts` 被改写为新文本、`ai.messages.splice(cut + 1)` 删掉
其后全部消息，然后才 `ai.send(..., { skipUserRecord: true })`。失败路径只还原输入框草稿与编辑锚点，
**不还原被删消息与被改写的原文**：旧回答只能靠刷新从服务端找回，而用户刚改的文本服务端从未收到
（刷新后一并丢失），用户也无法"改完再试"。

**修法**：删除前快照 `{ index, target, parts, removed }`；失败 / 断流 / 未发送（`outcome ∉ {ok, cancelled}`）
且仍是当代发送时 `restoreEditRerun(undo)`：

- `target.parts = undo.parts` + `deriveProjections(target)` ⇒ 原文与投影一起回来；
- 被删消息按原序回插在**编辑锚点之后**（它们本来就是"这条提问的回答与后续"）；
- 本次失败轮自己的助手气泡（错误卡宿主）留在末尾，错误卡与「重试本轮」入口不受影响；
- 之后沿用既有口径回填草稿与编辑锚点；用户已在流式中另写内容时只还原消息、不覆盖草稿（反向用例）。

**取舍**：回插位置选"提问之后、失败气泡之前"。另一种（放末尾）会让"上一轮的回答"排在本次失败之后，
阅读顺序更差；彻底移除失败气泡则超出了本项范围（错误卡是有用的现场）。

### 2.6 M-20 设置页重载保留其它卡片的脏值（`AiSettingsView.vue:96`）

**根因**：`fillForms()` 无条件重建**全部**卡片表单（`key: ''`），而任何一次 `load()` 都会调它（他卡保存 /
启停 / 拉模型 / 加删模型…）。于是"在 A 卡输入密钥 → 在 B 卡做任一操作"就把 A 的密钥静默清空；
再点 A「保存」时 `providerBody` 只按 `key !== ''` 带 `apiKey` ⇒ 请求体里**没有** apiKey，页面仍提示
"已保存"。用户以为存上了，首次调用才以 `AI_KEY_MISSING` 暴露。

**修法**：为每张卡维护"上一次服务端值"基线 `cardBaselines`，`fillForms` 改增量语义：

- 密钥：**永不因重载丢失**（服务端从不下发明文，`key` 只可能来自用户输入）；
- 其余字段：`form[field] !== baseline[field]` ⇒ 脏值优先（改名不被重载打回）；干净字段跟随服务端
  （他端改动 / 刚保存的结果仍要能回显）；
- 已不存在的 provider：表单与基线一起清（不留"点不到却会被读到"的幽灵卡）。

这样"保存成功却未提交"的载体消失：用户输入过的密钥在下一次保存时**确实**进请求体（原始用例断言
`body.apiKey === 输入值`，同时 `displayName` 也真的提交）。

## 5. 未验证项与已知取舍

1. **真机 E2E 全部未执行**（见 §4），包括 M-19 的"start 帧之前"时序：桩的 `stall-frames` 是恒定帧间隔，
   点停止时 start 是否真的还没到依赖时序，故该用例同时接受"该 run 已 CANCELLED"作为收敛证据。
2. **M-18 没有真机条**：需要后端发一张坏 schema 的 `generative_form` 帧，现桩不产这种帧；该行为只由
   单测锁定（4 个落点 + 保留其它卡）。若要补真机，需要给桩加一条"malformed-form"指令。
3. **M-15 的"明确不可用"仍限制发送**：与审计汇总的"发送闸只 `!loading && !suspended`"相比是**收窄**。
   理由：既有规格（`composer v2 health 明确不可用`）与本批"探针失败才解耦"的措辞；如果要彻底解耦，
   需同批改掉那条既有用例并确认产品口径。
4. **M-16 回插位置**取"提问之后、失败气泡之前"（取舍见 §2.5）；失败轮的错误卡仍留在末尾。

   在途轮。
6. **M-20 不覆盖"清空密钥"的显式动作**：`clear-key` 仍走 `clearKey: true` 专路径；基线只服务于
   "重载不得抹掉用户输入"。
7. **测试运行口径**：本工作树的 `frontend/node_modules` 是指向共享 node_modules 的符号链接（与同批其它
   工作树一致），vitest 必须带 `--pool=forks`；该符号链接被 `.gitignore` 覆盖，不进提交。
