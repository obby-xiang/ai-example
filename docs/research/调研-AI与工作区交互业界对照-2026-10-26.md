# 调研 · AI 与工作区交互业界对照（2026-10-26）

> **性质**：本件把同批 7 份外部研究稿（`ext-01`~`ext-07`）收成一份**可引用的对照件**：官方资料 + URL + 适用边界 + 对本仓的对照点。
> **口径**：只采用**官方文档、官方仓库、协议规范**；营销页、第三方评测、社区帖**不作为功能证据**，仅在与官方冲突时作为“存在此类说法”的反例登记。凡未找到一手源的，一律写“不可证”，**不反推内部实现**。
> **三条使用纪律**（来自本批多次踩坑）：
> 1. **“业界能做”≠“某函数/某版本默认就会”**——引用必须落到具体函数/参数/版本。
> 2. **框架的默认解不是行业强制**——某个框架有某能力，不能据此判本项目“缺”。
> 3. **不要把外部说法当事实**——本批已核出 4 条广泛流传但不成立的表述，见 §3。
> **与总册关系**：结论面见 `docs/research/排查-AI全量设计与交互审视-2026-10-26.md`；本件只负责“外部依据 + 边界”，不重复本仓缺陷编号。

## 3. 纠偏：本批核出的 4 条不成立/错引的外部说法

> 这一节存在的意义：这些说法在流传中很容易被当成“业界标准”写进设计依据。**引用外部结论时，必须把“业界能做”与“某函数/某版本默认就会”分开写。**

### 3.1 「OpenAI SDK 的标准生产模式＝断流后把半截助手消息放回上下文续写、前端无缝拼接、指数退避通常 3 次」

**判定：不成立（作为“标准模式”）。**“指数退避”方向成立，但**次数说法无依据**。

- 官方 Rate limits 指南写得最直白：“……**不要在消费了输出之后自动重放请求**”。
- 官方 Python SDK README：“某些错误默认自动重试 **2 次**，短指数退避……只有请求体可以安全重发时才重试”；并且“**流式消费不会自动重试**，因为重放会重复已经交付给应用的输出”。Node SDK 同口径（`maxRetries` 默认 2）。
- 所以“指数退避通常 3 次”与官方默认不符；官方只要求“同时限制次数与总时长”，示例里甚至出现过 6 次，**没有任何“3”的推荐值**。
- 官方确实提供“断点续传”，但**不是回填消息**：Responses API 的 `background` 模式配合 `sequence_number` 游标，从断点继续**同一个 response**（同一份生成继续流，不重跑模型、不重放已有字节）。
- **工具轮更不适用**：一是 SDK 重试的是 HTTP 请求体，不会替你重放工具执行；二是协议上“以 tool_calls 结尾的助手消息”后面必须跟对应的工具结果消息，把半截 tool_calls 放回上下文**本身就是非法历史**。⇒ “半截回填续写”最多适用于**纯文本、且无任何工具副作用**的场景。

### 3.2 「AI SDK 7 于 2026-10 发布 `streamRetries`；issue #2636 说明此前是断流 bug」

**判定：部分成立 —— 语义大半属实，版本、日期、issue 引用全错。**

**属实的部分**（官方文档）：

- `maxRetries` 只管“开始一次模型调用”阶段的失败，默认 **2**。
- `streamRetries` 管“响应已开始流式输出后收到的 provider 错误事件”，默认 **0（不启用）**；设为 0 时仍允许错误回调返回“重试”以触发**一次**回调式重试；自动重试耗尽后回调还能再要一次，总恢复次数上界为 `streamRetries + 1`。
- 语义原文要点：“重试**只重跑当前模型步**，此前已完成的步（含其工具调用与工具结果）不会被重放。”
- 工具边界：失败尝试里的工具输入、工具调用、审批请求、工具回调、客户端侧工具执行**一律丢弃**，只有在某次尝试成功完成模型调用之后才暴露或执行；但它**无法撤销 provider 侧已执行的工作**（在 provider 侧工作之后重试，可能重复该工作或成本）。
- **前端拿不到“无缝拼接”**：官方明确“provider 错误前已发出的非工具输出**不能被撤回**”，重试可能**追加重复或偏离的半截文本/推理/文件/来源**；源码行为是“关闭旧的文本/推理 part、用新 part 继续”，即 UI 会看到“前一段结束 + 新一段开始”。⇒ 要做“无缝”，客户端必须自己按 part id/尝试标记丢弃或回滚失败片段。
- 另一个限定：官方措辞是“**格式良好的 provider 错误事件**”，裸 TCP 断开是否走这条路径取决于适配器有没有把它转成错误事件。

**错的部分**：

- `ai@7.0.0` 发布于 **2026-06-25**（官方发布博客 + npm 时间戳一致），**不是 2026-10**。
- `streamRetries` 的变更落在 **7.0.91（2026-09-02）**；对应 PR 是 **#18718**“为流中途 provider 失败增加可配置、按尝试隔离的恢复”（同日合并，修复 **#18667**“流中途 provider 错误绕过 `maxRetries` 且不可分类、丢弃已完成生成”）。
- **`#2636` 的引用是虚构的**：该 issue 标题是“retry strategies and fallbacks”，2024-08-12 创建、至今 open，内容是希望支持备用模型/供应商，**与“断流不重试是 bug”无关**。**不得把 #2636 写成断流 issue。**

### 3.3 「ChatGPT 断流后只自动等待/恢复，不让用户重试」

**判定：不可证。**没有任何 OpenAI 一手文档描述 ChatGPT 断流后的恢复策略；能查到的只有用户侧报告（社区帖与代码仓库 issue 里反复出现的 “Connection interrupted. Waiting for the complete answer”），这只能证明“存在等待/恢复的提示”，**不能证明“没有重试入口”**。而 ChatGPT 常规界面一直有 Regenerate ⇒ 该说法至少是过度概括，**不应作为设计依据**。

### 3.4 「LangGraph 的 `tools_condition` 就是按任务生命周期状态过滤工具（例如已完成不暴露开始类工具）」

**判定：不成立。**官方措辞与源码都表明它**只是路由**：最后一条助手消息含工具调用 → 走“tools”节点，否则 → 结束。它**不读业务状态、不过滤工具列表**。

能做“按状态动态裁剪工具”的是另一套机制：在中间件里包装模型调用时**覆盖工具列表**（官方文档明确写“按状态/上下文选择相关工具”）。⇒ 正确表述是“**状态图/中间件能实现**按状态裁剪工具”，而不是“这个函数会”。

### 3.5 本项目重试闸门的两条相关纠偏（与外部说法区分开）

- 「`!已产出 && !副作用` 使重试几乎永远不触发」→ **夸大**：恰恰是最典型的瞬时故障（连不上、429、5xx、首包超时、只收到工具调用但无正文）**全部落在可重试区**，且有单测锁定“确实发了第 2 次调用”。真正失效面是“中途断流”，且是**有意**的（防重复正文/思考/工具）。
- 「配置 2 次实际仅 1 次是 bug」→ **不是 bug**：配置语义是“总尝试次数＝2”，即最多 1 次重试；对“有产出”的场景确实只 1 次，对“首包前”场景实打实 2 次。**建议把配置注释统一写成“总尝试次数”，避免反复误读。**
- 补充事实：所用 Spring AI 版本**内部没有第二层流式重试**（反编译核实：重试模板只在非流式调用生效）；项目自建的重试策略也只作用于非流式调用。⇒ “框架已经帮你重试了”不成立。

### 4.2 可直接借鉴的五条（都属“可对照”，不是“必须做”）

1. **范围要显式**：Excel 可点名列/区域、Notion 有“当前页 + 选中块 + 全部来源”、Airtable 限定当前 base、VS Code 用“活动会话”。⇒ 对照点：用户能否一眼看到当前工作区/配置包/导入批次/选中对象。
2. **方案与执行分离**：Excel 的 plan 模式“先审方案再启动”；Power Apps 先生成表与关系再“保存并打开”。⇒ 对照点：是否提供“只出方案/只读分析”与“直接执行”两种模式。
3. **变更前给可审阅的 diff，而不是一句话**：VS Code 的提交前 diff 与逐项 Keep/Undo、Cursor 的 checkpoint 预览。⇒ 对照点：配置级 diff、字段映射预览、影响对象清单。
4. **完成后的产物与下一步**：Notion 可视化结果并生成可下载文件；Cursor 把视频/截图/日志附到 PR；Airtable 有检查单与后续建议。⇒ 对照点：导入报告、失败行清单、导出包、差异清单、继续修复入口。
5. **AI 的边界**：Airtable 官方明确“原样迁入用**导入**比让 AI 做更可靠”，且其 AI **不能导出数据**。⇒ 对照点：确定性导入/导出引擎是核心，AI 只做解释、映射建议、差异定位与修复建议；**不要让聊天框成为唯一入口**。

### 4.3 必须一起说明的边界

- Excel 是**单文档直接操纵型**，plan 批准的是“做法”不是逐项业务变更；平台间能力不同（移动端主要是 chat/plan）。
- Notion 的“接受/丢弃/重试”是**内容级**，不是 schema/配置级；**多步 Agent 的批准与回滚页面未说明**，不能假设它已有完整变更治理。
- Airtable **撤销范围有限**（不能撤销对已有记录值的编辑、不能撤销创建表/界面/页面），且只撤销当前对话中它自己的动作。
- Cursor/VS Code 的审批是“**事后 diff/PR**”，不是业务字段级事前批准；且 VS Code 明确“**停止或恢复文件不会撤销已完成的终端命令、网络请求、部署或外部服务变更**” ⇒ 外部副作用必须由外部系统自己的手段恢复。
- OpenHands/Retool 的 UI 治理公开信息不足，只能做“工作区形态/组件嵌入”的参考。

## 5. 明确未知与不可证（不得当事实）

1. **没有公开的“业界统一阈值”**：上下文清理/摘要的触发值（10 万 / 15 万 / 967K / 模型默认）分属不同产品、不同机制、不同分词器，**不能互证，也不能直接搬**。社区流传的 90%/55%/76–83% 等数字未在官方核实。
2. **没有官方的压缩耗时或进度百分比**：能核实的只有“状态/生命周期”（CLI 的 “Compacting…” 提示、压缩前后钩子、“重压缩可能让流在最后一个 token 后多开几秒”）。**不要编造进度条。**
3. **官方没有承诺“压缩会降低前端渲染成本”**：压缩是模型上下文操作；长期打开的消息树仍需独立的前端性能工作。
4. **两家摘要的可审计性不同**：一家返回加密不透明的压缩项，另一家按需摘要可读但有签名且不可改。**不要当成同一种“摘要”。**
5. **上下文编辑的“服务端无需同步”只适用于该机制本身**：阈值压缩会要求客户端在下一次请求丢弃被摘要之前的内容；按需压缩还要求块在首位、每请求一个块。**“服务端会处理”不是通用结论。**
6. **记忆工具不托管存储**：路径只是前缀，实际存储、权限、过期、路径穿越防护都在应用侧。
7. **产品内部行为不可从公开资料推断**：某产品断流后是否禁止重试、上游返回原文还是摘要、多页签真实连接数——**必须实测或产品确认**。
8. **框架版本演进快**：本件引用的 hook/参数名与语义按 2026-10 的官方页面；落地前须按锁定版本复核。已知需注意的口径变化：CopilotKit v2 的注册面名称与 v1 的旧 API 不要混用；Vercel 的 `toolApproval` 与已标记弃用的 `needsApproval`；AG-UI/MCP 的版本演进。

### 6.1 一条“不要做”的清单（同样来自一手资料）

- **不要**引入“把半截助手消息回填上下文再续写”（无官方支持；工具轮会产生非法历史或重复副作用）。
- **不要**为了“无缝”假定前端能自动拼接（官方明确“已发出的非工具输出不能撤回”，需要客户端自己丢弃失败片段）。
- **不要**把“确认”当成一个全局布尔开关（业界是可配置的风险策略 + 预览 + 决策语义 + 可恢复契约）。
- **不要**把框架的默认值（重试次数、压缩阈值、最近轮保留数）当行业标准。
- **不要**为了对齐某个框架而改造协议（例如参数流式、“准备参数”状态），除非后端确实流式收到参数。

## 7. “什么适合自动、什么必须由人决定”（本批外部研究的共识表）

| 更适合自动 | 条件 | 依据 |
| --- | --- | --- |
| 只读/检索/预览/校验 | 不改状态；结果可复核 | 各框架默认自动；只读注解可跳过确认 |
| 草稿/内部转换 | 不对外发布；可编辑 | 默认自动执行 |
| 可逆低风险写入 | 可撤销/可编辑；无外部副作用 | 前端工具直接执行 |
| 幂等/预批准范围 | 有幂等键；同键重试安全 | 幂等注解；重放幂等要求 |
| 只读导出（无敏感外发、有权限与审计） | “只读”不等于“无风险” | 开放世界注解要求审查输出 |

| 必须由人决定 | 为什么 | 依据 |
| --- | --- | --- |
| 不可逆/破坏性（删除、覆盖、发布、权限变更、扣费） | 失败不可逆、影响范围大 | 破坏性注解；编辑/拒绝决策 |
| 外部副作用（发信、通知、导出给第三方、公开发布） | 影响外部主体、声誉、合规 | HITL 定位；开放世界注解 |
| 敏感数据/同意（PII、凭据、跨境/跨租户） | 合规与信任 | 征询规范明确**不得**收集敏感信息 |
| 高不确定/信息不足 | 模型不应猜 | 响应 schema + 类型化表单 |
| 策略例外（超阈值、工作区外、异常收件人） | 需要人判断/授权 | 按参数决定的审批谓词 |
| 法律/合同/审计 | 责任归属与可追溯 | 三段审计（提案→决策→结果） |

**关键澄清**：一手资料**不支持**“所有写操作都必须确认”。共同模式是“**默认自动 + 风险/参数/策略分级 + 始终可拒绝/取消 + 可审计/可恢复**”。
