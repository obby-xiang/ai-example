## 一、压缩机制：各家对照

### 1.1 硬参数对照表

| 产品 / 层 | 触发条件 | 压缩动作 | 压后如何恢复 | 证据 |

| 触发点 | 产品 | 证据 |
|---|---|---|
| **~50%** | Gemini CLI、Hermes | ★★ |

| **96–99%** | OpenCode | ★★ |
| **~96.7%** | Claude Code（原生 1M 窗口模型的默认 967K） | ★★★ |

**结论（★★★，纠正常见误解）**：**「92%/95% 容量」的传闻不成立于官方文档。** 官方口径是**按模型/配置定的 token 边界**，不是统一百分比。真实分布从 50% 一路铺到 96.7%，跨度极大。

**社区共识是「别等那么晚」（★）**：多篇社区文章主张在 **50–60% 主动 `/compact`**，理由是 90%+ 才压，摘要在噪声里找重点、质量更差。

**反面成本（★）**：全文摘要会**打碎 prompt cache**——一次约 12.5 万 token 的压缩约等于 20 多次「暖缓存跟随轮」，所以「50% 就狂压」会把缓存红利吐回去。**阈值不是越早越好，也不是越晚越好。**

## 二、压缩阶梯共识：无 LLM 剪枝 → 保留尾巴 → LLM 摘要

**业界做法分类（★，分类学本身有用）**：一篇中文综述把做法拆成八类——A 工具输出剪枝、B 明文 LLM 交接摘要、C 服务端加密 compact、D 训练式自摘要（Cursor Composer）、E 结构化状态快照（Gemini CLI 七段强制字段 + probe）、G 非破坏隐藏 + 结构回注（Roo condensation，可 rewind）、H 事件存储型擦除（OpenHands）、F 隔离与外置（子 agent / 新会话 / 文件记忆）。**主流是「主路径 + 辅路径」，多数产品叠用 2–3 种。**

**核心共识（推断，由多家官方约定交叉推得）**：

1. **纯滑动窗口截断已经不是主流主路径**，只剩降级 / failure fallback（Gemini CLI 快照失败退截断、Roo 失败退滑动截断）。
2. **主流是混合阶梯**，顺序固定为：
   - **① 无 LLM 剪枝**（最便宜，先做）：清/截断陈旧工具输出与日志。Anthropic 的 `clear_tool_uses_20250919` 就是这一层的官方实现，**默认 trigger 100,000 input tokens、保留最近 3 组 tool use、支持 `exclude_tools` 白名单**——这套默认值可直接照搬。
   - **② 保留近期原文尾巴**（保连续性）：Claude Code 保留最近读/改的 5 个文件引用；Kimi 默认保留最近 2 条；Gemini 保留最近 30% 原文。
   - **③ LLM 结构摘要**（最贵，留到最后）：结构化字段式交接（Anthropic 五段模板：Task Overview / Current State / Important Discoveries / Next Steps / Context to Preserve；Gemini 七段强制字段 + probe）。
   - **④ 压后回注**（可选）：从磁盘重注 `CLAUDE.md`、auto memory、plan、文件，或回填加密 blob。
3. **Anthropic 官方给的长时域三件套（★★★）** 进一步说明了层次关系：**compaction（摘要重开）+ structured note-taking（窗口外文件记忆）+ sub-agent 架构（各自独立窗口，只回 1–2K tokens 结论）**。官方明确把 **「context rot」**（token 越多，召回越差）作为压缩的根本理由。
4. **合规敏感场景不允许静默降级（推断，较强）**：Anthropic 与 OpenAI 在 API 文档里都强调**摘要是有损的**——「任务需要精确回忆早期细节时不适合 compaction」。这决定了压缩必须**对用户可见、可手动触发、可关闭**。

## 三、token 可视化与用量契约

### 3.1 协议层事实标准：ACP `usage_update`

**事实（★★）** ACP（Agent Client Protocol）已在 **2026-06-05 把 session usage 定为 Completed 并稳定**：

- agent 通过 `session/update` 推送 **`usage_update{used, size, cost?}`**；
- 明确 **「客户端自行算 remaining / percentage」**；
- 明确 **「cached tokens 也算占位」**；
- 明确 **「没有意义的窗口就干脆不发」**。

**这就是业界「向后端/前端暴露 usage」的事实标准**，且不与任何单一厂商绑定。

### 3.2 ACP 给出的推荐分档（75 / 90 / 95）

| 使用率 | 建议行为 |
|---|---|
| **<75%** | 正常 |
| **75–90%** | **黄色**指示，提示「context 快满了」 |
| **90–95%** | **橙色**，建议「开新会话或摘要」 |
| **>95%** | **红色**，警告「下一条可能失败，建议交接」 |

### 3.3 CLI / IDE 侧暴露现状

| 产品 | 暴露形式 | 证据 |
|---|---|---|
| Claude Code | `/context`（按类别拆解 + 优化建议）、`/usage`（session token、成本、prompt cache 命中率/未命中/预期重建/冷热）、可配 status line 常显、OpenTelemetry 导出 | ★★★ |
| Kimi Code CLI | 底部状态栏**实时显示 context 使用率** | ★★★ |
| Cursor | 编辑器内有 context 指示器；usage feed 事件级 token 拆分（input/output/cache-read/cache-write） | ★★ |
| Copilot CLI | `/statusline` 可常驻显示 context 与 token | ★★ |
| Gemini CLI | 社区请求 `/context`（含「压缩阈值指示线」）——即**尚未提供** | ★ |

### 3.4 API 侧惯例（★★）

- `usage` 对象（input/output/缓存读写）是通例，但**流式下不一定默认给**：OpenAI 形状需 `stream_options: {"include_usage": true}`，用量落在最后一块；Anthropic 在 `message_start` / `message_delta` 报。
- Anthropic 另有免费的 **`count_tokens`** 端点，可预览「压缩后会剩多少 token」。

### 3.5 消费级网页侧：基本不暴露「上下文层」，只暴露「记忆层」（★★ / ★★★）

- **ChatGPT 网页不显示 token 用量或上下文余量**；社区持续提 feature request 要求「接近上限前给警告」「加进度条」——说明**当时并不存在**。Claude 网页同理，需第三方扩展才能看到「上下文表」（★）。
- 网页端**有**的是**记忆层**可视化：ChatGPT 的 Memory summary / Saved memories 可在设置里读、改、删，回答下方可显示 **Sources**（哪条过去会话/记忆/文件影响了这次回答）；Claude 的 Settings → Memory 列出 Topics，可编辑删除，检索过去会话时显示**引用出处**并可跳回原对话。

## 四、记忆分层：两轴结论

### 4.1 官方骨架（★★★，Anthropic 命名最清晰）

1. **窗口内（短期）** = compaction 摘要，只服务当前对话连续性；
2. **窗口外文件（工作/长期）** = structured note-taking / memory tool，**agent 自己写、按需读回**；memory tool 是**客户端文件协议**（view / create / replace / insert / delete），**存储归你**；
3. **跨会话检索（长期）** = RAG 式检索历史会话；
4. **隔离** = sub-agent 用干净窗口，只回摘要（严格说不是压缩，是「别让历史挤进这一窗」）。

### 4.2 各家实现要点

| 产品 | 记忆机制要点 | 证据 |
|---|---|---|
| **ChatGPT** | **两套机制 + 多来源**：**Saved memories**（显式条目，可搜索、排序、自动优先级、版本历史；删原对话不会自动删这条记忆）+ **Reference chat history**（隐式，ChatGPT 自己从历史挑，随上下文变化，**没有单独存储上限**；关掉后 30 天内清除）；另有 custom instructions、Library 文件、连接应用；**Project-only memory** 把记忆限定在项目内（项目外不可见，企业/健康版默认关闭）；临时对话不创建也不更新记忆 | ★★★ |
| **Claude（网页）** | **主题化 + 项目隔离 + 统一到 Cowork**：**边聊边存 Topic**（不是会话结束后总结），可「remember this」显式写入，改一个 topic 会在之后**所有**会话生效；**每个 Project 有独立记忆空间和项目摘要**；chat 与 Cowork 共用一份记忆；过去会话检索走 RAG 并以 **tool call 形式**出现在对话里；有 incognito chat 与「单聊关闭 memory」两种排除方式。旧版描述为「每 24 小时合成一次记忆摘要」 | ★★★ |
| **Claude Code** | 明确分成**「人写的」vs「模型自己写的」**两套并存：`CLAUDE.md`（人写；项目/用户/组织多级作用域；建议 <200 行；>4MiB 跳过）与 **auto memory**（模型自己记四类：user / feedback / project / reference，存于用户主目录的 per-project memory 目录，`MEMORY.md` 作索引，**每次会话只加载前 200 行或 25KB**，话题文件按需读）。关键：**两者都不进系统提示**，是作为 user message 注入的「上下文而非强制配置」 | ★★★ |
| **Codex** | **最自主**：后台两阶段从 rollout 抽取结构化记忆 → consolidate 到用户主目录记忆目录，**由沙箱内 sub-agent 做**，带**引用追踪**与**使用频次排序** | ★★ |
| **Gemini CLI** | 反向走**人类审核 inbox**：抽取后产出 patch 到 `.inbox/`，用户 `/memory` 审阅应用 | ★★ |
| **Hermes** | 故意做得极小：`MEMORY.md` **2,200 字符** + `USER.md` **1,375 字符**，**冻结快照**以免破坏 prompt cache；跨会话靠 **SQLite FTS5** 的确定性检索，**全程无 LLM 调用** | ★★ |

### 4.3 结论一：真正的两轴（推断）

业界「记忆分层」实际是**两轴，不是教科书三分**：

- **轴一 = 谁在写**：人 / 模型 / 模型 + 人审。
  - 人写：`CLAUDE.md`、custom instructions、显式「remember this」；
  - 纯模型写：Codex 后台 consolidate、ChatGPT Reference chat history、Claude Code auto memory；
  - 模型写 + 人审：Gemini CLI 的 `.inbox/` + `/memory`，以及 ChatGPT / Claude 的「可读可改可删」管理 UI。
- **轴二 = 何时进上下文**：每次加载 / 按需读 / 检索命中。
  - 每次加载：`CLAUDE.md`、Hermes 的冻结快照（且**限制载入体积**：200 行或 25KB、2,200 字符）；
  - 按需读：Claude Code auto memory 的话题文件、memory tool 的 view/replace；
  - 检索命中：SQLite FTS5（Hermes）、RAG 检索历史会话（Claude / ChatGPT）。

**「短期/长期/工作记忆」这种三分并不对应产品实现**——它是认知科学的比喻，不是工程切面。产品实现里唯一真正重要的是：**这份内容谁有权写、什么时候被塞进窗口、塞进来占多少 token。**

**共同工程约束（★★★）**：**载入体积必须设上限**。这是所有产品的隐含纪律（200 行 / 25KB / 2,200 字符），因为记忆是「永久占位」而不是「可压缩」。

### 4.4 结论二：400 万行 harness 语料中，**没有任何 agent runtime 用向量嵌入检索**（★★）

源码级研究（arXiv 2609.00006，覆盖七家 harness、约 400 万行代码）的明确结论：

> **整份语料约 400 万行代码里，没有任何 agent runtime 用向量嵌入检索代码。**

跨会话召回普遍走 **SQLite FTS5** 这类**确定性检索**（Hermes），或干脆不做检索、只靠**有界文本快照**（Codex 的 consolidate 文件、Claude Code 的 `MEMORY.md` 索引）。

**工程含义（推断）**：向量库不是上下文治理的必经之路，甚至不是主流路径。**文本/文件式记忆 + 索引 + 确定性检索**才是生产环境（4M 行量级）的实际选择。上向量库会同时引入「不可解释的召回」「存储与索引运维」「检索结果不稳定导致 prompt cache 失效」三重成本，而这些产品显然认为不划算。

## 五、长对话体验的标配分界：agent 场景 vs 消费级

| 产品 | 接近上限时用户看到什么 | 证据 |
|---|---|---|
| **Claude Code / Codex / Kimi CLI / Gemini CLI** | 可见用量或百分比 → 到阈值自动压缩（可能无提示）→ 可手动 `/compact`；关掉自动压缩则报 **context-limit error** 并提示 `/compact or /clear` | ★★★ / ★★ |
| **Claude 网页版** | 到长度上限**直接报错**（"Claude hit the maximum length for this conversation"），必须开新对话；**没有**上下文余量指示；Projects 让每个新对话都带 fresh 200K + project knowledge + project memory | ★★ |
| **ChatGPT 网页版** | 单条过长报 "Message too long"；整段过长时模型「忘掉」早期内容（**静默丢 oldest**，此机制为**推断**），到点提示开新会话；**无**剩余量指示 | ★★ |
| **Kimi 网页版** | **差异化做法**：输入时可显式选**「对话长度：超长」**（K3 的 100 万 token 上下文，需最高档会员）；上下文过长会提示并建议新建对话 | ★★★ |
| **DeepSeek 网页版** | 有「对话长度超限」的说明与用户绕行方案（让 AI 先总结，再贴进新会话），未见可见余量指示 | ★（证据弱） |
| **Gemini / Copilot / Cursor** | IDE/CLI 有指示；网页端与 ChatGPT 类似，无上下文仪表 | ★★ |

### 分界结论（推断，较强的模式总结）

1. **凡是 agent / CLI / IDE 场景 → 用量可见 + 自动压缩 + 手动压缩。** 原因：用户是专业人士，且上下文爆炸会**直接烧钱**（token 即账单）。
2. **凡是消费级对话场景 → 不给余量指示，只在失败时报错并建议开新会话。** 唯一例外是 **Kimi 把「对话长度」做成显式选项**——把复杂度交给用户主动选择（默认不给指示，但允许主动买长窗口）。
3. **共同点：「静默降级」不存在于合规敏感场景。** Anthropic / OpenAI 都在 API 文档里强调摘要是有损的，因此压不压、什么时候压必须是**用户可见、可手动触发、可关闭**的决策。
4. **推论**：一个**内网平台**的定位更接近 agent 场景（专业人士 + 有成本约束 + 静默丢工作就是事故），所以应当走第 1 条路线，**而不是**照抄消费级网页的「到点报错」。

## 六、功能标配 vs 分化项

### 6.1 最小编辑机制集（★★，UX 综述）

聊天产品的**最小必需集**：**重新生成（regenerate）+ 编辑用户消息并重发（edit & resend）+ undo 或 branch 二者之一**。

现状对比：ChatGPT 有 regenerate-with-model-choice 与编辑，主界面**无**分支；Claude.ai 的 regenerate 是「1 of N」分页器（**保留之前的回答**），有编辑，主界面**无**分支；Cursor 的 agent 模式把分支做成一等公民。

**分支在消费级产品里是「隐式存在、显式缺失」（★★）**：ChatWidget/ChatTree 这类扩展的卖点正是「ChatGPT / Claude / DeepSeek / Kimi 每次编辑或重新生成**都产生新分支**，但界面只给你 `< 1/2 >` 箭头」。

**收紧信号（★）**：2026-03 起 ChatGPT 把「编辑任意消息」收紧为**只能编辑最后一条用户消息、只能重试最后一个回答**（无公告）。

### 6.2 清单

| 功能 | 判定 | 说明 |
|---|---|---|
| 重新生成 | **标配** | 所有主流产品都有；差异只在「旧回答是否保留」（Claude 用分页器，ChatGPT 直接替换） |
| 编辑并重发 | **标配** | 但「能编辑多早的消息」在分化（ChatGPT 2026 收紧到只允许最后一条） |
| 点赞/点踩反馈 | **标配** | ChatGPT / Claude / Gemini 三家 UI 都有 |
| 会话列表 + 搜索 | **标配** | 消费级产品都有 |

| 停止生成 / 复制 / 流式 | **标配** | — |

## 七、给本项目的 5 条借鉴

> **以下 5 条全部是推断**——基于上述事实做的迁移设计建议，**不是任何厂商的官方主张**。每条末尾标注依据出处。

**1. 把「页签生命周期」直接绑定到 token 预算，并把用量做成可见的一等 UI。**
既然没有跨会话持久记忆，「页签内的上下文」就是用户**唯一的记忆载体**，静默降级等于丢工作。建议直接采用 **ACP 的分档着色（75% 黄 / 90% 橙 / 95% 红 + 建议动作）**，并把 `used/size/cost` 作为会话级字段暴露给后端——这套契约**已被协议标准化**（2026-06-05 Completed），且不绑定任何单一厂商。
依据：§3.1 ACP RFD；§5 消费级「无指示 → 到点报错」是最被诟病的体验。

**2. 压缩走「阶梯」，不要一上来就全文摘要。**
顺序：**① 清/截断陈旧工具输出与日志（无 LLM 成本）→ ② 保留最近 k 轮原文尾巴 → ③ 全文结构摘要（带 focus/hint 参数）**。Anthropic 的 `clear_tool_uses` 默认参数（trigger 100K、keep 3、`exclude_tools` 白名单）**可以直接照搬为默认值**。
依据：§2 Claude Code microcompact→full compact 的两层结构；arXiv 源码研究的七家对照。

**3. 默认阈值调早（建议 80%±5，且允许用户调），并给一个「现在就压缩」按钮。**
官方默认值（Claude Code 967K / Codex 90% / OpenCode 96–99%）被社区一致认为**「压晚了」**；但也不要 50% 就狂压——全文摘要会**打碎 prompt cache**。Gemini CLI 的 50% 与 Kimi 的 0.85 是这个区间的两端参考，80% 取其中间偏晚处，兼顾摘要质量与缓存红利。
依据：§1.2 阈值分布表 + §1.2 缓存成本（一次 12.5 万 token 压缩 ≈ 20 多次暖缓存跟轮）。

**4. 把「关页签」从「丢弃」改造成「留下最小可恢复状态」。**
内网平台不该指望用户自己复制交接文档。可选做法：接近上限或即将关闭时**自动生成一段交接摘要**（进度 / 改动面 / 坑 / 下一步），并允许用户**一键把它作为新页签的首条消息回填**。技术上等价于 Codex / Mistral Vibe 的「compaction envelope 重注原始目标」与 Roo 的**非破坏隐藏**（原文保留、可恢复）。
依据：§2 八类做法中的 G/H 类；§5 消费级「开新会话 + 手贴总结」是当前最普遍的土办法（DeepSeek 用户社区的做法）。

**5. 重生成 / 编辑重发 / 撤销（或分支）三件套一起上，缺一个用户就会死在一句没写好的提示上。**
这是 Prompt Bench 给出的**「最小编辑机制集」**，且**成本不对称**：regenerate 最便宜（前缀缓存仍有效），编辑越靠前的消息越贵。对一个「页签即会话」的平台，**undo 比 branch 更划算**（实现只需保留一份前一状态），branch 可作为高级手势后置。
依据：§6.1 编辑机制成本模型 + Cursor/Pi 的分支实践。

**一条附带的架构提示（推断）**：如果将来要加**跨页签记忆**，优先选**文本/文件式记忆**（`CLAUDE.md` + `MEMORY.md` 索引那一套：**人写的规则与模型自己记的笔记分开放、限制载入体积、可读可编辑**），**不要先上向量库**——400 万行生产 harness 代码的研究结论是那里**没有任何一家用向量嵌入做检索**，跨会话召回普遍用 SQLite FTS5 这类确定性检索。
依据：arXiv 2609.00006；Claude Code memory 文档。
