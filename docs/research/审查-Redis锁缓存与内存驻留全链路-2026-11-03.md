### 1.2 结论先行

1. **Redis 侧存在明确的增长/驻留点，但性质不同**：`kb:cache:doc:*` 无 TTL 且无下线删除，是最需要补删除路径的一族；`ai:creq` 在活跃会话期字段随发送次数增长（整键 TTL + 会话销毁 DEL 兜底）；`ai:ledger` 的增长受 run 生命周期约束（单轮 ≤25 步、run TTL 24h、`deleteRun` 13 键 DEL），但它承担跨进程防重复执行的真值，**不能靠裁剪解决**；`ai:purge:pending` 与 `ai:runs` 的"无 TTL"是**有意的 durable / 发现面设计**，只列容量与运营风险。
2. **Cluster 同槽面成立**。所有多键 Lua 与多键 `DEL` 的 KEYS 同 hash tag；跨槽面被显式拆成单键命令或 pipeline。唯一依赖隐式约定的是 `RedisFrameStore.xadd` 的原生命令路由（key 必须是 `args[0]`），当前实现正确但脆弱。
3. **锁的核心语义已收口，仍有两处确定缺陷**：`TaskService.createIdempotent` 的 `synchronized` 在 `@Transactional` 方法体内（提交晚于解锁），`JobHeartbeatRegistry.cleanupDeadLocalRunner` 的 `GET→DEL` 非条件删除。其余"误删他人锁"路径均已改为值精确匹配的 Lua。
4. **进程内驻留的主要问题不在"缓存"，而在异常出口与跨实例残留**：`drivingRuns` 取租异常漏删、`JobWatchdog` 两个集合无清理、`JobCancellationRegistry` 非执行实例取消残留，三处均已由代码路径直接证实。`LeaseService.ended`、`ToolActivityBeacon.lastActivityAtMs` 等属"以内存换正确性/取证"的取舍，按条件风险记录。
5. **前端唯一持久面是 1 个 localStorage + 8 类 sessionStorage**，全部集中在 AI 对话域；无 IndexedDB / Service Worker / Cookie / 浏览器历史镜像。隔离键形（`tenantId:userId` 指纹）整体扎实；真正的缺陷是**清理缺口**（表单草稿逐击键写、`mermaidPending`、`historyMdCache`、用户消息集合、`recentActions`），不是存储面失控。
6. **前端有界缓存的残留不等于数据泄露**。`historyMdCache`（256 块/8MB）、`dedupeCache`、`snapshotCache` 等的残留都在内存、UI 不可达、不上盘；本文按"内存驻留/陈旧镜像"记录，不按"界面可读的数据泄露"记录。

### 3.10 重点详述

**（1）`ai:ledger`（K05）——容量与读放大，但不能靠裁剪解决。**
`IDEM_PUSH_SCRIPT` 只有 `LLEN/RPUSH/HSETNX/PEXPIRE`，没有 `LTRIM`；每条记录含 `resultText` 全文（模型侧单条上限 20000 字符，UI 帧侧 64KB）。增长约束有三：单轮工具步数由 `app.ai.resilience.max-tool-steps=25` 在应用层限制；run 快照 TTL 24h 且每次写整额续期；`deleteRun` 一次 `DEL` 13 个同 tag 键。**关键约束**：这个 LIST 是"工具是否已真实执行"的跨进程真值，`ai:idem` 的索引值指向台账下标（`LINDEX` 读取），直接 `LTRIM` 会同时破坏幂等依据并使索引失效；因此它不能当作可裁剪的普通缓冲。真正的成本在 `ledger()`/`ledgerCounts()`：全量 `LRANGE` 为 O(N) 且把正文全部拉回 JVM。处置口径：保留执行事实完整性，先评估实际体量与审计读取必要性；若优化读路径，不得删除判重事实或破坏索引；任何存储结构调整需另行设计。

**（2）`ai:xevents`（K08）——上界是"单实例可证"。**
window 由 `min(6000, 64MiB ÷ (本轮观察最大帧+256B))` 计算，下限 256；`MAXLEN ~` 近似裁剪允许超出约 99 条。多实例交叉写大帧时，各实例只知道自己观察到的最大帧，全局上界会退化（`:513-529` 自述）。读侧一次 `XREVRANGE COUNT window` 最坏 6000 条 × 64KB，属于"能证明有界、但峰值很高"的设计。

**（3）`ai:xack`（K15）——短命键 churn，不是泄漏。**
每帧一个 UUID token 键、TTL 120s，高帧率下瞬时键数=2 分钟内帧数。它放大 `used_memory` 波动与 `INFO keyspace` 噪声，但每个键都会被 TTL 回收。改成"按 run 的短 TTL HASH + 固定 field"可消除，属优化项，不影响正确性。

**（4）`ai:runs`（K31）——无 TTL 是有意的发现面设计。**
全局 SET 是启动续跑/死轮扫描的唯一发现面。若给整键 `EXPIRE`，活跃轮会被一起删掉，所以刻意不设 TTL，改为按成员 `EXISTS` 惰性剔除（10m 节流）。代价是：单 SET 单槽（Cluster 热键）、清理 O(N)、崩溃残留成员要等快照 TTL 24h 后才可能被剔除。成员带 `t/u`，带身份线程只清自己成员；系统线程按成员身份判活。

**（5）`ai:creq`（K38）——字段淘汰缺失，但整键有 TTL。**
每次 claim/cancel 都 `PEXPIRE` 整键，所以"活跃会话"会让整键一直活着，字段随发送次数累积；value 只有 `RUN:<uuid>`/`CANCELLED`（约 50B），单条很小，但 field 数无界。会话销毁整键 `DEL`（`AiSessionPurgeService.java:1396`），TTL 兜底。属"可观测的缓慢增长"，不是急性故障。

**（6）`ai:purge:pending` / `ai:purge:retry:due`（K50/K51）——durable 台账 + 失败态容量。**
pending 无 TTL 是设计：它是"会话已销毁但资源未清完"的 durable 记录，只有 `complete` 一条删除路径；永久失败（权限/坏值/文件不可删）的会话会留下永久 pending 键与 guard。ZSET 对耗尽项只 `defer` 改分数、不摘成员，所以成员数随永久失败会话单调增长。规模通常很小，但属确认的"失败态无界"，需要容量告警与人工 `DELETE` 入口。

**（7）`kb:cache:doc`（K54）——真正缺删除路径的一族。**
`syncToCache` 只写"变更文档"，不删除 manifest 中已消失的 doc 键；`RedisKbCacheStore.delete` 只被 `KbCache.unlock` 用于锁键。知识库长期演进（文档下线/改名）会留下永不回收的 `kb:cache:doc:*`。全局知识域无租户是正确的，缺的是"差集删除"。

**（8）`task:events`（K62）——每 task 单消费者 + 上层多路复用。**
`RedisTaskEventBus.subscribers` 是 `Map<taskId, Consumer>` 单值覆盖，但 `TaskSseService` 对同一 taskId 维护 `List<SseEmitter>`，只在"首订阅"时向总线注册一次、在"末订阅"时退订（`TaskSseService.java:159-186`、`:339-368`），跨实例帧到达后由 `deliverJson` 扇出到本机全部 emitter。因此单值 map 不会丢订阅；这是"总线按 task 单消费者、接入层多路复用"的正确分层。

### 4.8 锁序、死锁与误删专项

**锁序（未发现成环）**

1. DB：`task → job`。`TaskRepository` 注释、`JobService.createAndStart/cancel`、`TaskService.delete` 一致；`JobProgressService.startItem` 只锁 job、不取 task；`JobTerminalWriter` 用 `REQUIRES_NEW` 先提交 job 终态再锁 task，切断"持 job 等 task"的反向边。
2. Redis：无嵌套多锁；每个脚本要么单键，要么同 tag 三键；`ToolResourceLocks` 固定 task → job 且不等待（job 被拒立刻归还 task）；扫描/清理/会话门互不嵌套。
3. JVM：`submitLock → emitLock`（决策落库后发回执帧）、`finalizeMonitor → emitLock`（终态写后发终帧）、`identityLock`/`emitLock` 只在同一 emitter 内、`FrameWakeListener → RedisFrameWakeBus`（监听器锁内调 `bus.subscribe`，bus 锁内不回调监听器）、`TaskSseService task 锁 → RedisTaskEventBus`（bus 回调不取 task 锁）。未发现反向边。
4. 同线程重入：`synchronized` 可重入，`cancelTerminal` 在 `finishSuccess` 内重入同一 monitor 安全（`ResilientChatService.java:2226` 注释）。

**误删他人锁：已收口项**

- `LeaseService` 续/验/放：`<epoch>|<owner>` 精确匹配（`:204-233`）。
- `SessionGate` 续/放/强放：`runId|token` 精确匹配；强放只匹配 `runId` 或 `runId|*`（`:183-196`），且核对身份。
- `KbCache` 比对删（`RedisKbCacheStore.java:26-34`）。
- `ClientRequestRegistry.releaseBinding` 条件 HDEL（`:130-138`）。
- `RunStore.tryClaimExecution` 回滚只删自己写入的 `claimValue`。

**仍存在的非原子删除**

- `JobHeartbeatRegistry.cleanupDeadLocalRunner`：`GET → DEL` 无值比对（L-2）。
- `RunStore.deleteRunKeys` 的 13 键 `DEL`：语义是轮次回收，但若与在跑驱动并发，会强删租约/fence/计数器。当前 purge 路径先 cancel、再等终态，窗口存在但窄；归入 C 组同类风险（与 C-18 联动），不单列编号。

### 7.2 原生命令路由与序列化

- **原生命令路由**：`RedisFrameStore.xadd` 使用 `connection.execute("XADD", key, "MAXLEN", …)`（`RedisFrameStore.java:1185-1193`）。Cluster 下按 **args[0] 的 key** 路由；当前实现 key 是第一个参数，正确但**脆弱**——任何把 key 挪位的重构会静默写到随机节点。
- **命令面**：全仓**无** `XREAD/XREADGROUP/XACK/XGROUP`、无 consumer group、无多 Stream 跨槽问题；无 `KEYS`、无 `FLUSH*`、无 `SELECT/setDatabase`（与 CI 守卫 `scripts/ci/forbid-redis-cluster-unsafe.mjs` 一致）。
- **序列化**：全部 `StringRedisTemplate`（`StringRedisSerializer`）；Lua ARGV 一律传字符串（`SettlementObservationStore.java:127-131`、`RunStore` 各脚本、`SessionPurgePendingStore` 等），避开 "Long → ClassCastException 被吞成 fail-open"。
- **返回值解码**：脚本返回数组时用 `DefaultRedisScript<List>` 并按 `Number/String/byte[]` 兼容解码（`RedisFrameStore.java:700-718`）；`RENEW_SAME_SLOT` 特意返回逗号串而非数组（`RunStore.java:754-757`），避免 MULTI 逐元素反序列化失败。
- **字符串往返**：`SeqSplit.headText()/tailText()` 把 UTF-8 负载转 Java String 再交给 Lua；负载来自 Jackson（合法 UTF-8），`FrameSizeLimiter` 只做字段级降采样、不做字节截断（`ai/run/FrameSizeLimiter.java:90-131`）⇒ 往返字节一致。

### 7.5 全局键与非缺陷判定（重申）

- `Task.id` / `Job.id` 是全局 IDENTITY，`ai:lock:task/job`、`job:*` 不含 tenant **不会跨租户撞键**；若未来业务表多租户化，才需要把 tenant 加进键。这是"当前模型正确"，不是"遗漏隔离"。
- `ai:cfg:*`、`kb:cache:*`、`ai:purge:retry:lock`、系统面 `ai:lock:resume-scan` 的全局性由业务语义决定（配置全局、知识域全局、清理全租户批次、扫描全集群单飞）。
- `ai:runs` 无 TTL 是为保住发现面；`ai:purge:pending` 无 TTL 是为 durable 台账。两者都需要容量/运营手段（告警、批次限额、人工入口），而不是简单加 TTL。
- 生产 HTTP 入口由 `TenantIdentityFilter` 拦截缺失/非法身份，系统账号 `-1` 禁止 HTTP。因此"无身份键落到 legacy 命名空间"只在内部调用/异步线程契约失配时出现，写成 C-01/C-02 的**内部契约风险**，不写成已发生的跨租户访问。

### 交付结论

- **Redis 侧**：62 个键族全部列清。容量/驻留点需分开看：`kb:cache:doc:*` 缺下线删除；`ai:creq` 活跃期字段增长（任何淘汰必须保留未完成请求与停止墓碑）；`ai:ledger` 受 run 生命周期约束，但承担跨进程判重真值，不能简单裁剪；其余"无 TTL / 字段只增 / 短命键"都在有意的设计约束或 TTL/轮删下收敛。
- **锁侧**：核心 fencing、会话门、资源锁、决策/认领/观测的仲裁语义成立；确定缺陷集中在 `TaskService.createIdempotent` 的锁范围与 `cleanupDeadLocalRunner` 的非条件删除。
- **后端内存**：45 个结构全部列清；确定缺陷是 `drivingRuns` 异常漏删、`JobWatchdog` 两集合无清理、`JobCancellationRegistry` 跨实例残留；其余按"有界 / 有清理 / 以内存换正确性"的取舍记录。
- **前端**：唯一持久面是 1 个 localStorage + 8 类 sessionStorage，隔离键形扎实；确定缺陷是 5 处清理缺口（草稿逐击键、`mermaidPending`、`historyMdCache`、用户消息集合、`recentActions`）。
- **未验证项**：所有运行时数值、真实 Cluster 行为、浏览器配额与并发规模；这些列在 §2.5 与 §8.1，不用静态结论替代运行证据。
