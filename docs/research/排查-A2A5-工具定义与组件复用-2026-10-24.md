## 1. 总体结论

### 1.1 健康度判断

| 面 | 评级 | 一句话 |
|---|---|---|
| **A-2 工具定义·后端** | 良（治理骨架最扎实，1 条 🔴） | 37 个工具全部显式声明 `@ToolScope/@ToolRisk/@ToolCategory`，四类危险作业统一进确认门、三个前端写族各有后端复核；唯一的 🔴 是「11 个 String 工具仍被 JSON 二次编码」——已判定过、只修了一半的收口项。 |
| **A-2 工具定义·前端** | 中（1 条真缺陷） | 18 条登记 + 4 条工作区动作 + 1 条特判 = 23，与后端 `@ToolChannel(FRONTEND)` **精确对齐**；围栏（快照闸 / epoch / consequential 零点击 / 预览人确认）质量高于同类实现。但 `confirm_step` 会把 AI 刚改在浏览器内存里的表格**刷回服务端文件**，而该工具在元数据里是 READ、不经任何确认。 |
| **A-5 复用·后端 AI 域** | 良（0 条 🔴） | 没有"自写 SSE 解析 / 自拼 OpenAI 请求 / 自造 tokenizer"这类结构性重造，协议、工具循环、schema、记忆 advisor 全踩官方链路。问题是"同一小组件被写 2～4 份"（不可见字符清洗器 **4 份**、SHA-256 hex **4 份**、数值兜底 **20 处**、`new ObjectMapper()` **10 处**）。 |
| **A-5 复用·后端业务域** | 中（1 条 🔴） | 没有自写 xlsx 解析、没有手拼 SQL、没有自写 IO；但四套作业 Runner 大量复制粘贴（进度事件 / `doneEvent` / `rowKey` / `scopeType`），且 `ExcelReader` 不校验 `_meta.def_code` —— 套错模板可静默"0 行成功"。 |
| **A-5 复用·前端** | 差（4 条 🔴，全部集中在样式面） | "无样式块"做到极致（22 个 `.vue` 零 `<style>`、零 `:deep(`、零字面 `!important`），但代价是把样式全搬进 class 串：**534 处硬编码 hex、0 处 `var(--el-*)`、25 档任意字号**，并形成 AiPanel / AiSettingsView 两个"零 Element Plus"孤岛 + 3 处 Tailwind `!` 覆写。组件复用层面反而健康（四个共享件都在被复用）。 |
| **业界对照** | 同构偏严 | 工具注册形态、风险分级、HITL 挂起、前端工具通道、生成式表单白名单五处与业界主流同构甚至更严（确认绑定服务端挂起条目 + CAS）；真正落后的是「契约的单一事实源」与「设计系统没有 token 层、也没有任何 lint 门」。 |

**一句话**：**A-2 的病在"描述与元数据说谎"（不影响跑通、影响模型选对），A-5 后端在"小组件重复"，A-5 前端在"样式纪律只有事实、没有机制"。**

### 1.2 最重要的 5 条

1. **`confirm_step` 是写入缝（🔴 R3-02）**：`replace_values` 等回执说"未保存、仅在浏览器内存"，同一轮 `confirm_step` 推进导入向导第 1 步时，`flushEditors()` 会把含 AI 改动的**整表**写回服务端文件，而该工具元数据是 `READ`、无确认卡、也不需要用户点任何按钮。后续 PRECHECK/IMPORT/PUBLISH 读的就是这份被 AI 改过的内容。
2. **11 个后端业务工具的文本结果仍被 JSON 二次编码（🔴 R3-01）**：`list_config_defs`/`list_tasks` 这类多行清单在模型侧是"首尾多一对引号、换行变字面 `\n`"的单行串，既费 token 又容易被模型当字面量复述。L-88 只修了 KB 三个工具（`KbTools` 已带 `resultConverter`），`AiTools` 一行没改。
3. **`ExcelReader` 不校验 `_meta.def_code`，错文件可静默"0 行成功"（🔴 R3-25）**：模板/导出件第 0 列明明写了 `def_code`，读取端跳过不比对；表头对不上就把整列记成 `_unknown_*` 再丢弃 → 0 行 → 预检查 `totalErrors=0` 判 COMPLETED。这是数据面正确性缺口，不是风格问题。
4. **前端样式纪律没有机制（🔴 R3-54/55/56/57）**：534 处硬编码 hex（其中 120 余处是 Element Plus 自己的调色板被逐字重写）、0 处 `var(--el-*)`、25 档任意字号（含 12.1/12.3/16.5px 这类一次性值）、3 处 Tailwind `!` 直接覆写 EP 组件内部；而前端**没有 eslint、没有 stylelint、CI 也没有 lint 步骤**，纪律只靠评审与注释。
5. **契约的单一事实源缺位（🟡 R3-03 主发现 + R3-04）**：同一份工具描述存在三处手抄副本（后端 `@Tool` 描述 → 前端 `types/tools.ts` → `@ToolParam` 内嵌的整份 schema 文本），**已实测漂移**（前端 `ui_snapshot`/`ui_click` 少句；`generative_form` 顶层写六型、白名单是七型、`attachment` 只藏在参数描述中段）；`tools.yaml` 只覆盖 27/37，缺的正好是最新两批（`kb_*` 3 条 + `ui_*` 7 条）。

- **[🔵] P-69 下发前 / 回灌前双闸 + 超时结局"未知"，逐条对上 MCP 的安全建议**（S6）。`tool/FrontendToolGuard.java:12`、`gate/SpToolCallingManager.java:1464`、`AiTools.java:541`：前端通道工具下发前校验入参原文（`inspectArguments`），不合法就不挂起、直接把结构化错误回填；回灌前再校验结果（`inspectResult`），不合法保持 `PENDING` 可重试；前端真超时定义为"结局未知"（`FRONTEND_TIMEOUT`）而非失败。MCP 规范的四条 SHOULD（敏感操作确认、调用前展示入参、结果先校验、实现超时）在这里都有对应物，而且校验用的是**入参原文**而非反序列化对象（能看见被静默忽略的未知属性）——比多数实现细。建议把"为什么必须看原文"提炼进对外设计文档，否则后续维护者容易改成反序列化后校验。
- **[🔵] P-70 `Channel.FRONTEND` 就是业界的 client-side tool，且服务端仍保管契约**（S6）。`ToolMeta.java:50`、`AiTools.java:374`：前端工具方法体一律 `return FRONTEND_STUB`，真实副作用在浏览器；服务端挂起、等回灌；通道判定按元数据做，不在方法体里做。与 AI SDK"客户端工具＝服务端无 execute、调用下发、`addToolOutput` 回灌"完全同构；差别是本仓把"下发许可"和"回灌校验"留在服务端（AI SDK 默认把客户端结果直接塞回消息），因此更严。注意固有代价：client-side tool 的执行语义只能在前端单测里验证，后端契约测试锁不到"前端真的支持描述承诺的全部能力"。
- **[🔵] P-71 `generative_form` 是"受约束组件目录"，不是自由 HTML**（S6）。`AiTools.java:547`、`FormRenderer.vue:1`：白名单七型、描述明写"禁止 HTML/脚本/自定义属性"，前端按类型 v-if 渲染、未知类型不渲染。这是 Puck 总结的"component registry + prop schema + 组合规则"三件套的最小实现：合法输出空间被枚举，视觉一致性由渲染层保证（对比 OpenUI 指出的"生成 HTML 不继承 design token"，本仓从结构上避免了）。**保持白名单制**；新增字段类型时同步 `GenerativeFormRules` 与 `FormRenderer` 的穷尽分支，别让"描述里支持、渲染器不支持"。
- **[🔵] P-72 `ui_*` 原语的"看得见才可操作 + consequential 永不执行 + ref 不是选择器"三条声明式纪律**（S6）。`frontend/src/utils/ai-dom-tools.ts:10`、`AiTools.java:877`：只遍历已注册区域内带 `data-ai-ref` 的元素；`data-ai-risk="consequential"` 一次都不点；入参只接受语义 ref + epoch，不接受 selector/XPath/HTML；`ui_fill` 只对 `data-ai-fill="allow"` 生效。业界对"通用 DOM 操作工具"的最大担忧就是它会绕过业务确认门（AI SDK 的 approval 只在服务端工具上生效，客户端工具一旦拿到 DOM 就能点任何东西），本仓用"页面自己声明哪些元素可被 AI 操作、哪些永久不可"把能力面收回产品代码，**比主流更强**。注意 fail-closed 与 `ui:on` 的 fail-open（`extra.uiRegionCount` 缺失即视为存在，`ToolScope.java:21`）别互相抵消。
- **[🔵] P-73 工具注册形态的对外提醒**：若将来接入 MCP server 端，注意本地 `@Tool` 与远端 MCP 工具同名不会被自动去重（Spring AI 2.0 文档明说前缀生成器只管 MCP 侧）——此条与 P-64 同源，单列以提醒集成期。
- **[🔵] P-74 业界四问速览（本仓 vs 主流）**：① 工具写法与描述——主流 `@Tool` 声明式为主、描述必须写清"做什么 + 何时用"；本仓同形态，缺"何时不该用"与示例。② HITL 分级与确认闸——主流三档 + 确认必须在服务端校验；本仓 `READ/WRITE/DANGER` + DANGER 挂起 + 服务端 `PENDING` CAS，缺 `edit`/`respond`（R3-24）。③ 前后端边界与组件复用——主流"客户端工具＝服务端无 execute + 受约束组件目录"；本仓同构，但前端名册分三处维护（R3-23）、表单控件不复用 EP（R3-68）。④ 设计系统不可覆写——主流 eslint + stylelint + CI 阻断；本仓事实纪律很好（0 覆写）、但无 lint、无 token 层（R3-70 / R3-56）。
- **[🔵] P-75 `element-plus` 全量注册与 `main.ts` 的引入方式本身是规范的**：`frontend/src/main.ts:16`（全量 CSS）+ `:20` `app.use(ElementPlus)`，`element-plus ^2.9.3`、`tailwindcss ^3.4.17`（`tailwind.config.js` `preflight: false`）。这解释了为什么"EP 可用却不用"的每一处（AiSettingsView、ConditionForm 错误壳、原生 select/checkbox）都是可回收的——基础设施没缺，缺的是纪律。
- **[🔵] P-76 `.tip` / `.tip-arrow` 是"无 CSS 的语义类名"而非样式丢失**：`AiPanel.vue:930/941/978/989/1000` 等 10 处 + `utils/markdown.ts:134-141`（`RENDER_MARKER_CLASSES` 白名单）。`.tip`/`.tip-arrow` 已无任何 CSS 定义（`ai-chat.css` 已删），实际外观由 `TIP_CLASS` 承担；这两个类现在的作用是 (a) 标记 className 白名单、(b) e2e 选择器锚点（如 `frontend/tests/ai-panel-parts-render.spec.ts` 的 `send.find('span.tip')`）。**不是缺陷**，但容易被误读为"样式定义丢了"；建议在 `markdown.ts:131` 注释里固定语义。

### 4.2 调研①：Spring AI 工具调用与工具描述

- **官方推荐写法**（Spring AI 1.1.x，与本仓 `spring-ai.version=1.1.7` 同线）：声明式 `@Tool(description=...)` 是首选；编程式 `MethodToolCallback` 只在"不拥有源类 / 运行期动态构建工具定义"时使用；`FunctionToolCallback` 用于 lambda。官方对描述的态度很硬：不写 `description` 会退回方法名，而"Failing in providing a good description can lead to the model not using the tool when it should or using it incorrectly"。`@ToolParam(description=...)` 应写清格式、取值范围、枚举；默认全部必填，可选需 `required=false` 或 `@Nullable`。2.0 文档新增：`defaultTools` 里的工具"every request"都下发，"risk-tier and destructive tools should typically be added per call, not as defaults"。
- **描述怎么写模型才不误选**（三份材料交叉）：
  1. Anthropic 工程博客：工具应"少而精"、按服务/资源命名空间分组（`asana_projects_search`）、返回高信号而非低层标识符；描述要能让人和模型都一眼判断"何时该用它"。
  2. 实证论文（**856 个工具 / 103 个 MCP server**）：**97.1%** 的工具描述至少含一处"smell"，**56%** 未能清楚陈述目的；按六要素补齐后任务成功率中位 **+5.85pp**、部分目标完成率 **+15.12%**，但执行步数 **+67.46%**、**16.67%** 的用例反而退化——**长度不是越多越好**，应做紧凑变体。六要素 = Purpose / Guidelines / Limitations / Parameter Explanation / Examples / Length & Completeness。
  3. Spring AI 与 AI SDK 文档同调：描述是"when the tool is picked"的主要信号，参数描述是"how to fill it"的主要信号。
- **对本仓的落点**：本仓在 Purpose、Parameter Explanation 两项已经很好，缺 Guidelines 与 Examples（R3-22）；而"描述的多份手抄副本"直接破坏了"描述即契约"的前提（R3-03）。

### 4.3 调研②：HITL 工具分级与确认闸的主流模式

- **分级心智模型**：MCP 规范给工具加了可选 `annotations`（行为提示），社区通行四个布尔 `readOnlyHint / destructiveHint / idempotentHint / openWorldHint`；多份社区文档一致指出其默认值偏"悲观"（未声明即按可写、破坏性、非幂等、开放世界处理），客户端据此决定是否弹确认（该默认值出自 schema 与社区文档，本次未取到规范页表格原文）。MCP 规范页明确要求：客户端 SHOULD 在敏感操作前提示用户、调用前把入参展示给用户、把结果校验后再交给模型、实现超时、记录审计日志。
- **决策类型**：LangChain JS `humanInTheLoopMiddleware` 定义四种人工决策 `approve / edit / reject / respond`，支持 `when` 谓词按入参条件拦截（"只拦写 workspace 之外的路径""只拦非 SELECT 的 SQL"），要求 checkpointer 持久化中断点。`respond` 专用于"ask_user"型工具（人直接充当工具作答），并明确警告"不要用 respond 去否决副作用工具，因为它会被当成成功结果"。
- **确认不可伪造**：Vercel AI SDK 把工具执行分三种形态——服务端自动执行、客户端自动执行（`onToolCall` + `addToolOutput`）、需要用户批准（工具部件进入 `approval-requested`，客户端 `addToolApprovalResponse`）。它专门提示：`useChat` 每轮把完整消息历史发回服务端，"a modified client could fabricate an approval response"，因此敏感工具要开 `experimental_toolApprovalSecret` 由服务端验签。
- **Spring AI 侧**：1.1.x 参考文档没有内建确认闸；官方扩展点就是自己实现 `ToolCallingManager`（工具执行生命周期）+ `ToolExecutionExceptionProcessor`，这与本仓 `SpToolCallingManager` 的落法一致（🔵 P-68/P-69）。

### 4.4 调研③：前端工具 vs 服务端工具的边界，以及组件复用

**边界的三条主流判据**：
1. **副作用发生在哪**：浏览器状态（路由、剪贴板、本地表格内存、文件选择手势、焦点/高亮）→ 客户端工具；需要凭据、需要防篡改、需要跨用户一致 → 服务端工具。AI SDK 的措辞："For tools that need to run in the browser (updating UI state, accessing browser APIs), use client-side tools instead"。
2. **谁持有契约**：客户端工具在服务端**没有 `execute`**，服务端这一轮就此暂停，等客户端 `addToolOutput` 回灌；因此"什么时候允许下发、回灌什么算合法"必须由服务端保管——这正是 MCP 那三条（校验入参 / 把入参给人看 / 校验结果）的落点。
3. **能力面要可枚举**：不要让模型自由生成 DOM/HTML，而是给"已注册区域的语义键（ref）+ 动作动词"或"组件白名单 + props schema"。Puck 的结论直白：自由生成会 "misuse primitives, duplicate existing abstractions, or bypass higher-level components"，产生并行实现与技术债；OpenUI 补充：生成出来的 HTML 不继承设计 token，视觉一致性要额外做。

**组件复用主流形态（三派）**：
- **受约束组件目录**（Puck / 本仓 `generative_form`）：模型只输出"用哪个组件 + 什么 props"，渲染层由产品代码负责，因此天然复用设计系统。
- **客户端工具驱动 UI**（AI SDK / TanStack AI / CopilotKit）：工具名 + 入参即可，UI 由前端按 tool part 状态渲染。
- **沙箱 widget + 组件桥**（OpenAI Apps SDK / MCP Apps）：工具返回 UI 资源，在沙箱 iframe 里渲染，通过 bridge 回调工具（`window.openai.callTool` 一类）；换来隔离与可移植，付出"样式不共享"的代价。

### 4.5 调研④：「设计系统不可覆写」的通行落地

- **Atlassian Design System 是公开可查的最完整样板**：`eslint-plugin-design-system` 里同时有
  - `no-unsafe-style-overrides`："Discourage usage of unsafe style overrides used against the Atlassian Design System"（直接对应"不可覆写"）；
  - `ensure-design-token-usage` / `use-tokens-space|shape|typography|motion`："Enforces usage of design tokens rather than hard-coded values"；
  - `no-html-button|no-html-select|no-html-text-input` 等"别用原生元素，用设计系统组件"；
  - 配套 `stylelint-design-system`：官方说明它 "prevents new contributors from accidentally adding hard-coded color or spacing values"。
- **纯 CSS 侧的通用做法**：`stylelint-declaration-strict-value`（指定属性必须用变量/函数/关键字，禁裸 hex、裸 px、裸字体名）、`declaration-no-important` 防特异性升级。
- **Tailwind 侧**：`eslint-plugin-tailwindcss` 对 `bg-[#3b82f6]` 这类任意值报警/报错（**stylelint 只看 CSS 文件，看不进 `class` 属性，所以必须有 eslint 这一半**）。
- **落地顺序（业界共识）**：token 层（theme / CSS 变量）→ lint 规则 → CI 阻断 → 视觉回归（VR）兜底。**缺 token 层时先上 lint 只会产出大量无法自动修的告警**——这正是本报告把 R3-56 排在 R3-70 前面的理由。

### 4.6 与业界对照后的三条判断

1. **本仓在"机制"上不落后，在"可机器校验"上落后**：确认不可伪造（服务端 PENDING + CAS）、入参原文校验、consequential 零点击、受约束组件目录，这四项都达到或超过主流；但**描述契约、前端名册、设计 token、lint 门**四项全靠人记，没有一条机器断言。
2. **A-5 的"复用"问题集中在"同一语义多份实现"，不是"重造轮子"**：S3/S4 均未发现自写 SSE/HTTP/tokenizer/xlsx/JSON-Schema/IO；这与业界主流框架的使用姿势一致。真正该抄的作业是"抽一层参数化的共享件"（R3-27 清洗器、R3-28 hex、R3-34 Runner 事件、R3-65 卡片壳）。
3. **A-2 的"误识别"问题一半来自描述、一半来自工具粒度**：R3-05/R3-06/R3-08 是同一类（相邻工具无互斥判据），业界给出的解法就是"给易混工具对补一行分工 + 一个示例"，不必全量扩写描述。
