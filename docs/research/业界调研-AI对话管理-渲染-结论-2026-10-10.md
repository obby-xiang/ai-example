## 二、明确结论：ChatGPT 官方 web **不原生内联渲染** Mermaid

**结论**：ChatGPT 官方 Web 端对 Mermaid 的行为是**「受支持时出现 `Preview` 按钮 → 点击后在沙箱中预览」**，**不是自动把 `mermaid` 代码块内联渲染成图**。若某代码块没有出现 `Preview`，说明该代码块类型不支持预览。官方支持回复原文：*"Supported Mermaid code blocks can now be previewed inside ChatGPT—select Preview when it's available. Actions vary by device and account"*（2026-09-06）。同帖中 2025-01 的请求与 2025-10 / 2026-02 / 2026-04 的追加吐槽，说明该能力在此前长期缺失。

- **来源 URL**：
  - https://community.openai.com/t/rendering-support-for-mermaid-code/1085642
  - https://help.openai.com/en/articles/20001246 （《ChatGPT 中的写作与代码块》；含 Preview 受支持类型清单：HTML 页面、React 组件、SVG、**Mermaid 图**、Vega/Vega-Lite 图表；预览/执行在沙箱环境，需要外部资源时会请求授权）

**工程含义（推断）**：把「渲染」做成**显式门控的用户动作**（按钮 / 折叠 / 开关），既对齐业界主流，又天然规避「流式期每 token 重渲染 Mermaid」的性能与闪烁问题，同时把沙箱/权限诉求收敛到一次显式交互上。

## 三、开源栈选型结论

### 3.1 依赖事实（一手：直接读依赖清单 / 官方文档 / 源码）

| 项目 | Markdown 解析 | 高亮 | 数学 | Mermaid | sanitize |
|---|---|---|---|---|---|
| **Vercel ai-chatbot** | Streamdown `^2.3.0` | shiki `^3.21` | katex `^0.17` + `@streamdown/math` | `@streamdown/mermaid` | Streamdown 内建 |
| **Streamdown**（Vercel） | remark-parse + remark-gfm + remark-rehype + `hast-util-to-jsx-runtime`（**不用 react-markdown**） | shiki | remark-math + katex | `@streamdown/mermaid`（可选独立插件） | rehype-raw + **rehype-sanitize** + **rehype-harden** |
| **LobeChat / Lobe UI** | react-markdown `^10` + remark-gfm/math/breaks/cjk-friendly + `@lobehub/streamdown` + `remend` | shiki + `@shikijs/stream` | katex | `beautiful-mermaid`（开关 `enableMermaid`） | rehype-raw + **rehype-sanitize** |
| **open-webui** | marked | highlight.js + shiki + lowlight | katex | mermaid `^11` | **DOMPurify**（覆盖不全，见第六节） |
| **LangChain 官方前端指南** | React：react-markdown + remark-gfm；Vue/Svelte/Angular：marked + dompurify | 未规定 | 未规定 | 未涉及 | 非 React 栈必须 DOMPurify |

补充：Lobe UI 的 Markdown 组件 API 暴露 `enableMermaid` / `enableLatex` / `enableStream` / `allowHtml` / `enableHtmlPreview`——即开源实现把「数学 / Mermaid / 流式 / HTML 预览」当作**可独立开关的能力**，而非一体化的默认行为。

### 3.2 选型结论：两大流派

1. **unified（remark/rehype）系**——**React 生态主流**：react-markdown，或 Streamdown / Lobe UI 这类**自建 unified 管线**（Streamdown 刻意不用 react-markdown，直接 remark-parse → remark-rehype → `hast-util-to-jsx-runtime`）。
   - 高亮首选 **Shiki**（三方名单里 shiki 出现 4 次，是事实上的新默认；highlight.js/lowlight 属旧栈）。
   - sanitize 走 **rehype-sanitize**，且必须排在 `rehype-raw` **之后**。
   - raw HTML 是**可选**能力（`rehype-raw`），默认不开最安全。
2. **marked 系**——**Vue / Svelte / 纯 HTML 栈主流**（open-webui；LangChain 对 Vue/Svelte/Angular 的官方推荐）：产物是 **HTML 字符串**，因此**必须 DOMPurify**，高亮常见 highlight.js。
3. **数学：KaTeX 全票**。调研到的所有开源栈（ai-chatbot、Streamdown、Lobe UI、open-webui）**一律 KaTeX**，未出现 MathJax，且都配 remark-math。

**结论一句话**：React 系选 **remark/rehype + Shiki + KaTeX + rehype-sanitize**（可整包用 Streamdown 或 Lobe UI 的流式 Markdown 组件）；Vue/Svelte 系选 **marked + DOMPurify**（高亮建议同样换 Shiki）；数学两边都是 **KaTeX**。

## 四、流式渲染共识

**问题定性（一手）**：token 逐条到达时，Markdown 天然处于「语法半成品」状态——未闭合代码围栏会吞掉后续全部内容、半截表格、未闭合加粗，这是核心难点。

**共识一：全量重解析是主要性能瓶颈（O(n²)），解法是「分块 + 块级 memo」**
- 「每个 token 触发整段累积文本的全量 re-parse」＝工作量随长度**平方**增长。
- **业界共识做法**：把流式 Markdown 切成**离散块**，并对每块 **memo**，避免每个 token 重解析**已完成**的内容。AI SDK 官方 cookbook 明确推荐此法；Streamdown 把它做成了库能力——组件级 `React.memo` + **块级 memo**，只有内容变化的块重渲染，**已完成块保持稳定**。

**共识二：未闭合块的处理——两条路线并存**
- **路线 A（保守，观感稳）**：流式期间先以纯文本呈现，"done" 后整体渲染 Markdown；或**检测到围栏闭合才渲染代码块**。
- **路线 B（增量修复 / 自动闭合，观感更「活」）**：解析器每帧自动闭合未闭合标记——未闭合 ``` 渲染为「仍在填充的代码块」，而不是字面反引号（参见 mdstitch 的 crate 说明；PanelUI 的「已上屏的字不能消失」原则；Streamdown 的未闭合块解析）。
- 附带一致性原则：**已上屏的内容不得回退/消失**（避免"闪回"）。

**反共识噪音（重要的免过度优化口径）**
- LangChain 给出量化口径：`marked` 约 **1 MB/s**，**5 KB 聊天消息 < 5 ms**；「对典型聊天消息，每 token 全量重解析已足够，只在很长（**>50 KB**）且观察到卡顿时再上 `requestAnimationFrame` 节流 / 增量解析」。
- 即：**< 50 KB 全量重解析够用**，增量解析器不是起步阶段的必需项。

**共识三：重型渲染器（KaTeX / Mermaid / 高亮）绝不能每帧跑**
- 数学：每个 chunk 全量跑 KaTeX 既浪费算力又造成**可见闪烁**，应增量处理或只处理**已完成块**。
- Mermaid：Streamdown 官方明确「**不要在每 chunk 重渲染 Mermaid**」，否则**慢且闪**；给出 `useIsCodeFenceIncomplete()` 钩子——未闭合时显示**占位**，**围栏闭合后立刻渲染**（**不等整条消息结束**），并用 `isAnimating` 在流式期禁用交互。open-webui 同款策略：**只有 code fence 已闭合才渲染**（判据 `(token?.raw ?? '').slice(-4).includes('```')`）。
- **反例**：VS Code Copilot Chat 正是踩了「**每个 token 都重渲染 Mermaid 图**」这个坑。
- **进阶做法（本次调研最值得抄的工程做法之一）**：把 **KaTeX / Mermaid 的解析挪到 Web Worker**——Kimi Code 官方原文「**KaTeX 数学公式与 Mermaid 的解析改到 Web Worker 执行，流式输出时界面更跟手**」。

## 五、Mermaid 的工程代价（三条硬约束）

### 5.1 体积（一手实测口径）
- 官方 `mermaid@11.12` 的 `dist/mermaid.min.js` = **2684.6 KB ≈ 2.6 MB（未 gzip）**；同版本 `dist/mermaid.esm.min.mjs` 入口仅 **25.6 KB**（ESM 分片壳）。
- gzip 后量级：第三方实测 **≈ 315 KB gzip（v11.14）**。
- 其他口径（第三方，供区间参考）：核心 + 懒加载图 chunk **≈ 480 KB**；渲染 **50–200 ms / 图**；某项目实测懒 chunk **≈ 620 KB**；另有一处把 mermaid 包成「≈ 3 MB minified」的 IIFE 的反例。
- **Tiny build**：官方提供约半体积的精简版，**不含 Mindmap、Architecture、KaTeX 渲染、lazy loading、ELK**（官方原文：tiny build 从未包含 ELK）。

### 5.2 硬约束一：**不可有效 tree-shake，必须 dynamic import**
图解析器在**模块初始化时**注册进 registry——「import mermaid 就得到**全部图类型**」。因此官方/社区一致建议：**绝不要把 mermaid 放进全局 app shell**，按路由 code-split 或**首次需要时 dynamic import**。

懒加载惯例（一手）：**先探测页面/消息里是否真的有 mermaid 块，再 dynamic import**——
- open-webui：遇到第一个 mermaid 围栏才 `await import('mermaid')`；
- Streamdown：**viewport-based lazy loading**（进入视口才渲染）；
- Loomcycle：`import("mermaid")` 懒 chunk。

### 5.3 硬约束二：**围栏闭合才渲染，绝不每 token 重渲染**
见第四节共识三。这是三条约束里**唯一会直接毁掉体验**的一条（VS Code 已给出反面案例）。

### 5.4 硬约束三：**失败必须回退到源码块（+ 重试 / 关闭开关）**
- 库侧：Streamdown 默认 `suppressErrorRendering: true`（避免半成品渲染），提供自定义 error 组件（`error` / `chart` / `retry` 三参，含 "Try Again" 重试），并**保留源码可复制/下载 `.mmd`**。
- 产品侧范式（可择一）：
  - **按钮预览**：ChatGPT「当且仅当支持时显示 Preview」；
  - **全局开关**：Kimi Code `mermaid = "off"`；
  - **双模式**：Qwen Code `render` / `raw`，原则是「**原始源码始终可访问**」；
  - **失败落代码块**：open-webui 渲染失败 `console.error` 后回退代码块。

**安全档位**：Mermaid 官方默认 `securityLevel: 'strict'`（HTML 标签编码、禁用 click）；`sandbox` 用 iframe 隔离，官方提示「site owner 需自行判断用户可信度」。

## 六、安全惯例：AI 输出渲染的 XSS 防线

**这不是假想风险（一手）**：Escape 的安全团队在两家互不相关的公司发现**同一类存储型 XSS**，根因都是 Markdown 栈装配为 `react-markdown + remark-gfm + rehype-raw` 而**没有任何 sanitizer**；并使用 `<iframe srcdoc="...">` 绕过 react-markdown 默认的 URL scheme 白名单（`srcdoc` 不在 URL 属性清单里，React 会原样写入 DOM，浏览器按新文档解析）。同文另引用两个 CVE：

- **CVE-2026-17496（NoteGen）**：markdown-it 配 `html: true` + `dangerouslySetInnerHTML` + CSP 置空 → 恶意 skill 的 `REFERENCE.md` 让模型输出 `img onerror`，在 Tauri webview 内执行。
- **CVE-2026-32308（OneUptime）**：Mermaid 以 `securityLevel: "loose"` 渲染后把 SVG 用 `innerHTML` 注入，Mermaid 的 `click` 指令变成**执行原语**，波及所有渲染 Markdown 的字段。

**惯例清单**
1. **首选不渲染 raw HTML**。`react-markdown` 默认把 raw HTML 转成纯文本（安全默认）；对多数团队就是**删掉 `rehype-raw`**——表格、链接、代码块都还能用。
2. **若必须开 raw HTML**：`rehype-sanitize` **必须排在 `rehype-raw` 之后**（顺序反了等于没做，因为节点仍是未解析的 raw node）；用默认 schema **白名单**而非黑名单，并**逐属性枚举**（`srcdoc` / `on*` / `src` / `action`）；iframe 若保留**必须 `sandbox` 且不给 `allow-same-origin`**；配套 CSP（无 `unsafe-inline`，含 `img-src` / `form-action` / `frame-src`）。
3. **KaTeX 与 sanitize 的顺序**：若信任 KaTeX，`rehype-katex` 要跑在 `rehype-sanitize` **之后**（官方包 README 原文警告）。
4. **「每个渲染扩展都是第二个 HTML 生成器」**：语法高亮、KaTeX、Mermaid 一旦把结果送进 `innerHTML`，就重新打开了刚关上的风险面；典型反模式是「sanitizer 放在这些插件之后会剥掉它们的产物，于是被挪到前面，最后停在 `rehype-raw` **前面形同虚设**」。
5. **工业级默认值参考（Streamdown）**：默认 `rehype-sanitize`（GitHub schema，扩展 `tel:`）+ `rehype-harden`（协议 / 链接域名 / 图片来源白名单，可关 base64 图以防追踪与 CSRF），暴露 `allowedProtocols` / `allowedLinkPrefixes` / `allowedImagePrefixes` / `skipHtml` / `allowedTags` / `urlTransform`；并明确警告「覆盖 `rehypePlugins` 时**必须带上 `defaultRehypePlugins.sanitize`**，否则 XSS 防护失效」。
6. **流式会让「只检查成品」的 sanitizer 失效**（浏览器已被分片渲染过）。同一份输出可能出现在多个渲染面（工单看板、客服回放、Slack 展开、PDF 导出），要**逐个渲染点加固**。
7. **链接属性惯例**：Markdown 标准无法表达 `target`；行业惯例是自定义 link 组件对站外链接加 `target="_blank"` + `rel="noopener noreferrer"`（两者一起用），站内链接走路由组件。Streamdown 走另一条路：用 `linkSafety` / `allowedLinkPrefixes` 限制可达域，不安全链接渲染为 `[blocked]`，而非依赖 `target`/`rel`。
8. **现实提醒：开源实现经常覆盖不全**。open-webui 公开安全公告显示其 **23 处 `{@html}` 只有 9 处（39%）经过 DOMPurify**；`MarkdownInlineTokens.svelte:130` 是安全写法（`DOMPurify.sanitize(token.text, {ADD_ATTR:['target']})`），但存在未覆盖的「防御传播缺口」（GHSA-hcwp-82g6-8wxc / CVE-2026-45318）。
9. **反例（不要照抄）**：open-webui 当前用 **`securityLevel: 'loose'`** 初始化 Mermaid（其 `utils/index.ts` 的 `initMermaid`）——正是 CVE-2026-32308 出事的档位；对比 Streamdown Mermaid 插件默认 **`securityLevel: 'strict'`** 与 Mermaid 官方默认 **`strict`**。

**一句结论**：安全上是「**不做比做错好**」。不开 raw HTML 是成本最低、收益最高的默认；一旦开了 raw HTML，或引入 Mermaid / 高亮这类「第二 HTML 生成器」，**sanitizer 的顺序与属性白名单**才是关键，而现实中开源实现的覆盖率可能只有 39%。

## 八、给后续重启的要点（**推断**，非来源结论）

1. **Markdown 渲染已是行业默认，不是可选项**：调研到的所有面向用户的对话产品都渲染 Markdown（含代码块 / 表格 / 列表），差别只在「覆盖面与稳定性」。不渲染会明显低于基线体验。
2. **Mermaid 是分层的、不是统一的**：ChatGPT 用 Preview 按钮门控、Claude 用 Artifacts 容器、Copilot（web）不在聊天里渲染、DeepSeek 至今只高亮。**「原生自动内联渲染」反而是少数派**——「先只做代码块 + 可选预览/渲染按钮」是完全站得住的落地形态。
3. **若做 Mermaid，三条硬约束不可绕**：① 必须 dynamic import（≈0.3 MB gzip、不可 tree-shake）；② 必须「围栏闭合才渲染」，绝不每 token 重渲染；③ 失败必须回落到源码块 + 重试 / 关闭开关。
4. **安全上「不做比做错好」**：不开 raw HTML 是成本最低、收益最高的默认；开后，sanitizer 的顺序与属性白名单才是关键。
5. **流式不必一开始就上增量解析器**：LangChain 的量化口径支持「先整段重解析 + 块级 memo」；只有长回答 / 多图 / 高 TPS 时才需要更重的方案（Streamdown 式未闭合块解析、Web Worker 卸载 KaTeX / Mermaid）。

**证据薄弱处（重启时请留出余量）**：Claude 正文渲染明细与数学实现、Gemini 的 Mermaid 能力、Cursor 的渲染实现、通义 / 文心的具体渲染栈，均缺一手文档，已在表内标注为**推断 / 弱证据 / 未获得数据**。
