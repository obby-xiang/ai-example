# 调研 · HITL 与表单超时设计业界惯例 · 2026-10-20

> 调研问题：AI 面板里的人机交互卡（HITL 审批卡 / 生成式表单卡）该不该有超时？若有，尺度、语义与交互形态应如何设计？本件扫 **CI/CD 人工门禁、ITSM/OA 审批、AI Agent 工具确认、支付/OTP/会话超时、表单与生成式 UI** 五类场景。
> 来源：GitHub / Microsoft / ServiceNow / 飞书 / 钉钉官方文档，MCP 规范、OpenAI Agents SDK、AG-UI、CopilotKit、Claude Code 官方文档，W3C WCAG 2.2.1 与 Apple HIG / NN/g 设计准则；访问日期 2026-10-20。厂商大多允许改配置，故本件**优先记录默认值**，不把可配值当默认；二手整理仅在第 9、25 条出现并显式标注。
> 结论：**业界没有"审批几分钟不点就自动拒绝"的短超时惯例** —— 决策型默认是「无限等待」或「小时到天的 fail-closed」（常见 30 天），秒级倒计时只出现在**有真实资源占用**的场景（OTP / 锁座 / 支付会话）；表单型普遍不硬过期，靠「草稿保留 + 续期 + 恢复窗口」兜底。冲突不在数值，而在**把资源占用型的倒计时套到了决策型 / 填写型的卡上**。
> 边界：本件是调研稿，不含本仓施工结论；§5「建议 1~3」是研究方向，不构成接口契约或验收承诺。§5 里的 240 s / 120 s 是调研时点的 demo 取值。
> 脱敏：无账号显示名、无本机绝对路径、无密钥、无原始会话内容；官方 URL 原样保留。

## 0. 一句话结论

业界没有"审批 4 分钟不点就自动拒绝"这种短超时惯例。**审批类默认都是 fail-closed 或无限等待，超时尺度是小时到天（常见 30 天）；只有"资源占用型"场景（OTP、锁座、支付会话）才用秒级倒计时。** 表单类则普遍不硬过期，超时靠"草稿保留 + 续期 + 恢复窗口"兜底。我们两类卡片的 demo 冲突，问题不在数值，而在**把"资源占用型的倒计时"套到了"决策型/填写型"的卡上**。

## 1. HITL 审批/确认的超时：默认行为

### 1.1 CI/CD 人工门禁

| 产品 | 默认超时 | 超时后的结果 | 是否可配 | UI 是否读秒 |
|---|---|---|---|---|
| GitHub Actions（Environment required reviewers） | **30 天** | 作业**自动失败**（auto-fail），不是通过 | 不可配（社区多年诉求未实现） | **不读秒**，只显示状态 `Waiting` |
| Azure DevOps（Approvals check） | **30 天** | 阶段标记为 **skipped**（跳过，不是 rejected），之后可重试阶段 | 可配，上限 365 天 | 不读秒，审批面板给 approvers + instructions + timeout |
| Power Automate / Teams Approvals | 约 **30 天**（受单次 cloud flow 运行上限约束） | 审批过期，flow 失败 | 需用 relay/双 flow 绕开 | 不读秒 |

GitHub 文档原话：*"While a job is awaiting approval, it has a status of 'Waiting'. If a job is not approved within 30 days, it will automatically fail."*（[GitHub Docs](https://docs.github.com/en/actions/deployment/about-deployments/deploying-with-github-actions)）
Azure 文档原话：*"If approvals aren't completed within the specified Timeout, the stage is marked as skipped."*，并明确 *"You can retry a stage when approvals and checks time out."*（[Microsoft Learn](https://learn.microsoft.com/en-us/azure/devops/pipelines/process/approvals)）；默认 30 天、上限 365 天见 [ApprovalOptions](https://learn.microsoft.com/en-us/javascript/api/azure-devops-extension-api/approvaloptions)。
GitHub 不可配置这一点在社区讨论里已确认多年（[discussion #5673](https://github.com/orgs/community/discussions/5673)）。

**要点：超时的语义是"未获批准 → 不放行"，而且"超时"与"拒绝"在状态机里是两个不同状态**（Azure 是 skipped，不是 rejected）。这是最值得抄的一点。

### 1.2 ITSM / OA 审批流

- **ServiceNow**：`Ask for Approval` 的 Due date 是**可选**的。设了 due date，才在到期时按配置 **auto-approve / auto-reject / auto-cancel**；不设就**一直 pending**，只靠提醒和升级催办。文档：*"If a due date is added to an approval, the approval is automatically approved, rejected, or canceled if the approvers have not responded by the designated time."*（[ServiceNow Docs](https://www.servicenow.com/docs/r/build-workflows/workflow-studio/ask-approval-flow-designer.html)、[Flow Designer Approvals 概览](https://www.servicenow.com/community/workflow-automation-articles/flow-designer-approvals-overview-workflow-automation-center-of/ta/p/2528202)）
- **飞书审批**：企业可配三段式规则——**超时提醒**（单仍有效，机器人催办）→ **超时关闭**（单据失效）→ **恢复有效期**（关闭后一段时间内提交人可恢复数据，过期才需重提）。官方帮助中心：[管理员设置审批超时规则](https://www.feishu.cn/hc/zh-CN/articles/852878870528-%E7%AE%A1%E7%90%86%E5%91%98%E8%AE%BE%E7%BD%AE%E5%AE%A1%E6%89%B9%E8%B6%85%E6%97%B6%E8%A7%84%E5%88%99)。三段式的粒度是**小时/天**，不是秒。
- **钉钉 OA**：模板高级设置里是"到期提醒/超时催办"，审批人节点可设"自动通过"；"限时审批"到期失效属于可选项，不是默认（[钉钉](https://www.dingtalk.com/qidian/page-JEntVt7N.html)）。

**要点：OA 世界的默认不是"到点拒绝"，而是"提醒 → 关闭 → 可恢复"。自动通过必须显式配置，且通常只用于低风险/低金额。**

### 1.3 AI 侧的工具确认（与我们最同构）

- **MCP Elicitation**：协议层**没有超时**，只有三态响应 `accept` / `decline` / `cancel`（关闭弹窗、按 Esc 属于 cancel，**不等于拒绝**）。规范还要求 *"Clients SHOULD allow users to decline elicitation requests at any time"*。（[MCP Spec 2025-06-18](https://modelcontextprotocol.io/specification/2025-06-18/client/elicitation)）
- **OpenAI Agents SDK**：工具审批是"暂停 run → 返回 interruptions → 之后用序列化的 `RunState` 恢复"，文档专门有一节 *"Dealing with longer approval times"*，明确为"可以隔很久再批"设计，**无 TTL**。（[OpenAI Agents SDK HITL](https://openai.github.io/openai-agents-js/guides/human-in-the-loop/)）
- **Claude Code**：权限对话框会一直阻塞 CLI（无头脚本会"hang silently waiting for approval"），"don't ask again" 的授权范围是会话级；没有任何倒计时。（[Claude Code permissions](https://code.claude.com/docs/en/permissions)）
- **AG-UI（我们用的协议）**：interrupt 上有一个**可选的** `expiresAt`（ISO-8601 TTL）。规则是：*"Clients must not submit a resume past an interrupt's expiresAt. Stale resumes produce RunError."* 同时 `cancelled`（用户放弃）与 `resolved`（用户作答）是两个状态。（[AG-UI Interrupts](https://docs.ag-ui.com/concepts/interrupts)）
- **CopilotKit**：`renderAndWaitForResponse` 的 API 只有 `respond()`，**没有 timeout 参数**，卡片会一直等用户操作。（[npm: @copilotkit/react-core](https://www.npmjs.com/package/@copilotkit/react-core)）

**要点：AI HITL 的行业默认是"无限期挂起 + 可恢复"，不是短超时。若必须加 TTL，AG-UI 的范式是：TTL 可选、过期产生显式错误状态、过期与用户取消分开记账。**

### Q1 结论

1. 默认行为排序：**无限等待（ServiceNow 无 due date、MCP、Agents SDK、Claude Code）> 长超时后 fail-closed（GitHub 30d、Azure 30d、Power Automate 30d）> 提醒/升级（飞书、钉钉）> 自动拒绝（必须显式配置）> 自动通过（极少，且只用于低风险）**。
2. **没有主流产品默认"几分钟不响应就自动拒绝"**。自动通过更是反模式（等于把"没人看"当成"同意"）。
3. 秒级/分钟级超时只出现在**有真实资源占用**的场景（OTP、锁座、支付会话），不出现在审批。
4. 超时 UI 惯例：CI 类**不读秒**，只显示 `Waiting` + 谁发起的 + 何时发起；OA 类显示"剩余 X 天/已超时"；只有资源型场景才 mm:ss。

## 2. 倒计时显示惯例：读秒 / 截止时刻 / 不显示

业界实际是按**时间尺度**分档的，不是按"卡片类型"：

| 剩余时间 | 惯例 | 例子 |
|---|---|---|
| 30 s – 15 min（资源会被释放） | **mm:ss 读秒**，到期前有明确状态变化 | OTP 重发倒计时（30–60 s）；锁座/占库存 "reserved for 12:43"；支付会话 |
| 1 h – 24 h | **绝对截止时刻**或粗粒度相对值（"今天 18:00 前"），一般不读秒 | 会话过期；Stripe Checkout 会话默认 24h TTL（文档只规定过期，不要求秒级倒计时） |
| > 24 h / 数天 | **只显示日期或"剩余 3 天"**，不显示时分秒 | 审批 due date、SLA 到期日 |
| 无固定期限 | **不显示任何时间**，只显示状态与已等待时长 | GitHub `Waiting`、ServiceNow 无 due date 的 pending |

具体证据：

- **OTP**：主流做法是 30–60 s 内禁用重发并显示可见倒计时（"Resend code in 00:30"），到点后按钮才可用。这是"防滥用冷却"，倒计时本身就是功能说明。（[sms8 最佳实践](https://sms8.io/blog/phone-number-verification-best-practices)、[UX Patterns: Code Confirmation](https://uxpatterns.dev/patterns/forms/code-confirmation)）
- **锁座/占库存**：电商用 "Your cart is reserved for 15:00" 的 mm:ss，因为倒计时对应**真实资源释放**；反过来，如果库存没真的被锁，这种文案被视为 dark pattern（[AppLass: Cart Reservation Timer](https://applass.com/blog/shopify-cart-reservation-timer)）。W3C 在解释 WCAG 2.2.1 时也用了"选座 2 分钟，超时座位回池"的例子。
- **支付/会话**：Stripe Checkout 会话默认 24 小时过期，是服务端 TTL、可用 `expires_at` 调整；文档层面没有"秒级倒计时"的要求，倒计时是商户前端自行加的（[Stripe Docs](https://docs.stripe.com/payments/checkout/how-checkout-works)）。
- **无障碍硬约束（唯一有规范效力的）**：WCAG 2.2.1 Timing Adjustable 要求，对内容设置的时间限制至少要满足其一：可关闭 / 可调到默认值 10 倍以上 / **到期前预警并给至少 20 秒用简单操作续期，且允许续期至少 10 次**。（[W3C](https://www.w3.org/WAI/WCAG22/Understanding/timing-adjustable.html)）

这条对我们最要命：**任何"到点就不可提交"的卡片，如果没预警、没续期，严格说是不符合 WCAG 2.2.1 的**（除非能论证"essential"例外，比如座位/库存真的会释放）。

### Q2 结论

- 读秒不是"更专业"，而是"时间尺度匹配"：**< 10 分钟的硬截止才读秒；超过 1 小时一律给绝对时刻；无期限就不显示时间。**
- 读秒必须配三件事：**到期前预警（≥20 s）、可续期、到期后的明确终态**。只读秒不给续期 = 制造焦虑且不合规。
- 读秒本身要无障碍：不要只靠颜色/闪烁，用文本 + `aria-live="polite"`，且不要每秒都播报。

## 3. 表单/填写的超时设计

### 3.1 主流表单：不硬过期，草稿优先

- 表单平台的标准能力是 **autosave + Save and Continue Later + 草稿链接**，而不是"到点作废"。Jotform 有 "Save and Continue Later" 开关（[Jotform](https://www.jotform.com/help/227-how-to-enable-autofill-on-forms/)）；Form.io 明确建议 wizard 每页提供手动"保存草稿"入口（[Form.io](https://form.io/features/auto-form-saving/)）。
- 真正的会话超时（银行、政务表单）通常是 **15–30 分钟不活动**，且必配"即将退出，是否继续"的续期弹窗——这正是 WCAG 2.2.1 的落地形态。
- **飞书的三段式**是"超时后数据去留"最完整的公开范式：提醒（仍有效）→ 关闭（失效）→ **恢复有效期**（关闭后仍可取回数据，过期才重填）。([飞书帮助](https://www.feishu.cn/hc/zh-CN/articles/852878870528-%E7%AE%A1%E7%90%86%E5%91%98%E8%AE%BE%E7%BD%AE%E5%AE%A1%E6%89%B9%E8%B6%85%E6%97%B6%E8%A7%84%E5%88%99))

### 3.2 生成式 UI 里的表单卡存活期

- **AG-UI 的 interrupt 默认没有 TTL**；`expiresAt` 是可选的，而且过期会返回 `RunError`，客户端必须**显式处理**，不能静默丢弃。([AG-UI](https://docs.ag-ui.com/concepts/interrupts))
- **CopilotKit 的 `renderAndWaitForResponse` 无限等待**，卡片随会话存在，用户什么时候填都行。([npm](https://www.npmjs.com/package/@copilotkit/react-core))
- 换言之，生成式 UI 领域的惯例是：**卡片是对话的一部分，不是一次性令牌**；生命周期由会话/线程决定，而不是由卡片自己倒计时。

### Q3 结论

- 表单卡的行业默认是"**长期有效 + 草稿保留 + 可恢复**"，120 秒硬失效属于明显偏离。
- 若业务上必须有 TTL（例如表单结果要写回一个会过期的后端事务），正确形态是：**软到期（可续期/可重开）→ 硬到期（数据保留 + 明确"已过期"终态 + 一键恢复）**，而不是"到点按钮变灰、内容丢失"。
- 超时后的数据去留必须有明确承诺：保留多久、在哪看、能否一键重提。

## 4. 审批卡的信息密度

### 4.1 有明确规范表述的

- **Apple HIG（Alerts）**：*"each one offers only essential information and useful actions"*；*"Include informative text only if it adds value"*；标题不超过两行；按钮最多 3 个；尽量避免需要滚动的 alert。([Apple HIG](https://developer.apple.com/design/human-interface-guidelines/alerts))
- **Nielsen 渐进披露**：首屏只放"最常用/最重要的少量选项"，细节按需展开；层级不要超过 2 层。([NN/g](https://www.nngroup.com/articles/progressive-disclosure/))
- **NN/g 确认对话框**：只用于高后果、不可逆动作；滥用会让用户形成"闭眼点掉"的习惯，反而降低安全性。([NN/g](https://www.nngroup.com/articles/confirmation-dialog/))
- **CI 审批的实际字段**：GitHub 的 review 弹窗只有"选择 environment + 可选 comment + Approve/Reject"；Azure 的 approval 面板是 approvers + instructions + timeout。**没有把 diff/日志全文塞进审批卡**。

### 4.2 可提炼的"决策所需最少信息"

审批卡应回答四个问题，而不是复述上下文：

1. **要做什么**（动作 + 一句话后果，用动词，不用 "OK/确认"）
2. **对什么做**（目标对象、环境、金额、影响范围）
3. **有多大风险 / 可不可逆**（风险标签、是否可撤销）
4. **凭什么信**（谁发起、何时、依据哪条规则/哪个请求）

其余（原始 payload、完整 diff、历史记录）**折叠或给链接**。这与 GitHub/Azure 的实际字段、Apple "only essential"、NN/g 渐进披露一致。

### Q4 结论

- 有规范表述，且方向一致：**最小决策集 + 详情按需**。没有哪家主流产品把"完整上下文"放进审批卡首屏。
- 信息过多不只是丑，它会**训练用户不读**（NN/g 的 confirmation fatigue），对审批安全是负收益。

## 5. 对我们场景的裁决与三点建议

我们的场景：业务工作区右侧 AI 面板、内部工具、审批卡 240 s、表单卡 120 s。

**先给冲突裁决**：两个 demo 里，"审批卡到点自动按拒绝收尾"比"表单卡 120 s 后按钮直接禁用"更接近业界，但两者都需要改。审批卡的**方向对（fail-closed）、语义和交互不对（把超时混同拒绝、没有预警/续期）**；表单卡的**方向错（生成式 UI 不该有 120 s 硬 TTL）**。

### 建议 1：审批卡 240 s 保留 fail-closed，但改成"预警 → 可续期 → 独立超时终态"

- **不要自动"按拒绝"**。超时的终态应是 **`已超时（未决）`**，与 `已拒绝` 并列且互斥；文案与审计都分开。依据：Azure 超时是 `skipped` 而非 `rejected`；MCP 的 `cancel` 与 `decline` 分开；AG-UI 的 `cancelled` 与 `resolved` 分开。
- **T-30 s 预警 + 一次一键续期**（如 +240 s，最多 2 次，续期动作入审计）。这是 WCAG 2.2.1 的最低合规形态；240 s 本身在"人可决策"的区间内，读秒是合理的。
- **显示方式**：全程 `剩余 3:58`（mm:ss）+ hover/副标题给绝对 `截止 14:32`；最后 30 s 变色并 `aria-live="polite"` 播报一次，不每秒播报。
- **到期后**：卡片保留，给 `重新发起审批` 与 `查看详情`，不要把卡片变成死块。
- 明确**永不自动通过**：参考 ServiceNow 把 auto-approve 作为显式配置、OA 世界只对低风险使用。

### 建议 2：表单卡取消 120 s 硬失效，改为"软到期 + 草稿保留 + 一键恢复"

- **首选**：去掉 TTL，让卡片随会话存活（这是 AG-UI / CopilotKit 的默认范式）。120 s 对"读题 + 填 3 个字段 + 想一下"太短，且生成式 UI 用户预期是"我随时回来填"。
- **若后端事务确实要过期**：120 s 只作为**软截止**——到期时不禁用提交，而是提示"本次填写已超时，可继续提交或重新生成"；已填内容**不清空**，并提供一键"用原参数重新发起"。
- **硬截止必须有恢复窗口**：抄飞书的三段式（提醒 → 关闭 → 恢复有效期）。至少保证离开卡片/刷新后草稿还在。
- **倒计时只在前 30 s 显示**（或全程显示但必须可续期），不要从第一秒就开始读秒——120 s 全程读秒会显著抬高焦虑和误提交。

### 建议 3：统一"倒计时组件 + 状态词汇 + 信息层级"，按时间尺度分档

- **一个组件，三档策略**：`<10 min` → mm:ss + 预警 + 续期；`<24 h` → 绝对时刻（"今天 18:00 截止"）；`≥24 h 或无期限` → 只显示状态和"已等待 X"，不显示倒计时。
- **四态互斥**：`已批准 / 已拒绝 / 已超时（未决） / 已取消`。任何"超时按拒绝"的合并都会污染审计与用户心智。
- **审批卡信息三层**：首屏 = 动作 + 目标 + 风险 + 发起人/时间；第二层 = 关键参数摘要（折叠）；第三层 = 原始 payload / 完整上下文（链接或抽屉）。参照 Apple HIG 的"only essential"和 GitHub/Azure 的实际字段。
- **可访问性**：倒计时用文本而非仅颜色，`aria-live="polite"`，并遵守 WCAG 2.2.1 的 20 s 预警与续期要求。

> 后续口径（入库时注记）：§5 的两案（审批卡 240 s 保留 fail-closed + 预警/续期、表单卡软到期）**均未被采用** —— 2026-10-20 用户直裁审批卡 / 表单卡**不做超时限制**（一直等、一直可填），倒计时族与后端 `expiresAt` 门控整体退役（`docs/决策看板.md` 10-20「去超时裁决」行、`docs/evidence/补档-去超时批-复核确认-DS-Flash.md`）。本件保留调研时点原貌、不回头修订；其中「业界默认无短超时」的结论与该裁决方向一致，「超时 ≠ 拒绝、四态互斥」的口径仍对未决卡状态语义有效。
