## 0. 方法与证据分级

### 0.1 三条判定原则

1. **先问「这个数字是否该存在」**，再问「值对不对」。业界大量前端常量根本没有公开基线（例如「快照单行截断 120 字符」），这类项的正确结论是「**无统一标准**，按本仓预算自洽即可」，而不是硬凑一个「业界值」。
2. **有基线的项，比的是「量级与关系」而不是「具体数字」**。例如 HTTP 超时：业界没有「必须 60s」，但有「普通请求应在 10s 量级给反馈、长任务单独放宽、前端 deadline 要晚于/早于后端并明确方向」这三条关系；本册据此判断，而不是抄某个产品的数字。
3. **相等不等于对齐**。两个阈值数值相同、语义不同（前端看门狗 vs 后端判死）时，业界做法是让二者**派生**（一方 = 另一方 ± 心跳/交付余量），而不是各写一个相同字面量。

## 1. 结论摘要（先看这 10 条）

1. **212 行里只有 66 行能引用到 S 级业界来源**（HTTP/SSE 超时与退避、分页、Playwright、Web Storage 配额、Excel 规范、mermaid 上游默认、Element Plus 默认页大小）；**33 行显式没有统一标准**，其余 115 行是**本仓自治阈值**，正确结论是「无统一标准 + 保留/补依据」，不是「改成业界值」。
2. **`MESSAGE_MAX_CHARS = 8192` 的值可以保留，交互必须改**：主流产品根本不暴露字符上限（限制以 token 计），而本仓「输入非空即显示剩余字数 + `maxlength` 静默截断粘贴」。建议改成「用量 ≥75% 才显示计数器 + 取消硬截断、提交时校验」——值不动，心智负担和丢字风险都消失。
3. **三处「前后端同值零余量」都必须错层，但方向不同**：首帧 30s=30s 二选一——35s 收后端错误帧，或 25s 由前端自带文案，**关键是不能相等**；作业帧空闲 90s=90s 触发的是「降级轮询」，75s（更快拿真相）或 120s（优先收终态帧）都可，取决于降级是否用户可见；发布墙钟 300s=300s 必须**前端更晚**（360s，因为段预算会重置、墙钟不会）。
4. **页面就绪 8s 与定义就绪 10s/10s 是「一个值 + 一个分叉 + 一句过期注释」**：8s 本身站得住（SPA 就绪通常 <1s，8s 是看门狗不是期望值），问题在 3s→8s 无记录、注释仍写 10s。建议抽一个共享常量，定义就绪显式写「= 页面就绪 + 2s 余量」。
5. **分页真正的病灶是 200 不是 50**：50 与 AIP-158/GitHub 同量级；200 是「一次拉完再截断」，应改 50 + 加载更多。
6. **表格 2000 格 / 200 行 / 100000 格三阈值全部缺吞吐依据**，而它们的作用是「决定要不要吓用户一跳」和「拒绝执行」，必须用 SpreadJS 实测算出 cells/s 才能定，属于**必测项**。
7. **镜像 120 条 / 512K 字符有硬上限可算**：sessionStorage 5MiB/origin（S15），512K UTF-16 ≈ 1MiB ≈ 20% 配额，量级合理；但「末条不受预算约束」是唯一可能击穿配额的路径，应给末条也封顶。
8. **Playwright 视口 1440×900 确认未生效**（静态可判定）：`project.use` 的 `...devices['Desktop Chrome']` 覆盖顶层 `viewport`，实际 **1280×720**（S13）。这是 212 行里唯一「写了一个值、跑的是另一个值」的项。
9. **Playwright 120s 合理、180s 需背书、`retries: 0` 与官方 CI 建议相左**：官方默认用例 30s、断言 5s（S11），120s 已是 4×；两处 180s 无注释。CI 上 0 重试会把基础设施抖动记成产品缺陷。
10. **最该先做的不是改数字，而是补三样东西**：① 每个「相等」阈值写出派生式；② 每个「无基线」常量写出预算来源（token/内存/吞吐）；③ 一次真机测量（消息长度分布、首帧 TTFT、SpreadJS 写入吞吐、navigate 就绪耗时）。

## 2. 专题一：对话输入 `MESSAGE_MAX_CHARS = 8192`（重点详析）

### 2.1 主流产品到底公开了什么

| 产品 | 公开的输入约束 | 是否公开「单条字符上限」 | UI 是否显示剩余字数 |
|---|---|---|---|
| ChatGPT（Web） | 上下文窗口按模型/套餐不同，以 token 计；帮助中心只给 token 换算（1 token ≈ 4 字符英文） | **否** | **否**（S23 观察） |
| Claude（claude.ai） | 文档只讲 context window（200k/1M）与超限 `400 prompt is too long`；提供 compaction | **否** | **否**（S23） |
| Gemini | 上下文窗口以 token 计 | **否** | **否**（S23） |
| GitHub Copilot Chat / Cursor | 上下文窗口 + 仓库索引；超长靠截断/附件 | **否** | **否**（S23） |

**可以据此下的结论**（不依赖产品观察也成立）：

- 主流产品的「输入上限」是**模型上下文 token 预算**，不是字符数；超限的表现是**提交时 400/提示过长**，而不是输入框拦字（S1、S2）。
- 因此「8192 字符」在本仓的定位应当是**输入合法性闸**（防超大请求、审计可读、DB 列宽），而不是「上下文治理手段」。这一定位决定了后面所有建议。

**为什么本仓仍应有字符闸**：内网产品需要可预期的请求体上限、日志/反馈摘要可存、以及「一句话需求」的产品约束；业界对应做法是「硬上限存在，但对用户**软呈现**」——输入不被静默改写，提交时给可操作错误（S3 的 GOV.UK 模式正是如此）。

### 2.2 UI 是否该显示剩余字数、何时显示才不增加心智负担

**现状（实读）**：composer 底栏的字数提示只在**输入非空**时出现（`v-if="inputText.length > 0"`），但一旦出现就是「剩余 N 字」——输入第一个字就显示「剩余 8191 字」，此后逐字递减；四档 `normal / near(≤500) / limit(=0) / over(<0)` 中 `normal` 档同样渲染文本（`composerCounterText`）。同时 `textarea` 带 `:maxlength="MESSAGE_MAX_CHARS"`，浏览器会**阻止**继续输入并**截断粘贴**。

**业界基线（S3，GOV.UK 设计系统）给了三条可直接引用的规则**：

1. 「先在不带计数器的情况下测试你的服务」——计数器的默认状态是**不显示**；
2. 只有「有正当理由限制输入」时才用；若用户经常顶到上限，应该**提高上限**而不是加计数器；
3. 当上限远高于用户可达长度时，用 `data-threshold`（示例 75%）**只在超过阈值后显示**计数器；
4. 计数器**不阻止**用户输入超限内容，允许「先粘进来、再改下去」，错误另在字段上方提示。

**心智负担的量化**：8192 的上限意味着绝大多数消息（估计 p99 < 1000 字）永远碰不到上限。而输入第一个字就出现的「剩余 8191 字」，在 0–8000 区间**信息量为零**，却持续占位、并持续暗示「你被限额」。真正的信息点只有两个：**接近上限**、**已超限**。

**静默截断是更严重的问题**：`maxlength` 在粘贴 9000 字时会把内容截成 8192，用户看不到任何提示（S4 说明浏览器会 generally prevent 超出；GOV.UK 明确把「允许超出再改」作为设计原则）。对 AI 对话，这等于**悄悄丢掉用户最后 800 字**，模型基于半句话回答——与本仓「裁决 A1：截断会让模型基于半句话下结论」的后端原则直接矛盾。

### 2.3 前后端同尺、token 与压缩的关系

**同尺性（好）**：前后端都以 **UTF-16 码元**计数（Java 侧注释与 yml 明确；前端 `String#length` 与 `maxlength` 同口径）。中文 BMP 字符各计 1，8192 汉字 = 24576 UTF-8 字节，不会被字节数提前判死。

**同尺性的两个缺口**：

1. **代理对（emoji、部分生僻字）计 2**：用户看到「8192 字」但只能输入 4096 个 emoji。GOV.UK 把这个列为已知问题（S3）。建议文案写明「字符（emoji 计 2）」，或改用 `Intl.Segmenter` 按字形簇计数并**同步后端**（成本高，暂不建议本批做）。
2. **`maxlength` 与「软校验」不可兼得**：只要保留 `maxlength`，就一定有静默截断；要「允许超出再改」，就必须去掉 `maxlength` 或把它抬到 2× 作为防爆保护。

**与 token 的关系（估算，需实测校准）**：OpenAI 的经验换算只对英文成立（1 token ≈ 4 字符，S1）；中文常见量级是 **1 token ≈ 1–1.5 汉字**（不同 tokenizer 差异大）。据此：

| 量 | 估算 | 占比 |
|---|---|---|
| 8192 汉字 | 约 8k–12k tokens | 128k 上下文（N-AI-010）的 **6%–9%** |
| 8192 汉字（按 1–1.5 字/token 估） | 约 8k–12k tokens | 记忆 token 预算 48000（N-AI-008）的 **17%–25%** |
| 压缩触发 | 70% × 128k ≈ 89.6k tokens | 单条 8192 **不会**触发压缩 |

结论：**8192 对「单条消息」是宽松的，对「40 条记忆窗口 + 48000 token 预算」却不是小数**——一条顶格消息可以吃掉记忆预算的四分之一。这也解释了为什么「调大 8192」是错误的治理方向：调到 32768，一条消息就能吃掉整个记忆预算。上下文治理应继续由 40 条 / 48000 token / 70% 压缩三件套负责，**不要让输入闸兼职**。

**另一个联动**：前端 `maxlength` 截断后，后端永远收不到超限请求，`400 MESSAGE_TOO_LONG` 的分支在产品里几乎不可达——意味着后端这条防线长期未被真实流量验证。改软校验后，它会重新变成有效防线（也更容易暴露前后端不同尺的问题，属于好事）。

### 2.4 明确建议（值 / 交互 / 契约 / 观测）

| # | 建议 | 具体做法 | 理由 |
|---|---|---|---|
| 1 | **值：保留 8192** | 不改；后端键 `app.ai.input.max-chars` 仍是唯一事实源 | 无业界反例；上调会侵蚀记忆预算；下调（如 4096）需先看长度分布 |
| 2 | **计数器：改为阈值显示** | 仅当 `已用 ≥ 75%`（剩余 ≤ 2048）显示；保留现有 `near(≤500)` 变琥珀、`limit`、`over` 三档；`normal` 档不渲染文本 | 直接采用 S3 的 `data-threshold=75` 模式；非空即显示的计数零信息量 |
| 3 | **取消静默截断** | 去掉 `maxlength`（或设为 16384 仅防爆），改为 `canSubmit` 校验 + 提交时红字错误「超出 N 字，请删减」；`over` 档禁用发送 | S3：允许超限后再改；避免粘贴丢字导致模型基于半句话回答 |
| 4 | **文案补口径** | placeholder/帮助写「上限 8192 字符（emoji 计 2）」；错误文案给「还差 N 字」 | S3/S4 的代理对问题；减少「为什么我只打了 4000 个表情就满了」的困惑 |
| 5 | **配置化** | 前端从 `/api/ai/health`（或现有 health 载荷）读 `inputMaxChars`，失败回落 8192；不再硬编码 | 现在靠注释「与后端同值」维持，属双份事实源；改后端键必漏改前端 |
| 6 | **可访问性保持** | 保留「每档一个常量、只在跃迁时播报」的现有实现 | 已经优于业界常见做法（逐字播报会打断屏读用户），不要回退 |
| 7 | **需实测（30 天）** | 采集 `message.length` 的 p50/p95/p99/max、`over` 档触发次数、粘贴被截断次数（改软校验前无法采到，可先采长度） | 决定 8192 是否该降到 4096；也给「长文本转附件」的需求判断提供依据 |

**一句话**：**数字不动，交互重做**——把「输入即显示的配额条 + 硬截断」换成「接近上限才提示 + 提交时校验」。这是本册 212 行里「改动最小、收益最大」的一项。

## 3. 专题二：零余量超时链（首帧 30s / 帧间 45s / 发布 300s / 作业 90s）

### 3.1 业界的两条硬原则

1. **Deadline 必须分层且方向明确**：外层等待应覆盖内层全部工作 + 交付余量；两个不同层用同一个数值，等于让两层同时判死，错误归属随机（S16 的 10s 注意力上限解释了「为什么要尽快给结论」，S7 解释了「超时后如何重试」）。
2. **看门狗阈值应显著高于正常 p99**：AWS 的建议是「超时设在高分位之上，让重试处理长尾，而不是让超时处理长尾」（S7）。这解释了为什么 45s（正常帧间隔 <5s 的 9 倍）是合理的，而「与后端判死点完全相同」不合理。

### 3.2 四处逐一判断（关键：方向不同，且方向必须与文案一致）

| 位置 | 现值 vs 后端 | 应有方向 | 建议 | 理由 |
|---|---|---|---|---|
| 首帧 `DEFAULT_FIRST_FRAME_TIMEOUT_MS`（N-FE-009） | 30s vs 首包 30s | **必须错层，方向二选一** | **35s**（后端 + 5s 投递余量，优先收后端错误帧）；若更看重快速失败则 **25s**，但前端必须自带可解释文案 | 相等时两个判据同时触发，用户看到哪种错误取决于竞态。选 35s = 让后端 400/错误帧先到；选 25s = 前端自己给「模型未响应」，不能既想快又想拿后端文案 |
| 帧间 `DEFAULT_IDLE_TIMEOUT_MS`（N-FE-002） | 45s vs 90s | 前端更早（已正确） | **保留 45s** | 1/2 错层是这条链里唯一写对的；45s < nginx 默认 60s 读空闲（S6），不会被代理先掐 |
| 作业帧空闲（N-FE-021） | 90s vs 30s×3=90s | **必须错层，方向取决于「降级是否用户可见」** | **75s**（降级对用户不可见时，尽快转轮询拿真相）或 **120s**（降级会闪「通道断开」时，优先收终态帧）；不要 90s | 这个看门狗触发的是**降级到 3s 轮询**，不是直接判失败。相等时「降级」与「后端判死」同刻发生，两条路径的提示会互相竞争 |
| 发布墙钟（N-FE-024） | 300s vs 段预算 300s | **前端更晚** | **360s** 或读服务端 deadline | 段预算会因挂起/恢复**重置**，墙钟不会；同值必然出现「合法运行被前端先收摊」 |

> 一句话记忆：**首帧可以早也可以晚，但必须错层且文案与方向一致；等终态的（发布）必须更晚；等帧间的（45s）可以更早。**

### 3.3 容易漏掉的一层：墙钟 vs 单调时钟 vs 后台节流

- 浏览器后台标签的定时器会被节流：Chrome 不可见 >5 分钟且静默 >30s 后进入 intensive throttling，**每分钟只检查一次**（S14）。任何用「墙钟差」实现的 300s/90s 看门狗，在后台都会**显著晚触发**。
- 建议：所有「是否超时」的判定用 `performance.now()`（单调）或服务端时间戳差值，不用 `Date.now()` 差值；`setTimeout` 只做唤醒，到点后**重新读时钟**再判定。这条对 N-FE-021/022/024/162 全部适用。

### 3.4 本轮不建议动的地方

- 帧间 45s、建连 15s（N-FE-007）、重连 4 次 / 1-2-4-8s（N-FE-003/004/006）：与业界「指数退避 + 抖动 + 有界次数」一致（S7），且 45s < 60s（S6）有代理层依据，**保留**。
- 唯一小问题是重连抖动 ±25%（N-FE-005）：AWS 的 full jitter 是 `[0, cap]`，equal jitter 是 `[cap/2, cap]`；本仓 `[0.75, 1.25]` 属「窄幅 equal jitter」，对只有 4 次重连的场景足够，**保留**。

## 4. 专题三：页面就绪 8s 与定义就绪 10s/10s

| 项 | 现值 | 业界基线 | 判断 |
|---|---|---|---|
| `PAGE_READY_TIMEOUT_MS`（N-FE-017） | 8000（旧 3000） | 无「前端内部等待」标准；Playwright 用例默认 30s、断言 5s（S11）只作量级参考；SPA 路由就绪通常 <1s，冷启动大表 <5s | **8s 合理**（作为看门狗），但 3s→8s **无记录**是治理问题 |
| `DEFINITIONS_READY_TIMEOUT_MS`（N-FE-173 导出） | 10000 | 无「定义列表就绪」公开基线（D）；量级只能与页面就绪对齐 | 注释写「与页面就绪同量级（10s）」，但页面就绪已 8s，**注释过期** |
| `DEFINITIONS_READY_TIMEOUT_MS`（N-FE-174 导入） | 10000 | 无公开基线（D）；同一语义应共用同一常量 | 与 173 同名同值却是两份独立常量 |
| `DEFINITIONS_RETRY_COOLDOWN_MS`（N-FE-175） | 5000 | 无基线 | 合理的失败冷却（防止每个工具调用各发一次请求吃满 60s 预算） |

**建议**：

1. 抽 `PAGE_READY_TIMEOUT_MS = 8000` 到共享常量，三个向导共用；
2. 定义就绪**显式派生**：`DEFINITIONS_READY_TIMEOUT_MS = PAGE_READY_TIMEOUT_MS + 2000`（=10000），注释写「比页面就绪多 2s，因为要多等一次定义列表请求」，而不是「同量级」；
3. 若要简化，就统一成 8000，并接受「定义列表慢于 8s 时 fail-closed」——**不要**保留三个独立字面量；
4. 需实测：`navigate_to` 后页面 handler 注册耗时 p95（决定 8s 是否可降到 5s），以及定义列表接口 p99（决定 +2s 余量是否够）。

**为什么 8s 不必降到 3s**：这是「等不到就如实告知」的上限，不是期望耗时；调低只会把「慢但成功」判成失败。真正该做的是把 p95 测出来写进注释——如果 p95 = 300ms，8s 就是 26 倍余量，可以放心保留。

## 5. 专题四：分页 50/200 与表格 2000/200/100000

### 5.1 分页：50 是对的，200 是反模式

| 基线 | 默认页大小 | 上限 |
|---|---|---|
| Google AIP-158（S8） | 示例 50 | 示例 1000，超出向下钳制 |
| GitHub REST（S9） | 30 | 100 |
| Element Plus `el-pagination`（S10） | 10 | 由 `page-sizes` 决定（默认到 100） |
| 本仓作业问题（N-FE-026） | 50 | 无 |
| 本仓导入发布冲突（N-FE-032） | **200** | 无（超出静默截断） |

判断：**50 与业界同量级，保留**；**200 是「一次拉完 + 静默截断」，应改 50 + 加载更多**。理由不是「200 太大」，而是：

- 200 条明细会让响应体与渲染同时变大（问题条目含 message/字段名），首屏变慢；
- 「超 200 只显示前 200」是**静默数据丢失**，用户无法知道还有多少；
- 同一资源出现 50/200/后端默认三套页大小，后续改后端默认必漂。

### 5.2 表格写：三个阈值缺的是「吞吐」，不是「数字」

| 阈值 | 现值 | 作用 | 业界基线 |
|---|---|---|---|
| `SHEET_WRITE_SMALL_DIFF_MAX_CELLS`（N-FE-108） | 2000 格 | 判定「小改动/大改动」预览档 | 无统一标准（D）；同类产品多用「影响行数」或「整表替换」做档位 |
| `SHEET_WRITE_LARGE_ROW_THRESHOLD`（N-FE-109） | 200 行 | 超此要求勾选「我了解影响范围」 | 无统一标准（D） |
| `SHEET_WRITE_HARD_MAX_CELLS`（N-FE-111） | 100000 格 | 绝对拒绝 | 无统一标准（D），但必须 < 单次工具预算能写完的量 |

**必须先测的量**：SpreadJS 批量写吞吐 `cells/s`（含 `suspendPaint`、`resumePaint`、公式重算）。

- 若实测 20k cells/s：100000 格 ≈ 5s，硬上限安全，2000 格 ≈ 0.1s，确认框可以更激进（例如 5000 格）；
- 若实测 3k cells/s：100000 格 ≈ 33s，已吃掉 60s 工具预算的一半，硬上限应下调到 30000–50000 格；
- 2000 格 / 200 行的「小改动」档应以「预计耗时 ≤ 300ms」为判据反推，而不是拍一个格数。

**结论**：这两项不是「选个业界数字」，而是「测出吞吐后反推」。在测出来之前，**保留现值 + 注释写「待吞吐实测」**，不要凭感觉调。

## 6. 专题五：镜像缓存 120 条 / 512K 字符

| 项 | 现值 | 可算的约束 | 判断 |
|---|---|---|---|
| `MIRROR_MAX_MESSAGES`（N-FE-055） | 120 条 | 后端记忆窗口 40 条 | 120 = 3× 后端窗口，作为「刷新恢复」够用；但无算式 |
| `MIRROR_MAX_CHARS`（N-FE-056） | 524288 字符（UTF-16） | sessionStorage 5MiB/origin（S15） | 512K 字符 ≈ **1MiB 字节** ≈ **20% 配额**，量级合理 |

**两个必须补的算式**：

1. **配额余量**：`512K 字符 × 2 B = 1MiB`，占 5MiB 的 20%；剩余 4MiB 要容纳其他 sessionStorage 键（页签状态、草稿等）。建议注释写「≤ 25% 配额」，并在写入失败（`QuotaExceededError`）时降级为「只存最近 N 条」而不是整体失败（S15 明确要求 try/catch 处理配额异常）。
2. **末条例外**：当前「末条不受字符预算约束」意味着**单条超长消息可以把镜像顶到 1MiB 以上**。建议给末条也设上限（例如 64K 字符），超出则存摘要 + 标记「已截断」，避免一条消息击穿配额导致整个镜像写失败。

**与 40 条记忆窗口的关系**：镜像只服务「刷新/重挂恢复 UI」，不参与模型上下文；120 条不必等于 40。但应在注释里写清「120 = 3× 后端 40，仅为 UI 恢复；不进入模型上下文」，否则后续维护者会误以为要同步。
