## 3. 重点专项一：`list_config_defs` / `list_tasks` 20 → 100 是否合适

### 3.1 先固定事实（源码现值，不引用册内结论）

| 事实 | 位置 | 值 |
|---|---|---|
| 常量 | `ai/tools/AiTools.java:130` / `:244` | `LIST_CONFIG_DEFS_MAX_ROWS = 20` / `LIST_TASKS_MAX_ROWS = 20` |
| 截断方式 | `:178` / `:274` | `defs.stream().limit(常量)`、`tasks.stream().limit(常量)`；**无 offset/cursor 参数** |
| 告知文案 | `:141-142` / `:269` | 后缀由常量拼接（`" 个，仅显示前 " + 常量 + " 个"`）→ 改常量后后缀自动跟随 |
| `@Tool` 描述 | `:156` / `:274` | **字面量**「最多返回前 20 个」/「最多返回前 20 条」→ 必须手改 |
| 取数面 | `definitionService.findAll()` / `taskService.findAll()` | **改常量不改变 DB 读取量**（本来就是全量再截断），无 SQL 成本问题 |
| 单行最宽 | `V1__schema.sql`：`config_definitions.code 64 / name 128 / level 16`；`tasks.title VARCHAR(256)` | defs ≈ **215 字符/行**；tasks ≈ **325 字符/行** |
| 单行典型 | 同上（code≈10、name≈8、title≈10） | defs ≈ 40 / tasks ≈ 48 字符/行 |

### 3.2 三道闸的算式（这是「100 不合适」的全部理由）

下游闸门（按施加顺序）：`result-budget.model.max-rows 200` → `default-max-chars 20000` → SSE 单帧 `65536B` → `memory.token-budget 48000`。

| 闸 | 20 行（典型 / 最坏） | 100 行（典型 / 最坏） | 判定 |
|---|---|---|---|
| 行数 200 | 20 / 20 | 100 / 100 | ✅ 都过 |
| 字符 20000（defs） | 800 / 4,300 | 4,000 / **21,500** | ❌ 最坏越界 → 在约 **93 行**处被字符闸截断，而截断标记会**替换掉**「共 N 个」后缀 → `@Tool` 承诺的「超出时给出总数」变成假话 |
| 字符 20000（tasks） | 960 / 6,500 | 4,800 / **32,500** | ❌ 最坏在约 **61 行**处截断（同样丢总数） |
| 单帧 64KiB（tasks 最坏，CJK 3B/字） | 6,500×3 ≈ 19.5KB | 32,500×3 ≈ **97.5KB** | ❌ 触发 `FrameSizeLimiter` 分片/降采样 → 历史卡面与实时帧形态变化 |
| token（最坏 ÷1.7） | 3,824 | **11,765** | 单条占 48000 预算 **24.5%**、占可用窗口（128000−13000=115000）**10.2%** |
| 同轮 5 对工具结果（`keep-tool-pairs 5`） | 19,120（39%） | **58,825（>48,000）** | ❌ 预算装不下 5 对 → 每轮都必然触发 L1 清除/压缩 |

**结论**：100 在「典型值」下能跑（约 4–5k 字符），但在**最坏值下三道闸同时破**。而 `backend-ai.md` 给 20 写的注释恰恰是「必须 < 200，否则二次截断会先于本上限生效，告知就成了假话」——100 只是把「200 行」这道闸换成了「20000 字符」这道闸，同样的假话换了个位置。

### 3.3 业界对标：20 是「默认页」，100 是「页上限」，都不是「单轮全量」

| 系统 | 默认页 | 上限 | 形态 |
|---|---|---|---|
| GitHub REST [S5] | 30 | 100 | `per_page` + `link` 头翻页；超限静默降级 |
| Stripe [S6] | 10 | 100 | `limit` + `starting_after` 游标 |
| Claude Code（MCP 工具结果）[S4] | — | 25,000 token（10,000 token 起告警） | 按 token 截断，而不是按条数 |

也就是说：**20 对标的是「默认页」，100 对标的是「最大页」**。这两个数在一套**有翻页能力**的接口里可以并存（默认 20、上限 100）；在一套**没有翻页参数**的工具里，「100」等于「一次吐满 100 条且再也看不到第 101 条」——这是把「最大页」误当「默认页」用。GitHub/Stripe 之所以敢给 100，是因为有 `link`/`starting_after`；我们的 `list_*` 只有 `level` 过滤，没有翻页。

### 3.4 明确建议（三选一，按推荐度排序）

**方案 A（推荐）：常量 20 → 40，并给两个工具加可选 `limit`/`offset`（`limit` 上限 100、缺省 20）。**
- 40 = 2×20，最坏值下三闸全绿：defs 8,600 字符、tasks 13,000 字符（≈39KB < 64KiB）、5 对合计 38,235 < 48,000。
- 加 `limit`/`offset` 后，「要 100」的场景由模型显式翻页完成，且每页仍受 20000 字符约束；`@Tool` 描述由「最多返回前 20 个」改为「缺省 20、可用 limit 指定（最多 100）、用 offset 翻页，超出时给出总数」。
- 联动：`N-AI-205/206`（常量）、`N-AI-260`（2 处 `@Tool` 字面量 + 2 处后缀）、`AiToolsListTasksTruncationTest.SPEC_MAX_ROWS`（裁决侧锁值 = 20，必须同改）、`ListTasksHistoryProjectionTest`（断言 `endsWith("（共 21 条，仅显示前 20 条）")` 与 `hasSize(LIST_TASKS_MAX_ROWS)`，夹具要改成 41）。

**方案 B（仅改常量，不动协议）：20 → 40。**
- 最坏值仍全绿；`limit` 概念不存在，模型只能靠 `level` 过滤缩小面。
- 联动同上（2 常量 + 2 字面量 + 2 测试文件），但**不需要**改归档投影的解析逻辑。
- 这是「不想动协议」时的最大安全值。

**方案 C（要 100 的做法，成本最高）：先加行内截断，再改 100。**
- 两个工具的行渲染各自收口：`title` 截到 60 字符、`name` 截到 40、`code` 截到 64（已是列宽）。改后 tasks 单行 ≈ 130 字符 → 100 行 ≈ 13,000 字符 ≈ 39KB，三闸全绿。
- 代价：模型看到的是**被截断的标题**，而 `list_tasks` 的归档投影按行反解（`LIST_TASKS_ROW_PREFIX` / `STEP_TOKEN` / `STATUS_TOKEN`），截断位置若落在标记附近会破坏反解——必须先补投影测试。
- 另外必须把 `result-budget.model.per-tool` 给这两个工具显式设 ≥ 32,000（或保持 default 20000 并接受 tasks 最坏 61 行截断），否则「仅显示前 100」仍然是假话。

**不建议**：直接把两个常量改成 100 并同步 `@Tool` 字面量。它会在「定义名/任务标题较长」的租户上稳定产生「告知与事实不符」的结果，而这正是本册 2026-10-10 裁决②要消除的「谎报族」。

### 3.5 与 `max-rows=200` / `20000` 的关系（回答「是否要一起调」）

- `max-rows 200` **不要动**：它是「行数笼」，与字符档是**串联**关系；把 200 调到 300 只会让字符闸更早生效，问题不变。
- `default-max-chars 20000` **不要为 100 而上调**：20,000 字符 ≈ 11,765 token，已经接近 Claude Code 对 MCP 结果的 25,000 token 缺省 [S4]；再抬就撞上「一条工具结果吃掉四分之一个记忆预算」。
- 正确的做法是**在工具侧控制单行宽度**（方案 C），而不是放宽下游闸门。下游闸门是最后防线，不该为上游的展示需求让路。

## 4. 重点专项二：对话输入 8192 UTF-16 码元

### 4.1 事实与换算

| 项 | 值 | 说明 |
|---|---|---|
| 后端 | `app.ai.input.max-chars: 8192`，`AiController:376` 判 `text.length()` | UTF-16 码元；超限 **400 MESSAGE_TOO_LONG**，不截断 |
| 前端 | `AiPanel.vue:1816` `MESSAGE_MAX_CHARS = 8192` | `<textarea maxlength>` 同一把尺 |
| 字节 | 8192 汉字 = **24,576 B**（UTF-8 3B/字） | 若全为 ASCII 则 8,192 B |
| token | 8192 ÷ 1.7 ≈ **4,819** | 用本册 `CJK_CHARS_PER_TOKEN` |
| 占默认模型上下文 | 4,819 / 1,000,000 = **0.48%** | [S9] `deepseek-flash` 1M |
| 占本仓回退窗口 | 4,819 / 128,000 = **3.8%** | N-AI-010 |
| 占记忆预算 | 4,819 / 48,000 = **10.0%** | N-AI-008 |
| 占预留 | 4,819 / 13,000 = **37%** | N-AI-011 |

### 4.2 与业界比：8192 不是「模型输入上限」，而是「产品护栏」

| 对照物 | 数值 | 与本值的倍差 |
|---|---|---|
| Anthropic Messages 单请求体上限 [S3] | 128 MB | 24KB 是它的 **1/5,400** |
| OpenAI 旗舰上下文 [S8] | 1.05M token | 4,819 token 是 **0.46%** |
| DeepSeek `deepseek-flash` 上下文 / 最大输出 [S9] | 1M / 384K | 0.48% / 1.25% |
| 本仓「一句需求」的产品定位 [D] | — | 8192 汉字 ≈ 4 页 A4；正常需求 20–200 字 |

**结论**：主流 AI 产品**没有**公开的「单条消息字符上限」（它们用 token 预算兜），所以「8192 低于/高于主流」这个问法本身没有权威答案（〔无统一标准〕）。能确定的只有：**8192 远低于任何模型/协议上限**，它的作用是①阻止误粘贴整篇文档把单轮成本打满；②给限流一个可计算的成本上界（20 次/分 × 4,819 token = 96,380 token/分/会话的输入上界）。

### 4.3 是否要调？（明确建议：保留 8192）

- **不升**：升到 32,768 会让最坏单会话输入成本 ×4，而模型侧根本没有「装不下」的问题；真要贴长文，已有附件通道（`MAX_ATTACHMENT_BYTES 5MiB` / 总 20MiB，N-AI-222/223），语义也更正确（附件不进 `input.max-chars`，走另一条预算）。
- **不降**：降到 4,096 会切掉「贴一段 200 行日志 + 一句话问题」这个真实场景，而该场景恰好是排障类 Agent 的高频用法；且会与前端 4 档提示的档位设计冲突。
- **不改计量单位**：UTF-16 码元是**唯一**能让 `<textarea maxlength>` 与 `String.length()` 对齐的口径。改成「字符（码点）」会让 emoji（代理对）在前端算 1、后端算 2 或反之，出现「前端没到顶、后端 400」。这条比数值本身更重要。

### 4.4 「剩余字数提示」是否增加心智负担？（建议：减档，不减值）

现状 4 档（`AiPanel.vue:2302`）：常态灰「剩余 N 字」→ ≤500 琥珀 → 到顶「已达 8192 字上限」→ 超限标红。

- 对一个 8192 的预算，正常输入 20–200 字，常态显示「剩余 8000 字」**信息量为零**，属于纯噪音；且它会随每次按键变动，制造无意义的视觉抖动。
- 建议收到 **2 档**：**≤500 才出现**「剩余 N 字」（琥珀），**到顶**「已达上限」（灰，仍可发送）。超限档保留（程序化回填时才有用）。
- 这与主流对话产品的交互习惯一致（输入框上不常显剩余额度，只在接近硬限/超限时提示）。本文**没有**找到任何厂商公开的交互规范可引用，故此条是**产品判断**而非业界标准；可对照的是：真正需要「剩余额度」的是**上下文/成本**，那应该在会话级提示，而不是每条消息级。

### 5.1 三组「同值零余量」——该动前端，不该动后端

| 组 | 前端 | 后端 | 现在的后果 | 建议 |
|---|---|---|---|---|
| 首帧 | N-FE-009 **30s** | N-AI-025 `first-byte-timeout` **30s** | 同时判死：后端 30s 到点后还要**发错误帧**，前端已经在同一毫秒复位 loading → 用户看到「超时」而不是后端的结构化错误（`UPSTREAM_*`） | **后端留 30s**，前端改 **40s**（= 30 + 2 个 5s 心跳）。这样后端先判、先发帧、前端还能渲染错误语义；40s 仍远小于 nginx/ALB 的 60s 空闲断连 [S10][S11] |
| 作业帧 | N-FE-021 **90s** | N-BE-044×046 = 30×3 = **90s** | 前端恰好在本后端判死点放弃，拿不到 `FAILED` 终态帧，无法区分「后端判死」与「网络断」 | **后端留 90s**，前端改 **120s**（= 90 + 1 个 30s 判死周期） |
| 发布墙钟 | N-FE-024 **300s** | N-AI-028 `total-budget` **300s** | 段预算在**挂起/恢复时重置**，前端墙钟不重置 → 合法的长任务被前端先收摊 | **后端留 300s**（[S14] 裁决），前端改 **600s**，或改为「无硬墙，等终帧 + 显示已用时」。若坚持墙钟，必须写成 `600s = 2 × 段预算` 并注明「一次恢复」 |

为什么不反向改后端：三个后端值分别被 ①E2E 读窗（`verify-e2e.ps1` 手抄 300s）、②`zombie-age = max(exec, inter-event) + margin` 的 fail-fast 校验、③前端 4 个看门狗的派生关系锁住。改后端一处要动 3–4 处；改前端一处只动 1 个常量 + 1 个测试。

### 5.2 工具超时：值是对的，结构不对

| 项 | 现值 | 业界 | 判断 |
|---|---|---|---|
| `tool.exec-timeout` | 120s | Claude Code 前台 Bash 缺省 **120000ms**、模型可调到 **600000ms** [S4] | **值对齐主流**；缺的是「per-tool 覆盖」——`start_export` / `start_import` / `start_publish` / `start_precheck` 四个作业型工具与 `get_config_def` 共用 120s，长作业会被结算成 `TOOL_TIMEOUT/executed=false`，而副作用可能已发生（本册 P-3） |
| `hitl.frontend-tool-timeout` | 120s | Vercel/常见 5–60s（本册引） | 受「前端预算 = 120 − 回灌 POST 60s」锁死，单改会掐断已知成功路径（实测最慢成功回灌 30.6s）。**先改前端折算面，再降 90s**；否则保留 120s |

建议的形态：`app.ai.tool.exec-timeout` 保持 120s 作缺省，新增 `per-tool-timeout: {start_export: 300s, start_import: 300s, start_publish: 300s, start_precheck: 180s}`，并在 `SpToolCallingManager#executeWithTimeout` 取 `max(缺省, 覆盖)`。这比「全局抬到 300s」安全：只读工具仍然 120s 兜底。

### 5.3 上下文压缩：70/80/95 比业界「更早、更细」，但没有实测

- 业界形态：Anthropic 提供**服务端压缩**（compaction）+ **工具结果清除**（tool result clearing）两种策略 [S1]；Claude Code 的自动压缩阈值**只能调低不能调高**（说明缺省已贴近上限）[S4]。也就是说：业界主流是「贴近窗口上限才压」，本仓是「70% 清工具结果、80% 滑窗+摘要、95% 硬截断」——**更保守，成本更高（摘要调用更多），但更安全**。
- 结论：**三个百分比保留**（改小会频繁摘要、改大会失去 L1 的「无 LLM 成本」优势）；真正缺的是**一次并发压缩压测**：`summary pool 4 / queue 8`（N-AI-081/082）在 20 路挂起池同时触发 L2 时的排队与拒绝路径，以及 `summary-timeout 60s` 是否覆盖 `chunk-tokens 8000` 的最坏一次摘要。
- 一个容易忽略的自洽点：`max-tokens 8192` 后，L3 触发点 `95% × 115,000 = 109,250`，加满输出 `+8,192 = 117,442 ≤ 128,000` ✅。本册写的「L3 余额 5.75K > 4096」用的是**保护带**口径（5% × 115,000），不是模型窗口口径；**真正的硬约束是模型窗口**（`l3% × (limit − reserve) + max-tokens ≤ limit`，现余 10,558 token），保护带口径只是设计裕度。两个口径都要写清，否则下次换模型会把裕度当上限算。

## 9. 边界、假设与未验证项（如实登记）
