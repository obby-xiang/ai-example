### H-01 首轮驱动从不持有续跑租约，僵尸接管与死轮放行可造成同一轮双驱动

**严重度** 高（原评：高；机制置信度高、现场可达性中）｜**证据** 代码事实 + 条件性 ｜**来源** R1-F1

- **问题**：`chat()` / `driveResumed` 全程不取 `ai:lease:run:{run:<runId>}`，首轮所有持久化写入无 fence；另一实例按超龄判死后接管，两个驱动同时持有同一轮。
- **位置**：`backend/src/main/java/com/example/configmgr/ai/run/ResilientChatService.java:532`、`:754`（不取租）；取租点仅 `gate/ConfirmGate.java:609-611`；`run/RunStore.java:924`、`:960-976`（`heldRunEpoch==0` 走 plain `SET`）、`:1843-1846`（`permittedToWrite` 在 `epoch<=0` 直接 true）；`run/RunLiveness.java:42-62`；`run/StartupResumeRunner.java:313-325`、`:446-470`；`run/ResumeService.java:1288-1307`（僵尸分支不复核超龄）、`:1357-1371`；`session/SessionGate.java:213-231`（同 runId 视为接管）；`config/AiProperties.java:279-303`（合法静默基线不含预检）；`gate/SpToolCallingManager.java:664-691`（`preflight.inspect` 同步重活，仅 `markPassiveActivity`）。
- **触发**：首轮进入 `executeToolCalls`，预检（多文件 sha256/大文件）耗时 > `zombie-age`（出厂 180s），期间无业务帧、无租约、无 Redis 活动锚点；另一实例 `sweep()` 判死 → `resume(runId,true)` → 会话门"同 runId 接管"放行 → 交棒 `driveResumed`。
- **用户影响**：同一轮重复执行（重复模型费用、可能重复写操作）、两套 `tool_start/tool_result`、两条 `done`；快照 last-writer-wins（首轮 plain SET 可覆盖接管方的 `DONE`）；`convergeMemory` 整窗覆盖写双方都通过，后写者抹掉对方整轮工具历史；违反"恰好一个 done/error 且为最后一帧"。
- **最小修复方向**：`chat()` 建快照后立即 `acquireRunLease(runId)` + `markDriving`，让首轮与续跑共用同一套所有权；或新增 `ai:drive:<runId>` 由驱动线程续期、接管必须确认其已过期；`resumeInternal` 僵尸分支补一次 `activeAtMs` 复核；把预检纳入合法静默基线或给 `preflight.inspect` 加同源超时。

### H-02 终帧唯一性在失败出口不成立：快照已是 DONE/FAILED 时仍发 `error`

**严重度** 中高 ｜**证据** 代码事实 ｜**来源** R1-F2

- **问题**：`failLocked` 在快照为 DONE 时跳过写状态**但仍发 `error`**；快照为 FAILED 时重写并再发一条 `error`。`markDriveFailureLocked` 同理。
- **位置**：`run/ResilientChatService.java:2335-2350`（`failLocked`）、`:2116-2134`（`cancelTerminalLocked` 的幂等判据对照）、`:1647`（`emitUnconfirmedTerminal` 查归档）；`run/ResumeService.java:1729-1737`（`markDriveFailureLocked`）；`web/AiController.java:570-585`（见终态直接返回、不发帧——正确口径）。
- **触发**：任一"成功终帧之后发生的失败收尾"——H-01 的双驱动（一条成功、一条失败），或 `ResumeService` 驱动任务在收尾段抛异常（`ResumeService.java:1640-1647` 的 catch）。
- **用户影响**：归档出现 `done` 后又出现 `error`；重挂回放会把已成功的轮展示成失败；"终帧之后无业务帧"的前端不变量被破坏。
- **最小修复方向**：两处在 `RunSnapshot.isTerminal` 时统一先查 `out.terminalFrameArchived()`（TRUE 只记日志返回，null 按未归档继续，与取消侧同口径）；或收敛成 `SseChatEmitter` 内 `AtomicBoolean terminalSent` 的单一原子闸。
- **备注**：同一不变量在仓内有四处实现，仅两处带归档判据——这是结构性缺陷而非单点。

### H-03 会话销毁撞上"首轮建快照前"的轮次：报 `complete=true` 而该轮随后完整写入，且取消了用户自己的取消键

**严重度** 高 ｜**证据** 代码事实 ｜**来源** R2-N1

- **问题**：`/chat` 先取会话门再提交线程池；线程内 `store.create` 之前有一段"零 Redis 键"的请求前压缩窗口。此时 `DELETE /api/ai/session/{sid}` 把"门点名但快照缺失"的轮判为 inactive，删掉自己刚写的 `ai:cancel`，报告销毁完成，随后该轮正常跑完并保留全部数据。
- **位置**：`web/AiController.java:414`、`:466`；`exec/AiExecutorConfig.java:44-55`（队列 0 + AbortPolicy）；`run/ResilientChatService.java:601-649`（`compactBeforeRequest` 在 `store.create` 之前）；`session/AiSessionPurgeService.java:496`、`:562`、`:400`、`:733-752`、`:755-788`、`:795-798`（`snapshot==null` 一律降级 `active=false`）、`:1077-1080`、`:1097-1101`（`deleteObservabilityKeys` 删 `ai:cancel`）、`:1014-1017`。

- **用户影响**：用户点了销毁，服务端报成功，但其后仍生成并保留该轮完整回答（`/api/ai/events/{runId}` 可回放正文，`/runs/current` 可返回）；之前的取消信号被销毁流程自己删除；`complete` 字段说谎。

### M-28 条件草案的"逆映射"有损，而 `persistStepData` 每步都会用草案**重写**服务端条件 ⇒ AI 设的多值 `IN` 失效、同字段多条件被裁剪

- **位置**：`types/condition.ts:515-545`（`draftModelFromCondition`：`GTE+LTE → BETWEEN`，其余**只取 `list[0]`**）、`:499-507`（`draftValue`：数组 → 逗号串）、`:210-252`（`expandFields`）；`views/ExportWizardView.vue:539-547`（`loadTask` 用逆映射回填）、`:968-987`（`persistStepData`：草案非空就 PUT，不看是否有改动）、`:2184-2209`（`set_condition` handler 存逆映射草案、却 PUT 原始 condition）；后端口径 `data/service/ConditionEvaluator.java:107-116`（`IN` 仅值是 `List` 时逐项匹配，否则 `s.equals(expect)` 字面比较）。
- **触发**：① AI `set_condition` 传 `{operator:'IN', value:['USD','EUR']}` → handler PUT 数组（正确），草案里存成 `'USD,EUR'`；② 之后任一步骤推进（用户"下一步"或 AI `confirm_step`）→ `persistStepData` 用草案重建 → PUT `{IN, value:'USD,EUR'}` → 后端按字面比较 ⇒ 该条件永不命中（导出 0 行）。③ 同字段 >2 条条件（如 `GT100 + LT200 + NE150`）在 handler 写入时草案就只剩前者，推进后服务端被裁剪为区间条件。
