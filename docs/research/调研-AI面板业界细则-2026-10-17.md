## 第 4 轮 · 对话输入框（composer）

**结论**

1. **默认 1 行，随内容自适应**：四家 AI 产品空态均为单行条 / 单行卡（ChatGPT「Empty messaging bar」、Claude「Empty card」、Gemini「Empty pill bar」、Perplexity「Ask bar」），不存在"默认两行"的主流做法。
2. **可编辑态必须"看得见"**：容器化（圆角 + 边框 + 浅底 + 轻微层次）+ 合格对比度的 placeholder；**置灰低对比是 disabled 的语义**，不能用来表达"可编辑"。
3. **WCAG 把 disabled 排除在对比度要求之外**（inactive components exempt），这正是"置灰=看起来不能编辑"的制度性成因；而**仍可输入的控件不属于 inactive**，必须满足对比度。
4. **流式生成中变的是按钮，不是输入框**：发送钮原位变停止钮，输入框保持可编辑。
5. **工具栏惯例：左工具、右发送**；空输入时发送钮禁用但必须可见。

**关键来源**

- AI UX Playground 四家 composer 对比（空态形态 / 工具披露 / 语音位置）：https://aiuxplayground.com/teardowns/compare/design-the-composer
- AI UX Playground composer 设计指南（"A calm bar is not a barren bar"；工具出现时机；模型/成本控制必须在发送前）：https://aiuxplayground.com/guides/how-to-design-ai-chat-composer
- Material Design 3 文本域（只读态与常规态同样式、清晰标注）：https://m3.material.io/components/text-fields/guidelines
- WCAG 2.1 SC 1.4.3 / 1.4.11（inactive 组件豁免对比度）：https://www.w3.org/community/auto-wcag/wiki/1.4.html ；WCAG2ICT 对 inactive 的解释：https://kma.global/wp-content/uploads/2023/08/Guidance-on-Applying-WCAG-2.2-to-Non-Web-Information-and-Communications-Technologies-WCAG2ICT.pdf
- Carbon「Read-only states」：disabled 不被屏幕阅读器读取、且不过对比度，需要被读的内容必须用 read-only：https://www.carbondesignsystem.com/building-blocks/core/patterns/read-only-states

**对本项目口径**

- AiPanel composer：**1 行起步（40–44px）→ 随内容增高 → 到上限内滚**（上限见第 5 轮）；焦点在发送后保留。
- 可编辑态 = 有边框的容器 + 合格对比度 placeholder；**禁止**用灰底/降对比表达可编辑；disabled 仅用于无权限/会话失效/系统锁定，且必须给原因文案。
- 流式中：**输入框不禁用**，发送钮原位换停止钮；忙碌用 `aria-busy` 表达，不用 `disabled`。
- 工具栏：左 `+`（附件/工具/指令），右发送；至少一个工具入口常驻可见（不全部塞进 `+` 菜单）。

## 第 5 轮 · 输入框细则（17 条）

**结论**

- **上限行数**：无厂商公开数字，但实务落点是 **5 行左右**（"scroll bar after the 5 lines"），**8 行偏多**；推荐 **6 行（约 160–180px，或视口 30%）封顶后内滚**。
- **tooltip 是规范问题不是偏好**：图标按钮必须有**可访问名称**（WCAG 4.1.2，`aria-label` 或可见文本）；浮层必须满足 **WCAG 1.4.13**（可关闭 / 可悬停 / 持久）；**延迟落点 500ms**（GitLab Pajamas 明确值）；**不要用原生 `title` 充当 tooltip**。
- **停止钮**：与发送钮**同位同尺寸**，图标换**方块**；颜色用**品牌色/中性深色**（ChatGPT 黑、Claude 橙）；**红色留给"取消不可逆操作"**。12 个企业级 AI 系统研究中 **83% 在生成期把 Send 换 Stop，12 个里 10 个用方形图标**。
- **Enter**：Enter 发送 / Shift+Enter 换行是绝对主流；**中文 IME 组合期 Enter 绝不能发送**（判据 `isComposing || keyCode === 229`，Safari 需 composition 状态锁兜底）。
- **运行中 Enter**：Claude 已确认**排队**；ChatGPT 官方口径未找到。推荐排队 + "已排队 N 条" chip + 可取消。
- **长粘贴**：ChatGPT / Claude 均把超长粘贴转为附件 chip（`Pasted text.txt`），ChatGPT 另给 "Show in text field" 反悔项；副作用是自动附件会留在 Library（隐私提醒）。

**17 条细则表**

| # | 项目 | 细则 |
|---|---|---|

## 第 6 轮 · 卡片种类区分（工具卡 / 确认门 / 表单卡 / 已决回执）

**结论**

- **业界不靠"换配色"，而靠三重冗余**：**左色条/色带 + 卡头图标（形状）+ 文案（标题/状态词）**。WCAG 1.4.1 明确：颜色不得是唯一区分手段（约 1/12 男性有色觉障碍）。
- **企业卡片的既定语言**：Slack 的 `color` 就是**左边缘色条**，且只支持三档语义 **good / warning / danger**；飞书是**卡头 `template` 主题色 + 主/副标题 + 后缀标签 + 图标**；钉钉是**头部（图+文字+标签）/ 内容 / 操作 三段式**。
- **"需决策"应有结构性差异**，不只是颜色：NNG 原则"需要用户决策 → 打断（模态/对话框）"；WAI-ARIA 给出程序化区分：`role="alert"`（无需输入）vs `role="alertdialog"`（需要输入、焦点移入）。
- **已决态要"退场"**：去掉高饱和色条/阴影/按钮，只留 2px 状态色或中性，否则聊天流会累积一堆高亮卡。

**关键来源**

- Slack 左色条 + good/warning/danger：https://docs.slack.dev/tools/node-slack-sdk/reference/types/interfaces/MessageAttachment ；Block Kit 本身无法渲染左色条（只有 legacy attachments）：https://zudo-slack-wisdom.takazudomodular.com/docs/messaging/posting-and-block-kit/
- 飞书卡头（主题色 + 主/副标题 + 后缀标签 + 图标）：https://open.feishu.cn/document/common-capabilities/message-card/message-cards-content/card-header
- 钉钉三段式与状态变更：https://open.dingtalk.com/document/development/message-card-sending-and-updating
- M365 Adaptive Cards 卡解剖 + 渐进披露 + `View details` 用于摘要卡：https://learn.microsoft.com/en-us/agents/design-guidelines/adaptive-cards-for-agent-design
- NNG 模态原则：https://www.nngroup.com/articles/modal-nonmodal-dialog/
- ARIA `alert` vs `alertdialog`：https://pressbooks.library.torontomu.ca/wafd/open/download?type=pdf
- WCAG 1.4.1：https://www.w3.org/community/auto-wcag/wiki/1.4.html
- GOV.UK Tag 明文"不得只靠颜色"：https://design-system.service.gov.uk/components/tag/

**四通道方案（落地面）**

| 通道 | 左色条 | 卡头图标 | 标题/状态 | 边框/层次 | 动作区 |
|---|---|---|---|---|---|
| **A 工具卡（中性）** | 无 / 2px 中性灰 | 工具线性图标 | 陈述句 + 中性状态（执行中/已完成/失败） | 1px 描边、无阴影 | 仅"查看详情" |
| **B 确认门（需决策）** | 4px 琥珀；不可逆 → 红 | ⚠ 三角 | "待你批准：…" + 风险等级 | 边框加粗/浅底/抬升，可打断 | 批准 / 拒绝（+ 暂不，见修订注） |
| **C 表单卡（需填写）** | 4px 品牌蓝 | 编辑/清单图标 | "请填写…（N 项必填）" | 1px 品牌描边 + 浅底 | 提交 / 取消 |
| **D 已决回执** | 2px 状态色（绿/灰/红） | 结果图标 ✓/✗/⏱ | 过去式结论 | 无边框/极浅底，退后 | 仅"查看详情" |

- 色弱友好：**琥珀与红必须叠加图标差异**（⚠ vs ⛔）或文案差异；不可逆可加双线/斜纹左条用"形状"承载语义。
- 程序化：A 普通区域；B `role="alertdialog"` + 焦点移入；C `role="form"`；D `role="status"`。

**对本项目口径**

- 现网三类卡"卡头完全一样"是**放弃了最强的区分位**；按上表补：**卡头图标 + 左色条 + 标题动词化 + 状态 chip**。
- **两族徽标**（HITL 系 / 表单系）以 2026-10-17 裁决为准，四通道只负责"视觉频道"，不另造词表。
- 已决回执必须"退场"（去高饱和、去按钮），与 `裁决-回执原卡只读态-2026-10-15.md` 的"原卡只读态"同向。

## 第 7 轮 · 窄栏侧边面板（copilot side panel）

**结论**

- **宽度地板是 360px**：Chrome 侧栏最小宽度在 Chromium 中**硬编码 360px**，且不随窗口自适应，只能手动拖；VS Code 侧栏默认约 **251px**，并在 **≤300px 触发 narrow 模式**（隐藏次要信息）。
- **窄栏卡片的官方铁律（M365）**：inline 卡**不许内部滚动、不许 tab/分页/筛选、动作 ≤2、无多级分组**，高度要"widget-sized 而非 application-sized"；放不下 → **升级 side-by-side**；**不要默认升级**（progressive escalation）。
- **面板级能力**：可拖宽、可收起、可换侧/移到更大视图、**记住宽度与开合**；右栏的定位是"deep-context expert"，但**存在感弱**是公认局限，需要与主工作区联动来补。
- **窄栏 composer 上限应小于全屏**（全屏 5–6 行 → 窄栏 3–4 行），且 composer 应**贴底停靠不浮动**。

**关键来源**

- VS Code 侧栏默认 ~251px、≤300px narrow：https://github.com/microsoft/vscode/issues/118511
- Cursor 最小宽度被调大引发反弹：https://forum.cursor.com/t/allow-configurable-minimum-width-for-the-right-sidebar/156036
- M365 窄面卡片铁律与渐进升级：https://learn.microsoft.com/en-us/microsoft-365/copilot/extensibility/plugin-mcp-apps-ui-guidelines
- M365 卡片内边距 24px：同上
- 右栏定位与局限：https://uxdesign.cc/where-should-ai-sit-in-your-ui-1710a258390e
- 侧栏 vs 主区的分工批评：https://www.theskinsfactory.com/uiux-design-blog/ai-copilot-ux-design
- 任务越重越需要屏幕面积（全屏 / 侧栏 / 半宽三档）：https://uxforai.com/p/ux-best-practices-copilot-design
- Material 3 supporting pane：https://m3.material.io/foundations/adaptive-design/canonical-layouts

**对本项目口径**

- 380–420px 保持；**可拖拽 320–560**，**记住宽度/开合/滚动位置**；**≤340px 进入 narrow**（隐藏次要元数据、卡内边距 16→12）。
- 卡内**绝不内滚长表**：表格只给主标识列 + 2–3 关键列 + "共 N 行"；**>5 字段或需要复杂表格 → 分步或"在面板内展开 / 在主工作区打开"**。
- 卡片内边距 12–16px（M365 的 24px 是为更宽 surface）；正文 13–14px、行高 1.5。
- 与主区联动为必补项：AI 提到的记录/配置项要能在左侧定位并高亮（同时缓解"存在感弱"与"所见即所批"）。

## 第 11 轮 · 一次多问的分层（队列 / 一屏 / 逐题 / 分步）

**结论**

- **不存在单一"多问形态"，业界按层级分工**：
  1. **多个独立待办** → **队列逐条**（Agent Inbox 的 inbox 列表）；
  2. **单个中断内的多个 action** → **一屏并列多卡 + 汇总提交**（LangChain 官方 `MultiActionReview` + "Submit All Decisions"）；
  3. **多个字段同属一次输入** → **一屏 + 一次提交**（Adaptive Cards 的 `isRequired` 未过不发、飞书 `form` 容器一次提交）；
  4. **对话式代理的多个问题** → **逐题**（Copilot Studio 一个问题节点只收一个变量）；
  5. **字段间有依赖** → **必须分步**（NNG 对 wizard 的定义："后续步骤可能依赖前一步的输入"）。
- **Typeform 数据要打折**：官方 2023《Data on Data》（2.6M 表单 / 568M 提交）称平均完成率 **47.3%** vs 行业 **~21.5%**，Clay 案例 +70% —— 但这是**厂商口径**；第三方结论是"会话式只在**短表单**上提升，多步对短表单反而更差"。
- **Baymard** 的结论更实用：**别纠结步数，去减字段**（平均站点 32 个字段，整改最多 +35% 转化），并**把已完成的步骤折叠成摘要**。
- **CopilotKit 的中间态最值得抄**：`interrupts[]` 列成一屏，**逐个 resolve/cancel，全部处理完才恢复运行**。

## 第 12 轮 · 选择型问题（单选 / 多选 / 其它 / 溢出）

**结论**

- **数量—形态阈值**（多来源收敛）：**≤5 项 → radio / 列表（NNG 明确"小集合不要用下拉"）**；**6–15 → 下拉**（ServiceNow 官方：radio <7、dropdown >7 且 <15）；**>10 且用户已知答案 → 可搜索下拉**。2–5 项是灰区，Sabre 一类规范更严（>3 就建议下拉）。
- **聊天/AI 面用 chips（quick replies）**：Copilot Studio 的 Question 节点支持 quick replies，**web 端实测只显示 3 个**；聊天平台 LivePerson 支持 1–24 个 chips。
- **「其它」= 末位选项 + 选中就地展开文本框**（不是跳下一题）；值是**双字段**（"Other" 标记 + 自由文本），Typeform 把 Other 当独立字段、Google Forms 则扁平化成逗号串（后者被公认要额外清洗）。
- **多选在窄栏的标准解法**：**chips + 「+N」溢出计数**（Ant Design `maxTagCount: responsive`；组件文档："`maxTagCount` decides when the chips collapse into a '+N' counter, which keeps a multi-select from growing taller than the field"）；选项多再加搜索框。
- **表单过长的四条出路**：M365 = **升级更大容器（side-by-side）**；Typeform = **一问一屏**；Baymard = **减字段 + 已完成折叠**；SAP Fiori = **没有向导 floorplan**（多步需 freestyle 自建）。

## 第 13 轮 · 多选 + 「其它」混着提交

**结论**

- **成立且是主流**：Google Forms 的复选框可勾 A、B 再勾「其它」填文本，结果里**选项与其它文本都保留**（导出为逗号分隔，需二次清洗）；Typeform 多选返回 `choices.labels` 数组，**Other 以字面量 `"Other"` 标记**，自填文本以独立键返回（集成方必须单独映射 `other`，否则漏数据）。
- **企业先例**：SharePoint 选择列支持 "Allow fill-in choices"（固定选项 + 手动填写）；**飞书/钉钉/Slack 的组件层是预定义选项，未找到终端用户自填支持**（需自行拼"其它 + 输入框"）。
- **框架先例**：Ant Design `Select mode="tags"` 明确允许"输入自定义值并显示为标签"，是选项 + 自由输入混排的正解。
- **校验**：勾了「其它」即视为该题已作答，**文本为空则未完成**；问题必填时文本随之必填。
- **回显**：选项用 chip 标签、**其它文本单独一行**（并标注"其它"），不要拼成一条字符串（Google Forms 的扁平化正是被诟病的点）。

- Google Forms 复选框 + Other 的响应行为（选项与其它文本都保留、逗号分隔）：https://fomr.io/help/features/components/checkboxes ；清洗痛点：https://doc2form.dev/blog/single-vs-multiple-choice-google-forms/
- Typeform Responses API 结构（`choices.labels` / 单选用 `choice.label`；示例里 Other 的 label 即 "Other"）：https://www.typeform.com/developers/responses/JSON-response-explanation/
- 集成侧需单独映射 other：https://community.zapier.com/how-do-i-3/typeform-trigger-responses-with-other-content-and-filtering-action-for-certain-responses-10293 、https://community.n8n.io/t/typeform-how-to-parse-other-answers/13854

**对本项目口径**

- H2 多选允许"若干选项 + 其它文本"混合提交；**数据结构固定为 `{ selected: ["optA","optB"], other: "自定义文本" }`**，保留"哪项是 Other"的元信息。

## 第 14 轮 · 多步跳过、异构组合与终了 review

**结论**

- **跳过必须显式，且不可与"完成"混同**：可选步骤显示 **Skip（与 Next 并列）**，步骤指示器标 **skipped（灰 ↷）而非 complete**，**必填步骤永不显示 Skip**；企业审批确有"跳过审批人"——ServiceNow 置 **"No Longer Required"** 时活动结果为 **`skipped`（不是 `not_required`）**，SAP Concur/Harness/DigiCert 也都有条件跳过。
- **审计口径**：**skipped 是被记录的决策/状态，不是"未发生"**（ServiceNow 有独立结果值）。
- **异构组合是协议级支持**：LangGraph 一个 interrupt 可含多个不同 action 的 `actionRequest`，且 `reviewConfigs` **按 action 逐个**配 `allowedDecisions`；CopilotKit 的 `interrupts[]` 亦然；LangChain 自定义表单允许 select/checkbox/textarea/currency 混排。**"批准/拒绝必须独立成步"的明确论述未找到**——业界倾向"每张决策卡各自声明动作集"。
- **终了 review 页是标准配置，且是附加层**：PatternFly 的向导最后一步可为 Review/Summary；Baymard 要求 review 页"只汇总已知事实、不得引入新费用/新信息、必须可 skim"；**步骤级"已完成折叠为摘要"与最终 review 页两层并存**，不是用最终摘要替代逐步只读卡。

**对本项目口径**

- **跳过**：按裁决**不设步骤级 Skip**；可选性下沉到字段级（选项给"不限制"、字段允许留空）。若未来恢复步骤级跳过，必须落 `status: "skipped" + actor + at + reason`，且指示器与"已完成"分色分形。

## 第 15 轮 · 三类型卡片 × 状态（tool / HITL / form）

**结论**

1. **单行折叠卡头是共同形态**：VS Code 官方文档明写「tool call details are collapsed by default…selecting the tool summary line」；AI Elements 的 `Tool` 是「collapsible component」，由 `ToolHeader`（工具名 + 状态 Badge）+ `ToolContent` 组成；assistant-ui 的 `ToolFallback` 自述为「a collapsed one-line summary」。三家都把「一次调用 = 一行摘要，点开看参数 / 结果」作为默认。
2. **状态是有限枚举，不是自由文案**：AI Elements `getStatusBadge` 列七态（Pending / Running / Awaiting Approval / Responded / Completed / Error / Denied）；assistant-ui 的 `status.type` 为 `running` / `complete` / `incomplete`（带 reason，如 cancelled）/ `requires-action`；CopilotKit 的 `useHumanInTheLoop` 内置 `InProgress → Executing → Complete` 三态机。**等待人工 = 独立状态**，与执行中分开。
3. **类型 / 工具标识与状态是两个正交槽位**：assistant-ui 的 trigger 是「状态图标（spinner / check / X-circle / alert）+ `Running tool: <name>` 等动作词 + 耗时 + 右侧 chevron」；AI Elements 是「工具名 + 状态 Badge」；VS Code 是整行摘要可点。三家都把状态放在卡头的**独立槽位**（图标 / Badge / 文字），不与工具名混写。但**左右次序各家不同**：状态图标在行首（assistant-ui）、在工具名之后（AI Elements）。故「左类型图标 · 右状态标签」是本项目落点，不是业界统一排布；业界可借用的是「两通道分离」这一原则。
4. **审批 / 打断是同一张卡的另一种状态**：assistant-ui 的 `requires-action` 默认展开，卡内给 Allow / Deny，结算后原位换过去式 receipt，且明确「滚动回看不会出现已决策的活按钮」；CopilotKit `useInterrupt` 以 `RUN_FINISHED{outcome.interrupts}` 挂起，`resolve` / `cancel` 逐条记录，**全部处理完才恢复 run**；AI Elements 把 `approval-requested` / `approval-responded` 直接作为状态枚举。⇒ 不需要为「待决策」另起一种卡型。
5. **已决态必须过去式、只读、零活按钮**：receipt 文案（Allowed / Denied / Expired before a decision）与历史回放不重新暴露操作；与本项目 2A 批「已决原卡只读」同向。

- AI Elements `Tool`（`ToolHeader` / `ToolContent` / `getStatusBadge` 七态）：https://elements.ai-sdk.dev/components/tool
- assistant-ui `ToolFallback`（单行摘要 + 四态 + `requires-action` 默认展开 + 结算 receipt）：https://www.assistant-ui.com/elements/tool-fallback
- CopilotKit `useInterrupt`（标准 interrupt 流、逐条 resolve / cancel、全员处理完才恢复）：https://docs.copilotkit.ai/human-in-the-loop/useInterrupt
- 本仓 `调研-CopilotKit-HITL实现-2026-10-17.md`（`inProgress` / `executing` / `complete` 三态机与刷新恢复的源码取证）
