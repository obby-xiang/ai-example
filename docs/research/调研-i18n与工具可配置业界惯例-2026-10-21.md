## 2. 五问结论

### Q1 前端 i18n（vue-i18n v10/v11）

1. **版本与 API 形态**：直接用 v11，Composition API 模式（`createI18n({ legacy: false })`）。v11 已弃用 Legacy API（v12 移除）、移除 `tc/$tc`、弃用 `v-t`；新代码不应再写 Options API 风格。v9/v10 已 EOL。
2. **消息目录组织**：两种主流：① 单文件 `locales/zh-CN.json`、`en-US.json`（小项目足够）；② 按业务域/路由拆 namespace（`common.json`、`chat.json`、`tool.json`），运行时按 namespace 合并。键用点分层级、语义化（`tool.web_search.title`），不要用中文当 key。规模上来后再拆，不要一开始过度设计。
3. **懒加载**：官方模式是 `loadLocaleMessages(i18n, locale)`：`await import('./locales/${locale}.json')` → `setLocaleMessage` → `nextTick()`；在路由守卫或语言切换处调用，并记录已加载 locale 避免重复。首屏只加载当前语言，其余按需。
4. **插值 / 复数 / ICU**：vue-i18n 是自有消息格式——`{name}` 命名插值、`{0}` 列表插值、竖线分隔复数、`@:key` 链接、`@.lower:` 修饰符；**默认不是 ICU MessageFormat**。中英双语用竖线复数 + 命名插值足够（中文无复数变化，写单数分支即可）；只有斯拉夫/阿拉伯等复杂复数或需要和 ICU 生态（翻译平台、TM）互通时才引入 `messageCompiler` 替换或 `@formatjs/intl` 处理数字/日期。
5. **Element Plus 接入**：`<el-config-provider :locale="elLocale">` 包住根组件（或 `app.use(ElementPlus,{locale})`），`elLocale` 用 `computed` 从 Pinia 的 locale 派生（`zhCn`/`en` 从 `element-plus/es/locale/lang/*` 静态导入即可，体积很小）；**别忘了 Day.js**：`import 'dayjs/locale/zh-cn'` 并在切换时 `dayjs.locale(...)`，否则 DatePicker 仍是英文月份。
6. **切换持久化与后端联动**：推荐优先级 **用户偏好（后端 profile）> localStorage > navigator.language > 默认 zh-CN**；切换语言时同时做四件事：`i18n.global.locale.value = x`、`document.documentElement.lang = x`、`localStorage` 落盘、axios/fetch 拦截器设置 `Accept-Language`（或显式的 `X-Lang`）。未登录用户只走 localStorage + navigator；登录后用后端偏好覆盖并回写 localStorage。**Accept-Language 与用户偏好冲突时，以用户显式偏好为准**（Accept-Language 是“我接受什么语言”，不是“我要什么语言”）；后端只在没有用户偏好时用它做协商。纯 SPA 可略 `storage` 事件同步；多标签页场景再加。
7. **Pinia 形态**：`useLocaleStore` 持 `locale`、`availableLocales`、`loadedLocales`，action `setLocale()` 内做持久化 + 副作用（html lang / dayjs / header），组件不直接改 `i18n.global.locale`，避免状态双源。

### Q2 后端 i18n（Spring）

1. **主流用法**：`spring.messages.basename=messages`、`spring.messages.encoding=UTF-8`；`AcceptHeaderLocaleResolver` + `setDefaultLocale` + `setSupportedLocales`（REST 无状态，优于 Cookie/Session resolver）；`MessageSource.getMessage(code, args, LocaleContextHolder.getLocale())`；`@Valid` 直接 `message="{user.name.required}"`，Spring 会把 `MessageSource` 注入 `LocalValidatorFactoryBean`。
2. **fallback 链**：`messages_zh_CN` → `messages_zh` → `messages`（默认文件）。所以**只提供 `messages_zh.properties` 与 `messages_en.properties`**，区域变体自然回落，不要为 `zh-CN/zh-TW/zh-HK` 各建一份。默认文件建议写英文（或中文，但必须显式 `setDefaultLocale` 对齐），避免“缺 key 时把 key 本身返回”暴露给用户。
3. **错误码 + 消息键 vs 直接多语言文案**：**两者都要，但职责分离**——响应里必须有稳定、语言无关的 `code`（如 `TOOL_NOT_FOUND`、`VALIDATION_FAILED`，配 `args`/`field`），`message/detail` 只是“给人看的兜底”。前端如果自己有该 code 的翻译就用前端文案（体验最好、可离线、可改文案不发版），没有才展示后端返回的本地化 message。**不要只返回本地化字符串**：调用方无法稳定分支，日志/告警也无法聚合。
4. **API 错误响应惯例**：RFC 9457 ProblemDetail（`application/problem+json`）是当前标准形态：`type`（稳定的问题类型 URI/码）、`title`、`status`、`detail`、`instance`，可加扩展成员（`code`、`args`、`traceId`、`fieldErrors`）。Spring 6/Boot 3 原生支持（`spring.mvc.problemdetails.enabled=true`），`ResponseEntityExceptionHandler` 路径可用 `getDetailMessageArguments()` 让 `title/detail` 从 messages 解析；自定义异常用 `@RestControllerAdvice` 统一组装。`code` 放扩展成员或 `type`，**不要**把 code 拼进 detail 文本。
5. **Accept-Language 解析**：`AcceptHeaderLocaleResolver` 已处理 q 值；但 **`LocaleContextHolder` 是 ThreadLocal**——异步/线程池/`@Async`/WebFlux 场景会丢失，需要显式把 locale 传进服务层，或在任务装饰器里 `LocaleContextHolder.setLocale()`。这是一个常见坑。
6. **何时不做服务端翻译**：如果产品只有自己的 Web 前端、且前端有全量文案，后端可以只返回 code + args，由前端翻译（更符合“错误码优先”）。但只要有第三方 API 消费者、邮件/通知、审计日志，就必须有服务端 `messages` 兜底。**结论：code 必做，服务端 messages 作为兜底保留**。

### Q3 工具可配置化（name / description / 参数说明）

1. **三种来源的形态与适用面**
   - **编译期注解**（Spring AI `@Tool(description=...)`/`@ToolParam`，LangChain4j `@Tool`/`@P`）：最省事，适合“工具集稳定、文案由工程师维护、改动随代码发布”。**硬限制：Java 注解元素必须是编译期常量**（JLS 9.7.1；Baeldung 的注解属性限制总结），因此注解里的字符串**不可能**来自 DB、i18n bundle 或配置中心，也无法热更。
   - **配置文件 / DB（外置元数据 + 代码内实现绑定）**：Spring AI 的 `MethodToolCallback` + `ToolDefinitions.builder(method).description(...)` 明确用于“运行期构建工具定义”；LangChain4j 的 `ToolSpecification.builder()...` 且支持 `toJson()/fromJson()`，配合自定义 `ToolExecutor`，可以把“定义”和“执行”彻底解耦。适合“文案/参数说明需要产品、运营或领域专家改；需要按租户/环境差异化；需要留痕与回滚”。
   - **Prompt 管理平台（Langfuse / LangSmith / PromptLayer 的 registry 模式）**：不可变版本 + 标签（production/staging/tenant/实验）+ 按标签取用 + 移标签即发布/回滚 + 版本 diff + 与 trace 关联。适合“prompt 迭代频繁、非工程角色参与、需要 A/B 与效果归因”。**注意它不是给 Java 工具做绑定的**，工程上通常只借它的“版本 + 标签 + 指针”模型，不一定要引入 SaaS。
2. **运行时改工具描述对模型行为的影响**：工具描述本身就是 prompt，改它等价于改 prompt——会改变工具选择与参数填充；同时**会击穿 prompt 缓存**（Anthropic 的哈希顺序是 tools → system → messages，改任一工具定义整段前缀失效；Pydantic AI 的实测也是“改一个工具描述，整段前缀重建”）。所以“运行时可改”必须配**发布节奏**：草稿 → 评测 → 发布（标签/指针）→ 可回滚；不建议“保存即生效”地面向所有流量。是否需要灰度：**工具数量多、调用量大、或描述改动会影响关键路径时，需要**（按租户/用户百分比挂不同版本指针）；小工具集可以只做“发布 + 回滚”两态。
3. **MCP 的 `tools/list` 动态发现是不是“工具外置”的业界答案**：**是“工具外置”的协议层答案，但不是“文案可配置”的全部答案**。MCP 把工具变成运行时可发现的外部能力（`tools/list` + `listChanged` + `tools/call`），并原生区分 `name`（机器标识）、`title`（人可读展示名）、`description`（给模型）、`inputSchema`（JSON Schema）、`annotations`（只读/破坏性等提示）。它解决“工具从哪来、有哪些、结构是什么”，不解决“谁来编辑 description、如何审校/回滚/多语言”——后者仍是 registry/发布流程的事。对本项目：**不必为了可配置而先上 MCP**；但应借鉴它的字段分离（尤其 `title` vs `description`）与 `listChanged` 的变更通知语义。
4. **一个常被忽略的点**：工具数量增长后，业界已经从“全量塞给模型”转向**渐进披露**（Spring AI 的 `ToolSearchToolCallingAdvisor`、Anthropic 的 tool search）。这反过来说明：工具定义应当是“可检索的元数据”，而不是散落在注解里的字符串——外置是规模化的前提。

### Q4 工具文案的 i18n

1. **给模型看的 description 用哪种语言**：业界的**事实标准是英文单语、语言无关**。依据：
   - 实践指引直接写明“Write tool descriptions in English regardless of the languages you support”（AssemblyAI 多语言语音 agent 指南）。
   - 实证：阿拉伯语提问下工具调用准确率下降 5–10%，**无论工具描述是阿语还是英语**（arXiv 2601.05101）——把描述翻译成用户语言并不能修复语言带来的性能损失。
   - 实证：多语言工具调用的主要失败模式是**参数值语言不匹配**（模型把用户语言写进参数值），而工具接口本身是语言不变的；提示“参数用英文”能缓解但不能追平英文（MLCL，arXiv 2601.05366）。注意该实验**只翻译了用户 query，没有翻译工具描述**，所以它证明的是“接口保持语言不变 + 输出语言由 system prompt 控制”这条路线，而不是“翻译描述更好/更差”。
   - 成本：多语言描述会让“同一工具”产生多份不同的 prompt 前缀，直接放大缓存失效与评测矩阵（每种语言 × 每个版本都要评）。
2. **结论**：**模型侧 description / 参数说明只保留英文一份**；不要按用户语言切换工具描述。用户语言的影响放在 system prompt 的“respond in the user's language”与前端展示层解决。若模型对某语言明显更差，正确做法是换模型/加 few-shot/加语言指令，而不是翻译工具 schema。
3. **“用户可见的工具展示文案”与“模型可见的工具描述”必须分离**——这是有协议级背书的惯例：MCP 在 2025-06-18 引入 `title`（human-readable display name，与机器名分离），展示优先级 `title` → `annotations.title` → 由 `name` 派生；`description` 仍是给模型的。工程上等价做法：
   - 模型侧：`name`（英文 snake_case，稳定）+ `description`（英文）+ `inputSchema` 的 `description`（英文）。
   - 用户侧：`title`/`summary`/图标/分组 → 前端 i18n key（如 `tool.web_search.title`），按 `tool_key` 关联；**不要把展示文案塞进工具定义表的多语言列**。
   - 运行时事件（tool call 卡片、审批弹窗）只传 `tool_key` + 结构化参数，前端用 i18n 渲染；缺失时回退到后端 `title` 或 `name`。

### Q5 对本项目的建议（含裁决）

#### 5.1 裁决：注解 vs 外置

**“工具不应该做成注解”这个判断方向正确，但需要精确化：不是“注解无用”，而是“注解不能作为可编辑文案的唯一来源”。**

裁决建议（一句话）：**注解保留为“实现绑定 + 缺省元数据”，name/description/参数说明外置到版本化的工具注册表，运行时装配 `ToolSpecification`/`MethodToolCallback` —— 即“注解做默认、外置做覆盖”的混合模式；模型侧文案只保留英文一份，用户侧展示文案走前端 i18n。**

理由（按重要性）：
1. **语言机制决定注解做不到**：注解值必须是编译期常量，无法读 DB/MessageSource/配置中心，也无法热更（JLS 9.7.1；Baeldung）。
2. **变更节奏不匹配**：工具描述是 prompt，按 Anthropic 的经验需要“评测驱动地反复改”，改一次要跑 eval；这跟 Java 代码的发版节奏（编译、测试、部署）冲突。外置 + 发布指针能把“改文案”从“发版”降级为“发布一个版本”。
3. **框架已经给了官方出口**：Spring AI 明确提供 `MethodToolCallback`（runtime 构建）+ `ToolCallback` bean + `ToolDefinition.description()` 覆盖；LangChain4j 的 `ToolSpecification` 可 `toJson/fromJson`。这不是“绕过框架”，而是框架设计的第二条路。
4. **协议层已把“展示名”和“模型描述”拆开**：MCP 的 `title` vs `description` 说明业界认为这两类文案的生命周期和受众不同，不该焊死在一个注解里。
5. **注解仍有价值**：它是“这个方法是一个工具”的强类型标记，编译期可检查、IDE 可跳转、AOT 友好；完全废掉会让绑定关系退化成字符串反射，反而更脆。

#### 5.2 推荐形态（分阶段，不锁死）

**抽象先行**：定义 `ToolDefinitionSource` 接口，暴露 `List<ToolDefinition> load()` 与 `version()`；实现可替换：
- **阶段 A（推荐起步）：classpath YAML/JSON + 版本号 + 启动加载 + 受控 reload**。适合单租户、工具数 < 20、改动由工程师发起。工具定义文件进 Git，天然有 diff/评审/回滚；`@Tool` 只留作“缺省值 + 绑定声明”，YAML 里同 `tool_key` 的条目覆盖注解。
- **阶段 B（有运营/租户需求时）：DB 版本表 + 发布指针**。借鉴 Langfuse：**行是不可变版本**，另用一张“指针/标签”表决定当前生效版本；发布 = 移动指针，回滚 = 把指针移回旧版本；`draft` 版本可预览不可用。
- **不建议**：把 description 直接做成“保存即生效”的可编辑字段——会同时击穿缓存与评测基线，且没有回滚。

**表结构草案（阶段 B）**：

```
ai_tool_def(
  id, tool_key,            -- 稳定标识，永不变，如 doc.search
  version,                 -- 自增/语义版本
  model_name,              -- 模型侧 name（英文 snake_case）
  description_en,          -- 模型侧 description（英文，唯一语言）
  input_schema_json,       -- JSON Schema，property 的 description 也在此
  title_key,               -- 仅 UI 用：i18n key，如 tool.doc_search.title
  impl_ref,                -- 绑定：bean 名 + 方法签名（或由代码侧 registry 反查）
  status,                  -- draft / published / archived
  eval_ref, change_note, created_by, created_at,
  unique(tool_key, version)
)
ai_tool_release(tool_key, label, version, updated_by, updated_at)  -- label: production / staging / tenant-x
```

运行时：启动加载 `production` 指针 → 构建 `ToolSpecification`（LangChain4j）或 `MethodToolCallback`（Spring AI）→ 按 `tool_key` 绑定到 Java 方法（代码侧维护 `Map<tool_key, ToolInvoker>`，由注解扫描或显式注册填充）→ 内存快照，请求路径零 DB 读；变更走事件/短轮询刷新快照。发布前校验：JSON Schema 合法、`tool_key` 不可变、必填参数未删、`model_name` 唯一、描述长度上限。

**混合模式是否有先例**：有。Spring AI 的 `@Tool` 是默认，`ToolDefinitions.builder(method).description(...)` 在运行期覆盖；MCP 的 `title` 有 `title → annotations.title → name` 的回落链；LangChain4j 同时支持注解与 `ToolSpecification`，且 `ToolSpecification` 可反序列化。**“默认来自代码、覆盖来自外部、按 key 合并”是成熟框架的通用做法**，不是自创。

#### 5.3 工具文案归哪一侧

- **模型侧（英文 description / 参数说明）→ 后端工具注册表**。不进前端 i18n，不做多语言，不随用户语言切换。
- **用户侧（工具名、卡片标题、审批弹窗、参数标签）→ 前端 i18n**，key 与后端 `tool_key` 对齐：`tool.<tool_key>.title`、`tool.<tool_key>.param.<paramName>`。后端事件只传 `tool_key` + 原始参数 + 可选 `title_key`。
- **参数枚举值的展示**：模型侧用英文枚举（`CELSIUS`/`FAHRENHEIT`），前端用 `tool.<tool_key>.enum.<value>` 映射为“摄氏/华氏”，**不要**把中文枚举值塞进 JSON Schema 的 `enum`。

#### 5.4 i18n 落地顺序（推荐）

1. **先做“契约”，再做“翻译”**：第一步把后端错误响应统一成 `code + args + traceId`（ProblemDetail 扩展成员），前端先按 code 显示中文兜底。这一步不改任何文案，但决定了后面所有 i18n 的边界。
2. **前端先行**（第 1 周）：`createI18n({legacy:false})` + `useI18n` + Pinia `localeStore` + `ElConfigProvider` + Day.js + 持久化 + `Accept-Language` 拦截器 + `html lang`。用户可见收益最快，且不依赖后端。
3. **后端 messages 跟上**（第 1–2 周）：`messages_zh.properties` / `messages_en.properties` + `AcceptHeaderLocaleResolver` + `@RestControllerAdvice` 统一从 code 解析 message；`@Valid` 用 `{key}`；补 `LocaleContextHolder` 在线程池场景的传递。
4. **工具注册表外置**（第 2 周起，可与 3 并行）：先抽象 `ToolDefinitionSource` + YAML 实现，把现有注解文案迁进去（脚本抽取 `@Tool.description` 生成初版 YAML），保持行为不变；再加版本/发布指针。
5. **工具 UI 文案接入前端 i18n**（最后）：`tool_key` 稳定后再补 `tool.*` 的英文 key，避免返工。
6. **不建议的顺序**：先做工具文案多语言（收益低、放大评测矩阵、击穿缓存），或先做 DB 化工具表（没有发布流程时只是把硬编码换成难 review 的硬编码）。

# 附录 A：专项补查 —— AI 对话区的国际化（2026-10-21 追加）

> 本节回答“对话区”特有的 i18n 问题：系统提示词语言、输出语言跟随、静态 chrome 与模型生成内容的边界、schema 驱动表单的字段文案。
> 证据分级：**官方文档/规范** > **泄露的系统提示词（非官方，仅作形态参考）** > **基准论文** > **厂商工程博客** > **未能取得直接证据（显式标注）**。

## A.1 系统提示词语言策略：英文单语 + 一条“跟随用户语言”指令

**结论：主流产品是“系统提示词本体英文单语 + 一条语言跟随指令”，不是整份本地化。**

| 产品 | 证据 | 形态 |
|---|---|---|
| Claude Code 文档助手 | 泄露系统提示词（非官方） https://github.com/asgeirtj/system_prompts_leaks/blob/main/Anthropic/claude-code/claude-code-docs-assistant.md | 整份英文；单独一节 `## Language`：“Answer in the language the user wrote in.”，并要求文档链接用读者 locale 前缀（`/ko/`、`/ja/`、`/zh-CN/`） |
| Microsoft Copilot / Sydney | 泄露提示词分析（非官方） https://labs.zenity.io/post/stealing-copilots-system-prompt ; https://blog.matt-rickard.com/p/a-list-of-leaked-system-prompts | 英文提示词内含一句“I can understand and communicate fluently in the user's language of choice such as English, 中文, 日本語, Español, Français, Deutsch” |
| ChatGPT | 官方帮助中心 https://help.openai.com/en/articles/8357869-how-to-change-your-language-setting-in-chatgpt ；泄露分析（非官方） https://llmrefs.com/blog/chatgpt-system-prompt-leak | UI 语言按浏览器/设备语言自动检测并可手动设置；系统提示词本体英文。泄露分析还显示：即使用户用非英语提问，联网检索词也强制英文（**这只证明“内部规范用英文”，不证明存在语言跟随指令**） |
| Cursor | **未取得直接证据**（无公开系统提示词，规则文件 `.cursor/rules` 通常由用户以英文书写） | 形态推测同“英文规则 + 模型自然跟随输入”，但不应作为已证实结论引用 |

**为什么不做整份本地化（工程理由）**：
1. **评测矩阵爆炸**：每种语言 × 每个版本都要评测，而基准显示非英语下指令遵循本身就更差。
2. **缓存成本**：系统提示词位于 tools 之后的缓存前缀，按语言分叉等于每个 locale 一套前缀。
3. **指令遵循随语言退化有实证**：Multi-IF 基准（IFEval 的多轮 + 7 语种扩展）发现**所有被测模型都在英语下最好**，非拉丁文字（印地语、俄语、中文）错误率更高；o1-preview 的平均准确率从第 1 轮的 0.877 掉到第 3 轮的 0.707（https://arxiv.org/abs/2410.15553 ）。另一份多语言指令遵循评测同样报告显著跨语言差异（https://arxiv.org/html/2503.07539v2 ）。**因此策略应是“英文写规则（更可靠）+ 显式语言指令控制输出”，而不是把规则翻译成中文去“提升中文表现”。**

**边界**：以上是“产品形态”证据，不是“A/B 实验证明英文提示词优于本地化提示词”的直接证据；后者**未找到**。可确定的是：没有任何一家主流产品把系统提示词按用户语言整份切换。

## A.2 模型输出语言跟随：三种机制的组合，指令是主手段

1. **系统指令（主手段，几乎所有产品都用）**：一条显式规则，如 Claude Code 文档助手的 `Answer in the language the user wrote in.`；OpenAI 的 Model Spec（2025-04-11 版）**没有**找到对应的语言条款（https://model-spec.openai.com/2025-04-11.html ），说明这属于产品层指令而非模型规范层。
2. **显式用户偏好（辅助）**：ChatGPT 的 Language 设置是**界面语言**，官方帮助中心描述的是“自动检测浏览器/设备语言并匹配”，并未承诺控制回复语言（https://help.openai.com/en/articles/8357869-how-to-change-your-language-setting-in-chatgpt ）。把“界面语言”当“回复语言”是常见误读——需要产品自己补一条偏好字段并在提示词里注入。
3. **自动检测输入语言（兜底）**：模型天然倾向跟随输入语言，但**不可靠**：OpenAI 社区有“模型忽略用户语言、持续用默认语言回复”的报告（https://community.openai.com/t/model-ignores-user-language/1360573 ）；工程实践也指出“只在英文管线里加一句 respond in the user's preferred language”往往不够，需要把语言作为一等参数贯穿管线（https://www.zenml.io/llmops-database/building-multilingual-ai-agents-with-translation-pipelines ）。

**多语言混输的边界（建议写进产品规则）**：
- **跟随“最后一条用户消息的主语言”**；同一句混输时按主句/多数 token 判定，不要按单个词切换。
- **不翻译**：代码块、标识符、文件路径、JSON 字段名、工具名、枚举值、URL、引用原文。
- **不让模型做本地化格式**：数字/日期/货币/单位由前端 `Intl`/dayjs 按 locale 渲染；模型输出统一用中性格式（ISO 日期、纯数字）。
- **推理语言与回答语言可分离**：LuckyStar（Cohere × LG CNS）用“language-consistency rewards”约束“韩语用户可见回答”，而中间推理可用英文（https://arxiv.org/abs/2606.31648 ）；这与“工具/推理用英文、面向用户用本地语言”的总体策略一致。
- **切换语言只影响后续轮次**：已生成内容不回溯翻译；UI chrome 立即切换，历史消息保持原语言（这也是 ChatGPT/Claude 的实际行为）。

## A.3 对话区三类文本的 i18n 边界

把对话区拆成三层，各走各的通道：

| 层 | 例子 | 语言由谁决定 | 推荐通道 |
|---|---|---|---|
| **静态 chrome** | 发送/停止按钮、HITL 确认卡的“批准/拒绝/编辑”、输入框 placeholder、时间分组“今天”、空状态 | 当前 UI locale | 前端 i18n（vue-i18n key），**永不由后端下发** |
| **模型生成内容** | 回答正文、卡标题、预检摘要、解释性文案 | 请求开始时的输出语言（system 指令） | 模型 token 流，**不做二次翻译**；前端只做排版与代码高亮 |
| **系统/协议通知** | SSE error 帧、限流、工具失败、审批超时、连接断开 | 稳定 code + args | 后端发 `code + args + requestId`（+ 英文兜底 message），前端按 code 渲染本地化文案 |

**业界哪种多？**
- **面向终端用户的 UI 文案：前端按 code 渲染是主流，且被明确写成“最佳实践”**。Canva 开发者文档直接把它列为“坏实践”：不要渲染后端返回的未翻译字符串，应把后端响应映射到前端预定义消息（https://www.canva.dev/docs/apps/localization/bad-practices/ ）。PhotoPrism 的 issue 也要求后端通知只发布“未翻译的 message id + 参数”，由前端按当前 locale 渲染（https://github.com/photoprism/photoprism/issues/5682 ）。
- **面向开发者/集成方的错误：英文 + 稳定 code，不做本地化**。Stripe 明确要求“不要解析错误消息来控制逻辑，用 error code”；**只有**面向持卡人的 `card_error` 才由服务端本地化，SDK/读卡器错误永远是英文（https://docs.stripe.com/terminal/features/locale-config ）。这是“按受众分层”的最清晰范例。
- **两者的折中**：服务端**可以**本地化，但必须同时给 code；客户端优先用 code 自己的翻译，缺翻译才回退到服务端 message。**不要只给本地化字符串**（无法稳定分支、日志无法聚合）。
- **SSE 特有约束**：流已建立后 locale 不应中途改变（服务端通常按请求头锁定）；错误帧里的 `code` 必须能表达“参数级”信息（`{code:"TOOL_ARG_INVALID", args:{field:"date", reason:"format"}}`），否则前端只能显示笼统文案。**未找到**专门讨论“SSE 错误帧 i18n”的规范或大厂文档，以上是由 REST 错误惯例 + 流式约束推导的工程结论（标注为推断）。

## A.4 生成式表单（schema 驱动）的字段文案

**核心事实：JSON Schema 的 `title`/`description` 是单字符串，规范不支持多语言对象**；把 `{"zh":"...","en":"..."}` 塞进 schema 是不符合规范的。业界的通用解法是**结构与展示分离**：

- **JSON Schema 只保留一种语言**（通常是英文，且是给模型/校验用的 canonical 文案）；
- **UI Schema / 展示层持有 i18n key**，运行时按 locale 从消息目录取；
- 解析优先级：**显式 label → i18n key → schema `title` → 字段路径兜底**。

证据：
- `jsonschema-editor` 的 README 明确写出这张分层表：“JSON Schema：One language per field；UI Schema：i18n key on controls → message catalog”，并给出 `{"type":"Control","scope":"#/properties/name","i18n":"person.name"}` 的写法与上述优先级（https://github.com/eumicro/jsonschema-editor ）。
- JSON Forms 通过 `i18n` prop 的 `locale / translate / translateError` 注入翻译函数，错误消息也走 `translateError`（https://jsonforms.io/docs/i18n ）；RJSF 社区的标准做法是渲染前用 `intlSchema()` 把 schema 转成当前语言（https://github.com/rjsf-team/react-jsonschema-form/issues/739 ）。

**对本项目的映射**：
- 工具注册表里 `input_schema_json` 是**模型可见的英文 canonical schema**；
- 另存一份 `ui_schema_json`（或 `ui_hints`）：每个字段给 `i18n` key（如 `tool.doc_search.form.query.label` / `.placeholder` / `.help`），前端 `SchemaForm` 组件按 key 取 vue-i18n 文案；
- **模型动态生成的表单**：要求模型输出 `field_key`（稳定英文标识）+ 可选 `title` 兜底，**不要**要求模型输出中文 label（不可控、不可审校、每次生成可能不同）；前端缺 key 时才显示模型给的 `title`，并在 UI 上标注“AI 生成”；
- **校验错误**：不要直接显示 AJV 的英文 message；按 `keyword + params` 映射到前端 i18n 模板（`validation.required`、`validation.min`），这与后端 `code + args` 是同一套思路。

## A.5 对本项目（Vue3 + Element Plus + Spring Boot + SSE 帧驱动卡面）的一句话建议

**SSE 帧只传“语义”（`code + args + tool_key + schema_ref` + 英文兜底 message），前端用当前 locale 渲染所有静态 chrome、错误提示与表单 label；模型生成内容不翻译、语言由请求开始时的 system 指令锁定；切语言立即影响新帧与新卡片，但不回溯历史消息。**

## A.7 本节诚实边界

- **“英文系统提示词优于本地化提示词”没有直接 A/B 证据**；只有产品形态证据 + “非英语指令遵循更差”的基准证据，两者方向一致但不等价。
- **ChatGPT/Claude 是否对“回复语言”有独立用户设置**：ChatGPT 官方只描述界面语言；Claude 未见官方“回复语言”设置说明。**未取得直接证据**。
- **Cursor 的系统提示词语言策略**：无公开材料，未验证。
- **SSE 错误帧的 i18n**：没有找到规范级或大厂专门文档，A.3 的通道划分是由 REST 错误惯例（code + message）与流式约束推导的工程建议，不是引用现成标准。
- **AI 生成表单的 label**：未找到“模型输出 i18n key”的大厂明文规范；该建议与 JSON Schema/UI Schema 分层惯例一致，但属于推断。
