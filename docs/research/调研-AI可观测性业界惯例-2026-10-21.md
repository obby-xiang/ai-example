## 0. 结论摘要（先看这 9 条）

1. **标准化方向已明确，但标准本身未定稿**：OpenTelemetry GenAI 语义约定（`gen_ai.*`）目前状态仍是 **Development**（低于 Stable），且 2026-06-12 的 semconv v1.42.0 起整块 GenAI 命名空间被**迁出核心仓库**，独立到 `open-telemetry/semantic-conventions-genai`，核心包里的旧常量被标记 deprecated。含义：可以照着做，但必须把属性名收敛在一层自己的映射里，不能散落全代码。
2. **两个关键空白正好落在本仓痛点上**：GenAI 约定里**没有「人工审批 / HITL」的 span 或事件定义**；**流式分块留痕一节至今是 `TODO`**（官方只规定「缓冲后整体记录」）。这两块必须自定义扩展，并写成项目内规范。
3. **Spring AI 1.1.8 的 observation 已经能产出 `gen_ai.*` 的 span 和 metric**，span 命名 `chat {model}` 与 semconv 一致，但属性体系落后一版（用 `gen_ai.system` 而非 `gen_ai.provider.name`，ChatClient/Tool/Advisor 层用 `framework` 作 operation 名），且**没有 TTFT 指标** —— 需要出口侧映射补齐。
4. **方案版图在 2026 年发生了两件影响选型的事**：Helicone 于 2026-03-03 被 Mintlify 收购并进入 maintenance 模式；Arize Phoenix 的许可证已从 Apache-2.0 变为 **Elastic License 2.0（ELv2，非 OSI 开源）**。两者都会影响「长期押注」的判断。
5. **自托管成本的真实差异不在「能不能装」，而在「几个有状态组件」**：Langfuse 自托管需要 PostgreSQL + Redis + ClickHouse + S3 四件套；标准可观测栈（Collector + Tempo/Jaeger + Prometheus + Grafana）通常可复用团队既有的 Prometheus/Grafana。
6. **轨迹粒度业界共识**：一次 LLM 调用一个 span、一次工具执行一个 span、一轮/一个会话一个顶层 span（`invoke_agent` / trace / session），每步至少记录 输入、输出、耗时、状态、error.type；「决策理由」放在 assistant 消息的文本与 `tool_calls` 里，属 Opt-In 内容。
7. **SSE 帧级留痕**：没有任何主流平台逐帧存 span。通行做法是「全量聚合为一条 generation + 首帧时间戳（TTFT）+ 帧数/字节数」；逐帧明细只在开发环境或异常窗口全量留。Langfuse 的 `completion_start_time` 就是这一模式的产物。
8. **prompt/response 默认不落**是行业默认值（Spring AI、OTel 都是 opt-in）；脱敏有四层落点（SDK 出口、Collector、后端扫描、存储访问控制），最实用的是 **Collector 的 redaction processor**（白名单 + 值正则 + HMAC 哈希）。
9. **给本仓的推荐**：以 OTel 为唯一埋点契约（Collector 做语义映射），先落「路线 1（Tempo + Prometheus + Grafana + 自研帧/审批表）」，把 HITL 与帧留痕的**自定义属性先定规范**；Langfuse 作为「调试体验增强」按需旁挂，不做唯一依赖。

### 1.2 选型要点（结论）

- **要「开箱即用的 LLM 调试体验」**：Langfuse（自托管）或 LangSmith（付费 SaaS/企业自托管）。前者省 license 钱、费运维；后者省运维、费钱且绑定 LangChain 生态叙事。
- **要「和现有 K8s/Prometheus 栈同构、只要 OTLP」**：Phoenix（最轻）或直接 Tempo/Jaeger。注意 Phoenix 的 ELv2 不允许对外提供托管服务。
- **要「只看调用与成本、几乎不改代码」**：proxy 型（Helicone）最省事，但其已进入维护模式，新项目不建议作为长期底座。
- **已经是 Datadog 客户**：直接用 OTLP 接 Agent Observability，避免第二套后端；代价是按 span 计费且数据出境需评估。

## 2. OpenTelemetry GenAI 语义约定（重点）

### 2.1 稳定度与仓库迁移（最重要的元事实）

- 官方文档页现在挂的是「Semantic conventions 1.44.0」，且顶部明确写着：**GenAI 语义约定已迁移到 open-telemetry/semantic-conventions-genai 仓库，本页不再维护**（[opentelemetry.io GenAI 页面](https://opentelemetry.io/docs/specs/semconv/gen-ai/)）。
- 新仓库 README 自述覆盖 GenAI client、MCP、以及 OpenAI/Anthropic/Bedrock/Azure 等 provider 特定约定，状态统一为 **Development**（[仓库首页](https://github.com/open-telemetry/semantic-conventions-genai)、[GenAI 文档索引](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/README.md)）。
- **v1.42.0（2026-06-12）是分水岭**：核心 semconv 仓库把 `gen_ai.*` 常量标记 deprecated 并指向新仓库（[v1.42.0 release](https://github.com/open-telemetry/semantic-conventions/releases/tag/v1.42.0)）。最新核心版本为 v1.44.0（2026-08-04）。
- **工程含义**：不能假设「属性名一年不变」。项目内应有一层「内部事件模型 → OTel 属性」的映射代码/Collector 配置，改名时只改一处。

### 2.2 属性体系（当前版本）

|---|---|---|
| 身份 | `gen_ai.provider.name` | **取代旧的 `gen_ai.system`**；旧名仍被多数后端兼容（Datadog 明确「回退到 gen_ai.system」） |
| 操作 | `gen_ai.operation.name` | `chat`、`text_completion`、`generate_content`、`embeddings`、`execute_tool`、`invoke_agent`、`create_agent`、`plan`、`invoke_workflow`、`fetch_response`、`retrieval`、`memory` |

### 2.3 Span 结构与命名

```
invoke_agent {agent.name}            (CLIENT/INTERNAL, 顶层：一次 Agent 运行)
├── chat {request.model}             (CLIENT, 一次模型推理，含工具调用决策)
├── execute_tool {tool.name}         (INTERNAL, 一次工具执行)
│   └── （工具内部的下游调用：DB / HTTP span）
├── plan {agent.name}                (规划步骤)
└── chat {request.model}             (下一轮)
```

- 命名规则：`{gen_ai.operation.name} {gen_ai.request.model}`；工具为 `execute_tool {gen_ai.tool.name}`；Agent 为 `invoke_agent {gen_ai.agent.name}`（无名字时退化为 `invoke_agent`）。
- 传输重试：**一个逻辑 span 覆盖全部重试**，不拆成多个 span。
- 错误不新建 span，只设 span status + `error.type`。

出处同上（`gen-ai-spans.md` 的 Span name / Span kind / Requirement level 段落）。

### 2.4 事件（prompt/completion 的承载方式）

- 约定把「输入/输出消息」既允许放在 span 属性（`gen_ai.system_instructions`、`gen_ai.input.messages`、`gen_ai.output.messages`），也允许放在**事件** `gen_ai.client.inference.operation.details` 里；当语言 SDK 尚不支持结构化属性时，**span 上序列化为 JSON 字符串、事件上保留结构**。
- 消息结构有正式 JSON Schema（input/output messages），支持 text / tool_call / tool_call_response / uri（多模态）等 part 类型。
- 另有 `gen_ai.evaluation.result` 事件（评测分数）、`gen_ai.client.operation.exception`（异常）。

出处：[gen-ai-spans.md「Capturing instructions, inputs, and outputs」](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-spans.md)、[gen-ai-events.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-events.md)。

### 2.5 内容捕获与 PII 处理建议（官方口径）

官方给了三档策略，并明确 **instrumentation 默认不采集**：

1. **默认：不记录** instructions / inputs / outputs。
2. **直接记在 span 属性上**：适合「遥测体量可控、且隐私法规不适用或存储合规」的场景，官方点名 **pre-production 环境**。
3. **外存 + span 上只留引用**：生产推荐，便于单独做访问控制与成本控制。

配套机制：

- **显式 opt-in 开关**，如 `OTEL_INSTRUMENTATION_GENAI_CAPTURE_MESSAGE_CONTENT`。
- **进程内 hook**：instrumentation 可暴露上传/改写钩子，在序列化前调用，钩子内可做脱敏后再落属性；钩子**不受采样决策影响**（即使 span 被采样丢弃也会被调用）。
- **截断选项**：允许截断单条消息内容但保留 JSON 结构。

出处：同上 `gen-ai-spans.md` 同节。

### 2.6 流式（SSE）—— 标准尚未定义

这是本次调研最关键的一条空白：

- `gen-ai-spans.md` 的「Streaming chunks」小节内容就是 **`TODO`**，没有任何 chunk 级记录约定；标准只覆盖「响应收完后缓冲记录」。
- 标准对流式的补偿是**指标层面**：`gen_ai.client.inference.time_to_first_chunk` 与 `gen_ai.client.inference.time_per_output_chunk`（[client-inference.md](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/client-inference.md)）。
- 结论：**帧级留痕必须自建**，但「首帧时间 + 总时长 + 帧数」可以直接映射到标准指标，这决定了自研方案要长什么样（见 §3.4）。

## 3. 轨迹（trajectory）与可回放

### 3.1 轨迹到底是什么：三层结构，业界叫法已趋同

| 层 | 含义 | OTel 表达 | LangSmith 叫法 | Langfuse 叫法 |
|---|---|---|---|---|
| Turn / Trace | 一次用户请求到最终响应 | 一条 trace（root span） | trace | trace |
| Session | 多轮会话 | `gen_ai.conversation.id` 相同的多条 trace | thread | session |
| Trajectory | 把整个会话压平成有序消息序列（去掉嵌套） | 无标准，需从 span 树投影 | **trajectory（一等公民）** | 无独立概念（用 session 视图） |

LangSmith 对 trajectory 的定义值得直接借用：**「trajectory 是 thread 上的一个投影，包含 human / AI / tool 消息各一次、按首次出现顺序排列、去掉 run 的嵌套」**（[LangSmith 概念](https://docs.langchain.com/langsmith/observability-concepts)）。这与「可回放」需求高度吻合：回放要的是消息序列，不是 span 树。

### 3.2 每步记录什么（主流粒度）

一个 Agent 步骤（span）最小充分集：

| 字段 | 作用 | 对应 OTel |
|---|---|---|
| 步骤类型 | llm / tool / plan / agent | `gen_ai.operation.name` |
| 名称 | 模型名或工具名 | `gen_ai.request.model` / `gen_ai.tool.name` |
| 输入 | prompt 或工具参数 | `gen_ai.input.messages` / `gen_ai.tool.call.arguments`（Opt-In） |
| 输出 | 文本/工具结果 | `gen_ai.output.messages` / `gen_ai.tool.call.result`（Opt-In） |
| 耗时 | 端到端与首字节 | span 起止时间；TTFT 用 metric |
| 状态 | ok/error + 错误类别 | span status + `error.type` |
| 用量 | tokens（分输入/输出/缓存/推理） | `gen_ai.usage.*` |
| 决策依据 | 模型为什么调这个工具 | assistant 消息里的文本 + `tool_calls`（一个 part，无需另设字段） |
| 关联 | 属于哪轮、哪个工具调用 | `gen_ai.conversation.id`、`gen_ai.tool.call.id` |

不建议把「决策理由」做成独立字段去解析模型思维链：一是各家格式不同，二是 reasoning token 可能不可见。把原始 assistant 消息存全，回放时自然可读。

### 3.3 HITL：标准空白，需要自建 span（**本条为建议，非业界标准**）

已确认的事实：GenAI Agent spans 覆盖 `create_agent` / `invoke_agent` / `invoke_workflow` / `plan` / `execute_tool` / skill 相关 span，**没有任何 approval / human / review 类型**（[gen-ai-agent-spans.md 目录](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-agent-spans.md)）。平台的「人工」能力都落在**事后标注**：Langfuse 的 score / annotation queue（[文档](https://langfuse.com/docs/scores/annotation)），LangSmith 的 feedback / annotation queue。框架层（如 LangGraph 的 `interrupt()`）把审批当作**状态检查点**保存，也不是 span。

对本仓（自研 16 帧协议 + 自研审批流）的建议模型：

```
invoke_agent {agent}                       # 一次运行
├── chat {model}                            # 模型决定调用工具
├── approval {tool.name}   (INTERNAL)       # 新增：人工决策点
│    hitl.request.id / hitl.tool.name
│    hitl.decision = approve|reject|edit|timeout
│    hitl.actor = user:123 / role:reviewer
│    hitl.wait_ms  (审批等待时长，单独成 span 才能与工具耗时分离)
│    hitl.edited = true|false
├── execute_tool {tool.name}  (INTERNAL)    # 用 span link 指回 approval
└── chat {model}                            # 拿到结果后继续
```

要点：

- **审批等待必须是独立 span**，否则 P99 延迟被人工时长污染，工具耗时指标失真。
- 用 **span link** 而非父子关系连接 approval 与 execute_tool（Datadog 的 Execution Graph 正是用 span link 表达「某步输出喂给另一步」，[文档](https://docs.datadoghq.com/llm_observability/instrumentation/otel_instrumentation/)）。
- 审批结果同时作为**属性**（可聚合）与**事件**（可按时间点回放），不要只存日志。
- 若走 Langfuse，可再补一个 score（如 `approval_outcome`）以便和评测体系打通。

### 3.4 SSE 帧级留痕：全量 / 采样 / 滚动窗口怎么选

事实基础：

- 标准层面：chunk 级记录是 TODO，只有「收完再记」。
- Langfuse 在 generation 上提供 `completion_start_time`（模型开始生成的时刻），TTFT 由此计算（[Langfuse OTel 属性映射表](https://langfuse.com/integrations/native/opentelemetry)）。
- Langfuse 的采样是**客户端、trace 级**：`sample_rate` 默认 1（全收），命中采样则整条 trace 的 observations/scores 一起保留（[Sampling 文档](https://langfuse.com/docs/observability/features/sampling)）。
- Datadog 直接按 span 计费，逐帧存帧会线性放大成本（[定价说明](https://docs.datadoghq.com/llm_observability/)）。

业界实际做法（归纳，非单一出处）：

| 方案 | 内容 | 成本 | 适用 |
|---|---|---|---|
| 全量逐帧 | 每一帧作为 event 附在 generation span 上 | 极高（帧数 × 属性体积），且多数后端属性有长度上限 | 仅开发/联调 |
| **全量聚合（主流）** | 一条 generation 存完整文本 + 首帧时间 + 帧数 + 总字节 + 结束原因 | 低 | 生产默认 |
| trace 级采样 | 按 trace 抽样（如 10%），被采中的整条保留 | 可控 | 生产常态 |
| 滚动窗口 / 尾部保留 | 内存环形缓冲保留最近 N 帧；出错时把缓冲快照落盘/上报 | 低，排障友好 | 生产 + 事故复盘 |
| 异常触发全量 | 仅当 status=error、帧解析失败、超时、用户点踩时把该次全量帧落库 | 低 | **推荐与上一条组合** |

**对本仓的具体建议**（自研 16 帧协议，帧语义比通用 HTTP chunk 更丰富，值得留结构而不只留文本）：

1. 每次 SSE 响应 = 1 条 generation span；记录 `gen_ai.request.model`、`gen_ai.usage.*`、`gen_ai.response.finish_reasons`、`sse.frame.count`、`sse.bytes`、`sse.first_frame_ms`、`sse.last_frame_ms`、`sse.frame.type.histogram`（各帧类型出现次数，低基数）。
2. **帧明细默认不落 span 属性**，写本地环形缓冲（每请求最近 N 帧，N 按最大帧体积定），仅在 `error` / 超时 / 用户反馈负向时整体快照写入对象存储或 DB，span 上只留一个引用键（这正是 semconv 推荐的「外存 + 引用」模式）。
3. 开发环境开关 `observability.sse.capture=full`，生产为 `tail`；两个值都要有测试覆盖。
4. 帧级时间戳用于算 TTFT 与 TPOT，并映射到 `gen_ai.client.inference.time_to_first_chunk` / `time_per_output_chunk`，这样即使后端不认自研属性，延迟指标依然在标准体系内。

## 4. 指标体系（Prometheus / Micrometer 生态）

### 4.1 该盯的指标集

| 维度 | 指标 | OTel 标准名 | Prometheus 形态 | 备注 |
|---|---|---|---|---|
| 时延 | 推理总时长 | `gen_ai.client.inference.duration`（历史名 `gen_ai.client.operation.duration`） | `..._seconds_bucket/_sum/_count` | 桶按 semconv 建议 |
| 时延 | 首帧 | `gen_ai.client.inference.time_to_first_chunk` | `..._seconds_*` | 用户感知的核心 |
| 时延 | 每帧 | `gen_ai.client.inference.time_per_output_chunk` | 同上 | 抖动检测 |
| 用量 | 输入/输出/缓存/推理 token | `gen_ai.client.inference.usage.{input_tokens,output_tokens,cache_read...,reasoning...}` | `..._tokens_total`（counter） | 按 `gen_ai.token.modality` 分维 |
| 成本 | 单次成本 | 无标准；`gen_ai.cost.estimated_total`（Datadog 已识别）、`gen_ai.usage.cost`（Langfuse 已识别） | gauge/counter | 建议用「token × 单价表」在 Collector/服务端算，单价变更要有版本 |
| 工具 | 工具执行时长 | `gen_ai.execute_tool.duration` | `..._seconds_*` | 与审批等待分离 |
| 工具 | 工具调用次数 | `gen_ai.invoke_agent.tool_calls` | counter | 每次 agent 调用的工具数分布 |
| 审批 | 等待时长（自定） | `hitl.approval.wait`（自定名） | `..._seconds_*` | 按工具名/审批人角色分维 |
| 审批 | 决策分布（自定） | `hitl.approval.decisions`（自定名） | `..._total` | approve/reject/edit/timeout |
| 错误 | 错误率 | 由 span status + `error.type` 派生 | `..._total{error_type=...}` | 低基数枚举 |
| 缓存 | 缓存命中率 | 由 cache_read / input_tokens 派生 | 比值 | 直接反映成本优化 |
| 服务端 | 模型服务视角 | `gen_ai.server.request.duration`、`time_to_first_token`、`time_per_output_token` | 同上 | 自建推理服务才用得上 |

出处：[GenAI metrics](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-metrics.md)、[token metrics](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/gen-ai-token-metrics.md)、[client inference](https://github.com/open-telemetry/semantic-conventions-genai/blob/main/docs/gen-ai/client-inference.md)。

### 4.2 直方图桶（容易踩坑）

- semconv 给 `gen_ai.client.operation.duration` / `gen_ai.execute_tool.duration` 的显式桶是 **0.01, 0.02, 0.04, …, 40.96, 81.92**（倍增序列）。
- 该序列适合「秒级以内到十几秒」的调用，但**不适配 TTFT**：TTFT 常见 0.2–5s，用这套桶会导致低端分辨率不足。建议对 TTFT/TPOT 单独定义桶（如 0.05/0.1/0.25/0.5/1/2/5/10/30），或改用指数直方图。
- Prometheus 侧务必开 `publishPercentileHistogram`（或 Micrometer 的 `serviceLevelObjectives`），否则只有 sum/count/max，算不出 P95/P99；开启后时间序列形态为 `_bucket/_gcount/_gsum`（[Micrometer Prometheus 文档](https://docs.micrometer.io/micrometer/reference/implementations/prometheus.html)）。

### 4.3 命名转换（OTel → Prometheus）

- 默认策略 `UnderscoreEscapingWithSuffixes`：`gen_ai.client.token.usage` → `gen_ai_client_token_usage_total`，单位进后缀（`_seconds`、`_bytes`），counter 加 `_total`（[OTel Prometheus exporter 规范](https://opentelemetry.io/docs/specs/otel/metrics/sdk_exporters/prometheus/)）。
- 后果：**同一个指标在 OTel 侧与 Prometheus 侧名字不同**，看板/告警/文档必须固定用哪一侧的名字，否则会出现「同一个指标两个名」的长期混乱。
- Spring AI 已在文档里给出映射表（`gen_ai_client_operation_seconds_*`、`gen_ai_client_token_usage_total`、`gen_ai_chat_client_operation_seconds_*`），可直接对照（[Spring AI Observability](https://docs.spring.io/spring-ai/reference/1.1/observability/index.html)）。

### 4.4 Micrometer 惯用接法（Java 侧）

- 应用只依赖 `ObservationRegistry` + `spring-boot-starter-actuator`；**同时挂两个 registry**（`micrometer-registry-prometheus` + `micrometer-registry-otlp`）即可一套埋点、两条出口：Prometheus 出指标，OTLP 出 trace（也可出指标给 Collector）。
- 低基数键进 metric、高基数键只进 trace —— 这是 Micrometer Observation 的既定约定（Spring AI 文档明确说明）。
- 业务自定义指标（审批等待、帧数）用 `Timer.builder("hitl.approval.wait").tag("tool", ...).publishPercentileHistogram()`，**标签值必须来自枚举**，工具名可枚举，用户 ID 绝对不行。
- 告警建议基于「比值」而非绝对值：错误率、`cache_read/input`、P95 TTFT、审批超时率。

## 5. 日志与脱敏

### 5.1 主流分层（四层，缺一层就等于没有）

| 层 | 手段 | 代表实现 | 特点 |
|---|---|---|---|
| L1 应用/SDK 出口 | 序列化前改写 span 属性 | Langfuse `mask_otel_spans`（Python SDK 导出阶段钩子，覆盖第三方 OTel span）；OTel GenAI 的内容 hook | 最彻底，数据不出进程 |
| L2 Collector | 白名单 + 值正则 + 哈希 | OTel Collector `redaction` processor（`allowed_keys` 默认拒绝、`blocked_values` 正则、`hash_function: hmac-sha256`） | 与语言无关，统一策略，可审计 |
| L3 后端扫描 | 入库后扫描并遮盖 | Datadog Sensitive Data Scanner / Agent Observability 的敏感数据扫描 | 兜底，但数据已经出境 |
| L4 存储/访问 | 加密、分权、保留期 | 自托管对象存储 + RBAC；SaaS 的 restricted dataset | 合规最后一道 |

出处：[Langfuse Masking](https://langfuse.com/docs/observability/features/masking)、[Collector redaction processor](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/processor/redactionprocessor/README.md)、[Datadog 概览（敏感数据扫描）](https://docs.datadoghq.com/llm_observability/)。

### 5.2 掩码形态怎么选

| 形态 | 可读性 | 可关联性 | 风险 | 场景 |
|---|---|---|---|---|
| 固定星号 `****` | 保留结构，能看出「这里有个手机号」 | 无 | 低 | 默认首选 |
| 哈希（HMAC-SHA256） | 不可读 | **可关联**（同一用户哈希相同） | 低（需管好 key） | 需要「同一用户多次请求」分析时 |
| 可逆加密/令牌化 | 不可读 | 可还原 | 高（密钥 + 权限） | 合规要求可回溯且能审批解密，少见 |
| 字段删除 | 结构塌陷 | 无 | 低 | 明确不需要的字段（如整段 system prompt） |

`redaction` processor 的配置语义值得直接照抄：**默认 fail-closed**（`allowed_keys` 为空则删光所有属性）、`allowed_values` 优先于 `blocked_values`（可白名单本公司域名）、支持 `hash_function: md5|sha1|sha3|hmac-sha256|hmac-sha512`。

### 5.3 采样与保留期

- **采样**：按 trace（而非按 span）采样，保证一条轨迹完整；错误与审批轨迹**强制保留**（tail sampling / 客户端 `always_sample` 标记）。Langfuse 默认 `sample_rate=1`，采样在客户端完成（[Sampling](https://langfuse.com/docs/observability/features/sampling)）。
- **保留期**：LangSmith SaaS 为 **180 天**，到期永久删除、仅留统计元数据（[LangSmith 观测概念](https://docs.langchain.com/langsmith/observability-concepts)）。业界通行基线是「**热 30 天 / 温 90 天 / 冷存按合规**」：30 天覆盖绝大多数排障，90 天覆盖季度复盘（[MLflow 关于 LLM 数据保留的讨论](https://mlflow.org/articles/data-retention-llm/)）。
- 对本仓：建议「trace 元数据 + 指标 90 天；prompt/response 原文 7–30 天（且默认脱敏）；审批记录按审计要求长期保留（审批是合规证据，不能随 trace 一起过期）」。

### 5.4 一条硬规则

**prompt/response 默认不落**是行业默认值（Spring AI 的 `log-prompt` / `log-completion` 默认 false；OTel 默认不采集内容）。开启必须是「按环境 + 按字段白名单 + 有到期时间」的显式动作，而不是一个全局开关。

### 6.2 能不能「直接吃到」OTel GenAI 约定：能，但只到七成

| 差距 | 具体表现 | 影响 | 补法 |
|---|---|---|---|
| provider 属性名 | 用 `gen_ai.system`，非 `gen_ai.provider.name` | 新版后端（Datadog 已兼容回退；Langfuse 主要认 `gen_ai.system`） | Collector `transform` 复制一份 `provider.name` |
| operation 语义 | ChatClient/Advisor/Tool 层 `gen_ai.operation.name=framework` | 后端按 operation 分类会归到 unknown | 按 `spring.ai.kind` 映射：`chat_client→chat`、`tool_call→execute_tool` |
| 缺 `execute_tool {name}` 命名 | Tool 层是 `spring.ai.tool` | 无法按工具聚合 | Collector 重命名 span |
| 无 `invoke_agent` 顶层 | Spring AI 不感知「一次 Agent 运行」 | 轨迹缺根节点，回放困难 | **自建**：进入 SSE 请求时开一个 `invoke_agent {app}` span |
| 无结构化消息事件 | 只有 `gen_ai.prompt` 字符串（可选） | 后端无法渲染对话气泡 | **自建** `gen_ai.client.inference.operation.details` 事件（JSON messages） |
| 无 TTFT | 只有 `spring.ai.chat.client.stream=true/false` | 流式体验无法量化 | **自建** timer（首帧/每帧） |
| 无 HITL | 无对应属性 | 审批不可观测 | **自建** approval span（见 §3.3） |

桥接实现路线（按侵入从小到大）：

1. **Micrometer Tracing + OTLP**：`micrometer-tracing-bridge-otel` + `opentelemetry-exporter-otlp`，把 observation 变成 OTLP span，Collector 做属性映射。注意 OTel Java instrumentation **没有 Spring AI 专用模块**，官方 supported-libraries 里 Spring AI 一行的模块列是 `N/A`，信号靠 Micrometer 桥（[supported-libraries.md](https://github.com/open-telemetry/opentelemetry-java-instrumentation/blob/main/docs/supported-libraries.md)）。
2. **自定义 `ChatModelObservationConvention` / `ChatClientObservationConvention`**：直接产出合规属性名，避免 Collector 逻辑。适合「属性名稳定后」再收口。
3. **Collector `transform` processor**：不改代码，最快见效，但映射规则要随 semconv 版本维护，需进版本库并写测试（可用 `otelcol` 的 `--config` 校验）。

### 6.3 `SimpleLoggerAdvisor` 的边界（源码核对）

```java
protected void logRequest(ChatClientRequest request)  { logger.debug("request: {}", ...); }
protected void logResponse(ChatClientResponse resp)   { logger.debug("response: {}", ...); }
// stream: new ChatClientMessageAggregator().aggregateChatClientResponse(stream, this::logResponse)
```

- **只有 DEBUG 级**，生产默认静默；要开就得整体调 DEBUG，噪音大。
- **流式是「先聚合再打日志」**：拿不到首帧时间，长响应会在内存里聚合完整文本，且日志只在结束时出现一次 —— 正好丢掉 SSE 最有价值的时序信息。
- **没有脱敏钩子**：只能替换 `requestToString` / `responseToString` 函数，属于「自己写脱敏」，不是内置能力。
- 结论：`SimpleLoggerAdvisor` 适合本地开发「看 prompt 长什么样」，**不能当作可观测方案**；生产要么关掉，要么用自定义 advisor 只输出「长度 + 哈希 + traceId」。

### 6.4 版本提示

Spring AI 文档站当前标注最新稳定版为 **2.0.1**（1.1.8 页面顶部提示「For the latest stable version, please use Spring AI 2.0.1」）。升级前需确认 2.x 的 observation 属性是否已切到 `gen_ai.provider.name` —— 若已切，Collector 的映射规则要做兼容（两个版本并存期）。

## 7. 自托管落地组合与运维成本

### 7.1 三种典型组合

| 组合 | 组件 | 能力覆盖 | 运维负担 | 适用 |
|---|---|---|---|---|
| **A. 标准可观测栈** | OTel Collector + Tempo（或 Jaeger）+ Prometheus + Grafana | 全量 trace、指标、告警、日志关联；LLM 语义靠映射 | 中：4 个组件，但多数团队已有 Prometheus/Grafana | 已有 K8s 可观测体系的团队 |
| **B. Langfuse 一把梭** | Langfuse Web + Worker + PG + Redis + ClickHouse + S3（前置可选 Collector） | LLM 专用体验最好：trace 树、session、score、prompt 版本、成本 | 高：4 个有状态依赖，ClickHouse 要会调优/备份 | 小团队、无既有栈、重视调试体验 |
| **C. 双写混合** | App → Collector →（Tempo + Prometheus）与（Langfuse 或 Datadog） | 通用排障 + LLM 语义兼得 | 最高：两套存储、两套权限、两套保留策略 | 中大型、事故复盘要求高 |

### 7.2 运维成本对比（定性 + 可验证事实）

- **有状态组件数**：A 组合 2 个（Tempo/Jaeger 的对象存储 + Prometheus 本地盘，通常已有）；B 组合 4 个（PG、Redis、ClickHouse、S3），且 Langfuse 官方明确「Web 与 Worker 两个应用容器 + 四类存储」（[自托管架构](https://langfuse.com/self-hosting)）。
- **规模优化**：Langfuse 的写入路径是「先落 S3，再入 ClickHouse」，抗尖峰但要理解 S3 生命周期与回放；A 组合的 Tempo 同样依赖对象存储，概念相近。
- **License 约束**：Grafana 与 Tempo 是 **AGPL-3.0**，Prometheus / Jaeger / Collector 是 **Apache-2.0**（[grafana](https://github.com/grafana/grafana)、[tempo](https://github.com/grafana/tempo)、[prometheus](https://github.com/prometheus/prometheus)、[jaeger](https://github.com/jaegertracing/jaeger)），对外提供服务时需法务确认 AGPL 义务；Phoenix 的 ELv2 则明确禁止「把软件作为托管服务提供给第三方」（[LICENSE](https://github.com/Arize-ai/phoenix/blob/main/LICENSE)）。
- **人天估算（经验值，非出处）**：B 组合首装 2–3 人日、每月维护 0.2–0.5 人日；A 组合在已有栈上首装 1–2 人日（Collector 配置与看板为主），维护并入既有值班。两者差距主要在「ClickHouse 出问题时谁修」。

### 7.3 一个被低估的细节

无论选哪条，**Collector 都是值得单独存在的组件**：它同时承担「语义映射（semconv 版本兼容）」「脱敏」「采样」「双写」。把这三件事写进应用代码，等于把厂商/版本风险写进了业务代码。

## 8. 给本仓的三条候选路线

### 路线 1（推荐起步）：OTel 主干 + 自研语义扩展

```
Spring Boot (Micrometer Observation)
   ├─ /actuator/prometheus ──► Prometheus ──► Grafana（指标/告警）
   └─ OTLP ──► Collector（transform 映射 + redaction + tail sampling）
                 ├─► Tempo（trace，S3 后端）
                 └─► （可选）Loki/现有日志栈
自研：approval span、SSE 帧环形缓冲 + 异常快照、trajectory 投影接口
```

- 优点：与现有 Java/Spring 生态零摩擦；一套埋点两套出口；License 干净（Apache-2.0 为主，Grafana/Tempo 注意 AGPL）；后续接任何后端只需改 Collector exporter。
- 缺点：没有现成的「LLM 会话视图 / score / prompt 版本」，需要自己写 1 个 trajectory 页面（把 trace 树投影成消息序列，工作量约 3–5 人日）。
- 适合：以「线上定位问题 + 开发期调试」为目标、不想引入 ClickHouse 的团队。

### 路线 2：Langfuse 为主，Prometheus 为辅

```
Spring Boot ──OTLP──► Collector ──► Langfuse（自托管 compose：PG+Redis+ClickHouse+S3）
                    └─► Prometheus（只取 token/成本/时延指标做告警）
```

- 优点：开箱即得 trace 树、session、score、prompt 版本、成本核算；Spring AI 被 Langfuse 列为「由 OTel 驱动的框架集成」之一（[OTel 集成页](https://langfuse.com/integrations/native/opentelemetry)），接入成本低；未来可无缝换 SaaS。
- 缺点：4 个有状态依赖；自研 16 帧与 HITL 仍要自定义属性（Langfuse 支持 `langfuse.observation.*` 扩展，但**非标准**）；数据合规要看是否自托管。
- 适合：调试体验优先级最高、团队有人能维护 ClickHouse。

### 路线 3：双写（主干 + LLM 专用视图）

```
Spring Boot ──OTLP──► Collector ─┬─► Tempo + Prometheus（全量，SLO/告警/事故）
                                 └─► Langfuse（filter：仅 gen_ai.* 与 approval.*，采样 10–20%）
```

- 优点：通用排障与 LLM 语义兼得；Langfuse 只收采样后的关键 span，成本可控。
- 缺点：两套系统、两套权限与保留策略；Collector 的 filter 规则如果按 span 过滤会破坏 trace 完整性（Langfuse 要求 root span 必须送达，[文档](https://langfuse.com/integrations/native/opentelemetry)），必须按 trace 级过滤。
- 适合：已决定长期投入可观测、且线上事故复盘要求高的阶段。

### 建议的落地顺序（若采纳路线 1）

1. 定义《可观测性属性规范 v1》：固定 `gen_ai.*` 用法、`hitl.*` 扩展、`sse.*` 扩展、以及「哪些字段允许落内容」。
2. 在 SSE 入口开 `invoke_agent` root span；在工具执行处开 `execute_tool` span；在审批处开 `approval` span（三者构成可回放骨架）。
3. Collector 配置三件事：semconv 映射（system→provider.name、kind→operation）、redaction（白名单 + 手机号/身份证/邮箱正则 + HMAC）、tail sampling（错误与审批全留）。
4. 指标补齐：TTFT、审批等待、工具成功率、token 成本；看板按「模型 / 工具 / 审批结果」三个维度切。
5. 二期再评估是否旁挂 Langfuse：只需改 Collector exporter，不动业务代码 —— 这是把路线 1 做成「可升级」的关键。
