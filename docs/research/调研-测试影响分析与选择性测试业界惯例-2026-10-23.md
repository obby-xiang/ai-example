## 0 结论先行

1. **业界有，而且是一整条成熟产品线，不是偏方。** 三支谱系各有名字：Test Impact Analysis（TIA，依赖/覆盖映射，确定性）、Predictive Test Selection（PTS，机器学习概率排序）、以及构建/测试工具原生的变更集映射（`--changed`、`--related`、`nx affected`、`bazel-diff`）。
2. **主流形态不是"只跑选择集"，而是"PR 跑选择集 + main/nightly 跑全量"的分层。** Google 把这条写进书里（presubmit 只跑快而稳的测试，postsubmit 兜底），微软 TIA 把它做成产品选项（按周期跑全量），Gradle Develocity 把"覆盖率只在关掉 PTS 的构建里量"写进手册。
3. **本仓不具备任何现成的构建图设施**：单模块 Maven + 单应用前端，Nx/Bazel 的 affected 分析与本仓形态不匹配；前端 Vitest 4.1.11 原生支持 `related`/`--changed`（已实测）；后端没有任何 Maven 原生 TIA，而两个学术工具与本仓技术栈**硬冲突**（STARTS 只测到 Java 15；Ekstazi 只支持 JUnit 3/4，本仓 256 个测试类全是 JUnit 5）。
4. **本仓的真实耗时结构决定了最划算的一刀不在"选测试"，而在"按模块跳 job"。** CI 五个 job 每个 PR 全跑（含 25 分钟上限的 E2E），但纯文档改动完全不需要后端/前端/E2E。这一步零漏测面、改动面最小（一个 workflow 文件），应先做。
5. **推荐保守起步四档**：A 档 CI 按变更集跳过无关的贵 job（先做）；B 档本地门禁分"提交级=相关集+固定冒烟集 / 合流级=全量双 locale"两级；C 档前端接 `vitest related`；D 档后端自建"变更类 → 测试类"选择脚本（约 250 行，零新依赖）。**明确不做**：ML 预测（样本与提交频率不匹配）、STARTS/Ekstazi（版本与 JUnit 5 硬阻断）、为 affected 分析重构成多模块/Bazel。

## 1 业界的三种机制（概念谱系与成熟度）

### 1.1 一张表看清三支谱系

| 谱系 | 判断"该跑哪些测试"的依据 | 代表实现 | 成熟度 | 采纳前提 |
|---|---|---|---|---|
| 静态/动态依赖分析（TIA 正统） | 源码/字节码依赖图 + 测试覆盖映射；变更点 → 反向可达的测试 | Ekstazi、STARTS（Java）；Azure DevOps TIA（.NET）；Develocity 的 impacted 兜底 | 学术工具成熟但生态窄；平台内置版**范围受限** | 需要可靠的依赖抽取（反射、动态代理、配置文件是天然盲区） |
| 机器学习预测（PTS） | 历史"变更 × 测试结果"训练出的概率模型，按失败概率排序取 top-k | Meta PTS；Google TAP Presubmit 的 ML 过滤与 TRANSPRED；Develocity PTS | 大厂内部长期生产运行；商业产品化（Develocity） | 需要大量历史执行数据与稳定的结果回流；冷启动期必须回退到全量 |
| 变更集映射（工具原生） | 模块图/导入图 + `git diff base..head`，直接给出受影响测试文件 | Jest `--onlyChanged`/`--findRelatedTests`；Vitest `related`/`--changed`；Nx `affected`；Bazel `rdeps`/`bazel-diff` | 最成熟、零训练成本、已是日常开发默认能力 | 只要"静态可解析的导入关系"；动态 import/反射同样会漏 |

概念上的分化点只有一个：**TIA 问"这个变更可能影响谁"（保守、可解释、偏多跑），PTS 问"这个测试有多可能抓到这个变更的 bug"（激进、要数据、可少跑）**。CloudBees 的综述把这条分界写得很直白：TIA 是确定性规则 + 依赖映射，PTS 是概率模型 + 历史结果【二手】<https://www.cloudbees.com/blog/predictive-test-selection-vs-test-impact-analysis>。

### 1.2 逐家事实（带数字与出处）

**Meta（Facebook）Predictive Test Selection，2018 起生产**【一手·官方】<https://engineering.fb.com/2018/11/21/developer-tools/predictive-test-selection/>：

- 明确论证了"纯依赖图不够"：按构建依赖把所有传递依赖的测试都跑，在它的移动端代码库上平均会跑到全部测试的约四分之一，仍然太贵；静态变更影响分析在超大规模多语言仓里"不可行"。
- 做法是梯度提升决策树（GBDT）估计"某测试在某变更下失败的概率"，只跑概率高的；训练数据来自历史变更与测试结果。
- 效果口径：**捕获 >99.9% 的回归，只跑约三分之一的"传递依赖被改动的测试"**，测试基础设施效率翻倍。
- 抖动处理：训练数据采集时**对失败测试激进重试**，把"稳定失败（真回归）"和"偶发失败（flake）"分开，否则模型学不准。
- 论文：Machalica 等，*Predictive Test Selection*（arXiv:1810.05286）【一手·论文】<https://arxiv.org/pdf/1810.05286>。

**Google TAP（Test Automation Platform）**【一手·官方/论文】：

- presubmit 口径写在《Software Engineering at Google》第 23 章：*"which tests should be run on presubmit? Our general rule of thumb is: only fast, reliable ones. You can accept some loss of coverage on presubmit, but that means you need to catch any issues that slip by on post-submit"*；并给出两条具体做法：**"typically limit presubmit tests to just those for the project where the change is happening"**、以及"测试范围可以被限制在特定 scope，**或按一个预测其发现失败概率的模型来选**"；脚注还补了一句关键事实：TAP 在后台会把一部分 presubmit 测试**优化成 postsubmit 再跑**<https://abseil.io/resources/swe-book/html/ch23.html>。
- postsubmit 是"补全覆盖"的那一层：TAP 每个"综合测试周期"跑**自上次以来所有 affected（按构建依赖判定）的测试**；作者同时承认，长期只靠构建图的静态选择在 Google 规模上"不可持续"，因此另加投机周期（Speculative Cycles）用 ML 抓新破坏【一手·论文】<https://hackthology.com/speculative-testing-at-google-with-transition-prediction.html>。
- 该 2025 论文的量化：在**只给 25% 目标预算**时，Transition Prediction 的召回为 **85%**；投机周期把新破坏的发现时延中位数从 107 分钟降到 37 分钟（约 65%）。这组数字是"选择集永远有漏"的最好注脚——Google 也不敢把全量周期砍掉。

**Gradle Develocity Predictive Test Selection**【一手·官方】<https://docs.develocity.ai/2026.3/using-develocity/predictive-test-selection/>：

- 模型用 Build Scan 里的"变更 × 测试结果"训练，叠加跨项目的海量执行先验；**项目历史不足时，退化为"跑全部 impacted 测试"**（冷启动安全）。
- 硬规则：**永远选上"最近新增、最近改动、最近失败、被标记为 flaky"的测试**——这是把四类高风险测试钉死在选择集里的工业级做法。
- 手册里的两条边界同样重要：只跑子集时**结果不会写入 build cache**；**开启了覆盖率统计的构建不建议同时开 PTS**（覆盖率会失真，应在关 PTS 的构建里量）<https://docs.gradle.com/develocity/predictive-test-selection/>。

**Azure DevOps Test Impact Analysis（微软）**【一手·官方】<https://learn.microsoft.com/en-us/azure/devops/pipelines/test/test-impact-analysis?view=azure-devops>：

- 机制是"测试方法 → 依赖文件"的映射表（managed code 的 `.cs`/`.vb` 自动生成，其他语言可手写 XML 映射），按提交里改到的文件反查测试。
- 三条设计值得抄：**安全回退**（遇到无法理解的提交/文件类型，例如只改了 HTML/CSS，直接跑全部测试）；**可配置的周期全量**（"TIA can be conditioned to run all tests at a configured periodicity"，官方标注为 recommended）；**把先前失败与新增测试纳入选择集**。
- 但成熟度要打折：官方明确 TIA **只支持 VSTest 任务、.NET managed code、单机拓扑，且不支持 .NET Core**；启用后不支持并行与覆盖率采集。这是一家平台厂商做了十年仍然"范围受限"的实证。
- 官方还给了**验证选择器的方法**：在流水线里跑两个测试任务，T1 只跑 impacted、T2 跑全量，"若 T1 全绿则核对 T2 是否也全绿；若 T1 有红，核对 T2 报的是不是同一批红"。这套对照法是本仓将来验证自建选择器的现成模板。
- 另有实践建议：**依赖映射需要定期用全量重生成**<https://learn.microsoft.com/en-us/azure/devops/pipelines/tasks/reference/vstest-v3?view=azure-pipelines>。

**Nx affected**【一手·官方】<https://nx.dev/ci/features/affected>：

- 机制是"项目图/任务图 + git diff"：`nx affected -t build test` 先找分支改动的文件，再选"输入包含这些文件"的任务，以及读取被选任务产出的下游任务。
- 两条运维口径：CI 里必须显式给 `--base`/`--head`，**推荐 base 取"main 上最近一次成功的提交"**（否则每次 push 都重算同一批）；`fetch-depth: 0` 是硬前提。
- 官方自己写了局限：**改到大多数项目都依赖的库、或改到所有任务共享的输入时，affected 会选中绝大多数任务**；每个 PR push 都与同一个 base 比较，因此同一批任务会被反复选中（要靠远程缓存摊薄）。

**Bazel**【一手·官方】<https://bazel.build/query/guide>：

- Bazel **没有**内置的 "affected targets" 命令；标准做法是用查询语言做反向依赖：`rdeps(universe, set(//path:file))`，即"在给定范围内，哪些目标依赖我改的文件"。
- 工程上把它产品化的是 `bazel-diff`：对两个 git 版本各算一遍全图哈希，再取差集，得到"精确受影响目标集"，然后 `--target_pattern_file` 喂给 `bazel test`<https://github.com/Tinder/bazel-diff>。它不看文件路径，看的是目标内容哈希，因此能正确处理"改了下游依赖"。

**Jest / Vitest（JS 生态最普及的一档）**【一手·官方】：

- Jest：`--onlyChanged`（基于 git/hg 的改动 + **静态依赖图**，官方明说"requires a static dependency graph (ie. no dynamic requires)"）、`--findRelatedTests <files>`（给定源文件跑覆盖它们的测试，官方推荐用于 pre-commit hook）、`--changedSince <branch>`、`--listTests`<https://jestjs.io/docs/cli>。
- Vitest 4.1.11（本仓现装版本）：`vitest related <files>`（只认**静态 import**，动态 `import(filepath)` 不认）、`--changed [since]`、`--shard`；并有实验项 `experimental.recordDependencies`，用"运行时实际加载的模块"替代静态图来给 `--changed`/`--related` 用，**没有记录的测试文件一律跑**（保守兜底）<https://vitest.dev/guide/cli.html>。

**学术工具（Java 侧）**：

- **STARTS**（静态、类级 RTS，Maven 插件）：`mvn starts:select` 给出受影响测试、`mvn starts:starts` 选完就跑；官方前置条件写明 **"We have tested on Java 8 through Java 15"**、Maven 3.2.5+、Surefire 2.14+<https://github.com/TestingResearchIllinois/starts>。
- **Ekstazi**（动态、文件级 RTS，javaagent 记录运行时依赖）：官方支持矩阵里 JUnit 只列 **3.8.2 / 4.10 / 4.13.2**，Java 21 需要额外的 `JAVA_TOOL_OPTIONS` 开关<https://github.com/gliga/ekstazi>。
- 可靠性不是免费的：RTSCHECK 对 Clover、Ekstazi、STARTS 三个工具做系统校验，**共发现 27 个 bug**【一手·论文】<https://www.cs.cornell.edu/~legunsen/pubs/ZhuETAL19RTSCheck.pdf>。

## 2 主流形态：选择集 + 定期全量，而不是"只跑选择集"

### 2.1 四家的分层惯例

| 组织/产品 | 提交流程上的选择 | 兜底全量 | 出处 |
|---|---|---|---|
| Google TAP | presubmit 只跑"快而稳"的、通常只限本项目；TAP 还会把部分 presubmit 测试挪到 postsubmit | postsubmit 综合周期跑"自上次以来所有 affected 测试" | SE@Google ch23；TRANSPRED 论文 |
| Meta PTS | 每个变更只跑概率最高的子集（约 1/3） | 未公开表述为"定期全量"，但对 flake 做重试清洗、并对模型设 95% 预测准确 / 99.9% 捕获的验收线 | Meta 工程博客 |
| Develocity PTS | PR/本地跑预测子集 | 历史不足时跑全部 impacted；覆盖率统计只在关 PTS 的构建里做 | Develocity 文档 |
| Azure DevOps TIA | 流水线按提交选 impacted | 官方提供"按周期跑全量"选项，并标注 recommended；遇到无法理解的改动直接回退全量 | Microsoft Learn |

一句话概括业界共识：**选择集负责"快"，全量负责"不漏"；两者是配套关系，不是替代关系。**

### 2.2 漏测的五个来源与对应的业界对冲

| 漏测来源 | 具体形态 | 业界对冲（有出处） |
|---|---|---|
| 依赖图不全 | 反射、动态代理、`import(filepath)`、Spring 容器装配、配置文件、资源文件 | 微软"未知文件类型回退全量"；Vitest `recordDependencies` 让"无记录的测试一律跑"；Nx 允许显式声明 `implicitDependencies` |
| 选择器无法判断"没改到测试但改到了共享契约" | 改帧类型集、改公共 DTO、改配置默认值 | Develocity"永远选 recent/changed/failed/flaky"；微软"把先前失败与新增测试纳入" |
| 新测试未被识别 | 新增测试文件在旧映射里不存在 | 微软显式把"newly added tests"纳入；Develocity 同 |
| flake 被误当成"无需跑"或反过来污染模型 | 偶发红被记为真红/真绿 | Meta 训练前激进重试；Google 有全公司级 flake 分类、并把 flaky 测试临时移出 presubmit；Develocity 把 flaky 测试钉进选择集 |
| 选择器本身有 bug | 工具算错依赖、漏算边 | RTSCHECK 在三个 Java RTS 工具里查出 27 个 bug；微软官方给了 T1/T2 对照验证法 |

### 2.3 给本仓的三条判据（从上面提炼）

1. **选择器必须有"回退全量"的机械条件**，而不是靠人记得：改配置/迁移/资源/公共契约/依赖清单、以及"选择集为空或异常"时，一律全量。
2. **固定冒烟集必须常跑**：跨切面的契约测试（本仓是 `ai/conformance/` 那 9 个类）和上下文装配测试，不参与"被选中"的博弈。
3. **选择器要被验收，而不是被相信**：nightly 或合流前用"选择集先跑、全量后跑"的对照跑，记录"全量红而选择集漏掉"的次数，作为选择器可信度的唯一指标。

## 3 仓内勘察（事实与锚点）

### 3.1 后端：单模块、无任何原生选择性测试能力

- 构建面：`backend/pom.xml` 共 165 行，Spring Boot 3.5.14 / Java 21；`<build>` 段只有 resources 拷贝与 spring-boot 插件（`backend/pom.xml:123-164`），**没有任何 surefire 配置**——即用父 POM 默认的"单 JVM、串行、reuseForks"，这是全量跑起来慢的直接原因之一。
- 规模：主代码 252 个 `.java`；测试 256 个类、`@Test` 标注 1666 处，门禁口径 **1674 例**（参数化展开后；`docs/任务看板.md` 2026-10-23 行）【留痕】。
- 分布高度集中：`ai/` 包 **217 个测试类 / 约 1447 例 = 约 86%**；其余 `job/` 18 类、`task/` 5 类、`common/` 5 类、`definition/` 4 类、`data/` 4 类、`config/` 3 类【粗算】。
- 耗时：最近一次可查的全量留痕是 **1419 例 / 216 类 / 02:20 min**（`docs/evidence/fix-s6-locale-gate-zh.log:10312,10317`）；按用例数外推当前 1674 例约 2:40–3:00【推算】。
- 耗时结构（关键）：该次留痕可见的逐类耗时累计 **136.2 s**（与 Maven 汇总 2:20 一致），其中 **30 个 `@SpringBootTest` 类占 54.4 s = 40%**；单类最慢的是 `StreamWatchdogSegmentBudgetTest` 19.6 s、`ConfirmGateFrontendTimeoutTextTest` 10.0 s、`AiConfigSeederTest` 10.0 s【留痕，按 `Time elapsed` 汇总】。全仓共 **35 个 `@SpringBootTest` 类 / 236 例**。
- 变更到测试的可达性【粗算，静态扫描测试源码中是否出现主类简单名】：252 个主类里，**中位数 2 个测试类**引用它，均值 7.5，p90 = 20，**最大 123（`AiProperties`）**；`CancellationRegistry`/`RunRegistry` 69、`PendingToolCall`/`SseChatEmitter` 64、`RunStore` 59、`ConfirmGate` 54；**36 个主类没有任何测试引用**。
- 结论：后端"按变更选测试"在原理上能省大钱（中位只跑 2 个类），但**有 40% 的时长被 Spring 上下文测试占住**，这部分只能靠"固定冒烟集"保底；同时**按类名映射不可行**——`*Test` 与主类同名者只有 62/256（24%），测试是按行为命名的（如 `AiChatTargetResolutionTest`），必须做"测试源码引用扫描"而不是文件名对照。

### 3.2 前端：工具原生支持，但收益分布极不均匀

- 工具面：`frontend/package.json:42` 为 `vitest 4.1.11`，脚本只有 `test: "vitest run"` 与 `test:watch`（`:11-12`）；配置 `frontend/vitest.config.ts` 仅 13 行（jsdom + `tests/**/*.spec.ts` + `setup.ts`）。CLI 实测 `related [...]` 与 `--changed [since]` 均存在，无需升级或加依赖。
- 规模：110 个 spec、1357 例；`src/` 79 个 `.ts/.vue`。
- 全量耗时【实测，本机本次】：**110 文件 / 1357 例 / 46.33 s**（`Duration 46.33s`，transform 17.69s / setup 70.69s / import 211.03s，后三项为并行累计）。
- `related` 的实测收益（同一工作树）：

| 改动对象 | 选中 spec 文件 | 用例 | 耗时 | 相对全量 |
|---|---|---|---|---|
| 叶子工具模块 `src/utils/ai-suggestions.ts` | 20 / 110 | 326 | 9.70 s | 省约 79% |
| 中心 store `src/stores/ai.ts` | 81 / 110 | 999 | 39.43 s | 省约 15% |
| 公共类型 `src/types/definition.ts` | 92 / 110 | 1112 | 47.76 s | 几乎无收益 |

（`definition.ts` 那一跑含 2 例红，属工作树在途改动，与本件无关；计时仍有效。）

- 静态图粗算（spec → `@/…` 导入 → 传递闭包）：**中位数 76/110 个 spec 会命中同一个源文件**（均值 57.8，p90 = 84，分布左偏：54 个源文件被 >50 个 spec 命中、9 个为 0）；命中最多的源文件是 `src/locales/index.ts`（98）、`src/utils/excel.ts`/`src/utils/spreadjs.ts`（87）、`src/api/http.ts`（86）；命中最少的是 `src/stores/locale.ts`（4）与各 `AiPanel` 组件（20–21）【粗算】。
- 结论：**`vitest related` 能接，但只是"便宜可选项"，不是"省时主力"**——本仓 spec 的粒度是"挂载整块面板 + 打桩 transport"，共享基建（i18n、http、excel 包装）被几乎所有 spec 引入，改到这些就等于全量。真要提升，得先拆"共享模块的测试隔离"（把 `@/api/http`、`@/locales` 做成每 spec 独立 stub），那是测试架构改造，不是选择器问题。

### 3.3 CI：五个 job 全量触发，没有任何变更集判断

`.github/workflows/ci.yml` 现状（372 行）：

| job | 名称 | 触发即跑的内容 | 超时 | 依赖 |
|---|---|---|---|---|
| `backend` | 后端编译与单测 | `mvn -B test` **全量**（`:50-51`） | 20 min | — |
| `frontend` | 前端类型检查与构建 | `yarn typecheck` + `yarn test`（全量）+ `yarn build`（`:75-84`） | 20 min | — |
| `e2e` | E2E 全流程（35 用例） | 打 jar + 桩 + Redis + 真跑 E2E（`:115-262`） | 25 min | `needs: backend` |
| `docs` | 文档一致性门禁 | `check-docs.mjs` + `check-i18n-residue.mjs`（`:274-293`） | 10 min | — |
| `scan-history` | 全历史脱敏扫描 | 扫全部历史 blob（报告制，`:315-372`） | 10 min | — |

触发面为 `push: [main]` + `pull_request: [main]`（`:17-21`），**没有 `paths` 过滤、没有 job 级 `if`、没有 `concurrency` 取消**。也就是说：改一行 `docs/` 里的文字，后端全量单测、前端全量单测、E2E 三件都会完整跑一遍。

注意两个"看起来无关其实是耦合"的点，做 path gating 时必须算进后端/前端：`docs/kb-samples/**` 在构建期被原样拷进 `classes/kb-samples` 作为运行时首启播种源（`backend/pom.xml:129-150`）；前端 locale 文件被 `check-i18n-residue.mjs` 扫描，属于 `docs` job 的输入。

### 3.4 本地门禁：纪律而不是脚本，痛点集中在这里

- `scripts/githooks/pre-commit` 只做脱敏扫描（暂存区三条规则，`:40-76`），**不跑测试**；"提交前全量复跑"是提交官的作业纪律，不是仓内脚本。
- 提交官每次提交实际执行的量（按 `docs/任务看板.md` 2026-10-23 的 42be816 行留痕）：后端全量 **两遍**（默认 locale + `-Duser.language=en -Duser.country=US`）、前端全量、`vue-tsc --noEmit`、`vite build`、`check-docs`，外加针对本批的变异红测。
- 单次耗时推算：后端两遍约 5:30（按 2:45/遍）、前端 46 s、build 31.87–34.22 s（留痕）、typecheck 数十秒、check-docs 秒级，合计 **约 7–8 分钟/笔**，且大部分时间是"与本批改动无关的测试"【推算】。这就是用户感知到的痛点，且它发生在**每笔提交**上，比 CI 更频繁。

### 3.5 现成方案在本仓的适用性判定

| 方案 | 判定 | 依据 |
|---|---|---|
| Nx `affected` | **不适用** | 本仓不是 monorepo（单 Maven 模块 + 单前端应用），没有"项目图"可算；引入 Nx 等于为两个应用建一层无关的工作区抽象 |
| Bazel / bazel-diff | **不适用** | 需要 Bazel 化构建，改造面远超收益；本仓 1674 例的量级用不上目标哈希比对 |
| Azure DevOps TIA | **不可用** | 仅 VSTest + .NET managed + 单机，且不支持 .NET Core；本仓是 Java 21 + JUnit 5 |
| STARTS | **不适用（硬阻断）** | 官方只测到 Java 15，本仓 Java 21；且是类级静态选择，对本仓"行为命名测试"帮助有限 |
| Ekstazi | **不适用（硬阻断）** | 官方支持矩阵的 JUnit 只有 3.8.2/4.10/4.13.2；本仓 256 个测试类全部 `org.junit.jupiter` |
| Develocity PTS | **不适用（成本/数据）** | 商业产品 + 需要 Build Scan 长期数据；本仓提交频率与样本量撑不起模型，冷启动期还得跑全量 |
| GitHub `paths` 工作流过滤 / `dorny/paths-filter` | **适用** | 纯 workflow 改动；`paths` 只能做 workflow 级，job 级要用 `paths-filter` 或自算 `git diff`（其 README 明说内置 path 过滤"不作用到单个 job/step"）<https://github.com/dorny/paths-filter>；另注意否定规则的 OR 语义陷阱——"`!dir`" 会被"目录之外的任何文件"命中，使过滤器几乎恒真【二手】<https://blog.danielepetrollo.com/en/dorny-paths-filter-negation-always-true> |
| Vitest `related` / `--changed` | **适用（原生）** | 版本支持已实测；收益见 §3.2 |
| 自建"变更类 → 测试类"脚本 | **适用（推荐）** | 只需 Node + `git diff` + 测试源码引用扫描；本仓 252 主类规模下耗时 < 1 s |

## 4 落地建议（分档、改动面、风险、收益）

### 4.0 推荐路线

```
PR / 本地提交            合流前 / main / nightly
─────────────────       ────────────────────────
A 档 变更集判 job  ──┐
B 档 相关集+冒烟集   ├──►  全量（后端双 locale + 前端 + E2E）
C 档 vitest related  │
D 档 后端选测脚本   ──┘
```

原则：**贵的、可跳的按变更集跳；便宜的、全局的永远跑；保底的定期跑全量。**

### 4.1 档 A（建议先做）：CI 按变更集跳过无关的贵 job

- 改动面：`.github/workflows/ci.yml` 新增一个 `changes` job（`git diff --name-only origin/${{ github.base_ref }}...HEAD` 或 `dorny/paths-filter`），给 `backend` / `frontend` / `e2e` 三个 job 加 `if:`；`docs` 与 `scan-history` **保持无条件跑**（秒级到十秒级，且 `docs` 承担全仓命名纪律与盘符路径扫描，任何新增文件都与它相关）。
- 必须写进 gating 规则的耦合项：`docs/kb-samples/**` → 后端；`frontend/src/locales/**` → 前端（同时仍触发 docs）；`backend/pom.xml`、`frontend/package.json`、`frontend/yarn.lock`、`vite.config.ts`、`vitest.config.ts`、`tsconfig*.json` → 对应侧；`.github/workflows/**`、`scripts/**` → 全部。
- 收益：纯文档 PR 从"后端全量 + 前端全量 + E2E"降为"docs + scan-history"，省掉后端全量、前端全量、E2E 三段机器时间与排队时间（仓内未归档 Actions 运行时长，具体分钟数以历史 run 为准，不在本件估算）。
- 风险与对冲：①**required checks 语义**——GitHub 的必需检查在 job 被跳过时可能一直挂起或报 skipped，需按仓库分支保护配置确认；②**跨子树耦合漏配**——首次上线建议先"只加 `changes` job 并把结果打进 job summary"观察一周，比对"它说该跑"与"实际红了"是否一致，再真正加 `if`；③路径大小写/中文路径——`git diff --name-only` 输出按仓库设置转义，脚本里要加 `-c core.quotepath=false`；④**`needs` 与 `if` 的交互**——`e2e` 现在写着 `needs: backend`（`.github/workflows/ci.yml:119`），一旦 `backend` 被跳过，`e2e` 会被**连带跳过**（除非给 `e2e` 加 `if: always() && ...` 或把它的 `needs` 换成 `changes`），这是本项目特有的坑，改 gating 时必须一起处理。

### 4.2 档 B：本地门禁分两级（需用户裁决，因为这是纪律变更）

- **提交级（每笔）**：后端"变更相关集 + 固定冒烟集"（默认 locale）、前端 `related`（变更文件）+ typecheck、`check-docs`、i18n 残留；**不跑** build、E2E、en-US 全量。
- **合流级（入库/合并前）**：现行为不变——后端全量双 locale、前端全量、typecheck + build、check-docs、必要的 E2E。
- 固定冒烟集（建议，理由见 §3.1）：`ai/conformance/` 全部 9 个类（`FrameTypeSetFrozenTest`、`SseFrameSequenceConformanceTest`、`ToolFrameSequenceConformanceTest`、`ReattachLastSeqConformanceTest` 等，锁帧契约与重挂语义）；`ai/config/` 的 `*GuardTest` 与 `*DefaultsTest`（配置校验与默认值，改任何 yml 都可能打穿）；1–2 个 `@SpringBootTest`（`AiConfigUnavailableSpringTest` 一类）验证上下文装配。
- 收益：提交级从约 7–8 分钟降到约 1.5–2.5 分钟【推算：后端选测中位 2 类 + 冒烟集 + 前端 10–40 s + 类型检查】。
- 风险：①**纪律松动**——"提交前全量"是既有治理口径，改成分级等于承认"提交级可能漏"，必须由用户裁决并写进决策看板；②**冒烟集选择偏差**——冒烟集本身要随缺陷演进（每次"选择集漏了"的事故都要回填一个新类进去）；③**en-US 全量只在合流级跑**意味着 locale 相关回归最晚到合流才发现，需接受。

### 4.3 档 C：前端接 `vitest related`（零新依赖，低风险）

- 改动面：`frontend/package.json` 加一个脚本（如 `test:related`），或直接由门禁脚本调用；不需要改 `vitest.config.ts`。
- 用法：`git diff --name-only --diff-filter=ACMR <base>...HEAD -- 'frontend/src/**'` → 转成相对 `frontend/` 的路径 → `vitest related <files> --run`；变更里含 `tests/**` 时按文件名直跑对应 spec；**变更集为空或含 `src/api/http.ts`、`src/locales/**`、`src/types/**` 这类高扇出模块时，直接退化为全量**（实测这三类命中 86–98/110 个 spec）。
- 风险：①`related` 只认静态 import，`vi.mock` 与动态 `import()` 造成的边不参与（官方明示），本仓 71 个 spec 用了 `vi.mock`，需接受"mock 掉的真依赖改动不会被选中"；②收益不均（§3.2），不要把它当主要节省手段；③若要更准，可开 `experimental.recordDependencies`（用运行时记录替代静态图，无记录的测试一律跑），但它是实验项，且会给每次运行加缓存写入成本。

### 4.4 档 D：后端自建"变更类 → 测试类"选择脚本（推荐，但排 A/B 之后）

设计要点（不引入新依赖，Node 内置模块即可）：

1. **输入**：`git diff --name-only --diff-filter=ACMR <base>...HEAD`。
2. **全量触发器**（任一命中即 `--all`）：`backend/pom.xml`、`backend/maven-settings.xml`、`backend/src/main/resources/**`（含 `application*.yml`、Flyway 迁移）、`docs/kb-samples/**`、`backend/src/test/resources/**`、以及变更集中出现"引用它的测试类 > 50"的主类（按 §3.1 粗算，当前是 `AiProperties`/`CancellationRegistry`/`RunRegistry`/`PendingToolCall`/`SseChatEmitter`/`RunStore`/`ConfirmGate` 这一档）。
3. **映射算法**：对每个改动的主类，扫 `backend/src/test/java/**/*Test.java` 源码里是否出现该主类的简单名（词边界匹配），取并集；再并入固定冒烟集。**不要用 `FooTest` 与 `Foo.java` 的文件名对照**——本仓同名率只有 24%。
4. **输出**：`mvn -o test -Dtest=A,B,C` 的类列表；加 `-Dsurefire.failIfNoSpecifiedTests=false` 防"选空了直接红"。
5. **逃生口与可观测**：`--all` 参数；每次在摘要里打印"选中 N/256 类、命中原因（哪条规则）、是否触发全量"，并落一份 JSON 到 `backend/target/`（已被 `.gitignore` 排除）。
6. **验收**：照抄微软的 T1/T2 对照法——nightly 先跑选择集、再跑全量，记录"全量红而选择集未选中"的类，作为唯一可信度指标；连续两周为 0 再考虑把它提到提交级默认。

风险：①**静态引用扫描会漏反射/Spring 装配**（本仓 35 个 `@SpringBootTest` 尤其危险），必须靠冒烟集与 nightly 对照兜底；②**扫描器自身是新代码**（RTSCHECK 的 27 个 bug 是前车之鉴），因此它只能"减少跑的量"，不能"决定是否允许合流"；③维护成本——新测试若命名不含被改类名，会被漏选，需在 PR 模板里写一句"新测试请显式提及被测类"。

### 4.5 明确不做（并给出理由）

| 不做 | 理由 |
|---|---|
| ML/PTS | 需要长期"变更 × 结果"数据与稳定回流；本仓提交频率低、样本少，冷启动期只能跑全量，收益排不到前面；且引入训练/推理设施与数据治理成本，与"单仓小团队"不匹配 |
| STARTS / Ekstazi | 版本与框架硬阻断（Java 21 / JUnit 5），且 RTSCHECK 证明这类工具有真实 bug 面 |
| 为 affected 分析改造成多模块 Maven 或 Bazel | 改造面远大于收益；1674 例的规模用不上目标级图计算 |
| 把 E2E 也做成"选择集" | E2E 是跨进程链路，用例粒度粗（35 条），选择集化的收益小、漏测面大；只需按 §4.1 在"整块无关"时跳过 |

### 4.6 收益预估（汇总）

| 场景 | 现状 | 档 A 后 | 档 A+B+C+D 后 |
|---|---|---|---|
| 纯文档 PR 的 CI | 后端全量 + 前端全量 + E2E 全跑 | 只跑 docs + scan-history | 同左 |
| 单模块小改的 CI | 同上 | 只跑对应侧全量 + E2E | 对应侧选测 + E2E（E2E 仍全跑） |
| 本地每笔提交 | 约 7–8 分钟（含后端双跑） | 不变 | 约 1.5–2.5 分钟 |
| 合流前 | 全量 | 全量 | 全量（不变，这是保底层） |
| 漏测面 | 无（全量） | 无（只跳"整块无关"） | 有，靠冒烟集 + nightly 全量 + T1/T2 对照兜底 |

数字口径：【实测】前端全量与 `related` 三例；【留痕】后端 1419 例 02:20 与 build 31.87–34.22 s；其余为【推算】，落地前应以一次真实跑替换。

## 5 未决问题（需用户裁决，本件不构成施工承诺）

1. **提交级门禁是否可以不是全量**——这是纪律变更，涉及"提交前全量复跑"这条既有治理口径；若不允许，则 B/D 两档只能用于本地开发自测，提交官仍走全量。
2. **CI 是否接受 nightly 全量**——分层方案的另一半；仓内目前没有 nightly workflow，只有 `push(main)` 与 `pull_request(main)`。
3. **required checks 如何配置**——job 被跳过时是否阻断合并，取决于仓库分支保护设置，本件无法从代码侧判断。
4. **是否愿意为提升选择精度改造前端测试隔离**（把 `@/api/http`、`@/locales` 做成每 spec 独立 stub）——不做的话，前端 `related` 的收益上限就是"叶子组件省 79%、中心模块省 15%"。
