## 点 1｜`ConfirmGateDeadlockResumeTest.doesNotTriggerWhenInProcessGateWoken:130` 间歇红

### 根因（两个缺陷叠加）
1. **测试屏障只等到"闸门登记"，没等到"等待方真的在等"**：`await` 的第一条语句就是 `latches.put(key, latch)`（`backend/src/main/java/com/example/configmgr/ai/gate/ConfirmGate.java:205-206`），而测试的屏障只轮询 `gate.hasActiveLatch`（`backend/src/test/java/com/example/configmgr/ai/gate/ConfirmGateDeadlockResumeTest.java:287-292`，10ms×≤200 次）。`hasActiveLatch` 在该行就变真，此时等待线程 **还没** 做首次 `store.pending` 读、也**还没**阻塞进 `latch.await`（`:229-240`）。
2. **mock 每次返回同一个可变对象**：`:118-119` `when(store.pending(RUN_ID, TOOL_CALL_ID)).thenReturn(entry)` —— 提交线程与等待线程拿到 **同一个** `PendingToolCall` 实例。而提交侧的状态改写发生在互斥锁 **之外**：`ConfirmGate.java:415` 读、`:419-431` 就地 `setStatus(APPROVED)`，直到 `:435-439` 才 `synchronized (submitLock) { putPending; confirmDecision; woke = signal(...) }`。等待方退出循环的判据是 `fresh.resolved()`（`:232`，`!PENDING.equals(status)`，`run/PendingToolCall.java:107-109`）——**不需要被唤醒就能看到决策**。

### 间歇性机制（同一把锁的时序裂缝）
失败要求等待方在 `signal()` 之前注销自己的闸门，而注销发生在 `finally`（`ConfirmGate.java:258-266`）——**不在 `submitLock` 内**。故只需提交线程在 `:422` 之后、`:438` 之前被抢占（该窗口含两次共享 mock 调用 + `lock` 获取；CI 慢机上还有首次类加载/GC/监视器竞争放大），等待方即可跑完"读→`resolved()==true`→返回→`latches.remove`"这一微秒级路径；随后 `signal` 在 `:635` 取到 null → `woke=false` → `:130` 红。**长停顿变体**（同族、门槛更低）：提交线程停顿 >2000ms，等待方 `latch.await(min(remain,2000))`（`:240`）先超时，下一轮读到的已是 APPROVED → 同样先注销。
生产侧同类窗口存在但实际不可达：真实 `pending()` 走 Redis 且写库 `putPending` 发生在锁内（`:436`），读不到"已改但未唤醒"的状态；**mock 的对象同一性是把这个窗口从"天文级罕见"变成"每次运行两个线程都在同一段代码里"**。项目自己已记载该替身性质：`backend/src/test/java/com/example/configmgr/ai/conformance/InMemoryRunStore.java:34-38`（"真实 `pending()` 每次反序列化出新对象，本替身返回同一个引用……隔离性断言不在本替身能力范围内"）。
测试件确自 2026-10-09 未改（`git log` 仅 `cb52622`），与 CI 观测一致。

### 修复候选
| 候选 | 改动面 | 风险 | 评价 |
|---|---|---|---|
| (a) `store.pending` 每次返回新副本（`thenAnswer(inv -> copyOf(entry))`） | 该 spec 1 个 helper + 3-4 处 stub | 极低（不动断言、不动生产码） | **首推**：等待方无法绕开 `signal` 退出 ⇒ 确定性 |
| (b) 屏障升级到"等待方已做首次 pending 读"（在 stub 里计数并 await） | 该 spec 3-5 行 | 低 | 单独用仍留 2s-stall 残窗，宜与 (a) 合用 |
| (c) 生产侧：把 `:419-431` 移入 `synchronized (submitLock)`（`:435`），使"改状态+唤醒"对外原子 | `ConfirmGate` 三处入口 | 中（改生产码需复核；临界区只多几行纯内存写） | 结构最干净，但为单测抖动动生产码，值不值由指挥官裁 |
| (d) 换用 `InMemoryRunStore` | 换替身 | — | **无效**：该替身同样返回同一引用（javadoc:34-38） |

**倾向（仅建议）**：做 (a)，必要时叠 (b)；不建议为此单独改生产码 (c)，不建议 (d)。

## 点 2｜`restore-reconcile.spec.ts` 负例① 高负载撞 5s

### 5s 是什么
- **Vitest 默认 `testTimeout = 5000ms`**（`frontend/node_modules/vitest/dist/chunks/coverage.DM_a_rWm.js:538`：`resolved.testTimeout ??= ... : 5e3`），而 `frontend/vitest.config.ts` 只设了 `environment/include/setupFiles`，**未覆盖 `testTimeout`**；该 spec 内无任何 5000 字面量。⇒ 5s 只能是"整个 `it()` 被默认测试上限掐掉"。
- **不是** `vi.waitFor` 超时：其默认 `{ interval: 50, timeout: 1000 }`（`node_modules/vitest/dist/chunks/test.DNmyFkvJ.js:3361`、`:3409`），若它超时会以 ~1s 红、签名是 `Timed out in waitFor after 1000ms`。**不是**镜像防抖：`frontend/src/stores/ai.ts:537` 的 300ms `setTimeout` 从不被 await。

### 为什么会撞
嫌疑点 = `frontend/tests/restore-reconcile.spec.ts:92` 的 `await vi.waitFor(() => expect(api.runsCurrent).toHaveBeenCalledWith('sess-a'))`（该用例 `:83-104`）。负例① 是文件**首个** `it()`，临界路径全靠真实定时器推进：① `freshStore()`（`:55-60`）在计时区间内做 `vi.resetModules()` + 动态 `import('@/stores/ai')`，把 2091 行的 store 及依赖图**整体重新实例化**（测试内唯一重活）；② `:92` 以 50ms 间隔轮询，是唯一屏障；③ store 的 `startMirror()`（`ai.ts:529-537`）在同一事件循环上挂 300ms 防抖定时器。CI 上 Vitest 4 默认 `forks` 池按 CPU 并发多 spec（ubuntu-latest 2 vCPU），定时器延迟/GC 停顿/模块重实例化被放大；而常态整文件仅 441–739ms（`仓外/chat-timeline-pkg/evidence-p13/phase0-gates.txt:13`、`evidence-p15/fe-gates-p15.txt:10`、`evidence-p16/fe-gates-p16.txt:8`、`evidence-b2/flip-green-full-suite.txt:11`），余量约 10-20 倍，进程级饥饿即可吃掉。
在仓留痕：`docs/evidence/补档-R149-issue7-收口修报告.md:38`（"首跑 restore-reconcile 负例①（**真实计时敏感用例**）一次 flaky 失败，单跑与全量复跑均绿"）；口径来源 `仓外/_cu-r149/payload-handoff6.txt:23`。**我未找到带 `Test timed out in 5000ms` 原文的日志**（仓内与 scratch 均无）⇒ "5s=testTimeout" 属"与唯一可达上界一致"的推断；若实际签名是 `Timed out in waitFor after 1000ms`，根因收窄到 `:92` 自身，修法同 (a)。

### 修复候选
| 候选 | 改动面 | 风险 | 评价 |
|---|---|---|---|
| (a) 换确定性屏障：`runsCurrent.mockImplementation((sid)=>{ called.resolve(sid); return gate.promise })` + `await called.promise`，删掉 `vi.waitFor` | 该 spec 2 行 + 1 个 deferred | 极低（断言、生产码不动） | **首推**：临界路径只剩微任务，定时器再慢也不撞 |

## 点 3｜`vite build` esbuild Temp 占用连败

### 命令链与性质
- `frontend/package.json`：`"build": "vue-tsc --noEmit && node scripts/build.mjs"`；`frontend/scripts/build.mjs` **在 `import('vite')` 之前**把 `TMP/TEMP/TMPDIR` 指到 `frontend/.tmp-esbuild`（`.gitignore:19` 已排除），再 `await build()`。
- CI 前端 job（`.github/workflows/ci.yml` `frontend:`，步骤"生产构建（vue-tsc + vite build）"→ `yarn build`）**`runs-on: ubuntu-latest`** ⇒ **该抖动是本机 Windows 环境抖动，不是 CI 抖动**（Linux runner 无 Defender/索引器句柄抢占），不可能把 CI 弄红。
- 原始观测 `docs/evidence/补档-MANUALREFRESH-手动刷新批-复核报告-GLM-5.3.md:19`、`:55`：系统 Temp 下"esbuild 中间文件 remove … Access is denied"连败 5 次，"**换 TMP** 干净通过"；`docs/verification-results.md:25` 同口径。注意"换 TMP"意味着那些命令**没走 wrapper**（走了的话 TMP 早已被换）——即裸 `vite build` 才吃这个坑；`frontend/.tmp-esbuild` 现为空目录。
- 现场实据（只读）：`<USER>\AppData\Local\Temp\` 现存 3 个 `esbuild-<64hex>` **普通文件**（5,938,758B @10-12 15:00、2,329,692B @15:00、2,329,692B @12:40），正是 `frontend/node_modules/esbuild/lib/main.js:2095-2097` `randomFileName()` 写入 `os.tmpdir()` 的临时文件，其 unlink 失败被 `main.js:1834-1835`／`:1863-1867` 的 `catch {}` 静默吞掉 ⇒ 残留。**随机命名 ⇒ 陈旧残留不会撞新构建**（"清 esbuild-*"并非必需），失败只能是同一次运行内"刚写出的文件立即被外部句柄占用 → 删除/改名 Access is denied"。

### 加固候选
| 候选 | 改动面 | 风险 | 评价 |
|---|---|---|---|
| 1. 文档钉死 wrapper 为唯一入口（README:193 已是 `yarn build`；补"Windows 禁裸 `npx vite build`"） | 文档 | 0 | **性价比最高** |
| 2. `build.mjs` 设 `ESBUILD_BINARY_PATH` 指向 lockfile 内的 `@esbuild/win32-x64/esbuild.exe`（存在性校验） | build.mjs ~5 行 | 低，但版本需与 esbuild 同步（漂移会报 host/binary 版本不符），且跳过 esbuild 自身校验 | 想让裸 `vite build` 也稳时才值 |
| 3. `build.mjs` 构建前清 `esbuild-*` 残留 + 失败后清目录重试一次 | build.mjs ~8 行 | 低（`force` 吞 EPERM/EACCES）；有掩盖真错风险 | 把"连败 N 次"收敛为"1 次自愈" |
| 4. CI 步骤级 retry（新 action / 循环） | ci.yml | 打破仓内"actions 一律 v5"约定；且平台不对 | **明确否掉**（收益≈0） |
| 5. Defender/索引器排除仓库目录与 `%TEMP%` | 仓外、需管理员，落到开发手册"环境前置" | 0（对仓库） | 治本但需人工 |

**倾向（仅建议）**：1 + 3 足以关掉本机连败体验；2 可选；4 否掉。以上均为建议，裁决归指挥官。
