## 0. 结论速览（先给答案）

| # | 裁决 | 一句话依据 |
|---|---|---|
| **C1** | 用户的判断**方向对、边界要修正**：业界没有一家主流厂商主张「业务数据绝不进模型」；它们主张的是「**不进无必要的数据**」——按任务最小必要、经受控通道、可审计 | M365 Copilot 明确把 Graph 内容拼进 grounded prompt（[架构文档](https://learn.microsoft.com/en-us/copilot/microsoft-365/microsoft-365-copilot-architecture)）；Einstein Trust Layer 同样承认 prompt 带客户数据，用 masking + 零留存兜（[Salesforce](https://www.salesforce.com/artificial-intelligence/trusted-ai/)） |

| **C5** | 大量数据进上下文**同时是质量问题**，不只是成本问题 | Chroma「context rot」：18 个模型、长度一涨能力就退化；LongMemEval 全量 ~113k tokens vs 聚焦 ~300 tokens，全量显著更差（[Chroma](https://research.trychroma.com/context-rot)） |
| **C6** | 本仓现状**已经是「最小化」形态**：18 个工具全部只返回元数据/聚合，**没有任何一个工具返回业务数据行**；导出走服务端文件、导入文件内容不进模型 | 见 §3 逐条审计（`AiTools.java` 全文 + `ExportJobRunner` + `FileStorageService`） |

**一句话口径**：业务数据不是「绝对不能给 AI 看」，而是「**默认不看原文、只看经裁剪的摘要/元数据/聚合；要看原文必须逐次授权并承担出域责任；大量数据一律改为出域执行或产出文件**」。

## ① 业界结论与证据链

### 1.1 企业级产品到底把什么送进模型

| 产品 | 送进模型的 | 明确兜底的控制 | 来源 |
|---|---|---|---|
| **Microsoft 365 Copilot** | grounded prompt = 用户输入 + **Microsoft Graph 检索到的邮件/文档/聊天片段**（在租户内、按用户 ACL 裁剪） | ①仅在租户服务边界内 ②只给用户有权限的内容 ③**不用于训练基础模型** ④Purview/DLP/审计/保留策略 ⑤EU Data Boundary、数据驻留 ⑥XPIA 分类器挡提示注入 ⑦声明**退出** abuse monitoring 的人工审阅 | [架构](https://learn.microsoft.com/en-us/copilot/microsoft-365/microsoft-365-copilot-architecture)、[Data, Privacy, and Security](https://learn.microsoft.com/en-us/microsoft-365-copilot/microsoft-365-copilot-privacy) |
| **Salesforce Einstein Trust Layer** | 动态接地后的 CRM 记录/知识条目 | ①secure data retrieval（按运行用户的共享规则/FLS 取数）②data masking（PII/PCI → 占位符，返回时反解）③**zero data retention**（与模型商的合同禁止留存/训练）④毒性检测 ⑤审计轨迹 | [Salesforce Trusted AI](https://www.salesforce.com/artificial-intelligence/trusted-ai/) |
| **OpenAI API（企业）** | 请求体原样（含业务数据），但**不入训练** | 2023-03-01 起 API 数据不用于训练；abuse monitoring 日志默认留 30 天；可申请 **Modified Abuse Monitoring / Zero Data Retention**（ZDR 下 `store` 强制 false） | [Your data](https://platform.openai.com/docs/guides/your-data) |
| **Anthropic API（企业）** | 同上 | 输入/输出后端 **30 天内删除**；命中 Usage Policy 违规可留 2 年；另有 ZDR 合同形态 | [Privacy Center](https://privacy.anthropic.com/en/articles/7996866-how-long-do-you-store-my-organization-s-data) |
| **GitHub Copilot** | 编辑器上下文（内联补全：提示 + 周边约 150 字符参与公共码比对；Chat/Agent：工作区与索引内容） | **content exclusion**：被排除文件的**内容既不进补全、也不进 Chat/Agent、也不进 code review**（并如实承认语义信息可能经 IDE 间接泄漏） | [Content exclusion](https://docs.github.com/en/copilot/concepts/context/content-exclusion)、[Code suggestions](https://docs.github.com/en/copilot/concepts/completions/code-suggestions) |

**读法**：这五家的共同点不是「不给模型看数据」，而是四件事同时成立——
1. **数据面被裁剪**（ACL / 分页 / 片段 / 排除清单）；
2. **通道是受控的**（工具/检索/接地，不是把库表拼进 prompt）；
3. **责任可落地**（零留存、不训练、驻留、审计）；
4. **出事有边界**（不越权、不跨租户、可撤销）。

缺任一条，「把数据丢给 AI」就从不合规变成事故。

> 反证一个常见误解：「零留存」≠「数据不离开你的边界」。Einstein Trust Layer 的 ZDR 只约束模型商**不留存/不训练**，prompt 仍然要出域（[Salesforce](https://www.salesforce.com/artificial-intelligence/trusted-ai/)）。所以「合同挡住了」不能替代「少发一点」。

### 1.2 为什么「能不进就不进」成了主流工程方向

**（a）注意力被稀释 —— 质量理由**
Anthropic 把上下文定义为**有限注意力预算**：transformer 是 n² 两两关系，token 一多就摊薄；工程目标是「**找到最小的高信号 token 集**」，而不是「尽量塞满窗口」（[Effective context engineering for AI agents](https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents)）。
Chroma 的受控实验进一步把「长度」单独隔离出来：**18 个模型**在 NIAH/长记忆/复述任务上**随输入变长一致退化**，且「有干扰项比无干扰项差、语义相近的干扰项更差」；LongMemEval 里**全量 ~113k tokens 的输入 vs 只给相关片段的 ~300 tokens**，全量显著更差（[Context Rot](https://research.trychroma.com/context-rot)）。
⇒ 这不是「窗口够大就行」的问题：**塞进去的每一行都在扣分**。

**（b）成本/延迟 —— 经济理由**
Anthropic 的代码执行模式把工具定义 + 中间结果移出上下文：**150,000 → 2,000 tokens（-98.7%）**；同文给出的做法是「在执行环境里过滤，只把 5 行 log 回模型」（[code execution with MCP](https://www.anthropic.com/engineering/code-execution-with-mcp)）。
RAG vs 长上下文的系统级对比也一致：整段长上下文在吞吐/时延上远贵于检索式（1M-token 场景差数个数量级，[RAGO](https://arxiv.org/pdf/2503.14649v1)）。

**（c）数据通道就是指令通道 —— 安全理由（最硬）**
- **EchoLeak / CVE-2025-32711**：一封精心构造的邮件即可让 M365 Copilot **零点击**外泄数据；攻击链包含绕过 XPIA 分类器、用引用式 Markdown 绕过链接脱敏、滥用自动抓图与 Teams 代理（[arXiv 2509.10540](https://arxiv.org/abs/2509.10540)）。论文给出的缓解正是「prompt 分区、输入输出过滤、**基于来源的访问控制**、严格 CSP」。
- **ForcedLeak**：攻击者只花约 5 美元，通过 **Web-to-Lead 表单字段**注入指令，让 Agentforce 把 CRM 数据外泄（CVSS 9.4，[Noma](https://noma.security/blog/forcedleak-agent-risks-exposed-in-salesforce-agentforce)、[Varonis](https://www.varonis.com/blog/forcedleak)）。
- **教训**：只要「业务数据原文」进了上下文，它就同时成了「**不可信指令载体**」。最小化的收益不是省 token，而是**缩小注入面**。OWASP 把这条列为 LLM01（提示注入）与 LLM02（敏感信息泄露）两宗（[OWASP LLM02](https://genai.owasp.org/llmrisk/llm022025-sensitive-information-disclosure/)）。

**（d）合规 —— 责任理由**
- **GDPR**：把模型商当处理者，必须有 Art.28(3) 合同（含「仅按**书面指示**处理，包括向第三国传输」），跨境传输另受 Art.44 约束（[Art.28](https://gdpr-info.eu/art-28-gdpr/)）。
- **国内**：《生成式人工智能服务管理暂行办法》**第十一条**——对使用者输入信息与使用记录「不得收集非必要个人信息，不得非法留存可识别身份的输入信息与使用记录，**不得非法向他人提供**」；**第二条**明确「企业等研发、应用生成式AI技术，**未向境内公众提供**服务的，不适用本办法」；**第十七条**——具舆论属性/社会动员能力的须做**安全评估 + 算法备案**（[CAC 全文](https://www.cac.gov.cn/2023-07/13/c_1690898327029107.htm)）。
- **执法现实**：网信办通报的典型案例中已有「以 API 中转站方式调用多个大模型接口、未按规定开展安全评估」被责令改正并处罚（[案例通报](https://www.jsjc.gov.cn/yaowen/202609/t20260916_1358915.shtml)）。
⇒ 对本仓这类**内网配置管理平台**：暂行办法第二条大概率不直接适用（非面向公众），但**PIPL/数据安全法的处理者义务、以及「调第三方模型 = 数据出域」这一事实不会因此消失**。

### 1.3 所以「明确不行」到底行不行：三档口径

| 档 | 断言 | 业界是否成立 | 证据 |
|---|---|---|---|
| A | 「**把整库/整表/整份文件无差别塞进 prompt**」 | ✅ 明确不行（一致） | C2；context rot；OWASP；EchoLeak/ForcedLeak |
| B | 「**按任务需要、经工具通道、经裁剪的业务数据可以进上下文**」 | ✅ 这是主流做法，且是产品价值来源 | M365 Graph grounding；Einstein dynamic grounding；本仓 `get_row_count` 类工具 |
| C | 「**敏感/高体量数据优先不进上下文，改出域执行或产出文件**」 | ✅ 2025–2026 明确趋势 | Anthropic code execution（-98.7%）；OpenAI Code Interpreter；本仓「导出 xlsx 不给模型」 |

**给用户的原话修正**：不是「不应该把业务数据丢给 AI」，而是「**不应该把业务数据的原文整块丢给 AI**」。业界通常允许三样东西进上下文：**元数据、聚合值、经裁剪/脱敏的少量样本**；其余要么**工具化按需取**，要么**服务端算完只回结论**，要么**产出文件让人看**。

## ② 工程模式谱系表

| # | 模式 | 机制 | 代表产品 / 出处 | 适用面 | 反面代价 |
|---|---|---|---|---|---|
| P1 | **schema-only 披露** | 只给字段名/类型/必填/引用关系，不给行 | 本仓 `get_config_def`；M365 semantic index 只做定位 | 模型需要"知道有什么字段"才能写查询条件 | 看不到数据分布，需配合 P3 |
| P2 | **聚合/统计** | 只回 count / 进度 / 错误数 | 本仓 `get_row_count`、`check_job_status`；BI copilot 的「先 count 再决定」 | 判断规模、决定是否分页/加条件 | 无法回答"值长什么样" |
| P3 | **工具化取样 + 分页 + 上限告知** | 工具只回前 N 条并**明示截断** | 本仓 `list_tasks`（20 条 + 总条数）；GitHub 默认 30/上限 100；Anthropic「实现 `search_contacts` 而不是 `list_contacts`」（[writing tools](https://www.anthropic.com/engineering/writing-tools-for-agents)） | 需要少量样本做判断/举例 | 上限写错就变成"谎报全集" |
| P4 | **服务端执行 / 数据不出域** | 模型写代码/查询，在沙箱里跑，只回结论 | Anthropic code execution with MCP；OpenAI Code Interpreter（[your data](https://platform.openai.com/docs/guides/your-data) 中 Hosted containers 条目） | 全表扫描、join、去重、大文件 | 需沙箱与资源限额 |
| P5 | **渐进披露（progressive disclosure）** | 工具/资料按上下文**按需加载**，不是一次全给 | 本仓 `@ToolScope` + `ToolRegistry.forContext`；Anthropic filesystem 工具、`search_tools` 分级 detail | 工具多、页面多 | 多一跳延迟；披露集须冻结（本仓已做） |
| P6 | **检索式接地（RAG）** | 只把 top-k 片段拼进 prompt | M365 Graph grounding；Einstein dynamic grounding | 非结构化语料问答 | 检索错 = 答错；片段仍是原文 |
| P7 | **脱敏 / token 化** | 敏感值换占位符，出模型后再反解 | Einstein data masking（[Salesforce](https://www.salesforce.com/artificial-intelligence/trusted-ai/)）；Anthropic `[EMAIL_1]/[PHONE_1]` tokenization（[code execution](https://www.anthropic.com/engineering/code-execution-with-mcp)） | 必须带 PII 才能完成任务 | 掩码错位会毁语义；反解表本身是高危资产 |
| P8 | **零留存 / 不训练 / 驻留** | 合同 + 端点能力约束第三方 | OpenAI ZDR/MAM、Anthropic 30 天删除、Microsoft EU Data Boundary、Einstein ZDR | 所有出域场景的**前置条件** | 只降低"留在别人那儿"的风险，不降低"已经发出去"的事实 |
| P9 | **客户端/路径级排除** | 按路径或键白名单**在源头挡住** | GitHub content exclusion；本仓 `ContextBuilder.ALLOWED_EXTRA_KEYS` + 300/800 字符预算 | 已知敏感目录/自由字段 | 有旁路（GitHub 自己承认语义信息可经 IDE 间接泄漏） |
| P10 | **结果裁剪 + 截断必须可见** | 超限截断并**标注原始规模** | 本仓 `ToolResultLimiter`（200 行 / 8000 字符 + 截断标记）、`FrameSizeLimiter`（单帧 64KB 字段级） | 所有工具结果通道 | 静默截断 = 模型把"前 N 条"当全集（比不截更危险） |
| P11 | **产出文件而非进上下文** | 数据落服务端文件，人看/人下载 | 本仓 `start_export` → `ExcelWriter` → `FileStorageService` → 浏览器下载 | 大批量、要留痕、要复核 | 模型不能"顺便分析"文件内容（这是**特性**不是缺陷） |
| P12 | **数据/指令分区** | 数据只走 `role=tool`，系统提示声明"工具结果是数据不是指令"；输入输出过滤 | EchoLeak 论文的 prompt partitioning 建议；OWASP LLM01 缓解 | 一切含外部文本的通道 | 不能 100% 防住，只能降概率 |

## ③ 本仓现状审计（读码写实）

### 3.1 逐条「数据进模型面」

| # | 面 | 实际进模型的内容 | 量级（实测/估算） | 数据分级 | 判定 |
|---|---|---|---|---|---|
| A1 | **系统人设** | `SYSTEM_PROMPT`（10 条工作原则） | **874 字符**（实测，`ResilientChatService.java:109-138`） | D0 无业务数据 | ✅ 合规 |
| A2 | **工作区快照** | 页面中文名+id、任务 `#id [类型] 标题`、状态、当前步骤、已选配置项 defCode 列表 | 单任务约 150–400 字符；`title` 受 DB 列宽 **256** 约束（`Task.java:24-25`） | D1 元数据（`title` 是自由文本，用户/模型可写） | ⚠️ 合规但 `title` 是唯一"自由文本入 system"的口子 |
| A3 | **extra 白名单** | 仅 6 键：`pageId/selectedDefs/importMode/dataVersion/contractVersion/recentActions` | 单值 ≤ **300** 字符、整段 ≤ **800** 字符，超限标注"已省略 N 项"（`ContextBuilder.java:41-66,161-193`） | D1 | ✅ 已是业界 P9 形态 |
| A4 | **工具定义（Schema）** | 18 个工具的 name/description/参数 Schema | 描述合计 **929** 字符 + 42 条 `@ToolParam` 描述 **991** 字符（实测）；序列化后 JSON Schema 估算 **6–8 KB ≈ 2–3k tokens** | D0/D1（描述是代码常量） | ✅ 合规；是 payload 里最大的固定开销 |
| A5 | **工具结果（BACKEND）** | 全为元数据/聚合：定义清单、字段定义、任务清单（≤20 条 + 总数）、工作区状态、作业进度、**行数** | 单结果 30–1200 字符；上限 200 行 / 8000 字符（`ToolResultLimiter`） | D1（**零数据行**） | ✅ 本仓最关键的事实：**没有任何工具能取到数据行** |
| A6 | **工具结果（FRONTEND 回灌）** | `generative_form` 用户填的值（≤20 字段、白名单类型）+ 前端动作回执 | 数百字符；受 `GenerativeFormRules` 类型/选项复核 | D1/D2（用户主动填） | ✅ 合规，且来源是"用户当场授权" |
| A7 | **统一信封** | 每个工具结果被包成 `{ok,code,outcome,retryable,target,evidence,message}` JSON，`message` 先过裁剪再序列化 | 信封固定开销约 150 字符（`ToolResultEnvelope.java:34-114`） | D0 | ✅ 结构稳定，便于断言 |
| A8 | **记忆窗口** | 最近 **40 条**消息（含全部 `tool` 结果、`assistant(tool_calls)`）每轮整串重发 | 理论上限 = 40 × 8000 字符 ≈ **320k 字符**（中文按 ≈1 字符/token 估 ≈30 万 tokens，中英混合 ≈8–30 万）；实际常态远低（单轮 3–8 个工具 × 数百字符） | D1 | ⚠️ **本仓最大体量面**：靠"工具结果本来就小"侥幸安全，不是被闸门保护的 |
| A9 | **用户输入** | `message` 原文 | **无任何长度校验**（`AiController.java:179-181` 只判非空） | 不可控（用户可粘贴整表） | ❌ **未受控面**（见 3.3 缺口 1） |
| A10 | **导出数据** | **不进模型**：`ExportJobRunner` 逐 def 读已发布行 → `ExcelWriter` → `FileStorageService`（本地 `app.file.storage-path`）→ 浏览器下载/SpreadJS 编辑 | 文件在服务端磁盘，模型只见"作业 #id 已启动" | D2 全量业务数据 | ✅ 教科书式 P11（数据出域到文件，不进上下文） |
| A11 | **导入数据** | 上传文件落服务端；`PrecheckJobRunner` 服务端解析；`ValidationIssue` 只入库 | 模型侧**只有** `check_job_status` 的 `进度/错误数`；**没有任何工具能读 `validation_issues` 或文件行**（`grep ValidationIssue src/main/java/com/example/configmgr/ai/` 零命中） | D2/D3 | ✅ 合规；错误明细只给人看（`GET /api/jobs/{id}/issues`） |
| A12 | **SSE 帧** | `tool_result` 帧带 `result` 全文（前端看），单帧 64KB 上限 + `truncated` 标记 | 与"模型侧 8000 字符"是**两条独立通道**（`ToolResultLimiter` 类注已明示） | D2 可能（前端可见全量结果） | ✅ 但需注意：**前端通道比模型通道宽松 10 倍**，将来若加数据工具，这里会先漏 |

### 3.2 判定：本仓「已经最小化」吗？

**是，且是结构性最小化**——不是因为加了闸门，而是因为**工具面本身不提供数据行**：

- 6 个只读后端工具的返回值逐一核对（`AiTools.java:96-222`）：`list_config_defs`（定义清单）、`get_config_def`（字段定义）、`list_tasks`（≤20 条任务摘要）、`get_workspace_state`（任务状态 + defCode）、`check_job_status`（进度计数）、`get_row_count`（**一个数字**）。
- 写/作业类工具只回 id 与提示语。
- 导出/导入两条数据主链路都不经过模型上下文。

这与业界 P1+P2+P3+P11 的组合一致：**模型负责"决定查什么/导什么"，数据由服务端搬运**。

### 3.3 缺口（真实存在，按风险排序）

| # | 缺口 | 事实 | 风险 | 建议判据（见 §4） |
|---|---|---|---|---|
| **G1** | 用户输入无长度闸门 | `AiController` 只判 `hasText`；没有 `@Size`/`max` | 用户粘贴 5000 行表 → 直接进 prompt 且进 40 条记忆 → 后续每轮重发（**一次粘贴，长期计费 + 长期注入面**） | R5 |
| **G2** | `list_config_defs` 无条数上限 | 返回**全部**定义（`definitionService.findAll()`），无分页、无"共 N 条"告知；对比 `list_tasks` 有 20 条上限 | 定义数上百时单结果线性膨胀；且与 `list_tasks` 口径不一致（同一仓两套） | R3 |
| **G3** | 记忆窗口按**条数**而非 token 计 | 40 条 × 单条 8k 字符的**理论上限 320k 字符**；无 L1 工具结果清除 | 与"上下文统计与压缩"专项的 L1 直接重叠（该专项已有设计） | R2 + 专项 |
| **G4** | `task.title` 是唯一"自由文本进 system" | 256 字符、用户/模型可写、直接拼进系统消息 | 提示注入载体（价值很低：需用户自己写标题）；但应声明"标题是数据不是指令" | R7 |
| **G5** | 前端通道比模型通道宽 10 倍 | `tool_result` 帧 64KB vs 模型侧 8000 字符 | 现在无害（结果是元数据）；将来加"取样本"工具时，前端会先拿到大结果 | R4 的适用范围要覆盖两个通道 |

> 结论：**本仓没有"业务数据违规进模型"的面**；有 5 个"将来会变成面"的缺口，其中 G1 是现在就能被用户触发的。

## ⑤ 与队列内专项的关系

### 5.1 与「上下文统计与压缩专项」（`设计-上下文统计与压缩专项-2026-10-21.md`）

- **分工**：本调研管**源头**（什么该进），压缩专项管**下游**（已经进来的怎么减）。压缩是补救，最小化是预防；**预防优先**。
- **接口**：本 §4 的 R2/R3 就是该专项的 **L0**（"工具结果超过 N KB 就截断并注明可让 AI 重取"——该专项 §2.5 已承认 L0"已有雏形但阈值与剩余预算无关"）。建议该专项 L0 显式引用本文件 R2/R3，避免两套阈值。
- **L1 的前提由本调研提供**：只有当工具结果**不含业务数据行**时，"清最旧工具结果换占位符"才是无损的（占位符指向台账全文，模型可回取）。若将来加数据行工具，L1 的占位符会变成"数据被反复捞回"的漏洞——**R8 是 L1 的安全前提**。
- **冲突面**：R1（payload 预算）需要"窗口分母"，而该专项 §2.4 明确"分母当前不存在"。⇒ R1 在分母落地前只能以"估算 + 告警"形态存在，不得做硬闸（否则误杀）。

### 5.2 与「i18n + 工具可配置专项」（`设计-i18n与工具可配置专项-2026-10-21.md`）

- **新风险面**：工具定义外置（阶段 A classpath YAML / 阶段 B `ai_tool_def` 表）会把**工具描述从"代码常量"变成"可配置数据"**。描述是每轮都进模型的文本（A4：约 1.9k 字符），因此它同时成为：① token 面的调节旋钮 ② **提示注入的新载体**（谁能改描述，谁就能改模型行为）。
- **建议加进该专项的守卫**（本调研的建议，非其现有范围）：
  - 单工具描述 ≤ **500 字符**、全量 ≤ **4000 字符**（否则 Schema 固定开销失控）；
  - 描述文本**禁止含业务数据**（含数据即视为 D2 泄漏，评审拒绝）；
  - 每次发布沿用它已有的"不可变版本 + 标签指针"模型 → **描述变更必须可审计**（这正好覆盖提示注入的溯源需求）。
- **披露面协同**：该专项让"描述可配"，本调研的 `@ToolScope` 披露面（P5）让"工具可有可无"——两者叠加后必须保证**披露集在请求边界冻结**（本仓已做），否则配置热更新会造成"同一轮工具子集漂移"。

### 5.3 与「模型配置功能专项」

- R9（第三方留存）与该专项的 provider 表天然同处：建议 provider 记录增两个布尔字段 `zero-retention` / `no-train`，作为"能不能发 D2/D3"的**硬前置**（缺省 false = 只允许 D0/D1）。
